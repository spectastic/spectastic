What's coming up

A live list of unrouted items, the small things that don't need a spec, and what's deferred.

Status Active Owner Brian Corbin · brian@example.com Updated 12 Jun 2026 Read time

The small-batch entry point. Paste a list of items into /spectastic.triage and one <spec-triage> card lands here per item, with the layer= attribute set to one of the routing exits. /spectastic.implement drains the just-do queue one at a time. Use this for cross-cutting fixes, typos, small UI tweaks, and anything that doesn't fit cleanly inside a single spec's triage log.

1 · Card states

Unrouted
No layer= attribute yet. Just-captured items. Needs classification.
Just-do
layer="just-do". Small enough that a spec would not change the decision — one file, no public-contract change, revert-safe. Implement immediately; no proposal.
Defer
layer="defer". Back-burner. Carries defer-to= pointing at a sibling spec ID, TBD, or never.
Routed to a layer
layer="spec" | plan | implementation | cross-spec | principles | platform. The item became (or needs to become) a spec change-proposal or constitutional amendment.

Once a just-do card is implemented, it gets data-status="done" and stays in the inbox as history — strikethrough, faded, with a DONE pill.

Rename /spectastic.implement → /spectastic.build

Spec upstream

Debugging the verb taxonomy after one full cycle, root cause is the choice of implement — a domain-specific word that pulls weight only inside the spec-driven-development frame; fixed by renaming to build, which is closer to universal dev vocabulary; regeneration fails because every artifact and command file still hard-codes the old name.

Expected
The verb appears in user-facing copy and is recognisable without the spec-driven-development prior — /spectastic.build.
Actual
/spectastic.implement in commands/, .claude/commands/ symlinks, README.md, CLAUDE.md, the lifecycle table, the small-batch flow, the meta-spec example, and scripts/test_spectastic.py::EXPECTED_COMMANDS.
Diagnosis
The verb was chosen early for resonance with the spec → implementation chain. A full first-cycle run-through shows build reads as plainly and avoids the spec-driven-development reach. Single-rename change, but hits many files.
Fix
One /spectastic.propose against the lifecycle: rename commands/spectastic.implement.md → commands/spectastic.build.md, migrate every cross-reference, update EXPECTED_COMMANDS in scripts/test_spectastic.py, refresh the symlinks under .claude/commands/.
Deep dive — cascade required

Touches the 001-cli spec directly: FR-001 names the eight commands by file name, and the test suite hard-codes spectastic.implement.md in EXPECTED_COMMANDS. The rename proposal must carry one <spec-delta op="modified" target="FR-001"> for the FR list and a coordinated update to the test constant. The slash-command symlink set is regenerated by the same shell snippet documented in the gitignore commit; no manual fixup needed for the dev environment.

Tasks artifact still uses <div class="task"> instead of a semantic element

Spec upstream

Debugging the visual inconsistency between spec.html (semantic custom elements) and tasks.html (generic <div>/<span>), root cause is a missing entry in the component vocabulary; fixed by adding a <spec-task> element with id, parallel, and status attributes; regeneration fails because templates/tasks.html is still the source of truth for new task breakdowns.

Expected
Each task renders as <spec-task id="T-NNN" parallel status="done|open">…</spec-task>, matching the semantic pattern used for requirements, decisions, and triage cards.
Actual
Each task is a <div class="task"> with three <span> children (.id, .par, .path) and one inline <style> block in the template.
Diagnosis
When templates/tasks.html was authored, the component vocabulary did not yet include a task element. The styling was solved one-off with classes. The gap surfaces P-2 ("Semantic tags over class soup") — the principle exists; the application is missing.
Fix
One /spectastic.propose against the component vocabulary: add <spec-task> styling to assets/spec.css (move the inline block out of the template), update templates/tasks.html, refresh commands/spectastic.tasks.md's authoring instructions, and migrate specs/001-cli/tasks.html in the same change.
Deep dive — principles cascade

The fix realigns tasks.html with P-2 "Semantic tags over class soup". The principle itself does not need to change; the application gap is what surfaced. The component-vocabulary table in README.md grows by one row (<spec-task>). No cross-spec contract is touched — task IDs (T-NNN) keep their semantics; only the surrounding wrapper changes.

Implement command lacks drain / phase / parallel modes

Spec upstream

Debugging the 33-task drain that required /goal as a workaround, root cause is the "one task per invocation" discipline being too strict for the common case; fixed by adding optional drain modes to /spectastic.implement; regeneration fails because the current command file mandates serial execution and forbids silent chaining.

Expected
/spectastic.implement accepts either a single task ID (current default), or a flag to drain (--all), restrict to a phase (--phase=us1), or spawn parallel agents for [P]-marked tasks (--parallel).
Actual
Command implements exactly one task per invocation; draining requires either a manual loop in chat or a /goal session hook. The user had to do the latter for 001-cli's 33 tasks.
Diagnosis
The discipline section of commands/spectastic.implement.md reads: "One task per invocation. If the user wants to drain a phase, they invoke the command in a loop; you do not silently chain." This is the right default for risky or contested work and the wrong default for an MVP-first solo drain.
Fix
One /spectastic.propose against commands/spectastic.implement.md: keep one-per-invocation as the default; add --all, --phase=<id>, and --parallel as opt-in drain modes; document the parallel mode's Agent spawn strategy for [P] tasks.
Deep dive — none required

No cross-spec contract, no principles invariant, no hotfix needed. The change is local to the command's spec and behavioural prose. Task ID semantics, the failing-test-first discipline, and the no-silent-test-edits rule all remain unchanged.
