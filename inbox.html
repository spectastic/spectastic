A live list of unrouted items, the small things that don't need a spec, and what's deferred.

Status Active Owner Brian Corbin · @briancorbinxyz Updated 12 Jun 2026 Read time

The small-batch entry point. Paste a list of items into /spectastic.triage and one <spec-triage> card lands here per item, with the layer= attribute set to one of the routing exits. /spectastic.implement drains the just-do queue one at a time. Use this for cross-cutting fixes, typos, small UI tweaks, and anything that doesn't fit cleanly inside a single spec's triage log.

1 · Card states

Unrouted
No layer= attribute yet. Just-captured items. Needs classification.
Just-do
layer="just-do". Small enough that a spec would not change the decision — one file, no public-contract change, revert-safe. Implement immediately; no proposal.
Defer
layer="defer". Back-burner. Carries defer-to= pointing at a sibling spec ID, TBD, or never.
Routed to a layer
layer="spec" | design | implementation | cross-spec | principles | platform. The item became (or needs to become) a spec change-proposal or constitutional amendment.

Once a just-do card is implemented, it gets data-status="done" and stays in the inbox as history — strikethrough, faded, with a DONE pill.

A prototype is interactive by nature, and P-11 forbids exactly that

Defer TBD-prototype-embedding

The visual family can hold a render, which is a still. It cannot hold a prototype — the thing a designer actually produces and a reviewer actually wants to click — because P-11 makes executable content in an artifact an error, and a prototype is executable content by definition.

What's wanted
An embedded, clickable prototype inside a design artifact, so a reviewer can exercise a flow rather than read a description of one. Possibly an <iframe>, possibly something narrower.
Why it's blocked
P-11 is a principle, not a relaxable rule, and no-executable-content enforces it at error severity — flagging <script>, on*= handlers, javascript:/data: URIs and <iframe> specifically. The obvious mechanism is the one already named and blocked. Demonstrated live in 105/T-007: a real design export failed validate on its own runtime script.
Why it is not obviously wrong to want
The courses precedent exists — a course carries sanctioned inline gate JS and is exempted by its title, with TBD-course-csp already open for a hash or nonce policy. So the system already admits that some artifacts legitimately execute, and has an unfinished answer for how to permit it narrowly. A prototype would be the second such case, and a stronger one, since the content is somebody else's.
Why deferred
It is a principles-level question wearing a feature's clothes, and answering it under time pressure is how a security posture gets quietly widened. The visual family's first slice deliberately made a render evidence, not a baseline, so nothing built so far depends on this. Raised now so the tension is on the record rather than rediscovered.
Deep dive — the shape of an answer, not the answer

Three postures worth weighing when it is picked up, in ascending order of what they concede: reference a prototype by URL and never embed it (concedes nothing, delivers least); embed a sandboxed frame with a deny-by-default policy, treating the prototype as untrusted third-party content — which is what it is; or extend the course carve-out to a second artifact class with a hash or nonce policy, which is the same unsolved problem TBD-course-csp already carries.

Whichever is chosen, the load-bearing distinction is that an imported prototype is somebody else's executable content, arriving in bulk, marked unreviewed. That is a materially worse threat model than a course's own authored gate script, and an answer that treats the two as equivalent is wrong.
