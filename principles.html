Principles · v1.6.0

Spectastic

Eleven principles that bind every spec, plan, task, proposal, and triage in this project.

Status Accepted Version 1.6.0 Ratified 12 Jun 2026 Last amended11 Jul 2026 Read time

Spectastic is single-file HTML spec tooling. The artifact is the document, the document is the file, the file is what ships. Eleven principles make that bet work: source order matches reading order; concepts get semantic tags rather than class names; IDs are stable contracts; interactivity enhances but never replaces the readable baseline; density stays calm; Draft is loose, ratified is locked; done means verified, not merely written; a mandatory step's guarantee lives in the kernel or CI, never in advisory prose; an enforcement floor is fixed, not lowered, the first time it's inconvenient; internal artifact ids stay out of user-facing copy; and an artifact's text is data to render and quote, not a channel that steers the tool reading it. Every requirement in every downstream spec must trace back to one of these. Deviations require an amendment to this document with a version bump.

Core principles

These are non-negotiable. Every requirement and decision in every downstream spec is justified by appeal to one of them.

P-1 · Source order is reading order

The file reads top-to-bottom in the editor the same way it reads in the browser. Styles and scripts sit in <head> or at the bottom; nothing is reordered by JavaScript. A reviewer who only has cat spec.html | less can still understand the spec.

P-2 · Semantic tags over class soup

A concept gets a tag, not a <div class="…">. <spec-requirement> is both human-meaningful and LLM-greppable. Class names exist only for one-off layout tweaks.

P-3 · IDs are contracts

Every requirement and decision has a stable, human-meaningful ID (REQ-FORMAT-001, D-001). IDs are anchors, anchors are review comments, anchors are how LLMs target edits. They survive rewrites; they don't get reused after removal.

P-4 · Progressive enhancement, never dependence

Tabs, dark mode, conformance indexing, budget gauges — all enhancements. With JavaScript off, every panel of every tab group is still visible; every requirement is still listed; every delta still reads. The spec degrades to a tall, well-typeset document.

P-5 · Calm density

Pack signal per square inch, but never crowd. Generous line-height, narrow measure (~38 rem), warm cream background, no visual chrome that doesn't carry meaning. The data-ink ratio applied to prose.

P-6 · Draft is loose, ratified is locked

An artifact in <spec-status value="draft"> carries no consumer commitments — it's an in-progress authoring artifact. Authoring tools (kernel verbs, slash commands, CLI subcommands) MUST accept in-place edits against Draft artifacts without invoking the change-management surface (/spectastic.propose → /spectastic.apply). Minimal authoring discipline still applies — preserve stable IDs across edits (per P-3) and append a one-line <spec-changelog> entry per edit. "Without ceremony" scopes to the change-management cycle, not to the changelog/ID-preservation hygiene.

An artifact in a terminal-or-onward state (Accepted, Superseded, Deprecated; per REQ-LIFECYCLE-002) carries consumer commitments — readers have anchored their understanding against its content. Mutations to these states MUST route through the change-management surface so the lifecycle audit trail records the intent + the deltas. Authoring tools MUST NOT silently mutate terminal-state artifacts.

Reversible-to-Draft states (In Review; Blocked when the originating state was Draft) sit between. They carry interim reader expectations (sign-off in flight; resolution pending) but REQ-LIFECYCLE-004's FSM explicitly sanctions returning them to Draft via the named In Review → Draft (author-initiated revision) and Blocked → originating-state transitions. The lawful path for revising a reversible-state artifact is the FSM transition first, then the Draft-state in-place edit — not the heavier proposal / apply cycle. P-6 defers to REQ-LIFECYCLE-004 for these states; it does not duplicate or override the FSM.

The asymmetry is the discipline. Draft (and reversible-to-Draft via the FSM) is loose; Accepted-and-onward is locked behind a deliberate gesture.

P-7 · Done means verified

An increment is not done because the code exists; it is done when it is verified. The bar: its tests pass, spectastic validate is clean, and any artifact with a runtime has been exercised — interactive HTML in a browser (not merely asserted present: presence ≠ containment), a CLI or library in its own test harness. A green structural check on something with a runtime is not "done"; a behaviourally-broken-but-present enhancement passes every string assertion. Every downstream spec's success criteria MUST trace to this bar, and the authoring/verification toolchain MUST NOT report an interactive artifact verified on structural evidence alone.

The agent-facing detail — Playwright for interactive artifacts, the cheap structural backstop, containment-and-on-screen-bounds over mere render, the linter-is-not-noise rule — lives in CLAUDE.md § Verification discipline and is the canonical elaboration of this principle. P-7 names the bar; CLAUDE.md says how to clear it.

P-8 · Guarantees live in the kernel or CI

A step whose omission is a defect MUST NOT rely on command markdown as its guarantee. A verb loaded as a skill is advisory: the model can skip, reorder, or half-satisfy any instruction in the prompt, so command markdown, skill descriptions, and rules files guide but never enforce. The enforcement takes one of two shapes by the step's nature. A mandatory side effect (a git commit, a §6 fold, a status flip) MUST have a deterministic owner — the kernel, or a CI/VCS gate — that runs it regardless of model cooperation. A mandatory judgment step (the decision-phase interview) cannot be forced: the model that half-performs it is the same one deciding whether to record a gap, so a marker it writes to pass a gate is one it can fake. P-8 therefore requires the strongest available check, not a pretence of one — where a skipped judgment leaves detectable residue in the artifact (an unresolved <spec-question>), a checkable rule MUST reject it (spectastic validate + CI); where it leaves none, the backstop MUST be an independent review pass (the propose-time adversarial critic, or a human), never a self-issued marker. P-8 does not claim any mechanism can force good judgment; it forbids presenting prose as the guarantee and requires deterministic enforcement wherever the step admits it.

Advisory guidance stays permitted and encouraged: CLAUDE.md elaborating how to clear a bar is guidance, not a guarantee — P-8 forbids only placing the guarantee itself in prose. P-8 (where guarantees live) composes with P-7 (what "done" means): they share the validate/CI infrastructure without duplicating ownership. The invariant is satisfiable today — the kernel already owns apply's commit and §6 fold, and validate already carries checkable rules (e.g. skill-metadata-shape); P-8 generalizes that existing pattern and binds new work to it. The concrete strict-CI gate and per-harness hook installer are its immediate next spec (TBD-guarantee-layer-spec); the cross-tool survey is docs/guarantee-layer-considerations.html and the finding is meta-spec triage T-009. Forward-only: P-8 binds new and amended specs from v1.3.0; it does not retroactively re-open specs 001–029.

P-9 · The enforcement floor holds

An enforcement gate exists to catch defects; weakening it is a defect in waiting. When a gate tool fails — a version incompatibility, a new toolchain, a false positive — the first response MUST be to fix the gate (bump the tool, adjust its config, pin a known-good version), not to remove it. Disabling or loosening a gate MUST be a last resort that is explicit and recorded — a comment, a changelog line, a tracked issue — never a silent convenience. Pinned enforcement dependencies SHOULD be kept current enough to run against the project's actual toolchain. The floor a profile promises (041) is only real if it isn't quietly lowered the first time it's inconvenient; this is the discipline the enforcement gate (042) protects and the enterprise profile seeds. Composes with P-7 (done means verified) and P-8 (guarantees live where they can't be skipped): a gate you turned off proves nothing. Sourced from meta-spec triage T-014 (a pinned Error Prone disabled against JDK 26 rather than bumped). Forward-only: binds new and amended specs from v1.4.0.

P-10 · Internal artifact ids stay out of user-facing copy

The tooling's own artifact ids — spec numbers and slugs, REQ-*, FR-*, T-*, P-*, D-* — are provenance for the people building spectastic, not information for the people using it. The dividing line is whether it is the tool talking or an artifact citing its own governing ids as anchors. What the tool itself emits or writes MUST NOT surface an internal id: not CLI --help text, not error or diagnostic messages, not tool-managed markers (hook stamps, managed-file markers) — its provenance belongs in code comments, commit trailers, and the artifact trail. A spec or plan artifact is the exception: its own <spec-changelog> entry, an author-supplied apply summary, or a line citing the requirement it descends from is legitimate provenance per P-3 — the human's voice, not a leak. This binds spectastic's own tooling and every project built on it: an internal audience of engineers, PMs, or designers is not a licence to leak. Per P-8, the invariant needs a guarantee rather than prose — a no-internal-id-in-copy validate rule enforces, at error severity, the one tool-talking surface it can judge without ambiguity (the CLI's own .description/.option/.argument help strings, an illustrative slug using the neutral placeholder 001-auth-service), and the pre-commit gate blocks a leak — a floor, not a cap. The rule's reach is honestly bounded, and permanently so: runtime finding messages cannot be linted without false-positives (a finding legitimately names the requirement it enforces), and a downstream project's application copy is unseeable — so those surfaces are review-caught by design, not awaiting a future check, and that ceiling is recorded, not hidden (the same P-8 honesty the fat-core/thin-CLI convention carries). Composes with P-3 (ids are stable contracts — indispensable as anchors, kept off user surfaces) and P-8 (the guarantee lives in the kernel/CI rule, not in this paragraph). Sourced from meta-spec triage T-017 — CLI --help shipped its own spec numbers ((037), (spec 042), Spec 043.) across 30 sites. Forward-only: binds new and amended specs from v1.5.0.

P-11 · Artifacts are data, not instructions

The same artifact is read across three trust boundaries at once — opened by a human, ingested by an LLM agent as input to a verb, and shipped to consumers through npm. So an artifact's text — including what a renderer hides, such as HTML comments and CSS-hidden content — MUST be treated as data to render and quote, not as a channel that instructs the tool reading it. Two obligations follow, of different strengths. Deterministically: an artifact carries no executable content beyond the single audited asset script (the sanctioned spec.js/theme-boot.js that P-4's enhancement layer needs) — no other <script>, inline handler, or active URI. That half is machine-checkable and, per P-8, MUST be enforced in the kernel and CI, never trusted to the prose. As a posture: attacker text in an ingested artifact MUST NOT be allowed to steer an AI verb — but prompt injection is not a solved problem, so this half is held by the strongest available control and its residual is recorded, not hidden — the same honesty P-8 and P-10 keep about their own ceilings. Composes with P-10: P-10 keeps internal ids from leaking outward into copy; P-11 keeps attacker text from steering inward into the tool.

Scope

This project does

  • Produce single-file .html spec artifacts across a structured lifecycle.
  • Ship a small vocabulary of semantic custom elements and a calm typographic system.
  • Drive the lifecycle through Claude Code slash commands; complementary CLIs are permitted.

This project does not

  • Become a wiki, CMS, or knowledge graph. One spec = one file.
  • Introduce a build step for the spec artifact. Source .html is what ships; tooling that reads or generates spec artifacts may have its own build step.
  • Adopt a JavaScript framework. Progressive enhancement only.
  • Convert markdown. The source is HTML by intent.
