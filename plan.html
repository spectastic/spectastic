Spectastic

How we built it. The architectural moves that keep the artifact small.

Status Accepted Spec 000-spectastic v0.1 Principles v1.0.0 Owner Brian Corbin · @briancorbinxyz Branch main Created 12 Jun 2026 Read time

The plan is small because the bet is small. Single-file HTML, hand-written CSS, ~5 KB of progressive-enhancement JS, custom elements as the authoring vocabulary, eight Claude Code slash commands as the workflow. No framework, no bundler, no transpiler, no test suite. The biggest architectural move is what's absent: there is no build step between source and shipped artifact. The single file is what ships.

2 · Technical context

Languages
HTML5, CSS3 (no preprocessor), vanilla ES2020+ JavaScript. No TypeScript, no SCSS.
Frameworks
None. No React, no Vue, no Svelte, no Lit. Custom elements as plain HTML.
Storage
Filesystem. Artifacts open from file:// or any static server. Git for versioning + history.
Fonts
Fraunces, Source Serif 4, Lato, IBM Plex Mono via Google Fonts CDN; degrade to system serifs/sans/mono on failure.
Testing
Visual verification in browser + git history. No unit test suite. The single-file artifact is the test — if it renders, it works.
Perf targets
Source under 200 KB before fonts (REQ-FORMAT-003). Render under 2 s including Google Fonts load on a cold cache, broadband.
Constraints
No build step. No bundler. No transpiler. The file on disk is the file the browser renders.
Distribution
Copy this directory into a project; install slash commands into .claude/commands/; done. No package manager.

3 · Approach

The single file is the artifact. Every other architectural move flows from that. The CSS is hand-written so it doesn't need a preprocessor; the JS is ~5 KB so it doesn't need a bundler; the SVG is inline so diagrams diff cleanly; the slash commands are markdown files so Claude Code reads them with zero glue. The whole thing fits on a small static host or runs from file:// on a phone.

The custom-element vocabulary is the heart. Authoring with <spec-requirement> instead of <div class="requirement"> moves the schema into the tag name, where it's both human-meaningful and LLM-greppable. The browser renders unknown elements with whatever styles their CSS rules provide — no JS registration needed for the baseline. JS enhances (auto-builds the conformance index, drives tabs, etc.) but never produces content.

The lifecycle is structured but optional: principles → spec → plan → tasks → implement → propose → apply → triage. Each phase is a Claude Code slash command that fills a template. Greenfield projects start at principles; brownfield projects start at spec; small-batch work skips the formal lifecycle entirely and lives in inbox.html.

5 · Decisions

The meta-spec already carries three founding decisions: D-001 (custom elements over div+class), D-002 (inline assets at publish, link during dev), and D-003 (calm typographic defaults). Rather than copy them here, the plan adopts them by reference. The decisions below are implementation-specific — the moves that landed during build.

D-004 · Custom elements without JavaScript registration

Status
Accepted
Context
Custom-element specs let you register classes with customElements.define() to attach behaviour. Doing so would couple every component to the JS runtime.
Decision
Treat custom-element tags as styled-by-CSS only. Skip customElements.define(). The browser renders unknown elements with whatever rules the stylesheet provides — no registration needed.
Consequences
+ With JS off, every component still renders. + No framework-shaped lifecycle to learn. − No encapsulation; specs share a CSS namespace. The namespace is small enough that this is fine.

D-005 · Slash commands as markdown files; Claude reads on invocation

Status
Accepted
Context
Spec-driven tooling typically ships a CLI (spec-kit's specify, OpenSpec's openspec). A CLI is a runtime dep.
Decision
Define every slash command as a markdown file in commands/. Claude Code discovers them automatically. No npm install, no binary.
Consequences
+ Zero install: copy the dir, done. + Discovery is grep. − Tied to Claude Code; non-Claude editors need separate wiring (deferred).

D-006 · Inbox + small-batch loop as a complement, not a replacement

Status
Accepted
Context
The structured lifecycle (spec → plan → tasks → implement) is overkill for "I have three small things in my head." The classic ceremony-vs-velocity tension.
Decision
Ship inbox.html at project root + extend /spectastic.triage and /spectastic.implement to drain it. No new verbs.
Consequences
+ "Few items in your head → being worked on" closes in three commands. + The formal lifecycle stays available for items that warrant it. − Two discipline modes coexist; documentation must teach the boundary.

8 · Complexity tracking

One deliberate complexity worth flagging:

The project carries two discipline modes — the formal lifecycle (spec → plan → tasks → implement) and the small-batch loop (paste → triage → implement-from-inbox). The duality is intentional (D-006) but creates a teaching burden: when does something warrant the formal path? The current heuristic, documented in commands/spectastic.triage.md, is "one file, no public-contract change, revert-safe → just-do; otherwise → spec." If telemetry surfaces consistent misclassification, this heuristic gets sharpened — but the simple version is the right default to ship.

9 · Open questions

  1. Cross-tool installer. The slash commands are markdown that any Claude-Code-shaped tool could pick up, but the conventions (file locations, frontmatter) are Claude-specific. Cursor and Aider use different surfaces. Worth a future proposal once there's a concrete user; not now.
  2. Validator. A spectastic validate script that walks the HTML, checks ID uniqueness, anchor resolution, delta targets, and INVEST blockers, would close the no-test-suite gap. Scoped out of v0.1; tracked as a TBD slice in the meta-spec §2.
  3. Action-detecting unified command. The eight verbs are explicit; an experienced user might prefer /spectastic.next that detects state and picks the right phase. Considered and deferred — pedagogy beats detection for now, but worth revisiting if usability friction shows up.
