Handover · Learning surface

/spectastic.explain

One verb, in all the forms discussed — the just-in-time coach and the grounded, ephemeral --course mode that builds the person. This doc carries the accepted decisions, the evidence behind the design, what ships in v1, what is deliberately deferred, and the two seams that must be reserved now so the deferral never forces a spec migration.

The deliverable is one verb, /spectastic.explain, in every form discussed: explain <target> is an ephemeral, in-chat, just-in-time explanation; explain --course generates a persistent, blended, grounded-and-verified course. Three decisions are accepted: it ships as a mode of explain (not a ninth hero verb); the eight lifecycle verbs are the core / hero set while explain is an extended, opt-in verb; and a course lives outside specs/, may be cross-spec, and is ephemeral. The rest of the original research — the rubber-stamping sign-off gates and the document-format extensions — is deferred to a later tier / v2. The single caveat that shaped this doc: defer only what is cleanly additive. Two pieces are not cleanly additive — the extended-verb packaging and the --proficiency flag surface — so their seams are reserved now even though their full features wait. §6 is that analysis.

1 · What's decided (accepted)

These three were ratified by the product owner and are recorded as Accepted decisions. They are the frame everything else hangs on. The design ADRs in §4 are still Proposed and need ratification before build.

D-006 · The course is explain --course, not a standalone command

Status
Accepted
Context
The idea arrived as /spectastic.university. But the training-wheels research already proposes an explain verb (D-003) as the on-demand, just-in-time coach. A course is the bigger, persistent sibling of an explanation — not a separate concern.
Decision
Ship it as a mode: explain <target> gives an ephemeral in-chat explanation; explain --course <target | topic> generates a persistent blended course. One verb, two depths. (explain reads truer to the calm house voice than "university"; the mode flag carries the meaning.)
Consequences
+ No new top-level verb to justify. + The course inherits explain's grounding machinery. + Clear mental model: explain is small, course is large. − explain itself still has to be specified and built (it is only proposed today in D-003).

D-007 · Reframe: eight hero verbs, plus extended opt-in verbs

Status
Accepted
Context
The "don't add a ninth verb" discipline was treated as a hard cap. That framing made every genuinely useful capability fight for one of eight slots. The real intent is to keep the day-to-day surface minimal, not to forbid all further verbs.
Decision
Reframe the command surface in two tiers. Core / hero verbs (8): principles · spec · plan · tasks · implement · propose · apply · triage — the minimal lifecycle set, installed by default. Extended verbs: opt-in capabilities (e.g. explain) that need not be installed by default and are not "hero" features. explain (and thus --course) lives in the extended tier.
Consequences
+ Resolves the ninth-verb tension without diluting the core. + Lets the product grow capabilities without bloating the first-run surface. + Keeps the OpenSpec-style "small core" win intact. − Needs an install/enable story for extended verbs — a real, if small, packaging decision (see §6; this is migration-sensitive). − The per-verb "pay rent" discipline must still apply inside the extended tier, or it becomes a junk drawer.

D-008 · A course lives outside specs/, may be cross-spec, and is ephemeral

Status
Accepted
Context
The lifecycle artifacts under specs/<id>/ are stable, ID-bearing contracts. A course is the opposite: it may draw on several specs (or none — an ad-hoc topic), it is generated on demand for one learner at one moment, and it goes stale the instant the underlying code or spec moves. Filing it under specs/<id>/ would imply a permanence and single-spec scope it does not have.
Decision
Courses are written outside the spec tree, in a dedicated ephemeral location (recommended: project-root courses/ or .spectastic/courses/, git-ignored by default with an explicit opt-in to keep one). A course carries no stable IDs of its own; it references stable IDs in the specs/code it teaches. It may span multiple specs.
Consequences
+ The contract directory stays clean. + Cross-spec and ad-hoc courses have a natural home. + Ephemerality is honest — a stale course is regenerated, not maintained. − Need a regeneration story (re-run explain --course) rather than an update/migrate one. − A team that wants a canonical onboarding course keeps it via deliberate opt-in, not by default.

2 · The verb, in all its forms

This is the deliverable. One verb, two depths, a small set of flags, and an artifact that reuses existing machinery — no new <spec-*> elements are required to ship it. The command file follows the existing shape (front-matter description + argument-hint; narrative intro; Inputs; Procedure with the two-phase interview; Output style).

explain <target>
   # ephemeral, in-chat, just-in-time explanation (the D-003 coach)

explain --course <target | topic> [--proficiency=wheels|completion|independent] [--keep]
   # generates a persistent blended course artifact, grounded + verified

# <target>       = a spec-id, a requirement/decision ID, a file/dir path, or several
# <topic>        = an ad-hoc subject with no repo anchor (weakest mode — see caveat)
# --proficiency  = explicit band; later may DEFAULT from stored state (see §6 seam)
# --keep         = opt out of the git-ignore default and retain this course (D-008)
 
Chat phase:    learning goal; what's already known; time budget;
               which spec(s)/paths/topic to ground in.

Decision phase (AskUserQuestion):
               proficiency band (defaults from D-001 if/when stored);
               scope (one decision ↔ whole spec ↔ cross-spec);
               depth.
               NOTE: never ask "learning style." Format mix is DERIVED
               from each objective's Bloom level, not chosen (D-009).
 
<spec-meta>        learner · proficiency band · objective · mastery state
<spec-tldr>        "by the end you'll be able to…"
objectives         rendered as <spec-task> checkboxes = a MASTERY LEDGER
                   (:has(input:checked) strike = mastered)
per objective:     <spec-tabs> → Read / Quiz / Build variants
                   <spec-decision> teach-back PROMPT (ungraded in v1;
                   the graded gate is deferred — see D-005 / §6)
<spec-glossary>    context-scoped domain vocab
Lives in:          courses/<date>-<slug>/course.html (git-ignored; D-008)

Build order. explain (ephemeral, in-chat) ships first; --course is added once the grounding/verification path (D-010) is proven on the cheaper mode. The bare coach is also where the just-in-time, expertise-reversal-safe behaviour lives: coaching is pulled, never pushed.

3 · Why — the evidence

Two research efforts feed this verb. The first asked how a junior or product person can meaningfully engage with a spec; the second asked how a "university" feature should actually teach. They converge on the same two-part answer: fade the scaffold as competence grows, and ground every word in real artifacts, just-in-time.

3.1 · The fading spine (why --proficiency exists)

Four citable effects give the coach its shape and justify a competence band rather than an always-on tutor:

  1. Scaffolds work by blocking wrong paths, not adding prose. The original training-wheels HCI study made error-prone states unreachable and measured faster learning; the control group spent ~¼ of its time recovering from errors the training interface simply blocked. Carroll & Carrithers, "Training Wheels in a User Interface," CACM 27:8 (1984). ACM · NN/g.
  2. Layer knowledge — but no more than two deep. Progressive disclosure defers detail to a secondary surface; beyond two levels, users get lost between layers. Nielsen, Progressive Disclosure (1995). NN/g.
  3. The wheels must come off. The expertise reversal effect: guidance essential for novices actively degrades expert performance. A permanent training-wheels mode is a bug — hence the band, and hence coaching-on-demand only. Kalyuga, Expertise Reversal Effect, Educational Psychology Review (2007). Springer.
  4. Fade on a competence trigger, not a clock. The guidance-fading effect: worked example → completion problem → independent problem beats static full guidance on post-tests. Renkl & Atkinson (2004). Springer.

3.2 · What teaches (why --course looks un-flashy)

Six research streams converged on one reframe: the failure modes of a "university" feature are all about detachment — detached content doesn't transfer, self-paced courses don't finish, and LLM content detached from the real repo hallucinates. Grounding is the whole game.

RuleWhy (evidence)
Personalize to knowledge state, never a "learning style." Drive format from the objective's Bloom level + the learner's mastery state. "Learning styles" is one of the most robust negative findings in education research.Pashler et al., "Learning Styles: Concepts and Evidence." review. The minimal viable learner model is per-skill mastery (BKT ≈ four numbers/skill), which maps onto the proficiency band (D-001).
Modality follows the cognitive target — and blend it. MCQ for Remember/Understand; hands-on for Apply/Analyze; Create is unreachable by MCQ. Interleave and space. Assessment validity (no single modality spans Bloom) and learning science: interleaving roughly doubles delayed-test scores; spacing beats massing.Wiggins (authentic assessment); Rohrer & Taylor (interleaving); Cepeda et al. 2006 (spacing). Interleaving feels harder, so learners under-adopt it.
Invest in the inner loop (step-level feedback), not a clever recommender. Step-based tutoring carries most of the ITS effect (d≈0.76, ≈ human tutoring); commercial adaptive platforms show weak/null causal effects.VanLehn 2006/2011 (outer/inner loop); Knewton/adaptive-courseware null results. For a chat-native tool, good feedback while you work beats any sequencing algorithm.
Ground every item in real source, then verify it. Retrieve real code/spec as context; check generated exercises against the repo. Strongest evidence here: LLMs confidently hallucinate APIs that don't exist; retrieval-grounding measurably fixes it (23–61% gains).De-Hallucinator (arXiv); "LLM Hallucinations in Practical Code Generation" (arXiv). Same spirit as spectastic's "verify the spec wasn't lying" discipline.
Motivate with feedback, not points. No streaks, badges, or leaderboard. Completion-contingent tangible rewards undermine intrinsic motivation (d≈−0.40); verbal/informational feedback enhances it (d≈+0.33).Deci, Koestner & Ryan 1999 meta-analysis; Lepper et al. 1973. Also fits the calm house voice.
Small, real, in-flow — and measure declared intent. Favor a "small real change" shape; micro + spaced units. Self-paced completion is ~5–15% and ~52% never start; in-flow learning solves the transfer problem.Reich & Ruipérez-Valiente 2019 (MOOC completion); Baldwin & Ford (transfer). "Learn by shipping a small real change" is strong practitioner consensus, anecdotal not controlled.

The biggest trap is the obvious one. The seductive default — a polished course catalogue with XP, streaks, and a completion bar — is precisely the design the evidence says fails. Build the un-flashy version: grounded, mastery-gated, feedback-rich, ephemeral, in-flow.

4 · Proposed design (needs ratification)

All of the below reuses existing machinery. These three ADRs are Proposed. D-001 is carried over from the training-wheels research as the minimal learner-model dependency that explain --course needs.

D-001 · Proficiency bands as the learner model and fading engine

Status
Proposed · dependency of explain
Context
Scaffolding must fade on competence or it harms experts (expertise reversal). A protocol needs a single variable that gates every other scaffold, and a course needs a learner model — the band is both.
Decision
A per-author, per-bounded-context proficiency value (wheels | completion | independent), surfaced as a status pill, driving interview depth, worked-example pairing, and block-vs-nudge behaviour. Fade on the existing triage-card competence signal; reset locally on new domains. For explain, the band is the entire learner model — nothing more is needed.
Consequences
+ One lever controls the whole scaffold and the course personalization. + Reuses the triage signal already produced. − Needs a place to persist per-author state, which a single file lacks natively (the open storage question; see §6 — the flag ships now, the storage is deferred but additive).

D-009 · Mastery-state personalization; Bloom-driven modality (no styles, no fancy recommender)

Status
Proposed
Context
The personalization promise is the risky part — it invites a "learning style" picker and a sequencing algorithm, both of which the evidence rejects.
Decision
The learner model is the proficiency band (D-001) plus a per-objective mastery flag — nothing more. Modality per objective is derived from its Bloom verb (recall → MCQ-with-feedback; apply/create → hands-on/build). Objectives are interleaved and spaced, not blocked. The band drives fading: Wheels gets worked examples + every objective; Independent gets a terse, skippable refresher. No streaks/badges/XP — feedback is the motivator.
Consequences
+ Cheap and evidence-aligned. + Reuses D-001 wholesale. + Sidesteps the learning-styles myth and the null-result recommender. − Must explain why interleaving "feels harder" (desirable difficulty), or learners resist it. − Needs to read band/mastery state from somewhere (ties to D-001's storage question).

D-010 · Retrieval-grounded generation, verified against the repo

Status
Proposed
Context
Confident-but-wrong content is the dominant, rigorously-documented failure mode of codebase-grounded learning. A course that teaches a hallucinated API is worse than no course.
Decision
Every question/exercise is generated from retrieved real source (the named spec/decision/file), never synthesized from generic training. Before a course ships, each item is verified against the repo: build exercises run/compile/test; conceptual items pass a guessability check (reject any the model can answer with the source hidden); referenced symbols/paths are confirmed to exist. The existing risk-pass critic agent is the natural generator; the existing "verify the spec wasn't lying" discipline is the natural verifier.
Consequences
+ Directly attacks the dominant failure mode with the best-supported mitigation. + Ad-hoc topic mode (no repo anchor) is explicitly the weakest mode and is flagged as such to the learner. − Verification costs time/compute. − Some objectives can't be auto-verified (design judgement); those route to a teach-back graded by a human or LLM-as-judge — which is the deferred D-005 gate, so v1 keeps the prompt ungraded (see §5).

5 · Deferred to a later tier / v2

Everything the original research proposed around the verb — the rubber-stamping sign-off gates and the document-format extensions — is deferred. Each was checked against one test: does deferring it force a later spec migration? Where the answer is "no, it's cleanly additive," it waits with a clear conscience. The two items where the answer was "yes" are not in this list — they are in §6.

Deferred item (origin)What it wasMigration-safe to defer?
D-002 · <spec-signoff> A sign-off element with a required "verified / escalated" field, "Yes, if" field, named accountable human, and role="shadow" variant; promotion blocked while a risk is open. Yes. A new optional element added to spec artifacts later is purely additive.
D-005 · teach-back gate Gating promotion to accepted on a graded teach-back, faded by band. Yes, with one precaution. The course artifact already carries ungraded teach-back prompts (§2); since courses are ephemeral and regenerated (D-008), adding the graded gate later changes no stored format. Keep the prompt block now so the gate is additive.
D-004 · Tier-0 JSON-LD emitter Emitting each spec's requirements/decisions/glossary as schema.org JSON-LD for an in-document knowledge graph. Yes. An added <script type="application/ld+json"> block is additive.
D-003 (lens half) · reading-lens toggle + KG Tiers 1–3 A Product/Engineer lens toggle on <spec-audience-map>; linked-ontology / GraphRAG / code-graph enrichments "where available." (The coach half of D-003 is explain itself — that is the deliverable, not deferred.) Yes. Lens toggle is additive JS that degrades to "everything expanded"; KG tiers are optional attributes designed to be absent by default.
New <spec-*> elements generally Any further document-format extensions implied by the above. Yes. The format is additive by construction (forward-compatible decoders / unknown-element tolerance).

Net: the entire rubber-stamping and doc-extension surface can wait without painting v1 into a corner — provided the course artifact keeps an (ungraded) teach-back prompt block so D-005 lands additively. The grading is the deferred part; the slot is not.

6 · Seams to reserve now (the migration caveat)

Two pieces failed the "cleanly additive" test. Deferring them whole would force a breaking change later, so v1 must reserve the seam even though the full feature waits.

D-011 · Decide the extended-verb packaging seam at explain-spec time

Status
Proposed · migration-sensitive
Context
D-007 makes explain the first extended verb. If it ships as a plain ninth command file with no notion of tiers, then formalizing the core/extended split later means moving command files and/or introducing a manifest the existing install never had — a migration for every installed project.
Decision
Pin the minimal packaging mechanism now, when explain is specified: where extended verbs live, how one is enabled, and how the installer distinguishes core from extended. It can be as small as a manifest flag or a separate install path — but it must exist before the first extended verb ships, not after. (This resolves what was open question 2 in the handover.)
Consequences
+ The core/extended tiering is a config decision, not a later file-move migration. − A small amount of packaging design has to happen up front rather than being deferred with the rest.

D-012 · Ship the --proficiency flag now; defer only the persistent storage

Status
Proposed · migration-sensitive
Context
D-001's storage (per-author, per-context state in a single-file world) is a real open question and is fine to defer. But the flag surface is not: if explain ships without --proficiency and the band concept, adding personalization later changes the CLI contract and any scripted invocation — a breaking change.
Decision
Ship --proficiency=wheels|completion|independent as an explicit flag in v1, with the band vocabulary fixed. Persistent storage is deferred; until it exists, the flag is passed explicitly and defaults to wheels (safe: more scaffold, never less). When storage lands, the flag simply defaults from stored state — a purely additive change, no contract break.
Consequences
+ The CLI surface is stable from v1; personalization arrives without a migration. + Defaulting to wheels fails safe. − A flag exists before the state that would make it automatic, so early users set it by hand.

8 · Open questions for the implementer

  1. Where exactly do courses live, and is git-ignore the default? courses/ at root vs. .spectastic/courses/. Recommendation: git-ignored by default, --keep to retain (D-008) — confirm the path.
  2. What is the minimal extended-verb packaging mechanism? A manifest flag, a separate install path, a marketplace listing? Must be pinned before explain ships (D-011), not after.
  3. Where is the learner's band + mastery state stored? The single-file-HTML world has no native per-author state. The flag ships regardless (D-012); resolve storage once for both explain and the wider band concept.
  4. Who grades a hands-on / teach-back item? Repo (tests pass), LLM-as-judge (gameable), or a human shadow reviewer — likely all three by item type. Which is the v1 default, and does a failed item block "mastered" or only advise? (The graded gate itself is D-005, deferred; v1 keeps the prompt ungraded.)
  5. Ad-hoc topic mode. A topic with no repo anchor is the weakest, least-grounded mode. Keep it behind a warning, or drop it for v1?
  6. Sequencing confirm. Build explain (ephemeral, in-chat) first, then add --course once grounding/verification is proven — agreed?

Method & confidence. Merged from two research syntheses: the training-wheels protocol (six streams + a four-stream pass on comprehension gates) and the course handover (one codebase-grounding stream + five web angles). Web-page fetching was blocked in both sessions, so non-GitHub quotes rest on search-result extracts — well-corroborated for canonical sources (Carroll & Carrithers, Kalyuga, Renkl & Atkinson, VanLehn, Corbett & Anderson, Wiggins, Deci & Ryan, Pashler, Reich & Ruipérez-Valiente) and flagged inline where vendor-sourced or single-study. 9 · Glossary

explain
The extended verb delivered here. explain <target> is an ephemeral in-chat coach; explain --course generates a persistent grounded course.
course
A persistent, blended, grounded learning artifact generated by explain --course; ephemeral, git-ignored by default, may span multiple specs (D-008).
proficiency band
The learner model and fading lever: wheels | completion | independent, per author and bounded context (D-001). Drives interview depth and course personalization.
fading
The deliberate removal of scaffolding as competence grows — triggered by demonstrated outcome, not a clock.
expertise reversal
The effect whereby guidance that helps novices degrades expert performance — the reason coaching is pulled, not pushed, and why the wheels come off.
grounding
Generating every item from retrieved real source and verifying it against the repo, rather than synthesizing from generic training (D-010) — the dominant mitigation for confident-but-wrong content.
teach-back
Confirming understanding by having a person explain the material in their own words. Present as an ungraded prompt in v1; the graded comprehension gate (D-005) is deferred.
hero verb
One of the eight core lifecycle commands installed by default. Extended verbs (e.g. explain) are opt-in and live outside the hero set (D-007).
migration-sensitive seam
A design point where deferring the whole feature would force a later breaking change, so the seam is reserved in v1 even though the feature waits (D-011, D-012).
