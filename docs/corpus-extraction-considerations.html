Considerations · Standalone corpus

The corpus wants to be its own tool

A curation, provenance, and citation layer grew inside a spec-driven tool. It is nearly self-contained, it already lives in repos that never run the lifecycle, and the one feature it was told it couldn't have — PDF conversion — is only forbidden because of a constraint a standalone tool wouldn't carry.

Status Draft Type Architecture & landscape survey Author Brian Corbin · @briancorbinxyz Created 27 Jul 2026 Sources 21 external, retrieved 27 Jul 2026 · codebase audit Read time

The knowledge-corpus subsystem has quietly become product-shaped: ~3,000 lines in one cohesive module (packages/core/src/knowledge/), coupled to the lifecycle through only two thin seams (prompt injection + validate gates), and the core was deliberately built for a second surface — its file-IO port names "an MCP server with capability-scoped IO" as an intended adapter. The external migration already proved corpus knowledge lives in repos that never touch the lifecycle. So the question is real: make it a standalone corpus product — separately installable, usable without spec-driven development, and finally free to own PDF conversion (descoped from the kernel only for a Node-only constraint a standalone tool doesn't carry). The landscape confirms a niche: the open-source world splits into retrieval infrastructure (LangChain, RAGFlow, vector DBs) and packaging (the SKILL.md standard, agent-skills marketplaces) — and this corpus is neither. It is the provenance / citation / curation layer: human-curated, KB-NNNN-cited, injected-not-embedded. The interview surfaced a bigger prize than a library: an MCP server serving the corpus and the specs/ estate across multiple repos — the doc-MCP category is established, targeted retrieval saves context over file-reads, and spectastic's citation contract is exactly the provenance a generic doc-server can't carry. That multi-repo move exposes a collision the doc has to answer: spec ids and KB-NNNN are both repo-local, so a federated index is ambiguous — but the corpus already carries the fix (the DOI-shaped marketplace prefix), and specs need the same prefix they lack today; namespace both and a top-level orchestrator could route a requirement to its owning service by the spec-sensitive corpus (a forward-look, human-confirmed). Recommendation: three staged slices — extract the library (in-monorepo first), give PDF a home (a shell-out wrapper, no bundled runtime), and build the MCP serving surface (likely its own repo, federated-identity-aware) as the headline bet.

1 · The ask — a corpus that outlives the lifecycle

Spectastic's corpus began as a grounding aid: give the AI verbs trustworthy, cited source material so a generated spec cites a real requirement instead of hallucinating one. But it kept accreting the machinery of a knowledge product — a two-layer identity (062), a citation contract with edition pinning (052), integrity and grounding gates (053), licensing checks (058), an ingester (061), and marketplace discoverability (063). None of that is about spec-driven development. It is about curating a trustworthy, citable body of domain knowledge.

Two facts turn "nice module" into "candidate product." First, the corpus already lives where the lifecycle doesn't: the external-repo migration (example-cash-snapshot, spectastic.io) reshaped and pushed corpus packs in repos that are not driven by spectastic specs. Second, the one feature the kernel refused — a PDF converter — was refused for a reason that evaporates outside the kernel. The rule (051, 056, marked TBD-never) is "the kernel stays Node-only; a converter means a Python/GPU runtime we won't take on." A standalone corpus tool is not the kernel and carries no such vow.

So the prompt is: can the corpus be a product in its own right — separately downloadable, useful to someone who wants a knowledge base and citation discipline but never writes a spec? And if so, how does knowledge get out of it, given that today the only exit is prompt injection into spectastic's own verbs?

2 · What's actually extractable

The encouraging finding from the codebase audit: the corpus is one of the most self-contained subsystems in the tree, and the architecture was designed to be lifted. The surface, module by module:

PieceWhereWhat it owns
The library packages/core/src/knowledge/ — 15 modules, ~2,960 LOC Parse, ingest, adapt, resolve citations, publish/sync marketplace.json, validate (well-formed / registry / grounding), licensing, provenance fencing, the registry + index format, pack-agnostic resolution.
The CLI edge packages/cli/src/commands/corpus.ts (~200 LOC) + config/corpus.ts One command group: adapt, import, interview, source, publish. Thin — it parses args and delegates to the library, per the fat-core / thin-CLI convention.
The schema rules packages/schema/src/ — citation-shared.ts, rules/corpus-citation-form.ts The citation-form check + the shared citation grammar.
Lifecycle seams (the only coupling) AI verbs + validate Two. (1) Prompt injection: every AI verb calls buildCorpusPromptBlock(loadCorpus(cwd)) + withCorpusHint. (2) Validate gates: the scanCorpus* functions import from @spectastic/core/knowledge.

The architecture already anticipates this. The core's file-IO port (packages/core/src/providers/node-fs.ts) states its own reason for existing as "a browser-based web editor, an MCP server with capability-scoped IO" — the IO abstraction was written so a second surface could drive the same deterministic kernel, and core/src/types.ts repeats the intent ("MCP / VS Code adapters render the choices in their own UI"). A corpus library with its own thin CLI (and later an MCP edge) is not a new pattern to invent — it is the seam the codebase already assumes. There is direct precedent too: @spectastic/core already ships a standalone-library import as a first-class, tested guarantee (002, SC-004). Extraction here is a well-trodden move, not a leap.

The two seams are the whole cost. Extraction is not free — the prompt-injection call and the validate scans must invert from "core reaches into knowledge/" to "core (or the CLI) depends on the extracted corpus package": a mechanical dependency flip across a handful of call sites, not a redesign. The graceful-absence NFR (the lifecycle works with or without a corpus, 051) already makes both seams null-safe, which is what keeps the flip low-risk.

3 · The landscape — two worlds, and this sits in neither

The open-source knowledge-base world in 2026 splits cleanly, and understanding the split is what tells us whether a standalone corpus is a redundant re-entry or an underserved niche.

WorldExemplarsProblem it solves
Retrieval infrastructure LangChain, LlamaIndex, Haystack; RAGFlow (chunk-level citation, GraphRAG); vector stores Chroma, Qdrant, Milvus, txtai. Query-time retrieval over embeddings. Chunk, embed, index, similarity-search, re-rank. The pipeline engineering problem.
Packaging / agent-skills The SKILL.md open standard (16+ tools by early 2026 — Claude Code, Codex, Cursor, Gemini CLI); agent-skills marketplaces; llms.txt. Portable, progressively-disclosed, versioned knowledge/skill packs. Build once, consume from any compatible agent.
The gap this fills Spectastic's corpus. Curation, provenance, and citation. Human-curated, KB-NNNN@edition-cited, provenance-stamped, license-checked, injected-not-embedded. The trust problem, upstream of both.

It is not a RAG tool, and shouldn't pretend to be. RAGFlow and the vector DBs answer "how do I retrieve the relevant chunk fast?" This corpus answers a question they punt on: "can I trust this source, cite it precisely, and know when its edition went stale?" A corpus document carries authority provenance (converted / interviewed / sourced), a license verdict, a stable id, and edition pinning so a citation survives supersession (052) — the curation layer, orthogonal to retrieval and largely unserved by the retrieval-infra tools, which take "whatever markdown lands in the index" on faith. So the honest positioning: spectastic-corpus is upstream of RAG (it produces trustworthy, cited, licensed source a LangChain or RAGFlow pipeline can consume) and aligned with SKILL.md packaging (062/063 already emit a marketplace.json and portable packs). It should lean into both rather than compete with either. Refusing to become a vector DB isn't a limitation to apologize for — it is the product's spine.

4 · Getting knowledge out — the retrieval seam

Here is the real design problem. Today the corpus is write-and-inject only: you curate documents in, and the only way knowledge comes back out is through spectastic's own AI verbs quietly prepending a prompt block. A standalone product needs a first-class read path — a way for a person, or any agent, to ask the corpus a question and get cited answers without running a single spec command.

Two exits, and they compose. A query CLI (corpus query "T+1 settlement window" → matching documents with their KB-NNNN ids and provenance) is the deterministic, scriptable floor. An MCP server is the ambient one: any MCP-speaking agent (Claude Code, Codex, Cursor) connects and pulls cited corpus context on demand. Both are established prior art — dedicated documentation MCP servers ("maintain docs in one place, available to humans via the web and to agents via MCP") already exist, and multi-server aggregation (one endpoint fronting many repos' servers) is a known pattern.

This read path is additive, not a rewrite of injection. The query CLI and MCP server are how external consumers — a person, another agent — get cited knowledge out. Spectastic's own AI verbs are unchanged: they keep injecting directly from knowledge/ on disk via buildCorpusPromptBlock(loadCorpus(cwd)), exactly as today. Nothing here proposes rerouting the verbs' injection through the MCP server — not in slice 1, and not as part of this survey. The extracted library reads the same files; the server is a second doorway onto them, not a replacement for the first.

The interview widened this past the corpus. If a server is serving cited knowledge, the specs/ estate is the same shape of thing — structured, cross-referenced, id-anchored HTML. An agent asking "what does REQ-FORMAT-004 require?" or "show me the SC→acceptance→test trace for this spec" is a retrieval problem the server could answer directly and cheaply: one requirement or one trace is far less context than an agent reading whole spec.html files (code-intelligence MCP servers report large token reductions over file-reads for exactly this reason). Two properties make this spectastic's to win rather than a generic doc-server's:

  • Provenance is native. A generic doc-MCP server returns text; spectastic returns text with its KB-NNNN@edition citation and authority provenance. "Cite the paragraph you relied on" is not a bolt-on — it is the corpus's existing contract.
  • Multi-repo is the multiplier. One server pointed at several checkouts turns an org's whole spec-and-corpus estate into a single queryable, cited surface — the thing no single-repo tool offers.

Because that server serves both corpus and specs, is a long-running process (unlike every existing CLI verb), and may aggregate multiple repositories, it is architecturally a different animal from the corpus library — plausibly its own component, quite possibly its own repo, consuming the extracted library and a read-only view of the specs. That is the headline bet, and the piece worth the deepest scrutiny before building.

D-001 · The read path is a query CLI plus an MCP server; the MCP server serves corpus and specs, multi-repo

Status
Proposed
Context
A standalone corpus is useless without a way to get cited knowledge out; today the only exit is spectastic's prompt injection. Doc-MCP servers and multi-server aggregation are established patterns; spectastic's differentiator is native provenance and a citation contract a generic server lacks.
Decision

5 · Identity & namespacing across the federated estate

The multi-repo ambition of §4 hides a load-bearing problem the moment a server fronts more than one repo: identity collides. A federated index that keys on the ids artifacts carry today is ambiguous, on two axes at once.

AxisThe collisionWhy
Spec ids Every spectastic repo has a spec 042, a REQ-FORMAT-004, a T-017. Across repos they are not the same thing and there is nothing to tell them apart. Spec ids are purely repo-local — every project starts at 000 and re-uses the same REQ-/FR-/T- grammar. There is no namespace layer at all; spectastic.json carries no project identity.
Corpus ids The same KB-0001 exists in every repo that dogfoods the corpus. KB-NNNN is repo-unique, not global — it is "project-assigned and repo-unique" in the root registry (052 resolver). It is a local convenience, not a federation key.
Duplicated knowledge The same pack (spectastic-concepts) installed in ten repos is the same knowledge appearing ten times. A federated index that can't recognise "this is the same document" either double-counts it or returns ten near-identical hits.

The corpus already solved this — with a DOI. The corpus-identity survey faced exactly "a globally-unique id without a global coordinator" and adopted the identifier world's canonical answer: a DOI is a namespace prefix (assigned by an agency) plus a local suffix. Spectastic's prefix is the marketplace; the durable cross-repo key is marketplace · plugin · slug @ edition (the label renderCitationLabel already derives), and KB-NNNN is only the repo-local suffix. So federation of the corpus is a solved shape: key results on the marketplace coordinate, not KB-NNNN, and the same pack in ten repos dedupes for free because all ten share one coordinate. The identity survey even anticipated this in its own open questions — "one registry or many… when a repo imports from several marketplaces."

The marketplace default is federation-fragile. corpus.marketplace defaults to the repo's directory name (063) — fine for one repo, but two repos that both default to a generic dir name (or the local sentinel) collide in the namespace that is supposed to prevent collision. Federation is what turns TBD-corpus-owner-config (an owner/org-qualified, genuinely-global prefix) from a nicety into a prerequisite, and promotes 061's identity-fragmentation validate warning into a federation-integrity check.

Specs have no such prefix — that is the real gap. The corpus can be federated today with care; specs cannot, because they carry no namespace at all. The fix is the same DOI move applied to the spec side: a stable project prefix + the repo-local spec id → a federation-unique coordinate, surfaced as an MCP resource URI (spectastic://<project>/spec/042#REQ-FORMAT-004). This is not exotic: the MCP ecosystem has already converged on exactly this — the 2026-07-28 spec makes "roots become resource URIs," and aggregators uniformly namespace resources by their source to avoid conflicts when many servers sit behind one endpoint. Spectastic would be adopting the platform's own convergent pattern, not inventing one.

D-002 · Federate on qualified coordinates; weigh one project namespace vs. two

Status
Proposed
Context
Spec ids and KB-NNNN are both repo-local; a federated index keyed on them is ambiguous. The corpus already has a DOI-shaped answer (the marketplace prefix); specs have no prefix at all.
Decision
Key every federated result on a qualified coordinate — corpus on marketplace · plugin · slug @ edition (never bare KB-NNNN), specs on a new project prefix + the repo-local id — and surface both as source-namespaced MCP resource URIs. The open sub-question the follow-on spec must settle: whether that project prefix is one unified namespace (generalize corpus.marketplace / a new project field so a single coordinate qualifies both corpus and specs — one thing for an orchestrator to route to, and TBD-corpus-owner-config becomes the single load-bearing primitive) or two parallel namespaces (corpus keeps its publish-scoped marketplace, specs get an independent repo-scoped project-id — more faithful to the 062/063 split between "published pack" and "this repo"). Leaning unified — the corpus already proves the prefix works and an orchestrator wants one coordinate — but the two-systems fidelity is real and the spec should decide it deliberately.
Consequences
+ A federated estate whose every result is globally unambiguous and whose duplicated packs dedupe. + Reuses the corpus's proven DOI model and the MCP world's convergent source-prefixing. − Specs need an identity primitive they lack today (a project field in spectastic.json). − Retrofitting a prefix onto existing repo-local spec ids is a migration, and the unified-vs-parallel choice is a genuine fork, not a detail.

The payoff is an orchestrator that knows where a spec belongs. Once the estate is namespaced, provenance-carrying, and queryable as one federated index, a forward-looking possibility opens that no single-repo tool has: a top-level orchestrator for a multi-service project. Given a fresh requirement, it asks the index "which service's spec-sensitive corpus and existing specs is this closest to?" and proposes where the resulting spec(s) should live — routing a requirement to its owning service the way CODEOWNERS routes a PR to its owning team, or Backstage catalogs a service, but semantically, driven by the domain signal the corpus already holds. The namespacing above is the hard prerequisite: you cannot route to a service whose artifacts aren't distinctly addressable.

Placement is a ranked suggestion, never a silent decision. This orchestrator suggests where a spec belongs with a confidence, and a human confirms — the same human-in-the-loop posture the corpus already takes with provenance and sign-off. It is a forward-look, gated behind the namespacing work, not a slice to build now; it is here because it is the reason the namespacing is worth doing, not because it is next.

6 · PDF finally gets a home

The kernel refused a PDF converter on a single, principled ground: staying Node-only. Outside the kernel that ground is gone, and a standalone corpus tool is the natural owner of the "documents arrive as PDFs" reality that a curation product will hit constantly. The de-facto open-source converters, from the 2026 surveys:

ConverterShapeBest when
MarkItDown Microsoft · MIT Thin wrapper over format libraries; no models, no GPU; broad format tail (PDF, DOCX, PPTX, XLSX, HTML, images). pip install and go. Clean, digital PDFs you control. The fast default.
Docling IBM · MIT Layout-detection model + optional small vision model; emits a structure-preserving document, not just text. Tables, formulas, multi-column academic layouts where structure carries meaning.
Marker Datalab OCR-based (Surya), GPU / CPU / Apple-MPS; highest structural fidelity at scale. Scanned or messy PDFs, high fidelity needed, GPU budget available.

None is universally best — the choice is a speed / fidelity / hardware trade, and that variance is the design cue: the corpus tool should not marry one converter. The clean move is a corpus convert subcommand that shells out to a user-installed converter (MarkItDown default, Docling for structure, Marker for fidelity), then routes the markdown into the existing adapt/import provenance path — stamping the source PDF, the converter used, and a byte hash, exactly as 056 already records converted-origin provenance. No bundled Python, no GPU dependency, no lock-in; the converter stays the user's install, and the tool owns only orchestration and provenance.

D-003 · A corpus convert wrapper that shells out; the tool never bundles a converter

Status
Proposed
Context
PDF was descoped from the kernel only for the Node-only vow; a standalone tool doesn't carry it. Three converters own the space, none universally best — a speed/fidelity/hardware trade.
Decision
Add corpus convert <file> that invokes a user-installed converter (MarkItDown default, Docling / Marker documented alternatives) and feeds the markdown into the existing provenance-stamping adapt path. The tool owns orchestration + provenance, never the converter binary.
Consequences
+ Closes the TBD-never without a Python/GPU runtime. + Reuses 056's converted-origin provenance machinery. + Converter-agnostic, so it tracks the field instead of betting on one tool. − The converter is a documented user prerequisite, not bundled. − Conversion quality is the converter's, not the tool's — but the provenance records which converter, so a bad conversion is attributable.

7 · Packaging shape — monorepo package or its own repo

Two ways to ship the extracted corpus, with a real trade between them.

ShapeWhat it isCost / benefit
In-monorepo package recommended first A new @spectastic/corpus package beside core/cli/schema, with its own spectastic-corpus binary. Spectastic depends on it via the two seams. Least disruption; shared tooling, tests, release. Still a separate npm install for standalone users. Mirrors the @spectastic/core standalone-lib precedent. But the boundary is "polite," not enforced — nothing stops a future import from re-coupling it.
Separate repo A standalone spectastic-corpus repository, published independently; spectastic consumes it as an external dependency. Cleanest boundary, true "separate download," independent release cadence, its own issue tracker for non-SDD users. But adds cross-repo version coordination, a second CI, and a release-lockstep tax every time a shared type changes.

The measured call: start in-monorepo, defer the repo split. The extraction's value — a clean package boundary, a standalone binary, a reusable library — is captured immediately by the package move; the separate repo's extra value is mostly organizational (independent releases, a home for non-SDD users) and only pays off once there is real standalone adoption to serve. Splitting later is cheap when the boundary is already clean; un-splitting a premature repo is not. The MCP server (§4) is the exception — serving specs and running as a process, it is the piece most likely to warrant its own repo from the start, decided independently of where the library lives.

8 · Recommendation — three staged slices

Two theses anchor this: the corpus is a curation/provenance product, not a retrieval engine, and ship the library boundary before the process that fronts it. Ordered so each slice stands alone and de-risks the next.

  1. Slice 1 — extract the library. Lift packages/core/src/knowledge/ + its schema rules into @spectastic/corpus, a package with a thin spectastic-corpus CLI (the existing adapt/import/interview/source/publish verbs plus a query/get read path), and invert the two seams to depend on it — inverting means the import source flips to the extracted package; injection still reads knowledge/ on disk exactly as today. In-monorepo; graceful-absence keeps the flip low-risk. The foundation every other slice sits on.
  2. Slice 2 — PDF gets a home. Add corpus convert, shelling out to a user-installed converter and feeding the markdown into the converted-origin provenance path. Closes the TBD-never without a bundled runtime — small, self-contained, high symbolic value.
  3. Slice 3 — the MCP serving surface (the bet). A distinct component, likely its own repo, serving the corpus and a read-only view of the specs/ estate across repos as provenance-carrying MCP resources/tools — federated-identity-aware (§5): corpus keyed on the marketplace coordinate, specs on a new project prefix, so a multi-repo index doesn't collide. Highest value and scope; gated behind Slice 1 and worth its own survey first — especially the specs-over-MCP half and the unified-vs-parallel namespace choice, which may each separate into their own spec.
Do not let the MCP server pull in a vector store by the back door. The moment "serve knowledge to agents" meets "the corpus is large," the pressure to add embeddings is real — and taking it on turns this from a differentiated curation product into a weaker RAGFlow. The line to hold: spectastic-corpus produces trustworthy cited source and serves it by exact lookup; fuzzy semantic recall is a RAG pipeline's job, and the two interoperate. That boundary is the product's identity, not a gap in it.

Suggested next artifacts

  • A new spec: extract @spectastic/corpus (library + thin CLI + a query/get read path), inverting the prompt-injection and validate-gate seams to depend on it. Slice 1 — the foundation.
  • A new spec: corpus convert — a converter-agnostic shell-out wrapper (MarkItDown / Docling / Marker) feeding the existing converted-origin provenance path. Slice 2.
  • A new spec: the MCP serving surface for the corpus (query / get, provenance-carrying), multi-repo. Slice 3, corpus half.
  • The specs-over-MCP half — serving the specs/ estate (requirements, SC→test traces) to agents as cited MCP resources; may be its own spec if it separates from the corpus MCP.
  • A new spec: the federated resource-URI addressing scheme — corpus keyed on marketplace · plugin · slug @ edition, specs on a project prefix, source-namespaced MCP resource URIs. The identity substrate Slice 3 sits on (§5, D-002).
  • A stable project prefix for specs in spectastic.json — the DOI move the spec side lacks; settles the unified-vs-parallel namespace choice (generalize corpus.marketplace vs. a separate project-id).
  • Promote the corpus marketplace from a repo-dir-name default to an owner/org-qualified, globally-unique prefix — a nicety single-repo, a prerequisite once the estate is federated (raised by 063, now load-bearing).
  • A forward-look: a top-level orchestrator that routes a requirement to its owning service by the spec-sensitive corpus (semantic CODEOWNERS/Backstage), suggesting spec placement with confidence — human-confirmed, gated behind the namespacing above.
  • The separate spectastic-corpus repo split — deferred, gated on evidence of standalone (non-SDD) adoption.
  • A documented interop recipe: exporting cited corpus source into a RAG pipeline (LangChain / RAGFlow) so the curation layer feeds retrieval without owning it — recorded as the boundary, not built.

9 · Caveats on the sources

  • The landscape moves fast, and its figures are directional. The RAG-framework and PDF-converter surveys are dated 2026 and reshuffle quarterly — the durable finding is the shape of the split (retrieval vs. packaging vs. curation), not any single tool's ranking. Likewise the "targeted retrieval beats file-reads" token savings and the "16+ tools" SKILL.md tally are real but vendor/ecosystem-reported: treat them as motivation for the MCP bet, not guaranteed numbers.
  • "Extractable" is a claim about coupling, not effort. The two-seam audit is accurate, but a real extraction still carries the ordinary cost of a package split — build config, exports, test relocation, the dependency-direction flip. Low-risk is not zero-work.
  • MCP identity-federation is itself still settling. The 2026-07-28 spec reworks resource URIs and aggregators have converged on source-prefixing, but true nested federation, identity propagation, and session semantics through intermediaries are explicitly still open on the roadmap. §5's namespacing is a self-imposed discipline spectastic controls (its own coordinates), deliberately not dependent on the protocol solving federation — the right posture while the standard moves.
