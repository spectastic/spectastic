Considerations · Engineering governance

Architectural guardrails

spectastic's guarantee layer is real and deterministic — but it is pointed at whether an artifact is well-formed, not at whether a decision was honoured. That is the whole gap.

Status Draft — Phase 1, awaiting review Type Self-assessment against an external rubric Author Brian Corbin · @briancorbinxyz Created 12 Sep 2026 Rubric Theo Valmis, Architectural Guardrails for AI-Generated Code, O'Reilly (31 Aug 2026) Scope spectastic enterprise profile Read time

Assessed against the ten-item rubric under its own harsh bar (a row is "full" only against a committed passing test), spectastic scores 2 full · 5 partial · 3 does-not. The pattern is sharp and honest: the two "must-not-be" items that already carry a test pass cleanly (not AI-reviews-AI, not vendor-locked); the other two "must-not-be" items (not an agent, not RAG-as-verdict) are structurally correct but unguarded by a test on the enforcement path, so they land at partial; and it is weak on the capabilities the layer must have (a decision corpus with precedence/scope/enforcement, path-scoped retrieval, decisions injected before writing, decision-scoped CI enforcement). The reason the must-haves fail is structural: spectastic's decisions are per-design Nygard cards with an id and a grounding tag but no scope, no precedence, no supersede link, and no enforcement link — so there is nothing for a retrieval, a plan gate, or a coverage metric to operate on. Its own honesty markers already say so: the architecture prompt "provides no enforcement that the chosen pattern is followed," and the enforcing half is the deferred TBD-architecture-fitness-function. The Priya PR would pass spectastic today — at plan (the governing decision is never surfaced by path) and at merge (no decision is wired to an executable check).

A real enterprise repo confirms the texture, not a different verdict (§5): the one project that wired ArchUnit under enterprise guidance (spec-tictactoe-2) does carry a decision↔fitness-function link (D-008 ↔ NoWallClockRule) — but as a hand-repeated string across four files, with no machine guard against drift. spectastic can produce the link by authorial discipline; nothing guarantees it. And the enforced invariant there is determinism, not an architecture style — so the Priya layering/boundary case is un-demonstrated by any existing project, which makes Phase 4 load-bearing.

Two assumptions in the brief do not hold against this repo and are corrected in §6: the debugger and shifu skills it references do not exist (zero matches repo-wide), and considerations docs are single-file HTML, not markdown.

1 · The Valmis argument, and why it is a live risk for us

Valmis's scenario: an agent-authored PR (Priya's, 340 lines) adds an endpoint that writes to a table directly, bypassing the internal service API and therefore the audit-log hooks that live in that API. The code is clean, the tests pass, and a reviewer new to the team approves it. A two-year-old ADR forbade exactly this; its author had left; nobody current remembered; "the ADR was available in the repository. It was never surfaced to the agent, and the reviewer had not read it." Two weeks later the missing audit logs surface in production. He names the failure architectural drift — "code that individually looks fine but collectively pulls the codebase away from where the team agreed it should go" — and the missing discipline engineering governance.

His two load-bearing claims. First, instruction files like CLAUDE.md are "the right instinct at the wrong resolution" — free text with no precedence, no versioning, no lifecycle, no enforcement; "documents in the shape of configuration." Second, a second LLM reviewing the PR cannot fix this, because it has the same blind spot as the first: "two probabilistic passes over the same blind spot are not one deterministic pass with sight." The governance layer he prescribes must hold decisions with precedence and lifecycle, retrieve them reliably, inject them before generation, and enforce them deterministically in CI — and it must not be an agent, not RAG-as-verdict, not AI-reviews-AI, and not vendor-locked.

Why this is our risk, not a theoretical one. spectastic is an agent system: its verbs are skills a model runs, and we have just spent a week proving (spec 111, the cross-tool spike) that a skill is advisory — a weaker model under "Big Pickle" ticked a task over untested dead code and only wrote tests when a human nudged it. Rubric item 5 ("not an agent") is therefore a live constraint for us specifically: the moment enforcement is something a model does rather than a script that runs, it inherits exactly the non-determinism 111 documented. Our own principle P-8 ("guarantees live in the kernel or CI") is the same claim Valmis makes; the question this document answers is whether we have actually carried it into architectural governance, or only into artifact well-formedness.

2 · How spectastic models governance today

Three surfaces matter, so the scoring below has a shared referent.

The constitution
principles.html — versioned SemVer with a bump policy (principles.html:280) and forward-only binding (:301+). Two principles touch architecture: P-8 · Guarantees live in the kernel or CI (:108) and P-14 · Library-first boundaries (:231) — the latter self-declaring that its kernel-vs-CLI boundary is "a judgment call" it "cannot yet" machine-enforce.
The decision card
<spec-decision> in a spec's design.html (templates/design.html:273-298) — a Nygard/MADR card: stable D-NNN id, a free-text status pill, a grounding= tag, prose Context/Decision/Consequences. There is no repo-level ADR corpus; decisions live inside one spec's design.
The guarantee layer
spectastic validate (packages/core/src/commands/validate.ts) folded into a git pre-commit hook (packages/cli/src/commands/init/hook.ts:57) and CI (.github/workflows/ci.yml:105) — a deterministic, no-LLM scan that emits typed Findings. Plus spectastic enforce (packages/core/src/enforce/), a per-profile tooling-coverage gate.

Per-row evidence

1 · Structured decision corpus — partial

Present: a stable D-NNN id (templates/design.html:276; uniqueness enforced, packages/schema/src/rules/no-duplicate-ids.ts:33) and a grounding= tag (verified|spike|assumed|n-a, design.html:280). A status pill can read superseded, and the command tells authors to "link to the replacement" (commands/spectastic.design.md:108).

Absent — and this is the row: the status and supersede are convention, not structure — no schema rule enumerates decision status or requires a supersede link (searched all of packages/schema/src/rules/; the only enumerated status sets are for risks and components). There is no precedence (which decision wins when two conflict — the only "precedence" in the repo is spec/unit ordering, packages/core/src/ordering/, unrelated), no scope (no path-glob or package pattern a decision governs — scope= exists only on <spec-component>), and no enforcement link (nothing ties a decision to a rule id). A tool cannot answer "which decision governs this file" or "which active decisions conflict" from the structure. It is a decision log, not a governance corpus.

2 · Reliable retrieval — does not

No command or function takes a set of file paths and returns the governing decisions. The nearest machinery is spectastic order (packages/core/src/commands/order.ts) — a precedence DAG over spec ids, not decisions, not by code path — and unit placement (packages/core/src/units/placement.ts), which self-describes as "a judgment a human can check — never a decision" (placement.ts:5). There is nothing deterministic, path-scoped, and logged to retrieve. This is the first half of what lets the Priya PR through.

3 · Context injection before writing — does not

The mechanism exists: the knowledge corpus injects domain facts into the AI verbs' prompts (054-corpus-in-prompt), and the design's grounding step reads sources the author names. But no path-scoped decisions reach the agent before it writes code — the corpus carries settlement windows and regulatory thresholds, not "the ADRs governing the file you are about to touch." The channel Valmis requires is empty of the payload he requires. Partial mechanism, absent content — scored to the requirement, which is that the relevant decisions arrive before generation.

4 · Deterministic CI enforcement — partial

The half that is excellent: the verdict path has no model on it. The pre-commit hook is literally exec node <cli> validate <globs> (hook.ts:57); validate.ts imports only static schema/policy maps (no fetch/provider/model — grounding pass confirmed); CI runs the same binary (ci.yml:107) with no LLM step. A Finding reconstructs entirely from disk — file, line, column, rule, severity, message, fixHint (packages/schema/src/types.ts:26-38). This fully satisfies items 5 and 6.

The half that is absent: what it enforces is artifact schema — is this spec.html well-formed — not architectural decisions. A finding is keyed to a rule id (types.ts:31), never to a decision id, and carries no decision reason and no typed source→target. And the check that would hold a design to its declared architecture is the deferred TBD-architecture-fitness-function; the prompt that exists says so itself — REQ-LIFECYCLE-008 (specs/089-lifecycle-contract/spec.html:266): "This prompt is advisory … and provides no enforcement that the chosen pattern is followed." The machine is right; it is aimed at the wrong target. This is the second half of what lets the Priya PR through.

5 · Not an agent — partial

Structurally correct: the enforcement path runs when called, produces a verdict (an exit code + typed findings), and stops. The pre-commit hook is literally exec node <cli> validate <globs> (hook.ts:57); CI runs the same binary (ci.yml:107). Nothing iterative, nothing to argue with.

Why not full, under the brief's own bar: no committed test guards the enforcement verdict path against a model ever appearing on it. The discipline is testable and tested elsewhere — render.egress.test.ts and brief-generation.no-network.test.ts assert no-network on sibling paths — but not on validate/enforce. The brief's Phase 3 asks to add exactly this test ("the enforcement entry point has no network access and no model client import"), which is itself the tell that it does not exist yet. True today, unguarded against regression: partial.

6 · Not RAG-as-verdict — partial

The verdict is a deterministic scan; no probabilistic retrieval sits in it. This is vacuously clean — there is no decision-RAG at all (items 2/3) — so while the discipline would hold if retrieval were added per the design brief, there is nothing to point a committed test at today. Structurally sound, untested-because-absent: partial.

7 · Not AI-reviews-AI — full, and a genuine strength

spectastic already draws the line Valmis draws, and a committed test proves it. The adversarial critic (agents/spectastic-critic.md) finds risks but is forbidden from deciding: "You do not disposition risks — leave every finding at status="identified"; the human commits the status" (critic.md:34-35). The verdict is the deterministic kernel, which refuses to proceed while a critic-raised risk is unresolved — asserted by a passing test, packages/core/test/apply.principles.test.ts:116 ("refuses when a risk is still identified"). Probabilistic recommends; deterministic decides. The direct answer to "two probabilistic passes are not one deterministic pass with sight."

8 · Not vendor-locked — full

The deterministic gate is a plain Node CLI (node packages/cli/bin/spectastic …) that runs under any tool or none. The verbs ship as portable Agent-Skills (packages/cli/_bundled/.agents/skills/, spec 111), with committed passing tests on the vendor-neutral output — the render/translation primitive (packages/core/test/skills-translate.test.ts) and the scaffold/profile inventory (packages/cli/test/init/default-scaffold.test.ts, profiles.test.ts) — and this month the same skills ran unmodified across Codex, Antigravity and opencode. init emits a lean vendor-neutral AGENTS.md (compose.ts:133). Caveat: the per-vendor hook adapters that feed gate output back into the agent loop (the brief's item) are not built; that capability inherits item 3's gap, but the enforcement itself already runs everywhere.

9 · Enforcement coverage is visible — does not

spectastic enforce reports coverage over a fixed tooling-category enum — formatter, linter, type-checker, security, supply-chain, test-runner, coverage, observability, contract-first (packages/core/src/enforce/types.ts:9-18) — detected by file signals. There is no per-decision coverage: nothing measures "% of active decisions that carry an executable check," because no decision carries an enforcement link to count (item 1). The metric the brief asks for has no operand.

10 · A failure teaches — partial

A finding is already actionable by a reviewer who has read nothing: it carries the rule id, a human message, an optional fixHint, and file:line (types.ts:26-38). What it does not carry is the decision — no ADR id, no ADR's stated reason, no typed source→target — so a failure teaches "this rule fired," not "this decision, made for this reason, forbids this call." And the shifu Socratic layer the brief assumes does not exist (§6). Partial: the teaching is generic, not decision-anchored, and the tool that would make it Socratic is absent.

What the dogfood shows, and the design trap to avoid. The one repo that teaches on failure (spec-tictactoe-2, §5) does it the wrong way for a tool to generalise: the decision id and reason are hand-typed into ArchUnit's .because("P-10 / D-008: production code must be deterministic…") string — the enforcer's own message channel. That does not travel. AspectJ has no .because(); Semgrep has a different message: channel; a DB GRANT denial has none; a custom checker has whatever it invents — and in every case the reason is a second copy of the decision's reason, free to drift. The agnostic answer is to split detector from explainer: the enforcer emits only {rule-id, file:line, [source→target]} (a floor any tool can meet), and spectastic composes the teaching by joining rule-id → decision-id → the decision's own recorded reason — the reason living once, in the decision, never re-typed into the tool. This is what the brief's item 4 already implies ("the verdict must reconstruct … from the code, the ADR, the … rule text"): reason from the ADR, location from the rule, the verdict a composition no tool authored. shifu's question is templated the same way — from the decision's rule statement, not the enforcer. Design consequence carried to §7.

4 · Gaps, ordered by risk to the Priya scenario

The ordering answers one question: which gap would have let the Priya PR through? The honest answer is that two of them would, independently — which is why the PR is a double failure in spectastic today, at plan and again at merge.

  1. G1 — No decisions surface by path at plan time (items 2 + 3, and gate D). The governing decision is never retrieved for the touched path, and no plan gate fails when a plan ignores an in-scope decision. Priya's plan is grounded, well-formed, and silent about the one ADR that matters — and passes. This is where the PR must die in the happy path, and today it does not.
  2. G2 — No decision is wired to an executable check at merge (item 4). Even bypassing spec and plan entirely — committing PositionReconciliationJob with a direct UPDATE positions — nothing catches it: no ADR carries a rule id, the architecture-fitness check is deferred, and validate is keyed to schema rules, not decisions. The merge gate has no verdict to give here.
  3. G3 — Decisions carry no scope, precedence, or enforcement link (item 1). The structural precondition for G1 and G2. Even if retrieval were built tomorrow, decisions expose no scope to retrieve by, no precedence to sort by, and no check to enforce. Everything downstream rests on fixing the corpus shape first.
  4. G4 — The blind spot is invisible (item 9). Nobody can see that the ADR governing positions has no executable check, because coverage is measured over tooling, not decisions. The gap that sank Priya is itself un-surfaced.
  5. G5 — A caught failure would not name the decision (item 10). The least-bad gap: if G1/G2 were fixed but G5 were not, the reviewer would see "rule X failed" without "ADR-0007, for this reason." Still an improvement, but not the teaching the scenario needs.

The one-sentence diagnosis. spectastic built a real, deterministic, vendor-neutral guarantee layer and pointed it at artifact well-formedness; the Valmis rubric asks for the same layer pointed at architectural decisions, and the pointing is the work.

5 · Dogfood evidence — what the enterprise profile actually produced

The sections above score the meta-spec's capabilities. This one checks them against a real downstream project spectastic's enterprise profile guided: ~/Code/spec-tictactoe-2 (profile enterprise, .spectastic/profile.json), which introduced ArchUnit — a JVM architecture-fitness-test library — under that guidance. It is the single best available evidence for items 1, 4, 9 and 10 in practice. (The older ~/Code/spec-tictactoe is not a second data point: no profile file, no ArchUnit, no CI — it predates the profile mechanism and runs the old plan.html verb set.)

The finding cuts both ways, and the honest version is more interesting than either extreme.

What is genuinely there — a real, bidirectional decision ↔ fitness-function link

The enterprise profile did not leave ArchUnit floating. The rule cites its decision and the decision describes the rule, both directions, reinforced by a spec requirement and a task:

  • The decision names its enforcement — specs/001-human-vs-cpu/plan.html:318-326, <spec-decision id="D-008">: "No wall-clock or unseeded random in production code (enforced by a small custom ArchUnit rule that fails the test suite on Instant.now(), currentTimeMillis(), Math.random(), or new Random() without a seed)."
  • The rule cites its decision — src/test/java/.../invariant/NoWallClockRule.java:9-11 Javadoc: "Encodes plan D-008 (and, upstream, principle P-10 and spec 001 NFR-002)," and the rule's own .because("P-10 / D-008: production code must be deterministic; …") (:34-50).
  • It is genuinely gated — the @ArchTest runs under test→check (build.gradle.kts:49), and CI runs ./gradlew --no-daemon check on every PR to main (.github/workflows/ci.yml:42). A violation blocks merge, deterministically, with no model on the path.
  • It reached the spec layer — an applied change proposal added NFR-005 (spec.html:165-167): the build "MUST enforce the determinism invariant … via a static-analysis rule … MUST block merge with no allowlist entries," and modified NFR-002 to read "Enforcement is by NFR-005's static-analysis rule."

That is a better showing than the generic scoring implies: a disciplined author, prompted by the enterprise profile, produced exactly the decision→check→CI chain the rubric wants — and the failure would even teach (item 10), because the decision id and reason are hand-written into the .because() clause that ArchUnit prints on failure.

What confirms the gap — the link is prose, not structure

Every part of that chain is a human-maintained convention, not a machine-guaranteed one, which is the precise distinction this whole assessment turns on:

  • No machine-readable link. The tie between D-008 and NoWallClockRule is the string "D-008" repeated by hand across four files (plan, Javadoc, .because(), NFR prose). Nothing parses it. There is no enforcement= attribute, no shared rule id, no registry. Delete D-008 from the plan and the Javadoc reference dangles silently; rename the rule and the decision's prose is quietly wrong. Neither drift is caught — the same failure mode Valmis names in CLAUDE.md, one level up, in <spec-decision> prose instead. (Confirms items 1 and 4 at partial.)
  • No scope on the decision. D-008 carries no path glob or package pattern; the only scope (packages = "co.briancorbin.tictactoe2") lives in the test's @AnalyzeClasses, disconnected from the decision. Nothing can retrieve "which decision governs this path." (Confirms item 2 at does not.)
  • No coverage metric. Nothing reports that D-008 has a check while other decisions do not — the one decision with enforcement is uncounted. (Confirms item 9 at does not.)

The finding that reshapes Phase 4

The enforced invariant in the only enterprise repo is determinism (no wall-clock / no unseeded PRNG), not an architecture style. Neither repo contains a layeredArchitecture(), onionArchitecture(), or ports-and-adapters boundary rule. So the Priya scenario's exact shape — "only the persistence adapter touches data-access APIs," a layering/boundary fitness function wired to a decision — is un-demonstrated by any existing spectastic project. Phase 4's position-keeper would be the first time spectastic produces a boundary guardrail, not a reproduction of an existing pattern. This makes Phase 4 genuinely load-bearing evidence rather than a dressed-up regression fixture — and it reinforces §6's correction that the debugger/shifu/grading-fixture machinery is net-new.

Net effect on the scores: the dogfood does not move any verdict, but it changes their texture. Items 1, 4 and 10 are "partial" not because spectastic cannot produce the link — a real repo shows it can, by authorial discipline — but because nothing guarantees it: the link is exactly as durable as a reviewer remembering to keep four copies of a string in sync. That is the cleanest possible statement of the work Phases 2–3 must do: promote the existing prose convention to a structured, drift-guarded, machine-retrievable one, without losing the disciplined authorship that already works.

6 · Two assumptions in the brief that do not hold

Per the brief's own instruction to say so where an assumption is wrong rather than force the fit:

The debugger and shifu skills do not exist in this repo. A whole-repo search (.claude/, agents/, commands/, packages/, docs/, templates/, the empty skills/) for shifu, socratic, fixture-and-grading, or any grading/eval-fixture skill returns zero matches. Rubric item 10's "shifu Socratic follow-up" and Phase 4's "same fixture-and-grading pattern as the debugger skill" therefore rest on capabilities that would have to be built, not assessed. This does not change the item-10 score (partial for independent reasons), but it materially changes Phases 2–4: the teaching-on-failure and grading-fixture work is net-new, not an extension of an existing pattern.

 Considerations documents in this repo are single-file HTML (docs/*-considerations.html); there is no docs/considerations/ or docs/design/ directory. This document is written as HTML to match that convention rather than the brief's docs/considerations/architectural-guardrails.md — trivially convertible if markdown is wanted, but flagged as a deliberate deviation.

7 · Open questions for a human to decide

These cannot be answered from the code; they are the decisions that shape Phase 2.

  1. Repo-level ADRs, or per-spec decision cards? The rubric (and the reference repo's docs/adr/0007) assume a repo-level ADR corpus. spectastic's decisions live inside one spec's design.html. The load-bearing Phase-2 fork: extend <spec-decision> with scope/enforcement and build a cross-spec decision index over the existing cards, or introduce a new first-class repo-level ADR artifact. The first reuses the estate; the second matches the rubric's mental model. This choice governs everything else.
  2. How is scope expressed? Path globs, package patterns, or both? (A hexagonal rule like "only the persistence adapter touches data-access APIs" is naturally package/type-shaped; a "no writes to positions" rule is naturally path/SQL-shaped. The reference needs both.)
  3. Where does the enforcement link live, and where does the teaching reason live? (near-decided) The dogfood (§5) and the .because() trap (item 10) point hard at one answer, so this is recorded as a leaning rather than an open fork. The decision should carry a structured enforcement: list of {tool, rule-id} pairs (so rule-id → decision-id is a machine join, not a string match on "D-008"), and the decision's reason is a field on the decision, composed into the failure message by spectastic — never re-typed into the enforcer's own channel (.because(), Semgrep message:, etc.), which duplicates and drifts. The enforcer is a detector that emits {rule-id, file:line, [source→target]}; spectastic is the explainer. The one genuinely open sub-question: how rich a source → target we require, given it is clean from ArchUnit, config-derived from a DB grant, and line-level from a grep — i.e. is it a guaranteed field or best-effort per enforcer? (Leaning best-effort, with {rule-id, decision-id, reason, file:line} as the guaranteed floor.)
  4. Warn or block, and where is the default? Per-decision posture, per-profile default (enterprise = block?), or both? spectastic's precedent (the enforce floor, waivers) suggests block-at-enterprise with a justified, expiring waiver — but that is a decision, not a given.
  5. How are cross-repo decisions distributed? Reuse the corpus/marketplace machinery (specs 062/063, which already carry provenance and a per-marketplace identity), or a separate mechanism? A decision that governs three repos has no owning coordinate today.
  6. Do we build the teaching layer (shifu) and the grading-fixture harness at all? Phase 4 depends on both, and neither exists. Are they in scope for this effort, deferred, or rescoped?
  7. Doc format: honour the brief's .md paths, or the repo's .html convention (as used here)?
