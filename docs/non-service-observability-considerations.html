Considerations · Observability beyond services

A library has no endpoint

The trace asks every project which objective covers this requirement, and scores the silence as a gap. For a command-line tool that will never serve traffic, the silence is the correct answer — and it has been rendered as a failure seventy-seven times.

Status Draft Type Artifact critique & landscape survey Author Brian Corbin · @briancorbinxyz Created 02 Aug 2026 Companion observability-slo · verify-view-actionable Sources 8 external, retrieved 02 Aug 2026 · full audit of 61 verify views Read time

The observables trace is empty, and the reason is not that nobody has got round to filling it. An audit of all 61 verify views finds 37 carry an observables section, every row in all 37 is a gap, 77 gap rows in total, and not one <spec-slo> has ever been authored anywhere in the estate — 24 exist in fixtures, so the feature demonstrably works. The mechanism is doing exactly what it was built to do: a row is a loud gap when the requirement "reads as a measurable target", which is a property of the requirement's prose. Nothing anywhere asks whether the project is the kind of thing that could have a service level objective at all. A command-line tool with "completes in under two seconds" is a quantified requirement, earns a loud gap, and has no objective to link because it serves no traffic, exposes no endpoint and has no steady state to be reliable in. Three separate mechanisms make the same silent assumption — the gap condition, the capture field typed as "the metrics endpoint that was checked, e.g. GET /metrics", and the observability enforcement category that looks for an exporter in the manifest — and the profile system has six axes and not one of them is project shape. Every axis ladders rigor; none says what kind of thing this is. On the remedy, the instinct to reach for a metrics gateway is the one to resist: Prometheus's own documentation calls the Pushgateway "explicitly not an aggregator" but "a metrics cache", recommends it only for capturing the outcome of a service-level batch job, and warns that its metrics persist until manually deleted. What a library actually wants already exists and needs no infrastructure — the in-memory metrics exporter is a Stable part of the OpenTelemetry specification, whose stated purpose is "useful for e.g. unit tests", and it ships in the JavaScript SDK today as InMemoryMetricExporter. Recommendation: name the shape, let the gap key on it, and make the observable evidence for a non-service project an assertion in a test rather than an endpoint nobody will ever curl.

1 · The ask — a trace with nothing in it

The observability survey made the requirement → objective → indicator → instrumentation chain first-class, and its fourth and final move (048) gave that chain a rendered trace in the verify view so a reliability requirement acquires a proof leg the way a success criterion already had one. Both landed, both are tested, and both work.

What they produce, on this project, is a table of blanks. The complaint that prompted this survey put it plainly: the observables trace is barebones for projects that are not services, and an enterprise-tier project ought to have some way to collect metrics — "even if it's just in test". The instinct is right. The diagnosis this survey lands on is that the emptiness is not a data-entry problem to be solved by collecting metrics, but a category error to be solved by asking a different question.

A hundred-per-cent gap rate across 37 artifacts is not a backlog. It is a signal that the question is wrong for the population being asked. And the population is not unusual: this project is a set of libraries and a command-line tool, which is what a great many downstream projects will also be.

The distinction matters for how the finding is read. If one or two views had gaps, the gaps would be doing their job — naming real, fixable omissions. At 37 of 37 with zero counter-examples, the row has stopped carrying information and become chrome, in exactly the way the companion survey found the always-none toggle row had.

3 · The missing axis — rigor is laddered, shape is not

The profile system is the estate's vocabulary for "what kind of project is this". It carries six axes — verification, enforcement, toggles, grounding, frameworks and contracts — and each of them ladders how rigorous a project intends to be. Not one of them says what the project is.

That absence is invisible until a mechanism needs it, and then it is invisible in a specific way: the mechanism does not fail, it quietly picks a default. Every observability mechanism in the estate has defaulted to "service", because a service is what the observability literature is about and what the survey that motivated the work had in view.

Status Proposed

Context spectastic-profiles.json defines six axes, all of which express rigor. No field anywhere in the profile marker, the config, or the enforcement policy distinguishes a long-running service from a batch job from a library or command-line tool. The STRUCTURALLY_UNDETECTABLE map in packages/core/src/enforce/policy.ts already establishes the precedent that a category can be inapplicable — but it keys on ecosystem (observability: ['swift','cpp']), which is the wrong axis for this problem.

Decision Introduce project shape as a first-class, declared property — at minimum distinguishing a long-running service, a short-lived or scheduled job, and a library or command-line tool. Declared, not inferred: the same argument the interface-detection work settled, that dependency presence cannot tell a producer from a consumer, applies here with more force, since a web framework in a manifest may be a test fixture, an example, or a documentation site.

Consequences
+ Gives three already-shipped mechanisms a correct answer instead of a silent default, without changing what any of them do for services.
+ Reusable well beyond observability — the enforcement floor, the principles catalogue and the stack interview all currently reason about rigor when some of their questions are really about shape.
− A seventh axis is real surface area, and an axis nothing reads is worse than no axis; it must land with at least one consumer.
− Shape is not always singular: a repository may hold a service and the client library for it, which is an argument for declaring shape per unit rather than per project and is not resolved here.

4 · Where the assumption is written down

Three mechanisms encode "this project is a service", none of them deliberately.

The gap condition. A row is a loud gap when the requirement "reads as a measurable target" — evaluated by a shared heuristic against the requirement's own prose or its light annotation. That heuristic was built for a different and correct purpose: deciding whether a requirement is quantified. Reused here, it answers "does this look like a reliability target" with a judgment about sentence structure, and a command-line tool's latency budget passes it. The quiet case exists — a non-reliability requirement renders plainly — but the discriminator is the prose, never the project.

The capture field. The instrumentation evidence is typed as a metrics endpoint, documented as "the metrics endpoint that was checked, e.g. GET /metrics", alongside the golden signals observed there. For a library this field has no honest value. The format's own escape hatch — mark the capture unverified and it renders "suggested — not yet run" — is the wrong shape too: the endpoint was not unverified, it does not exist.

The enforcement category. The observability category detects a metrics registry or exporter dependency by its deliberate export name, and sits in the verified and enterprise floor. Its recorded ceiling is already that a declared exporter is not a live endpoint. For a library the ceiling is worse than recorded: a library that adds a Prometheus exporter to its dependencies to satisfy the floor has made itself worse, by forcing an exporter choice on every downstream consumer — the opposite of what the category wants.

Status Proposed

Context The gap keys on isQuantifiedTarget, a prose heuristic; 77 loud gaps have been produced against zero authorable objectives. The format already distinguishes quiet gaps for non-reliability requirements, so a second discriminator is a widening of existing behaviour rather than a new concept.

Decision Key the loud gap on shape as well as prose. A quantified reliability requirement in a service keeps its loud gap, unchanged. The same requirement in a declared library or command-line tool renders plainly — not as a gap, and not hidden either, since the requirement still appears in the trace with its target.

Consequences
+ Removes 77 rows of noise without weakening a single check that applies, and restores the gap's meaning as a real omission.
+ Costs nothing for projects that declare no shape, which can keep today's behaviour as the conservative default.
− A project could evade a legitimate gap by mis-declaring its shape; this is a real hole and the honest answer is that a declared shape is checkable by review, not by machine.
− If the default for an undeclared project stays "service", every existing project keeps its 77 rows until it declares — which argues for the declaration being part of the profile marker rather than opt-in.

5 · Three shapes, three mechanisms — and only one is built

The observability field does not have one answer to "how do metrics get out"; it has three, chosen by how long the process lives.

ShapeHow metrics leaveWhat the evidence is
Long-running serviceScraped from an endpoint the process exposesA real request to /metrics showing the expected signals — what the format assumes today.
Short-lived or scheduled jobPushed on completion, since nothing is alive to scrapeA push destination and the job's outcome metric. This is the one case a gateway is for.
Library or command-line toolIt does not export at all — it records, and the embedding application exportsA test asserting the instrument was recorded with the expected value and attributes.

The third row is the one this project and most downstream libraries occupy, and it is the one with no representation in the format. It is also, usefully, the row with the least infrastructure: a library's observability obligation is to emit correctly, and whether anything is collecting is the application's problem, not the library's. That obligation is verifiable in a unit test, offline, with no running backend.

The tooling for exactly this is mature and specified. The OpenTelemetry specification defines an in-memory metrics exporter — "a Push Metric Exporter which accumulates metrics data in the local memory and allows to inspect it (useful for e.g. unit tests)" — and marks it Stable. It ships across the major SDKs, and in this project's own ecosystem it is present today: @opentelemetry/sdk-metrics@2.10.0 exports InMemoryMetricExporter. Java and Python expose the same capability as a reader rather than an exporter, a surface difference that does not change the shape of the answer.

6 · Not a gateway — what the push path is actually for

A metrics gateway is the obvious reach for "we have no endpoint to scrape", and it is the wrong tool for two of the three shapes. Prometheus's own documentation is unusually direct about this. The Pushgateway is "explicitly not an aggregator or distributed counter but rather a metrics cache"; it is not "capable of turning Prometheus into a push-based monitoring system"; and it is recommended only in limited cases, "specifically for capturing the outcome of a service-level batch job."

The operational caveats are as pointed. Metrics persist in the gateway after the pushing process is renamed or removed, because the cache's lifecycle is decoupled from the process's — stale series must be deleted by hand or by automation somebody writes. And because availability is deduced from a scrape succeeding, the gateway has an up metric for itself but not for anything behind it, so a job that silently stops running looks exactly like a job that is fine.

None of that disqualifies it for the second row of the table above, which is precisely the case it was built for. It disqualifies it as a general answer for "not a service", and it makes an OpenTelemetry Collector — a genuine deployable component with its own configuration, lifecycle and failure modes — a heavier answer still for a library whose real obligation is a unit test.

Status Proposed

Context The ask was for a metrics gateway or collector so that non-service projects have a mode for collecting metrics, at minimum in test. Prometheus restricts the Pushgateway to service-level batch jobs and documents permanent staleness and lost availability signal; OpenTelemetry specifies a stable in-memory exporter whose stated purpose is unit tests.

Decision For libraries and command-line tools, recommend the in-memory exporter asserted in a test — no gateway, no collector, no running backend. Keep the push path in the vocabulary for the job shape, where it is correct, and carry Prometheus's caveats with it rather than recommending it bare.

Consequences
+ Delivers the "even if it's just in test" ask with a stable, specified mechanism that already exists in this ecosystem — no new infrastructure and no new dependency for consumers, since the exporter belongs in development dependencies.
+ A test asserting an instrument was recorded is stronger evidence than the enforcement category's current signal, which is only that an exporter appears in a manifest.
− An in-memory assertion proves the library emits, never that anything downstream collects; the honest claim is narrower than "this project has observability".
− Three shapes with three mechanisms is more to explain than one rule, and the boundary is genuinely blurred for a long-running command-line process such as a watcher or a daemon.

7 · Recommendation — three slices, in order

  1. Name the shape. A declared project shape distinguishing service, job, and library or command-line tool — written at initialisation, asked in the design interview when detection is ambiguous, and never inferred from a dependency. Land it with its first consumer attached, so it is not an axis nothing reads.
  2. Let the gap key on it. Widen the loud-gap condition so a quantified reliability requirement in a declared library or command-line tool renders plainly rather than as an omission. Seventy-seven rows of noise disappear and the remaining gaps mean something again. Small, and worth doing on its own even if the third slice never lands.
  3. Give non-service evidence a home. Generalise the instrumentation capture so its evidence can be a test that asserts on recorded instruments rather than a request to an endpoint — and reconsider what the enforcement category should require of a library, where an exporter in the manifest is not merely weak evidence but an active harm to consumers.
Do not close this by authoring objectives. The obvious way to make 77 gaps disappear is to write service level objectives for the requirements that have none. For a library that would mean inventing a steady state, a window and an error budget for something with no traffic, no availability and no operator — ceremony that would satisfy the trace and inform nobody, and would make the estate's first 77 objectives all fiction. The gap is right that something is missing; it is wrong about what.

Suggested next artifacts

  • A new spec: project shape as a declared property — its vocabulary, where it is written, how the design interview asks for it, and the explicit refusal to infer it from dependencies (D-001).
  • A /spectastic.propose against 048: key the loud gap on shape as well as on the quantified-prose heuristic, with today's behaviour retained for any project that declares nothing (D-002).
  • A new spec: instrumentation evidence that is a test rather than an endpoint — the capture shape, its rendering, and the recorded ceiling that emitting correctly is not the same as being collected (D-003).
  • A /spectastic.propose against 042: what the observability category should require of a library, where a manifest exporter dependency is a cost imposed on consumers rather than evidence of instrumentation.
  • A follow-on question, deliberately unresolved here: whether shape belongs to the project or to the unit, since a repository may hold both a service and its client library — which the unit-edge work has now given a vocabulary for.

8 · Caveats on the sources and the audit

  • The audit is one estate. Sixty-one views, one project, and a project that is a CLI and a set of libraries — precisely the shape that produces a 100% gap rate. A service-heavy estate would show the mechanism working, and this survey would not exist. The finding is that the format has no answer for one shape, not that its answer for services is wrong.
  • One earlier note in this session was wrong and is corrected here. I had recorded that Node lacked a built-in in-memory metrics exporter. It does not: InMemoryMetricExporter is exported from @opentelemetry/sdk-metrics@2.10.0, verified by unpacking the published package and reading its declarations. The recommendation rests on that being present, so it was checked rather than recalled.
  • "Zero authored objectives" is a scoped claim. It counts <spec-slo target=…> elements under specs/, examples/ and templates/. Twenty-four exist in package fixtures and tests, which is why the feature is known to work; a reader re-running the scan across the whole repository will find those.
  • The Prometheus caveats are the project's own documentation, not independent evaluation. They are strong evidence about intended use and weak evidence about how the Pushgateway performs in practice, where many teams use it well outside the documented recommendation.
  • Shape is proposed, not designed. Three values are named because three mechanisms need them; whether that is the right granularity, and whether shape is a profile axis or a separate field, are open. The per-unit question in particular is raised and left open rather than answered.
  • No downstream project was consulted. The claim that many downstream projects will be libraries and command-line tools is an inference from what the tool is for, not a measurement of adoption.
