The guardrail across a repo boundary

The merge verdict catches Priya's bypass in one repo. Split the estate into services, each with its own specs and corpus, and ask the harder question — not "is this write allowed here?" but "does this change even belong in this repo?"

Status Draft — awaiting review Type Web-backed architecture survey; lands recommendations + TBDs Author Brian Corbin · @briancorbinxyz Created 13 Sep 2026 Follows Architectural guardrails (the single-repo layer, specs 112–118) Read time

Take the position-keeper example — where the merge verdict kills Priya's direct UPDATE positions at plan and merge — and make it a multi-repo microservice estate, each service its own repo with its own specs/ and knowledge corpus. Two questions were hiding inside one. The verdict question ("is this write allowed here?") is repo-local by construction: retrieval reads only join(cwd, 'specs')/*/design.html, and a decision's scope is a repo-relative path glob that cannot name a file — or a table — in another checkout. So a decision authored in the position-keeper repo is invisible to a verdict run in Priya's repo. Closing that needs three things landing together, of which the deferred TBD-guardrail-decision-index is only one; the missing primitive is a decision scope that names a federation-unique resource, not a path.

But the sharper case dissolves the first one. Database-per-service saves you from the wrong thing. Per-service grants stop Priya reaching into the position store — yet nothing stops her rebuilding its responsibility inside her own service, simply because that is the repo her team knows. That is not a boundary bypass a grant or a federated rule could catch; it is a boundary duplication — right change, wrong service — and it is invisible to every mechanical check. It is Conway's Law operating exactly as predicted: the change lands where the communication structure points, not where it belongs. Now two services own position-like data and will silently diverge — the settlement-consistency failure KB-0001 warns about, promoted to cross-service scale.

This is the placement question, and spectastic already decided it is review-caught, not machine-enforceable (P-14) — which the industry corroborates without exception (Conway; Team Topologies): ownership is a social fact, and tooling can only enforce a boundary after a human declares it as data. The wrong-service misplacement is caught only if all four legs hold — ownership declared as data, the estate federated, the check run at design time, a human confirming the hedge — and Conway predicts the one reviewer who knows the store belongs elsewhere is not on the misplacing repo's PR. Net: keep the guardrail honestly repo-local and say so; the real cross-service seam is the contract, not the code; and the wrong-service case is a design-time, human-confirmed suggestion, never a merge gate — exactly the posture the placement survey already lands.

1 · Two failures were hiding in one question

"Does spectastic make the correct decisions around where database changes should land?" reads as one question and is two. They fail by different mechanisms, at different lifecycle stages, and one of them is not spectastic's to solve.

The rest of this survey takes them in turn, then shows why the microservice split makes the second the dominant one.

2 · The verdict half — repo-local by construction

The guardrail layer (specs 112–118) is deterministic and honest, and it is strictly single-checkout. Three facts from the code, not speculation:

  • Retrieval reads only the current repo. loadDecisions walks join(ctx.cwd, 'specs') and parses <spec-decision> out of each local design.html (packages/core/src/commands/adrs.ts). There is no fetch, no clone, no path that traverses to another checkout.
  • Scope is a repo-relative path glob. D-007's scope src/**/persistence/** is anchored ^…$ against a normalised relative path (packages/core/src/guardrail/glob.ts). The grammar admits only **, *, ? — no host, no authority, no ../. A path glob cannot name a file in another repository, still less a table.
  • The coordinate is addressable but never dereferenced. spectastic://<owner>/<project>/decision/<spec>/<D-NNN> is federation-unique (067), but every use of it is display or prompt injection — the retrieval log, the --explain output. parseResourceUri states outright that resolving a coordinate to a local artifact is "a deliberately separate operation … no dereference of any kind." It is a string, not a pointer.

So a decision authored in the position-keeper repo is invisible to a verdict run in Priya's repo. The exact class the single-repo demo was built to catch passes silently across the boundary.

What it would actually take — three legs, not one

The obvious candidate is the deferred TBD-guardrail-decision-index (spec 113's out-of-scope: "reading from a decision registry rather than design.html … a later distribution concern"). It is necessary but not sufficient. Cross-repo enforcement needs all three of:

  • Distribution — the decision index itself, so repo B can read repo A's decisions rather than only its own design.html. (the named TBD)
  • A data-resource scope — a decision must govern a federation-unique resource (the positions store on a spectastic:// coordinate), because a repo-relative path glob is meaningless in another tree. This primitive does not exist and is not specced.
  • Reach + trust — repo B must know to load repo A's decisions (a declared consumes/unit edge, 079/080 — and by the settled rule, declaration outranks inference, because the same table name appears in owner and non-owner alike) and be able to (082 is single-checkout; cross-repo reading needs the federated read surface in spectastic-mcp).

Miss any leg and the verdict still sees nothing. The decision-index alone buys a channel with nothing addressable to carry.

3 · The reframe — database-per-service saves you from the wrong thing

Before building leg (b), notice what the topology change does to the premise. In a correct microservice estate the position store is private to the position-keeper service and reachable only through its API — the database-per-service pattern, and its named inverse the shared-database anti-pattern (microservices.io; Fowler, IntegrationDatabase). Priya's repo cannot issue UPDATE positions against another service's database; the demo's raw cross-table write only exists because the monolith shares one database.

The position-keeper exemplar already knows this. D-007 lists three enforcement layers — an ArchUnit boundary rule, a Semgrep content rule, and "a DB grant as the operational backstop (D-008)." That grant is precisely the database-per-service answer: assign each service its own credentials and let the database refuse the write (data sovereignty per microservice). The code-level checks are the in-repo convenience; the grant is the thing that holds across a repo boundary the code cannot see. The exemplar is smarter than the single-repo demo makes it look — and the honest read is that in a federated world the grant does more work than the verdict does.

4 · Priya in the wrong service — the failure the boundary does not catch

Here is the case that dissolves the first one. Priya's change genuinely belongs in the position-keeper service. But her team owns the reconciliation service, and that is the repo they know — so she builds it there. She does not reach into the position store (the grant would refuse her). She reinvents its responsibility: a positions-shaped table of her own, a second writer of the same truth.

Walk it against every mechanical check and each one stands down for a correct reason:

CheckVerdictWhy it does not fire
Per-service DB grantsilentShe writes her own service's database — no grant is violated.
Federated D-007 (hypothetical leg a+b+c)silentD-007 governs the position store. A parallel table in another service is not a write to that store — it is a new store that should not exist.
ArchUnit / dependency-cruisersilentSingle-repo by construction; the duplication spans repos, and within her repo the code is well-layered.
Contract test (Pact)silentChecks a consumer against a published contract, never a producer's internal ownership. The duplication publishes nothing to test.
The merge verdictsilentRepo-local, and no rule in her repo says "positions belongs to someone else."

This is not a boundary bypass; it is a boundary duplication — and it is worse, because it is invisible. Two services now believe they own position-like data, and they will diverge exactly the way KB-0001 (settlement consistency: the book and its consumers must never silently diverge) warns — only now the divergence is across a service boundary, where no single database, no single test, and no single reviewer sees both halves.

And the driver is not malice or incompetence — it is Conway's Law: "any organization that designs a system will produce a design whose structure is a copy of the organization's communication structure" (Fowler). The change lands where Priya's communication structure points — her team's repo — not where the domain says it belongs. This is the concrete, human mechanism behind the placement survey's abstract thesis, resemblance is not ownership: the change resembles the reconciliation service because Priya, embedded in that context, wrote it in that service's vocabulary. Improving any similarity signal makes the wrong answer more confident, because the change genuinely does resemble the repo it was written in.

5 · What could catch it — four legs, at design time, human-confirmed

The wrong-service misplacement is catchable, but only as a suggestion before the work, never a gate after it — and only if all four legs hold at once:

  • Ownership declared as data. Someone must have written "the position store belongs to the position-keeper service" in a form a machine can read — a spec.owner in a catalog, an ownership manifest, a bounded-context registry. spectastic has no ownership field today beyond enforce.waivers[].owner; TBD-project-ownership-field was deliberately left unbuilt as "vocabulary ahead of need." This is the load-bearing prerequisite — with it absent, every downstream leg is moot.
  • The estate is federated. The check in Priya's repo must be able to read the position-keeper's ownership claim. That is the spectastic-mcp read surface; 082's placement verdict is single-checkout precisely because this does not yet exist here.
  • The check runs at design time. By merge the code is already in the wrong repo and the reviewers are already the wrong reviewers. The natural home is the design/plan interview — a hedged prompt: "this change touches the positions domain, which the estate says the position-keeper service owns, not this repo. Intended?" This is the injection/nudge layer (116): advisory, P-8 — it improves the odds, it does not guarantee.
  • A human confirms the hedge. The engine must propose, never route, and must carry "no confident owner" as a first-class outcome (placement D-007: the most damaging failure is routing confidently to a plausible-but-wrong owner because abstention was not on the menu). Ownership is a social fact; the tool surfaces it, a person ratifies it.

Conway supplies the cruel corollary: leg 4's reviewer — the person who knows positions belongs elsewhere — is, by the same law that caused the misplacement, not on the misplacing repo's PR. Which is why legs 1–3 have to carry the signal to that person, at design time, or it never reaches them at all.

6 · The industry ceiling — so we are not claiming a gap nobody has closed

spectastic is not behind the field here; it is at the same ceiling everyone hits.

  • No mature machine-readable federated decision store exists. ADRs everywhere (MADR, Log4brains) are per-repo markdown prose read by humans. A store that CI in repo B queries to learn a rule authored in repo A is aspirational across the whole discipline, not an off-the-shelf thing spectastic merely lacks.
  • The deterministic cross-repo levers all require ownership declared as data first. DB-side grants (runtime/infra); Atlas schema-ownership lint — the one shipping tool that fails CI when a migration touches another service's tables, but Pro-only and authorship-time (a raw UPDATE in app code slips past it); OPA/Conftest with a shared central policy repo — enforceable in every pipeline, but only as good as the ownership manifest behind it.
  • The contract is the seam that makes the write illegitimate, and cannot detect the bypass. Pact checks a consumer against a published contract only; the producer's database is invisible across the boundary by design. The contract is the argument that a direct write is wrong, never a detector of it.
  • Ownership is organizational. Conway's Law and Team Topologies (stream-aligned teams owning a service end-to-end; the inverse-Conway maneuver as a deliberate ownership decision) both say the boundary is a social fact. "Who should own this?" is undecidable-by-tooling; "does this change respect an ownership someone already declared?" is the only checkable form.

7 · The corpus cannot carry it either

"Each service with its own knowledge corpus" is part of the scenario, so name what the corpus can and cannot do. Per the placement survey's D-004, the corpus is addressed per-marketplace — every document belongs to exactly one marketplace coordinate. An edge between two projects belongs to neither and has no legal coordinate, so the corpus is structurally incapable of storing a cross-repo decision or ownership edge. Two services can still share domain facts — both citing the settlement-domain pack keeps KB-0001 grounding consistent across repos — but the corpus is evidence, never the store for a rule that spans the boundary. It informs a placement suggestion; it does not hold one.

8 · Decisions

All status=Proposed; this is a survey, not a spec. Where a decision reuses a settled call, it cites it rather than re-litigating it.

  1. D-001 — Keep the verdict honestly repo-local; say so in the copy. Cross-repo enforcement is a federation problem, not a flag. The verdict's help/output should state that it judges the current checkout against the current repo's decisions — so an operator never mistakes a green verdict in one service for an estate-wide guarantee.
  2. D-002 — The missing primitive is a decision data-resource scope, not the decision index. A decision must be able to govern a federation-unique resource (a data store, a table, a topic on a spectastic:// coordinate), not only a repo-relative path glob. Without it, distribution (leg a) has nothing addressable to carry across the boundary. This is the primitive to build first, because even a single federated pair of repos needs it.
  3. D-003 — In a federated estate the placement failure dominates the enforcement failure. Grants block the reach; nothing mechanical blocks the duplication. So investment should tilt toward the design-time placement suggestion, not toward making the merge verdict cross-repo — the verdict catches the case the grant already catches.
  4. D-004 — Placement stays a design-time, human-confirmed suggestion (P-14), never a merge gate or an auto-route. Inherit the placement verdict shape wholesale: typed evidence, three-band confidence with an automatic hedge, and "no confident owner" as a first-class outcome. The wrong-service case is caught only when all four legs of §5 hold; the honest default when a leg is missing is silence, not a guess.
  5. D-005 — Elevate the DB grant from a footnote to the named cross-boundary backstop. The exemplar's D-008 already models it; guidance and any generated design should treat the grant (and the contract seam) as the cross-service control, with the code-level checks framed as the in-repo convenience they are.
  6. D-006 — The corpus remains evidence, never the store for a cross-repo decision or ownership edge (inherits placement D-004). Shared domain packs keep grounding consistent; they carry no rule that spans the boundary.

9 · Recorded ceilings

  • Nothing here was prototyped. No federated read was run, no ownership manifest authored; every claim is reasoned from shipped code, the placement survey's precedent, and the web landscape — materially weaker footing than a running system.
  • P-14 binds this whole survey. "Which service should own this" is a judgment call a linter cannot decide without false positives; everything in §5 is a suggestion engine because of that, and 075 already refused a neighbouring layer check on the same ground.
  • The ownership field is the gate on everything, and is deliberately unbuilt. Until TBD-project-ownership-field has a real consumer, legs 1–4 cannot run; this survey is the second independent motivation for it, not a mandate to build it now.
  • The demo's bypass is the easy case. A raw UPDATE positions string is content-detectable; the wrong-service duplication is not a string at all. The survey's most useful finding is precisely that the catchable version is the one the topology already prevents.

10 · What to build — planted slugs

  • TBD-decision-data-resource-scope — specced (13 Sep) as 119-decision-resource-scope, grounded in a run spike: a decision scopes a federation-unique datastore resource + an owner, and the verdict becomes owner-aware (reproduces the path rule in the owning service; flags any touch in a non-owner, even a well-layered one — ownership, not layering). Proven in one checkout with two real projects — the consumer is a Gradle subproject with its own spectastic.json, still carrying a verbatim copy of D-007; the cross-repo read stays TBD-federated-decision-read. The one piece even a single federated repo pair needs.
  • TBD-federated-decision-read — legs (a)+(c): read decisions across the estate via the decision index + the spectastic-mcp read surface, reached by a declared consumes/unit edge. Depends on TBD-guardrail-decision-index and the mcp federation work.
  • TBD-placement-ownership-prompt — leg 3: a design-time hedged "this looks like it belongs in service X" suggestion, human-confirmed, never a route. Gated behind TBD-project-ownership-field and TBD-placement-engine.
  • TBD-ownership-manifest — leg 1: declare "this store/domain belongs to that service" as machine-readable data (the prerequisite for every other slug; connects to the deliberately-unbuilt TBD-project-ownership-field and the catalog/spec.owner prior art).
  • TBD-verdict-scope-honesty — landed (13 Sep): the verdict now states it is repo-local, so a green result is never misread as an estate-wide guarantee. The Verdict artifact carries scope: "repo-local" + decisionsEvaluated (the count of accepted decisions from this checkout it looked at), and the human output prints "Scope: repo-local — … Decisions owned by other repositories are not evaluated" on both the clean and violation paths (--json stays pure — the claim is in the artifact). The cheapest slug here, and the only one that ships value with no federation at all.

Recommended order: TBD-verdict-scope-honesty (landed), then TBD-decision-data-resource-scope (specced as 119) (the primitive), then the federation and placement slices once spectastic-mcp and an ownership field earn their keep. Deliberately not re-planted: TBD-project-ownership-field and TBD-placement-engine — this survey is a second motivation for them, not a new artifact.
