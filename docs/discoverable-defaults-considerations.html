Considerations · Defaults & configuration

A default you cannot find is a rule

Being opinionated is a service. Being opinionated without saying so is indistinguishable, from where the user is standing, from having no opinion at all — and from refusing to hear theirs.

Status Draft Type Principle proposal & landscape survey Author Brian Corbin · @briancorbinxyz Created 03 Aug 2026 Companion verify-view-actionable · engineering-principles Sources 7 external, retrieved 03 Aug 2026 · codebase audit Read time

The proposed principle has three clauses — opinionated, not dogmatic, always discoverable — and only the third is failing, comprehensively. The tool has around eleven configuration sections; this repository's own spectastic.json declares five, so six are invisible from the file a user actually holds. Sixteen of twenty readers parse the config themselves, there is no canonical reader, nothing validates the file's shape, --help mentions it zero times, and there is no config command. The prompting suggestion — ship an annotated spectastic.jsonc — aims at exactly the right gap, and the audit reorders it: the defaults are not data anywhere. They are sixteen independent fallback expressions, so nothing in the codebase is in a position to enumerate them, and every downstream idea depends on fixing that first. On the mechanism, the closest peer's record is a caution: TypeScript's own tracker carries a request that tsc --init stop emitting comments, the generated file runs past 500 lines, and it is not valid JSON. Meanwhile this repository's own biome.jsonc opens with "$schema" — the project already relies on schema-driven discovery every day for its linter and offers nothing equivalent for itself. Recommendation: a canonical reader, then a published schema (which buys autocomplete and catches the typo that is silent today), then a config explain that answers the question users actually have — not "what keys exist" but "what is the effective value here, and where did it come from". And a fourth clause the principle needs: where a default is deliberately not yours to change, that has to be discoverable too.

1 · The ask — three clauses, one of them failing

The candidate principle is short: be opinionated, but not dogmatic, and always discoverable. Taken apart, it makes three separate promises, and they are not equally kept.

ClauseWhat it promisesHow spectastic does
OpinionatedThe tool decides, so the user does not have toKept. A spec budget of 1,500 words. An amber band at 80%. Profile tiers with enforcement floors. A model tier per verb. The tool has views and acts on them.
Not dogmaticThose decisions can be overriddenMostly. Config keys exist for a good deal of it. Some defaults are fixed, one of them deliberately — see §7.
Always discoverableYou can find out what was decided, and that you may change itFailing. The rest of this survey.

The third clause is the load-bearing one, because it is what makes the first two honest. An opinion the user cannot see is not an opinion they can disagree with; it is just behaviour. And an override nobody knows about protects nobody. Undiscoverable and dogmatic are the same experience from the outside — the user hits a decision they did not make, cannot find where it came from, and concludes the tool does not bend. Whether an escape hatch exists somewhere in the source is, at that moment, irrelevant.

2 · The audit — what a user can actually see

Every reader of spectastic.json in the repository was traced back to the section it consumes.

MeasureFinding
Configuration sections that existAround eleven — project, git, models, decider, enforce, validate, verify, corpus, consumes, design, changeRisk
Sections this repository's own config declaresFive. Six are invisible from the file a user holds and edits
Readers that parse the file themselves16 of 20. packages/core/src/config/ contains one module, edit.ts — a writer
Anything validating the file's shapeNone. No unknown-key check, no type check
Mentions of the config in --helpZero, and there is no config command
DocumentationTwo passing mentions in the README; no page

Read together, these describe a specific failure rather than a general untidiness. A user who wants to change something has no path to the knowledge: not from the file, which shows five of eleven sections; not from the terminal, which never mentions it; not from the docs, which do not cover it; and not from the editor, which has nothing to autocomplete against. The only reliable route is reading the source — which is a route, and is precisely the one an opinionated tool exists to save people.

The sharpest edge is the silence around a mistake. Misspell a key and nothing happens: no warning, no error, no effect. The user believes they have overridden a default and has not, and the tool's behaviour is identical to the behaviour it would have had if the override were refused. That is the point at which "not dogmatic" stops being true in practice regardless of what the code permits.

An earlier draft of this survey cited a code comment — "consumers are free to ignore unknown keys" — as evidence that the silence is deliberate. It is not evidence: that comment governs the AI provider's chat options, not the config file. The silence is real and was confirmed directly; the comment has nothing to do with it.

3 · The prerequisite — the defaults are not data

The obvious first move is to write down the defaults: generate a file, or a page, or a schema, listing every key and what it is set to when you say nothing. The audit says that move is not currently available, and the reason is worth stating plainly.

There is no single place that knows what the defaults are. Sixteen call sites read the config independently, each reaching for the key it cares about and supplying its own fallback inline. The default for a given key is an expression sitting next to its one consumer. Nothing aggregates them, nothing names them collectively, and nothing could enumerate them without a human going and looking. So a generator that emits an annotated config has nothing to generate from, and would be a second hand-written copy of knowledge that lives in sixteen places — which is to say, a third source of truth, drifting from the other two.

This reorders the work rather than blocking it. A canonical reader — one module that declares the shape, holds the defaults as data, and hands typed values to callers — is not itself a feature anyone asked for. It is the thing that turns every requested feature from "hand-maintain a copy" into "read the map".

Status Proposed

Context 16 of 20 config readers call JSON.parse themselves and supply inline fallbacks; packages/core/src/config/ holds only a writer. No module knows the config's shape.

Decision A canonical config reader comes first: one module owning the shape, the defaults as data, and the resolution order. Every other move in this survey reads from it rather than restating it.

Consequences
+ Turns the defaults into something enumerable, which is the precondition for a schema, a command, a doc page, or an annotated starter — all four become derivations rather than copies.
+ Gives the unknown-key problem somewhere to live: a reader that knows the shape can say what it does not recognise.
+ Fits the fat-core convention exactly — cross-cutting deterministic logic that a second caller obviously wants.
− It touches sixteen call sites, which is a wide diff for a change that adds no user-visible behaviour on its own.
− Centralising resolution risks changing behaviour where two readers quietly disagree today; that has to be found and settled rather than assumed away.

4 · The annotated-config idea has a track record

Shipping a commented default configuration is a well-established pattern and the prompting suggestion for this survey. It is worth looking at how it went for the tool that did it most visibly.

tsc --init generates a tsconfig.json with every option present and explained. The project's own issue tracker carries a request that it stop doing so; the generated file runs past 500 lines; it is described as spammy; and users report that deleting the comments is their first action after generating it. A separate request asks for a comment-free variant. And a third issue records the structural cost: the output is not valid JSON, which breaks tools that consume it.

The recurring counter-argument in those threads is the one that matters here: a modern editor already supplies each option's description and a link to its documentation, so inline comments duplicate something the user's tools would have told them anyway — at the cost of burying the four lines they actually set.

None of that makes the underlying goal wrong. It calibrates the artifact. The instinct — a user should be able to see what the tool decided and what else they could set — is correct and unmet. The specific vehicle, a long commented file, is the part that has been tried and found wanting, and it fails hardest exactly where spectastic would need it most: on a config with eleven sections, most of which any given project will never touch.

Status Proposed

Context The peer implementation of the annotated-config pattern generated sustained requests to disable it, produced invalid JSON, and is routinely stripped by its users. The rebuttal offered in those threads is that editor tooling already carries the descriptions.

Decision Do not make a long annotated file the primary discovery mechanism. Keep a short annotated starter — the handful of keys most projects touch — as an on-ramp, and put the exhaustive knowledge where it can be queried rather than scrolled.

Consequences
+ Avoids a documented failure mode rather than rediscovering it, and keeps the file a user edits about what they set.
+ A short starter still answers the "what does this file even look like" question, which is the first five minutes and genuinely matters.
− Someone offline, or in an editor with no schema support, loses the browsable list the long file would have given them.
− "Short" is a judgment call with no obvious line, and it will drift upward under pressure unless something holds it.

5 · A schema does two jobs at once

A published JSON Schema, referenced from the config by a $schema key, gives an editor everything the comments would have: the list of valid keys, a description per key, the accepted values, and completion as the user types. Editors resolve the reference automatically, and a schema registered with the community store is picked up for matching filenames with no reference at all.

The second job is the one that makes it more than a documentation choice. A schema is a machine-readable statement of what the config may contain, so the same artifact that supplies autocomplete also answers the question nothing answers today: is this key real? The typo that currently vanishes without trace becomes a finding — in the editor as the user types, and at the command line wherever the project chooses to check.

The precedent is already in this repository. Its own biome.jsonc opens with a $schema line pointing at the linter's published schema. The project depends on exactly this mechanism, daily, for someone else's configuration — and offers nothing equivalent for its own. That is not an argument from fashion; it is the working demonstration sitting in the root directory.

That file settles the comments question too, by doing both things at once and keeping them in their places. It is .jsonc, and it carries nine comment lines — not a generated catalogue of every option, but a handful of notes explaining this project's choices to the next person who opens it. The schema supplies what the tool knows; the comments supply what the author decided. Neither is doing the other's job, and the file is short because the exhaustive half was never copied into it. That is the division this survey recommends, already in production here with a different tool's config.

Status Proposed

Context A schema supplies editor completion and per-key documentation, and simultaneously makes an unknown key detectable. biome.jsonc in this repository already uses the pattern.

Decision Publish a schema for spectastic.json, generated from the canonical reader, and have init write the $schema reference into new configs. Treat unknown-key detection as part of what the schema is for, not a separate feature.

Consequences
+ One artifact closes both the discoverability gap and the silent-typo gap, and it is machine-checkable — which is where this project's guarantees are supposed to live.
+ Derived from the reader, it cannot drift from the code the way a hand-written document would.
− It has to be hosted at a stable URL and versioned alongside the tool; the project publishes no such URL today, and a broken reference is worse than none.
− It helps only inside an editor that resolves schemas. The terminal-side answer is §6, and neither substitutes for the other.
MechanismLists what existsCatches a typoShows the effective valueWorks offlineScore

The top two rows tie, and that is the finding rather than an indecision: they answer different questions and neither covers the other's column. The scoring is what argues for building both, in that order.

6 · The question users actually ask

A schema and a commented file both answer "what may I set". Neither answers the question that sends someone looking in the first place, which is nearly always some form of: why is it behaving like this?

That question needs three things a static document cannot supply — the value in force right now, whether it came from a default or from something the user wrote, and if the latter, from where. A tool that can print that turns configuration from a thing you edit hopefully into a thing you can interrogate. It also makes the principle's second clause visible at the moment it matters: seeing a value labelled default is what tells a user, without them having to go looking, that there is something here they are allowed to change.

Status Proposed

Context Discovery mechanisms enumerate the possible. Users arrive holding an observed behaviour and needing its cause. No current surface connects the two, and no static artifact can.

Decision A config command that prints the effective configuration with provenance per value — what it is, whether it is a default, and where an override came from. It reads the canonical reader, so it cannot disagree with what the tool actually does.

Consequences
+ Answers the real question, works offline and in any editor, and needs no hosted URL.
+ Every value it prints as a default is an override the user has just been told exists, without a document being read.
+ Gives --help something to point at, which is the gap that leaves the config unmentioned today.
− Another command on a surface this project deliberately keeps small; it earns its place only by being the sole thing that can show provenance.
− Provenance is only as good as the reader's bookkeeping; a value resolved through several layers has to carry its origin, which the current inline fallbacks discard.

7 · Beyond the config file — and where fixed is correct

Configuration is where this started, and it is not the whole of what the principle governs. The tool's opinions arrive in three distinct forms, with three different override stories.

KindExampleCan a user change it?Can they find out?
Config keyvalidate.quantifiedNfrFloorYesNot from any surface the tool provides
Named constantTen DEFAULT_* exports across the packages — timeouts, thresholds, tiers, weightsSome, through config; some not at allOnly by reading the source
Baked-in literalThe amber band at 80%; a spec's 1,500-word budgetThe budget, per artifact. The band, noThe band's rationale is documented; that it is fixed is not stated anywhere a user would look

The amber band deserves the attention, because it looks like a violation and is not. The 80% threshold is a literal in the stylesheet's companion script, and it is pinned there deliberately: a schema rule guards it against drifting from the requirement that owns it, so the number in the code and the number in the specification cannot diverge. That is a considered decision with a mechanism behind it — dogmatism in the strict sense, and correct.

So the principle cannot demand that everything be overridable. Some defaults are load-bearing, and letting a project quietly move one would break the guarantee it exists to provide. What the principle can demand is that the fixity be stated. A user who wants to change the band should be able to find out, quickly, that it is fixed and why — rather than searching for a configuration key that was never going to exist. Discoverability covers the refusals as well as the choices; an unexplained "no" is the dogmatism the principle is trying to name.

8 · The principle

Status Proposed

Context The candidate wording has three clauses. The audit shows the third failing and the second compromised by it, and §7 shows a fourth case the three clauses do not cover — a default that is fixed on purpose.

Decision Propose a principle binding every default the tool imposes — configuration keys, named constants, budgets, bands, profile tiers, enforcement floors, model policy — to three obligations: the default and its value are findable without reading the source; whether it can be overridden is stated; and where it cannot be, the reason is given. Silence on any of the three is the defect the principle names.

Consequences
+ Covers the cases outside the config file, which is where the least discoverable defaults currently sit.
+ The fixity clause makes deliberate rigidity legitimate rather than an embarrassment to be hidden, which is what stops the principle from being unsatisfiable.
+ Composes with this project's existing honesty rules about recording ceilings rather than concealing them.
− Broad enough that a mechanical check cannot cover it end to end; conformance for constants and literals will be review-caught, which the principle should admit outright rather than imply.
− It creates ongoing obligation: every future default is now something that must be surfaced, and that cost is real and permanent.

Worth saying plainly: the principle is not "make everything configurable". A tool that surfaced every constant as a knob would be neither opinionated nor usable, and the cost of a configuration surface is paid by every reader of it forever. The obligation is to be legible — to let a user find the decision, understand its standing, and know whether the conversation is open.

9 · Recommendation — four slices, in dependency order

  1. A canonical config reader. One module holding the shape, the defaults as data, and the resolution order, with the sixteen call sites reading from it. No user-visible change, and nothing else here is honest without it.
  2. A published schema, and the $schema reference in new configs. Generated from the reader. Buys editor completion, per-key documentation, and the unknown-key detection that is missing today.
  3. A config command showing effective values with provenance. The terminal-side answer, and the only one that addresses why rather than what.
  4. Accept comments on read; keep any generated starter short. A user who wants to annotate their own configuration should not be punished for it — the strongest evidence being that this project already does exactly that in biome.jsonc, where nine hand-written lines explain its own choices alongside a schema that supplies everything else. What §4's evidence argues against is the tool generating the long file, which is a different act with a different outcome.
Do not start with the annotated file. It is the most visible slice and the most tempting, and it is the one that cannot be done well yet: with the defaults living in sixteen inline fallbacks, a generated annotation is a hand-maintained third copy that will drift from both the code and the schema. It is also the mechanism with the worst track record. Build the reader, and it becomes a derivation instead of a liability.

Suggested next artifacts

  • A new spec: the canonical configuration reader — the declared shape, defaults as data, resolution order, and the migration of the existing readers onto it, including any behaviour differences that migration surfaces (D-001).
  • A new spec: the published schema generated from the reader, the $schema reference written by init, hosting and versioning, and unknown-key reporting (D-003).
  • A new spec: the config command — effective values, default-versus-overridden, and the origin of each override (D-004).
  • A smaller slice: accept comments in a user's own configuration on read, without generating them. Blocked on the canonical reader, since sixteen independent parsers would otherwise each need teaching.
  • A question this survey opens and does not close: where a deliberately fixed default is recorded, so a user can discover the refusal and its reason as easily as they discover a key. The amber band is the worked example (§7).
  • A /spectastic.propose against the principles: the principle itself, in the four-obligation form D-005 lands on.

10 · Caveats on the sources and the audit

  • The section count is approximate, and deliberately hedged. "Around eleven" comes from tracing readers back to the keys they consume; a first pass over-counted by matching method calls that merely looked like config access. The named sections were each confirmed against a reader, but a section read in one obscure place could have been missed, and the number should be treated as a floor.
  • This survey's own first draft made an attribution error. It cited a comment about the AI provider's options as evidence that unknown config keys are ignored by design. The silence is real and was confirmed directly; the comment was irrelevant. Recorded because a reviewer re-running the search would find that comment and could repeat the mistake.
  • A second correction, caught at verification. The draft named the linter config biome.json; it is biome.jsonc, and the difference is not cosmetic. The real file carries a schema reference and nine hand-written comments, which is a stronger and more useful precedent than the one first claimed — it demonstrates the split this survey recommends rather than merely the schema half. Found by re-running the grep the verification step asks for, which is the entire reason that step exists.
  • The peer evidence is a public record, not a measurement. The TypeScript issues show sustained dissatisfaction with a generated commented config; they do not quantify how many users are bothered, and plenty of projects ship annotated configs happily. It is a caution drawn from the nearest large example, weighted accordingly.
  • Nothing here was prototyped. No reader, no schema, no command. The claim that a schema can be generated from a canonical reader is ordinary but untested in this codebase, and the migration of sixteen call sites is exactly the kind of work that surfaces disagreements nobody knew existed.
  • The schema recommendation carries an unfunded dependency. It needs a stable, versioned URL the project does not currently publish. A dangling $schema is worse than none, so the hosting question has to be answered before the reference is written into anyone's config.
  • The principle is broader than any check can cover. Config keys can be verified mechanically once a schema exists; constants and baked-in literals cannot, and conformance there will be review-caught. That is the same honest ceiling this project already records elsewhere rather than a gap discovered late.
