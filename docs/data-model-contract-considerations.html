Considerations · Data models & contracts

The data model has to leave the repo

Entities are prose in the spec. The interface contract is nowhere at all. Both are survivable right up to the moment another team — in another repository — needs the shape, and prose turns out to be the one format nothing can generate from, diff, lint, or hand over.

Status Draft Type Architecture & landscape survey Author Brian Corbin · @briancorbinxyz Created 30 Jul 2026 Companion event-driven-interface · engineering-principles Sources 16 external, retrieved 30 Jul 2026 · codebase audit Read time

The premise turned out to understate the problem: it isn't that design squeezes data models into prose, it's that the model sits at the wrong altitude and the contract has no home at all. Today spec.html §4 is a <dl> of entity → sentence (67 of 69 specs use it), and design.html — the artifact that actually decides how — has no data-model or contract section anywhere in its eleven. Meanwhile the vocabulary is already built everywhere except the artifact: the contract-first enforce category detects OpenAPI, .proto, GraphQL SDL, AsyncAPI and contracts/*.schema.json; the contracts profile axis ladders informal → contract-first → contract-checked → versioned+governed; and the seeded principle already promises a contract ships "before the code behind it." Nothing in the design verb honours any of it. The landscape is unambiguous — in 2026 the unit of an API is the schema, not the endpoint, design-first is the default, and machine-readable contracts measurably outperform prose as an agent's target. Decisively, the closest peer tool has already answered the "one verb = one artifact" objection: Spec Kit's /plan emits plan.md plus data-model.md and a contracts/ directory of OpenAPI/GraphQL files. One verb, one primary artifact, sidecars alongside. On where the file goes, two lifecycle states settle it — a spec authors a proposed contract beside its design, and promotion writes the effective one to the project's ecosystem-conventional path and archives the proposal, exactly as apply already folds and archives a change proposal, so one live copy exists at every instant. A third gap found along the way — the enforcement gate recognises no message broker of any kind, so an event-driven service owes no contract at all — outgrew this doc and became the companion survey. Recommendation: three staged slices — give the contract a home, render it honestly (a bounded, generated, drift-guarded view — the CSP forbids transclusion, so an embed is a materialised copy and must be policed like one), and make it exportable across the repo boundary as the headline bet — which 067 has already unblocked by landing the spectastic://<project>/… coordinate an exported contract should inherit rather than duplicate.

1 · The ask — a shape that outlives one repository

The scenario is concrete. A spectastic project is a backend service. Somewhere in its design stage it settles what a Settlement looks like on the wire: which fields, which are nullable, which enum values are legal, what the error envelope is. A different team, in a different repository, is building the UI against it. They need that shape — not a paragraph describing it, the shape itself, in a form their code generator, their type-checker, and their mock server can all read.

Today spectastic gives them a paragraph. The entities live as a definition list in the spec, which is excellent for a reader and useless for a compiler. Nothing in the lifecycle produces a file the other repository could consume, and nothing references one if a human happens to write it by hand.

The instinct to resist is a good one and worth naming precisely, because it is the reason the gap exists. Spectastic holds a strong line that each verb owns exactly one honest artifact — design.html is the design doc, the way tasks owns the work plan. Multiplying outputs per verb is how tools acquire the sprawl this one was built to avoid. So the question is not "should we relax the principle" but the sharper one: is a machine-readable contract a second artifact, or is it the same artifact in the form a machine can read? §4 shows the field has already answered this, and §5 shows the answer survives contact with a single-file HTML design system.

Two secondary pressures push the same way. A large model — thirty entities, not three — is unreadable as prose regardless of where it lives; the reading-measure that makes a spec calm makes a schema illegible. And the primary consumer of these artifacts is increasingly an agent, for which the difference between prose and schema is not stylistic but functional.

2 · Where spectastic puts models today — three gaps, not one

The audit found the problem one level up from where it was reported. The complaint was that the design doc forces data models into prose. In fact the design doc doesn't hold them at all — and a third gap, wider than either, sits underneath both.

Gap one — the spec holds the model, as prose. templates/spec.html §4 Data model is a definition list and a note:

<h3>Entities</h3>
<dl>
  <dt>[ENTITY_1]</dt><dd>[FIELDS_AND_PURPOSE]</dd>
  <dt>[ENTITY_2]</dt><dd>[FIELDS_AND_PURPOSE]</dd>
</dl>

Sixty-seven of sixty-nine shipped specs carry the section. In this repo it reads well, because this repo's specs mostly introduce no persisted entities at all — 064's §4 says the slice "introduces no new persisted artifact", 068's says "No new persisted entity." That is a self-selecting sample. A settlement service or a booking system fills the same <dl> with thirty rows of fields-and-purpose, and it degrades exactly as you'd expect.

Gap two — the design doc has nowhere to put a contract. templates/design.html runs Principles check, Technical context, Grounding, Approach, Alternatives, Decisions, Project structure, Risks, Complexity, Open questions, Change log. No data section, no schema section, no contract section. The nearest thing is a single interview prompt in commands/spectastic.design.md — "Persistence shape if storage was discussed (e.g. SQL / KV / object store / in-memory only)" — whose answer lands as a row in the Technical-context table. Storage class, not storage shape.

Gap three — the whole apparatus assumes a synchronous request/response interface. The gate that decides whether a contract is owed at all matches a fixed list of dependency names, every one of them an HTTP framework, a GraphQL server, or a gRPC toolchain. A service whose public surface is broker topics is therefore exempt from the contract floor at every tier. That finding outgrew this survey and has its own: Not every interface is an endpoint. It matters here only as context — the sections below assume a synchronous interface throughout, and where they say "endpoint" or "response", an event-driven project should read "message" and "payload" without the argument changing.

The strange part is that everything else is already built. The vocabulary for contracts exists throughout the codebase; it simply never reaches the artifact:

MachineryWhereWhat it already knows
contract-first enforce category packages/core/src/enforce/detect.ts Detects openapi|swagger|asyncapi.{yaml,json}, *.proto, *.graphql, and *.schema.json under contracts/ — searching root plus api/ proto/ schema/ contracts/, one level, no recursion. Interface-gated: a gap only when a web/RPC framework is detected without a contract. The search path is narrow enough to miss most ecosystem-conventional layouts — see §6.
contracts profile axis spectastic-profiles.json Four rungs already named: informal → contract-first → contract-checked → versioned+governed. Advisory vocabulary; nothing reads it.
Seeded principle (standard tier and up) spectastic-profiles.json "A component that exposes an interface ships a checked-in contract … before the code behind it. The contract is the agent's target and the consumer's guarantee." Names OpenAPI, JSON Schema and typed signatures — not AsyncAPI, and not .proto or GraphQL SDL either.
INTERFACE_SIGNALS — the gate's antecedent packages/core/src/enforce/detect.ts Forty-odd dependency signals across six ecosystems, all HTTP, GraphQL or gRPC — the subject of the companion survey.
The design verb templates/design.html, commands/spectastic.design.md Nothing. No section, no interview question, no element, no link.

So the enforcement floor can already fail a project for not having a contract that the lifecycle gives it no way to author, no place to record, and no prompt to consider — and can simultaneously pass, in silence, a project whose interface it cannot see. That is the actual defect, and it has two faces.

One further inconsistency falls out of the same audit, worth fixing whatever else is decided: the contracts axis sets standard tier to contract-first, but contract-first only enters enforce.required at verified. A standard-profile project therefore declares a contract-first posture that nothing checks — the axis and the floor disagree by one rung.

3 · Altitude — conceptual, logical, physical

Before deciding where a schema lives, decide which schema. "Data model" names at least three different documents, and conflating them is what makes the placement question feel unanswerable. The separation is old and well-settled: the three-schema architecture distinguishes an external level ("a user's view of the database describes a part of the database that is relevant to a particular user"), a conceptual level ("a way of describing what data is stored within the whole database and how the data is inter-related"), and an internal level, which "involves how the database is physically represented on the computer system."The ANSI-SPARC three-level architecture, whose stated purpose is data independence — separating the levels so "the DBA can change the database storage structures without affecting the users' views" [8].

Map that onto the lifecycle and the answer is almost mechanical:

LevelWhat it isArtifact that should own it
Conceptual Entities, relationships, invariants, state transitions. Technology-agnostic. Survives a rewrite. spec.html §4 — where it already is. Prose is the right medium here.
Internal / physical Tables, columns, indexes, serialization, partitioning. Consequences of the stack choice. design.html — currently homeless.
External What a consumer sees: request/response shapes, event payloads, error envelopes. The published projection. design.html, as a referenced contract file — currently homeless.

The third row is the one that repays the framing. An API contract is not a description of the persistence model; it is the external schema — deliberately not the internal one, deliberately stable while the internal one churns. That is the whole point of the separation, and it is why "the data model" and "the API contract" are two artifacts that must be allowed to differ. A spec that pins the conceptual model, a design that records the physical one, and a contract file that publishes the external one is not three competing sources of truth; it is one model observed from the three altitudes the lifecycle already has verbs for.

It also resolves the tension in §1 without touching the spec's prose. §4 keeps doing what it does well — naming the entities a feature owns and the invariants a reviewer should look twice at — and stops being asked to carry field types it was never shaped for. Practitioner reports of design-first work describe the same direction of travel: changes were "done first in the API design, and then trickle down until the data-model."A team's account of adopting design-first with a typed API DSL, including the review sessions, the decision log, and the CI drift checks [3].

D-001 · The spec keeps the conceptual model; the design owns the physical model and the external contract

Status
Proposed
Context
"Data model" conflates three levels. Spec §4 is already the right home for one of them and the wrong home for the other two, and the design artifact — which decides the stack that determines both — holds neither.
Decision

4 · The landscape — the schema is the unit, and the peers already ship sidecars

The field has consolidated hard since the last time this question was open. The 2026 framing is that "the unit of an API is the schema, not the endpoint" — schemas are authoritative, and documentation, client SDKs, server stubs, test fixtures, and agent tool definitions are all generated from them rather than written alongside them.A survey mapping JSON Schema, OpenAPI 3.1, AsyncAPI 3.0, GraphQL SDL, Protobuf, Smithy and TypeSpec against each other, dated May 2026: "A good 2026 API is not hand-coded — it falls out of the schema" [2]. The standards body is blunter still: the OpenAPI Initiative writes that "the importance of using Design-first cannot be stressed strongly enough," and warns that arriving at the description after the code yields "unintuitive and incomplete descriptions, that will rarely scale in the future."OpenAPI Initiative, Best Practices — which also insists on exactly one authoritative location, because with two "newcomers to the project will not know which one is actually in use and mistakes will be made" [1].

Notably, the consolidation has a second floor: authorable DSLs — TypeSpec, Smithy — are increasingly the source of truth, with OpenAPI itself demoted to a generated artifact [2]. That matters for spectastic only as a warning: whatever home the contract gets must not assume the file is hand-written OpenAPI, because for a growing fraction of projects it will itself be generated from something upstream.

The agent argument is the one closest to this tool's purpose. Documentation written only for humans measurably degrades machine consumption — agents "hallucinate parameters that don't exist, miss authentication requirements, and generate code that fails" — while a machine-readable definition lets docs, token-efficient markdown, index files and SDK examples all fall out of one source, so "when the API changes, everything updates together."On preparing API surfaces for agent consumption; the same source notes that HTML "includes navigation menus, styling markup, and visual formatting that AI models must process but cannot use" — a caution worth holding onto for §5 [4]. Spectastic's own seeded principle already asserts this — the contract is "the agent's target" — which makes the absence of a place to put one awkward rather than merely incomplete.

And the peer tools have already settled the artifact-count objection. This is the decisive finding, because it is the closest available prior art.Spec Kit's plan template lists the Phase 1 outputs as data-model.md, /contracts/* and quickstart.md [5]; its methodology document states the ordering constraint plainly — create contracts/ with API specifications before creating source files [6]. Kiro's spec documentation names no data model or schema among its design contents [7] — the omission is the point: the strict-one-artifact position exists in the field, and it is the position spectastic currently shares.

ToolDesign-stage outputsWhere the model and contract go
Spec Kit plan.md + research.md + data-model.md + contracts/ + quickstart.md Explicit sidecars. data-model.md carries "entities, fields, and relationships"; contracts/ holds API specifications "in OpenAPI/GraphQL format", one file per surface area. The task verb reads them as inputs.
Kiro requirements.md + design.md + tasks.md One design doc, covering "system architecture and component design, sequence diagrams and data flow, error handling and testing strategy." No data model or schema named.
Spectastic (today) design.html Neither. The conceptual model sits one artifact upstream; the contract is absent.

The reframing this permits is exact, and it is what §1 was reaching for. Spec Kit did not abandon one-verb-one-artifact; it distinguished the primary authored artifact (the plan a human reads and reviews) from sidecar artifacts the same verb produces because a machine has to read them. Spectastic already has this distinction and already relies on it: verify.html is a derived view, not a second authored output, and the repo's own note on the pattern is that "one authored artifact per verb" is preserved precisely because the derived thing is a view rather than an output. A contract file is that same category — not a rival design doc, but the design's external schema in the only format a code generator, a linter, a mock server, or another team's build can consume.

5 · Representation — four options, and two hard constraints

Two findings from the codebase bound the design space before any preference does.

The CSP forbids transclusion. Every spec-family template ships a strict deny-by-default policy — default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline' …; img-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none' — and the element vocabulary contains no src=-style include anywhere. There is no mechanism, and deliberately so, by which an artifact can load a schema file at view time. "Embed the schema in the page" can therefore only mean materialise a copy of it at generate time. That is not a detail: a copy is a second source of truth unless something actively polices it, which turns a rendering question into a drift question.

There is no bounded-scroll container. pre is styled overflow-x: auto and is vertically unbounded; nothing in assets/spec.css caps a block's height and scrolls it. A four-hundred-line schema pasted into a design doc today does not scroll — it runs the document, and takes the calm-density property of the whole design system with it. Any embedded view needs a new bounded container, not just a new element name.

A third constraint is external and points the same way: the OpenAPI Initiative's own guidance for large descriptions is to split them — factor repeated blocks into components and reference them with $ref, and distribute a big description across multiple documents along the URL hierarchy [1]. The industry answer to "this schema is too big to read" is not a taller scrollbar; it is references. Whatever spectastic renders should assume the authoritative thing is a file — possibly several — and that the artifact shows a view of it.

With that established, the options:

OptionHandoverToolingReviewDriftCostTotal
A · Prose <dl> only — the status quo 0043512
B · Author the schema inside the HTML — the artifact is the contract 1134413
C · Sidecar file, referenced, with a bounded generated view 5543320
D · Published package or registry only — no in-repo artifact 5514116

Handover — can another repository consume it. Tooling — can a generator, linter or differ read it. Review — does it read well in a browser and a pull request. Drift — how few copies can disagree. Cost — effort to author and to build, higher is cheaper.

A scores well only on the axes that measure doing nothing. B is the tempting one and the trap: it keeps the single-file promise, but a schema authored inside HTML is invisible to the contract-first detector that already scans the filesystem, unreadable by every generator in §4, and — per the agent finding — wrapped in exactly the presentational markup that machine consumers must process and cannot use. It buys tidiness at the cost of every reason to have a contract. D is where a mature organisation ends up but is wrong as a starting point: it strands the reviewer, who now has to leave the artifact to see what was decided, and it presumes distribution machinery that §6 shows is not yet groundable here.

C is the one the constraints select. The contract is a file, in the places the enforce detector already searches — root, or api/ proto/ schema/ contracts/. The design doc references it, the way a decision references a requirement. And because a reviewer should not have to leave the page to see what shape was agreed, the artifact may carry a generated, bounded view of it — explicitly a projection, never the source.

D-002 · The contract is a sidecar file where the enforce detector already looks; the design references it

Status
Proposed
Context
A contract's entire value is being machine-readable by things outside this document — generators, linters, differs, another team's build. Authoring it inside HTML forfeits all of that, and would also be invisible to the contract-first gate that already scans the filesystem for exactly these files.
Decision

Consequences

The embedded view needs the same discipline as the verify page. Once the artifact carries a copy of any part of the contract, the copy can go stale — and spectastic has already solved this exact problem once. The verify-view-stale rule exists because verify.html materialises links that can drift from the bundle it was generated against, and the answer was a validate finding, not a promise to remember. An embedded contract excerpt is the same shape of hazard and should get the same shape of guard, rather than a new mechanism invented for the occasion.

D-003 · Any in-artifact rendering is a bounded, generated, drift-guarded view — never the source

Status
Proposed
Context
The CSP forbids runtime transclusion, so an embed is necessarily a materialised copy; no bounded-scroll container exists, so a large schema would run the page; and the industry answer to a large description is references, not scrollbars.
Decision
Render the contract as a generated view: materialised at generate time, height-bounded and scrolled within its own container, visibly labelled as a projection of a named file, and drift-guarded by a validate finding that clones the verify-view-stale shape. 6 · Where the file lives

"A checked-in file" is not yet an answer. The path decides three things at once: whether the enforcement gate can see it, whether a consuming repo can address it, and who owns it as the interface changes over the years. Two facts from the codebase constrain the choice before any preference does.

The detector cannot see into specs/. detectContract lists the project root and then reaches exactly one level into api/ proto/ schema/ contracts/ — five non-recursive directory listings, no recursion anywhere. A contract at specs/042-orders/contracts/orders.openapi.yaml is never found; the same file at contracts/orders.openapi.yaml is found immediately.

This is a fact about today's detector, not a law. It is worth stating plainly because the rest of this section could easily be written as if the detector's reach were a constraint to design around. It is not — it is a narrow implementation that should be widened, and the convention below is chosen on its merits, then detection is expected to follow. Designing the artifact layout around a fifty-line function's current search path would be the tail wagging the dog.

And that reach is narrower than it first appears. Held against the conventional layouts of the ecosystems spectastic already claims to detect, it misses more than it finds:

Ecosystem conventionConventional pathFound?

Multi-module Gradleservice-a/src/main/proto/…No
Rust, tonic serverproto/*.protoYes

Two consequences follow. The narrow one: a purely spec-local convention would make a project with a perfectly good contract fail contract-first, so location still has to account for what the gate sees — but as a defect to fix alongside, not a boundary to respect. The broader one: the effective contract belongs wherever its ecosystem conventionally puts it, and a Gradle project should not be asked to move its protos out of src/main/proto/ into a spectastic-shaped contracts/ to satisfy a gate. A tool that makes projects rearrange themselves to be detectable has inverted its own charter.

The detector also cannot tell a producer from a consumer. The progenitor case makes this concrete: a crate using it is generating a client for someone else's API, so the OpenAPI document it points at is an upstream contract it consumes, not one it publishes. Vendor that document into api/ and the gate marks the project covered — a false positive whose mirror image, a whole class of interface the gate cannot see at all, is the subject of the companion survey. The same applies to a checked-in .proto for an upstream gRPC service. Detection by file presence cannot distinguish the two; only a declaration can, which is an argument for the design artifact naming its contract explicitly rather than the gate inferring one from the filesystem.

A contract outlives the spec that introduced it. Spec 042 does not own "042's contract"; the project owns one interface, which many specs change over time. Under a spec-local rule, the current interface's location would depend on which spec last touched it, and a consumer would have to know spec ids to find it — the opposite of a handover.

Against that, the spec-local instinct is not wrong, and the closest peer does exactly it. Spec Kit writes contracts/ inside the feature directory, alongside data-model.md — because during the work, the contract is a property of the change being made, and keeping it there is what lets the task verb read it as an input. The provenance that buys is real: which spec introduced this interface, and what did it look like when that spec was approved.

OptionVerdictNote
Project root only Insufficient Gate and consumers are served, but an in-flight interface change has nowhere to live except the live contract — so a proposed shape and the effective one are indistinguishable while the work is open.
Spec-local only Reject Spec Kit's shape, and unusable here: invisible to detectContract, addressable only by spec id, and the current contract's home moves with edit history.
Spec-local proposed, promoted to root effective Adopt Two lifecycle states, one live copy. Exactly the relationship changes/<slug>/proposal.html already has with the live spec.html.

The winning option is not a compromise; it is a pattern this tool already runs on. The objection to holding a contract in two places is the one the OpenAPI guidance makes in §6 — with two copies, "newcomers to the project will not know which one is actually in use." That objection lands against two live copies. It does not land against a proposal and the artifact it will be folded into, which is the entire propose/apply cycle: an authored change sits in specs/<id>/changes/<slug>/, apply folds it into the live spec, and the source is moved to changes/archive/ so it can never be mistaken for current. A contract can travel the same road. The spec-local file is the proposed contract; the root file is the effective one; promotion archives the proposal. At every instant exactly one copy is authoritative, and which one is never ambiguous.

That also gives both URI shapes an honest job, rather than forcing a choice between them. spectastic://<project>/spec/<id>/contract/<name> addresses the proposed contract — genuinely a sub-resource of that spec, because before promotion it belongs to nothing else. spectastic://<project>/contract/<name> addresses the effective one as a sibling kind, which is the composition 067's own design anticipated when it noted the scheme "composes with a future corpus URI." Same coordinate, two kinds, one of them nested — and the nesting means something rather than being a filing convention.

One naming note. The word references/ is already spoken for: in the corpus it means a pack's flat set of citable .md documents plus a superseded/ subdirectory, sitting one level under a per-unit directory — the same shape and position a contracts folder would occupy, with entirely different semantics. Using contracts/ at both ends avoids that collision and has the further merit that the proposed and effective directories share a name, differing only in location and lifecycle state.

D-004 · The spec-local contract is a proposal; the root contract is effective; promotion archives the proposal

Status
Proposed
Context
A contract must be where the detector looks (root or one of four conventional dirs) and where a consumer can find it without knowing spec ids — but an in-flight interface change also needs somewhere to live that is not yet the live contract. Those are two states of one artifact, not two artifacts, and the propose/apply cycle already models exactly that relationship.
Decision
A spec authors its contract at specs/<spec-id>/contracts/<name> — the proposed interface. Promotion writes it to the project's ecosystem-conventional contract location — src/main/proto/ for a Gradle project, proto/ for a tonic crate, contracts/ where the project has no convention of its own — as the effective interface, and archives the spec-local copy, mirroring how apply archives a folded proposal. The design artifact names that path explicitly, so the effective contract is declared, not inferred. Use contracts/ for the spec-local half, not references/, which the corpus already owns. Address the two states as spectastic://<project>/spec/<id>/contract/<name> and spectastic://<project>/contract/<name> respectively.
Consequences
+ One live copy at every instant, so the single-authoritative-location rule holds without giving up per-spec provenance. + Projects keep their ecosystem's layout instead of rearranging to be detectable. + An explicit declared path sidesteps the producer/consumer ambiguity that pure filesystem inference cannot resolve. + Reuses a cycle the tool and its users already understand instead of inventing a second one. + An un-promoted contract is invisible to the gate, which is correct: it is not yet effective. − Requires widening detectContract, whose four-directory, one-level reach misses most conventional layouts — so this decision creates detector work rather than avoiding it. − Promotion is new machinery on apply or implement, including the archival step, and until it exists the convention is manual. − Nothing prevents a hand-edited effective contract that never passed through a spec, so this is a workflow, not an invariant — review-caught, like the fat-core/thin-CLI boundary. − A spec that only changes an existing contract must copy the whole file to amend it, since a partial delta of a schema is not itself a valid schema.

7 · Crossing the repo boundary

The motivating scenario is a distribution problem wearing an authoring problem's clothes. Getting the contract into a file solves authorship. It does not yet get the file to the team in the other repository, and the options for that are well-mapped and differ enormously in cost.The vendoring pain is named by the protobuf ecosystem itself — "teams feel that their only option is to copy/paste (vendor) these schemas manually" — against which a registry offers modules that depend on modules, automatic SDK publication to NPM/Go/Maven/Gradle/Swift, and governance where "schema owners can audit, approve, and reject breaking changes before they're deployed to production clients" [10], [11]. Generation tooling for the package route is mature and multi-language [12], and multi-team guidance frames sharing contracts in a unified way as "a must", recommending the interface be stored "as structured metadata in code" rather than in curated wikis [9].

MechanismWhat it costsWhen it fits
Monorepo — both sides share the file directly Nothing, if you already have one The common case, and genuinely the right answer when available. Consumers read the path.
Vendored copy — the consumer checks in a duplicate Near zero, then silent divergence The default people fall into. Protobuf's own ecosystem names this as the pain a registry exists to remove.
Generated client published as a package CI job, versioning policy, a release cadence The mainstream cross-repo answer — generate an SDK from the contract and publish it to npm, Maven, PyPI or Go modules.
Schema registry Infrastructure, governance workflow, org buy-in Where large estates land. Modules can depend on modules, SDKs are published automatically to native package managers, and breaking changes are approved or rejected before reaching clients.

Spectastic should own the first link in this chain and none of the others. Its job is to make the design stage produce a checked-in, correctly-located, referenced contract — which makes every mechanism above available, since all four take a file as their input. Publishing packages, running registries and brokering compatibility are solved by tools whose whole purpose that is, and a spec tool that grew a package publisher would be repeating precisely the category error the corpus survey warned against when it refused to absorb a vector store.

The naming problem this would have hit is already solved. A cross-repo contract needs a stable, globally-meaningful name, and until recently spectastic's spec estate had none — spec ids are repo-local integers. That gap closed with 067: an owner-qualified project identity in spectastic.json read through a single-source-of-truth resolver, a canonical federation-unique URI of the form spectastic://<project>/spec/<spec-id> with an optional anchor fragment, and a deterministic spectastic id to print it. Critically for this question, that identity is unified rather than parallel — an unset corpus.marketplace derives from project, so one coordinate already qualifies both specs and the corpus.

So a contract does not need a naming scheme invented for it; it needs to be another resource kind under the coordinate that exists — the same shape as the spec URI, differing in the kind segment rather than in the authority. That is a materially better position than this survey expected to find, and it removes the only structural blocker on the third slice. What remains open is not what to call an exported contract but which distribution mechanism to bless — and that is an organizational question the profile tier is better placed to answer than this doc is.

D-005 · The in-repo file is the export unit; an exported contract inherits 067's coordinate rather than minting one

Status
Proposed
Context
Every distribution mechanism — vendoring, generated SDK packages, registries — consumes a checked-in contract file. Producing that file reliably is the part only the lifecycle can do; distributing it is well served by existing tools. The cross-repo identity this would otherwise have needed already exists: 067 landed an owner-qualified project and a spectastic://<project>/… URI scheme, unified with the corpus coordinate.
Decision
Ship the contract file and its reference now, and treat that file as the export unit: a consumer vendors it, generates from it, or publishes it with tooling of their choice. When a spectastic-owned export surface is built, it MUST address contracts as a resource kind under 067's existing coordinate rather than introduce a contract-specific naming scheme — the identity question is settled, so only the distribution mechanism remains open.
Consequences
+ Unblocks the motivating scenario immediately — a UI repo can consume the file the day it exists. + Avoids building a package publisher or registry that mature tools already do better. + Inherits a solved, federation-unique identity instead of minting a second scheme to reconcile later. − The handover stays manual in the interim; nothing detects that a consumer's copy has fallen behind. − A team wanting governed versioning today gets a pointer to external tooling rather than a lifecycle answer. − Binds a future export surface to 067's coordinate shape, so a later change there propagates here.

8 · Profile sensitivity — what each rung should buy

This should not be a flat behaviour, and the ladder already exists. A throwaway internal tool and a governed enterprise interface want very different amounts of this, which is exactly what profiles are for — and the contracts axis already names four rungs that nothing currently reads. The useful move is to give them mechanical meaning rather than invent a parallel scale.

API maturity models converge on the same progression and, helpfully, on where automation enters. Style guides appear first as written expectations checked in code review; linting becomes automated a rung later; registries, versioning policy and spec-as-source-of-truth arrive later still.A five-level API management maturity model: ad-hoc → standardized ("a written API style guide exists … compliance is checked in code reviews") → managed ("linting catches style guide violations before merge") → automated (schema registries, policy as code) → optimizing [16]. Mapped onto the existing axis:

RungProfileWhat it should mean mechanically
informal lean Nothing. The design section is offered and skippable; no gate. A spike must not owe anyone an OpenAPI file.
contract-first standard A project that exposes an interface has a contract file, and the design references it. The reference resolves — a cheap, deterministic, kernel-side check. This is also the rung where the axis-versus-floor inconsistency from §2 gets settled.
contract-checked verified The contract is linted against a style ruleset and diffed for breaking changes in CI. Both are commodity: a JSON/YAML linter with OpenAPI and AsyncAPI rulesets, and a breaking-change differ with a ready-made action.
versioned+governed enterprise Versioning policy, a deprecation window, and an approval path for breaking changes — the registry rung. Almost entirely organizational; spectastic's contribution is recording the policy as a decision and keeping the artifact honest about it.

One new machine check, not four. The temptation here is to build the whole ladder. But almost all of it already exists as mature external tooling, and the enforce engine's job is to detect whether a project has wired that tooling up — which is precisely the shape of the eight categories it already runs.Spectral lints OpenAPI 2.0/3.x, AsyncAPI 2.x and generic JSON/YAML against extendable rulesets, and is built for "editors, Git hooks, continuous integration, GitHub Actions" [13]. oasdiff detects changes that "break existing API clients", emits a consumer-facing changelog and ships a GitHub Action [14]. Both Apache-2.0; the protobuf equivalent is the registry's own compatibility check [11]. So the only genuinely new deterministic check worth spectastic owning is the one no external tool can perform, because it is about spectastic's own artifacts: does the contract path a design references actually exist? A design that links a schema which was renamed or never written is a broken artifact, and nothing today would notice. Everything above that rung is a tightening of the existing contract-first category — detect a configured linter and differ, the same way the coverage category detects a declared threshold rather than a coverage library.

Runtime compatibility — consumer-driven contract testing, where consumers publish expectations and providers verify them before deployingPact's definition: contract testing checks "each application in isolation to ensure the messages it sends or receives conform to a shared understanding that is documented in a 'contract'" [15]. — is deliberately left outside this. It is a test-suite and deployment concern, it needs both sides of an integration running, and it belongs to the testing and coverage categories if anywhere. Naming it here is to mark the boundary, not to plan it.

D-006 · Tier on the existing contracts axis, and add exactly one new machine check

Status
Proposed
Context
The axis already names four rungs and nothing reads them; maturity models agree on where automation enters; and linting plus breaking-change detection are commodity, permissively-licensed, CI-ready tools that the enforce engine is already shaped to detect rather than replace.
Decision
Give the four existing rungs mechanical meaning rather than a new scale. Add one new deterministic check — a design's referenced contract path must resolve — because only spectastic can perform it. Express contract-checked as a tightening of the existing contract-first enforce category (a configured linter and breaking-change differ detected), not as new rules. Leave consumer-driven contract testing out of scope, and reconcile the standard-tier axis-versus-floor mismatch found in §2.
Consequences
+ Reuses the whole profile mechanism — waivers, structurally-undetectable handling, the fail-safe posture — rather than duplicating it. + One small rule is cheap to build and impossible to argue with. + Keeps spectastic out of the API-linter business. − A resolving path proves the file exists, not that it is valid, current, or actually served — a ceiling worth recording explicitly, as the security and observability categories already record theirs. − Detecting "a linter is configured" is weaker than "the linter passes", the same known limitation the other categories carry.

9 · Recommendation — three staged slices

Two theses anchor this: the contract is a file, and the artifact is the argument about it; and fix the altitude before adding any markup. Ordered so each slice stands alone and de-risks the next.

  1. Slice 1 — give the contract a home. Add a data-and-contracts section to templates/design.html and the matching interview questions to commands/spectastic.design.md, so the design verb asks about physical shape, interface shape and consumer contract the way it already asks about persistence class. The spec authors a proposed contract beside its design; promotion makes it effective at the project's conventional path, which the design declares. Add the one new check — a declared contract path must resolve — and settle the standard-tier axis-versus-floor mismatch. Widen contract detection to the ecosystem-conventional paths it misses today, which this slice depends on. Also tighten spec §4's guidance to conceptual-only, which is a wording change, not a schema change.
  2. Slice 2 — render it honestly. A bounded, generated view of the contract inside the design artifact: a new element, a height-capped scrolling container (the first in the design system), a visible "projection of file" label, and a staleness finding cloning verify-view-stale. Pure reviewer convenience, deliberately built after the authoritative path is proven, so a copy never precedes the original.
  3. Slice 3 — cross the repo boundary (the bet). Make the contract a first-class export: a named, versioned thing another repository can depend on and be told about when it changes, addressed as a resource kind under the spectastic://<project>/… coordinate 067 already landed. Highest value, and still correctly last — not because identity blocks it (that is solved) but because the choice between "publish a generated SDK" and "point at a registry" is an organizational one the profile tier is better placed to make, and deserves its own survey.
Do not let the design doc become the schema. The pressure will be constant and reasonable-sounding: the view is right there, the file is one more thing to open, why not just author the fields in the artifact where they render nicely. The moment that happens there are two sources of truth, and the HTML one is the one no generator reads, no linter checks, no differ diffs, and no other team can consume — which is every reason the contract exists. The line to hold: the file is the contract; the artifact is the argument about it. If a change to the shape can be made without touching the file, the boundary has already been lost.

Suggested next artifacts

  • A new spec: the two-state convention and its guarantee — a proposed contract beside the spec, promotion to the project's declared conventional path, archival of the proposal, and a validate rule that a declared contract path resolves. Slice 1, the machine half (D-004).

  • A /spectastic.propose against 042: widen contract detection beyond its four-directory, one-level reach to the ecosystem-conventional layouts it misses — src/main/proto/, nested proto/ and api/ trees, openapi/, and AsyncAPI documents under other names — and prefer a declared path over filesystem inference where the design supplies one — which also addresses the producer/consumer false positive. 10 · Caveats on the sources

  • The maturity-model rungs are a framing device, not a measurement. Vendor-published API maturity models are marketing-adjacent and their level boundaries vary between publishers. What is durable — and is corroborated by the standards guidance and by practitioner accounts — is the ordering: written convention precedes automated linting, which precedes registries and governed versioning. The mapping onto spectastic's four existing rungs is this doc's inference, not a citation.
  • "Sixty-seven of sixty-nine specs" measures this repo, which is unrepresentative. Spectastic's own specs mostly introduce no persisted entities, so the §4 prose format has never been stressed here. The claim that it degrades at scale is reasoned from the format's properties and from what peer tools chose, not observed in this corpus — a real project with thirty entities would be the honest test, and none was available.
  • The peer-tool comparison is a snapshot of fast-moving tools. Spec Kit's plan outputs and Kiro's design contents were read from current documentation in July 2026; both projects iterate quickly and either could add or drop a sidecar artifact. The structural point — that the field contains both a sidecar position and a single-artifact position, and that the sidecar position is compatible with one-artifact-per-verb — is more durable than either tool's current file list.
  • The ecosystem-layout table is reasoned from convention, not measured. The paths listed as missed follow from reading detectContract against each ecosystem's documented default layout; no corpus of real repositories was sampled. Conventions also vary within an ecosystem — plenty of Gradle projects do keep protos in a top-level proto/. The claim that survives is directional: the search path is narrow relative to the space of normal layouts, and the two examples that prompted the check both fell outside it.
  • The agent-consumption evidence is largely vendor-reported. The claim that machine-readable schemas outperform prose for agent code generation is well-attested directionally and matches this project's own experience, but the supporting write-ups come from companies selling schema tooling. Treated here as motivation, not as a measured effect size.
