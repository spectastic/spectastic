Considerations · Multi-stack

One spec, many stacks

The spec already doesn't care what language you build it in — that's the whole point of a spec. So a feature that ships in three stacks isn't a spec problem. It's a composition problem, and the tool already has the seam for it.

Status Draft Type Research synthesis Author Brian Corbin · @briancorbinxyz Created 22 Jul 2026 Sources 7 primary, verified 22 Jul 2026 Companion deployment-operations · stack-selection Read time

Some features ship across several technology stacks — a polyglot SDK in Python + TypeScript + Go, or one API contract implemented by services in different languages. spectastic today assumes one spec → one plan → one stack: the plan's §2 Technical context has a single Language(s) row, and verify.html is entirely stack-blind. The question is whether to model "N stacks in one plan." The answer is a deliberate non-goal — and it falls out of a principle spectastic already holds. A spec's success criteria are technology-agnostic by rule; the SDD canon says the same ("one durable specification, implementations across different tech stacks"). So the spec is already the stack-agnostic invariant — the stack binds one layer down, at the plan. A feature needing N stacks therefore doesn't want new per-stack sub-structure inside a plan; it wants N plans, and the tool's <spec-parent> child-slice seam already composes exactly that — one sibling spec per stack, each binding one stack, sharing a contract-first spine (the one primitive that is already language-neutral: a single OpenAPI/proto doc satisfies the contract regardless of which language declared the framework). Keeping one stack per plan is what keeps the design → tasks → verify trace honest — one stack's tests, SLOs, and coverage, not a blur. Cross-stack orchestration (codegen, polyglot CI) is a per-project build concern, not the spec tool's job. Notably, the plural primitive already exists where it belongs — detectEcosystems returns a set, and enforce/gitignore already treat a repo as many stacks; only the authoring model collapses to one, on purpose.

1 · The question — where do the stacks bind?

A real feature sometimes has to exist in more than one technology stack at once. A client SDK ships in Python, TypeScript, Go, and Java from one design. An API is defined once and implemented by a Rust service and a Node BFF. A design-system component is built for web, iOS, and Android. In each case there is one intent — one set of requirements, one definition of "done" — and several implementations.

spectastic assumes one stack. The plan's §2 Technical context carries a single Language(s) row and a single Frameworks row; the just-shipped stack-selection interview picks one stack; and verify.html has no concept of a stack at all. So the question a careful reader asks: should the tool grow a way to model N stacks inside one spec or plan — a profile axis, repeated §2 blocks, per-stack task lanes? Or is that the wrong layer entirely?

2 · What the canon already settled

The spec is supposed to be stack-agnostic. That is not a new idea to bolt on — it is the defining move of spec-driven development. SDD "decouples the what (requirements) from the how (tech stack)," so a "technology-independent spec … can generate multiple distinct implementations" — the canonical examples are literally "moving from React to Vue, from Go to Python."SDD decouples the technology-agnostic specification (what/why) from the implementation (how); one durable spec, many implementations across stacks [1], [2]. The whole value proposition is "maintain a single, durable specification while generating implementations across different technology stacks." spectastic already enforces this at the spec layer: success criteria are technology-agnostic by rule ("users complete sign-up in under 90 seconds," never "we use a faster auth library"), and requirements are outcomes, not implementations. The spec is the invariant; the stack is chosen later.

The shared spine is the contract, not the stack. When several stacks implement one thing, the field's answer is a language-neutral contract — an OpenAPI or .proto document as the single source of truth, from which each stack's client/server is generated and against which each is checked.Contract-first as the polyglot spine: OpenAPI/proto as the shared source of truth; generators emit clients/servers per language and fail the build on drift [3], [4]. "The key to making a polyglot monorepo work is a contract between languages." This is exactly the shape spectastic already has as its contract-first enforce category — and it is the piece that lets N stacks share one design without the spec having to know their names.

So the representation question has four candidate answers, and the canon points hard at the last two working together:

3 · Where spectastic stands today

The striking finding: the plural primitive already exists — one layer below the authoring model. The collapse to a single stack is a modeling choice, not a limitation of detection.

  • Detection is already plural. detectEcosystems(cwd) returns a Set<string> — python, js, java, go, rust, swift, cpp — and spectastic enforce and spectastic gitignore already consume it as a stacks[] list. A polyglot repo is a first-class, plural concept at the enforcement layer.
  • The model collapses at the plan and verify. The plan's §2 has one Language(s) <dd> (every real plan in the repo carries exactly one); a second stack can only be crammed as prose into the same cell. verify.html has no stack concept at all — it traces success criteria, SLOs, and observables, with nowhere to attach a second stack's tests. This is where "one stack" is actually assumed.
  • The composition seam already exists. The <spec-parent specid="…"> child-slice mechanism (guarded by the spec-parent-well-formed and parent-child-reciprocity rules) lets a parent spec carve out children — proven in-repo by 006 slicing into 007–014. Nothing stops those children from being per-stack instead of per-sub-feature; today they simply never are.
  • Polyglot is a deliberate skip, not a gap. Where the tool could guess a single stack for a polyglot repo, it declines: 043 — "undetectable / polyglot stack at plan → the base block stands; stack entries are skipped with a note, never guessed"; 042 — "unknown/polyglot ecosystem → detection reports what it can … never a false failure." The tool already refuses to flatten a polyglot repo into a lie.

Put together: the spec is the invariant (by principle), detection is plural (by implementation), and the only place a single stack is genuinely assumed is the authoring model — the one plan, the stack-blind verify. The question is whether that assumption is a defect to fix or a boundary to keep.

4 · Recommendation — a deliberate non-goal, with a sanctioned recipe

Keep it a non-goal. "N stacks in one plan" is the wrong layer: the spec already doesn't bind a stack, so the fix isn't new per-stack sub-structure — it's to let the existing composition seam do what it already can. What spectastic should add is guidance, not machinery.

D-001 · One stack per plan stays a deliberate boundary

Status
Proposed
Context
The spec is stack-agnostic by rule (tech-agnostic SC) and the SDD canon agrees; only the plan and verify assume one stack. Making a plan hold N stacks would fork §2 into per-stack blocks and give verify.html no honest way to trace which stack's tests cover which criterion.
Decision
Do not model multiple stacks inside a single plan or add a packaging/stack axis. Keep one stack per plan. A plan's §2, its tasks, and its verify.html trace exactly one stack's build, tests, SLOs, and coverage.
Consequences
+ The design → tasks → verify trace stays honest — no "which of these three stacks is this test for?" ambiguity. + Zero new schema, no false "polyglot = more mature" axis. + Consistent with the existing polyglot-degrade-to-skip posture (043/042). − A genuinely multi-stack feature needs more than one plan — addressed by D-002, not by stretching one plan. − Cross-stack "keep them in sync" (codegen, drift) is left to the project's build, not modelled here (a recorded ceiling).

D-002 · The sanctioned recipe — parent spec, per-stack child slices, contract-first spine

Status
Proposed
Context
A feature that truly ships in N stacks still needs to be expressed. The <spec-parent> child-slice seam already composes sibling specs, and contract-first already provides a language-neutral centre — both exist and are enforced.
Decision
Document (in commands/spectastic.spec.md + README) the recipe: a stack-agnostic parent spec (the requirements + tech-agnostic SC), a child slice per stack (each a normal spec+plan binding exactly one stack, <spec-parent> pointing home), and a contract-first artifact (OpenAPI/proto) as the shared spine every child implements. Advisory guidance, not a new element.
Consequences
+ Reuses the only existing composition seam (proven by 006→007-014) and the existing contract-first category — no new machinery. + Each child's verify trace is honest (one stack). + The parent holds the single definition of done; the contract holds the single interface. − More ceremony than one plan for a small two-stack case — the recipe is for features that genuinely warrant it, not every repo that happens to have two languages. − Per-stack conformance to the contract (does each child actually match?) is checked by the project's codegen/tests, not by spectastic — the honest boundary.

Suggested next artifacts

  • The one positive follow-on: document the parent + per-stack child-slice + contract-first recipe in commands/spectastic.spec.md and the README, so the sanctioned path is written down rather than folklore. Advisory guidance; no schema change.
  • Recorded and rejected for now: repeated per-stack §2 blocks inside one plan. It half-closes the gap — tasks and verify.html still collapse to one stack, so the trace would lie about which stack a test covers.
  • Recorded and rejected for now: making verify.html stack-aware (per-stack test/SLO lanes). Only worth building if D-001 is ever reversed; today it would be structure with no authoring model behind it.

5 · Caveats on the sources

  • "The spec is stack-agnostic" is a principle, not a guarantee. A careless author can leak an implementation detail into a requirement; spectastic's tech-agnostic-SC rule pushes against it but can't fully prevent it. The argument rests on the intended shape of a spec, which is also the SDD canon's.
  • Contract-first covers interfaces, not everything. An OpenAPI/proto contract is the spine for API-shaped multi-stack work; a polyglot SDK or a cross-platform UI shares intent but not always a single wire contract. The recipe still holds (parent spec + per-stack children), but the "shared spine" is then the parent's requirements, not a generated contract.
  • The child-slice seam wasn't designed for per-stack splits. It was built for sub-feature slicing (006→007-014). Using it per-stack is a reuse, sound in structure (the schema rules don't care why a child exists) but unproven in practice in this repo — which is exactly why D-002 is guidance to try, not a mandate.
  • "Non-goal" is revisitable. If a real project hits friction the recipe can't absorb, the rejected TBDs above are the re-entry points. The recommendation is "don't build it yet," not "never."
