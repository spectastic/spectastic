Considerations · Corpus identity

One KB id, two owners

A pack numbers its own references; the project numbers what it has ingested. Conflate the two and a citation resolves by luck — the order the packs happened to load in.

Status Draft Type Design brief — feeds sequenced specs Author Brian Corbin · @briancorbinxyz Created 26 Jul 2026 Sources 4 primary, verified 26 Jul 2026 Read time

The knowledge-corpus family (051–059) shipped an id model that breaks under real use, in two ways a code read confirms. First, both packs in the repo use KB-001, and the resolver returns the first pack whose id matches — so KB-001@2026-07-25 resolves by array order, not intent. Second, 051 requires an id "unique within the repo," while 057 requires a pack to be independently authored and published — an independent pack can't know what else will share its repo, so the two rules can't both hold. The identity has to be composite. The fix is the DOI model: a project-assigned namespace (like a DOI's agency prefix) plus a pack-internal id (like its assigner suffix) gives uniqueness without global coordination. Concretely: each pack numbers its references with a portable slug (001-settlement-windows), its curated map inlined in SKILL.md; the consuming project assigns each an opaque, stable KB-NNNN in a new root knowledge/index.md, keyed on the marketplace (name, version) coordinate. The citation token stays opaque KB-NNNN@edition — resolving against the root registry, deterministic at last — while a render layer shows the human label from the row (the hybrid). Re-importing a newer pack keeps the KB-NNNN and appends the new edition; a vanished reference is flagged, never dropped. This builds nothing — it feeds amendments to 051/052 and a new root-index-plus-ingester spec.

1 · Two failures, both in the code

The collision is real, not hypothetical. The repo ships two corpus packs, and both assign KB-001 to their first document — knowledge/spectastic-concepts's foundations doc and examples/knowledge/finance-settlement's settlement-windows doc. A citation of KB-001@2026-07-25 is therefore ambiguous, and the resolver does not detect the ambiguity: resolveCitation loops the packs and returns the first id match it finds. knowledge/resolve.ts — for (const pack of packs) { … if (current) return current; }. The answer depends on the order the loader happened to assemble the packs, which no citation author can see. Which document a citation grounds against is decided by array order.

The contract contradicts itself. 051 FR-002 says every document "MUST carry a stable source ID of the form KB-NNN, unique within the repo." But the validator only enforces uniqueness within a packknowledge/validate.ts, duplicateIdFindings(pack): "KB-NNN ids must be unique within a pack." The repo-wide guarantee 051 promises was never built — so the collision above passes validation clean. — so the two KB-001s never trip a finding. Worse, the repo-wide rule can't be satisfied even in principle: 057 requires a pack to be "installable into any skills-compatible client," authored and published on its own. An independently-authored pack cannot know which other packs a downstream repo will import alongside it, so it cannot guarantee its KB- ids are unique in that repo. Repo-uniqueness and independent authorship are mutually exclusive for a flat id.

The root cause is a single conflation: who owns the number? Today the pack author owns it (they write KB-001 into their own index.md), but the number is asked to be unique in a scope the author doesn't control (the consuming repo). Every downstream symptom follows from that one mistake.

2 · What the identifier field already knows

The problem — a globally-unique identifier without a global coordinator — is old, and its canonical answer is the DOI. A DOI is a composite: a prefix assigned by a registration agency (a namespace) and a suffix assigned by the publisher.The DOI Handbook, §2 Numbering [1]; DataCite, DOI Basics [2]. "The prefix is used as a namespace so that DOIs are globally unique without requiring global coordination for every new identifier." The publisher numbers freely inside its suffix space; the agency's prefix keeps two publishers from colliding. That is exactly our shape: the pack (publisher) numbers its references freely; the project (agency) prefixes them into a repo-unique namespace at import.

Two more rules from the persistent-identifier literature bear directly on the design. Avoid semantic meaning in the identifier. DOI/PID guidance is blunt: "adding meaning to the identifier (e.g. by using a prefix with the name of the data repository) is always dangerous, because — despite best intentions — all names can change over time."PLOS Biology, "Identifiers for the 21st century" [3]; the DOI Handbook makes the same point — once assigned, an id "shall not be changed, regardless of any changes … of the referent." That is a direct warning against baking a skill name (or a coined skill-code like SW) into the resolvable citation: rename the skill and the citation rots. And once assigned, an id never changes — the whole value of a persistent identifier is that the referent can move, be re-organised, or be re-ingested at a newer edition while the id stays put.

The platform we publish onto already supplies the coordinate we need. A Claude Code marketplace plugin carries a name and a version (pinned explicitly, or the git commit SHA when omitted), and a marketplace-level renames map that migrates a former plugin name to its current one.Claude Code plugin marketplaces [4]. The schema's granularity stops at the plugin — there is no per-reference field — so a per-reference registry has to be a spectastic artifact layered on top of (name, version), not a field inside marketplace.json. That (name, version) pair is the stable coordinate a re-import can anchor on, and renames is the precedent for how a rename migrates rather than breaks.

3 · The model — two owners, five decisions

The recommendation splits identity into two layers with two owners, and resolves the 051↔057 contradiction by giving each layer the scope it can actually guarantee.

D-001 · Two-layer identity — a portable slug plus a project-assigned KB-NNNN

Status
Proposed
Context
Repo-uniqueness (051 FR-002) and independent authorship (057) can't both hold for a flat id; the DOI model resolves it with a namespace/suffix split [1].
Decision
Each reference carries a pack-internal slug (001-settlement-windows), unique only within its pack — the portable unit the pack author owns and publishes. On import the project assigns each a stable, opaque, monotonic KB-NNNN (4-digit baseline; the id shape is already \d{3,}, so wider baselines cost nothing), unique within the repo. The pack never mints a KB- id.
Consequences
+ Both 051's repo-uniqueness and 057's independence hold, each in the scope it can guarantee. + A pack stays a clean, publishable Agent Skill with no repo knowledge. − Two id layers is more to explain than one flat number. − Every existing pack-scoped citation and both shipped packs must migrate (§5).

D-002 · A root knowledge/index.md registry, keyed on the marketplace coordinate

Status
Proposed
Context
The KB-NNNN→reference mapping has to live somewhere the project owns; marketplace.json is the publisher's manifest and has no per-reference slot [4].
Decision
Add a new root knowledge/index.md — the project's registry, one row per imported reference: KB-NNNN | marketplace | plugin | internal-slug | title | edition | path. The row is keyed on (marketplace-name, plugin-name, internal-slug) — the platform's own stable coordinate. Per-pack index.md is retired (its map moves to SKILL.md, D-005).
Consequences
+ One deterministic place to resolve a citation and to answer "what have we ingested." + Reuses the marketplace coordinate rather than inventing a parallel identity. − A new artifact to scaffold and validate. − The registry is a consumer-side file; a pack dropped in by hand (not imported) needs a registry row written for it.

D-003 · Hybrid citation — an opaque token that renders a human label

Status
Proposed
Context
A citation must be stable (PID rule: no semantic meaning, never changes) yet legible at the citation site; a baked-in skill name violates the first to serve the second [3].
Decision
The citation token stays opaque — KB-NNNN@edition — and resolves against the root registry (deterministic; the array-order bug dies here). The @edition pins the document edition from provenance, exactly as 052 defines it today — not the marketplace version. A render / validate layer surfaces the human label (finance-settlement · settlement-windows) from the registry row, so the citation reads without a mutable name in the token.
Consequences
+ Stable and legible without the semantic-rot risk of a composite token. + The resolver becomes deterministic. − The label needs the registry present at render time — in a plain-agent context the token is fully opaque (but there are no spectastic citations there anyway; the binding is harness-side per 052). − "Edition vs version" must be stated loudly or the two will be conflated (§4).

D-004 · Re-import anchors on the marketplace coordinate; supersede-by-append; flag orphans

Status
Proposed
Context
The point of the split is that re-importing a newer pack keeps citations valid; that needs a stable anchor to re-map KB-NNNN to the same reference across versions [4].
Decision
The ingester anchors on (marketplace-name, plugin-name, internal-slug), reusing the platform renames map for a renamed plugin. A matching key → the same KB-NNNN, edition bumped, and the prior edition retained (supersede-by-append, 052 FR-003 unchanged, so an edition-pinned citation still resolves). A reference present before but gone at re-import → its KB-NNNN is flagged orphaned, never silently dropped. A genuinely new reference → a fresh KB-NNNN.
Consequences
+ Citations survive a version bump; the KB-NNNN never moves. + Leans on the platform's own rename migration. − renames covers plugin renames, not per-reference slug renames — a renamed slug orphans its id (§4, finding 1). − Assigning a monotonic id is stateful; it must be kernel-serialised (P-8).

D-005 · The pack's curated map moves inline into SKILL.md

Status
Proposed
Context
A pack is one self-describing unit; a separate index.md beside SKILL.md splits the pack's map from its discovery file, and the root registry now owns cross-pack identity anyway.
Decision
Inline the pack's curated reference map into SKILL.md (the llms.txt-spirit table, now over internal slugs, no KB- ids). Retire the per-pack index.md. The pack ships as SKILL.md + references/ — a plain Agent Skill, exactly what 057 asks for.
Consequences
+ The pack is a single self-contained discovery unit; one fewer file to keep in sync. + The map is over portable slugs, so it carries no project state. − SKILL.md grows a table; a large pack's discovery file gets longer. − 051's index-scaffold and the adapter both move from writing a pack index.md to writing the SKILL.md map plus a root registry row.

4 · Adversarial pass

An honest survey names what the chosen model still gets wrong. These five are the residue after the decisions above; each is a mitigation or a recorded ceiling, in the P-8/P-11 posture — not a claim that the model is airtight. The eventual proposals run the real spectastic-critic; this is the design-time self-critique the user asked for.

1 · Reference-rename gap (against D-004). The platform renames map migrates a renamed plugin, but nothing migrates a renamed reference slug inside a pack — a re-imported pack that renamed 001-settlement-windows breaks the (name, version, slug) anchor and orphans its KB-NNNN. Recorded ceiling: pack-internal slug stability is a pack-author contract — the P-3 "ids are contracts" rule applied one layer down. The ingester flags the orphan for a human to reconcile; it never silently drops or re-maps. A content-hash lineage as a second anchor is a §6 open question, not this slice. 2 · Two meanings of "version" (against D-003). Marketplace version (a plugin release) and corpus edition (a document's provenance date) are different axes — a plugin bump need not change a document's edition, and an edition can change without a bump. Conflate them and @edition becomes meaningless. Mitigated by wording: the citation's @edition pins the document edition (052, unchanged); version is only the re-import anchor coordinate, never the citation pin. The amendment to 052 must state this in one sentence, and the registry row carries both columns so the distinction is visible. 3 · Migration is a breaking change on Accepted specs (against D-001). Every live pack-scoped @edition citation and both shipped packs are on the old 3-digit model. Re-scoping to a root registry with project-assigned ids dangles every existing citation if done without a bridge. Mitigated by a migration slice: a dedicated TBD-corpus-identity-migration maps old→new for the two packs and any live citation, with a back-compat window (the renames primitive is the precedent). The corpus is small today — two packs, one document each — so the migration is cheap now and only gets costlier; that argues for doing it before more citations accrue. 4 · Monotonic assignment is stateful (P-8) (against D-004). "Assign the next KB-NNNN" reads the current max from the registry; two imports racing, or a hand-edit, could mint a duplicate or a gap. Mitigated by ownership: assignment is a deterministic, kernel-owned step with the root registry as the single source of truth for "next id" — the same P-8 posture apply uses for its own sequential fold ranges. The ingester is the only writer of the id column; a hand-edited collision is a validate finding. 5 · Don't reinvent the platform coordinate (against §2). A bespoke composite key that ignores the marketplace's own (name, version) + renames would drift from the platform and fight the next Claude Code update. Adopted, not reinvented: D-002/D-004 key the registry on the marketplace coordinate and reuse renames; the spectastic layer is only the per-reference registry the platform schema doesn't provide. If the schema later grows a per-reference field, the registry maps onto it rather than competing.

5 · Migration — the old→new map

The corpus is small, which is the moment to change it. Two packs, one document each; a handful of citation forms in the CLAUDE.md review-hint and the specs. The migration is:

  • Packs. Rename each references/KB-001-*.md to its slug form (001-settlement-windows.md); drop the KB- id from the document frontmatter (the pack no longer mints it); move the pack's index.md table inline into SKILL.md over slugs.
  • Root registry. Write a new knowledge/index.md assigning KB-0001, KB-0002, … to the imported references, keyed on (marketplace, plugin, slug), carrying edition and path.
  • Live citations. Re-point any KB-001@edition in a <spec-decision> or the CLAUDE.md hint to its new KB-NNNN@edition. A back-compat window (accept the old form, warn) covers anything missed, mirroring the marketplace renames migration path.
  • Code + rules. resolveCitation resolves against the root registry; duplicateIdFindings splits into a repo-wide check over KB-NNNN and a pack-local check over slugs; the adapter and 051's init scaffold write the SKILL.md map plus a registry row instead of a pack index.md.

None of this is in this brief's scope — it is the shape the migration slice will take, recorded so the sequencing is legible.

6 · Open questions

  1. Baseline width. KB-NNNN (4 digits) covers 9,999 references; the id shape already accepts more. Is a 4-digit baseline right, or should the convention be width-free (\d{4,}) from the start to avoid a future re-pad?
  2. One registry or many. Is the root knowledge/index.md a single file, or one registry per marketplace source — trading a single lookup for cleaner provenance when a repo imports from several marketplaces?
  3. A second re-import anchor. Should the ingester carry a content-hash lineage alongside the (name, version, slug) key, so a reference that renamed its slug but kept its content can still be re-mapped rather than orphaned (finding 1)? Cheap to store, and it turns an orphan into a warning-with-a-guess.

7 · Out of scope

  • Amending 051 — the two-layer id shape, the pack-vs-repo uniqueness resolution, and moving the index to root plus the inline SKILL.md map.
  • The new spec — the root knowledge/index.md registry and the spectastic corpus import ingester (assign KB-NNNN, marketplace-anchored, supersede-by-append, orphan-flag).
  • Amending 052 — resolve against the root registry, the 4-digit baseline, the rendered label, and the "@edition pins the document edition" clause.
  • Migrating the two shipped packs and the live citations, and the CLAUDE.md review-hint.
  • How a retrieval index interacts with the root registry — the registry is the cited source of record; an index is a rebuildable layer above it, already 059's concern.
  • Redistribution terms of the material a re-imported pack bundles — a licensing concern, not an identity one.
