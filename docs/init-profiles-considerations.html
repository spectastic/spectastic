Considerations · Init profiles & agent guidance

Profiles: from principles to practice

Principles say what a project believes. Nothing today carries that belief into how the agent behaves tomorrow — or enforces it.

Status Draft Type Research synthesis Author Brian Corbin · @briancorbinxyz Created 09 Jul 2026 Sources ~24 primary, verified 9 Jul 2026 Prompted bya request to seed AGENTS.md + profiled principles at project setup Read time

Spectastic can author principles — a project's constitution — and then stops. It never writes the AGENTS.md/CLAUDE.md that would carry those principles into the agent's daily behaviour, and it has no notion of a project's ambition level: a throwaway tool and a regulated service get the same treatment. This doc proposes profiles — named presets (Lean · Standard · Verified · Enterprise) chosen at init, each a composition of underlying axes — that seed both a profile-shaped constitution and a lean, command-first AGENTS.md. The pivotal finding from surveying the field: the best practitioners have converged on spectastic's own P-8 — "toolchain-enforced rules belong in linters/config, not the guidance file", and LLM-generated guidance files measurably hurt. So a profile's teeth can't live in prose. They live in the toolchain, which is ecosystem-bound and only knowable at plan time — the profile carries a policy; the plan verb resolves it to the real gate (Ruff, Error Prone, clippy, clang-tidy…), escalating to a hand-built checker when the ecosystem has none. And because most projects are brownfield, a profile amends and gap-fills by category — it never overrides a tool a team already chose.

1 · The gap today

spectastic init is a pure file-copy: it drops eight slash-commands, two assets, and seven templates into a project and points the user at /spectastic.principles. That verb, when run, authors a constitution — P-1…P-N, non-negotiable, with governance. Good so far. Then the chain breaks in two places:

  1. No operating manual. The principles describe what the project believes. But the coding agent working in that repo reads its AGENTS.md/CLAUDE.md, not principles.html. Spectastic writes neither, so nothing translates the constitution into the daily instructions an agent actually consults — build/test commands, the "done" bar, the conventions it can't infer.
  2. No sense of ambition. A one-afternoon script and a regulated, always-on service are held to the same (absent) standard. There is no dial that says this project verifies everything and builds a checker when none exists versus this one just needs to not embarrass us.

The motivating cases, in the requester's words, are three points on that dial:

  • "Complete is verified." Every level of testing is part of what's produced; where no framework exists, the agent builds a tool to self-verify. Presence is never accepted for proof — the direct descendant of P-7.
  • "Enterprise / superpowers." Every feature behind a toggle; explicit framework expectations, grounding, and the best practices a staff or principal engineer would apply by reflex.
  • "Simpler." Less ceremony for a project where the heavier discipline would be overkill.

These aren't three files to write. They're three compositions of the same handful of choices — which is exactly what a profile is.

2 · What the field already agrees on

Before designing anything, it's worth noting that the guidance-file question is no longer open. AGENTS.md has become a cross-tool standard read natively by 30+ agents (Claude Code, Copilot, Cursor, Codex, Gemini CLI, Aider, Windsurf…). The community-converged shape is narrow and consistent:

  • Sections: project overview · tech stack (version-pinned) · setup/build/test commands · code style · testing · architecture notes · PR/commit conventions · security.
  • Command-first, task-organised, closure-defined — exact invocations (not descriptions), grouped by task, with explicit "done" criteria the agent can check itself against.
  • Lean and hand-written. Effective files stay under ~150 lines and carry only what the agent can't infer from the code and manifests.

Two research findings make the "lean and hand-written" point load-bearing rather than stylistic:

Gloaguen et al. (2026) found that LLM-generated context files reduce agent task-success in 5 of 8 settings while raising inference cost by over 20%. Hand-written minimal files helped by only ~4% — and only when genuinely precise. Unnecessary instruction "broadens exploration and increases reasoning cost without improving outcomes."

And the sharpest line, which any spectastic reader will recognise:

"Toolchain-enforced rules belong in linters/config, not the guidance file. If a constraint can be expressed elsewhere, it must not live here."

That is P-8 — "guarantees live in the kernel or CI, never in the prompt" — arrived at independently by the wider field. The convergence is the strongest possible endorsement of the bet spectastic already made, and it dictates the whole design below: a profile's guidance file is a lean, curated skeleton; a profile's guarantees are gates, not sentences.

The closest prior art is a spec-driven-development toolkit that pairs a constitution command (≈ spectastic's principles, with a plan-time "constitution check") and a separate step that writes the tool-specific guidance file. Useful confirmation that the what and the how are two artifacts — but it has no notion of profiles, and no brownfield/gap-fill story. Those are the gaps this doc fills.

3 · The profile model — presets over dimensions

A closed set of named profiles is memorable but rigid; a pile of independent switches is flexible but forces a decision the user shouldn't have to make at setup. The resolution is named presets over dimensions: a few profiles, each a preset composition of the same underlying axes, which an advanced user may override per-axis.

The axes:

Verification rigor
How far "done" reaches — from "it runs" up to "every level tested; build a checker if none exists."
Enforcement posture
Which promises are backed by a blocking gate vs left advisory.
Feature-toggle policy
Whether new surface ships dark behind a flag by default.
Grounding depth
How much a decision must cite before it's allowed to stand.
Framework / convention expectations
The staff-level defaults a project assumes without restating.

The presets map cleanly onto the requester's three cases (and add a sensible middle):

AxisLeanStandardVerifiedEnterprise
Verification rigor It runs; a smoke check. Unit + the demoable path. All levels; build a self-verify tool if no framework exists. Verified + perf/soak + release rehearsal.
Enforcement posture Formatter only. Lint + type-check + test gate. + security scan + custom rules for the spec's invariants. + supply-chain + toggle + staff-convention gates, all blocking.
Feature-toggle policy None. Optional. Recommended for risky surface. Every feature dark by default.
Grounding depth Light. Decisions cite. Decisions cite + risks logged. Full ledger; ungrounded decisions rejected.
Requester's word "Simpler." — "Complete is verified." "Superpowers."

A profile is therefore a name plus a row of axis values. It ships as data (a manifest), not code — which is what lets init stay deterministic (§5) and lets a future profile be added without touching a verb.

4 · Two artifacts, one profile — the what and the how

A profile fills two different documents, and conflating them is the trap the research warns against.

principles.html — the whatAGENTS.md — the how
RoleThe constitution: non-negotiable beliefs.The operating manual: the agent's daily instructions.
ReaderHumans + the spec/plan verbs.The coding agent, every session.
ShapeProse principles, governance, semver.Lean, command-first, ≤~150 lines, "done" criteria.
How the profile fills itPre-seed a principle preset, then interview to refine.A deterministic, profile-keyed skeleton, then human-refined.
Why that wayBeliefs need judgement — the interview earns them.Generated prose hurts (§2); a curated skeleton the human tightens is what wins.

On the guidance file itself, the decision is AGENTS.md as canonical, with a thin CLAUDE.md that points at it — the emerging convention that avoids two files drifting apart. This deliberately reverses spectastic's own 021 deferral ("promote agent-facing detail into AGENTS.md only if/when spectastic goes cross-tool"): the file is now a cross-tool standard in its own right, so the trigger the deferral waited for has arrived. The verification detail P-7 currently delegates to CLAUDE.md is exactly the kind of content that belongs in the canonical file.

Crucially, the AGENTS.md a profile writes stays command-first and points at the gate — run just check, not a paragraph re-explaining the lint rules. Restating enforceable rules in prose is the anti-pattern §2 measured. The rules live in the toolchain; the manual just names the command.

5 · Where it lives — init selects, principles authors

Three homes are possible; the split follows directly from §2 and §4.

OptionWhat it meansVerdict
init selects + seeds; principles authors init --profile deterministically records the choice, drops the lean profile-keyed AGENTS.md skeleton + thin CLAUDE.md, and pre-seeds principles.html with the preset. /spectastic.principles, now profile-aware, runs the interview to finish the constitution. Adopt. Keeps init deterministic (its whole design); honours "skeleton beats generated."
All in /spectastic.principles The principles verb gains a profile arg and authors both files; init stays a pure copy and points at it. Folds a mostly-deterministic AGENTS.md into the AI constitution verb, and moves the profile choice off the bootstrap moment where it belongs.
All in init init becomes AI-backed and generates everything at setup. Contradicts the LLM-generated-hurts evidence and couples pure file-copy with AI generation.

init already has the machinery: the buildPlan → executeWrites → printSummary pipeline and its per-file conflict prompt. Adding --profile as a selection dimension mirrors exactly how --tools was bolted on in 031 (its D-004) — a new mode over the same pipeline, no new architecture.

6 · The advisory-vs-enforced spine

This is the doc's thesis, and it is now double-anchored — spectastic's P-8 / guarantee-layer lesson and the independent field consensus of §2. A profile makes promises. Prose can ask; only a gate can guarantee. So every promise gets classified honestly:

Profile promiseAdvisory prose can…Guaranteed only by…v1 status
"Every feature behind a toggle" (Enterprise) Tell the agent to add a flag. A validate rule / CI check that fails when new surface ships un-gated. Advisory; enforcement mapped.
"All levels tested" (Verified) List the levels expected. A gate asserting the test tasks exist and run (the P-7 / verify.html lineage). Advisory; enforcement mapped.
"Build a self-verify tool when none exists" Instruct the agent to build one. A gate that a checker exists and executes in CI. Advisory; enforcement mapped.
"Decisions are grounded" (Enterprise) Ask for citations. The existing ungrounded-decision signal, promoted to a blocking rule. Partly enforced today; tighten.

v1 profiles generate prose; the doc's job is to name, for each promise, the gate that would make it real — and defer those gates to explicit follow-on specs (the guarantee layer, the 031 pre-commit precedent). A profile that quietly implied enforcement it didn't have would be the exact T-009 failure mode: advisory copy dressed as a guarantee. Honesty about the gap is the design.

7 · Ecosystem-bound enforcement — the profile is a policy, the plan resolves it

Here is the mechanism that turns the spine into teeth. A profile cannot name a linter, because the stack isn't chosen until planning. So the profile carries an enforcement policy ("Verified ⇒ lint + types + security + custom rules for the spec's invariants"), and the profile-aware plan verb resolves it to the concrete toolchain for whatever ecosystem the plan settles on — a "Toolchain / enforcement" section in design.html, the direct analogue of a plan-time constitution check.

This adds a third touchpoint to §5's split: init selects + seeds, principles authors the constitution, and plan resolves enforcement.

The escalation ladder

The resolver walks down until a promise is enforceable:

  1. Wire the ecosystem's standard gate — the row above, keyed to the chosen stack.
  2. Author a custom rule when a convention isn't expressible off-the-shelf — Semgrep is the polyglot convergence point (30+ languages, YAML patterns, "a useful rule in ~10 minutes"), with ast-grep and ESLint-flat as AST-local alternatives.
  3. Build a minimal project-specific checker when even that can't express it, or the ecosystem is too young to have the tool (the Mojo row). This is the literal spectastic verification philosophy — "the agent builds a self-verify tool when no framework exists" — and it is the Verified/Enterprise duty, not the Lean one.

The obligation therefore scales with the profile: Lean stops at a formatter; Standard reaches step 1 for lint + types + tests; Verified adds security + step 2/3 for its spec's invariants; Enterprise adds supply-chain, toggle, and staff-convention gates, all blocking in CI. And throughout, the AGENTS.md stays command-first — it points at just check; it never restates the rules (P-8, §2).

8 · Brownfield — amend, and gap-fill by category

Most projects a profile meets already exist, with tools and conventions already chosen. A profile that bulldozed them would be worse than useless. Two non-negotiable moves keep it a good citizen:

Amend, never blind-overwrite

Context. Re-running a profile on a live project must be safe. Decision. Re-run updates principles.html / AGENTS.md in place — reusing init's existing per-file conflict resolution and the principles Sync-Impact-Report + semver amend discipline — rather than clobbering. Consequence. Profiles become an ongoing dial a project can re-run as its ambition grows (Lean → Standard → Verified), not a one-shot at init.

Gap-fill by category, never override

Context. A brownfield repo may already run ESLint, or SpotBugs, or its own formatter. Decision. The plan-time resolver detects existing tooling by category — formatter · linter · type-checker · security · supply-chain · test runner — from the repo's own config and manifests (pyproject.toml [tool.ruff], .clang-tidy, biome.json/.eslintrc, build.gradle plugins, Cargo.toml lints / deny.toml, .swiftlint.yml, .pre-commit-config.yaml, CI workflows) — and fills only the missing categories. A tool the team already chose is left untouched; substitution is opt-in only, via an explicit --replace-tools. Consequence. The profile respects a codebase instead of fighting it — the greenfield-vs-brownfield axis that setup installers routinely miss.

9 · If we acted — a sketch

Not a build spec — a shape, to hand to /spectastic.spec as 041:

  • Profile definitions ship as data — a manifest sibling to commands.json, one row of axis values per named profile. Adding a profile touches no verb.
  • init --profile <name> extends the existing pipeline: record the choice, write the profile-keyed AGENTS.md skeleton + thin CLAUDE.md, pre-seed principles.html. Deterministic; no AI on this path.
  • /spectastic.principles and /spectastic.design become profile-aware — principles interviews from the preset; plan grows the "Toolchain / enforcement" section, runs the category-detection probe, and walks the escalation ladder.
  • CI drives any AI path deterministically via the existing SPECTASTIC_AI_STUB, so the profile machinery is testable without a live model.
  • The gates named in §6/§7 are separate follow-on specs — the profile scaffolds and advises in v1; the enforcement layer lands behind it, on the 031 guarantee-layer precedent.

10 · Open questions

  1. Per-axis override UX. Presets cover the common cases, but how does an advanced user override a single axis at init without turning setup into a questionnaire? A repeatable --axis verification=verified flag, an interactive fallback, or a profile-with-diffs file?
  2. Category taxonomy granularity. Is "linter" one category, or do "style linter" and "bug/security linter" need to be distinct so gap-fill adds SpotBugs to a repo that only has Checkstyle? Too coarse and it under-fills; too fine and detection gets brittle.
  3. Interaction with --tools. The 031 guarantee-layer installer already owns the pre-commit hook and command adapters. Does --profile compose with it (a Verified profile implies --tools), or stay orthogonal?
  4. Who authors the enforced-tier validate rules? "Every feature behind a toggle" needs a concrete, language-aware check. Is that a spectastic-shipped rule pack, a per-project Semgrep ruleset the profile scaffolds, or a duty handed to the agent per the ladder?
  5. Is plan-time enforcement resolution in-scope for the profiles feature, or a mapped follow-on? The clean v1 boundary is "profiles scaffold + advise"; the resolver and its gates are the natural second spec — but the line is worth drawing explicitly before 041 starts.
