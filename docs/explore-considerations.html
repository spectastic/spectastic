Considerations · Lifecycle design

Explore

Vibe coding has real value spec-driven design throws away. Here's how to keep the discovery — without keeping the fragility.

Status Draft Type Design brief (a /doc — feeds a future /spectastic.spec) Author Brian Corbin · @briancorbinxyz Created 24 Jun 2026 Sources 6 primary, verified 24 Jun 2026 Read time

Sometimes you don't know what to build until you've tried building it — and spec-driven design, by demanding the spec first, throws that discovery away. explore is a proposed extended, opt-in verb that brings the exploratory loop into the lifecycle: capture a one-line intent, build and run loosely (the SDD ceremony off, a thin principles floor on), then — when you're happy — a graduation interview classifies what you built (a throwaway spike or a keepable tracer-bullet), extracts the spec from it, and restores every relaxed gate. The running build becomes grounding="verified" evidence a cold-start spec never has. The slogan is "vibe to learn, spec to keep." It is the differentiation: where Kiro and spec-kit forbid the prototype, spectastic graduates it — and a guard (mandatory graduation) makes sure the throwaway can never ship.

1 · The gap

spectastic's lifecycle is deliberate from the first move: spec demands user stories, success criteria, an INVEST self-check, and a "smallest demoable" before a line is written. That rigor is the point — but it has a cost the rest of AI development doesn't pay: speed, a short feedback loop, and tactile back-and-forth. The reason regular AI coding feels good is that you can try something, see it run, and let the attempt tell you what you actually wanted. Spec-driven design asks you to know the answer before you've earned it.

Sometimes you don't know what to build until you've tried building it.

The field frames this as a war. "Vibe coding" — Karpathy's term, Collins Dictionary's word of the year for 2025 — means accepting AI-generated code without review; spec-driven tools (Kiro, spec-kit) were built to cure it. Their cure is prohibition: spec first, no exploration. They throw out the discovery to get the safety. That is a false choice. The exploratory build is not the enemy of a good spec — it can be its best source, if you graduate it instead of shipping it.

spectastic already has the closest thing to a fast path — the just-do inbox card ("small enough that a spec would not change the decision; one file, revert-safe; no proposal cycle"). But just-do is for changes you already understand. explore is for the case just-do can't touch: you don't yet know the shape, and the point of building is to find it.

2 · What the field does

Vibe coding is fast and fragile; SDD is safe and slow to start

The honest read on vibe coding is that its speed is real and its failure mode is also real: "working code that doesn't meet the actual requirements — cycles of prompt-and-fix that compound into a fragile codebase," code that "drifts from architectural intent, misses edge cases, and breaks under production load" (vibe vs SDD, Kiro). SDD's answer is to require a formal spec before any code — which fixes the drift but forfeits the discovery. Neither side keeps both halves. explore is the synthesis.

Discovery has a name, and the prototype is its output

Dual-track agile (Cagan & Patton) split work into a discovery track that decides what to build and a delivery track that decides how — and its load-bearing claim is the one this brief turns on: "the prototype serves as the spec for delivery" (SVPG). Discovery validates by building cheap, not by writing documents. That is precisely explore: a discovery track whose artifact is a running prototype, feeding the delivery track (spec → design → tasks).

Not all prototypes are the same — and that decides their fate

The Pragmatic-Programmer taxonomy is the sharpest tool here. A spike is a throwaway experiment to answer a question ("does this approach work?") — you keep the learning, not the code (Spike Solution). A tracer bullet is a narrowly-scoped, kept, production-error-checked skeleton you build on top of: "tracer code is not disposable; you write it for keeps" (tracer bullets). The user's instinct — call it a spike, but keep it and back-fill the spec — is really a tracer bullet. The right design doesn't force one; it classifies at graduation.

The one rule you must not break

Brooks: "plan to throw one away; you will, anyhow" — the first build's value is what you learn, not the code. But he is equally clear on the failure: delivering the throwaway "buys time, but only at the cost of agony for the user, distraction for the builders… and a bad reputation for the product" (Plan to Throw One Away). So the single non-negotiable for explore is mechanical: the prototype must not be able to ship un-graduated.

3 · The thesis — vibe to learn, spec to keep

explore is a four-move loop: intent → build loosely → graduate → restore rigor. You state a one-liner, build and run with the ceremony off, and when you're happy a graduation interview turns what you built into a real spec/plan/tasks. The decisions below carry it.

D-1 · An extended, opt-in verb upstream of spec

Status
Recommended
Context
The core lifecycle is eight verbs and guards that number. But explain already established the escape valve — an extended, opt-in tier ("eight hero verbs + an extended opt-in tier," D-007) for verbs that aren't load-bearing for every project. explore is discovery — not everyone wants it — so it fits that tier exactly.
Decision
/spectastic.explore is an extended, opt-in verb sitting upstream of spec — the discovery track. It does not join or alter the core eight; it feeds them.
Consequences
+ Verb count discipline preserved (the core stays at 8). + Reuses the explain packaging seams. − A second extended verb to maintain; the ex- pair (explain/explore) needs to read as deliberate, not accidental.

D-2 · Graduation classifies: spike vs tracer-bullet

Status
Recommended
Context
What happens to the built code is the central call. "Always throw away" (Brooks-purist) is safe but discards working code; "always keep + harden" risks blessing a messy prototype as production. The Pragmatic-Programmer split says the answer depends on what you built.
Decision
The graduation interview classifies. Spike — it answered a question; keep the learning, write a clean spec, rebuild. Tracer-bullet — it's a usable skeleton; keep the code, back-fill the spec, harden in place. The explorer chooses based on the artifact, not a blanket rule.
Consequences
+ Honours both real modes; no working code thrown away needlessly, no mess promoted by default. − Two graduation paths to specify (clean-rebuild vs refactor-to-comply); the classification itself becomes a decision that must be honest.

D-3 · A thin principles floor during explore; full rigor at graduation

Status
Recommended
Context
"Loose" needs a definition. Relax everything (incl. principles) and graduation inherits a heavy refactor; keep everything and the vibe is gone. The user's distinction — load-bearing vs necessary-but-not — draws the line.
Decision
During explore, a thin principles floor stays on — the cheap, foundational ones (single-file, semantic tags). The SDD ceremony is off: no test-first, no requirement IDs, no INVEST, no smallest-demoable, no proposal cycle. Every relaxed gate is restored at graduation — requirement IDs, NFRs, success criteria, test-first tasks, the estimability + grounding gates, full principles compliance, and the normal quality passes (adversarial if must-tier; the plan's principles check).
Consequences
+ Fast but not feral; a tracer-bullet that kept the floor needs only a light refactor-to-comply. − The floor's exact membership is a judgment that must be drawn precisely (see §6), or it drifts.

D-4 · Quarantine + mandatory graduation — the anti-ship guard

Status
Recommended
Context
Brooks' one hard warning: the throwaway that ships is worse than no prototype. A discovery mode that relaxes gates is only safe if its output cannot be promoted silently.
Decision
An exploration's output is quarantined — a clearly-marked spike/PoC status and a location that signals "not production." Graduation is mandatory before anything ships or merges; there is no path from a loose build to production that skips it.
Consequences
+ The relaxation is safe because it's bounded; the discovery can be fearless. − Needs a real enforcement mechanism (a status the lifecycle refuses to ship, a hook, a check) — not just a convention (see §6).

D-5 · The running build is grounding="verified" evidence

Status
Recommended
Context
A cold-start spec rests on assumption — its grounding ledger (REQ-LIFECYCLE-006) is mostly assumed until a spike resolves it. An exploration has already run the thing.
Decision
Graduation extracts the spec from the build (dual-track's "the prototype serves as the spec"; specification-by-example). The facts the prototype demonstrated enter the spec's grounding ledger as verified — the strongest grounding there is. explore feeds the spec interview; it does not replace it (intent, NFRs, and edge cases the build never surfaced are still interviewed).
Consequences
+ Specs born from exploration start better-grounded than cold ones. − Requires capturing what actually ran (cross-links the verify.html Run/Demo block — the same record serves both).

4 · The graduation interview

Graduation is where the loose build re-enters the disciplined lifecycle. Three steps:

Classify
Spike or tracer-bullet (D-2)? The answer decides whether the code is kept (refactor-to-comply) or discarded (clean rebuild against the new spec).
Extract
Read the spec out of what was built — the screens, the flows, the behaviours it demonstrated become user stories, requirements, and success criteria; the facts it proved enter the grounding ledger as verified (D-5). What the build never answered — intent, quantified NFRs, edge cases — is interviewed, exactly as a cold /spectastic.spec would.
Restore
Turn the relaxed gates back on (D-3): IDs, test-first tasks, INVEST, the estimability + grounding gates, full principles, the adversarial pass if a must-tier requirement landed. The thin-floor build gets a refactor-to-comply pass (tracer-bullet) or is rebuilt clean (spike).

The output is an ordinary spec.html / design.html / tasks.html — but one whose history says "this was discovered, not guessed," with a grounding ledger to prove it.

6 · Open questions

  1. Quarantine enforcement. What actually stops an un-graduated build from shipping — a lifecycle status the verbs refuse to advance, a git hook, a branch convention, a CI check? D-4 is only as strong as this mechanism.
  2. Spike-vs-tracer-bullet mechanics. Is "refactor-to-comply" a generated task list against the principles check, and "clean rebuild" simply the normal tasks flow with the build deleted? How is the classification recorded so it can't be quietly reversed?
  3. The thin floor's exact membership. Which principles are cheap enough to keep on during explore (single-file? semantic tags?) and which wait for graduation? Drawn wrong, it either slows the vibe or grows the refactor debt.
  4. Capturing the run. How does explore record what it built and ran so it becomes verified grounding — and can that be the same record the verify.html Run/Demo block needs?
  5. Relationship to a think-first discovery mode. Explore is build-to-learn; another idea we've discussed is think-to-learn (reason before building). Both sit at the front of the lifecycle as discovery modes — are they two doors into the same spec interview, and should they share the ledger shape?

7 · Out of scope (for this /doc)

  • Building /spectastic.explore, the quarantine mechanism, or the graduation flow — this brief feeds a future /spectastic.spec.
  • A think-first discovery mode (think-to-learn) — another idea we've discussed, a sibling at the front of the lifecycle, considered separately.
  • Adopting Kiro's EARS requirement notation — out of scope; spectastic's RFC-2119 <spec-rule> form stands.
