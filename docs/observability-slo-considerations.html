Observability & SLOs from NFRs

A quantified NFR is an SLO in prose. It implies an SLI, which implies a metrics endpoint. Make that chain implicit at the elevated profiles — and give NFRs the proof leg they lack.

Status Draft Type Research synthesis Author Brian Corbin · @briancorbinxyz Created 11 Jul 2026 Sources 20 primary, verified 11 Jul 2026 Companion engineering-principles · verify Read time

SLIs, SLOs, and observability obligations descend from the NFRs in a product spec: a customer-facing non-functional requirement ("p95 < 200 ms", "99.9% available") is an SLO in prose — it implies an SLI (what you measure) which implies instrumentation (a metrics endpoint). Spectastic already captures NFRs and its template even prompts a quantified one — but nothing downstream consumes the number: verify.html traces only success criteria, so every NFR (and its latent SLO) has no proof leg. This doc makes the chain first-class, especially at verified/enterprise, via four moves: (1) a tiered observability/SLO principle; (2) an observability enforce category that detects the metrics stack (Micrometer/Actuator, Quarkus, OTel, Prometheus client) so "monitoring is possible" is a checkable floor; (3) SLOs linked to their NFR in the artifact model (two representations, presented not pre-decided); (4) a verify.html observables trace (SLO → SLI → instrumentation) that finally gives NFRs a proof leg and extends P-7 "done means verified." On the taxonomy question: categorize by the Four Golden Signals (Latency, Traffic, Errors, Saturation) as the default, with RED for request services and USE for resources — complementary lenses, not rivals. And yes: a Spring Boot / Quarkus / Go service under an elevated profile would carry the Prometheus/OTel endpoints — that's exactly what the enforce category requires, and it is statically detectable.

1 · The chain — NFR → SLO → SLI → instrumentation

Reliability engineering runs on a decomposition the Google SRE book pins down precisely. An SLI is "a carefully defined quantitative measure of some aspect of the level of service"; an SLO is "a target value or range of values for a service level that is measured by an SLI"; an SLA is the outer contract that "includes consequences of meeting (or missing) the SLOs."SLI/SLO/SLA definitions [2]. The rung above the SLO, in a product spec, is the NFR: "the API must be fast and reliable" is refined into an SLI ("fraction of requests served < 300 ms"), bounded by an SLO ("99% over 28 days"), and each SLI is exactly what instrumentation emits. ISO/IEC 25010's performance efficiency (time behaviour, capacity) and reliability (availability, fault tolerance) are the canonical NFR quality attributes that operationalize into SLOs.ISO/IEC 25010 quality characteristics as the NFR taxonomy [8]; the standard defines the attributes but does not itself prescribe SLOs — the mapping is engineering practice.

So the chain is: NFR (the product target) → SLO (the internal promise) → SLI (the measurement) → instrumentation (the metric that produces it). Spectastic already owns the first rung — it captures NFRs — but drops the chain there. The whole opportunity is to carry it through.

2 · The SRE grounding — and the taxonomy answer

Error budgets convert reliability into a currency. The gap between 100% and the SLO is the error budget (error budget = 1 − SLO); when it is spent, "the development team focuses exclusively on reliability issues until the system is within SLO." That mechanism only works if the SLIs are chosen from what users actually feel, measured at percentiles (not averages, which "obscure a long tail").Error budget = 100% − SLO; the freeze mechanism + a written error-budget policy [3]. An SLI is a ratio: good events ÷ valid events.

On your question — "Saturation, Latency, Traffic, Errors, or some other way?" — the answer is: yes, categorize, and the Four Golden Signals are the right default, but they are one of three complementary lenses.

MethodMetricsScopePerspective
Four Golden Signals (Google SRE)Latency · Traffic · Errors · SaturationUser-facing systems (the superset)"Is the user experience good?"
RED (Tom Wilkie)Rate · Errors · DurationRequest-driven services (APIs, gateways)"Are users happy?" — one dashboard per service
USE (Brendan Gregg)Utilization · Saturation · ErrorsEvery resource (CPU, memory, disk, queues)"Are the machines healthy?"

The crisp synthesis: Golden Signals ≈ RED + Saturation — RED's Rate/Errors/Duration map to Golden's Traffic/Errors/Latency, and Golden adds Saturation.Four Golden Signals — "if you can only measure four metrics of your user-facing system, focus on these four" [1]. RED = Rate/Errors/Duration, and the "USE for machines, RED for users, they're complimentary" framing [5]. USE = Utilization/Saturation/Errors "for every resource" [4]. Wilkie's own framing: "RED is about caring about your users… USE is about caring about your machines… two different views on the same system." The practical recommendation for spectastic: the Four Golden Signals are the default service-level SLI menu; use RED as the request-service specialization and USE for resource views. (One subtlety worth a footnote: "Saturation" in Golden Signals is closer to Utilization in USE — the same word means different things across frameworks.Golden-vs-RED-vs-USE comparison; the Saturation/Utilization naming overlap [7].)

SLOs can be declared as code: OpenSLO is an open YAML spec (SLO / SLI / objectives / timeWindow / budgetingMethod) that fits Git and CI — the tooling counterpart to Google's written error-budget policy.OpenSLO — declarative YAML SLOs, object model + budgeting methods [6], [6b]. That is a useful shape to keep in mind for how a spectastic <spec-slo> might look.

3 · The instrumentation reality — Spring, Quarkus, Go

Your worked example: would a Java (Spring Boot / Quarkus) or Go service end up with the Prometheus endpoints that make monitoring possible? Yes — and largely for free. Across every mainstream stack, wiring up metrics converges on the same shape: add one named dependency, get a Prometheus/OTel-format metrics endpoint plus auto-instrumented HTTP-server metrics.

StackDependency (the signal)EndpointDetectable in
Spring Bootspring-boot-starter-actuator + micrometer-registry-prometheus/actuator/prometheuspom.xml / build.gradle
Quarkusquarkus-micrometer-registry-prometheus / quarkus-opentelemetry/q/metrics (or OTLP push)pom.xml / build.gradle
Goprometheus/client_golang / go.opentelemetry.io/otel/metricsgo.mod
Nodeprom-client / @opentelemetry/*/metricspackage.json
Pythonprometheus_client / opentelemetry-*/metrics (or OTLP)pyproject.toml

Auto-instrumentation delivers the golden signals without hand-written metric code. Spring Boot auto-configures an http.server.requests timer (rate + latency + errors, one meter); Quarkus auto-times http_server_requests_seconds_*; the OpenTelemetry Java agent is zero-code (bytecode injection captures HTTP + JVM telemetry with no application changes). The stable OTel HTTP semantic conventions define http.server.request.duration (a latency histogram), http.server.active_requests, and an error.type attribute — latency, traffic, errors out of the box.Spring Actuator /actuator/prometheus + auto http.server.requests [9]; Quarkus Micrometer + /q/metrics [10]; OTel Java zero-code agent [11]; OTel stable HTTP server metrics (duration histogram, active_requests, error.type) [12].

Crucially for a detector: because instrumentation is dependency-gated (you cannot get the endpoint without the dep) and the dependency names are stable, distinctive substrings, "the metrics stack is present" is reliably detectable by substring-matching the root build manifest — and its absence is a strong "no observability at all" signal, exactly the useful direction for an enforcement floor.Prometheus client libraries + the /metrics scrape convention [13]; OpenMetrics: the endpoint SHOULD be /metrics.

Presence ≠ working. A dependency can be on the classpath but not wired (Spring's endpoint must be exposed via management.endpoints.web.exposure.include; Go's client_golang is a library, not an auto-registered agent) and an OTLP-push service has no local /metrics endpoint at all. So the right test is "detect an observability dependency," not "detect a /metrics route," and prefer registry/exporter/starter names (a deliberate export choice) over core-library names (which arrive transitively). Manifest-substring detection is necessary-signal detection; proving it's wired is a deeper config/runtime check — recorded, not hidden.

4 · Where spectastic stands today

Spectastic captures NFRs but drops the chain immediately after:

  • NFRs exist and are prompted to be quantified. They are <spec-requirement id="NFR-NNN"> under an <h3>Non-functional</h3> heading; templates/spec.html §3 literally prompts "p95 latency < 200 ms, not 'fast'." Real latent SLOs already ship — 042 NFR-002 ("well under 500 ms"), 026 NFR-001 ("≤ 1 s p95").
  • But nothing consumes the number. No SLO/SLI representation, no validate rule that an NFR be measurable, and — the sharp gap — the verify.html proof view traces only SC-NNN (success criteria). NFRs appear in no trace, so a quantified reliability target has no proof leg at all.
  • No observability anywhere. A repo-wide search for SLO / SLI / observability / metrics / prometheus / "error budget" / "golden signal" returns only incidental hits (the word "observability" as a Polish-phase cleanup bucket). Not a principle, not an enforce category, not a profile.

The machinery to fix this is, however, already shaped for it. The enforce category system (packages/core/src/enforce/) is a string-literal union + a signal table keyed on root-config-file substrings — adding an observability category is a one-line union edit plus data rows, and policy.ts/compose.ts pick it up for free. The verify.html generator already has the exact reader machinery (it walks requirement ids and phase-closing notes) — an NFR-keyed trace mirrors the existing SC-keyed one. The gap is real; the surface to close it is small.

5 · Recommendation — four moves, tiered

Make the chain first-class, weighted to the elevated profiles, keeping the principle/enforce split spectastic already uses for coverage and contract-first: the principle states the intent, a validate/enforce check gives it teeth (P-8), and the verify view proves it (P-7).

D-001 · Carry NFR → SLO → SLI → instrumentation through the profiles and the verify view

Status
Proposed
Context
SLIs/SLOs descend from NFRs; observability is what makes SLIs measurable. Spectastic captures NFRs but consumes nothing downstream, and its proof view ignores NFRs. The industry default categorization is the Four Golden Signals; instrumentation is dependency-gated and statically detectable.
Decision
Four moves: (1) A tiered observability/SLO principle — verified: "observability is instrumented; the golden signals (latency, traffic, errors, saturation) are emitted"; enterprise: "each customer-facing NFR carries an SLO with an error budget." Added to spectastic-profiles.json principles[] at those tiers. (2) An observability enforce category — detect the metrics stack (Micrometer / spring-boot-starter-actuator / quarkus-micrometer / quarkus-opentelemetry / go.opentelemetry.io/otel / prometheus/client_golang / @opentelemetry/ / prometheus_client) in the root manifest — added to verified/enterprise enforce.required so "monitoring is possible" is a checkable, hard-gated floor. Prefer registry/exporter names over core-lib names; record that presence ≠ wired. (3) SLOs linked to their NFR — presented, not pre-decided: either a first-class <spec-slo target="NFR-NNN"> carrying its SLI + target + window (mirroring how <spec-risk target> links a requirement, and shaped by OpenSLO), or an annotation on the NFR itself. The follow-on spec picks one. (4) A verify.html observables trace — a new <section id="observables"> aggregating SLO → SLI → instrumentation, grounded in the real run (does the /metrics endpoint exist? are the golden-signal SLIs emitted?). This gives NFRs the proof leg they lack and extends P-7.
Consequences
+ Turns a latent, unconsumed NFR number into a tiered principle, a machine-checkable floor, and a proven line in the verify view. + Reuses the enforce-category + verify-trace machinery almost entirely (small surface). + Answers "at what profile level" the same way the industry tiers rigor — observability is a production-grade concern, so it lands at verified, SLOs+error-budgets at enterprise. − Static detection is necessary-signal only (present ≠ wired; OTLP-push has no local endpoint) — an honest ceiling. − Principles are advisory (T-009); the enforce category + verify trace are where the guarantee lives. − Adds an artifact element (or NFR fields) — deferred to the follow-on to keep the schema change deliberate.

6 · Caveats on the sources

  • The SLI ratio wording — the SRE workbook renders it "good events / total events"; newer Google material prefers "good events / valid events" (excludes events that shouldn't count). Treat as equivalent.
  • The "NFR is the outer rung above SLO/SLI/SLA" framing is a common-practice interpretation; the SLA/SLO/SLI distinction itself is canon (SRE book), but ISO 25010 "does not explicitly discuss SLOs" — the attribute→SLO mapping is engineering practice.
  • "Go gets the golden signals for free" is weaker than the JVM claim: the reliable Go path is an explicit otelhttp handler wrap, not a zero-touch agent (eBPF auto-instrumentation is newer).
  • Detectability is necessary-signal only: a manifest match can't see whether the endpoint is exposed or the exporter started (Spring exposure config, Quarkus quarkus.otel.metrics.enabled), and an OTLP-push service has no local /metrics. Prefer exporter/registry names; treat absence as the strong signal.
