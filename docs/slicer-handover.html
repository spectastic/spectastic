Handover · agentic slicer (W-2)

Specing the value-ranked slicer

One oversized spec → many dependency-ordered child slices, ranked by value. The headliner the git-strategy arc parked behind. This is everything you need to take it to /spectastic.spec — what's decided, what's open, and the foundation it stands on.

Status Draft Type Handover (a /doc — synthesises three considerations briefs into a spec kickoff) Author Brian Corbin · @briancorbinxyz Created 2026-06-30 Feeds a future spec.html for W-2 (and likely one for R-002 first) Read time

W-2 · the value-ranked slicer takes one over-budget spec and emits N child slices, each independently demoable, ranked by RICE and ordered by dependency. It is the build-side complement to the nudges spectastic already ships (the smallest-demoable prompt, the amber/red budget band, the propose-time splitting nudge) — those flag "this is too big"; the slicer does the split. It sits on two unbuilt layers: R-002 (the dependency DAG + topological sort that sequences the children) and the git-strategy G-005 decision (how the ordered children branch and merge). The single biggest spec-shaping question: is W-2 a new verb, or a multi-agent workflow over the existing spec/propose/apply? The evidence leans workflow.

1 · What W-2 is

From roadmap-ranking: "W-2 · value-ranked slicer is the more bounded headliner: it composes the existing spec + propose + apply and adds only the ranking judge + the coverage critic." From agent-workflows: "one oversized spec → many slices, ordered by business value."

So the slicer is mostly orchestration of verbs that already exist, plus two new agentic pieces:

The ranking judge
Scores candidate slices by RICE (primary; WSJF as a portfolio cross-check). It must be a judge panel, not a single scorer — the agent-workflows brief is explicit that "a naïve 'score each slice 1–10' is fragile" against LLM-as-judge biases (position, verbosity, self-preference).
The coverage critic
Verifies the child slices actually cover the parent (nothing dropped, nothing duplicated) and that each is independently demoable — which is already spectastic's smallest-demoable prompt, applied per slice.

The slicer is the artifact form of disciplines spectastic already preaches. Reuse them: per-slice INVEST self-check, the estimability gate, the <spec-budget> bands, <spec-parent> + defer-to= reciprocity. The slicer shouldn't invent a parallel "what makes a good slice" rubric — it should run the existing ones.

2 · The foundation it stands on — R-002 (spec this first?)

RICE/WSJF rank (one number each); they do not sequence. The slicer needs hard "X before Y" ordering, and that is R-002 · order by dependency-respecting value (roadmap status: Recommend, unbuilt). Its decision, four parts:

  1. A precedence DAG over slices.
  2. A priority-respecting topological sort — RICE/WSJF breaks ties among dependency-ready slices.
  3. Elevate by the critical-path value of the unblocked subtree (a cheap foundation that unlocks a lot ranks above a high-value leaf).
  4. A vertical-slice + acyclicity guard — a cycle is an error; a foundation is a walking skeleton, not a horizontal layer.

The roadmap doc is explicit that "the W-2 slicer will need it." So the stack is:

R-002  dependency DAG + topological sort     ← foundation (independently valuable for roadmap ordering)
   ↓
W-2    value-ranked slicer                   ← produces dependency-ordered children
   ↓
G-005  splitting under the branch model      ← branches + merges those children (git-strategy)

The first decision is sequencing. Two viable paths: (a) spec R-002 first as its own slice — it's a foundation, independently valuable for any roadmap/backlog ordering, and unblocks W-2 cleanly; or (b) spec W-2 with R-002 folded in as its Phase-1 prerequisite, the way 027 folded its two contract amendments. Foundation-first discipline favours (a); the 027 precedent shows (b) works when the foundation is small. Anchor this before writing.

3 · What's already decided — don't re-litigate

  • RICE primary, WSJF cross-check for the ranking (roadmap §2.4).
  • Judge panel, not a single scorer — to counter LLM-as-judge bias (agent-workflows).
  • Each child is independently demoable — reuse the smallest-demoable / INVEST bars, don't reinvent them.
  • R-002 supplies the ordering — the slicer consumes a topological sort, it doesn't invent sequencing from scores.
  • G-005 owns the branch/merge shape of the output: a topological merge sequence on trunk (each child its own NNN-slug branch off main), stacked PRs as an opt-in, the epic integration branch rejected, the parent flipped Superseded with reciprocal defer-to= per child and each child carrying <spec-parent>, and a contiguous N-id reservation in one origin/<default> scan (the 025 spec-id-unique gate stays the net).
  • No AI as author of record — if the slicer commits via the git layer, REQ-GIT-002 applies (humans-only; Assisted-by for the model).

4 · The decisions to anchor when specing

These are the non-obvious forks a careful interview must settle:

Verb or workflow?
The load-bearing question. CLAUDE.md lists "/spectastic.split retrofit command" as deferred with the note "the workflow does this with existing verbs," and the 8-verb surface is a stated win ("don't add more without a good reason"). The agent-workflows brief frames W-2 as one of six workflows. Leaning: a multi-agent workflow that orchestrates spec/propose/apply + the judge + the critic — not a 9th verb. Confirm, because it sets the entire shape.
Where does the DAG live?
R-002's precedence graph — authored by hand in the parent spec? inferred by an agent from the slices' defer-to= / <spec-parent> reciprocity? a new <spec-dag> element? This is R-002's core data-model decision.
What triggers the slicer?
Manual invocation only, or auto-suggested when a spec crosses the red budget band (the gauge already computes it)? The propose-time splitting nudge is the existing hook to extend.
Human-in-the-loop gates
Does the slicer propose the split for confirmation (the AskUserQuestion decision-phase pattern) before minting N specs, or mint-then-review? How are the RICE inputs (reach/impact/confidence/effort) sourced — interviewed, or agent-estimated and confirmed?
Parent's fate
G-005 says Superseded by its children — but confirm the mechanics: the split proposal lands on the parent's branch; children branch off main; reciprocal defer-to=. Is the parent ever partially kept (a residual slice), or always fully superseded?
Coverage proof
How does the coverage critic prove the children cover the parent — by requirement-ID partition (every parent FR lands in exactly one child)? That's a checkable invariant worth making a success criterion.

5 · Scope boundary

W-2 owns

  • The orchestration: parent spec → candidate slices → ranked + dependency-ordered → N child spec.html.
  • The ranking judge + coverage critic agents.
  • The concrete form of G-005's method-level details (the N-id reservation, the supersede-on-split, the merge sequence emission, the --stacked opt-in) — the git-strategy brief explicitly defers these to "the W-2 / /spectastic.split spec."

Not W-2

  • R-002 itself — the dependency-ordering primitive is a foundation W-2 consumes; spec it separately (or as W-2's Phase 1).
  • The git layer — 026/027 + REQ-GIT already ship branch/commit/trailers; W-2 uses them, it doesn't rebuild them.
  • General roadmap ranking — scoring a whole backlog (W-1 · hands-off pipeline territory) is a different headliner; W-2 ranks the children of one spec.

7 · Recommended first move

Open the interview on the verb-vs-workflow question and the R-002 sequencing question — everything else hangs off those two. The cleanest path:

  1. /spectastic.spec R-002 (the dependency-ordering primitive) — small, foundational, independently valuable; gives W-2 a real dependency to build on rather than a folded prerequisite.
  2. /spectastic.spec W-2 as a multi-agent workflow over spec/propose/apply + the two agents, consuming R-002's ordering and emitting G-005's branch/merge sequence.

If the foundation feels small enough to fold, the 027 precedent (amendments-first, in one slice) is the fallback. Either way: anchor verb-vs-workflow before writing a line of the spec.
