Considerations · Version control

Git Strategy

The lifecycle already projects onto git — verb is the commit type, spec id is the scope, the slice is the branch. The work is to formalize that projection, not invent a parallel bureaucracy.

Status Draft Type Design brief (a /doc — research + considerations, feeds future meta-spec slices) Author Brian Corbin · @briancorbinxyz Created 27 Jun 2026 Sources Repo evidence (cited inline) + primary specs: Conventional Commits, git-interpret-trailers, spec-kit (see §2) Read time

Three questions drive this brief: how to secure stable ids when many developers branch in parallel; how to make smart branch/commit choices after each verb without the developer thinking about it; and how to carry git attribution (Reviewed-by, Acked-by) that falls out of spectastic's own review and authorship. The key finding is that spectastic already has a latent git grammar — its commit history follows <verb>(NNN): (verb = type, spec id = scope), its historical branches (018-explain, 019-explain-course) already match their spec directories, and its proposals already use collision-resistant <date>-<slug> ids. The recommendation is to make that grammar explicit and opt-in (default off — the house enforcement stance from C-005): feature-branch-per-spec, a verb→git commit map, a CI collision gate that keeps the readable NNN ids safe across branches, and attribution trailers derived from the <spec-meta> author/reviewer fields and the adversarial risk pass. G-005 extends the model to the case that stresses it — when a spec auto-splits into many dependency-ordered children, the topological order becomes the merge sequence (branch-per-slice on trunk; stacked PRs opt-in; the parent Superseded by its children). §3–§5 are the answers as decision cards (G-001..G-005); §6 names the downstream meta-spec slices this brief feeds; §7 is the guardrails and open questions.

1 · The opportunity — the lifecycle already projects onto git

Most teams adopting a spec workflow have to bolt git onto it: invent a branch convention, agree a commit format, decide who reviews what. spectastic was built with those seams already cut — and, without anyone designing it, the project has been using a git grammar all along. Four pieces of evidence from this very repository:

  • Commit type = verb, scope = spec id. The history reads spec(024), plan(024), tasks(024), implement(024), propose(…), apply(…), triage(…) — that is Conventional Commits, where each lifecycle verb is the commit type and the spec id is the scope. The grammar exists; it is just unwritten.
  • Branch = spec slice. The repo has carried branches named 018-explain and 019-explain-course — identical to specs/018-explain/ and specs/019-explain-course/. The slice id already doubles as the branch name in practice.
  • Collision-resistant ids already exist — for proposals. A change folder is changes/<YYYY-MM-DD>-<slug>/ (REQ-CHANGE-001). Two developers proposing on the same day rarely collide; the date prefix sorts and disambiguates. Only the global spec NNN races.
  • CI is already PR-shaped. docs/ci-examples/github-actions.yml runs spectastic validate and uploads SARIF on pull_request over specs/** — so findings already land as inline annotations on a PR diff. The review surface is assumed to be a PR.

Two checks already stand at the seams a git workflow cares about: spectastic validate (a deterministic gate any pre-commit hook or CI job can run) and P-7 (done means verified, the merge bar). And one discipline already constrains the design: the verb surface is deliberately small (eight core verbs; "don't add more without a good reason"). So this strategy adds no new verbs — it layers git onto the verbs that exist.

The thesis

Treat the artifacts as the source of truth and git as a projection of the lifecycle: branch = spec slice, commit = verb, trailers = artifact metadata. Everything below follows from making that projection explicit, opinionated, and opt-in.

2 · Prior art (cited)

The strategy borrows four established conventions and one deliberate gap. None require inventing notation.

spec-kit — branch-per-feature, numbered dirs
spec-kit creates a numbered feature branch and houses the feature under a matching numbered directory; the branch is the unit of work and the unit of review. spectastic's latent 018-explain pattern is the same shape — this brief adopts it as the default (G-002).
Conventional Commits — type(scope): subject
A machine-readable commit grammar. spectastic's verbs map onto it with zero translation: the verb is the type, the spec id is the scope (G-003).
Git trailers — Reviewed-by, Acked-by, Co-authored-by
Structured key-value lines in a commit footer, parsed by git interpret-trailers and surfaced by forges. The Linux kernel's submitting-patches process defines Reviewed-by / Acked-by as exactly the review signal spectastic produces — but does not yet record by name (G-004).
OpenSpec's deliberate no-enforcement gap (C-005)
The most-cited limitation of comparable tools is that agents ignore the specs because nothing forces them to. The house response, already on record, is an opt-in Claude Code hook running spectastic validate --strict before a commit — default off, documented loudly. This brief inherits that stance verbatim (G-003).

3 · Securing stable ids against parallel-branch collisions

spectastic's ids are contracts (P-3): stable, human-meaningful, never reused. That is a solo-developer comfort that becomes a multi-developer hazard the moment two branches mint ids without seeing each other. The collision surface, graded:

IdHow it's mintedParallel-branch risk
Spec dir NNNresolveNextId scans specs/ + explorations/, takes max+1 (packages/cli/src/commands/explore.ts:85-95) — no atomicityHigh — two branches both grab 025
FR/NFR/SC/D-NNNAI-generated, spec-local (per-slice)Low across specs (namespaced by slice); a within-spec re-entry can silently double FR-001
T-NNN (tasks)Deterministic formula from FR count (packages/core/src/commands/tasks.ts)None — regeneration is idempotent
REQ-TOPIC-NNN (project-wide)Hand-authored, 3+ dash segmentsLow — already caught by the cross-file no-duplicate-ids rule
T/I-NNN (triage/inbox)Offset-based from a caller-supplied startMedium — needs the start coordinated

Only the spec dir NNN is a genuine, unmitigated race. The instinct is to make it collision-proof by switching to a date or hash id — but that throws away what makes NNN good: it is readable, sortable, and already aligns with the branch name. The better move keeps NNN and makes the rare collision safe and loud rather than impossible.

G-001 · Keep NNN; make the branch the reservation and CI the safety net

Status
Adopt
Context
The spec dir NNN races (resolveNextId, explore.ts:85-95); FR/SC/D are spec-local so parallel specs don't collide, but a within-spec edit can double an id, and nothing checks that today (no-duplicate-ids only checks 3+-segment qualified ids cross-file).
Decision
Three parts. (a) Branch = reservation: allocate the next NNN against the remote default branch (git fetch, then scan origin/<default>) at branch-creation, and name the branch NNN-slug — the branch holding the directory is the claim. (b) CI collision gate: a new schema rule spec-id-unique (extending packages/schema/src/rules/no-duplicate-ids.ts to spec directory ids) runs on the PR against the merge base and hard-fails when two branches grabbed the same NNN — caught at merge, never silent; renumbering pre-merge is cheap because dir ids aren't referenced cross-spec until merged. (c) Within-spec duplicate check: a cheap per-file rule so a re-entry can't silently double FR-001.
Consequences
+ Keeps readable, sortable, branch-aligned ids. + The common case is safe (the branch reserves), the rare case is loud (CI fails), and the fix is a one-line renumber. − A late renumber is friction on a long-lived branch. − Requires a git fetch at allocation time when the integration is enabled. Rejected: a tracked specs/.ids registry — every branch edits it, so it becomes its own merge-conflict hotspot and duplicates what CI already checks.

4 · Branch & commit model

The "didn't have to think about branches and commits" feel comes from the verb knowing its own git shape: a verb has just written a typed artifact, so it already knows its commit type (itself), its scope (the spec id in the artifact), and which branch the slice lives on. The map below is deterministic — there is nothing for the developer to decide.

VerbBranch actionCommit
spec (new slice)create + switch to NNN-slug off the default branchspec(NNN): <title>

implementstay on NNN-slugimplement(NNN): T-xxx … per task or per drain

G-002 · Feature-branch-per-spec; merge to main when Accepted/Applied

Status
Adopt
Context
The repo already carried 018-explain / 019-explore-course branches matching their spec dirs, and the CI is already PR-shaped (docs/ci-examples/github-actions.yml). A slice is the natural unit of review.
Decision
Each spec slice is a branch named NNN-slug; a proposal is a short-lived change/NNN-<date>-<slug> branch. The slice merges to the default branch when the spec flips Accepted (its bundle is green); a proposal branch merges when Applied. Reviews, id-collision checks, and attribution all attach to the PR.
Consequences
+ A clean review boundary; the PR is where validate + SARIF + the spec-id-unique gate run. + Matches the latent pattern and spec-kit's proven shape. − A heavier flow than committing straight to main for tiny work — mitigated by leaving just-do / triage / hotfixes on main (the brief does not force a branch for one-file revert-safe work).

G-003 · Commit grammar = the verb; delivered opt-in, default OFF

Status
Adopt
Context
The history already speaks <verb>(NNN):. There is no git automation in code today, and the house enforcement stance (C-005) is opt-in, default off, documented loudly.
Decision
Formalize <verb>(NNN): <subject> (Conventional Commits) as the commit grammar, and ship the automation as an opt-in layer, never a new verb: a config switch (git.auto = off | commit | branch+commit, default off), an opt-in Claude Code hook, and spectastic init --tools as the installer — giving the already-deferred installer a concrete payload (the hook + the CI workflow from docs/ci-examples/ + a commit-message template). Each verb's "After" step gains a --commit/--no-commit escape hatch. When enabled, the verb derives type, scope, and branch from the artifact it just wrote.
Consequences
+ The "didn't have to think about it" feel, without surprising developers who run their own git flow (off by default). + No verb-surface growth. + One grammar for humans, hooks, and forges. − Two code paths (manual + automated) to keep coherent. − The hook must compose with the existing P-6 state-gate and the explore quarantine (§7).

One case stresses the model: a future spec — the W-2 value-ranked slicer / the deferred /spectastic.split — takes one oversized spec and emits many child slices. Branch-per-spec then has to fan one branch into N, and those N are not independent: the dependency layer makes them a partial order. The branch model has to say what that looks like — and spectastic has no epic / umbrella concept to lean on.

G-005 · Splitting fans the branch model into a dependency-ordered merge sequence

Status
Adopt
Context
Branch-per-spec (G-002) + auto-split (W-2) + the dependency DAG (roadmap R-002) = N child branches with a precedence order. There is no epic/umbrella concept today, so the parent spec's fate on split is also undecided.
Decision
(1) The topological sort is the merge order. Default to a topological merge sequence on trunk: each child is its own NNN-slug branch off main, merged in dependency order — ready slices in parallel, and a dependent re-branches off the updated main once its prerequisite lands (so it becomes independent). Branch-per-spec holds; the split only sequences the merges. This is the small-batch path (trunk-based dev, DORA — "three or fewer active branches … merge to trunk at least daily"; Fowler on integration frequency). (2) Stacked PRs are the opt-in — child B branches off child A, auto-restacked (Graphite / Sapling) — for the case where a dependent must be reviewed before its foundation merges; default off like G-003, and mind the ~3–4-PR cognitive ceiling. The epic integration branch is rejected (Fowler's long-lived-branch merge-hell; it contradicts the small-batch + vertical-slice + foundation-first discipline). (3) The parent is Superseded by its children — it flips to Superseded (REQ-LIFECYCLE-004), gains a reciprocal defer-to per child (the parent-child-reciprocity rule), and each child carries <spec-parent>; the split proposal lands on the parent's branch, the children branch off main. (4) Id allocation is one operation: a split reserves N contiguous NNN ids in a single scan against origin/<default> (far lower race risk than N independent devs); the spec-id-unique CI gate (G-001) stays the cross-branch safety net.
Consequences
+ Branch-per-spec survives the split and reuses §4's order for free, staying small-batch. + Parent supersession reuses the existing lifecycle + reciprocity — no new concept. − A dependent that can't wait for its foundation needs the stacked-PR opt-in (extra tooling). Method-level here: the concrete --stacked flag, the supersede-on-split automation, the N-id contiguous reservation, and how the slicer emits the merge sequence are deferred to the W-2 / /spectastic.split spec.

5 · Attribution from review & authorship

spectastic already captures authorship and produces a review signal — they just don't reach git. The <spec-meta> block carries Owner (specs) and Author (proposals) as name · handle; the adversarial risk pass (REQ-CHANGE-004) produces dispositions a human confirms (<spec-risk status="identified|accepted|mitigated|rejected">); and every status transition appends a dated <spec-changelog> entry. The mapping to trailers is direct — with one gap to close.

TrailerSource in the artifact
Author:The <spec-meta> Owner / Author — the human
Co-authored-by:Additional human authors (e.g. a proposal Author ≠ committer)
Reviewed-by:The sign-off person on In Review → Accepted — not captured today (the gap)
Acked-by:The human who dispositioned the adversarial risk pass (REQ-CHANGE-004)
Refs:The archived proposal / changelog entry — making artifact ↔ commit bidirectional
No machine attribution. Per the project rule, spectastic commits carry no AI co-author trailer. Attribution names humans only — author and reviewer. The AI is the tool, not a contributor of record.

G-004 · Derive trailers from metadata; first close the reviewer-capture gap

Status
Adopt — pending a lifecycle amendment
Context
Review is status-driven, not person-driven: REQ-LIFECYCLE-004 says "In Review → Accepted: reviewer sign-off" but records no who; the Reviewers <spec-meta> field is present but empty in every live spec; the changelog entry names the triggering condition, not the person.
Decision
Map the trailers above on the relevant commits (the flip commit carries Reviewed-by; the apply commit carries Acked-by from the risk-pass dispositioner; both carry Refs:). To make Reviewed-by real, propose a small amendment to REQ-LIFECYCLE-004: the In Review → Accepted transition MUST record the reviewer's identity — filling the Reviewers field and naming them in the changelog entry — which then flows into the trailer. Until that lands, Reviewed-by is omitted rather than faked.
Consequences
+ Review and authorship become first-class, queryable git history derived from the spec, not re-keyed by hand. + Closes a real lifecycle gap (who reviewed) worth closing regardless of git. − Adds one required field to a transition (mild ceremony). − Acked-by from an automated critic needs care: it names the human who dispositioned the finding, never the critic agent.

6 · Where each piece lands (downstream slices)

This brief is a /doc — it argues the strategy; it builds nothing. Each decision feeds a named meta-spec slice, to be specified, built, and behaviorally tested through the normal lifecycle. Sequenced by foundation-first:

① Schema rules — the CI safety net (G-001)
A spec-id-unique rule (extend packages/schema/src/rules/no-duplicate-ids.ts to spec directory ids) + a per-file within-spec duplicate rule. Pure, deterministic, unit-testable; ships ahead of any automation and is valuable on its own. Wire into docs/ci-examples/ against the merge base.
② REQ-GIT-* on the meta-spec (G-002, G-003)
A /spectastic.propose against specs/000-spectastic/ adding the branch/commit contract: the NNN-slug branch model, the <verb>(NNN): grammar, the verb→git map, and the opt-in default-off delivery. The risk pass fires (must-tier, lifecycle-touching).
③ The REQ-LIFECYCLE-004 reviewer amendment (G-004)
A small proposal making the In Review → Accepted transition record the reviewer — the prerequisite for an honest Reviewed-by. Worth doing on its own merits.
④ spectastic init --tools + the git layer (G-003)
The opt-in installer (already deferred in the meta-spec §2 out-of-scope) gains a concrete payload: the config switch, the Claude Code hook (validate-before-commit, per C-005), the CI workflow, and a commit-message template that renders the trailers from <spec-meta>. Each verb's "After" step gains the --commit hook.
⑤ Splitting under the branch model (G-005)
The W-2 slicer / /spectastic.split spec owns the concrete form: emit the child slices' topological merge sequence, the contiguous N-id reservation, the parent Superseded flip, and the --stacked opt-in. Sequenced after the branch model and the dependency layer land.

7 · Guardrails & open questions

  • Opt-in, default off. Nothing here touches a developer's git unless they enable it. The grammar and the CI gate are valuable even with automation off; the automation is the cherry, not the cake.
  • Compose with the P-6 state-gate. The apply/tasks state-gate already refuses to overwrite a past-Draft artifact. The opt-in commit hook must run after that gate, never around it — a commit is the reward for a clean verb, not a way past its refusal.
  • Respect the explore quarantine. A quarantined exploration must stay un-committable to a shippable branch by the same guard that already makes validate fail — the git layer reads, never weakens, that signal.
  • Full history on main — no squash by default. The project keeps full per-commit history on the default branch; this strategy must not propose squash-on-merge as a default. Per-verb commits are the point: they are the legible record of the lifecycle.
  • Open: monorepo vs per-project. The meta-spec lives in the same repo as the engine; a consuming project has only specs/. The NNN-slug branch model fits both, but init --tools must detect which it is installing into.
  • Open: the just-do / triage exception. Small, revert-safe work stays on main by design (G-002). The exact boundary ("one file, no contract change") is the same line the just-do triage layer already draws — reuse it, don't invent a second one.

Recommended order: ① the schema rules (foundation, independently valuable), then ③ the reviewer amendment (small, unblocks attribution), then ② the REQ-GIT-* contract, then ④ the installer that ties it together.
