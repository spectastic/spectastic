Architecture patterns for agent-built code

The field hasn't crowned one pattern. Every serious spec-driven tool prompts for architecture rather than prescribing it — and splits the decision across two layers spectastic already has.

Status Draft Type Research synthesis Author Brian Corbin · @briancorbinxyz Created 11 Jul 2026 Sources 20 primary, verified 11 Jul 2026 Read time

Two questions: which internal architecture patterns is the industry converging on for agent-built code, and where should spectastic capture that guidance? On the first: Clean / Hexagonal / Onion have consolidated into "known-good but frequently over-applied," while Vertical Slice and the Modular Monolith rise as the pragmatic greenfield defaults — usually as a hybrid (dependency discipline at the core, slices for features). On the second — the decisive finding — not one leading spec-driven tool prescribes a house pattern. Spec Kit, Kiro, OpenSpec, Tessl, and BMAD all prompt for architecture per-project, and they split it across two layers: a project-wide constitution/steering for standing principles and stack rules, and a per-feature plan/design for the concrete decision. Spectastic already has exactly that shape — principles plus plan — but carries zero architecture-pattern vocabulary anywhere in the repo. Recommendation: don't prescribe a pattern; add lightweight pattern-awareness at the plan stage — a decision-phase choice that lands an ADR and shapes §6 Project structure — matching the field and spectastic's own init(base)→plan(stack) split.

1 · The question

An agent building a downstream project has to land somewhere architecturally. If nothing tells it where, it picks — and the pick is driven by prompt phrasing, not deliberate design. So two sub-questions: (a) which internal architecture patterns is the industry actually converging on in 2025–2026, and (b) where in a spec-driven lifecycle should the pattern be captured — a project-wide rule, or a per-feature decision? The second question matters more to spectastic than the first: our job is not to have opinions about hexagonal architecture, it is to know where the decision belongs.

2 · The pattern landscape (2024–2026)

There is no single winner, and the shape of the conversation has shifted from "which layered pattern" to "how much structure does this actually need."

  • Clean / Hexagonal / Onion — consolidating, increasingly critiqued as over-engineering. The recurring 2024–2025 framing is that these are valuable for complex, long-lived systems but produce "a lot of unnecessary boilerplate," excess interfaces and adapters, and a steep learning curve on small services. They are not being abandoned — they are demoted from automatic default to "earn it."Hexagonal vs Clean pros/cons and the over-engineering critique [2]; "start simple and let the architecture grow."
  • Vertical Slice Architecture (VSA) — the rising alternative. Coined by Jimmy Bogard, VSA organizes code by feature (each slice owns its API + logic + data access) rather than by technical layer, explicitly "to fight the chaos that develops when Clean Architecture's intentions deteriorate under deadlines." N-layered vs Clean vs VSA as the live decision [3]; VSA-vs-Clean hybrid recommendation [4].
  • Modular Monolith — the clearest convergence signal. Teams are re-evaluating the cost, latency, and organizational complexity of distributed systems and treating the modular monolith as the "sweet spot," with microservices reframed as "a destination, not a starting point."Modular monolith as the 2025–26 default starting point [5], [6].

The modal 2025–2026 recommendation for a new greenfield service is a hybrid: Clean/Hexagonal dependency discipline at the domain core, vertical slices for feature delivery, packaged inside a modular monolith. "Screaming Architecture" (the directory structure should reflect the domain, not the framework) shows up as the philosophy behind VSA rather than a separately-adopted pattern.

The honest reading: the industry has converged on a meta-principle — "match structure to complexity; start simple; make dependency direction explicit" — far more than on any one named pattern. That is a strong argument against spectastic shipping a default pattern and a strong argument for making the choice a deliberate, recorded one.

3 · How spec-driven tools handle it — the crux

This is the load-bearing finding. Across the leading spec-driven and agent-native tools, the pattern is unanimous: they prompt for architecture per-project; none prescribes a house pattern. And they consistently split the capture across two layers.

ToolPrescribe vs promptWhere architecture is captured
GitHub Spec Kit Prompts / defers — constitution ships principles (Simplicity, Anti-Abstraction, Library-First), not a pattern Split: constitution = project-wide principles + phase gates; /plan = the concrete tech-stack & architecture decision
Amazon Kiro Prompts / defers Split: project-wide steering (tech.md, structure.md) holds standing stack + structural conventions; per-feature design.md documents this feature's architecture
OpenSpec Prompts / defers, deliberately non-prescriptive ("fluid not rigid") Split: project-wide project.md/AGENTS.md describe stack + patterns; per-change design.md holds the change's ADR-shaped decision
Tessl Defers — architecture is emergent from behavior; "the same spec produces different code from different agents" Specs describe what, not how; the Spec Registry is a reuse layer, not an architecture mandate
BMAD-METHOD Prompts / generates bespoke — the Architect agent produces a project-specific architecture.md Project-wide but in the planning phase, before stories (Phase 3 "Solutioning") — so architecture shapes the work breakdown
AGENTS.md standard Convention, not a prescriber Project-wide: committed "project standards, tech choices, and architecture rules"; folder-level files for component rules

The two layers are strikingly consistent. A project-wide layer (Spec Kit constitution / Kiro steering / OpenSpec project.md / the AGENTS.md standard) holds standing tech-stack rules and cross-cutting architectural principles — the things true for every feature. A per-feature layer (Spec Kit /plan / Kiro design.md / OpenSpec per-change design.md / BMAD's pre-story architecture.md) holds the concrete architecture decision for this unit of work — chosen frameworks, component design, data flow, tradeoff rationale, often in explicit ADR shape.Spec Kit constitution + /plan split [1], [9]; Kiro steering vs design [11], [14]; OpenSpec [12].

BMAD is the informative outlier: it puts the architecture decision in a project-wide doc that nonetheless lives in the planning phase, before stories — a reminder that "project-wide vs per-feature" is really "standing invariant vs decided-once-per-effort," and greenfield architecture is a once-per-project decision, not a per-story one.BMAD architecture in Phase 3, before stories [18].

4 · Agents and architecture — does telling them help?

Agents have an implicit "house style," and it is driven by the prompt, not a stable pattern. The strongest primary source coins "vibe architecting" — architecture that emerges from natural-language prompts rather than deliberate design — and shows empirically that prompt phrasing alone yields structurally different systems for an identical task: 141 LOC / 2 files vs 472 / 4 vs 827 / 6 across three prompt variants (a 5.9× code swing), warning that review "cannot keep pace with agent speed."Architecture Without Architects — vibe architecting, the 5.9× swing, the governance gap [7].

Does giving the agent an explicit architecture reduce that drift? Practitioner consensus is a confident yes — an agent "starts fresh each session" and "can systematically violate architecture decisions across every file because it never learned the rules," so the fix is explicit layer rules, naming conventions, and dependency directions in the files agents auto-read. But this is asserted in blogs, not empirically measured — the one academic source documents that drift exists without testing whether constraints fix it. The same practitioner sources add the honest belt-and-suspenders: prose conventions are "not perfect," so pair them with automated fitness functions (a check that fails the build on a violated dependency rule) — which is exactly spectastic's own P-8 posture (guarantees live in the kernel/CI, not the prose).Explicit context helps but "not perfect"; fitness functions as the real defense [8]; Claude Code guidance: stack + the 3–5 dirs that matter, kept under ~200 lines [13].

5 · Where spectastic stands today

Spectastic already has the field's two-layer shape — a project-wide principles constitution and a per-feature plan that is explicitly "stack, architecture, decisions, risks, ADRs." What it lacks is any architecture-pattern vocabulary: a repo-wide search for onion, hexagonal, clean architecture, and ports-and-adapters returns zero hits. The nearest concept is "vertical slice," but only in the value-ranked slicer (decomposing work), never internal code architecture.

Where architecture-adjacent decisions land today:

So the machinery is already in the right shape and in the right place: architecture is a plan-stage concern (§5 Decisions + §6 Project structure), which is exactly where the field puts the concrete decision. The gap is narrow — there is a slot for the decision but no prompt that makes an agent make it deliberately, and no vocabulary to make it with. Left unaddressed, "vibe architecting" is the default: the agent picks a shape from prompt phrasing and never records why.

6 · Recommendation

D-001 · Prompt for the pattern at plan time; don't prescribe one

Status
Proposed
Context
The industry has converged on a meta-principle ("match structure to complexity; make dependencies explicit"), not a single pattern, and every leading spec-driven tool prompts for architecture rather than prescribing it. Spectastic already captures architecture at plan §5/§6 but never makes the agent choose deliberately, and has no pattern vocabulary.
Decision
Add lightweight architecture-pattern awareness to the plan stage — not a house pattern. Concretely: a decision-phase AskUserQuestion ("architecture pattern") offering domain- and stack-appropriate contenders (e.g. layered / hexagonal-ports-and-adapters / vertical-slice / modular-monolith), landing an ADR in plan §5 (<spec-decision> with grounding=) that shapes the §6 Project-structure sketch. Standing, cross-feature constraints (dependency-direction rules, "no framework in the domain core") stay in principles where a project wants them; the profiles' frameworks posture axis is left as-is.
Consequences
+ Matches the field (Spec Kit / Kiro / OpenSpec) and spectastic's own init(base)→plan(stack) split — architecture is domain/stack-specific, so it is plan-time, not a profile constant or a rigid principle. + Turns "vibe architecting" into a recorded, grounded decision. + No new verb; reuses the existing decision-phase + ADR machinery. − Prose guidance is advisory (P-8): the prompt nudges, it can't guarantee the agent honors the pattern. The durable enforcement — an architecture fitness function (a dependency-rule check) — is a larger, separate effort, flagged below.
 Optional principle floor. A one-line principle — "architecture is a decided, grounded choice, not an emergent accident" — would give the plan prompt a constitution to trace to, echoing how P-7/P-8 were sourced. Worth considering but not required for the plan-stage change to land.

Suggested next artifact

  • A /spectastic.propose against the meta-spec adding the plan-stage architecture-pattern prompt (a REQ-* on the plan verb + a commands/spectastic.design.md step + a templates/design.html §6 cue), then /spectastic.implement.
  • An architecture fitness function — a validate/CI check that enforces the chosen pattern's dependency rules — is the P-8 guarantee half and a heavier, later effort; the practitioner evidence says prose alone won't hold.

7 · Caveats on the sources

  • "Explicit architecture reduces agent drift" is a strong practitioner prior, not established fact — it appears in blogs with mechanism-and-reasoning; the one academic source documents drift's existence and magnitude but explicitly does not test whether constraints reduce it.
  • "Microservices are dead / modular monolith has won" is overstated by the punchy posts; the careful reading is "modular monolith as the default starting point," with microservices still correct at scale.
  • VSA as the new default has real momentum but is concentrated in the .NET commentary sphere; the Java/Go/Node worlds lean on the "hybrid" framing. Slightly ecosystem-skewed.
  • The elaborate five-tier AGENTS.md loading hierarchy came from a third-party site, not the canonical agents.md, which describes a simpler single-file-plus-nesting model.
