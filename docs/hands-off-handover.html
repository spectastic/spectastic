Handover · hands-off pipeline (W-1)

Answering decisions without a human

The unblocker W-1 was waiting on is built. This handover nails the one design question that stops a lifecycle from running unattended: who answers the decisions, and what makes that a guarantee.

The brief named one prerequisite: the decider + effort dial. That is now built and landed (033–036). This handover records the design that makes W-1 run unattended honestly: every decision the lifecycle takes is answered by the configured Decider — human, agent, or panel — and the answer is enforced by the orchestrator (code), never by command markdown. The kernel's fixed gates already route through the Decider; the adaptive interviews are answered by injecting a decider-backed AIProvider (CLI home) or by the workflow script convening the decider per decision (Workflow home). Both are code, so P-8 holds. The punchline: decideChoice (036) already is the interview-answerer — W-1's auto-answerer is a one-line wrapper over it.

1 · What W-1 is

From the brief: "Submit a spec, walk away. After a human approves the spec, an orchestrator drives slice → design → tasks → implement → verify, pausing only at the value-laden checkpoints." It composes patterns spectastic already has (prompt-chaining the verbs, orchestrator-workers for implement, evaluator for the verify gate) and needs no new artifact types — the verbs already emit and validate them. Its one hard dependency was the "who decides" question, which the brief spun out as the decider + effort work.

That dependency is discharged. 033–036 built the Decider and wired it into every kernel checkpoint. What remains for W-1 is the orchestration — and the single design decision this handover exists to settle: how the lifecycle's decisions get answered when there is no human in the loop.

2 · The unblocker — decisions without a human

A lifecycle is a chain of decisions. Some are fixed bounded-choice gates in kernel code (propose's risk disposition, the slicer's RICE-accept, triage's hedge gate). Others are adaptive interviews — the decision-phase AskUserQuestion passes in the slash commands, where the model chooses what to ask from the live conversation. A hands-off run has to answer both without a person, and — this is the load-bearing part — it has to do so as a guarantee, not a suggestion (P-8).

2.1 · The fixed gates are already solved

033–036 routed every kernel ai.ask / critic gate through the Decider:

  • 033 — propose's adversarial critic → human / agent / panel, with the four guardrails in the kernel.
  • 034 — --effort=auto sizes the decider's depth from the change's own risk.
  • 035 — the slicer's scoring panel adopts the Decider (numeric arbitration).
  • 036 — decideChoice: the bounded-choice gates (confirmRice, escalateLayer) answer by role. Human is the default; agent/panel answer unattended.

So in a hands-off run configured decider=agent (or panel), these gates already resolve without a human, deterministically, in kernel code. Nothing more is needed for them.

2.2 · The adaptive interviews — answer them by injection, not by markdown

The slash-command interviews can't be kernel gates — the model calls the harness AskUserQuestion tool directly, and the interview is adaptive by design (that flexibility is why it lives in markdown). Telling the markdown "if decider=agent, decide it yourself" would work sometimes and fail silently others — an advisory nudge, exactly the T-009 reliability gap. So the orchestrator answers them instead, two ways, both enforceable because the orchestrator is code:

CLI driver home
The pipeline runs the verbs through their kernel/CLI path (006 FR-009) and injects an auto-answering AIProvider — one whose ask(questions) delegates to decideChoice(cfg, questions, base) instead of prompting a person. Every kernel interview point (the ai.ask<T>() surface documented on PrinciplesInput and used by the choice gates) is then answered by the configured agent/panel. The kernel just calls ask(); the guarantee is that the orchestrator chose the provider.
Workflow script home
A Claude Workflow script runs headless and cannot stop to ask a person (brief §3 note), so it must answer decisions itself. It convenes the Decider per decision — one agent() for agent, a voting fan-out for panel — the same roles, expressed as the script's own calls. The script is code, so the role is enforced, not suggested.

The punchline. decideChoice (036) already answers a Question batch by role. The CLI home's auto-answering provider is a one-line wrapper: ask = (qs) => decideChoice(cfg, qs, base). So 036 did not just wire two gates — it built the exact primitive W-1's interview-answerer needs. W-1 is now assembly, not invention.

2.3 · The human never fully leaves — escalation is the safety rail

"Hands-off" is not "no human ever." The Decider's escalation guardrail (033 FR-008) already forces irreversible / high-stakes decisions to a human regardless of configured role. In a pipeline, those escalations surface between phases: the orchestrator runs an autonomous stretch, and when an irreversible call arises it returns, the main loop raises a real AskUserQuestion gate, and the next phase launches on the answer. This is the brief's "bursts bracketed by human gates," now with a precise trigger (the risk signals) rather than a guess.

4 · Open questions for the W-1 spec

  1. Orchestrator home. CLI driver (spectastic run <spec-id> with an injected decider-provider), Claude Workflow script, or both — the CLI for portability, the script for the Claude surface? The answerer design above works for either; the packaging is the call (brief §7 Q1).
  2. Interview fidelity on the CLI path. The kernel/CLI interview surface (the ai.ask fallback on inputs like PrinciplesInput) is thinner than the slash-command's adaptive interview. Does an unattended run accept the thinner interview, or does W-1 need the decider to drive a richer question set? This is the sharpest spec question.
  3. Checkpoint granularity. One human-escalation gate (before implement) or several (after slice, plan, tasks)? Likely a flag, --checkpoints=minimal|each (brief §7 Q2).
  4. Cost ceiling & graceful degradation. A full run fans out many deciders; what is the per-run budget, and does the pipeline degrade (shallower panels, fewer voters) as it approaches it rather than halting? (brief §7 Q4)
  5. Re-entrancy. Is each verb safe to re-run unattended on a Draft artifact (the P-6 in-place path) after a failed step, or does the orchestrator need explicit checkpoint/rollback state? (brief §7 Q5)
  6. Verdict logging across the run. Each decider answer already records its grounds on the touched artifact (033 FR-009 / 036). Does W-1 also emit a per-run decision log so a walked-away human can audit what was decided and why?

5 · Out of scope / not this

  • Making the slash-command markdown interviews "use decideChoice" directly — the answerer is injected/convened by the orchestrator, never asserted in prose (that would demote the guarantee; the whole point of §2.2).
  • The slicer internals — W-1 calls slice as a step; 029/035 own it.
  • A richer decider-driven interview question set (open question 2), if the thin CLI interview proves insufficient — could be its own slice.
