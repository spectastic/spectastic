Considerations · Deployment & operations

Where DR, canary, and rollout strategy belong

They feel like one bucket — "the ops stuff." They are three. A recovery target is an NFR. A rollout strategy is a decision. The rollout machinery is infrastructure. Route each to the layer built for it, and the answer to "profile axis or per-project?" stops being a false binary.

Status Draft Type Research synthesis Author Brian Corbin · @briancorbinxyz Created 22 Jul 2026 Sources 18 primary, verified 22 Jul 2026 Companion observability-slo · agent-architecture Read time

The question — "do disaster recovery, canary testing, and deployment strategy (blue/green, rolling restarts) belong in the profile categorization, or as a per-project concern the user defines outside spectastic?" — has a false binary buried in it. These concerns are not one kind of thing, and spectastic already routes concerns by their nature: the observability/SLO chain put the principle in profiles, the threshold number in the plan, the artifact in <spec-slo>, and the proof in the verify view. Apply the same lens here. (1) Deployment strategy (blue/green · canary · rolling) is a contextual choice trading infra cost for release safety — a plan-stage decision → ADR, sibling to the architecture-pattern prompt, not a maturity ladder. (2) DR / availability / recoverability (RTO/RPO) are ISO 25010 reliability sub-attributes — targets that descend from business need, i.e. reliability NFRs quantified as SLOs; <spec-slo> already fits. (3) The runtime mechanics (Argo Rollouts / Flagger config, backups, failover, runbooks) are per-project infrastructure, out of scope — and by construction: progressive-delivery config lives in a separate GitOps repo, so root-only detection would false-fail most stacks. So it is deliberately not a profile axis (the choice is contextual, not a rigor level) and not a hard enforce category (detection is unreliable). At most, an advisory enterprise-tier principle — "safe progressive delivery", "tested disaster recovery" — in the same band as Ship dark by default and Service level objectives. Notably, "deployability" is not even a listed quality attribute in ISO 25010 — a tell that it is a decision, not a measurable axis. Packaging (containerize or run on bare-metal) is a further concern of the same decision nature — but with a twist: a Dockerfile sits at the app repo root, so unlike rollout config it is statically detectable, and the plan can seed that decision from it — still a plan-stage ADR, still not enforced.

1 · The question — one bucket, or several?

The prompt bundles four things: disaster-recovery strategy, canary testing, deployment strategy (blue/green, rolling restarts), and — implicitly — the operational readiness that decides a service is safe to ship. The instinct is to treat them as one category ("the ops stuff") and ask a single question: does the category live inside spectastic's profile ladder, or outside it as something each project defines for itself?

That framing hides the real answer. These concerns differ in kind, and a tool that already routes by kind should not flatten them. A recovery-time target is a requirement — a number that descends from what the business can tolerate. A choice between canary and blue/green is a decision — a tradeoff you make given your architecture and cost envelope. The Argo Rollouts manifest that implements the canary is infrastructure — config that lives in the delivery pipeline, often in a different repository entirely. Spectastic has a distinct home for each of those three natures already. The task is not to invent a new bucket; it is to route each concern to the layer built for it.

2 · Three different kinds of thing

The software-quality canon draws the line cleanly, and it is worth naming precisely because it settles the "axis vs decision" question on its own.

Recoverability is a quality attribute; deployability is not. ISO/IEC 25010 decomposes reliability into availability ("operational and accessible when required"), fault tolerance ("operates as intended despite faults"), and recoverability ("recover the data and re-establish the desired state" after an interruption).ISO/IEC 25010 reliability sub-characteristics — availability, fault tolerance, recoverability [1]. Disaster recovery — RTO (max tolerable downtime) and RPO (max tolerable data loss)RTO = maximum tolerable downtime; RPO = maximum acceptable data loss, measured in time [2]. — is exactly the measurable face of availability and recoverability. But "deployability" is absent from ISO 25010's quality model — the standard has no such characteristic.Deployability (and scalability, safety) are noted as missing from the ISO 25010 model [3]. That absence is the tell: recoverability is something you measure and require; how you deploy is something you decide.

Deployment strategy is an ADR-shaped tradeoff, not a rigor level. Blue/green, canary, and rolling are not points on a maturity ladder where "further right = better." They trade infrastructure cost for release safety along different axes, and the right pick depends on architecture and budget, not seniority.

StrategyWhat it doesBuys youCosts youFits
Rolling (the default)Gradually replaces old instances with newNo extra infra; steady rolloutSlow rollback; mixed versions in flightMonolith or microservice
Blue/greenTwo identical envs; swap live trafficInstant rollback (slot swap)≈2× infrastructure while both runMicroservices; low-risk-tolerance
CanaryShip to a small % first; widen if metrics holdGraduated exposure; early detectionNeeds traffic-shaping + good SLIsMicroservices with a metrics stack

The choice "involves considerations around infrastructure requirements, application architecture, and monitoring capabilities"Blue/green (instant rollback, extra resources), canary (graduated exposure), rolling (balance, no extra infra); the choice trades infra cost for deployment safety [4], [5]. — the exact shape of an architecture decision record: a context, a decision, and consequences. It belongs where spectastic already records decisions: the plan.

Packaging is the same shape of decision. Containerize or run on bare-metal (or serverless) is another ADR-shaped tradeoff — the CNCF frames "containers on bare metal or on virtual machines" as, literally, "an architectural decision."Containers on bare metal vs VMs framed as an architectural decision; the isolation/performance/cost tradeoff [15], [16]. A container buys multi-environment consistency and isolation at the cost of overhead and operational complexity — and the reverse is a real choice: for a single-server, stable, small-team, predictable-traffic workload, "Docker adds complexity without solving real problems," and bare-metal or serverless is simpler.When not to containerize — single-server, stable requirements, predictable traffic, small team: the overhead isn't earning its keep [17]; containers-on-bare-metal vs on-VMs weighs isolation against performance [18]. Not a maturity rung; a contextual pick. Same nature, same home — the plan.

Operational readiness is a checklist, not a spec field. The "is this safe to ship" gate — Google SRE's Production Readiness Review (which "look[s] at recent incidents and postmortems… gauging the demands of emergency response and the availability of well-established operational controls")Google SRE Production Readiness Review — reviews incidents/postmortems and operational controls before onboarding a service [6]. and AWS's Operational Readiness Review (a checklist covering "monitoring, security, incident response, and backup")AWS Well-Architected operational-readiness review — a consistent ORR checklist across monitoring, incident response, backup [7]; production-readiness checklists [8], [9]. — is a per-service, per-infra ritual. It draws on the requirements and decisions above, but it is not itself an artifact spectastic authors; it is an operational practice a project runs. (A recurring finding in that literature: teams "define RTO/RPO and configure multi-region failover but then never actually test whether it works"The common failure: RTO/RPO defined and failover configured but never tested [9]. — which is why the reliability target is the durable artifact and the test is an operational obligation, not a schema field.)

3 · What's detectable, and what isn't

The observability enforce category earned its place because the metrics stack is dependency-gated and statically detectable in the root manifest — add micrometer-registry-prometheus, get an endpoint; the dependency name is a stable, distinctive substring. Deployment strategy fails that test on every count, which is the decisive argument against making it an enforce category.

SignalWhere it livesDetectable at repo root?
Metrics stack (observability)App's own build manifest (pom.xml, go.mod, package.json)Yes — root-manifest substring
Deployment strategy (canary/blue-green)Argo Rollouts / Flagger CRs, k8s Deployment.strategyUsually no — GitOps repo, not the app repo
Packaging (containerize?)Dockerfile / compose.yaml at the app repo rootYes — a root file, unlike rollout config
DR posture (backups, failover)Terraform / cloud console / runbooksNo — infra tier, often another repo/tool
RTO/RPO targetsA business decisionNo — a requirement, not a file

Progressive delivery lives in a separate repo by design. The two dominant tools make this concrete. Argo Rollouts replaces the k8s Deployment resource with a Rollout CR and pairs with Argo CD; Flagger runs alongside existing Deployments, driven by a declarative analysis spec, typically with Flux.Argo Rollouts (replaces Deployment, Argo CD-native) vs Flagger (loosely coupled, works alongside Deployments) for progressive delivery [10]. In both, the strategy config is GitOps state — "component YAML, resiliency policies, and app deployments are all managed through Git pull requests with automated sync to clusters," in repository structures that "separate… base configurations, overlays for different environments, and applications."GitOps stores rollout/config as code in Git, commonly in a repo/overlay structure separate from application source [11]. Spectastic scans root-only (the sole exception being the contract-first category, which reaches into api/, proto/, schema/, contracts/). A deployment-strategy detector would therefore either see nothing in the vast majority of app repos, or require a STRUCTURALLY_UNDETECTABLE escape hatch for nearly every stack — the same warn-not-fail crutch coverage needs for Go and observability needs for Swift/C++, but here it would be the rule, not the exception. A category that can't honestly fail is not a floor.

Packaging is the one detectable exception — and still not a requirement. A Dockerfile sits at the app repo root, so unlike rollout config the tool can see it. But detectable is not required: bare-metal services, serverless functions, libraries, and CLIs are all perfectly valid without a container, so a "must have a Dockerfile" gate would false-fail whole classes of project — not because the signal is missing (as with rollout config) but because its absence is legitimate. So detection here earns something narrower and more useful than a gate: it lets the plan pre-seed the packaging decision (a detected Dockerfile → "containerized, confirm?") rather than ask it cold. Seed the decision; don't enforce the artifact.

An enforce category here would certify the wrong thing. Even where a Rollout CR is co-located, its presence proves only that a manifest exists — not that the canary analysis has meaningful SLI gates, nor that DR has ever been tested. The same "present ≠ wired" ceiling the observability category records would apply, but with far worse false-negative rates. The reliable, honest signal is the requirement (an RTO target) and the decision (a recorded strategy) — both of which are things a human states, not things a scanner infers.

4 · Where spectastic stands today

None of these concerns has a home in any of spectastic's four routing layers — but the layers they should route to already exist, and two of them already hold the adjacent concept.

  • No profile axis. The six axes (verification, enforcement, toggles, grounding, frameworks, contracts) carry nothing on deployment, rollout, or DR. The nearest neighbour is toggles (none → optional → recommended → every-feature) and its enterprise principle Ship dark by default — but that is reversible exposure (feature flags), not rollout mechanics.
  • No enforce category. The nine categories are all build/CI-gate concerns (formatter, linter, type-checker, security, supply-chain, test-runner, coverage, observability, contract-first). None is operational, and §3 is why none should be.
  • No plan row. The plan's §2 Technical-context <dl> carries Language, Frameworks, Architecture (scoped to code structure — layered / hexagonal / vertical-slice, explicitly not deployment topology), Storage, Testing, Coverage, Perf targets, Constraints. There is a Perf targets row — the one quantified NFR the plan captures — but no Deployment, Rollout, or Availability row, and the decision-phase interview never asks the strategy question.
  • No spec artifact. The just-landed <spec-slo target="NFR-NNN"> (047) and its verify trace (048) give reliability NFRs a first-class objective/SLI/error-budget shape and a proof leg — but availability there is an SLO objective measured on the golden signals, and nothing models a recovery target (RTO/RPO) or a deployment decision as such.

So the gap is real, but the machinery is not missing — it is unused for these concerns. Deployment strategy wants the plan's decision phase (which already produces ADRs). DR wants the NFR → SLO chain (which already exists). The work is routing, not building a new layer.

5 · Recommendation — route by nature

Answer the "profile axis or per-project?" question by refusing its binary. The intent lands as plan and spec artifacts inside spectastic, at the layer matched to each concern's nature; the implementation stays per-project infrastructure outside it. This is the same split-by-nature move the observability/SLO chain made, applied one band over.

D-001 · Deployment strategy → a plan-stage decision → ADR (not a profile axis)

Status
Proposed
Context
Blue/green vs canary vs rolling is a contextual tradeoff of infra cost against release safety, gated by architecture and budget — not a maturity level. ISO 25010 does not even list "deployability" as a quality attribute. The plan already runs a decision-phase interview and emits <spec-decision> ADRs, and already asks the sibling architecture-pattern question.
Decision
Add deployment strategy as a plan-stage decision-phase question — "How does this ship: rolling (default) / blue-green / canary / not-in-scope?" — anchored via AskUserQuestion and recorded as a <spec-decision> ADR when non-default. It rides the same rails as the pending architecture-pattern prompt and may fold into that pass. Not an axis, not enforced.
Consequences
+ The strategy becomes a recorded, reviewable decision instead of tribal knowledge. + Zero new schema — reuses the plan's ADR machinery. + Keeps the profile ladder honest (no false "canary = more mature" rung). − Advisory only; nothing verifies the strategy is actually wired (correctly — that's infra's job). − One more decision-phase question to keep from bloating the interview.

D-002 · DR / recoverability → a reliability NFR quantified as an SLO

Status
Proposed
Context
RTO/RPO and availability are ISO 25010 reliability sub-attributes — targets that descend from business tolerance. Spectastic captures NFRs and, since 047, quantifies reliability NFRs as <spec-slo> with objective/window/error-budget. Availability is already an SLO objective measured on the golden signals; a recovery target is the same shape.
Decision
Treat DR targets as reliability NFRs, scaffolded so a recovery objective (RTO/RPO) and its SLO are a prompted shape, not a blank. Light guidance/template work — a reliability-flavoured NFR prompt in the spec template and an example <spec-slo> carrying a recovery objective — rather than a new element. The verify observables trace (048) then gives it the same proof leg as any other SLO.
Consequences
+ Reuses the whole NFR → SLO → verify chain that just landed; no new artifact type. + An RTO/RPO becomes a first-class, traceable target instead of prose. + Consistent with how latency/availability are already handled. − "Recovery tested" is an operational obligation the artifact can state but not prove (the DX/SRE literature's exact failure mode) — recorded as a ceiling. − Needs the follow-on to decide whether recovery objectives need any signal vocabulary beyond the four golden signals.

D-003 · Runtime mechanics stay out of scope; offer only an advisory enterprise principle

Status
Proposed
Context
Argo Rollouts / Flagger config, backups, and failover live in GitOps/infra repos separate from the app source; root-only detection would false-fail most stacks, and presence wouldn't prove correctness. But the elevated profiles already carry advisory maturity principles (Ship dark by default, Service level objectives) that state intent without machine teeth.
Decision
Do not add a profile axis or a hard enforce category for deployment/DR. Optionally add one or two advisory enterprise-tier principles — "safe progressive delivery" and/or "tested disaster recovery / operational readiness" — to spectastic-profiles.json principles[] at the enterprise tier, in the same advisory band as SLOs and dark-launch. The runtime mechanics themselves remain the user's platform/infra concern.
Consequences
+ Keeps the enforce floor honest — no category that can't honestly fail. + Names operational maturity where it belongs (enterprise) without pretending to verify it. + Draws a clean tool boundary: spectastic holds intent, the delivery pipeline holds mechanics. − Advisory principles are a nudge, not a guarantee (T-009). − Leaves a real capability (does a canary's analysis actually gate on SLIs? has DR been drilled?) unmodelled — a recorded ceiling, revisitable if a reliable in-repo signal ever emerges.

D-004 · Packaging (containerize vs bare-metal) → a plan-stage decision, seeded from a detected Dockerfile

Status
Proposed
Context
Containerize-or-not is an architectural tradeoff (multi-env consistency + isolation vs. overhead + cost), the same nature as deployment strategy — and today it has no home in the taxonomy (no SIGNALS entry, no enforce category, no axis, no plan row). Unlike rollout config, a Dockerfile/compose.yaml is at the app repo root, so it is statically detectable.
Decision
Add packaging as a plan-stage decision-phase question, folded into the deployment-strategy prompt of D-001 — but seeded from detection: a root Dockerfile pre-fills "containerized (confirm?)", its absence pre-fills "bare-metal / serverless / n/a". Recorded as a <spec-decision> when non-trivial. Not an enforce category and not a profile axis.
Consequences
+ The plan asks a grounded question instead of a cold one — the detected artifact does the first draft. + Reuses the same ADR machinery as D-001; zero new schema. + Keeps the enforce floor honest — absence of a Dockerfile is legitimate (bare-metal / serverless / library / CLI), so a "must containerize" gate could never honestly fail. − Detection sees only that a Dockerfile exists, not whether it's good or actually used to deploy — a recorded ceiling, like the "present ≠ wired" note above. − Containerization isn't "more mature," so an axis would imply a false ordering — deliberately avoided.

6 · Caveats on the sources

  • "Deployability absent from ISO 25010" is accurate for the quality model's eight characteristics; portability/maintainability touch adjacent ground, and the 2023 revision refines wording but does not add a deployability characteristic. The claim is "not a first-class quality attribute," not "never discussed."
  • RTO/RPO as "the measurable face of availability/recoverability" is engineering-practice framing; ISO 25010 defines the attributes but does not itself prescribe RTO/RPO or SLOs — the mapping is practice, as the observability doc notes for the SLO mapping too.
  • GitOps repo separation is a strong convention, not a law. Some teams co-locate delivery config with app source (a single monorepo). The detectability argument is "unreliable enough to be a poor hard-gate," not "impossible" — which is exactly why the recommendation is advisory-principle, not enforce.
  • Deployment-strategy taxonomy blurs at the edges. "Canary" and "progressive delivery" are often used interchangeably, and rolling can be tuned to approximate a canary; the table is the common-practice three, not a partition.
