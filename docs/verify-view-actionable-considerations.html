Considerations · The verify view

A demonstration is not an instruction

The view records what the author built, what the author tested, and what the author looked at. Every one of those is a fact about the past. The reader wants a sentence in the imperative — and that is the one thing the format has no field for.

Status Draft Type Artifact critique & landscape survey Author Brian Corbin · @briancorbinxyz Created 02 Aug 2026 Companion orchestrator-placement · observability-slo Sources 9 external, retrieved 02 Aug 2026 · full audit of 61 verify views Read time

The complaint that prompted this — "I should have been left with no question of what command to run" — sounds like a failure of the Run/Demo block's discipline. It is not. An audit of all 61 verify views shows the discipline is working: the test command is copy-pasteable in 60 of 61, and the run command is present and runnable in 58. The gap is structural and narrower than it looks. run is a build command in 53 of 58 cases — pnpm -r build, cd packages/core && npx tsup — because for a library or a CLI, building is what "run" means. The command that makes the feature actually do something therefore has nowhere to go except demo, and demo is the one field the governing spec explicitly permits to be prose: it asks for "a human demo path". So the estate has 24 demos with a command buried mid-sentence, 9 with no command at all, and 19 carrying a placeholder you must substitute. Each of those is conformant. The format is not being violated; it is being satisfied. This is the canonical documentation failure that Diátaxis names — reference and how-to are different documents, and one field cannot be both, because provenance is past-tense and specific to the author's machine while instruction is imperative and must port to the reader's. The closest peer has the same unsolved gap and fails it in the opposite direction: Spec Kit's per-feature quickstart.md has a purpose contested in its own discussions, and has been reported filling with 454 lines of implementation code. There is no verify.sh in Spec Kit to copy. Recommendation: give the exercise command its own typed field distinct from the build, keep the demo as prose where prose is honest, and put the guarantee where guarantees go — execute the captured commands in CI rather than linting their grammar, which is the one move that stops the field rotting quietly the way a string field always does.

1 · The ask — grounded, and still not enough

Spec 021 built the verify view around a question it stated plainly: "It's built. How do I run it, see it work, and what do I turn on?" Its context section is blunt about the failure it was closing — dogfooding a downstream project, "the UI shipped with no way to tell how to run the whole thing, and 'done' to 'I can see it' was private archaeology."

Its first success criterion is correspondingly ambitious: a reviewer who has never seen the spec can run, toggle, test and demo the feature using only verify.html, without reading the source or asking the author. The acceptance scenario tightens it to something machine-checkable in principle — "copy-pasting the Run and Tests commands reproduces the feature's verification."

So the standard being appealed to is not new, and not imported from a competitor. It is this project's own, already ratified. The question this survey answers is why an artifact that meets that standard on its own terms still leaves a reader asking what to type.

The trigger was concrete: after landing a placement engine, the author had to ask which command exercised it. The view's demo field at that moment read rankPlacement on the producer/consumer fixture — a function name. Entirely accurate, entirely unrunnable, and entirely conformant.

2 · The audit — the discipline is working, which is the problem

All 61 verify.html files in this estate were read and their typed fields extracted. The first-pass reading of the numbers was wrong in a way worth recording, because it inverts the recommendation: measured across the whole Run/Demo block, only 9 of 60 views looked both copy-pasteable and self-evidencing, which reads as a broken format. Measured field by field, against what each field was actually specified to carry, the picture is almost the reverse.

FieldWhat it was specified to carryWhat the estate holds
tests"the exact test command"60 of 61 copy-pasteable. No placeholders, no prose. The one absence is a spec with no Run/Demo block at all.
run"build/start command(s)"58 of 61 present and runnable — but 53 of 58 are a build or install, not a start.
toggle"feature flag / env var / setting, or none"The literal string none in 50 of 61.
demo"the human demo path (click-path, import, or request)"27 open with a command · 24 bury one mid-sentence · 9 contain no command at all. 19 carry a placeholder; 12 require a manual "open and look" step; only 21 say what you should see.

Read that table in the right order and the diagnosis falls out. The two fields specified to hold commands hold commands, reliably, across 61 artifacts and many months. The field specified to hold a path a human walks holds exactly that — and a path a human walks is not a command, which is why nine of them contain no command and nobody noticed.

One absence is a genuine defect rather than a design consequence: 046 carries no run, no tests and no demo. Two more (047, 048) carry no run command. Those are three cards for triage, not evidence about the format.

3 · The missing field — run means build, and nothing means try it

For a web application, run is unambiguous and sufficient: npm start serves the thing, and the reader opens a browser. For a library or a command-line tool — which is what this estate almost entirely consists of, and what a great many downstream projects will be — "run the project" and "exercise the feature" are different acts, and only the first has a field.

The consequence is visible in adjacent rows of the same artifact. A recently landed spec records run as (cd packages/core && npx tsup) && (cd packages/cli && npx tsup) — a build — and tests as a vitest invocation. Both are correct. Neither tells a reader that the thing they want to type is spectastic owner "…". That sentence exists only in demo, sharing a field with click-paths, HTTP requests, import snippets and, in nine cases, a paragraph of English.

Status Proposed

Context CapturedRun (packages/core/src/types.ts:662) types run as "build/start command(s)" and demo as "the human demo path". An audit of 61 views finds run holds a build or install in 53 of 58 populated cases. The exercise command has no field, so it lands in demo by default.

Decision Treat this as a missing field, not as authoring laxity. Add a distinct typed field for the command that exercises the feature, separate from the command that builds the project — and leave demo as prose, because a click-path genuinely is prose and forcing it into command shape would make the honest cases dishonest.

Consequences
+ The one sentence a reader most wants acquires a home, a name and a position, instead of competing for a field with four other kinds of content.
+ Existing views stay valid: nothing currently in demo becomes wrong, and the new field is simply absent until captured — the format's existing "loud gap, never a silent blank" behaviour already covers that.
− A fourth command field is more surface to leave empty, and a field that is optional will be omitted; §7 is about why that cannot be fixed by making it required.
− The boundary between "exercise" and "demo" is a judgment call for a web UI, where starting the server may be the whole of it.

4 · Two documents wearing one field

The deeper reason a stricter prose rule would not have caught this is that the Run/Demo block is doing two jobs whose requirements point in opposite directions.

Diátaxis separates reference — "technical description; facts a user needs in order to do things correctly… free of distraction and interpretation" — from how-to guides, which are "goal-oriented", address "an already-competent user", and are "strictly about doing". The framework's central claim is that these are different documents, and that conflating them degrades both.

The verify view is a reference artifact by design and by principle. P-7 — done means verified — requires that what it records be what actually happened; 021's own criterion insists the fields be "grounded evidence, not aspirational". The format already carries a provenance flag for exactly this: verified: false renders a visible "Suggested — not yet run" banner. That is a reference document being careful about its facts, and it works.

But the reader arriving at the file wants a how-to. And the two have incompatible tenses. Provenance is past and particular — I ran this, on my machine, against that fixture, which is why spectastic change-risk in a real git fixture repo is a perfectly good provenance record and a useless instruction: the fixture was real, and it was mine. Instruction is imperative and portable — you run this, anywhere. A single free-text field will drift toward whichever the author is thinking about while writing, and the author, having just finished the work, is always thinking about what they did.

Status Proposed

Context The block serves provenance (P-7, the verified flag, "grounded not aspirational") and instruction (021 SC-001, "a reviewer… can run, toggle, test and demo… without asking the author") through the same untyped string fields. Diátaxis names this conflation as a standard failure mode.

Decision Keep both jobs in one artifact — a reader should not need two files — but stop expecting one field to serve both. Provenance is the record of the run; instruction is what a stranger should type. Where they coincide, capture once and render twice; where they diverge, the instruction is the one that must port.

Consequences
+ Explains why every previous tightening of this block improved grounding without improving usefulness: the two were never in tension, they were never distinguished.
+ Gives a principled test for any future field — is this a fact about the past or a direction to the reader?
− Some captures genuinely differ between the two, and an artifact showing both risks looking like it contradicts itself.
− Two renderings from one capture is more generator complexity for a view that is already the most derived artifact in the estate.

5 · The peer tool — same gap, opposite failure

The obvious move is to copy the nearest competitor, and the premise worth correcting first is that there is something there to copy. Spec Kit ships no verify.sh. Its scripts — check-prerequisites.sh, common.sh, create-new-feature.sh, setup-plan.sh, setup-tasks.sh — are lifecycle plumbing that scaffolds and validates the artifacts themselves. None of them verifies a built feature.

What Spec Kit does emit per feature is quickstart.md, and it is instructive precisely because it is unsettled. A discussion opened in its own repository asks what the file is for, noting the "exact role isn't clearly described in the official documentation"; the answer given is that it is a "lightweight onboarding and context guide rather than a formal part of the Spec Kit specification" — no validation scenarios, no runnable commands among its listed contents. Elsewhere the project's documentation says /plan "produces a quickstart guide capturing key validation scenarios." Those are two different artifacts sharing one filename. And an issue reports the practical result: on a new application, quickstart.md came back with 454 lines of models, migrations, validations and tests — implementation code, in the onboarding file.

So the comparison does not yield a design to adopt. It yields a useful calibration: this is an unsolved problem in the category, and the two tools fail it from opposite ends. Spectastic's verify view is too disciplined — grounded, terse, provably real, and quiet about what to type. Spec Kit's quickstart is too loose — a file whose purpose is contested filling with whatever the model had most recently generated. Between the two, the disciplined failure is much the better place to be standing, because adding a field to a strict format is tractable and constraining an unconstrained one is not.

6 · What the field does instead — name the entry point, then run it

Outside spec-driven tooling, the problem of "what do I type" has two well-worn answers, and neither is a document.

The first is a normalized entry point. GitHub's Scripts to Rule Them All convention fixes the script names across every project — script/bootstrap, script/setup, script/test, script/server — so that a contributor who has never seen the repository already knows the command. The scripts are language-agnostic by design: script/bootstrap may call bundle install or npm install or carthage bootstrap, and the caller does not need to know which. This solves the reader's problem by removing the question rather than answering it, and it is the right shape for the project level. It does not answer "how do I see this feature work", which is what a per-spec view exists for.

The second is executing the documentation. Runme parses shell blocks out of Markdown and runs them, and its "ReadmeOps" position is the load-bearing one here: run the documented commands in CI on every commit, so that documentation is "treat[ed] with the same level of care currently afforded to source code" and cannot bitrot. The same idea is old and proven in narrower forms — Rust and Python both execute the examples in their documentation as tests.

That second answer is the one this project's own principles already point at. P-8 puts guarantees in the kernel or CI and nowhere else; the estate has repeatedly learned that a rule expressed as prose in a command file is advisory. A validate rule that greps a demo string for an imperative verb would be a fourth restatement of that mistake. Running the command is the only check that distinguishes a command from a sentence about a command.

Status Proposed

Context Four mechanisms could give a reader a runnable command: a typed field, a generated per-spec script, a normalized project-level entry point, or executing the captured commands in CI. The estate's own history (T-009, the guarantee-layer work) is that discipline expressed only in markdown does not hold.

Decision Typed field first, executed-in-CI as the guarantee. A generated verify.sh per spec is rejected: it introduces an executable artifact into specs/, is not portable across shells, and drifts from the view it was generated from — reproducing the drift problem the embedded-contract work already had to solve once. The normalized entry point is a downstream convention worth recommending, not a mechanism this artifact can own.

Consequences
+ The cheap change lands first and independently; the expensive guarantee can follow without redesign.
+ Executing captured commands in CI also detects the silent rot — a command that was true when captured and stopped being true three refactors later, which no format rule can catch.
− CI execution cannot cover the honest prose cases: "open the file in a browser and confirm the card is not clipped" is unautomatable, and the block must not start pretending otherwise.
− Running arbitrary captured strings in CI is a real hazard and would need to be opt-in per project, which weakens it as a guarantee.

7 · Why "make it required" is the wrong fix

The tempting response to an under-filled field is to make it mandatory. The toggle row is the standing argument against that: it is required today, and it is the literal string none in 50 of 61 views. It is filled, conformant, and carries no information five times in six — a row of chrome that a reader learns to skip, which is a cost paid by every other row on the page.

A mandatory exercise field would go the same way for the specs that genuinely have nothing to exercise — a schema rule, a CI workflow, a documentation change. The format's existing instinct is better and already implemented: an omitted field renders as a loud gap rather than a silent blank, so absence is visible without being forced into a lie. The pressure to fill it should come from the gap being conspicuous, not from a validator that will be satisfied with n/a.

The same argument applies one section down the page, and is handed off rather than argued here. The Observables trace on a non-service project renders rows of "quantified but has no linked SLO" — technically correct, and noise for a library that will never emit a metric. Generated rows with no data are the same defect as a mandatory field with nothing to say. That belongs to the observability survey's successor and is named in §8 rather than solved here.

Status Proposed

Context toggle is a required field holding none in 50 of 61 views. The format already renders an omitted field as a visible gap rather than a blank.

Decision The new field is optional, and the enforcement is the conspicuousness of its absence plus CI execution of what is present — never a validator that a string exists. Do not add a required field; consider whether toggle should itself become optional on the same reasoning.

Consequences
+ Avoids manufacturing a second none row and keeps the page's information density honest.
+ Consistent with how the estate already treats unrecorded evidence everywhere else.
− An optional field is omitted more often, and some specs that should carry one will not.
− Relaxing toggle is a change to a shipped format and needs its own justification; it is raised here, not decided.

8 · Recommendation — two slices, in order

  1. Give the exercise command a field. Add it to the captured shape, the generator, the rendered block and the /spectastic.implement capture prompt, distinct from the build command already in run. Optional, rendering as a loud gap when absent. Backfill is not required — every existing view stays valid — but the handful of specs whose demo already opens with a bare command are a free first pass. This is small, self-contained, and improves the artifact whether or not the second slice ever lands.
  2. Run what was captured. An opt-in check that executes the recorded build, exercise and test commands for a spec and fails when one of them no longer runs — the only mechanism that distinguishes a command from a sentence, and the only one that catches a capture that silently stopped being true. Opt-in per project, with the prose fields explicitly out of its reach.
Do not fix this by tightening the demo field. Nine demos contain no command, and every one of them is conformant: the field asks for "a human demo path", and a click-path, an import snippet and a browser check are all legitimate answers that no imperative-verb rule could distinguish from an evasion. Constraining demo would break the honest cases to discipline a gap that lives in a field which does not exist yet.

Suggested next artifacts

  • A new spec: the typed exercise command — its place in the captured shape, the generator and the implement-time capture prompt, its rendering as a loud gap when absent, and the boundary against run for projects where starting the server is the whole of it (D-001, D-002).
  • A new spec: the opt-in check that executes a view's captured commands and fails on one that no longer runs, with the prose fields explicitly out of reach and the arbitrary-command hazard addressed rather than noted (D-003).
  • A /spectastic.propose against 021: make toggle optional on the evidence that it is none in 50 of 61 views, so a required row stops costing every other row its attention (D-004).
  • Triage, not a spec: 046 carries no Run/Demo block at all, and 047 and 048 carry no run command. Three genuine gaps the audit surfaced, distinct from the format question.
  • A follow-on question for the profile catalogue: whether an elevated profile should seed a normalized project entry point, so that "what do I type" is answered by convention at the project level and the per-spec field only has to carry what is feature-specific.

9 · Caveats on the sources and the audit

  • The audit's first pass was wrong, and the error is instructive. Classifying the whole Run/Demo block at once produced "9 of 60 usable", which reads as a broken format and would have justified a much larger intervention. Measuring each field against what it was specified to carry produced almost the opposite result. The numbers in §2 are the second reading; the first is recorded here because a reviewer running their own scan may reproduce it.
  • Field classification is heuristic. "Starts with a command" is a regular expression over the first token, and it initially rejected legitimate commands beginning cd or an opening parenthesis. The corrected counts are hand-checked at the boundaries, but a reader should treat single-digit differences as noise rather than signal.
  • This estate is not a representative sample. Sixty-one views, one project, one author, one ecosystem — and a project that is itself a CLI and a set of libraries, which is precisely the shape where run collapses into build. A web-application estate might find run entirely sufficient and this whole survey beside the point.
  • The peer comparison rests on the peer's public record, not on running it. The Spec Kit findings come from a discussion thread and an issue report, both of which describe the artifact as unclear or misbehaving. That is evidence the problem is unsolved there; it is not a measurement of how the file behaves on average.
  • No mechanism was prototyped. Both recommended slices are arguments from artifact shape and shipped precedent. In particular, the claim that CI execution is tractable assumes captured commands are mostly short and hermetic — true across this estate's vitest and tsup invocations, and untested anywhere else.
  • Diátaxis is a framework, not a finding. It is used here as a lens that names the conflation cleanly. It carries no empirical claim about whether splitting the two improves reader outcomes, and none is asserted.
