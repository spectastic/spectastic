Design brief · Engineering governance

Architectural guardrails

Point the guarantee layer that already works at artifact well-formedness at architectural decisions — by promoting the prose-and-hand-typed-id convention spec-tictactoe-2 already uses into a structured, drift-guarded, machine-retrievable one, and reusing the corpus's identity and retrieval machinery to do it.

Status Draft — Phase 2, for review Type Design brief (multi-spec; sequenced in §5) Author Brian Corbin · @briancorbinxyz Created 13 Sep 2026 Follows architectural-guardrails-considerations.html (Phase 1) Decides via4 human decisions (§1) + 2 deep-research passes over the corpus subsystem Read time

Nine design items, each closing a Phase-1 gap with the smallest change and a stated boundary. The spine: author a decision in an extended <spec-decision> (born from a requirement, carrying structured scope / enforcement / posture / status / reason) → register it into a decision index that reuses the corpus's id-allocation, editions and federation coordinate (a new decision resource kind) → retrieve the active decisions governing a set of paths with spectastic adrs --for, deterministically and to a log → inject them, fenced as data, before writing → gate twice (a plan-stage constraint that fails when a declared-touched path has an unacknowledged decision; a merge-stage verdict that reconstructs from disk) → teach by composing the decision's own reason into the failure, with an optional Socratic shifu hook that never touches the verdict.

The load-bearing correction to the brief (§4): spectastic is a Node CLI and must not reimplement ArchUnit/Semgrep. The merge gate does not "execute the enforcement as a plain script" in spectastic; the ecosystem's own enforcer detects, and spectastic orchestrates it and owns the traceability composition (rule-id ↔ decision-id ↔ reason) that no architecture-test tool provides. That composition — not re-detection — is the value. Two more brief assumptions are corrected: scope cannot be package-only (language-agnostic paths are the floor), and the blocking default is standard, not enterprise.

1 · What Phase 1 and the human decisions settled

Phase 1 scored the rubric 2 full · 5 partial · 3 does-not and named five gaps ordered by Priya-risk. This brief closes them. Four decisions that forked the design were put to a human and are now fixed:

Decision home (the governing fork)
Hybrid. Decisions are authored in an extended <spec-decision> inside the spec's design.html — born as a consequence of a requirement, which is Phase 4's whole demonstration — and are indexed, distributed and retrieved through the corpus's machinery via a new decision resource kind. The two deep-research passes showed why this is the right cut and not "store ADRs as corpus documents": the corpus's identity / coordinate / edition-supersede layer would host a decision gracefully (RESOURCE_KINDS is the codebase's blessed extension point; the screen kind already ships the exact two-segment coordinate shape), but its document model is a forced fit on four axes — no structured-metadata parsing, a "cited-against, never enforced-from" data-flow a decision reverses, no lifecycle status that any code respects (Provenance.status is "architecturally decorative"), and import-shaped identity that conflates "a decision this project made" with "a fact this project published." The hybrid takes the machinery and leaves the document model alone.
Scope shape
Paths are the universal floor; module/symbol patterns are optional and ecosystem-defined. Not every language has packages (Python, Rust, Go differ); a path glob is the one selector every ecosystem shares.
Posture default
Block at the standard profile and up, per-decision override, escape via a justified expiring waiver (reusing 042's enforce.waivers[] machinery). A contradicted accepted decision should fail the build from standard upward, not only at enterprise.
Teaching scope
Deterministic join now; shifu + grading-fixture harness net-new, designed here and implemented in Phase 3 (Phase 4's demonstrations 6–7 depend on them). The two skills the brief assumed exist do not.

2 · The architecture in one pass

Six stages, left to right. Everything above the line is where a decision is made and surfaced (probabilistic components may help here); everything at the gate is deterministic and reconstructs from disk (no model, ever).

AUTHOR REGISTER RETRIEVE INJECT GATE TEACH ────── ──────── ──────── ────── ──── ───── <spec-decision> → decisions/index.md → spectastic adrs → fenced, path- → plan-stage: constraint → compose: scope=… (reuses corpus --for <paths> selective, at complete? (declared) <decision-id> posture=block id-alloc, editions, → governing plan + write time ─ merge-stage: verdict (<reason>) status=accepted federation coord) active decisions (P-11: data, reconstructs from disk at <file:line> <enforcement + spectastic:// sorted by not instructions) from enforcer output + shifu (optional, tool= rule-id/> …/decision/… precedence, LOGGED + decision + log off the verdict) <reason> ───────────────────────────────────────────────────────────────── · · · ───────────────────────────────────────────── happy-path aid — helps the agent get it right │ the guarantee — a script, not a judgement P-8 line

The stages map to the rubric: register closes item 1 (structured corpus); retrieve closes item 2; inject closes item 3; the two gates close item 4 and Priya-gaps G1/G2; coverage (§3.7) closes item 9; teach closes item 10; and the whole verdict path being a script keeps items 5/6/7/8 — with the tests §3 adds turning items 5/6 from partial to full.

3 · Design items

Each item states what it does, the smallest concrete change, the artefact schema where relevant, and — mandatory per the brief — what it deliberately does not do.

3.1 · The decision record — extend <spec-decision> closes G3 · rubric 1

Add structured, machine-readable governance metadata to the existing card, so the human prose and the machine policy live in one authored place. Today's card carries only id, a free-text status pill, and grounding.

Schema (attributes + typed children on <spec-decision>):

<spec-decision id="D-008"
    status="accepted"          
    posture="block"            
    supersedes="D-003"         
    review-by="2027-09-13">    
  <spec-scope>                 
    <path>src/**/persistence/**</path>      
    <module>**.hex.core..</module>          
  </spec-scope>
  <spec-enforcement>           
    <rule tool="archunit" id="only_the_persistence_adapter_touches_data_access_apis"
          run="./gradlew test --tests *DataAccessRulesTest"/>
    <rule tool="semgrep" id="no-sql-writes-to-positions-outside-adapter"/>
    <!-- or: <none reason="enforced operationally by a DB grant; no static check"/> -->
  </spec-enforcement>
  <spec-reason>Every position change must emit PositionChanged so Risk and P&L stay
    consistent; a direct table write bypasses the event and the audit hooks.</spec-reason>
  <h4>D-008 · …</h4> …Context / Decision / Consequences prose as today…
</spec-decision>

Smallest change: one schema rule decision-well-formed (error) validating the enum values, the scope-required-once-accepted condition, and the enforcement "≥1 rule XOR one none-with-reason" shape; plus the CSS card already used by <spec-decision>. The reason is the single source of the teaching text (§3.9) — it is authored here and never re-typed into the enforcer's own channel (.because(), Semgrep message:), which is the drift the spec-tictactoe-2 dogfood exhibits.

Does not verify that rule id actually exists in the named tool's config (that is the merge gate's resolvable check, §3.6); does not infer scope from the code; does not compute precedence automatically — a conflict is resolved by an explicit supersedes, and two active un-superseding decisions overlapping a path is itself a reported finding, not a silent pick.

3.2 · The decision index + decision resource kind closes G3 · rubric 1, 8

Make decisions addressable and distributable by reusing the corpus's registry and coordinate machinery — the graceful half of the research. A decision registry (knowledge/decisions/index.md, the corpus registry table shape) allocates stable ids via the existing allocateRegistryIds / mergeRegistryRows (hand-edit-protected), records status, scope-digest, and the enforcement rule-ids, and supersede reuses the append-only edition pattern for "decision B replaced decision A."

Schema: add 'decision' to RESOURCE_KINDS (packages/schema/src/project-shared.ts:63 — the codebase's blessed single-declaration extension point) yielding a project-scoped coordinate spectastic://<project>/decision/<spec-id>/<D-NNN>. Project authority, not marketplace — this is the deliberate divergence from the corpus kind that avoids research forced-fit (d): a decision belongs to the project that made it, mirroring the spec kind (067), not a fact published for others to import.

Does not distribute decisions cross-repo in v1 (the coordinate grammar leaves room for a marketplace-authored decision pack later — see TBD-guardrail-cross-repo); does not mint marketplace ids for decisions; does not move the human-readable decision out of design.html — the index is a derived pointer, the design remains the source.

3.3 · Deterministic scoped retrieval — spectastic adrs --for <paths…> closes G1 (retrieve) · rubric 2

A single plumbing command (not a lifecycle verb — the eight stay eight; this sits with order / verify / id) and one pure function decisionsForPaths(paths, decisions) that glob-matches each active decision's scope against the paths and returns the governing set, sorted by precedence (status, then explicit supersede chain, then id). It writes a retrieval log artefact — the rubric's "logged" and "reconstruct from disk" requirement — recording the input paths, each matched decision id@edition, and a clock read from an injected clock (the 042 determinism precedent, so fixtures pin it). The agent calls it at plan time; CI calls the identical function at merge time; the two logs are diffed so a plan that retrieved a different set than the merge sees is itself a finding.

Does not do semantic or embedding retrieval — glob-match only, so the same paths always return the same decisions (rubric item 2's determinism is the point); does not rank by relevance beyond precedence; does not retrieve domain facts (that is the corpus get/query/grep read path — a different command over a different kind).

3.4 · Context injection before writing closes G1 (inject) · rubric 3

The research found the corpus injects into five authoring verbs but not into implement, the verb that writes code, and injects the whole index undifferentiated. Add a path-selective injection that feeds only the decisions governing the touched surface, at two points: design/tasks (against the plan's declared surface) and, newly, implement (against the task's target paths). Reuse buildCorpusPromptBlock's exact P-11 posture: the decisions are fenced as untrusted data to account for, the directive is unfenced harness text. Injection is a happy-path aid; the guarantee is the gate.

Does not make injection a guarantee (P-8 / T-009: an advisory prompt cannot force the agent to obey — the 111 "Big Pickle" episode is the live proof); does not replace either gate; does not trust the agent's compliance — a correctly-injected decision that the agent ignores is caught at §3.5/§3.6, not assumed away.

3.5 · Plan-stage constraint — where the Priya PR dies in the happy path closes G1 (gate) · rubric 4

The design artefact gains a required (at standard+) constraints acknowledgment: for every in-scope active decision, how the plan satisfies it. A folded, profile-gated CLI scan plan-constraints-complete (the quantifiedNfrFindings shape — reads the profile + the decision index) fails when a path in the plan's declared surface has an in-scope active decision the plan does not acknowledge. This is the "die in the happy path" gate.

Brief-assumption correction (carried to §4): spectastic has no code diff at plan time — the plan is prose. So the constraint operates on the plan's declared surface (the project-structure tree the design already sketches — the spec-tictactoe-2 plan's §7 file tree is exactly this), not on touched files. The actual-diff check is the merge gate.

Does not know the real touched paths (declared surface only — the diff is §3.6's job); does not auto-write the satisfaction prose (the author states how the plan complies); does not fire below standard (warn there).

3.6 · Merge-stage enforcement — the verdict that reconstructs from disk closes G2 · rubric 4, 5, 6

At merge, retrieve the decisions governing the actual diff (the drain hook already computes it — worktree.ts's git diff --cached HEAD / TaskOutcome.filesChanged — and currently discards it; this is its second consumer). Then produce a verdict per violation. The detector/explainer split is the core design decision here (§4): spectastic does not reimplement architecture detection. For language-agnostic rules (path-glob boundaries, forbidden-content like "no SQL naming positions outside the adapter") spectastic runs a native deterministic PerFileRule detector. For richer rules (ArchUnit type-graph) it orchestrates the ecosystem's own enforcer via the decision's run= and captures its machine-readable output. In both cases spectastic composes the verdict: {decision-id, rule-id, rule-reason, file:line, source→target}, persisted alongside the retrieval log, reconstructable entirely from the enforcer output + the decision record + the log. No model on the path — and a new test asserts it (turning rubric 5/6 from partial to full).

Does not reimplement ArchUnit/Semgrep or detect architecture in every language (it orchestrates the ecosystem tool for the rich cases); does not guarantee a rich source→target — that is best-effort per enforcer (clean from ArchUnit, config-derived from a DB grant, line-level from a grep), with {decision-id, rule-id, reason, file:line} the guaranteed floor; does not run inside any vendor's agent loop.

3.7 · Coverage lint — make the blind spot visible closes G4 · rubric 9

A folded scan reporting % of active decisions with an executable check: every active decision must carry either ≥1 enforcement rule or an explicit <none reason=…/>. Warn on none without a reason, and on a decision past its review-by. This is the metric that would have made "the ADR governing positions has no check" visible before Priya, rather than after.

Does not verify the check runs or passes — presence of a wired rule-id, not liveness (the same "present ≠ wired" ceiling the enforce categories record); does not count domain-fact citations; does not block on coverage itself (it reports; blocking is per-decision posture, §3.5/§3.6).

3.8 · Vendor neutrality closes rubric 8

The generated AGENTS.md points at spectastic adrs --for and the decision index — it does not restate ADR content (a hard brief constraint; also P-10). Enforcement lives in the Node CLI, never in a vendor skill format. Add hook adapters that feed gate output back into the agent loop for Claude Code (Stop / pre-tool) and one second tool, following the portable-skills precedent (spec 111 proved the same output runs across Codex/Antigravity/opencode).

Does not build every vendor's adapter in v1 (Claude + one more, demoed; the rest deferred to TBD-guardrail-vendor-adapters); does not put any enforcement logic in a hook — the hook only relays the CLI's deterministic verdict.

3.9 · Teaching on failure + shifu closes G5 · rubric 10

The deterministic failure message is a composition, not a stored string: At <file:line>, <source> → <target> violates <decision-id> — <reason>, where the reason is joined from the decision's own <spec-reason> (§3.1). The reason lives once; nothing is re-typed into the enforcer, so nothing drifts. shifu is a net-new, optional, post-verdict hook (off the enforcement path, so an LLM is permitted there) that asks exactly one Socratic question templated from the decision's rule statement — "the rule says driven adapters never call into the core; why does this job need the repository?" — and never proposes a fix. The grading-fixture harness is likewise net-new (the "debugger skill pattern" the brief assumes does not exist): the Priya PR and the seven Phase-4 behaviours become fixtures that fail the suite on regression.

Does not let shifu or any LLM touch the verdict (advisory, strictly after the deterministic result); does not let shifu propose a fix (one question, then stop); does not require shifu for the message — the deterministic composition stands alone, shifu only deepens it.

4 · Where the brief's design assumptions were wrong

Per the brief's instruction to correct rather than force-fit:

The merge gate does not "execute the enforcement as a plain script" inside spectastic. The brief (line 54) assumes spectastic runs each ADR's enforcement. spectastic is a Node CLI; it cannot run a JUnit/ArchUnit test or a Semgrep rule, and reimplementing them would be a worse ArchUnit that drifts from the real one. The correct model is detector / explainer: the ecosystem's own enforcer detects (ArchUnit for type-graph, Semgrep for content, a DB grant operationally, or spectastic's native PerFileRule for language-agnostic path/content rules), and spectastic orchestrates it and owns the traceability composition — rule-id ↔ decision-id ↔ reason ↔ location — which no architecture-test tool provides. That composition is spectastic's contribution; re-detection is not. The verdict still "reconstructs entirely from disk" (item 4), because it is composed from the enforcer's output file + the decision record + the retrieval log.

 Scope is not package-only. The brief's ADR-frontmatter sketch leans on package patterns; Python, Rust and Go have no uniform package concept. Path globs are the universal floor (§3.1); module/symbol patterns are an optional, ecosystem-defined refinement. The blocking default is standard, not enterprise. A contradicted accepted decision should fail the build from the standard profile upward — the human decision in §1 raised the floor the Phase-1 open question had pitched at enterprise. ADRs are the extended <spec-decision>, not a new markdown-frontmatter artefact. The brief's frontmatter schema is honoured as attributes/children on the existing card (the hybrid), so a decision is still born inside the spec that produced it — which is exactly what Phase 4 must show.

5 · Slicing into specs (dependency-ordered)

This brief is multi-spec. The order is forced by dependency — nothing can retrieve a decision that carries no scope, and no gate can compose a verdict without the record and the index.

  1. Slice 1 — the record + the index (§3.1, §3.2). Extend <spec-decision>; add the decision-well-formed rule; add the decision resource kind and the decision registry reusing corpus id-allocation. Everything downstream rests on this.
  2. Slice 2 — retrieval + the log (§3.3). spectastic adrs --for, the pure decisionsForPaths, the retrieval-log artefact. Independently testable against Slice 1's records.
  3. Slice 3 — the two gates (§3.5, §3.6) + coverage (§3.7). Plan-stage constraint; merge-stage verdict with the detector/explainer split and the no-model-on-the-path test; coverage lint. This is the guarantee layer proper.
  4. Slice 4 — injection (§3.4). Path-selective injection into design/tasks and, newly, implement. Sequenced after the gates deliberately: the guarantee must exist before the happy-path aid, so the aid is never mistaken for the guarantee.
  5. Slice 5 — teaching + shifu + grading harness (§3.9) and vendor adapters (§3.8). The deterministic message composes from Slice 3's verdict; shifu and the grading harness are net-new and land here, feeding Phase 4's demonstrations 6–7.

Cross-references to existing backlog: this design is the enforcement leg REQ-LIFECYCLE-008 explicitly lacks ("advisory … provides no enforcement that the chosen pattern is followed") and the substance of the deferred TBD-architecture-fitness-function; the merge-stage diff hook is the second consumer of the discarded per-task diff noted in the supply-chain survey (adjacent to TBD-change-risk-score / TBD-capability-accountability-principle, which score a capability-delta against the same diff — a sibling, not this).

6 · What this design deliberately does not do

  • No cross-repo decision distribution in v1. Decisions are project-scoped; the federation coordinate leaves room, but a platform team's ADR governing many repos is TBD-guardrail-cross-repo.
  • No liveness guarantee. Coverage proves a check is wired, not that it runs green — the recorded "present ≠ wired" ceiling.
  • No guaranteed rich source→target. Best-effort per enforcer; the floor is {decision-id, rule-id, reason, file:line}.
  • No LLM anywhere on the verdict path, including "just to summarise the failure" — the composition is deterministic; shifu is strictly post-verdict and advisory.
  • No replacement of human placement judgement. Two overlapping un-superseding decisions are reported, not auto-resolved (consistent with P-14 and 075's refusal to machine-decide a layer boundary).

7 · Open questions for implementation

  1. How does the plan declare its surface? Reuse the design's project-structure tree, or add an explicit declared-scope field? (Leaning: reuse the tree spectastic already authors, to avoid a new required field.)
  2. Registry location and command name. knowledge/decisions/index.md under the corpus root, or a top-level decisions/? And is the command spectastic adrs (the brief's word, industry-canonical) or spectastic decisions? (Leaning: adrs, under knowledge/ to signal the corpus reuse.)
  3. Orchestration seam shape. How does run= invoke the ecosystem enforcer safely — an allowlist, a timeout, a sandbox? (This inherits the 085 verify:exec guard-first posture: consent from the invoking project + a location guard, since executing a command stored in an artefact collides with P-11.)
  4. shifu's model boundary. shifu is off the verdict path, but it still reads the diff and the decision — does it run under the session model, or a pinned tier? (Leaning: inherit, like the other reasoning verbs.)
