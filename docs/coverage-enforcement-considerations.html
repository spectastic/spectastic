Considerations · Enforcement & coverage

Where code coverage belongs

Profiles or plan? Both — split by nature. The gating discipline is stack-agnostic; the threshold number is not.

Status Draft Type Research synthesis Author Brian Corbin · @briancorbinxyz Created 11 Jul 2026 Sources 20 primary, verified 11 Jul 2026 Read time

The question — "should coverage tooling and enforcement be stated in the verified/enterprise profiles, or at the plan stage?" — has a clean answer the literature has already converged on: both, split by nature. The measurement-and-gating discipline ("coverage MUST be instrumented, reported on every change, and gated so a change never lowers coverage of the code it touches") is genuinely stack-agnostic and belongs in an org-wide policy — for spectastic, a new coverage category in the verified/enterprise enforce.required floor. The threshold number is context-dependent and belongs per-project — for spectastic, the plan stage, exactly where Perf targets → [QUANTIFIED_TARGETS] already lives. Every serious source (Fowler, Google, the maturity models) refuses to endorse a single universal percentage, because a mandated number is a textbook Goodhart target — trivially gamed, and 100% is a smell. The modern synthesis that lets a stack-agnostic rule coexist with per-project numbers is diff / patch coverage: the rule ("new code is tested") is universal; the exact thresholds are local. Coverage has zero representation in spectastic today — not a category, a principle, or a plan field.

1 · The question

Spectastic draws a deliberate line between what init can seed without knowing the stack (base policy) and what plan resolves once the ecosystem is known (stack-specific tooling) — the 041→042 profile / enforcement split, mirrored again by 043's gitignore. Code coverage arrives at exactly that fault line: is "we enforce coverage" a stack-agnostic policy that a profile can declare at init, or a stack- and feature-specific number that only makes sense at plan time? The answer decides whether coverage becomes a seventh enforcement category or a new plan-stage field — and the research says it is not an either/or.

2 · Where coverage policy lives

The recurring shape across mature-org practice is: measurement and gating discipline are org-wide; the number is decentralized.

  • Measurement comes first, and it is the org-wide part. Codecov's "5 levels" maturity model sequences measurement before enforcement: Level 1 is "expose coverage on every change" via non-blocking checks; thresholds only arrive later. Measurement-first is the recommended order.The 5 levels of coverage — measure/visualize first, enforce thresholds later [17].
  • The number is deliberately decentralized. Google publishes guideline bands — 60% acceptable, 75% commendable, 90% exemplary — but "prefer to stay away from broad top-down mandates and encourage every team to select the value that makes sense for their business needs."Google "Code Coverage Best Practices": 60/75/90 bands, no top-down mandates [3]; corroborated by an ex-Google/Amazon principal: "no ideal number universally applies" [4].
  • The lever that works is measurement, not a mandated percentage. The documented cultural shifts (Amazon's company-wide coverage tooling) came from making measurement ubiquitous, not from enforcing a universal number — and any mandate "should be accompanied by infrastructure investments to make testing easy."

The takeaway that maps directly onto spectastic's question: the org-wide policy is "measure everywhere and gate on the diff" — stack-agnostic, statable once — while the concrete percentages are a per-project knob.

3 · A floor and a diagnostic, not a target

Coverage is a Goodhart trap. Martin Fowler's canonical piece is unambiguous: "If you make a certain level of coverage a target, people will try to attain it. The trouble is that high coverage numbers are too easy to reach with low quality testing." He expects "a coverage percentage in the upper 80s or 90s" from thoughtful testing but is "suspicious of anything like 100% — it would smell of someone writing tests to make the coverage numbers happy." Coverage's real use is finding untested code, not "a numeric statement of how good your tests are."Fowler, TestCoverage — diagnostic not target; 100% is a smell [1]. Brian Marick's distinction: a naturally-high number is healthy, a mandated one invites gaming.

Google echoes it: engineers "may start treating the target like a checkbox and avoid increasing coverage beyond it, even if doing so would be prudent" — coverage is necessary, not sufficient; a covered line can still hide untested branches and logic. This is the strongest argument against spectastic ever encoding a single universal percentage as policy: the number is not the invariant — the discipline is.

4 · Diff coverage — the synthesis

The practice that reconciles "a stack-agnostic rule" with "no universal number" is gating on the diff, not the total. Codecov's patch coverage "calculates the percentage of your new code that is covered by tests… only measures lines adjusted in the pull request." Demanding 100% project coverage "puts an undue burden on a team… shifts engineering resources to the wrong tasks," whereas developers have direct control over new code — so the reframing is 100% patch coverage instead of chasing project-wide totals, with the project floor kept lenient or trend-based ("don't let a PR drop coverage by more than N%").Patch vs project status [7]; why patch > project [8]; Coveralls PR-drop threshold [10].

This is the key insight for spectastic: diff coverage is exactly what lets a stack-agnostic rule ("new code is tested; a change never lowers coverage of what it touches") coexist with per-project numbers (the patch target, the project tolerance). The rule is universal and belongs in the policy floor; the numbers are local and belong in the project's own coverage config — which is also where they are machine-enforceable.

The "80%" everyone quotes is folklore (commonly attributed to the Pareto principle, without a study behind it). Real orgs cluster at 70–85% total with a lean toward ~80% on the patch and tiered targets by criticality — never a single flat global mandate.

5 · Per-ecosystem tooling & detectability

Every mainstream ecosystem ships a coverage tool, but they differ in whether intent is declared in a config file (statically detectable — the signal spectastic's detectTooling reads) or only via a runtime flag (needs CI inspection). This distinction is what makes a coverage enforcement category feasible or not.

The detection principle: config-file-declared thresholds (Python fail_under, Jest coverageThreshold, JaCoCo rules, .NET .runsettings) encode intent and are statically detectable; flag-only tools (Go's built-in, a bare --coverage) require inspecting the CI invocation. That mirrors exactly how spectastic's existing test-runner signals work — they detect a runner's config presence, not its invocation — so a coverage signal is a natural, same-shaped extension (e.g. @vitest/coverage in package.json, [tool.coverage] in pyproject.toml, a JaCoCo check rule) with an honest "flag-only ecosystems can't be statically detected" caveat.

6 · Where spectastic stands today

Coverage has zero representation anywhere — not an EnforcementCategory, an enforce.required value, a principle, or a plan field. The existing machinery is a near-perfect fit for the split, though:

  • The enforcement floor — packages/core/src/enforce/types.ts defines six categories (formatter · linter · type-checker · security · supply-chain · test-runner); detect.ts maps config-file signals to them; policy.ts diffs required-vs-covered. Profiles' enforce.required escalate (verified adds security; enterprise adds supply-chain). This is the stack-agnostic policy at init surface — exactly where a coverage category would live, and it would flow automatically into spectastic enforce, the AGENTS.md "Enforcement floor" block, and the plan's gap analysis with no per-plan authoring.
  • The plan stage — templates/design.html §2 Technical context already carries Testing → [TEST_STACK_AND_STYLE] and Perf targets → [QUANTIFIED_TARGETS], and plan.md step 7 anchors "Test style" and a quantified "Perf budget" via AskUserQuestion. A coverage threshold is structurally identical to a perf budget — a stack/feature-specific number — so it fits here as a §2 row + a decision-phase prompt, needing no profile change.

The two halves land cleanly on the two existing surfaces. Note also that the verified profile already ships a "Done means verified" principle about testing levels (unit / integration / behavioral) and "presence is never accepted as proof" — coverage is the missing quantitative complement to that qualitative bar.

7 · Recommendation

D-001 · Split it — a coverage category in the profile floor, the threshold at plan time

Status
Proposed
Context
Coverage governance is two things with two homes: a stack-agnostic measurement/gating discipline and a stack/feature-specific number. The literature (Fowler, Google, the maturity models) warns against a single mandated percentage; diff coverage is the practice that lets a universal rule coexist with local numbers. Spectastic's init(base)→plan(stack) machinery already separates these two surfaces.
Decision
(a) Profile floor: add a seventh EnforcementCategory, coverage, meaning "coverage measurement is wired up and gated" — added to verified and enterprise enforce.required, with detect.ts signals for the config-detectable ecosystems and an explicit caveat for flag-only ones (Go). This is stack-agnostic and knowable at init. (b) Plan stage: capture the coverage threshold as a per-project number — a Coverage → [DIFF_AND_PROJECT_TARGETS] row in plan §2 and a decision-phase AskUserQuestion, modelled exactly on "Perf budget." (c) Framing: state the policy as diff-aware ("a change never lowers coverage of the code it touches"), never as a single universal percentage.
Consequences
+ Matches the field's split and spectastic's own 041→042 / 043 convention precisely. + The category flows automatically into enforce + AGENTS.md + the plan gap analysis. + The threshold reuses the proven Perf-budget pattern. + Avoids the Goodhart failure mode by never hard-coding a number in the policy. − Static detection can't see flag-only coverage (Go) — recorded, not hidden (the honest ceiling). − Adds one category + its signals + one plan field; small, but touches the meta-spec contract, so it goes through propose.

Suggested next artifact

  • A /spectastic.propose against 042-profile-enforcement adding the coverage category (a FR-* extending the category enum + detect.ts signals + verified/enterprise enforce.required), then /spectastic.implement.
  • A sibling plan-verb change adding the Coverage §2 row + decision-phase prompt (mirroring Perf budget) — could ride the same proposal or a plan-scoped one.

8 · Caveats on the sources

  • Google's 60/75/90 bands and "no top-down mandates" are corroborated across a co-author's article and a search extract; the 2020 best-practices page is JS-rendered and its body wasn't read verbatim — strong despite the fetch gap.
  • "80% originates from the Pareto principle" is widely repeated folklore, single-lineage; treat as "commonly claimed," not established.
  • The "70–85% for mature orgs" band comes from an engineering-metrics vendor blog — directional, not a study.
  • Codecov's "5 levels" is one vendor's opinionated model (with an incentive to push escalating enforcement) — useful framing, not an industry standard. The measure-before-enforce ordering, however, is echoed widely.
