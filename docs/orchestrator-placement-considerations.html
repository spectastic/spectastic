Considerations · Placement

Resemblance is not ownership

A requirement arrives. Somewhere across a dozen repositories sits the project that ought to own it — and one directory inside that project where the change ought to land. The estate can already say what every artifact is and what it is about. It cannot say what depends on what, and the one thing it can rank by is the thing that misleads.

Status Draft Type Architecture & landscape survey Author Brian Corbin · @briancorbinxyz Created 02 Aug 2026 Companion corpus-extraction · agent-architecture · data-model-contract Sources 16 external, retrieved 02 Aug 2026 · codebase audit Read time

The forward-look this survey drains proposed routing a requirement to the service whose specs and corpus it most resembles. Resemblance produces the exact failure the orchestrator exists to prevent — a requirement written in the vocabulary of the consumer resembles the consumer's estate most closely, which is precisely how a fix that belongs in a library gets built in the application that calls it. Similarity finds where a topic is discussed; placement needs to know where a change belongs, and those are different questions over different data. The audit corrected three things I expected to find. A dependency graph already ships — spec 028's precedence DAG, exposed as spectastic order — but its nodes are specs, its scope is one checkout, and its edges mean build this first, not this owns that. The estate's precedence rule is declaration over inference, settled at must-tier by 073 on identical reasoning, so any "infer first" posture contradicts shipped code. And the design artifact is already read as standing project state — the real defect is subtler and worse: declarations shadow rather than accumulate, so a project with seventy-nine specs has exactly one visible contract declaration set. The recommendation is a typed edge over units cut on the repo boundary, a verdict shape inherited wholesale from triage and the slicer rather than invented, and two refusals held as first-class outcomes — never mint a service, and never route to a plausible owner because "no owner" was not on the menu.

1 · The ask — a change with no address

Two failures motivate this, and neither is exotic. A team runs a shared library and four services that consume it. A requirement arrives describing a defect in the vocabulary of one consuming service, because that is where a human noticed it. An orchestrator reads the requirement, finds the consuming service's specs discuss exactly this behaviour, opens that repository, and builds a local workaround around a bug that lives one layer up. The library keeps the defect. The other three consumers keep it too. Nothing about the outcome looks wrong until the second consumer reports the same thing.

The second failure is finer-grained and lives inside one service. A requirement lands in a codebase arranged as concentric rings — domain at the centre, application services around it, adapters at the edge. The change might belong to the domain, to an existing service, or to a service that does not exist yet. Getting this wrong does not fail a test. It produces code that works and erodes the arrangement that made the codebase tractable, which is the failure mode that compounds.

Both are architectural questions, and architecture is the one thing the estate does not hold. A spec.html holds requirements. A knowledge corpus holds domain facts. Neither knows that payments-core is upstream of checkout-api, or that this project keeps framework types out of its domain ring. That knowledge — where it is written down at all — lives in the design.

A different orchestrator already exists; this is not that one. Spec 037 ships spectastic run, which drives design → tasks → implement → verify unattended on an approved spec, answering each decision through the configured decider. It takes a spec id as input — it operates on work that has already been placed. Everything below sits upstream of that entry point: it decides which project's specs/ the spec should be created in, and which boundary inside that project the change belongs to. Where the distinction matters this survey says placement, never the bare word.

The slug being drained, TBD-orchestrator-spec-placement, was planted in the corpus-extraction survey §5 as a forward-look: once the estate is namespaced and queryable, ask the federated index which service's spec-sensitive corpus and existing specs a requirement is closest to, and propose where the spec should live — semantic CODEOWNERS, human-confirmed. Identity landed (067, 078); the serving surface landed in a separate repository. The forward-look is now drainable, and the first thing to say about it is that its proposed mechanism is wrong.

Scope, stated plainly. This survey covers change placement, laddered: which project, then which boundary inside it, then the case where the honest answer is neither. Spec placement — where a spec.html is created — is the coarsest rung of that same ladder, not a separate problem. That widens the original slug, which asked only about the coarsest rung, and the widening is deliberate: an orchestrator that places specs correctly and changes incorrectly has not helped anyone.

2 · The graph that already ships — and why it is the wrong one

The obvious claim about this estate is false. It is tempting to say spectastic has spent seventy-nine specs describing nodes and never once describing an edge — that 067 and 078 gave every artifact a federation-unique name and nothing gave any two of them a relationship. It is a clean story and a reviewer would refute it by running one command.

Spec 028 ships a real dependency graph. packages/core/src/ordering/graph.ts builds a typed {nodes, edges, dangling} structure over the spec corpus, with cycle detection, dangling-reference reporting, transitive subtree value, and per-node dependsOn / unblocks. It is exposed as spectastic order. The graph is not hypothetical and it is not small.

Its edge admission rule is the part worth stealing. An edge from parent to child is admitted only when reciprocated: the child's <spec-parent specid="P"> must be matched by the parent's own <li defer-to="child">. The module comment states the consequence directly — "a bare, unreciprocated defer-to is a see-also, not an edge." One side asserting a relationship is a claim; two sides asserting it is a fact. That is a genuine design idea, already load-bearing, and it is the answer to a question federation raises acutely: in a multi-repo estate, what stops one project from unilaterally declaring itself downstream of another?

So the honest finding is not absence. It is mismatch, on all three axes at once:

Axis028's graphWhat placement needs
NodeA specA unit — a project, or a module inside one
ScopeOne checkout's specs/Every project in the estate
Edge meaningPrecedence — build A before BDependency — A is built on B, so a change to their shared surface belongs to B

Precedence and dependency are not the same relation wearing different hats. Precedence is a scheduling fact about work: it expires the moment both specs are done. Dependency is a structural fact about artifacts: it holds for as long as the code does, and it is the one that answers "which side does this change belong on". A graph optimised for the first tells you nothing about the second — which is why 028's DAG, for all its machinery, cannot be pointed at this problem.

D-001 · Reuse 028's edge-admission rule, not its graph

Status
Proposed
Context
A precedence DAG over specs already ships (packages/core/src/ordering/graph.ts, spec 028, surfaced as spectastic order). Its nodes are specs, its scope is one checkout, and its edges encode build order. Placement needs edges over units, across the estate, encoding dependency. Its reciprocity rule — an edge exists only when both ends declare it — is independent of all three and directly addresses federated trust.
Decision
Do not extend 028's graph and do not model placement as an ordering problem. Build a separate unit graph, and carry the reciprocity rule across as the admission test for a cross-project edge: a unilateral claim is a see-also; a matched pair is an edge.
Consequences
+ Federated trust gets a rule rather than a policy — no project can conscript another into a relationship. + The estate keeps one clear meaning per edge type instead of overloading precedence. + 028 stays untouched, so spectastic order cannot regress. − Reciprocity is cheap within one corpus and expensive across repositories, where the counterpart may be unreadable or absent; the fallback for an unmatched claim must be specified, not assumed (see §4). − Two graphs mean two mental models, and a reader may reasonably ask why spectastic order does not answer placement.

3 · One question or two — and where to cut

The two motivating failures look like different problems, and the split is real, but the obvious place to cut is wrong. The tempting division is by question type: producer-versus-consumer on one side, ring placement on the other, each getting its own mechanism. That cut fails on the case most teams actually have.

Consider a monorepo containing a library and the application that consumes it. Is "does this belong in the library or the app?" a producer/consumer question or a module-boundary question? It is plainly both, and it falls through a question-type split in a way that matters mechanically. Spec 076's consumes[] array — the estate's only project-to-project edge — is explicitly designed to be empty in exactly this case. Its NFR-002 states that a monorepo where producer and consumer coexist "SHOULD incur at most 0 additional steps, since the export problem does not arise there", and notify.ts reiterates it: such a project "needs no entry at all". The one mechanism a question-type split assigns to the producer/consumer half does not fire for the most common shape of that half.

Cut on the repository boundary instead and the questions collapse where they should. Inside one repository, "library or app?" and "domain or service?" are the same question — which unit owns this? — asked in two vocabularies, and the ecosystem already answers both with one mechanism, module boundary rules over named units. Across repositories, the same question needs a different transport, because there is no shared build graph and no shared filesystem: it needs coordinates and declared edges. The question is invariant; only the transport changes.

D-002 · Cut on the repository boundary, not the question type

Status
Proposed
Context
Splitting by question type (producer/consumer vs. ring placement) leaves the monorepo case falling through both halves: 076 NFR-002 deliberately keeps consumes[] empty in a monorepo, so the cross-repo mechanism does not fire, while the intra-repo mechanism was assigned to the other half. Inside one repository the two questions are the same module-boundary question in different words.
Decision
Model one relation — a typed edge over units — and let the repository boundary select the transport. A unit is a module or package intra-repo and a project coordinate cross-repo. Placement resolves the same way in both; only edge acquisition differs.
Consequences
+ The monorepo case is served, and it is the common case. + One relation means one verdict shape, one explanation format, one thing to test. + Migrating a module out into its own repository changes the transport, not the model. − "Unit" is a new abstraction the estate does not currently name, and a vocabulary with no artifact behind it is a liability. − Intra-repo edges are dense and cross-repo edges are sparse; one ranking over both risks the dense side dominating.

4 · Declaration, then inference — the order is already settled

There is a strong argument for inferring the graph rather than authoring it, and it is nearly right. The software-catalogue literature is unambiguous about hand-maintained metadata: it rots, and it rots fast enough to poison trust in everything built on it. Practitioner accounts put stale ownership data past the point of usefulness within weeks, and the standing recommendation across the internal-developer-platform field is to auto-discover and reconcile rather than ask humans to maintain entries. The evidence from this repository is worse than the literature: of ten <spec-contract> declarations across seventy-four designs, every single one is shape="none". The one machine-readable structural element the design artifact has, in the project that invented it, has never once been used to declare an actual interface. And the root spectastic.json carries no consumes entry.

So a placement engine that waits for humans to author a graph will be a placement engine that never runs. That much is solid. The conclusion I first drew from it — infer first, let declarations override — is nonetheless wrong here, and wrong against shipped code rather than against taste.

Spec 073 settled this exact question, at must-tier, on identical reasoning. 073 FR-003:

Where a design declares an interface or a contract path, that declaration MUST take precedence over inference from dependencies or the filesystem — in both directions, establishing that a contract is owed and that one is not.

Its rationale is the argument this survey would otherwise have to make from scratch: "Inference cannot distinguish publishing from consuming, nor a published contract from a vendored one. Only a declaration carries intent, and both false directions have been observed." The spec goes further and names the ordering as load-bearing — "Reversing the first two would make a design's stated intent unable to correct a wrong guess, which is the only reason the declaration exists." It is implemented in declaredInterfaceState, which returns null when a project declares nothing so that inference runs exactly as before.

This matters directly for placement, because the producer/consumer distinction is precisely what dependency presence cannot see. A manifest entry for a messaging client appears identically in a publisher and a subscriber. A checked-in OpenAPI document appears identically in the service that publishes it and the client that vendored it to generate a stub. Inference establishes that an edge exists; only a declaration establishes which end of it owns a change. The engine needs both and must not confuse their roles.

The third bucket already exists too. enforce/policy.ts carries an advisory warned state for the case where a category plainly applies but only through a signal too weak to gate on — today, an event-driven recognition that cannot tell a publisher from a consumer. That is exactly the shape of an inferred edge with unknown direction. Placement should not invent a confidence vocabulary for this; it should reuse the one the enforcement system already ships.

D-003 · Declaration outranks inference; inference is never optional

Status
Proposed
Context
073 FR-003 settles the precedence at must-tier with reasoning specific to producer/consumer ambiguity, implemented in declaredInterfaceState; the event-driven survey landed the same emphasis. Against that, catalogue-staleness evidence and this repository's own record — ten <spec-contract> declarations, all shape="none", and no consumes entry in its own config — show that authoring alone yields an empty graph.
Decision
Keep 073's ordering: declaration, then inference, then fail-safe. The staleness evidence changes not the order but the obligation — inference MUST always run as the fallback and MUST NOT be switchable off, so an undeclared estate still produces a graph. An inferred edge whose direction is unknown resolves to the existing advisory state rather than a guess.
Consequences
+ Agrees with an Accepted must-tier requirement instead of contradicting it. + A project that declares nothing still gets ranked suggestions on day one. + The confidence vocabulary is inherited, not invented. − Placement quality is bimodal: sharply better where designs declare, floor-level where they do not, which will read as inconsistent. − An inferred graph is only as good as manifest conventions, so an unconventional project silently gets the weaker tier with nothing telling it why.

5 · Where the edge can live — four candidates, one disqualified on structure

The corpus is the first place anyone reaches, and it cannot work. It is the obvious candidate: a corpus is where domain knowledge already lives, it is citable, edition-pinned, provenance-carrying, and its type contract is young enough that widening it is still cheap by its own admission. The reason to reject it is not taste and not the advisory markdown rule that corpus citations are for domain facts only — that rule is real and confirms the answer, but it lives in command markdown and is by this survey's own standards not durable enforcement.

The disqualifying reason is structural. A corpus is addressed per-marketplace: spectastic://<marketplace>/corpus/<plugin>/<slug>. Every document belongs to exactly one marketplace, and identity is a containment hierarchy — marketplace, plugin, slug, edition — with, as the audit confirms, no concept-to-concept relation of any kind in any type, parser or renderer. An edge between two projects belongs to neither of them alone. It has no owning marketplace, so it has no legal coordinate, so there is nowhere in the corpus for it to be. A relation whose endpoints span the addressing scheme's own root cannot be filed under one root.

The design artifact is the second candidate, and here the audit contradicted me usefully. I expected to find that a design cannot hold standing project state — that §8 Project structure is diff-scoped ("only the new or changed paths"), that <spec-arch> carries no attributes across all sixty-eight of its real usages, and that the architecture pattern survives only as prose in a <dd>. All of that is true, and none of it is the argument.

The design artifact is already read as standing project posture. declaredInterfaceState walks specs/ and treats what it finds in a design as the project's current stated position, with the comment: "Last spec directory wins, so the project's most recent stated posture is the one that counts." The user intuition that plans hold this knowledge is not naive; the code already acts on it.

The real defect is in that same sentence, and it is worse than diff-scoping. The loop returns inside the first spec directory that contains any <spec-contract> at all. Designs do not accumulate — they shadow. A project with seventy-nine specs has exactly one visible contract-declaration set: whichever design is newest. Every earlier declaration is invisible to the detector that reads them. 073 accepted this because it needed a boolean about the project's current posture, and for that purpose newest-wins is defensible. For a project map it is fatal, because a map is precisely the thing you build by union.

6 · How the field answers this — three traditions, none of them sufficient alone

The catalogue tradition models the estate as typed entities with typed relations. Backstage's software catalog is the reference implementation: a Component declares providesApis, consumesApis, dependsOn, ownedBy and partOf, grouped into System and Domain. Its own guidance is instructive for the producer/consumer case — even where consumesApis is present, add dependsOn for the direct relationship to the providing component, particularly when the dependency is a shared library rather than an API. The field has already noticed that the library case is the one an API-shaped relation misses.

Backstage also supplies the cautionary half. The catalogue is hand-authored in catalog-info.yaml, and the practitioner literature on stale ownership is consistent enough that "auto-discover and reconcile" is now the standing advice rather than a refinement. The 2026 wave of work exposing Backstage catalogs to agents over the protocol makes the stakes sharper: an agent grounded on a stale catalogue is confidently wrong, and one documented failure is exactly the ownership case — an alert routed to a generic department of 134 people because the metadata was never maintained.

The domain-driven tradition supplies the vocabulary the catalogue tradition lacks. Context mapping names relationships between bounded contexts with a precision that dependsOn cannot reach: Customer/Supplier where the upstream negotiates with the downstream, Conformist where the downstream simply absorbs the upstream's model because the upstream has no incentive to help, Anticorruption Layer where the downstream translates defensively, Open Host Service and Published Language where the upstream deliberately serves many consumers. Every one of these is an upstream/downstream relation — precisely the direction placement needs — and each implies a different answer to "which end absorbs this change".

Better still, this has a machine-readable form. Context Mapper's CML expresses a map directly — VoyagePlanningContext [D,ACL]<-[U,OHS,PL] LocationContext — with the arrow pointing upstream to downstream, plus relationship attributes for implementation technology, exposed aggregates, and downstream rights on a scale from influencer to monopolist. That last attribute is a striking piece of prior art: it encodes how much say the downstream has over the upstream's roadmap, which is the organisational half of "should this change be made upstream or worked around locally".

The enforcement tradition answers the intra-repo half and is already in this repository. Architecture fitness functions — ArchUnit in Java, dependency-cruiser and Nx's module-boundary rule in the JavaScript world, import-linter in Python — encode layering as executable constraints. Nx is the closest fit: projects carry tags, and depConstraints declares which tags may depend on which, giving a named unit vocabulary that a placement engine could read directly.

Two things cut against leaning on this too hard, and §7 takes them up: the tools split on whether they declare layers positively or forbid edges negatively, and this repository is an example of the weaker form.

The retrieval tradition is where the original forward-look reached, and it is the weakest of the four for this job. Information-retrieval bug localisation has three decades of work on "given a report, which file changes?" — combining report text, stack traces, structural source information, and change history, typically hierarchically from files down to methods. Two findings transfer. First, text similarity alone is a weak signal and the field's gains came from adding structural and historical evidence to it. Second, the accuracy that this literature reports is top-k accuracy with human inspection assumed — the output was always a ranked shortlist for a person, never a decision. Both findings argue against resemblance as a primary router and for it as one evidence class among several.

And the negative result worth naming: CODEOWNERS, the mechanism the original forward-look reached for as an analogy, answers only "which file was modified". The critique in the practitioner literature is exactly this survey's opening failure — it is blind to the destination of the change, and cannot see architectural impact at all. Being semantic CODEOWNERS is not an ambitious target; it is the same blindness with better prose.

7 · Inside one repository — the boundary map, and where it goes quiet

The intra-repo half looks solved and is half-solved. The instinct is right: spectastic should not invent a layering model when the ecosystem already declares one machine-readably, and this is exactly the project's own house pattern for enforcement — the coverage category detects a declared threshold rather than a coverage library, and contract-first detects a checked-in contract rather than a framework. Detecting a declared boundary map is the same move, and enforce/detect.ts already has the machinery for it: FileSignal, ciInvokes, and checkIsConfigured, whose shape detectContractChecks already clones.

The problem is that the four obvious tools split two-and-two, and the split runs along exactly the axis placement cares about.

ToolFormNames units?Answers "where does this go"?
Nx depConstraintsPositive — tag-to-tag allow rulesYes, an enumerated tag vocabularyYes
import-linterPositive — an ordered layer listYes, named layersYes
dependency-cruiserNegative — forbidden edges over path globsNoOnly by elimination
ArchUnitNegative — arbitrary rules in Java test methodsNo — not a config formatNo

This repository is the weak example, and the way it is weak is a useful reversal. Its .dependency-cruiser.cjs holds a single forbidden rule — packages/corpus must not import packages/core — over path globs, whose own comment says the scope is deliberate: "this is not a general architecture-fitness tool adoption, just the machine-verified half" of one decision. It names no layers and enumerates none. And note what it actually encodes: a pairwise package edge. The repository's single piece of fitness-function evidence supports the producer/consumer half of the story, not the ring-placement half.

A negative constraint set yields a partial order at best, and only over paths that already exist. That limitation bites hardest in the case this survey is obliged to handle: when the destination directory does not exist yet, a glob-based rule set is silent by construction. It cannot distinguish "this belongs somewhere new" from "this belongs nowhere", because it was never asked to describe the space of legal destinations — only to forbid some traversals of the existing one.

The enforcement half of this already has a home and this survey should not re-plant it. The agent-architecture survey planted TBD-architecture-fitness-function — a validate or CI check enforcing the chosen pattern's dependency rules — and recorded it as the heavier, later, P-8 guarantee half. Placement is a new and better reason to drain it, because the artifact that enforcement needs and the artifact that placement needs are the same artifact: a declared, named unit vocabulary. What this survey adds is the observation that detecting such a map, where a project already declares one, is much cheaper than authoring one and should come first.

The word "layer" is taken. triage owns it with an incompatible meaning — its closed taxonomy of spec, design, implementation, cross-spec, principles, platform, just-do, defer classifies which lifecycle layer owns a fix, not which architectural ring owns a change. Any requirement written as "layer placement" will be misread by anyone who has used the triage verb. This survey says boundary or ring throughout, and a downstream spec should too.

8 · What placement returns — two refusals, both first-class

The verdict shape does not need inventing; two shipped verbs already have it. triage's classifier is the closest existing thing to a placement decision, and it is the same decision shape: a closed taxonomy of destinations, a model classification carrying layerConfidence: high | medium | low, an automatic hedged status when confidence is low or the returned layer is not valid, and a consolidated human escalation that runs after the concurrent pass rather than interleaved with it. The slicer supplies the other half — its Verdict is {kind:'split'} or {kind:'dont-split', reasons: string[]}, with the comment that dont-split is "a first-class verdict… never a forced cut."

Placement should inherit both rather than introduce a parallel confidence vocabulary. Where it needs more structure is in the evidence, and there the house pattern is to type findings, not scores: change-risk's RedFlagFinding carries a category and a weight, and its composite score is explicitly "a v1 default, not calibrated truth". A placement suggestion should carry its evidence the same way — a declared edge, an inferred edge with unknown direction, domain proximity, prior art in this project's own specs — each named and weighted, so a human reviewing a suggestion sees why and not merely how confident. That is the difference between a number to argue with and a case to check.

The first refusal is the one everyone expects, and it is usually stated too strongly. "Never bootstrap a service" conflates proposing with executing, and it is stricter than the project's own precedent: the slicer drafts new spec ids that are "provisional until minted" and runs dry, minting nothing. The honest line is propose, never mint. An orchestrator may absolutely conclude that no existing unit fits and that the right answer is a new one — that is a useful conclusion, and suppressing it would push work into whichever unit fits least badly. What it must not do is create the thing. Standing up a service is an organisational commitment about team boundaries and cognitive load, and the inverse-Conway literature is clear that architecture migration and team reorganisation are one act, not two.

The second refusal matters more and is easier to miss. A placement engine's most damaging failure is not proposing a service that should not exist. It is routing confidently to a plausible-but-wrong existing owner because "no confident owner" was not an available answer. This is the opening failure again, arriving through the back door: forced choice over a ranked list will always return something, and the thing it returns will be the unit whose vocabulary the requirement happened to borrow. "No confident owner", with reasons attached, must be a terminal state on the model — not a fallback, not an error, not the absence of a result.

There is no ownership field anywhere in spectastic. The only ownership datum in the entire estate is enforce.waivers[].owner — a free-text string attached to a single waiver, not to a project. A survey that reaches for Team Topologies and inverse Conway while the tool cannot name who owns a repository is gesturing at organisational theory it has no data for. Stated plainly rather than dressed up: ownership routing needs an ownership field first, and that field does not exist.

D-006 · Inherit triage's confidence-and-hedge shape; type the evidence, not the score

Status
Proposed
Context
triage/classify.ts already routes "which layer owns this fix" with a closed taxonomy, layerConfidence: high|medium|low, an automatic hedged status, and a consolidated human gate. slice/types.ts already makes a negative verdict first-class with attached reasons. change-risk types evidence at the finding level and declares its weights uncalibrated.
Decision
Placement returns a ranked shortlist with high|medium|low confidence and an automatic hedge, inheriting triage's shape and escalation timing. Evidence is a typed list of named classes with weights, not an opaque score, and the weights are declared uncalibrated defaults from the outset.
Consequences
+ No new confidence vocabulary, and the escalation ergonomics are already proven in a shipped verb. + A human sees the case, not just the number, which is what makes confirmation meaningful rather than ceremonial. + Uncalibrated-by-declaration avoids the score being read as measured truth. − Three confidence bands are coarse for a ranking problem, and a downstream spec may find they under-discriminate. − Typed evidence classes are a vocabulary that must be got roughly right early, since consumers will bind to the names.

D-007 · Propose, never mint — and never route for want of an alternative

Status
Proposed
Context
"Never bootstrap a service" is stricter than the project's own precedent — the slicer drafts provisional ids and mints nothing. Meanwhile the more damaging failure is unaddressed: forced choice over a ranked list always returns something, and what it returns is the unit whose vocabulary the requirement borrowed. spectastic has no ownership field beyond a per-waiver string.
Decision
Two first-class terminal outcomes, both carrying reasons: new unit proposed (a proposal that exits to a human; the engine never creates a repository, package or directory) and no confident owner (never a fallback and never an error). A suggestion is never auto-applied at any confidence.
Consequences
+ Matches the slicer's dry-run precedent instead of inventing a stricter rule. + The abstain path closes the survey's opening failure at the verdict level, where forced choice would reopen it. + Reasons make both refusals reviewable rather than opaque. − An engine that abstains often is an engine people stop consulting, so abstention rate becomes a quality metric that must be watched. − Human-confirmed at every confidence caps the throughput benefit, which is a real cost honestly paid.

9 · The engine — five stages, and what each already has

Laid out end to end, the mechanism is smaller than it sounds, because four of its five stages have shipped precedents.

Stage 3 is where the survey's opening failure is actually defeated, and it is worth being precise about how. Domain proximity — "this requirement resembles that project's corpus and specs" — stays in the evidence set, because it is genuinely informative and it is the only signal available for a project that declares nothing and whose manifests reveal nothing. What changes is that it is one weighted class among several rather than the ranking function, and that a structural edge pointing the other way is allowed to outrank it. The library case then resolves correctly: the requirement resembles the consumer, a declared or inferred edge says the consumer depends on the library for exactly this surface, and the two pieces of evidence are visibly in tension in the output rather than silently resolved in favour of the loudest one.

That tension is the thing to surface, not suppress. A suggestion reading "consumer ranks first on domain proximity; producer ranks first on structural dependency; confidence medium, hedged" is far more useful to a human than either unit returned confidently — and it is the shape the bug-localisation literature converged on for the same reason.

Staging follows the dependencies, and only the last stage is genuinely gated. Stage 1 is buildable now, entirely within this repository, against machinery that already exists. Stages 2–4 need only Stage 1's output and a single checkout — they work on a monorepo on day one and need no aggregating endpoint at all. Only the cross-repo case needs the federated read surface, and only the new-unit arm of Stage 5 needs an ownership field the estate does not have. The forward-look's posture that this is entirely gated behind aggregation turns out to be true of roughly one third of it.

10 · Recommendation — three slices, in order

  1. Make the edge exist. Generalise consumes[] into a declared unit-edge list in spectastic.json; give it a CLI surface and a design-interview question so something actually authors it; fix declaration shadowing so a project's posture is the union across designs rather than the newest one; add inference from manifests and workspace configs as the always-on fallback, with the advisory state for edges whose direction is unknown. Entirely within this repository, no new artifact kind, and it improves 073's existing detection whether or not placement is ever built.
  2. Make the boundary map readable. Detect a declared boundary map where a project already has one — tag-based rules first, since only the positive forms answer "where does this go" — reusing the FileSignal and checkIsConfigured shape the enforce detector already ships. Pairs with, and gives a fresh reason to drain, the already-planted TBD-architecture-fitness-function.
  3. Make the verdict honest. Rank with typed evidence, hedge on low confidence, and hold both refusals as first-class outcomes. Single-checkout first; the estate-wide form follows the federated read surface.
Do not build this by making resemblance better. The temptation, once a read surface can answer "which estate does this look like", is to improve the ranking and call it placement. Every improvement to a similarity ranker makes the opening failure more confident, not less, because the requirement genuinely does resemble the consumer most — the ranker is not making a mistake, it is answering a different question correctly. Structural evidence is not a refinement of resemblance; it is the thing that has to outrank it.

Suggested next artifacts

  • A new spec: the typed unit edge — its vocabulary, its two transports (module intra-repo, coordinate cross-repo), the reciprocity admission rule carried over from 028, and the fallback when a cross-repo counterpart is unreadable. Slice 1, the model (D-001, D-002).
  • A new spec: plumb the edge list so something authors it — a CLI surface, a design decision-phase question, and a validate rule that a declared coordinate is well-formed. Today consumes[] has no caller outside its tests and this project's own config carries none. Slice 1, the authoring half.
  • A /spectastic.propose against 073: make a project's declared interface posture the union across designs, newest-wins per contract name, rather than the newest design wholesale. Fixes shadowing independently of placement (D-005).
  • A new spec: detect a declared boundary map where a project has one, distinguishing positive (named units) from negative (forbidden edges) forms and recording that the negative form is silent when the destination does not yet exist. Cloning the enforce detector's signal shape. Slice 2.
  • A new spec: the verdict shape — typed evidence classes, three-band confidence with automatic hedge, and both refusals as terminal states carrying reasons. Inherits triage and the slicer wholesale. Slice 3 (D-006, D-007).
  • A /spectastic.propose against the meta-spec: a project-level owner, which the estate currently lacks entirely — the only ownership datum anywhere is a per-waiver free-text string. Prerequisite for anything that routes to a team rather than a repository.
  • A /spectastic.propose against 076: the federation key for a contract is its filename, so renaming or reformatting a contract file silently breaks every downstream entry with no rename detection, and two contracts in one project must have distinct basenames regardless of directory.
  • A follow-on survey then spec: the engine itself, once slices 1–3 land and there is real edge data to rank against — including whether the abstention rate is tolerable in practice, which cannot be answered before it runs.

Deliberately not planted: TBD-architecture-fitness-function, which the agent-architecture survey already planted for the enforcement half of the boundary question. Slice 2 is its detection-side companion, not a replacement, and re-planting it would double-count a pending slug.

11 · Caveats on the sources

  • The project's own principle says this judgment resists mechanisation. P-14 (Library-first boundaries) poses exactly the producer/consumer test — "would a second caller want this logic without the CLI attached?" — and then records that the boundary is "a judgment call… not a mechanical property a linter can decide without false positives, so it stays review-caught rather than machine-enforced." Everything above is a suggestion engine precisely because of that. A reviewer is entitled to ask whether a machine that cannot decide should be advising at all, and the only honest answer is that a ranked case with visible evidence is worth more than nothing and less than a decision.
  • 075 already refused a neighbouring machine check. Spec 075 deferred any machine check for layer violations, "deliberately not attempted, since the distinction requires judgment". That is a different sense of "layer", but the refusal rhymes, and a downstream spec should expect to be asked why this one is different.
  • The slicer encodes a bias against horizontal layers. Its semantic critic flags a horizontal-layer child as a defect. A placement mechanism whose output is frequently "which horizontal ring" sits awkwardly beside that, and the tension is unresolved here.
  • The staleness evidence is practitioner literature, not measurement. "Stale ownership kills trust within two weeks" is a widely-repeated field observation from platform-engineering vendors with an interest in the conclusion, not a study. It is directionally consistent with this repository's own record — ten shape="none" declarations and an empty consumes — which is a sample of one, honestly weighted.
  • The bug-localisation literature is about files, not repositories. Its top-k accuracy figures are not transferable to project-level routing, and I have used it only for its two structural findings — that text similarity alone is weak, and that the output was always a human-inspected shortlist.
  • No orchestrator was built or measured. Every claim about how placement would behave is an argument from artifact shape and shipped precedent, not from a running system. The abstention-rate concern in D-007 is exactly the kind of thing that only a real run can settle, which is why the engine is staged last.
