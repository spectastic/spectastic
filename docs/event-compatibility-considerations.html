Considerations · event compatibility vocabulary

Which words should an event compatibility stance use?

The registry world converged on four words. Adopting them is right — but only with the axis their defaults hide.

Status Accepted Author Brian Corbin · @briancorbinxyz Written 01 Aug 2026 Resolves the blocking vocabulary question in 077 Read time

Adopt the four registry words — backward, forward, full, none — and make the axis their defaults hide into an explicit second question. The ecosystem's non-transitive default checks a new schema only against the immediately previous version. That is a defensible default for a request/response API and the wrong one for events, because replay means a consumer reads messages written many versions ago. The registry world already has the fix — the _TRANSITIVE variants — but buries it in a suffix most teams never change. Surfacing it as its own question is not an embellishment: it is precisely what 077 FR-003 already demands, which asks the prompt to distinguish compatibility for future messages from readability of already-published ones. Those are the direction and the scope. Recommendation: two bounded questions, four words each, definitions pinned in the artifact. Enforcement: none, at any tier.

1 · The question

077 wants a design to record the producer's intended compatibility stance when a declared event contract changes. Its register left two questions blocking, and was explicit that the design verb refusing to run was the correct signal rather than a defect:

  1. Which compatibility vocabulary should the stance use? Registry ecosystems have converged on terms like backward, forward and full — but their precise meanings differ between implementations, and adopting one vendor's vocabulary imports its semantics. Expensive to get wrong, because the terms end up in authored artifacts.
  2. Should anything enforce the stance, and at which tier? Explicitly gated on the first.

This document answers both. It is deliberately narrow: it settles words and an enforcement posture, not a mechanism.

2 · What makes events different

The spec's context section states the problem precisely, and it is worth restating because everything below follows from it. A synchronous API change is bounded by today's callers. An event change is not, in two ways: messages persist, so a consumer may read something written months ago against a schema that has since moved; and consumers are not enumerable, so the set of things a change can break is unknown at change time. The field's own guidance is blunt about the second — without knowing consumers, you cannot govern breaking changes at all, which is why the mature answers are organisational (catalogs, lineage, contract testing) rather than technical.

Neither of those is something a spec tool can solve. What it can do — and what nothing else in the stack does — is make sure the decision was consciously taken and visible to a reviewer. That framing is already the spec's, and this survey does not widen it.

3 · The landscape

The words are settled

Confluent Schema Registry's vocabulary is the de facto standard across the Kafka ecosystem, and its meanings are stable and documented:

TermMeaningTypical permitted change
BACKWARDA consumer on the new schema can read data written with the old oneAdd optional fields; remove fields
FORWARDA consumer on the old schema can read data written with the new oneAdd fields; remove optional fields
FULLBoth of the aboveAdd or remove optional fields only
NONENo compatibility claimedAnything

BACKWARD is the registry default. The four terms apply uniformly across Avro, Protobuf and JSON Schema — the serialisation formats differ in mechanism, not in what the four words mean.

The mechanisms differ; the vocabulary does not

Worth knowing, because it is the most common reason people assume the words are format-specific. Avro pairs a writer schema with a reader schema and resolves at read time, which is why it leans so heavily on default values — a new field with a default lets old data be read as though the field had always existed. Protobuf instead tracks compatibility by field number, so renaming a field changes nothing on the wire, and the cardinal sin is reusing a retired number, because old bytes are then silently reinterpreted under a new meaning (hence reserved). Different machinery, same four words on top. Adopting the vocabulary therefore does not import a format's mechanism.

The trap: the default is scoped to one version

This is the finding that shapes the recommendation. A non-transitive check compares the new schema only against the latest version. The _TRANSITIVE variants — BACKWARD_TRANSITIVE, FORWARD_TRANSITIVE, FULL_TRANSITIVE — compare against all previous versions.

For a request/response API, checking against the latest version is reasonable: the callers are the callers, and they are current. For events it is close to meaningless. Replay is the entire reason events are different, and a replayed message may have been written many versions ago — precisely the range a non-transitive check does not examine. A producer can pass BACKWARD at every single step and still be unable to read its own topic from six months ago.

A concrete instance the guidance calls out: making a previously optional field required passes plenty of step-wise checks and breaks replay of retained or compacted messages. The registry world has the answer already — it is just a suffix that most teams never change away from the default.

4 · What the spec already asked for

The strongest evidence for the recommendation is that 077 arrived at the same distinction independently, before this survey ran. FR-003 requires the prompt to "distinguish compatibility for future messages from readability of already-published ones", and its rationale calls this "the distinction that makes events different from requests, and the one a diff-based check silently collapses."

Those two halves map exactly onto the registry model's two axes:

FR-003's wordingRegistry conceptQuestion to ask
Compatibility for future messagesThe directionbackward · forward · full · none
Readability of already-published onesTransitivity — the scopeAgainst the latest version, or against all retained history?

So the recommendation is not to invent a vocabulary, nor to adopt one wholesale. It is to adopt the four words and promote the suffix to a question — which turns an easily-missed default into a decision a reviewer can see, and satisfies FR-003 by construction rather than by interpretation.

5 · What adopting the vocabulary costs

  • The direction names are genuinely confusing. "Backward compatible" is routinely misread as "old readers can read new data" (which is forward). Mitigation: never ship the bare word. Every option carries its meaning inline — backward — a consumer on the new schema can read old messages — so the artifact is readable by someone who has never used a registry.
  • The words imply a registry that is not there. A reader may assume something validated the claim. Mitigation is already a requirement: FR-005 makes the tool say plainly that the stance is the author's claim, not a verified property.
  • Transitive is a stronger promise than most teams keep. Asking the question will sometimes surface that a team's real answer is "we do not know". That is a useful outcome, not a failure — but the option set must let them say it, so none stays a first-class answer rather than a failure state.

6 · Recommendation

D-001 · Adopt the four registry words, with meanings pinned in the artifact

Status
Accepted
Context
backward/forward/full/none are the de facto standard across the Kafka ecosystem and are format-independent — Avro, Protobuf and JSON Schema differ in mechanism, not in what the words mean. Inventing a vocabulary would cost every reader a translation.
Decision
Use the four terms. Never present a bare term: each option states its meaning inline, so the artifact is legible without registry experience.
Consequences
+ Readers and tools outside spectastic already understand the words. + Format-neutral, so one vocabulary covers AsyncAPI, proto and JSON Schema. − Imports a well-known naming confusion, mitigated by never shipping the word alone.

D-002 · Promote transitivity from a suffix to its own question

Status
Accepted
Context
Non-transitive checks compare only against the latest version; the _TRANSITIVE variants compare against all. Replay makes the latter the meaningful question for events, and the ecosystem default is the former. FR-003 independently asks for exactly this split.
Decision
Two questions, not one: the direction (four options) and the scope — against the latest version, or against all retained history. Record both.
Consequences
+ Satisfies FR-003 by construction. + Makes visible the single most consequential thing a step-wise check hides. + Two questions stay well within the decision-phase limits. − A second question on every event-contract change; justified because the answer is the one that governs replay.

D-003 · Record the stance; enforce nothing, at any tier

Status
Accepted
Context
077's second question asked whether anything should enforce the stance. Three facts settle it. FR-005 forbids the tool claiming to determine compatibility. The spec's out-of-scope list already excludes registry validation and structural breaking-change detection. And 074 already owns the "is a check configured" question for contracts generally — a second, event-specific version of the same detection would duplicate it while proving even less.
Decision
No enforcement and no new enforce category at any tier. The stance is recorded, surfaced to a reviewer, and optionally carried into the change notification. Any future enforcement is its own slug.
Consequences
+ The tool never implies it verified something it cannot. + No overlap with 074. + Keeps 077 documentation-and-prompt sized. − The stance is review-caught only, which is the honest ceiling for a claim about consumers the tool cannot see.

7 · Recorded ceilings

  • A stance is a claim, not a property. Nothing here verifies that a producer's declared stance matches what the payload actually did. A tool that says otherwise would be lying; FR-005 already requires it say so plainly.
  • Retention bounds what "all history" means, and this survey does not settle it. Transitive compatibility over a topic retained for seven days is a much weaker promise than over an infinitely retained one — and 077's out-of-scope list already defers retention and replay windows. The scope question therefore asks about intent, not about a measured window.
  • Format mechanics still bite beneath the vocabulary. A Protobuf producer reusing a retired field number breaks consumers while satisfying any stance it declares, because the wire format silently reinterprets old bytes. That is a structural detection problem, explicitly out of 077's scope, and the vocabulary cannot substitute for it.
  • Unknown consumers remain unknown. The organisational answers — catalogs, lineage, consumer-driven contract testing — are the real solution at scale and are all deliberately out of scope. Recording intent is strictly less than governing change, and is worth doing because nothing else in the stack does even that.
