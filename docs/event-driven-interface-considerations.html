Not every interface is an endpoint

The enforcement floor asks whether a project exposes a public interface, and answers by looking for a web framework. A service that publishes to a topic has consumers, a payload contract, and a compatibility problem — and is waved through in silence at every tier, including enterprise.

Status Draft Type Audit & landscape survey Author Brian Corbin · @briancorbinxyz Created 31 Jul 2026 Companion data-model-contract · coverage-enforcement Sources 8 external, retrieved 31 Jul 2026 · codebase audit Read time

Split out of the data-model and contract survey, which found this while looking for something else. INTERFACE_SIGNALS — the antecedent deciding whether contract-first applies at all — contains roughly forty dependency signals across six ecosystems, and every one of them is HTTP, GraphQL or gRPC. No Kafka, AMQP, NATS, Pulsar, SQS/SNS, EventBridge, Service Bus, Pub/Sub or Redis streams. So a service whose entire public surface is published topics passes the contract floor at verified and enterprise — marked covered, not warned, because the gate deliberately fails safe on the antecedent so CLIs and batch jobs are never false-failed. That posture is right for a CLI and wrong for an event producer. The oddity is that the tool already recognises the answer: isContractFile() accepts asyncapi.yaml, and AsyncAPI 3.0 covers request/reply as well as pub/sub, so it is not even a niche format. The tempting fix — reach for AsyncAPI when nothing says otherwise — is the one to avoid, because 050 FR-002 requires recommendations to be context-seeded and explicitly crownless where no source implies a winner. Recommendation: treat this as a symmetry defect, not a format preference. Widen the antecedent so an event-driven service is asked; add an interface-shape question to the design interview; let format follow the detected interface. And widen carefully — a broker client is often transitive, and dependency presence cannot distinguish publishing a topic from consuming one, which is exactly the false-failure 042 FR-014 was written to prevent.

1 · The ask — a service with no endpoints

This began as a footnote in another survey. The data-model and contract doc set out to answer where a backend's schema should live so a UI team in another repository could consume it. Reading the enforcement code to check how contracts are detected turned up something the question hadn't anticipated: for a large class of backends, the tool never asks for a contract at all.

The class is not exotic. A settlement service that publishes settlement.completed to a topic; an ingestion pipeline consuming from a queue and emitting enriched events; anything built on an event backbone rather than a request path. Each has downstream consumers who need the payload shape, each has a compatibility problem when that shape changes, and each has the same handover problem the companion doc is about. What none of them has is an endpoint.

Spectastic's own vocabulary makes the assumption visible once you look for it. The seeded principle promises that "a component that exposes an interface ships a checked-in contract"; the profile axis ladders informal → contract-first → contract-checked → versioned+governed. Neither says synchronous anywhere. The implementation does.

2 · What the gate actually looks for

The contract-first category is interface-gated, and the gate is a dependency-name match. exposesInterface() tests the project's root manifests against a fixed signal list. If nothing matches, the category is marked covered — "there is nothing to contract" — and the run moves on.

No Kafka client in any ecosystem, no AMQP, no NATS, no Pulsar, no SQS/SNS/EventBridge, no Azure Service Bus, no Google Pub/Sub, no Redis streams. Nor does any non-dependency signal contribute — a broker declared in a compose file, a serverless event mapping, or a .proto containing a stream all count for nothing, because the gate reads root manifests only.

The consequence is precise, and it is a silent pass rather than a visible gap. Run the enforcement gate against a service whose entire public surface is published topics, at the enterprise profile where contract-first sits in the hard floor, and it reports the category satisfied. Not warned. Not degraded to advisory. Satisfied — on the grounds that the project has no interface.

That is not a bug in the sense of a mistake. It is the deliberate fail-safe: warning on every interface-less project would fire on each CLI, batch job and internal library in the estate, which is precisely the warn-washing the enforcement design set out to avoid. The antecedent fails safe so that absence of evidence never becomes a hard failure. The defect is that the evidence being looked for is too narrow — a whole architectural style reads as absence.

The strangest part is that the answer is already recognised. isContractFile() accepts asyncapi.{yaml,yml,json} as a valid interface contract, and has since the category shipped. AsyncAPI is listed as an accepted contract in the spec text and in the generated project documentation. So the tool can recognise the answer to a question it has no way to ask. The gap is entirely on the asking side.

One smaller inconsistency sits alongside it. The seeded principle's own copy — the text written into a downstream project's constitution — names "OpenAPI, JSON Schema, or a typed signature." It omits AsyncAPI, and also .proto and GraphQL SDL, both of which the detector has always accepted. A project reading its own constitution would not learn that an AsyncAPI document satisfies the rule.

3 · The format — AsyncAPI, and what it now covers

If the gate is going to ask, the answer needs somewhere to go. AsyncAPI is the event-driven counterpart to OpenAPI: a document describing messages, channels and the binding to a particular broker — "depending on the protocol (such as MQTT, AMQP, Kafka), your AsyncAPI document may have additional fields."The AsyncAPI document concept and its protocol bindings [1]. It occupies the same position in the 2026 schema landscape that OpenAPI does for REST: a specification derived from JSON Schema, from which documentation, code and validation are generated rather than written alongside.The 2026 schema survey places AsyncAPI 3.0 beside OpenAPI 3.1 as a specification layer over shared JSON Schema, in a field whose organising claim is that "the unit of an API is the schema, not the endpoint" [2].

Worth knowing before treating it as the niche option: version 3.0 removed the assumption that "async" means fire-and-forget. It decoupled channels from operations — publish and subscribe were removed from the Channel Object, so channels became reusable across operations — and added an Operation Reply Object, making request/reply, "a very common messaging paradigm", expressible in an event-driven description.AsyncAPI 3.0.0 release notes [3]. The practical upshot for this doc: AsyncAPI is not confined to one-way pub/sub, so "which format" is a genuine choice for a mixed service rather than a foregone one.

So the format question is less binary than it looks. A service with both an HTTP surface and a published event stream does not have to pick; it honestly owes two documents, describing two contracts with two sets of consumers. Any rule that resolves to a single default would obscure exactly that case.

4 · Why not simply default to it

The obvious fix is to reach for AsyncAPI when nothing indicates otherwise. It is a reasonable instinct — the event-driven case is the one being neglected, AsyncAPI 3.0 generalises to request/reply, and a default costs nothing to state. It is also the one move this survey recommends against, and the reason is a standing requirement rather than a matter of taste.

050 FR-002 governs how the design verb recommends anything. Every recommendation "MUST be context-seeded — drawn from repo detection, standing docs … and the frameworks axis stance — and MUST NOT come from a spectastic-maintained house catalog," and, decisively for this question: "Where no source decisively implies a winner, options MUST be presented with no '(Recommended)' crown." A rule of the form default to format X absent context is precisely a crown in the no-context case — the exact state the requirement says must be crownless. The stance is load-bearing enough to carry a drift-guard test asserting the phrase survives in the command markdown, and the owning spec lists a maintained house catalog under out-of-scope as "deliberately never built."

The single sanctioned exception is narrow and does not fit: where context leaves contenders genuinely tied, the profile's frameworks axis breaks the tie by stance — minimal leans stdlib, staff-level leans batteries-included — never by naming a product. AsyncAPI-by-default names a product.

Separating the instinct from the proposed fix makes it stronger. The bias in the current system is not that it prefers OpenAPI to AsyncAPI. It is that it only recognises synchronous interfaces as interfaces at all. Correcting that is not a default; it is symmetry — and once the antecedent recognises a broker, the format follows from detection like every other stack choice, which satisfies FR-002 rather than needing an exception carved from it.

D-001 · Treat this as a symmetry defect; let the format follow the detected interface, never a default

Status
Proposed
Context
A service exposing only broker topics is exempt from contract-first at every tier, though asyncapi.yaml is already an accepted contract file. The obvious remedy — default to AsyncAPI absent context — would be a crowned recommendation in exactly the case 050 FR-002 requires to be crownless.
Decision
Fix the antecedent, not the default. Widen the interface signal set to include message-broker dependencies so an event-driven project is asked for a contract; add an interface-shape question to the design interview alongside persistence shape; and seed the format from what detection found — HTTP → OpenAPI, gRPC → .proto, GraphQL → SDL, broker → AsyncAPI, and both documents where both surfaces exist. Bring the seeded principle's copy to parity, since it names neither AsyncAPI nor .proto nor GraphQL SDL today.
Consequences
+ Closes a hole where an entire architectural style is silently exempt at the enterprise floor. + Context-seeded, so it satisfies FR-002 rather than requiring an exception from it. + Needs no new vocabulary — AsyncAPI is already recognised, so only the asking side changes. + A mixed HTTP-and-events service is prompted for both contracts instead of being nudged toward one. − Does nothing for a project whose broker usage is invisible to root manifests (infrastructure-only wiring, a managed bus configured out-of-repo). − Leaves format choice to detection, so an unusual stack still gets no recommendation — correct under FR-002, but less helpful than a default would feel.

5 · What widening actually costs

Widening an antecedent is not free, and the requirement it changes says so explicitly. 042's FR-014 does not omit brokers by oversight. It defines a detectable public interface as "an HTTP/RPC framework declared as a dependency", and then records the residual deliberately: an interface exposed via a framework outside the signal set "is silently exempt (a false-negative), which SHOULD be recorded as the honest ceiling rather than closed by widening the gate into false failures." So this is a change to a stated ceiling, arriving as a proposal, not an edit to a list.

That framing is right for an unlisted HTTP framework and, this survey argues, wrong for an entire architectural style — the difference between missing a member of a category and missing the category. But the caution it encodes is real and a proposal has to answer it.

A broker dependency is a weaker proxy than a web framework. Declaring express is close to declaring an intention to serve HTTP. Declaring a Kafka client is not: it may be a transitive dependency, an infrastructural concern pulled in by a framework, or a client used purely to consume from someone else's topic. Which leads to the sharper problem.

Dependency presence cannot distinguish publishing from consuming. A producer owes its consumers a contract; a consumer owes nobody one. The same kafkajs entry appears in both. Widening on the dependency alone would ask a pure consumer for a contract it has no business publishing — a false failure in exactly the direction FR-014 guards. The companion survey found the mirror image of this on the contract side: a project vendoring an upstream OpenAPI document to generate a client is marked covered though it publishes nothing.See the companion doc's §6 — a Rust crate using progenitor, an OpenAPI client generator, checks in a spec for an API it consumes [4]. Both directions have the same root: filesystem and manifest inference cannot read intent. Both point the same way: where the design artifact can declare the interface, a declaration should outrank inference.

And a newly-caught project inherits a harder compatibility problem than the synchronous case. Event contracts are, if anything, worse to evolve than REST ones: events persist and may be replayed by consumers that did not exist when they were written, so a change is not bounded by who is calling you today. The field's own conclusion is that "the best solution is to avoid breaking changes and minimise the need for versioning", with consumer-driven contracts, schemas published as code libraries, and registry-plus-broker validation as the practical options.On event-schema evolution and why replay makes it harder than request/response [5]. The schema-registry answer is the same one the protobuf ecosystem converged on [6]. Catching these projects is the right thing to do; it should be done knowing the tool has less to offer them afterwards than it does an OpenAPI project.

The tooling asymmetry is worth stating plainly, because it affects which rung of the contracts axis is honestly reachable. Linting and breaking-change detection are commodity for OpenAPI — a ruleset-driven linter and a diffing tool with a ready-made CI action, both permissively licensed.Spectral lints OpenAPI 2.0/3.x and AsyncAPI 2.x against extendable rulesets [7]; oasdiff detects changes that "break existing API clients" for OpenAPI [8]. Note the version gap: this doc cites AsyncAPI 3.0 for request/reply and channel decoupling, while the built-in lint ruleset covers 2.x. For AsyncAPI the equivalents are thinner, and thinner still for 3.x. A contract-checked rung that assumes parity would be overpromising.

D-002 · Prefer a declared interface over inferred presence; widen on evidence of publishing

Status
Proposed
Context
Dependency-name matching cannot tell a publisher from a consumer, and a broker client is a weaker declaration of public surface than a web framework. Widening naively would produce the false failures FR-014's ceiling was written to avoid, and the companion survey found the mirror false-positive on the contract-detection side.
Decision
Where the design artifact declares the interface a feature exposes, that declaration is authoritative and outranks manifest inference in both directions — it can establish that a contract is owed, and that one is not. Keep inference as the fallback for projects with no declaration, and when widening on inference alone, prefer signals that indicate producing over mere client presence. Do not raise a hard failure on inference alone for the broker case at first; land it as advisory and promote it once the signal proves itself.
Consequences
+ Resolves the publish-versus-consume ambiguity in the only place that actually knows the answer. + Same mechanism fixes the companion doc's vendored-spec false positive, so one change serves both. + Landing advisory-first matches how other categories earned their place in the floor. − A declaration is only as good as the design that carries it, so a project that skips the interview gets inference anyway. − Advisory-first means the hole stays open, more visibly, for however long the promotion takes. − Two sources of truth for "does this expose an interface", with a precedence rule to document and test.

6 · Recommendation — two moves, in order

One thesis anchors both: the defect is that the gate cannot see a whole class of interface, not that it prefers the wrong format. Fixing the seeing is the work; the format follows from it.

  1. Move 1 — make the gate able to ask. A proposal against 042 amending FR-014's definition of a detectable public interface to admit event-driven surfaces, with broker signals per ecosystem, landing advisory rather than in the hard floor until the signal proves itself. The proposal has to answer the publish-versus-consume ambiguity rather than defer it — that is the substance of the change, not a detail of it. Bring the seeded principle's format list to parity in the same batch, since it is a data/content delta on the profile catalog rather than a requirement change.
  2. Move 2 — make the design verb ask. An interface-shape question in the design interview, alongside the persistence-shape question that already exists: does this feature publish events, consume them, or neither, and on what transport. The answer seeds the contract format and — per D-002 — becomes the declaration that outranks inference. This is the half that makes the gate accurate rather than merely wider, and it belongs with the companion doc's design-section work.
Do not close this by widening the signal list alone. It is the smallest diff and it is the version most likely to cause harm: a project that merely consumes from a queue starts owing a contract it should not publish, the failure is hard at verified and enterprise, and the resulting noise is the strongest possible argument for reverting the whole change. The ceiling FR-014 recorded is a real warning, not bureaucratic caution. Widen with a way to say "this consumes, it does not publish" already in place.

Suggested next artifacts

  • A /spectastic.propose against 042: amend FR-014 to admit event-driven interfaces, with per-ecosystem broker signals landing advisory-first and the publish-versus-consume ambiguity answered in the proposal. Move 1 (D-001).
  • An interface-shape question in the design interview — publishes / consumes / neither, and on what transport — seeding the contract format and standing as the declaration that outranks inference. Move 2; pairs with the companion doc's design-section slug.
  • A data/content delta on the profile catalog: the seeded contract-first principle names OpenAPI, JSON Schema and typed signatures, omitting AsyncAPI, .proto and GraphQL SDL, all of which the detector already accepts. Copy fix, no requirement change.
  • A survey then spec: what contract-checked can honestly promise for events, given that the mainstream lint ruleset covers AsyncAPI 2.x while 3.0 carries the request/reply and channel-decoupling changes, and that breaking-change tooling is thinner than OpenAPI's.
  • The compatibility half, deliberately unscoped here: replayed events mean a payload change is not bounded by today's consumers, so the registry / consumer-driven-contract options are a different problem from "is a contract checked in."

7 · Caveats on the sources

  • The exemption is read from code, not observed in a running project. The audit traced exposesInterface() and the signal list directly and the conclusion follows from them, but no broker-only fixture was built and run through the enforcement gate to watch it pass. That test is the first thing a proposal should write, and it would be the honest confirmation this doc is reasoning toward.
  • "No broker signals" is a claim about the shipped list, which is a moving target. It was verified by reading the signal table and by searching the source for the obvious client names across ecosystems. A signal added after 31 Jul 2026 would not be reflected here.
  • The tooling-parity claim is directional. AsyncAPI's ecosystem is smaller than OpenAPI's, and the built-in lint ruleset cited covers 2.x — but the field moves quickly, generators and validators exist outside the two tools named, and "thinner" is not "absent". Treat it as a reason to scope contract-checked carefully, not as a verdict on the format.
  • Whether a category miss differs in kind from a member miss is a judgment, not a finding. This doc argues that missing all of event-driven architecture is different from missing one unlisted web framework, and that the ceiling FR-014 records was written with the second in mind. That is an interpretation of a requirement's intent, and the proposal it recommends is the proper place for it to be accepted or rejected.
