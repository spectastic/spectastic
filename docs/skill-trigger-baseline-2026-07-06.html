Skill-trigger accuracy baseline

The first recorded measurement of how reliably the ten command descriptions cause an LLM router to invoke the right verb — and what it reveals about where guarantees can and cannot live.

Status Accepted Type Measurement record (first baseline) Author Brian Corbin · @briancorbinxyz Created 06 Jul 2026 Method skill-creator run_eval, 20 queries/verb, 3 runs/query (~600 claude -p calls) Prompted bymeta-spec T-603 / REQ-TOOL-004 Read time

Across all 10 commands the trigger accuracy is a flat ~49%. The reason is mechanical: the descriptions reject a sibling's intent perfectly (0 false triggers in 98 negatives) but clear a should-trigger query never at a 2-of-3 majority (0 of 102) — only ~35% fired even once. The floor is uniform across every verb, so it does not rank description quality; it measures the general skill-under-triggering effect. Empirically, this is the guarantee-layer principle (P-8) in data: the description trigger surface cannot carry guarantees.

2 · What it says (and doesn't)

Precision is perfect. Not one description fired on a sibling's intent across 98 near-miss negatives — the sibling-boundary metadata (REQ-TOOL-004) does its job on the "don't grab the wrong verb" side. That is a real, positive result.

Recall is floored, and the floor is not description quality. It is a uniform 0%-at-majority across all ten verbs, with ~35% one-off firing. That uniformity is the tell: if wording drove the number, the verbs would spread. Instead they flatline, which points at the documented behaviour that a router consults a skill only for work it can't already do inline — most substantive-but-doable lifecycle intents get handled directly. Tuning the copy cannot move a metric that floors independent of it.

This is P-8 in data. 0 of 102 is about as clean a demonstration as exists that the trigger-by-description surface cannot carry guarantees. It is an ergonomic nudge — pleasant when it fires ~1-in-3 — not an invariant. Guarantees must live where a deterministic program, not an LLM's discretion, decides that a step runs: the kernel (REQ-CHANGE-008) and CI. See the guarantee layer.

3 · Why this is a floor, not a verdict on the copy

The local harness measures a proxy, not the production path. Three limits pull the number down uniformly and would need the deferred automated harness to remove:

  • Command, not skill. run_eval installs each description as a .claude/commands/*.md slash-command, which a router consults less autonomously than a first-class Skill.
  • Isolated, no competition. Each verb is tested alone — the real question ("given all ten present, does the right one win?") is never posed, so the family-competition signal the metadata is built for is untested here.
  • Coarse threshold. A 2-of-3 majority on three runs buckets a genuine ~30% trigger probability to a hard fail; more runs would surface a gradient.

A faithful measurement — all ten surfaced as real skills, competing, over more runs — is exactly the automated eval REQ-TOOL-004 defers to init --tools. Accordingly the "re-tune any command below the ≥90% target" leg of T-603 is not actionable against this signal (there is nothing to tune toward); it is deferred with the harness, and the ≥90% target remains a SHOULD. This document is the baseline that future, faithful runs are checked against.
