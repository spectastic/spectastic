Handover · Learning surface

explain --course

The "university" idea, reframed by the evidence: a personalized, blended, grounded learning mode that builds the person — sibling to the training-wheels protocol, which scaffolds the reviewer.

Status Handover · decisions locked, design proposed Kind Implementer handover (dogfooded in the design system) Owner Brian Corbin · @briancorbinxyz Last updated14 Jun 2026 Sibling Training-Wheels Protocol (D-001…D-005) Read time

The original ask — a /spectastic.university that spins up a custom mix of MCQ, hands-on work, and reading from the codebase / user / specs / an ad-hoc topic — is well-aimed, but the rigorous evidence reframes it. The thing that works is not a course platform; it is mastery + step-level feedback, grounded in real artifacts, delivered just-in-time. Three decisions are now locked: it ships as explain --course (a mode of an extended explain verb, not a ninth hero verb); the eight lifecycle verbs are reframed as the core / hero set while extended verbs like explain may be opt-in; and a course lives outside specs/, may be cross-spec, and is ephemeral. This doc records those decisions, the evidence behind the design, the recommended shape, the failure modes to avoid, and the open questions.

1 · What's decided

These three were ratified by the product owner during the research conversation and are recorded here as Accepted decisions. The design choices in §3 are still Proposed and need ratification.

D-006 · The course is explain --course, not a standalone command

Status
Accepted
Context
The idea arrived as /spectastic.university. But the training-wheels work already proposes an explain verb (D-003) as the on-demand, just-in-time coach. A course is the bigger, persistent sibling of an explanation — not a separate concern.
Decision
Ship it as a mode: explain <target> gives an ephemeral in-chat explanation; explain --course <target | topic> generates a persistent blended course. One verb, two depths. (Name: explain reads truer to the calm house voice than "university"; the mode flag carries the meaning.)
Consequences
+ No new top-level verb to justify. + The course inherits explain's grounding machinery. + Clear mental model: explain is small, course is large. − explain itself still has to be specified and built (it is only proposed today in D-003).

D-007 · Reframe: eight hero verbs, plus extended opt-in verbs

Status
Accepted
Context
The "don't add a ninth verb" discipline was treated as a hard cap. That framing made every genuinely useful capability fight for one of eight slots. The real intent is to keep the day-to-day surface minimal, not to forbid all further verbs.
Decision
Reframe the command surface in two tiers. Core / hero verbs (8): principles · spec · plan · tasks · implement · propose · apply · triage — the minimal set you actually need in the lifecycle, installed by default. Extended verbs: opt-in capabilities (e.g. explain) that need not be installed by default and are not "hero" features. explain (and thus --course) lives in the extended tier.
Consequences
+ Resolves the ninth-verb tension without diluting the core. + Lets the product grow capabilities without bloating the first-run surface. + Keeps the OpenSpec-style "small core" win intact. − Needs an install/enable story for extended verbs (a real, if small, packaging decision). − The per-verb "pay rent" discipline must still apply inside the extended tier, or it becomes a junk drawer.

D-008 · A course lives outside specs/, may be cross-spec, and is ephemeral

Status
Accepted
Context
The lifecycle artifacts under specs/<id>/ are stable, ID-bearing contracts. A course is the opposite: it may draw on several specs (or none — an ad-hoc topic), it is generated on demand for one learner at one moment, and it goes stale the instant the underlying code or spec moves. Filing it under specs/<id>/ would imply a permanence and a single-spec scope it does not have, and would pollute the contract directory with throwaway artifacts.
Decision
Courses are written outside the spec tree, in a dedicated, ephemeral location (recommended: a project-root courses/ or .spectastic/courses/ directory, git-ignored by default with an explicit opt-in to keep one). A course carries no stable IDs of its own; it references stable IDs in the specs/code it teaches. It may span multiple specs.
Consequences
+ The contract directory stays clean. + Cross-spec and ad-hoc courses have a natural home. + Ephemerality is honest — a stale course is discarded, not maintained. − Need a regeneration story (re-run explain --course) rather than an update/migrate one. − If a team wants to keep a canonical onboarding course, that is a deliberate opt-in, not the default.

2 · Why — the evidence that reshaped the idea

Six research streams converged on a single reframe: the failure modes of a "university" feature are all about detachment — detached-from-work content doesn't transfer, self-paced courses don't get finished, and LLM content detached-from-the-real-repo hallucinates. Grounding in the codebase / user / specs is therefore not a nice-to-have; it is the whole game. The six rules below are the design constraints that fall out.

RuleWhy (evidence)
Personalize to the knowledge state, never a "learning style." Drive --format from the objective's Bloom level + the learner's mastery state, not a self-declared style. "Learning styles" is one of the most robust negative findings in education research — no evidence for style-matching.Pashler et al., "Learning Styles: Concepts and Evidence"; review. The minimal viable "learner model" is per-skill mastery (BKT is four numbers/skill) — which maps onto the proficiency band (D-001).
Modality follows the cognitive target — and blend it. MCQ for Remember/Understand; hands-on for Apply/Analyze; Create is unreachable by MCQ. Interleave and space. Blending is double-backed: assessment validity (no single modality spans Bloom — Wiggins) and learning science — interleaving roughly doubles delayed-test scores; spacing beats massing.Wiggins, authentic assessment; Rohrer & Taylor (interleaving); Cepeda et al. 2006 (spacing). Cost: interleaving feels harder and lowers in-session performance, so learners under-adopt it.
Invest in the inner loop (step-level feedback), not a clever recommender. Step-based tutoring carries most of the ITS effect (d≈0.76, ≈ human tutoring); commercial adaptive platforms show weak/null causal effects.VanLehn 2006/2011 (outer/inner loop; effect sizes); Knewton/adaptive-courseware null results. For a chat-native tool: good feedback while you work beats any sequencing algorithm.
Ground every item in real source, then verify it. Retrieve real code/spec as context; check generated exercises against the repo (compile/run/test, or confirm referenced symbols exist). This is where rigorous evidence is strongest: LLMs confidently hallucinate APIs that don't exist in the real repo, and retrieval-grounding measurably fixes it (23–61% improvements).De-Hallucinator (arXiv); "LLM Hallucinations in Practical Code Generation" (arXiv). Same spirit as spectastic's "verify the spec wasn't lying" discipline.
Motivate with feedback, not points. No streaks, no badges, no leaderboard. Informational feedback + competence signals. Completion-contingent tangible rewards undermine intrinsic motivation (d≈−0.40, overjustification); verbal/informational feedback enhances it (d≈+0.33).Deci, Koestner & Ryan 1999 meta-analysis; Lepper et al. 1973. Also fits the calm, understated house voice.
Small, real, in-flow — and design for declared intent. Favor a "small real change" / good-first-issue shape; micro + spaced units; measure declared goals, not a completion funnel. Self-paced course completion is ~5–15% and ~52% never start (flat for a decade); in-flow learning solves the transfer problem.Reich & Ruipérez-Valiente 2019 (MOOC completion); Baldwin & Ford (transfer); 70-20-10's directional truth (the ratio itself is unvalidated folklore). "Learn by shipping a small real change" is strong practitioner consensus but its own evidence is anecdotal, not controlled.

The biggest trap is the obvious one. The seductive default — a polished course catalogue with XP, streaks, and a completion bar — is precisely the design the evidence says fails: shallow gamification crowds out intrinsic motivation, detached courses don't transfer, and ~52% never start. Build the un-flashy version: grounded, mastery-gated, feedback-rich, ephemeral, in-flow.

3 · Recommended design

All of the below reuses existing machinery; no new <spec-*> elements are required. These two decisions are Proposed — ratify before building.

Command anatomy

Follow the existing command-file shape (front-matter description + argument-hint; narrative intro; Inputs; Procedure with the two-phase interview; Output style). Sketch:

explain <target>
   # ephemeral, in-chat, just-in-time explanation (the D-003 coach)

explain --course <target | topic> [--proficiency=wheels|completion|independent]
   # generates a persistent blended course artifact, grounded + verified

# <target>  = a spec-id, a requirement/decision ID, a file/dir path, or several
# <topic>   = an ad-hoc subject with no repo anchor (weakest mode — see caveat)
 
Chat phase:    learning goal; what's already known; time budget;
               which spec(s)/paths/topic to ground in.
Decision phase (AskUserQuestion): proficiency band (defaults from
               D-001 if known); scope (one decision ↔ whole spec ↔
               cross-spec); depth. NOTE: do NOT ask "learning style."
               Format mix is DERIVED from each objective's Bloom level,
               not chosen by the learner.
 
<spec-meta>        learner · proficiency band · objective · mastery state
<spec-tldr>        "by the end you'll be able to…"
objectives         rendered as <spec-task> checkboxes = a MASTERY LEDGER
                   (:has(input:checked) strike = mastered)
per objective:     <spec-tabs> → Read / Quiz / Build variants
                   <spec-decision> teach-back prompt (wires to D-005)
<spec-glossary>    context-scoped domain vocab
Lives in:          courses/<date>-<slug>/course.html (git-ignored; D-008)

D-009 · Mastery-state personalization; Bloom-driven modality (no styles, no fancy recommender)

Status
Proposed
Context
The personalization promise is the risky part — it invites a "learning style" picker and a sequencing algorithm, both of which the evidence rejects.
Decision
The learner model is the proficiency band (D-001) plus a per-objective mastery flag — nothing more. Modality per objective is derived from its Bloom verb (recall → MCQ-with-feedback; apply/create → hands-on/build). Objectives are interleaved and spaced, not blocked. The band drives fading: Wheels gets worked examples + every objective; Independent gets a terse, skippable refresher. No streaks/badges/XP — feedback is the motivator.
Consequences
+ Cheap and evidence-aligned. + Reuses D-001 wholesale. + Sidesteps the learning-styles myth and the null-result recommender. − Must explain to the learner why interleaving "feels harder" (desirable difficulty), or they'll resist it. − Needs a place to read the band/mastery state from (ties to D-001's open storage question).

D-010 · Retrieval-grounded generation, verified against the repo

Status
Proposed
Context
Confident-but-wrong generated content is the dominant, rigorously-documented failure mode of codebase-grounded learning. A course that teaches a hallucinated API is worse than no course.
Decision
Every question/exercise is generated from retrieved real source (the named spec/decision/file), never synthesized from generic training. Before a course ships, each item is verified against the repo: build exercises run/compile/test; conceptual items pass a guessability check (reject any the model can answer with the source hidden — it's testing recall, not the spec); referenced symbols/paths are confirmed to exist. The existing risk-pass critic agent is the natural generator; the existing "verify the spec wasn't lying" discipline is the natural verifier.
Consequences
+ Directly attacks the dominant failure mode with the best-supported mitigation. + Ad-hoc topic mode (no repo anchor) is explicitly the weakest mode and should be flagged as such to the learner. − Verification costs time/compute. − Some objectives can't be auto-verified (design judgement); those route to a teach-back graded by a human or LLM-as-judge (D-005), not to an auto-passed quiz.

5 · Open questions for the implementer

  1. Where exactly do courses live, and is git-ignore the default? courses/ at root vs. .spectastic/courses/. Recommendation: git-ignored by default, explicit opt-in to keep one (D-008) — confirm.
  2. Extended-verb packaging. How is an extended verb like explain installed/enabled if not default (D-007)? A flag in a manifest, a separate install step, a marketplace listing?
  3. Where is the learner's band + mastery state stored? This is the same unresolved storage question as D-001 — a single-file-HTML world has no native per-author state. Resolve once for both.
  4. Who grades a hands-on / teach-back item? LLM-as-judge (gameable), a human shadow reviewer, or the repo itself (tests pass)? Likely all three by item type — but which is the v1 default, and does a failed item block "mastered" or only advise?
  5. Does explain ship before --course? explain is only proposed today (D-003). Sequence: build explain (ephemeral, in-chat) first; add --course once the grounding/verification path is proven.
  6. Ad-hoc topic mode. A topic with no repo anchor is the weakest, least-grounded mode (transfer problem, no verification). Keep it, gate it behind a warning, or drop it for v1?
