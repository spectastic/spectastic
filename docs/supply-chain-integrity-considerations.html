Considerations · Supply-chain integrity

When the spec is clean but the code is not

The xz backdoor hid where no one reads — a binary test blob and a release-only build script, landed by a maintainer who spent two years earning trust. A clean spec would not have stopped it. But intent held as data is a signal a raw diff can't offer.

Status Draft Type Threat model & research synthesis Author Brian Corbin · @briancorbinxyz Created 12 Jul 2026 Sources 21 primary, verified 12 Jul 2026 Read time

A spec-driven flow protects the human-facing surface — but the surface an attacker keeps clean is exactly spec.html. The xz-utils backdoor (CVE-2024-3094) is the worst case made real: the malice was not in any reviewable source diff. It lived in hand-crafted binary test fixtures and a build script that shipped only in the release tarball, introduced by a persona who spent ~2.5 years building trust while sockpuppet accounts pressured a burned-out maintainer into handing over the keys. Code review, CI, and any "no code-only PRs" policy would have — and did — sail past it; it was found by accident, through a 500 ms SSH slowdown. The blunt truth from the research is that detecting a deliberately-obfuscated backdoor's intent is unsolved, and the field has "no satisfactory solution for detecting malicious commits" today. So this doc does not promise detection. What it recommends instead is a risk score that forces a human look: spectastic holds the human-approved intent (spec → design → tasks) as structured data, and its coding drain already computes a per-task diff it currently discards. That gives it a signal generic scanners lack — a capability/scope delta versus what the spec authorized. A change that adds network, exec, filesystem, crypto, binary, build-script, or dependency surface unrelated to its stated task is cheap to compute and high-signal. Ranked cheap-first, downstream-project code first; spectastic's own build layer already sits near the top of the maturity curve.

1 · The threat — a spec-clean change hiding code malice

The fear is precise: in a spec-driven flow, a reviewer reads spec.html and approves the intent. But the malice need not live there. It can descend into the plan, the tasks, or — most dangerously — the code and build scripts, where the human-facing artifact stays innocent. The canonical instance is the xz-utils backdoor, CVE-2024-3094.

The malice was where no one reads. Andres Freund's original disclosure is blunt: "One portion of the backdoor is solely in the distributed tarballs" — a malicious macro in build-to-host.m4 that "is not in the upstream source of build-to-host, nor is build-to-host used by xz in git."Freund's oss-security disclosure [1]. An obfuscated script run at the end of configure rewrote the Makefile to decompress a payload hidden inside binary test fixtures (tests/files/bad-3-corrupt_lzma2.xz and a sibling — files "not even used for any tests"), piping them through xz -d | /bin/bash; the payload then hijacked the IFUNC resolvers to redirect RSA_public_decrypt. A normal git clone and build produced a clean binary — only the distro packaging path, which builds from the tarball, was compromised.TuxCare's mechanism write-up [2]; the binary blobs were hand-crafted with a hex editor, and a single stray . in CMakeLists.txt disabled a Landlock sandbox. There was no reviewable malicious source diff — the exploitable facts were binary blobs added to the repo and a build script that diverged from the source tree.

And it took years of trust. Russ Cox's timeline records the "Jia Tan" persona's first innocuous patch in October 2021; from April 2022 sockpuppet accounts ("Jigar Kumar", "Dennis Ens" — accounts that "never appeared elsewhere on the internet, even in data breaches") pressured maintainer Lasse Collin to hand off the project, exploiting his disclosed "longterm mental health issues"; commit authority came in December 2022; the backdoor shipped in v5.6.0 in February 2024.Russ Cox's canonical timeline [3]; Kaspersky's social-engineering analysis [4]. It was caught not by any security control but by chance — Freund investigating a ~500 ms SSH login slowdown and valgrind errors.The accidental discovery [5].

The lesson governs everything below: the attack was engineered to defeat human code review and diff-based tooling. No annotation requirement, no "no code-only PRs" rule, and no spec would have surfaced it.

2 · Why spec-driven development doesn't help by default

Spectastic's lifecycle runs spec → design → tasks → implement → verify, and its traceability is real but document-to-document: a success criterion links to a user story links to a test-task, all by id and href. That chain stops exactly where code begins. There is no persisted link from a requirement or task to the diff that fulfilled it — git trailers record attribution (Assisted-by, Acked-by, a Refs to the archived proposal), never a Task-Id or a diff hash. The <span class="path"> a task carries is authored intent ("this task should touch this file"), never checked against what actually changed.

So the attacker's move is easy: keep spec.html anodyne, and let the divergence live one layer down. A malicious task implementation, a compromised dependency added during the plan, a doctored build step — none of these contradict a clean spec, and spectastic captures no ground truth that would notice. The very thing that makes SDD reviewable to humans (the calm, high-level spec) is the surface an attacker most wants you reading.

3 · Where spectastic stands today

Every security control spectastic has shipped is scoped to the artifact injection surface — stopping attacker text from steering the tool inward (P-11, the no-executable-content rule, the template CSP, the 046 red-team). None of it inspects the project's source, build scripts, CI config, or dependencies. The exposure, boundary by boundary:

BoundaryExposure todayEvidence
Enforce categories Presence-only. The supply-chain category is "covered" if a renovate.json / gradle dependency-check / cargo deny.toml exists at the repo root. It opens no dependency, reads no lockfile, diffs no version. A configured updater ≠ a safe dependency tree. packages/core/src/enforce/detect.ts
Artifact security Injection surface only. The 045/046 layer blocks executable content and hidden-instruction channels inside a spec-family HTML document. It never reads a .ts/.py/.rs source file, a build script, or a diff. packages/schema/src/rules/no-executable-content.ts
Project code / deps / build Entirely unscanned. No source inspection, no lockfile/version-diff analysis, no build-script or CI-config review, no behavioral analysis of dependencies (the xz vector). No risk-score primitive exists anywhere. — (the gap)
Own release integrity Strong. npm --provenance via GitHub OIDC (Sigstore/SLSA attestation), a version-tag guard, Dependabot, frozen lockfile. Near the top of today's practical maturity curve. .github/workflows/publish.yml

The one boundary the research says most needs help — the project's own code and dependencies — is the one with zero coverage. And because spectastic's release integrity is already strong, the downstream project is where the marginal value is.

4 · What's detectable, what's advisory, what's unsolved

The research is unambiguous about not overclaiming. Malicious-code detection is provably undecidable in the general case, even weak obfuscation defeats commercial scanners, and a top-level ACM survey concludes practitioners "currently do not have satisfactory solutions for detecting malicious commits."Limits of static analysis [6]; ACM survey, state of the field [7]. The honest split:

TierSignalBasis
Detectable
cheap · deterministic		 Binary/blob files added (the exact xz vector); build-script / packaging / CI edits (*.m4, configure.ac, Makefile.am, CMakeLists.txt, .github/**, package.json scripts, .gitignore hiding build inputs); install/postinstall hooks; high-entropy / base64 blobs in a diff; new dependency additions; and diff-scope-vs-stated-task mismatch. OpenSSF Scorecard Binary-Artifacts + Code-Review checks [8]; "Backstabber's Knife" (56% of npm malware runs on install) [9]; "Weak Links in the npm supply chain" [10].
Advisory
real tooling / ML		 Capability-delta via call-graph — "did this update add a new capability (network / exec / fs / crypto)?"; LLM semantic intent-vs-code review that can articulate "this change does more than its stated purpose." Google Capslock compare mode [11], [12]; anomaly detection on commit metadata (Anomalicious, 53% caught) [13]; LLM PR-review routing humans (Datadog) [14].
Unsolved
do not claim		 Intent behind a deliberately obfuscated backdoor (undecidable); a patient trusted-insider campaign (the "Jia Tan" pattern); contributor/maintainer-trust scoring (no reliable tool). And note: LLM reviewers are themselves attackable — crafted PR metadata achieved a 100% detection-evasion rate in one study. Undecidability [15]; contextual-bias attack on LLM review [16]; social-engineering analysis [4].

The structural counter to xz lives at the build layer, not the spec layer. The only controls that would have caught the tarball-vs-repo divergence are reproducible builds and source↔artifact provenance — and SLSA itself treats reproducibility as recommended, not required, "considered very hard in practice."SLSA v1.1 FAQ on reproducible builds [17]; in-toto/SLSA attestation flow [18]. These are real, but they are a separate track from anything the spec layer can offer.

5 · The novel lever — capability delta vs. the authorized spec

Here is the one thing spectastic has that a generic scanner reading a raw diff does not: the human-approved intent, held as structured data. A `spec.html` says what the change is for; the plan and tasks say what it should touch. And — the key mechanical fact — spectastic's coding drain already computes a per-task diff in a sandboxed git worktree (it stages the worktree, takes git diff --cached HEAD, and already gates a task on "a file actually changed") before applying it into the working tree for review. Today that diff is applied and forgotten. It is exactly the ground truth a divergence score needs, available at exactly the moment a task's code lands.

The primitive: score a change by the capability and surface it adds, relative to what its task and spec authorized. A task described as "add a date-formatting helper" that touches a build script, adds a dependency, opens a network call, or drops a binary blob is surface unrelated to its authorized intent — a computable, high-signal anomaly. This is the deps.dev/Capslock idea ("flag when an update adds a new capability") re-based onto spectastic's advantage: not "new capability vs. the last version" but "new capability vs. the approved requirement." Composed the way mature tools compose risk — Scorecard's risk-weighted sum of cheap checks, CVSS×EPSS's impact×likelihood framing — it yields a single change-risk number.Scorecard's risk-weighted aggregation [19]; CVSS vs. EPSS (severity vs. exploit-likelihood) [20].

A score is not a verdict. Empirical work finds even mature scoring systems give conflicting, confusing signals on the same vulnerability."Conflicting Scores, Confusing Signals," 600 real vulnerabilities across CVSS/SSVC/EPSS [21]. The value of a change-risk score is not that it labels malice — it can't — but that it forces a human to look at the changes whose footprint exceeds their stated purpose. It raises the attacker's cost; it does not close the door.

6 · Recommendation — a layered, staged posture

Two theses anchor this: a change's capability should be accountable to its spec, and we surface risk, we do not claim detection. Ranked cheap-first; downstream-project code is the primary boundary (spectastic's own release integrity is already strong).

D-001 · Adopt a change-risk posture anchored by an accountability principle

Status
Proposed
Context
A spec-clean change can hide malice in the plan/tasks/code; spectastic scans none of it and has no risk primitive. Detecting obfuscated malice is unsolved, but spectastic uniquely holds the approved intent as data and already computes a per-task diff it discards.
Decision
Adopt the ranked controls below and ratify a principle — "a change's capability and scope must be accountable to the spec that authorized it" — as the invariant the controls trace to (the P-8 pattern: the principle is the contract; a deterministic change-risk scan is the guarantee half). The score forces review; it never certifies safety.
Consequences
+ A first project-code-facing security signal, staged so the cheap deterministic flags land first. + Reuses spectastic's own advantage — approved intent as data + the drain's diff hook — for a signal generic scanners can't compute. − The score is advisory and can conflict/misfire; that residual is recorded, not hidden. − It cannot detect an xz-style backdoor or a trusted-insider campaign — stated plainly, per the P-8/P-11 honesty posture.
  1. Cheap deterministic red-flags — the P-8 floor. A change-risk scan over a diff, surfacing weighted advisory findings: a binary/blob file added, a build-script / CI / packaging edit, an install/postinstall hook, a high-entropy or base64 blob, a new dependency. Deterministic, language-agnostic, and exactly the surface signals xz threw off. Reuses the PerFileRule / folded-CLI-scan shape and the hard-gate CI job pattern.
  2. Spec-anchored capability/scope-delta score — the headliner. At the coding-drain diff hook, score a task's real footprint against its declared path and its spec's authorized surface; flag capability (network / exec / fs / crypto) and files unrelated to the stated intent. Composes with the P-9 un-relaxable security/supply-chain floor.
  3. Advisory ceilings — recorded, not built now. Call-graph capability-delta (Capslock, language-limited) and LLM semantic intent-vs-code review (non-deterministic, and itself attackable via crafted metadata — so never the sole gate).
  4. Spectastic's own build layer — a secondary track. Reproducible-build / source↔artifact verification and hash-pinned GitHub Actions: the true structural counter to xz, deferred because release provenance is already strong.

Suggested next artifacts

  • A /spectastic.principles amendment ratifying "a change's capability and scope must be accountable to the spec that authorized it" as the anchoring invariant (the P-8 contract half; enforcement lands in the scan).
  • A new spec: the tiered change-risk scan — slice 1 the cheap deterministic red-flags, slice 2 the spec-anchored capability/scope-delta at the drain diff hook.
  • Spectastic's own build-layer hardening — source↔artifact / reproducible-build verification and hash-pinned Actions.
  • Verify incoming dependency provenance (SLSA/Sigstore attestation) at the supply-chain enforce boundary — moving that category from presence-only toward content-aware.
  • Contributor / maintainer risk signals — recorded as a far ceiling; no reliable tooling exists, and the social dimension the xz attack exploited is human judgment.

7 · Caveats on the sources

  • Malicious-commit detection is not solved, and no source claims it is. The ACM survey [7], the undecidability results [6][15], and the LLM-review attack [16] all point the same way: any composite score is a triage aid, not a guarantee.
  • Capability analysis is language-limited. Capslock's call-graph capability detection is strongest for Go; robust equivalents do not exist for every ecosystem. The cheap deterministic flags (tier 1) are the portable floor.
  • Scoring systems disagree. The empirical study [21] found significant disparity across CVSS/SSVC/EPSS on the same vulnerabilities — a caution against over-trusting any single composite number, including a spectastic change-risk one.
  • xz specifically would still evade the spec layer. Its payload was not in reviewed source, so a source-side capability-delta check alone would not have caught it. Only build-layer reproducibility/provenance structurally would — hence the secondary track.
