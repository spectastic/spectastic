Considerations · Competitive analysis

OpenSpec

What's worth absorbing from OpenSpec — and what isn't — given spectastic's calm-dense, single-file HTML bet.

Status Draft Type Pattern survey Author Brian Corbin · brian@example.com Created 12 Jun 2026 Sources 12 primary, verified 12 Jun 2026 Subject Fission-AI/OpenSpec v1.4.1 Read time

OpenSpec is the popular alternative to spec-kit — ~54k stars on GitHub, Node ≥ 20.19, MIT-licensed, YC-launched. It strips ceremony spec-kit imposes and earns its traction from lightness, not structure. Three of its patterns are clean wins for spectastic to absorb (change-as-folder, delta semantics, init-with-tools-flag); two are differentiators worth leaning into the opposite direction (stable IDs, the HTML renderer); two are deliberately out of scope for now (principles-required-by-default, action-detecting unified commands). The format we use to capture this analysis is itself an example of the bet: <spec-decision> cards and a <spec-matrix> carry the verdicts more honestly than markdown could.

1 · What OpenSpec is

OpenSpec is a spec-driven-development framework for AI coding agents, published by Fission AI (YC-launched). Its distinctive bet is spec-as-deltas: a long-lived specs/ folder records what currently exists, and each proposed change is a sibling folder containing only the delta. On archive, the delta folds into the live spec; the change folder is preserved verbatim under changes/archive/.

Format
All markdown, plus one optional YAML config touchpoint. No HTML, no JSON Schema, no renderer.

Directory layout

openspec/
├── specs/<domain>/spec.md             ← long-lived
├── changes/<change>/
│   ├── proposal.md                    ← intent / scope / approach
│   ├── design.md                      ← architecture decisions
│   ├── tasks.md                       ← hierarchical - [ ] checklist
│   ├── .openspec.yaml                 ← optional
│   └── specs/<domain>/spec.md         ← delta (ADDED / MODIFIED / REMOVED / RENAMED)
├── changes/archive/<YYYY-MM-DD-change>/
└── config.yaml

Commands

Two CLI verbs do real work; everything else is agent-side slash commands. Default action profile (v1.0+): /opsx:propose → /opsx:apply → /opsx:sync → /opsx:archive. The expanded profile adds /opsx:new, /opsx:ff, /opsx:continue, /opsx:verify.

OpenSpec ships no MCP server ("no API keys, no MCP required") and no hooks that prevent edits without a proposal. Discipline is conventional. Practitioner complaint #1 in the wild is that agents simply ignore the specs when nothing forces them to obey — openspec update is the standard remedy when that happens. This is a clean opportunity for a competitor to differentiate on enforcement.

2 · Patterns at a glance

One row per distinctive pattern. Verdict column is the recommended stance for spectastic; rows we should adopt are highlighted.

PatternVerdictNote
Change-as-folder Adopt One change = one PR-shaped folder. Reviewer-friendly; matches GitHub workflow.
Delta semantics (ADDED/MODIFIED/REMOVED/RENAMED) Adopt & improve Express as <spec-delta op="…">; tags carry semantics without OpenSpec's silent-fail hash counting.
init --tools <id> installer Adopt One command drops .claude/skills/ + commands into a project. Currently spectastic is "clone the dir."
validate command Adopt & exceed Queryable HTML > loose markdown. We can check anchors, ID uniqueness, conformance coverage in ways OpenSpec can't.
No MCP, no enforcement hooks Differentiate Ship a validate --strict CI hook + opt-in Claude Code stop-hook. Practitioner-stated gap.
No constitution (OpenSpec stance) Lean light Make spectastic's principles document truly optional — picked up if present, not required to start.
No stable requirement IDs (identity = header text) Opposite stance Our id="REQ-AUTH-001" is a contract. Lean in; never adopt OpenSpec's RENAMED escape hatch.
No renderer / viewer Already differentiated Single-file HTML with a calm typographic system is exactly the gap. Lead with it in copy.
Action-based commands (no phase gates) Out of scope Spectastic's five-phase commands are pedagogical. Detect-and-pick adds complexity without clear user benefit.
Adopt = build now if scope allows. Differentiate = ship the gap OpenSpec leaves open. Opposite stance / Already differentiated = continue current direction with confidence. Out of scope = revisit if telemetry justifies.

3 · Pattern deep-dives

One <spec-decision> per pattern, in the order of the matrix above.

C-001 · Change-as-folder

Status
Adopt
Context
OpenSpec's signature move. Each proposed change is a folder (changes/<name>/{proposal,design,tasks}.md + delta specs) mapping 1:1 to a PR. On archive, deltas fold into the live spec; the folder moves to changes/archive/<YYYY-MM-DD-name>/ preserved verbatim.
Decision
Add specs/<id>/changes/<date>-<name>/proposal.html as a sibling of the existing spec.html / plan.html / tasks.html. The proposal HTML wraps a <spec-change> root element with intent/scope/status and embeds one or more <spec-delta> children.
Consequences
+ Review surface matches GitHub PR shape exactly. + Living spec stays compact; history sits in archive/. + Multiple parallel changes can coexist for one feature without merge conflicts on the spec itself. − Authors must learn a new artifact type. − Slash commands grow by two (/spectastic.propose, /spectastic.apply).

C-002 · Delta semantics

Status
Adopt & improve
Context
OpenSpec deltas live under fixed markdown headers: ## ADDED Requirements, MODIFIED, REMOVED, RENAMED. The parser is strict-by-hash-count; ### Requirement: = 3 hashes, #### Scenario: = 4. A wrong-level header fails silently. REMOVED requires **Reason** and **Migration** bold-label fields.
Decision
Express deltas as typed custom elements: <spec-delta op="added|modified|removed|renamed" target="REQ-AUTH-007">. The op is an HTML attribute, machine-readable, parser-trivial. For op="removed", make reason="" and migration="" required attributes; the validator fails closed if either is missing.
Consequences
+ Zero silent-fail surface. + Stronger schema than markdown headers can carry. + Renames are atomic (the target attribute is the rename). − Authors learn one new element family. − The four ops need four distinct visual treatments in CSS — left-border colour + corner pill — to read at a glance.

C-003 · init --tools <id> installer

Status
Adopt
Context
OpenSpec ships an init command that writes per-tool skills + slash commands for Claude Code, Cursor, Windsurf, GitHub Copilot, Kimi, ForgeCode, Mistral Vibe, and Trae (25–30 tools by current count). Non-interactive flag: openspec init --tools claude,cursor.
Decision
Add scripts/spectastic (Python 3, single-file, already on every macOS box) with init [--tools claude] that copies assets/, templates/, and commands/ into the current project and registers them under .claude/commands/spectastic.*.md. Start with Claude Code; add more tools per concrete user request.
Consequences
+ One-command adoption replaces "clone or copy this directory". + No build step to introduce. − Python is a runtime dep, but it's pre-installed on the target user base (Mac/Linux devs).

C-004 · validate command

Status
Adopt & exceed
Context
OpenSpec's validate is structural-only: required headers present, correct hash counts, REMOVED carries Reason+Migration, tasks use - [ ]. No broken-link check, no requirement-coverage analysis, no archived-change reference graph. It runs automatically before archive.
Decision
Implement spectastic validate [path] [--strict] over the spectastic HTML tree, checking everything OpenSpec does plus: every anchor resolves; every id is unique across spec + active changes; every <spec-requirement> ID matches the project pattern; every <spec-delta op="modified|removed|renamed"> targets an ID that exists in the live spec; every <spec-delta op="added"> targets an ID that doesn't yet exist; every <spec-triage> has a valid layer= enum. --strict exits non-zero for CI.
Consequences
+ Beat OpenSpec on the dimension they're already getting field complaints about. + Single CI hook covers the whole project. − Validator must be kept in lockstep with the component vocabulary; a missed update breaks builds.

C-005 · Enforcement (the gap OpenSpec deliberately leaves)

Status
Differentiate
Context
OpenSpec advertises "no MCP required" and ships no hooks. The most-cited limitation in HN and blog write-ups is that agents ignore the specs because nothing forces them to obey. openspec update is the canonical "after the fact" remedy.
Decision
Ship an opt-in Claude Code stop-hook (settings.json snippet) that runs spectastic validate --strict before any commit and refuses edits to spec.html directly when an active changes/<name>/ folder exists. Default off; document loudly.
Consequences
+ Sharp competitive lever — the gap OpenSpec users explicitly ask for. − Hook setup is a one-time speed bump; some users will not enable it.

C-006 · Principles: light by default

Status
Lean light
Context
OpenSpec has no principles analogue. Spec-kit requires a constitution as phase 1. Spectastic currently sits closer to spec-kit. Practitioner write-ups consistently cite the constitution-as-required pattern as a brownfield friction point.
Decision
Update /spectastic.spec so it does not require principles.html — it picks one up if present and silently runs without one if not. /spectastic.plan's Principles-Check section becomes optional in the template when no principles document exists.
Consequences
+ Brownfield-friendly. + Greenfield projects still have the discipline available. − Some users will skip the principles forever; that's their choice.

C-007 · Stable requirement IDs (lean into our advantage)

Status
Already-have
Context
OpenSpec's requirements are identified by header text, e.g. ### Requirement: Dark mode toggle. Rename a requirement and every delta referring to it breaks unless you also write a RENAMED section. Identity is fragile; the parser can't help you find references.
Decision
Continue with stable id="REQ-<TOPIC>-<NNN>" attributes per our spec. Renames are content edits; the ID survives. Document this contrast explicitly in our positioning.
Consequences
+ Reliable cross-document linking. + LLMs target IDs, not names. + Validator can enforce uniqueness trivially. − Authors must invent IDs; mitigated by pattern conventions in the template.

C-008 · Renderer / viewer

Status
Already-have
Context
OpenSpec ships no renderer. Specs are read raw in editors. There is no web UI, no static-site exporter, no PR-preview integration.
Decision
Lead with this in marketing copy. Spectastic is the renderer. The artifact and the view are the same file. A reviewer opens spec.html in their browser and gets the document the author saw.
Consequences
+ Distinctive positioning. + Zero infrastructure to maintain. − Single-file size will grow over time; the inliner script must stay competitive on payload size.

4 · If we acted — three sketches

For each adoption candidate, a 150-word sketch of what implementation would look like. The point is that a future session can pick up without re-running the research.

Change-proposal workflow (C-001 + C-002). Add <spec-change> and <spec-delta op="…"> to assets/spec.css — ~80 lines, two new CSS rules per op (left-border colour + corner pill). Create templates/proposal.html following the standard spectastic header shape, with a <spec-change> root containing scope/intent and one or more <spec-delta> children. Add /spectastic.propose <change name> that scaffolds specs/<spec-id>/changes/<date>-<name>/proposal.html, pre-filled with target IDs the user names. Add /spectastic.apply that applies the deltas to spec.html, moves the change folder to archive/, and appends a <spec-changelog> entry. Ship a worked examples/proposal.html with all four op variants. Estimated effort: half a day.

CLI installer (C-003). Write scripts/spectastic as a Python 3 single-file with argparse. Subcommand init accepts --tools (default claude; future: cursor,aider,copilot) and copies assets/, templates/, commands/, scripts/inline.sh into the current working directory. For --tools claude, additionally write .claude/commands/spectastic.*.md (copies of the command files at project root) and, optionally, a minimal .claude/settings.json snippet enabling the stop-hook. Detect existing files and prompt before overwriting. README install instructions reduce to: curl -sL .../install.sh | sh && spectastic init. Estimated effort: a half-day, including a smoke test on a clean directory.

Validator (C-004 + C-005). Same Python file, subcommand validate [path] [--strict]. Use Python's built-in html.parser (no new deps); walk each .html in the tree; collect every element with an id attribute; collect every href="#…"; cross-check. For <spec-delta>, parse op and target and check against the live spec's IDs. Print human-readable errors with file:line. Exit 0 if clean, non-zero with --strict if any error. Bundle an example pre-commit hook in the README. Estimated effort: one day for full coverage; a half-day for v0.1 (anchors + IDs + delta target check).

5 · Open questions

  1. Order. If we commit to any of the three sketches, which comes first? The change-proposal workflow gives users the most visible new capability; the CLI installer unlocks adoption; the validator is the foundation for the others to be trusted in CI. Reasonable order: validator → CLI → change-proposal, but it's also defensible to start with the change-proposal so we can dogfood the workflow ourselves.
  2. Principles lightness. Do we want to actively de-emphasise the principles document, or just make it skippable? Spec-kit's brand is partly built on the constitution as a required phase 1; spectastic could either claim that lineage or distance itself.
  3. CLI distribution. If we ship a Python CLI, what's the install story? pipx install spectastic? A single-file curl-pipe-bash? A homebrew tap? Decision affects scripts/spectastic structure.
  4. Action-based commands. Out of scope today, but worth a revisit when telemetry shows users getting confused by the five-command lifecycle. The detect-and-pick approach is genuinely OpenSpec's most user-friendly choice.
  5. Cross-tool installer scope. Spectastic's components are HTML — they render in any browser. But the slash commands are Claude-specific. Is the Cursor/Aider/Copilot story worth building before there's a concrete user asking for it?
