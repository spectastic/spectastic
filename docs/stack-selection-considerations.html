Considerations · Stack selection

Choosing the stack at the plan stage

The plan records the stack it was handed. It never offers the choice. And when it does show alternatives, it crowns the one already chosen — by fiat, not by score. Two fixes, both at the plan's own decision phase.

Status Draft Type Research synthesis Author Brian Corbin · @briancorbinxyz Created 22 Jul 2026 Sources 12 primary, verified 22 Jul 2026 Companion agent-architecture · deployment-operations Read time

Spectastic decides the technical stack at the plan stage — but authors it by hand. The §2 Technical-context rows (Language, Frameworks, Storage, Testing) are filled from grounding reads and narrative chat; the decision-phase interview records a pick whose contenders already surfaced, but never generates a bounded choice-set with recommendations for a decision not yet made (Java vs C++, Spring Boot vs Quarkus, no-dep vs Cobertura vs JaCoCo). Worse for a greenfield: the plan command never reads CLAUDE.md / AGENTS.md / a linked architecture doc, so it can't even tell what's already decided to skip it — and the frameworks profile axis (minimal/conventional/staff-level) that could seed a recommendation is an inert token with zero code consumers. On the second concern — "alternatives considered only holds one option and always crowns the chosen one" — the audit both corrects and confirms it: the §5 <spec-matrix> does hold 3+ options, but each <spec-decision> card is a Nygard ADR that records only the chosen path (no per-decision options list, no link to its matrix), and the matrix's data-winner highlight is bound to the choice, not the score — nothing checks the crowned winner is the top-scored row, so it is a post-hoc justification device. The recommendation routes both through the plan's existing decision phase, not a new verb: (1) an optional, context-seeded stack interview (recommend from the detected ecosystem + the frameworks stance + standing docs; neutral where nothing decides it — prompt with context, never prescribe a house catalog); (2) wire the inert frameworks axis as that stance; (3) move the decision representation toward MADR — a "Considered Options" list with balanced pros/cons and named decision drivers, link matrix to decision, and make the crown follow the score (or drop it). Not a new verb, not a profile axis, not an enforce category.

1 · The question — record the stack, or help choose it?

Two complaints, one stage. First: spectastic defines the technical stack at plan time, but does so by hand — incrementally as the chat surfaces picks, or lifted wholesale from a standing instruction. There is no optional interview that presents the user with bounded choices and recommendations for decisions that have not yet been made. When the answer is genuinely open — Java or C++? Spring Boot or Quarkus? no-dep, Cobertura, or JaCoCo? — the plan does not help you decide; it waits for you to have decided, then transcribes it.

Second, a suspicion about the record. The "alternatives considered" surface seems to hold only one option, and seems to always weight whatever was chosen highest — even when the numbers might say otherwise. That is a falsifiable claim, and §3 adjudicates it precisely (it is half-wrong and half-worse-than-stated). Both complaints point at the same place — the plan's decision phase — and the canon has a clean answer for each.

2 · How the discipline chooses — and records — a stack

Two questions hide here: how do you drive a technology choice, and how do you record it so the record isn't just a rationalisation. The prior art separates cleanly.

Recording: Nygard ADR vs MADR. Michael Nygard's original ADR is a terse Context / Decision / Consequences — it documents the decision that was made, and by design centres the single chosen path.ADR templates — Nygard's minimal Context/Decision/Consequences shape alongside the richer variants [1]. MADR (Markdown ADR) adds exactly what a fair comparison needs: a first-class Considered Options list, Decision Drivers (the criteria), and Pros and Cons of the Options — with the choice justified in a Decision Outcome section rather than by making the winner louder.MADR — "the considered options with their pros and cons are crucial to understand the reasons for choosing"; supplemental parts include decision drivers and per-option pros/cons [2], [3]. The distinction is the whole of the second complaint.

ShapeStructureWhere the alternatives liveBias posture
Nygard ADRContext · Decision · ConsequencesNot recorded in the card — the chosen path onlyStructurally centres the one decision
MADRContext · Decision Drivers · Considered Options · Pros/Cons per option · Decision OutcomeFirst-class list, each with balanced pros/consChoice justified by drivers, not emphasis
Decision matrix / ATAMWeighted criteria × options → scored trade studyRows scored against explicit, pre-agreed criteriaWinner falls out of the scores — if criteria precede scoring

Driving: weighted criteria, and where the criteria come from. The heavyweight method is a decision matrix — prioritise and weight measurable quality criteria, score each architectural approach, let the total decide — which is the tractable cousin of the SEI's ATAM (a scenario-based, multi-day evaluation against competing quality attributes, "the gold standard for evaluating software architectures").ATAM — a structured, scenario-based evaluation against competing quality attributes; SEI's method collection [4], overview [5]. The criteria themselves are not invented per project: "when selecting criteria for a decision matrix, the quality model of the ISO standard can provide support" — ISO/IEC 25010's quality attributes are the reusable menu.Weighted decision matrices with ISO 25010 as the criteria source for well-founded architecture decisions [6]. The load-bearing subtlety: a matrix is only honest if the criteria are fixed before the options are scored — otherwise the scores are back-filled to make the pre-chosen option win.

Recommending without prescribing. The interactive-scaffold canon shows how to offer a choice well. create-t3-app "runs in interactive mode, prompting you with questions to configure your application," with "opinionated defaults that just work" — "opinionated enough to make decisions for you… but not so opinionated that it prevents you from swapping."create-t3-app — interactive prompts (Clack) + opinionated-but-swappable defaults [7], [8]. That is the shape to borrow — a recommended default the user can override — but with a critical difference: create-t3-app owns one stack and can ship a fixed catalog. Spectastic spans every ecosystem and is brownfield-respecting-by-charter, so its recommendation must be context-seeded, not a maintained house catalog.

Where the choice belongs. In spec-driven development the plan stage is where "technical design including architecture, tech stack, and dependencies" is settled, and the project's constitution holds the "high-level immutable principles that apply to every change" — the analogue of a repo's CLAUDE.md / AGENTS.md standing instructions.SDD — the plan stage owns architecture/stack/dependencies; the constitution codifies standing conventions read at every step [9], [10]. A stack interview belongs at plan, and it should read the standing docs first — both are exactly where spectastic has a gap.

3 · Where spectastic stands today

The machinery to fix this already exists — a two-phase interview, an AskUserQuestion path with a built-in "(Recommended)" convention, a decision element, a scored matrix, a profile axis, and a stack detector. None of it is wired to help choose a stack.

3a · No stack-selection interview

  • §2 is hand-filled. The Technical-context <dl> in templates/design.html carries free-text rows — [LANGUAGES_AND_VERSIONS], [FRAMEWORKS_AND_VERSIONS], [TEST_STACK_AND_STYLE] — with no structure for "chosen vs. alternatives" and no recommendation trace. Only the Architecture and Coverage rows are fed by an AskUserQuestion decision; the rest land from whatever the grounding read and chat surfaced.
  • The interview records, it doesn't generate. The one stack-relevant bullet in the decision phase — plan.md: "Each tech-stack pick that has 2–4 reasonable contenders (language version, async runtime, test framework, etc.)" — presupposes the contenders already exist. It anchors a pick the chat surfaced; it has no logic to enumerate a bounded choice-set for an undecided dimension. The recommendation machinery is right there but unwired: "First option is the recommendation, labelled (Recommended)." The grounding step frames the stack as something to verify — "confirm the symbol/option you intend to use exists," "the target language's hard constraints" — presuming it is already chosen.
  • Standing docs are never read. The plan command never opens CLAUDE.md, AGENTS.md, or a linked architecture doc (a grep for those names returns nothing). Only principles.html and .spectastic/profile.json (enforcement tools only) feed in — so the interview cannot know what's already decided in order to skip it.
  • The frameworks axis is inert. spectastic-profiles.json tiers it minimal / conventional / staff-level, but nothing in packages/ reads it — a documentary token with no build-vs-buy mapping. It is the obvious hook for a recommendation stance, currently unused. (And the detector in packages/core/src/enforce/detect.ts can see the existing ecosystems and exposed frameworks — but by explicit charter it "reports gaps, never prescribe[s] a specific tool," with no greenfield "recommend a stack when none exists" path.)

3b · The "alternatives considered" claim — adjudicated

The concern was that "alternatives considered only allows one option, and always weights the chosen highest even if something else was chosen." The audit both corrects and sharpens it.

Sub-claimVerdictWhy
"Only one option is considered"Half-trueFalse for §5: the <spec-matrix> scaffolds three option rows and the command asks for "1–3 alternatives" (">4, ask in chat"). True for the <spec-decision> card (§6): it is a Nygard ADR (Status/Context/Decision/Consequences) recording only the chosen path — no per-decision options list, and nothing links a matrix to a decision. Looking at a card, you correctly saw one option.
"Always weights the chosen highest, even if something else was chosen"True — and uncheckedThe command mandates "one row marked data-winner… the winner must be the one actually chosen," and the CSS crowns that row (highlight background + bold first cell). But the score column is unvalidated hand-typed placeholders, and no CSS, JS, or schema rule checks the crowned row is the top-scored one. A matrix can show Option B scoring higher while Option C stays crowned.
The matrix is a post-hoc justification device, not a decision aid. Because the winner is bound to the choice (not the score) and the criteria are scored after the pick is made, the scored matrix cannot drive a decision — it can only dress one already taken. That is the exact failure the decision-matrix canon warns against: criteria must precede scoring, or the numbers are motivated reasoning. The fix is not to delete the matrix (multi-option scoring is genuinely good) but to make the crown follow the score and to move the option comparison into the decision card where MADR keeps it honest.

4 · Recommendation — route both through the plan's decision phase

Both complaints live at the plan's decision phase, so both fixes go there — not a new verb (the eight-verb surface is a deliberate win; the decision phase already absorbs what other tools ship as a separate /clarify), not a profile axis, not an enforce category. Three coupled moves, weighted to keep spectastic's prompt-with-context, never prescribe posture.

D-001 · An optional, context-seeded stack-selection interview

Status
Proposed
Context
The plan authors §2 by hand and only records stack picks whose contenders already surfaced; it never generates a bounded choice-set with a recommendation for an undecided dimension, and never reads the standing docs that would tell it what's already fixed. The AskUserQuestion "(Recommended)" machinery already exists, unwired.
Decision
Add an optional decision-phase pass that reads standing context first — repo detection (detectEcosystems, INTERFACE_SIGNALS) + CLAUDE.md/AGENTS.md/a linked architecture doc + principles.html — to learn what's already decided or ruled out, then interviews only the undecided material dimensions (language, framework, test framework, coverage tool, persistence). Each is a bounded AskUserQuestion with a context-seeded default; where nothing decisive implies a winner, the options are presented neutrally with no crown. No spectastic-maintained house catalog. Skippable — a standing instruction that already fixes the stack short-circuits it.
Consequences
+ Turns "transcribe the stack" into "help choose it," using machinery that already exists. + Reading standing docs means the interview never re-asks a settled question. + Keeps faith with the detector's "report gaps, never prescribe a specific tool" — the recommendation is contextual, not a shipped opinion. − One more optional pass to keep from bloating the interview (bounded to undecided, material dimensions). − Advisory (T-009): it nudges a deliberate choice, it cannot guarantee one. − Requires the standing-doc ingest (D-adjacent, its own slug).

D-002 · Give the inert frameworks axis its first consumer

Status
Proposed
Context
The frameworks axis (minimal/conventional/staff-level) is a documentary token with no code consumer and no build-vs-buy meaning. A context-seeded recommendation needs a stance to seed from.
Decision
Map the axis to a build-vs-buy lean that seeds the D-001 default: minimal → prefer stdlib / no-dep; conventional → the mainstream framework; staff-level → the mature, batteries-included choice. The stance is a tie-breaker for the recommendation, not a gate — the detected ecosystem and standing docs still dominate, and the user still overrides.
Consequences
+ Finally makes an existing axis do work instead of sitting inert. + Gives the recommendation a principled, tier-aware default rather than an ad-hoc one. − Advisory only; no enforcement. − Must resist hardening into a prescribed catalog — the axis sets a lean, not a pick.

D-003 · MADR-ify and de-bias the decision representation

Status
Proposed
Context
The <spec-decision> card is a Nygard ADR that records only the chosen path; the option comparison lives in a separate, unlinked <spec-matrix> whose data-winner crown is bound to the choice, not the score, and is checked by nothing. So the record centres the winner by fiat.
Decision
Move the card toward MADR: a first-class Considered Options list with balanced pros/cons per option and named decision drivers (criteria fixed before scoring); link each matrix to its decision (a target= tie, mirroring <spec-risk target> / <spec-slo target>); and make the crown follow the score — either a schema rule that the data-winner row must carry the top Total, or drop the automatic visual crown so the choice is justified by the drivers, not by emphasis.
Consequences
+ Fixes both halves of the complaint at once — the card gains its options, the matrix stops crowning by fiat. + A driver-first, score-consistent matrix can actually drive a decision, not just dress it — and pairs naturally with D-001's interview output. + Ties the two artifacts that were silently disconnected. − A schema/template change to a load-bearing element — deliberate, so it's its own spec. − "Criteria before scoring" is a discipline the tool can encourage but not fully enforce (an honest ceiling).

Suggested next artifacts

  • A /spectastic.propose against the plan verb adding the optional decision-phase stack-selection pass — enumerate undecided material dimensions, present bounded options with a context-seeded (Recommended) default, skip what detection/standing-docs already fix.
  • Teach the plan grounding step to read CLAUDE.md / AGENTS.md / a linked architecture doc as standing stack constraints (so the interview asks only the open questions). May fold into TBD-plan-stack-interview as one plan pass.
  • Wire the frameworks axis (minimal/conventional/staff-level) as the recommendation stance — its first code consumer — feeding the interview's default lean.
  • A spec moving <spec-decision> toward MADR (Considered Options + decision drivers + per-option pros/cons) and linking each <spec-matrix> to its decision via target=.
  • A no-executable-content-style schema rule that the crowned data-winner row carries the top Total (or drop the automatic CSS crown). May fold into TBD-madr-considered-options.

5 · Caveats on the sources

  • "Nygard centres the chosen path" is about the template, not the author. A disciplined author can narrate alternatives in a Nygard Context/Consequences prose block; the point is that the structure doesn't scaffold it, whereas MADR does. The fix is making the good behaviour the default shape, not claiming Nygard forbids it.
  • ATAM is heavier than spectastic's altitude. A full ATAM is a multi-day, multi-stakeholder evaluation; the borrowable part is the weighted-criteria-before-scoring discipline, not the ceremony. The existing <spec-matrix> already gestures at the decision-matrix form — the gap is criteria-first honesty, not method weight.
  • "Context-seeded, never prescribed" is a posture, not a guarantee. A recommendation can still be wrong for a project the signals misread; it is a nudge with an override, consistent with the plan's existing "prompt, don't prescribe a house pattern" for architecture.
  • The create-t3-app analogy has a deliberate limit. It ships a fixed catalog because it owns one stack; spectastic cannot, which is exactly why the recommendation is seeded from per-project context rather than a maintained list. Read it for the interaction shape, not the catalog.
