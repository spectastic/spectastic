Recipes · Contract distribution

Getting a contract across a repository boundary

Two mechanisms, one coordinate. Neither is blessed, and the surface works identically under both — which is the point.

Spec 076 gives a contract a federation-unique coordinate and emits a notification when a promotion changes it. It deliberately does not ship a distribution mechanism: FR-004 requires the export surface be mechanism-agnostic, and forbids it requiring any particular package registry, schema registry or generator. Choosing one is an organisational decision, not a tooling one.

These are two worked recipes — vendoring and a published artifact — showing the same coordinate and the same notification serving both. Neither is built by spectastic; both are described so the claim "mechanism-agnostic" is something you can check rather than something you have to take on trust.

1 · What both recipes share

Whichever mechanism you pick, three things are identical, because they come from the producing repository's own artifacts rather than from the transport:

The coordinate
spectastic://<owner>/<repo>/contract/<name> — stable across the contract's whole life. It names what the contract is, never where its file sits, so the producer reorganising its own tree cannot break a consumer that pinned one. Resolve it locally with spectastic contract <name>.
The notification
Emitted by the promotion kernel when a contract lands, carrying the coordinate and the producer's claim about whether the change is breaking. A withdrawal is a breaking change carrying a reason, not a separate kind — so a consumer branching only on breaking-versus-not is still correct.
The consumer declaration
An optional consumes array in spectastic.json, listing the coordinates this project depends on. Absent by default; a monorepo where producer and consumer sit together needs no entry at all.

None of the three mentions a registry, a package manager, or a generator. That is the property the two recipes below exist to demonstrate — not a claim about how you should ship a contract.

2 · Recipe A — vendoring

The consumer keeps a copy of the contract in its own repository. Simplest to set up, no publishing infrastructure, and the copy is visible in review; the cost is that the copy can go stale, which is exactly what the notification is for.

Producer

  1. Declare the contract in the design's Data model & contracts section, with a stable name=.
  2. Land it through the normal lifecycle. Promotion writes the effective contract and emits the notification.

Consumer

  1. Copy the contract file into the consuming repository — conventionally under contracts/vendor/, so it reads as someone else's artifact rather than one this project owns.
  2. Record the coordinate it came from in spectastic.json: 
    {
  "consumes": ["spectastic://acme/billing/contract/invoices"]
}
  3. On a notification for that coordinate, re-copy the file and re-run your own checks. A breaking claim means read the diff before doing so.

What spectastic does here: gives you the coordinate, and tells you when it changed. The copy is yours to make — the tool never fetches it.

3 · Recipe B — a published artifact

The producer publishes the contract as a versioned artifact — an npm package, a Maven artifact, a schema-registry entry, an OCI artifact; the recipe does not care which. More setup, and the consumer's dependency tooling does the fetching and version pinning it already knows how to do.

Producer

  1. Declare the contract exactly as in Recipe A — no change. The declaration is unaware of the mechanism.
  2. Add a publish step to your existing release pipeline that ships the promoted contract file. Spectastic has no opinion about which packaging you use, and no step here is a spectastic command.

Consumer

  1. Depend on the published artifact through your ordinary dependency tooling.
  2. Record the same coordinate in spectastic.json — identical to Recipe A: 
    {
  "consumes": ["spectastic://acme/billing/contract/invoices"]
}
  3. On a notification for that coordinate, bump the dependency. A breaking claim means read the changelog before doing so.

What spectastic does here: exactly what it did in Recipe A. The coordinate, the notification and the consumes entry are byte-identical between the two recipes; only the steps spectastic has no part in differ.

Five of six rows are identical, and the one that differs is the row spectastic contributes nothing to. That is the mechanism-agnosticism claim, stated as something checkable. It is also SC-004, and the integration test exercises both recipes against the same surface rather than asserting the property in prose.

5 · What is deliberately not here

  • A per-tier recommendation of which mechanism to use. That would be an addition to the profile catalog — a posture ladder like the existing axes — rather than part of this surface, and it was re-deferred rather than left blocking a slice that does not depend on it.
  • Consumer-driven contract testing, which needs both sides of an integration running and belongs to the testing categories.
  • Spectastic fetching a remote coordinate. The tool resolves against local declarations and makes 0 network calls; adding a fetch would be a new capability, and the surface is designed not to need one.
