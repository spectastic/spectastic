Considerations · Lifecycle design

Verification

"How do I know it works — and how do I run it?" has no home in the lifecycle today. This is where it should live, and why it must be generated, not written.

Status Draft Type Design brief (a /doc — feeds a future /spectastic.spec) Author Brian Corbin · @briancorbinxyz Created 23 Jun 2026 Sources 6 primary, verified 23 Jun 2026 Read time

spectastic is thorough at specifying what should work and tasking what to build, but stops at "implementation complete" — no artifact tells a human how to run, demo, or verify the built feature. The fix is two layers in two places. The universal "definition of done" belongs in the constitution — a new principle P-7 · Done means verified plus the agent-facing detail in CLAUDE.md. The per-feature "how do I verify this" belongs in a generated verify.html that aggregates what already exists (success criteria, acceptance, test tasks) and adds the one genuinely-missing piece: a medium-agnostic Run / Demo block filled by /implement from what it actually ran. It is generated, not hand-written, because drift is the single thing developers dislike most — and peer tools (Kiro, spec-kit, Tessl) ship nothing here, so it is a clean differentiation.

1 · The gap

The lifecycle reads principles → spec → plan → tasks → implement → propose → apply → triage. It is rich at the front: spec.html carries measurable success criteria (SC-NNN), per-story acceptance conditions (§2 User scenarios), and a "smallest demoable" prompt in the header; tasks.html opens every user story with test-first task phases. But once /implement ticks the last box, the lifecycle goes quiet. Nothing answers the question a teammate actually asks:

"Great — it's built. How do I run it? How do I see it work? What do I have to turn on?"

This is not hypothetical. Dogfooding spec-tictactoe, the UI shipped and there was no way to tell how to run the whole thing — the spec said what it should do, the tasks said what was built, and the gap between "done" and "I can see it" was a private act of archaeology.

It also breaks a habit many engineers already keep. A good merge request reads what · why · how · validation. spectastic has clean homes for three of them — what → tasks.html, why → spec.html, how → plan.html — and validation is homeless, even though it is "a subset of tasks and the implemented code." spec-kit felt the same pull and shipped a per-feature quickstart.md (and, early on, an expectation that every feature be runnable from the CLI). The instinct is right; the execution is what this brief is about.

What already exists is genuinely good and must not be duplicated: the INVEST self-check ties V to an SC-NNN and T to an acceptance scenario; tasks.html is test-first; the conformance index auto-builds from requirements. The missing thing is narrow — the bridge from "verified in CI" to "here is how you run and see it."

2 · What the field does

Three findings shape the design.

Peer tools are weak here — which is the opportunity

Martin Fowler's comparison of the three leading spec-driven tools is blunt: there is "no evidence that any tool generates demo instructions, validation runbooks, or mechanisms to prevent acceptance criteria from diverging from actual code behavior… a significant unaddressed challenge" (SDD with 3 tools). spec-kit's quickstart.md is planning-phase guidance, and its checklists are "like a definition of done for each step (though interpreted by AI, so there is no 100% guarantee they will be respected)". Kiro and Tessl describe none. So "is it done, and how do I check?" is open ground (spec-kit).

Definition of Done is universal; Acceptance is per-feature

The agile literature draws a line spectastic can borrow wholesale: Acceptance Criteria are unique to one story (what this feature must do); the Definition of Done is a checklist that applies to every increment (tests pass, security, quality) (Scrum.org). That maps cleanly onto spectastic's question of "principles vs verbs": a universal bar belongs in the constitution; a per-feature one belongs in a per-feature artifact.

Drift is the enemy — so generate, don't write

The thing developers dislike most is documentation that lies. Stale docs correlate with higher defect rates, go materially out of date within 30–90 days, and erode trust until people stop reading them (documentation drift). The decisive mitigation is mechanical: "generated documentation cuts the manual work that creates inconsistencies… when the spec changes, documentation regenerates without human coordination" (generated vs manual). Gojko Adzic's Specification by Example says the same from the other side: keep the WHAT separate from the HOW, because "if we include unnecessary details, the specification becomes impossible to maintain… and will go out of date very quickly." The executable examples are the living documentation.

The lesson for spectastic: a hand-written verify.html would be the worst possible artifact — a fourth copy of the success criteria and test list, guaranteed to drift the moment the spec or tasks change. Anything we add here MUST be generated/aggregated, or it is a net negative.

3 · The thesis — two layers, two homes

Verification splits the way Definition-of-Done splits from Acceptance: a universal layer and a per-feature layer. Each gets the home its altitude demands.

D-1 · The universal "definition of done" goes in the constitution

Status
Recommended
Context
The bar that every feature must clear — tests pass, spectastic validate clean, interactive HTML browser-checked ("presence ≠ containment") — is identical across features. It already exists as prose under CLAUDE.md § Verification discipline, but as guidance, not a ratified rule, so it isn't traced by anything. DoD is universal (Scrum.org).
Decision
Add a principle — P-7 · Done means verified — elevating the verification discipline to a non-negotiable every downstream spec traces to. Keep the agent-facing detail (Playwright for interactive artifacts, the structural backstop, the linter-is-not-noise rule) in CLAUDE.md; promote it to AGENTS.md if/when spectastic goes cross-tool (a broader direction we've discussed).
Consequences
+ One canonical bar, greppable, citable from any spec's success criteria. + No per-feature duplication of "what done means." − A principle amendment (version bump) is required to land it.

D-2 · Per-feature verification is a generated view, never hand-written

Status
Recommended
Context
The per-feature inputs already exist, scattered: SC-NNN + acceptance in spec.html, the test-first phases in tasks.html. Copying them into a new doc guarantees drift (§2). spectastic already has the right pattern — <spec-conformance> auto-builds from requirements.
Decision
The per-feature surface aggregates (links + traces SC → acceptance → test tasks), it does not copy. The only net-new, hand-authored content is the one thing the codebase has nowhere: a Run / Demo block (see §4). Regeneration from the sources is the anti-drift mechanism.
Consequences
+ Cannot drift on the parts it borrows — they're links. + The authored surface shrinks to the single irreducible thing. − Cross-file aggregation needs a build step (single-file HTML can't fetch siblings — see §6).

D-3 · A standalone verify.html, over a buried section

Status
Recommended
Context
The view could be a co-located <spec-verify> section inside tasks.html ("verification ⊆ tasks", less lifecycle surface) or a standalone verify.html per spec. The dogfooding failure was specifically one of discovery — not not having the info, but not finding how to run it.
Decision
A standalone generated verify.html per spec. A reviewer landing in specs/<id>/ sees the file named for the question they have. The usual cost of a standalone doc is drift — but D-2 already removed that by generating it.
Consequences
+ Discoverable; maps to the MR "validation" section as a first-class artifact; spec-kit-quickstart-shaped without the staleness. − One more file per spec (justified by D-2 making it cheap to keep honest).

D-4 · No new verb — /tasks scaffolds it, /implement confirms it

Status
Recommended
Context
spectastic guards its 8-verb surface (a small command set is one of OpenSpec's wins worth keeping — see openspec considerations). And spectastic validate already names the schema validator, so a /validate verb would collide. (That collision is also why the artifact is verify.html: validate = the spec is well-formed; verify = the feature works.)
Decision
No new verb. /tasks scaffolds verify.html (the SC + acceptance + test-task links are derivable then). /implement confirms it — filling the Run / Demo block from what it actually ran and marking it verified, the way REQ-LIFECYCLE-006 grounds plan facts in real source.
Consequences
+ Verb count stays at 8. + The Run block is grounded, not guessed — it's the command the implementer actually used. − /tasks and /implement each grow a small responsibility.

4 · The Run / Demo block — the one new thing

Everything else verify.html shows is borrowed. This block is the net-new content, and it is deliberately medium-agnostic — spec-kit's old "every feature must run from the CLI" is too rigid; a UI feature's demo path is a click-path, a library's is an import, a service's is a request. It captures whatever the real path is:

Run
The build/start commands — e.g. pnpm --filter @spectastic/vscode build, then F5 in VS Code to launch the Extension Host.
Toggle
Any feature flag / env var / setting that must be on — e.g. SPECTASTIC_AI_STUB=…, or "none."
Tests
The exact command that exercises this feature's tests — e.g. npx playwright test tests/vscode/ — linked to the test tasks they cover.
Demo
The click-path / URL / request that shows it working to a human — e.g. "open the canvas panel, select a spec, click a node → its rendered artifact opens." Traces to the SC-NNN it satisfies.

Because /implement fills this from the commands it genuinely executed in its Verify step, the block is a record of a real run, not aspirational prose — the same grounding discipline the plan applies to design facts. That is what keeps it from rotting.

The proposed principle, in the existing principles.html shape:

P-7 · Done means verified (proposed principle)

Statement
An increment is not done because the code exists; it is done when it is verified — its tests pass, spectastic validate is clean, and anything with a runtime has been exercised in a browser, not just asserted present ("presence ≠ containment"). Every spec's success criteria trace to this bar, and every feature ships a verify.html that says how a human confirms it.
Why
The verification discipline already exists in CLAUDE.md but as guidance nothing traces to; a structurally-passing-but-behaviourally-broken artifact (019's quiz gate) shipped under exactly that gap.

6 · Open questions

  1. Aggregation needs a build step. Single-file HTML can't fetch its sibling spec.html/tasks.html at render time, so the "traced" links must be materialised by a generator (a spectastic verify build, or the /tasks+/implement verbs writing it). This is the same cross-file constraint as the deferred-roadmap rollup — worth solving once, generally.
  2. How is the Run block captured? Does /implement record the literal commands it ran (a typed <spec-run> element?), or does the author confirm a draft? Grounding wants the former.
  3. Feature-toggle representation. A typed element (so it's greppable and a missing-toggle renders loudly), or prose? Leaning typed, mirroring the visible-failure pattern.
  4. Does verify.html carry its own lifecycle status, or derive it from the spec's bundle (per REQ-LIFECYCLE-005)? Probably derive — it's a view, not an independent artifact.
  5. Is P-7 one change or two? The principle (a /spectastic.principles amendment) and the verify.html mechanism (a feature spec) are separable; the principle could land first and stand alone.

7 · Out of scope (for this /doc)

  • Building verify.html, the generator, or the /tasks//implement changes — this brief feeds a future /spectastic.spec.
  • Authoring the P-7 amendment to principles.html — a separable /spectastic.principles change.
  • Reviving spec-kit's "every feature must be CLI-runnable" requirement — explicitly rejected as too rigid; the Run / Demo block is medium-agnostic.
