Considerations · Reliability architecture

The guarantee layer

A verb loaded as a skill is advisory. If a step must happen, its guarantee cannot live in the markdown.

Status Draft Type Research synthesis Author Brian Corbin · @briancorbinxyz Created 2 Jul 2026 Sources ~20 primary, verified 2 Jul 2026 Prompted bymeta-spec T-008 / T-009 Read time

Spectastic's verbs are markdown slash-commands loaded as skills. Their steps — the pre-verb interview, the post-verb git commit — are prose the model can skip. That is not a tuning problem; it is structural: an instruction to an LLM is never a guarantee. A step is guaranteed only when deterministic code the model can't skip runs it and can say deny. The good news: spectastic already made the right bet — the kernel is that deterministic layer, and everything reliable today (apply's fold + auto-commit, the validate rules) lives there, not in the markdown. The reliability incidents (T-004, T-006, T-008) were all steps that lived outside the kernel. This doc surveys what other tools can and can't enforce, and concludes that the two deferred items — init --tools and validate --strict — are the guarantee layer, and should be reframed as such.

1 · The one distinction

A step is guaranteed only if both hold:

  1. The harness — not the model — invokes it. Deterministic code runs it whether or not the model cooperates.
  2. It can say deny. A pre-action gate that can abort the tool call, not a post-action observer that fires after the damage.

Everything else is the same class, no matter how it's dressed: command markdown, skill descriptions, .cursor/rules, copilot-instructions.md, conventions files, MCP tool descriptions. All of it is advisory prose the model can skip, reorder, or half-satisfy. Spectastic's current design — mandatory steps written into commands/*.md — has, by construction, zero enforcement. That single sentence is the whole T-004 / T-006 / T-008 arc: every incident was a mandatory step that lived in markdown and got skipped.

This is why REQ-TOOL-004 (better skill-invocation descriptions) is a UX nudge, not a guarantee — and that's fine, as long as the guarantee lives elsewhere. Two empirical pilots (skill-creator's run_loop against the tuned spec description) confirmed descriptions can't carry the load: sibling boundaries measured perfectly, but positive triggering is dominated by "the model just does the task directly," not by description quality.

2 · Two asks, two different answers

The post-verb side effect and the pre-verb judgment gate are not the same problem and don't have the same solution.

Post-verb side effect (git commit)Pre-verb judgment gate (the interview)
Guaranteeable? Yes — it's a deterministic side effect. No — not the way it's tempting to think.
Why A git commit is pure code; a hook or the kernel can just run it, model-independent. A hook can block the write until a marker exists — but if the LLM writes the marker, it fakes the gate. Hooks enforce tool execution, never model reasoning. You cannot force a good interview.
Where the guarantee lives Deterministic code: the kernel (already true for apply), a Stop/agentStop hook running git commit, or a git pre-commit/CI check. Make the output checkable, then reject bad output. An unresolved <spec-question> in the finished artifact is the "interview failed" signal — gate on it in validate + CI. Post-hoc artifact validation, not pre-hoc write-gating.

The interview insight is the subtle one: stop gating the write; gate the artifact. Spectastic already has the bones — the no-unresolved-question validate rule and the CLAUDE.md discipline that "an open <spec-question> in a finished artifact signals the interview failed." That is exactly the pattern the research points to. It just needs to become an unbypassable gate (CI), not advisory guidance.

3 · Cross-tool landscape

Every tool with a real guarantee shares one property: an external, harness-invoked process that can return deny. Everything that only reshapes the prompt is best-effort.

The skeptical finding worth internalising: MCP gives you nothing here. The spec is explicit that the host/LLM decides which tools to call and when; tools, sampling, and even elicitation (the closest thing to a "required interview") are advisory — the client only SHOULD honor them and every request can be declined. MCP is the wrong layer to seek a sequencing guarantee.

The enforcement primitive (blocking hooks) is per-harness — different event names, config paths, and return schemas per tool — and the one cross-tool protocol (MCP) can't enforce. So there is no single portable in-agent mechanism that guarantees pre/post steps across all tools. Portability has to come from below the agent (VCS/CI) or from owning the loop.

4 · The four options, ranked

  1. Own the loop with a deterministic orchestrator. LLM calls are nodes; control flow is code (LangGraph is the reference; a plain script driving the steps also counts). One enforcement point, fully portable, guarantee in your code. Strongest. Spectastic already owns this: the kernel.
  2. Push to VCS/CI. Server-side pre-receive / required status checks. Client pre-commit is bypassable (--no-verify); server-side/CI is unbypassable and harness-independent.
  3. Per-harness hook adapters. Ship .cursor/hooks.json, .github/hooks/, .claude/settings.json, etc., each calling one shared script. Real enforcement, N configs to maintain, nothing for hook-less tools.
  4. Prompt-only (today). A UX nudge, never a guarantee. Fine layered on top of 1–3; never the guarantee itself.

5 · What this means for spectastic

The kernel is your deterministic orchestrator — you already own option 1. Everything that reliably works today lives there, not in markdown: spectastic apply folds deltas and auto-commits (REQ-CHANGE-007 / -008, git.auto), the fold-gap guard, the validate rules. The research doesn't ask you to adopt something new — it says finish moving guarantees off the markdown and into the kernel + CI.

Two items already on the deferred list are the guarantee layer, and should be reframed as such:

spectastic init --tools → the hook-adapter + git-hook installer

Context. Deferred as an installer convenience. Decision. Reframe it as the home for option 3 (per-harness hook adapters) and for installing a git pre-commit hook that calls spectastic validate. Each harness's hook config is a thin adapter that calls one shared spectastic gate command. Consequence. This is exactly Copilot's documented pattern ("install a pre-commit hook so the agent can't commit without the check, even if it ignores the instruction"). It also owns the .claude/commands/ sync that T-006 needs.

spectastic validate --strict → the unbypassable CI gate

Context. Deferred as a CI convenience. Decision. This is where "artifact has an open <spec-question> → the interview was skipped → reject the merge" and "the commit/fold shape is wrong" become guaranteed, harness-independent, and unbypassable. Consequence. The interview guarantee is achieved here — not by gating the write, but by rejecting the artifact. Post-verb commit quality is guaranteed here too.

For post-verb commits specifically: route the hand-run paths through the kernel (or a thin Stop-hook adapter that calls spectastic), so the commit is code, not an LLM's good intention. The kernel already does this for apply; implement's hand-run path is the gap.

6 · Recommendation

This is a distinct architectural concern — the guarantee layer — bigger than any one verb. The candidate invariant, worth a principle:

A mandatory step's guarantee MUST live in the kernel or in CI, never in command markdown. Markdown is advisory; the kernel and CI are the enforcement. Any step whose omission is a defect must have a deterministic owner that can run it or reject its absence.

Concrete path: capture as a meta-spec triage card (T-009, principles layer) → a principle amendment → a spec that pulls init --tools and validate --strict forward as the guarantee layer. REQ-TOOL-004's descriptions stay as the UX nudge on top.

7 · Caveats on the sources

  • The Claude Code hook-event catalog returned by research included some speculative event names. The load-bearing mechanics are solid and independently corroborated: PreToolUse can deny via exit 2; Stop can run deterministic shell; PostToolUse only observes. Verify exact event names against the live docs before wiring any .claude/settings.json.
  • Aider's Python orchestration API is explicitly "not officially supported… could change without backwards compatibility." Treat orchestration-via-aider as unstable.
  • Continue.dev's "no blocking hooks" is absence-of-evidence; re-check directly before relying on it.
