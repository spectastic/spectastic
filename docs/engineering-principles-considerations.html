Considerations · Profile principles

Engineering principles, tiered by profile

Spec Kit ships its best principles as one untiered constitution. Spectastic's profiles can offer the same principles — laddered by rigor. That is the industry-correct answer, and no other spec-driven tool does it.

Status Draft Type Research synthesis Author Brian Corbin · @briancorbinxyz Created 11 Jul 2026 Sources 24 primary, verified 11 Jul 2026 Companion agent-architecture · observability-slo Read time

You love Spec Kit's Library-First and contract/OpenAPI-first data models — rightly, because those two are the ones that generalize best to agent-built code: both replace open-ended generation with generation against a fixed, inspectable target. The contract is the spec, and a schema check is deterministic verification — exactly the objective pass/fail signal an agent needs to self-correct. Beyond those two, the strongest candidates in the same spirit are Test-First, structured observability, idempotency / safe retries, and least-privilege — each gives the agent either a checkable target or a bounded blast radius; then semantic versioning, secure-by-default, integration-first testing, supply-chain hygiene, SLOs, and accessibility round out the canon. The crux — "at what profile levels?" — has a clean answer: rigor is a ladder, not a switch. Every serious maturity model tiers practice (DORA, OWASP SAMM's three levels, DSOMM's five, Well-Architected, Google's Production Readiness Review), and YAGNI + Amazon's one-way/two-way doors say ceremony must scale to stakes and reversibility. So most of these principles are "earn them at scale," not "always on." The differentiator: Spec Kit, Kiro, and every SDD tool surveyed ship a single untiered constitution — a profile system that changes which principles are mandatory by tier appears novel in the space. Spectastic already has that system; this doc recommends what to add to each tier.

1 · The question

Two parts. (a) Beyond Library-First and contract/OpenAPI-first, what other engineering "constitution" principles are worth offering a downstream project? (b) At which profile level — lean, standard, verified, enterprise — should each apply? The second part is where the real design judgment lives: a principle that is wisdom for a regulated service is premature ceremony for a weekend prototype, and imposing it there is itself a failure mode.

2 · Why Library-First and contract-first are the right instinct

Both give the agent a fixed target to generate against. That is the whole reason they feel so good for agent-built code, and it is worth naming precisely, because it tells you which other principles to reach for.

  • The contract is the spec. An agent generating against a fixed OpenAPI / JSON-Schema / protobuf definition has an unambiguous, checkable target — output either validates against the schema or it doesn't. This turns "did the agent build the right thing?" from a judgment call into a mechanical check.Design-first vs code-first; the contract as a machine-checkable artifact, breaking changes caught at design time [4]; Google's resource-oriented, design-first API Design Guide (AIP) [5].
  • Deterministic verification closes the agent loop. Schema validation, mock servers, and contract tests give a fast, objective pass/fail signal — the ground truth an agent needs to self-correct, and precisely the kind that structural-only "it renders" checks can't provide (spectastic's own P-7 "presence ≠ verified").
  • It decouples parallel agents and bounds hallucinated interfaces. A producer-agent and a consumer-agent can work against the shared contract without reverse-engineering each other, and a fixed contract stops an agent inventing endpoints or fields that drift from what consumers expect.
  • Library-First is the same move, one level up. Building a feature as a standalone library with a clear interface before wiring it into an app gives the agent a bounded module and testable seams — a target, not an open field.

So the selection heuristic for "what else": prefer principles that either give the agent a checkable target (contract-first, test-first, semver) or bound the blast radius of autonomous code (least-privilege, idempotency, ship-dark). Those two properties are what make a principle pull its weight when a machine, not a careful human, is writing the code.

3 · The principle canon

Spec Kit's constitution is a strong but opinionated starting point — its "nine articles" are really ~six fixed rules plus three project-defined slots, and reviewers note both that agents ignore the rules and that they over-comply (mechanically abstracting trivial features).Spec Kit's articles [1]; the "powerful rules file… false sense of control," agents ignore/over-comply critique [3]. The lesson mirrors spectastic's own T-009: offer principles as a menu, and put the real guarantee in the enforce floor / a validate rule, not the prose.

The candidates worth offering, with the property that earns their keep for agent code:

4 · Rigor is a ladder, not a switch

The "at what level?" question is already answered by how the industry structures engineering maturity: as explicit, cumulative tiers.

  • Security models ship the ladder. OWASP SAMM defines three maturity levels per practice (foundational → mature → advanced); DSOMM defines up to five, and OWASP ASVS and WCAG are cumulative (L1/L2/L3, A/AA/AAA) — you can borrow their rungs directly.SAMM three-level ladder [2]; DSOMM five-level, skip-levels-where-not-meaningful, feature-toggles at L4, blue/green at L5 [9].
  • Delivery maturity is tiered too. DORA sorts teams Elite/High/Medium/Low and studies which capabilities (CI/CD, trunk-based, small batches, test automation, observability, loosely-coupled architecture) move them up; AWS Well-Architected trades its six pillars against "your business context"; Google's Production Readiness Review is the explicit gate before a service is operated.DORA capabilities that ladder teams up [8]; Well-Architected pillars, tradeoffs by workload [10]; Google SRE PRR [11].
  • Ceremony must scale to stakes. YAGNI names the costs of building rigor ahead of need ("think ahead, don't build ahead"), and Amazon's one-way/two-way doors tie process weight to reversibility — reversible decisions get a light-weight process, and applying heavy process to reversible ones causes "slowness, unthoughtful risk aversion, failure to experiment." Mis-tiering upward is a real failure mode, the cousin of alert fatigue.YAGNI's four costs; think-ahead-not-build-ahead [12]; Amazon one-way/two-way doors [5].
The differentiator, stated plainly. The maturity-ladder concept is thoroughly precedented — but no spec-driven or agent tool surveyed applies it as selectable profiles that change which principles are mandatory. Spec Kit ships one untiered constitution; Kiro's steering is project-wide; Well-Architected is a review lens, not a profile. The closest analog — Spotify/Netflix "paved roads" — tiers by engineering discipline, not by stakes, with an opt-out-with-responsibility escape hatch. Spectastic's lean/standard/verified/enterprise profiles, each carrying a different principle bundle, are the structurally-novel move. This doc is about filling those bundles well.

5 · Where spectastic stands today

The profile manifest (spectastic-profiles.json) already carries a tiered principle set — but it is almost entirely verification / enforcement / shipping discipline, with none of the shape-of-system principles you're asking about.

TierPrinciples today (beyond the shared base)
base (all tiers)Clarity over cleverness · Small, reversible changes · Explicit over implicit · One set of conventions, enforced · Record the why
lean— (base only)
standard+ Tests accompany behavior
verified+ Done means verified · The enforcement floor holds
enterprise+ Ship dark by default · Decisions are grounded

So spectastic already covers, in its own words: simplicity (base "Clarity over cleverness" + "Small, reversible changes"), a light test-first (standard "Tests accompany behavior"), done-means-verified including integration testing (verified), ship-dark (enterprise), and grounding (enterprise "Decisions are grounded"). What it offers nothing on: Library-First, contract/API-first, observability, semantic versioning, secure-by-default, idempotency, least-privilege, supply-chain hygiene, SLOs, and accessibility — the entire "shape and contract of the system" family, including the two you named. The five axes (verification · enforcement · toggles · grounding · frameworks) give the tiering vocabulary; there is room for an interfaces or contracts axis alongside them.

6 · Recommendation — the additions, tiered

Add the principles at the lowest tier where each starts earning its keep, cumulative upward (a verified project inherits standard's set). Reading the ladder: lean stays near-empty (simplicity is already its base ethos); standard gets the "make it a real, contract-bearing product" bundle; verified gets the "operate it in production" bundle; enterprise ratchets each to audited/regulated strictness (SAMM L3 / DSOMM L5 / ASVS L3).

D-001 · Offer the shape-of-system principles, tiered — as principles, with enforce/validate as the teeth

Status
Proposed
Context
Library-First and contract-first are the agent-code standouts because they give the agent a checkable target; the broader canon adds more targets and blast-radius bounds. The industry tiers all of this by maturity, and no SDD tool ties principles to a selectable profile — which spectastic's profile system already does, but its bundles carry none of these.
Decision
Extend the profile manifest's per-tier principles[] with the additions above, placed at the lowest tier where each earns its keep. Lead with contract/API-first and Library-First at standard (the two you value, the two that fit agents best). Consider an interfaces/contracts axis alongside the existing five. Keep them principles (advisory, per T-009 / P-8) — where a guarantee is warranted, the durable form is an enforce category or a validate rule (e.g. an OpenAPI-present check), not the prose.
Consequences
+ Fills the one gap in spectastic's principle tiers with the highest-leverage family for agent code. + Turns a genuinely novel capability (profile-tiered principles) into a differentiator. + Reuses the existing 041 manifest + 042 enforce split — the contract-first principle at standard, a possible contract-present enforce category at verified. − Principles are advisory; agents ignore/over-comply, so the guarantee must live in enforce/validate for anything load-bearing. − Adds curation surface to the manifest; keep each statement one crisp sentence, deduped by name like the existing ones.

Suggested next artifact

  • A /spectastic.propose against 041-init-profiles adding the tiered principles to spectastic-profiles.json (contract-first + Library-First at standard first) — except the observability + SLO rows, which the observability doc owns; coordinate as one manifest pass. Then /spectastic.implement.
  • A companion enforce/validate teeth for the contract-first principle — a "public interface has a checked-in OpenAPI/schema" category — mirroring the coverage split (principle at standard, machine-check at verified).
  • An interfaces/contracts profile axis alongside the existing five, expressing the contract-rigor posture per tier.

7 · Caveats on the sources

  • Spec Kit's "nine articles" is partly scaffolding — Articles IV–VI are project-defined placeholders, and the exact versioning token ("MAJOR.MINOR.BUILD") is reported, not verbatim in the fetched text.
  • The cumulative maturity levels (SAMM L1–3, DSOMM L1–5, ASVS/WCAG) are corroborated across sources but several level definitions came from reputable secondaries (Codific) rather than a fully-rendered primary page.
  • DORA thresholds shift yearly — treat Elite/High/Medium/Low cut-points as indicative, and the capability catalog (not the numbers) as the durable part.
  • "Profile-tiered principles are novel" is an absence-of-evidence claim — confirmed for Spec Kit, Kiro, and Well-Architected, but "not found in the tools surveyed," not "proven novel anywhere."
  • The accessibility → tier mapping is synthesis, not drawn from a primary a11y-maturity model — lower confidence than the security rungs.
