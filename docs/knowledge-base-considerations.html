Considerations · Knowledge bases

The spec knows what the model knows

Spectastic already asks every design decision to cite a verified source. It just has nothing outside the repo to cite.

Status Draft Type Landscape survey & research synthesis Author Brian Corbin · @briancorbinxyz Created 24 Jul 2026 Sources 18 primary, verified 24 Jul 2026 Companions Worked example · EU AI Act evidence Read time

An authored spec is a function of four things: the model, the context it holds, the user's inputs, and the sibling specs already in the repo. Three of those are ours to control; the first is not. When the domain is one the model happens to know well, house knowledge carries the spec. When it isn't — a different model, a narrower domain, a regulation published after the cutoff — the quality drops silently, and the burden of being the subject-matter expert falls back on the user, which is precisely the burden the tool exists to lift. The gap is sharper than it looks, because spectastic already has the entire grammar of grounding and nothing external to ground against: REQ-LIFECYCLE-006 requires every design-bearing fact to be recorded as verified, spike or assumed with a cited source, a grounding profile axis already ladders that discipline across four tiers, and an ungrounded decision already renders as a visible failure — but every source those rules name is in-repo. This doc recommends a corpus convention, not a knowledge store: a committed, greppable knowledge/ directory shaped by the open Agent Skills references/ pattern, so it works on any skills-compatible agent rather than only the one that wrote it. It deliberately does not recommend building a vector database, and explains why the tools that tried have been walking that back.

1 · The gap — a spec is a function of house knowledge

The lifecycle assumes the authoring model brings competence to the table. For general software concerns that assumption holds: the model knows what a retry budget is, what idempotency costs, what an index does. For specialist domains it holds only accidentally — as a function of which model happens to be running, and what was in its training data.

The failure mode is not an error message. It is a plausible spec. A model that half-knows a domain produces requirements that read correctly, use the right nouns, and are wrong in ways only a practitioner would catch — an incorrect settlement window, a misstated capital treatment, a regulation cited by a name it no longer has. Nothing in the current pipeline distinguishes that from a good spec, because nothing in the current pipeline knows the domain either.

This is a different problem from prompt quality. Better interviewing extracts what the user knows. It does nothing when the user came to the tool precisely because they are not the domain expert — the case that motivates this doc.

2 · What spectastic already has — and what is missing

The important discovery is how little vocabulary needs inventing. Three mechanisms already exist and all three point at a corpus that isn't there.

MechanismWhat it already doesWhat it lacks
REQ-LIFECYCLE-006 Requires /spectastic.plan to ground every design-bearing fact "against real source", record an evidence ledger of verified / spike / assumed, and have each decision cite its source. Every source it names is in-repo: the consuming code, the dependency signature at the resolved lockfile version, quantified platform constraints. A domain fact has nowhere to point.
The grounding profile axis Ladders across the four profiles: light → decisions-cite → decisions-cite+risks → full-ledger. The rungs describe how much citation is expected, never what may be cited. At full-ledger the ceiling is still the repo.
<spec-decision grounding> Renders assumed loudly — an unverified decision is a visible failure, not a quiet one. Makes the absence of grounding legible without offering any way to close it for domain knowledge.

So the honest framing is not "spectastic needs a knowledge base." It is: spectastic already demands citations it cannot supply. Today a domain fact can only ever be assumed. A corpus is what lets it be verified.

And grounding is not only an authoring concern. A corpus is a grounding source, consumed wherever a domain claim is asserted or checked — so the same corpus that grounds a spec also arms the adversarial critic pass (the critic already reads the spec and principles.html; a domain-aware one catches a requirement that contradicts KB-001), the explain coaching read, and — as harness skills spectastic doesn't own but a committed corpus still feeds — code-review and security-review. Authoring is where it starts, not where it stops.

One more existing asset matters, in §8: the AI verbs already route untrusted artifact text through fenceArtifactText() in packages/core/src/security/fence.ts, which strips comments, hidden and aria-hidden elements, data: URIs, normalises Unicode, and wraps the result in an explicit "data, not instructions" guard. Ingesting third-party documents needs exactly that boundary, and it already exists.

3 · How comparable tools hold knowledge

Nobody in this space has solved specialist knowledge; several have converged on where to put it.

Instruction files (CLAUDE.md, Cursor rules)
One always-loaded file of conventions. Cheap and universal, but steering, not reference — it scales to "how we work here", not to a corpus, and everything in it costs context on every turn.
Kiro steering files
The closest spec-driven neighbour: modular markdown for persistent project context, deliberately split across files. Still steering rather than a document corpus — but the modular shape is the right instinct.
GitHub Spec Kit
The most direct SDD comparison — spec.md → plan.md → tasks.md, 30+ agents. Its context story is the artifacts plus the agent's file access; no first-class corpus primitive to import a domain into.
MCP servers
The right answer for knowledge that changes — the server owns freshness. Weaker for a stable reference corpus: a runtime dependency, an availability failure mode, and the cited source lives outside the repo, where it can change or vanish after the decision that cited it.
llms.txt
A curated, machine-readable index of a site's documents as markdown links. Still a community proposal in 2026, but adopted enough to be a useful shape precedent — a corpus wants an index, and this is what one looks like.
Agent Skills
The one that changes the calculus, covered next.
Agent Skills are the portable container.

A skill is a folder: a required SKILL.md carrying metadata and instructions, plus optional scripts/, assets/, and — the load-bearing part here — references/, for documentation loaded on demand. Agents consume it by progressive disclosure in three stages: at startup only each skill's name and description are loaded; when a task matches, the full SKILL.md is read in; referenced files are pulled only when the work actually calls for them. The format's own framing is packaging "company-, team-, and user-specific context into portable, version-controlled folders that agents load on demand" — which is the requirement in this doc, stated by someone else.

Two properties make it decisive. It was developed by Anthropic and released as an open standard, honoured across a wide field of agents and IDEs — Claude Code, OpenAI Codex, Cursor, Copilot/VS Code, Gemini CLI, Goose, OpenHands, Roo Code and more — including Kiro, the nearest spec-driven competitor. That is the direct answer to "what if I'm not using Opus": a corpus in this shape is addressed not to a model but to a format many models already honour.

4 · Retrieval — and the threshold that settles it

The instinct on hearing "knowledge base" is to build a vector database. The evidence points the other way, from two independent directions.

The tools that tried are walking it back. Claude Code removed vector search in favour of agentic search — letting the model decide what to look for with grep and glob, iteratively — and the reported reasons are simplicity, security, privacy, reliability and above all staleness. An index is a second copy of the truth that must be kept in sync; agentic search has no such failure mode because there is nothing to be stale. For a corpus that lives in the repo and changes with it, that argument transfers directly.

Most corpora are too small to need it. Anthropic's own retrieval guidance draws the line explicitly: for a knowledge base under roughly 200,000 tokens — about 500 pages — skip retrieval entirely and put the whole thing in the prompt, using prompt caching for cost and latency. That threshold matters because it covers most of what a project would actually curate: a domain glossary, a house standards document, a regulatory summary, a product's own reference manual. The corpora that genuinely exceed it are the exception, not the design centre.

Above the threshold the technique is well characterised, worth naming so a future slice doesn't reinvent it: contextual embeddings, then contextual BM25, then reranking form a known ladder that cuts retrieval failures by roughly a third, a half, and two-thirds respectively. A real and useful ladder — simply not the first thing to build.

The reflex to reach for embeddings first is the most expensive mistake available here. It buys a synchronisation problem, an infrastructure dependency and an opaque retrieval step, to solve a problem most projects do not have yet — and it puts the cited source somewhere a reviewer cannot simply open.

5 · Getting documents in — and what conversion costs

Domain knowledge arrives as PDFs, and a PDF is hostile to a language model: layout without structure. The open-source field has settled into three tools with a clear division of labour.

ToolCharacterWhere it fits
Docling (IBM)Structurally rich, slower. Materially better on tables, formulas and multi-column layouts; reported ~88% vs ~82% F1 against MarkItDown, with notably stronger table extraction.The default. Tables and formulas are exactly what a finance, clinical or engineering corpus is made of.
MarkItDown (Microsoft)Fast and shallow — reported 50–100× faster on clean digital PDFs, and covering far more input formats, at the cost of structure downstream retrieval depends on.The fast path for clean, digital documents you already control.
MarkerHighest fidelity, GPU-hungry.When accuracy dominates and GPU budget exists — dense academic or standards material.

All three are Python; spectastic's kernel is deterministic Node. So document the recipe and ship no dependency — the tool consumes whatever markdown lands in the corpus and never owns the converter, keeping the kernel free of an external runtime and a version matrix, at the honest cost that the first conversion is a manual step.

The cost that must not be glossed: conversion is lossy, and its losses are silent. A mis-parsed table becomes a confidently wrong "verified" fact — arguably worse than an assumed one, because it carries a citation. Any corpus slice needs a spot-check discipline, not blind trust in the converter.

6 · Citing a corpus that moves

A citation is only as durable as the thing it points at, and things move. Scholarship and law have fought link rot for decades and lost badly — studies find ~70% of academic-journal URLs and roughly half of US Supreme Court citation links now dead. A committed corpus dodges the worst of it, but two failure modes remain: a document gets superseded, and the corpus gets reorganised. The discipline that answers both is the one scholarship converged on, and it maps onto the corpus cleanly.

A persistent identifier, not a path
A decision cites KB-001 — a stable ID, in the spirit of a DOI or ARK — never a file path. The document can move, be reorganised into a different pack, or be re-ingested at a newer edition, and the citation still resolves. IDs are contracts; this is P-3 applied to the corpus.
An edition pin, so the citation names which text
The scholarly "as of" access date, made machine-checkable: a decision cites KB-001@2024-05-28, not bare KB-001. The pin records the exact edition the claim was grounded against — so when KB-001 is later re-ingested at a newer edition, the historical decision still says, unambiguously, which version it read.
The committed copy is the archive
Best practice in legal citation is to cite both the original URL and an archived snapshot ("archived at…", Perma.cc style). The corpus does this by construction: origin-url in the frontmatter is the original; the committed markdown is the snapshot. A cited source cannot silently change under you.
Supersede by append, never overwrite
Re-ingesting at a newer edition must not delete the old one while any decision still cites it — that is manufacturing a dangling reference. Keep the prior edition (or at minimum its content hash and provenance) reachable, so an edition-pinned citation always resolves to the text it actually named.

The first three are pure convention; the fourth wants a small piece of machinery — a staleness gate, a validate rule that flags a decision whose pinned edition is no longer current, surfacing stale grounding the way an assumed decision already is rather than letting it rot in silence. Together they sharpen the citation contract from "cite an ID" to "cite an ID at an edition" — a real supersession (US equities T+2 → T+1) is walked through in the worked example.

7 · The specialist case — why finance is the test

Finance makes the argument concrete because the failure is measurable rather than aesthetic. Language models fabricate financial metrics and invent regulatory citations; one benchmark reports GPT-4-Turbo incorrectly answering or refusing 81% of curated questions over SEC filings. Grounding generation in curated documents is reported to cut hallucination substantially — figures in the 70–90% range recur across the practitioner literature. "The model knows finance" is not a control; "the spec can prove where the number came from" is.

A working prototype built to this convention makes the whole proposition legible in a single screen — a finance-settlement corpus, and a plan whose decisions render verified (green, cited) beside ASSUMED (loud amber, uncited), with a fourth showing an edition-pinned citation caught going stale. It is walked through, openable, in the companion worked example: A corpus-grounded spec. The one-line takeaway it lands: today, without a corpus, every domain decision spectastic writes can only be assumed.

Regulation pulls the same direction, hard enough to deserve its own treatment: the EU AI Act's high-risk technical documentation (Annex IV) wants design choices with their rationale and basis — precisely a decision that cites its source. The potential compliance win, and the honest bounds on it (documentation evidence, not the Act's runtime logging), are in the second companion doc, EU AI Act — what evidence a spec trail can produce.

8 · Recommendation — a corpus convention, not a knowledge store

Be opinionated about the shape; stay unopinionated about the vendor. Concretely, eight positions:

  1. A committed, in-repo corpus. Converted markdown under a knowledge/ directory, versioned with the specs that cite it. Greppable by agentic search, diffable in review, reviewable offline, and — critically — a cited source that still exists next year, at the version that was cited.
  2. Stable source IDs, edition-pinned, with a curated index. Every document carries an ID a decision can cite at an edition (§6); an index in the llms.txt spirit gives an agent a cheap map before it reads anything. Provenance for each entry — origin, edition, license, converter, content hash — is part of the record, not a nicety, and a staleness gate flags a citation whose edition has been superseded.
  3. Shaped as Agent Skills references/. Adopt the open format's directory convention and progressive disclosure rather than inventing a spectastic-only layout. This is what makes the corpus portable across Claude Code, Codex, Cursor, Copilot, Gemini CLI, Kiro and the rest — the answer to the model-dependence problem that started this doc.
  4. Agentic search first; no vector database. Grep and glob over a committed corpus, matching where the field has converged. Revisit only when a corpus genuinely exceeds the ~200k-token threshold, at which point contextual embeddings + BM25 + reranking is the known ladder.
  5. Ingestion is an untrusted boundary — reuse the existing fence. Every corpus excerpt entering a prompt goes through fenceArtifactText(). A third-party PDF is a strictly worse injection surface than an in-repo artifact, and P-11 ("artifacts are data, not instructions") already governs it. Do not fork the sanitiser.
  6. Conversion documented, never depended on. Docling as the recommended default, MarkItDown as the fast path, Marker where fidelity justifies a GPU. Spectastic ships none of them.
  7. A reference implementation that lives by being used. A convention of frontmatter, a SKILL.md, an index and a citation contract needs a worked example or it is just prose. Ship the templates from init (as it already ships spec/plan templates) and let spectastic grow a small knowledge/ corpus of its own in-repo — the format proven by dogfooding, no new repo, kernel Node-only. The optional Python converter/ingest glue is the one piece that belongs in a separate helper.
  8. Keep the domain skill portable; put the spectastic binding in the harness. A domain pack is a distributable unit — Agent Skills ship as marketplace plugins (an anthropics/skills-style marketplace.json bundles them; a public registry with search/semver is reported by secondary coverage), installable into any of ~40 skills-compatible clients. So a finance-settlement pack should carry zero spectastic knowledge: the moment it embeds "cite this in a <spec-decision grounding>" it stops being a clean, publishable domain skill — a coupling the prototype's first SKILL.md got wrong. The citation binding belongs one level up, in the harness (next), so the pack is equally useful in a spectastic repo and in a plain Claude Code project.

The payoff is the closure in §2: a domain fact stops being permanently assumed and becomes verified against something a reviewer can open — consumed not just when a spec is authored but wherever a domain claim is checked (§2), which finally gives the grounding axis's upper rungs something real to ladder.

Making usage a directive, not a suggestion.

A corpus the harness merely suggests the agent "look for" is worth little — and a naive nudge is dangerous, since merely-prompted citation is where models fabricate sources (reported at 78–90%). The honest lever splits along the line the guarantee-layer doc already draws — presence is guaranteeable; use is only directable:

  • Presence — deterministic, harness-owned. When a corpus exists, core injects its index and a grounding directive into every AI-verb prompt, exactly as plan.ts/spec.ts already fence the principles. This is not markdown asking the harness to look — it places the corpus in front of the model every time. That is the directive.
  • Use — advisory by necessity. A prompt cannot force the model to actually cite, and no build-gate can tell a missed domain claim from a legitimately local one — "is this a domain claim?" is undecidable, so a hard gate would false-fail whole specs. Grounding therefore stays a warning (the "cited ID must resolve" rule), never a build failure; the profile-gated quantified-NFR scan is the shape it would take, and the reason it isn't cloned is exactly that domain-claim detection can't honestly fail closed.
A corpus you already have.

Most teams with specialist knowledge already hold it in some shape. First-class treatment (citable, edition-pinned, gated) is a property of the convention, not of any particular pile of files — so the honest answer is a tier, not a door:

Adopt the convention
Move the material under knowledge/ with provenance frontmatter and index rows. Fully first-class — citable, edition-pinned, gated. The most work, the most guarantee.
Adapt it
Run an adapter/generator that emits the frontmatter and index from an existing corpus shape (a markdown folder, an llms.txt). First-class once converted; the conversion is a one-time reference-implementation job, and the same silent-loss caveat as any ingestion applies.
Bridge it live
Reach an existing knowledge server through MCP. It works, and it is right for knowledge that changes — but the cited source then lives outside the repo, so it cannot be frozen, edition-pinned or gated (the exact trade §3 names for MCP). Fine for freshness; not a substitute for a committed citation.
Build, or recommend?

Both, split along the line spectastic already uses. Build the convention — layout, the edition-pinned citation contract, the index, the ingestion fence, the staleness gate, a reference corpus, and init scaffolding — small, deterministic, the tool's business. Recommend the tooling — converters and, later, retrieval engines — because those move faster than this project should track. Building a knowledge store would mean owning chunking, embeddings, an index format and their staleness; §4 says that is the wrong thing to own.

9 · Ceilings and open risks

Recorded rather than hidden, in keeping with how this project treats limits it cannot engineer away.

  • A corpus is not expertise. It makes claims checkable; it does not stop a model retrieving the wrong passage or misreading the right one. This raises the floor and does not raise the ceiling.
  • Conversion loss is silent (§5), and a citation makes a wrong fact more credible, not less.
  • Staleness is editorial at root. The edition pin and staleness gate (§6) can tell a machine that a citation's edition was superseded — but only once someone re-ingests the newer edition. Nothing here notices that the world changed; a regulation superseded upstream, with no one having re-ingested it, greps as cleanly as a live one.
  • Licensing becomes concrete the moment documents are committed. Vendored standards and paywalled material carry redistribution terms that an in-repo corpus makes unavoidable — the clearest cost of choosing in-repo over by-reference.
  • The corpus is a new prompt-injection surface. The fence is a strong deterministic control and not a solved problem; P-11's posture split between what is enforced and what is asserted applies here in full.
  • Context budget is finite. Progressive disclosure mitigates, but a large corpus plus a large spec still competes for the same window.
  • Use is directable, not guaranteeable (§8). The harness can guarantee the corpus is present in every prompt; it cannot guarantee the model grounds against it, and "is this a domain claim?" is undecidable — so grounding stays a warning, and a spec can still ship an ungrounded domain claim.
  • Portability and coupling pull against each other. A domain skill is only a clean marketplace unit if it carries no spectastic citation instructions (§8); the split keeps the binding in the harness, but it is a discipline to hold, not a thing a machine enforces on a third-party pack.
