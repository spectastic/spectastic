Considerations · Annotation surface

A stamp in a design file is not data

Everyone agrees what the categories are. Nobody has written them down in a form a program can read — and the standard that would have solved it has been a Recommendation since 2017.

Status Draft Type Architecture & landscape survey Author Brian Corbin · @briancorbinxyz Created 12 Aug 2026 Companion visual-spec Sources 11 external, retrieved 12 Aug 2026 · codebase audit Read time

The parent survey established that the industry's annotation vocabulary — behaviour, requirement, animation, API, tracking, accessibility, content — is broadly agreed and exists nowhere as a schema. The de facto accessibility standard ships as a design-tool component library under a content licence, which means the most careful annotation work in the field is drawings of data. This survey asks whether to build a surface that produces the real thing, and finds that the hard part is already solved. The W3C Web Annotation Data Model has been a Recommendation since February 2017, alongside a Vocabulary and a Protocol, and its architecture is the one this problem needs: annotations live separately from what they annotate and are re-anchored when the target is present. That single property answers the two objections that would otherwise sink an external annotator — a redesign moving every coordinate, and a designer in their own tool being unable to see what a developer wrote. So the question is adoption, not invention, and the build shrinks to an editor plus a mapping. On where that editor runs, the evidence corrects an earlier instinct: annotation is empirically a designer activity, so the first surface belongs in the tool the designer already has open, not in a code editor. What the editor must never become is the authority — the annotations are the project's, in the project's repository, which is the same posture the parent survey took on design tools generally.

1 · The ask — annotate anywhere, and a question about who

The parent survey left annotation half-built on purpose. 095 says what an annotation is — typed by accessibility role and state, so a declaration doubles as an assertion. Nothing says how one comes into existence. The design interview never asks for one, no scaffold produces one, and the import path was deferred to a slug scoped to tokens and renders that would have dropped it silently. The vocabulary has no author.

The ask is a surface that produces annotations against any of the five design sources, because none of them agrees with the others and two of them have no annotation concept at all. But the more consequential question is underneath it, and it is about people rather than formats: who does the annotating?

The evidence says designers do. The accessibility annotation kits that are the field's de facto standard were built by an inclusive-design team and are consumed by designers placing stamps on frames. Zeplin's own documentation puts it plainly — "during handoff, designers will add annotations to help document how a design should behave". Figma's annotations live in Dev Mode, authored by the designer for the developer to read. In all three, the author is on the design side and the reader is on the engineering side.

That is not the whole picture, and the boundary is genuinely moving. The data layer — what the screen fetches and what happens when it fails — is an engineering concern. The tracking layer is a product one. A single-persona tool would be wrong about a third of its own vocabulary. But "sometimes a developer annotates" is a much weaker claim than "usually a designer does", and a first surface has to be built for the usual case.

Worth separating two things this survey keeps distinct: the authoring gap, which is that nobody is asked for an annotation, and the import gap, which is that a design tool carrying annotations has no route into the project. The first is cheap and belongs with the authoring layer already specced. The second is what a surface or an adapter solves. They are often discussed as one problem and have different answers.

2 · The audit — what the five sources can actually carry

The parent survey's five sources do not merely disagree about annotation format. Two of them have no concept of one, which rules out any design that assumes a canvas to annotate on.

The two AI-native tools are the interesting column. They have no annotation feature to integrate with, no canvas to place a stamp on, and no file to write back to — and they are the two growing fastest. A design premised on plugins would serve three tools and structurally exclude two, which is exactly backwards from where the market is moving.

The other half of the audit is what the field's most careful annotation work actually is. The accessibility annotation kits — landmarks, headings, focus order, reading order, the whole apparatus — are distributed under a content licence as design-tool component libraries. There is no JSON, no schema, no code output. A team that annotates diligently using them produces a beautifully organised set of drawings of data, which a developer reads with their eyes and retypes. That is the gap, and it is not a tooling gap so much as a representation one.

3 · The peer record — the standard design tooling never adopted

There is no cross-tool annotation product. Searching for one returns design-tool comparisons and screenshot utilities. The premise that nothing exists is correct as far as design tooling goes.

It is not correct about the web. Annotation became a W3C standard on 23 February 2017, as three Recommendations: a Data Model, a Vocabulary and a Protocol. The Data Model is built on exactly the shape this problem needs — an annotation has a body and a target, and the target carries one or more selectors describing which part of the resource is meant. The selector types map onto the audit above with uncomfortable precision:

Source shapeSelectorRobust against redesign?
An emitted HTML artifact — Stitch, Claude Design, a running appCssSelector, XPathSelectorLargely, if the selector is semantic
A region drawn over a render — the pin-and-lasso pattern the kits already useSvgSelectorNo
A rectangle on an imageFragmentSelector (#xywh=)No
A node in a design toolA tool-specific IRIYes, while the node exists
A phrase of visible copyTextQuoteSelectorSurprisingly well

And the model permits several selectors on one target, which is the property that makes the whole thing work rather than merely fit.

The architecture matters more than the vocabulary. The standard's own framing is that "annotations live separately from documents and are reunited and reanchored in real-time whenever the relevant document is present", and that this puts them "under the control and election of the user, rather than at the sole discretion of the publisher". Read that against this problem: the annotations belong to the project rather than to whichever design tool the team is paying for this year, and they are re-anchored against whatever representation is to hand. That is not a convenient analogy — it is the same problem the standard was built for, one domain over.

It is also implemented rather than theoretical. The reference client passed three million annotations in 2018, and the client-server pattern it grew from was the most widely adopted early implementation. This is a standard with running code, which is a different thing from a standard with a specification.

The parent survey made the same kind of find twice, and it is becoming a pattern worth naming: the corpus turned out to be the model for a vendored component, the contract chassis turned out to be the model for a design system, and now a scholarly-annotation Recommendation turns out to be the model for design annotation. In each case the alternative was inventing a format. The discipline that keeps paying off is looking for the existing answer before designing the new one.

4 · Adopt the Recommendation, do not invent a format — D-001

OptionAnchoringTool independenceCost to buildInteropRot resistanceTotal
A · A local annotation format — design one to fit the vocabulary 2420210
B · Adopt one tool's model — mirror the dominant design tool's annotation shape 3042110
C · Extend the corpus provenance model — reuse what is already here 0441312
D · Adopt the W3C Web Annotation Data Model — body, target, selectors 5535523

Option C is worth a word because it is the one this project would normally reach for. The corpus's provenance model is the right shape for where a thing came from and has nothing at all to say about which part of a resource an annotation is about, which is the entire problem here. Reusing it would mean inventing selectors anyway and calling the result a corpus extension. Option B fails on the one requirement that started this: it would serve three sources and exclude the two with no annotation concept.

D-001 · The interchange format is the W3C Web Annotation Data Model

Status
Proposed
Context
Design tooling has an agreed annotation vocabulary and no schema; the field's de facto accessibility standard is distributed as component libraries. Meanwhile a W3C Recommendation from February 2017 defines body, target and a family of selectors covering DOM nodes, drawn regions, image fragments, quoted text and arbitrary resource identifiers, permits several selectors per target, and has a reference implementation with millions of annotations behind it.
Decision
Adopt the Web Annotation Data Model as the interchange format. Express 095's accessibility-typed annotation as a body against that model rather than as a parallel schema, and map the design tools' category names onto it at the edges. Invent no selector types and no target model.
Consequences
+ The hardest part — robust anchoring across resources that are not all the same kind of thing — is specified, implemented and stable rather than something to design. + Annotations become readable by anything that speaks the standard, which is a larger world than design tooling and includes the accessibility and publishing communities the vocabulary came from. − The model is heavier than this problem strictly needs, carrying provenance, motivation and agent concepts that will mostly go unused, and a subset that is really a local format wearing a standard's name would be worse than either. − Nothing in design tooling speaks it today, so interoperability is a claim about the future rather than a benefit on day one.

5 · Annotations live apart from what they annotate — D-002

This is the decision that makes an external annotator viable at all. The obvious objection to annotating anywhere other than inside the design file is that the design file is where the stamps stay attached: a frame moves and its annotations move with it. Anything outside loses that, which is why the accessibility kits are Figma components and not a data format.

The standard's answer is to invert the relationship. Annotations are their own resource, stored independently, and re-anchored against the target whenever the target is available. The consequences for this problem are exact: the annotations live in the project's repository under the sidecar convention already specced, they survive the team changing design tools, they survive a source that was never a design tool at all, and a design tool that gains the ability to display them can be given them — because they were never locked inside a different one.

D-002 · The annotation store is the project's, and the design tool is never the authority

Status
Proposed
Context
Annotations held inside a design file are attached but captive: unreadable without a seat, lost on a tool migration, and impossible for the two sources that have no file. The standard's architecture stores annotations separately and re-anchors them when the target is present, explicitly so that they answer to the annotator rather than to the publisher.
Decision
Annotations are stored in the project, under the visual sidecar convention, as the authoritative copy. A design tool may be a source of annotations by import and a destination by export, and is never consulted as the authority at validate or measure time — the same posture the parent survey took on design tools generally, applied to a second kind of content.
Consequences
+ Annotations outlive the tool, the seat and the vendor, and become reviewable in the same place as everything else the project asserts. + It makes an export path to a design tool a feature rather than a reversal, since the project already holds the canonical copy. − The designer's own tool stops being where the truth lives, which is a real loss of convenience for the person most likely to be writing them. − A stored annotation can be re-anchored wrongly and look right; unlike a Figma stamp, nothing physically drags it along when the design moves.

6 · Anchor semantically, with coordinates as the fallback — D-003

Re-anchoring is only as good as what the annotation points at. A rectangle at (120, 340) means nothing after a redesign; the button whose accessible name is "Convert" survives almost anything short of a rename. The model permits both on one target, so the choice is not either-or — it is which is preferred and what happens when the preferred one is unavailable.

Anchoring quality therefore varies by source, and that variation is a property of the source rather than a shortcoming of the design. An emitted HTML artifact supports the strongest anchors. A design tool node id is stable while the node exists. A raster render supports only geometry — which is the honest reason the weakest anchoring belongs to exactly the workflow that is otherwise most convenient.

D-003 · A semantic anchor is preferred, a geometric one is a recorded fallback

Status
Proposed
Context
The model allows several selectors per target. 095 already types annotations by accessibility role and state, so a semantic anchor is available wherever an accessibility tree is — which is every emitted artifact and every running surface, but no raster image.
Decision
An annotation records the strongest anchor its source supports and MAY record weaker ones alongside. A geometric-only anchor is valid and is marked as such, so a reader can tell an annotation that will survive a redesign from one that will not. Re-anchoring failure is reported rather than silently resolved to the nearest match.
Consequences
+ 095's accessibility typing turns out to buy two things rather than one: an assertion, and a durable anchor. + The fragility of an annotation becomes visible in the annotation itself rather than discovered when a redesign lands. − It makes the raster workflow visibly second-class, which is the workflow a designer exporting a PNG will reach for first. − "Reported rather than silently resolved" means a redesign produces a pile of re-anchoring failures for a human to work through, and nothing here makes that pile smaller.

7 · One model, several surfaces — D-004

The framing that resolves the plugin question is that this is not one tool. The standard ships a Data Model, a Vocabulary and a Protocol, and the Protocol exists precisely so that different clients can read and write the same store. Once the model is settled, an editor is a client, and clients can be justified one at a time by who uses them rather than argued about in the abstract.

SurfaceReachesCostAnchoring available
A plugin in the designer's toolThe usual author, in the file they already have openOne codebase and one review process per tool, coupled to a vendor APIStrongest — real node ids, and the stamps move with the frames
An overlay on an emitted artifactThe two AI-native sources, and any running appOne codebase, no vendor couplingStrong — semantic selectors against a live tree
An overlay on a renderAnyone with a screenshot, including tools nobody integratedShared with the aboveWeakest — geometry only
The editor extensionDevelopers, and the engineering-side categoriesInfrastructure already exists hereWhatever the artifact supports

Read as a set rather than a contest, the answer is unremarkable: the first surface goes where the usual author already is. That is a correction to this survey's own starting instinct, which was to build in the editor extension because the infrastructure is there — a reason about convenience for the builder rather than about who the tool is for.

D-004 · Surfaces are clients of one store, and the first one goes where the designer already works

Status
Proposed
Context
Annotation is empirically a designer activity in all three tools that support it. Two of the five sources have no canvas at all, so a plugin-only strategy structurally excludes the fastest-growing pair. The standard's protocol layer is designed for several clients over one store, so surfaces need not be chosen against each other.
Decision
Settle the model and the store first, then add surfaces independently, each justified by an audience rather than by symmetry. The first is a plugin in a designer's tool. The overlay on an emitted artifact follows, because it is the only route for the sources that have no canvas. The editor extension is a later client aimed at the engineering-side categories, not the first surface.
Consequences
+ No surface is load-bearing: the store is, and a plugin that a vendor breaks costs one client rather than the capability. + It meets the usual author where they are instead of asking a designer to open a code editor. − It commits to maintaining vendor plugins, which is an ongoing tax paid in someone else's release cadence and review queue. − Several clients over one store invites divergence between what each can express, and the model does not stop a plugin exposing a subset that quietly becomes the real vocabulary.

8 · The editor question, and the fork

The roles really are merging, and that argues against a single-surface answer rather than for any particular one. A tool that assumes a designer will be wrong about the data and tracking layers; a tool that assumes a developer will be wrong about most of the rest. D-004's several-clients-one-store is the shape that survives the ambiguity, because it does not need to decide who the user is in order to be built.

The larger idea in the same territory — that this project could one day fork a code editor and take on some of a designer tool's identity — deserves an honest answer rather than a deferral. It is a legitimate strategy with working examples, and it is also the most expensive route to the audience in question, for a reason worth stating plainly: a fork of a code editor is still a code editor. A designer who will not open one is not objecting to its keybindings. They are working in a canvas, with their team's libraries, their comment threads and their file history, and a fork inherits the identity along with the source. It would buy a developer-adjacent surface with designer affordances, which is a real thing to want and is not the same as reaching the person who currently writes the annotations.

It is also a product-strategy decision rather than an architecture one, and D-004 is deliberately arranged so that it stays open: if the store is the authority and surfaces are clients, a forked editor is one more client and costs nothing that has already been spent. Nothing in this survey needs it, and nothing in this survey forecloses it.

Do not start with the model as a subset. The temptation, once the Recommendation is adopted, is to implement the fifth of it this problem needs and grow later. That produces a local format wearing a standard's name — the worst of both, since it neither interoperates nor is free to be convenient. Either speak the model as specified for the parts used, or do not claim it.

9 · Recommendation — three slices, in dependency order

  1. Settle the model and the store. Adopt the Data Model, express 095's accessibility-typed annotation as a body against it, define the anchoring preference and where the store lives under the sidecar convention. No editor. This buys a format that everything else is a client of, and it is the only slice with no external dependency.
  2. Build the first two clients. A plugin in a designer's tool, and an overlay on an emitted artifact — in that order, because the first reaches the usual author and the second is the only route for the sources with no canvas. This buys annotations that exist.
  3. Round-trip and the engineering side. Export back to a design tool that can display them, and a client in the editor extension for the data and tracking layers. This buys the designer's own view of what the developer wrote, which is what an external store otherwise costs them.
Do not start with the plugin. It is the most visible slice and the most demoable, and it writes into a store that does not exist — which means the store's shape gets invented inside a vendor's plugin API, in whatever form that API made convenient. The second temptation to refuse is the editor extension, for a subtler reason: its infrastructure already exists here, which makes it the cheapest thing to build and the wrong first audience.

Suggested next artifacts

  • A new spec: the Web Annotation Data Model as this project's annotation interchange — the body shape for an accessibility-typed annotation, the selector preference order, the mapping from the design tools' category names, and where the store lives under 094 (D-001, D-002, D-003).
  • A follow-on survey then spec: which design tool gets the first plugin. The open-source one has a published plugin API, no seat cost and an annotation concept distinct from comments, which makes it the cheapest to build and test; the dominant one has the larger audience and a metered API. The choice is about audience against cost and should be made on its own evidence (D-004).
  • A new spec: the overlay client for an emitted artifact, which is the only annotation route for a source with no canvas — including whether it can be a spectastic artifact at all, given that an interactive editor collides with the deny-by-default artifact policy (D-004).
  • A new spec: what happens when a target moves — how a re-anchoring failure is reported, and how a person works through a redesign's worth of them without the tool guessing (D-003).
  • A question this survey opens and does not close: whether exporting annotations back into a design tool is worth its cost, given that it is the one thing an external store takes away from the person most likely to be writing them (D-002, D-004).

Deliberately not planted: a slug for the editor-extension client. D-004 places it in the third slice and nothing about it is uncertain enough to need surveying — it is a client of a store, and it can be specced when the store exists. Likewise the fork, which is a product decision this survey deliberately leaves open rather than converting into work.

One slug this supersedes. TBD-annotation-authoring, planted hours before this survey, asked how an annotation gets written. That question is answered here by a surface rather than by an interview prompt, so the slug should be drained into TBD-annotation-model rather than specced separately — with the caveat that a project using no annotation surface at all still needs the interview to ask, and that much survives.

10 · Caveats on the sources and the audit

  • Nothing was prototyped, and no plugin API was exercised. Figma's annotation write capability, Penpot's comment permissions and Sketch's annotation surface are all read from documentation. The claim that a plugin can write what this needs is a documented capability, not a demonstrated one.
  • The standard's fit is argued, not tested. The selector types map onto the source shapes cleanly on paper. Whether re-anchoring against a design render behaves acceptably in practice is exactly the kind of thing that looks fine in a specification and disappoints in a browser.
  • Its adoption is outside this domain. Three million annotations is real and is scholarly and publishing usage. No design tool speaks the model, so the interoperability benefit is a bet on a future rather than a feature that works on the first day.
  • "Designers annotate" is inferred from three tools' documentation, not measured. It is a strong inference and it is still an inference; a team where engineers write every annotation would find the first surface aimed at the wrong person.
  • Penpot's annotation feature is not fully characterised. Annotations are distinct from comments and appear in the Inspect tab, and a free-placement annotation layer is an open community request — which suggests the current feature is narrower than a plugin would need. That is a gap in this audit, not a finding.
  • This survey corrected its own starting position. It began intending to recommend the editor extension first, on the grounds that the infrastructure exists. That is a reason about the builder's convenience rather than the user's, and the evidence about who annotates reversed it. A reviewer running the same audit should reach the same reversal.
