Considerations · Lifecycle automation

Agentic Workflows

The lifecycle is already a pipeline of typed artifacts. That is exactly the shape a multi-agent workflow orchestrates — and exactly where spectastic's gates become the guardrails that make autonomy safe.

Status Draft Type Design brief (a /doc — research + considerations, feeds future /spectastic.spec slices) Author Brian Corbin · @briancorbinxyz Created 25 Jun 2026 Sources Primary sources, fetched + quoted 25 Jun 2026 (see §2.6) Read time

spectastic's lifecycle — principles → spec → plan → tasks → implement → propose → apply → triage — is a chain of deterministic verbs, each reading and writing a typed, validatable single-file artifact. That is the textbook substrate for agentic workflows: the seams are explicit, the hand-offs are typed, and spectastic validate + the done-means-verified principle already sit between every step. §2 is a cited read on the field — the workflow-vs-agent distinction, the canonical pattern library, the primitives every orchestration framework shares, how to rank work by business value, and how to keep autonomous pipelines safe. §3 distils a small, tool-agnostic primitive vocabulary (the same six shapes appear in Claude's Workflow tool, LangGraph, CrewAI, and the OpenAI Agents SDK). §4 proposes six spectastic workflows, led by the two requested headliners — a hands-off lifecycle pipeline (submit a spec, walk away) and a value-ranked slicer (one oversized spec → many slices, ordered by business value). §6 is the part that matters most: spectastic's existing discipline (validate gates, P-7, the explore quarantine) is the guardrail layer the research says autonomy requires. §9 is an addendum answering two sharp questions: a checkpoint need not be a human — it is a configurable Decider (human · grounded agent · panel + arbitrator) — and a single effort dial can scale the whole pipeline from a cheap sequential pass to a voting panel, the same control Anthropic and OpenAI already ship.

1 · The opportunity — a lifecycle is a pipeline

Most teams reaching for agent orchestration have to invent the seams: where does one step hand off to the next, what shape does it pass, how do you know a step succeeded? spectastic was built with those seams already drawn. Each verb is a pure-ish transform over a typed artifact, and two checks already stand between every pair of steps:

  • Typed hand-offs. spec.html → plan.html → tasks.html each carry stable IDs (P-3) and a machine-checkable structure — a downstream agent reads a contract, not prose it has to re-interpret.
  • A validator between steps. spectastic validate is a deterministic gate any orchestration can run after each verb — the cheapest possible defence against the failure the research calls error compounding (§2.5).
  • A verification bar at the end. P-7 (done means verified) is the project's name for the "human review remains crucial even when automated testing passes" guardrail the field recommends.

So the question this brief answers is not "could spectastic use agent workflows" — it is "which stretches of the lifecycle are worth handing to a workflow, and where do the human checkpoints belong." The answer turns on a distinction the field draws sharply, which §2 opens with.

2 · What the field does

A grounded read, quoted from primary sources (listed in §2.6). The synthesis below was recovered by fetching each cited source directly.

2.1 · Workflows vs agents — the load-bearing distinction

Anthropic's Building Effective Agents draws the line this brief turns on. Workflows are "systems where LLMs and tools are orchestrated through predefined code paths." Agents are "systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks." The guidance is to prefer the former: "find the simplest solution possible, and only increasing complexity when needed… add complexity only when it demonstrably improves outcomes."

This matters for spectastic because the lifecycle is a predefined code path — the verb order is known. So most of what follows is workflow, not open-ended agent: deterministic orchestration of model calls along a path spectastic already defines. The one genuinely agentic step is implementation itself, and Anthropic flags exactly that case — "resolving software engineering tasks" — as where autonomous agents earn their cost.

2.3 · The primitives every framework shares

The Claude Agent SDK gives subagents two properties that recur across the field. Context isolation: "Each subagent runs in its own fresh conversation. Intermediate tool calls and results stay inside the subagent; only its final message returns to the parent" (subagents docs). Parallelization: "independent subtasks finish in the time of the slowest one rather than the sum of all of them." For fan-outs beyond a handful, the docs point at the Workflow tool, "which moves the orchestration into a script the runtime executes outside the conversation context" — the boundary between turn-by-turn delegation and a real pipeline.

The same shapes appear under other names. CrewAI's processes are either sequential ("tasks… completed in an orderly progression," each output the next's context — a pipeline) or hierarchical, where a manager agent does "task planning & delegation… output review… completion assessment" — the orchestrator-worker pattern with a built-in evaluator. LangGraph models the human checkpoint as a first-class interrupt that pauses a stateful graph and resumes with injected state. The lesson: a small set of primitives — fan-out, pipeline, evaluator/judge, orchestrator-worker, human-checkpoint, bounded loop — is shared across every orchestrator. §3 turns that into spectastic's portable vocabulary.

2.4 · Ranking work by business value

The requested "order slices by business value" workflow has a well-established method behind it. WSJF (Weighted Shortest Job First, from SAFe) is the canonical formula (SAFe / agility-at-scale):

WSJF = (User-Business Value + Time Criticality + Risk Reduction / Opportunity Enablement) ÷ Job Size

The numerator is the cost of delay; the denominator is size, "typically scored using relative sizing" on a "modified Fibonacci scale (1, 2, 3, 5, 8, 13, 20)," with all items scored relative to each other in one session, never in isolation. That last property is the important one for an agent: WSJF is a comparative judgement over a set, which is exactly what an LLM judge does best — and worst.

WSJF is not the only such rubric, and for this job it may not be the best. RICE (Reach × Impact × Confidence ÷ Effort) is the other canonical value-÷-effort formula — and the two are not interchangeable: "RICE looks for the highest impact per effort. WSJF asks what brings the most urgent value now… pick one as your main tool and use the other for a gut check." The standard layering puts WSJF at the portfolio level and RICE at the team backlog — and splitting one oversized spec into slices is a backlog-level decision, so RICE is the better default for the W-2 slicer (§4). It also has a property WSJF doesn't: an explicit Confidence term, which maps onto something spectastic already owns — the grounding ledger. §10 develops the rubric family, that mapping, and a way to slice by RICE contribution.

The reliability caveat is real. An LLM acting as a judge carries documented biases — position/order bias, verbosity bias, and self-preference among them — so a naïve "score each slice 1–10" is fragile. The mitigations the field converges on (e.g. the G-Eval rubric-scoring approach) are: an explicit rubric (the WSJF components are that rubric), pairwise comparison with position-swapping rather than absolute scores, and a multi-vote panel to dampen any single judge's bias. spectastic's judge panel pattern (§3) is built to carry exactly these. Agile vertical-slicing supplies the complementary half — a slice should cut top-to-bottom and deliver end-to-end value, so each ranked slice is independently demoable (which is already spectastic's smallest-demoable prompt).

2.5 · Keeping autonomous pipelines safe

The strongest warning in Building Effective Agents is about exactly the hands-off case: "The autonomous nature of agents means higher costs, and the potential for compounding errors. We recommend extensive testing in sandboxed environments, along with the appropriate guardrails." They add that "human review remains crucial" even when automated testing passes, and that agents should be able to "pause for human feedback at checkpoints or when encountering blockers."

Read against spectastic, every one of those guardrails already has a home: sandbox → the explore quarantine; verification gate → validate + P-7; checkpoint → the AskUserQuestion decision phase the interview verbs already use; error compounding → the typed artifact + validate between every step. The design work in §4–§6 is mostly wiring the guardrails spectastic already owns into the pipeline, not inventing new ones.

3 · The primitive layer — write once, port anywhere

Rather than couple spectastic to one orchestrator, name the six primitives the field shares (§2.3) and treat any concrete tool as a backend. A workflow designed in this vocabulary runs on Claude's Workflow tool today and ports to LangGraph, CrewAI, or the OpenAI Agents SDK with no design change.

A single --effort dial scales this whole table at once — how wide the fan-out, how deep the decider, how long the loop. §9.2.

One constraint, with a way around it. A Claude workflow script runs headless, outside the conversation — it cannot itself stop to ask a person. So human checkpoints sit between workflow phases: a workflow runs an autonomous stretch, returns, the main loop surfaces an AskUserQuestion gate, and the next phase launches on the answer. But a checkpoint is really "consult the decider," and the decider need not be human — an agent or a panel decider runs inline, inside the script. §9.1 makes the checkpoint a configurable role, which is what turns "bursts bracketed by human gates" into a dial between fully-hands-off and fully-gated.

4 · Six workflows for spectastic

Led by the two requested headliners (W-1, W-2). Each is tagged with the pattern(s) it uses, the primitives it composes, where it would live, and the one guardrail it must not ship without.

W-1 · Hands-off lifecycle pipeline headliner

Submit a spec, walk away. After a human approves the spec, an orchestrator drives slice → plan → tasks → implement → verify, pausing only at the value-laden checkpoints.

Patterns
Prompt chaining (the lifecycle is the chain) + orchestrator-workers (implement) + evaluator-optimizer (the verify gate).
Primitives
pipeline (artifact → artifact) · evaluator (validate + P-7 between every step) · human-checkpoint (approve slices & must-tier) · bounded loop (implement --all drains tasks).
Lives
An orchestration script calling the existing verb CLIs — the deferred action-detecting /spectastic.next composed into a loop. No new artifact types; the verbs already emit + validate them.
Guardrail
Checkpoint before implement (and at slice priorities); validate after every step to stop error compounding; the P-7 verify gate before "done." This is the autonomous case Anthropic warns about (§2.5) — it ships sandboxed and gated or not at all.

W-2 · Value-ranked slicer headliner

One oversized spec → many slices, ordered by business value. Take a spec that trips the amber/red <spec-budget> and emit sibling slice-specs, each with a <spec-parent> back-reference and a value-ranked index.

Patterns
Parallelization — sectioning (draft candidate slices) + voting (rank) — plus a completeness critic (did the slices cover the parent?).
Primitives
fan-out (draft each candidate slice) · judge-panel (score each by a pluggable rubric — default RICE, WSJF when time-criticality dominates, ICE for a quick pass — pairwise + multi-vote to dampen bias, §2.4) · orchestrator (merge + order) · human-checkpoint (confirm the ranking). A slice's Confidence is its grounding status and its Reach × Impact is its smallest-demoable boundary (§10).
Lives
The deferred /spectastic.split — already noted as composable from spec + propose + apply; this adds the ranking judge and the coverage critic on top.
Guardrail
Business value is a human-owned call. The panel proposes a WSJF-ranked order; the user confirms via AskUserQuestion. The completeness critic must prove no parent requirement was dropped before any slice is written.

W-3 · Adversarial proposal hardening

Scale the existing propose-time risk pass from one shot to a panel: N skeptics each try to refute a proposal or surface a risk; majority vote decides what becomes a <spec-risk>.

Patterns
Parallelization — voting / adversarial verify.
Primitives
fan-out skeptics · judge (majority-refute kills a weak risk; survivors are logged).
Lives
/spectastic.propose --adversarial exists as a single pass — this widens it to a panel.
Guardrail
Risks land as <spec-risk status="identified"> and apply already refuses while any remain unresolved — the human dispositions each. The panel proposes; it never auto-closes a risk.

W-4 · Conformance & drift sweep

A whole-repo audit: sweep every spec/plan/tasks/verify bundle for the judgement calls the deterministic validator cannot make — "does this plan actually satisfy its spec?", "has this verify view drifted?", "does this requirement still trace to a task?"

Patterns
Multi-modal sweep + completeness critic.
Primitives
fan-out (one agent per spec, or per check-dimension) · pipeline (find → adversarially verify) · completeness critic (what did we miss?).
Lives
An agentic layer above spectastic validate — the deterministic rules stay the cheap backstop; the workflow adds the semantic checks.
Guardrail
Findings are advisory: each becomes a <spec-triage> card, never a silent edit. The validator remains the source of truth for structural conformance.

W-5 · Triage list-intake fan-out

Paste a long list of defects/ideas; one agent per item classifies its layer (just-do / defer / spec / …) in parallel; cards append to inbox.html.

Patterns
Parallelization — sectioning.
Primitives
fan-out (one classifier per item) · orchestrator (collect → append in order).
Lives
/spectastic.triage list-intake mode runs this sequentially today — parallelizing it is a drop-in speedup.
Guardrail
The just-do-vs-spec boundary is the human-commit decision the triage discipline already routes through AskUserQuestion; the fan-out flags ambiguous items for that gate rather than guessing.

W-6 · Explore graduation

The deferred back half of 022-explore: turn a quarantined build into a real spec/plan/tasks — classify spike vs tracer-bullet, extract the spec from what was built, restore the relaxed gates.

Patterns
Orchestrator-workers + evaluator (the run record becomes verified grounding).
Primitives
pipeline (extract → classify → restore) · human-checkpoint (classification is an honest call) · evaluator (promote the captured run to grounding="verified").
Lives
The TBD-explore-graduation sibling slice of 022.
Guardrail
Quarantine + mandatory graduation is the anti-ship guard already shipped; the classification is recorded so it can't be silently reversed.

W-1 and W-2 are the only two that need genuinely new orchestration; W-3, W-4, W-5 scale existing verbs from one-shot to fan-out, and W-6 is a deferred slice that happens to be workflow-shaped. The cheapest path to value is W-5 (pure speedup, no new surface) and W-3 (the panel already has a home); the highest-value is W-1.

6 · Guardrails — spectastic already owns them

The field's safety advice (§2.5) reads like a description of spectastic's existing discipline. The design job is to wire these into any workflow, not to invent them:

Start simple
Prefer a workflow (predefined path) over an agent for every step except implementation. The lifecycle order is known — don't hand it to an open-ended planner.
Validate between steps
Run spectastic validate after every verb. A typed artifact that fails validation halts the pipeline before the error compounds into the next step.
Verify before "done"
P-7 is the bar: tests pass, validate clean, runtime exercised. No workflow may report a step done on structural evidence alone.
Sandbox the risky stretch
Anything build-to-learn runs in the explore quarantine — the anti-ship guard already refuses to ship un-graduated work.
Checkpoint the value calls
Business-value ranking (W-2), must-tier scope (W-1), risk disposition (W-3), and the spike/tracer-bullet call (W-6) are human decisions surfaced via AskUserQuestion between phases. The agent proposes; the person commits.
Bound every loop
Drain loops (implement --all) and discovery loops stop on a tasks-exhausted, dry, or budget condition — never an open-ended "keep going."

7 · Open questions

  1. Orchestrator home. Does W-1 ship as a Claude Workflow script, a tool-agnostic CLI driver (spectastic run <spec-id>) that shells the verbs, or both — the script for the Claude surface, the CLI for portability? The primitive layer (§3) says the design is the same either way; the packaging is the call.
  2. Checkpoint granularity for W-1. One approval gate (before implement) or several (after slice, after plan, after tasks)? Fewer gates = more hands-off but more rework risk if an early step drifts. Likely a flag: --checkpoints=minimal|each.
  3. WSJF inputs for W-2. Does the judge infer the WSJF components from the spec text, or does the user supply business-value / time-criticality per candidate slice and the agent only computes + orders? The research (§2.4) says LLM ranking is most reliable as pairwise comparison against a rubric, not absolute scoring — which leans toward agent-proposes-pairwise, human-supplies-weights.
  4. Cost ceiling. A full hands-off run fans out many agents; what is the per-run budget cap, and does the pipeline degrade gracefully (fewer voters, shallower panels) as it approaches the ceiling rather than halting?
  5. Verb re-entrancy. W-1 assumes each verb is safe to run unattended on a Draft artifact (the P-6 in-place-edit path). Are all verbs idempotent enough that a re-run after a failed step is safe, or does the orchestrator need explicit checkpoint/rollback state?

9 · Addendum — tuning the autonomy surface

Two refinements that the first draft under-served. They share a thesis: autonomy is not a switch but a surface with two dials — who decides at a checkpoint (§9.1) and how much orchestration a step spends (§9.2). Both are grounded below in primary sources, re-fetched and quoted.

9.1 · The Decider — a checkpoint is a role, not a person

§3 said human checkpoints must bracket a headless workflow. True for humans — but a checkpoint is really "consult the decider," and the decider is a configurable role on one interface, with three implementations:

human default
An AskUserQuestion gate between phases. Highest trust, not inline. A checkpoint is opted down from here — so full hands-off is a deliberate choice, never the silent default.
agent
One specialist agent that decides inline, grounded in a constitution and, optionally, a knowledge source (a spec corpus, a knowledge graph). This is established: Anthropic's Constitutional AI trains preferences by having "a model… evaluate which of the two samples is better," and RLAIF shows AI feedback "achieves comparable performance to RLHF." spectastic already ships the constitution: principles.html.
panel
N diverse agents plus an arbitrator (majority vote, or a dedicated arbiter agent). The panel paper Replacing Judges with Juries finds a panel of smaller models "outperforms a single large judge, exhibits less intra-model bias due to its composition of disjoint model families… over seven times less expensive," and multi-agent debate improves factuality when an arbitrator resolves the exchange.

This maps straight onto spectastic's existing AIProvider interface (packages/core/src/types.ts), which already has ask() (bounded human choice) and subagent() (spawn a specialist) — a Decider is the small abstraction over both.

The guardrails the research demands — non-negotiable if a decider is not human:

  • Never let an agent judge its own output. Self-preference bias is measured: LLM judges "assign significantly higher evaluations to outputs with lower perplexity… regardless of whether the outputs were self-generated" (Self-Preference Bias). Separate the author-agent from the decider-agent.
  • A panel needs diverse lenses, not N copies. The panel's value is the disjoint model families (above); N identical judges share their mistakes. Returns also diminish as voters grow — cap the panel rather than scale it without limit.
  • Keep human for high-stakes / irreversible calls — escalate by risk, the pattern the field converges on. The agent proposes; for anything that can't be cheaply undone, the person commits.
  • Log every verdict. A decider's call and its grounds are recorded — which is just spectastic's artifact-trail ethos applied to a non-human reviewer.

9.2 · The effort dial — one knob, sequential pass to voting panel

The second dial answers "panel vs pipeline, sequential vs parallel" with a single --effort level (low · medium · high · xhigh · max). This is not a novel invention — it is exactly the control the platforms already ship. Anthropic's effort parameter lets you "control how eager Claude is about spending tokens… with a single model," and crucially it "can affect all token spend including tool calls. For example, lower effort would mean Claude makes fewer tool calls." OpenAI's reasoning_effort does the same, "using fewer tokens for simpler tasks and thinking harder for complex tasks."

spectastic's move is to extend that dial from how hard one model thinks to how much orchestration the step uses — scaling the whole §3 primitive table at once:

--effortReasoningFan-outDeciderLoop
lowlownone — single sequential passsingle agent (or skip)none
mediummediumlimitedsingle-voteshallow
highhighparallel3-vote panelloop-until-dry
xhigh / maxxhigh / maxwide fan-outdiverse panel + arbitrator + completeness criticdeep, budget-bounded

The pattern is already live in this very tool: Claude Code's ultracode mode, per Anthropic's docs, "pairs the xhigh effort level with standing permission… to launch multi-agent workflows" — an effort level that scales orchestration, not just thinking. The accuracy case is well-established: self-consistency (sample diverse reasoning paths, take the majority) lifts reasoning accuracy by up to ~18 points, and scaling test-time compute can let inference-time effort substitute for a much larger model — but "effectiveness… critically varies depending on the difficulty of the prompt," so resources should be allocated adaptively, not uniformly.

That last finding is why the default is --effort=auto: derive the level from signals spectastic already computes. The propose adversarial pass is the prototype — it auto-fires on a must-tier touch, a removed op, or ≥2 topic prefixes (packages/core/src/commands/propose.ts); the <spec-budget> amber band is another. auto generalises these into one rule: spend more orchestration when the change is riskier. It also unifies the scattered knobs — propose --adversarial, implement --all/--phase/--parallel — into one coherent vocabulary, mapping straight onto the Workflow tool's existing per-agent effort + budget.

9.3 · How they compose + open questions

The two dials are orthogonal but interact: effort selects the decider's depth. At low, a value-checkpoint consults a single agent (or, if human, defers cheaply); at high+, the same checkpoint convenes a diverse panel with an arbitrator. The headliner workflows inherit this directly — W-2's rubric ranking (§10) is a high-effort panel decider; W-5's triage classification is a low-effort single agent.

  1. Where the Decider is configured. A per-run flag (--decider=human|agent|panel), per-checkpoint config in the spec/plan, or a project-level default in settings? Likely all three with precedence, mirroring how --effort overrides an auto default.
  2. The auto mapping. What exact signal → effort table does --effort=auto use, and is it per-verb (propose's heuristic differs from implement's)? This is the one piece that must be specified before W-1 can run unattended.
  3. Decider grounding for agent. Is the constitution just principles.html, or also the spec bundle + grounding ledger? A richer ground reduces hallucinated verdicts but widens the agent's context cost.

10 · Addendum II — ranking rubrics: RICE, WSJF & slicing by value

§2.4 leaned on WSJF; the W-2 slicer now defaults to RICE. This addendum says why, maps RICE's softest input onto something spectastic already owns, and proposes a way to slice by RICE contribution — flagged honestly, because the literature doesn't cover it.

10.1 · The rubric is pluggable — RICE, WSJF, and the family

Prioritization rubrics are a family, not a winner. They divide by the question they answer:

RubricFormulaBest when
RICEReach × Impact × Confidence ÷ EffortTeam-backlog, feature-level ranking with an explicit uncertainty discount — the default here
WSJFCost of Delay ÷ Job SizePortfolio sequencing where time-criticality and deadlines dominate
ICEImpact × Confidence × EaseA quick triage pass — RICE minus Reach; fast but blind to audience size
MoSCoWMust / Should / Could / Won'tScope negotiation within one release — buckets, not a ranking
Kanodelighters vs must-havesDiscovery — categorising by user emotion before any scoring

RICE and WSJF are not interchangeable: "They answer different questions, so pick one as your main tool and use the other for a gut check" (Product Blueprint). The standard allocation is explicit — "At the portfolio level… WSJF excels. At the team's backlog, RICE provides the quantitative rigor needed to rank 20–50 features" (Fygurs). Splitting one oversized spec is a backlog decision, so RICE is W-2's default; WSJF is the opt-in when a slice carries a real deadline. Because the W-2 judge scores against whatever rubric it's handed (§4), the rubric is just config — and an effort dial (§9.2) decides how many judges score it.

10.2 · Grounding is RICE's Confidence

RICE's softest term is Confidence — the multiplier that exists "to curb enthusiasm for exciting but ill-defined ideas" (Intercom), scored 100% / 80% / 50% with anything lower a "moonshot." In most teams that number is a guess. In spectastic it is an artifact: the plan's grounding ledger already grades every design-bearing fact as verified ("opened the source this turn"), spike ("decidable only by a time-boxed investigation"), or assumed ("taken as true without verification"), per REQ-LIFECYCLE-006.

Grounding status→ RICE Confidence
verified100% — the fact was checked against real source
spike (resolved)80% — decidable by a bounded investigation that ran
assumed / unresolved spike50% or below — a moonshot until grounded

The fit is more than cosmetic. RICE says a high-reach, high-impact, low-confidence idea is a signal to "do research… to learn more" — which is precisely spectastic's spike: a named, time-boxed investigation that raises a fact's grounding. So a low-Confidence slice doesn't just score lower; it nominates its own spike. RICE's hand-waviest number becomes a typed, auditable input.

10.3 · Slicing by RICE contribution

The sharpest question — can slices split into their RICE contribution? — turns out to be unanswered in the literature. Published guidance decomposes a feature only to estimate Effort; there is no standard method for rolling Reach and Impact across slices, nor for the double-counting that follows. So the proposal below is spectastic's own, offered with its caveats rather than as received practice.

Score each candidate slice as its own RICE row and order by per-slice score — this naturally front-loads the high-reach, high-confidence, low-effort slices, which is exactly a value-ranked emission. Two honest hazards must be handled, and spectastic happens to hold the tools for both:

Marginal, not additive, Reach
Slices share users, so summing each slice's Reach over-counts. Score a slice's incremental reach given what's already shipped — the contribution, not the gross. (Unsolved in the literature; name it, don't paper over it.)
Dependencies
RICE is documented-blind to ordering — it "evaluates alternatives without considering dependencies." spectastic isn't: the <spec-parent> and defer-to graph already encodes which slice unblocks which, so an enabling slice can take a ranking boost the bare RICE score would miss.

The result is a ranking that reads as "ship this slice next" with a defensible reason — Reach×Impact from the smallest-demoable boundary, Confidence from grounding, Effort from the plan, ordered with dependencies honoured.

10.4 · Other homes, failure modes & sources

Where else value-scoring earns its keep in spectastic: ranking the deferred-slice backlog — the defer-to="TBD-*" items and inbox layer="defer" cards accumulate, and RICE answers "which deferred slice next?"; and the <spec-budget> amber-band split nudge, which already says "should some of this be its own slice?" — RICE ranks the resulting candidates.

Failure modes to respect (numeric rubrics invite false confidence): RICE "weights all reach equally, treating a feature used once by a million users the same as one used daily by a thousand power users" and "does not account for time sensitivity or cost of delay" (Fygurs) — which is the WSJF gap, and the reason the rubric stays pluggable. Multiplicative scores are gameable and falsely precise. spectastic mitigates two of these natively (grounding → an honest Confidence; the parent/defer graph → dependencies), but the human still owns the final order (W-2) — the rubric proposes, it does not decide.
