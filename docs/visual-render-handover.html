Handover · visual renders

Why no images landed

A design import that reports two files refused "because they carry a runtime" looks like a refusal rule dropped the renders. It didn't. The refusal rule is sound, and the real blocker is one nobody can see fail.

Status Draft Type Handover — findings from a real import, ready to take to /spectastic.spec Author Brian Corbin · @briancorbinxyz Created 17 Aug 2026 Surfaced inexample-currency-converter · 001-currency-conversion Feeds a binary-FileSystem change and a new visual:render verb Read time

A Claude Design project with eleven screen states in light and dark was imported with visual:import. No images landed. Four causes, none of them the refusal rule: no Claude Design export contains renders of its own artboards (they exist only once a browser executes the runtime); spectastic has no render capability at all; the FileSystem land path is text-only, so a binary would have been corrupted even if one had been present; and .thumbnail — the sole tool-made image — is filtered as a dotfile before it is ever read. Fix the FS first, then add a separate verb. Do not touch landingWouldViolate().

1 · The question this answers

A Claude Design project — iPhone Currency Converter Screens — was imported into a spectastic project via spectastic visual:import. The design draws eleven screen states, each in light and dark. None of them landed as images.

The generated import manifest reports two files under Not landed, with the reason "These carry a runtime", which reads as though a safety rule discarded the renders. That reading is wrong in a way worth writing down, because it points the fix at the wrong file.

2 · No renders existed to land

This is the decisive one. No Claude Design export contains rendered images of its own artboards. Verified across three exports on disk:

ExportImages it contains
iPhone Currency Converter Screens.zip.thumbnail only
Wazocal initial screen designs.zip.thumbnail, plus uploads/*.jpg — user-supplied inputs, not renders
Spectastic Website Prototype/, Spectastic.io (2)/favicon.svg, uploads/draw-*.png, screenshots/*.png — all uploads or hand-curated handoff assets

The only image the tool emits itself is .thumbnail: one WebP preview of the whole canvas, not per-artboard renders.

An artboard exists only as .dc.html source plus a runtime. It becomes an image only when a browser executes it — support.js fetches React 18.3.1, ReactDOM and Babel from unpkg at load time and renders client-side. There is no point in the export pipeline at which a picture is written to a file.

Only Claude Design exports were examined. Whether exports from other design tools carry renders is unverified, and a render verb's design should not assume either way.

3 · spectastic has no render capability

rg -l "puppeteer|playwright|screenshot|renderTo|toPng" packages/*/src
# → no matches

No verb turns a design export into images. This is the actual gap, and everything in §7 exists to close it.

4 · The land path is text-only — fix this first

packages/core/src/types.ts:27

readFile(path: string, encoding?: 'utf8'): Promise<string>;

There is no binary read or write path on the FileSystem interface. visual:import reads every export file as a UTF-8 string (packages/core/src/visual/import.ts:312), hashes that string with FNV-1a over charCodeAt, and writes the string back out.

A PNG or WebP through this path is corrupted, not landed — and nothing errors. No exception, no refusal, no manifest entry: the bytes simply arrive mangled. This is why .thumbnail would have been destroyed even had it not been filtered, and why "land the renders" is not a policy change to the importer but a prerequisite change to the FS abstraction.

Two things to decide when changing it: what the content hash does for binary input, since the current FNV-1a implementation is text-shaped by construction; and whether landing binaries trips anything downstream — the security scan's globs, or the artifact content policy.

Not checked: whether any FileSystem provider other than providers/node-fs.ts already handles binary.

5 · .thumbnail is filtered as a dotfile, deliberately

packages/core/src/visual/import.ts:208

for (const name of (await fs.readdir(dir)).filter((f) => !f.startsWith('.')).sort()) {

The doc comment immediately above names the file explicitly: ".thumbnail is not design material, and neither is anything inside a dot directory it might ship." That judgement is defensible — a canvas preview chip is not per-state evidence — so this is the lowest-value of the four fixes.

One wrinkle worth recording. The filter runs before any read, so .thumbnail is the single file that is neither landed nor reported. Every other read-but-not-copied file appears in the manifest's Not landed list; this one is invisible rather than refused, which is a different thing from the reader's side.

6 · Not a bug — leave this alone

support.js (68 KB) landed, while Converter States.dc.html was refused for carrying a runtime. The runtime landed; the file referencing it did not. It reads as an inconsistency and it is not one.

landingWouldViolate() only inspects HTML suffixes:

export function landingWouldViolate(name: string, body: string): boolean {
  const lower = name.toLowerCase();
  if (!HTML_SUFFIXES.some((suffix) => lower.endsWith(suffix))) return false;
  return carriesExecutableContent(body);
}

The comment block above it already anticipates exactly this objection, citing triage T-018 and FR-014's second sentence: a bare .js lands on purpose, because the check protects "the project staying valid after an import" and artifact rules parse HTML, not JS. Refusing it "would mean deciding what BELONGS in a project rather than what is SAFE to copy — a judgement with no crisp test." The call is sound; re-opening it would relitigate a decision that has already been made twice.

7 · Recommended order of work

  1. Binary-capable FileSystem — packages/core/src/types.ts:27 plus providers/node-fs.ts. Everything else is blocked on it, and it is the one that fails silently today.
  2. A separate visual:render verb — not a flag on visual:import. This distinction is the load-bearing recommendation in this document. visual:import advertises "No network, no account, no design-tool licence" and executes nothing. Rendering requires a headless browser and network egress to unpkg. Folding it into import would silently void a property that verb promises today, so it needs its own verb and its own permission story.
  3. <spec-render> wiring — nothing new required. The screen vocabulary already carries it and spectastic validate accepts it: 
    <spec-render src="renders/stale-loud-light.png" contexts="mode=light scale=two-decimal"></spec-render>
    Once files land this is one attribute per state. A render is evidence and never a dependency, so its absence is not a gap and nothing checks for one — which means step 3 can lag steps 1 and 2 safely.
  4. Optionally, stop dropping .thumbnail silently — or at minimum report it, so it is refused rather than invisible.

8 · What makes the render verb cheaper than it looks

The artboards carry their own identity in the DOM. From Converter States.dc.html:

<div data-screen-label="{{ s.id }} · light">      <!-- and "… · dark" -->
<div data-screen-label="picker {{ p.id }} · light">

A render pass can name every capture from that label and derive the grid context directly, so contexts="mode=light" falls out of the renderer rather than being hand-authored twenty-two times.

The state inventory and props sit in the data-props / DCLogic script at the end of the same file: eight converter states (no-rate, empty, converted, fetching, stale-marked, stale-loud, unavailable, same-currency), three picker states (browsing, searching, no-results), and a pair enum of three values (EUR→USD, USD→JPY, USD→BHD) that maps cleanly onto a decimal-scale axis of 2, 0 and 3 places.

9 · Reproducing the render

This worked first try, with no modification to the export.

unzip -q "~/Downloads/iPhone Currency Converter Screens.zip" -d /tmp/dx
cd /tmp/dx && python3 -m http.server 8899
# then drive a headless browser to:
#   http://localhost:8899/Converter%20States.dc.html
# viewport 1600x1200; the runtime self-bootstraps React from unpkg

It renders the full state gallery correctly — light section, then dark. Three gotchas for whoever builds the verb:

  • Network is required. support.js pulls react@18.3.1, react-dom@18.3.1 and @babel/standalone@7.29.0 from unpkg. Offline it throws dc-runtime: window.React is not available yet. A render verb either needs egress or must vendor those three.
  • The page logged one console error, uninvestigated. It did not visibly affect rendering, but a render verb should surface console errors rather than swallow them — a silently half-rendered artboard is worse evidence than none.
  • The Playwright MCP server writes into the current working directory — probe.png and a .playwright-mcp/ directory land in whatever repo you are standing in. Run it from a scratch dir, or clean up after.

10 · Evidence that renders are worth landing

Rendering the export immediately caught a genuine authoring error in the consuming project's screen file (specs/001-currency-conversion/visual/converter.html in example-currency-converter). A <spec-refusal text="—" context="figure slot"> forbade a dash in the result slot, citing FR-004 — but the design legitimately draws a dash in the empty state, where a rate is held, its age is on screen, and the slot is empty only for want of a typed amount. The refusal would have told an implementer the design violated a requirement it did not.

Already fixed there by rescoping the refusal to "result slot when no rate is held". Recorded here because of how it was found: invisible when reading the export's source, obvious in the picture.
