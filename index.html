v0.1 · single-file HTML specs

Spectastic

Specs that read like quiet essays and review like good design docs. One self-contained .html file per artifact — rich, information-dense, hand-editable.

See an example spec → Read the README

One file. Twelve semantic custom elements. A calm typographic design system in ~25 KB of hand-written CSS. Seven Claude Code slash commands across the spec lifecycle — principles → spec → plan → tasks → implement → propose → apply → triage. No build step. No framework. No bundler.

Why HTML, not Markdown

Long markdown specs lack visual hierarchy, can't embed diagrams, mangle tables, and force reviewers to hold many duplicated artifacts in their head at once. HTML solves these directly. The hard part is keeping the source as editable as markdown — which is what the spectastic component vocabulary is for.

Tabular data

real <table>, with row groups and totals.

Design data

typography and spacing that signals where to look.

Code

<pre> + <code> with margin annotations.

Illustrations

inline SVG — diffable, scalable, editable.

Interactions

tabs, copy-link, conformance index. JS-off still works.

Workflows

boxes-and-arrows architecture sketches as small SVG.

Spatial data

positioning and grid without escaping markdown's fence.

Images

<img>, ideally a sibling file, base64 only when necessary.

Responsive

fluid type and a media-query-driven sidenote fallback.

Shareable

one file, one link, one attachment.

The lifecycle

Four core phases. Each is a Claude Code slash command that fills a template.

/spectastic.principles

./principles.html

The non-negotiable principles every downstream artifact must respect.

/spectastic.spec

specs/<id>/spec.html

What the feature is, for whom, and how we know it worked.

/spectastic.plan

specs/<id>/plan.html

How we will build it — stack, decisions, alternatives, risks.

/spectastic.tasks

specs/<id>/tasks.html

Ordered, parallelizable work. Tests precede implementation.

/spectastic.implement

code edits · checkbox ticked

One task per invocation. Read context, do the work, tick the box. Loop to drain.

/spectastic.propose

specs/<id>/changes/<date>-<slug>/proposal.html

PR-shaped change proposal with typed deltas. ADD / MODIFY / REMOVE / RENAME.

/spectastic.apply

spec.html patched · folder → archive/

Fold approved deltas into the live spec. Change folder preserved verbatim.

During implementation, /spectastic.triage appends a single <spec-triage> card per debug session to a triage log — five required fields, deep-dive only when a cross-spec / principles / hotfix trigger fires. See the worked triage log, the archived change proposal, and the OpenSpec considerations that drove the proposal design.

Component vocabulary

Twelve custom elements cover the spec-shape. The names are self-describing; an LLM can target them without re-reading the design system.

<spec-meta>
header metadata block — status, owner, version, dates.
<spec-status>
inline pill — draft / review / accepted / superseded / deprecated / blocked.
<spec-tldr>
boxed one-paragraph abstract, always near the top.
<spec-audience-map>
"read this first" navigation — Exec / Reviewer / Implementer paths.
<spec-goals> / <spec-non-goals>
tickbox and crossbox lists; non-goals styled as deliberate, not absent.
<spec-requirement>
the unit of conformance. Stable ID + priority="must|should|may".
<spec-rule>
inline RFC 2119 keyword — MUST, SHOULD, MAY.
<spec-decision>
ADR card with Context / Decision / Consequences.
<spec-note>, <spec-warning>, <spec-question>, <spec-assumption>, <spec-tip>, <spec-example>
typed admonitions; each gets its own colour gutter and label.
<spec-tabs> / <spec-tab>
tab group for alternative views (Source / Rendered / DOM, before / after).
<spec-diff>
red/green change block — uses semantic <ins> and <del>.
<spec-matrix>
option × criterion decision table with a data-winner row.
<spec-tradeoff>
inline bar sparklines scoring options on a few axes.
<spec-questions>
numbered open-question register, one per section or one at the end.
<spec-changelog>
append-only revision history with timestamps.
<spec-arch>
frame around an inline SVG architecture diagram.
<spec-conformance>
auto-built index of every requirement in the document.
<spec-glossary>
definition list with serif terms and cross-linked <dfn> references.
<spec-sidenote>
Margin note for asides; collapses inline below 1100 px.
<spec-newthought>
small-caps section opener for visual rhythm in long prose.

That's more than twelve, because the admonitions count as one family and the inline pills count as one. The promise stands: a handful of well-named tags do the work of a hundred class names.

Getting started

  1. Clone or copy this directory into a project.
  2. Run /spectastic.principles <project name> in Claude Code.
  3. Run /spectastic.spec <feature> to draft a spec.
  4. Run /spectastic.plan to add the technical plan.
  5. Run /spectastic.tasks to derive the task list.
  6. Open the resulting .html files in any browser. Edit the source directly whenever you like.
  7. When you want a single-file artifact to email or attach, scripts/inline.sh specs/001-foo/spec.html > dist/spec.html.
