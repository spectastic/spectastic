Three MODIFY deltas correct where graduation's verified grounding lands. FR-004 says the run record's proven facts enter the extracted spec's grounding ledger — but a spec has no such element; REQ-LIFECYCLE-006 places the evidence ledger in the plan (§3 Grounding & evidence + <spec-decision grounding>). So the extract leg must emit a Draft spec + plan bundle and seed the run facts into the plan's evidence ledger. Ground the extracted bundle in the plan, not the spec

Applied

1 · Intent

Surfaced during T-100 (the extract test): writing the assertion forced the question "where does grounding="verified" actually render?" — and the answer is the plan, not the spec. REQ-LIFECYCLE-006 defines the evidence ledger as a /spectastic.plan artifact: §3 Grounding & evidence rows plus <spec-decision grounding="verified|spike|assumed">. No spec carries a grounding-ledger element; the only occurrences of grounding="verified" in any spec are prose code-spans describing the concept.

So FR-004 as written is unbuildable — it points the extract at a spec element that does not exist. The fix: graduation's extract leg emits a Draft spec + plan bundle, and the run record's proven facts seed the plan's evidence ledger as verified rows. This also sharpens D-007: the extract genuinely feeds both /spec and /plan, reusing both interviews rather than just one.

2 · Scope

In scope

  • Correct FR-003 (extract emits spec + plan), FR-004 (run facts → the plan's §3 evidence ledger), SC-002 (verified grounding in the extracted plan), and FR-006 (grounding ledger explicitly plan-borne; bundle = spec + plan + tasks).
  • Fold the consequent updates — the spec's data-model/assumptions prose, the plan's D-004/D-007, and the US1 task contracts — as §6 tasks.

Out of scope

  • The transaction kernel, archive move, classify record, and atomicity (FR-005–FR-008, NFR-001) — unchanged; grounding location does not touch them.
  • Re-running the whole US1 implementation here — it proceeds after apply on the corrected contract.

3 · Approach

Four MODIFY deltas, one topic (the graduation extract). The architectural shift is small but real: the extract leg's output grows from one artifact (spec.html) to two (spec.html + plan.html), because grounding has nowhere to live in a spec. The plan's §3 evidence ledger is seeded with one verified row per proven fact in the run record (citing the archived exploration), and the decisions those facts support carry grounding="verified". The restore tasks.html (US2 / FR-005) is unchanged — the bundle is now spec + plan from FR-003 and tasks from FR-005, which together is the ordinary three-file slice.

5 · Risk register

Adversarial pass ran (touches must-tier requirements). One <spec-risk> per finding; status= defaults to identified; apply refuses until each transitions to accepted, mitigated, or rejected.

Making the extract emit plan.html means an AI reads a loose, ceremony-off prototype into binding plan design decisions; a thin-evidence build then either fabricates verified-looking decisions or stalls at REQ-LIFECYCLE-006's must-tier grounding gate — neither failure the old spec-only output could produce.

FR-003 — "reading the build's … behaviours into … the plan's design decisions".

Only facts present in the run record become verified rows; the plan interview marks every gap assumed or spike, and the gate blocking an un-grounded must decision is working as intended — a graduation that proved little SHOULD interview the gaps before /tasks, accepting residual gaps as tracked <spec-risk>s (the gate's own escape hatch). The build grounds what it ran, not what it didn't.

FR-006 (a must-tier requirement not in the deltas) names "the grounding ledger" among the extracted bundle's full-discipline artifacts, framed spec-side — so the applied spec's contract still implies a spec-borne ledger, the exact bug this change fixes elsewhere. The fix is partial.

FR-006 — "the extracted bundle is produced under full discipline (requirement IDs, NFRs, success criteria, INVEST, the grounding ledger, full principles compliance)".

Mitigated — the author added the 4th MODIFY delta on FR-006, naming the bundle's three artifacts and locating the evidence ledger in the plan. The applied spec is now internally consistent across FR-004 / SC-002 / FR-006.

Scope is too narrow at the contract boundary: folding the FR-006 correction into a post-apply §6 prose task rather than a delta understates the change's true contract surface and risks an applied spec internally contradictory between FR-004/SC-002 (plan) and FR-006 (spec) until a later, unguaranteed task runs.

§2 In scope — "Fold the consequent updates — the spec's data-model/assumptions prose … — as §6 tasks".

Mitigated — FR-006 promoted to a delta. The data-model and assumptions halves are genuinely non-requirement prose a delta cannot target, so those correctly stay §6 tasks.
