Specification · 025-id-uniqueness

ID uniqueness — collision-safe stable ids across branches and within a file

Two small, pure validation rules that make stable ids collision-safe: no two spec directories may share a number, and no id may be declared twice inside one file. The foundation the branch-per-spec model rests on.

1 · Context

Stable ids are a spectastic contract (P-3). The git-strategy brief's G-001 chose to keep the readable, sortable, branch-aligned NNN directory ids and treat the one real race — two developers on two branches both running resolveNextId (which has no atomicity) and both minting 025 — as a merge-time concern: caught loudly by CI, never silent.

The existing validator already detects duplicate project-wide qualified ids (REQ-TOPIC-NNN) across files (no-duplicate-ids, 002 · FR-011). But two gaps remain, and they are exactly the gaps the branch model exposes: (1) nothing flags two directories sharing an NNN — the cross-branch collision; (2) nothing flags a spec-local id (FR-001) declared twice within one file — the gap a /spectastic.spec re-entry edit can silently open. This slice closes both with two pure rules — the foundation every later git-strategy slice (branch automation, init --tools, the split work) assumes.

2 · User scenarios & testing

Each story MUST be independently testable. Both are P1 — the two halves of id-collision safety.

US1 · Catch a cross-branch number collision P1

As CI / a reviewer, I want two specs that grabbed the same NNN on different branches to fail validation when they meet so that a collision is loud at merge, never a silent double-claim of an id.

Acceptance: a tree containing specs/025-foo/ and specs/025-bar/ (two distinct directories, same number) produces an error finding on each, citing the other. The real tree (no two dirs share a number) and a graduated spec (explorations/023/ → specs/023/ reuse the id by design) produce no finding.

US2 · Catch a within-file id double P1

As a spec author, I want a spec-local id declared twice inside one document flagged so that a re-entry edit can't silently give two requirements the same anchor.

Acceptance: a spec.html declaring FR-001 on two <spec-requirement> elements produces an error on each, citing the other. A file with all-distinct ids produces none.

Edge cases

  • The three bundle files in one dir (spec.html + plan.html + tasks.html under 025-foo/) share the dir id 025-foo — that is the bundle, not a collision. The rule groups by distinct directory name, then by number.
  • Archived / withdrawn proposals (**/archive/**, **/withdrawn/**) are excluded, exactly as no-duplicate-ids already excludes them.

3 · Requirements

Keywords (MUST, SHOULD) follow RFC 2119.

Functional

A new cross-file rule spec-id-unique MUST emit an error when two distinct specs/<NNN>-slug/ directories share the same numeric NNN prefix. The directory id is derived from each document's path (the existing specs/([^/]+)/ regex); documents are grouped by distinct directory name, then by number. Each colliding site cites the other(s) via related locations.

Scope

specs/ only; explorations/ excluded (graduation reuses the id by design); **/archive/** + **/withdrawn/** excluded, as no-duplicate-ids does.

A new per-file rule id-within-file-unique MUST emit an error when a spec-local id (the two-segment form FR/NFR/SC-NNN on <spec-requirement>, D-NNN on <spec-decision>, T-NNN on <spec-task>) appears on two or more elements within a single document. Each duplicate site cites the other(s).

Scope

Spec-local ids only; qualified REQ-TOPIC-NNN dups (within a file or across) stay with no-duplicate-ids, so the two rules don't overlap.

Both rules MUST be registered in packages/schema/src/rules/index.ts so the default spectastic validate run includes them at error severity — no flag required.

Both rules SHOULD be pure and deterministic — given the same document set they produce identical findings, with no AI and no network. This is what lets the existing validate-on-PR CI (docs/ci-examples/github-actions.yml) plus branch-protection "require up to date with main" make spec-id-unique bite at the second PR, with no new CI tooling.

Each finding SHOULD name every colliding site (the related locations) and carry a fixHint grounded in P-3 — renumber the colliding directory, or give the duplicate a fresh id; stable ids are never reused.

Non-functional

The two rules SHOULD add no measurable regression to validation performance — they operate on the already-parsed AST and the file path, reading no extra files — keeping within the validate budget of 002 (p95 under 100 ms per file).

Out of scope (deferred to other slices)

  • The CI workflow / branch-protection config itself — the existing docs/ci-examples/ + the deferred spectastic init --tools (git-strategy §6 ④) own the wiring; this slice ships only the rules.
  • Branch/commit automation and remote-aware id allocation (git fetch-then-scan) — git-strategy G-002/G-003. This slice is the safety net, not the allocator.
  • The dependency-graph rules (a typed dependency edge + an acyclicity / no-cycles check) — the dependency-ordering layer (roadmap §4 / R-002).

4 · Data model

No new entities. Two rule objects join the existing registry; each consumes the already-parsed document(s) and emits standard Findings.

spec-id-unique
A CrossFileRule: maps each doc's path → its specs/<dir>/ name → the numeric prefix; a prefix held by 2+ distinct dir names yields one finding per site.
id-within-file-unique
A per-file rule: walks one document's AST, collects spec-local ids per id-bearing element, and yields a finding for any id seen on 2+ elements.

5 · Success criteria

Technology-agnostic, measurable outcomes.

Given two distinct specs/ directories sharing an NNN prefix, validate emits an error on each (citing the other); given the real project tree and any graduated spec (explorations→specs id reuse), it emits zero such findings.

Given a document declaring a spec-local id twice (e.g. two FR-001), validate emits an error on each duplicate; a document with all-distinct ids emits none.

Both rules run in the default spectastic validate set at error severity (no flag), and the full project (specs/** + docs/*) continues to validate clean with them enabled — no false positive on the existing tree, no measurable per-file p95 regression.

6 · Assumptions

The working template is packages/schema/src/rules/no-duplicate-ids.ts — same CrossFileRule shape, the same walk/getAttr/getLocation helpers, and the same specs/([^/]+)/spec.html path-derivation already used by no-broken-defer-to and parent-child-reciprocity.

The existing docs/ci-examples/github-actions.yml already runs spectastic validate on pull requests over specs/**; with branch-protection "require branches up to date before merging," the second colliding PR validates against an updated base and fails — so no new CI machinery is in scope.
