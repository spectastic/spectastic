Design · 025-id-uniqueness

ID uniqueness — collision-safe stable ids

How we will build it.

Status Accepted Spec 025-id-uniqueness Owner Brian Corbin · @briancorbinxyz Branch main Created 27 Jun 2026 Read time

Two pure rules, each a near-clone of an existing one: spec-id-unique is a CrossFileRule modeled on no-duplicate-ids.ts (derive the spec-dir from the path, group distinct dirs by numeric prefix, flag a shared number); id-within-file-unique is a PerFileRule modeled on requirement-id-required.ts (walk one doc, flag a spec-local id seen twice). Register both in rules/index.ts; add registry-driven fixtures. Every design fact is verified against existing source — no spikes, no assumptions. The only risk is a false positive on the real tree, retired by running the new rules over the whole project.

4 · Approach

Two new files in packages/schema/src/rules/, each a near-clone of an existing rule, registered in index.ts. spec-id-unique (cross-file): for each doc, match its path with the spec-dir regex; build a Map<numericPrefix, Set<dirName>>; any prefix held by 2+ distinct dir names emits one error per participating doc, each citing the others. id-within-file-unique (per-file): walk the doc, collect ids on <spec-requirement/decision/task> matching the spec-local pattern into a Map<id, Element[]>; any id on 2+ elements emits one error per site. Tests are fixtures the existing harness discovers automatically.

One combined rule can't satisfy the type system — within-file is PerFileRule, cross-dir is CrossFileRule. Folding into no-duplicate-ids overloads one rule with three concerns and muddies its single-responsibility. Two rules each clone a proven template.

6 · Decisions

D-001 · spec-id-unique as a CrossFileRule cloned from no-duplicate-ids

Status
Accepted
Context
The cross-file template exists (no-duplicate-ids.ts); the spec-dir regex (no-broken-defer-to.ts:7) and glob exclusion (glob.ts:13-14) are reusable.
Decision
Group distinct specs/<dir>/ names by numeric prefix (/^(\d+)-/); a prefix held by 2+ distinct dirs emits one error per site with related locations (FR-001). Explorations/archive/withdrawn excluded for free.
Consequences
+ A proven shape; the cross-branch collision is caught at merge. − A second cross-file rule (the project keeps these "sparingly" — justified: collision-safety is exactly cross-file).

D-002 · id-within-file-unique as a PerFileRule cloned from requirement-id-required

Status
Accepted
Context
The per-file template exists (requirement-id-required.ts); the spec-local id pattern is the complement of PROJECT_WIDE_ID.
Decision
Walk <spec-requirement/decision/task>; collect ids matching /^[A-Z]+-[0-9]+$/ into a Map<id, Element[]>; any id on 2+ elements emits one error per site (FR-002). Qualified REQ-* stays with no-duplicate-ids — no overlap.
Consequences
+ Closes the re-entry gap with a proven shape. − The two id patterns must stay complementary; a unit test pins the boundary.

D-003 · Registry-driven fixtures; the cross-file rule uses the directory form

Status
Accepted
Context
The harness (rules.test.ts) auto-discovers fixtures/<rule-id>/{positive,negative}; cross-file positives need a directory of 2+ files with preserved paths.
Decision
spec-id-unique: positive/ with specs/025-foo/spec.html + specs/025-bar/spec.html (same NNN), negative/ with distinct NNN. id-within-file-unique: single-file positive.html (an id twice) + clean negative.html. Plus a whole-project clean run (SC-003).
Consequences
+ No new test wiring — fixtures are the test. − Fixture paths must match the spec-dir regex exactly (pinned by the positive case firing).
