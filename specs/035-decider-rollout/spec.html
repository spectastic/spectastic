1 · Context

033 shipped the Decider but wired only propose's adversarial pass — a categorical checkpoint (which risks survive?). Its numeric arbitration branch (median of N votes, 033 FR-005) shipped untested by a real caller. Meanwhile the slicer (029) has its own hand-rolled scoring panel (slice/panel.ts): a fixed 3 scorers, a serial loop, a private median.

These are the same shape. This slice makes the slicer panel a Decider adopter — proving the abstraction is verb-agnostic (033's whole premise) and retiring the duplicate. The Decider's numeric path finally has a real consumer, and the slicer panel inherits config, auto, and concurrency for free.

Who this is for: the maintainer slicing an oversized spec who wants the ranking panel to obey the same one dial as every other checkpoint — and to run faster.

2 · User scenarios & testing

Each story is independently testable: implementing only US1 still yields a viable MVP.

US1 · The slicer panel is Decider-sized P1

As a maintainer, I want the slicer's scorer count to come from the effort dial so that ranking rigour obeys the same knob as every other checkpoint.

Acceptance: the scorer count is effortToDepth(effort).voters with a high floor — so it is ≥ 3 (029's rule) and dials to 5 at max; --effort=auto resolves via the slicer's signal.

US2 · Scorers run concurrently and share one median P1

As a maintainer, I want the panel's scorers fanned out, not serial, and the two panels to share one median so that ranking is faster and there's one arbitration to trust.

Acceptance: the N scorers run under 032's bounded pool; per-RICE-input aggregation uses the shared Decider median; the slicer's private median is retired.

Edge cases

  • 029 parity. At the default (floor high → 3 scorers), the panel behaves as 029 shipped — same count, same median.
  • Explicit count. A caller passing an explicit scorer count still gets exactly that (back-compat with 029's tests).
  • Interviews. The decision-phase interviews (spec/plan/propose/triage) consult a human via the harness, not a kernel AIProvider call — they can't be Decider-wrapped; out of scope.
  • confirmRice. The slicer's RICE-accept gate stays a human confirmation; only the scoring panel adopts the Decider in this slice.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) per RFC 2119.

Functional

The slicer's scoring panel MUST derive its scorer count from the Decider effort table (effortToDepth(effort).voters), config-driven, rather than a hard-coded constant.

The slicer panel MUST apply a high floor — the resolved count is never below 3 — preserving 029's ≥ 3-scorer rule (029 NFR-001).

The slicer MUST register an auto-effort signal (breadth = candidate count) so --effort=auto sizes its panel; with the high floor it resolves to ≥ high.

The N scorers MUST run concurrently under a bounded pool (spec 032's mapPool) rather than a serial loop, preserving input-order aggregation.

Both panels MUST share one median implementation — the slicer's private median is retired in favour of the Decider's, exercising 033's numeric arbitration (033 FR-005).

A caller passing an explicit scorer count SHOULD still receive exactly that count — 029's existing tests and callers are unbroken.

Non-functional

Config precedence (flag > project > default) SHOULD apply to the slicer panel exactly as to propose — one resolution path, not two.

Out of scope (deferred)

  • Wrapping the decision-phase interviews in the Decider — they consult a human via the harness's AskUserQuestion, not a kernel AIProvider call, so there is no kernel seam to wrap (advisory by nature, per T-009).
  • Making confirmRice (the RICE-accept gate) Decider-configurable — a human confirmation today; a later slice if a non-human accept is ever wanted.
  • W-1 consuming the now-uniform checkpoints to run unattended.

4 · Data model

No new entity — the slicer panel is re-expressed over the existing Decider effort table + median.

Entities

Slicer signal
The auto-effort signal for the slicer: { irreversible: false, breadth: candidateCount } (FR-003).
Scorer
Unchanged from 029 — one panellist rating each child's RICE inputs; the panel now sizes and runs them via the Decider.

The two arbitration types now have one home each: categorical (propose risks — majority vote) and numeric (slicer RICE — median), both in the Decider module. This slice is what makes "type-dependent arbitration" (033 FR-005) real rather than latent.

5 · Success criteria

The slicer panel runs effortToDepth(effort).voters scorers, floored at 3 — observable by counting scorer invocations at high (3) and max (5).

At the default, the panel runs exactly 3 scorers and produces the same median ranking as 029 shipped (parity).

The scorers run concurrently — observed peak concurrency > 1 under the bounded pool, not a serial 1.

A grep confirms one median implementation remains in the codebase — the slicer's private copy is gone.

6 · Assumptions

029's panelScore per-RICE-input median semantics are unchanged; only the sizing, concurrency, and median source change. The ranking output at 3 scorers is identical.

The Decider's median (033) and the slicer's medianRice compute the same value per input, so consolidating them is behaviour-preserving.
