Design · 042-profile-enforcement

Profile enforcement

How we will build it.

Status Accepted Spec 042-profile-enforcement Owner Brian Corbin · @briancorbinxyz Branch main Created 09 Jul 2026 Read time

A new deterministic spectastic enforce command: read 041's .spectastic/profile.json marker, run a data-driven category detector over the project's config, compare against the profile's required categories (a new enforce field in spectastic-profiles.json), and exit 1 when a hard-gate profile has a gap. Biggest risk is detection false-negatives (a project enforces a category by a means we don't recognise) — mitigated by a soft default and a broad, extensible signal table.

4 · Approach

Add a spectastic enforce [path] subcommand. It loads the marker (041) and the profile manifest, runs a detectTooling(cwd) that walks a data table of (config signal → category, ecosystem) over the project root, and diffs the covered categories against the profile's enforce.required. Output lists covered / missing categories; the exit code follows the profile's gate severity. FR-006 threads the same detector into 041's compose step (tailor the AGENTS.md gate section); FR-007/FR-008 are command-markdown edits so the plan/principles verbs read the marker.

6 · Decisions

D-001 · The gate is a command, not a validate rule

Status
Accepted
Context
The validate engine parses spec-html and never sees project config (rules/index.ts).
Decision
Ship spectastic enforce [path]; the 031 pre-commit gate can invoke it (FR-005).
Consequences
+ Sees the real project; returns an exit code. + Lives at the git boundary (P-8). − A new command surface to test.

D-002 · Detection is a data-driven signal table

Status
Accepted
Context
Seven ecosystems, six categories; the mapping is broad and will grow.
Decision
A detect.ts const table of { ecosystem, signal (file or file+contains), category }; detectTooling(cwd) returns the set of covered categories. A category is covered if any signal matches.
Consequences
+ Extending detection is a data edit. − Detection is a heuristic; false-negatives possible → soft-fail default (D-003).

D-003 · Severity scales with the profile

Status
Accepted
Context
A false gap must not break a low-rigor project; a real gap must fail a high-rigor one.
Decision
enforce.gate per profile: none (Lean, no-marker) → exit 0; soft (Standard) → warn, exit 0; hard (Verified/Enterprise) → exit 1 on any gap.
Consequences
+ Proportionate. + The dial the user already chose sets the strictness. − Two exit-code paths to test (SC-003).

D-004 · spectastic-profiles.json gains an enforce field

Status
Accepted
Context
FR-003: required categories are policy, and policy is data (041 D-001).
Decision
Each profile carries enforce: { gate, required: Category[] }. The 041 loader parses it (fail-safe to none).
Consequences
+ Adding a category to a profile is a data edit. − One manifest-schema addition; keep the loader backward-compatible.

D-005 · Should/may items reuse existing seams

Status
Accepted
Context
FR-005 (hook), FR-006 (compose gap-fill), FR-007/8 (verb markdown) are additive.
Decision
FR-006 threads detectTooling into 041's compose.ts (tailor the AGENTS gate lines). FR-005 appends an enforce line to 031's generated hook. FR-007/8 edit the plan/principles command markdown to read the marker.
Consequences
+ No new architecture. − FR-005 spike (hook chaining) verified during implement; the AI-verb markdown is advisory (T-009), not a guarantee — acceptable for should/may.

9 · Complexity tracking

Detection is deliberately a shallow heuristic, not a build-system parse. Justified: a precise "is this category truly enforced" oracle would require running the toolchain; the shallow signal + soft default for lower profiles is a proportionate proxy that stays deterministic and fast (NFR-001/002).
