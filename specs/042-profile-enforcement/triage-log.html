042's deterministic detection + policy live in the CLI, not the core kernel

Implementation code

Debugging a placement inconsistency surfaced while reviewing 043, root cause was drift from the fat-core / thin-CLI convention — 042's pure detection (SIGNALS, detectTooling, detectEcosystems) and policy diff (evaluateEnforcement) sit in the CLI package though they're deterministic kernel logic; fixed by moving them to @spectastic/core and keeping only the commander registration CLI-thin; regeneration passes — behaviour is correct, the fix is code placement, not an upstream gap.

Expected
Deterministic logic lives in @spectastic/core (every verb's core is there); the CLI is a thin wrapper that registers the command and calls core — and P-8: a guarantee belongs in the kernel.
Actual
packages/cli/src/commands/init/detect.ts (signal table + detectTooling/detectEcosystems) and enforce.ts's pure evaluateEnforcement are CLI-local; three CLI files (init.ts, enforce.ts, gitignore.ts) import detect from there.
Diagnosis
042 shipped correct behaviour but placed its deterministic pieces in the CLI. The convention (fat core / thin CLI) isn't written as a principle or a validate rule, so nothing caught the drift — and 041, 042, and 043's first pass all drifted the same way. Behaviour-neutral; purely organisational (NFR-001 "deterministic core" is met either way, but the kernel isn't its home).
Fix
Move the signal table + detectTooling/detectEcosystems and evaluateEnforcement (+ the shared EnforcementCategory/EnforceGate/Signal types) to packages/core/src/ with tsup entries + package.json exports; repoint the three CLI importers; keep registerEnforce CLI-thin. Mirrors the 043 review fix (0cb5330). No behaviour change; tests move with the code.
Fixed
Detection and the policy diff live in the kernel — packages/core/src/enforce/{detect,policy,types}.ts — and packages/cli/src/commands/enforce.ts imports them, so the CLI is the thin edge the fat-core convention asks for.
Deep dive — the convention isn't written down (surfaced, not promoted)

No cross-spec contract; no hotfix. The recurrence is the real signal: 041, 042, and 043-as-first-authored all put deterministic logic in the CLI, because "fat core / thin CLI" lives only as an unwritten habit — not a principle, not a validate rule, not a lint boundary. The immediate fix is this implementation move for 042. Whether to prevent recurrence — a one-line convention in CLAUDE.md, or an architectural boundary check (e.g. an ESLint rule that CLI command modules may only register + delegate) — is a separate, higher-layer question surfaced here, not silently promoted into this card's scope. 043's own core logic now sits correctly in @spectastic/core/gitignore; this card brings 042 in line.

An event-driven service is silently exempt from contract-first at every tier

Spec upstream

Debugging why a broker-only backend never sees the contract gate, root cause was FR-014 defining "detectable public interface" as an HTTP/RPC framework dependency, so INTERFACE_SIGNALS carries no message broker and exposesInterface() returns false; fixed by amending FR-014 to admit event-driven interfaces; regeneration fails — any session implementing today's FR-014 rebuilds the same HTTP-only signal list, so the gap is upstream of the code.

Expected
A service that publishes messages to Kafka/AMQP/NATS/Pulsar/SQS/SNS/Service Bus/Pub Sub exposes a public interface, so at verified and enterprise it owes a checked-in contract — an asyncapi.yaml, which isContractFile() already accepts.
Actual
exposesInterface() matches only HTTP, GraphQL and gRPC dependency names, so the antecedent fails, evaluateEnforcement marks contract-first covered ("nothing to contract"), and no warning is emitted — the gate deliberately fails safe on the antecedent so CLIs and batch jobs aren't false-failed.
Diagnosis
FR-014 enumerates only HTTP/RPC frameworks and treats the residual as an accepted ceiling ("SHOULD be recorded as the honest ceiling rather than closed by widening the gate into false failures"). That framing is right for an unlisted HTTP framework and wrong for an entire architectural style: the tool recognises the answer (AsyncAPI) to a question it can never ask. Correctly distinct from FR-010 — this is not undetectable, merely undetected.
Fix
specs/042-profile-enforcement/ — a /spectastic.propose MODIFY on FR-014 admitting message-broker dependencies as interface signals, then the matching INTERFACE_SIGNALS entries. Widen the antecedent only; leave the fail-safe posture intact. Sibling copy fix: the standard-tier seeded principle in spectastic-profiles.json names OpenAPI/JSON Schema/typed signatures and omits AsyncAPI, .proto and GraphQL SDL.
Fixed
Closed by 073: EVENT_INTERFACE_SIGNALS adds broker and managed-bus clients across six ecosystems, and FR-014 was amended by proposal to widen the antecedent — advisory-only, so no existing verdict moved.
Deep dive — deferred functionality exposed + a cross-spec copy inconsistency

Scope-deferred functionality exposed — surfaced, not promoted. FR-014 does not omit brokers by oversight; it records the miss as a deliberate ceiling. So this card asks for that ceiling to be revisited, not for the gate to be quietly widened. The counter-argument FR-014 anticipated still applies and must be answered by the proposal: a broker client is often a transitive or infrastructural dependency, and the signal cannot distinguish publishing a topic from consuming one — so widening the antecedent risks false failures in the direction FR-014 was written to prevent. That trade is a requirement-level decision, which is why this sits at spec and not implementation.

Cross-spec (copy only). The seeded principle text lives in spectastic-profiles.json, owned by 041's profile catalog, while the gate is 042's. Amending FR-014 without the principle's format list leaves the two saying different things about what counts as a contract. Small, but it should land in the same batch as a data/content delta.

No hotfix required — the failure mode is a silent pass, not a break. Surfaced by the audit in docs/event-driven-interface-considerations.html, which owns the full audit (D-001, D-002).

Contract detection misses most ecosystem-conventional layouts

Spec upstream

Debugging why a project with a perfectly good contract can still fail contract-first, root cause was detectContract's four-directory, one-level search — scoped that way by NFR-002's shallow-detection invariant and the adversarial narrowing recorded with FR-014; fixed by widening the searched paths to conventional layouts; regeneration fails — the narrow scan is what the spec describes, so a fresh session rebuilds it.

Expected
A checked-in contract is found where its ecosystem conventionally puts it — a project should not have to rearrange itself to be detectable.
Actual
detectContract lists the root plus one level into api/ proto/ schema/ contracts/, no recursion. It misses Gradle/Maven's src/main/proto/** (the protobuf-plugin default), multi-module <module>/src/main/proto/, buf workspaces (proto/<module>/v1/), Go's api/proto/v1/, Spring's src/main/resources/, the openapi/ protos/ graphql/ directory names, and any AsyncAPI document not literally named asyncapi.{yaml,yml,json}.
Diagnosis
The four-dir/one-level reach was a deliberate compromise — NFR-002 asks detection to stay shallow and sub-500 ms, and the contract-dir widening was already scoped narrowly on adversarial review. But "shallow" was calibrated against root manifests, not against build-tool conventions that are three levels deep by default. The result is a hard gate that can fail a compliant project.
Fix
specs/042-profile-enforcement/ — a /spectastic.propose widening the contract search paths to conventional layouts (bounded, so NFR-002's budget still holds), and preferring an explicitly declared contract path over filesystem inference where one is available. Benchmark against NFR-002's 500 ms budget as part of the change.
Fixed
Closed by 073: CONTRACT_SEARCH_PATHS widened from four directories to seventeen named conventions, plus bounded MODULE_TREE_ROOTS expansion for buf/Gradle trees. Residual, recorded not hidden: isContractFile still matches only a literal asyncapi.{yaml,json} filename, so an AsyncAPI document under another name is still missed — outside this card’s Fix, and a separate widening if it ever bites.
Deep dive — an NFR trade, plus a false-positive the same mechanism creates

The fix trades against NFR-002, which is why it is a requirement-level change rather than a code tweak: every added directory or level costs a readdirSync, and NFR-002 sets both a posture (shallow) and a budget (well under 500 ms). A proposal should widen by named convention rather than by general recursion, so the cost stays bounded and predictable.

The same mechanism produces a false positive in the other direction. Detection by file presence cannot tell a contract a project publishes from one it consumes: a Rust crate using progenitor, or any project vendoring an upstream .proto to generate a client, checks in a contract for an API it does not own — and is marked covered. Only a declaration can distinguish the two, which is the second half of the fix above and the reason it is worth doing alongside the path widening rather than after it.

No hotfix required. Surfaced by the same audit as T-002 (docs/data-model-contract-considerations.html, §6).

A standard-profile project declares contract-first as its posture, and nothing checks it

Cross-spec upstream

Debugging why the contracts posture ladder and the enforcement floor disagree, root cause was cross-spec: 041 seeds the axis value contract-first at standard, while this spec only admits the contract-first category to enforce.required at verified — so a standard project is told it holds a posture no gate enforces; fixed by deciding, in a proposal, which of the two moves; regeneration fails — neither spec states that the axis and the floor must agree, so any future session would re-seed exactly this mismatch.

Expected
A profile's declared contracts posture and the enforcement floor at that tier describe the same commitment, or the divergence is stated deliberately.
Actual
Measured across the manifest: lean → axis informal, not required (consistent); standard → axis contract-first, not required; verified → axis contract-checked, contract-first required; enterprise → axis versioned+governed, contract-first required.
Diagnosis
Two specs own two halves of one idea and neither owns their relationship. 041 landed the axis as advisory vocabulary — a pure data delta, with the machine teeth explicitly deferred — while 042's FR-014 set the floor at verified. Both are internally correct; together they let a tier advertise a posture with no gate behind it. Note the axis runs ahead of the floor at verified and enterprise too, but there it is arguably the intended aspirational ladder; at standard the gap is a full rung with nothing at all beneath it.
Fix
A proposal, not a patch — the two credible resolutions have different costs and only the owner should pick: (a) lower the standard axis to informal, making the ladder describe what is enforced; (b) admit contract-first to the standard floor, which would newly gap real standard projects; or (c) state explicitly in 041 that axes are aspirational and may lead the floor, which legitimises the gap at every tier. Target specs/041-init-profiles/spec.html or specs/042-profile-enforcement/spec.html depending on the choice.
Deep dive — cross-spec contract

Shared contract: the meaning of a contracts axis value. 041 owns the vocabulary (informal → contract-first → contract-checked → versioned+governed); 042 owns which enforcement categories are required per tier. Nothing binds the two, which is why this reads as a disagreement rather than a bug in either.

Do not resolve by patching the manifest. Editing either value silently would pick one of three answers without recording why, and the drift-guard test in packages/cli/test/init/profiles.test.ts pins the current per-tier values deliberately — it would have to move in the same change, which is exactly the signal that this needs a proposal.

Timing. 074 is about to define what contract-checked means mechanically at verified. Resolving this card before 074 lands is worth considering, since 074 sharpens the verified rung and would otherwise be built on a ladder whose lower rung is known to be unbacked. No hotfix required — the mismatch is advisory-only today and breaks nothing at runtime.

Surfaced by the same audit as T-002 and T-003 (docs/data-model-contract-considerations.html), which flagged it in passing as worth a triage.
