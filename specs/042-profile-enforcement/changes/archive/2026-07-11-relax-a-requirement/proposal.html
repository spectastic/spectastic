Change proposal · 042-profile-enforcement

Relax a requirement — per-category enforcement waivers

A team may opt out of a floor category — but only out loud: a waiver with a reason and an expiry that warns, never a silent skip, and never for the categories that matter most.

Status Applied Change ID 2026-07-11-relax-a-requirement Spec 042-profile-enforcement Author Brian Corbin · @briancorbinxyz Created 11 Jul 2026 Targets 2 modified (FR-004, NFR-001) + 3 added (FR-011, FR-012, FR-013) + 1 data/content delta (manifest enterprise.enforce.unwaivable) Read time

Today the enforcement floor is all-or-nothing: a team on the verified/enterprise hard gate that wants to opt out of one category (say observability because it ships metrics over a push exporter with no local endpoint to detect) has only three coarse escapes — cover it with a tool it doesn't use, drop to a lower profile wholesale, or delete the marker and disable all enforcement. Each is the silent gate-lowering P-9 forbids. This change adds the missing middle: a per-category waiver in spectastic.json (enforce.waivers[]) carrying a {category, reason, until, owner}. An active, well-formed waiver demotes its category from a blocking failure to an advisory warning surfaced as its own relaxed tally — never folded into the passes, never silent (MODIFY FR-004, ADD FR-011). Justification and expiry are part of the shape, not etiquette: a missing/boilerplate reason or a past/over-horizon date is rejected, and a waiver auto-expires so "ignore forever" is impossible (ADD FR-013). The highest-risk categories stay un-waivable — enterprise cannot relax security or supply-chain (ADD FR-012 + a data/content delta). Secure by default throughout: absent, malformed, expired, or un-waivable → the gate fires. A coupled P-9 amendment (separate /spectastic.principles change, flagged below) names the waiver as the sanctioned "recorded" form.

Relax a requirement — per-category enforcement waivers

Applied

1 · Intent

042 made the profile floor real by gating it. But a floor with no honest relief valve manufactures its own defeat: the only ways to skip a single category today are to fake coverage of a tool you don't run, lower the whole profile (dropping a bundle of unrelated principles and categories with it), or remove the marker and turn the gate off entirely. Every one of those is the quiet convenience P-9 exists to prevent — and because they are the only options, the floor pressures teams toward exactly the reflex it was built to stop. The gap is a legitimate, narrow, recorded opt-out.

The governance literature converged on this shape long ago and it is worth borrowing wholesale. A compliance baseline is tailored to what applies, and every exclusion carries a justification (a Statement of Applicability marks each control applicable or not-applicable-with-reason). Policy-as-code engines count an exception as its own line in the report, not a silent pass, and disable exceptions by default while forbidding them for the highest-risk controls. Inline security-scanner suppressions bake the reason — and, at their best, an expiry date — into the token itself, because a justification that is merely conventional rots into boilerplate ("comply-or-explain" fails exactly when the explanations go unread). This proposal is that pattern, sized to spectastic: a waiver is a first-class, reason-bearing, auto-expiring, owned record; a relaxed category still warns; and some categories cannot be relaxed at all.

Coupled principles amendment (flagged, not folded). P-9 today says weakening a gate "MUST be … explicit and recorded … never a silent convenience" but names no mechanism. A separate forward-only /spectastic.principles change amends P-9 to name the structured waiver as that sanctioned recorded form and to state the enterprise un-relaxable floor (security + supply-chain). It is deliberately not a delta here — principles ship through their own kernel apply path (spec 030), and this proposal's deltas are all against 042. Landing order: this proposal, then the P-9 bump.

2 · Scope

In scope

  • MODIFY FR-004: the exit-code rule accounts for waivers — a required-but-uncovered category with an active, well-formed, waivable waiver degrades to an advisory warning (a distinct relaxed tally), rather than a hard exit 1.
  • ADD FR-011: the waiver artifact — spectastic.json enforce.waivers[] of {category, reason, until, owner}, all fields required, secure-by-default.
  • ADD FR-012: un-relaxable categories per profile (enforce.unwaivable); enterprise forbids security + supply-chain; a waiver naming one is inert and flagged.
  • ADD FR-013: the enforce-waiver-well-formed validate scan (error severity) + enforce failing closed on a malformed/expired waiver at runtime — the two-guard, kernel/CI enforcement of P-8.
  • Data/content delta: add enterprise.enforce.unwaivable: ["security","supply-chain"] to spectastic-profiles.json; no enforce.required array changes.
  • Core machinery (§6): the EnforceWaiver type, a fail-safe loadWaivers, the evaluateEnforcement waiver/expiry/unwaivable resolution with a relaxed/expired result, the CLI tally, the validate scan, fixtures + tests.

Out of scope

  • A dedicated human-readable waiver register artifact (a Statement-of-Applicability-style enforce-waivers.html). The machine-read spectastic.json section is the v1 source of truth; a rendered register with its own lifecycle is a larger, separate effort.
  • A dedicated separation-of-duties workflow — an approver distinct from the requester, tiered by risk. For v1 the waiver lives in git-tracked spectastic.json, so the PR review is the approval surface and the owner field records who accepted the risk (stated in FR-011); a first-class approver-vs-requester workflow is the deferred enhancement.
  • Surfacing active waivers in verify.html as part of the per-spec proof trace. This change makes enforce and validate waiver-aware; the verify-view trace is a follow-on.

3 · Approach

The waiver lives in the downstream project's spectastic.json, as a new typed enforce section — the fourth instance of the sanctioned section-per-feature config pattern (git, decider, models already follow it; a typed feature section with its own loader is the approved shape, not the "general settings bag" that convention forbids). It is not in the .spectastic/profile.json marker: the marker is tool-written state locked to {profile, schema}, whereas a waiver is a human decision — owner, reason, expiry — that belongs in the git-tracked, PR-reviewable file.

The runtime change reuses machinery 042 already has. evaluateEnforcement (packages/core/src/enforce/policy.ts) already demotes a gap to a warning for the structurally-undetectable case (FR-010); a waiver is the second demotion path, resolved per gap in a fixed order: (1) structurally undetectable in every ecosystem → warn (FR-010, wins first — it is the honest state); (2) else an active (until ≥ now), well-formed waiver whose category is not unwaivable → relaxed (warn); (3) else a waiver exists but is expired → expired and falls through to blocking; (4) else → missing. The exit rule is unchanged in spirit — gate==='hard' && missing.length > 0 — but relaxed never counts toward missing, so it never blocks, while expired does. An injectable now keeps it deterministic and filesystem-only.

Two guards, never one, keep a waiver honest — the P-8 "guarantee lives in the kernel or CI" split. At runtime, loadWaivers is fail-safe: any malformed entry is silently dropped, so a broken waiver can never accidentally disable a gate — a dropped waiver just means the category keeps gating. At the git/CI boundary, a new enforce-waiver-well-formed validate scan is fail-loud: it reads spectastic.json and errors on an unknown category, a category not in the profile's floor (a dead waiver), a category that is unwaivable, an empty or boilerplate reason, or a until that is missing, invalid, already past, or more than 365 days out. Neither guard trusts the waiver blindly; together they make "my waiver is broken" fast, specific feedback while a broken waiver never once weakens the floor.

The un-relaxable set is data, per-profile in spectastic-profiles.json — matching 042's "the floor is data" convention. Enterprise ships unwaivable: ["security","supply-chain"]; verified ships none (its lower-rigor floor is fully waivable); a waiver naming an unwaivable category is inert at runtime and flagged by validate.

4 · Deltas

One <spec-delta> per requirement touched, plus one data/content delta against the manifest. All target the enforcement topic on 042 — a single intent, no split warranted.

What changes: the exit-code rule now recognises an active, well-formed, waivable waiver as an advisory demotion (a distinct relaxed tally), not a hard failure — while expired, malformed, or un-waivable waivers still block.

enforce MUST exit non-zero when a required category is unmet for a hard-gate profile (Verified/Enterprise); Standard MUST warn but exit 0; Lean and no-marker MUST exit 0 — so a pre-commit/CI gate can block precisely where it should. A required-but-unmet category that carries an active, well-formed waiver (FR-011) whose category is not un-relaxable for the profile (FR-012) MUST degrade to an advisory warning and MUST be reported as a distinct relaxed count, never folded into the covered categories — so a relaxed floor is always visible, never silent. A waiver that is expired, malformed, or names an un-relaxable category MUST NOT relax its category: the gate fires as if no waiver were present.

Rationale — the honest middle between "cover it" and "turn it off"

Without a per-category demotion, a team's only opt-out is to lower the whole profile or delete the marker — the silent gate-lowering P-9 forbids. Making the relaxed category a separate reported tally (rather than counting it as covered) is the load-bearing honesty: the floor a profile promises stays legible even when one category is deliberately relaxed. The secure-by-default clause (expired/malformed/unwaivable → still blocks) means a waiver can only ever weaken the gate when it is complete and current.

What's added: the waiver artifact and its required shape, secure-by-default.

A downstream project MAY relax a single enforcement category by declaring a waiver in spectastic.json under enforce.waivers[]. Each waiver MUST carry four fields: category (a valid enforcement category present in the project's profile floor), reason (a non-empty, non-boilerplate justification), until (an ISO YYYY-MM-DD expiry no more than 365 days in the future), and owner (who accepted the risk). A waiver whose until has passed MUST auto-expire — its category resumes gating with no further action. The mechanism MUST be secure-by-default: an absent enforce section relaxes nothing, and a waiver missing any field, carrying a boilerplate reason, or bearing an invalid/expired/over-horizon date MUST NOT relax its category. Expiry MUST be evaluated against an injectable clock (default: the current date) so a fixture project pins the clock for reproducible CI (NFR-001). A waiver is a change to git-tracked spectastic.json, so its PR review is the v1 approval surface — a distinct approver-vs-requester workflow is deferred (TBD-waiver-approval), and the owner field records who accepted the risk.

Rationale — reason and expiry are shape, not etiquette

Justification and expiry baked into the token achieve near-total compliance; the same fields left conventional rot into boilerplate (the comply-or-explain failure mode). A mandatory expiry with a hard horizon turns "ignore forever" into a dated decision that must be renewed or fixed — the single most-cited control that keeps an exception mechanism from becoming a footgun. The section-per-feature home (enforce.waivers) matches the established git/decider/models config shape.

What's added: per-profile un-relaxable categories, so the highest-risk floor cannot be waived.

A profile MAY declare an enforce.unwaivable set of categories that a waiver cannot relax. The enterprise profile MUST mark security and supply-chain un-relaxable. A waiver naming an un-relaxable category MUST be inert — its category keeps gating regardless of the waiver — and MUST be flagged by validation (FR-013) so the author learns the waiver has no effect rather than assuming relief.

Rationale — some controls are not tailorable

Mature governance forbids waiving the highest-risk controls even as it allows tailoring the rest — the exception mechanism itself is gated. Enterprise's security and supply-chain categories are the two whose silent relaxation would be most regrettable, so they are removed from the waivable set entirely; verified, a lower-rigor tier, keeps its whole floor waivable. Verified is deliberately the lighter hard-gate tier — full waiver latitude, including over security and supply-chain, is precisely what distinguishes it from enterprise; a team that needs an un-waivable security floor chooses enterprise, and the tier choice is itself the recorded, explicit decision. Declaring the set as per-profile data (not code) keeps it on 042's "the floor is data" footing and lets the set evolve without a code change.

What's added: the two-guard enforcement — a fail-loud validate scan plus fail-closed runtime — so a broken waiver is caught early and never silently weakens the gate.

validate MUST include an enforce-waiver-well-formed check that reads the project's spectastic.json and reports, at error severity, any waiver that: names an unknown category, names a category not in the project profile's floor (a dead waiver), names an un-relaxable category (FR-012), carries an empty or boilerplate reason, omits owner, or bears a until that is missing, malformed, already past, or more than 365 days out. Independently, enforce MUST fail closed: a malformed or expired waiver is ignored at runtime (the category keeps gating), never trusted. The two guards are complementary — validate gives fast, specific authoring feedback; enforce guarantees a broken waiver can never disable a gate even if validation is skipped.

Rationale — the guarantee lives in the kernel or CI (P-8)

A waiver is a gate-weakening instrument, so its well-formedness is exactly the kind of invariant P-8 requires be machine-checked, not left to prose. The scan is a folded repo-file check (it reads project state, so it joins the skill-metadata / no-internal-id-in-copy family of CLI scans rather than the spec-HTML schema rules). Surfacing a silently-expired waiver as an error is deliberate: an expired waiver that still sits in the file is a stale decision the author should remove or renew, not leave to rot.

What changes: the determinism guarantee is scoped to filesystem + an injected clock, since a waiver's mandatory expiry (FR-011) makes an active waiver a function of the date. From the adversarial pass: without this, a green fixture would turn red purely by the passage of time, contradicting "so CI drives them with fixture projects."

enforce and detection MUST be deterministic given the filesystem and an injected clock — no network, no model — so CI drives them with fixture projects. Where a result depends on the current date (a waiver's expiry, FR-011), the date MUST be an injectable parameter (default: the system date) so a fixture pins it for a reproducible run.

Rationale — bounded, declared clock dependency

Auto-expiry is the anti-rot control, but it makes an active waiver time-dependent, which would otherwise break the "fixture projects drive CI" promise. Scoping determinism to the filesystem and a supplied clock keeps the guarantee honest: the only non-filesystem input is a clock the caller controls, so a fixture that pins the date is fully reproducible, and production reads the system date as expected. This is the same injectable-now discipline the policy layer already uses for testability.

What's added: enterprise.enforce.unwaivable: ["security","supply-chain"] in spectastic-profiles.json. A data/content delta (target names the manifest key, embeds a <spec-diff>, no requirement-body change). No enforce.required array is touched — purely additive and revert-safe.

enterprise.enforce.unwaivable: ["security", "supply-chain"] (verified.enforce.unwaivable: absent — its whole floor stays waivable)
Rationale — why enterprise only

The un-relaxable floor is a rigor concern that earns its place at the top tier: enterprise is where security and supply-chain are hard-gated in the first place, and where silently waiving them is most regrettable. Verified carries neither in an un-relaxable set, so a verified project retains the full waiver latitude. The bundle (_bundled/spectastic-profiles.json) is rebuilt so the shipped manifest matches.

5 · Risk register

From the adversarial pass (auto-fired: FR-004 is must-tier, and three requirements are added). Three findings, all dispositioned in the review interview; each records the human who committed the transition.

Marking security + supply-chain un-relaxable at enterprise only leaves Verified — itself a hard-gate tier — able to relax its two highest-risk categories with a self-authored, self-owned waiver for up to a year.

The data/content delta enterprise/enforce-unwaivable and its §3 note: "verified ships none (its lower-rigor floor is fully waivable)", against live FR-004, which hard-gates Verified too.

Rejected. The asymmetry is deliberate, not an oversight: Verified is the lighter hard-gate tier, and full waiver latitude is exactly what distinguishes it from Enterprise. A team needing an un-waivable security floor chooses Enterprise — and that profile choice is itself the explicit, recorded decision P-9 asks for. FR-012's rationale now states this defense; the un-relaxable set can still be extended to Verified later as data, without a code change, if the tier's meaning shifts.

A waiver's mandatory time-based expiry makes enforce's exit code a function of the wall-clock date, so the same fixture project exits 0 today and 1 once until passes — with no filesystem change — contradicting NFR-001's "deterministic and filesystem-only … so CI drives them with fixture projects."

Live NFR-001 vs. the §3 rule until ≥ now: an injectable now rescues unit tests, but a real pre-commit/CI invocation reads the system clock, so a green build turns red purely by time.

Mitigated. NFR-001 is MODIFY'd (§4) to scope determinism to filesystem + an injected clock: where a result depends on the date (waiver expiry), the date is an injectable parameter defaulting to the system date, so a fixture pins it for a reproducible run. Expiry stays a runtime demotion (D3 intact), but the clock dependency is now bounded and declared rather than a hidden contradiction — the same injectable-now discipline the policy layer already uses. FR-011 carries the injectable-clock clause.

Deferring separation of duties leaves v1 a purely self-approving gate-lowering tool — one developer writes the reason, names themselves owner, and relaxes a hard gate for up to a year with no second party — thinner than the P-9 "recorded, never a silent convenience" bar the proposal invokes.

§2 Out of scope, defer-to="TBD-waiver-approval", against P-9: "recorded" without "reviewed" is weaker than the framing implies.

Mitigated. The deferral stands, but the review surface is now named, not unstated: the waiver is a change to git-tracked spectastic.json, so the PR review is the v1 approval surface — recorded and reviewed by whoever approves the change. FR-011 and the §2 out-of-scope item now say so explicitly, making the self-approval limit an honest P-8 ceiling rather than a hidden gap; a first-class approver-vs-requester workflow stays TBD-waiver-approval.
