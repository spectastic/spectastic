Widen the contract-first interface antecedent

FR-014 records today's narrow signal set as an accepted ceiling. The ceiling moves before the code does.

Status Applied Change ID 2026-08-01-widen-interface-detection Spec 042-profile-enforcement Source 073-interface-detection-widening, D-005: this amendment is that spec's own task one, ordered before any detection code lands. Author Brian Corbin · @briancorbinxyz Created 01 Aug 2026 Targets 1 modified (FR-014) Read time

FR-014 gates contract-first on a detectable public interface, and today that antecedent recognises only HTTP, GraphQL and gRPC — a service whose entire surface is broker topics reads as having nothing to contract, at every tier including enterprise. It also has no notion of a design's own declaration overriding a filesystem/dependency guess, which is the only mechanism that can tell a publisher from a consumer given the same client library. This MODIFIES FR-014 to recognise event-driven interfaces (advisory-only, so no project's verdict changes), and to make a design's declared interface/contract state outrank inference in both directions. The residual ceiling — a mechanism outside the named signal set — stays honestly recorded, narrower than before but not eliminated. The code implementing this (073's own tasks.html) follows once this amendment lands, per 073 D-005.

Widen the contract-first interface antecedent

Applied

1 · Intent

042's own FR-014 already names the gap it has: "an interface exposed via a framework outside the signal set is silently exempt... SHOULD be recorded as the honest ceiling." Two considerations surveys (data-model/contract, and its event-driven-interface follow-on) found that ceiling is wider than the sentence implies — the antecedent has no message broker at all across six ecosystems, and separately, contract discovery only reaches four directories one level deep. This proposal amends FR-014 for the first miss (the antecedent) and the declaration-precedence fix both misses share; contract discovery's path widening is a separate FR (FR-002) 073 touches directly in code, since FR-002 doesn't assert a ceiling the way FR-014 does and needs no amendment to widen.

The amendment is deliberately narrow: it changes what FR-014 asserts, not what the code does today. 073's own tasks.html is where the detection code actually changes; this proposal exists because P-6 forbids that code crossing a ceiling this Accepted spec still asserts, without the spec moving first.

2 · Scope

In scope

  • MODIFY FR-014: widen the interface antecedent to recognise event-driven (message-broker/managed-bus) dependencies, at advisory severity only; add that a design's declared interface/contract state outranks dependency/filesystem inference in both directions; narrow the residual-ceiling sentence to match.

Out of scope

  • The actual detection code — broker signals, the widened contract-path set, the declaration-precedence implementation. Tracked in 073's own tasks.html, which this amendment unblocks.
  • Promoting the event-driven signals from advisory to the hard floor once field evidence supports it.
  • Closing the residual ceiling entirely — an interface exposed through a mechanism outside the named signal set remains an honest, recorded gap, not a defect to chase into false failures.

3 · Approach

FR-014's antecedent gains a third branch — an event-driven interface, recognised the same way the existing two are (a dependency signal) — but reported through the existing per-category advisory mechanism (STRUCTURALLY_UNDETECTABLE, already proven twice) rather than the hard-fail path the HTTP/RPC/GraphQL/gRPC branches use. This is additive: a project that fails today keeps failing the same way; a project that was silently exempt now gets a warning it did not get before. No currently-passing project starts failing, which is what keeps this a widening and not a new hard requirement landing without its own interview.

The declaration clause is the part that generalizes past this one requirement: 073's D-004 finding is that dependency matching cannot separate a publisher from a consumer, or a project's own contract from one it vendored to generate a client. A design's declaration is the only place that distinction is knowable, so FR-014 now says explicitly that where one exists, it overrides inference — in both directions, since either a false "nothing to contract" or a false "already covered" is possible today.

4 · Deltas

What changes: the interface antecedent gains an event-driven (message-broker/managed-bus) branch, reported at advisory severity only via the existing per-category mechanism — never a hard fail on that branch alone. A design's declared interface/contract state, where present, is stated to outrank inference in both directions. The residual-ceiling sentence is narrowed to "a mechanism outside the named signal set," since the broker branch closes the specific gap the original sentence named.

The contract-first category MUST be interface-gated: it is a gap only when the project exposes a detectable public interface — an HTTP/RPC framework declared as a dependency (e.g. express/fastify/@nestjs, flask/fastapi/django, spring-web/jakarta.ws.rs, gin/echo, actix-web/axum), a gRPC/Protobuf toolchain, a GraphQL server, or an event-driven interface — a message-broker or managed-bus client (e.g. Kafka, AMQP/RabbitMQ, NATS, Pulsar, SQS/SNS, EventBridge, Service Bus, Redis streams) declared as a dependency — and no checked-in contract is present. Detection of an event-driven interface alone, with no HTTP/RPC/GraphQL/gRPC signal also present, MUST report the gap at advisory severity via the existing per-category mechanism (the same one that already demotes an undetectable stack under FR-010) and MUST NOT hard-fail a profile floor on that branch alone, until the signal set is deliberately promoted — this is a distinct mechanism from FR-010's stack-cannot-express-this-category demotion: here the category plainly applies (an interface was detected), and only the detecting signal's strength is weaker.

Where a design (per 069/070) declares an interface's shape or a contract's path, that declaration MUST take precedence over inference from dependencies or the filesystem, in both directions: a declared contract path establishes one is owed even where dependency or filesystem inference alone would find none, and a declaration of shape="none" establishes none is owed even where a broker dependency is present. This is conditional on a design existing and declaring — a project with no spectastic design gets inference only, exactly as before.

A project with no detected interface — by dependency inference or an overriding declaration — MUST be treated as covered for contract-first (there is nothing to contract) — MUST NOT hard-fail — so a CLI, batch job, or internal library is never false-failed for lacking an API schema. This is categorically distinct from FR-010 and does NOT override it: FR-010 warns when a category that does apply cannot be expressed in the project's stack (an applicable-but-undetectable gap); contract-first's applicability is itself conditional — "no interface detected" means the category may not apply at all, not that an applicable category is invisible — so the correct posture is exempt, not warn. Warning on every interface-less project (each CLI, batch job, and library) would be the warn-washing FR-010's demotion is expressly not meant to cause. Because the gate fails safe on the antecedent, it requires no FR-010 undetectable entry; the residual is that an interface exposed via a mechanism outside the named signal set is silently exempt (a false-negative), which SHOULD be recorded as the honest ceiling rather than closed by widening the gate into false failures.

Rationale — fail safe on "does this even expose an interface?"

The other eight categories are unconditionally applicable at their tiers; contract-first is conditional on the project's nature. The choices are: hard-require it everywhere (false-fails interface-less projects — the P-9 reflex), make it advisory everywhere (a weaker, non-gating category for projects that plainly do expose an HTTP/RPC surface), or gate it on a detectable antecedent with a graduated signal strength. Interface-gating with an advisory-only event-driven branch is the option that keeps the HTTP/RPC/GraphQL/gRPC case a real hard gate, adds a genuinely new signal for event-driven services without inventing a false confidence in it, and never false-fails where no interface is detected at all. The trade is a persisting false-negative on unlisted mechanisms — deliberately preferred over a false-positive, because a false failure trains teams to disable the gate, while a false-negative is a missed nudge the principle (advisory, at standard) still covers.

5 · Risk register

Auto-fired: FR-014 is must-tier. Self-reviewed against the draft delta above (no subagent dispatch for this pass); all three findings dispositioned inline.

"Advisory-only" language sitting inside a requirement that otherwise reads as a hard MUST invites a future reader to think the whole contract-first gate has been softened to advisory — exactly the P-9 regression the design's own §10 argues against.

Design 073 §10: "Advisory-first is not a P-9 softening... No project that fails today starts passing." The risk is the WORDING failing to carry that distinction as clearly as the design reasons it.

Mitigated. The delta scopes the advisory clause explicitly to "detection of an event-driven interface alone, with no HTTP/RPC/GraphQL/gRPC signal also present" — so a reader cannot generalise it to the pre-existing branches, which stay exactly as hard as they are today.

FR-014 already carries one explicit distinction from FR-010 (interface-gating vs. stack-undetectable); adding a second advisory mechanism (event-driven-only demotion) risks reading as the same thing as FR-010's demotion, confusing an implementer about which applies when a category is both interface-gated and stack-undetectable.

Existing FR-014 text: "This is categorically distinct from FR-010 and does NOT override it." The new clause needed the same discipline applied to itself.

Mitigated. The delta states directly that the event-driven advisory path "is a distinct mechanism from FR-010's stack-cannot-express-this-category demotion: here the category plainly applies (an interface was detected), and only the detecting signal's strength is weaker" — naming the difference rather than leaving a reader to infer it.

Stating that "a design's declaration outranks inference" without qualification could be read as requiring every project to author a spectastic design to get an accurate contract-first verdict — overstating an optional escape hatch as a new precondition.

Design 073 §10: "The producer/consumer distinction is only solved for projects that declare... A project with no spectastic design still cannot be classified, and gets the advisory" — the design is explicit this is conditional, and the requirement text needed to be equally explicit.

Mitigated. The delta opens the clause with "Where a design... declares" and closes it with "This is conditional on a design existing and declaring — a project with no spectastic design gets inference only, exactly as before" — leaving no room to read it as a new universal precondition.
