Change proposal · 042-profile-enforcement

Give the contract-checked rung mechanical meaning

The profile axis has said contract-checked at verified since the axis landed. Nothing checked anything.

Status Applied Change ID 2026-08-01-contract-checked-rung Spec 042-profile-enforcement Source 074-contract-checked-tier, task one: the category's definition changes at verified and above, so the spec that owns it moves first. Author Brian Corbin · @briancorbinxyz Created 01 Aug 2026 Targets 1 modified (FR-002) Read time

The contracts profile axis ladders informal → contract-first → contract-checked → versioned+governed, and contract-checked has never meant anything a machine could evaluate — a verified project satisfies the floor by holding a file. This MODIFIES FR-002 so that at verified and above, holding a contract also requires a configured linter and a configured breaking-change differ. Three guards keep it honest: the signal is a declared configuration, never a bare dependency (coverage's precedent); a format whose tooling genuinely lacks one half reports advisory rather than hard-failing (AsyncAPI's diff story is thinner than OpenAPI's); and the condition is tier-gated, so no lean or standard project changes verdict. The recorded ceiling moves up one rung but does not disappear — detection still proves a check is configured, never that it passes or blocks a merge.

Give the contract-checked rung mechanical meaning

Applied

1 · Intent

041 landed a contracts axis whose verified value is contract-checked, explicitly as advisory vocabulary with the note that "the machine teeth stay TBD-contract-first-enforce". Those teeth landed for the first rung — a contract must exist — and the second rung has sat undefined since. A verified project today satisfies the contract floor by checking in a file nothing validates and nothing diffs, which is the distance between holding a contract and honouring one.

This proposal closes that distance at the requirement level only. The detection code is 074's own tasks.html; this exists because P-6 forbids the code implementing a floor the Accepted spec that owns the category does not describe.

2 · Scope

In scope

  • MODIFY FR-002: at verified and above, holding a contract also requires a configured linter and breaking-change differ; the signal is a declared configuration, never a bare dependency; a capability-limited format reports advisory; below verified nothing changes; the configured-≠-passing ceiling is stated.

Out of scope

  • The detection code, capability map, and per-contract reporting. Tracked in 074's own tasks.html, which this amendment unblocks.
  • Requiring that a differ actually blocks a merge rather than merely reporting — the same reported-versus-enforced ceiling every other category carries.
  • The rung above: versioning policy, deprecation windows, and an approval path for breaking changes.

3 · Approach

A second condition inside the existing contract-first category rather than a tenth category. The category already answers "does this project honour its interfaces?"; splitting that across two categories would make a project with a contract but no linter read as covered-and-missing simultaneously, and would need its own tier placement, waiver semantics and axis label for a distinction the contracts axis already draws.

Detection follows coverage's precedent exactly: match the declared configuration — a Spectral ruleset, a buf.yaml breaking stanza, an oasdiff or buf invocation in a CI definition — never a package-manifest entry. An installed linter that no configuration ever runs certifies nothing, and counting it would make the rung a formality. The capability carve-out is the honest asymmetry: Spectral's AsyncAPI ruleset covers 2.x while the request/reply story is 3.0, and event-diff tooling is thinner than OpenAPI's, so a format short of mainstream tooling reports advisory with the limitation named rather than failing a project for tooling that does not exist.

4 · Deltas

What changes: the contract-first clause gains a verified-and-above condition — a configured linter and breaking-change differ — with the declared-configuration signal rule, the capability-limited advisory carve-out, the explicit below-verified no-change guarantee, and the configured-≠-passing ceiling. Every other category's clause is untouched.

Detection MUST classify present enforcement categories — formatter · linter · type-checker · security · supply-chain · test-runner · coverage · observability · contract-first — from config/manifest signals across Python, JS/TS, Java, Go, Rust, Swift, and C++. For coverage, the signal MUST be a declared threshold or check (e.g. fail_under, a coverageThreshold block, a JaCoCo check rule), not a bare coverage library — because for coverage alone, presence of the tool does not imply a gate. Detection proves a coverage threshold is configured; it MUST NOT be surfaced as proof that a CI diff-gate blocks a coverage drop. For observability, the signal MUST be a metrics registry/exporter/starter dependency matched by its deliberate export name (e.g. micrometer-registry-prometheus, spring-boot-starter-actuator, prometheus/client_golang, @opentelemetry/exporter-prometheus, prometheus_client, the Rust prometheus crate), not a transitively-arriving core library or a tracing-only package (e.g. @opentelemetry/api). Detection proves an observability exporter is a declared dependency ("monitoring is possible"); it MUST NOT be surfaced as proof that the /metrics endpoint is wired or exposed. For contract-first, the signal MUST be a checked-in interface contract — an OpenAPI/Swagger document, a *.proto, a GraphQL SDL, or an AsyncAPI document (a JSON Schema counts only under an explicit contracts/ directory, since a bare *.schema.json is usually a config-validation schema, not an interface contract) — found at the project root or a conventional contract directory — and the category is interface-gated per FR-014. Detection proves a contract is checked in; it MUST NOT be surfaced as proof that the contract is valid, complete, or matches the running interface. At the verified tier and above only, holding a contract additionally MUST require a configured contract linter and a configured breaking-change differ — the mechanical meaning of the contract-checked posture the profile axis already names. The signal MUST be a declared configuration (a ruleset file, a buf.yaml breaking stanza, an oasdiff/buf invocation in a CI definition) and MUST NOT be satisfied by the mere presence of a tool as a dependency — the same distinction coverage draws between a declared threshold and a bare coverage library, for the same reason: an installed tool that never runs certifies nothing. Where a contract's format has no mainstream tool for one half of the check, that half MUST be reported at advisory strength with the limitation stated and MUST NOT hard-fail the floor. This condition MUST NOT change the verdict below verified: a lean- or standard-profile project is evaluated exactly as before. Detection proves a check is configured; it MUST NOT be surfaced as proof that the check passes, or that it blocks a merge.

Rationale — thresholds, gaps, ceilings, and interface-gating

An .eslintrc means lint runs, so most categories survive presence-detection; coverage breaks that (threshold-bearing signal; Go flag-only gap → FR-010), and observability has an exporter-manifest convention outside Swift/C++ (FR-010) with a "declared ≠ wired" ceiling. Contract-first breaks it differently: a contract is only owed if an interface is exposed, so the signal is paired with an interface-gate (FR-014) rather than an FR-010 undetectable entry — the gate fails safe on "no interface detected", and its ceiling is that a contract is checked in, not that it is correct. The verified-and-above tightening raises that ceiling by one rung without pretending to clear it: a configured linter and differ is a materially stronger claim than a file existing, and still a claim about configuration, not about a check passing. It is tier-gated rather than universal because the contracts axis already ladders posture by rigor — standard says contract-first, verified says contract-checked — so the floor is following a distinction the profiles already draw, not inventing one. Asymmetric tool maturity per format (AsyncAPI's diff story is thinner than OpenAPI's) is handled by an advisory carve-out rather than by lowering the bar for everyone.

5 · Risk register

Auto-fired: FR-002 is must-tier. Self-reviewed against the draft delta; all three findings dispositioned inline.

Raising a floor inside an existing category means a verified project that passes today can fail tomorrow with no change of its own — the upgrade-breaks-the-build surprise that trains teams to pin or disable a gate.

Every prior category addition (coverage, observability) landed as a NEW category, which a project could see arriving in its required list; this one changes the meaning of a category already in that list.

Mitigated by tier-gating plus the existing waiver machinery, both now explicit in the requirement: the condition applies only at verified and above (where contract-checked is already the declared posture, so the project has stated this intent), it cannot touch lean or standard at all, and a project that needs time can waive contract-first with a reason and expiry like any other category. The alternative — a tenth category — was considered and rejected in §3 for making one question read as two.

"Configured linter and differ" without a per-format capability rule would hard-fail every AsyncAPI project for lacking a mainstream breaking-change differ — failing projects for tooling that does not exist, which is precisely the warn-washing FR-010 was written to prevent.

The event-driven-interface survey's recorded finding: Spectral's ruleset covers AsyncAPI 2.x while request/reply is 3.0, and event-diff tooling is materially thinner than OpenAPI's — so contract-checked "shouldn't promise parity".

Mitigated. The delta states that a format whose tooling lacks one half reports that half at advisory strength with the limitation stated, and never hard-fails. Stated rather than silently downgraded, so the rung neither overclaims nor quietly exempts.

A rung called contract-checked that can only see configuration invites exactly the overclaim the category's existing ceiling guards against — a reader will hear "checked" and assume the contract passes its linter, when nothing has run.

FR-002's own existing ceilings for coverage ("configured", not "a CI diff-gate blocks") and observability ("declared", not "wired") — the same trap, one rung up.

Mitigated. The delta closes with the parallel sentence: detection proves a check is configured; it MUST NOT be surfaced as proof the check passes or blocks a merge. 074 FR-005 carries the same clause into the generated enforcement copy, and its T-901 pins it with a drift guard so a later edit cannot quietly upgrade "configured" into "passing".

6 · Tasks

Scoped to this change. Deliberately empty: the detection code this amendment unblocks is tracked entirely in 074's own tasks.html (T-002 onward), so folding a duplicate list into 042's tracker would leave the same work listed twice.

7 · Open questions

None outstanding. The tighten-versus-new-category choice, the declared-configuration signal rule, the capability carve-out and the tier gate were all settled in 074's own interview; this proposal carries them into 042's requirement text.
