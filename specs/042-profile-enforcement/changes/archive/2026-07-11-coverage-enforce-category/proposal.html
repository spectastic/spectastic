This makes coverage the 7th enforcement category — but coverage is unlike the other six in two ways the adversarial pass surfaced, and both are handled honestly. Add coverage as the 7th enforcement category

Applied

1 · Intent

042 gates a profile's enforcement floor over six categories. Coverage is the obvious seventh, and the literature is unanimous that a single universal coverage percentage is a Goodhart target (100% is a smell; the discipline, not the number, is the invariant). The reconciliation is diff coverage — a stack-agnostic rule ("a change never lowers coverage of the code it touches") that coexists with per-project numbers. That split maps onto spectastic's own 041→042 convention: the discipline is the floor (this change), the number is plan-time (P2b, landed).

But coverage is not a drop-in seventh category, and shipping it as one would have been dishonest in two ways the adversarial pass caught (§5). Presence of a coverage tool is not a running gate — unlike an .eslintrc, which does mean lint runs — so a bare coverage library must not certify the floor as met. And coverage config does not exist at all in some ecosystems (Go), so a hard gate on it would false-fail a well-tested project, contradicting 042's own "never a false failure" contract and inviting the disable-the-gate reflex P-9 forbids. This proposal ships the honest version: threshold-bearing detection, and a category-level undetectable→warn rule (FR-010) that lets coverage sit in the hard floor without blocking an ecosystem that cannot express it.

2 · Scope

In scope

  • MODIFY FR-002: add coverage, detected only from a declared threshold/check (not a bare library); state that detection proves a threshold is configured, not that a CI diff-gate runs.
  • ADD FR-010: a required category structurally undetectable in the project's ecosystem(s) degrades to a warning, never a hard failure — the category-level generalisation of §2's stack-level rule.
  • ADD coverage to the verified and enterprise enforce.required arrays + refresh both axes.enforcement labels (a data/content delta) — safe now that FR-010 protects Go.
  • Core machinery (§6): the EnforceCategory union, threshold-bearing SIGNALS, the FR-010 undetectable-category→warn policy, honest compose.ts floor wording, fixtures + tests.

Out of scope

  • A coverage threshold number in the floor. The number is plan-time (P2b); a mandated universal percentage is the Goodhart target the literature warns against.
  • A diff-aware runtime gate that computes patch coverage and blocks a drop in CI. 042 detects that a coverage threshold is configured; wiring a real patch-coverage computation is a larger, separate effort — and the surfaced copy (FR-002, the AGENTS floor block) is worded to claim only what detection proves, never that gate.

3 · Approach

Two of the three integration points are the uniform category machinery every category shares: the EnforceCategory union gains 'coverage' (packages/core/src/enforce/types.ts) and ALL_CATEGORIES gains it (detect.ts). The third — the SIGNALS rows — is where coverage differs: each row's contains matches a threshold/check declaration, not a bare dependency. Python [tool.coverage] with fail_under / .coveragerc; JS/TS a coverageThreshold block (vitest/jest) or an .nycrc with a threshold; Java a JaCoCo check / violationRules in pom.xml / build.gradle; Rust/C++ where a threshold config exists. Go is the recorded gap — go test -cover is a flag with no config file, so presence-detection cannot see it.

That gap is what makes FR-010 necessary rather than optional. detectEcosystems (spec 043) already knows the project's languages; the FR-010 policy consults a small structurally-undetectable map (today just { coverage: ['go'] }): when a required category is undetectable in every detected ecosystem, it degrades to a warning instead of a hard failure. So a Go verified project gating coverage in CI is nudged, not blocked, and policy.ts's required-vs-covered diff stays honest for the ecosystems where coverage is visible. The manifest half — coverage in verified/enterprise enforce.required + the axis-label refresh — is a data/content delta (target names the manifest, embeds a <spec-diff>), so apply touches 042's requirements body only for the FR-002 MODIFY and the FR-010 ADD.

The honesty line, held everywhere coverage surfaces (FR-002 rationale, the composed AGENTS "Enforcement floor" block): detection proves a coverage threshold is configured — it does not prove CI blocks a coverage drop on a diff. The real diff-gate is TBD-coverage-diff-gate; the copy must not claim it early.

4 · Deltas

What changes: coverage joins the enumerated set, detected only from a declared threshold/check; the honesty limit (threshold configured ≠ CI gate runs) and the Go flag-only gap are recorded.

Detection MUST classify present enforcement categories — formatter · linter · type-checker · security · supply-chain · test-runner · coverage — from config/manifest signals across Python, JS/TS, Java, Go, Rust, Swift, and C++. For coverage, the signal MUST be a declared threshold or check (e.g. fail_under, a coverageThreshold block, a JaCoCo check rule), not a bare coverage library — because for coverage alone, presence of the tool does not imply a gate. Detection proves a coverage threshold is configured; it MUST NOT be surfaced as proof that a CI diff-gate blocks a coverage drop.

Rationale — threshold-bearing, and Go is a recorded gap

An .eslintrc means lint runs, so the other six categories survive presence-detection; coverage breaks that equivalence because measuring and gating are separable, so it detects only a threshold/check declaration. Go coverage is flag-only (go test -cover, no config file), so it is not statically detectable at all — recorded here and handled by FR-010 rather than papered over with a false signal.

What's added: the category-level generalisation of §2's "undetectable stack → warn" rule — so a hard gate never false-fails a floor the ecosystem structurally cannot express (the Go/coverage case).

A required enforcement category that is structurally undetectable in every one of the project's detected ecosystems — the category has no config-file surface there, as with coverage in Go (go test -cover is a flag) — MUST degrade to a warning, never a hard failure, even under a hard-gate profile. This generalises the §2 stack-level guarantee ("an undetectable stack degrades to a warning, never a false failure") to the category level, so a well-tested project is never blocked for a floor its ecosystem cannot express. A category that is detectable in the project's ecosystems but simply unconfigured still fails the hard gate as before.

Rationale

Without this, adding coverage to the verified/enterprise hard floor would exit 1 on every Go project — a false failure that contradicts 042's founding "never a false failure" contract and manufactures the exact disable-the-gate reflex (P-9) the floor exists to prevent. FR-010 keeps coverage a real hard gate where it is detectable and an honest warning where it is not; the structurally-undetectable set is data (today { coverage: ['go'] }), extensible as new categories or ecosystems reveal gaps.

What's added: coverage appended to the verified and enterprise enforce.required arrays in spectastic-profiles.json, both axes.enforcement labels refreshed. A data/content delta (target names the manifest, embeds a <spec-diff>, no requirement-body change). Safe under the hard gate now that FR-010 protects structurally-undetectable ecosystems.

verified.enforce.required: [… , "security", "coverage"] verified.axes.enforcement: "lint+types+tests+coverage+security+custom" enterprise.enforce.required: [… , "supply-chain", "coverage"] enterprise.axes.enforcement: "lint+types+tests+coverage+security+supply-chain+toggle+custom"
Rationale — why verified + enterprise

Coverage gating is a higher-rigor concern: standard's floor is formatter/linter/test-runner, so a coverage gate starts earning its keep at verified and hardens at enterprise — matching the coverage doc and the existing rigor ladder. With threshold-bearing detection + FR-010, a green coverage at these tiers means a real configured threshold, and no ecosystem is false-failed.

5 · Risk register

From the adversarial pass (auto-fired: FR-002 is must-tier). All three findings dispositioned in the review interview; each records the human who committed the transition.

Certifying coverage "covered" on the mere presence of a coverage tool — not a running gate — will be reporting green floors that don't hold, the exact P-9 failure the category was sold to prevent.

§4 FR-002 rationale ("detected by the presence of a coverage config") + bare @vitest/coverage-* signals, against detectTooling (detect.ts:129-136) which marks a category covered if any one signal matches — so @vitest/coverage-v8 with no threshold passes. The considerations doc §5 detects only threshold-bearing config.

Mitigated. FR-002 now requires the coverage signal to be a declared threshold/check (fail_under / coverageThreshold / JaCoCo check), never a bare library, and §6's SIGNALS rows match on the threshold substring. A green coverage means a configured threshold.

Adding coverage to the verified/enterprise hard enforce.required forces enforce to exit 1 where coverage gating isn't in a root config — Go always (flag-only) — contradicting the live "never a false failure" guarantee.

Live FR-004 + §2 Edge cases: "an undetectable stack degrades to a warning, never a false failure." The proposal concedes Go coverage "is not statically detectable" yet puts it in both gate:"hard" floors.

Mitigated. New FR-010 generalises the stack-level "undetectable → warn" rule to the category level: a required category structurally undetectable in the project's ecosystems (coverage in Go) warns, never hard-fails. Coverage stays a real hard gate where detectable; Go is nudged, not blocked. The structurally-undetectable set is data ({ coverage: ['go'] }), extensible.

The category detects only tool presence (the diff-lowering gate is deferred), yet lands in the hard floor under a name + AGENTS.md block that read as "coverage is gated" — too narrow a mechanism for the promise it ships into.

§2 Out-of-scope defer-to="TBD-coverage-diff-gate" vs. the compose.ts "Enforcement floor" block an agent reads as an enforced floor.

Mitigated. The stated meaning is narrowed everywhere it surfaces (FR-002's MUST NOT clause, the §3 honesty note, the composed AGENTS floor wording — a §6 task): detection proves "a coverage threshold is configured," never that a CI diff-gate blocks a drop. The real diff-gate stays TBD-coverage-diff-gate; the copy claims only what detection proves.
