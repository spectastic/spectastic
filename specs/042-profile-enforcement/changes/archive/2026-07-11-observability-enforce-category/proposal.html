Add observability as an enforcement category

Applied

1 · Intent

The observability survey's argument is that a production-tier project should make its health observable — the golden signals through a standard registry or exporter — and that this, unlike an SLO number, is statically detectable: a service that wires metrics does it by adding one named registry/exporter/starter dependency that shows up in the manifest. P1b landed the principle at verified; this turns it into a checkable floor, the same way 042 already gates formatter/linter/security/coverage.

The adversarial pass sharpened two things a first cut got wrong. Detection must match the deliberate export choice (a Prometheus/OTel exporter), not an OTel namespace prefix that also catches tracing-only core libraries — otherwise a project emitting zero metrics earns a green gate. And "detectable in every ecosystem" was false: Java/Go/JS/Python/Rust have an exporter-manifest convention, but Swift and C++ do not, so they take an FR-010 undetectable-category entry (warn, never a hard failure) — the same machinery coverage-in-Go introduced, now with its second user. Hard-gated at verified/enterprise is deliberate: because the signal is a chosen exporter (never transitive), a missing signal means the team never chose to export metrics — a real gap at the operate-in-production tiers, on par with a missing security-scanner config. The one permanent ceiling, recorded not hidden: presence proves the exporter is declared, not that the endpoint is wired.

2 · Scope

In scope

  • MODIFY FR-002: add observability, detected from a metrics exporter/registry/starter dependency (the deliberate export name, never a core/tracing-only library); state the present ≠ wired ceiling and the hard-gate justification.
  • ADD observability to the verified and enterprise enforce.required arrays + refresh both axes.enforcement labels (a data/content delta).
  • Core machinery (§6): the EnforceCategory union, exporter-specific per-ecosystem SIGNALS (incl. Rust), an observability entry in STRUCTURALLY_UNDETECTABLE for Swift + C++ (FR-010), fixtures + tests extending SC-002.

Out of scope

  • The verify-page observables trace (SLO → SLI → instrumentation) that gives NFRs a proof leg. Its own spec (P4d).
  • SLOs linked to NFRs in the artifact model. Its own spec (P4c).
  • Proving the /metrics endpoint is actually wired/exposed (Spring's management.endpoints.web.exposure.include, an OTLP push target). A deeper config/runtime check; 042 detects the necessary manifest signal and records the ceiling. The hard gate is justified on the deliberate-exporter-choice signal (see FR-002 rationale), not on a claim the endpoint is live.

3 · Approach

The uniform category path, third time: the EnforceCategory union gains 'observability' (packages/core/src/enforce/types.ts), ALL_CATEGORIES gains it (detect.ts), and per-ecosystem SIGNALS rows detect the exporter. policy.ts and compose.ts consume it for free. The FR-010 machinery from the coverage change is reused, not rebuilt — an observability entry in STRUCTURALLY_UNDETECTABLE names the ecosystems with no exporter-manifest convention.

Detection signals — the deliberate export name only: Java micrometer-registry-prometheus / spring-boot-starter-actuator / quarkus-micrometer-registry-prometheus / quarkus-opentelemetry; Go prometheus/client_golang / go.opentelemetry.io/otel/exporters/prometheus; JS/TS prom-client / @opentelemetry/exporter-prometheus / @opentelemetry/sdk-metrics; Python prometheus_client / opentelemetry-exporter-prometheus; Rust the prometheus crate / opentelemetry-prometheus in Cargo.toml. Never the top-level @opentelemetry/ namespace or a tracing-only core lib (@opentelemetry/api), which arrive transitively and would false-positive. Swift and C++ have no standard exporter-manifest surface → an FR-010 STRUCTURALLY_UNDETECTABLE entry, so a well-built Swift/C++ verified project warns instead of false-failing.

Present ≠ wired, recorded not hidden (the security-category posture): a matched exporter dependency is a necessary signal that monitoring is possible — not proof the /metrics endpoint is exposed or scraped. FR-002 states this; the surfaced copy claims only "an observability exporter is declared."

4 · Deltas

What changes: observability joins the enumerated set, detected from a deliberate metrics exporter/registry/starter dependency (never a core/tracing-only library); the present ≠ wired ceiling and the hard-gate justification are recorded. The coverage clause is unchanged.

Detection MUST classify present enforcement categories — formatter · linter · type-checker · security · supply-chain · test-runner · coverage · observability — from config/manifest signals across Python, JS/TS, Java, Go, Rust, Swift, and C++. For coverage, the signal MUST be a declared threshold or check (e.g. fail_under, a coverageThreshold block, a JaCoCo check rule), not a bare coverage library — because for coverage alone, presence of the tool does not imply a gate. Detection proves a coverage threshold is configured; it MUST NOT be surfaced as proof that a CI diff-gate blocks a coverage drop. For observability, the signal MUST be a metrics registry/exporter/starter dependency matched by its deliberate export name (e.g. micrometer-registry-prometheus, spring-boot-starter-actuator, prometheus/client_golang, @opentelemetry/exporter-prometheus, prometheus_client, the Rust prometheus crate), not a transitively-arriving core library or a tracing-only package (e.g. @opentelemetry/api). Detection proves an observability exporter is a declared dependency ("monitoring is possible"); it MUST NOT be surfaced as proof that the /metrics endpoint is wired or exposed.

Rationale — thresholds, gaps, ceilings, and why observability hard-gates

An .eslintrc means lint runs, so most categories survive presence-detection; coverage breaks that (measuring and gating separable → threshold-bearing signal; Go is a flag-only gap handled by FR-010). Observability has an exporter-manifest convention in Java/Go/JS/Python/Rust but not Swift/C++, which take an FR-010 undetectable-category entry (warn, never a false failure). It shares coverage's honesty limit — a dependency can be on the classpath but not wired (Spring's endpoint must be exposed; an OTLP-push service has no local /metrics) — so the signal is the deliberate export choice and the claim is bounded to "declared", not "live". It is nonetheless hard-gated at verified/enterprise: matching only a chosen exporter (never a transitive core lib), a missing signal means the team never chose to export metrics — a real gap at the operate-in-production tiers, on par with a missing security-scanner config, and the strongest floor obtainable without the (deferred) verify-page proof leg.

What's added: observability appended to the verified and enterprise enforce.required arrays in spectastic-profiles.json, both axes.enforcement labels refreshed. A data/content delta (target names the manifest, embeds a <spec-diff>, no requirement-body change per REQ-CHANGE-002/008).

verified.enforce.required: [… , "coverage", "observability"] verified.axes.enforcement: "lint+types+tests+coverage+security+observability+custom" enterprise.enforce.required: [… , "coverage", "observability"] enterprise.axes.enforcement: "lint+types+tests+coverage+security+supply-chain+observability+toggle+custom"
Rationale — why verified + enterprise

The observability principle (P1b) sits at verified (repeated into enterprise); its enforce teeth belong at the same tiers. A verified/enterprise project without a declared metrics exporter is flagged — hard-gated like the other required categories, and safe to hard-gate because Swift/C++ (the ecosystems with no exporter-manifest surface) are protected by the FR-010 entry.

5 · Risk register

From the adversarial pass (auto-fired: FR-002 is must-tier). All three findings dispositioned in the review interview; each records the human who committed the transition.

The observability signals hard-gate on OpenTelemetry name-prefix matches (@opentelemetry/, opentelemetry-) that fire on tracing-only or transitive core libraries with no metrics registry, so a verified project earns a green observability gate while emitting zero metrics — the exact core-library false-positive the proposal swears off.

Draft FR-002 listed @opentelemetry/ among "deliberate export name … not a transitively-arriving core library" exemplars; @opentelemetry/api is precisely that core library and matches the prefix.

Mitigated. FR-002 and §3 now require the deliberate export name — @opentelemetry/exporter-prometheus / @opentelemetry/sdk-metrics, opentelemetry-exporter-prometheus, go.opentelemetry.io/otel/exporters/prometheus — never the top-level namespace, and explicitly exclude @opentelemetry/api. §6 adds a core-library-only negative fixture asserting non-classification.

FR-002 requires detection "across Python, JS/TS, Java, Go, Rust, Swift, and C++," but the draft signal table spanned only four; with no FR-010 entry, a verified/enterprise Rust/Swift/C++ project falls through to missing and hard-exits 1 — a false failure that manufactures the P-9 disable-the-gate reflex.

FR-010 + §2 "an undetectable stack degrades to a warning, never a false failure", against the draft's false "detectable in every ecosystem … no FR-010 exemption is needed".

Mitigated. The false claim is dropped. A Rust exporter signal is added (the prometheus crate / opentelemetry-prometheus in Cargo.toml), and STRUCTURALLY_UNDETECTABLE gains observability: ['swift', 'cpp'] — the ecosystems with no exporter-manifest convention warn instead of false-failing. The second user of the FR-010 machinery, validating its extensibility.

A new hard gate paired with a permanent refusal to verify wiring means the strongest thing this category can prove is "a dependency string is in the manifest" — materially weaker than every sibling — thin justification for a build-failing gate rather than a warn.

§Scope out-of-scope defer-to="never" ("Proving the /metrics endpoint is wired") against §4 appending observability to the hard floor.

Accepted, with the justification made explicit in FR-002's rationale: with the Risk-1 fix matching only a deliberate exporter/registry choice (never a transitive core lib), a missing signal means the team never chose to export metrics — a real gap at the operate-in-production tiers, on par with a missing security-scanner config, and the strongest floor obtainable before the deferred verify-page proof leg (P4d). Kept hard, not warned; the ceiling is recorded, the gate is honest about what it proves.
