Profile enforcement

A profile's promises become real when a gate can say no — not when the prose asks nicely.

Read time

041 made profiles advise — it seeds principles and a lean AGENTS.md but its promises ("every level tested", "every feature toggled") live in prose an agent can skip (P-8, T-009). 042 gives the enforcement floor teeth: a deterministic spectastic enforce command that reads the project's profile marker, detects which enforcement categories the toolchain actually covers, and exits non-zero when an enforcing profile's required category is missing — so a pre-commit or CI gate can block on it. Because the toolchain is ecosystem-specific and only knowable in the project, the profile carries a policy (required categories) and detection resolves it to reality. Brownfield-safe: it reports what's missing, never dictating a tool a project already chose.

1 · Context

041 ships the profile skeleton: a seeded principles.html and a lean AGENTS.md whose gate section says "run your checks." But nothing verifies the checks exist. A Verified project that promises "every level tested; build a checker when none exists" is, today, a sentence — exactly the advisory-prose gap P-8 and the considerations doc warn about.

The architectural fork, resolved. The obvious home — a spectastic validate rule — does not fit: the validate engine parses spec-html documents, not project state (it never sees pyproject.toml or .eslintrc). So the gate is a new command, spectastic enforce, that inspects the project and can exit non-zero — installable into the 031 pre-commit gate, so the guarantee lives at the git/CI boundary where P-8 says it must.

Users: developers who chose a rigorous profile and want its floor to actually hold.

2 · User scenarios & testing

Each story MUST be independently testable.

US1 · The floor is a gate that can fail P1

As a developer on a Verified project, I want spectastic enforce to fail when my toolchain is missing an enforcement category the profile requires so that the profile's promise is real, not prose.

Acceptance: in a Verified-profile project with no linter/type-checker config, spectastic enforce exits 1 and names the missing categories; once they're present, it exits 0. This is the smallest demoable.

US2 · Detection is ecosystem-aware and honest P2

As a developer in any stack, I want enforcement categories detected from my project's real config so that the gate reflects what I actually run, not a guess.

Acceptance: detection classifies representative signals per ecosystem (Python, JS/TS, Java, Go, Rust, Swift, C++) into categories — formatter, linter, type-checker, security, supply-chain, test-runner.

US3 · Respect a brownfield toolchain P3

As a developer retrofitting a profile, I want the guidance to fill only the gaps so that a profile respects the tools I already chose instead of fighting them.

Acceptance: brownfield init --profile runs detection and the composed AGENTS.md gate section names only the missing categories; existing tools are acknowledged, not replaced (unless --replace-tools).

Edge cases

  • No profile marker → enforce is a no-op exit 0 with a note (nothing to enforce).
  • Lean profile → no required categories; exit 0 always.
  • Standard profile → a missing category warns but exits 0 (only Verified/Enterprise are hard gates).
  • Unknown/polyglot ecosystem → detection reports what it can; an undetectable stack degrades to a warning, never a false failure.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

spectastic enforce [path] MUST read the project's .spectastic/profile.json marker and report the enforcement categories the profile requires against those the toolchain provides.

Detection MUST classify present enforcement categories — formatter · linter · type-checker · security · supply-chain · test-runner — from config/manifest signals across Python, JS/TS, Java, Go, Rust, Swift, and C++.

Each profile MUST declare its required enforcement categories as data (an enforce field in spectastic-profiles.json): Lean none, Standard a floor, Verified and Enterprise progressively more.

enforce MUST exit non-zero when a required category is unmet for a hard-gate profile (Verified/Enterprise); Standard MUST warn but exit 0; Lean and no-marker MUST exit 0 — so a pre-commit/CI gate can block precisely where it should.

init --tools (031) SHOULD optionally wire spectastic enforce into the pre-commit gate so the floor holds at the git boundary.

Brownfield init --profile SHOULD run detection and tailor the composed AGENTS.md gate section to the missing categories, acknowledging existing tools; --replace-tools overrides.

The /spectastic.plan verb SHOULD read the profile marker and emit a "Toolchain / enforcement" section resolving the policy to the detected ecosystem's tools plus the escalation ladder (standard gate → custom rule → build a minimal checker).

The /spectastic.principles verb MAY read the marker to tailor its interview to the chosen profile.

Non-functional

enforce and detection MUST be deterministic and filesystem-only — no network, no model — so CI drives them with fixture projects.

Detection SHOULD read only shallow config signals (root manifests + known config files), completing well under 500 ms on a typical project.

Out of scope (deferred)

  • Installing tools or editing a project's package manifests — spectastic does not manage the user's package manager.
  • Auto-writing CI workflow files for the resolved gate.
  • Automating the "build a minimal checker when none exists" duty — that is agent behavior guided by AGENTS.md, not spectastic code.
  • A shipped per-language custom-rule pack (Semgrep/ast-grep) for spec invariants.

4 · Data model

Entities

Enforcement category
One of: formatter · linter · type-checker · security · supply-chain · test-runner. The unit both the profile policy and detection speak in.
Detection signal
A mapping from a config/manifest marker (e.g. [tool.ruff] in pyproject.toml, .clang-tidy, deny.toml) to the category it satisfies, per ecosystem. Ships as data.
Profile enforce policy
The enforce field on each profile: the required categories + gate severity (hard/soft/none).

Invariant: a category is "covered" if any signal for it is present — detection reports gaps, never prescribes a specific tool (brownfield respect).

5 · Success criteria

In a Verified-profile fixture with no linter/type-checker, spectastic enforce exits 1 and names the missing categories; in a fully-tooled Verified fixture it exits 0. (The smallest demoable.)

Detection classifies representative config files for each of the seven ecosystems into the correct category (a fixture per ecosystem).

Gate severity scales: Lean and no-marker exit 0 unconditionally; Standard with a gap warns and exits 0; Verified/Enterprise with a gap exit 1.

Brownfield init --profile in a project that already has a linter configured produces an AGENTS.md whose gate section does not tell the agent to add a linter for that category.

6 · Assumptions

The 041 profile marker (.spectastic/profile.json) is the source of truth for which profile a project runs.

Shallow config-signal detection is a good-enough proxy for "the category is enforced"; a project can suppress a false gap by pointing detection at its setup (a future refinement, not v1).

None outstanding — the architectural fork (gate is a command, not a validate rule) is resolved in §1; scope, severity model, and the brownfield boundary were anchored against 041 and the considerations doc.
