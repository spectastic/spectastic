Specification · 042-profile-enforcement

Profile enforcement

A profile's promises become real when a gate can say no — not when the prose asks nicely.

Status Accepted Spec ID 042-profile-enforcement Owner Brian Corbin · @briancorbinxyz Reviewers — Created 09 Jul 2026 Principlesv1.3.0 Follows 041-init-profiles — the enforcement follow-on (a sibling spec, not a slice) Smallest demoablespectastic enforce in a Verified-profile project with no linter exits 1 and names the missing category; a fully-tooled one exits 0. Read time

041 made profiles advise — it seeds principles and a lean AGENTS.md but its promises ("every level tested", "every feature toggled") live in prose an agent can skip (P-8, T-009). 042 gives the enforcement floor teeth: a deterministic spectastic enforce command that reads the project's profile marker, detects which enforcement categories the toolchain actually covers, and exits non-zero when an enforcing profile's required category is missing — so a pre-commit or CI gate can block on it. Because the toolchain is ecosystem-specific and only knowable in the project, the profile carries a policy (required categories) and detection resolves it to reality. Brownfield-safe: it reports what's missing, never dictating a tool a project already chose.

1 · Context

041 ships the profile skeleton: a seeded principles.html and a lean AGENTS.md whose gate section says "run your checks." But nothing verifies the checks exist. A Verified project that promises "every level tested; build a checker when none exists" is, today, a sentence — exactly the advisory-prose gap P-8 and the considerations doc warn about.

The architectural fork, resolved. The obvious home — a spectastic validate rule — does not fit: the validate engine parses spec-html documents, not project state (it never sees pyproject.toml or .eslintrc). So the gate is a new command, spectastic enforce, that inspects the project and can exit non-zero — installable into the 031 pre-commit gate, so the guarantee lives at the git/CI boundary where P-8 says it must.

Users: developers who chose a rigorous profile and want its floor to actually hold.

A required enforcement category that is structurally undetectable in every one of the project's detected ecosystems — the category has no config-file surface there, as with coverage in Go (go test -cover is a flag) — MUST degrade to a warning, never a hard failure, even under a hard-gate profile. This generalises the §2 stack-level guarantee ("an undetectable stack degrades to a warning, never a false failure") to the category level, so a well-tested project is never blocked for a floor its ecosystem cannot express. A category that is detectable in the project's ecosystems but simply unconfigured still fails the hard gate as before.

Rationale

Without this, adding coverage to the verified/enterprise hard floor would exit 1 on every Go project — a false failure that contradicts 042's founding "never a false failure" contract and manufactures the exact disable-the-gate reflex (P-9) the floor exists to prevent. FR-010 keeps coverage a real hard gate where it is detectable and an honest warning where it is not; the structurally-undetectable set is data (today { coverage: ['go'] }), extensible as new categories or ecosystems reveal gaps.

A downstream project MAY relax a single enforcement category by declaring a waiver in spectastic.json under enforce.waivers[]. Each waiver MUST carry four fields: category (a valid enforcement category present in the project's profile floor), reason (a non-empty, non-boilerplate justification), until (an ISO YYYY-MM-DD expiry no more than 365 days in the future), and owner (who accepted the risk). A waiver whose until has passed MUST auto-expire — its category resumes gating with no further action. The mechanism MUST be secure-by-default: an absent enforce section relaxes nothing, and a waiver missing any field, carrying a boilerplate reason, or bearing an invalid/expired/over-horizon date MUST NOT relax its category. Expiry MUST be evaluated against an injectable clock (default: the current date) so a fixture project pins the clock for reproducible CI (NFR-001). A waiver is a change to git-tracked spectastic.json, so its PR review is the v1 approval surface — a distinct approver-vs-requester workflow is deferred (TBD-waiver-approval), and the owner field records who accepted the risk.

Rationale — reason and expiry are shape, not etiquette

Justification and expiry baked into the token achieve near-total compliance; the same fields left conventional rot into boilerplate (the comply-or-explain failure mode). A mandatory expiry with a hard horizon turns "ignore forever" into a dated decision that must be renewed or fixed — the single most-cited control that keeps an exception mechanism from becoming a footgun. The section-per-feature home (enforce.waivers) matches the established git/decider/models config shape.

A profile MAY declare an enforce.unwaivable set of categories that a waiver cannot relax. The enterprise profile MUST mark security and supply-chain un-relaxable. A waiver naming an un-relaxable category MUST be inert — its category keeps gating regardless of the waiver — and MUST be flagged by validation (FR-013) so the author learns the waiver has no effect rather than assuming relief.

Rationale — some controls are not tailorable

Mature governance forbids waiving the highest-risk controls even as it allows tailoring the rest — the exception mechanism itself is gated. Enterprise's security and supply-chain categories are the two whose silent relaxation would be most regrettable, so they are removed from the waivable set entirely; verified, a lower-rigor tier, keeps its whole floor waivable. Verified is deliberately the lighter hard-gate tier — full waiver latitude, including over security and supply-chain, is precisely what distinguishes it from enterprise; a team that needs an un-waivable security floor chooses enterprise, and the tier choice is itself the recorded, explicit decision. Declaring the set as per-profile data (not code) keeps it on 042's "the floor is data" footing and lets the set evolve without a code change.

validate MUST include an enforce-waiver-well-formed check that reads the project's spectastic.json and reports, at error severity, any waiver that: names an unknown category, names a category not in the project profile's floor (a dead waiver), names an un-relaxable category (FR-012), carries an empty or boilerplate reason, omits owner, or bears a until that is missing, malformed, already past, or more than 365 days out. Independently, enforce MUST fail closed: a malformed or expired waiver is ignored at runtime (the category keeps gating), never trusted. The two guards are complementary — validate gives fast, specific authoring feedback; enforce guarantees a broken waiver can never disable a gate even if validation is skipped.

Rationale — the guarantee lives in the kernel or CI (P-8)

A waiver is a gate-weakening instrument, so its well-formedness is exactly the kind of invariant P-8 requires be machine-checked, not left to prose. The scan is a folded repo-file check (it reads project state, so it joins the skill-metadata / no-internal-id-in-copy family of CLI scans rather than the spec-HTML schema rules). Surfacing a silently-expired waiver as an error is deliberate: an expired waiver that still sits in the file is a stale decision the author should remove or renew, not leave to rot.

The contract-first category MUST be interface-gated: it is a gap only when the project exposes a detectable public interface — an HTTP/RPC framework declared as a dependency (e.g. express/fastify/@nestjs, flask/fastapi/django, spring-web/jakarta.ws.rs, gin/echo, actix-web/axum), a gRPC/Protobuf toolchain, a GraphQL server, or an event-driven interface — a message-broker or managed-bus client (e.g. Kafka, AMQP/RabbitMQ, NATS, Pulsar, SQS/SNS, EventBridge, Service Bus, Redis streams) declared as a dependency — and no checked-in contract is present. Detection of an event-driven interface alone, with no HTTP/RPC/GraphQL/gRPC signal also present, MUST report the gap at advisory severity via the existing per-category mechanism (the same one that already demotes an undetectable stack under FR-010) and MUST NOT hard-fail a profile floor on that branch alone, until the signal set is deliberately promoted — this is a distinct mechanism from FR-010's stack-cannot-express-this-category demotion: here the category plainly applies (an interface was detected), and only the detecting signal's strength is weaker.

Where a design (per 069/070) declares an interface's shape or a contract's path, that declaration MUST take precedence over inference from dependencies or the filesystem, in both directions: a declared contract path establishes one is owed even where dependency or filesystem inference alone would find none, and a declaration of shape="none" establishes none is owed even where a broker dependency is present. This is conditional on a design existing and declaring — a project with no spectastic design gets inference only, exactly as before.

A project with no detected interface — by dependency inference or an overriding declaration — MUST be treated as covered for contract-first (there is nothing to contract) — MUST NOT hard-fail — so a CLI, batch job, or internal library is never false-failed for lacking an API schema. This is categorically distinct from FR-010 and does NOT override it: FR-010 warns when a category that does apply cannot be expressed in the project's stack (an applicable-but-undetectable gap); contract-first's applicability is itself conditional — "no interface detected" means the category may not apply at all, not that an applicable category is invisible — so the correct posture is exempt, not warn. Warning on every interface-less project (each CLI, batch job, and library) would be the warn-washing FR-010's demotion is expressly not meant to cause. Because the gate fails safe on the antecedent, it requires no FR-010 undetectable entry; the residual is that an interface exposed via a mechanism outside the named signal set is silently exempt (a false-negative), which SHOULD be recorded as the honest ceiling rather than closed by widening the gate into false failures.

Rationale — fail safe on "does this even expose an interface?"

The other eight categories are unconditionally applicable at their tiers; contract-first is conditional on the project's nature. The choices are: hard-require it everywhere (false-fails interface-less projects — the P-9 reflex), make it advisory everywhere (a weaker, non-gating category for projects that plainly do expose an HTTP/RPC surface), or gate it on a detectable antecedent with a graduated signal strength. Interface-gating with an advisory-only event-driven branch is the option that keeps the HTTP/RPC/GraphQL/gRPC case a real hard gate, adds a genuinely new signal for event-driven services without inventing a false confidence in it, and never false-fails where no interface is detected at all. The trade is a persisting false-negative on unlisted mechanisms — deliberately preferred over a false-positive, because a false failure trains teams to disable the gate, while a false-negative is a missed nudge the principle (advisory, at standard) still covers.

2 · User scenarios & testing

Each story MUST be independently testable.

US1 · The floor is a gate that can fail P1

As a developer on a Verified project, I want spectastic enforce to fail when my toolchain is missing an enforcement category the profile requires so that the profile's promise is real, not prose.

Acceptance: in a Verified-profile project with no linter/type-checker config, spectastic enforce exits 1 and names the missing categories; once they're present, it exits 0. This is the smallest demoable.

US2 · Detection is ecosystem-aware and honest P2

As a developer in any stack, I want enforcement categories detected from my project's real config so that the gate reflects what I actually run, not a guess.

Acceptance: detection classifies representative signals per ecosystem (Python, JS/TS, Java, Go, Rust, Swift, C++) into categories — formatter, linter, type-checker, security, supply-chain, test-runner.

US3 · Respect a brownfield toolchain P3

As a developer retrofitting a profile, I want the guidance to fill only the gaps so that a profile respects the tools I already chose instead of fighting them.

Acceptance: brownfield init --profile runs detection and the composed AGENTS.md gate section names only the missing categories; existing tools are acknowledged, not replaced (unless --replace-tools).

Edge cases

  • No profile marker → enforce is a no-op exit 0 with a note (nothing to enforce).
  • Lean profile → no required categories; exit 0 always.
  • Standard profile → a missing category warns but exits 0 (only Verified/Enterprise are hard gates).
  • Unknown/polyglot ecosystem → detection reports what it can; an undetectable stack degrades to a warning, never a false failure.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

spectastic enforce [path] MUST read the project's .spectastic/profile.json marker and report the enforcement categories the profile requires against those the toolchain provides.

Detection MUST classify present enforcement categories — formatter · linter · type-checker · security · supply-chain · test-runner · coverage · observability · contract-first — from config/manifest signals across Python, JS/TS, Java, Go, Rust, Swift, and C++. For coverage, the signal MUST be a declared threshold or check (e.g. fail_under, a coverageThreshold block, a JaCoCo check rule), not a bare coverage library — because for coverage alone, presence of the tool does not imply a gate. Detection proves a coverage threshold is configured; it MUST NOT be surfaced as proof that a CI diff-gate blocks a coverage drop. For observability, the signal MUST be a metrics registry/exporter/starter dependency matched by its deliberate export name (e.g. micrometer-registry-prometheus, spring-boot-starter-actuator, prometheus/client_golang, @opentelemetry/exporter-prometheus, prometheus_client, the Rust prometheus crate), not a transitively-arriving core library or a tracing-only package (e.g. @opentelemetry/api). Detection proves an observability exporter is a declared dependency ("monitoring is possible"); it MUST NOT be surfaced as proof that the /metrics endpoint is wired or exposed. For contract-first, the signal MUST be a checked-in interface contract — an OpenAPI/Swagger document, a *.proto, a GraphQL SDL, or an AsyncAPI document (a JSON Schema counts only under an explicit contracts/ directory, since a bare *.schema.json is usually a config-validation schema, not an interface contract) — found at the project root or a conventional contract directory — and the category is interface-gated per FR-014. Detection proves a contract is checked in; it MUST NOT be surfaced as proof that the contract is valid, complete, or matches the running interface. At the verified tier and above only, holding a contract additionally MUST require a configured contract linter and a configured breaking-change differ — the mechanical meaning of the contract-checked posture the profile axis already names. The signal MUST be a declared configuration (a ruleset file, a buf.yaml breaking stanza, an oasdiff/buf invocation in a CI definition) and MUST NOT be satisfied by the mere presence of a tool as a dependency — the same distinction coverage draws between a declared threshold and a bare coverage library, for the same reason: an installed tool that never runs certifies nothing. Where a contract's format has no mainstream tool for one half of the check, that half MUST be reported at advisory strength with the limitation stated and MUST NOT hard-fail the floor. This condition MUST NOT change the verdict below verified: a lean- or standard-profile project is evaluated exactly as before. Detection proves a check is configured; it MUST NOT be surfaced as proof that the check passes, or that it blocks a merge.

Rationale — thresholds, gaps, ceilings, and interface-gating

An .eslintrc means lint runs, so most categories survive presence-detection; coverage breaks that (threshold-bearing signal; Go flag-only gap → FR-010), and observability has an exporter-manifest convention outside Swift/C++ (FR-010) with a "declared ≠ wired" ceiling. Contract-first breaks it differently: a contract is only owed if an interface is exposed, so the signal is paired with an interface-gate (FR-014) rather than an FR-010 undetectable entry — the gate fails safe on "no interface detected", and its ceiling is that a contract is checked in, not that it is correct. The verified-and-above tightening raises that ceiling by one rung without pretending to clear it: a configured linter and differ is a materially stronger claim than a file existing, and still a claim about configuration, not about a check passing. It is tier-gated rather than universal because the contracts axis already ladders posture by rigor — standard says contract-first, verified says contract-checked — so the floor is following a distinction the profiles already draw, not inventing one. Asymmetric tool maturity per format (AsyncAPI's diff story is thinner than OpenAPI's) is handled by an advisory carve-out rather than by lowering the bar for everyone.

Each profile MUST declare its required enforcement categories as data (an enforce field in spectastic-profiles.json): Lean none, Standard a floor, Verified and Enterprise progressively more.

enforce MUST exit non-zero when a required category is unmet for a hard-gate profile (Verified/Enterprise); Standard MUST warn but exit 0; Lean and no-marker MUST exit 0 — so a pre-commit/CI gate can block precisely where it should. A required-but-unmet category that carries an active, well-formed waiver (FR-011) whose category is not un-relaxable for the profile (FR-012) MUST degrade to an advisory warning and MUST be reported as a distinct relaxed count, never folded into the covered categories — so a relaxed floor is always visible, never silent. A waiver that is expired, malformed, or names an un-relaxable category MUST NOT relax its category: the gate fires as if no waiver were present.

Rationale — the honest middle between "cover it" and "turn it off"

Without a per-category demotion, a team's only opt-out is to lower the whole profile or delete the marker — the silent gate-lowering P-9 forbids. Making the relaxed category a separate reported tally (rather than counting it as covered) is the load-bearing honesty: the floor a profile promises stays legible even when one category is deliberately relaxed. The secure-by-default clause (expired/malformed/unwaivable → still blocks) means a waiver can only ever weaken the gate when it is complete and current.

init --tools (031) SHOULD optionally wire spectastic enforce into the pre-commit gate so the floor holds at the git boundary.

Brownfield init --profile SHOULD run detection and tailor the composed AGENTS.md gate section to the missing categories, acknowledging existing tools; --replace-tools overrides.

The /spectastic.design verb SHOULD read the profile marker and emit a "Toolchain / enforcement" section resolving the policy to the detected ecosystem's tools plus the escalation ladder (standard gate → custom rule → build a minimal checker).

The /spectastic.principles verb MAY read the marker to tailor its interview to the chosen profile.

A hard-gate profile's enforcement guidance SHOULD carry the P-9 discipline — a failing gate tool is fixed (version bump / config / known-good pin) before it is disabled, and any weakening is explicit and recorded. Delivered through the verified/ enterprise profile content (041), since a disabled tool silently defeats the floor enforce protects.

Non-functional

enforce and detection MUST be deterministic given the filesystem and an injected clock — no network, no model — so CI drives them with fixture projects. Where a result depends on the current date (a waiver's expiry, FR-011), the date MUST be an injectable parameter (default: the system date) so a fixture pins it for a reproducible run.

Rationale — bounded, declared clock dependency

Auto-expiry is the anti-rot control, but it makes an active waiver time-dependent, which would otherwise break the "fixture projects drive CI" promise. Scoping determinism to the filesystem and a supplied clock keeps the guarantee honest: the only non-filesystem input is a clock the caller controls, so a fixture that pins the date is fully reproducible, and production reads the system date as expected. This is the same injectable-now discipline the policy layer already uses for testability.

Detection SHOULD read only shallow config signals (root manifests + known config files), completing well under 500 ms on a typical project.

Out of scope (deferred)

  • Installing tools or editing a project's package manifests — spectastic does not manage the user's package manager.
  • Auto-writing CI workflow files for the resolved gate.
  • Automating the "build a minimal checker when none exists" duty — that is agent behavior guided by AGENTS.md, not spectastic code.
  • A shipped per-language custom-rule pack (Semgrep/ast-grep) for spec invariants.

4 · Data model

Entities

Enforcement category
One of: formatter · linter · type-checker · security · supply-chain · test-runner. The unit both the profile policy and detection speak in.
Detection signal
A mapping from a config/manifest marker (e.g. [tool.ruff] in pyproject.toml, .clang-tidy, deny.toml) to the category it satisfies, per ecosystem. Ships as data.
Profile enforce policy
The enforce field on each profile: the required categories + gate severity (hard/soft/none).

Invariant: a category is "covered" if any signal for it is present — detection reports gaps, never prescribes a specific tool (brownfield respect).

5 · Success criteria

In a Verified-profile fixture with no linter/type-checker, spectastic enforce exits 1 and names the missing categories; in a fully-tooled Verified fixture it exits 0. (The smallest demoable.)

Detection classifies representative config files for each of the seven ecosystems into the correct category (a fixture per ecosystem).

Gate severity scales: Lean and no-marker exit 0 unconditionally; Standard with a gap warns and exits 0; Verified/Enterprise with a gap exit 1.

Brownfield init --profile in a project that already has a linter configured produces an AGENTS.md whose gate section does not tell the agent to add a linter for that category.

6 · Assumptions

The 041 profile marker (.spectastic/profile.json) is the source of truth for which profile a project runs.

Shallow config-signal detection is a good-enough proxy for "the category is enforced"; a project can suppress a false gap by pointing detection at its setup (a future refinement, not v1).

None outstanding — the architectural fork (gate is a command, not a validate rule) is resolved in §1; scope, severity model, and the brownfield boundary were anchored against 041 and the considerations doc.
