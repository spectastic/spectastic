Design · 006-kernel-extraction

Kernel extraction — implementation plan

How @spectastic/core ships with validate as the first verb — small, atomic, bench-gated, with the architectural surface that seven sibling extractions follow.

Status Accepted Spec 006-kernel-extraction Owner Brian Corbin · @briancorbinxyz Branch main (squashed-snapshot pattern) Created 16 Jun 2026 Read time

Add packages/core/ as the third pnpm-workspace package, alongside packages/cli and packages/schema. Ship one verb — validate — as a pure function (validateCommand) that wraps @spectastic/schema's engine and receives all IO + AI access via an injected KernelContext. Per-verb subpath exports prevent eager loading; the init-help-cold-start bench scenario is the regression guard for the lazy-loading discipline. The CLI subcommand becomes a thin shim that imports from @spectastic/core/commands/validate; its behaviour stays byte-identical. Single PR; unit tests first; ~8 ADRs cover the architectural surface seven sibling extractions inherit.

2 · Technical context

Language(s)
TypeScript 5.7, Node ≥20 (matches existing packages).
Frameworks
None new. Inherits tsup (build), vitest (test), commander (CLI dispatch from @spectastic/cli), parse5 (transitively via @spectastic/schema).
Storage
In-process; no persistence. Kernel functions are pure modulo ctx.fs reads.
Testing
Unit-first: kernel tests against stub ctx.fs in packages/core/test/; existing CLI integration tests stay green as the wiring regression detector.
Perf targets
All four bench/baselines.json scenarios stay within budget. init-help-cold-start (150 ms) is the explicit lazy-loading regression guard.
Constraints
Byte-identical CLI behaviour (FR-006); 64/64 tests green; bench p50 within ±20% of today's baseline (NFR-002).

3 · Approach

Three moves, in one PR. One: scaffold packages/core/ with the same shape as packages/cli + packages/schema (package.json + tsconfig.json + tsup.config.ts + src/ + test/). Two: define the kernel's public surface in src/index.ts (types only — KernelContext, FileSystem, AIProvider, Question, and the per-verb input/result types) and the first verb's implementation at src/commands/validate.ts. Three: refactor @spectastic/cli's validate subcommand to import from @spectastic/core/commands/validate instead of @spectastic/schema directly; the subcommand stays the owner of glob expansion, file reads, output formatting, and exit code translation.

Per-verb subpath exports (./commands/<verb>) force lazy loading: importing @spectastic/core's main entry only loads type declarations — no code. Importing @spectastic/core/commands/validate loads the validate function plus its dependency on @spectastic/schema (which transitively loads parse5). The init-help-cold-start bench scenario remains the regression guard: if it ever exceeds 150 ms, parse5 has crept onto the init path through a stray top-level import in src/index.ts or a careless re-export.

Pattern A wins on all three axes: it preserves the existing CLI shape, runs in CI today (no daemon lifecycle), and reuses the bench scaffold as its regression guard. Pattern B (MCP daemon) was tempting for the per-invocation latency win, but adds operational complexity (long-lived process, daemon lifecycle, MCP transport) that's worth paying for once Pattern A is proven. "Skip kernel" violates the strategy plan and forces re-implementation per surface.

5 · Decisions

D-001 · New @spectastic/core package at packages/core/

Status
Accepted
Context
The kernel needs a home; merging it into @spectastic/schema would conflate "spec-html grammar" with "verb procedures."
Decision
Third pnpm-workspace package parallel to cli + schema. Same shape: package.json, tsconfig.json, tsup.config.ts, src/, test/. "publishConfig": {"access": "public"}; synced versioning per 004's policy.
Consequences
+ Clean separation of grammar (schema) from procedures (core); + future Tier 2 / 3 consume one package, not two. − Three packages to coordinate version-wise; the publish workflow's verify gate (004 FR-003) needs to cover the third.

D-002 · tsup multi-entry build for per-verb subpath exports

Status
Accepted
Context
Lazy-loading discipline requires consumers to import each verb from a distinct subpath. tsup's entry array maps to per-file outputs without manual rollup config.
Decision
Single tsup.config.ts declares an entry array: ['src/index.ts', 'src/commands/validate.ts', 'src/providers/claude.ts'] (claude entry empty in v1; reserved for 007). Each compiles to its own dist/<path>.js + .d.ts. The package's exports field references them per-subpath.
Consequences
+ Adding a verb is one new entry + one new export. + Subpath enforcement is structural, not convention. − The exports field grows linearly with verb count.

D-003 · KernelContext shape — required cwd, optional fs + ai

Status
Accepted
Context
Every kernel function needs to know where to resolve relative paths; some need IO; some need AI. Making all three required forces callers to construct stubs for verbs that don't use them.
Decision
{ cwd: string; fs?: FileSystem; ai?: AIProvider }. cwd required (no implicit process.cwd() per FR-003). fs defaults to a thin node:fs/promises wrapper when undefined. ai stays undefined for deterministic verbs (validate).
Consequences
+ Deterministic verbs don't need an AIProvider stub. + Unit tests with stub fs are one-liners. − Callers must always pass cwd; a future resolveContext() helper might smooth this.

D-004 · AIProvider interface — forward-looking, chat + ask<T> + subagent

Status
Accepted
Context
Three downstream verbs need distinct AI primitives: chat (narrative), ask (typed bounded choice), subagent (adversarial pass in 013). Declaring all three in v1 saves a future interface extension; declaring only what 006 needs (nothing) means 007 + 013 both ship breaking changes.
Decision
Define the full interface in v1: chat(prompt, opts?): Promise<string>; ask<T>(questions: Question[]): Promise<T>; subagent(prompt, opts?): Promise<SubagentResult>. No implementations ship with 006 (validate doesn't need them); the Claude impl lands with 007.
Consequences
+ 007 and 013 are additive PRs, not interface-extending. + Downstream surfaces (MCP, VS Code) can plan wiring against the full shape now. − Ships unused signatures; subagent's exact shape may be revisited when 013 actually implements it.

D-005 · FileSystem — custom minimal interface, not raw node:fs/promises

Status
Accepted
Context
Kernel functions need file IO but the kernel must not bind to Node's fs surface — MCP servers and VS Code extensions have their own IO primitives (workspace.fs, MCP filesystem capabilities).
Decision
Four methods: readFile, writeFile, readdir, stat (with a tiny { isFile, isDirectory } result). The kernel ships a default nodeFs implementation that wraps node:fs/promises; lazy-loaded only when ctx.fs is undefined.
Consequences
+ Unit-test stubs are four functions. + VS Code's workspace.fs maps cleanly. − Need to grow the interface as future verbs need more (mkdir, rename, etc.); each addition is a v1.0 minor bump (per FR-012).

D-006 · validateCommand wraps schema; no new logic

Status
Accepted
Context
The validate logic already lives in @spectastic/schema's validate + validateMany. The kernel's job is to expose it as a verb function, not reimplement.
Decision
validateCommand({files, format?, ignore?}, ctx) reads each file via ctx.fs.readFile, calls schema.validateMany, structures the result as {findings, exitCode, filesValidated}. Exit code: 0 (clean) / 1 (findings) / 2 (usage / read error). Glob expansion stays in the CLI subcommand — the kernel takes resolved paths.
Consequences
+ Zero new behaviour in core; bug parity with today's CLI is automatic. + Schema package keeps its grammar role. − Glob expansion stays a CLI concern; an MCP consumer that wants glob support must resolve patterns first.

D-007 · CLI subcommand becomes a thin shim; behavioural parity strict

Status
Accepted
Context
The CLI subcommand currently owns formatters (human/json/sarif), exit codes, and stdout. The kernel returns structured data; the CLI translates.
Decision
CLI's src/commands/validate.ts imports validateCommand from @spectastic/core/commands/validate; passes the resolved file list; receives ValidateResult; runs the existing human/json/sarif formatters against result.findings; calls process.exit(result.exitCode). Existing packages/cli/test/cli.test.ts integration tests stay verbatim as the regression detector for FR-006.
Consequences
+ The CLI keeps its existing test coverage; refactor is type-safe. + No user-visible change. − Glob expansion + read errors are split between CLI (glob, read) and kernel (validation) — slight increase in the read-error code path's surface.

D-008 · Unit-first test approach; CLI integration tests untouched

Status
Accepted
Context
Two test layers catch different bugs: kernel unit tests (input → result, deterministic; stub ctx.fs) catch logic regressions; CLI integration tests (process spawn, real fs) catch wiring regressions.
Decision
packages/core/test/validate.test.ts lands first: in-memory ctx.fs stub with three fixture files (one clean, one with a finding, one missing); assert findings shape + exitCode for each. CLI tests stay verbatim; their green state proves wiring.
Consequences
+ SC-003 is satisfied by construction. + Unit tests run in <50 ms; fast feedback during the refactor. − Unit tests duplicate part of the integration coverage; acceptable cost for the bisectability.

7 · Risks & mitigations

RiskLikelihoodImpactMitigation
Eager-loading creep — src/index.ts accidentally re-exports a verb module, defeating subpath enforcement.MHBench's init-help-cold-start (150 ms) catches it on the first PR; ESLint rule could enforce later.
Type drift — @spectastic/cli and @spectastic/core pin different versions of Finding from schema.LMKernel re-exports schema's Finding directly (no new declaration); CLI imports from kernel. One source.
Subpath exports + TypeScript module resolution friction — older Node module-resolution modes don't honour exports.LMProject pins moduleResolution: "NodeNext" in tsconfig (matches existing packages); Node ≥20 honours exports natively.
Behaviour drift — kernel produces subtly-different findings than today's CLI.LHCLI integration tests stay verbatim (D-007); they fail loudly on drift. SC-004 enforces byte-identical full-project output.
subagent() shape locked too early — 013's actual implementation needs a different surface.MLPre-1.0 versioning (FR-012) allows minor-bump breakage; 013's PR can refine the shape if needed; signature is documented as provisional.

8 · Complexity tracking

Two deliberate additions warrant flagging:

Forward-looking AIProvider interface (D-004). Ships three method signatures (chat, ask, subagent) with zero implementations in 006. The user explicitly chose this over a minimal-now interface to keep 007 and 013 as additive PRs. Cost: a reader of @spectastic/core's types sees methods that have no purpose in v1. Mitigated by docblock prose explicitly naming which sibling spec lights each one up.

Custom FileSystem interface (D-005) over raw node:fs/promises. Adds an abstraction layer that v1 doesn't strictly need (validate only reads files via the CLI's glob). Justified because the abstraction is what makes the kernel callable from non-Node consumers (MCP, VS Code) — abstracting later means a breaking change in the same PR that adds the second consumer. Pay the cost once, now.
