Kernel extraction — @spectastic/core as the verb-logic spine

Pull the eight slash-command procedures into one TypeScript package the CLI, the future MCP server, and the future VS Code extension all share. Start with one verb; prove the shape; repeat.

1 · Context

Eight slash commands (principles, spec, plan, tasks, implement, propose, apply, triage) are markdown procedures executed by the LLM in-process; only validate has TypeScript code, split between @spectastic/cli (wiring + formatters) and @spectastic/schema (parser + rules + engine). This works for Claude Code today but doesn't scale to Tier 2 MCP, Tier 3 VS Code, or Tier 6 web editor — each would re-implement every verb.

The trigger to do this now is the bench scaffold at f3e249d (bench/measure.mjs + bench/baselines.json). Kernel extraction is exactly the change that can accidentally eager-load parse5 on the init path (the I-019 failure mode); the bench is its regression guard. Without it, the kernel work would ship and silently regress.

2 · User scenarios & testing

Each story is independently testable: if you implemented only US1, you would still have a viable MVP that proves the shape.

US1 · CLI consumer sees no change P1

As a contributor or CI consumer running spectastic validate, I want to see byte-identical behaviour before and after the extraction so that the extraction is invisible to my workflow — same exit codes, same output, same flags.

Acceptance: Running the full-project validate (node packages/cli/dist/index.js validate "specs/**/*.html" "examples/**/*.html" inbox.html principles.html) before and after the extraction produces identical stdout (modulo any trivial whitespace normalisation) and the same exit code (0 on the clean repo). The bench passes within budget.

US2 · Future verb extraction has a pattern to follow P1

As a contributor extracting the second verb (likely triage in a sibling slice), I want to import the existing kernel function and copy its shape so that I'm not re-deriving the architecture from scratch and the second verb's PR is purely additive.

Acceptance: The second extraction's PR adds packages/core/src/commands/<verb>.ts alongside validate.ts; the new function follows the same signature shape (input: VerbInput, ctx: KernelContext) => Promise<VerbResult>; the package's exports field gains one new subpath. No refactor to the existing validateCommand is required.

US3 · Downstream surface imports the kernel directly P2

As a future MCP server or VS Code extension author, I want to import validateCommand from @spectastic/core/commands/validate and call it without spawning a CLI process so that tool-call latency is in the millisecond range rather than the 100ms+ Node-startup range.

Acceptance: A separate Node program (or in this slice, a test file under packages/core/test/) calls validateCommand(input, ctx) against a fixture and receives the same findings the CLI produces. No process spawn; total call time is well under 10 ms once the module is loaded.

Edge cases

Five tracked failure modes the extraction handles
  • Subpath exports unavailable — fallback path if Node <16.8 ever needs to consume the package. Out of scope: Node 20+ is already required project-wide.
  • tsup multi-entry config drift — if subpath outputs ever stop building, the test harness's import will fail loudly; CI catches it before merge.
  • Eager re-export creep — a future contributor adds export * from './commands/foo' to the umbrella index.ts; the bench's init-help-cold-start budget catches the regression because parse5 would land eagerly on init.
  • Type drift across packages — @spectastic/cli pins @spectastic/schema's Finding type while @spectastic/core re-exports a different version. Mitigation: kernel re-exports schema types directly; one source of truth.
  • Behaviour drift in the extraction — the kernel function returns subtly-different results than the pre-extraction CLI did. Mitigation: the existing CLI integration tests (packages/cli/test/cli.test.ts) stay; SC-004 enforces byte-identical output.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional — the kernel package

A new package @spectastic/core MUST exist at packages/core/, parallel to packages/cli/ and packages/schema/. It MUST follow the established workspace shape (package.json, tsconfig.json, tsup.config.ts, src/, test/) and use the same build tool (tsup), test runner (vitest), and TypeScript version as the other packages.

The package MUST declare per-verb subpath exports in its package.json exports field. Consumers MUST import each verb from its own subpath (e.g. import { validateCommand } from '@spectastic/core/commands/validate') — never via an umbrella re-export. The package's main entry (.) MUST export only types (KernelContext, AIProvider, per-verb input/result interfaces) and MUST NOT eagerly load any verb's command code.

Every verb function MUST follow the signature async function <verb>Command(input: <Verb>Input, ctx: KernelContext): Promise<<Verb>Result>. The function MUST be pure with respect to its arguments: all IO, AI access, and prompt UX flow through ctx; no module-level side effects; no implicit process.cwd(), process.env, or console usage inside the function body.

validateCommand MUST be implemented at packages/core/src/commands/validate.ts as the first worked example. It MUST wrap @spectastic/schema's validate / validateMany functions and return a ValidateResult shape that includes findings, exitCode, and the resolved input metadata. It MUST NOT touch the filesystem directly — file reads flow through ctx.fs (or a callback provided by the caller).

The @spectastic/cli's validate subcommand MUST import validateCommand from @spectastic/core/commands/validate (not from @spectastic/schema directly). The subcommand owns the shell-side concerns: glob expansion, file reads, output formatting (human/json/sarif), exit code translation. The kernel function owns the deterministic core: parse + validate + structure the result.

CLI behaviour MUST be unchanged post-extraction. The exit-code contract (0 clean, 1 findings, 2 usage / invalid args), the output formats (human / json / sarif), the finding shape, and every existing flag MUST match pre-extraction behaviour byte-for-byte (modulo trivial whitespace normalisation). No user-visible change.

The package MUST define the KernelContext and AIProvider TypeScript interfaces in its main entry, even though validate does not consume AIProvider. Defining the surface now lets the second verb's PR add the Claude adapter additively rather than as a major surface change; downstream consumers (MCP, VS Code) can plan their wiring against v1 types.

Each verb function's docblock MUST link to the canonical procedure file (commands/spectastic.<verb>.md for slash-command verbs; the docblock itself for verbs without a slash command, like validate). The markdown procedure remains the source of truth the LLM reads at slash-command invocation; the kernel docblock summarises and points back. The markdown MUST NOT be auto-generated from the docblock in v1.

Slash commands MAY instruct the LLM to invoke spectastic <verb> via Bash for deterministic operations, but MUST NOT be required to. Existing markdown procedures continue to work end-to-end without the kernel; the kernel is an alternate code path, not a hard dependency. The v1 of this slice does not modify any slash-command markdown (validate has no slash command; the seven that do are out of scope).

The kernel function MUST be unit-tested at packages/core/test/validate.test.ts as a pure function: no process spawn, no real filesystem IO (use stub ctx.fs or in-memory fixtures). The existing packages/cli/test/cli.test.ts integration tests MUST stay green; together the two layers catch logic regressions (kernel test) and wiring regressions (CLI test).

The package MUST declare "publishConfig": {"access": "public"} and follow the established synced-version policy: @spectastic/core, @spectastic/cli, and @spectastic/schema share the same version number on every release. The publish workflow's version-verify gate (004 FR-003) MUST be extended to cover the new package.

The package's README SHOULD document the pre-1.0 versioning policy explicitly: breaking changes to the kernel API MAY land in minor version bumps until 1.0.0, at which point strict semver applies. Downstream consumers SHOULD pin tightly (~0.2.0) rather than loosely (^0.2.0) during the pre-1.0 phase.

Non-functional

The extraction MUST NOT regress any scenario in bench/baselines.json past its declared budget. The bench's init-help-cold-start scenario (150 ms budget) is the explicit regression guard for the I-019 lazy-import failure mode — if it ever exceeds budget, parse5 has crept onto the init path via the kernel.

The validate-full-project bench scenario's p50 SHOULD stay within ±20% of today's baseline (175 ms on M1 dev; 295 ms on ubuntu-latest CI). Re-export through @spectastic/core should add negligible overhead when subpath exports are wired correctly.

Out of scope (deferred to other slices)

  • Extract /spectastic.triage — second verb pick; exercises AI adapter on a low-stakes verb.
  • Extract /spectastic.implement; drain modes (--all / --phase / --parallel) deserve their own slice.
  • Extract /spectastic.spec; tests AIProvider.ask<T>() end-to-end.
  • Extract /spectastic.plan; pairs with spec.
  • Extract /spectastic.tasks; deterministic generation from spec + plan.
  • Extract /spectastic.propose; adversarial-pass spawn needs sub-agent semantics on AIProvider.
  • Extract /spectastic.apply; mostly deterministic (deltas, archive, changelog).
  • Extract /spectastic.principles; smallest of the slash verbs.
  • MCP server wrapping the kernel (Tier 2). Needs at least 3-4 verbs extracted first.
  • VS Code extension (Tier 3); same multi-verb dependency.
  • Web editor (Tier 6); deferred pending VS Code usage data.
  • OpenAI / local-LM AIProvider adapters. Claude adapter lands with the second verb; others are a separate slice.
  • Cross-tool installers (Cursor, Aider, Copilot). Tier 2; presumes kernel + MCP both shipped.
  • Auto-generating slash-command markdown from kernel docblocks. Decided against — markdown stays canonical.
  • Making slash-command Bash-invocation of the kernel mandatory. Decided against — kernel is an alternate code path.

4 · Data model

Two types this slice owns: KernelContext (the injected IO/AI surface) and the per-verb Input/Result interfaces (one pair per verb; v1 ships ValidateInput + ValidateResult).

Entities

KernelContext
Fields: cwd: string (the directory to resolve relative paths against), fs?: FileSystem (optional; defaults to a thin wrapper over node:fs/promises when the caller doesn't supply one), ai?: AIProvider (optional; undefined for deterministic verbs like validate; required for verbs that prompt the model). Passed by every kernel function; never read from globals.
AIProvider
Interface declaring chat(prompt, opts?) for freeform model invocation and ask<T>(questions) for the typed bounded-choice pattern used by the decision-phase interviews. v1 ships the interface only; the Claude implementation lands with the second verb.
ValidateInput / ValidateResult
ValidateInput: files: string[] (resolved paths or glob patterns), format?: 'human' | 'json' | 'sarif', ignore?: string[]. ValidateResult: findings: Finding[] (re-exported from @spectastic/schema), exitCode: 0 | 1 | 2, filesValidated: string[]. The CLI's validate subcommand translates ValidateResult into stdout output + process exit code; downstream surfaces consume the structured shape directly.

5 · Success criteria

Technology-agnostic, measurable outcomes.

pnpm test passes post-extraction with at least the current count plus the new kernel-level unit tests for validateCommand. No existing test moves to skipped or pending.

pnpm bench passes all four scenarios on CI with p50 within their declared budgets in bench/baselines.json. The init-help-cold-start scenario's p50 remains within ±20% of today's baseline (52 ms on CI).

A test file under packages/core/test/ imports validateCommand from @spectastic/core/commands/validate, calls it against an in-memory fixture, and receives the same findings shape the CLI produces against the same fixture file. No process spawn required for this test.

Running node packages/cli/dist/index.js validate "specs/**/*.html" "examples/**/*.html" inbox.html principles.html produces stdout byte-identical (modulo trivial whitespace normalisation) to the pre-extraction baseline, with the same exit code (0 on a clean repo).

6 · Assumptions

Four preconditions: pnpm workspace, tsup multi-entry, Node 20 subpath exports, bench discipline already shipped.

pnpm workspaces support three sibling packages (cli, schema, core) with cross-package workspace:* dependencies, matching today's two-package shape extended by one. No tooling change required.

tsup supports multi-entry output for subpath exports via its entry array config. Each entry compiles to its own JS + .d.ts pair; the package's exports field references them. Established pattern in the ecosystem; no novel build work.

Node 20+ honours the package.json exports field with subpath patterns. Already a hard requirement project-wide via engines.node.

The bench scaffold (bench/measure.mjs + bench/baselines.json) runs in CI as a step in the build-and-test job and gates merge on regression. Already shipped at commit f3e249d; this assumption is verified, not future-tense.
