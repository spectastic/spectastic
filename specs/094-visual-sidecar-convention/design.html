Design · 094-visual-sidecar-convention

Visual sidecar convention

How we will build it.

Status Accepted Spec 094-visual-sidecar-convention Owner Brian Corbin · @briancorbinxyz Branch spec/093-design-visual-section Created 12 Aug 2026 Read time

Two checks and a guard, on machinery 093 already built. A declared path must sit at its scope's conventional location — a token set under the project's visual/, screens under their own spec's — which is what turns a named convention into one a second author cannot get wrong. Two designs disagreeing about where the token set lives is an error rather than a union, because there is one design system and two paths are two claims about it. The resolve half of this spec's own FR-003 is already built, in 093, and inheriting it rather than rebuilding it is the largest single thing this design decides.

3 · Data model & contracts

The spec's three conceptual entities are all locations or references to them. None is persisted; the declaration, not the filesystem, is the authority, so nothing here enumerates a directory's contents.

Conceptual entityPhysical shapeNotes
Project visual directory <root>/visual/ — a path prefix, never a listing. Exists when something is declared into it. Nothing creates it, and nothing reports its absence.
Feature visual directory specs/<spec-id>/visual/, the spec id taken from the declaring design's own path. Zero or one per spec. A design outside specs/ has no owning spec, so the check stands down rather than guessing.
Declared path DeclaredVisualPath { path, kind, specId, ratified } — already produced by 093's reader. kind is what makes the scope check expressible at all: without it, a path is just a string with no idea which convention governs it.

This feature exposes no interface. It adds two checks over declarations another spec defined, consumed entirely inside the tool.

5 · Approach

Two pure functions and one guard. The location check takes the declarations a design already parsed plus the file they came from, and reports a path that sits outside its scope's conventional location — a prefix comparison on strings, no filesystem access at all. The disagreement check reads the project-wide state the gating scan already computes and reports more than one distinct token-set path. The guard is a test asserting no visual check module names an image, which is how a negative requirement survives the commit that would quietly violate it.

Nothing else is owed. The resolve half landed with 093 and is inherited; the ignore requirement turned out to be already satisfied and needs a test rather than a change. That two of this spec's six functional requirements resolve to "already true, now guarded" is the honest result of slicing a convention out from the declaration it governs, and is recorded rather than padded.

This design carries no Visual surface section, and its sections therefore run 1–12 rather than 1–13. That is 093 FR-002 working on the first design authored after it landed: spectastic has no user interface, so the scaffolded section was deleted rather than filled in. The differing numbering between this document and an interface project's is exactly the consequence 093's D-002 predicted, which is why every cross-reference in the template is now a named link.

6 · Alternatives considered

The question with real alternatives was how strictly to hold a declared path to its conventional location. Scored on whether it makes SC-003 true — an author can place a file from the convention alone — on false-positive risk, and on whether it enforces the MUST that FR-001 actually states. 5 is best.

OptionMakes SC-003 trueFalse-positive riskEnforces the stated MUSTTotal
Warning at both scopes3519
Error on scope, silent on the directory name25310
Error at both scopes — chosen54514

The scope-only option is the interesting loser. It catches the confusion US2 actually describes — a project file placed in a feature directory — while leaving the name free, which reads as tolerant. But an author who may name the directory anything cannot determine a location from the convention alone, which is the criterion SC-003 names, and the spec's own rationale chose visual/ on collision evidence rather than taste. Tolerance here would spend that reasoning and get nothing for it.

7 · Decisions

D-001 · A declared path must sit under its scope's conventional prefix, and not merely inside the project

Status
Accepted
Context
FR-001 and FR-002 are both MUST-tier and name exact locations; SC-003 asks that an author can place a file from the convention alone. 093 checks only that a path resolves, which a token set under design/ does perfectly well. The declaration already carries kind, so the check is expressible without new plumbing.
Decision
A tokens path must resolve under <root>/visual/; a screens path under specs/<owning-spec-id>/visual/, the id taken from the declaring design's own path. Error severity. A prefix comparison, never equality, so FR-008's permission to subdivide survives.
Consequences
+ The convention is enforced rather than described, which is the difference between a convention and a paragraph. + A wrong-scope path — the confusion US2 names — is caught by the same check. − A project with a genuine reason to organise differently is blocked with no waiver; the escape hatch is a proposal, which is heavier than a flag and deliberately so. − The screens rule needs an owning spec id, so a design outside specs/ is unchecked; stated rather than papered over.

D-002 · The disagreement check extends the project pass that already runs

Status
Accepted
Context
declaredVisualState already walks every design once per validate and returns every declared path tagged with its declaring spec. FR-004 needs exactly that set and nothing more. A third independent pass would re-read every design to learn what one already knows.
Decision
Compute the distinct token-set paths from the state the gating scan already has, and report one error per project when there is more than one — naming every disagreeing path and the spec that declared it, since a reader told only that paths disagree cannot act.
Consequences
+ No additional filesystem cost, which is what keeps NFR-001 true. + Provenance comes free, because the state already carries it. − Reported once per project rather than per file, so it appears against the project rather than a line; a validate run over a single file cannot see it at all, which is the same honest limit every cross-project check here has.

D-003 · A negative requirement gets a guard test, not a sentence

Status
Accepted
Context
FR-005 is a prohibition: no check may depend on a rendered image, and its absence must never be reported. Prohibitions are the easiest requirement to satisfy today and lose next quarter, because nothing fails when someone adds the dependency — which is the shape of failure P-8 exists to refuse.
Decision
Assert it over the source: no visual check module references an image extension or an images directory. Plus a fixture project carrying declarations and zero renders, asserted to validate clean.
Consequences
+ The commit that makes a render load-bearing fails a test rather than passing review. + Cheap and fast — a string scan over three files. − A source scan is a proxy: someone could depend on an image without naming an extension, and the test would not see it. It raises the cost of the mistake rather than making it impossible, and saying which of those it is matters.

D-004 · The ignore requirement is already satisfied, so it gets a test and no change

Status
Accepted
Context
FR-006 asks that the scaffolded ignore rules not exclude either visual directory. Reading them settles it: BASE_ENTRIES holds two spectastic-output entries and ECOSYSTEM_IGNORES holds build artifacts across seven ecosystems, with no image pattern anywhere. This repository's own /*.png is root-anchored and says nothing about a subdirectory — which is the spec's third edge case, already a non-event.
Decision
Change nothing. Add a test asserting no scaffolded ignore entry would exclude a file under either visual directory. Do not add a defensive negation entry.
Consequences
+ No entry is added that negates something nothing ignores, which would puzzle every future reader of the managed block. + A future entry that would break it fails a test. − "Already satisfied" is a weaker guarantee than "enforced", since it holds only for the entries spectastic writes and says nothing about a rule the project wrote itself — which is exactly what the requirement's SHOULD tier admits.

D-005 · FR-003 is inherited from 093 rather than implemented here

Status
Accepted
Context
This spec's FR-003 and 093's FR-010 state the same requirement in almost the same words. 093 could not defer it — a declaration nothing checks is prose, its own rationale — so it was built there, and this spec's change log already records that.
Decision
Implement nothing for FR-003. The verify view's trace cites 093's tests for it rather than duplicating them, so the requirement is traced to a real proof rather than quietly unproven.
Consequences
+ One implementation, one test suite, no divergence. − Two specs describe one check, so this spec's implementation is smaller than its requirement count suggests; the change log note is the only thing that stops that reading as work skipped.

Anywhere this plan introduces complexity not strictly required by the spec, justify it here.
