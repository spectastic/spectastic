Specification · 094-visual-sidecar-convention

Visual sidecar convention

Two directories, at two scopes, with a rule for what may live in each — the place every other visual slice writes into.

Status Accepted Spec ID 094-visual-sidecar-convention Owner Brian Corbin · @briancorbinxyz Reviewers — Created 12 Aug 2026 Principlesv1.9.0 Smallest demoableA project with a declared token set validates, and one whose token path has moved reports exactly one error. Read time

093 gave the design a section that declares a token set and the screens a feature touches. It deliberately said nothing about where those files live. This spec answers that, and the answer has two halves because the things being declared have two cardinalities: a project-scoped directory for the design system every feature shares, and a feature-scoped one beside the spec that owns its screens. It fixes the name — visual/, chosen against two candidates that collide with vocabulary already in use — states what may and may not live there, and settles the question the sibling specs would otherwise each answer differently: renders are evidence, not baselines, so they are optional and never load-bearing. It also closes a small inconsistency the exemplar exposed, where a repository ignoring root images has no policy for images anywhere else.

1 · Context

093 declares a token set and a screen inventory by path and deliberately refuses to say where those paths point. That refusal was correct — it kept 093 to one slice — but it leaves every sibling slice free to invent a different answer, and the worked exemplar already proved the risk: it placed everything at the project root while the survey said the sidecar sat beside the spec, and neither noticed for a day.

Two directories are needed rather than one because the declared things have different cardinalities. A design system is shared by every feature; a screen belongs to the feature that draws it. The users are the author choosing where to put a file, and the check that has to find it again later.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · A declared path is found, or the failure is loud P1

As an author, I want to be told when a declared visual path no longer resolves so that a moved token set is a build failure rather than something a reader discovers.

Acceptance: Validating a project whose declared token path has been moved or renamed produces exactly one error naming that path; validating the same project before the move produces none.

US2 · The two scopes are unambiguous P1

As an author adding a screen, I want to know without asking whether it belongs to my feature or to the project so that two features do not each place the same kind of file differently.

Acceptance: The convention names one location for project-scoped material and one for feature-scoped, and a file of either kind placed in the other location is reported.

Edge cases

  • A project whose token set extends an external one, where only overrides are local — the local directory exists and is thin, which is correct rather than incomplete.
  • A feature that touches no screen. Its feature-scoped directory is absent, not empty.
  • A repository that ignores images at the root, which says nothing about images anywhere else.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

Project-scoped visual material — the token set and anything else shared by every feature — MUST live in a single directory at the project root, named visual/.

Rationale

The name is chosen against collisions rather than taste. surface is the most-loaded word in modern design-system vocabulary; views means a component in the platform SDKs this is aimed at and a generated artifact inside this tool; references belongs to the knowledge corpus and contracts to 070.

Feature-scoped visual material — the screens a feature touches and their annotations — MUST live in a directory of the same name beside the spec that owns it.

Rationale

The same name at two scopes is deliberate, and mirrors 070, where a proposed contract and an effective one share a name and differ by location.

A declared visual path MUST resolve to a file or a directory inside the project, and a path that escapes the project directory MUST be rejected rather than followed.

Two designs in one project MUST NOT declare different paths for the project's token set. A disagreement MUST be reported as an error rather than resolved by precedence or union.

Rationale

There is one design system, so two paths are two claims about one thing. A union is right for N contracts and meaningless here — the failure declaredInterfaceState's accumulate fix would otherwise reproduce.

A rendered image of a screen MUST be treated as evidence for a reader and MUST NOT be load-bearing: no check may depend on one being present, and its absence MUST NOT be reported.

Rationale

Follows from the survey's central decision. Fidelity is established by measuring a running artifact against declared tokens, never by comparing images, so an image is something a human looks at. Making it load-bearing would reintroduce the baseline-image workflow that decision exists to refuse.

A project SHOULD be able to commit rendered images without a repository-wide image policy silently excluding them, and the scaffolded ignore rules SHOULD NOT exclude either visual directory.

Rationale

This repository ignores root-level images, which is a root-level decision that has never said anything about images elsewhere. A convention that places images somewhere an existing rule silently drops them would be a trap.

Material that already has an owning convention SHOULD NOT be placed in either directory — a contract belongs to 070's location and a citable document to the corpus.

A project MAY subdivide either directory, and the convention MAY place no constraint on that layout beyond the declared paths resolving.

Non-functional

Path resolution MUST stat only the declared paths: at most 1 filesystem call per declaration, and at most 0 directory walks, so that a project with many specs pays a cost linear in declarations rather than in files.

Rationale

The bound the contract resolve check already holds to. An unbounded walk finds vendored copies and costs unbounded time on a monorepo.

The check MUST be deterministic: the same project state produces byte-identical findings across at least 3 consecutive runs, with at most 0 reads of the clock, the network or the environment.

Out of scope (deferred to other slices)

  • What the files in these directories actually contain — the element family for screens, states and annotations.
  • The axis grid, which is project-scoped material this convention gives a home to without describing.
  • Where a component lives at each of its states, and the move between them.
  • Versioning the token set this convention locates.
  • Reading anything in these directories to check a build against it.

4 · Data model

No persisted entity. This spec adds two locations and a policy about what occupies them.

Entities

Project visual directory
One per project, at the root. Holds material every feature shares. Exists when the project has declared any; absent otherwise.
Feature visual directory
Zero or one per spec, beside it. Holds material belonging to that feature alone.
Declared path
A project-relative reference from a design to something in either directory. Resolves to a file or a directory, or the declaration is in error.

Neither directory is a registry. Nothing enumerates their contents, and a file present but undeclared is invisible to every check here — which is the same posture the contract convention takes, and the reason the declaration rather than the filesystem is the authority.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For a project whose declared visual path has moved, validate reports exactly 1 error naming that path; before the move it reports 0.

Across a project with several designs, the count of distinct declared project token-set paths is 1, or the disagreement is reported.

An author placing a new visual file can determine its correct location from the convention alone, without reading another spec's directory to infer it.

6 · Assumptions

One project has one design system. A repository holding two products with two token sets would need two project directories, which this convention does not provide — the same limitation the project-shape work will meet when it asks whether shape belongs to the project or the unit.

Authors will commit rendered images if the convention permits it. If they do not, nothing breaks: renders are evidence and their absence is never reported.

7 · Open questions

None outstanding. The name was settled on collision evidence, the two scopes follow the cardinality split the survey landed, and the renders-are-evidence rule follows from the decision that fidelity is measured rather than compared.
