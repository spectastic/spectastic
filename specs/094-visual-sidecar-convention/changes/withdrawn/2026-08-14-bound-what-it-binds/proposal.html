Change proposal · 094-visual-sidecar-convention

Bound what it binds

A budget whose stated reason is wider than its stated scope. It has now misled two separate pieces of reasoning.

Status Withdrawn Change ID 2026-08-14-bound-what-it-binds Spec 094-visual-sidecar-convention Author Brian Corbin · @briancorbinxyz Created 14 Aug 2026 Targets 1 requirement — 1 modified Read time

NFR-001 binds path resolution — one filesystem call per declaration, zero directory walks — and then explains itself with a promise about something it does not bind: "so that a project with many specs pays a cost linear in declarations rather than in files." That is a claim about the whole validate pass. Materialising a view runs in the same pass, reads every screen file, and is bounded separately by 099 NFR-003. The numbers stay; the purpose clause narrows to the operation it governs.

Bound what it binds

Withdrawn

1 · Intent

The requirement is right and its reason is too big. Subject: "Path resolution MUST stat only the declared paths." Purpose: "so that a project with many specs pays a cost linear in declarations rather than in files." The first binds one operation; the second describes what a whole validate pass costs. Nothing in this spec makes the second true, and something in the codebase makes it false — materialiseVisualViews reads every screen file under a declared directory, in the same pass, on every validate.

That is not a violation. Materialisation is a different operation with its own budget: 099 NFR-003 allows it "under 100 ms … for a feature declaring up to 20 screens" — a bound that plainly contemplates reading many files. Two requirements, two operations, no conflict. The defect is only that this one's stated reason claims territory it never bound.

It is worth fixing because it has already done damage twice, and both times to careful readers. 093's correction cited this budget as its justification for giving up an enumerating check — a capability surrendered to protect a bound that was never at risk. And a triage card filed against this spec repeated the reasoning and claimed a violation that does not exist. A sentence that misleads twice in two days is not prose to leave alone.

2 · Scope

In scope

  • Narrowing NFR-001's purpose clause so it describes the cost of the operation the requirement binds, and stops asserting a property of the whole pass.
  • Recording in the rationale that materialisation is bounded elsewhere, so the next reader who wonders where the whole-pass cost lives has somewhere to go instead of concluding it is unbounded.

Out of scope

  • The numbers. One filesystem call per declaration and zero directory walks are the right bound for path resolution and are unchanged — this narrows a reason, never a limit. defer-to=never.
  • Introducing a whole-pass budget. Nothing has asked for one, no reader has been harmed by its absence, and inventing an unowned cross-spec NFR to satisfy a sentence would be a much larger claim than the sentence was making. defer-to=TBD-validate-pass-budget.
  • Anything about materialiseVisualViews. It honours the budget that governs it; the belief that it violated this one was the error being corrected. defer-to=never.
  • 093 FR-014, which was narrowed on the strength of this sentence. Whether that correction should be revisited is 093's question and needs its own propose — the apply kernel folds same-spec deltas only. defer-to=093-design-visual-section.

4 · Deltas

What changes: the purpose clause only. The bound, its numbers and its subject are untouched.

Path resolution MUST stat only the declared paths: at most 1 filesystem call per declaration, and at most 0 directory walks, so that resolving a project's declarations costs time linear in the number of declarations rather than in the number of files beneath them.

Rationale

The bound the contract resolve check already holds to. An unbounded walk finds vendored copies and costs unbounded time on a monorepo. Both unchanged — this is the same limit on the same operation.

The purpose clause previously read "so that a project with many specs pays a cost linear in declarations rather than in files", which is a statement about a whole validate pass rather than about resolution. This requirement never bound a pass, and other work in that pass legitimately reads more: materialising a view reads the screen files it projects, under its own budget at 099 NFR-003, which permits up to 20 screens per feature. Naming that here so a reader who follows the old promise finds where the cost actually lives.

Narrowed rather than widened deliberately. Making the subject match the old purpose — binding the whole pass — would put a conforming implementation in violation on the day it landed and contradict 099's deliberate allowance. The sentence was wrong about its own reach, not about its limit.
