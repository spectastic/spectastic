Change proposal · 094-visual-sidecar-convention

Bind the checks

One consumer relies on the wide reading. One falsifies it. Both are right, so the requirement has to say which.

Status Withdrawn Change ID 2026-08-14-bind-the-checks Spec 094-visual-sidecar-convention Author Brian Corbin · @briancorbinxyz Created 14 Aug 2026 Targets 1 requirement — 1 modified Read time

NFR-001 binds path resolution and then explains itself with a claim about the whole pass: "a project with many specs pays a cost linear in declarations rather than in files." A shipped comment relies on that wide reading as a real constraint; the view materialiser contradicts it in the same pass. The subject widens to cover every check, and view materialisation becomes a named exception with its reason — so the sentence stops being false without losing the constraint something already depends on.

Bind the checks

Withdrawn

1 · Intent

The requirement's subject and its reason disagree. The subject binds path resolution: one filesystem call per declaration, zero directory walks. The reason promises something larger — that a project with many specs pays a cost linear in declarations rather than in files, which is a property of the whole validate pass.

Both halves have a live consumer, which is why this took two attempts to see. The wide reading is relied upon: the doc comment on scanVisualProject — the function implementing FR-004's cross-design token-set check — reads "computing it per file would re-read the whole estate N times and is what NFR-001's 'linear in declarations, not in files' excludes." That is the constraint keeping that scan to one pass, and it is correct. The wide reading is also false: materialiseVisualViews walks the declared screens directory and reads every file in it, on every document carrying a declaration, in that same pass.

An earlier attempt narrowed the reason to match the subject. That was withdrawn: narrowing would have orphaned the constraint scanVisualProject depends on, and its replacement rationale claimed materialisation was bounded by 099 NFR-003 — which is should-tier and bounds a design generation, not a validate. So the correction would have written a false cross-spec claim into a must-tier requirement while removing a real one.

The reason was never too big. It was addressed to the wrong subject, and it lacked the one exception that makes it true.

2 · Scope

In scope

  • Widening NFR-001's subject from path resolution to every check in the pass, which is what the reason has always described and what one implementation already treats as binding.
  • Naming view materialisation as an exception, with its reason — it exists to project file contents, so it cannot be linear in declarations, and pretending otherwise is what made the sentence false.
  • Recording that the exception is currently unbounded at must-tier, rather than implying a bound exists somewhere it does not.

Out of scope

  • The numbers. One call per declaration and zero walks stay exactly as they are for everything the requirement binds. defer-to=never.
  • Giving materialisation a must-tier budget of its own. It needs one — 099 NFR-003 is should-tier and governs generation, so nothing absolute covers the validate-time cost — but inventing a number here, in the spec that does not own the view, would be the same cross-spec overreach just withdrawn. defer-to=099-visual-embedded-view.
  • Changing materialiseVisualViews. It is not in violation once the exception is stated; whether its cost is acceptable is 099's question. defer-to=099-visual-embedded-view.

4 · Deltas

What changes: the subject widens to every check; view materialisation becomes a named exception. The numbers are untouched.

Every check MUST stat only the declared paths: at most 1 filesystem call per declaration, and at most 0 directory walks, so that a project with many specs pays a cost linear in declarations rather than in files. Materialising a view MUST NOT be read as a check for this purpose — it projects file contents and is necessarily linear in files — and its cost MUST be bounded by the spec that owns the view rather than here.

Rationale

The bound the contract resolve check already holds to. An unbounded walk finds vendored copies and costs unbounded time on a monorepo. Unchanged, and now stated over everything it was always meant to cover.

The subject was path resolution while the reason described the whole pass, and both readings had a live consumer. scanVisualProject cites the wide reading as the constraint keeping FR-004's cross-design check to one pass, which is correct and would have been orphaned by narrowing. The view materialiser contradicts it, which is what made the sentence false. Widening the subject keeps the first; the exception admits the second instead of pretending it away.

The exception is deliberately narrow and deliberately incomplete. Materialisation reads file contents to project them — no phrasing makes that linear in declarations. But nothing at must-tier currently bounds it: 099 NFR-003 is should-tier and governs a design generation, not a validate. Pointing at the owning spec rather than inventing a number here is the same discipline that withdrew the previous attempt, which claimed a bound that did not apply.
