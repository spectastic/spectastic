A place for a render

A render is permitted, never required, and never mentioned — so no project has one. Visible absence, without a check that depends on presence.

A place for a render

Applied

1 · Intent

The first real downstream project reached a validating design with eleven declared states and zero renders. No check, prompt, command or template ever mentioned one. The element exists and has never been used outside a fixture.

This is not a rule being broken. FR-005 says a render is evidence for a reader and must not be load-bearing — no check may depend on one being present — and that is right, for the reason it was written: a design system whose validation demands screenshots turns every visual change into a re-capture chore, and the picture is not the authority.

What happened is that never required was built as never mentioned. Those are different, and the gap between them is where a whole capability went unused. An empty slot invites filling; an absent concept does not exist.

2 · Scope

In scope

  • A place for a render in the generated view, per state, showing its absence plainly.
  • FR-005 left exactly as it is — nothing here makes a check depend on a render.

Out of scope

  • Capturing renders. Producing an image is a build concern and the sources differ per platform. defer-to=TBD-render-capture.
  • Landing renders through the design import. Worth deciding, and it belongs with the importer rather than with the convention. defer-to=TBD-import-renders.
  • Comparing a render to anything. Fidelity is measured against declared tokens, never by comparing pictures, and that position is unchanged. defer-to=never.

3 · Approach

A slot, not a check. The generated view gains a render cell per state which reads not recorded when empty — the same mechanic the observables trace and the run block already use, and for the same reason: an unfilled field is visible in a way a missing concept is not, and it costs nothing when a project has no renders and never will.

The alternative that reads as stronger is a warning when a declared surface carries no renders. It was rejected on a technicality that is not a technicality: a warning is a check, and it depends on absence. FR-005 says no check may depend on a render being present, and a rule that fires when none is present is that rule inverted. Taking it would mean amending FR-005, and FR-005 is right.

A prompt in the design command was the cheapest option and is the one that already failed. Nothing asked, because command markdown is where an expectation goes to be skipped — P-8 and triage T-009 both say so, and this artifact is the evidence.

4 · Deltas

A generated view of a declared surface MUST show, for each state, whether a render of it has been recorded, and an absent render MUST be shown as not recorded rather than omitted. No check MUST depend on a render being present.

Rationale

FR-005 makes a render evidence rather than a baseline, which is right — a validation that demands screenshots turns every visual change into a re-capture chore, and the picture is not the authority. It was implemented as never mentioning one, which is a different thing: the first real downstream project reached eleven declared states with no render and nothing anywhere had said the word.

A slot rather than a rule. An unfilled field is visible where an absent concept is not, and it costs nothing for a project that has no renders and never will. The same mechanic the observables trace and the run block already use.

The third sentence restates FR-005's constraint inside this requirement deliberately, because the tempting stronger version — warn when a surface has no renders — is that constraint inverted. A warning is a check and it would depend on absence. Written here so a later reader finds the argument rather than rediscovering the temptation.

5 · Risk register

Self-run rather than delegated. Recorded rather than glossed.

Eleven rows of "not recorded" is the noise this project has already been burned by

The estate's own precedent argues against this. The verify view's required toggle field reads as the literal string none in 50 of 61 views — a row of chrome costing every other row its attention — and the observables trace produced 77 gap rows across 37 artifacts with a 100% gap rate, which was diagnosed as the question being wrong for the population rather than as a backlog. A render slot on every state of every screen could reproduce both at once.

Mitigated. The requirement asks the view to show whether a render was recorded, not to render a prominent gap per state — so a screen with no renders can say so once rather than eleven times. The distinction is the lesson from those two precedents applied in advance instead of after 37 artifacts.

It sits one word away from contradicting the requirement it exists to respect

FR-005 forbids a check depending on a render's presence. This adds a requirement about renders to the same spec, and any future tightening of it — a warning, a completeness count, a coverage figure — crosses that line without obviously looking like it does.

Mitigated. The prohibition is restated inside the new requirement rather than left one section away, so the two cannot be read apart, and the rationale names the specific tempting version and why it was refused.

The slot has no filler

Capture is out of scope and import-of-renders is deferred, so this ships a place to put something nothing yet produces.

Accepted. A render is authored evidence and a person can commit one today — the sidecar convention already permits it and the ignore rules already allow it. The slot is what makes that possible to notice. Building capture first would be building a producer for a consumer that does not exist.

6 · Tasks

  • Add the render slot to the materialised view, showing absence once per screen rather than once per state.
  • Style it as the run block and observables trace style theirs, so an unrecorded slot reads consistently across the estate.
  • Mention renders in templates/design.html and the design command's visual questions — a nudge, explicitly not the guarantee.
  • Tests: absence renders as not recorded; a present render renders; no check fails for an absent render, asserted directly since that is FR-005 and the thing most likely to erode.

7 · Open questions

None outstanding. Capture and import are deferred as named slugs rather than left open here.
