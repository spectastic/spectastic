Cards

FR-009 contradicts FR-005 outright, and both are must-tier

Spec upstream

Debugging what a rule author should build, root cause was that the change landed a requirement whose central clause is the negation of a requirement already in the same document; fixed by narrowing FR-005's prohibition to what it was actually protecting; regeneration fails, because the spec now says both things and an implementer must pick one.

Expected
One position on whether a reader is told a render is absent.
Actual
Two, verbatim.

FR-005: "…no check may depend on one being present, and its absence MUST NOT be reported."

FR-009: "an absent render MUST be shown as not recorded rather than omitted."

Both must-tier. 099 restates the strong form independently, so the estate now asserts the prohibition twice and its negation once.

Diagnosis
The proposal raised a risk against FR-005 and dispositioned it mitigated on the ground that "the prohibition is restated inside the new requirement". What was restated is FR-005's first clause — the no-check-depends half. The absence-reporting half is the one FR-009 crosses and it is not addressed anywhere. The proposal's scope explicitly said "FR-005 left exactly as it is", which was the error stated as a feature: the change needed a MODIFY on FR-005 narrowing "reported" to mean a validate finding, and instead declared the requirement untouched. A self-run pass graded its own mitigation and did not read the sentence to the end.
Fix
specs/094-visual-sidecar-convention/spec.html — a propose. MODIFY FR-005 so the prohibition names what it protects (no validate finding, no gate) rather than all reporting, and MODIFY FR-009 to sit inside it. The intent behind FR-005 is right and survives; only its reach was wider than its reason.
Fixed
Applied 2026-08-14-narrow-the-prohibition. FR-005's prohibition now names what it protects — no finding, no gate — so the reach matches the reason and a view may still tell a reader nothing was captured. FR-009 was removed rather than repaired, because its real defect was placement.
Deep dive — cross-spec

099 FR-009 carries the strong form too, so the narrowing has to reach it or the contradiction just moves. Sequence the MODIFY on 094 first, since 099 is where the view actually lives and would otherwise be amended twice.

A prohibition written as a MUST, in the channel that exists to be machine-read

Spec upstream

Debugging why the safety clause reads oddly, root cause was that "No check MUST depend on a render being present" tags an absolute requirement onto the proposition it means to forbid; fixed by using the prohibition keyword; regeneration fails, because the construction is already in three places and reads as house style.

Expected
A prohibition uses MUST NOT. KB-0001@2026-07-25 commits the vocabulary, and the <spec-rule> wrapper exists precisely so a tool can find every must-tier requirement without parsing prose.
Actual
The negation sits in the subject, outside the tag. A reader parses it correctly; a machine reading <spec-rule> tags sees an absolute requirement asserted over "a check depends on a render being present" — the exact inverse. FR-005 gets the same constraint right one requirement earlier with "MUST NOT be load-bearing". One spec, one constraint, two conformance levels.
Diagnosis
Not a typo — 099 FR-006 and 099 FR-009 carry the identical construction. A spreading idiom, which is the argument for correcting it while it is in three places rather than thirty.
Fix
Fold into T-001's propose. Worth considering a check: a <spec-rule>MUST</spec-rule> preceded by a negating word in the same clause is mechanically detectable, and this is exactly the machine-readable channel P-8 says should carry the guarantee.
Fixed
The inverted construction is gone from the requirement that carried it, and its replacement in 099 FR-009 is written MUST NOT. The idiom survives elsewhere and is deferred as TBD-negated-must-rule — a <spec-rule>MUST</spec-rule> preceded by a negating word is mechanically detectable, which is the check worth having.

The requirement legislates a surface another spec owns, and contradicts itself on granularity

Cross-spec upstream

Debugging where the render slot belongs, root cause was that a requirement about the generated view landed in the directory-convention spec while 099 owns the view — and says the opposite about granularity; fixed by moving it; regeneration fails, because the next person will not look here.

Expected
094 adds two locations and a policy about what occupies them; its own out-of-scope defers what the files contain elsewhere. The view belongs to 099, which already owns every neighbouring requirement and explicitly permits a later slice to contribute a section without amending it.
Actual
FR-009 legislates the view from 094. Worse, it says "for each state" while the change's own task says "once per screen rather than once per state" — and the noise mitigation rests entirely on the task's reading. Only the requirement binds, so as applied it mandates the eleven-cell rendering the risk was raised to avoid, reproducing the 77-gap-rows and 50-literal-nones precedents it cites by name.
Diagnosis
099 is draft, so it takes an in-place edit with no ceremony. An accepted spec was re-opened through the heavy path to add a requirement that could have been authored for free in the draft spec that owns the surface.
Fix
Fold into T-001's propose: REMOVE FR-009 from 094 and author it in 099 at the granularity the mitigation assumed. Also fold the two out-of-scope slugs — TBD-render-capture and TBD-import-renders — into the live spec, since they exist only inside an archived proposal and are invisible to every backlog-audit resolution signal.
Fixed
FR-009 removed here and re-authored as 099 FR-013, in the spec that owns the view, at the granularity the mitigation had assumed: once per screen, with the per-state form now explicitly forbidden. The two orphaned deferrals are folded into this spec's out-of-scope block.

The correction reproduces the contradiction it corrects, in the spec it moved to

Cross Specupstream

Debugging whether the re-authored render slot is sound, root cause was that making render-presence content of a drift-checked view turns an absent render back into an error-severity finding — the exact defect this change existed to remove.

Expected
Moving the slot to 099 and narrowing FR-005 removes the contradiction.
Actual
099 FR-013 makes render-presence content of the materialised view. The drift check compares the whole artifact and errors. So the moment a screen's last render is removed the marker flips, the artifact stops round-tripping, and validate reports an error — colliding with 099 FR-009, 099 SC-003 ("deleting every render produces 0 findings about their absence") and the very FR-005 clause this change authored. Before FR-013 absence was genuinely silent; requiring the view to state it positively removed the escape.
Diagnosis
Two compounding errors of mine. The migration note said "nothing implemented it" — false: 099 is labelled draft but the render element, its shape rule, the materialiser and the drift check all ship, so the edit landed on running code. And the edit was performed under an out-of-scope label, so no delta carried FR-013's text and no reviewer saw the wording — structurally the same move as the "FR-005 left exactly as it is" that caused the original defect.

P-6's leniency was also misapplied: it is written for an artifact carrying no consumer commitments, and code enforcing the requirements is a consumer. Its changelog floor was missed too — the edits landed unrecorded until now.

Fix
Decide whether absence can be view content at all, given the drift check compares the whole artifact. It probably cannot.
Correction — 14 Aug, and it retires this card
The contradiction described here does not exist in shipped code. Verified after an independent critic killed the propose written from it. Two facts neither this card nor that propose checked. readRenders (packages/core/src/visual/render.ts) imports only parser helpers and never touches a filesystem — it reads <spec-render> declarations out of the screens sidecar, so deleting an image file changes nothing in the regenerated artifact and produces zero findings. And 099 FR-013's per-screen recorded/not-recorded marker is implemented nowhere, so there is no marker to flip.

So "the moment a screen's last render is removed the marker flips, the artifact stops round-tripping, and validate reports a finding" is false in all three clauses. The only edit that moves the drift check is changing a <spec-render> element inside the sidecar — a change to a file the view projects, which is the case FR-004 exists for and which clears on regeneration.

The propose is withdrawn (099/2026-08-14-absence-is-not-drift), and its delta would have been actively harmful: it would have carved an authored sidecar element out of the only drift check watching it, contradicting 099 SC-002 — must-tier, same document — which requires that changing a declared sidecar produce at least one finding. Corroborating evidence the card also missed: 099 FR-002 already enumerates what the view projects — screens, states, annotations, contexts and token-set version — and renders are not on that list, so "the files it projects" never reached render presence and no amendment was needed to establish the reading.

Left open rather than closed: whether absence should be view content is a real question for whenever FR-013 is built. It is not a live contradiction today, so it is 099's question to answer when it implements the marker — not a defect in 094.
Rejected because
The contradiction it describes does not exist in shipped code — see the correction above. readRenders never touches a filesystem and 099 FR-013's marker is implemented nowhere, so no render deletion has ever failed a gate. The propose written from this card was withdrawn after a critic showed its premise was absent. Marked here rather than left implied: the correction was written and the status was not set, so the card read as open work for a session after it had been retired.

NFR-001's zero-directory-walks budget is spent by shipped code, and was still being spent as a reason

Implementation code

Debugging whether 093 could enumerate screens without breaking this spec's budget, root cause was that the budget is already broken — the same validate pass walks the declared screens directory unconditionally; regeneration passes, because NFR-001 states the bound plainly and the materialiser simply does not honour it.

Expected
NFR-001: path resolution "MUST stat only the declared paths: at most 1 filesystem call per declaration, and at most 0 directory walks, so that a project with many specs pays a cost linear in declarations rather than in files."
Actual
materialiseVisualViews (packages/core/src/visual/materialise-view.ts, lines 190–196) stats the declared screens path, and where it is a directory calls fs.readdir and then fs.readFile on every .html file it finds. That is one walk plus n reads per declaration — cost linear in files, which is the shape the budget exists to forbid. It runs unconditionally from validate.ts:979 and again from design.ts:108, so an ordinary validate pays it.
Diagnosis
A budget stated in a requirement and never given a check. Nothing counts filesystem calls, so the violation is invisible until someone reads both files together — which happened only because 093's correction cited this budget as its justification for giving up an enumerating check. So the capability was traded away to protect a bound that had already been exceeded, and the trade is now recorded in a live spec as a deliberate refusal. Independent of T-004 and of how 093 is resolved: the violation is there either way.
Correction — 14 Aug, before any propose acted on this
The headline claim above is wrong and is left standing so the error is legible. Two facts it did not check. NFR-001's subject is "path resolution", and its rationale names "the bound the contract resolve check already holds to" — it governs the FR-003 resolve check, not view materialisation. And materialisation is bounded, by 099 NFR-003: "under 100 ms to a design generation, for a feature declaring up to 20 screens" — a budget that explicitly contemplates reading many screens. So the materialiser does not violate NFR-001; it is a different operation with its own budget in the spec that owns it.

What survives, and it is narrower and better. NFR-001's subject and its purpose clause disagree. The subject binds path resolution; the purpose promises "a project with many specs pays a cost linear in declarations rather than in files", which is a claim about the whole pass. Materialisation runs in that same pass and is linear in files, so the purpose is defeated while the subject is honoured. That is a wording defect in NFR-001 — a bound whose stated reason is wider than its stated scope — not a violation.

And the consequence for 093 changes. The claim that its correction "traded a capability to protect a bound already exceeded" does not hold: the bound was never exceeded. Whether NFR-001 reaches an enumerating check at all is a live question — such a check is neither path resolution nor materialisation — and 093's propose has to answer it rather than inherit this card's answer.

Third time this session that checking a card against the source changed the answer, after T-024's and 095/T-005's. The pattern is the card, not the reader.
Fix
Decide which is wrong — the bound or the materialiser — and make them agree. If the walk is legitimate (a view has to project what the screens contain, and a directory-valued path is explicitly permitted by 093 FR-005), NFR-001 needs amending to state the real bound and say why. If the bound is right, the materialiser needs the declared file list rather than a directory read. Either way it is a propose against this spec, not a patch, and it should land before anything else cites this budget again.
Rejected because
Two proposals tried to fix this wording and both were withdrawn, in opposite directions — which is the evidence that the wording was never the defect. Narrowing the purpose clause would have orphaned the constraint scanVisualProject relies on, and justified itself with a should-tier budget that governs generation rather than validate. Widening the subject would have put four shipped checks into violation — including scanVisualProject itself, the very function cited as evidence for the wide reading, which does readdirSync(specs/) plus a read per design.

The real asymmetry, found only by trying both: the comment relies on a relative bound — do not re-read the estate N times — while NFR-001 states an absolute one, zero directory walks. Those were never the same claim, and no edit to the sentence reconciles them because the bound does not describe what the code does or what the comment needs. Rewriting it would require deciding what the bound should be, which is a performance question nobody has asked and no reader has been harmed by.

Left exactly as it is. The subject/purpose mismatch is real and is now documented here rather than in a requirement — which is the cheaper place for it, given the sentence has cost two proposals and misled two readers. A third attempt should start from "what should the bound be", not from "what should the sentence say".
Deep dive — cross-spec, and why no check caught it

Cross-spec. The bound is 094's, the violating code serves 093's declaration and 099's view, and the requirement that permits a directory-valued screens path is 093 FR-005. Any fix has to name which spec owns the cost, which is a question none of the three currently answers.

Why nothing caught it. Performance budgets in this estate are prose in an NFR; validate reads artifacts and cannot count another module's syscalls. That is the same P-8 ceiling recorded elsewhere — a guarantee living in prose — and it is worth noting the estate has two instances now, this one and the fold's path handling (meta-spec T-025). Not promoted here; named so a third has somewhere to point.
