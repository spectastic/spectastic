1 · Execution strategy

Setup → Foundational → US1 → US2 → Polish. US1 is largely a proof that the inherited resolve check satisfies this spec's acceptance; US2 is where the new code lands.

US2 alone is the shippable half — the location and disagreement checks are what this spec adds. US1 could be taken on trust from 093, which is exactly why it is written as a test instead.

5 · Phase 3b — US2 · The two scopes are unambiguous

Tests (write & fail first)

Implementation

Implement the disagreement finding — one per project, naming every disagreeing path with the spec that declared it. packages/core/src/commands/validate.ts

Confirm the estate and the exemplar stay clean — every declared path already conforms, so landing this must change nothing about what validate reports today. specs/

Closes FR-001, FR-002, FR-004, FR-008, NFR-001, SC-002, SC-003.

6 · Phase 4 — Polish

Guard the ignore entries — assert no scaffolded entry would exclude a file under either visual directory, so a future addition that would fails rather than passes. packages/core/test/visual-renders.test.ts
Assert determinism — the same project state produces byte-identical findings across three consecutive runs, with no read of the clock, network or environment. packages/core/test/visual-location.test.ts
Re-copy the command sources — the running slash command reads a gitignored copy that does not auto-sync. .claude/commands/
Generate the verify view — with a real captured run, citing 093's tests for the inherited requirement rather than claiming an unproven one. specs/094-visual-sidecar-convention/verify.html

Closes FR-005, FR-006, NFR-002. All three are properties rather than features — a prohibition, an already-satisfied condition, and a determinism claim — so each is closed by the test that would fail if it stopped being true, which is the only form of closure they admit.
