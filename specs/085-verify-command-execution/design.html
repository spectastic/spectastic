Design · 085-verify-command-execution

Running what was captured

Most of this design is about what the tool refuses to do. That is the correct proportion — the executing part is small, and the part that decides whether to execute is the feature.

Status Accepted Spec 085-verify-command-execution Owner Brian Corbin · @briancorbinxyz Created 02 Aug 2026 Principles v1.9.0 ArchitectureA guard-then-execute pipeline: every refusal resolves before a process exists. Kernel decides, adapter spawns. Coverage Diff-aware: every refusal path covered, and the pass/fail path exercised against a real command. Read time

The P-11 collision decides the structure. Consent and location are separate guards, both mandatory, both resolved before any process is spawned — and the location guard is not configurable, because the failure it prevents (an installed bundle executing on a consumer's machine) must not be reachable by a flag. The executor itself is small: three typed fields, a timeout, and a verdict per field in which skipped is a distinct outcome from passed.

3 · Data model & contracts

No interface crosses a repository boundary. The one externally visible surface is a config key, whose absence is the safe default.

The verdict's physical shape is a per-field outcome plus captured output. Skipped and absent are separate values from passed on purpose: collapsing them would let a run that examined nothing report green.

5 · Approach

Guard, then execute — and structure the code so that ordering is not a convention someone could reorder.

  1. Resolve consent. Read the invoking project's config. No key, no execution.
  2. Resolve location. Normalise the artifact path; refuse anything outside the project root or inside a dependency directory. Not configurable.
  3. Select fields. Build, entry point and tests. Skip an address-shaped entry point; never look at demo.
  4. Execute under a limit, capturing output, via an injected runner port.
  5. Report a verdict per field, with skipped distinct from passed.

Steps 1–3 are pure and take no port, which is what makes NFR-001 testable: the refusal paths can be exercised with no runner injected at all, so a test proving "0 processes spawned" is structural rather than a matter of watching for side effects.

7 · Decisions

Status Accepted

Context P-11 forbids an artifact instructing the tool that reads it, across three trust boundaries including distribution. Executing recorded commands crosses that line, and on a vendored bundle it is remote code execution.

Decision Take the exception, and bound it structurally: consent from the invoking project's own config, and a location guard that refuses anything outside the project or inside a dependency directory. The location guard is not configurable — no flag may waive it — so the distribution boundary P-11 is protecting stays protected whatever a user sets.

Consequences
+ The feature exists, and the failure that actually matters — an installed package running code — is unreachable rather than discouraged.
+ The trust assumption becomes explicit and familiar: a project's own artifacts are as trusted as its own test files, which is what every test runner already assumes.
− It is still an exception to a principle, and a hostile commit to your own repository will be executed. Recorded, not argued away.
− A legitimate use — checking a bundle you deliberately vendored — is refused with no override. Accepted: a waivable guard is not a guard.

Status Accepted

Context A verdict could collapse "skipped" into "passed" to keep reporting simple.

Decision Keep skipped, absent, passed, failed and timed out as distinct outcomes, and require the report to show them.

Consequences
+ A run that examined nothing cannot report green — which, for a check whose whole value is honesty about staleness, is the one bug that would make it worse than useless.
− More states to render, and a report that is longer than a bare pass/fail.

Status Accepted

Context Whether an entry point is executable cannot be known from the field alone — 083 permits both a command and an address.

Decision Treat a value that parses as a URL, or begins with a bare navigation verb, as an address and skip it. Anything else is attempted.

Consequences
+ The case 083 designed the field for is not penalised by a check that arrived later.
− A heuristic, so it will occasionally attempt something unexecutable. That surfaces as an ordinary failure with the command's output attached, which is diagnosable — the failure mode is noisy, not silent.

10 · Complexity tracking

P-11 exception — justified. The principle's purpose is that an artifact must not steer the tool reading it, because artifacts cross into contexts their author does not control. This feature deliberately reads an instruction from an artifact, and is therefore an exception rather than a compliant design.

What makes it acceptable is that the exception is confined to the one context where the author and the reader are the same party: a project executing artifacts it wrote and committed. Every other context — a dependency, a vendored copy, anything outside the project root — is refused structurally, with no configuration that can permit it. The residual is stated plainly and is not eliminated: a hostile commit to a project's own repository will be executed by this check, exactly as a hostile commit to that project's test files would be executed by its test runner. That is the trust boundary the whole ecosystem already sits on, and this feature does not widen it.

11 · Open questions

None outstanding. The principle exception was raised to the author and settled deliberately rather than assumed; the sandbox, the CI gate and command normalisation are deferred with slugs rather than left open.
