Specification · 085-verify-command-execution

Running what was captured

A recorded command is a claim about the world. Running it is the only check that tells a command from a sentence about one — and the only way to notice when a true claim quietly stopped being true.

Status Accepted Spec ID 085-verify-command-execution Owner Brian Corbin · @briancorbinxyz Reviewers — Created 02 Aug 2026 Principlesv1.9.0 Smallest demoableA command that runs one spec's captured build and test commands and fails when either no longer runs. Read time

The verify view's commands are grounded when captured and unguarded afterwards. A refactor three months later can leave every one of them stale while the artifact still asserts them, and no format rule can notice — only running them can. This feature is in direct tension with a principle, and the tension shapes it. P-11 requires an artifact's text to be data "not a channel that instructs the tool reading it", and names npm-shipped artifacts as one of three trust boundaries an artifact crosses. Executing a command stored in a vendored bundle would be remote code execution. So the check is first-party and opt-in by construction: it refuses any artifact outside the invoking project, refuses anything under a dependency directory, and refuses to run at all unless the project has explicitly asked. It executes only typed command fields, never the prose demo. The residual — that a hostile commit to your own repository is executed, exactly as a hostile commit to a test file is — is recorded rather than argued away.

1 · Context

The verify view records commands that were genuinely run at capture time. That grounding is real and it is instantaneous: nothing re-checks it afterwards. A package rename, a script removal, a moved test file leaves the recorded command false while the artifact goes on asserting it, and every structural check stays green — a format rule can tell that a string exists, never that it still works.

The actionability survey's D-003 named this as the guarantee half of its recommendation, and noted the mechanism is the only one that distinguishes a command from a sentence about a command. It also named the hazard: running arbitrary captured strings.

The hazard is sharper than "arbitrary strings". P-11 exists because the same artifact is read across three trust boundaries — opened by a human, ingested by an agent, and shipped to consumers through npm. A tool that executes commands found in a verify view turns an installed or vendored spec bundle into remote code execution. That is not a corner case for a project whose artifacts are designed to be distributed. It is the reason this spec constrains what it will consent to run before it describes what it does.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Catch a command that stopped working P1

As a maintainer, I want to run a spec's captured commands and be told when one no longer works so that a stale claim fails a build instead of misleading the next reader.

Acceptance: With the check enabled, a spec whose recorded commands all succeed reports success; break one — rename the script it calls — and the check fails, naming which field and showing the command's own output.

US2 · Refuse to execute anything foreign P1

As a consumer who installed this tool, I want to be certain it will never execute a command from an artifact I did not author so that installing a package cannot run code on my machine.

Acceptance: Pointed at an artifact under a dependency directory, or at any path outside the invoking project root, the check refuses and explains why; with no explicit opt-in in the project's configuration, it refuses regardless of the path.

US3 · Leave the prose alone P2

As an author, I want to keep writing human demo paths in prose so that enabling the check does not force every field into command shape.

Acceptance: The demo field is never executed and never reported on; a captured entry point that is an address rather than a command is skipped and labelled as such, not attempted and not failed.

Edge cases

  • An entry point that is a URL — legitimate per 083, and not executable. Skipped with a reason, never attempted.
  • A command that hangs. Bounded by a timeout, and a timeout is a failure with its own message rather than an indefinite wait.
  • A command that is genuinely slow but correct. The timeout must be configurable, or the check punishes honest builds.
  • A view whose fields are all empty — nothing to run, and that is a pass with a note, not a failure.
  • A view marked as suggested-but-not-run. Its commands were never claimed to work, so executing them would test a claim nobody made.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The check MUST NOT execute anything unless the invoking project has explicitly enabled it in its own configuration; absent that opt-in it MUST refuse and say so.

Rationale

Executing recorded commands is a capability, not a default. A tool that gains it silently on upgrade would be a supply-chain change nobody consented to.

The check MUST refuse any artifact resolving outside the invoking project root, and any artifact within a dependency directory, regardless of the opt-in.

Rationale

This is the whole answer to the P-11 collision. An artifact ships to consumers; a vendored bundle must never be a code-execution vector, and no configuration flag may waive that.

The check MUST execute only the typed command fields — the build/start command, the exercise entry point, and the test command — and MUST NOT execute the demo field.

Rationale

The demo is specified to be prose and is the one field where a click-path or a browser check is the honest answer. Executing it would force every author to make it a command, which is the opposite of what the format decided.

An entry point that is an address rather than an executable command MUST be skipped and reported as skipped, never attempted and never counted as a failure.

Rationale

083 deliberately permits the field to hold a URL where the build step already serves the feature. Treating that as a broken command would penalise the case the field was designed for.

A command exceeding a configurable time limit MUST be terminated and reported as a timeout, distinguishable in the output from a command that ran and failed.

A failing command's report MUST name the spec, the field and the command, and include the command's own output, so a failure is diagnosable without re-running it by hand.

A view whose block is marked as suggested-but-not-run MUST be skipped, and a view with no populated command fields MUST report success with a note rather than a failure.

Rationale

A suggested block never claimed its commands work, so failing it would report a promise nobody made as broken. An empty block is the honest state for a spec with nothing to run.

The check SHOULD be runnable across every spec in a project in one invocation, reporting per spec and failing if any spec fails.

Non-functional

The check MUST apply its refusals before any process is spawned — 100% of refusal paths reached with 0 commands executed — so a rejected artifact cannot run anything even briefly.

The default per-command time limit SHOULD be no more than 300 s, so a hung command fails a build in bounded time rather than occupying a runner indefinitely.

Out of scope (deferred to other slices)

  • Sandboxing execution. The refusals bound whose commands run, not what a command may do once running; confining that needs an isolation mechanism this project does not have.
  • Wiring the check into this repository's own CI as a blocking gate. Worth doing once the captured commands have been observed to pass reliably, not before.
  • Rewriting a captured command so it runs from a different working directory. Several existing captures assume a specific cwd, which is a real portability gap and a separate problem.

4 · Data model

One new concept; the captured run is unchanged.

Entities

Execution verdict
The outcome of attempting one spec's captured commands: per field, one of passed, failed, timed out, skipped or absent, together with the output of anything that ran. Its defining property is that skipped is not passed: a check that quietly counts what it declined to attempt as success would report a green result for an artifact it never examined.
Execution consent
The project's explicit statement that it permits this. It is a property of the project doing the invoking, never of the artifact being read — an artifact cannot consent on a reader's behalf, which is the whole content of the P-11 constraint.

The invariant: consent and location are checked independently, and both must pass. Consent without a first-party path is refused, and a first-party path without consent is refused. Neither can be traded for the other, because they guard different failures — one is about what the user agreed to, the other about whose code it is.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

A deliberately broken captured command — one calling a script that has been removed — causes the check to fail and names the offending field, where every existing structural check on the same artifact still passes.

Every refusal path is exercised and spawns 0 processes: an artifact in a dependency directory, an artifact outside the project root, and a project with no opt-in are each refused with a distinct explanation.

Run across this repository's own specs with the opt-in enabled, the check reports a per-spec result and its skipped entries are all explained — 0 fields reported as passed that were never attempted.

6 · Assumptions

A project's own committed artifacts are as trustworthy as its own committed test files. This is the assumption the whole design rests on, and it is exactly as strong as the equivalent assumption every test runner makes. It is also why the refusals are structural rather than configurable: the assumption holds for first-party content and collapses entirely for anything vendored.

Captured commands are mostly short and hermetic. True across this estate's build and test invocations, and untested anywhere else — the survey's own caveat, restated here because the timeout default depends on it.

7 · Open questions

None outstanding. The principle collision was surfaced and resolved deliberately — first-party and opt-in, with the residual recorded — rather than resolved by the author's judgment alone.
