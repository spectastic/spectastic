Auto-re-entry silently sharpens an Accepted plan without ceremony

Spec upstream

Cascade of 008/T-001 with the opposite failure mode: spectastic design <spec-id> auto-re-enters when design.html exists regardless of its <spec-status>. The auto-detect IS the in-place behaviour 008's user wanted — but here it runs even on Accepted plans, which is too loose.

Expected
Auto-re-entry when destination is Draft (current behaviour, correct). Refuse-with-pointer-to-/propose when destination is Accepted or any past-Draft state; the user must opt into amending a ratified plan via the change-proposal cycle, not by re-running the verb.
Actual
CLI subcommand (packages/cli/src/commands/design.ts lines 23–27) auto-detects existing design.html via fs.readFile and passes it as existingPlan to the kernel. The kernel's re-entry mode honours that flag without checking the spec's status; an Accepted plan gets silently sharpened.
Diagnosis
012's spec specified re-entry mode (FR-006 of 012 spec: ADD/ENHANCE/SUPERSEDE) but didn't gate it on lifecycle state. Per REQ-LIFECYCLE-004, an Accepted artifact has consumer commitments — amending it bypasses the change-management surface (REQ-CHANGE-*) the meta-spec mandates.
Fix
Open /spectastic.propose against specs/012-core-plan/spec.html: MODIFY the re-entry FR to gate on destination state (Draft = auto-re-entry as today; past-Draft = refuse with structured error pointing at /spectastic.propose). Hotfix the CLI to inspect the existing plan's <spec-status value="…"> before deciding to re-enter or refuse.
Closed by
P-6 ratification + 2026-06-16-p6-cascade-plan (MODIFIED FR-003). CLI hotfix at packages/cli/src/commands/design.ts via shared gateOnDestinationState helper. Silent-sharpen failure mode closed.
Deep dive — third of three cascade cards

Three of three cascade cards from 008/T-001 (009 + 011 + this). 012's failure mode is the mirror image of 011's: 011 silently overwrites, 012 silently sharpens past-Draft artifacts. Both elide the change-management surface the meta-spec mandates for ratified content. Version-policy half of 008's defect does NOT cascade (design.html template carries no <b>Version</b> field). 013-core-propose is exempt from the cascade because each proposal lands in its own dated folder — no destination collision is possible.

FR-011's must-tier ADR preservation has never been implemented — re-entry destroys and renumbers

Implementation code

Debugging why design --visuals found no visual declaration, root cause was that re-entry renders a fresh document from the model’s JSON and writes it over the existing one, so every part of the prior design the schema has no field for is deleted — including the <spec-decision> blocks FR-011 says MUST be preserved; fixed by carrying prior content across rather than regenerating over it; regeneration passes — the requirement is already written and unambiguous, so a session implementing FR-011 from the spec would build it correctly.

Expected
FR-011: re-entry “MUST preserve every existing <spec-decision> block — including stable IDs, status, and content … MUST NOT renumber or silently rewrite an existing ADR.”
Actual
Measured on a Draft design carrying a hand-authored D-007: after one ordinary spectastic design <id>, D-007 is at 0 occurrences and the document carries D-001 instead. Both halves breached — destroyed and renumbered — with no warning and a successful exit. The same run deletes <spec-visual>, <spec-contract> and hand-written prose, none of which FR-011 covers.
Diagnosis
renderDesignHtml builds the entire document from parsed — the model’s JSON — and designCommand writes it out whole. Nothing reads the prior design except the prompt, which is handed input.existingDesign.slice(0, 6000) and asked to restate it; whatever the model omits, or whatever sits past 6 KB, is gone. The verb’s own re-entry prompt says “ADD or ENHANCE only; never remove existing ADRs” — an instruction aimed at the model and then broken by the code that renders what the model returns, which is the P-8 gap exactly: the guarantee was put in a prompt rather than in the kernel. The spec’s own §6 assumes re-entry parses the prior document with @spectastic/schema’s walker; no such parse exists.
Fix
packages/core/src/commands/design.ts — carry the prior design’s content across rather than rendering over it, with a test per FR-011 clause (an existing ADR survives; its id is not renumbered). The declarations the same run destroys are outside FR-011’s text, so widening preservation beyond ADRs is a spec question and belongs in its own propose rather than being smuggled in under this card.
Fixed
Shipped as proposed, and the widening followed immediately rather than later. carryForward in packages/core/src/commands/design.ts carries prior ADRs across; a hand-authored D-007 now survives with its id intact, verified through the real binary, where before it came back as D-001. The declarations the same run destroyed landed as FR-016 via 2026-08-23-preserve-what-the-generator-does-not-emit, whose adversarial pass produced the fact that made the requirement writable: two generators produce this artifact — templates/design.html scaffolds both declarations and the kernel's renderer emits neither — so the rule names the two elements outright rather than describing them by a predicate that would silently stop covering them as the code improves. The existing re-entry test that stayed green throughout is the other half of the lesson: it drove a stub returning the preserved set, so it proved the kernel renders faithfully and never that preservation happens.
Deep dive — a must-tier requirement that shipped untested for two months

No cross-spec contract; no hotfix sequencing. What is worth recording is that this was not a gap in the text. The requirement is written, must-tier, unambiguous, and named in the spec’s own TL;DR and its INVEST Negotiable row as a contract the spec sets — and it was never implemented and never tested. A first draft of the change that found this proposed adding a preservation requirement, on the reasoning that none existed; the adversarial pass produced FR-011 and the draft was discarded rather than reworded. The interesting question is therefore not what to write but why a must-tier rule went unenforced, which is a question about where guarantees live rather than about this one verb.

Also surfaced rather than folded in: the sibling generating verbs (spec, tasks) render their artifacts through the same shape and may lose content the same way. Not measured, and asserting it without measuring would repeat the error this card exists to correct.
