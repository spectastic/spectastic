Gate auto-re-entry on destination state (cite P-6)

Mechanical application of newly-ratified P-6 to the plan verb's auto-re-entry trigger. One MODIFY on FR-003.

Status Applied Change ID 2026-06-16-p6-cascade-plan Spec 012-core-plan Source 012/T-001 · sibling of 2026-06-16-p6-draft-is-loose Author Brian Corbin · @briancorbinxyz Created 16 Jun 2026 Targets 1 modified (FR-003) Read time

FR-003 currently says re-entry mode triggers on the presence of an existing plan.html — no flag, no state check. Per 012/T-001, this silently sharpens Accepted plans, bypassing the change-management surface the meta-spec mandates for ratified content. Per P-6, the right gate is the destination's <spec-status>: Draft → auto-re-enter, past-Draft → refuse.

Gate auto-re-entry on destination state (cite P-6)

Applied

1 · Intent

One of four mechanical cascades from P-6. 012's failure mode is the mirror of 011's: where 011 silently overwrites, 012 silently sharpens. Both elide the change-management surface for ratified content. P-6 ratified destination-state as the right gate; MODIFY FR-003 to honour it.

2 · Scope

In scope

  • MODIFY FR-003 to gate auto-re-entry on the destination's <spec-status> per P-6.
  • Hotfix packages/cli/src/commands/plan.ts: inspect <spec-status> of the existing plan.html before passing existingPlan to the kernel.

Out of scope

  • FR-011's re-entry-mode preservation guarantees (preserve every existing <spec-decision>, never renumber, ADD or ENHANCE only). Untouched — those govern the shape of re-entry once it's triggered, not whether it triggers.
  • 013-core-propose's auto-re-entry behaviour. Structurally exempt — each proposal lands in its own dated folder, so destination collision is impossible (confirmed in 012/T-001's deep-dive).

3 · Approach

Single MODIFY on FR-003. The post-state preserves the explicit-no-flag re-entry-trigger design (a deliberate ergonomic choice — re-running plan against a spec with an existing plan SHOULD auto-re-enter) but narrows the auto-re-enter path to Draft destinations. Past-Draft destinations require --force or a route through /spectastic.propose.

4 · Deltas

What changes: Auto-re-entry triggers on existence AND <spec-status value="draft">; past-Draft destinations refuse per P-6.

The CLI MUST expose a spectastic plan <spec-id> subcommand that resolves <spec-id> to specs/<spec-id>/spec.html, invokes planCommand, and writes PlanResult.html to specs/<spec-id>/plan.html. Re-entry mode MUST gate on the destination's <spec-status> per P-6: a Draft plan.html (or no existing plan.html) MUST trigger auto-re-entry / fresh authoring (no flag); a past-Draft plan.html (Accepted, In Review, Superseded, Deprecated, Blocked) MUST be refused with a typed error pointing at /spectastic.propose. A --force override MAY bypass the past-Draft refuse with a one-line warning that the operation skips the change-management surface.

Rationale

Cascade of 012/T-001: the original FR-003's flag-less auto-re-entry trigger was correct for Draft destinations (it IS the in-place behaviour P-6 wants) but silently sharpened Accepted plans. P-6 ratified destination-state as the right gate; this FR keeps the ergonomic flagless auto-re-entry for Draft while routing past-Draft mutations through the change-management surface.

5 · Risk register

Adversarial pass deliberately opted out (--no-adversarial). Substance exhausted at parent P-6 proposal; this is a mechanical cascade.
