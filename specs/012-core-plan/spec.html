1 · Context

/spectastic.plan is one of the eight slash commands carved out for extraction in 006. It pairs with a spec: reads specs/<spec-id>/spec.html, produces plan.html alongside. The procedure is interactive (two-phase interview), gated (refuses while the spec has blockers), and structured (ADRs with stable IDs, optional SVG sketch, alternatives matrix with a winner row, principles walk).

Today the procedure lives only in commands/spectastic.plan.md. Every future surface (MCP, VS Code, web editor) would re-implement it. This slice moves the logic into @spectastic/core/commands/plan behind the kernel contract 006 defined, re-using the ai.ask<T>() pattern proven in 011-core-spec. CLI gains spectastic plan <spec-id>; the slash-command markdown gains a MAY-Bash-to-CLI note.

2 · User scenarios & testing

Each story is independently testable.

US1 · Maintainer plans a freshly-authored spec P1

As a maintainer who just authored specs/<id>/spec.html, I want to run spectastic plan <id> and walk the same two-phase interview the slash command runs so that I get a populated plan.html without invoking the slash command.

Acceptance: Against a spec with no blockers, the CLI runs the interview and writes plan.html with at least one <spec-decision id="D-001">, a principles-check table, a project-structure block, and a risks table.

US2 · Estimability gate refuses a blocked spec P1

As a maintainer running spectastic plan <id> against a spec with open questions, I want to be halted with every blocker and its file location so that I fix the spec instead of guessing past it.

Acceptance: When the source spec contains any open <spec-question>, [NEEDS CLARIFICATION], missing defer-to=, or failed INVEST row, the kernel returns without writing and the CLI exits non-zero with a structured blocker list.

US3 · Re-entry deepens an existing plan P2

As a maintainer iterating on an existing plan.html, I want to re-run spectastic plan <id> and have the kernel detect re-entry so that my prior ADRs are preserved while new decisions get added.

Acceptance: When plan.html already exists, the kernel parses it, preserves every existing <spec-decision>, and only adds or enhances. No existing D-NNN ID is reassigned or removed.

Edge cases

Four tracked failure modes the kernel handles.
  • Principles VIOLATION mid-walk — a candidate decision the user proposed violates a stated principle. Kernel halts, surfaces the principle + the violating decision, and asks the user to revise or amend principles. No plan.html written.
  • Spec file missing — spec.html not found at the resolved path. Kernel returns a structured error; CLI exits 2.
  • Principles file absent — principles.html at the project root is optional. When absent, the principles-walk step is skipped and the plan's §1 records "no principles defined"; no halt.
  • Single-component feature — the inline SVG sketch is only required when the feature has more than one moving part. The kernel asks the user (or infers from the spec's component count) before scaffolding the SVG; trivial features get a one-sentence approach paragraph and no sketch.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional — kernel

The kernel function MUST conform to 006 FR-003's signature: async function planCommand(input: PlanInput, ctx: KernelContext): Promise<PlanResult>. The function MUST be pure with respect to its arguments; all IO and AI access flow through ctx.

planCommand MUST be implemented at packages/core/src/commands/plan.ts and exported via the @spectastic/core/commands/plan subpath per 006 FR-002.

The CLI MUST expose a spectastic plan <spec-id> subcommand that resolves <spec-id> to specs/<spec-id>/spec.html, invokes planCommand, and writes PlanResult.html to specs/<spec-id>/plan.html. Re-entry mode MUST be triggered by the presence of an existing plan.html at the destination — no explicit flag.

The kernel MUST read the source spec via ctx.fs; never via direct node:fs calls. It MUST refuse to plan if the spec fails the estimability gate (FR-005).

The estimability gate MUST halt and report when the source spec contains any of: an open <spec-question> admonition; a [NEEDS CLARIFICATION] marker in body text; a <spec-out-of-scope> <li> missing defer-to=; or an INVEST row in <dl class="invest"> marked with <dd class="fail">. The gate MUST emit a structured list of every blocker with file location, not just the first.

The interview MUST be two-phase: ctx.ai.chat() for narrative answers (high-level approach, alternatives narrative, project-structure prose, risks); ctx.ai.ask<T>() for bounded decisions (test style, risk tolerance, perf budget, persistence shape, tech-stack picks, candidate-ADR thumbs-up). The kernel MUST skip questions whose answers are already in PlanInput, the source spec, or upstream artifacts.

The principles check MUST walk every principle in principles.html when present, marking each OK, EXCEPTION, or VIOLATION. An EXCEPTION MUST produce a §8 Complexity-tracking entry in the output. A VIOLATION MUST halt the kernel and surface the principle + the offending candidate decision; no plan.html is written until resolved.

Architecture Decision Records MUST use stable D-001, D-002, … IDs assigned in encounter order. Each ADR MUST carry the four-field shape: Status, Context, Decision, Consequences (with + positives and − negatives). Superseded decisions keep status superseded and link forward; IDs are never reassigned.

An inline SVG architecture sketch SHOULD be included for features with more than one moving part. The kernel MUST infer or ask whether the feature warrants a sketch; trivial single-component features skip it.

The alternatives matrix MUST include a scored table with at least two non-chosen options; exactly one row MUST carry the data-winner attribute, and that row MUST be the alternative actually adopted in the ADRs.

Re-entry mode MUST preserve every existing <spec-decision> block — including stable IDs, status, and content. The kernel may ADD new ADRs (next available D-NNN ID) or ENHANCE existing ones (appending to Context / Consequences with a dated note); it MUST NOT renumber or silently rewrite an existing ADR.

The kernel MUST return a structured PlanResult ({ html, decisionsCount, principlesCheck }); the caller is responsible for writing html to disk. The kernel MUST NOT call ctx.fs.writeFile itself — that's the CLI's job.

Functional — CLI + slash-command coupling

Tests MUST include kernel unit tests at packages/core/test/plan.test.ts (stub AIProvider, stub ctx.fs, fixture spec inputs) and a CLI integration test in packages/cli/test/cli.test.ts that drives the spectastic plan subcommand against a fixture spec.

commands/spectastic.plan.md MUST be updated to add a MAY-Bash-to-CLI note: the LLM MAY invoke spectastic plan <spec-id> via Bash for the deterministic estimability gate, but the slash-command procedure continues to work end-to-end without it (per 006 FR-009).

The planCommand docblock MUST link to commands/spectastic.plan.md as the canonical procedure (per 006 FR-008); the markdown MUST NOT be auto-generated from the docblock.

Non-functional

The extraction MUST NOT regress any scenario in bench/baselines.json past its declared budget (per 006 NFR-001). In particular, init-help-cold-start stays within budget — no eager parse5 load via the plan subpath.

Out of scope (deferred to other slices)

  • Amending an accepted plan via a structured proposal flow (separate from re-entry, which mutates the live file). Belongs in a future slice that pairs with /spectastic.propose extraction.
  • Cross-spec plan linkage (auto-resolving sibling plan references when a spec links to another spec's plan). Out of scope until at least two extracted plans exist in the wild.
  • Kernel skeleton, KernelContext, AIProvider interface, subpath-exports policy — all already established in 006.

4 · Data model

Four types this slice owns: PlanInput, PlanResult, Decision, PrinciplesCheckResult.

Entities

PlanInput
Fields: specId: string (the NNN-slug identifier resolved against ctx.cwd); mode?: 'fresh' | 'reentry' (optional explicit override; default is auto-detect by checking for an existing plan.html at the destination).
PlanResult
Fields: html: string (the full plan.html content the caller writes to disk); decisionsCount: number (count of <spec-decision> blocks in the output, including preserved ones in re-entry mode); principlesCheck: PrinciplesCheckResult.
Decision
Fields: id: string (D-NNN, stable forever); status: 'accepted' | 'superseded' | 'proposed'; context: string; decision: string; consequences: string (with + / − markers).
PrinciplesCheckResult
Fields: ok: number; exceptions: number; violations: number. A non-zero violations count means the kernel halted before completing; the caller should report rather than persist.

5 · Success criteria

Technology-agnostic, measurable outcomes.

Against a fixture spec with no blockers and a stub AIProvider returning canned decisions, planCommand produces byte-identical output across two invocations (same input → same HTML). Verified in packages/core/test/plan.test.ts.

Against a fixture spec containing each of the four blocker types (open <spec-question>, [NEEDS CLARIFICATION], missing defer-to=, failed INVEST row), the estimability gate halts and the returned blocker list names every offence with its file location. No plan.html is produced.

A test file under packages/core/test/ imports planCommand from @spectastic/core/commands/plan, calls it with a stub ctx.ai and stub ctx.fs, and receives a structured PlanResult. No process spawn; no real filesystem touched.

pnpm bench passes all scenarios within budget post-extraction, confirming the plan subpath does not regress cold-start or validate-full-project times.

6 · Assumptions

The AIProvider interface shipping with 011-core-spec exposes a ask<T>(questions) method whose return shape matches AskUserQuestion well enough that the kernel can drive the decision-phase interview without a wrapper layer.

Parsing existing plan.html for re-entry mode can rely on @spectastic/schema's parse5-based walker (the same dependency already used by validateCommand); no new HTML parsing library is needed for plan-specific element extraction.
