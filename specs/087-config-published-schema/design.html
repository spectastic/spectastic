Design · 087-config-published-schema

The published config schema

Two consumers, one derivation. The editor gets a schema it already knows how to read; the gate gets an answer that needs neither an editor nor a network.

Status Draft Spec 087-config-published-schema Owner Brian Corbin · @briancorbinxyz Created 03 Aug 2026 Principles v1.9.0 ArchitectureA pure generator over the registry, a committed artifact checked against it, and one folded scan cloning the existing non-HTML validate scans. Coverage Diff-aware: generator and scan covered directly; the committed schema guarded by a regeneration check. Read time

The generator is a pure function from the registry to a schema object — no filesystem, no clock, so determinism is structural rather than tested for. The artifact is committed and shipped in the package, which is what makes the version-pinned CDN address work at all: the address resolves because the file is inside the published tarball. The unrecognised-key scan clones the shape the other non-HTML validate scans already use, and reports at warning severity, because a key from a newer version of the tool is indistinguishable from a typo and refusing to run would be worse than the silence being fixed.

3 · Data model & contracts

This is the spec that gives the configuration file a real contract. It is consumed outside the repository — by editors resolving the reference, and by any downstream project validating its own file — so it is declared here rather than treated as an internal artifact.

The contract is generated, which changes what declaring it means: the source of truth remains the registry, and the schema is its published projection. A change to the contract is therefore a change to the registry, never an edit to the file.

5 · Approach

  1. Generate — a pure function from the registry to a schema object, with keys emitted in sorted order so the output is byte-stable.
  2. Commit the artifact and regenerate it as part of the build, so the published package carries it and the CDN address resolves.
  3. Guard it — a test regenerating from the registry and comparing, so a hand edit or a stale build is a failure rather than a silent divergence.
  4. Scan — walk a project's configuration against the registry and report an unrecognised key, suggesting a near match where one exists.
  5. Reference it — write the version-pinned address into configurations the tool creates.

7 · Decisions

Status Accepted

Context The survey flagged hosting as an unfunded dependency. Two options were live and both were checked by fetching them: the package CDN and the project's own domain, which returned HTTP 200.

Decision Publish at a version-pinned address on the package registry's CDN.

Consequences
+ No infrastructure, and immutable per version — a configuration written today keeps resolving against the surface it was written for, which the unversioned alternative cannot offer.
+ Releasing the package publishes the schema; there is no second step to forget.
− A third party sits in the resolution path, so a user offline or behind a restrictive proxy gets no editor assistance. That is precisely why the validate scan does not depend on it.
− The address carries a version number, which is noise in an otherwise clean file.

Status Accepted

Context The schema could be generated on demand by a command, or committed and shipped.

Decision Commit it and regenerate during the build, guarded by a test that regenerates and compares.

Consequences
+ It is in the published tarball, which is the only reason the CDN address resolves at all — an on-demand schema has no address.
+ A reviewer sees the surface change in the diff when the registry changes, which is a useful signal rather than a chore.
− A generated file in version control, with the usual cost: it will occasionally be committed stale, which is what the guard exists to catch.

Status Accepted

Context An unrecognised key could be an error or a warning. It is genuinely ambiguous: a typo and a key belonging to a newer version of the tool are the same observation, and nothing at check time separates them.

Decision Warning. Name the key, and suggest a near match where the edit distance is small.

Consequences
+ A colleague on a later version does not make the build fail for everyone else, which an error-level check would.
+ The suggestion is what makes the finding actionable — "unknown key" states a problem, naming the intended key solves it.
− A warning can be ignored, and the failure being fixed is precisely a user not noticing something. Mitigated only by the finding appearing on a surface people already read.
− Severity is a judgment that may prove wrong; it can be raised later without any other change.

Status Accepted

Context The obvious implementation validates the file against the generated schema with a validator library.

Decision Do not. The question is whether a key is declared, which is a set-membership test the registry answers directly, with no dependency and no schema file needed at check time.

Consequences
+ No new dependency, and the check works with no network and no schema present — which is what makes it independent of D-001's third party.
+ Faster and simpler than parsing and applying a schema to answer one question.
− It checks only key names. Validating a key's value would genuinely want a validator, and is deferred rather than approximated here.
− Two mechanisms now describe the same surface — the schema for editors, the registry for the scan — and both derive from the registry, so they cannot disagree.

10 · Complexity tracking

No principle exceptions. The one piece of added surface — a committed generated artifact — is justified by D-002: without a file in the published package there is no address, and without an address there is no editor integration at all.

11 · Open questions

None outstanding. Hosting and reporting surface were anchored in the interview; the no-validator decision follows from what the check actually asks.
