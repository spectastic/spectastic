Specification · 087-config-published-schema

The published config schema

The registry knows what the configuration may contain. A schema is that knowledge in a format the user's editor already speaks — and the same file is what finally makes a misspelt key say something.

Status Draft Spec ID 087-config-published-schema Owner Brian Corbin · @briancorbinxyz Reviewers — Created 03 Aug 2026 Principlesv1.9.0 Smallest demoableA misspelt configuration key produces a finding naming the key it was probably meant to be. Read time

A misspelt configuration key currently does nothing at all: no warning, no error, no effect. The user believes they have overridden a default and has not, and the tool behaves exactly as it would have if the override were refused — which is the point at which "not dogmatic" stops being true whatever the code permits. 086 made the surface enumerable; this spec turns that enumeration into a JSON Schema generated from the registry, published at a version-pinned URL, referenced from configurations the tool writes, and — the half that does not depend on anyone's editor — used to report an unrecognised key as a validate finding on the surface the pre-commit gate already watches. 1 · Context

The discoverable-defaults survey opened on a specific silence: misspell a configuration key and nothing happens. No warning, no error, no effect. The user thinks they changed a default and did not, and cannot tell the difference from the outside.

086 removed the reason that silence was unavoidable. The configuration surface is now declared as data — ten sections, their keys, their types and their defaults, in one place any consumer can walk. Two things become possible that were not, and this spec builds both from the same artifact.

The first is ordinary: a JSON Schema, which every mainstream editor already knows how to consume, giving completion and per-key documentation as a user types. This project already depends on that mechanism daily for somebody else's tool — its own linter configuration opens with a schema reference — and offers nothing equivalent for itself.

The second is the one that matters more. A schema is a machine-readable statement of what the file may contain, so the same artifact that helps an editor also answers is this key real? — in a terminal, in CI, with no editor involved and no network. That half is what turns the silence into a finding, and it is the half a user without schema support in their editor would otherwise never get.

Users: anyone editing a configuration, who currently has no way to discover what may go in it; and the maintainer, for whom a typo in a project's own file is presently indistinguishable from a deliberate omission.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Be told about a typo P1

As a user who has just edited a configuration, I want to be told when a key is not one the tool recognises so that I find out now, rather than concluding the tool ignores my settings.

Acceptance: A configuration containing an unrecognised key produces a finding naming it; where the key is close to a real one, the finding names the likely intended key. A configuration containing only recognised keys produces no finding.

US2 · See what may go in the file P1

As a user opening a configuration in an editor, I want to see the available keys and what each one does so that I can discover the surface without reading the source.

Acceptance: A schema describing every declared section, key, type, default and description is published; a configuration the tool writes references it; and the reference resolves.

US3 · Trust that the schema is current P2

As a maintainer, I want the schema to be generated from the registry rather than maintained beside it so that the two cannot describe different tools.

Acceptance: The schema is produced from the registry by a repeatable step, and a check fails if a committed schema no longer matches what the registry would produce.

Edge cases

  • A key that is unrecognised but deliberate — a user's own annotation, or a key from a newer version of the tool. The finding must be advisory rather than fatal, since neither is a mistake the tool should refuse to run over.
  • The $schema key itself, which is not part of the configuration surface and must not be reported as unrecognised.
  • An unrecognised key nested inside a recognised section, which is the more likely typo and must be caught as readily as a misspelt section.
  • A configuration written by a future version, whose keys this version has never heard of. Indistinguishable from a typo, and treated the same way — which is why the finding is advisory.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A JSON Schema describing the configuration MUST be generated from the registry, and MUST NOT be hand-maintained.

Rationale

A hand-written schema is precisely the third source of truth 086 was built to prevent — it would drift from the registry, and the drift would be invisible because both look authoritative.

The generated schema MUST carry every declared section, key, type, description and — for a key that has one — its default.

The schema MUST be published at a version-pinned address, so a configuration written against one version of the tool continues to resolve against the surface it was written for.

Rationale

An unversioned schema validates an old configuration against a newer surface, so a key removed in a later release becomes a false error in a file that was correct when written.

A configuration the tool writes MUST carry a reference to the published schema, and that reference MUST resolve.

Rationale

A dangling reference is worse than none: it produces editor errors about the schema rather than about the file, and teaches users to ignore the mechanism.

An unrecognised key in a configuration MUST be reported as a validate finding, without requiring an editor, a network connection, or the schema file.

Rationale

This is the half that reaches everyone. The schema helps only inside an editor that resolves it; the failure being closed is a silence, and a silence in CI is the same silence.

The unrecognised-key finding MUST be advisory rather than fatal, and MUST NOT report the schema reference itself as unrecognised.

Rationale

A key from a newer version of the tool is indistinguishable from a typo, and refusing to run over a file written by a colleague on a later version would be worse than the silence. The schema reference is metadata, not configuration.

Where an unrecognised key closely resembles a declared one, the finding SHOULD name the likely intended key.

Rationale

"Unknown key" tells a user they have a problem; naming the key they meant tells them the answer. The typo case is the overwhelmingly common one.

A check SHOULD fail when a committed schema no longer matches what the registry would generate.

Non-functional

Generation MUST be deterministic: 100% of runs over an unchanged registry produce a byte-identical schema, with no dependence on key enumeration order or the clock.

Rationale

Stated as a proportion because a generator that is usually reproducible produces spurious diffs, and a spurious diff in a generated artifact trains reviewers to stop reading them — which is how a real drift gets waved through.

The unrecognised-key scan MUST perform 0 network requests and MUST complete in under 50 ms for a configuration of ordinary size.

Out of scope (deferred to other slices)

  • The command that prints effective values with provenance. It reads the same registry and is the terminal-side answer to a different question.
  • Accepting comments in a user's own configuration.
  • Registering the schema with the community store so editors associate it by filename without a reference in the file.
  • Validating a recognised key's value — a string where a number belongs, an out-of-range threshold. This spec checks that a key is real, not that its value is sensible.

4 · Data model

No new concept; one existing thing gains a second representation.

Entities

Published schema
The registry expressed in a format editors and validators already understand, addressed at a version-pinned location. Its defining property is that it is derived: it holds no knowledge of its own, so it can never be right about something the registry is wrong about, nor wrong about something the registry has right.
Unrecognised key
A key present in a configuration that the registry does not declare. It is a suspicion, not a verdict — a typo and a key from a later version of the tool are the same observation, and nothing available at the time of the check can distinguish them. That is what fixes its severity as advisory.

The invariant: the schema is generated, so anything true of the registry is true of the schema and nothing else is. A hand edit to the schema is therefore not a change to the configuration surface — it is a defect, and FR-008 is what makes it a visible one.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

A configuration containing a misspelt key produces a finding naming that key, where the same configuration today produces none — demonstrated against a real misspelling, not a fixture alone.

The published schema describes 100% of the registry's declared sections and keys, and the reference written into a configuration resolves successfully.

Regenerating the schema from an unchanged registry produces a byte-identical file, and 0 valid configurations in this repository produce an unrecognised-key finding.

6 · Assumptions

A version-pinned address on the package registry's content delivery network is durable enough to embed in a user's file. It is immutable per version and needs no infrastructure, which is why it was chosen — but it is a third party in the resolution path, and a user offline or behind a restrictive proxy gets no editor assistance. The validate finding is deliberately independent of it for exactly that reason.

Users would rather be told about a suspicious key than have the tool refuse to run. Taken as true, and the reason the finding is advisory; if it proves wrong the severity can rise without any other change.

7 · Open questions

None outstanding. The hosting address and the reporting surface were both anchored in the interview, and the generated-not-written constraint follows from what 086 was built to prevent.
