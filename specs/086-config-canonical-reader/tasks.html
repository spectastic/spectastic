The canonical config reader

Status Accepted Spec 086-config-canonical-reader Design design.html Created 03 Aug 2026 Strategy Incremental — the registry and resolver land first and separately, so the new logic is reviewable before sixteen call sites move onto it. Read time

Fifteen tasks. US1 builds the registry and resolver; US2 migrates the readers, dedicated config modules first and inline readers second, because the inline ones are where a disagreement is most likely; US3 adds the completeness guard and proves it against a planted key.

Phase 1 · US1 — ask the tool what its defaults are

Tests first, and failing, before any implementation task in this phase starts.

Write the registry's tests — every section enumerable without knowing any key's meaning, and a key with no default distinguishable from one defaulting to a value. packages/schema/test/config.registry.test.ts
Write the resolver's tests — origin reported per value, and an absent or malformed file yielding defaults rather than throwing, per NFR-001. packages/schema/test/config.registry.test.ts
Declare the registry — the ten sections with their keys, types, descriptions and defaults, in the one package all three others depend on. packages/schema/src/config/registry.ts
Build the resolver — read once, return values with origin, fail safe on anything unreadable. packages/schema/src/config/resolve.ts
Export it and wire the build — a subpath consumers can import, and the bundler entry alongside it. packages/schema/src/config/index.ts
 Closes FR-001, FR-002, FR-003 and NFR-001; evidences SC-001.

Phase 2 · US2 — one answer per key

Each module keeps its existing tests green as it moves; those tests are the regression guard, not an afterthought.

Migrate the corpus reader first — it is the package furthest from the kernel, so it proves the hosting decision before anything depends on it. packages/corpus/src/config.ts
Migrate the dedicated config modules — git, models and decider become thin typed views over the resolver rather than parsers. packages/cli/src/config/
Migrate the kernel's config modules — enforce and change-risk, keeping their fail-safe behaviour exactly. packages/core/src/enforce/config.ts
Migrate the inline kernel readers — units, contracts and the execution guard, whose defaults are security-relevant and must not shift. packages/core/src/units/read.ts
Migrate the inline command readers — validate, verify-exec, owner, init and the identity reads. packages/cli/src/commands/
Record any disagreement found — where two readers differed about a key or default, resolve it deliberately and write the resolution into this file's change log, per FR-005. specs/086-config-canonical-reader/tasks.html
 Closes FR-004 and FR-005; evidences SC-002.

Phase 3 · US3 — notice when the list falls behind

Write the guard's counter-example first — a planted read of an undeclared key that must fail the check, so the guard is proven rather than asserted (SC-003). packages/schema/test/config.drift.test.ts
Build the completeness guard — scan the source for configuration access and fail on a key the registry does not declare, naming it and where it was read. packages/schema/test/config.drift.test.ts
File the phantom key for triage — the advertised key with no reader, surfaced for a decision rather than implemented or removed here. inbox.html
Confirm nothing regressed — the full suite and a whole-corpus validate, with any failure reconfirmed in isolation before it is called a flake. packages/
 Closes FR-006, FR-007 and FR-008; evidences SC-003.

  3. 03 Aug 2026All 15 ticked. T-205 — what the migration found. The readers were never in conflict: they had divided the labour implicitly, some raising a loud error on a malformed file and the rest falling back, with the enforce reader saying so outright — "the git config reader owns the loud error for that". So the shared reader carries both policies as a named argument rather than picking one. The assumption underneath is unchanged and now visible: it holds only while a loud reader runs first, and would fail silently for a command that resolved enforcement alone. Two callers additionally need text rather than a file read — the contract notifier takes its IO on an injected port, and the config writer does read-modify-write — so a pure parseConfigText serves them, leaving exactly one parse in the repository. And the migration briefly broke two refusals: the writer and the unit-edge writer must treat an unparseable file as a refusal rather than as empty, or they clobber it. Their existing tests caught both, which is precisely the role the design assigned them.
