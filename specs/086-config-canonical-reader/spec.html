Specification · 086-config-canonical-reader

The canonical config reader

Sixteen readers, sixteen private opinions about what the defaults are, and no module in a position to say. Everything the tool wants to tell users about its own configuration waits on one place that knows.

Status Draft Spec ID 086-config-canonical-reader Owner Brian Corbin · @briancorbinxyz Reviewers — Created 03 Aug 2026 Principlesv1.9.0 Smallest demoableOne module that lists every configuration section and its default, with the readers taking their values from it. Read time

The tool's configuration defaults are not written down anywhere. They are sixteen inline fallback expressions, each sitting beside its one consumer, so no module can enumerate them and nothing can tell a user what the tool decided on their behalf. That blocks a published schema, a config command, a documentation page and an annotated starter — all four are derivations of a list that does not exist. This spec builds the list: one registry declaring every section, every key and every default as data, living where all three packages can reach it, with every reader taking its values from it. Two findings from surveying the ground are folded in: one advertised key has no reader at all, and a section counted in the survey turned out not to be one — so the registry ships with a drift guard, because a list claiming to be complete and quietly not is worse than no list.

1 · Context

The discoverable-defaults survey proposed that the tool be opinionated, not dogmatic, and always discoverable, and found the third clause failing across the board: ten configuration sections against five declared in this project's own file, no shape validation, no mention in --help, no config command, no documentation page. A misspelt key does nothing at all, silently.

Its first decision is the one this spec builds, and it reordered the obvious work. The tempting first move is to write the defaults down — generate an annotated config, or a page, or a schema. None of those is available, because the defaults are not data anywhere. Sixteen call sites read the configuration file independently, each reaching for its own key and supplying its own fallback inline. Nothing aggregates them. A generator would therefore be a second hand-written copy of knowledge held in sixteen places — a third source of truth, drifting from the other two.

Surveying the ground for this spec produced two corrections worth stating up front, because they are what the registry is for. One advertised key — documented in the README and honoured by a command's markdown — has no reader in the kernel at all; its only trace in the packages is a test asserting the markdown mentions it. And one section the survey counted turned out not to be a configuration section. Both were invisible until something tried to enumerate the whole surface, which is precisely the argument for enumerating it.

Users: every downstream discoverability surface, which cannot be built before this; and the maintainer, for whom "what is the default for this?" currently means reading source.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Ask the tool what its defaults are P1

As a surface that needs to describe the configuration — a schema generator, a command, a documentation page — I want to read every section, key and default from one place so that what I describe cannot disagree with what the tool does.

Acceptance: A single import yields every configuration section, its keys, each key's default, and whether it has one; nothing needs to know which module consumes a given key in order to describe it.

US2 · One answer per key, not sixteen P1

As a maintainer, I want every reader to resolve its values through the registry so that two parts of the tool cannot disagree about a default, and changing one changes it everywhere.

Acceptance: No module parses the configuration file for itself; each obtains typed values from the registry, and the existing behaviour of every migrated reader is unchanged unless a difference is deliberately resolved and recorded.

US3 · Notice when the list falls behind P2

As a reviewer, I want a check that fails when the code reads a key the registry does not declare so that a list that claims to be complete stays complete.

Acceptance: Introducing a read of an undeclared configuration key fails the check, naming the key and where it was read.

Edge cases

  • An advertised key with no reader. Surfaced, not silently adopted: declaring it would make the registry assert a capability that does not exist.
  • A key whose default differs between two current readers. A real possibility with sixteen independent fallbacks; the difference must be resolved deliberately and recorded, never averaged away.
  • A malformed or absent file. Every reader today fails safe to its default; that must survive migration exactly, since several of those defaults are security-relevant.
  • A key with no meaningful default — an identity, a list of waivers. The registry must distinguish "defaults to this" from "has no default", or a generated document will invent values.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A single registry MUST declare every configuration section, its keys, each key's type, and each key's default value as data — enumerable by a consumer that knows nothing about which module uses a given key.

Rationale

Enumerability is the whole point. A registry expressed as code paths rather than data can be read by a human and by nothing else, which leaves every downstream surface hand-written.

The registry MUST distinguish a key that has a default from one that has none, and MUST NOT represent the absence of a default as a default value.

Rationale

A project identity and a waiver list have no sensible default. Rendering them as empty strings or empty arrays in a generated document would advertise a value the tool does not actually assume.

The registry MUST live in the package that every other package already depends on, so that the corpus, kernel and command-line packages can all read it without creating a new dependency edge.

Rationale

A one-way package boundary is machine-enforced here: the corpus package must not import the kernel. A registry the corpus cannot reach would immediately need a second copy, which is the defect this spec exists to remove.

Every module that currently reads the configuration file MUST obtain its values through the registry, and MUST NOT parse the file for itself.

Migration MUST NOT change any reader's observable behaviour; where two readers currently disagree about a key or its default, the disagreement MUST be resolved deliberately and the resolution recorded, never silently averaged.

Rationale

The one thing a refactor of this shape must not do is quietly change what the tool does. Several current fallbacks are security-relevant defaults that fail safe.

A check MUST fail when the codebase reads a configuration key the registry does not declare, naming the key and its location.

Rationale

The registry's value is entirely in being trusted as complete. Without a guard it is complete on the day it ships and decays from the next commit — and a list believed complete but quietly stale is worse than no list, because downstream surfaces present it with confidence.

A configuration key that is advertised to users but has no reader MUST NOT be declared as though it were implemented; it MUST be surfaced for a decision instead.

Rationale

At least one such key exists. Declaring it would make the registry — and every document generated from it — assert a capability the tool does not have, which is the discoverability failure inverted rather than fixed.

The registry SHOULD record, per key, a one-line description suitable for presentation to a user.

Rationale

Every downstream surface needs prose per key. Held with the key rather than in each surface, it is written once and cannot diverge between the schema and the command.

Non-functional

Resolution MUST be deterministic and side-effect free apart from reading the file: the same file and working directory yield identical results across runs, and a malformed or absent file MUST yield defaults rather than an exception in 100% of cases.

Reading and resolving the whole configuration SHOULD complete in under 50 ms, so that a command paying this cost at startup is not measurably slower.

Out of scope (deferred to other slices)

  • Generating and publishing a schema from the registry, and writing the reference into new configurations.
  • The command that prints effective values with provenance. It reads this registry; it is not built here.
  • Accepting comments in a user's configuration. Cheap once one reader exists, and a separate decision.
  • What to do about the advertised key with no reader — implement it, or withdraw the advertisement. This spec surfaces it; choosing is a change to a shipped promise.

4 · Data model

One new concept, and one existing thing given a shape it never had.

Entities

Configuration registry
The complete declared surface: every section, the keys within it, and for each key its type, whether it has a default, and what that default is. It is data, not behaviour — its defining property is that a consumer can walk it without knowing what any key is for. It is authoritative: a key absent from the registry is a key the tool does not have, which is what makes the drift guard meaningful.
Resolved configuration
What a reader gets back: for each key, the value in force and whether it came from the file or from the default. Carrying the origin alongside the value is what later lets a user be told where a setting came from; discarding it, as the current inline fallbacks do, makes that question unanswerable after the fact.

The invariant worth stating: the registry describes the tool's configuration surface, and the file describes one project's choices within it. Anything in the file that the registry does not know about is unrecognised — not merely unused. That distinction is the whole basis for ever reporting a misspelt key, and it is why the registry must be complete before anything is built on top of it.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

Every configuration section and key the tool reads is obtainable from one enumeration — 100% of them, with no consumer needing to know which module uses which key.

0 modules parse the configuration file for themselves, and the full test suite passes unchanged apart from tests deliberately updated for a recorded behaviour resolution.

Adding a read of an undeclared configuration key fails the guard, and the failure names the key — demonstrated against a deliberately planted example rather than argued.

6 · Assumptions

The sixteen readers agree about the keys they share. Taken as true and explicitly not verified in advance — finding out is part of the migration, and FR-005 exists because the assumption may not hold.

Reading the whole configuration where a module previously read one section is affordable. The file is small and read once; if that proves wrong the registry can resolve lazily without changing its shape.

7 · Open questions

None outstanding. The scope — a complete registry with the full migration rather than a partial one — was anchored in the interview, and the package that must host it follows from the enforced dependency boundary rather than from preference.
