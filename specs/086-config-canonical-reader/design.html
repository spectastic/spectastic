Design · 086-config-canonical-reader

The canonical config reader

The package boundary decides where this lives, the existing readers decide what it must preserve, and a guard decides whether it stays true. Very little of it is a choice.

Status Accepted Spec 086-config-canonical-reader Owner Brian Corbin · @briancorbinxyz Created 03 Aug 2026 Principles v1.9.0 ArchitectureA declared registry plus a thin resolver in the shared floor package; every consumer reads through it. No new dependency edge. Coverage Diff-aware: the registry and resolver covered directly; each migrated reader keeps its existing tests as the regression guard. Read time

Where this lives is settled by a machine-enforced boundary rather than taste: the corpus package must not import the kernel, so @spectastic/schema — the only package all three already depend on — is the single legal home. The registry is a plain data structure walked by consumers that know nothing about any key's meaning; the resolver returns values with their origin, since discarding provenance is what makes "where did this come from" unanswerable today. Migration keeps each reader's existing tests as its own regression guard, and the drift guard is a test that greps the source for configuration access and fails on anything the registry does not declare.

3 · Data model & contracts

Nothing crosses a repository boundary. The registry is an internal module; the configuration file's shape is a user-facing surface, but this spec only describes what already exists rather than changing it — the published schema that would make it a contract is deferred.

The registry's physical shape is a frozen record of sections, each a record of key descriptors. A descriptor carries a type tag, an optional description, and either a default value or an explicit marker that there is none — FR-002's distinction, represented rather than implied, because undefined would be ambiguous between "no default" and "defaults to undefined".

5 · Approach

  1. Declare the registry in the shared floor package: ten sections, their keys, types, descriptions and defaults, with "no default" represented explicitly.
  2. Add a resolver that reads the file once and returns values with their origin, failing safe to defaults on anything unreadable.
  3. Migrate the readers, one module at a time, keeping each module's existing tests green as it moves. Where the file is read for a section that has a dedicated config module, that module becomes a thin typed view over the resolver rather than a parser.
  4. Add the drift guard — a test that scans the source for configuration access and fails on a key the registry does not declare — and prove it against a planted key.
  5. Surface the phantom key as a triage card rather than resolving it here.

Migration order is deliberate: the modules with a dedicated config file first, because they already have the shape and the tests, then the inline readers, which are the ones most likely to disagree with each other.

7 · Decisions

Status Accepted

Context The registry must be readable by the corpus, kernel and command-line packages. @spectastic/corpus depends only on @spectastic/schema, and a corpus→core import is failed by dependency-cruiser in CI (064's one-way boundary).

Decision The registry and resolver live in @spectastic/schema. Not a preference — it is the only package all three already depend on.

Consequences
+ No new dependency edge, and the enforced boundary stays intact without an exception.
+ Follows the precedent that put the shared project-identity and finding primitives in the same package.
− Schema accumulates responsibility beyond validation, and its name becomes a slightly poorer description of its contents.
− Anything the resolver needs must be available in the floor package, so it cannot reach for kernel helpers.

Status Accepted

Context The registry has to be walkable by a generator that knows nothing about any key, and the project's TypeScript settings are strict.

Decision Express it as plain frozen data and derive the types from it, rather than declaring types and keeping a parallel table of defaults.

Consequences
+ One artifact, so the types and the enumeration cannot drift apart — the failure mode the parallel-table option carries by construction.
+ A schema generator later walks the same structure with no adaptation.
− Deriving types from data is less readable than writing an interface, and error messages when it is wrong are worse.

Status Accepted

Context A resolved value that has lost track of where it came from cannot later be explained, which is what the deferred config command needs. The current inline fallbacks discard this.

Decision The resolver returns each value with its origin — file or default. Consumers wanting only the value take it from a thin accessor, so the extra structure costs the common case nothing.

Consequences
+ The next slice becomes a formatting exercise rather than a re-derivation.
+ Makes it possible to tell "explicitly set to the default value" from "not set", which is a real distinction for a user reasoning about their own file.
− Every consumer sees a richer return type than it needs; the accessor keeps that from being a burden, but it is one more concept.

Status Accepted

Context FR-006 needs a check that the registry has not fallen behind. A type-level guarantee would be stronger but cannot see a key read by string indexing, which is how several current readers work.

Decision A test that scans the source for configuration access and fails on a key the registry does not declare, proven against a planted example.

Consequences
+ Catches the string-indexed reads a compiler cannot, which is the majority of the current call sites.
+ Costs nothing at runtime and fails at the boundary where this project puts its guarantees.
− A textual scan is a heuristic: it can be evaded by a computed key, and it may need teaching about a legitimate pattern it does not recognise. That is a false failure rather than a false pass, which is the safer direction.

9 · Risks & mitigations

Two readers disagree today and the migration picks oneMediumMediumFR-005 forbids averaging: a difference is resolved deliberately and recorded in the change log where a reviewer can see it

10 · Complexity tracking

No principle exceptions. The registry adds a module to the floor package whose only justification is that three packages want it — which is the fat-core test met by evidence rather than anticipation, since all three already read the same file today.

11 · Open questions

None outstanding. The hosting package follows from the enforced dependency boundary, the registry's expression and the guard's mechanism were settled here, and the phantom key is deliberately surfaced rather than decided.
