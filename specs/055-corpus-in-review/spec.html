Corpus in review

Grounding isn't only an authoring concern — the same corpus that grounds a spec arms the critic that tries to break it.

1 · Context

The corpus family began as an authoring aid, but grounding is not only an authoring concern. A corpus is a grounding source wherever a domain claim is asserted or checked. The clearest downstream consumer is the adversarial critic pass (REQ-CHANGE-004): it already reads the spec and the principles to find the most regrettable change, the requirement most likely contradicted, and a scope concern — and a domain-aware critic gains a fourth angle, catching a requirement that quietly contradicts KB-001.

Two more surfaces benefit. The explain coaching read can cite real sources when it teaches a requirement. And the harness review skills (code-review, security-review) — which spectastic does not own — can still be fed a committed corpus. The honest framing keeps that distinction sharp: spectastic guarantees what it places in a prompt, never how a skill it doesn't own behaves.

2 · User scenarios & testing

Each story MUST be independently testable.

US1 · The critic catches a domain contradiction P1

As a proposer, I want the adversarial critic to read the corpus so that it flags a requirement that contradicts a cited domain fact before I apply the proposal.

Acceptance: a proposal whose delta contradicts a KB-001 fact produces a critic <spec-risk> naming the contradiction.

US2 · explain teaches from real sources P2

As a reader using explain, I want the coaching read grounded against the corpus when one is present so that the explanation cites the document a claim rests on, not model recall.

Acceptance: an explain of a corpus-grounded decision references the cited KB source.

US3 · The corpus reaches the review skills as data P3

As a reviewer, I want a committed corpus available to the harness review skills so that a review can consult domain facts — while the tool stays honest that it does not own or guarantee those skills' behaviour.

Acceptance: the committed corpus is discoverable by code-review / security-review as fed data; spectastic makes no behavioural guarantee about them.

Edge cases

  • No corpus present — critic, explain, and review behave exactly as today (NFR-001).
  • A corpus fact that the requirement neither asserts nor contradicts — no finding; the critic flags contradiction, not mere non-citation.
  • Corpus text carrying an injection payload reaching the critic — neutralised by the fence (FR-004).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

When a corpus is present, the adversarial critic pass MUST receive the corpus index (fenced) so it can flag a requirement that contradicts a cited domain fact.

Rationale

The critic already reads the spec and the principles; adding the corpus gives it a domain angle — the same reuse of the fenced-injection mechanism 054 establishes, on the review surface.

The explain coaching read SHOULD ground its explanation against the corpus when one is present, citing the source a claim rests on.

The corpus SHOULD be available, as fed data, to the harness review skills (code-review, security-review); spectastic MUST NOT claim to own or guarantee those skills' behaviour.

Rationale

These skills live in the harness, not in spectastic. The committed corpus is greppable data any of them can consult, but the tool's guarantee stops at what it places in a prompt — honesty about the boundary, not an overclaim.

All corpus text reaching these surfaces MUST pass through fenceArtifactText() (P-11); the sanitiser MUST NOT be forked or bypassed for the review surfaces.

Non-functional

Graceful absence. With no corpus present, the critic pass, explain, and any review surface MUST behave exactly as today — the same findings, the same coaching, no new output.

Out of scope (deferred to other slices)

  • Injecting the corpus into the authoring verbs (spec, plan) — the same guarantee, on the authoring surface.
  • The deterministic validate-time checks that a citation resolves / is current.
  • Guaranteeing the behaviour of harness review skills spectastic does not own — outside the tool's reach by construction.

4 · Data model

The entities this feature owns or substantially changes.

Entities

Critic corpus input
The fenced corpus index handed to the adversarial critic pass alongside the spec and principles it already reads.
Grounded explanation
An explain read that references the cited KB source(s) for the claims it teaches.

No new artifact type. This spec re-points an existing input (the critic's context, explain's context) at the corpus; the corpus itself is owned by 051, the fence by P-11.

5 · Success criteria

Technology-agnostic, measurable outcomes.

A propose whose delta contradicts a cited KB-001 fact produces a critic <spec-risk> naming the contradiction; the same proposal with no corpus does not.

An explain of a corpus-grounded decision cites the KB source; with no corpus, the explanation is unchanged from today.

With no corpus present, the critic pass produces the same findings it produces today on the same input.

6 · Assumptions

The adversarial critic pass and explain each expose a prompt-assembly seam where a fenced corpus block can be added, mirroring the principles injection.

The harness review skills consult committed files via agentic search; a corpus under knowledge/ is therefore reachable by them without spectastic wiring anything into skills it doesn't own.

7 · Open questions

None outstanding — the surfaces the corpus feeds and the ownership boundary (fed data, not a behavioural guarantee, for skills spectastic doesn't own) were anchored in the interview.
