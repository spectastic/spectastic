Design · 098-token-set-versioning

Token set versioning

How we will build it.

Status Accepted Spec 098-token-set-versioning Owner Brian Corbin · @briancorbinxyz Branch spec/visual-slice-095-098 Created 12 Aug 2026 Read time

An HTML artifact beside the token set carrying its version, its bump policy as prose in the same file, and the forward-only binding — which is precisely how principles.html already works, and the reason a bump here is affordable rather than a migration project. The amendment guard is a compare-and-swap cloned from the principles apply: refuse when the declared from-version does not equal the live one, naming both. That needs no notion of which version is later, which matters because NFR-001 forbids computing an ordering — every versioning mechanism in this project compares by equality and none orders, and that is a property to preserve rather than a gap. The change class is the three bump tiers themselves rather than a second vocabulary, and every surface says producer claims, because breaking-change detection for tokens does not exist: hundreds of classified rules for an API contract, one diffing plugin for a design system.

3 · Data model & contracts

Three conceptual entities, two elements and one attribute. Nothing is persisted; the version is authored and read.

Conceptual entityPhysical shapeNotes
Token set version <spec-token-set version binds-from external-base>, in visual/tokens.html. The bump policy is the element's own prose, in the same file — a policy that lives elsewhere is one nobody reads at the moment of bumping.
Release <spec-release from to class> class is one of the three bump tiers, and every surface renders it as a claim.
Deprecation The token format's own $deprecated channel, in the JSON. Not re-expressed here. FR-007 is explicit that the format's channel is used rather than a mechanism invented in this project.
Binding stamp tokens-version on <spec-screen>. The screen is the work that gets accepted, so the stamp travels with the thing whose conformance is in question.

This feature exposes no interface. It adds a version, a policy and a claim to material that already exists.

5 · Approach

One artifact at visual/tokens.html carrying <spec-token-set> with the version, the binding, and the bump policy as its own prose; plus a <spec-release> per transition. A schema rule checks the shape and the closed class set; a second checks that a release never removes a token it deprecates in the same breath. A kernel guard refuses an amendment whose declared from-version does not equal the live one.

The design is almost entirely inherited. The guard is the principles apply's, the producer-claims rendering is 077's, the policy-in-the-artifact is principles.html's, and the deprecation channel is the token format's own. What this spec adds is the observation that they compose: a version that binds forward only, checked by equality, with a change class nobody pretends to verify, is a versioning scheme that costs a team almost nothing to adopt — which is the property that makes it get used.

The temptation this design refuses is ordering. Once a tool can say which of two versions is later it can offer "you are three releases behind", and that is genuinely useful — but it requires committing to a comparison contract forever, and every existing mechanism here has declined to. NFR-001 makes the refusal a requirement, and the test asserts the module contains no comparison at all rather than merely not calling one.

6 · Alternatives considered

The choice with real alternatives was the change-class vocabulary. Scored on whether it needs a second vocabulary kept consistent with the tiers, how well it tells a consumer what happened, and whether two fields can contradict each other. 5 is best.

OptionOne vocabularyTells a consumer what happenedCannot self-contradictTotal
breaking / additive / corrective25512
Tier plus an impact word1517
The three bump tiers — chosen53513

The impact words genuinely describe a release better, and lose because FR-009 already speaks in tiers — "classified at the highest tier of the bump policy" — so a second vocabulary would need mapping onto the first, and the policy prose already says what each tier means. The two-field option is worst: two values that can contradict each other, with nothing able to adjudicate.

7 · Decisions

D-001 · The version lives beside the token set, with its policy in the same file

Status
Accepted
Context
FR-001 requires the bump policy in the artifact carrying the version, because a policy living elsewhere is one nobody reads at the moment of bumping. The token format defines no version field — the survey corrected itself on this — so putting it in the JSON means inventing one, from a draft that says not to implement it.
Decision
visual/tokens.html, carrying <spec-token-set> and the policy as its prose. The JSON stays pure DTCG.
Consequences
+ The token files stay portable to every other tool that reads the format. + The policy sits where somebody about to bump will see it, exactly as principles.html does. − The version is one file away from the tokens it describes, so a build reading only the JSON cannot see it — acceptable, because checking a build against its claimed version is explicitly another slice.

D-002 · Compare-and-swap on equality, and no ordering anywhere

Status
Accepted
Context
FR-004 wants a stale amendment refused; NFR-001 forbids computing an ordering. Both are satisfied by the same mechanism, and the principles apply already implements it — reading the live value, comparing for equality, throwing with both values named.
Decision
Clone it. The guard compares strings for equality and contains no comparison operator over versions at all; a test asserts the absence rather than the behaviour.
Consequences
+ No format contract is taken on beyond what the policy states. + A stale amendment cannot land on top of one it never saw. − The tool can never say "you are three releases behind", which is genuinely useful and genuinely requires a commitment nothing here has made. − Two amendments produced from the same live version race, and the second is refused rather than merged; refusal is the honest outcome.

D-003 · The change class is a claim, and the tiers are the vocabulary

Status
Accepted
Context
oasdiff classifies 509 distinct changes for an API contract; for design tokens the state of the art is one diffing plugin. Nobody has classified what "breaking" even means for a token, so a tool asserting it would be inventing the taxonomy and presenting the invention as a finding.
Decision
A closed set of the three bump tiers, rendered everywhere as "producer claims …", cloning 077's wording and its stylesheet treatment. Nothing verifies it, and FR-006 forbids any future diff from reporting whether a change breaks — only what changed.
Consequences
+ One vocabulary, already defined by the policy prose. + The tool never asserts something no mechanism establishes. − A consumer reading "minor" learns how far the number moved, not what happened to them; the release's prose carries that, and prose is not checkable. − A producer can claim wrongly and nothing notices, which is stated rather than mitigated.

D-004 · The binding stamp goes on the screen, because the screen is what gets accepted

Status
Accepted
Context
FR-003 wants the version recoverable after later bumps, so the stamp must travel with whatever's conformance is in question. A feature-level stamp loses the ordinary case where two screens in one feature were accepted months apart.
Decision
tokens-version on <spec-screen>, the element 095 already defines.
Consequences
+ Per-screen granularity matches how work is actually accepted. + Reuses an element rather than adding one. − A ten-screen feature carries ten stamps that mostly agree, which is repetition a feature-level stamp would have avoided; accepted because the disagreeing case is the one that matters.

D-005 · Deprecation uses the token format's own channel, not one invented here

Status
Accepted
Context
FR-007 is explicit, and the format already carries a standard deprecation field taking a replacement message. Re-expressing it in this project's vocabulary would make a rename legible to this tool and invisible to every other one that reads the file.
Decision
Deprecation lives in the JSON, in the format's channel. This spec adds only the release-level rule that a token is not removed in the release that deprecates it, and that removal is classified at the highest tier.
Consequences
+ A rename ships the new token, a working alias and a reason, all readable by other tooling. − The deprecation and the release that describes it live in different files, so nothing cross-checks that a release claiming a deprecation actually made one; a real gap, and smaller than the interoperability it buys.

9 · Risks & mitigations

10 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here.

A test asserting the absence of a version comparison is more than NFR-001 literally asks for — it asks that at most 0 orderings be computed, which a behavioural test could establish for the cases it covers. The source-level assertion is here because the requirement is about what the module must never learn to do, and that is a property of the code rather than of any particular call.
