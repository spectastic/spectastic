Specification · 098-token-set-versioning

Token set versioning

A version that binds forward, so a bump is not a migration project — and a change class that says "claims", never "is".

Status Accepted Spec ID 098-token-set-versioning Owner Brian Corbin · @briancorbinxyz Reviewers — Created 12 Aug 2026 Principlesv1.9.0 Smallest demoableA token set at 2.0.0 with a screen bound to it; a bump to 2.1.0 leaves that screen conformant and says so. Read time

The token set is the one piece of visual material every feature depends on, which makes it the only piece that needs a version. This gives it one, and the whole design is borrowed from the single versioned artifact this project already has: semantic versioning, a stated bump policy written into the file itself, a compare-and-swap guard so two amendments cannot race, and — the clause that matters most — forward-only binding. A version binds the work authored after it and does not reopen what was accepted before, which is the answer to the question that stops most design-system bumps: what happens to the forty screens already built. A release also declares a change class, and that class is the producer's claim rather than a verified property. Nothing checks it, and nothing can: an API contract has 509 classified breaking-change rules behind it, while the entire tooling for diffing design tokens is one editor plugin. Deprecation uses the token format's own channel rather than a local invention, so a rename ships an alias and a deadline instead of a removal.

1 · Context

A feature's visual spec has a change log and no version, because it changes when the feature changes and affects nothing else. The token set is the opposite: it changes on its own schedule and every screen in the project depends on it. Those are different rates of change, and one number over both would be wrong in one direction or the other — either bumping a design system because a single feature moved, or changing a colour and silently invalidating work nobody re-examined.

The hard part is not the number. It is what the number does to work already accepted. The field's usual answers are a deprecation window and a migration project; this project already has a better one in use on its own constitution, and has never applied it twice.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · A bump does not reopen finished work P1

As a design-system owner, I want a version to bind the work authored after it so that changing a token is not a project-wide migration.

Acceptance: A screen accepted under one version remains conformant to that version after a later one lands, and the version it was built against is recoverable.

US2 · Two amendments cannot race P1

As a reviewer, I want an amendment that was written against a superseded version to be refused so that a stale change cannot land on top of one it never saw.

Acceptance: An amendment declaring a from-version that no longer matches the live one is refused with both values named.

US3 · A rename does not break a consumer overnight P2

As a consumer of a renamed token, I want the old name to keep working while telling me what replaced it so that I can migrate on my own schedule.

Acceptance: A renamed token ships alongside a deprecated alias naming its replacement; removal happens in a later, larger bump.

Edge cases

  • A token set extending an external one, where the base moves on the vendor's schedule and only overrides are local.
  • A change nobody can classify — a darker accent that breaks a contrast ratio without touching a layout.
  • A project with a token set and no screens yet, where forward-only binding has nothing to protect.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The token set MUST carry a semantic version, and its bump policy MUST be stated in the artifact that carries the version rather than only in documentation.

Rationale

A policy that lives elsewhere is a policy nobody reads at the moment of bumping. The project's own constitution states its policy in its governance section, and that is the precedent.

A version MUST bind forward only: it governs work authored or amended from that version onward and MUST NOT reopen work already accepted under an earlier one.

Rationale

This is the clause that makes bumping affordable. Without it every change to a shared design system is a migration project, which is why most teams stop making them.

Work bound to the token set MUST record which version it was accepted under, so that conformance is recoverable after later bumps.

An amendment MUST declare both the version it was written against and the version it produces, and MUST be refused when the declared from-version does not equal the live one.

Rationale

A compare-and-swap rather than an ordering check. It needs no notion of which version is later, which is the property every versioning mechanism in this project deliberately lacks.

A release MUST declare a change class drawn from a closed set, and every surface that displays it MUST present it as the producer's claim rather than as a verified property.

Rationale

Breaking-change detection is mature for API contracts and absent for design tokens — hundreds of classified rules on one side, a single diffing plugin on the other. Presenting the class as verified would assert something no mechanism establishes.

Nothing MUST claim to verify the change class, and any diff that is built MUST report what changed rather than whether it breaks.

Deprecation MUST use the token format's own deprecation channel, naming the replacement, rather than a mechanism invented here.

Rationale

The format already carries a standard deprecation field, so a rename can ship the new token plus a working alias and a reason. Using it keeps the deprecation legible to every other tool that reads the file.

A token MUST NOT be removed in the same release that deprecates it, and removal MUST be classified at the highest tier of the bump policy.

A token set that extends an external one SHOULD version only what it owns, and SHOULD record the external base's version separately rather than folding it into its own.

Rationale

The base moves on somebody else's schedule. Folding two clocks into one number reproduces exactly the error this spec exists to prevent, one level up.

A project MAY state a deprecation window, and MAY choose any length — this spec requires that one be stated where a token is deprecated, not that it be any particular duration.

Non-functional

Version comparison MUST be equality only, with at most 0 orderings computed, so that no format contract is taken on beyond the one the policy states.

Rationale

Every versioning mechanism in this project compares by equality and none orders. That is a property to preserve: equality is decidable without agreeing an ordering, and a mechanism claiming to know which version is later must then enforce that claim forever.

The guard MUST fail closed: on a malformed or absent version it MUST refuse the amendment, with at most 0 amendments applied on an unreadable version.

Out of scope (deferred to other slices)

  • Checking a build against the version it claims to be bound to.
  • The external base's own version, which this spec keeps separate without describing.
  • Importing a token set from a design tool, and what its version means on arrival.

4 · Data model

No persisted entity. This spec adds a version, a policy and a claim to material that already exists.

Entities

Token set version
A semantic version on the project's token set, with a stated bump policy and a from-version binding. One per project.
Release
One transition from one version to the next, carrying a change class that is the producer's claim and is never verified.
Deprecation
A token marked superseded, naming its replacement, expressed in the token format's own channel. Survives at least one release before removal.

The version answers "which rules was this built under", not "which is newer". Nothing here orders two versions; the binding compares for equality against a recorded value, which is all the mechanism needs and all it can honestly promise.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

After a bump, the count of previously-accepted screens reported as non-conformant is 0, and the version each was accepted under is recoverable for 100% of them.

An amendment declaring a stale from-version is refused 100% of the time, naming both the declared and the live value.

Across every surface that displays a change class, the count asserting it as verified rather than claimed is 0.

A renamed token remains resolvable through at least 1 subsequent release, with its replacement named.

6 · Assumptions

Authors will classify a release honestly. A wrong claim is worse than no claim because it looks like diligence, and this spec accepts that weakness knowingly — the alternative is asserting a verification nothing performs.

One project has one token set to version. A repository holding two products with two design systems would need two, which this spec does not provide.

7 · Open questions

None outstanding. The semver policy, the forward-only binding, the compare-and-swap guard and the claims posture each transfer from a working precedent in this project, and the refusal to detect breaking changes is settled by the survey rather than deferred.
