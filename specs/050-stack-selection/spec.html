Specification · 050-stack-selection

Stack selection at the plan stage

Give the plan a way to help you choose the stack, not just transcribe it — a context-seeded interview for the undecided picks — and make the decision it records honest, not a rationalisation of what was already chosen.

Status Accepted Spec ID 050-stack-selection Owner Brian Corbin · @briancorbinxyz Reviewers — Created 22 Jul 2026 Principlesv1.8.0 Smallest demoableOn a greenfield plan, one undecided stack dimension is offered as a bounded choice with a context-seeded recommendation, and the confirmed pick lands in §2 — no hand-editing. Read time

Today the plan records a stack it was handed; it never offers the choice, and the decision it writes crowns whatever was chosen regardless of the scores. This spec does both. First, an optional, self-skipping stack-selection interview surfaces every undecided material pick as a bounded choice with a context-seeded recommendation — from repo detection, standing docs (CLAUDE.md/AGENTS.md/a linked architecture doc), and the frameworks profile stance — never a maintained house catalog. Second, it makes the record honest: <spec-decision> gains an optional MADR-style Considered Options list with pros/cons and decision drivers, a matrix can link to its decision, and a validate rule requires the crowned winner to be the top-scored row. The halves compose: a material interview pick auto-scaffolds its decision card with the offered options pre-filled.

1 · Context

The plan stage defines the technical stack, but authors it by hand: the §2 Technical-context rows (Language, Frameworks, Storage, Testing) are filled from grounding reads and narrative chat. The decision-phase interview records a pick whose contenders already surfaced — it never generates a bounded choice-set with a recommendation for a decision not yet made (Java vs C++, Spring Boot vs Quarkus, no-dep vs Cobertura vs JaCoCo). The plan command never reads CLAUDE.md/AGENTS.md/a linked architecture doc, so it cannot tell what is already decided to skip it; and the frameworks profile axis that could seed a recommendation is an inert token with no code consumer.

Separately, the record is biased: each <spec-decision> card is a Nygard ADR recording only the chosen path, and the matrix's data-winner highlight is bound to the choice, not the score — nothing checks the crowned row is the top-scored one. This spec builds out the stack-selection considerations doc, for the developer driving a plan and the reviewer reading its decisions.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Offer the undecided choice P1

As a developer planning a greenfield feature, I want to be offered bounded stack choices with a recommendation for decisions I haven't made so that I don't hand-fill §2 or research options blind.

Acceptance: on a plan where the framework is undecided, the plan presents a bounded choice with one context-seeded recommendation; confirming it writes the pick into §2 without hand-editing.

US2 · Never re-ask a settled decision P2

As a developer whose stack is already fixed (existing repo or a standing doc), I want the plan to skip questions it can already answer so that the interview only surfaces genuine gaps.

Acceptance: a plan whose language/framework are fixed by detection or a standing doc raises zero questions for those dimensions.

US3 · A record that informs, not rationalises P2

As a reviewer, I want a decision's record to show the real alternatives with pros/cons and a winner that matches the scores so that the record explains the choice instead of dressing it.

Acceptance: an interview-driven decision shows ≥2 considered options with pros/cons; a matrix whose crowned row is not the top-scored one is flagged by validate.

Edge cases

  • No signals at all (empty greenfield, no standing docs, no profile) — options are presented neutrally with no "(Recommended)" crown; the interview never invents a preference.
  • Conflicting signals (a standing doc says X, detection says Y) — the conflict is surfaced to the user, never silently resolved.
  • Placeholder matrix (scores are template [N] placeholders, not numbers) — the winner-integrity rule skips it, so unfilled templates don't false-fire.
  • Opted out (spectastic.json disables it) — the pass does not run; §2 stays hand-authored, exactly as today.
  • One viable option — the pick is recorded with no matrix; the spec never fabricates alternatives to fill a table.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional — the stack-selection interview

The plan MUST, in its decision phase before §2 is written, run a stack-selection pass that identifies the undecided material stack dimensions and presents each as a bounded choice.

Rationale

Today the one stack bullet only records picks whose contenders already surfaced; nothing generates a choice-set for an undecided dimension. This is the core capability.

Each recommendation MUST be context-seeded — drawn from repo detection, standing docs (CLAUDE.md/AGENTS.md/a linked architecture doc), and the frameworks axis stance — and MUST NOT come from a spectastic-maintained house catalog. Where no source decisively implies a winner, options MUST be presented with no "(Recommended)" crown.

Rationale

Honours the detector's charter ("report gaps, never prescribe a specific tool") and the plan's "prompt, don't prescribe": the recommendation is contextual, overridable, and silent when context doesn't earn it.

The pass MUST be self-skipping: any dimension already fixed by detection or a standing doc is not asked. Conflicting signals across sources MUST be surfaced, not silently resolved.

The pass MUST cover any undecided material stack pick (e.g. language, framework, test framework, coverage tool, persistence, build tool), not a fixed list, and MUST coordinate with — not duplicate — the existing architecture-pattern question and the profile's enforcement-tool resolution.

Rationale

"Cobertura vs JaCoCo" sits on the boundary with enforcement-tool resolution: the interview surfaces the undecided choice, the profile resolves the enforcement policy — neither re-asks the other's question.

The pass MUST be auto-attempted by default and MUST be opt-out-able via a spectastic.json setting; when disabled, §2 is authored exactly as today.

The frameworks axis (minimal / conventional / staff-level) MUST map to a build-vs-buy recommendation lean that seeds the default (minimal → stdlib/no-dep; conventional → mainstream; staff-level → mature, batteries-included). The lean is an advisory tie-breaker, not a gate.

Rationale

Gives the inert axis its first consumer. Detection and standing docs still dominate; the axis only breaks ties in the recommendation.

Confirmed picks MUST be written into the §2 Technical-context rows of the plan.

Functional — the honest decision record

<spec-decision> MUST support an optional MADR-style Considered Options list (per-option pros/cons) and named decision drivers, additive to the existing Context / Decision / Consequences. Existing Nygard-shaped cards MUST remain valid unchanged.

Rationale

Augment, not replace — 49 existing specs use the Nygard shape. The new fields appear only where an author (or the interview) adds them.

A <spec-matrix> SHOULD be linkable to its governing <spec-decision> via a target= attribute, mirroring <spec-risk target> and <spec-slo target>.

A validate rule MUST require the data-winner row of a matrix to carry the top Total, and MUST skip any matrix whose scores are non-numeric placeholders so unfilled templates do not fire.

Rationale

This is the enforceable guarantee (P-8): the interview is an advisory nudge, but the winner-integrity check is a kernel/CI floor that a divergent record cannot pass.

When the interview settles a material pick, it MUST auto-scaffold a <spec-decision> whose Considered Options are pre-filled from the offered choices and whose recommendation is captured as a decision driver.

Rationale

The payoff of shipping both concerns together: the honest record is a byproduct of the interview, not extra manual work.

Non-functional

The pass and the winner-integrity rule MUST be deterministic given identical repo state — no network, and the same inputs yield the same recommendation and the same finding every run.

The winner-integrity rule SHOULD add no new runtime dependency and SHOULD follow the existing per-file schema-rule shape.

Out of scope (deferred to other slices)

  • A maintained per-ecosystem house stack catalog — deliberately never built; it contradicts the brownfield "never prescribe a specific tool" charter.
  • Automated weighted multi-criteria (ATAM-style) scoring of options — the matrix stays author-scored; only its winner integrity is checked.
  • Migrating the 49 existing Nygard decision cards to full MADR — augment-only was chosen.
  • Architecture-pattern selection and enforcement-tool resolution already live in the plan verb — coordinated with, not re-specified here.

4 · Data model

The feature owns the shape of an undecided stack decision and extends two existing artifact elements.

Entities

Stack dimension
A material pick under consideration: its name, its detected/standing value or undecided, the candidate options, the seeded recommendation (or none), and the source that seeded it (detection / standing doc / axis).
Opt-out setting
A spectastic.json key (e.g. plan.stackInterview: false) that disables the pass.
Decision (extended)
<spec-decision> gains optional Considered Options (each with pros/cons) and decision drivers, additive to Context/Decision/Consequences.
Matrix link
<spec-matrix target="D-NNN"> ties a scored matrix to its governing decision.

Invariant: a matrix's crowned data-winner row and its top Total are the same row — unless the scores are placeholders, in which case the check stands down. The record never crowns a loser.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

On a greenfield plan where the framework is undecided, the user is presented a bounded choice with a context-seeded recommendation and the confirmed pick appears in §2 — with no hand-editing of the template.

A plan whose language and framework are already fixed by detection or a standing doc raises zero stack-selection questions for those dimensions.

An interview-driven decision card shows ≥2 considered options with pros/cons, and validate flags a matrix whose crowned row is not the top-scored row (while passing a matrix with placeholder scores).

Every pre-050 spec.html and design.html in the repository still validates with zero new findings after the change ships.

6 · Assumptions

The interview itself is advisory (a UX nudge that cannot be guaranteed to run); the enforceable guarantee is the winner-integrity validate rule and the MADR schema shape, per P-8 / T-009.

Standing-doc ingestion reads CLAUDE.md/AGENTS.md and a doc explicitly linked from them or the spec; it does not crawl the repository for architecture prose.

"Material" picks are app-stack and tooling choices a plan would record in §2; ephemeral or trivial dependencies are not interviewed.
