Change proposal · 050-stack-selection

Withdraw a configuration key nothing reads

A documented switch that no code consults is a promise the tool does not keep.

Status Proposed Change ID 2026-08-12-withdraw-stack-interview-key Spec 050-stack-selection Author Brian Corbin · @briancorbinxyz Created 12 Aug 2026 Targets 1 requirement(s) Read time

design.stackInterview is documented in the README and honoured by the design command's markdown, and no package reads it. Its only appearance under packages/ is a test asserting the markdown mentions it. A user setting it to false gets the interview anyway. Two ways out — implement it or withdraw it — and this proposes withdrawal, because the gate it would control lives in a prompt, and a guarantee resting on command markdown is one this project has already ruled out twice.

Withdraw a configuration key nothing reads

Proposed

1 · Intent

The key is advertised as a way to turn the stack-selection interview off. Nothing reads it. The interview is run by the design command's markdown, so the only thing that could honour the key is a model choosing to — which T-009 and P-8 both exclude as a place a guarantee may live.

Implementing it properly would mean moving the interview's gate into the kernel, which is a much larger change than the key implies and is not obviously wanted. Withdrawing it costs a line of documentation and makes the tool's surface honest.

2 · Scope

In scope

  • Removing the key from the documented configuration surface.
  • Recording that the interview is unconditional, so its absence is a decision rather than an omission.

Out of scope

  • Moving the interview into the kernel so a key could gate it — the larger change, deliberately not requested here.
  • Any other configuration key; this touches one.

3 · Approach

Withdraw rather than implement, and say why in the requirement itself so the next reader does not re-propose the key. If a kernel-side interview later exists, reinstating the key is a small proposal against a spec that will by then have somewhere real to put it.

4 · Deltas

What changes: the requirement stops implying a configurable interview and states plainly that it is unconditional, with the reason.

Stack recommendations MUST be seeded from the project's own context and MUST NOT come from a house catalog; where nothing in the context implies a winner, options MUST be presented without a recommendation. The interview MUST be unconditional: no configuration key gates it, because the interview is run by command markdown and a switch that only a prompt honours is not a switch.

Rationale

A configurable gate was advertised as design.stackInterview and read by no package, so setting it changed nothing. Stating the unconditionality here stops the key being re-proposed, and leaves reinstating it as a small change once the interview has a kernel-side owner that could honour it.

5 · Risk register

The adversarial pass triggered on a must-tier requirement being modified. One finding, recorded and answered.

Withdrawing the key removes a capability some user may already be relying on, without a migration.

"no configuration key gates it"

Accepted rather than mitigated. Nothing reads the key, so no user can be relying on its effect — only on its documentation. The migration is that the interview they hoped to disable was never disabled; naming that plainly is the honest correction.
