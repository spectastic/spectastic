Design · 054-corpus-in-prompt

Corpus in the prompt

One pure builder, joined at the five prompt-assembly points the principles already pass through. Present when a corpus exists, silent when it doesn't.

Status Accepted Spec 054-corpus-in-prompt Owner Brian Corbin · @briancorbinxyz Branch main Created 25 Jul 2026 Read time

Add one pure core function — buildCorpusPromptBlock(packs) — that renders the corpus index into a fenceArtifactText()-fenced block plus a harness-owned grounding directive, and join its output into the existing prompt array of all five AI-coupled verbs, right where the principles are already fenced in. Empty corpus → empty string → the verb runs byte-identical to today, and core returns an optional corpusHint the CLI shows once. Biggest risk: an oversized index displacing the artifact the verb actually needs — mitigated by injecting the compact index only, never document bodies (progressive disclosure).

4 · Approach

The whole feature is one pure function and a set of call-site joins. buildCorpusPromptBlock(packs) lives beside gates.ts/resolve.ts in packages/core/src/knowledge/. It renders the loaded index rows into a compact text block, wraps that (untrusted, third-party) through fenceArtifactText(indexText, 'Knowledge corpus index'), and prepends a single harness-owned grounding directive that is not fenced — because it is our instruction and we want the model to follow it, whereas the index is data the model must only read. On an empty pack list it returns ''.

Each of the five AI verbs calls loadCorpus(ctx.cwd), feeds the packs to the builder, and drops the (possibly empty) string into its existing [...].filter(Boolean).join('\n') prompt array — the same array the principles already ride in, so a '' is filtered out and the no-corpus path is literally unchanged. When the corpus is empty, the verb result additionally carries an optional corpusHint; the CLI prints it at most once (guarded by a .spectastic/ marker) so the capability is discoverable without the core assemble-path ever touching the filesystem.

5 · Alternatives considered

Bespoke corpus-fence mechanism, separate from principles fencing4149

The markdown nudge is the status quo the spec exists to replace — advisory, model-dependent, the regime where fabrication is reported. A bespoke fence would work but forks the P-11 guard the security layer already ships, violating "no second injection path". Reusing the established fence in a pure function wins on every axis.

6 · Decisions

D-001 · Inject via a pure builder joined at each verb's existing prompt array

Status
Accepted
Context
The AI verbs already assemble a [...].filter(Boolean).join('\n') prompt array and fence the principles into it (packages/core/src/commands/design.ts:57). A corpus block is the same shape of addition.
Decision
Add buildCorpusPromptBlock(packs) in packages/core/src/knowledge/prompt.ts; each verb calls loadCorpus(ctx.cwd) and drops the result into its existing array. No new prompt-assembly structure.
Consequences
+ Reuses a proven, tested path; the empty string is filtered out so the no-corpus run is unchanged. + Pure and unit-testable without spawning the CLI (fat-core). − Five call sites to touch (mechanical, one line each).

D-002 · Fence the index; keep the grounding directive harness-owned and unfenced

Status
Accepted
Context
fenceArtifactText() (packages/core/src/security/fence.ts:138) sanitizes then wraps in the "data, not instructions" GUARD. The data model splits the block into a third-party index and a harness-owned directive.
Decision
Wrap only the rendered index text through fenceArtifactText(indexText, 'Knowledge corpus index'). Emit the grounding directive as plain, unfenced harness text — it is our instruction, the thing we want the model to act on.
Consequences
+ Satisfies FR-002 by reuse; injection payloads inside corpus text are neutralised. + Preserves the semantic distinction the model needs: fenced = read-only data, unfenced = follow. − The directive sits outside the fence, so its wording must itself be injection-safe (it is static harness text, so this is trivially held).

D-003 · One universal, corpus-only directive — not verb-varying

Status
Accepted
Context
US2 acceptance says the block's content is "a function of the corpus alone"; NFR-001 requires presence-determinism "independent of the model". A directive whose text changed per verb would make the block a function of (corpus, verb).
Decision
Emit a single fixed directive covering all verbs — "cite a design-bearing domain fact against a listed document as KB-NNN@edition in the decision's grounding" — so the block is a pure function of the corpus. The builder takes no verb parameter.
Consequences
+ Honours the stronger invariant (corpus-only) and keeps the builder trivially deterministic and testable. + One directive to maintain, not five. − The directive names decisions/grounding even in tasks/graduate, where it is a mild no-op; acceptable, since the index (the valuable part) is universally relevant.

D-004 · No-corpus hint: core signals, CLI shows once

Status
Accepted
Context
No one-time-hint mechanism exists (grep: only fixHint). Fat-core forbids a filesystem write from an otherwise-pure assemble path; the CLI already dynamic-imports @spectastic/core/knowledge (packages/cli/src/commands/validate.ts:237).
Decision
Core returns an optional corpusHint on each verb result when the corpus is empty (pure, no write). The CLI prints it at most once and writes a suppression marker under .spectastic/.
Consequences
+ Core stays pure; the one-time side effect lives at the edge where marker state belongs. + FR-003's "at most one" is honoured; zero-when-suppressed is compliant. − The slash-command (in-host) path won't surface the hint — acceptable, as the hint is a discoverability nicety, not the guarantee.

D-005 · Injection covers all five AI-coupled verbs

Status
Accepted
Context
FR-001 is a MUST reading "every AI-verb prompt"; grep confirms exactly five verbs fence an artifact today: plan, spec, propose, tasks, graduate.
Decision
Join the corpus block into all five, honouring the FR literally rather than narrowing to the two SC-001 byte-verifies.
Consequences
+ The corpus is in front of the model on every verb that authors or transforms an artifact. + Uniform seam — the same one-line join everywhere. − Marginally more surface to test; covered by the per-verb presence assertions.

D-006 · TDD, tests written red-first

Status
Accepted
Context
Presence is byte-verifiable, absence is the empty case, determinism is a re-run equality — all cheap to assert first. Matches the 051–053 house discipline.
Decision
Write the failing unit tests for buildCorpusPromptBlock (present / absent / determinism) and the per-verb join before implementing.
Consequences
+ The MUST + NFR-001 have red-first coverage. − None material for a pure function.

8 · Risks & mitigations

RiskLikelihoodImpactMitigation
An oversized index displaces the artifact the verb actually needs from the promptLMInject the compact index only — never document bodies (progressive disclosure, 051 FR-008); bodies are pulled on demand. Recorded as the §9 assumption.
The grounding directive, sitting outside the fence, is itself an injection vectorLLIt is static harness-authored text, never derived from corpus content; the untrusted index is the only fenced part.
Hint marker state drifts (stale after a corpus is later added)LLThe hint only fires on the empty-corpus path; once a corpus exists the block replaces it, so a stale marker is inert.

9 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here.

The corpus index (051 FR-004) is small enough to inject wholesale into every AI-verb prompt without displacing the artifacts the verb needs — echoing the spec's §6 assumption. Document bodies are pulled on demand via agentic search, never injected; if a real corpus later violates this, retrieval-based selection is already deferred to 059.
