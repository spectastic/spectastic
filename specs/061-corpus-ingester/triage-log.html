FR-008 remote-source ceiling lifted — RealPackFetcher now git-clones an object-sourced plugin

Implementation code

Not a defect — a deliberately-deferred ceiling now built. FR-008 ("the import door MUST drive the install") shipped cache-read-only: an installed or string-sourced plugin resolved, but an object-sourced (remote) plugin threw and named /plugin install as the ceiling (plan D-002 / the T-100 spike, to avoid re-implementing git). That ceiling is now lifted — a remote plugin is git-cloned. Regeneration passes: the change is entirely in code behind the existing seam; the spec/plan are unchanged and still correct.

Expected
An object-sourced plugin in an added marketplace resolves without a manual /plugin install — FR-008's "drive the install" met for the remote case, not just the cached one.
Actual
Before: RealPackFetcher threw PackFetcherError on an object source, naming /plugin install / --from as the only paths.
Diagnosis
A recorded scope ceiling (plan D-002), not a bug: the object-source clone was deferred at 061 to avoid re-implementing a git client. Building it fully satisfies the must-tier FR-008.
Fix
packages/core/src/providers/pack-fetcher.ts — a new GitRunner seam (real impl shells a hardened git; a fake is injected in tests so CI never clones) + parseGitSource for the url/git-subdir/github shapes. Clones shallow, no submodules, hooks disabled, pinned to the manifest sha when present; cached under ~/.claude/plugins/.spectastic-cache/<coordinate>@<rev> and reused. 14 fetcher tests green.
Fixed
The FR-008 remote-source ceiling is lifted — RealPackFetcher git-clones an object-sourced plugin (shallow, cached, atomic .partial rename) behind an injectable GitRunner, with fakes in the tests.
Deep dive — security posture + the residual ceiling

Trust boundary. The clone URL comes from a marketplace the user added via /plugin marketplace add — a trust decision already made — so import clones by default (no extra --allow gate, unlike the arbitrary-web-fetch source door). Integrity comes from pinning to the manifest's immutable sha when present (the supply-chain-integrity-considerations lever), plus a hardened clone that runs no remote code (no hooks, no submodule recursion).

Residual ceiling (recorded, not hidden). An unknown marketplace still errors — its manifest, and thus any URL, isn't on disk until /plugin marketplace add. Cloning a whole marketplace from its known_marketplaces.json source is a further step, not built here. A ref/HEAD (unpinned) source is cached mutably by name; only a sha is immutable-by-key.

No marketplace-free path to register an in-repo pack — import assumes a marketplace coordinate

Spec upstream

Migrating a downstream repo (example-cash-snapshot) hit a wall: its knowledge/finance-settlement/ pack was authored in-repo, never fetched from a marketplace, and the repo has no marketplace.json — but corpus import is shaped entirely around a <plugin>@<marketplace> coordinate, so there is no first-class way to register/migrate a local pack into the root registry. Regeneration fails: the acquisition model in the spec has no marketplace-free door.

Expected
A repo with an in-repo, never-from-a-marketplace pack has a clean way to register it into the root knowledge/index.md and migrate it to two-layer — without inventing a fake marketplace or a marketplace.json it will never publish.
Actual
corpus import (FR-008) requires a marketplace coordinate; the only way to register a local pack today is the 062 workaround — stage a copy and run corpus import <plugin>@<synthetic-namespace> --from <stage>. Downstream that read as "it took our root-level knowledge as canonical but demanded a marketplace we don't have".
Diagnosis
The same gap 062 papered over for spectastic-concepts (synthetic spectastic namespace + staging hack, and 062 FR-009 recording consumer-only). It resurfaced downstream because the workaround was never generalised into a real requirement/verb.
Fix
Direction chosen (26 Jul 2026): make import marketplace-optional — corpus import <plugin> --from <path> with no @marketplace files the pack under a default project-local namespace (reusing installPack wholesale; no new verb, 8-verb discipline held). import <plugin>@<marketplace> stays the fetch-from-marketplace path. Lands as a /spectastic.propose on 061 (with T-003).
Fixed
corpus import <plugin> --from <path> with no @marketplace resolves through the repo-name default and falls back to the local sentinel, never an empty column; a re-import pins to the existing row so a config change cannot re-key the pack.
Deep dive — cross-spec (062/056) + the design options to discuss

Cross-spec. Touches 062 FR-009 (a consumer root carries no distributable marketplace.json) and 056 (corpus adapt, the raw-conversion primitive that predates the ingester). The question is where a local pack enters the registry.

Options (to weigh). (a) import gains a marketplace-optional / local mode: corpus import <plugin> --from <path> with no @marketplace, filed under a default project-local namespace. (b) A dedicated corpus register-local <path> verb (but the 8-verb discipline resists a new top-level verb — it'd be a corpus subcommand). (c) Route local migration through corpus adapt, reshaped to write the root registry. (d) Keep the coordinate but make the marketplace half optional with a clear default. The friction downstream is the strongest signal this needs a first-class answer, not a per-repo hack.

Ambiguity to confirm. "It took our root-level knowledge as canonical" — needs the exact downstream symptom confirmed (a wrong cwd/registry resolution, vs. simply the missing marketplace door) before the fix is scoped.

installPack drops a source pack's references/superseded/ on import

Spec upstream

corpus import reads only the top-level references/*.md of a source pack; a pre-existing references/superseded/<slug>@<edition>.md is silently skipped, so a pack with retained prior editions loses them on import — and an edition-pinned citation to that prior edition then dangles. Regeneration fails: the import contract never says a source's superseded editions must be carried over.

Expected
Importing a pack that already retains superseded editions preserves them, so an edition-pinned citation to a prior edition still resolves after migration (052 FR-003).
Actual
installPack lists sourceReferencesDir non-recursively and filters .md (ingest.ts:251-254), so the superseded subdir is never read; the dest superseded/ is only written when a re-import supersedes a live edition (FR-005). example-cash-snapshot's references/superseded/001-us-equities-settlement-cycle@2017-09-05.md would be dropped.
Diagnosis
FR-005 covers supersede-on-re-import but no requirement covers preserving a source's already-retained superseded editions on first import — a gap between 061's import and 052 FR-003's "prior edition must remain reachable".
Fix
Agreed (26 Jul 2026): pin a 061 requirement — import MUST preserve a source pack's retained superseded editions — and make installPack copy each source references/superseded/*.md into the dest verbatim (no new registry rows — superseded resolves via the pack scan's matchSuperseded). Folds into the same 061 /spectastic.propose as T-002.
Fixed
preserveSourceSuperseded in packages/corpus/src/knowledge/ingest.ts copies a source pack’s already-retained references/superseded/ editions verbatim (FR-013), so migrating a pack no longer dangles an edition-pinned citation.
Deep dive — cross-spec (052 FR-003)

Cross-spec contract. 052 FR-003 guarantees an edition-pinned citation to a retained prior edition resolves; that guarantee rests on the superseded file existing on disk. 061's import is the migration path onto the two-layer shape, so if it drops superseded editions the 052 guarantee is quietly broken for every migrated pack that had them. The fix is a few lines, but it needs to be a stated requirement (not just a code tweak) so the two specs stop disagreeing.

Note. The superseded filename shape (<slug>@<edition>.md) already matches what loadSuperseded parses, so a verbatim copy is enough — no rename or re-derivation.
