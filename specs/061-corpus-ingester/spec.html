Specification · 061-corpus-ingester

Corpus ingester

Something has to write the registry. One front door, three ways in, one opaque id out — and a re-import that never dangles a citation.

Status Accepted Spec ID 061-corpus-ingester Owner Brian Corbin · @briancorbinxyz Reviewers — Created 26 Jul 2026 Principlesv1.8.0 Smallest demoablecorpus import finance-settlement@spectastic-examples assigns KB-0001, writes the root-registry row, and a KB-0001@edition citation resolves green. Read time

The corpus family (051–059) shipped everything that reads a corpus registry — the resolver, the grounding gates, the render label, the root knowledge/index.md template — but nothing writes one. The registry stays empty, and every KB-NNNN citation dangles, until an ingester exists to assign ids and maintain rows. 051 FR-009 and 052 FR-002 both defer that behaviour here. This spec is the ingester: a corpus-group front door with three ways in — install an existing marketplace skill, interview a subject-matter expert, or source from an allowlisted authority — all converging on one registration backbone that assigns a stable, opaque, repo-unique KB-NNNN, writes the registry row, and, on re-import at a newer edition, supersedes by append while flagging any reference that vanished. The install door is the must; the other two doors are lighter stories whose deeper mechanics have their own follow-on specs.

1 · Context

The two-layer identity model (corpus-identity considerations, D-001–D-005) split a corpus id into a pack-owned slug and a project-assigned, opaque KB-NNNN held in a new root knowledge/index.md registry. The amendments to 051 and 052 landed the registry's shape and taught the resolver to prefer it — deterministically ending the array-order collision two packs sharing KB-001 used to hit. But those amendments were deliberately scoped to reading a registry that something else fills. Nothing fills it. A fresh project's registry is empty, and stays empty; the only tool that writes corpus documents today, 056's corpus adapt, writes the retired per-pack model (a pack-local index.md and pack-minted KB- ids), not a root-registry row.

Acquisition also turns out to have more than one door. The corpus-acquisition considerations observe that a corpus reference can arrive three ways — converted from an existing document or skill, interviewed out of a person, or sourced from an authoritative URL — but every door produces the same artifact: a provenance-stamped document addressable by a stable id. This spec is the front door onto that one contract, and the backbone that turns any arrival into a registered KB-NNNN. The people it serves are the plan authors who cite the corpus and the reviewers who must trust that a citation resolves to real, attributable text.

2 · User scenarios & testing

Each story MUST be independently testable. US1 is the MVP: installing one skill and citing it green proves the whole backbone end-to-end without any other door built.

US1 · Install an existing marketplace skill P1

As a project author, I want to install a published domain skill and have its references registered so that a plan decision can cite them by a stable id the moment the install finishes.

Acceptance: corpus import finance-settlement@spectastic-examples fetches the plugin, converts each reference, assigns a repo-unique KB-NNNN, writes a root-registry row and the pack's SKILL.md slug map, and a <spec-decision> citing KB-0001@edition resolves green.

US2 · Re-import a newer edition without dangling a citation P1

As a project author, I want re-importing an updated skill to keep every id stable and every old citation resolvable so that a document moving on doesn't silently break a decision that grounded against the version it read.

Acceptance: re-running corpus import on a newer edition keeps the same KB-NNNN, bumps the registry edition, moves the prior document under references/superseded/, and a reference dropped from the new release is marked orphaned in its row — never deleted. A genuinely new reference gets a fresh KB-NNNN.

US3 · Capture a subject-matter expert P2

As a team with in-house expertise no document holds, I want to interview an expert into a corpus document so that house knowledge becomes a citable, attributable source instead of tribal memory.

Acceptance: corpus interview runs the interview discipline, persists a document with an interview: <role>, <date> origin, registers it, and marks it not citable until the expert's sign-off is recorded.

US4 · Source from an authoritative URL P3

As a project author needing a public primary source, I want to fetch a document from an allowlisted authority and register it so that a domain fact is grounded against the real text, not the model's memory of it.

Acceptance: corpus source fetches only from an allowlisted origin, drafts a document carrying the fetched URL + retrieval date + content hash, registers it, and marks it not citable until a human confirms the ingestion.

Edge cases

  • A re-import where the marketplace plugin was renamed — the renames map migrates the row; the KB-NNNN never moves (FR-006).
  • A re-import where a reference slug was renamed — the (marketplace, plugin, slug) anchor breaks; the old id is flagged orphaned, never silently re-mapped (FR-007).
  • Two imports racing, or a hand-edited registry id — assignment is the ingester's alone; a duplicate KB-NNNN is a validate finding (FR-003).
  • A conversion that can't read a provenance field — it is written as TODO, never guessed; the content hash is always computed (FR-009).
  • An offline or CI run — the install fetch is a seam a stub satisfies, so registration is testable without a network (NFR-002).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional — the registration backbone

The ingester MUST assign each newly-registered reference a repo-unique, opaque, monotonic KB-NNNN, continuing from the highest id in the root knowledge/index.md registry and never reusing a retired one.

Rationale

The registry is the single source of truth for "next id" (051 FR-009). Monotonic never-reused assignment is what makes an id a stable anchor a citation can trust forever.

The ingester MUST write each registration as a row in the root knowledge/index.md, merging into any existing registry non-destructively — a hand-edited cell (title, edition) MUST survive a re-run.

The ingester MUST be the only writer of the registry's KB-NNNN column, and assignment MUST be deterministic and serialised so no two references ever collide on an id.

Rationale

Stateful "read the max, add one" assignment is a P-8 concern: it belongs in the kernel, serialised, with the registry as the sole authority. A hand-edited collision is caught as a validate finding, not silently minted.

A registration MUST be keyed on the (marketplace, plugin, slug) coordinate, so re-importing the same reference resolves to the same registry row.

Re-importing a reference at a newer edition MUST keep its existing KB-NNNN, bump the row's edition, and retain the prior edition by append (under references/superseded/) so an edition-pinned citation to the older text still resolves (052 FR-003).

The ingester SHOULD migrate a renamed plugin across a re-import via the marketplace renames map, so a plugin rename never orphans its references.

A reference present in a prior import but absent from a re-import MUST be flagged orphaned in its registry row (never deleted), and a validate scan SHOULD surface the orphan as a warning.

Rationale

Silently dropping a row would dangle any citation that still points at it. A visible orphaned marker plus an advisory finding keeps the loss a decision, not an accident — the same secure-by-default, never-silent posture the enforce waivers use.

Functional — the three doors

The import door MUST drive the install of a marketplace skill named as <plugin>@<marketplace>, convert each of its references through the shared conversion primitive, and register them via the backbone above. A --from <path> option MUST register a local checkout instead, for offline and CI use. When the coordinate omits @<marketplace> — an in-repo pack that was never fetched from a marketplace — the door MUST register it under a project-local namespace: the spectastic.json corpus.namespace value when set, else the sentinel local. The namespace so resolved is a label in the (marketplace, plugin, slug) anchor (FR-004), never a marketplace.json or a publication claim (062 FR-009).

To keep that anchor stable (mitigating the identity-fragmentation risk), a marketplace-less re-import MUST resolve to an existing registry row for the same (plugin, slug) whose namespace was locally derived, reusing that row's recorded namespace — so the namespace is pinned at first registration and a later corpus.namespace change never silently mints a second KB-NNNN for the same pack. As a further guard, a validate scan SHOULD warn when a local-namespaced row coexists with a configured corpus.namespace, so any residual fragmentation is surfaced, never silent.

Rationale

An in-repo pack has no marketplace, so forcing a <plugin>@<marketplace> coordinate meant inventing one (the 062 staging + synthetic-namespace hack). A configured-else-local default gives a first-class door without faking distributability — the marketplace column stays a namespace, exactly as the interview and source doors already treat it. Pinning the namespace at first registration keeps FR-004's re-import stability honest even if the configured default drifts later.

Conversion MUST NOT fabricate provenance: a field is populated only from a value genuinely read, everything else is the literal TODO, and the content hash is always computed from the source bytes.

Rationale

The never-fabricate rule 056 established (its FR-002/D-004) is the whole basis of a corpus a reviewer can trust. The ingester reuses it verbatim rather than loosening it at a new front door.

Every door MUST produce the identical registered artifact — a provenance-stamped document plus a registry row — differing only in origin and the status guard that makes it citable. The interview and source doors MUST mark a document not citable until, respectively, an expert sign-off or a human confirmation is recorded.

The source door SHOULD fetch only from an origin on a curated per-domain authority allowlist, and MUST NOT register a document fetched from an origin absent from it.

All doors SHOULD be subcommands under the existing corpus command group, adding no new top-level lifecycle verb, so the eight-verb slash surface is unchanged.

Importing a pack whose source already carries retained superseded editions under references/superseded/<slug>@<edition>.md MUST preserve them — copying each into the installed pack verbatim — so an edition-pinned citation to a prior edition still resolves after import (052 FR-003).

Rationale

FR-005 retains a prior edition created during a re-import; nothing covered a source that already retained superseded editions at first import. installPack reads only top-level references/*.md, silently dropping the superseded/ subdir — so migrating a pack with prior editions dangled every edition-pinned citation to them. Superseded editions resolve through the pack scan, so preserving the files is enough; no registry row is added.

Non-functional

The backbone (id assignment, registry merge, supersede-by-append) MUST be deterministic — the same inputs produce byte-identical registry output — and MUST read no wall-clock except where a door records a genuine retrieval or interview date.

The install fetch MUST sit behind an injectable seam so a stub satisfies it in tests and CI — registration MUST NOT require a live network to be exercised.

The ingester SHOULD be idempotent and non-destructive — a re-run that changes nothing writes nothing, and never rewrites a hand-corrected field back to TODO (056 NFR-001, extended to the registry).

Out of scope (deferred to other slices)

  • Migrating the two shipped packs and the live citations onto the two-layer shape, and flipping the resolver to registry-only (retiring the pack-scan fallback).
  • The resolve-must-succeed gate that turns "never cite from memory" into a build finding; the staleness gate already lives in 053.
  • The full shape and governance of the authority allowlist FR-011 fetches against — this spec assumes it, a sibling owns it.
  • How a retrieval index interacts with the registry — the registry is the record; an index is a rebuildable layer above it.
  • Redistribution terms of material a re-imported skill bundles.

4 · Data model

The ingester owns no new persistent entity — it writes entities 051 and 052 already defined. It substantially changes how two of them are produced, and adds one column.

Entities

Registry row
One line in root knowledge/index.md (051 FR-009): KB-NNNN | marketplace | plugin | slug | title | edition | path, gaining a status column (blank when current, orphaned when a re-import dropped the reference — FR-007).
Provenance
The frontmatter each conversion stamps (056): origin, origin-url, edition, license, converter, content-hash, status. The door decides origin and the status guard; the never-fabricate rule (FR-009) decides the rest.
Superseded edition
A prior document retained under references/superseded/<slug>@<edition>.md on re-import (052 FR-003), so an edition-pinned citation to the older text always resolves.

Invariant: a KB-NNNN, once assigned to a (marketplace, plugin, slug) coordinate, is never reused and never moves — not on a plugin rename (the row migrates), not on an edition bump (the row updates), not on an orphan (the row is flagged, not freed). This is the persistent-identifier discipline the whole two-layer model rests on.

5 · Success criteria

Technology-agnostic, measurable outcomes.

Importing a two-layer skill into a project with an empty registry produces a root knowledge/index.md with one repo-unique KB-NNNN row per reference, and a <spec-decision> citing one of them at its edition resolves green through the grounding gate.

Re-importing the same skill at a newer edition leaves every KB-NNNN unchanged, retains each prior edition on disk, and a citation pinned to a prior edition still resolves — no dangling reference is produced.

A reference dropped between two imports appears with status=orphaned in the registry and raises exactly one advisory validate finding — and is never removed from the file.

The full import → convert → register flow runs to a written registry in CI with no network access, driven entirely through the stubbed fetch seam.

6 · Assumptions

The ingester operates on the two-layer pack shape — a SKILL.md slug map and slug-named references with no pack-minted KB- id. The two in-repo packs are still on the legacy 056 shape, so this spec's tests use two-layer fixtures; dogfooding against the real packs waits on TBD-corpus-identity-migration. This ordering is deliberate, not an oversight.

A Claude Code marketplace supplies the (name, version) coordinate and a renames map; the registry is a consumer-side artifact layered on top of that coordinate, not a field inside marketplace.json (there is no per-reference slot in the platform schema).

The conversion primitive from 056 (deriveProvenance, the content hash, the title/description derivation) is reusable as-is; only its output shape changes — a SKILL.md slug map plus a registry row, in place of the retired per-pack index.md and pack-minted ids.

7 · Open questions

None outstanding — the scope (full front-end over one backbone), the smallest demoable (install one pack), the orphan representation (a registry status column plus a warning scan), the import coordinate (plugin@marketplace with a --from escape hatch), the adapter relationship (coexists, reshaped), and the single idempotent import were all anchored in the interview.
