Local-pack import + preserve superseded editions

Applied

1 · Intent

061's import door was built around a marketplace: a <plugin>@<marketplace> coordinate, fetched from an added marketplace or (now) cloned from a remote source. But a project's own in-repo pack — authored in the repo, never fetched, and correctly carrying no distributable marketplace.json (062 FR-009) — has no natural marketplace. 062 papered over this for spectastic-concepts by staging a copy and inventing a spectastic namespace; the workaround resurfaced as a wall when the same migration was attempted downstream, where the author reasonably expected to register their own pack without faking a marketplace.

The migration also exposed a data-loss bug: import reads only the top-level references/*.md of a source pack, so a pack that already retains prior editions under references/superseded/ loses them on import — and an edition-pinned citation to that prior edition then dangles. example-cash-snapshot's finance-settlement pack retains a T+2 edition exactly this way. Both are import gaps; this change closes both.

2 · Scope

In scope

  • A marketplace-optional local mode of import: corpus import <plugin> --from <path> with no @marketplace, filed under a project-configured namespace (else the sentinel local).
  • Preserving a source pack's already-retained references/superseded/ editions on import.
  • Simplifying the downstream migration path (drop the staging + synthetic-namespace hack).

Out of scope

  • The still-ambiguous downstream symptom "it took our root-level knowledge as canonical" — captured on T-002 pending the exact repro; if it is a distinct cwd/registry-resolution bug it gets its own triage, not this proposal.
  • Publishing a consumer's corpus as a distributable marketplace — stays TBD-corpus-publish (062 FR-009).
  • Auto-migrating existing registry rows when a project later changes its configured namespace — a namespace change re-keys the (marketplace, plugin, slug) anchor and is the author's explicit action, not a silent migration.

3 · Approach

Both changes live in the existing backbone; neither adds a verb or a subsystem. parseCoordinate already returns an empty marketplace when the coordinate omits @; the local mode fills that empty namespace from spectastic.json's corpus.namespace, or the sentinel local when unset, so the registry's required marketplace column is never blank and the (marketplace, plugin, slug) anchor (FR-004) still holds. The default is resolved at import time; a project that may later publish should set corpus.namespace up front rather than lean on the fallback (see risks). For superseded, installPack gains a verbatim copy of each source references/superseded/*.md into the installed pack — no new registry rows, since a superseded edition resolves through the pack scan's matchSuperseded, and the <slug>@<edition>.md filename already matches what loadSuperseded parses.

4 · Deltas

One <spec-delta> per requirement touched.

What changes: add a marketplace-optional local mode — a --from import whose coordinate omits @marketplace registers an in-repo pack under a project-configured namespace (else local).

The import door MUST drive the install of a marketplace skill named as <plugin>@<marketplace>, convert each of its references through the shared conversion primitive, and register them via the backbone above. A --from <path> option MUST register a local checkout instead, for offline and CI use. When the coordinate omits @<marketplace> — an in-repo pack that was never fetched from a marketplace — the door MUST register it under a project-local namespace: the spectastic.json corpus.namespace value when set, else the sentinel local. The namespace so resolved is a label in the (marketplace, plugin, slug) anchor (FR-004), never a marketplace.json or a publication claim (062 FR-009).

To keep that anchor stable (mitigating the identity-fragmentation risk), a marketplace-less re-import MUST resolve to an existing registry row for the same (plugin, slug) whose namespace was locally derived, reusing that row's recorded namespace — so the namespace is pinned at first registration and a later corpus.namespace change never silently mints a second KB-NNNN for the same pack. As a further guard, a validate scan SHOULD warn when a local-namespaced row coexists with a configured corpus.namespace, so any residual fragmentation is surfaced, never silent.

Rationale

An in-repo pack has no marketplace, so forcing a <plugin>@<marketplace> coordinate meant inventing one (the 062 staging + synthetic-namespace hack). A configured-else-local default gives a first-class door without faking distributability — the marketplace column stays a namespace, exactly as the interview and source doors already treat it. Pinning the namespace at first registration keeps FR-004's re-import stability honest even if the configured default drifts later.

Importing a pack whose source already carries retained superseded editions under references/superseded/<slug>@<edition>.md MUST preserve them — copying each into the installed pack verbatim — so an edition-pinned citation to a prior edition still resolves after import (052 FR-003).

Rationale

FR-005 retains a prior edition created during a re-import; nothing covered a source that already retained superseded editions at first import. installPack reads only top-level references/*.md, silently dropping the superseded/ subdir — so migrating a pack with prior editions dangled every edition-pinned citation to them. Superseded editions resolve through the pack scan, so preserving the files is enough; no registry row is added.

5 · Risk register

Adversarial pass ran (touches must-tier FR-008 + adds a must FR). Three findings + one corpus check, all dispositioned by the author: two mitigated (folded into FR-008 + §6), one accepted. No finding remains open, so the apply risk-gate is clear.

The local fallback fragments identity: a project that imports a pack under local today and later sets corpus.namespace (or publishes the pack under a real marketplace) will re-key the (marketplace, plugin, slug) anchor, so the same pack registers a second time under a fresh KB-NNNN instead of resolving to the existing row — the most likely 30-day regret.

MODIFY FR-008: "the spectastic.json corpus.namespace value when set, else the sentinel local".

Mitigated. FR-008 now carries a validate warning when a local-namespaced row coexists with a configured corpus.namespace, so fragmentation is never silent (§6 task on validate.ts). Paired with the Risk-2 namespace-pin, the common path never fragments and the residual case is surfaced loudly.

The requirement this most likely contradicts is FR-004 ("registration MUST be keyed on (marketplace, plugin, slug) so re-importing resolves to the same row"): a marketplace-derived-by-default coordinate makes the anchor's first component depend on config state at import time, so FR-004's re-import stability holds only while the namespace resolution is itself stable.

FR-004 vs. the MODIFY FR-008 default-namespace clause.

Mitigated. FR-008 now pins the namespace to the row permanently: a marketplace-less re-import resolves to an existing (plugin, slug) row whose namespace was locally derived and reuses that recorded namespace, so config drift can never silently re-key it (§6 task on ingest.ts). FR-004's anchor is preserved; the local mode just resolves the namespace stably rather than re-deriving it each run.

Scope may be too narrow: the proposal explicitly defers the "took our root-level knowledge as canonical" symptom, so if that phrase describes a real second bug (not just the missing marketplace-free door), this change ships without fixing what the user actually hit.

§2 Out of scope: "the still-ambiguous downstream symptom … pending the exact repro".

Accepted (narrow scope). The two grounded gaps (T-002 door, T-003 superseded) are what reproduced against real files and are worth shipping now. The ambiguous phrase stays flagged on T-002; if it proves a distinct bug it earns its own triage rather than inflating this proposal.

No domain-fact contradiction: the repo's knowledge/ corpus (spectastic-concepts KB-0001 — SDD / RFC 2119 / grounding; finance-settlement KB-0002 — settlement windows) commits facts orthogonal to the ingester's import mechanics, so neither delta contradicts a committed domain fact.
