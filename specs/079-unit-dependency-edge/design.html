Unit dependency edge

A pure edge algebra with the filesystem held at arm's length, so the rules that decide what an edge is worth can be tested without a single fixture directory.

Frameworks
None. One new runtime dependency, yaml, into @spectastic/core (D-003).
Architecture
Ports-and-adapters over a pure resolution core — filesystem behind a narrow port, one inference adapter per ecosystem (D-001).
Storage
None. Reads spectastic.json and manifests; writes nothing (NFR-002).
Testing
TDD, tests red before implementation (D-005). Unit tests for the algebra, fixture projects for the adapters.
Coverage
90% of changed lines, and a change never lowers coverage of the code it touches. Diff-aware, never a project-wide percentage.
Perf targets
Under 500 ms for at most 200 units; at most 0 network calls (NFR-001).
Constraints
Deterministic — no clock, no iteration-order dependence. Malformed input degrades to a finding, never an exception (NFR-003).

Toolchain / enforcement

The project is on the enterprise profile with a hard gate. spectastic enforce, run while authoring this design, reports 8 covered · 1 relaxed · 0 missing — formatter, linter, type-checker, test-runner, security, supply-chain, coverage and contract-first are all satisfied by the existing toolchain, and observability carries a live waiver. There is no gap for this slice to close, so no new gate is designed. The one obligation the floor does place on this work is the coverage row above: the patch target is stated diff-aware, per the profile's requirement that a threshold be declared rather than assumed.

3 · Data model & contracts

This slice exposes no interface across a process or repository boundary. It is a library read path plus a CLI verb, both in-process; the coordinates it emits are identifiers, not an endpoint.

No request/response, RPC, GraphQL or event-driven surface. The unit coordinate kind is a naming grammar rather than an interface: nothing serves it, and adding it obliges no producer to publish anything.

The physical shape of a declared edge is the existing consumes array in spectastic.json — a list of coordinate strings, widened by FR-009 to carry unit coordinates alongside the contract coordinates it already holds. No new file, no new configuration section.

5 · Approach

The rules worth protecting are not the reading. What must be right is the small algebra that decides what an edge is: that a declaration outranks an inference for the same pair, that the same relation asserted twice is one edge, that a far end which agrees marks the edge reciprocated while one that cannot be read marks it unverified, and that these two marks are independent so an unverified edge can never be reciprocated. That algebra is pure. It takes two lists of candidate edges and a lookup of what each far end says, and returns a resolved set.

Everything else is acquisition, and acquisition is where the variety lives: a JSON manifest here, a YAML workspace file there, a config key, a far end that may or may not exist on disk. Holding that behind a narrow port keeps the variety out of the rules — and, more practically, means the state matrix in the paragraph above is testable with plain objects rather than a directory of fixture repositories per case.

The far-end lookup deserves a note, because it is the one place the port is doing something subtle. To mark an edge reciprocated, resolution must know what the far end declares — which means reading another project's spectastic.json. That read can fail for entirely ordinary reasons, and the failure is the signal: not readable is what makes an edge unverified. So the port returns a three-valued answer per far end (agrees · does not agree · unreadable) rather than a boolean, and resolution maps those onto the two marks.

A is what enforce/detect.ts does today and it is genuinely simpler, but filesystem access threads through the middle, so the edge-mark matrix could only be exercised against real directories — the highest-value logic tested in the most awkward way. C keeps ecosystems fully independent at the cost of reimplementing the reciprocity and verification rules per slice, which is exactly the logic that must not drift between them.

7 · Decisions

D-001 · Ports-and-adapters over a pure resolution core

Status
Accepted
Context
The edge-mark rules form a small state matrix that must be exactly right, while acquisition spans a JSON manifest, a YAML workspace file, a config key and a possibly-absent far end. Existing detection (enforce/detect.ts, signalMatches) interleaves the two, which is why its logic is only testable against fixture directories. The estate already uses a port for exactly this separation in the corpus IO layer.
Decision
A pure resolve taking candidate edges plus a far-end lookup and returning the resolved set, with all filesystem access behind a narrow workspace port and one inference adapter per ecosystem. The far-end lookup is three-valued (agrees · does not · unreadable), not boolean.
Consequences
+ The rules that decide an edge's worth are unit-testable with plain objects, no fixture directories. + A second ecosystem is an adapter, not a change to the rules. + Matches an existing estate precedent rather than inventing a shape. − One more indirection than the layered form, in a codebase whose sibling detector is layered. − The port's three-valued return is a contract that must be got right early, since both marks depend on it.

D-002 · A unit is named by its package name, verbatim

Status
Accepted
Context
Inference matches dependency entries against workspace members, and the string a manifest uses is the package name. A directory path would be more human-legible but needs a name-to-directory lookup on every inferred edge, and a package referenced but absent from the workspace has no directory at all. The spike (§4) confirmed a scoped name survives: @spectastic/core composes, parses back intact, and URL.href round-trips byte-identically.
Decision
The coordinate name is the package name exactly as the ecosystem writes it, including the scope separator, which the grammar already tolerates as multi-segment (the corpus kind uses plugin/slug). No escaping, no translation table.
Consequences
+ Inference matches by string equality against what manifests actually contain, so no lookup can be wrong. + A referenced-but-absent package is still nameable. + Coordinates read as the name the ecosystem uses. − A package rename re-keys its coordinate, the same exposure 076 FR-007 records for contracts. − A unit name is not a filesystem path, so a reader wanting the directory must resolve it.

D-003 · Take yaml as a core dependency so pnpm workspaces are readable

Status
Accepted
Context
Core has no YAML parser. This repository declares its workspace only in pnpm-workspace.yaml — the root package.json has no workspaces field — so JSON-only inference resolves zero units here. A feature blind to its own repository can only ever be tested against synthetic fixtures, and its dogfooding claim would be hollow. yaml@^2.9.0 is already a dependency of @spectastic/corpus in this workspace.
Decision
Add yaml to @spectastic/core at the version already vendored here, and read pnpm workspace membership properly rather than by hand.
Consequences
+ Inference works on this repository from the first commit, so every claim about it is checkable here. + Adopts a version already audited and shipped in this workspace rather than widening the supply-chain surface. − One more runtime dependency in the kernel, which the package has so far kept small. − Hand-reading the few lines pnpm actually uses would have avoided it, at the cost of a parser that mis-reads a valid file later; rejected for that reason.

D-004 · The unit kind lives in schema; resolution lives in core

Status
Accepted
Context
ResourceKind and the parse-time KNOWN_KINDS set both sit in @spectastic/schema, and every other kind was added there. P-14 puts deterministic reusable logic in the library core with the CLI as a thin caller.
Decision
Widen the union and the parse set in schema — both, since composing a kind that will not parse is the failure mode the grounding row names. Edge resolution, the port and the adapters go in core under a new module; the CLI registers a verb and prints.
Consequences
+ One place owns the grammar, so no second kind list can drift from it. + Later slices import resolution without the CLI attached. − Touching schema means rebuilding it before the CLI sees the change, the rebuild trap this estate has hit before.

D-005 · Tests red before implementation

Status
Accepted
Context
The edge marks are a state matrix — verified × reciprocated × declared-versus-inferred — and an assertion written after the fact tends to encode what the code does rather than what the requirement says. A judgment call about method, with no external fact to verify.
Decision
Each requirement's test is written and seen failing before its implementation. Unit tests cover the pure algebra; fixture projects cover the adapters, including this repository itself as the pnpm case.
Consequences
+ The matrix is specified by tests rather than discovered. + A fixture that fails for the wrong reason is caught while the expectation is still fresh. − Slower per cycle than writing the reader first and asserting afterwards.

9 · Risks & mitigations

RiskLikelihoodImpactMitigation
Widening the union without widening KNOWN_KINDS ships a kind that composes but never parses MediumHigh Named explicitly in D-004 and in the grounding table; the first test written is a compose-then-parse round-trip for the new kind.
Inference reads a far end's config and mistakes an unrelated consumes entry for agreement MediumMedium Reciprocity requires the far end to name this unit's coordinate specifically, not merely to have entries. Asserted as its own case in the algebra tests.
A monorepo yields a large unit count and blows the 500 ms budget LowMedium Enumeration is bounded by declared workspace globs, never a tree walk. Measured against NFR-001 on this repository as a build task, the way 073's budget was.
Adding yaml to core is resisted in review as kernel bloat LowLow D-003 records the dogfooding argument and that the version is already vendored here; the alternative and why it was rejected are on the record.
Reciprocity reads another project's configuration. That read is ordinary — a local file in a checkout the user already has — but it is the first time this estate reads config belonging to a different project. It must stay read-only, must never follow a path outside the checkout it was given, and must treat every failure as "unreadable" rather than propagating it. NFR-002 and NFR-003 already require this; it is called out because the code is where a shortcut would be tempting.
