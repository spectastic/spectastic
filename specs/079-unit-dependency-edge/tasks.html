Unit dependency edge

Ordered, parallelizable work. Tests precede implementation. Drive through with /spectastic.implement — one task per invocation.

Status Accepted Spec 079-unit-dependency-edge Design design Branch main Created 02 Aug 2026 Read time

29 tasks across five phases. Setup → Foundational → User stories (US1·US2·US3) → Polish. Tasks marked [P] can run in parallel — different files, no dependency. Tests for a story MUST be written and failing before its implementation tasks start (D-005).

1 · Execution strategy

The fit here. Setup → Foundational → US1 → US2 → US3 → Polish, each story closing its conformance before the next opens. US2's marks depend on US1's resolution existing, and US3's inference feeds the same algebra, so the stories genuinely stack rather than merely being ordered.

US1 alone is a shippable read path: declared edges resolve and print. Viable if the marks can wait — though US2 is what makes the output trustworthy, so shipping without it invites a reader to over-trust an unverified edge.

Not a fit for one author. The port contract (D-001) is the only clean seam, and it is small enough that coordinating across it would cost more than doing both sides.

8 · Dependencies

  • T-011 blocks everything downstream — no coordinate names a unit until the kind parses.
  • T-013 blocks T-210 and T-310 — both adapters implement the port, so its shape settles first.
  • T-111 blocks T-211 and T-312 — the marks and the merge extend the algebra rather than replacing it.
  • T-901 must not run in the same file-writing window as any other task — it asserts an absence, so a concurrent write elsewhere would fail it spuriously. Sequential for that reason, independently of the file-sharing rule below.
  • A task is [P] only where no sibling in its phase touches the same file. Most test tasks here land in one spec file, so they are sequential even though their assertions are independent — concurrency is bounded by the file, not by the logic.
