Specification · 079-unit-dependency-edge

Unit dependency edge

The estate can name every artifact and nothing that connects them. This is the edge — one relation, addressable at both ends, honest about what it has actually checked.

Status Draft Spec ID 079-unit-dependency-edge Owner Brian Corbin · @briancorbinxyz Reviewers — Created 02 Aug 2026 Principlesv1.9.0 Smallest demoableA project declares edges; a read-only command prints them resolved, each showing direction, whether it was verified, and whether the far end agrees. Read time

Specs 067 and 078 gave every artifact a federation-unique name. Nothing gives any two of them a relationship, so no tool can answer which side of a dependency does this change belong on — the question behind both failures the placement survey opens with. This adds the missing relation: a depends-on edge between units — a module inside a repository, or a whole project, both on one coordinate grammar. The consumer declares its own dependencies, since only the consumer knows it consumes; where the far end independently agrees, the edge is marked reciprocated. An edge whose far end cannot be read is still an edge, marked unverified: an estate where most providers are not checked out must still produce a graph. And because declaration alone yields an empty one in practice, edges are also inferred from manifests and workspace configuration — always, as a fallback that cannot be switched off.

1 · Context

Every relation the estate holds today is either containment (a marketplace holds a plugin holds a document) or precedence (spec 028's DAG: build this before that). Neither answers the question a change needs answered. A fix reported against a consuming application may belong in the library beneath it; a change inside one service may belong in its domain, one of its services, or none of them. Both are the same question — which side of a dependency does this belong on — and the estate cannot express the dependency, let alone the side.

One relation exists in embryo. Spec 076 added a consumes list of coordinates so a contract-change notification can be routed rather than broadcast. It is contract-scoped, has no authoring surface, and this project's own configuration carries no entry — but it is the right shape, and generalising it is cheaper than inventing a second list beside it.

Two users: a maintainer stating what their project is built on, and a tool reading those relations uniformly whether or not they cross a repository boundary.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Declare what this project is built on P1

As a maintainer, I want to declare the units my project depends on so that the relationship is recorded where a reviewer and a tool can both see it.

Acceptance: given a project declaring one intra-repo and one cross-repo dependency, a read-only command prints both, each with its resolved coordinate and its verification mark. A malformed entry is reported and skipped rather than failing the read.

US2 · Tell a checked relationship from a claimed one P1

As a reviewer, I want to see which declarations were actually verified against the far end so that I can weigh a confirmed relationship differently from an assertion.

Acceptance: an edge whose target resolves and independently declares the counterpart prints as reciprocated; one whose target resolves but does not is plain; one whose target cannot be read at all prints as unverified. All three are edges.

US3 · Get a graph from a project that declared nothing P2

As a tool, I want edges inferred from what the ecosystem already declares so that a project that has authored no edges still produces a usable relation set.

Acceptance: a workspace whose manifests express an internal dependency yields that edge with no authored configuration. Where a declaration and an inference disagree, the declaration is the one reported.

Edge cases

  • A declared edge naming a unit that does not exist anywhere — reported as dangling rather than silently dropped, mirroring 028's handling.
  • A self-edge, or two units declaring each other. Cycles are not this spec's concern; it does not compose a graph.
  • A monorepo where an inferred intra-repo edge duplicates a declared one — the same edge, not two.
  • A declared coordinate that is well-formed but names a project this checkout has never heard of. Legal: parsing never dereferences.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A unit MUST be addressable by the existing coordinate grammar, extended with a unit resource kind, so a module inside a repository and a whole project are named the same way and an edge is always coordinate-to-coordinate.

Rationale

A path for modules and a coordinate for projects leaves a module unreferenceable from outside its repository, so promoting one to its own repository breaks every edge naming it. One scheme costs a grammar addition once and survives that migration.

The relation MUST be a single directed depends-on edge in this slice. Additional relation kinds MAY be added later.

Rationale

Both motivating failures reduce to "which side of a dependency does this belong on", which one relation answers. A vocabulary is additive to widen and expensive to correct, so shipping one well-understood kind beats guessing at three.

The depending unit MUST be the one that declares an edge. A unit MUST NOT be able to place itself on the far end of another unit's edge by its own declaration alone.

Rationale

Only the consumer knows it consumes, and it matches the shape consumes already has. The prohibition is 028's insight restated: one side asserting a relationship is a claim, and a project must not be conscriptable into a relationship it never agreed to.

Where the far end independently declares the counterpart relationship, the edge MUST be marked reciprocated. A one-sided edge MUST remain a real edge.

Rationale

028 admits an edge only on reciprocity, which works because both specs sit in one corpus. Across repositories that would yield almost no edges, since it needs every counterpart present and cooperating. Marking rather than gating keeps the stronger signal available to anything that wants to weight it, without making the common case empty.

An edge whose far end cannot be read — absent, not checked out, inaccessible — MUST be reported as an edge marked unverified, and MUST NOT be indistinguishable from one whose far end was read.

Rationale

Most consumers do not have their providers checked out, so refusing unverifiable edges makes the model useless in the ordinary case. Equating them instead would conflate "I checked" with "someone claimed" — the distinction the estate's grounding vocabulary exists to preserve.

Edges MUST also be inferred from the ecosystem's own dependency declarations — manifests and workspace configuration — and inference MUST NOT be disableable.

Rationale

A declaration-only model produces an empty graph: this repository's own record is ten contract declarations that all decline to declare an interface, and no consumes entry at all. Inference is what makes the relation useful on day one; making it optional would recreate the emptiness it exists to prevent.

Where a declared edge and an inferred edge describe the same relation, the declared one MUST be the one reported; where they disagree, the declaration MUST take precedence.

Rationale

Spec 073 settled this precedence at must-tier for interface detection on reasoning that transfers exactly: inference sees that a relation exists but not what it means, and only a declaration carries intent. Reversing it would make a stated relationship unable to correct a wrong guess.

A declared edge naming a unit found nowhere MUST be reported as dangling rather than silently discarded.

The existing consumes key SHOULD carry the generalised edge, with a contract coordinate remaining a legal target, rather than a second overlapping list being introduced.

Rationale

Two lists a project must keep in sync is a maintenance trap and leaves an author guessing which to use. Widening in place keeps every existing entry valid; the amendment to 076 records it.

A read-only command SHOULD print the resolved edge set, each edge showing its direction, its verification mark, and whether it is reciprocated.

Non-functional

Resolving a project's edges MUST make at most 0 network calls, and MUST complete in under 500 ms on a project of at most 200 units.

Rationale

Matches the detection budget the enforcement path already holds itself to, so edge resolution can sit alongside it without widening the cost of a routine run. Reading a far end means reading a local checkout, never a fetch.

Reading edges MUST be free of side effects and MUST write at most 0 files.

A malformed or unreadable declaration SHOULD degrade to a reported finding rather than an exception: at most 0 read failures may abort resolution of the remaining edges.

Out of scope (deferred to other slices)

  • The authoring surface — a command that writes an edge, the design decision-phase question that prompts for one, and a validate rule that a declared coordinate is well-formed.
  • Reading a project's declared boundary map (tag rules, layer lists) as a source of intra-repo structure.
  • Ranking, evidence weighting, confidence and any verdict. This spec produces relations, never conclusions.
  • Composing edges into a traversable graph with cycle detection and transitive reach — deferred until a consumer needs it, since 028 shows what it costs to build and this slice has no traversal requirement.
  • Relation kinds beyond depends-on, including the context-mapping vocabulary (Customer/Supplier, Conformist, anti-corruption layer) the survey found.

4 · Data model

Two entities, and the marks that qualify one of them.

Entities

Unit
A thing that can depend on another thing: a module or package inside a repository, or a whole project. Every unit has exactly one coordinate, and that coordinate is unique across the estate. A unit's identity does not change when it moves between repositories — only which coordinate segment carries it does.
Edge
A directed depends-on relation from a depending unit to a depended-on unit. An edge is declared by its depending end, or inferred. The pair (depending, depended-on) identifies the edge: the same relation asserted twice, or asserted once and inferred once, is one edge and not two.

An edge carries two independent marks and they answer different questions. Verified says the far end was read at all. Reciprocated says the far end, having been read, agrees. So an unverified edge can never be reciprocated, while a verified one may or may not be — and the three resulting states are exactly what a reader needs to weigh a relationship. Neither mark is authored; both are established at read time and must never be settable by a declaration.

5 · Success criteria

Technology-agnostic, measurable outcomes.

A project declaring both an intra-repo and a cross-repo dependency resolves both, and a reader can tell from the output which were verified and which were reciprocated — for at most 0 edges is the verification state unstated.

A workspace that has authored no edges at all still resolves the internal dependencies its own manifests express: at most 0 authored entries are required to produce a non-empty relation set.

A unit that declares nothing is named on at most 0 edges as a depending end by any other unit's declaration, demonstrating that no project can be conscripted into a relationship.

Across a fixture estate containing a declaration that contradicts an inference, the declared relation is the one reported in at most 0 fewer than all such cases.

6 · Assumptions

A far end is "readable" when its checkout is present on the local filesystem. No fetch, discovery or registry lookup is assumed, and none is permitted by NFR-001.

The ecosystems whose manifests inference reads are the ones detection already covers. Widening that set is a detection concern, not this spec's.

A module's coordinate segment can be derived from its position in the workspace without an authored name. Where a project's layout makes that ambiguous, the author can declare the unit explicitly — the same escape hatch declaration provides everywhere else.
