Enterprise enforce floor (dogfood)

Make spectastic pass the enterprise floor it demands of everyone else — the three absent quality gates, self-certification, the detector gaps dogfooding surfaces, and a principles reconciliation.

Read time

spectastic defines what enterprise means — its own enterprise profile is a hard-gate floor of nine enforce categories plus a fifteen-principle catalog — but it doesn't dogfood that floor on itself: there is no profile marker, and three required categories are genuinely absent (no formatter, no CI-enforced linter, no coverage). Two more (security, supply-chain) are covered in substance but invisible to the detector — the repo runs a bespoke security red-team and uses Dependabot, but the detector looks for Semgrep and Renovate. This spec closes that self/downstream gap: it adds the three missing gates (blocking, green from day one), adds real SAST, teaches the detector to recognise Dependabot (a fix every downstream Dependabot user benefits from), waives the categories that don't apply to a CLI (observability), self-certifies via a .spectastic/profile.json = enterprise marker, and reconciles the hand-authored principles against the enterprise catalog. Coverage is diff-aware, never a project percentage. For the spectastic maintainers — and, through the detector fix, every downstream enterprise project.

1 · Context

spectastic ships an enterprise profile whose enforce floor is a hard gate over nine categories — formatter, linter, type-checker, test-runner, security, supply-chain, coverage, observability, contract-first (security and supply-chain unwaivable) — and a fifteen-principle catalog. It is the standard the tool holds downstream projects to. The tool does not hold itself to it: there is no .spectastic/profile.json marker, so spectastic enforce has never certified the repo against its own bar.

Mapping the repo against that floor: type-checker (tsc) and test-runner (Vitest) are covered; contract-first is auto-exempt (no web/RPC interface). But formatter, linter, and coverage are genuinely absent — there is no Prettier/Biome config, no CI-enforced linter (the SonarLint-style diagnostics are an editor plugin, not a build gate), and no coverage measurement at all. And security and supply-chain are covered in substance but invisible to the detector: the repo runs a bespoke injection red-team as a hard CI gate and uses Dependabot, yet the detector's signals are Semgrep (.semgrep.yml) and Renovate (renovate.json). The Dependabot blind spot is a real defect — every downstream project on Dependabot hits the same false gap.

Who it's for: the spectastic maintainers (a tool that enforces a floor it doesn't meet is a credibility hole) and, via the detector fix, every downstream enterprise project using Dependabot.

2 · User scenarios & testing

Each story MUST be independently testable: US1 alone (the three quality gates) is a viable MVP — real robustness even before the repo self-certifies.

US1 · The three absent quality gates land, blocking, green from day one P1

As a spectastic maintainer, I want a formatter, a linter, and coverage enforced in CI so that a formatting drift, a lint error, or a coverage drop on changed lines fails the build — not just an editor squiggle.

Acceptance: a formatter and a linter run over all repo source (all five packages + bench/scripts) and coverage over the four core packages (schema/corpus/core/cli); each is a blocking CI gate; the existing codebase is brought to green (the surfaced backlog fixed, not suppressed); coverage is diff-aware — ≥ 80% of changed lines, and a change never lowers coverage of the code it touches — never a universal project percentage.

US2 · The repo self-certifies against its own enterprise profile P1

As a spectastic maintainer, I want the repo marked enterprise and spectastic enforce to pass so that the tool provably meets the floor it demands of everyone else.

Acceptance: a .spectastic/profile.json = enterprise marker exists; spectastic enforce reports the repo passes — every required category covered, waived, or exempt, with zero blocking gaps; the categories that don't apply to a CLI/library (observability — no runtime service, no metrics surface) are handled by a well-formed, justified, expiring waiver, never a silent pass; and activating the marker leaves the existing spec corpus's profile-gated validate (the quantified-NFR gate, 047) green.

US3 · Dogfooding hardens the detector for everyone P2

As a downstream project on Dependabot, I want the enforce detector to recognise Dependabot as supply-chain tooling so that I'm not falsely failed for using a first-class dependency-update tool.

Acceptance: the detector recognises .github/dependabot.yml as a supply-chain signal; a real SAST config (Semgrep) is added and recognised as a security signal (additive to the bespoke injection red-team, not a replacement); both changes are additive — a project already passing a category stays passing. A dependency-vulnerability audit gate runs in CI.

US4 · Principles reconciled with the enterprise catalog P2

As a spectastic maintainer, I want the hand-authored principles audited against the fifteen-principle enterprise catalog so that the constitution reflects the enterprise standard where it genuinely applies.

Acceptance: every enterprise-catalog principle is either already present in principles.html, folded in as a genuinely-missing and scope-applicable rule (e.g. formal accessibility conformance — the repo already generates user-facing HTML and runs axe-core), or recorded as not-applicable with reasoning (e.g. SLOs for a CLI) — never blanket-seeded as noise. The amendments land via /spectastic.principles (the constitution's own verb).

Edge cases

  • Adopting a formatter reformats the whole tree once — a large one-time diff, acceptable and expected; subsequent diffs stay clean.
  • The linter surfaces a backlog (unused imports, cognitive-complexity). US1 fixes it; if a rule proves too noisy to satisfy honestly, it is tuned down with a recorded reason, never blanket-disabled.
  • Marking the repo enterprise activates all profile-gated validate rules across the whole specs/ corpus, not just enforce — the quantified-NFR gate (047) most of all. The plan spike confirmed 104 historical NFRs would fire; FR-009's convention floor exempts them (they predate the discipline) while still gating new specs — never a silent corpus reddening, and never a retroactive marathon.
  • The vscode extension's host-dependent (VS Code) tests can't contribute to a Node coverage number — it is formatter/linter-covered but out of the coverage gate, recorded explicitly, not silently.
  • A detector change that recognised the wrong thing could relax a downstream gate — so the change is strictly additive (new signals only) and covered by a fixture proving a previously-passing project still passes.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A formatter and a linter MUST be configured over all repo source (all five packages plus bench/scripts) and run as blocking CI gates; their config MUST be the file the enforce detector recognises for the formatter and linter categories.

Rationale

The largest robustness hole — zero formatter, no CI-enforced linter today. The detector-recognised config is what makes enforce see the category as covered (US2).

The existing codebase MUST be brought to a green lint + format state (the surfaced backlog fixed, not baseline-suppressed) so the gates block genuinely from the first commit. A rule tuned down to stay honest MUST carry a recorded reason.

Coverage MUST be measured over the four core packages (schema/corpus/core/cli) with a declared threshold the detector recognises, and gated diff-aware: ≥ 80% of changed lines covered, and a change MUST NOT lower coverage of the code it touches. A universal project-wide percentage MUST NOT be the gate.

Rationale

The tool's own doctrine (042): a mandated project % is a Goodhart target and 100% is a smell; the invariant is diff-aware.

A .spectastic/profile.json marker MUST declare the repo enterprise, and spectastic enforce MUST then report the floor passes — every required category covered, waived, or exempt, with zero blocking gaps.

Categories that do not apply to a CLI/library MUST be handled explicitly: observability (no runtime service / metrics surface) via a well-formed, justified, expiring waiver (never a silent pass); contract-first via the detector's existing no-interface exemption (no work). A waiver MUST pass the enforce-waiver-well-formed validate rule.

The quantified-NFR validate gate (047) MUST gain a convention floor so that adopting the enterprise marker does not retroactively turn the historical spec corpus red: only specs at or above the floor are gated; specs below it predate the quantified-NFR discipline and are exempt. The floor mirrors the existing verify-view-missing rule's convention-floor pattern, and the gate MUST still fire on new (at/above-floor) specs. The 047 requirement text MUST be amended to record the floor, via /spectastic.propose.

Rationale

The spike (plan §3) found 104 unquantified NFRs across 59 historical specs — retrofitting a measurable target onto each is a low-value marathon, and many (e.g. "adds no meaningful latency") resist a number. The repo already solved exactly this shape for verify.html with a convention floor ("specs below predate the convention, exempt"); the same pattern makes self-certification honest without a corpus rewrite. This is the amendment US2 depends on.

The enforce detector MUST recognise .github/dependabot.yml as a supply-chain signal, and a real SAST config (Semgrep) MUST be added and recognised as a security signal (additive to the injection red-team). Both detector changes MUST be strictly additive — a project already covered for a category stays covered.

Rationale

The unwaivable categories must pass on substance, and the Dependabot blind spot is a real defect every downstream Dependabot user hits — fixing the shared detector, not gaming the local gate.

A dependency-vulnerability audit gate (e.g. an advisory-database / OSV scan) SHOULD run in CI, so a known-vulnerable dependency is caught, not merely auto-updated.

principles.html SHOULD be reconciled against the enterprise catalog: each catalog principle is present, folded in where genuinely missing and scope-applicable, or recorded not-applicable with reasoning — never blanket-seeded. The amendment SHOULD land via /spectastic.principles.

Non-functional

The new gates MUST be deterministic and reproducible — the same source yields the same formatter/linter/coverage verdict locally and in CI, so a passing local state cannot fail CI on formatting/lint alone.

Landing this MUST NOT leave CI red: after the backlog fix and the marker, the full gate suite (typecheck, dependency-boundary, tests, format, lint, coverage, enforce, and the existing security/dogfood gates) MUST pass on the current codebase.

The added CI gates SHOULD keep the pull-request feedback loop practical — the full required suite completing within roughly ten minutes on the standard runner, so the floor is a guardrail, not a tax.

Out of scope (deferred to other slices)

  • Supply-chain provenance beyond the enforce category — SBOM (CycloneDX/SPDX) generation, build attestation, and pinning GitHub Action versions to commit SHAs. The enforce category needs recognised automation + an audit gate; the enterprise provenance principle's SBOM/attestation is heavier and separable.
  • Governance files — SECURITY.md / vulnerability-disclosure policy, CODEOWNERS. Cheap best-practice, but not part of the enforce floor.
  • Branch-protection / required-status-checks configuration — a GitHub repo setting, not a committable file; documented, not file-configured, here.
  • Migrating the manual chore(release) + version-check flow to a changesets-style automated release.
  • Turborepo/nx build caching — a DX/perf concern, not a robustness gap.

4 · Data model

No new persisted entity — this spec adds config and a declaration, consumed by the existing enforce engine and CI.

Entities

Profile marker
.spectastic/profile.json declaring enterprise — the switch that makes spectastic enforce and the profile-gated validate rules evaluate the repo against the enterprise floor (041).
Enforce waiver
A {category, reason, until, owner} entry (in spectastic.json) that demotes a required-but-inapplicable category (observability) from a blocking gap to an advisory relaxed tally — justified, expiring, and validate-checked (042).
Detector signal
A row in the enforce detector's signal table mapping a config file (e.g. .github/dependabot.yml) to a category (supply-chain). This spec adds signals; it removes none.

Invariant: every required category resolves to exactly one of covered (a detected signal), waived (a well-formed waiver), or exempt (the detector's own antecedent, e.g. no web interface for contract-first) — never a silent gap. The floor passes iff every required category is one of the three.

5 · Success criteria

Technology-agnostic, measurable outcomes.

spectastic enforce against the marked repo reports the enterprise floor passes — zero blocking gaps — with each of the nine required categories shown as covered, waived, or exempt.

A pull request that introduces a formatting violation, a lint error, or drops coverage of its changed lines below 80% fails CI; an equivalent clean pull request passes — both observable against a fixture change.

The full required CI suite (typecheck, dependency-boundary, tests, format, lint, coverage, enforce, and the existing security/dogfood gates) runs green on the current codebase — the backlog fixed, nothing suppressed.

A fixture downstream project using Dependabot (and no Renovate) is reported supply-chain-covered by the updated detector; a fixture project already covered for any category remains covered (additive, no regression).

With the enterprise marker active and FR-009's convention floor in place, a full-corpus validate produces zero quantified-nfr-required errors on below-floor (historical) specs, while a fixture at/above-floor spec with an unquantified NFR still errors — the floor exempts the past without disabling the gate.

Every principle in the enterprise catalog is accounted for in principles.html — present, folded in, or recorded not-applicable with a reason — with none blanket-seeded as noise.

6 · Assumptions

The enforce engine (042) and profile system (041) run correctly against this monorepo root — the detector reads root-level config, and per-package tsconfig/test setups don't confuse category detection. The plan verifies this against a real enforce run.

The historical spec corpus is not broadly quantified — the plan spike found 104 unquantified NFRs across 59 specs, so activating the enterprise marker would redden the corpus without FR-009's convention floor. This assumption was disproven and is recorded here so the floor's necessity is legible; the floor is the resolution, not a corpus rewrite.

Bringing the codebase to lint-green is a bounded one-time effort — the code was written under ad-hoc SonarLint discipline, so the backlog is small (unused imports, a few cognitive-complexity hotspots), not a rewrite.

7 · Open questions

None outstanding — the scope (full floor pass + marker), the detector-gap resolution (fix the shared detector + add real SAST, not a config workaround), the principles reconciliation, the diff-aware coverage target (≥ 80% changed lines + never-lower), the green-from-day-one backlog fix, and the package scope (all source; coverage on the four core packages) were all anchored in the interview. Tool choices (Biome vs ESLint+Prettier, coverage provider, SAST ruleset) are deferred to the plan by design.
