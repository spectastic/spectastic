Tests for a story MUST be written and failing before its implementation tasks start — for the two code changes (US2's convention floor, US3's detector signal) that means TDD; for the config/CI stories (US1, US2's marker, US4) it means a fixture proving the gate would catch a bad case before it's wired blocking. 1 · Execution strategy

Story IDs follow the spec's numbering (T-1xx = US1, T-2xx = US2, T-3xx = US3, T-4xx = US4) regardless of build order. Priorities are US1 = P1, US2 = P1, US3 = P2, US4 = P2.

Setup → Foundational → US1 (the three quality gates, P1) → US3 (detector fix + SAST, P2 — pulled forward because US2 needs its substance) → US2 (self-certify: the floor, the waiver, the marker, P1) → US4 (principles, P2) → Polish. US2's marker task (T-215) is a hard sync point: it does not run until US1's gates and US3's security/supply-chain substance are both real, per plan D-006/§4.

Setup → Foundational → US1 only → ship. Real, blocking robustness (formatter, linter, coverage) lands and is valuable even before the repo self-certifies. Add US3, US2, and US4 as fast-follows.

After Foundational, US1 (quality gates) and US3 (detector signal + SAST + audit gate) touch disjoint files and can run fully in parallel. US4 (principles) is independent of all three and can start any time. US2 is the integration story — it must wait for US1 and US3 to land before its marker task, so it's the natural point where the parallel tracks rejoin.
