Spec data-model layering

Say out loud that a spec's data model is the conceptual one — so field types and wire formats stop drifting upstream by habit.

Status Accepted Spec ID 075-spec-data-model-layering Owner Brian Corbin · @briancorbinxyz Reviewers — Created 31 Jul 2026 Principlesv1.9.0 Smallest demoableThe spec template's §4 states that it holds the conceptual model, and points at the design for physical shape and wire contract. Read time

"Data model" names at least three different documents, and a spec template that says only Data model invites all three. The separation is old and settled: a conceptual model of entities, relationships and invariants, independent of storage; an internal model of tables, columns and serialisation; and an external one — what a consumer actually sees, deliberately stable while the internal one churns. The spec owns the first and only the first: it is the layer that survives a rewrite, and the layer a reader who does not know the stack can still evaluate. This spec makes that explicit in the template, in the authoring guidance, and in the sizing advice — so a thirty-entity feature stops filling a definition list with field types that belong one artifact downstream. No new element, no new rule, no change to the sixty-seven existing sections, all of which are already conceptual. It is a wording change whose value is that it stops the slow drift the wording currently permits.

1 · Context

The spec template's fourth section is headed Data model and offers a definition list of entity to fields-and-purpose. Sixty-seven of sixty-nine shipped specs use it, and in this repository it reads well — because this repository's specs mostly introduce no persisted entities at all, so the format has never been stressed. That is a self-selecting sample.

A settlement service or a booking system fills the same list with thirty rows, and the rows acquire types, nullability, enum members and wire names, because the prompt does not say not to and there is nowhere else to put them. The result is a spec that cannot be read without knowing the stack, cannot be evaluated by a reviewer who does not, and is invalidated by a refactor that changes nothing a user could observe.

The fix is not a new format for the section — a schema in the spec would be the same mistake with better syntax. It is to say which of the three layers the section holds, and to name where the other two live. That is a wording change, and its whole value is preventive: it costs nothing now and stops a drift that is expensive to reverse once specs carry field-level detail.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · The section says what it holds P1

As a spec author, I want the data-model section to tell me it wants the conceptual model so that I do not fill it with field types by default and discover the mismatch at review.

Acceptance: The template's section states the altitude and names where physical shape and wire contract belong; a spec generated from it carries that framing.

US2 · A reviewer can evaluate without the stack P1

As a reviewer who does not know the implementation, I want the spec's entities expressed as concepts and invariants so that I can judge whether the model is right without judging whether the types are.

Acceptance: A spec written against the revised guidance is readable end to end without reference to a language, framework, or storage engine.

US3 · The displaced detail has somewhere to go P2

As an author with genuine field-level detail to record, I want the guidance to point me downstream so that the instruction is a redirection rather than a refusal.

Acceptance: The guidance names the design artifact as the home for physical and external models, so following it never leaves an author with nowhere to put real information.

Edge cases

  • A feature whose entire point is a storage format — the physical shape is the user-visible outcome.
  • A spec with no entities at all, which most in this repository are.
  • An invariant that can only be stated in terms of a concrete type, such as a precision or range constraint.
  • An existing spec whose §4 already carries field types — guidance changes, but nothing forces a rewrite.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The spec template's data-model section MUST state that it holds the conceptual model — entities, relationships, invariants and state transitions — independent of storage and wire format.

Rationale

An unqualified heading invites all three layers. Naming the layer is the entire mechanism.

The guidance MUST name where the physical model and the consumer-facing contract belong, so the instruction redirects rather than merely forbids.

The spec verb's authoring guidance SHOULD carry the same framing, so the interview asks for concepts and invariants rather than fields.

The guidance SHOULD allow a concrete constraint where the invariant genuinely requires one — a precision, a range, a uniqueness rule — without treating it as a layer violation.

Rationale

Some invariants are only expressible concretely. A rule that forbids them pushes real requirements out of the spec entirely, which is worse than the drift it prevents.

Existing specs MUST NOT be invalidated: at most 0 of the shipped specs may become non-conforming through this change.

Rationale

The existing sections are already conceptual. A guidance change that retroactively condemned them would be a migration disguised as a clarification.

The sizing guidance MAY note that a data model outgrowing the section is a signal the detail belongs downstream, rather than a signal to split the spec.

Non-functional

The change MUST be documentation-only: at most 0 new validate rules, at most 0 new elements, and at most 0 changes to generated artifact structure.

Rationale

The distinction is a judgment a machine cannot make — a type in an invariant is legitimate and a type in a field list is drift, and no rule separates them. Enforcing it mechanically would produce false findings on exactly the cases FR-004 protects.

Out of scope (deferred to other slices)

  • The downstream home this guidance points at.
  • Any machine check for layer violations — deliberately not attempted, since the distinction requires judgment.
  • Revising existing specs whose §4 carries physical detail; none in this repository does.

4 · Data model

No entities. This spec changes authored guidance; it introduces no artifact structure and no persisted state.

Worth noting for the irony and the test: this section is itself the shape the spec argues for. It names no fields because there are none to name, and a reader can evaluate the claim without knowing what the template is written in.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

A reviewer can read a spec generated under the revised guidance end to end without reference to a language, framework or storage engine, in 100% of specs whose feature is not itself a storage format.

At most 0 of the existing shipped specs become non-conforming, and at most 0 new validate findings appear across the estate.

An author given a feature with at least 20 entities produces a spec section of concepts and invariants, with field-level detail recorded downstream rather than in the spec.

6 · Assumptions

Authors fill the section the way it asks. The drift this prevents is the result of an unqualified prompt rather than of deliberate over-specification, so changing the prompt is sufficient.

The three-layer distinction is intuitive enough to apply without training. If it is not, the symptom will be authors asking where a given detail belongs — which is a better failure than silently putting it in the wrong place.

7 · Open questions

None outstanding — the altitude split was settled by the survey, and the decision not to enforce it mechanically follows from the judgment FR-004 protects.
