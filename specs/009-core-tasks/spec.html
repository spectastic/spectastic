Core tasks verb — derive the breakdown from spec + plan in the kernel

1 · Context

Today's /spectastic.tasks is a markdown procedure (commands/spectastic.tasks.md) the LLM executes in-process: read spec.html + plan.html, copy templates/tasks.html, generate the five phases (Setup / Foundational / US1..US3 / Polish), check every FR / SC is referenced by at least one task. Works in Claude Code; doesn't reach Tier 2 MCP, Tier 3 VS Code, or Tier 6 web editor — each would re-implement the procedure.

This slice extracts the verb under the kernel pattern fixed in 006-kernel-extraction. The verb takes spec + plan paths through ctx.fs (not raw strings, not pre-parsed ASTs), uses ctx.ai.chat() only for task-description prose, and keeps IDs, phase boundaries, and traceability deterministic in code.

2 · User scenarios & testing

Each story is independently testable: if you implemented only US1, you would still have a viable MVP that proves the kernel + CLI seam.

US1 · Maintainer runs the CLI subcommand P1

As a maintainer drafting a new spec, I want to run spectastic tasks <spec-id> and get a populated tasks.html so that I don't have to round-trip through the slash command for routine breakdowns.

Acceptance: Running node packages/cli/dist/index.js tasks 002-validate-cli writes a tasks.html with the same five phases and task-ID ranges (T-001+, T-010+, T-1NN/T-2NN/T-3NN, T-900+) as the existing file. Exit 0 on success; non-zero with a human-readable error when spec or plan is missing.

US2 · Slash command keeps working unchanged P1

As a contributor invoking /spectastic.tasks, I want to see no behavioural change so that muscle memory keeps working and the markdown stays the source of truth.

Acceptance: /spectastic.tasks 002-validate-cli produces a tasks file functionally equivalent to today's output. The markdown gains a MAY-tier note saying the LLM may invoke spectastic tasks via Bash for the deterministic skeleton.

US3 · Downstream surface imports the kernel directly P2

As a future MCP server or VS Code extension author, I want to import tasksCommand from @spectastic/core/commands/tasks and render the returned phases in-editor so that I get the structured breakdown without writing HTML to disk or spawning the CLI process.

Acceptance: A test under packages/core/test/ calls tasksCommand({ specPath, planPath }, ctx) with stub ctx.fs + ctx.ai and receives a TasksResult with the five phases populated, every FR/SC referenced, and the same task-ID structure the CLI produces.

Edge cases

Four tracked failure modes the extraction handles
  • Missing plan.html — the kernel surfaces a typed error (not a thrown string) so the CLI can print a friendly message and exit with code 2.
  • AI provider unavailable — if ctx.ai is undefined or its chat() rejects, the kernel still returns the deterministic skeleton with placeholder descriptions and a warning surfaced on TasksResult. The CLI translates the warning to stderr.
  • Spec with no user stories — the kernel emits Phase 1, Phase 2, Phase 4 only; phase 3 is empty. The traceability check still runs against FR/SC in the spec.
  • Requirement with no covering task — the kernel surfaces it as a <spec-warning> in the rendered HTML, matching today's slash-command behaviour. Not a fatal error.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional — the kernel verb

The tasks verb MUST conform to 006's KernelContext shape: single async function, no module-level side effects, all IO + AI access flow through ctx, no implicit process.cwd() / process.env / console usage.

tasksCommand MUST be implemented at packages/core/src/commands/tasks.ts and exported on its own subpath (@spectastic/core/commands/tasks) per the lazy-loading discipline in 006 FR-002. The package main entry MUST NOT eagerly load it.

@spectastic/cli MUST gain a tasks <spec-id> subcommand that resolves specs/<spec-id>/spec.html and specs/<spec-id>/plan.html, calls tasksCommand, and writes the returned HTML to specs/<spec-id>/tasks.html. The subcommand owns shell-side concerns (path resolution, file writes, stderr formatting); the kernel owns the deterministic core.

The kernel MUST take spec + plan as filesystem paths via ctx.fs, not as raw content strings and not as pre-parsed ASTs. Reading and parsing happen inside the kernel using @spectastic/schema's parser, so consumers don't need to pre-process inputs.

Rationale

Paths-through-ctx.fs matches the kernel pattern's IO injection rule and keeps the in-memory test path open (stub ctx.fs returns fixture strings). Raw content strings would force every consumer to read the disk themselves; pre-parsed ASTs would couple the consumer to @spectastic/schema's internal types.

The generated tasks file MUST contain the five canonical phases — Setup (T-001+), Foundational (T-010+), US1 (T-100+), US2 (T-200+), US3 (T-300+), Polish (T-900+) — per the discipline in commands/spectastic.tasks.md. Phase boundaries and ID ranges are computed deterministically in code, not delegated to the LLM.

The kernel MUST use ctx.ai.chat() only for generating human-readable task descriptions (the imperative one-liner and target file path per task). Task IDs, phase assignment, parallel markers, and the requirement-traceability cross-reference MUST be computed deterministically — they are stable across runs on the same inputs.

Rationale

Light AI usage keeps the verb fast and reproducible. The LLM is good at framing imperative task titles from requirement prose; it is bad at maintaining stable IDs across re-runs. Splitting the responsibilities lets the bench p50 stay tight and lets traceability stay exact.

The kernel MUST return a structured TasksResult (see §4) containing the rendered HTML string plus the phase data. The caller (CLI today; MCP / editor tomorrow) decides whether to write the HTML to disk, render the phase data in a UI, or both.

Every FR-NNN, NFR-NNN, and SC-NNN in the input spec MUST be referenced by at least one generated task. Requirements without a covering task MUST surface as a <spec-warning> in the rendered HTML — matching today's slash-command behaviour — not silently dropped.

The verb MUST ship with unit tests at packages/core/test/tasks.test.ts (pure function; stub ctx.fs + stub ctx.ai; in-memory fixtures) and CLI integration tests at packages/cli/test/cli.test.ts (real spec + plan; assert file written; assert phase / ID structure).

commands/spectastic.tasks.md MUST be updated with a MAY-tier note: the LLM may invoke spectastic tasks <spec-id> via Bash to delegate the deterministic skeleton to the kernel; it is not required to. The markdown procedure remains the canonical source of truth.

tasksCommand's docblock MUST link to commands/spectastic.tasks.md as the canonical procedure, per 006 FR-008. The markdown MUST NOT be auto-generated from the docblock.

The verb's behaviour against an existing destination tasks.html MUST gate on the destination's <spec-status> per P-6: a Draft destination MUST be edited in place (preserve T-NNN IDs per FR-006; append a one-line <spec-changelog> entry); a past-Draft destination (Accepted, In Review, Superseded, Deprecated, Blocked) MUST be refused with a typed error pointing at /spectastic.propose. A --force override MAY bypass the past-Draft refuse, but invoking it MUST emit a one-line warning that the operation skips the change-management surface.

Rationale

Cascade of 009/T-001: blanket refuse-if-exists conflated Draft with past-Draft. P-6 ratified the asymmetry; this FR makes the verb honour it explicitly so a future LLM session reproducing the verb inherits the gate.

Non-functional

The extraction MUST NOT regress any scenario in bench/baselines.json past its declared budget. The init-help-cold-start scenario is the explicit guard against eager-loading @spectastic/core/commands/tasks (and through it parse5 + the AI provider) on the CLI init path.

Out of scope (deferred to other slices)

  • Task amendments (re-running tasks on an updated spec, merging into an existing tasks.html). Owned by the implement verb's checked-state contract; this slice always writes a fresh file.
  • Cross-spec task linkage (a task in one spec depending on a task in a sibling spec). Surface for a later spec once the in-spec shape is proven.
  • Sibling — extract /spectastic.triage.
  • Sibling — extract /spectastic.principles.
  • Sibling — extract /spectastic.apply.
  • Sibling — extract /spectastic.spec.
  • Sibling — extract /spectastic.plan.
  • Sibling — extract /spectastic.propose.

4 · Data model

Four types this slice owns: TasksInput, TasksResult, TaskPhase, Task. All flow through @spectastic/core/commands/tasks's subpath export.

Entities

TasksInput
{ specPath: string, planPath: string }. Both are filesystem paths resolved against ctx.cwd; the kernel reads through ctx.fs. No raw content strings; no pre-parsed AST.
TasksResult
{ html: string, phases: TaskPhase[], totalTasks: number, parallelTasks: number }. html is the rendered single-file artifact ready to write to specs/<spec-id>/tasks.html. phases is the structured breakdown for downstream surfaces that want to render their own UI. totalTasks and parallelTasks are summary counts for the after-write report message the slash command surfaces today.
TaskPhase
{ id: string, title: string, tasks: Task[] }. id is one of setup / foundation / us1 / us2 / us3 / polish. title is the human label ("Phase 1 — Setup", etc.). Empty phases (e.g. us3 on a two-story spec) are omitted from the array.
Task
{ id: string, title: string, path?: string, parallel: boolean }. id matches T-NNN. title is the imperative one-liner. path is the target file or directory shown via <span class="path">; optional for tasks that span multiple files. parallel mirrors the boolean parallel attribute on <spec-task>.

The rendered HTML html field and the structured phases array are two views of the same underlying data — keep them in sync. The kernel computes the structured form first, then renders to HTML; consumers that want machine-readable output skip the render step entirely.

Technology-agnostic, measurable outcomes.

Running node packages/cli/dist/index.js tasks 002-validate-cli writes a tasks.html with the same five phases and same total task count as today's slash-command output on the same inputs (modulo trivial whitespace and AI-generated description wording).

6 · Assumptions

Two preconditions: 006's KernelContext shape is final, and @spectastic/schema's parser surfaces enough structure to enumerate FRs / SCs.

The KernelContext shape (cwd, fs, ai) defined in 006 FR-007 is stable. If it changes, this slice updates its function signature and tests; no other change cascades.

@spectastic/schema's parser exposes (or can be cheaply extended to expose) the FR / NFR / SC IDs and user-story headings from a parsed spec.html. Without that, the kernel would need to re-parse the HTML itself — duplicative and a violation of single-source-of-truth.
