Implementation plan · 009-core-tasks

Core tasks — implementation plan

How tasksCommand ships — kernel reads spec + plan via ctx.fs, parses via @spectastic/schema, deterministic phase + ID skeleton, one chat call per phase for prose, structured TasksResult back.

Status Accepted Spec 009-core-tasks Owner Brian Corbin · @briancorbinxyz Branch main (squashed-snapshot pattern) Created 16 Jun 2026 Read time

Extract /spectastic.tasks into @spectastic/core/commands/tasks under 006's kernel contract. The verb takes { specPath, planPath } through ctx.fs, parses both with @spectastic/schema (one new helper surfaces FR / NFR / SC / user-story IDs), computes the five-phase skeleton + every T-NNN deterministically in code, and uses ctx.ai.chat() once per non-empty phase for task-description prose. Returns a structured TasksResult; CLI subcommand owns disk writes. Slash command keeps working with a MAY-Bash note. Single PR; ships as v0.1.0-pre.11.

3 · Approach

Three moves, one PR. One: extend @spectastic/schema with extractSpecMetadata(doc) so the kernel enumerates FR / NFR / SC / user-story IDs without re-parsing (D-006). Two: implement tasksCommand at packages/core/src/commands/tasks.ts; reads + parses spec + plan, computes the deterministic phase + ID skeleton (D-002, D-003), invokes ctx.ai.chat() once per non-empty phase for prose (D-004), emits traceability (D-005), returns { html, phases, totalTasks, parallelTasks }. Three: add a spectastic tasks <spec-id> CLI subcommand that resolves paths, builds ClaudeProvider + KernelContext, calls the kernel, writes tasks.html, prints the after-write report.

The deterministic-skeleton-plus-light-AI split is the architecturally-interesting piece. Phase IDs, task-ID ranges (T-001+, T-010+, T-1NN, T-2NN, T-3NN, T-900+), and requirement → phase mapping are pure functions over the parsed spec — no LLM, no flakiness. Chat only fills the imperative one-liner + optional target path. Per-phase calls give intra-story style consistency without ballooning call count.

4 · Alternatives considered

OptionDeterminismAI costEffortTotal
Per-task chat call — one LLM round per T-NNN2136
Single chat call — one LLM round for the entire tasks file2439
One chat call per non-empty phase — chosen43411

Per-task calls drift in style; one big call risks dropped tasks. Per-phase calls keep prompts small, share style within a story, bound cost to 4–6 calls, and on failure fall back to placeholder prose with a warning — IDs and structure still hold.

5 · Decisions

D-001 · Spec + plan as paths via ctx.fs; parsed inside the kernel

Status
Accepted
Context
Verb needs the two docs as ParsedDocuments. Options: raw strings, pre-parsed ASTs, or paths read+parsed inside. FR-004 locks paths.
Decision
TasksInput = { specPath, planPath }; kernel calls ctx.fs.readFile then schema.parse. Re-uses the existing parser surface — no duplicate parse path.
Consequences
+ Matches IO-injection rule (006 D-005); + unit tests stub ctx.fs.readFile with fixture strings. − Two read+parse ops per call; trivially cheap (~2 ms / doc).

D-002 · Phase assignment — deterministic heuristic, not AI

Status
Accepted
Context
Five-phase shape is fixed per the slash-command markdown. Phase boundaries are stable across re-runs only if a pure function decides them.
Decision
Six fixed slots: setup, foundation, us1..us3, polish; emitted in order, empty omitted. Heuristic: scaffolding / install → setup; shared types / schemas / middleware → foundation; requirements referenced from a US block → that story; perf / docs / observability / cleanup → polish. In tasks-phases.ts with branch-coverage tests.
Consequences
+ Same input → same mapping; reviewable, testable. − Unusual phrasing may misroute; FR-008 warning catches obvious gaps.

D-003 · Task-ID assignment — deterministic per-phase counter

Status
Accepted
Context
IDs are contracts (P-3). FR-005 fixes the ranges; slash-command markdown lays out the discipline.
Decision
Each phase has a start ID (1, 10, 100, 200, 300, 900) and a counter; tasks append in source-requirement order. Within a US phase, test-tagged tasks precede impl via a stable sort key. No LLM input.
Consequences
+ SC-001's ID guarantee is structural. − Re-ordering requirements renumbers tasks (the future implement verb's checked-state merge handles amendments, deferred). − ≥4 stories overflow into T-4NN+ with a warning.

D-004 · Light AI — one ctx.ai.chat() per non-empty phase

Status
Accepted
Context
D-002 / D-003 do the structural work; AI only writes the imperative one-liner + optional target path. Per-task (no context), one-big-call (drops tasks), or per-phase.
Decision
One chat() per non-empty phase at temperature: 0. Prompt: phase's requirement context + task IDs to title. Response: JSON list of { id, title, path? }. Kernel validates length + IDs; parse failure → placeholder prose for that phase with a <spec-warning> on TasksResult.warnings.
Consequences
+ Bounded cost (4–6 calls); intra-phase style consistency; scoped failure. − Wording isn't bit-stable; SC-002 carves out wording variance.

D-005 · Traceability — <spec-note> per US phase + <spec-warning> for uncovered

Status
Accepted
Context
FR-008 requires every FR/NFR/SC to be referenced by ≥1 task; uncovered → warning. The per-task requirement linkage comes from D-002.
Decision
Each task carries a closed-requirement set. End of each US phase emits a <spec-note> listing union of FR/SC IDs closed, with anchor links. After all phases, renderer compares full FR/NFR/SC set against referenced; uncovered → <spec-warning> atop §6 Polish. TasksResult.warnings mirrors for non-HTML consumers.
Consequences
+ Traceability is a function of structured data, not LLM prose; degrades gracefully. − One extra pass at render time, trivially cheap.

D-006 · Schema gains extractSpecMetadata helper

Status
Accepted
Context
Spec author flagged: does the parser need a method to enumerate FR/SC IDs? Today's parser exposes only the AST primitives; the kernel could re-implement enumeration but duplicates schema knowledge.
Decision
Add extractSpecMetadata(doc): { frIds, nfrIds, scIds, userStories } to @spectastic/schema; each story carries { id, heading, requirementIds }. ~40 LoC over findAll/getAttr. Core peer-bumps.
Consequences
+ Single source of truth for spec structure; reusable by 011 / 012 / 014. − Schema gains a structured-introspection surface; future helpers cluster there.

D-007 · Single-PR migration; ships as v0.1.0-pre.11

Status
Accepted
Context
Slice lands four pieces (schema helper, kernel verb, CLI subcommand, markdown note); staging couples kernel to an unshipped helper.
Decision
Single PR per 006 / 007 precedent. Ships as v0.1.0-pre.11 (007=pre.9, 008=pre.10). Three packages bump in lockstep per 004's policy. Bench enforces lazy loading; CLI test asserts SC-002; unit tests cover SC-001.
Consequences
+ Atomic; reverts cleanly. − Larger diff; bench/test failure blocks the whole slice.

8 · Complexity tracking

Two deliberate additions warrant flagging:

Three-file split in packages/core/src/commands/. tasks.ts + tasks-phases.ts + tasks-render.ts rather than one file. Phase heuristic + renderer are pure, independently testable, and reused by future verbs (renderer for implement amendments; heuristic when spec evolves). Single-file would couple the three.

New helper bumps schema's API surface (D-006). Adds extractSpecMetadata + SpecMetadata exports — pre-1.0 minor bump per 006 FR-012. Schema gains a structured-introspection surface; future verbs (011 / 012 / 014) cluster there. Justified: the alternative is re-parsing inside core, which duplicates schema knowledge.
