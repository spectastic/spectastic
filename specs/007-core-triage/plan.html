3 · Approach

Three moves, one PR. One: implement triageCommand at packages/core/src/commands/triage.ts following 006's signature; both modes (single-card + list-intake) in scope; the kernel returns structured TriageCards and does no IO beyond the AI call. Two: ship the first concrete ClaudeProvider at packages/core/src/providers/claude.ts using @anthropic-ai/sdk; lazy-loaded via its own subpath. Three: add a spectastic triage CLI subcommand that constructs the ClaudeProvider + KernelContext, reads the current max-existing-ID from the destination, invokes triageCommand, and routes each returned card to its destination based on layer.

ask<T>() is the architecturally-interesting piece. The interface mirrors Claude Code's AskUserQuestion exactly so future surfaces (MCP, VS Code) can route the call to native UI without re-shaping. The Claude implementation here can't escalate to a human at run-time (the CLI runs unattended), so the kernel uses ask<T>() the way the slash-command markdown intends: as a typed prompt to the LLM itself, returning the LLM's pick across the bounded set. The implementation is a structured-prompt + JSON-parse with one stricter-prompt retry; raw chat() with temperature: 0 gives reliable JSON for small option sets.

4 · Alternatives considered

OptionRobustnessSDK churnEffortTotal
Tool-use API for ask<T>()4239
structured-output / JSON-schema mode4127
Structured prompt + JSON parse + retry — chosen34411

The two SDK-feature alternatives offer stricter contracts at the cost of needing recent-enough SDK versions and tying the kernel's ask<T>() shape to Anthropic-specific surface area. The chosen structured-prompt approach works on every SDK version that ships messages.create; if the JSON parse fails once, a retry with a stricter system prompt almost always succeeds for bounded option sets. The 011 / 012 / 013 specs will exercise ask<T>() much harder; if the JSON-parse approach proves flaky in practice, switching to tool-use is a Claude-provider-internal change with no API surface impact.

5 · Decisions

D-001 · ClaudeProvider implementation via @anthropic-ai/sdk

Status
Accepted
Context
The kernel's AIProvider interface (006 FR-007) declared three methods; this slice lands the first concrete implementation. The official Anthropic SDK is the lowest-friction path.
Decision
Class ClaudeProvider implements AIProvider at packages/core/src/providers/claude.ts; @anthropic-ai/sdk as a regular dependency with caret range (^0.32.0 at land time). subagent() stays unimplemented (throws "not implemented in v1" — 013 lights it up). Lazy-loaded via subpath; never imported from the umbrella entry.
Consequences
+ Batteries-included (auth, retries, errors); + dependabot manages updates. − Bundles SDK weight; − the unimplemented subagent() stub is dead code until 013.

D-002 · ask<T>() via structured prompt + JSON parse + one-retry

Status
Accepted
Context
The kernel calls ctx.ai.ask<T>(questions); the Claude provider has to translate. Tool-use API or JSON-schema response_format would be stricter but tie the kernel to SDK feature flags.
Decision
Format the Question[] as a JSON description in the prompt body + a strict system instruction ("return ONLY JSON matching schema X"); call chat() with temperature: 0; parse the response; if parse fails, retry once with a stricter system prompt. Validate parsed shape against the Question structure before returning.
Consequences
+ Works on any SDK version with messages.create; + isolates provider-internal concerns from the kernel surface. − Two-call worst case; − validation logic per call; − bounded option sets only (large sets risk truncation).

D-003 · Card-ID assignment — caller passes startingId

Status
Accepted
Context
Cards have stable IDs (T-NNN per-spec, I-NNN for inbox). Per FR-010 the kernel MUST NOT hard-code destination paths — which would also include max-ID scanning of those destinations.
Decision
The CLI subcommand reads the target file (specs/<spec-id>/triage-log.html or inbox.html) before invoking the kernel, finds the max existing ID via regex on id="T-(\d+)" / id="I-(\d+)", passes it as input.startingId. Kernel returns cards numbered from startingId + 1. For list-intake mode the kernel may need to know both starting IDs (per-spec for diagnostic cards, inbox for routing exits) — passed as { startingIdT, startingIdI }.
Consequences
+ Kernel stays pure; + caller serialises writes against its own destination. − Two-pass per invocation (caller reads, then kernel produces); − caller has to know about both ID spaces for mixed list-intake.

D-004 · Layer classification — LLM-based with ask<T>() escalation

Status
Accepted
Context
The eight layer values (FR-009) require judgement; pure heuristics undercount. The skill markdown today uses LLM reasoning + escalates to AskUserQuestion when boundary cases are ambiguous (e.g., implementation-vs-spec, just-do-vs-spec).
Decision
Single-card mode: kernel asks Claude to classify in one chat call alongside characterisation. If the response indicates ambiguity (low confidence, explicit "could be X or Y" hedge), kernel calls ctx.ai.ask<T>() with the narrow choice (e.g. Diagnostic-or-Routing? then narrower layer choice — matching today's two-step split for the >4-option limit). List-intake mode: per-card classification; ambiguous items get their own ask call.
Consequences
+ Matches the slash-command's discipline; + ask escalation is a typed commitment, not prose hedging. − Two-pass on ambiguous cards; − tuning the "ambiguous" detector is a real concern.

D-005 · ANTHROPIC_API_KEY redaction strategy

Status
Accepted
Context
NFR-002 forbids the key from appearing in any surfaced output. The SDK's default error messages may include request headers including auth.
Decision
ClaudeProvider catches every error from messages.create calls and rewraps as a typed ClaudeProviderError whose .message + .stack are scrubbed: any substring matching the key value (read once at construction) is replaced with [REDACTED]. Default Node error handlers can't expose the raw error because the wrapping is final. Unit test deliberately constructs a provider with a known fake key and asserts the key value doesn't appear in any thrown error's serialised form.
Consequences
+ Defence-in-depth: even if the SDK changes how it formats errors, the rewrap stays effective. − Wraps every error path; the original stack-trace shape is partially obscured for non-key debugging.

D-006 · List-intake heuristic — preserved from existing skill markdown

Status
Accepted
Context
FR-005 requires detecting list inputs. The slash-command markdown defines the heuristic (commas, semicolons, newlines, numbered items, phrases like "things"/"items"/"stuff").
Decision
Port the heuristic verbatim to a small pure function detectMode(description) inside triage.ts; when caller supplies input.mode explicitly, kernel honours it without detection. Ambiguous detection in the unit test triggers a warning; the CLI subcommand prompts the user.
Consequences
+ One source of truth for the heuristic (the TS function); markdown can refer to it. − Heuristic-vs-LLM detection has trade-offs; sticking with heuristic for v1 matches today's behaviour.

D-007 · Network-test gating via vitest.skipIf

Status
Accepted
Context
SC-004's real-Claude integration test runs in dev (env var set) and must skip cleanly in CI when the secret isn't exposed. Custom --network-tests flag would be another knob to remember.
Decision
test.skipIf(!process.env.ANTHROPIC_API_KEY) per test that hits the real API. The CI workflow exposes ANTHROPIC_API_KEY as an Actions secret on push events to main only (not forks); local dev runs the test whenever the env var is set.
Consequences
+ Zero flags; + skipped count surfaces in test output (visible signal that the test exists but wasn't exercised). − Forks contributing PRs don't run SC-004; relies on maintainer-side validation on main.

D-008 · Single-PR migration, bench-gated

Status
Accepted
Context
007 lands three things: the verb extraction + the first AI provider implementation + the slash-command markdown update. Staging could reduce per-PR scope but the pieces are tightly coupled (no provider → no verb tests; no markdown update → discoverability gap).
Decision
Single PR per 006's precedent (D-008 there too). Ships as v0.1.0-pre.9. The bench enforces the lazy-loading discipline; CLI integration tests prove SC-001 byte-identity; npm view on the published tag confirms the slice.
Consequences
+ Atomic; + reverts cleanly; + simpler version bookkeeping. − Larger diff than typical; − bench/test failure during apply blocks the whole slice.

7 · Risks & mitigations

RiskLikelihoodImpactMitigation
@anthropic-ai/sdk creeps onto the init path through an eager top-level import in src/index.ts.MHBench's init-help-cold-start (150 ms budget) catches it; D-001 forbids it explicitly.
ask<T>() JSON parse flakes on edge inputs.MMOne-retry fallback with stricter prompt (D-002); unit tests exercise both happy + malformed-JSON paths; later slices can switch to tool-use without changing the kernel surface.
Key leaks into a surfaced error after an SDK change.LHDefence-in-depth scrub (D-005); unit test asserts redaction on a constructed error path; CI fails if the assertion stops holding.
SC-001 byte-identity is unattainable because today's slash command produces non-deterministic LLM prose.MMCompare structured fields (layer, ID, FR/SC references) not free prose; allow whitespace and prose-wording variance; the integration test asserts on structure, not LLM-generated bytes.
Card-ID race when caller batches list-intake against a shared destination.LLD-003 documents caller-serialised writes as the contract; single-author assumption (spec §6).

8 · Complexity tracking

Two deliberate additions warrant flagging:

Stub subagent() on ClaudeProvider (D-001). The forward-looking AIProvider interface (006 D-004) requires implementations to declare the method; v1's Claude impl throws "not implemented; lands with 013-core-propose." Dead code until 013. Justified: declaring the unimplemented method in v1 keeps 013's PR additive.

SC-001 byte-identity is structural, not literal (Risks table). The spec writes "byte-identical modulo trivial whitespace"; the implementation has to interpret that pragmatically because LLM prose isn't bit-stable. The integration test asserts shape + IDs + classifications match, not exact words. Documenting here so a reviewer reading the assertion shape doesn't think it under-delivers.
