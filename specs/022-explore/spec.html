Specification · 022-explore

explore — vibe to learn, spec to keep

A second extended verb, upstream of spec: explore <intent> scaffolds a quarantined exploration you build loosely — the SDD ceremony off, a thin principles floor on — that the lifecycle refuses to ship until it graduates.

Spec-driven design demands the spec before a line is written, and so throws away the discovery that comes from building to learn. explore is a second extended, opt-in verb (after explain) that brings the exploratory loop into the lifecycle. This first slice ships the front half: explore <intent> captures a one-line intent, scaffolds a quarantined exploration under explorations/<id>/ with the thin principles floor on and the SDD ceremony off, and wires the anti-ship guard so the core verbs and the validator refuse to advance an un-graduated build. The graduation interview that turns a loose build back into spec/plan/tasks is deferred to a sibling slice; this slice captures the run so graduation can later promote it to verified grounding.

1 · Context

spectastic's lifecycle is deliberate from the first move: spec demands user stories, success criteria, an INVEST self-check, and a smallest-demoable before a line is written. That rigor is the point — but it forfeits the one thing regular AI coding does well: building something, running it, and letting the attempt tell you what you actually wanted. Sometimes you don't know what to build until you've tried.

The existing fast path — the just-do inbox card — is for changes you already understand. It cannot help when you don't yet know the shape and the point of building is to find it. The field treats this as a war: vibe-coding tools accept un-reviewed AI code; spec-driven tools (Kiro, spec-kit) cure that by forbidding the prototype. That is a false choice. An exploratory build is not the enemy of a good spec — it can be its best source, if you graduate it instead of shipping it.

The stakeholders are explorers (the engineer building to learn) and reviewers (who must trust that nothing loose can reach production). The design brief in explore-considerations.html settles the shape across five accepted decisions (D-1…D-5); this spec scopes the front half of that loop — scaffold and quarantine — and defers graduation to a sibling.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP — a verb that scaffolds an exploration.

US1 · Scaffold a quarantined exploration P1

As an explorer, I want to run explore <intent> and get a scaffolded, quarantined exploration so that I can start building to learn without paying the SDD ceremony up front.

Acceptance: running the verb with a one-line intent creates explorations/<id>/ with an explore.html ledger carrying the intent, a quarantined status, and the thin principles floor in force; no requirement IDs, INVEST, or proposal cycle are demanded.

US2 · The lifecycle refuses to ship un-graduated work P1

As a reviewer, I want the lifecycle to refuse to advance or ship a quarantined exploration so that a throwaway prototype can never silently reach production.

Acceptance: every attempt to advance (spec/plan/tasks/propose/apply) or ship a quarantined exploration is refused; spectastic validate reports an un-graduated exploration as an error-level finding; the only in-scope exits are graduation (deferred) or deletion.

US3 · Record what was built and ran P1

As an explorer, I want explore to record what I built and ran so that a later graduation can turn those facts into verified grounding without re-capturing them.

Acceptance: the exploration carries a structured run record whose shape is shared with the verify.html Run/Demo block; the fields verify consumes are present and reusable.

Edge cases

  • An exploration whose build is never run — the ledger is still valid; the run record is empty until there is a run to record.
  • Two explorations open at once — each owns its directory and marker; the guard applies per-exploration.
  • An explorer tries to apply or ship the loose build directly — refused (FR-006); there is no bypass.
  • The git-ignored explore.html ledger is lost — the tracked marker still preserves the quarantine status, so the guard still bites; the learning prose may be local-only (an accepted tradeoff of the git-ignore default).
  • Deleting an exploration — removes the directory and marker; no residue blocks the lifecycle.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

/spectastic.explore <intent> MUST be an extended, opt-in verb positioned upstream of /spectastic.spec, and MUST NOT join or alter the core eight verbs.

Rationale

D-1: discovery is not for every project, so it fits the extended opt-in tier established by explain rather than expanding the hero set.

explore MUST capture a single-line intent and scaffold a new exploration under explorations/<id>/ — a location, sibling to specs/, that signals "not production."

Rationale

D-4: a distinct top-level tree is the clearest "not production" signal. Graduation is what later moves an extracted spec into specs/.

explore MUST create an explore.html ledger that records the intent and, as the build proceeds, what was built, tried, worked, and didn't.

A version-controlled, machine-readable quarantine marker MUST record the exploration's quarantined status, so the guard is visible to teammates and CI even though the explore.html ledger itself MAY be git-ignored by default.

Rationale

The chosen guard is status + validate refusal; for the validator to refuse in CI rather than only locally, the status must live in the repository. The ledger stays ephemeral (like explain --course); the small marker carries the signal the guard relies on.

The core lifecycle verbs (spec, plan, tasks, propose, apply) MUST refuse to advance a quarantined exploration, and spectastic validate MUST report an un-graduated exploration as an error-level finding.

There MUST be no path from a quarantined exploration to a terminal-or-onward spectastic state without graduation; graduation MUST be mandatory before anything the exploration produced can ship or merge.

Rationale

D-4 / Brooks: the throwaway that ships is worse than no prototype. The relaxation is only safe because the output cannot be promoted silently. Graduation's mechanics are deferred, but the guarantee that it is unavoidable ships here.

During an exploration the thin principles floor — P-1 (source order / single-file) and P-2 (semantic tags) — MUST remain in force for spectastic artifacts, while the SDD ceremony (test-first, requirement IDs, INVEST, smallest-demoable, the propose→apply cycle) MUST be relaxed.

Rationale

D-3: fast but not feral. The floor's exact membership is the cheap, foundational structural pair; everything that is ceremony waits for graduation. The loose prototype build itself is not a spectastic artifact and is unconstrained beyond living in the quarantined location.

explore MUST record what was built and ran in a structured run record whose shape is shared with the verify.html Run/Demo block, so a later graduation can promote those facts to grounding="verified".

Rationale

D-5: the running build is the strongest grounding a spec can have. One record serves both the explore ledger and verify; don't invent a second.

The only exits from a quarantined exploration in this slice MUST be graduation (deferred to a sibling) or deletion; explore MUST NOT introduce an "abandoned" terminal state.

Rationale

Keeps the status set minimal for the front half. An exploration that won't work is deleted, not parked; a richer terminal-state vocabulary can be added by the graduation slice if a negative-result record proves worth keeping.

explore SHOULD reuse the extended-verb packaging seams established by 018-explain so the ex- pair reads as deliberate rather than accidental.

Non-functional

The quarantine guard MUST be deterministic: every attempt to advance, apply, or ship a quarantined exploration MUST be refused — zero false "shippable" outcomes.

The quarantine marker SHOULD be machine-checkable without parsing the full ledger, so spectastic validate and a CI step can detect quarantine in a single read.

Out of scope (deferred to other slices)

  • The graduation interview — classify (spike vs tracer-bullet), extract the spec from the build, restore the relaxed gates. The whole back half of the loop.
  • Spike-vs-tracer-bullet classification and how it is recorded so it cannot be quietly reversed; refactor-to-comply vs clean-rebuild paths.
  • A think-first discovery mode (think-to-learn) — a sibling at the front of the lifecycle, considered separately.
  • Adopting Kiro's EARS requirement notation — spectastic's RFC-2119 <spec-rule> form stands.

4 · Data model

This slice owns the exploration tree and the quarantine signal. Graduation owns nothing here yet.

Entities

Exploration
An id (NNN-kebab, shared scheme with specs), a one-line intent, a location (explorations/<id>/), and a status (quarantined). The unit the guard acts on.
Explore ledger (explore.html)
Single-file HTML artifact: the intent plus the running record of what was built, tried, worked, didn't. Git-ignored by default.
Quarantine marker
A small, version-controlled, machine-readable record carrying the exploration id and quarantined status. What the guard and CI read.
Run record
Structured capture of what was built and ran — shape shared with the verify.html Run/Demo block. The seed of later verified grounding.

Status in this slice is a one-value set (quarantined) with exactly two in-scope transitions out: graduate (deferred — the only path to a production state) and delete. No "abandoned" state (FR-009). The git-ignored ledger and the tracked marker are deliberately split so the discovery prose stays ephemeral while the guard stays enforceable in the repo.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

100% of scaffolded explorations live outside specs/ and carry a quarantined status; an observer can tell an exploration is not production from its location and status alone.

Zero un-graduated explorations reach a terminal-or-onward spectastic state or ship: every advance, apply, or ship attempt against a quarantined exploration is refused, and spectastic validate errors.

Every exploration that ran carries a structured run record containing at least the fields the verify.html Run/Demo block consumes, reusable by a later graduation with no re-capture.

6 · Assumptions

Exploration IDs share the NNN-kebab scheme with specs; a later graduation reuses the same ID for specs/<id>/, so the discovered-not-guessed history is traceable by ID.

Multiple concurrent explorations are allowed, each in its own directory with its own marker.

The loose prototype build is not a spectastic artifact and is not held to the spectastic principles during explore beyond residing in the quarantined location; only the ledger and marker are governed by the thin floor.

The git-ignore default for the ledger is repo-configurable; the guard relies on the tracked marker, not on the ledger being present.

7 · Open questions

None outstanding — every decidable question was anchored in the interview. The brief's §6 open questions resolved as: quarantine enforcement = a quarantined status the verbs refuse + a validate error (FR-005, FR-006); the thin floor = P-1 + P-2 only (FR-007); run capture = the shared verify.html Run/Demo record (FR-008). Spike-vs-tracer-bullet mechanics and the think-first sibling mode are deferred, not open (§3 Out of scope).
