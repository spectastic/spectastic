Specification · 104-tracking-plan

What the interface reports

An analytics plan written next to the element that emits the event, gated on a consent question nobody has answered yet, so that answering it is a switch rather than a retrofit.

1 · Context

This slug was planted as a question the survey declined to close: whether a tracking plan belongs in a visual spec, or beside one. Declining to close a question is a reason not to answer it hastily, not a reason to keep refusing once the evidence accumulates on one side — and it has. The same survey calls this the layer the design tools get right and the field under-represents, the annotation vocabulary already names tracking as a category it cannot type, and both worked examples specify it well unprompted.

The question it leaves genuinely open is where, and that is answerable. An event belongs next to the element that emits it for the same reason a state belongs next to the screen it describes: the alternative is a separate document that drifts from the interface it claims to describe, and drift is the failure this whole family exists to make visible.

The consent gate is what makes writing it early safe. A plan authored before the privacy question is answered is a design decision; a plan shipped before it is answered is a liability. Recording the dependency means the plan can be reviewed at design time and cannot leak into a build by inattention.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · An event is declared beside the element that emits it P1

As an author, I want to declare the event a control emits next to the control so that the plan cannot drift from the interface it describes.

Acceptance: A declared element can carry an event with a stable name; the event is readable from the screen declaration without opening an analytics document.

US2 · A payload is typed, not described P1

As a privacy reviewer, I want to see exactly which fields an event carries so that I can tell whether anything identifying is among them.

Acceptance: An event declares its fields; a field with no declared type is reported; an event declaring no fields is valid and means it carries none.

US3 · A plan is inert until consent is settled P1

As a reviewer, I want to see that no event may ship until the consent question is answered so that writing the plan early is safe rather than a liability.

Acceptance: A tracking plan references the question that gates it; a plan with no gate is reported; the gate's presence is visible without running anything.

Edge cases

  • An event emitted by something that is not a control — a screen appearing, a request completing.
  • A field whose value is a user's own input, which is the case a privacy review exists for.
  • A project that answers the consent question with "no analytics", which must be a real answer rather than an absence.
  • An event already shipping in a build that predates the plan.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

An event MUST be declarable on the element that emits it, with a stable name.

Rationale

Beside its element for the same reason a state sits beside its screen: the alternative is a separate document that drifts from the interface, and drift is the failure this family exists to surface.

An event MUST be able to declare the fields it carries, and a declared field MUST carry a type.

Rationale

The typed payload is the whole reason a privacy reviewer can use this. "Carries the pair" is prose; a named field with a type is something a person can say yes or no to.

An event declaring no fields MUST be valid and MUST mean it carries none.

Rationale

The one place in this family where absence is a positive claim rather than "not recorded", and it is deliberate: an event with no payload is the safest kind and the shape must not push an author toward inventing a field to look complete.

A tracking plan MUST reference the question that gates it, and a plan referencing none MUST be reported.

Rationale

What makes authoring a plan early safe. The gate is a reference to an open question the register already models, so the mechanism exists and only the obligation is new.

Nothing in this vocabulary MUST cause an event to be emitted, and no check MUST read a declared event as evidence that one ships.

Rationale

The plan is a design decision and not an implementation. Reading a declaration as a shipped event would let a spec claim a privacy posture the build does not have — the exact overclaim this family refuses everywhere else.

A field MUST be able to record that its value derives from user input.

Rationale

The case a privacy review exists for. A currency pair is a choice from a fixed list; an amount is something a person typed, and the two are not the same risk even when both are numbers.

An answered consent question MUST be able to record that the answer is no analytics, and such an answer MUST NOT be read as the question being unanswered.

Rationale

The rule this family keeps restating. A project that decided not to collect anything has made a decision, and a shape that renders it identically to a project that never asked erases the decision.

An event SHOULD be declarable on a screen or a state rather than only on a control.

Rationale

Not everything that reports is a button. A screen appearing and a request completing are both events, and restricting the declaration to controls would push those into prose.

An event SHOULD be able to record that it already ships, so a plan authored after the fact SHOULD NOT read as a proposal.

A project MAY declare no events at all, and that MAY NOT be reported.

This vocabulary MAY NOT model the wire format, the transport or the destination of an event.

Rationale

Stated as a requirement rather than left to scope, because it is the direction this would grow in first. The plan records what the interface reports and why; how it travels belongs to whatever ships it.

Non-functional

Every declared event, field and gate MUST render with scripting disabled: 100% of the authored content readable with JavaScript off.

The shape check MUST be pure: at most 1 pass over the document, 0 network reads, and byte-identical findings across at least 3 runs.

Out of scope (deferred to other slices)

  • Checking that a build emits the events it declares, or only those. It needs to observe a running application, which is a different instrument entirely.
  • Rendering a tracking plan inside the design.
  • Importing a plan from a design tool that carries one.
  • The other category the annotation vocabulary names as having no accessibility analogue.

4 · Data model

An event, its fields, and the gate that holds the plan inert.

Entities

Event
Something the interface reports, with a stable name, declared on the element, state or screen that emits it. May declare no fields, which means it carries none.
Field
One item an event carries. Always typed. May record that its value derives from user input, which is the distinction a privacy review turns on.
Consent gate
A reference from the plan to the question that must be answered before anything ships. An answer of "no analytics" is an answer, not an absence.

The invariant that makes early authoring safe: a declaration is never evidence of an emission. Nothing here causes an event to ship, and no check may read a declared event as proof that one does — otherwise a spec could claim a privacy posture the build does not have.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For a feature declaring a tracking plan, a privacy reviewer can name every event and every field it would carry from the declaration alone, opening 0 other files.

Declared fields carrying no type number 0, or each produces exactly 1 finding.

Tracking plans with no consent gate number 0, or each produces exactly 1 finding.

Checks that read a declared event as evidence of a shipped one number 0, verified by inspection of every check this spec adds.

6 · Assumptions

A consent question is the right gate for every project. It is the right gate where a privacy regime applies and a formality where none does — and the cost of the formality is one reference, which is why this errs toward requiring it rather than detecting when it matters.

Declaring events early changes what gets built. Unverified, and the honest counter is that a plan nothing enforces may be ignored as easily as it is written. The gate is the hedge: an unanswered question is visible in a register that already surfaces unanswered questions.

None outstanding.
