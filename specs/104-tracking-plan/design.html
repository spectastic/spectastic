Design · 104-tracking-plan

What the interface reports

How we will build it.

Status Accepted Spec 104-tracking-plan Owner Brian Corbin · @briancorbinxyz Branch spec/visual-slice-095-098 Created 13 Aug 2026 Read time

An event declared on the element that emits it, a typed payload, and a consent gate that holds the plan inert. The rule that matters most is one this spec forbids: nothing may read a declared event as evidence that one ships, because that would let a spec claim a privacy posture the build does not have. One reading deliberately inverts the family's pattern — an event declaring no fields means it carries none, because an empty payload is the safest kind and the shape must not push an author into inventing one.

6 · Approach

An event element declarable on a control, a state or a screen, holding typed fields, plus a gate referencing the question that must be answered before anything ships. The reader is pure; the rule checks that fields carry types, that a plan references a gate, and that a gate's answer of no analytics is recorded as an answer rather than an absence.

Two rules invert what the rest of the family does, and both are deliberate. An event declaring no fields means it carries none — everywhere else absence means not recorded, but an empty payload is the safest kind and a shape that read it as unrecorded would push an author to invent a field to look complete. And FR-005 forbids any check from reading a declaration as evidence of an emission, which is the only thing standing between a design-time plan and a spec that claims a privacy posture the build does not have.

7 · Alternatives considered

Where an event is declared. Scored 1–5 on whether it can drift from the interface, whether a privacy reviewer can find every event, and how much new structure it needs.

A separate plan artifact1427

A separate artifact is how every analytics plan in the field is written, and it is the reason they are all out of date: nothing ties the plan to the interface, so the interface moves and the plan does not. The sidecar section is better and still lets the two drift within one file.

8 · Decisions

D-001 · An event is declared beside the element that emits it

Status
Accepted
Context
The survey behind this family called an analytics plan specified next to its element the most under-represented idea in the field. A separate plan is how it is normally done and is why those plans go stale.
Decision
On the control, state or screen that emits it — the same reasoning that puts a state beside its screen.
Consequences
+ The plan cannot drift from the interface, because moving the element moves the event. + A privacy reviewer reads one artifact. − Events are scattered across a sidecar rather than listed together, so "every event this product emits" needs a query rather than a page.

D-002 · No fields means no payload — the one place absence is a positive claim

Status
Accepted
Context
Everywhere else in this family an absent record means not recorded, and a sibling was corrected mid-proposal for reading absence as a claim. This inverts that deliberately.
Decision
An event declaring no fields carries none, and is valid.
Consequences
+ An empty payload is the safest event there is, and the shape must not push an author into inventing a field to look complete. + A reviewer scanning for payloads sees a genuinely short list. − The inversion is a second exception in a family that prizes one meaning for silence, so it is written down here to be found rather than rediscovered as an inconsistency.

D-003 · No check may read a declaration as an emission

Status
Accepted
Context
The plan is authored at design time, before anything is built. A check that treated a declared event as a shipped one would let a spec assert a privacy posture the build does not have — the overclaim this family refuses everywhere else.
Decision
Stated as FR-005 and asserted by test, in the shape 103 used for its own forbidden check.
Consequences
+ A declared plan never becomes evidence. − Nothing verifies that the build emits what the plan says, which is a real gap and is deferred rather than hidden.

11 · Complexity tracking

A second inversion of the family's silence rule. 102 required a record where the family otherwise does not; this reads an absence as a positive claim where the family otherwise does not. Both are written into their decisions rather than left to look like drift, because a reader who finds two exceptions and no reasoning will conclude the rule was never real.

12 · Open questions

None outstanding. The question this spec exists to close — whether a tracking plan belongs in a visual spec or beside one — is answered in favour of beside its element, on the same reasoning that puts a state beside its screen: a separate document drifts from the interface it describes.
