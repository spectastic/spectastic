Design · 099-visual-embedded-view

The visual view, inside the design

How we will build it.

Status Accepted Spec 099-visual-embedded-view Owner Brian Corbin · @briancorbinxyz Branch spec/visual-slice-095-098 Created 13 Aug 2026 Read time

Clone the contract view's placement and drift mechanism, and the verify view's derivation style — then diverge in the two places the contract view's own triage card says a clone would go wrong. One deterministic entry point both authoring paths reach, so a third inherits it for free; an absent view reported rather than permitted. The biggest risk is that the derived projection is the wrong shape for a reader, and nobody has yet read a visual view of either kind.

2 · Technical context

Language(s)
TypeScript, Node 20 target. Settled by the repository; not an open pick.
Frameworks
None new. parse5 via the schema package's parser for reading sidecars; Playwright for the browser pass.
Architecture
Ports-and-adapters at the existing seam — D-001. Pure derivation in the kernel behind a FileSystem port; two callers, one of them a thin CLI registrar.
Storage
None. The view is written into an artifact already on disk.
Testing
Tests-first per piece, plus a Playwright pass over the rendered view in both themes — D-006.
Coverage
Every new branch covered by a red-first test; a change never lowers coverage of what it touches. No universal project percentage.
Perf targets
NFR-003 — under 100 ms added to a design generation for a feature declaring up to 20 screens.
Constraints
The artifact content policy is deny-by-default: no frame, no data URI, no runtime fetch. Core returns HTML and never writes; the caller writes.

3 · Data model & contracts

No interface. This feature is a deterministic transform over files already in the project, invoked by a command; it exposes no endpoint, publishes no event, and its only consumers are the two callers named in D-001.

6 · Approach

A pure kernel function derives a model from the declared sidecars and renders it, and injects the result into the design's own <spec-visual> declaration — the placement the contract view already uses, with none of its verbatim projection. Reading a sidecar goes through the existing FileSystem port, so the interesting cases are testable without a fixture project per assertion; the function returns HTML and writes nothing, because core returns and the caller writes.

The part that is not a clone is the entry point. Both authoring paths call one deterministic command, so the guarantee is the command and not a step somebody may skip. Two checks sit beside the existing visual scans: one reports a view that no longer matches the files it projects, the other reports a declaration carrying no view at all — and the second is the divergence that makes this feature observable rather than quietly absent.

The thing nearly done instead was a materialise-on-validate autofix, which closes the gap everywhere at once and makes a read-only verb write to the working tree. Anyone running validate in continuous integration would find their checkout modified by a check.

7 · Alternatives considered

How materialisation reaches both authoring paths — the only decision here with genuinely competing answers. Scored 1–5 on whether the obligation is enforceable, whether a future third path inherits it, how much new surface it adds, and whether it surprises anyone.

OptionEnforceableInherited by a third pathNew surfaceNo surprisesTotal
A step in the command markdown115411
Materialise inside validate554115
One command both paths call — chosen553518

The markdown step loses on the two criteria that matter most, and loses to the requirement rather than to taste: FR-003 is must-tier, and P-8 excludes command markdown as a place a guarantee may live. Materialising inside validate scores well until the last column — a read-only check that writes to the working tree would modify a continuous-integration checkout, which is a worse defect than the one it fixes.

8 · Decisions

D-001 · One deterministic entry point, called by both authoring paths

Status
Accepted
Context
materialiseContractViews has exactly one caller, packages/core/src/commands/design.ts:102, inside the kernel verb. The canonical authoring path copies templates/design.html and interviews (commands/spectastic.design.md step 4), and 006 FR-009 makes that path canonical and the kernel path an alternate. So a design declaring a contract has never received a view.
Decision
A pure kernel function, exposed through one deterministic command. The kernel verb calls the function; the slash command calls the command as a step. Not a ninth verb — verify, contract and enforce are all command-only.
Consequences
+ The obligation is enforceable, which is what FR-003 requires and what P-8 demands of a must-tier side effect. + A third authoring path inherits it by calling one thing. + The same entry point retro-covers the contract view's gap, so 072/T-001 closes without a second one-off. − One more command in the surface, on a project that guards its verb count. − The slash command still has to call it, so the markdown is a step in the chain even though it is not where the guarantee lives.

D-002 · Derive a projection; never paste the sidecars

Status
Accepted
Context
The contract view projects an escaped, line-capped excerpt because a contract file is opaque text and an excerpt is the only projection available. The visual sidecars are this tool's own vocabulary and can be read. Measured on the worked example: screen 6.0 KB, grid 4.1 KB, token set 3.7 KB, against a 23 KB design.
Decision
Read the sidecars through the schema package's parser and render derived tables — screens and states, annotations, addressed contexts, token-set version. Escape every projected string, since a sidecar is untrusted from the generator's point of view.
Consequences
+ A reader gets an answer rather than three files' markup pasted into a fourth. + The artifact stays a readable size, which is P-5. − The projection has a shape somebody chose, and choosing wrongly is invisible until a reader complains. − It couples to the sidecar vocabularies, so a vocabulary change is a change here too — which is exactly what FR-012's seam exists to absorb.

D-003 · Report an absent view, unlike the contract view

Status
Accepted
Context
contractViewDriftFindings skips any declaration whose view is undefined (packages/core/src/commands/validate.ts:955), which is correct given 072 FR-008 makes rendering a MAY — and is why nobody noticed for months that the view never rendered.
Decision
A core scan beside the existing section gate: a declaration with no view is a finding, conditional on the declaration existing. A separate check from drift, because the reader's next action differs — generate for the first time, versus regenerate.
Consequences
+ The capability cannot be silently absent, which is the whole difference between this and its sibling. + Conditional on a declaration, so a project with no surface reports nothing. − One more scan on the project pass. − It will fire on every existing design the moment a declaration is added and the command has not been run, which is correct and will still read as noise the first time.

D-004 · A render is an attribute-bound reference in the grid's own grammar

Status
Accepted
Context
parseAxisContextPairs is exported from packages/schema/src/variant-grid.ts and already serves two callers. The content policy permits img-src 'self'; a data: URI in src= and an inline frame are error-severity violations.
Decision
<spec-render src= contexts=> nested in the state it depicts, with contexts in the axis=context grammar. Named, never embedded. Position carries the state and the attribute carries the cell.
Consequences
+ A reader meets one grammar rather than two. + No bytes copied, no drift surface, no size cost — the divergence from the text half, and the reason it is legitimate. − A render depicting two states has to be declared twice. − Nothing verifies that the image actually shows what it claims, and nothing can.

D-005 · Compare live, store no digest

Status
Accepted
Context
verify-view-stale re-derives expected identifiers from the sibling bundle and compares live, deliberately with no stored fingerprint. contractViewDriftFindings does the same, normalising line endings first.
Decision
Re-derive the projection and compare it to what the artifact carries. No digest anywhere.
Consequences
+ A fingerprint is a third thing to keep true and goes stale silently. + The comparison is exactly the generator's own output, so a green check means regeneration would be a no-op. − Every check re-reads the sidecars, which NFR-003 bounds rather than avoids.

D-006 · Tests first, and a browser pass on anything rendered

Status
Accepted
Context
Judgment, not a fact about the code. The evidence behind it is local: two stylesheet changes this week both carried cascade collisions that every structural assertion passed through, and both were caught only by reading computed style in a browser.
Decision
A red unit test before each piece, and a Playwright pass over the rendered view in both themes asserting computed content rather than presence.
Consequences
+ Catches the failure mode this area actually has. − Slower per piece, and the browser pass needs a served fixture.

9 · Project structure

New and changed paths only. Deterministic logic in the kernel, a thin registrar in the command layer — the convention this repository has paid for three times.

10 · Risks & mitigations

RiskLikelihoodImpactMitigation
The derived projection is the wrong shape for a reader — the one assumed fact this design rests onMMAccepted rather than mitigated; see the risk below. The seam in FR-012 means changing the shape does not reopen this spec.
The absent-view check fires across the estate the first time a declaration lands without the command having runHLCorrect behaviour rather than a defect, but it will read as noise. The finding names the command that fixes it, so the first encounter ends in one action.
The slash command's step is skipped, exactly as 072's wasMMWhat D-003 is for: the guarantee is not the step but the check that fires when the step did not happen.

D-002 chooses a derived projection over a verbatim one on an assumed fact — that a reader prefers a table to the sidecars' own markup. Nobody has read a visual view of either kind, so the shape is a guess.

Grounding row: "A derived table is what a reader wants" — status assumed, source "—".

Accepted rather than verified or spiked. Verifying means building both and showing them to someone, which costs more than changing the shape later would; and FR-012's seam is what makes changing it cheap. Recorded here because a must-tier decision resting on an assumed fact may not pass the grounding gate silently.

11 · Complexity tracking

Two places this design is more complex than the spec strictly requires.

A command where a function would do. The materialiser could have been a function the kernel verb calls, and the slash command told to run the verb. That is simpler and it fails the requirement: the slash command deliberately does not run the verb, and 006 FR-009 says that is canonical rather than a workaround. The extra surface buys an obligation that holds without anyone remembering it.

Two checks where one would do. Drift and absence could share a rule. They are separated because the reader's next action differs — regenerate, versus generate for the first time — and because merging them is how the sibling ended up unable to report absence at all.

12 · Open questions

None outstanding. Four decisions were anchored in the interview — the entry point, what reports an absent view, the render's shape, and the test posture — and the one fact this design takes on faith is carried as an accepted risk rather than left in the grounding table unremarked.
