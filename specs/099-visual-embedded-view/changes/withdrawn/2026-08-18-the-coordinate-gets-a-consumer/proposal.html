The coordinate gets a consumer

A screen address that nothing is obliged to use, and nothing does.

Status Withdrawn Change ID 2026-08-18-the-coordinate-gets-a-consumer Spec 099-visual-embedded-view Author Brian Corbin · @briancorbinxyz Created 18 Aug 2026 Targets 1 added Read time

095 defines an address for a screen, 093 obliges a design to refer to one, and this spec renders the view where such a reference would live — and no requirement anywhere obliges it to. The address has been shipped, exported and documented with, verifiably, zero callers. One added requirement giving it the consumer it was built for.

The coordinate gets a consumer

Withdrawn

1 · Intent

The mechanism landed in three parts and none of them is load-bearing. 093 FR-014 obliges a design to refer to each screen it declares and names no mechanism. 095 FR-013 defines the address and names no consumer. This spec renders the view and is obliged to do nothing with either.

The consequence is checkable and was checked: screenResourceUri is exported from packages/schema/src/project-shared.ts, carries a docstring explaining why a screen coordinate spans two segments, and has zero callers anywhere in the workspace — no core module, no command, no test.

The card that raised this is blunt about how it happened, and it was mine: 095/T-003 records that a scope risk accepted the view-linking half as a task rather than a delta, “which was the right instinct and the wrong conclusion, because shipping the consumer as a task rather than a requirement leaves the coordinate with no consumer at the level that matters”.

2 · Scope

In scope

  • Obliging the view to address each screen it projects by the coordinate 095 defines.
  • How a design refers to a screen. 093 FR-014 already obliges the reference and this proposal does not touch it — the gap being closed is the view's, not the design's.
  • Resolving a screen coordinate back to its declaration — following one rather than rendering one. The read path belongs with whatever serves these, not with the surface that emits them.

3 · Approach

One added requirement, on the spec that owns the view. The obligation is to address, not to resolve: the view emits the coordinate for each screen it projects, and nothing here follows one.

It says “the coordinate 095 defines” rather than restating the grammar. The two-segment shape, the choice of the declared name over the id, and the collision rule are all 095's, and a second statement of them in this spec is a second thing to keep in step — the failure mode a proposal earlier today created by copying a sibling spec's refusal into a place it could drift.

4 · Deltas

One <spec-delta>.

The view MUST address each screen it projects by the resource coordinate 095 FR-013 defines, so that a screen rendered here and the same screen named anywhere else are recognisably one thing.

Rationale

Without it the coordinate has no consumer at the level that matters. It is defined by one spec, referred to in prose by another, and emitted by nothing — which is the speculative-vocabulary failure 095 argued against, arrived at by 095 itself.

Addressing rather than resolving. The view emits the coordinate; following one is a read path that belongs with whatever serves these, and conflating the two would put a dereference inside a projection that FR-006 says must never be a source of truth.

The grammar stays 095's. Restating the two-segment shape here would create a second place for it to drift, which is exactly what a proposal earlier today had to undo after copying a sibling spec's refusal into a place it could diverge.

5 · Risk register

Populated by the adversarial risk pass. This proposal adds a must-tier requirement.

The view structurally cannot compose the coordinate, and the proposal budgets it as one line.

screenResourceUri(project, specId, name) — the view holds none of the three. ProjectedScreen carries id, states, annotations and renders; screen-naming.ts records the omission of name as deliberate, “keeps the view's model minimal”. And the coordinate keys on the declared name while the view's heading renders the id, so the address and the thing it labels would disagree.

Upheld, and it kills the delta rather than reshaping it. Verified by reading the model: three new inputs, one of them environmental, one of them a documented reversal of another module's decision. The requirement's own stated purpose — “recognisably one thing” — is defeated by the id/name split it never mentions.

Putting a config-derived string in the view makes a project rename mark every view stale.

visualViewDriftFindings re-runs the materialiser and compares whole documents — norm(regenerated) === norm(html) — at error severity. Every materialiser input becomes a drift trigger, and where project is unset it falls back to basename(cwd), so cloning into a differently-named directory would do it.

Upheld and verified in the source. The message would read that the screens changed when nothing changed, across every design at once. This estate has already re-keyed a project identity once, so it is not hypothetical.

Wrong topic group: it obliges minting addresses nothing can follow, which is the failure this family already recorded.

095/T-004 closed on “a coordinate that looks minted and is not”. And the premise is stale in the other direction: 093 FR-014/FR-015 now oblige a design to name screens by their declared identifier, which is a mechanism — §1 says 093 “names no mechanism”, inherited verbatim from a card written before that landed.

Upheld. The scope defers resolution while obliging emission, which multiplies exactly the condition 095/T-004 closed on.

The must-tier delta rests on a claim that is false in the form it is stated.

KB-0001@2026-07-25: a must-tier decision may not rest on an assumed fact, and verified means the source was opened. §1 says “zero callers anywhere — no core module, no command, no test”. True of the helper screenResourceUri; false of the coordinate — spectastic id --kind screen composes one via resourceUri, validates the name against the declared sidecar, and is tested.

Upheld, and this is the finding that decides the others. I verified the helper had no callers and reported it as the coordinate having no consumer. Those are different claims, and the second is the one the requirement rested on.
