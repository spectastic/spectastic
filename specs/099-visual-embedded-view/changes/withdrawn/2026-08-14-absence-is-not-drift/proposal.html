FR-013 puts render-presence into the view's content. FR-004 requires a view that no longer matches the files it projects to be reported. Absence is not drift

Withdrawn

1 · Intent

Three must-tier requirements in this spec are individually right and jointly contradictory. FR-009 says a render's absence "MUST NOT be reported as a finding or made to fail any gate." FR-013 says the view "MUST show, for each screen it projects, whether any render of that screen has been recorded." FR-004 says a view "that no longer matches the files it projects MUST be reported."

Compose them. Render-presence is view content, so removing a screen's last render changes what regeneration would produce; the drift check sees a difference and errors. A render — evidence a reader may delete freely, by this spec's own account — now fails a gate. 094 FR-005 states the same prohibition independently, so the estate asserts it twice and defeats it once.

The narrow question is what "the files it projects" means. A view projects screens; it mentions renders, and mentioning is what FR-013 exists to require. Read that way FR-004 never asked for this, and the implementation reaches further than the requirement — it compares the entire artifact (norm(regenerated) === norm(html)) because equality is a stronger and simpler property than diffing views, which is a good reason for the mechanism and not a licence for its scope. Read the other way, renders are among the projected files and FR-004 genuinely demands what FR-009 forbids.

So the ambiguity is the defect. It is not resolved by picking the reading that happens to match the code today; it is resolved by saying which one the spec means, in the requirement, where the next implementer will read it.

2 · Scope

In scope

  • Narrowing FR-004 so drift is measured against the screens a view projects, and render-presence is explicitly outside it.
  • Saying so in the requirement rather than in an implementation note, since the ambiguity is what produced the contradiction and a note does not bind the next implementer.

Out of scope

  • Touching FR-013 or FR-009. Both are right; only their composition through FR-004 was wrong, and amending either would trade a correct requirement for a mechanism's convenience. defer-to=never.
  • The whole-artifact comparison itself. Its stated property — "equality means regeneration would be a no-op" — survives the narrowing intact, as modulo render presence; the implementation change is a normalisation applied to both sides, not a new comparison strategy. defer-to=never.
  • 094 NFR-001's subject/purpose mismatch, found in the same grounding pass. A different spec and a different defect; the apply kernel folds same-spec deltas only, so it needs its own propose. defer-to=094-visual-sidecar-convention.

4 · Deltas

What changes: drift is measured against the screens a view projects. Render-presence is named as outside it, so FR-004 and FR-009 compose instead of colliding.

A view that no longer matches the screens it projects MUST be reported, compared against those screens as they are rather than a stored digest. Whether a render has been recorded MUST NOT be treated as drift, and a change to it alone MUST NOT produce a finding.

Rationale

A materialised copy is a drift problem by construction, which is what makes the check necessary rather than optional. Live comparison follows verify-view-stale: a stored fingerprint is a third thing to keep true, and it goes stale silently. Both halves are unchanged.

The second sentence exists because the first was ambiguous and the ambiguity was load-bearing. "The files it projects" can be read to include renders, and under that reading this requirement demands exactly what FR-009 forbids — deleting a render fails a gate — with FR-013 supplying the link by making render-presence view content. Three must-tier requirements, each right alone, composing into a contradiction.

A view projects screens. It mentions renders, which is FR-013's whole purpose, and a mention going out of date is not the failure this check exists to catch: the reader is not misled about a screen, and regenerating changes nothing about what the design says. Saying so here rather than in the check is the point — a requirement binds every implementation, a normalisation binds one function until someone tidies it away.
