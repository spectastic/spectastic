Specification · 051-knowledge-corpus

Knowledge corpus convention

A committed, greppable place for domain knowledge — so a domain fact can finally be something a reviewer can open.

Status Accepted Spec ID 051-knowledge-corpus Owner Brian Corbin · @briancorbinxyz Reviewers — Created 25 Jul 2026 Principlesv1.8.0 Smallest demoablespectastic init scaffolds a knowledge/ dir with a root registry and one pack (a SKILL.md-inlined map plus one reference document) that renders and validates. Read time

Spectastic already demands citations it cannot supply: every design-bearing fact must be recorded as verified / spike / assumed with a source, but every source it names is in-repo, so a domain fact can only ever be assumed. This spec defines the missing thing — a committed, in-repo knowledge/ corpus shaped as an open Agent Skills folder (SKILL.md + references/), with two-layer source ids (a pack-owned slug plus a project-assigned KB-NNNN, in a root registry), provenance frontmatter, a curated map, init scaffolding, and a small dogfooded corpus of spectastic's own domain. It is a convention, not a knowledge store: agentic search over committed files, no vector database, no runtime dependency. The corpus is strictly optional — with none present, every verb behaves exactly as today.

1 · Context

An authored spec is a function of the model, the context it holds, the user's inputs, and the sibling specs already in the repo. Three of those are ours to control; the model is not. When the domain is one the model knows well, house knowledge carries the spec; when it isn't — a different model, a narrower domain, a regulation published after the cutoff — quality drops silently and the burden of being the subject-matter expert falls back on the user. That is precisely the burden the tool exists to lift.

The gap is sharper than it looks because spectastic already has the entire grammar of grounding and nothing external to ground against: REQ-LIFECYCLE-006 requires every design-bearing fact to cite a source, a grounding profile axis ladders that discipline, and an ungrounded decision renders as a visible failure — but every source those rules name is in-repo. This spec supplies the external thing to cite. It is the first slice of the corpus family; the citation form, the gates, prompt injection, review, the adapter, licensing, and portability are its siblings.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · A committed, greppable corpus P1

As a project author, I want to keep domain knowledge in a committed knowledge/ directory with stable IDs so that a domain fact lives in the repo — greppable, diffable in review, and still openable next year at the version cited.

Acceptance: a pack under knowledge/<name>/ with a SKILL.md (its own curated slug map inlined) and a references/ document carrying a pack-internal slug (or a legacy KB-NNN ID) and provenance frontmatter passes spectastic validate with zero findings; once imported, its project-assigned KB-NNNN resolves from the root registry.

US2 · A working shape from init P2

As a project author, I want spectastic init to scaffold the corpus templates so that I start from a working shape and add a document without editing tool code.

Acceptance: a fresh init produces a knowledge/ scaffold — a root registry (knowledge/index.md) and a pack (a SKILL.md with its curated slug map inlined, a provenance-frontmatter example) — into which a user can drop a markdown document and have it validate.

US3 · A dogfooded reference corpus P3

As a maintainer, I want spectastic to grow a small knowledge/ corpus of its own domain in-repo so that the format is proven by being used, not just described.

Acceptance: the spectastic repo carries a small dogfood corpus (its own concepts — SDD, RFC 2119, grounding) that validates and is citable.

Edge cases

  • No knowledge/ directory at all — every verb runs exactly as today (see NFR-001); the corpus is optional, never assumed.
  • A pack with a SKILL.md but an empty references/ — valid but empty; nothing to cite yet.
  • Two documents sharing one pack-internal slug within the same pack, or two root-registry rows sharing one KB-NNNN — a uniqueness failure at whichever layer it occurs (IDs are contracts, P-3).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A corpus MUST live under a committed knowledge/ directory, one pack per subdirectory, each pack shaped as an Agent Skills folder — a required SKILL.md plus a references/ directory for the documents.

Rationale

Adopting the open format's directory convention rather than a spectastic-only layout is what makes the corpus portable across Claude Code, Codex, Cursor, Copilot, Gemini CLI, Kiro and the rest — the answer to the model-dependence problem that motivates the whole family.

Every corpus document MUST be identified at two layers. (1) A pack-internal slug — a short, path-independent id unique within its pack (e.g. 001-settlement-windows), authored and owned by the pack and carried in the document (its filename and frontmatter). This is the portable id the pack ships with; minting it MUST NOT require any knowledge of a consuming repo. (2) A project-assigned KB-NNNN — an opaque, repo-unique id (a KB- prefix and a zero-padded number, four-digit baseline, matching the existing \d{3,} shape) the consuming project assigns when it imports the reference and records only in the root registry (FR-009). A pack MUST NOT mint a KB-NNNN. A citation references the KB-NNNN independent of file path (052).

Rationale

A persistent identifier in the spirit of a DOI — and a DOI is composite for exactly this reason: a registration agency's prefix namespaces a publisher's suffix, so ids are globally unique without global coordination. The old flat KB-NNN asked the pack author to mint an id unique in a scope they do not control (the consuming repo), which both collides across independently-authored packs and contradicts 057. Splitting the id gives each layer the scope it can guarantee — the pack owns a pack-local slug, the project owns the repo-unique KB-NNNN. P-3 applied to the corpus, now at the right layer.

Every corpus document MUST carry provenance frontmatter: origin / origin-url, edition, license, converter, a content hash, and a status (e.g. illustrative-excerpt vs authoritative).

Rationale

Provenance is part of the record, not a nicety: the origin-url is the original and the committed markdown is the archived snapshot, so a cited source cannot silently change. The status field lets a hand-written illustrative excerpt declare it is not authoritative rule text.

Each pack MUST carry a curated map of its references — in the llms.txt spirit — inlined in its SKILL.md, listing each reference's pack-internal slug, title, one-line description, current edition, and path, so an agent has a cheap map before it reads anything. The map MUST be over the pack's own slugs and MUST NOT carry a KB-NNNN (the project assigns those, FR-009), so the pack remains a clean, self-describing, publishable unit. A separate per-pack index.md is retired.

Rationale

The pack is one portable, self-describing unit; its map belongs in the discovery file the agent already reads, not a sibling file that can drift from it. Keeping the map over slugs — never KB- ids — is what keeps the pack free of project state, so the same unedited pack works as a plain Agent Skill and, dropped into a spectastic repo, is citable via the harness binding (057).

Any corpus text entering an AI-verb prompt MUST pass through the existing fenceArtifactText() boundary; the sanitiser MUST NOT be forked.

Rationale

A third-party document is a strictly worse injection surface than an in-repo artifact, and P-11 ("artifacts are data, not instructions") already governs it. The boundary already exists; ingestion reuses it.

spectastic init SHOULD scaffold the corpus templates — a SKILL.md, an index, and a provenance-frontmatter example — as it already ships the spec and plan templates.

The spectastic repo SHOULD carry a small dogfooded knowledge/ corpus of its own domain, proving the format by use rather than by prose.

Agents MAY discover and read the corpus by agentic search (grep / glob) over the committed files; the convention MUST NOT require a vector index or a runtime server to be usable.

Rationale

The tools that tried vector search are walking it back (staleness, an infra dependency, an opaque step). For a corpus that lives in the repo and changes with it, "the codebase is the index" transfers directly. Retrieval at scale is a separate, threshold-gated slice (059).

A consuming project that imports corpus references MUST record them in a single root registry at knowledge/index.md. Each row MUST carry a project-assigned KB-NNNN and the reference it names: source marketplace, plugin (pack), pack-internal slug, title, current edition, and path. The KB-NNNN MUST be repo-unique and opaque — a KB- prefix and a zero-padded number (four-digit baseline), with no embedded pack or reference name — the stable id a citation resolves against (052). This requirement fixes the registry's existence, location, and columns, and the opaque-repo-unique KB-NNNN contract. How ids are assigned and rows maintained across imports — the (marketplace, plugin, slug) re-import key, monotonic never-reused assignment, supersede-by-append, orphan-flagging — is the ingester's contract (deferred, TBD-corpus-root-index-ingester), not this requirement. A project with no imported references owes no registry.

Rationale

The KB-NNNN→reference mapping must live where the project owns it, and marketplace.json is the publisher's manifest with no per-reference slot — so the registry is a consumer-side artifact layered on top of the marketplace's (name, version) coordinate, not a field inside it. A single root file is the one deterministic place to resolve a citation and to answer "what has this project ingested." Opaqueness follows the persistent-identifier rule so a pack or reference rename never rots a citation. The requirement is scoped to the static shape so it is satisfiable the moment it lands — the assignment behaviour that only the ingester can perform is stated as its contract, not demanded of a repo that has no import tool yet.

Non-functional

Graceful absence. With no knowledge/ directory present, every verb MUST behave exactly as today — no new output beyond a single discreet one-time hint that a corpus could be added. The corpus is strictly optional.

Rationale

Spectastic must work with or without the knowledge base. This is the load-bearing guarantee that keeps the corpus an addition, never a tax on projects that don't want one.

The convention MUST be model- and agent-agnostic — a corpus in this shape MUST be usable on any skills-compatible agent, not only the one that authored it.

Out of scope (deferred to other slices)

  • How a decision cites a corpus source (KB-NNN@edition) and the supersede-by-append rule.
  • The validate rules that a cited ID resolves and that a pinned edition is current.
  • Core injecting the corpus index + grounding directive into the AI-verb prompt.
  • Generating frontmatter + index from an existing corpus shape.
  • The spectastic-agnostic pack shape and marketplace distribution.
  • Redistribution policy for third-party material committed in-repo.
  • Retrieval at scale (embeddings + BM25 + reranking) above the ~200k-token threshold.
  • Shipping a PDF converter (Docling / MarkItDown / Marker) — documented as a recommendation, never a spectastic dependency; the kernel stays Node-only.

4 · Data model

The entities this feature owns.

Entities

Corpus pack
A subdirectory of knowledge/. Fields: a name, a SKILL.md (name + description discovery layer), a references/ directory of documents. Portable as an Agent Skill.
Corpus document
A markdown file under references/. Fields: a pack-internal slug (or, pre-migration, a legacy KB-NNN ID), body text, and provenance frontmatter.
Provenance frontmatter
origin, origin-url, edition, license, converter, content hash, status.
Slug-map entry
One row in a pack's own SKILL.md-inlined curated map: slug → title, one-line description, current edition, path. Pack-owned, portable, never a KB- id.
Registry entry
One row in the project's root knowledge/index.md (FR-009): an opaque, project-assigned KB-NNNN → the marketplace, plugin, and slug it names, plus title, edition, and path.

Invariant: a pack-internal slug is unique within its own pack; a project-assigned KB-NNNN is unique across the repo — and, once assigned, is never reused, a dropped reference keeps its id retired, exactly as spec IDs do. The pack's slug map is the portable half of the picture; the project's root registry is the repo-unique half; the document frontmatter is the source of truth for provenance either way.

5 · Success criteria

Technology-agnostic, measurable outcomes.

A committed corpus pack whose SKILL.md carries a curated map and whose references/ holds at least one slug-named document passes spectastic validate with zero findings; and for a project that has imported references, every KB-NNNN in the root knowledge/index.md registry resolves to a file on disk.

A fresh spectastic init produces a knowledge/ scaffold into which a user adds a markdown document — with no edit to tool code — and that document validates.

With no corpus present, a full verb run produces output identical to today apart from the single one-time hint (NFR-001).

6 · Assumptions

Most curated corpora fall under the ~200k-token / ~500-page threshold, so agentic search suffices and no retrieval index is needed for the common case; the exception is handled by 059.

Document conversion (PDF → markdown) happens outside spectastic; the tool consumes whatever markdown lands in the corpus and never owns the converter.

The Agent Skills references/ convention remains an open, widely-honoured format; a corpus in this shape stays portable across skills-compatible agents.
