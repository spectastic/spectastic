Change proposal · 051-knowledge-corpus

Two-layer corpus identity

Split the corpus id into the layer the pack can own and the layer only the project can — the DOI fix for the collision and the 051↔057 contradiction.

Status Applied Change ID 2026-07-26-two-layer-corpus-identity Spec 051-knowledge-corpus Author Brian Corbin · @briancorbinxyz Created 26 Jul 2026 Targets 4 requirements Read time

The corpus id model is flat — a pack author writes KB-001 into their own index and it is asked to be "unique within the repo" (FR-002). But a pack is authored and published independently (057), so it cannot know what else shares a downstream repo — both shipped packs collide on KB-001, and the resolver picks by array order. This amendment splits identity into two layers, each in the scope it can guarantee (the DOI model, per the considerations brief): a pack-internal slug the pack owns (MODIFY FR-002), a pack map inlined in SKILL.md over those slugs (MODIFY FR-004), and a new project-owned root knowledge/index.md registry that assigns each reference an opaque, repo-unique KB-NNNN (ADD FR-009). This fixes the convention; the corpus import command that maintains the registry, the citation grammar, and the migration are the sequenced follow-ons.

Two-layer corpus identity

Applied

1 · Intent

After real use of the corpus family (051–059), the id model breaks in two ways a code read confirms: both shipped packs assign KB-001, and resolveCitation returns the first pack whose id matches, so a citation resolves by array order; and FR-002's "unique within the repo" cannot coexist with 057's "independently authored and published," because an independent pack can't guarantee uniqueness in a repo it doesn't know. Both trace to one conflation — the pack author is asked to mint an id unique in a scope they don't control.

The fix, grounded in the considerations brief, is the DOI shape: a registration agency's prefix namespaces a publisher's suffix, giving uniqueness without global coordination. This amendment lands that split at the convention layer — the id contract, where the pack's map lives, and the existence and shape of the project's registry. The tooling that maintains the registry (the ingester), the citation grammar, and the data migration are deliberately separate, sequenced changes.

2 · Scope

In scope

  • MODIFY FR-002 — a corpus document carries a pack-internal slug (unique within its pack, authored by the pack) and the project assigns a repo-unique opaque KB-NNNN at import.
  • MODIFY FR-004 — the pack's curated map inlines into SKILL.md over its slugs; the per-pack index.md is retired.
  • ADD FR-009 — a single root knowledge/index.md registry, the project's record mapping each KB-NNNN to its (marketplace, plugin, slug, title, edition, path).
  • MODIFY SC-001 — re-word the must-tier acceptance from the retired per-pack-index model to the two-layer / root-registry world.

Out of scope

  • The spectastic corpus import command that assigns KB-NNNN and maintains the registry — marketplace-anchored, supersede-by-append, orphan-flagging. This amendment fixes the registry's shape; that spec builds the tool that writes it.
  • The citation grammar resolving against the root registry, the rendered human label, and the "@edition pins the document edition" clause — 052's contract.
  • Re-authoring the shipped packs, the external example repos, and the live citations onto the two-layer model.
  • A per-marketplace registry packaging — this amendment mandates a single root file (the marketplace column already records per-row provenance); splitting it is a future option only if a repo imports from many sources.

3 · Approach

The split follows a single principle: give each id layer the scope it can actually guarantee. A pack owns a slug unique only within itself — no repo knowledge required, so the pack stays a clean, independently-publishable Agent Skill (057). The consuming project owns the KB-NNNN — opaque, repo-unique, assigned at import and recorded only in its own root registry — so repo-uniqueness holds where it's controllable. A citation names the KB-NNNN (052's job), which resolves deterministically against the one registry, ending the array-order collision.

This proposal is scoped to the convention, matching how 051 already owns the corpus layout while 056 owns the adapter tooling: it fixes the id contract (FR-002), where the pack map lives (FR-004), and the registry's existence, location, columns, and KB-NNNN contract (FR-009). How the registry is populated — the assignment algorithm, the marketplace anchor, supersede-by-append, orphan-flagging — is the ingester spec, so this amendment adds no command and no assignment logic, only the artifacts they will operate on.

4 · Deltas

Two MODIFY + one ADD, all within 051's FR-* topic. Each embeds its post-state.

What changes: the flat repo-unique KB-NNN becomes two ids at two layers — a pack-owned slug and a project-assigned KB-NNNN — resolving the 051↔057 contradiction.

Every corpus document MUST be identified at two layers. (1) A pack-internal slug — a short, path-independent id unique within its pack (e.g. 001-settlement-windows), authored and owned by the pack and carried in the document (its filename and frontmatter). This is the portable id the pack ships with; minting it MUST NOT require any knowledge of a consuming repo. (2) A project-assigned KB-NNNN — an opaque, repo-unique id (a KB- prefix and a zero-padded number, four-digit baseline, matching the existing \d{3,} shape) the consuming project assigns when it imports the reference and records only in the root registry (FR-009). A pack MUST NOT mint a KB-NNNN. A citation references the KB-NNNN independent of file path (052).

Rationale

A persistent identifier in the spirit of a DOI — and a DOI is composite for exactly this reason: a registration agency's prefix namespaces a publisher's suffix, so ids are globally unique without global coordination. The old flat KB-NNN asked the pack author to mint an id unique in a scope they do not control (the consuming repo), which both collides across independently-authored packs and contradicts 057. Splitting the id gives each layer the scope it can guarantee — the pack owns a pack-local slug, the project owns the repo-unique KB-NNNN. P-3 applied to the corpus, now at the right layer.

What changes: the curated map moves from a per-pack index.md into the pack's SKILL.md, over slugs (no KB- ids — those are the project's, per FR-009).

Each pack MUST carry a curated map of its references — in the llms.txt spirit — inlined in its SKILL.md, listing each reference's pack-internal slug, title, one-line description, current edition, and path, so an agent has a cheap map before it reads anything. The map MUST be over the pack's own slugs and MUST NOT carry a KB-NNNN (the project assigns those, FR-009), so the pack remains a clean, self-describing, publishable unit. A separate per-pack index.md is retired.

Rationale

The pack is one portable, self-describing unit; its map belongs in the discovery file the agent already reads, not a sibling file that can drift from it. Keeping the map over slugs — never KB- ids — is what keeps the pack free of project state, so the same unedited pack works as a plain Agent Skill and, dropped into a spectastic repo, is citable via the harness binding (057).

What changes: the must-tier acceptance still describes the retired model (a per-pack index + KB-NNN documents); re-word it to the two-layer world so the criterion matches the FRs it verifies.

A committed corpus pack whose SKILL.md carries a curated map and whose references/ holds at least one slug-named document passes spectastic validate with zero findings; and for a project that has imported references, every KB-NNNN in the root knowledge/index.md registry resolves to a file on disk.

A consuming project that imports corpus references MUST record them in a single root registry at knowledge/index.md. Each row MUST carry a project-assigned KB-NNNN and the reference it names: source marketplace, plugin (pack), pack-internal slug, title, current edition, and path. The KB-NNNN MUST be repo-unique and opaque — a KB- prefix and a zero-padded number (four-digit baseline), with no embedded pack or reference name — the stable id a citation resolves against (052). This requirement fixes the registry's existence, location, and columns, and the opaque-repo-unique KB-NNNN contract. How ids are assigned and rows maintained across imports — the (marketplace, plugin, slug) re-import key, monotonic never-reused assignment, supersede-by-append, orphan-flagging — is the ingester's contract (deferred, TBD-corpus-root-index-ingester), not this requirement. A project with no imported references owes no registry.

Rationale

The KB-NNNN→reference mapping must live where the project owns it, and marketplace.json is the publisher's manifest with no per-reference slot — so the registry is a consumer-side artifact layered on top of the marketplace's (name, version) coordinate, not a field inside it. A single root file is the one deterministic place to resolve a citation and to answer "what has this project ingested." Opaqueness follows the persistent-identifier rule so a pack or reference rename never rots a citation. The requirement is scoped to the static shape so it is satisfiable the moment it lands — the assignment behaviour that only the ingester can perform is stated as its contract, not demanded of a repo that has no import tool yet.
