Contract promotion

Ordered, parallelizable work. Tests precede implementation. Drive through with /spectastic.implement — one task per invocation.

Status Accepted Spec 071-contract-promotion Plan plan Branch main Created 01 Aug 2026 Read time

22 tasks across five phases. Requires 070's reader. The first test written is the one that catches the design's headline trap — comparing the wrong pair and refusing every legitimate promotion. Tests for a story MUST be written and failing before its implementation tasks start.

1 · Execution strategy

US1 alone — a landing change writes its contract — is demoable, but shipping it without US3's refusal risks clobbering a moved destination. Treat US1+US3 as the real minimum.

Setup → Foundational → US1 → US2 → US3 → Polish. Recommended. All three stories touch the planner, so sequencing avoids collisions in one function.

Poor fit — planner and executor are two halves of one flow. The dry-run (T-902) is the only genuinely detachable piece.

2 · Phase 1 — Setup

Scaffold the promotion fixture projects — a change with one proposed contract, one with three, one with none, plus baseline states covering match, divergence and no-predecessor. packages/core/test/fixtures/promotion/
Define the plan types — PromotionPlan and PromotionConflict, so planner and executor tests can be written against a stable shape. packages/core/src/contracts/types.ts

3 · Phase 2 — Foundational

Baseline capture at authoring time. Nothing downstream can detect a conflict without it, so it lands before the planner.

Tests (write & fail first)

Write the failing baseline-capture tests — assert authoring a proposal that carries a contract copies the current effective file to the baseline location, and that no baseline file is written when no effective contract exists, since absence is the meaningful signal per D-005. packages/core/test/promote.baseline.test.ts

Implementation

Capture the baseline at propose time — write the verbatim copy to specs/<id>/contracts/.baseline/<name>. packages/core/src/commands/propose.ts

Mechanism for FR-003; the state the whole conflict check depends on.

4 · Phase 3a — US1 · Landing a change promotes its contract

Tests (write & fail first)

Write the comparison-direction test first — the design's headline risk. A proposal whose incoming content differs from the effective file, but whose baseline matches it, must promote; getting the comparison backwards would refuse every legitimate promotion. packages/core/test/promote.plan.test.ts
Write the failing planner tests — assert the plan lists one write and one archive per proposed contract, and is empty for a change carrying none. packages/core/test/promote.plan.test.ts
Write the failing executor tests — assert the effective file receives the proposed content and the proposal is archived beside its proposal.html. packages/core/test/promote.execute.test.ts

Implementation

Implement planPromotion() — read declarations via 070's reader, pair each with its proposed file and baseline, and return writes, archives and conflicts without touching disk. packages/core/src/contracts/promote.ts
Implement executePromotion() — write the effective contract first, archive second, per the fail-safe ordering apply's own archive step already documents. packages/core/src/contracts/promote.ts
Call promotion from the apply kernel — immediately before the existing proposal-archive step. packages/core/src/commands/apply.ts

Closes FR-001, FR-002, FR-006; contributes to SC-001.

5 · Phase 3b — US2 · Exactly one live copy afterwards

Tests (write & fail first)

Write the failing single-copy tests — assert exactly 1 readable contract for the interface after landing, and that nothing readable remains at the proposed location. packages/core/test/promote.execute.test.ts
Write the failing idempotence tests — assert a second run after success changes 0 files and exits zero, per FR-005. packages/core/test/promote.execute.test.ts
Write the failing atomicity test — a three-contract change where the third conflicts must write 0 files and archive 0, per FR-004. packages/core/test/promote.plan.test.ts

Implementation

Archive the proposal and its baseline together — move both under the applied change's archive folder so provenance travels with the proposal that carried it. packages/core/src/contracts/promote.ts

Closes FR-004, FR-005; contributes to SC-001 and SC-003.

6 · Phase 3c — US3 · A conflicting promotion refuses

Tests (write & fail first)

Write the failing conflict tests — assert a moved destination exits non-zero, writes 0 files, archives 0, and leaves the working tree byte-identical to its pre-run state. packages/core/test/promote.plan.test.ts
Write the failing no-predecessor tests — assert no baseline plus no effective file promotes, while no baseline plus an existing effective file refuses, per D-005. packages/core/test/promote.plan.test.ts

Implementation

Implement conflict detection — exact byte comparison of baseline against the current effective file, with no normalisation, per D-006. packages/core/src/contracts/promote.ts
Write the refusal message — name the conflicting path and, where determinable, the spec whose landed change moved it. packages/core/src/contracts/promote.ts

Closes FR-003, FR-007; contributes to SC-002.

7 · Phase 4 — Polish

Add the end-to-end apply integration test — drive a real change through the CLI and assert the contract lands, the proposal archives, and a re-run is a no-op. packages/cli/test/apply.contracts.integration.test.ts
Confirm the existing estate is unaffected — no spec carries a proposed contract, so apply must write 0 files and print nothing about contracts, per SC-004.
Wire the dry-run flag — render the plan instead of executing it, changing 0 files, per FR-008. packages/cli/src/commands/apply.ts
Check the timing budget — confirm promotion adds under 200 ms for a change carrying 10 contracts, per NFR-002.
