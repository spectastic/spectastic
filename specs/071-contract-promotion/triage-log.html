Cards

A first design has no way to promote the contract it declares

Spec upstream

Debugging a contract-resolve error with no way to clear it, root cause was that promotion is reachable only through apply, which requires a change-proposal slug a greenfield spec does not have; fixed by giving promotion an entry point of its own; regeneration fails, because nothing in the spec says which command performs it.

Expected
A design authors a proposed contract at specs/<id>/contracts/, declares the effective path, and promotion copies it there — the flow the design command documents in its own words.
Actual
There is no promotion verb. planPromotion is called from exactly one place, packages/cli/src/commands/apply.ts, behind --dry-run, and the real promotion runs inside apply <spec-id> <date>-<slug>. A first design has no proposal, so there is no slug to pass. Meanwhile contract-resolve errors at the declared effective path — correctly — and the only way to clear it is to copy the file by hand, which is what a real downstream project was reduced to doing.
Diagnosis
Promotion was built as a side effect of applying a change, which is right for a contract that already exists and is being amended. The first contract a spec ever declares does not arrive that way: it is authored during design, before any proposal exists. So the lifecycle has a documented step with no command behind it, and the gate that would catch the omission fires on the author rather than on the tool. The same shape as this spec's sibling 072/T-001 — a capability specified, built in the kernel, and unreachable from the path people actually take.
Fix
specs/071-contract-promotion/spec.html — a propose. Promotion needs an entry point that does not require a change proposal, and the spec should say which command performs it rather than leaving it to be inferred from where the kernel happens to be called.
Deep dive — cross-spec

Touches 070, which owns the proposed-versus-effective distinction, and the design command's own instructions, which describe promotion as though a user can invoke it. Nothing here is wrong about the destination — the two-location model is sound and the resolve rule is right to reject a path under specs/. Only the transition between them is unreachable.
