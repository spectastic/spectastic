Design · 071-contract-promotion

Contract promotion

How we will build it.

Status Accepted Spec 071-contract-promotion Owner Brian Corbin · @briancorbinxyz Branch main Created 01 Aug 2026 Read time

Promotion is a side effect of apply, which already folds a proposal and archives it — contracts ride the same gesture. The one genuinely new piece of state is the baseline: a verbatim copy of the effective contract, written beside the proposal when it is authored, so landing can ask "has the destination moved since?" rather than the useless "does it differ from what I am about to write?". Atomicity comes from a plan-then-execute split — resolve every contract, refuse on any conflict, and only then touch the disk — which also gives the dry-run for free, since a dry-run is the plan printed instead of executed.

3 · Data model & contracts

Promotion moves files between the two locations 070 defines. The one genuinely new piece of state is the baseline; everything else is derived at plan time and discarded.

Conceptual entityPhysical shapeNotes
Promotion baseline specs/<id>/contracts/.baseline/<name> — a verbatim byte copy Written when the proposal is authored, not when it lands. An absent baseline file means "no effective contract existed at authoring time", which is a distinct and legal state from an empty one.
Archived proposal specs/<id>/changes/archive/<slug>/contracts/<name> Co-located with the archived proposal.html that carried it, so provenance travels together. Never readable as a live contract because it is not at any declared effective path.
Promotion plan Derived, in memory — { writes[], archives[], conflicts[] } Computed in full before any write. Non-empty conflicts aborts everything (FR-004); printed instead of executed for the dry-run (FR-008).

No interface. Promotion is a filesystem side effect inside an existing command — no endpoint, no event, no wire surface. The contracts it moves belong to the projects using spectastic, not to spectastic.

5 · Approach

Promotion hooks into the apply kernel, which already resolves a change folder, folds it, and archives it. Two new core functions sit in front of the existing archive step: planPromotion() reads the design's declarations (via 070's reader), pairs each with its proposed file and its baseline, and returns a PromotionPlan of writes, archives and conflicts; executePromotion() applies that plan. A conflict is detected by comparing the current effective file against the baseline copy — not against the incoming content, which would flag every legitimate promotion.

Atomicity falls out of the split: the planner touches nothing, so a conflict on the tenth contract aborts before the first write. Idempotence falls out of the same structure — after a successful promotion the proposal is archived, so the planner finds nothing to do and returns an empty plan, which executes as a no-op and exits zero. The dry-run is the plan rendered rather than executed, so it cannot drift from what a real run would do. A change with no proposed contract produces an empty plan and stays completely silent, satisfying FR-006 by construction rather than by a guard.

6 · Alternatives considered

The load-bearing choice is how the baseline is recorded, since FR-003 is impossible without it. Scored 1–5, higher is better.

OptionNo new primitiveRefusal qualityPortabilityTotal
A sha-256 digest in the proposal1258
Resolve via git at the base commit4419
A verbatim baseline copy beside the proposal — chosen55515

The digest is the tempting answer — it is tiny and answers exactly the yes/no question asked. It loses on two counts: a grep confirms createHash appears nowhere in this codebase, so it introduces cryptography as a new primitive for one boolean; and a digest can only say that the destination moved, never show what moved, which makes FR-007's "name the conflicting path" the most it can ever offer. Git scores well on refusal quality but couples a filesystem-only guarantee to a VCS, breaking a plain checkout or an exported tarball.

7 · Decisions

D-001 · The baseline is a verbatim copy at contracts/.baseline/<name>

Status
Accepted
Context
FR-003 needs to know what the effective contract looked like when the proposal was authored. A grep for createHash over packages/*/src returns zero matches, so a digest would be a new codebase primitive.
Decision drivers
No new primitive · quality of the refusal message · portability without git
Considered options
  • A sha-256 digest in the proposal — + tiny, sufficient for a boolean. − Introduces crypto for one comparison; the refusal can never show what changed.
  • Resolve via git at the base commit — + no stored state. − Couples promotion to git; breaks in a plain checkout or tarball.
  • A verbatim baseline copy — chosen — + no new primitive, and the refusal can show the divergence. − Duplicates bytes on disk.
Decision
When a proposal carrying a contract is authored, copy the current effective file to specs/<id>/contracts/.baseline/<name>. Absence of that file records "no effective contract existed", distinct from an empty one.
Consequences
+ Comparison is a byte equality with no algorithm choice. + The refusal can name exactly what diverged. − Contract bytes are duplicated while a proposal is in flight; contracts are small and the copy is archived on landing.

D-002 · Promotion is hosted by the apply kernel

Status
Accepted
Context
FR-001 says "when a change lands". packages/core/src/commands/apply.ts:41,187-207 shows apply is that moment and already performs a structurally identical move-and-archive. P-8 requires a mandatory side effect to have a deterministic owner rather than living in command markdown.
Decision
Promotion runs inside applyCommand, immediately before the existing proposal-archive step. No new verb.
Consequences
+ Cannot be skipped by a model declining to run a documented step. + Reuses the injected filesystem port and the existing temp-dir test harness. − Apply grows a responsibility; bounded by keeping the planner and executor as separate exported functions rather than inlined logic.

D-003 · Plan-then-execute delivers atomicity, idempotence and the dry-run together

Status
Accepted
Context
FR-004 demands all-or-nothing across a change's contracts, FR-005 idempotence, FR-008 a dry-run. Apply's own comment at apply.ts:187-194 already establishes ordering-to-fail-safe as the house technique.
Decision
A pure planPromotion() that reads but never writes, returning writes, archives and conflicts; a separate executePromotion(). A non-empty conflict list aborts before any write. The dry-run prints the plan.
Consequences
+ One structure satisfies three requirements. + The dry-run cannot drift from the real run because it is the same plan. + Idempotence is emergent: after success the proposal is archived, so the plan is empty. − True crash-mid-write atomicity is not achievable without a journal; bounded and recorded in §10.

D-004 · The archived proposal travels with its change, not with the contracts directory

Status
Accepted
Context
FR-002 requires no readable contract remain at the proposed location. Apply already moves the change folder to specs/<id>/changes/archive/<slug>/, which is where the proposal that carried the contract ends up.
Decision
Archive to specs/<id>/changes/archive/<slug>/contracts/<name>, alongside the archived proposal.html, carrying the baseline with it.
Consequences
+ Provenance is co-located: the proposal, its contract and the baseline it was authored against sit together. + specs/<id>/contracts/ is left genuinely empty, so "no readable contract remains" is literally true. − A reader looking for a spec's contract history must open the archive rather than one directory.

D-005 · A missing baseline means "no predecessor", and promotion proceeds

Status
Accepted
Context
The first contract for an interface has no effective file to copy at authoring time. Treating that as a conflict would make it impossible to land a project's first contract at all — the same first-contract trap 074 resolved in its own register.
Decision
No baseline file recorded and no effective file present → promote. No baseline recorded but an effective file now exists → refuse, since something else created it.
Consequences
+ A project's first contract lands cleanly. + The refusal still catches a genuine race where a sibling change created the file first. − Relies on the baseline being written at authoring time; if it is missing for any other reason the check degrades to the second branch and refuses, which fails closed.

D-006 · Comparison is exact bytes, with no normalisation

Status
Accepted
Context
A conflict check could normalise line endings, trailing whitespace, or YAML key order before comparing. Each normalisation is a judgment about what "unchanged" means, and every one of them can hide a real edit. Pure judgment, no external fact.
Decision
Byte equality. A whitespace-only change to the effective contract counts as a conflict and refuses.
Consequences
+ No semantics to get wrong, and the check can never claim two differing files are the same. + Deterministic across platforms. − A reformatting of the effective file forces a re-authored proposal; the correct response, since a reformat means someone else touched the destination.

9 · Risks & mitigations

RiskLikelihoodImpactMitigation
The conflict comparison is written the wrong way round — incoming-versus-current instead of baseline-versus-current — making every legitimate promotion refuseMHThe spec's own data-model section names this trap explicitly. A fixture where the incoming content differs from the effective file but the baseline matches must promote; it is the first test written.
A crash between the write and the archive leaves a half-promoted stateLMOrdering follows apply's existing fail-safe precedent: write the effective contract first, archive second, so a crash leaves the proposal in place and a re-run is a clean retry. Recorded as a bounded ceiling in §10.
The baseline is never written because the proposal was authored by hand rather than through the verbMMD-005 fails closed — a missing baseline with an existing effective file refuses rather than clobbering. The author re-authors through the verb.

10 · Complexity tracking

P-12 exception — this slice writes outside specs/. Every lifecycle verb until now has confined its writes to the spec tree and its own artifacts. Promotion, by definition, writes to a project path the design declares. The capability is real and is justified by the spec's whole purpose, but it is bounded three ways: the destination is not chosen by the tool but declared in a reviewed artifact; it inherits 070's D-004 containment, so it cannot escape the project directory; and the dry-run makes the full write set inspectable before anything happens. Logged here rather than waved through, per the principles-check requirement that an exception carry a justification.

Atomicity is plan-level, not crash-level. FR-004 is satisfied against conflicts — no partial write occurs because of a detected conflict. It is not satisfied against a process kill between two writes; that would need a journal or a staging directory with an atomic rename, which is disproportionate for a handful of small files. The mitigation is ordering: the fail-safe sequence leaves a retryable state, exactly as apply's own archive step already does.

Two proposals against one interface refuse rather than merge. The spec puts merging out of scope, and this design does not smuggle it back in. The second proposal to land sees a moved destination and refuses — correct, because a schema merge is not a text merge and pretending otherwise would silently produce an invalid contract.
