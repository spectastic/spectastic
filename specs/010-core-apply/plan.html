Implementation plan · 010-core-apply

Core apply — implementation plan

How applyCommand ships — one entry point, two modes, byte-stable HTML mutation, atomic folder moves, all IO through ctx.fs.

Status Accepted Spec 010-core-apply Owner Brian Corbin · @briancorbinxyz Branch main (squashed-snapshot pattern) Created 16 Jun 2026 Read time

Extract /spectastic.apply into @spectastic/core/commands/apply per 006's kernel contract. Both modes share one entry: discriminated-union input to applyCommand. HTML mutation is targeted string replacement on stable anchors — no parse5 round-trip, no reformatting. Mutate first, atomic ctx.fs.rename last. Risk-register gate is a pure regex scan. No AI usage. Single PR; ships as v0.1.0-pre.12.

3 · Approach

Three moves, one PR. One: implement applyCommand at packages/core/src/commands/apply.ts with a discriminated-union input (ApplyInput | WithdrawInput) and shared helpers (gate, mutation, changelog append, folder move). Two: add rename to the FileSystem interface (impl in nodeFs via fs.promises.rename, mirrored in the test stub). Three: add the spectastic apply CLI subcommand at packages/cli/src/commands/apply.ts with commander flag parsing, translating between flags and the discriminated union. Update commands/spectastic.apply.md with the MAY-Bash note per FR-013.

The architecturally-interesting piece is HTML mutation. Targeted string replacement wins over parse5 round-trip: spec.html is author-curated and a round-trip would re-pretty-print everything, producing massive diffs and violating FR-010. The strategy locates each target by anchored regex on <spec-requirement id="…">…</spec-requirement>, replaces the matched substring, and leaves the rest byte-untouched. ADDED scans forward from the topic-group <h3> to the next <h3> or section close and inserts there.

4 · Alternatives considered

OptionByte-stabilityRobustnessEffortTotal
Full parse5 round-trip mutation1427
Hybrid parse5-locate + string-splice3339
Targeted string replacement on stable anchors — chosen43411

Full round-trip loses on byte-stability. Hybrid (parse-to-locate, splice-by-offset) adds parse5 weight per call and the offset math is fiddly. Targeted replacement wins because spec.html's anchors are stable and unique; if they ever drift, schema validation upstream catches it before apply runs.

5 · Decisions

D-001 · HTML mutation via targeted string replacement on stable anchors

Status
Accepted
Context
FR-010 requires byte-stable output. A parse5 round-trip would re-pretty-print everything.
Decision
Anchored regex: <spec-requirement\s+id="ID"[^>]*>[\s\S]*?<\/spec-requirement> for MODIFY/REMOVE/RENAME; <spec-status\s+value="…">…</spec-status> for status flips; closing </ol> inside <spec-changelog> for append. ADDED locates the topic-group <h3> and inserts before the next <h3> or section close. No parse5 in the mutation path.
Consequences
+ Byte-stable; preserves whitespace, attribute order. + No parse5 on the hot path. − Fragile to anchor drift; mitigated by upstream schema validation. − Regex authoring needs care; unit tests cover each op.

D-002 · Operation sequencing — mutate first, rename last; no rollback

Status
Accepted
Context
Apply has multiple side effects. Cross-process filesystem transactions are not a thing.
Decision
Strict ordering: (1) gate-check, (2) compute mutations in memory, (3) write live spec, (4) write archived/withdrawn proposal (status + changelog), (5) ctx.fs.rename the folder. Steps 1–2 leave nothing changed on failure; step 5 is single-syscall atomic per OS. No rollback code; git is the rollback mechanism, named in the CLI's error output.
Consequences
+ Simple, predictable. + No transaction code. − Crash between step 3 and step 5 requires git revert. − Apply is a development-time gesture, not production.

D-003 · Add rename to FileSystem interface

Status
Accepted
Context
006's FileSystem shipped four methods per 006 D-005. FR-005 requires atomic folder move via ctx.fs, never node:fs direct.
Decision
Add rename(from: string, to: string): Promise<void>. The nodeFs impl wraps fs.promises.rename (atomic per POSIX/NTFS, same-filesystem). Test stub rewrites map keys. First additive change to the interface, anticipated as a v0.x minor bump in 006 D-005.
Consequences
+ Single syscall keeps the move atomic. + VS Code's workspace.fs + MCP FS capabilities both expose rename. − Pre-1.0 interface broadening; release notes flag it. − Cross-filesystem fallback to copy+unlink on some OS; same-filesystem assumption documented.

D-004 · Discriminated-union input (ApplyInput | WithdrawInput) over separate functions

Status
Accepted
Context
FR-003 puts both modes under one verb; they share preconditions, folder-move, and changelog discipline. Two functions would duplicate that.
Decision
One applyCommand(input: ApplyInput | WithdrawInput, ctx). Input is a discriminated union with literal mode: { mode: 'apply', slug } or { mode: 'withdraw', slug, reason }. Kernel branches on mode; shared helpers as private functions.
Consequences
+ One entry, one test file, one CLI shim. + TS type narrowing is statically safe. − ApplyResult carries mode-specific fields (deltasApplied: 0 for withdraw); documented in spec §4.

D-005 · Risk-register gate — pure scan, structured refusal

Status
Accepted
Context
FR-008 requires apply to refuse if any <spec-risk status="identified"> remains, listing offenders by target=. Kernel must never transition statuses on its own.
Decision
Scan via regex /<spec-risk\s+[^>]*?status="identified"[^>]*?target="([^"]+)"/g (plus attribute-swapped variant). If matches non-empty, throw typed RiskGateError with { targets: string[] }. CLI catches and formats with exit code 2. No AI; no status mutation.
Consequences
+ Pure, fast, deterministic. + Typed error lets MCP / VS Code render their own UI. − Attribute-order variance needs both regex orderings; fixture covers each.

D-006 · Cross-spec reference rewrite for RENAME — intra-spec only; cross-spec surfaces as report

Status
Accepted
Context
FR-004 requires intra-spec rewrite on RENAME. Spec edge case defers cross-spec propagation to TBD-core-cross-spec but expects drift surfaced, not silently propagated.
Decision
Rewrite within live spec.html only (href="#OLD", ID attrs, prose mentions matching \bOLD\b). Do not rewrite archived proposals, siblings, or principles. After in-spec rewrite, scan folder siblings (plan.html, tasks.html) and other specs/**/spec.html for stray refs; surface each in ApplyResult.crossSpecWarnings: string[]. CLI prints them as "review manually" warnings.
Consequences
+ Honours "preserved verbatim" discipline. + Author retains control over cross-spec mutation. − Two-pass scan on RENAME (rare). − Warnings list may grow noisy; v1 accepts that.

D-007 · Changelog entry format + insertion point

Status
Accepted
Context
FR-006/FR-007 require <spec-changelog> append on live spec + paired entry on the moved proposal. Today's markdown specifies the exact shape.
Decision
Locate the closing </ol> inside <spec-changelog> (last occurrence) and insert a new <li> before it, matching the markdown template verbatim. Date comes from new optional ctx.now?.() — defaults to new Date(); test fixtures inject a fixed date. Summary derives from the proposal's <h1> / <spec-tldr>; caller can override via ApplyInput.summary?: string.
Consequences
+ Matches existing corpus; SC-001 byte-identity achievable. + Injected dates make tests deterministic. − Adds ctx.now (small additive). − Summary heuristic may pick poor text; --summary is the override.

D-008 · Single-PR migration, bench-gated, ships as v0.1.0-pre.12

Status
Accepted
Context
010 lands four pieces (kernel, FS interface additions, CLI, markdown). Tightly coupled; staging splits them poorly.
Decision
Single PR per 006 + 007 precedent. Ships as v0.1.0-pre.12 (007 shipped pre.9; pre.10/pre.11 reserved for interleaved sibling extractions). Bench enforces lazy loading; CLI integration tests prove wiring; byte-identity replay proves SC-001.
Consequences
+ Atomic; reverts cleanly; simpler version bookkeeping. − Larger diff; any failure blocks the whole slice.

7 · Risks & mitigations

8 · Complexity tracking

Two deliberate additions warrant flagging:

Regex-based HTML mutation (D-001). Conventional wisdom warns against regex-on-HTML. Justified here because spec.html is author-curated with stable anchors, schema validation runs upstream as the well-formedness guarantor, and parse5 round-trip violates FR-010 non-negotiably. The regex shape is bounded to anchored elements the schema enforces; not arbitrary HTML.

No rollback logic for partial failures (D-002). A crash between live-spec write and folder rename leaves a small inconsistent window. Accepted because apply runs under git, cross-process FS transactions are genuinely hard, and git revert is the universal escape hatch. CLI error output names the recovery gesture.
