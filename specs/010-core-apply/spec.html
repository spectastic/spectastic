1 · Context

Today's /spectastic.apply is a markdown procedure at commands/spectastic.apply.md executed by the LLM in-process. It enforces the REQ-CHANGE-001..005 contract (proposal-shaped folder, typed deltas, risk-register gate, dual-surface rejection workflow). Per 006-kernel-extraction, the eight slash-command verbs need a shared TypeScript kernel so future MCP, VS Code, and web-editor consumers don't re-implement each verb. This slice extracts apply — the most operationally-coupled deterministic verb (folder moves, multi-file mutations), a good test of whether the kernel contract holds for a verb that does real IO.

Apply mode and withdraw mode land together: they're two paths through one lifecycle gesture and share preconditions, the changelog-append discipline, and the folder-move logic.

2 · User scenarios & testing

Each story is independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Maintainer applies an approved proposal P1

As a maintainer with an approved changes/<slug>/proposal.html, I want to run spectastic apply <slug> and have deltas fold into the live spec, the folder move to archive/, and a changelog entry append so that the "approved → applied" gesture is one deterministic command.

Acceptance: Running the new CLI subcommand on any existing examples/changes/archive/<slug>/ proposal (apply temporarily reverted) reproduces the current archived state byte-for-byte.

US2 · Maintainer withdraws an authored proposal P1

As a maintainer whose authored proposal is no longer the direction, I want to run spectastic apply --withdraw <slug> --reason="…" so that the rejection is preserved as history per REQ-CHANGE-005's Surface B.

Acceptance: Running withdraw mode on a copy of examples/changes/withdrawn/2026-06-13-implement-to-build/'s pre-withdrawal state reproduces the current withdrawn state: status pill withdrawn, folder under withdrawn/, paired changelog entries on both the live spec and the moved proposal.

US3 · Downstream surface invokes apply programmatically P2

As a future MCP server or VS Code extension author, I want to import applyCommand from @spectastic/core/commands/apply and call it with a stubbed ctx.fs so that I can surface apply through a tool call without spawning the CLI.

Acceptance: packages/core/test/apply.test.ts calls applyCommand({ slug }) against an in-memory ctx.fs and receives an ApplyResult matching the expected live-spec string and folder layout. No process spawn.

Edge cases

Five tracked failure modes apply handles
  • Risk-register gate blocks apply — proposal carries a <spec-risk status="identified">. Per REQ-CHANGE-004, apply refuses and lists offenders. The user transitions each to accepted | mitigated | rejected in the proposal, then retries.
  • Delta target ID missing for MODIFY/REMOVE/RENAME — the live spec doesn't contain the ID the delta names. Apply stops; never guesses. Reported via DeltaApplication.result = 'gate-blocked'.
  • HTML re-formatting drift — a naive parse5-roundtrip would re-pretty-print the live spec and produce a giant diff. The kernel uses targeted-mutation only: change the requirement block in place, leave surrounding whitespace and attribute order alone.
  • Withdraw of an already-applied proposal — proposal status is applied or withdrawn. Withdraw refuses; lifecycle terminal states are one-way per REQ-CHANGE-005.
  • Cross-spec drift on a renamed ID — a RENAME updates the ID and intra-spec cross-refs but a sibling spec also references the old ID. v1 flags this as an open question in the apply report rather than propagating silently; full handling deferred (see Out of scope).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional — the kernel function

The applyCommand function MUST conform to the KernelContext shape defined in 006 FR-007: signature async function applyCommand(input: ApplyInput | WithdrawInput, ctx: KernelContext): Promise<ApplyResult>; all IO through ctx.fs; no module-level side effects; no implicit process.cwd(), process.env, or console usage.

The kernel function MUST be implemented at packages/core/src/commands/apply.ts with a subpath export @spectastic/core/commands/apply declared in the package's exports field, following the per-verb subpath pattern from 006 FR-002. The umbrella entry MUST NOT eagerly load apply.ts.

@spectastic/cli MUST expose spectastic apply <slug> (apply mode) and spectastic apply --withdraw <slug> --reason="<one-line>" (withdraw mode), both importing applyCommand from @spectastic/core/commands/apply. The CLI owns arg parsing, stdout formatting, and exit-code translation; the kernel owns deterministic operations.

Apply mode MUST implement the four delta operations per REQ-CHANGE-002: added inserts a new <spec-requirement> in its topic-group; modified replaces the body of the existing id="…" block; removed deletes the block; renamed updates the id="…" attribute and rewrites intra-spec cross-references to the old ID. Each operation MUST return a DeltaApplication entry naming the target, op, and result.

Apply mode MUST move the change folder from specs/<spec-id>/changes/<slug>/ to specs/<spec-id>/changes/archive/<slug>/ after all deltas apply. The move MUST be atomic (one rename via ctx.fs); the date-prefixed folder name is preserved.

Apply mode MUST append a <spec-changelog> entry to the live spec naming the archived proposal path with a one-line summary, flip the archived proposal's <spec-status> from approved to applied, and append a final entry to the proposal's own changelog recording the apply date. Markup shape follows commands/spectastic.apply.md's Procedure steps 5 and 7.

Withdraw mode MUST flip the proposal's <spec-status> to withdrawn, move the folder from changes/<slug>/ to changes/withdrawn/<slug>/ (sibling of archive/), append a "Considered <slug>, withdrew on <date> because <reason>." entry to the live spec's changelog, and append a paired entry to the moved proposal. Refuse if the folder already exists under archive/ or withdrawn/.

Apply mode MUST refuse if any <spec-risk> in the proposal's <spec-risk-log> carries status="identified", per REQ-CHANGE-004, and MUST list offenders by target=. Apply MUST NOT re-run the heuristic, re-spawn the critic agent, or transition statuses — the status field is the user's commitment and apply reads it.

Both modes MUST carry the <spec-risk-log> contents verbatim into the archived or withdrawn proposal. The kernel MUST NOT rewrite risk responses, statuses, or ordering during apply — the author's status calls are the artifact's record of how each risk was resolved.

HTML manipulation MUST be deterministic and byte-stable. Targeted mutations only: locate the requirement, changelog, or status block by ID/anchor and replace only that block, preserving surrounding whitespace, attribute order, and formatting. Whole-document parse5 round-trips that re-pretty-print are not acceptable. Running the kernel twice on the same inputs MUST produce byte-identical output.

All filesystem operations (reads, writes, folder rename) MUST flow through ctx.fs, never direct node:fs. Tests MUST exercise the function with an in-memory stub ctx.fs; no real filesystem IO at the unit-test layer.

Unit tests at packages/core/test/apply.test.ts MUST cover apply mode, withdraw mode, the risk-register gate, each delta op, and the deterministic-output invariant. @spectastic/cli's test suite MUST gain integration tests for both invocations against a temp-dir fixture.

commands/spectastic.apply.md MUST gain a note that the LLM MAY invoke spectastic apply <slug> (or the withdraw form) via Bash for deterministic execution, but is not required to — the markdown procedure stays canonical per 006 FR-009.

The kernel function's docblock SHOULD link to commands/spectastic.apply.md per 006 FR-008. The markdown MUST NOT be auto-generated from the docblock in v1.

Non-functional

The extraction MUST NOT regress any scenario in bench/baselines.json past its declared budget. The init-help-cold-start scenario MUST stay within ±20% of its 52 ms CI baseline — the apply subpath must not eager-load parse5 onto the init path.

Out of scope (deferred to other slices)

  • Cross-spec drift propagation when a RENAME updates an ID referenced from a sibling spec. v1 surfaces the drift as an open question in the apply report; full handling needs its own slice.
  • Conflict resolution between two concurrent proposals targeting the same requirement. The current procedure assumes one apply at a time; concurrent-apply detection is a separate problem.
  • Extract /spectastic.triage — sibling kernel slice; exercises AI adapter on a low-stakes verb.
  • Extract /spectastic.implement — sibling kernel slice; drain modes deserve their own scope.
  • Extract /spectastic.spec — sibling kernel slice; tests AIProvider.ask<T>() end-to-end.
  • Extract /spectastic.plan — sibling kernel slice; pairs with spec.
  • Extract /spectastic.tasks — sibling kernel slice; deterministic generation from spec + plan.
  • Extract /spectastic.propose — sibling kernel slice; adversarial-pass spawn needs sub-agent semantics on AIProvider.
  • Extract /spectastic.principles — sibling kernel slice; smallest of the slash verbs.
  • Auto-triggering /spectastic.plan or /spectastic.tasks from a large-change classification. Decided against by REQ-CHANGE-003 — apply states the routing rule as guidance only.

4 · Data model

Four types this slice owns: ApplyInput, WithdrawInput, ApplyResult, and DeltaApplication. KernelContext is reused from 006.

Entities

ApplyInput
{ slug: string }. The <YYYY-MM-DD>-<slug> folder name under specs/<spec-id>/changes/. Slug omitted at the CLI layer defaults to the most-recently-modified approved proposal — defaulting is the CLI's responsibility, not the kernel's.
WithdrawInput
{ slug: string, reason: string }. Both required; empty reason is rejected at the kernel layer (not just the CLI), per REQ-CHANGE-005's "refuses if --reason is empty" clause.
ApplyResult
{ liveSpec: string, archivedPath: string, deltasApplied: number, changelogEntry: string }. Returned by both modes — in withdraw mode, deltasApplied is 0 and archivedPath points at the withdrawn/ location. The CLI formats this into stdout; programmatic consumers read the fields directly.
DeltaApplication
{ target: string, op: 'added' | 'modified' | 'removed' | 'renamed', result: 'success' | 'gate-blocked', reason?: string }. One entry per delta in apply mode. gate-blocked entries surface a non-empty reason (e.g. "target not found", "ID already exists"). The kernel halts on first gate-block; subsequent deltas are not attempted, so a returned DeltaApplication[] never contains a mix of success after gate-blocked.

5 · Success criteria

Technology-agnostic, measurable outcomes.

For every proposal under examples/changes/archive/ and examples/changes/withdrawn/, running the kernel against a pre-apply (or pre-withdraw) snapshot reproduces the current archived state byte-for-byte: same live spec, same folder location, same paired changelog entries. Byte-identity regression detector.

pnpm bench passes all scenarios on CI with p50 within budget. init-help-cold-start stays within ±20% of its 52 ms baseline — apply's HTML-manipulation path does not leak onto init.

A test at packages/core/test/apply.test.ts imports applyCommand from @spectastic/core/commands/apply, calls both modes against an in-memory stub ctx.fs, and asserts on ApplyResult, DeltaApplication[], and post-state filesystem. No process spawn. Existing CLI integration tests stay green.

6 · Assumptions

Two preconditions: 006 kernel package shape is shipped, and HTML targeted-mutation is feasible without a full parse5 round-trip.

006-kernel-extraction has shipped: @spectastic/core exists with the established workspace shape, subpath-export pattern, and KernelContext / AIProvider interfaces. This spec builds on that contract; without it, FR-001 and FR-002 have no foundation.

Targeted HTML mutation (locate-by-ID, replace-block, preserve-surroundings) is implementable without a full parse5 round-trip that re-pretty-prints. The id="…" attribute on <spec-requirement>, the <spec-status> wrapper, and the <spec-changelog> block are all stable, anchorable elements. Implementation strategy (string-based block replacement vs surgical parse5 manipulation vs a hybrid) defers to the plan; this assumption is that some deterministic strategy exists.
