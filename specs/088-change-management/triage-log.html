Cards

A tick means both “closed” and “done”, so a closed-but-not-done task reads as owed forever

Cross-spec upstream

Debugging a session that repeatedly re-opened work already finished, deferred or retired, root cause was that REQ-CHANGE-010 forbids ticking a superseded task, so an unticked box means either open or closed-but-not-done and every consumer must carry an exclusion to tell them apart; fixed by making the tick mean closed and a status say why it closed; regeneration fails, because the requirement states the prohibition outright.

Expected
One question — is this task open? — with one answer any consumer can read without special cases.
Actual
Three consumers compute “what is left” three ways. The implement verb excludes superseded tasks from both the drain and the flip count. The REQ-LIFECYCLE-009 validate scan, written today, counts raw checkboxes and does not. An ad-hoc count during this session reported 25 owed tasks when 9 were — 16 of them retired and correctly marked. Two specs holding only superseded work show 8 unchecked boxes each and are complete.
Diagnosis
REQ-CHANGE-010: “A superseded task MUST NOT be deleted, renumbered, or ticked.” The prohibition is well-motivated — the implement verb states it plainly, “ticking it would claim a result nobody produced” — because a tick has historically meant the work was done. But a tick is also the only signal for this is not owed, and those are different facts. Forbidding the tick keeps the first honest by making the second unreadable, and pushes the distinction into an attribute every consumer must remember to check.
Fix
REQ-CHANGE-010 and REQ-LIFECYCLE-003: separate the two facts. The checkbox becomes open or closed, and data-status says how it closed — done, superseded, cancelled, declined. A closed task is ticked whatever closed it, so unchecked means exactly open and no consumer needs an exclusion. A ticked superseded task claims no result, because the status beside it says the work was retired rather than performed. This is the convention the triage card already uses (data-status="done" / "rejected") and it solved the same problem there.
Deep dive — cross-spec contract touched

The shared contract is “what an unchecked box means”, and it is stated in one spec and constrained by another. REQ-LIFECYCLE-003 owns the <spec-task> element and what it carries; REQ-CHANGE-010 owns the prohibition that makes the box ambiguous. Neither can be fixed alone: amending only the prohibition leaves the element with no status vocabulary, and amending only the element leaves the prohibition forbidding the tick that would use it.

This was predicted and not acted on. An adversarial pass on the proposal that added REQ-LIFECYCLE-009 said the scan “reports a raw checkbox count … the flip predicate and this validate rule read the same file by two different rules, and the two will disagree”, calling it “a third consumer of the condition T-031 said was stated once and consumed twice”. The finding was recorded as a note rather than a risk, and the disagreement shipped the same day.

Migration is the part to get right. Ticking every existing superseded task changes what those artifacts assert, so it belongs in the same change as the requirement — not left for whoever notices. The estate holds 16 such tasks across two specs today, which is a small enough population to convert in one pass and large enough that leaving them would keep the ambiguity alive in exactly the files that motivated the fix.

Naming, deliberately left open. Whether the closed states are done / superseded / cancelled / declined or some other set is a decision for the propose, not this card. What the card settles is that there is a set, and that the box is not part of it.
