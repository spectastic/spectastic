Cards

A tick means both “closed” and “done”, so a closed-but-not-done task reads as owed forever

Cross-spec upstream

Debugging a session that repeatedly re-opened work already finished, deferred or retired, root cause was that REQ-CHANGE-010 forbids ticking a superseded task, so an unticked box means either open or closed-but-not-done and every consumer must carry an exclusion to tell them apart; fixed by making the tick mean closed and a status say why it closed; regeneration fails, because the requirement states the prohibition outright.

Expected
One question — is this task open? — with one answer any consumer can read without special cases.
Actual
Three consumers compute “what is left” three ways. The implement verb excludes superseded tasks from both the drain and the flip count. The REQ-LIFECYCLE-009 validate scan, written today, counts raw checkboxes and does not. An ad-hoc count during this session reported 25 owed tasks when 9 were — 16 of them retired and correctly marked. Two specs holding only superseded work show 8 unchecked boxes each and are complete.
Diagnosis
REQ-CHANGE-010: “A superseded task MUST NOT be deleted, renumbered, or ticked.” The prohibition is well-motivated — the implement verb states it plainly, “ticking it would claim a result nobody produced” — because a tick has historically meant the work was done. But a tick is also the only signal for this is not owed, and those are different facts. Forbidding the tick keeps the first honest by making the second unreadable, and pushes the distinction into an attribute every consumer must remember to check.
Fix
REQ-CHANGE-010 and REQ-LIFECYCLE-003: separate the two facts. The checkbox becomes open or closed, and data-status says how it closed — done, superseded, cancelled, declined. A closed task is ticked whatever closed it, so unchecked means exactly open and no consumer needs an exclusion. A ticked superseded task claims no result, because the status beside it says the work was retired rather than performed. This is the convention the triage card already uses (data-status="done" / "rejected") and it solved the same problem there.
Deep dive — cross-spec contract touched

The shared contract is “what an unchecked box means”, and it is stated in one spec and constrained by another. REQ-LIFECYCLE-003 owns the <spec-task> element and what it carries; REQ-CHANGE-010 owns the prohibition that makes the box ambiguous. Neither can be fixed alone: amending only the prohibition leaves the element with no status vocabulary, and amending only the element leaves the prohibition forbidding the tick that would use it.

This was predicted and not acted on. An adversarial pass on the proposal that added REQ-LIFECYCLE-009 said the scan “reports a raw checkbox count … the flip predicate and this validate rule read the same file by two different rules, and the two will disagree”, calling it “a third consumer of the condition T-031 said was stated once and consumed twice”. The finding was recorded as a note rather than a risk, and the disagreement shipped the same day.

Migration is the part to get right. Ticking every existing superseded task changes what those artifacts assert, so it belongs in the same change as the requirement — not left for whoever notices. The estate holds 16 such tasks across two specs today, which is a small enough population to convert in one pass and large enough that leaving them would keep the ambiguity alive in exactly the files that motivated the fix.

The theming is load-bearing, not decoration. Today a superseded task hides its checkbox — the stylesheet says why: “Not disabled — a disabled control reads as ‘you may not tick this yet’, which is the opposite of the truth. It is simply no longer a question.” That absent box is the entire visual distinction. Ticking a closed task removes it, so a retired task would render identically to completed work — strictly worse than the state this card is trying to fix. Whatever the propose decides, the visual signal has to move in the same change.

Who needs the distinction, and who does not. A reader asking what is left needs only open-or-closed, which is the whole point of the fix. A reader asking did this actually happen needs more: a requirement whose tasks were all superseded is not implemented, while one whose tasks were all done is — a materially different claim about the codebase, and the question this session kept having to answer by hand.

Only the unusual closure earns a pill. The estate holds 2,383 tasks and 17 superseded ones — 0.7%. A pill on every closed task would be roughly eighteen hundred badges carrying no information, which is the failure the toggle row already demonstrates elsewhere (the required field reads none in 50 of 61 views, a row of chrome costing every other row its attention). Done is the ordinary case and the tick already says it; a pill belongs only where the closure was something else. The mechanism exists and is proven — the DONE and REJECTED pills on triage cards — and the <p class="retired"> line already carries the reason, so the pill is the glance and the line is the detail.

Naming, deliberately left open. Whether the closed states are done / superseded / cancelled / declined or some other set is a decision for the propose, not this card. What the card settles is that there is a set, and that the box is not part of it.

A proposal must say what it adds and need never say what it takes away

Spec upstream

Debugging why three changes in one day would each have silently removed something, root cause was that removal is only visible when it is the op — a clause inside a retyped post-state, a behaviour nobody wrote down, or an affordance the stylesheet provides are all invisible; fixed by making every proposal carry a subtraction record; regeneration fails, because nothing asks the question.

Expected
A proposal states what it removes as deliberately as what it adds.
Actual
Three instances in one session, each caught by something other than the process. An ADD restated a live requirement minus its no-network clause — caught by an adversarial pass. A MODIFY dropped a MUST and four rationale sentences — caught by the two guards that do exist. And a proposed change to tick semantics would have removed the only visual signal a retired task has, its hidden checkbox — caught by a human asking.
Diagnosis
conformance-dropped and rationale-dropped both compare a post-state against the requirement it targets, so they see a removal only when it happens inside a MODIFY. REQ-CHANGE-002 demands a reason and a migration for op="removed" — but only when a whole requirement goes. Nothing covers a clause lost in a retyped ADD, a sibling requirement contradicted (000/T-028), or a behaviour that was never a requirement at all. The two guards were built the same week and each closed the hole it was standing in front of.
Fix
088: require every proposal to carry a subtraction record — what this change removes, weakens, or makes unreachable — with nothing as a legitimate and explicit answer. The presence of the record is checkable; its content is judgment. This is exactly the shape REQ-AUTHOR-005 already uses for the open-questions register: the register must exist, and what it says is the author's.
Deep dive — cascade required

Why a record rather than a rule. The three instances are three different kinds — a dropped clause, a contradicted sibling, a removed affordance — and only the first is mechanically comparable. A checker for the third would need to know what the stylesheet conveys, which is not in any artifact. What is checkable is that the question was asked, which is the whole of the intervention: the adversarial pass already catches these when it runs, and it is the last and most expensive line rather than the first.

The cheaper half already exists and is unused. Both drop guards' fix hints say “or say in the What-changes line that it is being removed and why” — so the convention of declaring a removal in prose is already written down, for MODIFY only, as an escape from a warning rather than as an obligation.

Cascade. The record is a section in templates/proposal.html and a step in commands/spectastic.propose.md, so both move with the requirement. Whether a validate rule checks for the section's presence is the propose's call: it is checkable, and the estate has one precedent each way — skill-metadata-shape warns on a missing key, while several conventions are deliberately review-caught.
