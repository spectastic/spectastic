Declare what it retires

An unticked box is a claim that work is owed. Across three specs, five of twenty-nine were true.

Status Proposed Change ID 2026-08-16-declare-what-it-retires Spec 088-change-management Author Brian Corbin · @briancorbinxyz Created 16 Aug 2026 Source 000/T-024 Targets 2 requirements — 1 added, 1 modified Read time

REQ-CHANGE-006 folds every applied proposal's §6 into tasks.html and says nothing about what happens when a later change corrects the requirement an earlier phase was written against. So the earlier phase stays, unticked, indistinguishable from work that is genuinely owed.

Measured rather than asserted: across 093, 094 and 095, 29 tasks read as open and 5 were. Sixteen belonged to phases a later round reversed; eight were already done under another spec's banner. A drain cannot trust that queue, and the one that tried built a check three times.

This gives a proposal a way to say what it retires, and the fold a way to act on it.

1 · Intent

The gap is a consequence of a deliberate decision, which is why it has lasted. REQ-CHANGE-006 makes apply a uniform accept-and-route step — never context-dependent about whether it implements — and that uniformity is exactly what leaves no vocabulary for retiring a phase. Apply appends; it has never had a way to say that an appended phase stopped being true.

Nothing can infer it. A later proposal that reverses an earlier one does not resemble one that extends it: both are ordinary deltas against the same requirement, and the difference lives in the reasoning rather than the shape. That is the finding T-024's regeneration test records — it fails, because no implementation could derive what a proposal supersedes from what a proposal contains. So it has to be authored, and the only question was where.

The cost of leaving it is not the count. It is that the count is believed. A drain reads an unticked box as work owed, because that is what the format promises; and 095's three rounds ping-pong on one decision — phase 7 adds a resource kind, phase 8 forbids it and asks for a test asserting no kind was added, phase 9 adds it again — so draining in order builds and unbuilds, and draining out of order is guesswork.

2 · Scope

In scope

  • A way for a proposal to declare the change it supersedes.
  • What the fold does with the named phase, and what it does when the name does not resolve.
  • The mark itself — annotated, never deleted or renumbered, following REQ-CHANGE-009's data-status convention.

Out of scope

  • A validate rule. The apply-time gate is the only moment the information exists; a rule would re-read archived proposals against live task files to re-litigate a past decision, which is expensive and cannot fail usefully. defer-to=never.
  • A distinct mark for work that moved rather than being reversed. 094's phase 6 was relocated to 099 and completed there, which is a different fact from "never do this" — but it is a difference of reason, and one marker with a required reason carries it without a second enum value earning its keep across CSS, schema and every consumer. defer-to=TBD-relocated-task-mark.
  • Retiring the 16 phases this proposal's own evidence identifies. That is a drain against the new obligation, not a requirement change. defer-to=093-design-visual-section.

3 · Approach

An attribute on the <spec-change> wrapper the proposal already carries, read by the kernel before it folds. It sits with the change's own identity, needs no new element, and is available at exactly the moment the fold runs.

4 · Deltas

What changes — a proposal may declare the change it supersedes, and the fold acts on it. New requirement; nothing existing is narrowed.

A change proposal MAY declare the change it supersedes. Where it does, on /spectastic.apply the fold MUST mark every unchecked task in the named change's folded phase as superseded, annotated with a reason and the change that retired it. A superseded task MUST NOT be deleted, renumbered, or ticked, and a task already checked MUST be left as it stands. Where the named change does not resolve to a folded phase in the target's tasks.html, apply MUST refuse.

Rationale

Declared rather than inferred, because nothing distinguishes a proposal that reverses an earlier one from a proposal that extends it: both are deltas against the same requirement, and the difference is in the reasoning. This is the same posture 073 FR-003 settles for interface state — a declaration outranks an inference — reached here by a different route, since there is no inference to outrank.

Unchecked only. A ticked box records work that happened; retiring it would rewrite history to tidy a count. The distinction matters more than it looks: 095's phase 9 carries a task already ticked, and a rule that swept a whole phase would have unticked a real result.

Annotated, never deleted. REQ-CHANGE-009 already settled this shape for triage cards, and for the same reason — the two most useful cards in the estate are the ones where the proposed fix and the shipped fix disagree. A retired phase is evidence of a decision that changed, and deleting it leaves the next author to rediscover why.

Refuse rather than warn on an unresolvable name, matching a delta whose target does not exist. A supersession that silently no-ops leaves exactly the false backlog it was authored to clear, and says nothing — which is the failure mode this requirement exists to end, reproduced by its own mechanism.

One mark, and the reason carries the difference. Work that was reversed and work that moved to another spec and completed there are different facts, and 094 supplies a real instance of the second. A second enum value would have to earn its keep in the stylesheet, the schema and every consumer; a required reason line does the same work at the point a reader is already looking. TBD-relocated-task-mark holds the question open if the reason line proves too weak.

What changes — one sentence, naming where supersession lives so the fold's own requirement does not read as exhaustive. Nothing else: the phase shape, the ID sequencing, the provenance link, the must-not-implement clause and the uniformity claim are carried verbatim.

On /spectastic.apply, a proposal's §6 tasks MUST be folded into the target's tasks.html — specs/<id>/tasks.html for a spec, or the artifact's sibling tracker for the meta-spec / principles, created from templates/tasks.html if absent — as a new provenance-linked <spec-task> phase whose IDs continue the target's sequence. The provenance MUST link the archived proposal. /spectastic.apply MUST NOT itself implement the tasks; /spectastic.implement drains the folded phase. The archived proposal §6 remains the frozen intent record and MUST NOT be ticked in place. This makes apply a uniform accept-and-route step for every target — never context-dependent about whether it implements. Retiring a prior phase is REQ-CHANGE-010's, and does not vary this.

Rationale

Acceptance ≠ execution (a merge is not a deploy); a command must behave consistently (least astonishment); and the fold's provenance link is what lets a reader walk from a task back to the argument for it.

The final sentence is a pointer, not an exception. Apply still does the same thing every time: it reads the declaration and acts on it, whether or not one is present — which is uniform in the sense this requirement means, since the behaviour is a function of what the proposal declares rather than of what the kernel guesses about the target. Without the pointer, this requirement reads as the complete account of what a fold does, which is how the gap survived: it was not that anyone decided a phase should never be retired, but that nothing raised the question.
