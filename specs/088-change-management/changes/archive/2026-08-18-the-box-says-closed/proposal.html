Change proposal · 088-change-management

The box says closed

A tick means two things, so an unticked box means two things, and the wrong one is the common one.

Status Applied Change ID 2026-08-18-the-box-says-closed Spec 088-change-management Author Brian Corbin · @briancorbinxyz Created 18 Aug 2026 Targets 1 modified Read time

A tick currently means the work was done, so a task closed any other way cannot be ticked and reads as owed forever. The box becomes open or closed and the status beside it says how it closed. Every consumer then reads one unambiguous question, and the fact a tick used to carry moves to where it can be read without a special case.

The box says closed

Applied

1 · Intent

A tick carries two facts at once: this is not owed and the work was done. Because the second is true only sometimes, REQ-CHANGE-010 forbids ticking a retired task — which keeps the second fact honest by making the first unreadable.

The cost is paid by every consumer. The implement verb excludes superseded tasks from its drain and its flip count; the status-disagreement scan had to be taught the same exclusion after shipping without it; and an ad-hoc count during one session reported 25 owed tasks when 9 were. Two specs holding only retired work show eight unchecked boxes each and are complete.

Filed as 088/T-001 after a session spent repeatedly reopening work that was finished, deferred or retired.

2 · Scope

In scope

  • The checkbox answering one question — open or closed — with the status saying how it closed.
  • Migrating the 16 unclosed retired tasks in the estate, in this change rather than after it. Seventeen exist; one is already closed.
  • The visual signal, which the tick would otherwise remove.
  • Three clauses 089 owns, all directly contradicted by this change and all amended beside it: REQ-LIFECYCLE-003's “checked means done”, its requirement that CSS read state via :has(input:checked) “rather than a parallel data-status attribute” — which the retirement pill needs — and REQ-LIFECYCLE-004/005's flip predicate, whose wording is unchanged and whose meaning is not, since it would now count a retirement as a completion.
  • A second retirement kind, distinguishing work reversed from work that moved elsewhere and completed. Already deferred by the requirement being modified, and untouched here — the reason line still carries that difference.
  • Inventing closure kinds nothing has needed. The estate has exactly one non-done closure today; adding cancelled or declined against no case would be the speculative vocabulary this project argues against elsewhere.

3 · Approach

One modified requirement here, one beside it on 089, applied in the same session — a cross-spec obligation split across sessions is how the last one landed half-done.

The concern the current wording protects is kept, and narrowed to what it actually protects. REQ-CHANGE-010's rationale is right that “a ticked box records work that happened; retiring it would rewrite history to tidy a count” — and the clause that does that work is “a task already checked MUST be left as it stands”, not the prohibition on ticking. A task that was genuinely done keeps its status; supersession still never touches it. What changes is only what the box means for a task that was not done.

The migration is here, not after. Ticking 17 existing tasks changes what those artifacts assert, so it belongs with the requirement. Small enough for one pass, and large enough that leaving them would keep the ambiguity alive in exactly the files that motivated the change.

4 · Deltas

One <spec-delta>.

What changes: a superseded task is now ticked and carries its status, rather than left unticked. One prohibition is deliberately removed — “or ticked” — because it is the clause that makes an unticked box ambiguous. Everything else is carried through unchanged: never deleted, never renumbered, an already-closed task left as it stands, the refusal on an unresolvable name, and the report when nothing is marked. One rationale paragraph is rewritten rather than carried — the “unchecked only” argument said a ticked box records work that happened, which this change makes false; it now states what the clause protects under the new semantics. Carrying it verbatim would have made the requirement assert and deny the same fact.

A change proposal MAY declare the change it supersedes. Where it does, on /spectastic.apply the fold MUST mark every unchecked task in the named change's folded phase as superseded, annotated with a reason and the change that retired it, and MUST close its checkbox — a closed box records that a task is not owed, and the mark beside it records that the work was retired rather than performed. A superseded task MUST NOT be deleted or renumbered, and a task already checked MUST be left as it stands. Where the named change does not resolve to an archived proposal on the target, apply MUST refuse. Where it resolves but carries no folded phase, the fold MUST mark nothing and MUST report that it marked nothing.

Rationale

Declared rather than inferred, because nothing distinguishes a proposal that reverses an earlier one from a proposal that extends it: both are deltas against the same requirement, and the difference is in the reasoning. This is the same posture 073 FR-003 settles for interface state — a declaration outranks an inference — reached here by a different route, since there is no inference to outrank.

Unchecked only, and the reason survives the change in what it protects. The fold marks only tasks that were never closed: a task already closed is left exactly as it stands, so supersession never rewrites a result that happened nor re-annotates a retirement that already did. The distinction matters more than it looks — 095's phase 9 carries a task already ticked, and a rule that swept a whole phase would have overwritten a real result. Note that once a retired task is closed, this clause's checked guard subsumes its data-status guard: both now mean “already settled, do not touch”, which is the intended reading rather than an accident of ordering.

Annotated, never deleted. REQ-CHANGE-009 already settled this shape for triage cards, and for the same reason — the two most useful cards in the estate are the ones where the proposed fix and the shipped fix disagree. A retired phase is evidence of a decision that changed, and deleting it leaves the next author to rediscover why.

Refuse rather than warn on an unresolvable name, matching a delta whose target does not exist. A supersession that silently no-ops leaves exactly the false backlog it was authored to clear, and says nothing — which is the failure mode this requirement exists to end, reproduced by its own mechanism.

The refusal resolves the change, not the phase, and the distinction is the whole difference between a rule that works and one that cannot be satisfied. An earlier draft refused when the named change had no folded phase in tasks.html — which REQ-CHANGE-003 makes permanently unreachable for any large change, since re-running /spectastic.tasks regenerates the tracker and, in that requirement's own words, "supersedes the folded phase". Every phase is gone; every later supersedes= against a pre-regeneration change would refuse forever. The same deadlock arrives by a second route through REQ-CHANGE-007, where an empty §6 owes no phase at all. An archived proposal is a stable fact; whether its phase survived is not, so the refusal is anchored to the first and the marking is best-effort against the second. Reporting that it marked nothing is what stops best-effort becoming silent.

One mark, and the reason carries the difference. Work that was reversed and work that moved to another spec and completed there are different facts, and 094 supplies a real instance of the second. A second enum value would have to earn its keep in the stylesheet, the schema and every consumer; a required reason line does the same work at the point a reader is already looking. TBD-relocated-task-mark holds the question open if the reason line proves too weak.

The box answers one question and the mark answers the other. The original wording forbade ticking a superseded task, which kept “a tick means the work was done” honest by making “unticked means owed” false. That trade was the wrong way round: the ambiguous half is the one every consumer reads programmatically, and the unambiguous half is the one a person reads. Three consumers each had to be taught the same exclusion, one of them after shipping without it, and a count during a single session reported 25 owed tasks when 9 were. Closing the box makes unchecked mean exactly open with no exception for anyone to forget, and the fact a tick used to carry moves to the mark, where it can be read without one. The clause protecting a real result is untouched: an already-checked task is still left as it stands, so supersession still never rewrites work that happened.

4b · What this change removes

Each entry names one thing this change takes away. An empty register is the answer “nothing”.

  • The invariant that a ticked box means work was done. The most consequential line in this proposal and the one worth arguing with: after it, a tick means closed, and a reader who wants to know whether a result was produced must read the mark beside it. The fact is not lost — it moves — but any consumer that inferred “done” from a tick alone is now wrong, and that inference is older than the mark.
  • The hidden checkbox on a retired task. Today the stylesheet hides it, deliberately: “a disabled control reads as ‘you may not tick this yet’, which is the opposite of the truth.” That absent box is currently the only visual distinction a retired task has, and ticking it removes the signal. §6 replaces it with a pill rather than leaving the gap.
  • The exclusion from the two count surfaces. Removed on purpose — it is the point — but the drain skip is kept, because the kernel's first-unchecked regex admits data-status and that markdown line is the only thing stopping a retired task being built. Code that keeps subtracting superseded tasks from a count after this lands will under-report.

5 · Risk register

Populated by the adversarial risk pass. This proposal modifies a must-tier requirement.

§6 item 4 removes the only protection there is. The exclusion exists solely in command markdown; the kernel never had it.

coding/runtime.ts:18 — <spec-task\s+id=[^>]*> — whose [^>]* matches data-status="superseded", so the autonomous drain already returns retired tasks today. Deleting the markdown skip adds nothing and removes the only guard, and the failure points the dangerous way: a retired task becomes ordinary backlog and gets built.

Upheld and verified by reading the regex. Three corrections: the drain skip stays, §6 item 4 is narrowed to the count surfaces only, and a validate rule is added so the invariant this change depends on — a superseded task is closed — has a deterministic owner rather than resting on a migration that cannot reach a downstream project authored under the old rule.

The post-state asserts and denies the same fact: it carries “A ticked box records work that happened” verbatim while §4b removes exactly that proposition.

Post-state rationale paragraph 2, against §4b entry 1. The delta also claims “all six rationale paragraphs” are unchanged, which is true and is the defect.

Upheld, and it is an instructive failure: the drop guards taught me to carry rationale verbatim, and I carried a paragraph the change makes false. Faithful transcription is not the same as a correct post-state. Paragraph 2 is rewritten to say what the clause protects under the new semantics, and the delta no longer claims the rationale is untouched.

The related observation is upheld too — once retired tasks are checked, markSupersededPhase's checked guard subsumes its data-status guard. That is stated in the delta rather than left for a reader to discover.

The scope calls the sibling amendment “the element's own vocabulary”, and it is two must-tier clauses this change directly contradicts.

REQ-LIFECYCLE-003: “the completion state. checked means done. CSS MUST read the state via :has(input:checked) rather than a parallel data-status attribute, so the checkbox is the single source of truth.” The first is the invariant being removed; the second is what the RETIRED pill needs. And REQ-LIFECYCLE-004/005's predicate would count retirements as completions.

Upheld, and the understatement was mine. The out-of-scope item now names all three clauses, and §6 item 6 carries three obligations rather than one. Verified that the predicate defect is latent, not live: the only specs holding superseded tasks are 093, 095 and 105, and all three are accepted — which is the reason to name it now, since it surfaces on the first Draft spec to receive a supersession.

After this change, doneness is read from the absence of a mark — which is the silence-means-two-things failure the proposal exists to end, reappearing one level down.

KB-0001@2026-07-25: “the tasks still show what shipped against which requirement”. §4b concedes that any consumer inferring “done” from a tick alone is now wrong.

Accepted rather than mitigated, deliberately. The alternative is a positive completion mark on 2,366 tasks against 17 retirements — the chrome ratio this project has already recorded twice, and a migration far larger than the defect. Absence-meaning-the-ordinary-case is the estate's existing pattern: the questions register, the parallel marker, the subtraction register shipped hours ago.

The asymmetry that makes it tolerable: the silence being removed hid “is this owed”, which every consumer reads programmatically and got wrong; the silence being introduced hides “was a result produced”, which a person reads and which the mark answers positively whenever the answer is anything other than the default. KB-0001's claim survives — the tasks artifact still shows what shipped, now via the mark rather than the box — so no re-edition is owed. Recorded here so the trade is a decision somebody made rather than a consequence nobody noticed.
