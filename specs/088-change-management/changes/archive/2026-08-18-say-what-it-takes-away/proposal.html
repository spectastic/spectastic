Change proposal · 088-change-management

Say what it takes away

A proposal must say what it adds, and need never say what it removes.

Status Applied Change ID 2026-08-18-say-what-it-takes-away Spec 088-change-management Author Brian Corbin · @briancorbinxyz Created 18 Aug 2026 Targets 1 added Read time

Removal is only visible when it is the op. A clause lost inside a retyped post-state, a sibling requirement contradicted, or a behaviour that was never written down all pass unremarked — three of them in one day, each caught by something other than the process. One added requirement: every proposal carries a subtraction record, and nothing is a legitimate answer.

Say what it takes away

Applied

1 · Intent

A proposal is required to be explicit about what it adds. It is required to be explicit about what it removes only when removal is the op — and that is the rarest case.

Three changes in one session would each have removed something silently. An ADD restated a live requirement minus its no-network clause, on a rationale asserting nothing covered the behaviour, which an adversarial pass caught. A MODIFY dropped a MUST and four rationale sentences, which the two drop guards caught. And a proposed change to tick semantics would have removed the only visual signal a retired task has — its hidden checkbox — which a person caught by asking.

Three kinds, three different catchers, none of them the proposal itself. The guards see a removal only inside a MODIFY, because both compare a post-state against the requirement it targets; nothing sees a clause lost in an ADD, a sibling contradicted, or an affordance that was never a requirement.

2 · Scope

In scope

  • A typed subtraction register on every proposal, with an empty one meaning “removes nothing”.
  • Precedence against the per-delta record, so one question does not get three answers.
  • The presence check, so the must tier has a deterministic owner.
  • Detecting that an ADD contradicts an untouched sibling. Already filed as 000/T-028; it needs semantic comparison, where this needs only that the question be asked.
  • Checking that a subtraction record is correct. An author who writes “nothing” wrongly is not caught by this, and could not be — the record makes the claim visible and reviewable, which is all a record can do.
  • Checking a register is complete. Presence is decidable and ships here; whether an author noticed everything the change takes away is judgment, and a rule claiming to check it would be the false comfort this proposal exists to remove.

3 · Approach

One requirement, and the two artifacts that carry it — a section in the proposal template and a step in the propose verb — so the obligation and the place to discharge it move together.

A record, not a rule. The three instances are three different kinds and only the first is mechanically comparable. A checker for the third would have to know what a stylesheet conveys, which is in no artifact. What is checkable is that the question was asked — and asking it early is the whole intervention, because the adversarial pass already catches these when it runs, as the last and most expensive line rather than the first.

The shape is borrowed properly, which the first draft did not do. REQ-AUTHOR-005 works because its carrier is typed: the entry count is the answer and an empty register is zero, unambiguously. The first draft cited that precedent and then put the obligation on prose, which would have required the word “Nothing” in 44 of this estate's 123 proposals. Typing the carrier removes the chrome and makes the presence check trivial — it is the shape the delta-target check already uses.

4 · Deltas

One <spec-delta>.

A change proposal MUST carry a subtraction register, and each entry in it names one thing the change removes, weakens, or makes unreachable. A register with no entries MUST be the representation of “this removes nothing”, and the register's absence MUST be reported. The register covers what no delta can express — a clause dropped from a retyped post-state, an obligation a sibling requirement loses, a behaviour or affordance no requirement records; where a delta removes something itself, REQ-CHANGE-002's reason and migration remain authoritative for it.

Rationale

Removal is currently visible only when it is the op. conformance-dropped and rationale-dropped each compare a post-state against the requirement it targets, so both see a loss only inside a MODIFY; REQ-CHANGE-002's reason-and-migration applies only when a whole requirement goes. Everything else passes unremarked.

The third clause is the one no tool can reach. A behaviour that was never a requirement — a stylesheet hiding a checkbox so a retired task does not read as a question, say — is invisible to every check the project has and to every check it could build, because the fact lives in a file no requirement describes. A person can see it in a minute if asked, and never if not.

The carrier is typed rather than prose, which is the half the first draft got wrong. It claimed to borrow the open-questions register's shape and then put the obligation on a paragraph — but that register works because it is typed: the entry count is the answer, and an empty register is the single unambiguous representation of zero. Prose would have produced a paragraph reading “Nothing” in 44 of the 123 proposals in this estate, which are ADD-only, and a required field that says nothing in a third of cases is the chrome this project has already recorded costing every other row its attention.

Precedence is stated because the fact already has an owner where a delta can express it. A proposal otherwise carries three answers to one question — the delta's reason and migration, the What-changes line both drop guards point at, and this register — which is precisely the failure the sibling card T-001 was opened for one day earlier.

This obliges the register, not its correctness. An author who leaves it empty and is wrong has still made a reviewable claim, which is strictly better than the current state where there is nothing to review. That ceiling is the requirement's, not an accident of it — and it is why the presence half is checked rather than left to markdown: a missing register is detectable residue, which is the condition P-8 names for owing a rule.

4b · What this change removes

Each entry names one thing this change takes away. An empty register is the answer “nothing”.

  • TBD-subtraction-record-rule, planted by this proposal's own first draft and retired before it was needed — the presence check ships here rather than being deferred, so the slug would have named work nobody was going to do.

Nothing else. No existing requirement loses a clause, no behaviour is withdrawn, and no affordance becomes unreachable — the template gains a register and the propose verb gains a step, neither replacing anything.

Written with the register it introduces rather than the prose the first draft used, because a proposal that creates this obligation and discharges it in a different form is arguing against itself.

5 · Risk register

Populated by the adversarial risk pass. This proposal adds a must-tier requirement.

The requirement obliges a statement but names no carrier, so nothing can count it and the reliable product is a paragraph reading “Nothing” in at least a third of proposals — inverting the very shape it claims to borrow.

REQ-AUTHOR-005 puts its MUST on a typed carrier — a register whose <li> count is the answer and whose absence is zero. This draft put the MUST on prose. Measured independently: 44 of 123 proposals (36 per cent) are ADD-only and would write “Nothing” on day one.

Upheld, and it is the finding the others resolve around. A typed <spec-subtraction> register replaces the prose: each <li> is one thing the change takes away, and an empty register is the answer “nothing” — no chrome paragraph, and the same unambiguous representation of zero the questions register already ships.

A second, document-level record of a fact REQ-CHANGE-002 already assigns to the delta, with no precedence stated — so three surfaces now answer one question.

REQ-CHANGE-002 requires reason and migration on an op="removed" delta; the drop guards' fix hints route the same disclosure to the per-delta What-changes line. T-002's own deep dive concedes it: “The cheaper half already exists and is unused.”

Upheld, and sharpened by its own sibling: T-001, filed a day earlier, is one question with three consumers giving three answers. Precedence is now stated in the requirement — the per-delta record is authoritative for what a delta removes, and the register covers only what no delta can express. That is also the only part the three motivating instances needed, and it shrinks the empty-register population sharply.

A must-tier requirement whose only enforcement is a template scaffold and a markdown step — the two surfaces P-8 excludes by name.

P-8: a step whose omission is a defect must not rely on command markdown, and where a skipped judgment leaves detectable residue a checkable rule must reject it. All four existing must-tier requirements in 088 have a deterministic owner; this would be the first without.

Upheld. The rule is pulled into this change rather than deferred, which the typed carrier makes trivial — it is the same shape as the delta-target check. So the must tier keeps its owner and TBD-subtraction-record-rule is retired before it was ever needed.

Must-tier contradicts the committed definition, given neither correctness nor presence would be checked.

KB-0001@2026-07-25: “MUST — an absolute requirement. Its absence is a defect.” Six of 088's ten requirements chose should explicitly when codifying from few data points; this codifies from three instances and picked must.

Upheld as stated, and resolved by the finding above rather than by a downgrade: with the presence rule shipping, the absence of a subtraction register is a detectable defect, which is exactly what must tier means under the committed definition. Correctness remains uncheckable and the requirement says so in its own body — an author who writes an empty register wrongly has still made a reviewable claim, which is the ceiling, not an accident.
