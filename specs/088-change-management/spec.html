Change management

How an accepted spec changes: a PR-shaped proposal carrying typed deltas, an adversarial risk pass, and an apply that folds and archives.

Status Accepted Spec ID 088-change-management Owner Brian Corbin · @briancorbinxyz Reviewers Brian Corbin · @briancorbinxyz Created 11 Aug 2026 Principlesv1.9.0 Smallest demoableOne proposal authored, risk-passed, applied, and archived — with the live spec patched and its task list folded. Read time

The contract for evolving a ratified spec. Evolution happens through a change-proposal artifact rather than an edit in place, each change is a typed <spec-delta> against one requirement, non-trivial proposals face an adversarial risk pass whose findings must be dispositioned before apply, and apply folds the proposal’s tasks into the target’s task list before archiving the change folder.

1 · Context

Spec evolution is the half of the lifecycle that runs forever. A spec is written once and changed many times, so the change path carries more total traffic than the authoring path and needs a tighter contract: a proposal is reviewable on its own, a delta names exactly what it touches, and nothing lands while a raised risk is still open.

This spec is a slice of the spectastic meta-spec. Its requirements were authored there and moved here intact, keeping their stable ids: a requirement that was REQ-CHANGE-001 in the parent is REQ-CHANGE-001 here, so every existing citation still names the same contract. The parent keeps the project’s context, architecture, decisions and history; this file carries one family of requirements and nothing else.

2 · Requirements

Normative keywords follow RFC 2119.

Spec evolution MUST happen via change-proposal artifacts at specs/<spec-id>/changes/<YYYY-MM-DD>-<slug>/proposal.html. Each artifact MUST use the <spec-change> wrapper and contain at least one <spec-delta>.

Rationale

One proposal per discrete change, reviewable as a single file. The PR-shaped folder structure scopes review cleanly; folding intent / scope / approach / deltas / tasks into one document preserves spectastic's single-file principle.

Each <spec-delta> MUST carry an op attribute equal to one of added | modified | removed | renamed, and a target attribute naming what it touches: a requirement ID (FR-*, REQ-*, NFR-*, SC-*, D-*) for a requirement delta, or a manifest data key/path (e.g. standard/shape-of-system-principles in spectastic-profiles.json) for a data/content delta. A requirement delta MUST embed a <spec-requirement> showing the post-state; a data/content delta MUST NOT — its post-state is the §6 tasks that edit the manifest, and apply makes no change to the requirements body for it (the <spec-changelog> append still lands, as on every apply; see REQ-CHANGE-008). The data-delta-shape validate rule enforces the pairing: a target of requirement-ID shape (^[A-Z]+-) with no embedded <spec-requirement> is an error. For op="removed", the delta MUST also carry reason and migration fields — empty or missing renders visibly broken.

After /spectastic.apply lands a change, the command SHOULD surface the post-apply routing rule — where the user drives the follow-up implementation work — in both its documented output and its per-apply console report:

  • Small change (one or two requirements, behavioural addition, no new ADRs): the §6 tasks have been folded into the target's tasks.html as a new phase (per REQ-CHANGE-006); drive them with /spectastic.implement.
  • Large change (multi-requirement, architectural shift, new topic group): re-run /spectastic.design against the updated spec to revisit ADRs, then /spectastic.tasks to derive a fresh breakdown — which regenerates tasks.html and supersedes the folded phase — then /spectastic.implement to drain it.

The boundary is fuzzy by design: if more than one new ADR would land, the change is large enough to warrant plan + tasks; otherwise the proposal's inline tasks are the breakdown. The rule is guidance, not a guardrail — apply MUST NOT refuse or auto-trigger plan/tasks based on its own classification.

Rationale

The propose template already encodes the small-change shortcut by hosting tasks inside the proposal artifact. The apply command's prose never names the resulting routing rule, so a fresh reader hits the fork unsignposted. Surfacing the rule turns implicit design into explicit guidance and prevents the lifecycle's reading order from leaving a hole between apply and the next implement.

Non-trivial proposals — those that touch a priority="must" requirement, contain an op="removed" delta, OR span two or more topic prefixes — SHOULD carry a <spec-risk-log> populated by an adversarial risk pass run during /spectastic.propose.

Each <spec-risk> MUST carry:

  • target= — a delta ID, requirement ID, or §<n> section anchor. Missing renders the visible label MISSING TARGET.
  • status= — one of identified | accepted | mitigated | rejected (or no-value-found when the critic agent self-reports nothing of value). Default identified.
  • by= — when status is accepted | mitigated | rejected, the human who dispositioned the finding (name · handle, the recording shape the author's choice); never an automated agent. It stays empty while identified. This is the source the Acked-by trailer reads (spec 027).

/spectastic.apply SHOULD refuse if any <spec-risk> has status="identified" — gating on the user-confirmed status field only. Apply MUST NOT re-run the heuristic, re-spawn the critic Agent, or transition statuses on its own; the status field is the user's commitment, and apply reads it. This is what distinguishes the gate from REQ-CHANGE-003's "apply MUST NOT refuse based on its own classification" — the risk-register gate refuses on user input, not apply-side judgment. The heuristic, the three-finding agent prompt, and the response discipline are owned by commands/spectastic.propose.md §8; the apply gate by commands/spectastic.apply.md's Preconditions.

Rationale

Spectastic's lifecycle had no step that forced the strongest counter-argument into the artifact, so first-draft proposals shipped without critical pushback. The risk pass closes that loop. The vocabulary borrows from ISO 31000's risk register — same lineage habit as ADR, INVEST, RFC 2119, and DORA already in the project. Priority should rather than must because we're codifying from one data point; re-evaluate after ≥5 worked applications. The by= dispositioner record makes design-time sign-off attributable and gives the Acked-by trailer a human source.

Items considered but decided against MUST be preserved as history, not deleted. The lifecycle SHOULD support rejection at both surfaces:

Surface A — Inbox cards (pre-propose). A <spec-triage> card in inbox.html MAY carry data-status="rejected" and a <dt>Rejected because</dt> row inside its <dl>. The card stays in inbox.html (mirrors the existing data-status="done" convention for just-do cards). CSS renders a REJECTED pill, muted body, and strikethrough title.

Surface B — Authored proposals (post-propose). /spectastic.apply SHOULD accept a withdrawal mode invoked as --withdraw <YYYY-MM-DD>-<slug> --reason="<one-line>". The mode:

  • Refuses if the proposal status is already applied or withdrawn.
  • Refuses if --reason is empty.
  • Flips status to withdrawn.
  • Moves the folder from specs/000-spectastic/changes/<YYYY-MM-DD>-<slug>/ to specs/000-spectastic/changes/withdrawn/<YYYY-MM-DD>-<slug>/ (a sibling of archive/, not nested), MUST creating changes/withdrawn/ if it does not yet exist (mirroring the archive-move obligation, REQ-CHANGE-007, so a spec's first withdraw does not ENOENT at the move step). The date-prefixed folder name is preserved in both terminal states (applied and withdrawn) per REQ-CHANGE-001.
  • Appends a <spec-changelog> entry to the live spec it targeted: "Considered <YYYY-MM-DD>-<slug>, withdrew on <DD Mon YYYY> because <reason>."
  • Appends a changelog entry to the moved proposal recording the withdrawal date and reason verbatim.

Withdraw is intended as terminal: there is no --unwithdraw command. If you withdrew by accident or under time pressure, restoring the folder and status manually is unsupported but not forbidden — git-revert the move and flip the status field. If your thinking has actually updated since the withdrawal, author a new proposal instead so the lineage stays legible. Implementation ownership: Surface A in commands/spectastic.triage.md; Surface B's procedure in commands/spectastic.apply.md's Withdraw procedure section.

Rationale

The <spec-status value="withdrawn"> vocabulary has existed since v0.1 but has had no workflow behind it — an authored proposal the author decided against would either sit in changes/<YYYY-MM-DD>-<slug>/ indefinitely or get manually deleted. Inbox cards had no terminal-rejected state for routed layers. The lifecycle had no way to record "considered, decided against." This requirement closes both gaps with one discipline — preserve, don't delete — and one apply-mode extension. The withdrawn-folder mkdir-if-absent (added here) is the create-the-destination-if-absent obligation REQ-CHANGE-006 (tracker) and REQ-CHANGE-007 (archive) also carry — placed with the operation it governs. Priority should rather than must because we're codifying from zero applications; re-evaluate after ≥3 worked rejections.

On /spectastic.apply, a proposal's §6 tasks MUST be folded into the target's tasks.html — specs/<id>/tasks.html for a spec, or the artifact's sibling tracker for the meta-spec / principles, created from templates/tasks.html if absent — as a new provenance-linked <spec-task> phase whose IDs continue the target's sequence. The provenance MUST link the archived proposal. /spectastic.apply MUST NOT itself implement the tasks; /spectastic.implement drains the folded phase. The archived proposal §6 remains the frozen intent record and MUST NOT be ticked in place. This makes apply a uniform accept-and-route step for every target — never context-dependent about whether it implements. Retiring a prior phase is REQ-CHANGE-010's, and does not vary this.

Rationale

Acceptance ≠ execution (a merge is not a deploy); a command must behave consistently (least astonishment); and accepted work belongs in a project's tracked task list, not the triage inbox. One execution surface per target, no hand-copy, archive intact.

The final sentence is a pointer, not an exception. Apply still does the same thing every time: it reads the declaration and acts on it, whether or not one is present — which is uniform in the sense this requirement means, since the behaviour is a function of what the proposal declares rather than of what the kernel guesses about the target. Without the pointer, this requirement reads as the complete account of what a fold does, which is how the gap survived: it was not that anyone decided a phase should never be retired, but that nothing raised the question.

The §6 task-fold mandated by REQ-CHANGE-006 MUST have a deterministic implementation in the apply kernel (it has none today). The fold MUST run on the §6 content apply has already read, before the archive-folder move, so a fold or fidelity failure leaves the proposal in changes/ for a clean retry rather than a half-applied state. The archive-folder move MUST create its destination parent (changes/archive/) if it does not yet exist, so a spec's first apply does not ENOENT at the move step — the same create-the-destination-if-absent obligation REQ-CHANGE-006 places on the tracker and REQ-CHANGE-005 on the withdrawn-folder move. When the kernel folds, it MUST confirm the resulting phase faithfully carries the §6 work — a <spec-task> for every §6 item, carrying over each item's <span class="path"> and, where the §6 item declares it (the [P] convention), its parallel marker, in the <spec-task> shape REQ-LIFECYCLE-003 defines — before reporting success. Mere presence of a phase is insufficient (presence is not containment). A missing or incomplete phase MUST be completed, not returned as success. An empty §6 owes no phase and is skipped per REQ-CHANGE-006.

This adds a kernel capability; it does not change which path performs the fold. The CLI apply path, which already calls the kernel, folds deterministically as a result. Bringing the slash-command path onto the kernel fold is a separate change (it re-architects the markdown-canonical boundary and has an API-key wiring question), tracked as TBD-route-fold-through-kernel and dependent on this one.

Rationale

REQ-CHANGE-006 specifies the fold as an action but defines no post-condition, and the action lives only in slash-command prose — apply.ts has no tasks.html code at all. So the one step that orphans real work when skipped is the one with no deterministic implementation: the 2026-06-25-spec-budget-bands failure (triage T-004). A fidelity check (not mere presence) is required because the fold is real format work and a present-but-wrong phase would otherwise pass — the project's own presence-is-not-containment lesson. A validate backstop was evaluated across three passes and rejected (it cannot know a fold was owed without the archived §6 it ignores). The move-creates-parent clause codifies triage T-007: the kernel's bare fs.rename ENOENT'd on 023's first apply (changes/archive/ absent), failing after the deltas, fold, and proposal-flip had committed — the one path that breaks the fold-before-move atomicity this requirement promises. Priority should, codifying from incidents, matching REQ-CHANGE-004 / REQ-CHANGE-005; re-evaluate after a few real applies.

The mechanical steps of /spectastic.apply — applying each <spec-delta>, the live-spec <spec-changelog> entry (the kernel MUST accept an author-supplied one-line summary, so the changelog's human voice is preserved rather than reduced to a delta count), the archive-folder move, the proposal status flip to applied, and the §6 task-fold (per REQ-CHANGE-006 / REQ-CHANGE-007) — MUST be performed by the apply kernel (spectastic apply, which is deterministic and requires no ANTHROPIC_API_KEY), not re-implemented in the slash-command markdown. The apply markdown MUST run the preconditions — including the REQ-CHANGE-004 risk gate, listing any status="identified" risks by target= — and surface failures before invoking the kernel; the kernel's own gate is a deterministic backstop, not the user-facing refusal. It MUST also confirm spectastic apply resolves before invoking it, surfacing a missing or stale binary clearly rather than failing silently. Beyond the preconditions, the markdown owns only the post-apply routing nudge (REQ-CHANGE-003) and the inbox-card nudge.

When applying each <spec-delta>, the kernel MUST branch on whether the delta embeds a <spec-requirement>. Present — it is a requirement delta: apply the post-state into spec.html. For added, the kernel MUST insert the requirement immediately after the last existing <spec-requirement> whose id shares its family prefix (the id with its trailing number stripped — e.g. NFR-, SC-, REQ-CHANGE-), so it joins its own group beside its siblings, never the document's first </section>. Keying on the sibling requirements already present makes this work for both a downstream spec's FR/NFR/SC groups (kept as sibling <h3> within one requirements <section>) and the meta-spec's REQ-<TOPIC> groups, with no hard-coded section heading. When no existing requirement shares the prefix (the first of its kind), the kernel MUST append it after the last <spec-requirement> in the document rather than at an arbitrary position. For modified | removed | renamed, replace the id-matched requirement in place. Whenever the kernel writes an embedded <spec-requirement> into spec.html (both added and modified), it MUST re-base that requirement's relative links from the proposal's folder depth to the live spec's depth — the mirror of the path-deepening it already applies to the archived proposal — so a same-spec link, a principles.html link, or a sibling-spec link resolves from the live spec instead of pointing above the repository root; a same-document anchor (#ID) is depth-independent and passes through unchanged. Absent — it is a data/content delta whose target names manifest data: the kernel MUST make no change to the requirements body (the mandated <spec-changelog> append still lands) and let the §6 task-fold carry the change; it MUST NOT fabricate a <spec-requirement> from the delta body. As a guard, if a delta's target matches a requirement-ID shape (^[A-Z]+-…) yet embeds no <spec-requirement>, the kernel MUST gate-block it as malformed rather than silently skip — a requirement delta that forgot its post-state is an error, not a no-op.

This is a deliberate, named exception to 006 FR-008 ("the markdown procedure remains the source of truth") and FR-009 ("slash commands MAY invoke the CLI but MUST NOT be required to") for apply: its mechanical steps are pure and deterministic, and their prose-only form was the T-004 failure. Those general rules continue to govern the six verbs that need LLM judgment.

The obligation is scoped to same-spec applies. A cross-spec delta (whose target is a requirement in another spec) is the one mechanical step the kernel does not yet perform and MAY remain markdown-handled until it does (TBD-kernel-cross-spec-apply).

Rationale

Apply's mechanical steps need no AI and the CLI runs key-free, so making the kernel authoritative for them removes the whole class of skipped-step bugs on the in-host path (T-004) without touching the verbs that need judgment. The data/content branch (T-018) extends the same principle: the kernel, not a fabrication fallback, decides what a delta means, so a manifest-data proposal (041 principles, 042 enforce categories) folds and archives without corrupting spec.html. The placement and link-rebasing clauses codify triage T-019 / T-020: applying 019's NFR-003 ADD delta, the kernel dropped the new requirement at the document's first </section> (§1 Context, not §3 Non-functional) and spliced its embedded links in verbatim at proposal depth, so every cross-file reference pointed above the repository root — both hand-fixed in 019, both certain to recur without a contract that constrains placement and link depth. Hosted as a meta-spec requirement — not a MODIFY of 006 FR-009 — because a cross-spec delta could not be applied by the kernel this very requirement mandates, and because apply's contract already lives in REQ-CHANGE-*. Priority should: codifying apply's kernel-authoritative path from incident, matching REQ-CHANGE-004 / REQ-CHANGE-007; re-evaluate after a few real applies.

A <spec-triage> card in a per-spec triage log records whether it is still owed work. When a card's fix has landed, the card SHOULD carry data-status="done"; when a card is closed without a fix — not a defect, superseded, or deliberately declined — it SHOULD carry data-status="rejected" and a <dt>Rejected because</dt> row. These are the same two values and the same rendering REQ-CHANGE-005 defines for inbox cards; this requirement widens their scope to diagnostic cards rather than introducing a parallel vocabulary. A card carrying no data-status MUST be read as still open.

A card marked done SHOULD carry a <dt>Fixed</dt> row inside its <dl> recording what actually shipped, especially where that differed from the proposed Fix — the divergence is usually the most informative line on the card. The card is never rewritten to match the outcome: Fix stays as proposed and Fixed records reality, so the log preserves the reasoning as well as the result.

Closure is owed at the moment the fix lands. /spectastic.implement SHOULD mark the card when it drains work that resolves one, and /spectastic.apply SHOULD do so when the proposal a card called for is applied. Cards remain append-only and IDs stable (REQ-CHANGE-001): closing a card annotates it, never deletes or renumbers it.

No machine check exists, and none is proposed. validate reads artifacts and cannot know whether a proposal landed or a line of code shipped, so a rule could only nag on every open card or trust a marker it cannot verify. Per P-8 this is recorded as a review-caught discipline rather than dressed as a guarantee — the honest posture the fat-core/thin-CLI convention and the no-internal-id-in-copy ceiling already take.

Rationale

The format optimised for capture and never addressed the afterwards: the five Tier-1 fields (TRIAGE-001…TRIAGE-006) contain no resolution state, and Fix is a proposal, not a record that it happened. Measured at proposal time: 78 cards across 23 logs carried 19 markers; all 13 of 020's cards were fixed in code and 2 said so, including four whose own Fix fields called for proposals that had all long since landed. That is a log a reader cannot plan from. Reusing the two existing values rather than minting a resolved vocabulary follows the evidence — T-009 and T-010 reached for done on diagnostic cards before any requirement allowed it, and the CSS already renders it element-wide; a second spelling would cost every consumer and buy nothing. The evidence row is a SHOULD rather than a MUST so a fix that went exactly as proposed is not more ceremonious to close than to make. Priority should, matching REQ-CHANGE-005 / REQ-CHANGE-007: codifying from incident, re-evaluate once a few logs have been kept under it.

A change proposal MAY declare the change it supersedes. Where it does, on /spectastic.apply the fold MUST mark every unchecked task in the named change's folded phase as superseded, annotated with a reason and the change that retired it. A superseded task MUST NOT be deleted, renumbered, or ticked, and a task already checked MUST be left as it stands. Where the named change does not resolve to an archived proposal on the target, apply MUST refuse. Where it resolves but carries no folded phase, the fold MUST mark nothing and MUST report that it marked nothing.

Rationale

Declared rather than inferred, because nothing distinguishes a proposal that reverses an earlier one from a proposal that extends it: both are deltas against the same requirement, and the difference is in the reasoning. This is the same posture 073 FR-003 settles for interface state — a declaration outranks an inference — reached here by a different route, since there is no inference to outrank.

Unchecked only. A ticked box records work that happened; retiring it would rewrite history to tidy a count. The distinction matters more than it looks: 095's phase 9 carries a task already ticked, and a rule that swept a whole phase would have unticked a real result.

Annotated, never deleted. REQ-CHANGE-009 already settled this shape for triage cards, and for the same reason — the two most useful cards in the estate are the ones where the proposed fix and the shipped fix disagree. A retired phase is evidence of a decision that changed, and deleting it leaves the next author to rediscover why.

Refuse rather than warn on an unresolvable name, matching a delta whose target does not exist. A supersession that silently no-ops leaves exactly the false backlog it was authored to clear, and says nothing — which is the failure mode this requirement exists to end, reproduced by its own mechanism.

The refusal resolves the change, not the phase, and the distinction is the whole difference between a rule that works and one that cannot be satisfied. An earlier draft refused when the named change had no folded phase in tasks.html — which REQ-CHANGE-003 makes permanently unreachable for any large change, since re-running /spectastic.tasks regenerates the tracker and, in that requirement's own words, "supersedes the folded phase". Every phase is gone; every later supersedes= against a pre-regeneration change would refuse forever. The same deadlock arrives by a second route through REQ-CHANGE-007, where an empty §6 owes no phase at all. An archived proposal is a stable fact; whether its phase survived is not, so the refusal is anchored to the first and the marking is best-effort against the second. Reporting that it marked nothing is what stops best-effort becoming silent.

One mark, and the reason carries the difference. Work that was reversed and work that moved to another spec and completed there are different facts, and 094 supplies a real instance of the second. A second enum value would have to earn its keep in the stylesheet, the schema and every consumer; a required reason line does the same work at the point a reader is already looking. TBD-relocated-task-mark holds the question open if the reason line proves too weak.
