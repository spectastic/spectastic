An in-flight design cannot validate: both contract paths it could declare are errors

Cross-spec upstream

Debugging why a real design run had to write its contract into two places at once, root cause was that FR-002 forbids an effective path inside specs/ while contract-resolve requires the declared path to exist — and before promotion runs, no path satisfies both; fixed by describing the in-flight state, which no requirement currently does; regeneration fails, because a fresh session reaches the same dead end and invents the same workaround.

Expected
A design authored per commands/spectastic.design.md validates while it is still in flight. The command instructs: author the contract at specs/<spec-id>/contracts/, and promotion later copies it to the effective location.
Actual
Both available declarations are errors, reproduced directly: path="specs/001-x/contracts/api.openapi.yaml" → error: resolves inside specs/, so it can never be an effective declaration path="contracts/api.openapi.yaml" → error: no such file (promotion has not run) A real design run resolved it by writing the contract to contracts/ as well as the sidecar — which is the post-promotion state, reached by hand. As its author put it: "If you have a real promotion step, it will find its work already done."
Diagnosis
Each requirement is right on its own. FR-002 keeps the effective contract out of specs/ so a consumer reaches it without knowing which spec last changed it. FR-003 stops a proposed contract satisfying an effective declaration, which is what keeps exactly one copy authoritative. The resolve check enforces both. Nothing describes the interval between them — the period where the design exists, the proposed contract exists, and the effective one legitimately does not. path= is one attribute and the command's own wording concedes the problem: it says path= "names the contract's two locations across its lifecycle", which one attribute cannot do.
Fixed
17 Aug — applied as 2026-08-17-the-interval-between-two-locations, then built. Five states now behave: pending is silent, promoted is silent, missing errors, a pre-copy errors naming both paths, and an amendment with a captured baseline is silent. That last row is the one the adversarial pass saved — without it the rule errors on the ordinary state of every contract amendment, including three committed promotion fixtures.

commands/spectastic.design.md was the other half: it claimed path= named "two locations across its lifecycle", which one attribute cannot do and which the validator rejected outright. It now says the effective path will not resolve until promotion and that this is expected, and warns against pre-creating the file — the workaround this card was filed about.
Fix
A propose against 070 describing the in-flight state, with two shapes worth weighing. Either the resolve check learns that a declared-but-unpromoted path is pending rather than broken — recognisable because the proposed sidecar holds a file of that name — or the declaration carries the proposed location explicitly and path= means only the effective one, which is what FR-002 and FR-003 already assume. The second is likely right: it makes the two locations two attributes instead of one attribute meaning two things, and it gives promotion an unambiguous source. Either way the design command's wording needs correcting, since it currently describes a workflow the validator rejects.
Deep dive — cross-spec, and the workaround is the tell

Why cross-spec rather than a defect in one place. 070 owns the two locations, 071 owns the promotion between them, and the resolve check enforces a property neither of them scoped to a lifecycle stage. No single spec is wrong; the seam between them is undescribed, which is precisely what the layer means.

The workaround is the diagnostic. Writing the file to both places does not merely satisfy the checker — it performs promotion ahead of the verb that owns it, leaving 071 with nothing to do and no way to tell a promoted contract from one that was pre-copied to silence an error. A tool whose documented path can only be walked by pre-empting one of its own verbs has a gap in the specification rather than in the user's understanding.

Surfaced by dogfooding, not review. Found running /spectastic.design against a real design source in example-currency-converter — the first time the contract convention met a project that was actually mid-flight rather than already promoted.

The contract view re-derives the sidecar path instead of calling the helper that exists for it

Implementation code

Debugging why a path convention has two authors, root cause was that contracts/materialise-view.ts composes specs/<id>/contracts/<name> inline in two places while sidecarPathsFor exists in the validate scan to be the one place that knows it; fixed by calling the helper; regeneration passes, because the requirement is right and only the code duplicates it.

Expected
One function knows where a proposed contract sits.
Actual
Two do. materialise-view.ts re-derives the path at lines 122 and 168; sidecarPathsFor in commands/validate.ts derives the same thing for the resolve scan, and its own comment says it exists so the convention has a single author.
Diagnosis
The helper lives in the validate module rather than beside the convention, so the view could not reach it without a move. Nothing is wrong today — both derivations agree — which is precisely why it will stay wrong quietly: a change to the convention now has two sites and one of them is easy to miss.
Fix
Move sidecarPathsFor to a module both callers can reach and call it from the view. A judgment call worth stating: it is cross-cutting deterministic logic two verbs want, which is the kernel test the fat-core convention names.
Deep dive — none required

No cross-spec contract, no invariant. Filed rather than fixed inline because the task that asked for it said “file a card”, and because the move has a design question in it the card should carry rather than a drain deciding silently.
