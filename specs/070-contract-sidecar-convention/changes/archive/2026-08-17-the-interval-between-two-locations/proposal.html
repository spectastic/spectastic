The interval between two locations

The interval between two locations

A contract has two homes and a journey between them. The two were specified; the journey was not.

Status Applied Change ID 2026-08-17-the-interval-between-two-locations Spec 070-contract-sidecar-convention Author Brian Corbin · @briancorbinxyz Created 17 Aug 2026 Source 070/T-001 Targets 4 requirements — 2 added, 2 modified Read time

An in-flight design cannot validate. Both paths it could declare are errors: the proposed location is rejected because a path under specs/ can never be effective (FR-002), and the effective location does not exist until promotion runs. Reproduced both ways.

Each requirement is correct alone. What is missing is the interval between them — the period where the design exists, the proposed contract exists, and the effective one legitimately does not. This names that state and makes it silent, and makes the workaround it forced an error.

1 · Intent

The convention has been exercised only by projects whose contracts were already promoted. The first time a design ran against a live source and was still mid-flight, it hit a bind with no legal move: declare the sidecar and the effective-path rule rejects it; declare the effective path and the resolve check reports a missing file.

The run resolved it by writing the contract to both locations. That is not a shortcut, it is the only way through — and it is worse than it looks: it performs promotion ahead of the verb that owns it, leaving 071 nothing to do and no way to distinguish a promoted contract from one pre-copied to silence an error. A documented path that can only be walked by pre-empting one of the tool's own verbs is a gap in the specification rather than in the user's understanding.

The design command's own wording concedes it. It says path= "names the contract's two locations across its lifecycle, never a single fixed file" — which one attribute cannot do, and which FR-002, FR-003 and 071 FR-001 all contradict by reading path= as the effective location and nothing else.

2 · Scope

In scope

  • Naming the pending state, and requiring it be silent.
  • Making two readable copies an error — the state the workaround leaves behind.

Out of scope

  • A proposed= attribute. Not taken here, and not refused: an earlier draft wrote defer-to=never, which closes a door the evidence does not close. promote.ts derives the proposed path as basename(decl.path) — filename only, directory discarded — and the estate has already recorded that derivation as fragile (contract-name-unique documents api/v1/openapi.yaml and api/v2/openapi.yaml colliding on openapi as "the ordinary case, not a corner"), while FR-007 permits more than one effective declaration. Both new requirements inherit that fragility. Deferring lets the convention be tested before a second authoring surface is added. defer-to=TBD-contract-proposed-attribute.
  • Correcting commands/spectastic.design.md's description of path=. Necessary, and a §6 task rather than a requirement — the wording describes a mechanism the spec owns.
  • Whether promotion should run automatically when a change lands. defer-to=071-contract-promotion.

4 · Deltas

What changes — the error requirement gains the pending exception in its own text. Nothing else: the obligation to error on a path with no readable file is carried through word for word, and still fires for every case except the one FR-008 names.

spectastic validate MUST emit an error when a design declares an effective contract path that resolves to no readable file, unless that contract is pending promotion (FR-008).

Rationale

The exception lives here rather than in the new requirement because an earlier draft put it there — an op="added" saying a pending contract "MUST NOT be reported", which negated this requirement's text from another part of the same spec while claiming to narrow nothing. Two must-tier requirements would have contradicted each other with nothing recording which won. Stating the carve-out in the requirement it carves out of is the difference between an amendment and a collision.

What changes — the criterion gains the pending case. Nothing else — both existing counts are carried through unchanged.

A design declaring a contract path with no file behind it produces exactly 1 validate error; the same design with the file present produces 0; and the same design while the contract is pending promotion produces 0.

Rationale

Without the third clause this criterion is unsatisfiable the moment FR-004 gains its exception — it asserts exactly 1 error for a case that now legitimately produces none. Caught by the adversarial pass, which is the second thing it found that would have shipped as a contradiction between two must-tier statements.

What changes — the interval is named. New requirement; the suppression it authorises is written into FR-004 rather than asserted against it.

A design whose declared effective contract does not resolve, while the proposed location holds a contract of that name, is pending promotion. A pending contract MUST NOT satisfy any check that requires an effective contract.

Rationale

The state is the normal condition of every design between authoring and promotion, so erroring on it would fire on all of them — and today it does, which is why a real design run could not validate at all.

The remaining clause is what keeps FR-003 exactly: a pending contract is unreported and uncounted, which are different things. It still cannot mark an enforcement category covered or stand in for an effective declaration.

Both locations are derived rather than declared, following the convention promotion already uses. The recorded ceiling: a design that is never promoted stays silent forever, and this makes that legal. Deliberate — the alternative reports every in-flight design to catch the few that stall — but nothing then detects an abandoned contract, and the honest place to say so is here.

What changes — a pre-copied contract is an error, distinguished from an in-flight amendment by the baseline. New requirement.

A readable contract at both the effective and the proposed location for the same name, with no readable baseline captured for that name, MUST be reported as an error naming both paths.

Rationale

The baseline clause is the whole requirement, and an earlier draft omitted it — asserting instead that two readable copies could only mean a failed promotion or a hand copy. That is false, and 071's own machinery is the proof: captureContractBaseline copies the existing effective file to specs/<id>/contracts/.baseline/<name> at propose time so promotion can refuse on a moved baseline, which requires both copies to be readable together. Two copies is therefore the ordinary state of every contract amendment after the first. Without this clause the requirement would have errored on three of the five committed promotion fixtures — including the one for a successful promotion — and on this repository's own exemplar, while reproducing the exact bind the change was written to remove, one lifecycle step later.

With it, the signal is precise. A baseline present means in flight against a predecessor. A baseline absent beside two live copies means someone pre-copied the effective file, which is what the workaround did and what FR-003's "exactly one copy authoritative" exists to prevent.

5 · Risk register

The first FR-009 made the ordinary state of every contract amendment an error, and would have broken three committed fixtures and the exemplar

It asserted that two readable copies is reachable only by a failed promotion or a hand copy. False, and 071's own machinery is the proof: captureContractBaseline copies the existing effective file to .baseline/<name> at propose time so promotion can refuse on a moved baseline — which requires both copies readable together. So two copies is the normal state of every amendment after the first. It would have errored on fixtures/promotion/match/ (the successful promotion case), two more promotion fixtures, and this repo's committed examples/currency-converter/ — reproducing the exact bind the change exists to remove, one lifecycle step later.

Decisive, and the requirement is rewritten rather than defended. The distinguishing signal was already on disk and unused: a readable baseline means in flight against a predecessor; its absence beside two live copies is the pre-copy. Verified against the fixtures directly. My §6 cleanup task also named only the external app and missed the committed exemplar, which is the same blind spot in a second place.

FR-008 silently narrowed must-tier FR-004 while declaring that it narrowed nothing

Live FR-004 requires an error when a declared effective path resolves to no readable file. The added FR-008 said a pending contract "MUST NOT be reported as a finding" — a direct textual negation, carried by an op="added" under a what-changes line asserting nothing existing was narrowed. Must-tier SC-001 went with it: "exactly 1 validate error" becomes 0 in the pending case, leaving it unsatisfiable as written.

Fixed by moving the carve-out into FR-004's own text, plus a MODIFY on SC-001. This is the fourth silent narrowing caught in this session, and the first that the conformance-dropped guard built for exactly this could not see — the guard compares a MODIFY's post-state against the live requirement, and this was an ADD contradicting a requirement it never touched. Worth recording as the guard's discovered ceiling rather than a surprise: it catches deletion, not contradiction.

defer-to=never forecloses the card's preferred fix on a derivation the estate already records as fragile

The attribute was retired because promote.ts locates the proposed contract by convention. Accurate, but it does not carry the conclusion: the derivation is basename(decl.path) with the directory discarded, and contract-name-unique already documents that exact fragility — api/v1/openapi.yaml and api/v2/openapi.yaml colliding on openapi, "the ordinary case, not a corner" — while FR-007 permits more than one effective declaration. Both new requirements inherit it.

Changed to a deferral. Reversing the card's recommendation is legitimate; doing it with never was not, and the distinction matters — a refusal claims the question is settled when the fragility has not been tested. Now TBD-contract-proposed-attribute, with the collision case named so a later slice starts from the evidence rather than rediscovering it.

A must-tier delta rested on a row stamped verified whose cited source did not support it

KB-0001@2026-07-25 defines verified as a source opened this turn, and forbids a must-tier decision resting on an assumed fact without an accepted risk. Row 4 cited 071 FR-002 — which constrains only the state after promotion — and drew a conclusion about the window before it, which propose.ts refutes. An inference wearing a verified pill, carrying must-tier FR-009.

Restated to say what FR-002 actually constrains, and FR-009 re-derived from the baseline signal. Two further rows were added recording what was checked on disk this turn. The pattern is worth naming: rows 1–3 were genuinely verified and correct, and the false one sat among them reading identically — which is how a grounding table stops being evidence and becomes decoration.
