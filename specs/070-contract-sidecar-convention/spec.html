Specification · 070-contract-sidecar-convention

Contract sidecar convention

Two lifecycle states for one contract — proposed beside its spec, effective at the project's own path — and a check that a declared path actually resolves.

Status Accepted Spec ID 070-contract-sidecar-convention Owner Brian Corbin · @briancorbinxyz Reviewers — Created 31 Jul 2026 Principlesv1.9.0 Smallest demoablespectastic validate reports an error when a design declares a contract path that resolves to no file. Read time

A contract has two lives and only one of them is authoritative at a time. While a change is in flight, the contract it proposes belongs to that change — the way changes/<slug>/proposal.html belongs to its change and not to the live spec. Once the change lands, the contract is the project's, and a consumer must be able to find it without knowing a spec id. This spec names both locations and the rule that separates them: a proposed contract at specs/<spec-id>/contracts/, an effective contract at the path the design declares — the project's own ecosystem-conventional location, not a spectastic-shaped one. Exactly one is live at any instant, so the single-authoritative-location rule holds without giving up per-spec provenance. It also adds the one new deterministic check the survey recommended: a declared contract path that resolves to nothing is a broken artifact, and validate should say so. For authors, reviewers, and the consuming repository.

1 · Context

Once a design can declare a contract path (069), two questions follow immediately: where should that file be, and what stops the declaration pointing at nothing.

The location question looks like a fork and isn't. Putting the contract beside its spec gives excellent provenance — it is how the nearest comparable tool arranges its planning outputs — but makes the current interface's home depend on which spec last touched it, and forces a consumer to know spec ids. Putting it at the project root serves the consumer and the enforcement gate, but leaves an in-flight interface change nowhere to live except the live contract, where a proposed shape and an effective one become indistinguishable while the work is open. The resolution is that these are two states of one artifact, not two locations competing for it — precisely the relationship the propose/apply cycle already models, where an authored change sits with its spec until apply folds it in and archives the source.

The second question is the cheaper one and the reason this slice carries a check at all: a declared path is a promise, and a promise nothing verifies decays. Whose problem: the reviewer who cannot find the file, and the consuming team who discovers the path was stale only after generating from it.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · A declared path that isn't there is caught P1

As a reviewer, I want validate to error when a design names a contract file that does not exist so that a broken declaration is caught at the git boundary rather than by the team consuming it.

Acceptance: A design declaring a path with no file behind it produces exactly one error naming the path; the same design with the file present produces none.

US2 · An in-flight contract is visibly not live P1

As an author, I want to write a proposed contract next to my spec so that reviewers can see the shape I am proposing without it being mistaken for the interface in force.

Acceptance: A contract under specs/<spec-id>/contracts/ is treated as proposed by every consumer; it never satisfies an effective declaration and never marks an enforcement category covered.

US3 · A consumer finds the contract without a spec id P2

As an engineer in a consuming repository, I want the effective contract at the project's own conventional path so that I can find and generate from it without reading the spec estate.

Acceptance: The effective path is a project-relative location the project's ecosystem already uses; no spec id appears in it.

Edge cases

  • A spec that changes an existing contract: its proposed copy is a full file, since a partial delta of a schema is not itself a valid schema.
  • A design declaring a path inside another spec's directory — a proposed contract masquerading as an effective one.
  • A project whose ecosystem has no conventional location, so the declared path is simply wherever the author chose.
  • A declared path that exists but is a directory, or is empty.
  • Two specs in flight declaring the same effective path — legal here; the conflict is promotion's problem.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A proposed contract — one belonging to an unlanded change — MUST live under specs/<spec-id>/contracts/.

Rationale

Mirrors where an unlanded change proposal already lives, so the same mental model and the same review flow apply.

The effective contract MUST live at the project-relative path the design declares, which MUST NOT be inside specs/.

Rationale

The effective contract belongs to the project, not to whichever spec last changed it, and a consumer must reach it without knowing the spec estate.

A proposed contract MUST NOT be treated as effective by any consumer — it MUST NOT satisfy a design's effective declaration and MUST NOT mark an enforcement category covered.

Rationale

This is what keeps exactly one copy authoritative. Without it the two states collapse and the convention becomes ordinary duplication.

spectastic validate MUST emit an error when a design declares an effective contract path that resolves to no readable file, unless that contract is pending promotion (FR-008).

Rationale

The exception lives here rather than in the new requirement because an earlier draft put it there — an op="added" saying a pending contract "MUST NOT be reported", which negated this requirement's text from another part of the same spec while claiming to narrow nothing. Two must-tier requirements would have contradicted each other with nothing recording which won. Stating the carve-out in the requirement it carves out of is the difference between an amendment and a collision.

The convention MUST use the directory name contracts/ for the proposed location, and MUST NOT use references/.

Rationale

references/ already denotes a corpus pack's citable documents, at the same depth under a per-unit directory. Reusing it would collide in vocabulary while sharing no semantics.

The error SHOULD name the declared path and the design that declared it, and SHOULD distinguish "no such file" from "path exists but is not a readable file".

A spec MAY carry more than one proposed contract, and a design MAY declare more than one effective path.

A design whose declared effective contract does not resolve, while the proposed location holds a contract of that name, is pending promotion. A pending contract MUST NOT satisfy any check that requires an effective contract.

Rationale

The state is the normal condition of every design between authoring and promotion, so erroring on it would fire on all of them — and today it does, which is why a real design run could not validate at all.

The remaining clause is what keeps FR-003 exactly: a pending contract is unreported and uncounted, which are different things. It still cannot mark an enforcement category covered or stand in for an effective declaration.

Both locations are derived rather than declared, following the convention promotion already uses. The recorded ceiling: a design that is never promoted stays silent forever, and this makes that legal. Deliberate — the alternative reports every in-flight design to catch the few that stall — but nothing then detects an abandoned contract, and the honest place to say so is here.

Added by this change — what this boundary was drawn for. The condition above answers a reporting question: is an unresolved effective path a defect, or the normal state of a design in flight? For that, keying on the declared path not resolving is exactly right, because a contract that does resolve needs no exemption from a check about missing files. It is not a name for a phase of a contract's life, and reading it as one gets the common case backwards — a contract being amended in place is in flight in every sense a reader means, yet does not meet this condition, because the version being replaced still resolves at the declared path.

Two things that paragraph is deliberately careful about, because a first draft of it got both wrong. It says in place: an amendment that also relocates the contract declares a path that does not resolve while the sidecar holds the file, so it does meet this condition and is pending — the ordinary case once detection widens to ecosystem-conventional paths. And it does not claim the term's reach ends at validate: the clause above binds any check requiring an effective contract, which FR-003 makes concrete by naming the enforcement tally — a consumer that is not validate at all.

This is rationale rather than a rule, and that is the point rather than a compromise. A sentence about how to read a requirement has no defect condition: no artifact, fixture or run can breach it, so wrapping it in a conformance keyword would add must-tier coverage that nothing can cover — the pretence of a check that P-8 excludes. An earlier draft of this very change did exactly that, hours after the same mistake was corrected elsewhere in the estate.

A readable contract at both the effective and the proposed location for the same name, with no readable baseline captured for that name, MUST be reported as an error naming both paths.

Rationale

The baseline clause is the whole requirement, and an earlier draft omitted it — asserting instead that two readable copies could only mean a failed promotion or a hand copy. That is false, and 071's own machinery is the proof: captureContractBaseline copies the existing effective file to specs/<id>/contracts/.baseline/<name> at propose time so promotion can refuse on a moved baseline, which requires both copies to be readable together. Two copies is therefore the ordinary state of every contract amendment after the first. Without this clause the requirement would have errored on three of the five committed promotion fixtures — including the one for a successful promotion — and on this repository's own exemplar, while reproducing the exact bind the change was written to remove, one lifecycle step later.

With it, the signal is precise. A baseline present means in flight against a predecessor. A baseline absent beside two live copies means someone pre-copied the effective file, which is what the workaround did and what FR-003's "exactly one copy authoritative" exists to prevent.

Non-functional

The check MUST be deterministic and filesystem-only — at most 0 network calls, and no dependence on wall-clock time or environment beyond the project directory.

Rationale

Matches the determinism the validate engine already guarantees, so the check is safe in the pre-commit gate and in CI.

The check SHOULD add under 50 ms to a whole-project validate run.

Out of scope (deferred to other slices)

  • Moving a proposed contract to its effective path when the change lands, and refusing to clobber.
  • Showing any of the contract's content inside the design artifact.
  • Teaching the enforcement detector to find contracts at ecosystem-conventional paths, so a declared effective contract also satisfies the floor.
  • Making the effective contract addressable and consumable across repository boundaries.

4 · Data model

No persisted entity beyond files already on disk. This spec fixes the meaning of two locations and adds one derived judgment.

Entities

Proposed contract
A contract file under a spec's own contracts/ directory. Belongs to an unlanded change; never authoritative.
Effective contract
The contract file at the path a design declares, outside specs/. The single authoritative shape of that interface at any instant.
Resolution result
Derived, not stored: whether a declared effective path names a readable file. Feeds the FR-004 finding.

The invariant worth stating: at any instant, for a given interface, exactly one file is effective. A proposed contract does not reduce that count and does not compete with it — which is the whole reason two locations are safe here and would not be if both were live.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

A design declaring a contract path with no file behind it produces exactly 1 validate error; the same design with the file present produces 0; and the same design while the contract is pending promotion produces 0.

Rationale

Without the third clause this criterion is unsatisfiable the moment FR-004 gains its exception — it asserts exactly 1 error for a case that now legitimately produces none. Caught by the adversarial pass, which is the second thing it found that would have shipped as a contradiction between two must-tier statements.

Across 100% of fixtures, a contract present only under specs/<id>/contracts/ fails to satisfy an effective declaration — the proposed state never counts as the effective one.

A whole-project validate run over the existing spec estate gains under 50 ms and reports 0 new findings, since no design declares a contract path yet.

6 · Assumptions

Declared paths are project-relative and stable across checkouts. Absolute paths and paths outside the project are treated as malformed rather than resolved.

A contract small enough to be worth checking in is small enough to read from disk during a validate run without a caching layer.

7 · Open questions

None outstanding — the two-state model, the directory naming, and the single new check were settled by the survey that produced this slice.
