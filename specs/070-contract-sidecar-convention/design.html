Design · 070-contract-sidecar-convention

Contract sidecar convention

How we will build it.

Status Accepted Spec 070-contract-sidecar-convention Owner Brian Corbin · @briancorbinxyz Branch main Created 01 Aug 2026 Read time

Two locations and one check. The convention is documentation — a proposed contract at specs/<id>/contracts/, the effective one at the path the design declares — and the only executable work is a resolve check that errors when a declared path names no readable file. That check cannot be a schema rule: the rule engine is pure-AST with zero filesystem imports, so it lands as a core contractResolveFindings() folded in by a CLI scanContractResolve, exactly as the waiver and quantified-NFR scans already do. This slice also lands the shared readContractDeclarations() that 071–074 all import, which is why it is the cohort's prerequisite.

3 · Data model & contracts

No persisted entity. The spec's conceptual entities are two locations and one derived judgment; physically they are paths on disk and a returned Finding[].

Conceptual entityPhysical shapeNotes
Proposed contract specs/<spec-id>/contracts/<name> A path convention, not a type. Never read by the resolve check — FR-003 requires it never satisfy an effective declaration.
Effective contract The path= attribute of a <spec-contract>, resolved against the project root Project-relative and outside specs/. Read via the new ContractDeclaration record.
Resolution result Derived — a Finding or nothing Three distinguishable outcomes per FR-006: readable file (silent), no such path, path exists but is not a readable file.

No interface. This slice adds a library function, a finding producer and a CLI scan — all internal to the toolchain, none of them a wire surface another repository calls. The subject of the work is contracts; the work itself exposes none.

5 · Approach

Three pieces, in dependency order. First, readContractDeclarations(designHtml) in @spectastic/schema behind a new ./contract subpath: a pure function returning ContractDeclaration[] ({ shape, direction?, path?, format?, line, column }). It is the single parse of the 069 element, and 071–074 all import it rather than re-deriving it — the reason this slice is the cohort's prerequisite.

Second, contractResolveFindings() in @spectastic/core: given the declarations, the design's path and a filesystem port, it returns one Finding per declaration whose path= does not resolve to a readable file, distinguishing absent from present-but-not-a-readable-file per FR-006. Third, a thin scanContractResolve(files, cwd) in the CLI that reads the design files being validated and folds the findings in — the same nine-line shape scanQuantifiedNfr already has. The convention itself (contracts/, never references/) is documentation: a paragraph in the design template's §3 comment and a line in the command markdown.

6 · Alternatives considered

The load-bearing choice is where the resolve check lives, since it must read the filesystem. Scored 1–5, higher is better.

OptionFits the engineReuses precedentCost to buildTotal
A schema rule with a filesystem escape hatch1135
A standalone spectastic contracts verb4228
Core finding producer + thin CLI scan — chosen55414

The schema-rule option is the one to name and reject explicitly: it reads as the obvious home because every other validate check is a rule, but it would be the first rule anywhere to touch the filesystem, breaking an invariant 34 rules currently hold. A separate verb scores better on fit but worse on everything else — it would put a check nobody runs outside the gate that already blocks commits, which is precisely the P-8 failure mode.

7 · Decisions

D-001 · readContractDeclarations() lands in @spectastic/schema behind a ./contract subpath

Status
Accepted
Context
Four sibling specs (071–074) each need to read the same 069 element. P-14's test — would a second caller want this without the CLI — answers yes four times over. packages/schema/package.json already publishes ./slo and ./project as narrow subpaths, so the shape is established.
Decision
A pure readContractDeclarations(html): ContractDeclaration[] in packages/schema/src/contract-shared.ts, exported as @spectastic/schema/contract, cloning slo-shared.ts's file and export shape.
Consequences
+ One parse, four consumers; the attribute grammar has a single owner. + 071–074 touch disjoint files afterwards and genuinely parallelise. − 070 becomes a hard prerequisite for the cohort, so the drain is one-then-four rather than five-abreast.

D-002 · The resolve check is a folded core scan, not a schema rule

Status
Accepted
Context
A grep for node:fs, readFileSync and existsSync across packages/schema/src/rules/ returns zero matches — all 34 rules are pure AST over a parsed document. FR-004 needs a filesystem stat. The established seam is a core *Findings() plus a CLI scan*, used by copyLeakFindings/scanCopyLeak and six siblings.
Decision
contractResolveFindings() in @spectastic/core, folded by scanContractResolve(files, cwd) in the CLI. No schema rule is added.
Consequences
+ The pure-AST invariant survives intact. + Inherits the pre-commit gate for free, like every other folded scan. − The check does not fire from a bare validate(html) library call, only through the CLI — the same boundary the waiver and quantified-NFR scans already accept, recorded in §10.

D-003 · A proposed contract is excluded structurally, by path, not by inspection

Status
Accepted
Context
FR-003 requires a proposed contract never satisfy an effective declaration. Since a proposed and an effective contract can be byte-identical, no content test can separate them — only location can.
Decision
A declared path= resolving inside specs/ is itself the error: the resolve check rejects it rather than stat-ing it. This makes FR-002's "MUST NOT be inside specs/" machine-checked rather than merely stated.
Consequences
+ One rule enforces FR-002 and FR-003 together. + A proposed contract can never be mistaken for effective, even byte-identical. − A project that genuinely wants a contract under specs/ cannot have one; that is the intended constraint, not a limitation.

D-004 · A declared path is contained to the project directory

Status
Accepted
Context
P-11 treats artifact text as data, and a path= is attacker-influenceable text in an ingested artifact. NFR-001 already bounds the check to the project directory.
Decision
Resolve the declared path against cwd and reject anything escaping it — a leading /, any .. traversal, or a resolved path outside the project root — as a finding rather than following it. No symlink is traversed out of the project.
Consequences
+ A hostile design cannot make validate stat arbitrary filesystem locations. + Keeps the "project-relative" wording of FR-002 literally true. − An intentional out-of-tree contract (a sibling checkout) is unsupported; that is a monorepo-boundary question 076 owns.

D-005 · The convention itself ships as documentation, not a check

Status
Accepted
Context
FR-005 fixes the directory name contracts/ and forbids references/. Nothing generates the proposed directory, so there is no write path to gate; a check would have to invent an occasion to fire. Pure judgment.
Decision
State the convention in the design template's §3 comment and the command markdown. Add no rule for the directory name.
Consequences
+ No rule that fires on a project which simply has no contracts yet. − The references/ prohibition is review-caught; acceptable because the corpus already owns that word and the collision would be immediately obvious.

9 · Risks & mitigations

RiskLikelihoodImpactMitigation
The reader's shape is wrong for a sibling, forcing a breaking change mid-cohortMMThe record is deliberately wider than 070 needs — it carries shape, direction and format though only path is used here, precisely so 072/073/074 need no change. Additive fields stay additive.
The scan misses the design files because validate was invoked on a narrow globMLThe scan reads the files it is given, exactly as scanQuantifiedNfr does; a narrowed glob narrows every check equally, which is understood behaviour rather than a new trap.
The specs/-containment rule (D-003) false-positives on a project that nests its whole tree under a directory called specsLMThe comparison is against the resolved project-relative prefix, not a substring match, so a path like myspecs/api.yaml is unaffected. Covered by a fixture.
Perf regression on very large estatesLLThe scan is O(declarations) with one stat each, and the estate currently declares zero. The existing perf test holds the budget.

10 · Complexity tracking

Where this design accepts a ceiling, the reasoning lives here.

The resolve check does not fire from the library API. D-002 puts it in the folded-scan layer, so a caller invoking validate(html) directly gets every schema rule but not this check. That is the boundary the eight existing folded scans already sit behind — the alternative is a filesystem-touching rule engine, which is a much larger change than this slice justifies. Recorded, not hidden.

The references/ prohibition is review-caught. D-005 ships the naming convention as prose. A machine check would need an occasion to fire and would fire on every contract-less project. The collision it guards against — the corpus already owning references/ — is loud enough that a reviewer catches it.

Readability is judged by a successful read, not by a permissions model. FR-006 asks the finding to distinguish "no such file" from "exists but is not a readable file". The check answers that by attempting the read and classifying the failure, rather than by reasoning about modes and ownership — which is portable across platforms where a mode bit is not the whole story.
