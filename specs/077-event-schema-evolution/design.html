Event schema evolution

How we will build it.

Status Accepted Spec 077-event-schema-evolution Owner Brian Corbin · @briancorbinxyz Branch main Created 01 Aug 2026 Read time

Two interview questions and one attribute pair. The vocabulary survey settled the words — the four registry terms, with transitivity promoted from a suffix to its own question because replay makes the ecosystem's latest-version-only default near-meaningless. The stance rides on the existing <spec-contract> element as two attributes rather than a new element, so it renders through CSS with no JavaScript. Nothing enforces it: the whole slice is a prompt, a record, and a copy rule forbidding the tool from ever implying it verified the claim.

5 · Approach

The design interview gains two questions, asked only when a design changes a declared event contract. The first is the direction — backward, forward, full or none — with each option carrying its meaning inline rather than the bare term, because the survey found the names are routinely misread and the artifact must be legible to someone who has never used a registry. The second is the scope: does the claim hold against the latest version only, or against all retained history? That second question is the survey's central finding and FR-003's second half, and it is the one a diff-based check silently collapses.

Both answers land as attributes on the existing <spec-contract> element, so the stance identifies its contract structurally and renders through the same CSS attr() mechanism the card already uses. A shape rule extends 069's to validate both enums. Nothing enforces the stance — but one thing here is deterministically checkable and is checked: the copy. SC-003 requires generated text claim zero verified properties, so the rendered label reads as an explicit claim ("producer claims…") and a content test pins that wording so a later edit cannot quietly upgrade a claim into an assertion.

No architecture sketch: the feature is two attributes and a prompt, which is one moving part in the sense the design procedure means.

6 · Alternatives considered

The load-bearing choice is how the stance is recorded, given it must identify its contract and survive scripting being off. Scored 1–5, higher is better.

OptionBinds to its contractVocabulary costRenders JS-offTotal
A new <spec-compatibility target=…> element32510
Prose in the design's contract section25512
Two attributes on <spec-contract> — chosen54514

A dedicated element would need a target= to point back at its contract — reintroducing a reference that can dangle, when nesting already makes the binding structural. Prose is cheapest and cannot be validated: SC-001 wants 100% of qualifying designs to carry a stance, which needs something machine-readable to count.

7 · Decisions

D-001 · Two axes — the four registry words, plus scope as its own question

Status
Accepted
Context
The vocabulary survey found the four terms are format-independent and standard, and that the ecosystem's non-transitive default checks only against the latest version — near-meaningless under replay. FR-003 had already asked the prompt to separate future-message compatibility from readability of already-published messages.
Decision
compatibility= ∈ {backward, forward, full, none} and compatibility-scope= ∈ {latest, all}. Every prompt option states its meaning inline; the bare term is never shown alone.
Consequences
+ Satisfies FR-003 by construction. + Uses words the ecosystem already knows, so no translation cost. + Makes visible the single thing a step-wise check hides. − Two attributes rather than one; the alternative encodes the scope as a suffix, which is exactly the burial the survey argued against.

D-002 · The stance is attributes on the existing element, not a new one

Status
Accepted
Context
A stance is a property of a declared contract, not an independent thing. 069's <spec-contract> already renders attributes through CSS attr() and already has an optional-attribute precedent in its [direction] badge. FR-002 requires the record identify which contract it applies to.
Decision
Two attributes on <spec-contract>. No new element, no target=.
Consequences
+ The binding is structural, so a stance can never dangle or point at the wrong contract. + Inherits the JS-free rendering, satisfying P-4 with no new mechanism. + A multi-contract feature gets a per-contract stance for free. − The element's attribute set grows; bounded because both are optional and absent for non-event contracts.

D-003 · The prompt fires only on a change to a declared event contract

Status
Accepted
Context
FR-004 requires a design changing no published payload to prompt for nothing — at most 0 additional questions — and SC-001 measures it. 069's declaration already records the interface shape, so shape="event-driven" is the available antecedent.
Decision
Gate the questions on a declaration whose shape is event-driven and whose contract is changing. A request/response design, or an event design that changes no payload, is asked nothing.
Consequences
+ No interview tax on the common case, which is what keeps the addition acceptable. + Reuses 069's shape rather than inferring from a broker dependency, which cannot distinguish a producer anyway. − Depends on the shape being declared honestly; a mis-declared design is not prompted, which is the same declaration-trust 073 already rests on.

D-004 · Nothing enforces the stance; the copy rule is the one deterministic check

Status
Accepted
Context
The survey's D-003 settled this: FR-005 forbids claiming to determine compatibility; registry validation and structural detection are out of scope; and 074 already owns is-a-check-configured for contracts generally. But P-8 asks for the strongest available check, and one exists — SC-003's requirement that generated copy claim 0 verified properties is checkable.
Decision
No enforce category, no registry detection, no tier gate. Add a content test pinning the claim-not-verification wording in both the rendered label and the template, so the honesty clause cannot silently erode.
Consequences
+ The tool never implies it verified something it cannot. + No duplication with 074. + The one checkable thing is checked, rather than the slice shipping with no deterministic half at all. − Whether the stance is true is review-caught, permanently; recorded in §10.

10 · Complexity tracking

P-8 exception — the prompt cannot be forced, and the stance is not verified. Two unenforceable things sit here, and they are different. Whether the interview asks is a judgment step P-8 concedes cannot be forced and which leaves no residue when skipped — the backstop is review. Whether the stance is true is not merely unenforced but undecidable by this tool, since it would require knowing every consumer. What P-8 does demand is the strongest available check, and one exists: the copy honesty rule, which is deterministic and is taken. Recorded rather than glossed, because a slice whose only deterministic artifact is a wording test invites the assumption that nothing was checked at all.

"All retained history" is an intent, not a measured window. Transitive compatibility over a seven-day topic is a far weaker promise than over an infinitely retained one, and retention windows are explicitly out of this spec's scope. The scope question therefore records what the producer intends to hold, and the survey records this ceiling too. A future slice that knows retention could tighten it.

Format mechanics can break consumers beneath a satisfied stance. A Protobuf producer reusing a retired field number breaks readers while honestly declaring backward, because the wire format reinterprets old bytes silently. That is structural detection, out of scope by the spec's own list, and no vocabulary substitutes for it. The stance records intent; it does not inspect the payload.
