Event schema evolution

A published event outlives the consumers it was written for — so "is this change breaking" is a different question for events than for requests.

Status Accepted Spec ID 077-event-schema-evolution Owner Brian Corbin · @briancorbinxyz Reviewers — Created 31 Jul 2026 Principlesv1.9.0 Smallest demoableA design changing a published event's payload is prompted for its compatibility stance, and the decision is recorded where a reviewer can see it. Read time

For a request/response API, "who breaks if I change this" has a bounded answer: whoever is calling you. For a published event it does not. Events persist, are replayed, and are consumed by systems that did not exist when the payload was written — so a change is not bounded by today's consumers, and the usual diff-the-two-versions check answers a narrower question than the one that matters. The field's own conclusion is that the best outcome is to avoid breaking changes rather than version around them, supported by consumer-driven contracts, schemas published as libraries, or registry-plus-broker validation — three answers with very different operational weight. What spectastic can honestly contribute is not a compatibility engine but the thing it is uniquely placed to hold: the decision. A design that changes a published payload should be asked what compatibility it intends, and that stance should be recorded as reviewable provenance rather than discovered later from a replay failure. The enforcement half — whether a registry or a validator is wired up — is deliberately left open until the compatibility model is chosen.

1 · Context

Once the tool can see an event-driven interface and ask for a contract, the harder question arrives immediately: what happens when the payload changes. For a synchronous API this is well-trodden — diff the old description against the new, classify the changes, block the breaking ones. The tooling is commodity and the blast radius is knowable, because the callers are the callers.

Events break that assumption in two ways. They persist, so a consumer may read a message written months ago against a schema that has since moved. And they are consumed by systems the producer may not know about, so the set of things a change can break is not enumerable at change time. A diff still tells you something useful; it just answers a narrower question than the one being asked.

The field's practical answers are all heavier than a diff: consumer-driven contracts that require organisation-wide buy-in, schemas published as code libraries that shift the problem to dependency management, or a registry that validates at publish and runtime and costs real infrastructure. None of these is a thing a spec tool should build, and choosing between them is exactly the organisational judgment the tool should not pre-empt. What it can do — and what nothing else in the stack does — is make sure the decision was consciously taken and is visible to a reviewer. Whose problem: producers changing a payload, and every consumer who would otherwise learn about it from a replay.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Changing a payload is a conscious decision P1

As a producer, I want to be asked what compatibility I intend when I change a published payload so that the decision is taken deliberately rather than discovered by a consumer.

Acceptance: A design that changes a declared event contract prompts for a compatibility stance; a design that changes no published payload prompts for nothing.

US2 · A reviewer can see the stance P1

As a reviewer, I want the intended compatibility recorded in the design so that I can challenge it before it ships rather than after a replay fails.

Acceptance: The recorded stance is visible in the design artifact and identifies which event contract it applies to.

US3 · The replay case is named, not assumed away P2

As a producer, I want the prompt to raise the possibility of historical consumers so that I answer for messages already published, not only for the consumers I currently know about.

Acceptance: The prompt distinguishes compatibility for future messages from readability of already-published ones.

Edge cases

  • A field added with a default — non-breaking for readers, potentially breaking for strict validators.
  • A field removed that no known consumer reads, but historical messages still contain.
  • A semantic change with no structural change — same shape, different meaning, invisible to any diff.
  • An event retired entirely while its history is retained.
  • A payload change in a project with no retention at all, where replay is not a concern.
  • A first version, with no history and no consumers.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A design that changes a declared event contract MUST prompt for the intended compatibility stance.

Rationale

The cheapest available improvement on a problem whose other fixes are infrastructural: make the decision conscious.

The chosen stance MUST be recorded in the design artifact, identifying the event contract it applies to.

Rationale

An unrecorded decision is indistinguishable from no decision at review time, which is the only time it can still be cheaply challenged.

The prompt MUST distinguish compatibility for future messages from readability of already-published ones.

Rationale

This is the distinction that makes events different from requests, and the one a diff-based check silently collapses.

A design that changes no published payload MUST prompt for nothing: at most 0 additional questions.

Rationale

Most designs touch no event contract. A prompt they always see is noise that trains people to dismiss it.

The tool SHOULD NOT claim to determine whether a payload change is compatible: it records a stance and SHOULD say plainly that the stance is the author's claim, not a verified property.

Rationale

Semantic changes are invisible to structural analysis, and the consumer set is not enumerable. Overstating what the record proves would be the same overclaim the security categories are careful to avoid.

The recorded stance MAY feed the change notification produced on promotion, so a consumer receives the producer's intent alongside the fact of the change.

Non-functional

The addition MUST be deterministic and local: at most 0 network calls, and at most 0 dependencies on a running broker or registry.

Rationale

A design-time question must work offline and in CI, where no messaging infrastructure exists.

The prompt MUST respect the existing decision-phase limits — at most 4 questions per call, each offering 2–4 options.

Out of scope (deferred to other slices)

  • Consumer-driven contract testing, which needs both sides running.
  • Schema-registry validation at publish or runtime.
  • Structural breaking-change detection, which answers the narrower question well.
  • Retention and replay windows, which determine how far back compatibility must reach.

4 · Data model

No persisted entity. One authored decision, recorded in an artifact that already exists.

Entities

Compatibility stance
The producer's intent for a payload change: whether existing consumers continue to work, and whether already-published messages remain readable. Authored, not derived.

The invariant worth holding: the stance is a claim, never a verified property. The moment it is presented as verified, the record becomes worse than nothing — a reviewer stops checking a thing the tool never actually established.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

100% of designs that change a declared event contract carry a recorded compatibility stance; designs changing none carry at most 0 such prompts.

A reviewer reading the design can state, without consulting the producer, what the author claims about existing consumers and about already-published messages.

Generated copy describing the stance is checked to claim at most 0 verified compatibility properties.

6 · Assumptions

Producers can answer a compatibility question at design time. Where they cannot, the honest answer is "unknown", which is itself worth recording and is a better outcome than an unasked question.

A recorded stance changes reviewer behaviour. If it does not, this slice has bought provenance and nothing else — which is the weakest honest claim it makes.

7 · Open questions

None outstanding. Both were settled on 01 Aug 2026 by the event compatibility vocabulary survey this register called for.

The vocabulary is the four registry terms — backward, forward, full, none — with each option's meaning pinned inline rather than named bare, so the artifact is legible without registry experience. The survey found the words are format-independent: Avro, Protobuf and JSON Schema differ in mechanism (default values versus field numbers), not in what the four terms mean, so adopting them imports no format's semantics. The survey also found the ecosystem's non-transitive default checks a new schema only against the latest version, which is close to meaningless under replay — so transitivity is promoted from a suffix to a second question, which is what FR-003 had already asked for.

Nothing enforces the stance, at any tier. FR-005 forbids the tool claiming to determine compatibility; registry validation and structural detection are already out of scope; and 074 owns the is-a-check-configured question for contracts generally, so an event-specific version would duplicate it while proving less. The stance is recorded and surfaced; any future enforcement is its own slug.
