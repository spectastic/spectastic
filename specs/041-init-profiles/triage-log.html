Composed principles.html used ../assets/ instead of root-relative assets/

Implementation code

Debugging a broken stylesheet/script load in a project scaffolded with init --profile, root cause was implementation drift — the composer never rewrote the template's ../assets/ paths for the project-root destination; fixed by a one-line rewrite in renderPrinciplesHtml; regeneration passes (the 041 spec/plan don't mandate the rewrite, so the gap is code, not contract).

Expected
principles.html at the project root links assets/spec.css (next to the init-copied assets/ dir).
Actual
It linked ../assets/spec.css — one level above the project root — so CSS/JS 404'd when opened.
Diagnosis
compose.ts:renderPrinciplesHtml read templates/principles.html (which previews from one level down, so uses ../assets/) and filled it without the depth rewrite the /spectastic.principles verb documents. FR-002.
Fix
packages/cli/src/commands/init/compose.ts — html.split('../assets/').join('assets/') after reading the template. Landed with a regression test (compose.test.ts). ✓ done.
// rewrite template's ../assets/ to root-relative assets/ for the project-root file html = html.split('../assets/').join('assets/');
Deep dive — verification-discipline note

No cross-spec contract, no invariant, no hotfix needed. Worth recording why the original 041 browser verification missed this: the check served the file over http.server, which clamps a leading ../ back to the web root, so ../assets/spec.css happened to resolve. Presence- when-served is not correctness-in-context (the CLAUDE.md "presence is not containment" lesson). The regression test now asserts the literal path, not a served render.

Enterprise "ship dark by default" language forces a pointless launch gate on a first slice

Spec upstream

Debugging a dogfooded agent's "what feature flag did we use?" self-audit on a first CLI slice, root cause was over-strict profile language — the enterprise "Ship dark by default" principle reads absolutely ("every new feature behind a toggle") with no carve-out for the case a toggle exists to handle: existing users; fixed by encoding the "no prior users → nothing to gate" exception in the seeded principle + AGENTS line; regeneration fails at the profile content — every future enterprise project inherits the same ambiguity.

Expected
The seeded toggle discipline says what it's for — protecting people already relying on the system — so an agent doesn't gate a first slice that has no users to protect, and isn't tempted to flag the (correct) no-gate choice as non-compliant.
Actual
"Every new feature ships behind a toggle, off by default" reads absolutely. On a fresh CLI slice the agent had to reason its way to the exception each time, and a strict read would demand a useless launch gate (TICTACTOE_ENABLED=1) on the whole app.
Diagnosis
The enterprise profile's "Ship dark by default" principle + the AGENTS toggle line (spectastic-profiles.json, seeded by FR-002) state the rule without its rationale — a toggle protects existing users, and an initial shell has none. The behaviour was correct; the language forced re-derivation and admitted a strict misreading.
Fix
spectastic-profiles.json — reword the enterprise "Ship dark by default" principle + toggle AGENTS line to carve out the initial-shell / no-prior-users case ("gate new behaviour once there are users to protect; a first slice has nothing to gate"). ✓ done.
Deep dive — the toggle's purpose is the missing half

No cross-spec contract; no hotfix. The insight is that a feature toggle is a rollout-safety mechanism — it protects an installed base from a bad flip. A project with no installed base has nothing to protect, so gating its initial shell is cost with no benefit. Sibling slices (a rematch loop, a difficulty picker) do layer behaviour on a now-live app and genuinely need the toggle — the discipline reappears exactly when it earns its keep. Encoding the why in the seeded language means a future agent reads the exception instead of re-deriving it (or, worse, complying literally). Confirmed by the user as the correct reasoning.
