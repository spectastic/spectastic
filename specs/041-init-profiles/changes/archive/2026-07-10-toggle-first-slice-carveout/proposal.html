Reword enterprise "ship dark by default" — carve out the first slice

A toggle protects existing users. A project with no users has nothing to gate.

On a dogfooded Enterprise/Java first slice, an agent self-audited "what feature flag did we use?" — correctly concluding none was needed, because a toggle protects existing users and a fresh app has none. The reasoning was right, but the seeded "Ship dark by default" language reads absolutely, forcing that re-derivation each time and admitting a strict misreading (gate the whole app behind APP_ENABLED=1). This change rewords the enterprise profile's principle + toggle AGENTS line to encode the carve-out: gate new behaviour once the project has users to protect; the initial shell is exempt. A single content modification to spectastic-profiles.json; no numbered requirement changes.

Reword enterprise "ship dark by default" — carve out the first slice

Applied

1 · Intent

The enterprise profile seeds a "Ship dark by default" principle stating "every new feature ships behind a toggle, off by default." Triage T-002: on a first CLI slice with no prior users, that rule has nothing to protect — a launch gate would be pure cost. The dogfooded agent reached the right answer but had to derive the exception, and a stricter reading would demand the pointless gate. A feature toggle is a rollout-safety mechanism for an installed base; the seeded language stated the rule without that rationale, so it mis-fired on the one case (no users yet) where the rule doesn't apply. This change bakes the why into the seeded content so every enterprise project inherits the nuance.

2 · Scope

In scope

  • MODIFY the enterprise "Ship dark by default" principle statement + the enterprise toggle AGENTS line in spectastic-profiles.json to carve out the initial-shell / no-prior-users case.
  • Card the finding (T-002) and record the resolution.

Out of scope

  • Adding a numbered FR to 041's spec.html — this is a refinement of seeded profile content (data), not a change to the profile mechanism (FR-001..FR-009 unchanged).
  • Weakening the toggle discipline for a live app — once there are users, new behaviour is still gated; only the userless initial shell is exempt.

3 · Approach

A single content modification. State the rule with its purpose: the toggle protects people already relying on the system, so it binds new behaviour layered on a live app and exempts a first slice that has no one to protect. Adversarial pass did not auto-fire (a content-wording refinement to profile data, single topic, no must-tier spec.html requirement touched).

4 · Deltas

Before (enterprise profile principle):

Every new feature ships behind a toggle, off by default. Nothing reaches all users without a deliberate, reversible flip.

After — keyed on observable state (a change to a working system vs. bootstrapping it), not the agent-unobservable "are there users," and kept to one sentence so it stays lean:

A change to a working system ships behind a toggle, off by default — it reaches users by a deliberate, reversible flip. Standing the system up the first time is not a change to gate.

The enterprise toggle AGENTS line gains the same one-clause carve-out: "…a change to an already-working app ships behind a feature toggle, off by default (standing the app up the first time is not gated); …".
