Tasks · 002-validate-cli

spec-html schema + spectastic validate

Ordered, parallelizable work. Tests precede implementation. Drive through with /spectastic.implement — one task per invocation.

Status Accepted Spec 002-validate-cli Design design Branch 002-validate-cli Created 14 Jun 2026 Read time

50 tasks across five phases. Setup wires the pnpm monorepo and per-package scaffolds; Foundational builds the engine and types every rule depends on; US1 ships the local-validate path with all twelve rules and the human formatter; US2 adds JSON + SARIF formats and the cross-CI demonstrations; US3 polishes the schema as a published library; Polish closes docs and CI. Tasks marked [P] can run in parallel — different files, no dependency. Tests for each story MUST be written and failing before its implementation tasks start.

1 · Execution strategy

Implement US1 end-to-end (the 12 rules + the human CLI). Ship as v0.1.0. Iterate to US2 (JSON + SARIF + CI examples) and US3 (library polish) only after US1 is verified against the existing artifacts.

Setup → Foundational → US1 → US2 → US3 → Polish. Each story closes its conformance before the next opens. Lowest coordination cost; recommended for solo work.

One developer drives Foundational solo. After T-014 lands, one developer per user story works in parallel — the schema rule registry is the seam they coordinate on via the spec. Coordinate at packages/schema/src/index.ts and the registry, not in chat.

3 · Phase 2 — Foundational

Shared schema infrastructure. Order matters — engine depends on parser and types; index re-exports everything.

Define Finding, Rule, Severity, RuleContext types (the wire format between engine and consumers per D-001) packages/schema/src/types.ts
Wrap parse5 with sourceCodeLocationInfo; expose walk(doc, fn) and getElementLocation(el) helpers (D-002) packages/schema/src/parser.ts
Implement engine: takes parsed doc + rule list + context, runs each rule, returns Finding[]; computes summary counts packages/schema/src/engine.ts
Empty frozen rule registry exporting Rule[] (rules wire themselves in during Phase 3a) packages/schema/src/rules/index.ts
Public schema package surface: export validate(html, options): Finding[], types, rules registry — and nothing else (per FR-013, supports US3) packages/schema/src/index.ts

4 · Phase 3a — US1 · Author validates locally P1

Run spectastic validate path/to/spec.html against any file and get anchored findings with the right exit code. Tests fail first; rules land independently.

Tests (write & fail first)

Rules harness: walk packages/schema/fixtures/<rule-id>/ pairs and assert each positive triggers the matching rule, each negative does not packages/schema/test/rules.test.ts
Integration: validate every real artifact in the repo (specs/000-spectastic/spec.html, examples/triage-log.html, archived proposals, principles.html, specs/**); assert zero error findings (SC-001) packages/schema/test/integration.test.ts
CLI: spawn the compiled binary; assert exit codes (0 / 1 / 2) and human output format for clean, broken, and bad-arg inputs (FR-002, FR-003) packages/cli/test/cli.test.ts

Rules (one task per rule; each task ships fixture pair + impl + registry wire-in)

CLI shell + human formatter

commander entry: registers validate subcommand; default action prints usage and exits 2 (FR-001) packages/cli/src/index.ts
validate subcommand: reads paths, calls schema.validate, runs cross-file aggregation, dispatches to formatter, computes exit code (FR-001, FR-002, FR-014) packages/cli/src/commands/validate.ts
tinyglobby wrapper: expands patterns, exits 2 on matched-nothing, applies default --ignore for **/archive/** and **/withdrawn/** (mitigates the no-duplicate-ids false-positive risk in plan §7) packages/cli/src/glob.ts
Human formatter: one line per finding (file:line:col, rule, severity, message, fix hint) + summary line "N errors, M warnings"; picocolors for colour (FR-003) packages/cli/src/formatters/human.ts
Binary entry: shebang + import compiled index — must work both as `npx @spectastic/cli` and `npm i -g` install (NFR-002) packages/cli/bin/spectastic

Perf gate

Perf test: measure validate() p95 over the existing example set; assert <100 ms per file under 5,000 lines (NFR-001) packages/schema/test/perf.test.ts
