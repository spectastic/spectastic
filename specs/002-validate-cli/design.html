Design · 002-validate-cli

spec-html schema + spectastic validate

How we will build it.

Status Accepted Spec 002-validate-cli Owner Brian Corbin · @briancorbinxyz Branch 002-validate-cli Created 14 Jun 2026 Read time

Two TypeScript packages under a pnpm-compatible monorepo: @spectastic/schema owns parsing, the rule registry, and the engine; @spectastic/cli owns argv (commander), glob expansion, and the three output formatters (human / JSON / SARIF). parse5 reads spec.html with per-element source locations; vitest drives fixture pairs per rule. Biggest risk: SARIF subset compatibility across GitHub Code Scanning and GitLab Security Reports — pinned to documented common subset, smoke-tested via two CI workflow examples under docs/ci-examples/.

2 · Technical context

Language(s)
TypeScript 5.x targeting Node 20 LTS+. ESM-only packages.
Frameworks
parse5 (HTML5 parser w/ source-location tracking), commander (CLI argv), tinyglobby (glob expansion), picocolors (terminal colour). No web framework, no runtime DI.
Build
tsup (esbuild wrapper) per package; emits ESM + .d.ts. Single root pnpm-workspace.yaml; the canonical installer is pnpm, with pacquet permitted as a faster local alternative.
Storage
None. Validator is a pure function over an HTML string; engine state is request-local.
Testing
vitest. Fixture-driven per rule (one positive + one negative spec.html under packages/schema/fixtures/<rule-id>/); integration tests validate every real artifact in the repo; perf test asserts NFR-001 against the canonical examples.
Perf targets
NFR-001: <100 ms p95 per file under 5,000 lines.
Constraints
Schema package SHOULD have zero runtime deps beyond parse5. CLI installable via npx and npm i -g per NFR-002. Output formats fixed at three (FR-003/FR-004/FR-005).

3 · Approach

A five-stage pipeline. The CLI shell (commander) reads argv and expands globs into a flat list of file paths. Each file is read into a string and handed to the schema package's validate(html, options) function, which parses with parse5 (preserving source locations on every element), walks the rule registry once per file, and returns an array of Finding. The CLI accumulates findings across files, runs the cross-file no-duplicate-ids rule once over the aggregate, then dispatches the full list to the requested formatter — human (default, with picocolors), JSON (structured array), or SARIF (minimal 2.1.0 subset both GitHub Code Scanning and GitLab Security Reports accept). Exit code is computed from finding severities: 0 on no errors, 1 if any error-severity finding exists, 2 on usage errors.

The schema package is the contract surface for every future consumer (VS Code extension, MCP server, kernel). It exports the validate function, the Finding and Rule types, and the frozen rule registry — nothing else. No filesystem code, no process exits, no globals. The CLI package is a thin shell wrapping the engine for terminal users. That separation matches US3 — the schema is the library, the CLI is one consumer.

5 · Decisions

D-001 · Schema as a single TypeScript module

Status
Accepted
Context
The implicit grammar lives in CSS, JS, and slash-command prose. Every future consumer (VS Code, MCP, kernel) needs the same rules. Two reasonable forms exist: a separate schema file (RelaxNG / JSON Schema) + a runner, or a TypeScript module that is the schema.
Decision
The @spectastic/schema package's rules/ directory is the canonical schema. Each rule is a typed Rule definition with a check(doc, ctx) => Finding[] function. No parallel RNG/JSON Schema file.
Consequences
+ One source of truth; no sync drift between formats; full TS type-safety in consumers. + Adding a rule is a single file. − Cannot be consumed by non-TS tools without a port; mitigated because every planned consumer is TS/JS. − Documentation generation requires a generator (out of scope for v1).

D-002 · parse5 as the HTML parser

Status
Accepted
Context
Finding fidelity depends on per-element source locations. The validator must agree with the editor's gutter line numbers.
Decision
parse5 with sourceCodeLocationInfo: true. Use the tree-walker API; no jsdom layer.
Consequences
+ WHATWG-spec compliant; location info is precise. + Battle-tested via jsdom / html-validate / linthtml. − Larger bundle than htmlparser2 (~150 KB vs ~30 KB). − Tree API is verbose; mitigated with a thin helper in parser.ts.

D-003 · commander for CLI argv

Status
Accepted
Context
v1 ships one subcommand (validate); Tier 4 brings adopt and import; later tiers bring more. Raw argv parsing scales badly; lean libraries (sade) are less battle-tested.
Decision
commander. Each subcommand lives in packages/cli/src/commands/<name>.ts and registers itself from the binary entry.
Consequences
+ Familiar shape for contributors. + Subcommand growth is mechanical. − ~50 KB of deps that won't be tree-shaken; acceptable for a CLI.

D-004 · vitest as the test runner

Status
Accepted
Context
SC-002 requires one positive + one negative fixture per rule, run as a suite. The runner must support TypeScript natively, ESM, fast watch.
Decision
vitest at the workspace root, shared across packages. Fixtures live under packages/schema/fixtures/<rule-id>/<positive|negative>.html and are discovered by glob.
Consequences
+ Fast watch loop while writing rules. + jest-compatible API for any contributor familiar with it. − One extra dev-only dependency vs node:test; acceptable trade.

D-005 · pnpm-compatible workspaces; pacquet permitted

Status
Accepted
Context
Multi-package layout from day one — schema and CLI in v1; core, MCP, VS Code extension joining later. The chosen workspace shape must outlive Tier 1.
Decision
pnpm-workspace.yaml at the repo root with packages/*. CI uses pnpm (canonical); local dev may use pacquet for faster installs since it reads the same lockfile and workspace config. README documents both flows.
Consequences
+ Future packages drop in by adding a folder. + Independent versioning per package. − Contributors need pnpm or pacquet installed (not npm); documented in CONTRIBUTING and the README. − pacquet still maturing; treated as opt-in, not the default.

D-006 · SARIF 2.1.0 — minimal in-house emitter

Status
Accepted
Context
GitHub Code Scanning and GitLab Security Reports both accept SARIF 2.1.0, but each only reads a subset of the spec (tool driver + results + locations). Pulling in a full SARIF library or schema validator is overkill for the subset we emit.
Decision
Hand-roll a minimal SARIF emitter in packages/cli/src/formatters/sarif.ts. Output is validated in test against the official SARIF 2.1.0 JSON Schema (vendored once, no runtime dependency) and smoke-tested by the two CI workflow examples under docs/ci-examples/.
Consequences
+ Zero new runtime deps for SARIF. + Full control over which fields are emitted. − If GH or GL extends what they require, we add a field; small ongoing maintenance. − The schema-validation test depends on a vendored SARIF schema; refresh on SARIF version bumps (≤ once a year historically).

D-007 · Small-pick libraries: tsup, picocolors, tinyglobby

Status
Accepted
Context
Three low-stakes utility picks the spec doesn't constrain: build tool, terminal colour, glob expansion. Each has 3+ reasonable options; the differences don't change the architecture.
Decision
tsup for builds (esbuild under the hood; ESM + .d.ts in one config). picocolors for terminal colour (tiny, fast, zero deps; chalk and kleur are heavier without a meaningful capability gap for our use). tinyglobby for glob expansion (modern, fast, no deps; fast-glob would also work but ships with micromatch's full surface).
Consequences
+ Tiny runtime footprint; CLI install via npx feels instant. + No vendor lock-in — each is one file's worth of dependency to swap. − tinyglobby is newer; if a pattern surfaces it can't handle, fallback to fast-glob is a one-day port.

7 · Risks & mitigations

RiskLikelihoodImpactMitigation
SARIF subset GH and GL accept diverges over timeMMPin to the documented common subset; both CI examples in docs/ci-examples/ run on every release; D-006's vendored SARIF schema catches structural drift.
parse5 perf misses NFR-001 on outlier-sized specsLMtest/perf.test.ts measures p95 against existing examples on each CI run; file-too-large rule warns once a file exceeds 5,000 lines (no longer covered by NFR).
pacquet lockfile diverges from pnpm in the wildLLCI canonicalises on pnpm; pacquet is documented as a local-dev convenience, not the build-of-record. If divergence appears, drop pacquet from docs without code change.

Cross-file no-duplicate-ids rule false-positives on archived proposals (legitimate copies of stable IDs)MMDefault --ignore patterns exclude **/archive/** and **/withdrawn/**. Documented in CLI help; can be overridden.

8 · Complexity tracking

Two complexity additions worth justifying.

Two packages instead of one. The spec could ship as a single package with both schema and CLI surface. Splitting (@spectastic/schema + @spectastic/cli) costs a touch of monorepo overhead for v1. Justified because the VS Code extension, MCP server, and future kernel all consume only the schema; bundling CLI internals into their dependency closure would force fs/process imports into the browser bundle. The split is structural, not premature.

Vendored SARIF schema for tests. Pulling a SARIF-validation library at test time would solve a one-shot problem at ongoing cost. Vendoring one JSON file (no runtime dependency, refresh on SARIF version bumps) keeps the runtime closure clean. Justified by D-006.
