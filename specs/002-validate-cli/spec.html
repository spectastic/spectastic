Specification · 002-validate-cli

spec-html schema + spectastic validate

A TypeScript-native schema for the spec-html vocabulary and a single command that catches what reviewers shouldn't have to.

Status Accepted Spec ID 002-validate-cli Owner Brian Corbin · @briancorbinxyz Reviewers — Created 14 Jun 2026 Principlesv1.0.1 Smallest demoablespectastic validate examples/spectastic-spec.html exits 0; broken fixture exits 1 with anchored findings. Read time

The <spec-*> vocabulary is enforced today by CSS, JS warnings, and slash-command prose. This spec makes the enforcement first-class: a TypeScript schema package (@spectastic/schema) and a Node CLI (spectastic validate) that read any spec-html file, apply a published rule set, and exit non-zero on errors. Same engine powers a future VS Code extension, MCP server, and TypeScript kernel — so every surface judges spec validity against the same rules.

1 · Context

Spectastic's <spec-*> grammar lives implicitly: CSS marks <spec-delta> with no op= as "MISSING OP", JS logs a console warning when <spec-out-of-scope> <li> lacks defer-to=, and slash-command prose tells the author what's required. A reviewer who opens a spec.html sees the visible failures; a CI pipeline does not. There is no mechanical gate.

The strategy plan at ~/.claude/plans/serialized-whistling-sundae.md identifies a validator + formal schema as Tier 1's first piece because every later surface — VS Code diagnostics, MCP-exposed checks, the future TypeScript kernel — depends on shared rules. Authors, CI bots, and editor extensions are the users; today they have nothing.

2 · User scenarios & testing

Each story is independently testable. US1 alone is a viable MVP.

US1 · Author validates locally P1

As a spec author, I want to run spectastic validate path/to/spec.html so that I catch grammar slips before commit and don't ship a spec with broken anchors or missing required attributes.

Acceptance: Running against examples/spectastic-spec.html exits 0 silently (or with a green summary line). Running against a fixture with one <spec-out-of-scope> <li> lacking defer-to= exits 1, prints the file, line, column, rule ID (no-missing-defer-to), severity, and a one-line fix hint. No stack traces on rule violations.

US2 · CI gates on a glob P1

As a repo maintainer, I want to run spectastic validate "specs/**/*.html" --format sarif > out.sarif in CI so that GitHub Code Scanning and GitLab Security Reports both draw inline PR/MR annotations and the pipeline gates on errors.

Acceptance: Glob expansion across many files completes; aggregate exit code is 1 if any file has at least one error-severity finding, 0 otherwise. SARIF output validates against the SARIF 2.1.0 schema (subset that GitHub and GitLab consume). Human-format output remains usable when piped to a terminal log.

US3 · Schema imported as library P2

As a VS Code extension or MCP server author, I want to import @spectastic/schema and call validate(html, options) so that I render the same findings inline in the editor or return them as a structured MCP tool result, without re-implementing rules per surface.

Acceptance: The schema package exposes a documented TypeScript API returning an array of Finding objects (file, line, column, rule, severity, message, optional fix-hint). No CLI dependency; pure function over an HTML string. Type definitions ship in the published package.

Edge cases

  • Empty file — exits with a single error: empty-document. Not silent success.
  • Non-HTML file (binary, JSON, markdown) — exits 2 (usage error), not 1 (validation error), so CI can distinguish.
  • Glob matches nothing — exits 2 with a message, not 0. Silent zero on no-match has burned every linter that allowed it.
  • Two files reuse the same stable ID — the cross-file no-duplicate-ids rule fires once with both file:line locations cited in the finding's "related locations" field.
  • File over ~50,000 lines — parses but emits a single warning (file-too-large) that performance NFR is no longer guaranteed.
  • Pre-amendment principles.html — validates as today's principles describe; the validator does not enforce future principles versions retroactively.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional — the CLI

The CLI MUST accept one or more positional arguments, each of which may be a file path or a glob pattern. When run with no arguments, the CLI prints usage and exits 2.

The CLI MUST exit 0 when no error-severity findings are produced, 1 when at least one error-severity finding is produced across all files, and 2 on usage errors (unknown flag, non-HTML input, glob matches nothing).

The CLI MUST default to a human-readable output format: one line per finding, anchored as file:line:col, including rule ID, severity, message, and an optional one-line fix hint, followed by a summary line "N errors, M warnings".

The CLI MUST emit JSON when invoked with --format json: a top-level array of Finding objects, one per finding, suitable for VS Code, MCP, or CI script consumption.

The CLI MUST emit SARIF 2.1.0 when invoked with --format sarif, scoped to the subset accepted by GitHub Code Scanning and GitLab Security Reports. SARIF output is valid against the official schema.

Functional — the rules

The schema MUST flag any <spec-out-of-scope> <li> that lacks a defer-to= attribute (rule: no-missing-defer-to, severity: error).

The schema MUST flag any <spec-question> present in a spec whose status is accepted (rule: no-unresolved-question, severity: error). draft and review status produce a warning, not an error, so the validator does not block early-cycle authoring.

The schema MUST flag any <spec-delta> without an op= attribute, or with an op= value not in {added, modified, removed, renamed} (rule: delta-op-required, severity: error). The same element without a target= attribute fires delta-target-required (severity: error).

The schema MUST flag any <spec-risk> without a target= attribute (rule: risk-target-required, error) or without a status= in {identified, accepted, mitigated, rejected, no-value-found} (rule: risk-status-required, error).

The schema MUST flag any <spec-requirement> without an id= matching the pattern [A-Z]+-[A-Z]*-?[0-9]+ (rule: requirement-id-required, error) or any <spec-task> without an id= matching T-[0-9]+ (rule: task-id-required, error).

The schema MUST detect duplicates of project-wide stable IDs across the validated set. Project-wide stable IDs are id= values matching the topic-prefixed pattern (three or more dash-separated segments, e.g. REQ-AUTH-001, REQ-FORMAT-001) declared on a <spec-requirement> or <spec-decision> element. When two or more sites share the same project-wide ID, every site is flagged with rule no-duplicate-ids (severity: error) and each finding cites the other locations via relatedLocations. Spec-local IDs (FR-NNN, NFR-NNN, SC-NNN, D-NNN, T-NNN) are scoped by convention to their containing artifact and are not checked for cross-file uniqueness. Cross-file detection is the only cross-file check in v1.

FR-010 and FR-011 are orthogonal: FR-010 names which IDs must exist (any matching [A-Z]+-[A-Z]*-?[0-9]+); FR-011 names which IDs are checked for cross-file uniqueness (only the topic-prefixed, 3+ segment subset). The differing patterns reflect different purposes, not competing grammars.

The schema MUST flag any <dl class="invest"> with a <dd class="fail"> row when the containing spec's status is review or accepted (rule: invest-row-failed, severity: error). For draft status, the same condition fires as a warning.

Functional — the library

The schema package MUST publish a TypeScript API exporting validate(html: string, options?): Finding[] and a typed Rule definition shape. The package SHOULD have zero runtime dependencies beyond a single HTML parser.

Rules SHOULD declare a default severity in {error, warning}; the CLI gates on errors only. Per-rule severity overrides via config are out of scope for v1 (defer to TBD-validator-config).

Non-functional

Validation MUST complete in under 100 ms per file at p95 on a modern laptop (Apple M-series or comparable, ≥16 GB RAM) for spec files under 5,000 lines. Measured against the existing examples (examples/spectastic-spec.html and the archived proposals) plus the fixtures introduced in this slice.

The CLI MUST be installable as npx @spectastic/cli and as a global npm i -g @spectastic/cli with no OS-specific build steps for end users. Node 20 LTS is the minimum supported runtime.

The repository MUST be laid out as pnpm-compatible workspaces (workspace shape and lockfile format), so future packages (@spectastic/core, @spectastic/mcp, @spectastic/vscode-ext) can join without restructuring. The installer used during development (pnpm vs pacquet) is a plan-level decision, not a spec requirement.

Out of scope (deferred to other slices)

  • Auto-fix mode (--fix). HTML round-trip is risky and the v1 rules don't benefit enough to justify the implementation cost.
  • Watch mode (continuous validate on file change). The VS Code extension supersedes this need for editor users; CI uses run-to-completion.
  • User config file (spectastic.config.json) for per-rule severity overrides and rule disabling. v1 ships fixed defaults.
  • Conformance against source code (e.g. // @spec REQ-AUTH-001 comments). Tier 4 brownfield work; depends on a code scanner this slice does not build.
  • The VS Code extension itself. This spec ships the engine the extension imports; the extension is a downstream slice.
  • The MCP server. Same shape — engine here, server downstream.
  • Porting spectastic init to Node. The existing Python CLI continues serving init until the Node CLI reaches parity in a later slice.
  • Cross-file reference validation (e.g. <spec-delta target="REQ-AUTH-001"> resolves to a live requirement). Stays scoped to duplicate-ID detection in v1.

4 · Data model

Two shapes: Finding (the validator's wire format) and Rule (the registry entry).
Finding
Fields: file, line (1-indexed), column (1-indexed), rule (kebab-case), severity ("error" | "warning"), message, fixHint (optional), relatedLocations (optional; used by no-duplicate-ids). Wire format between engine and every consumer — formatters read, never extend; adding a field is a breaking change to the schema package.
Rule
Fields: id, defaultSeverity, check (function: (doc, ctx) => Finding[]). The registry is a frozen array exported by a TS module.

5 · Success criteria

Technology-agnostic, measurable outcomes.

Running the CLI against every spec-html artifact currently in the repository (examples/spectastic-spec.html, examples/triage-log.html, all archived proposals under examples/changes/archive/**, principles.html after the v1.1 amendment, and the canonical templates) produces zero error-severity findings on a clean checkout.

Each rule declared in §3 has at least one positive fixture (a spec.html demonstrating the violation, validated to produce that exact finding) and one negative fixture (a spec.html that does not trigger it). The fixtures live under packages/schema/fixtures/ and run in the test suite.

A demonstration CI workflow exists for both GitHub Actions and GitLab CI that runs spectastic validate on a sample repo and, given a deliberately broken spec, shows an inline PR/MR annotation pointing at the offending line. Workflows ship under docs/ci-examples/.

The schema package is importable from a separate Node project (npm i @spectastic/schema), the API matches the published types, and a single-page test app calling validate(html) renders findings without pulling in CLI internals or filesystem code.

6 · Assumptions

Four preconditions: principles amendment, parser line-info, SARIF stability, Python init coexistence.

Principles v1.0.1 (2026-06-14-clarify-tooling-scope) lands before this spec passes draft: "no separate CLI required" is replaced with "complementary CLIs are permitted"; the no-build-step non-goal is preserved.

parse5 (or a comparable parser) provides accurate line/column info on every element. Parser choice defers to the plan; both major options support source-location tracking.

SARIF 2.1.0 remains the format GitHub Code Scanning + GitLab Security Reports accept. If GitLab's wrapping diverges, a --format gitlab-codequality shim is a later slice.

Python scripts/spectastic init keeps working until the Node CLI's init reaches parity. The two CLIs coexist on the spectastic name; PATH wins for the transition's lifetime.
