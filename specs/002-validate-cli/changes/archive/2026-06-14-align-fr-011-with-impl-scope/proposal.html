Change proposal · 002-validate-cli

Align FR-011 wording with the topic-prefixed scope the implementation enforces

The current FR-011 reads as project-wide uniqueness for every id=; the rule actually narrows to topic-prefixed IDs on <spec-requirement> and <spec-decision>. Tighten the spec to match what ships.

Status Applied Change ID 2026-06-14-align-fr-011-with-impl-scope Spec 002-validate-cli Author Brian Corbin · @briancorbinxyz Created 14 Jun 2026 Targets 1 modification (FR-011) Read time

During implementation of T-118 we discovered the spec's FR-011 was too broad: it described "any duplicate id= across the validated set" but the project's dual ID convention treats FR-001/NFR-001/SC-001/D-001/T-NNN as spec-local (every spec numbers its own independently) while REQ-AUTH-001/REQ-FORMAT-001 are project-wide contracts. The strict reading would emit false-positive errors on every spec pair the moment they share an FR-001. The rule already narrowed to topic-prefixed IDs on <spec-requirement>/<spec-decision> during implementation; this proposal makes the spec say what the code does.

Align FR-011 wording with the topic-prefixed scope the implementation enforces

Applied

1 · Intent

The spec drift was surfaced during the integration test for SC-001: validate ran against the live repo (two specs, each with FR-001..FR-N, NFR-001.., SC-001..) and the no-duplicate-ids rule fired on every cross-spec collision — all spurious, none representing a real contract violation. The principles file's P-3 names "every requirement and decision has a stable, human-meaningful ID (REQ-FORMAT-001, D-001)"; the examples it gives are topic-prefixed. The narrower reading aligns with the principles and with the existing artifact set.

The rule's source comment already documents the narrowed scope and explicitly says "revisiting FR-011 wording is queued as a follow-up /spectastic.propose." This is that proposal. The implementation does not change; the spec catches up.

2 · Scope

In scope

  • Modify FR-011 to scope cross-file ID uniqueness to topic-prefixed IDs (3+ dash-separated segments) on <spec-requirement> and <spec-decision> only.
  • Explicitly name spec-local IDs (FR-NNN, NFR-NNN, SC-NNN, D-NNN, T-NNN) as not cross-file-checked.
  • Drop the stale "queued for /spectastic.propose" note from the source comment in packages/schema/src/rules/no-duplicate-ids.ts. Pure documentation cleanup — no rule behavior change.

Out of scope

  • Changing the rule implementation. It already enforces the narrowed scope; this proposal makes the spec say so.
  • Adding new rules to cover spec-local duplicate detection within a single file. That is a candidate for a later slice if a real spec-local collision foot-gun appears.
  • Touching other functional requirements, NFRs, or success criteria.

3 · Approach

Single MODIFY delta on FR-011. The new body keeps the conformance keyword (MUST), keeps the rule ID (no-duplicate-ids), keeps the severity (error), keeps the "cross-file detection is the only cross-file check in v1" note. It tightens the scope sentence by naming the pattern (3+ dash-separated segments) and the element-tag constraint (<spec-requirement> / <spec-decision>), and adds one sentence explicitly excluding spec-local IDs from the check.

No new requirement is created; no requirement is removed; no ADR is added. The implementation and the test suite already agree with the post-state — applying this change is a pure-wording reconciliation.

4 · Deltas

What changes: Narrow the scope sentence in FR-011 from "any id= across all input files" to project-wide stable IDs (topic-prefixed pattern, 3+ dash-separated segments) declared on <spec-requirement> or <spec-decision>. Add a clarifying sentence that spec-local IDs are not cross-file-checked. Conformance keyword, rule ID, severity, and cross-file-only scope note are unchanged.

The schema MUST detect duplicates of project-wide stable IDs across the validated set. Project-wide stable IDs are id= values matching the topic-prefixed pattern (three or more dash-separated segments, e.g. REQ-AUTH-001, REQ-FORMAT-001) declared on a <spec-requirement> or <spec-decision> element. When two or more sites share the same project-wide ID, every site is flagged with rule no-duplicate-ids (severity: error) and each finding cites the other locations via relatedLocations. Spec-local IDs (FR-NNN, NFR-NNN, SC-NNN, D-NNN, T-NNN) are scoped by convention to their containing artifact and are not checked for cross-file uniqueness. Cross-file detection is the only cross-file check in v1.

FR-010 and FR-011 are orthogonal: FR-010 names which IDs must exist (any matching [A-Z]+-[A-Z]*-?[0-9]+); FR-011 names which IDs are checked for cross-file uniqueness (only the topic-prefixed, 3+ segment subset). The differing patterns reflect different purposes, not competing grammars.

5 · Risk register

Adversarial pass triggers per the heuristic (touches must-tier FR-011). Three findings embedded below; status starts as identified and transitions to accepted/mitigated/rejected on author commitment.

The "in v1" qualifier on spec-local ID non-coverage creates a permanence commitment that may constrain future spec evolution if cross-file spec-local uniqueness becomes a requirement.

Spec-local IDs... are scoped by convention to their containing artifact and are not checked for cross-file uniqueness in v1.

Mitigated. Dropped "in v1" from the spec-local exclusion clause. The remaining "Cross-file detection is the only cross-file check in v1" sentence stays because that one IS about v1's overall scope, not the spec-local-vs-project-wide distinction. A future amendment can broaden coverage without needing to first repeal a misleading qualifier.

FR-011's explicit boundary (3+ dash-separated segments) contrasts with FR-010's [A-Z]+-[A-Z]*-?[0-9]+ pattern, which accepts 1–2 segments; readers may infer the requirements define different ID shapes rather than different scopes.

FR-010: "flag any <spec-requirement> without an id= matching the pattern [A-Z]+-[A-Z]*-?[0-9]+" vs. FR-011: "Project-wide stable IDs... (three or more dash-separated segments, e.g. REQ-AUTH-001)".

Mitigated. Added an orthogonality paragraph to FR-011's post-state body: FR-010 names which IDs must exist; FR-011 names which IDs are cross-file-uniqueness-checked. The differing patterns reflect different purposes, not competing grammars. The clarification lives inline in the requirement body where readers will encounter it, not in approach prose that gets archived separately.

The §Scope item "Changing the rule implementation... is out of scope" conflicts with §6 Tasks item 2, which commits to removing a source comment from no-duplicate-ids.ts; scope creep is small but not zero.

Non-goals: "Changing the rule implementation. It already enforces the narrowed scope; this proposal makes the spec say so." vs. Tasks: "Drop the 'queued for /spectastic.propose' note from packages/schema/src/rules/no-duplicate-ids.ts's source comment."

Mitigated. Added the comment cleanup as a third in-scope bullet in §2 — it's part of "align spec with code" and pulling it out would leave a stale TODO pointing at a proposal that's already landed. The non-goal stays accurate because comment-only edits are not a behavior change to the rule.
