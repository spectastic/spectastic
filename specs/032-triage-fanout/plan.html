Implementation plan · 032-triage-fanout

Triage list-intake fan-out

How we will build it.

Status Accepted Spec 032-triage-fanout Owner Brian Corbin · @briancorbinxyz Branch 032-triage-fanout Created 09 Jul 2026 Read time

Replace triage's serial list loop with one fan-out engine in @spectastic/core — a hand-rolled bounded pool that maps each item through a shared classifyItem (a total function: chat+parse, no gate), collects results in input order, then runs one post-pass that resolves hedged items and assigns I-NNN IDs. The engine is parameterized by provider method, so the same code is both backends: ai.chat (CLI) and ai.subagent (Workflow). Biggest risk: we own input-order + back-pressure correctness by hand — bought down by test-first behavioural specs over a new concurrency-safe stub.

4 · Approach

Extract a shared classification core from today's characterise: classifyItem(item, ai, {mode}) does the ai.chat call + parseCard and returns a total result — { draft, status: 'ok' | 'hedged' | 'failed' } — never calling ai.ask and never throwing (a parse/provider error becomes failed, satisfying FR-004). A tiny mapPool(items, mapper, concurrency) runs it over the list, returning results indexed by input position (FR-002) under a hard cap (FR-007/NFR-001).

After the pool drains, a single post-pass (a) resolves every hedged item through the existing escalateLayer gate — now grouped, after classification, never interleaved (FR-005) — and (b) assigns I-NNN/T-NNN in input order as the single writer (NFR-003). The engine is parameterized by which provider method it calls, so the same code is both backends: chat (CLI default — cheap, concurrent API calls) and subagent (the Workflow reading — isolated context per item). Single-item mode recombines classify+gate to stay byte-for-byte identical.

6 · Decisions

D-001 · One fan-out engine, parameterized by provider method

Status
Accepted
Context
FR-001 needs "two backends off one shared design." AIProvider already exposes chat() and subagent() (types.ts:113,119); panel.ts:46 is the subagent precedent. The sandboxed Workflow runtime can't import core, so a separate script would fork the prompt.
Decision
A single triageFanout engine in @spectastic/core, parameterized by mode: 'chat' | 'subagent'. CLI backend uses chat; the Workflow backend is the same engine in subagent mode. Prompt, taxonomy, routing, and gate live once.
Consequences
+ FR-001's "shared design" is genuinely shared code; drift-proof; the gate lives in one place (P-8/FR-006).
+ No Workflow-import problem — runs in-process under either method.
− subagent mode is heavier (isolated context per item) — chat stays the default; subagent opt-in (see §8).

D-002 · Hand-rolled bounded-concurrency pool (no new runtime dep)

Status
Accepted
Context
The serial loop at triage.ts:67 needs bounding. p-map@7.0.4 is the obvious library but is only a dev/CI transitive via @secretlint/node (pnpm-lock.yaml:2597) — promoting it adds a real runtime dep to the published package. Owner chose to keep @spectastic/core dependency-minimal.
Decision
A ~30-line internal mapPool(items, mapper, concurrency) that returns results indexed by input position under a hard cap — replicating the two semantics documented in p-map/index.d.ts:9,74 (input-order results, concurrency cap). Default cap 8, --concurrency override.
Consequences
+ No new runtime dependency on the shipped package; full control.
− We own input-order + back-pressure correctness — bought down by the test-first ordering & failure specs (D-004, §8 R-1).

D-003 · Split classifyItem from the gate; single post-pass for gate + IDs

Status
Accepted
Context
Today characterise (triage.ts:85-115) bundles chat + inline escalateLayer (ai.ask, line 102) + return, and IDs are assigned interleaved in the loop (triage.ts:73-80). Neither survives concurrency.
Decision
Extract classifyItem = chat + parse, a total function returning {draft, status: ok|hedged|failed} with no ai.ask and no throw. Run it through the pool; then one post-pass resolves hedged items via escalateLayer and assigns I-NNN/T-NNN in input order (single writer). Single-item mode recombines the two to preserve current behaviour.
Consequences
+ Satisfies FR-005 (gate after the pass), FR-002 (deterministic order), FR-004 (failure is a status, not a throw), NFR-003 (single-writer IDs).
− escalateLayer moves out of characterise; the single-item path must re-wrap it to avoid a behaviour change (covered by the existing 007 tests).

D-004 · Test-first over a concurrency-safe stub

Status
Accepted
Context
The stub AIProvider (stub.ts:90) consumes responses sequentially by index with no delay hook, so under concurrency the response↔item mapping is nondeterministic and SC-001's per-item delay is unsupported.
Decision
Build a test stub keying responses by item content with an optional per-item delay, then write failing tests first: ordering/determinism (SC-002), slowest-item bound (SC-001), failure isolation (SC-003), batched gate (SC-004). The subagent backend gets a real multi-item run (P-7/NFR-002).
Consequences
+ Behavioural guarantees, not structural — the failure modes concurrency actually causes are covered.
− The stub upgrade is a prerequisite (the first task).
