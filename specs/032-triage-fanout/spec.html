Triage list-intake fan-out

Paste a long list; classify every item at once instead of one after another — a drop-in speedup over triage list-intake that keeps every card, ID, and human gate in place.

Status Accepted Spec ID 032-triage-fanout Owner Brian Corbin · @briancorbinxyz Reviewers — Created 08 Jul 2026 Principlesv1.3.0 Smallest demoableA 10-item paste classifies concurrently and writes 10 input-ordered cards in the wall-clock of one item. Read time

Triage's list-intake mode classifies each pasted item into one <spec-triage> card — but serially, one blocking call after the next. Workflow W-5 parallelizes that loop: one classifier per item under a bounded cap, results collected back into input order, on two backends off one shared design (the CLI verb and a Claude Workflow script). The output is unchanged — N in, N out; IDs stay sequential; the just-do-vs-spec gate is preserved, now gathering ambiguous items into one decision phase. Pure speedup: no change to how a single item is judged.

1 · Context

Triage's list-intake mode turns "a few small things" into one classified <spec-triage> card per item in inbox.html. Today it is serial — the CLI walks a blocking for … await loop (packages/core/src/commands/triage.ts) and the slash-command path classifies items one after another. Each waits on the one before, so a 20-item paste is twenty sequential round-trips even though the items are wholly independent.

The agentic-workflows brief (W-5) names it — "one classifier per item in parallel" — and calls it the cheapest of the six workflows: items are already independent, per-item classification is unchanged, and the just-do-vs-spec guardrail already exists. Only the fan-out is missing. It serves the small-batch author triaging a backlog of typos, broken anchors and half-ideas in one pass.

2 · User scenarios & testing

Each story is independently testable: implementing only US1 still yields a viable MVP.

US1 · Fan out a pasted list P1

As a maintainer dumping a backlog, I want every item classified at once so that the batch is triaged in the time of one item, not the sum.

Acceptance: N items (N ≤ cap) are classified concurrently and written as N input-ordered cards to inbox.html with sequential I-NNN IDs; wall-clock is bounded by the slowest item plus overhead, not the serial sum.

US2 · Decide the ambiguous ones in one pass P1

As a maintainer, I want the low-confidence items gathered into a single decision phase so that I commit the just-do-vs-spec calls together, not interrupted item by item.

Acceptance: given several hedged items, the fan-out finishes classification first, then surfaces their layer-commit questions as one consolidated gate; no prompt interleaves with the parallel pass; a confident item never reaches the gate.

US3 · Survive a bad item P2

As a maintainer, I want one item's failure not to sink the batch so that a single transient error never loses the rest.

Acceptance: when one item fails to classify (provider error, unparseable response), it still becomes a card — flagged and routed to the human gate — while every other item lands normally; N in still yields N out.

Edge cases

  • List longer than the cap. Excess items queue and run as slots free; order and IDs unaffected.
  • Single item. Uses the existing serial path — nothing to fan out — byte-for-byte the current behaviour.
  • Mixed kinds. A diagnostic-layer item routes to its per-spec triage log, not inbox.html (unchanged).
  • Duplicate / empty items. Blank lines dropped (splitList); duplicates each get their own card.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) per RFC 2119.

Functional

List-intake classification MUST run items concurrently rather than in a blocking serial loop, on two backends sharing one classification design — the CLI triage verb and a Claude Workflow / subagent script. Both MUST use the same prompt, layer taxonomy, and routing, so a classification is independent of the backend that ran it.

Rationale

The brief (§3) holds the fan-out design is identical across orchestrators; only packaging differs. One shared core makes "two backends" a packaging choice, not two implementations that drift — and is where the classification guarantee lives (FR-006).

Cards MUST be emitted in input order with sequential I-NNN IDs by input position, regardless of completion order. Re-running on the same input MUST produce the same IDs in the same order.

Rationale

P-3 — IDs are contracts. Completion order is nondeterministic; the artifact is not.

N input items MUST yield exactly N cards — no item dropped, merged, or truncated.

If an item fails to classify (provider error, unparseable response), the fan-out MUST still emit a card for it — flagged and routed to the human gate — and MUST NOT abort the batch or affect any other card.

Rationale

A single transient error must never cost the author the rest of a long paste; degrade-and-flag keeps the N-in-N-out contract (FR-003) honest under failure.

Hedged items (e.g. just-do-vs-spec) MUST be collected during the parallel pass and their layer-commit questions surfaced as a single consolidated decision phase after classification completes — never interleaved with the concurrent pass.

The fan-out MUST NOT auto-commit a hedged layer boundary: a confident item is written directly, an ambiguous one routed to the gate (FR-005), never a guess. The test of whether an item is hedged MUST live in the shared core, not in either backend's orchestration prose.

Rationale

P-8 — guarantees live in the kernel, not advisory markdown. Because both backends call one shared core, the human-commit gate fires deterministically wherever the fan-out runs; the Workflow backend cannot skip it independently.

Concurrency MUST be bounded by a default cap (proposed: 8) with a --concurrency override. Items beyond the cap queue and run as slots free.

Per-card routing SHOULD be unchanged: a routing-exit item appends to inbox.html; a diagnostic-layer item routes to its per-spec triage log.

The interactive /spectastic.triage slash-command SHOULD fan out list-intake — dispatching one classifier per item in parallel (bounded cap) and writing input-ordered cards — rather than classifying serially. Because a slash-command is advisory markdown (P-8, T-009), the deterministic guarantee of concurrency is the CLI backend (FR-001); the interactive fan-out is a best-effort nudge over the same shared classification core.

Rationale

Triage T-001: 032 built the CLI + Workflow/subagent backends but not the in-host markdown path, so interactive list-intake (this session's own triages included) classified serially. Added via 2026-07-10-interactive-fanout.

Non-functional

The fan-out MUST NOT exceed the cap's concurrent provider calls at any instant — back-pressure against rate limits on long lists.

The Workflow / subagent backend carries a runtime; verification MUST exercise the fan-out behaviourally (a real multi-item run), not on structural evidence alone.

Rationale

P-7 — done means verified. A present-but-broken orchestration passes every structural check; the concurrency and ordering guarantees are real only if a run demonstrates them.

The write to inbox.html (ID assignment + append) SHOULD be a single ordered step after collection, so concurrent classification never races the I-NNN counter.

Out of scope (deferred to other slices)

  • Scaling a classifier to a multi-vote panel or an --effort dial — this ships one classifier per item; the panel/effort surface is the §9 addendum's slice.
  • Ranking the resulting cards by value — that is W-2; W-5 only classifies and appends.
  • A provider-advertised concurrency cap (an AIProvider interface change) — this slice uses a fixed default plus override.

4 · Data model

No new persisted entity — it reuses TriageCard and the I-NNN scheme, adding two transient shapes around the loop.

Entities

Classification task
A list item plus its input index — the ordering key that survives nondeterministic completion (FR-002).
Classification result
The TriageCard draft, its index, and a status: ok, hedged (gate, FR-005), or failed (degraded, FR-004). The write phase orders by index, assigns I-NNN, appends.

The invariant that makes concurrency safe: a pure fan-out (each task reads only its item, writes only its result) with a single writer — the I-NNN counter and inbox.html append are touched once after collection, in input order (NFR-003).

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For N items at or under the cap, total wall-clock is ≤ the slowest item's time + a fixed overhead — sublinear against the serial baseline. Measured with the stub AIProvider injecting per-item delays (one slow item among fast ones completes in ≈ the slow item's time).

N input items produce exactly N cards, in input order, with sequential I-NNN IDs — identical across repeated runs on the same input.

An injected mid-list failure yields a flagged, gate-routed card for that item and correct cards for every other; the batch neither aborts nor drops.

Given multiple hedged items, their layer-commit questions surface as a single consolidated gate after classification; no confident item reaches the gate.

6 · Assumptions

The stub and real AIProvider implementations are safe to call concurrently — chat() / subagent() are re-entrant with no per-call shared mutable state.

Per-item classification (characterise, the escalateLayer hedge test, the regeneration ladder) is unchanged — this slice reorders when items classify, not how one is judged. The existing splitList item boundary is adequate fan-out input.
