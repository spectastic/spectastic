The Claude case installs skills too

Make the portable Agent Skills the default everywhere — a Claude project gets .claude/commands and .agents/skills.

Status Applied Change ID 2026-09-12-claude-installs-skills Spec 111-codex-skill-adapters Author Brian Corbin (@briancorbinxyz) Created 12 Sep 2026 Targets 3 requirement(s) Read time

111 emits the portable Agent Skills only for --target codex; the default Claude install stays commands-only. But Claude Code reads the Agent Skills standard natively (it co-authored it), and the same output has now run unmodified in Codex and Antigravity. So make skills the default everywhere: plain spectastic init writes .claude/commands and .agents/skills. The machinery already exists — the AdapterTarget render is built — so this is an additive scaffold change plus one honest consequence: NFR-002's "default output byte-identical" guarantee is deliberately relaxed to "changes only by gaining the skills tree."

The Claude case installs skills too

Applied

1 · Intent

Spec 111 shipped one portable output (Agent Skills, .agents/skills/<verb>/SKILL.md) but gated it behind --target codex. The Claude default kept emitting only .claude/commands. That was the conservative first cut, but it under-uses what 111 built: Claude Code reads the Agent Skills open standard natively — it is one of the standard's co-authors — so a Claude project can carry the portable skill surface at no cost.

Two dogfood runs since 111 landed make the case concrete. The identical .agents/skills output produced by init --target codex was read, with no per-tool adaptation, first by Codex (codex-cli 0.153.4) and then by Antigravity (Gemini) — which advanced the same project's implementation. Portable-by-default is the natural conclusion: every project spectastic scaffolds should carry the format that already works across those hosts, not only the ones that pass a flag.

This is the TBD-portable-skill-adapters follow-on partially drained — additively. It does not retire .claude/commands; the full unification (skills as the only Claude surface) stays deferred.

The value is portability insurance. The point is that every project spectastic scaffolds carries the portable form, so opening it in any Agent Skills host — Codex, Antigravity, Cursor, Gemini CLI — just works. In Claude Code the slash commands stay the primary surface; the skills ride along. Claude Code does read Agent Skills (it even treats .claude/commands as a skills fallback), so the two coexisting is a deliberate redundancy, not a collision — and because the skills are carried rather than depended on, the change holds regardless of how any one host chooses to surface them.

2 · Scope

In scope

  • The default spectastic init (the Claude target) emits .agents/skills alongside .claude/commands — both surfaces, nothing removed.
  • Making the render host-aware: the Codex-specific inline-degradation note moves out of the shared translation so a Claude skill never misdescribes its host (FR-012, honouring FR-011).
  • Relaxing NFR-002 honestly: the default output now grows by exactly the skills tree, and nothing else changes.
  • Extending the --tools managed/drift guarantee to the Claude skills tree, so a managed Claude project's skills cannot ship stale either.
  • Re-baselining the T-002 default-scaffold snapshot and reconciling SC-003 to the new invariant.
  • A committed conformance test for the render — vendor an official Agent Skills schema if one is published, otherwise encode the standard's documented frontmatter contract (pulled into scope so distribution and verification land together).

Out of scope

  • Retiring .claude/commands in favour of skills (the full unification) — stays TBD-portable-skill-adapters.
  • Any change to what --target codex emits — only the shared render becomes host-aware (the Codex note moves to the Codex target); the Codex output is unchanged.
  • Richer Claude-only skills that add subagent wiring beyond the shared render — the Claude skill is the same body minus the Codex note; subagents stay in .claude/agents as today.
  • Fixing apply's inability to fold a <spec-criterion> — recorded as TBD-apply-fold-criterion, worked around here by ordering (SC-003 as the first task).

3 · Approach

The AdapterTarget seam and the CODEX_TARGET render already exist, and prebuild already renders .agents/skills into the bundle. So the scaffold change is small: the Claude branch of inventoryAt (packages/cli/src/commands/init/bundle.ts) starts including the .agents/skills tree in addition to .claude/commands and .claude/agents. Extended-verb filtering already understands the skills path (verbFromDestination was taught both shapes in 111), so --with keeps working unchanged.

The one real consequence is NFR-002. 111 built a byte-snapshot fence (T-002 / SC-003) guaranteeing the default scaffold never changes. That guarantee is now deliberately spent: the default output grows by the ten skill files. Rather than delete the fence, it is tightened around the intended change — the snapshot asserts the non-skills files (commands, agents, assets, templates, generated .gitignore/spectastic.json) stay byte-identical and the skills tree is the only addition. NFR-002 is reworded to match. SC-003 must move with it, but apply's fold cannot carry an SC (apply.ts:134-137 matches <spec-requirement> only), so SC-003 is reconciled as the first task, coupled to FR-012, closing the contradiction window inside the same drain. Under --tools, the Claude managed install generalises to stamp and drift-guard both trees, reusing the generateAdapters(cwd, target) and folded drift scan 111 already made target-aware.

The render must become host-aware. Today the inline-degradation note lives in the shared translateToSkill (translate.ts:132), appended to every subagent verb unconditionally — harmless while only Codex consumed the render, but wrong the moment Claude does (FR-011 scopes the note "under Codex"). So the note moves out of the shared translation into the Codex target's render; the Claude target renders the same skill without it. This is an implementation fix honouring the existing FR-011 wording, not a contract change.

Two surfaces, one verb. A Claude project will carry /spectastic.spec (the slash command) and $spectastic-spec (the skill) for the same verb — distinct invocation paths, a deliberate redundancy under the portability framing, not a collision. If it ever proves confusing the escalation is the full unification (retire .claude/commands), which stays TBD-portable-skill-adapters. The premise that Claude Code reads .agents/skills/ is author-confirmed (Claude Code is an Agent Skills host and treats commands as a skills fallback), so no verification precondition is owed — and under portability insurance a host that surfaced skills differently would not undermine the change anyway.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec.

The default spectastic init (the claude target) MUST also emit the portable Agent Skills adapters — one .agents/skills/<verb>/SKILL.md per in-scope verb — alongside the .claude/commands adapters, so a Claude project carries both invocation surfaces. Neither surface is removed, and the same verb-scope rules apply (core by default, extended via --with). A Claude-target skill MUST NOT carry the Codex-specific inline-degradation note: FR-011 scopes that note to the Codex host, so the shared render must be host-appropriate and a skill installed for Claude Code (which does have subagents) must not tell its reader the fan-out ran inline.

Rationale

Claude Code is documented as an Agent Skills host, and the same rendered output already runs unmodified in Codex and Antigravity. Making it the default carries the portable surface everywhere at near-zero cost — the render already exists. The one real cost the adversarial pass surfaced: the note that is correct for Codex is false for Claude, so the render must become host-aware (see Approach + Tasks).

Under spectastic init --tools, the Claude managed install SHOULD stamp a managed marker and drift-guard the .agents/skills tree as well as .claude/commands, so a managed Claude project's skills cannot ship stale either — the same "can't ship stale" guarantee (FR-007/FR-008) applied to the second surface.

Rationale

An unguarded second surface would silently drift from source the moment a command changed. should, not must: the unmanaged scaffold (FR-012) is the core ask; the managed guarantee is the natural completion, but a plain init without --tools is still valid.

What changes: the default scaffold is no longer byte-identical after this feature — it deliberately gains the .agents/skills tree (FR-012). The invariant is retained but scoped to everything else: the "byte-identical" guarantee now covers the non-skills files, and the skills tree is the single permitted addition. This is a conscious relaxation of the original absolute guarantee, recorded here rather than silently dropped.

Beyond the deliberate addition of the .agents/skills tree (FR-012), adding portable skills MUST NOT change the default spectastic init output: a Claude project's .claude/commands, .claude/agents, assets, templates, and generated .gitignore/spectastic.json stay byte-identical (≤ 0 changed non-skills files), and the run introduces ≤ 0 new validate findings.

4b · What this change removes

Each entry names one thing this change takes away. An empty register is the answer “this removes nothing”.

The only subtraction is the weakening of NFR-002's absolute "default output byte-identical" guarantee, and the op="modified" delta on NFR-002 above states it in full (reason and new post-state) — so no separate entry is owed here.

5 · Risk register

Populated by the adversarial risk pass (touches must-tier requirements). One <spec-risk> per finding; status= starts identified and apply refuses until each is accepted, mitigated, or rejected.

Shipping every Claude project the Codex render duplicates the full-fidelity .claude/commands verb and, worse, ships a propose/implement/triage skill that tells a Claude reader the fan-out "runs inline under Codex" — false on a host that has subagents.

FR-012, "a Claude project carries both invocation surfaces," read with the shared render at translate.ts:132 that appends the Codex note unconditionally; and the premise "Claude Code is an Agent Skills host."

Mitigated. The misdescription half is fixed at the contract level: FR-012 now forbids the Codex note on a Claude skill (honouring FR-011's "under Codex" scope), and a task moves the note out of the shared render into the Codex target. The grounding half is closed by the author's own knowledge: Claude Code reads Agent Skills and even treats .claude/commands as a skills fallback — so no verification precondition is owed, and the dogfood task is dropped. Under the settled portability-insurance framing (§Intent), a Claude project carries the skills so any host works while the slash commands stay primary in Claude, which makes the double-registration a deliberate redundancy, not a collision; the full unification (retire commands) stays TBD-portable-skill-adapters.

FR-012 adds ten files to the default scaffold — exactly SC-003's "Falsified by" condition — yet SC-003 is reconciled only through a §6 task, so on apply the live spec keeps a must-tier criterion that contradicts the new NFR-002.

SC-003 (validates="NFR-002"): "Changed files in the default scaffold ≤ 0 … Falsified by: Any difference in the default scaffold's file set or bytes." No <spec-delta target="SC-003"> exists.

Mitigated. A machinery constraint makes the task the only available mechanism: apply's fold matches <spec-requirement> and cannot carry an <spec-criterion> (apply.ts:134-137), so SC-003 cannot be a delta. The mitigation is ordering — SC-003's reconciliation is the first task and is coupled to FR-012, closing the contradiction window inside the same drain. The underlying "apply cannot fold an SC" limitation is filed as a separate meta-triage (TBD-apply-fold-criterion) rather than fixed here.

The change quietly does the deferred TBD-portable-skill-adapters work — making skills a standing surface for every Claude project — while deferring the one guard (schema conformance) that would prove the shipped-by-default skills are well-formed: maximum distribution before minimum verification.

§Scope in-scope "the default spectastic init … emits .agents/skills," on the evidence of two non-Claude dogfood runs.

Mitigated by pulling the conformance guard into scope — distribution and verification now land together. A committed conformance test is added to §6: it vendors an official Agent Skills schema and validates each rendered SKILL.md against it if one is published, and otherwise encodes the standard's documented frontmatter contract (required name+description, name lowercase-hyphen ≤ 64 matching its directory, description ≤ 1024, valid YAML, only known optional keys) as the committed check. This extends the existing 13 unit tests into a conformance suite, so the format reaches distribution and verification in the same change. The format also stays additive and fail-safe: an unmanaged .agents/skills tree triggers no validate finding (validate.ts:145), so the installed base is undisturbed.
