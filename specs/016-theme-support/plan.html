Implementation plan · 016-theme-support

Themes

How we will build it.

Status Draft Spec 016-theme-support Owner Brian Corbin · @briancorbinxyz Branch 016-theme-support Created 2026-06-18 Read time

Promote the theme-owned visual properties (per-role font weights, surface/card treatment, radii, border & rule widths, spacing density) out of hardcoded rules into CSS custom properties, so a theme is one attribute-keyed token block and a mode is one --c-* palette block — the cascade then produces the 2×2 for free. A tiny render-blocking theme-boot.js in <head> applies the saved selection before first paint; spec.js builds the switcher. Biggest risk: regressing today's calm look while tokenising — held down by making calm tokens reproduce the current literals exactly and screenshot-diffing.

Re-plan (T-002): tokens alone can't reach the reference's pills, columns, boxes and gauges, so the token base (D-001) now carries a per-theme component-override layer (D-006) — [data-theme="spectastic-vivid"]-scoped rules for shape and layout — verified against the SC-006 checklist. The work is sliced component-group-first (D-007); risk tolerance steps up to Medium.

2 · Technical context

Language(s)
HTML5, CSS (custom properties + attribute selectors), vanilla ES2019 (IIFE). No artifact framework.
Frameworks
None — progressive enhancement only (per P-4). No build step for the artifact.
Storage
Browser localStorage, two keys: spectastic-theme (theme id), spectastic-mode (light|dark).
Testing
Existing vitest stays for logic; the Playwright + axe-core browser tier (D-005) covers persistence, no-flash, and 4-combo contrast, and now a computed-style parity gate for SC-006.
Perf targets
theme-boot.js ~835 B gzip, render-blocking but < ~5 ms parse+exec; zero layout shift; no flash of the default look (NFR-001).
Constraints
Single self-contained artifact files; AA contrast on all four combos (NFR-003); calm must stay visually identical to today; risk tolerance Medium — attribute-scoped component CSS is proven, but the surface is broader and per-theme layout (2-col grid, gauge-as-bars) is new.

3 · Approach

Token-based theming. Today the theme-owned properties are scattered as literals in base rules (h1{font-weight:400}, h2{font-weight:300}), global tokens (--s-*, --r-*), and inline 1px borders. We promote the theme-owned set — per-role font weights, surface/card elevation, radii, border & rule widths, spacing density — into named custom properties that the base rules consume. :root carries the calm token values and the light palette as the no-JS default; [data-theme="spectastic-vivid"] overrides only the theme tokens; [data-mode="dark"] overrides only the --c-* palette. Because the two axes are independent attribute selectors, the cascade yields all four combinations with no per-combination rules. Adding a future theme is then exactly one [data-theme=…] block (SC-004).

Pre-paint apply, then enhance. A tiny render-blocking assets/theme-boot.js in every <head> reads the two keys, migrates a legacy spectastic-theme = light|dark value into spectastic-mode (FR-006), and writes data-theme/data-mode on <html> before first paint (NFR-001). The body-end spec.js reads that already-resolved state, builds a native <select> from a small theme registry, and rewires the existing footer toggle to flip mode — persisting both keys on change. Migration lives only in theme-boot.js (single source). The slice adds the one <head> line to all 67 artifacts via a scripted, depth-aware insertion.

Component parity, layered on the tokens (re-plan). Tokens carry every scalar a theme owns; the reference's pills, two-column grids, carded boxes and bar-style gauges need structure tokens can't express. So [data-theme="spectastic-vivid"] gains a second layer of component-scoped rules alongside its token block (D-006) — e.g. [data-theme=…] spec-status{border-radius:5px}, [data-theme=…] spec-goals dl{grid-template-columns:1fr 1fr}. Calm remains the untouched :root default, so the blast radius is scoped to the vivid selector. The work is sliced by component group (D-007): Slice 1 — shape (pills, cards, surfaces, radii, rule weights; touches every artifact, instantly visible), then Slice 2 — layout (goals two-column grid, budget-gauge-as-bars, decision/matrix treatment). Each slice ships against its slice of the SC-006 checklist. The shipped mechanism (switching, persistence, no-flash, migration, 4-combo AA) is regression-guarded and stays green.

4 · Alternatives considered

The pivotal choice is the CSS theming strategy. Scores out of 5; higher is better.

OptionExtensible (SC-004)MaintainableNo-build (P-1)No-flashTotal
Per-theme selector overrides (duplicate rule blocks)225413
Token custom properties, attribute-keyed555520
Separate stylesheet per theme (swap <link>)324211

Per-theme overrides duplicate every touched selector per theme and degrade with each new theme. A stylesheet-per-theme reintroduces a flash on swap and duplicates the shared rules. Tokens keep one rule set, isolate per-theme change to a token block, and need no build.

Re-plan note (T-002): the row above scored per-theme overrides as a pure strategy (duplicate the whole rule set per theme). D-006 is not that — it keeps tokens as the base and adds only the targeted shape/layout rules tokens can't express (pill radius, grid columns, gauge-as-bars), scoped to the vivid selector. The hybrid keeps the token strategy's wins while reaching the component-level parity FR-007 now demands.

5 · Decisions

D-001 · Token-based theming

Status
Accepted
Context
FR-002 makes a theme own typography and structure; SC-004 wants a new theme to be one stylesheet block.
Decision
Promote theme-owned properties to custom properties consumed by base rules. :root = calm tokens + light palette; [data-theme="spectastic-vivid"] overrides theme tokens; [data-mode="dark"] overrides --c-*.
Consequences
+ One rule set, 2×2 for free, a theme = one token block. + No build. − A tokenisation refactor of existing base rules, with calm-regression risk (R-1). Augmented by D-006 — tokens remain the base; component-level parity needs a scoped-rule layer on top.

D-002 · Pre-paint via dedicated theme-boot.js

Status
Accepted
Context
NFR-001 forbids a flash; CSS can't read localStorage, so something must run in <head> before paint.
Decision
A tiny render-blocking assets/theme-boot.js in <head> migrates + sets the attributes pre-paint; the switcher UI stays in body-end spec.js. Migration lives only in the boot script.
Consequences
+ Central source, no logic drift; only the critical path blocks paint, not the full enhancement layer. − A new asset and a one-line <head> edit in every artifact; a small first-load fetch on the critical path (R-3).

D-003 · Mode as [data-mode], drop html.dark

Status
Accepted
Context
FR-004 mandates data-theme/data-mode attributes; the current mechanism is a lone html.dark class.
Decision
Move the dark palette under [data-mode="dark"] and remove the html.dark alias. All artifacts are retrofitted in this slice, so nothing in-repo relies on the class.
Consequences
+ One mechanism, no dead selector. − An externally forked/saved copy of an old artifact loses dark until it reloads the new assets; accepted given the full in-repo sweep.

D-004 · JS-built native <select> from a theme registry

Status
Accepted
Context
FR-001 wants a dropdown in every artifact; SC-004 forbids per-artifact markup edits when a theme is added.
Decision
spec.js holds the theme registry and injects a native <select> beside the existing footer toggle (which becomes the mode control). No switcher markup in artifact files.
Consequences
+ Native, accessible, keyboard-friendly, no UI library; adding a theme touches only the registry. − Switcher absent with JS off (acceptable per NFR-002).

D-005 · Playwright + axe-core browser test tier

Status
Accepted
Context
SC-002 (first-paint frame) and SC-003 (rendered contrast ×4) are only faithfully observable in a real browser; the repo today has only vitest.
Decision
Add Playwright + axe-core as a browser test tier: persistence + no-flash specs, and an axe contrast sweep across all four combinations. Migration/registry logic may also be unit-checkable, but the must-SCs drive the browser tier.
Consequences
+ Faithful coverage of the must-level criteria. − A new dev dependency and CI tier to maintain (R-2 is gated by it).

D-006 · Per-theme component overrides (layered on D-001 tokens)

Status
Accepted
Context
FR-007 parity (after T-002) needs pill shape, two-column grids, carded boxes and bar-style gauges — structure the D-001 token set cannot express.
Decision
Keep tokens as the base; add a layer of component-scoped rules under [data-theme="spectastic-vivid"] (e.g. spec-status{border-radius:5px}, spec-goals dl{grid-template-columns:1fr 1fr}, the bar-style budget gauge). Calm stays the untouched :root default. Bounded by D-008: these rules are CSS-only over existing elements and add nothing to documents.
Consequences
+ Reaches full component parity without a build or a flash; blast radius scoped to the vivid selector. + Tokens still win for scalars. − Broader CSS surface raises calm-regression risk (R-1) and per-theme layout is new (R-6). − A theme is now a stylesheet section (tokens + overrides), loosening SC-004's "one block" to "one self-contained section" (no markup/switch-logic edits still holds).

D-007 · Slice the parity work by component group, demoable-first

Status
Accepted
Context
The sharpened spec's INVEST-S is strained — full parity across every artifact type is large and must not land as one opaque batch.
Decision
Slice 1 — shape: pills, cards/admonitions, surfaces, radii, rule weights (touches every artifact, instantly visible). Slice 2 — layout: goals two-column grid, budget-gauge-as-bars, decision/matrix treatment. Each ships against its slice of the SC-006 checklist.
Consequences
+ Intermediate demoables; calm-regression caught early on the cheap slice. + /spectastic.tasks can phase the work cleanly. − Two passes over spec.css rather than one.

D-008 · Themes are CSS-only over the existing vocabulary — opt-in, additive

Status
Accepted
Context
NFR-005. The reconsideration of D-006 was about carrying cost, not the override layer itself: as themes 3/4/5 arrive, rich styling must not tax documents that don't use a feature, and a new theme must not complicate existing ones.
Decision
Every theme is a self-contained [data-theme] CSS section over the existing semantic elements. No theme adds document markup; a document pays for a component's theming only by using that component. Hard layout cases use CSS over existing parents first (section:has(spec-goals):has(spec-non-goals){grid}); only if impossible, a minimal opt-in authoring-template hook — never a globally-forced wrapper.
Consequences
+ Adding theme N is additive CSS, bounded, with zero document or other-theme cost. + Reconciles D-006 with the §4 token win — scoped rules are acceptable precisely because they are CSS-only and opt-in by usage. + Bounds D-006 so it can never drift into forced scaffolding. − A few reference layouts need :has()/grid work or a small template hook (R-8). − Candidate to promote to a principle (P-7) once the theme count grows — flagged, not amended (§8).

D-009 · Vivid header — inject once, reveal per-theme via CSS (no runtime DOM moves)

Status
Accepted
Context
FR-009: every artifact gets a sticky top header carrying the brand/back-link, artifact path, theme dropdown, and a sun/moon mode toggle; the controls move out of the footer into it (calm renders the bar flat, vivid backdrop-blurred). Must honour P-1 (source order = reading order), P-4 (degrade without JS), and P-5 (calm density).
Decision
spec.js injects a semantic <header> at the start of <body> on every load (P-1). The theme dropdown + mode toggle render in the header, wired to the window.__spectastic registry + reflect handlers; CSS shows the header in both themes (position:sticky;top:0; calm a flat opaque-cream bar, vivid a backdrop-filter:blur() bar with an @supports solid-surface fallback), and the footer switcher is removed. Brand links to index.html; the path auto-derives from location.pathname (trailing segments) with a <body data-doc-path> override; the mode toggle is an inline sun/moon SVG. No runtime DOM relocation.
Consequences
+ No DOM churn on theme switch; both control sets stay in sync because they read one registry. + Header sits first in source order (P-1) and, being JS-injected + vivid-only, vanishes under no-JS/calm — degrading to today's footer switcher (P-4). + Vivid-only keeps calm's chrome minimal (P-5). − Two control instances to keep wired (mitigated: shared reflect handlers, one source of truth). − backdrop-filter is uneven across browsers (mitigated by the @supports fallback, R-9).

8 · Complexity tracking

Where this plan adds complexity beyond the literal spec, the justification lives here.

A separate theme-boot.js asset is more moving parts than a single toggle, but it is the only way to guarantee no-flash (NFR-001) across 67 files without copying the migration logic into each — trading one small fetch for unbounded drift. Justified.

A new Playwright + axe-core tier sits beyond the existing vitest/CLI stack. The deterministic parts (migration, registry resolution) could be unit-tested, but SC-002 (first-paint frame) and SC-003 (rendered contrast) are only honestly observable in a browser — so the new tier earns its keep.

Vivid weight map and dark hex values are taken from the reference design (Fraunces 500–700, Lato 900; the documented dark palette) as the starting point, tuned only where the AA gate (R-2) requires. The exact per-role map is settled in /spectastic.tasks / implementation, not here.

A per-theme component-override layer (D-006) adds CSS beyond the token block, which superficially resembles the per-theme-override strategy the §4 matrix rejected. The justification: it is targeted (only what tokens can't express) and vivid-scoped, not a duplicated rule set — and FR-007 component parity is unreachable by tokens alone. The cost is a broader calm-regression surface, paid down by strict selector scoping and a dual screenshot gate (R-6).

The theme-scaling contract (D-008 / NFR-005) reads like a project-wide invariant — it governs every future theme, not just vivid. It is flagged as a candidate principle (P-7) rather than amended into principles.html now: principle amendments are owner-gated, and one alternative theme isn't yet enough evidence. Promote when theme 3 lands and the pattern has held.
