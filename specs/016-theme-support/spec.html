Specification · 016-theme-support

Themes

Two orthogonal axes — a visual theme and a light/dark mode — so every artifact can read as spectastic-calm or spectastic-vivid, light or dark.

Status Draft Spec ID 016-theme-support Owner Brian Corbin · @briancorbinxyz Reviewers — Created 17 Jun 2026 Principles v1.1.0 Smallest demoableAny artifact offers a theme dropdown (calm / vivid) and a light/dark mode toggle; the choice persists and applies before first paint. Read time

Spectastic already ships a binary light/dark toggle. This spec generalises it into two independent axes: a theme (a visual identity — typography and structure) and a mode (a light or dark colour palette). Two themes ship — spectastic-calm (today's look, renamed) and spectastic-vivid (heavier weights and a denser, carded structure, derived from the reference design) — and each renders in both modes, a 2×2 matrix. Selection lives in data-theme/data-mode attributes, persists across artifacts, and applies before first paint so there is no flash.

1 · Context

Every spectastic artifact today carries a single [data-theme-toggle] button that flips an html.dark class and saves localStorage['spectastic-theme']. That is a mode toggle wearing the word "theme": it only ever changed colour, against a single typographic look.

We want a second visual identity — heavier type, derived from the reference design — without giving up dark mode in either look. That forces the concerns apart: a theme is the visual identity — typography and structure (weights, surfaces, radii, rule weights, spacing); a mode is the colour palette (light or dark). They are orthogonal, so the look-set is a 2×2 matrix, not a single switch. This affects every reader and author, and the shared assets/spec.css + spec.js all artifacts load.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Pick a typographic theme P1

As a spec reader or author, I want to choose between the calm and vivid themes from a dropdown so that I can read in the visual identity I prefer.

Acceptance: a theme dropdown (in the top header, both themes — FR-009) lists spectastic-calm and spectastic-vivid; selecting vivid re-renders the document in the heavier weights with no change to colour; the choice survives reload and carries to the next artifact opened from the same origin.

US2 · Switch mode within any theme P1

As a reader, I want to toggle light/dark independently of the theme so that either theme is comfortable in either lighting.

Acceptance: the mode toggle flips light↔dark; all four combinations (calm·light, calm·dark, vivid·light, vivid·dark) render correctly; mode and theme persist separately.

US3 · Return without a flash P2

As a returning visitor, I want my last theme and mode applied instantly on load so that the page never flickers from calm/light to my saved look.

Acceptance: on a hard reload with a saved non-default selection, the first painted frame already shows the saved theme and mode.

Edge cases

  • An existing visitor has only the legacy spectastic-theme = 'dark' saved (a mode, under the old key). They should land on dark mode with the calm theme — intent preserved, nothing broken (FR-006, SC-005).
  • JavaScript is disabled. The artifact still renders fully in the default theme and light mode; the switcher is simply inert (NFR-002).
  • An unknown data-theme/data-mode value (hand-edited or stale) falls back to the default (spectastic-calm, light) rather than rendering unstyled.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The design system MUST define a theme registry of at least two themes — spectastic-calm (the default) and spectastic-vivid — each selectable from a dropdown control present in every artifact.

Rationale

"First alternative" implies more will follow; a registry plus dropdown scales past two without UI rework. The existing theme is renamed to spectastic-calm because "light" now names a mode, not a theme.

A theme MUST control the full visual identity — typography (font families and weights), structural treatment (surface/card elevation, border radii, border and rule weights, the spacing/density scale), and component-level styling (pill shape, card and admonition treatment, multi-column layouts) — and MUST NOT redefine any colour custom property.

Rationale

The split is identity (theme) versus lighting (mode). A theme owns the shape and weight of the page — type weight, card rounding, spacing density, and how components like pills and the goals grid are laid out; a mode owns every colour, including what colour a border or surface is. Holding colour out of the theme keeps the look-set a clean 2×2: any theme renders in either mode against the same palette. Broadened on re-entry (T-002) from "type + base structure" to include component styling, since per-theme component rules are what FR-007 parity requires.

The design system MUST support two colour modes — light (default) and dark — toggled independently of the active theme, such that every registered theme renders correctly in both modes.

The active theme and mode MUST be expressed as data-theme and data-mode attributes on the root <html> element, and the stylesheet MUST key off those attributes.

The selection MUST persist across reloads and across navigation between artifacts, via two localStorage keys: spectastic-theme (theme id) and spectastic-mode (light|dark).

On load, a pre-existing spectastic-theme value of light or dark (the legacy mode-only key) MUST be migrated into spectastic-mode, with the theme defaulting to spectastic-calm.

Rationale

The old key stored a mode under a misleading name. Migrating it preserves every existing visitor's intent on first load after the upgrade, with no broken or ignored preference.

The spectastic-vivid theme MUST reproduce the reference design's visual identity at the component level — not only heavier Fraunces/Lato weights, but the reference's pill shape, carded boxes and surfaces, border radii, rule weights, spacing, and multi-column layouts (e.g. the two-column goals/non-goals grid and the budget gauge rendered as horizontal bars) — wherever those components appear, across every artifact type. It MUST reuse the four existing families (Fraunces, Source Serif 4, Lato, IBM Plex Mono), introducing no new typeface downloads. The sticky/blurred top bar is specified separately in FR-009 (un-deferred on this re-entry).

Rationale

Sharpened on re-entry after T-002: the original wording enumerated only "carded surfaces, radii, rule weights, spacing", which a token-only theme satisfied while still looking nothing like the reference (pills, columns, boxes were untouched). Parity is now defined at the component level and measured by SC-006. Components absent from the reference (it demonstrates a spec layout only — e.g. task checkboxes, deltas, triage cards) inherit vivid's structural treatment consistently; they have no reference target to match.

The change of theme or mode MAY animate via a short colour/type transition, matching the reference design's calm cross-fade.

Every artifact MUST present a sticky top header carrying, left to right: a brand/back-link (the spectastic mark, linking to the project landing index.html); the artifact's path/name; the theme dropdown; and a light/dark mode control shown as a sun/moon icon. The theme dropdown and mode control MUST live in this header — not the footer — in both themes. Each theme renders the header in its own register: spectastic-vivid presents the dense, backdrop-blurred, reference-faithful bar; spectastic-calm presents a minimal, calm-native treatment — flat warm-cream surface, a thin bottom rule, restrained height — carrying the same elements without vivid's blur or density (per P-5). The header is built by the existing switcher logic, so it needs no per-document markup (NFR-005); in each theme it MUST hold WCAG AA contrast over its backdrop (NFR-003), reflect the booted theme/mode with no flash (NFR-001), and — with JavaScript disabled — render no header at all (it is JS-built) while the artifact falls back to the default calm theme, fully readable (NFR-002).

Rationale

Un-deferred vivid-only on the 2026-06-19 re-entry to resolve the P-5 (calm density) tension. Re-weighed (T-009): the value is the header's positioning — always-visible navigation (brand/back-link → index.html), orientation (the path), and control (theme + mode), so they are never "go fish" in the footer — not vivid's aesthetic. Calm therefore gains the same elements and sticky position in a minimal, calm-native treatment (no blur or density), which honours P-5's "no chrome that doesn't carry meaning" while keeping the distinct calm and vivid identities. The footer switcher is removed in both themes. Component-level parity (height, blur, spacing) of vivid's bar is measured under SC-006.

Non-functional

The saved theme and mode MUST be applied before first paint via an inline <head> script, so there is no flash of the default theme/mode before the saved selection takes effect.

With JavaScript disabled, every artifact MUST render fully readable in the default theme (spectastic-calm) and light mode; theme and mode switching are progressive enhancements (per P-4).

All four theme×mode combinations MUST meet WCAG 2.1 AA contrast — at least 4.5:1 for body text and 3:1 for large text and UI components.

The inline head script and switcher logic SHOULD add no perceptible load cost and SHOULD introduce no build step, keeping each artifact a single self-contained file (per P-1).

A theme MUST be pure CSS keyed on data-theme over the existing semantic vocabulary: it MUST NOT require any document to carry added markup, wrappers, classes, or data-attributes, and a document incurs a component's theming only by using that component (opt-in by usage). Adding a theme MUST be additive — one new [data-theme] stylesheet section, with no change to base CSS, to documents, or to other themes.

Rationale & hard-case fallback

Raised while reconsidering how themes 3/4/5 scale: rich styling must not tax documents that don't use a feature, and a new theme must never complicate existing ones. Where a reference layout can't be reached by CSS over the current DOM (e.g. side-by-side goals/non-goals needs a shared parent), prefer a CSS-only solution (:has(), grid on the existing parent); only if that is impossible may the supporting structure be added as an opt-in authoring-template hook — present for newly-scaffolded documents that use the feature, never forced on documents that don't. Parity (FR-007) stays non-negotiable; this constrains how it's reached.

Out of scope (deferred to other slices)

  • OS preference detection (prefers-color-scheme) for the initial mode — default stays light until the user chooses.
  • A third theme beyond calm and vivid, and any user-authored/custom theme editor.
  • Themes that own colour (theme-specific accents) — excluded; colour stays mode-owned per FR-002.
  • Mixing themes within a single artifact (applying different themes to different sections/components of one document). Per-theme component styling — vivid styling pills and cards differently from calm — is in scope (FR-007); this item is only the different-themes-in-one-doc case.
  • Carding the §"User scenarios & testing" stories like the reference's Decision blocks — needs a new <spec-scenario> vocabulary element (cross-cutting, not theme-specific); specified in its own spec, with vivid then styling it. Tracked at T-006.

4 · Data model

The feature owns three small concepts. None is persisted server-side; the only store is the browser's localStorage.

Entities

Theme
A named visual identity. Fields: id (e.g. spectastic-calm), display name, font-family + weight assignments per role (heading, body, metadata, code), and structural tokens (surface/card elevation, border radii, border/rule weights, spacing-scale density). Owns no colour value.
Mode
A colour-palette lightness: light (default) or dark. Owns every --c-* colour custom property — including the colour of borders and surfaces whose geometry the theme sets.
Preference
The persisted pair { theme, mode }, stored as localStorage['spectastic-theme'] and localStorage['spectastic-mode'], and reflected on <html> as data-theme / data-mode.

Invariant: theme ⊥ mode. Any theme is valid in any mode; the default selection is (spectastic-calm, light). An unrecognised value on either axis resolves to that default rather than rendering unstyled.
Reference palette (the modes' colours derive from this)

Light ≈ today's values (cream #f6f5f1 ground, #353534 ink). Dark: ground #1b1917, raised #252220, ink #e9e4da, with brightened accents (link #e98cb6, sea #42cadd, purple #b29bdf, salmon #f08a79). Exact mapping onto --c-* names is a plan detail.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

A reader can select any of the four theme×mode combinations on any artifact, and the same selection is in effect after reload and after navigating to a different artifact from the same origin (4/4 combinations, persistence verified both ways).

On a hard reload with a saved non-default selection, the first painted frame already shows the saved theme and mode — no visible flip from the default.

All four combinations pass an automated WCAG AA contrast check (4.5:1 body, 3:1 large/UI) on a representative artifact.

Adding a third theme touches only the stylesheet (one theme block — its typography and structural tokens) and the theme registry — zero edits to any artifact's markup and zero changes to the switch logic (verifiable by diff).

An existing visitor whose only saved preference is the legacy spectastic-theme = 'dark' lands on dark mode with the calm theme after migration — their original intent is preserved.

Under spectastic-vivid, the computed styling of every component the reference design exhibits matches the reference's measured target values on a representative artifact of each type — verifiable property-by-property via computed styles, no human judgement required. Targets are measured from example.html (connector computed styles), not transcribed or guessed.

Parity checklist (measured from example.html)

Shape: status-pill radius 5px; tag/priority-pill radius 4px; card/admonition/decision radius 12px; budget-gauge-card radius 10px; card border 1px; left/top accent bar 3px; Fraunces headings h1 500 / h2·h3 540; status & label weight 900.

Pills (bright, filled, AA): status pills and requirement priority pills (MUST/SHOULD/MAY) are filled chips, and the requirement id chip is a filled sea chip — all drawn from the --c-pill-* palette (fixed fill+text pairs ≥ 4.5:1, so they stay AA in both modes). The reference's exact pill colours are sub-AA (e.g. salmon+cream ≈ 3.4:1); vivid keeps the bright filled treatment and hue family but deepens to clear NFR-003 — a deliberate, documented colour divergence.

Layout: goals/non-goals as a two-column grid (1fr 1fr, gap 20px); the budget gauge as a horizontal flex row of cards (label+value above a thin bar); the changelog as a timeline with a 2px left rail connecting the dated entries; <spec-requirement> as a card (id chip + priority pill on a top row, body below); one column top-to-bottom — vivid unifies the reading measure (≈42rem) so every top-level block (header, meta, budget, cards, prose) shares one width and aligns left+right, like the reference (calm keeps its narrow-prose/wide-element split); <spec-meta> as an aligned key/value grid compacted to two pairs per row (the reference's single inline row suits its 4 short fields; spectastic's 8 fields — one a long prose field — read better aligned, so the grid is kept aligned rather than run inline — a readability divergence).

Header (vivid only, FR-009): a sticky, backdrop-blurred top bar — brand/back-link (→ index.html) at left; artifact path, theme dropdown, and sun/moon mode toggle at right — matching the reference's measured bar height, blur radius, padding, and border; the footer carries no switcher under vivid. Calm has no header (resolves the P-5 density tension).

Documented divergences (reference is law except these, decided deliberately): pill colours are deepened from the reference's exact (sub-AA) values to satisfy NFR-003 (see Pills above); <spec-meta> stays an aligned grid rather than the reference's inline row (readability with 8 fields). The earlier "keep the requirement gutter" divergence was reversed on review — requirements now match the reference's card; the sticky/blurred header is no longer deferred — see FR-009.

6 · Assumptions

The four families already loaded by every artifact include the heavier weights spectastic-vivid needs (Fraunces up to 700, Lato 900); the vivid theme reuses them and adds no new typeface downloads.

The carded surfaces, radii, border/rule weights, and spacing seen in the reference design are owned by the theme (per FR-002), not shared global primitives. spectastic-calm captures today's lighter, airier structure as one theme's tokens; spectastic-vivid defines its own denser, carded structure. Both inherit colour from the active mode.

The reference artifact is the visual target for both the vivid weights and the palettes; because its palette is close to today's, the modes refine existing --c-* values rather than introduce a new colour system.

Print output is unaffected by theme or mode (print uses its own baseline) and is not gated here.

7 · Open questions

None outstanding. Every scope and mechanism decision was anchored during the spec interview (see the change log). The remaining choices — the exact weight-per-role map, the dark hex values mapped onto --c-*, and the precise reference component values (radii, paddings, column counts) confirmed against example.html at implementation time — are Negotiable implementation details for the plan, not unresolved questions.
