Unrouted <spec-triage> pill fails WCAG AA contrast

Implementation code

Debugging a sub-AA component pill, root cause was the unrouted-state pill colour (salmon on the mode surface, ~3:1) combined with a coverage gap in the SC-003 contrast fixture; fixed by making the pill colour mode-aware and adding the unrouted state to the fixture; regeneration passes — NFR-003 already mandates AA for every component, so the miss is code/fixture drift, not a requirement gap.

Expected
Every component meets WCAG AA (≥4.5:1) across all four theme×mode combinations (NFR-003, SC-003).
Actual
The unrouted <spec-triage> pill renders salmon #e1624f on the surface (~3:1 light, ~3.3:1 dark) — below 4.5:1.
Diagnosis
The SC-003 axe sweep runs on tests/fixtures/all-components.html, which omits an unrouted <spec-triage>; the sub-AA rule (spec-triage:not([layer]) .layer-pill in assets/spec.css) therefore never reached the gate.
Fix
assets/spec.css — give the unrouted pill a mode-aware colour (the surface is var(--c-surface), so a single literal can't pass both modes): add a --c-danger token (light #b0392a / dark #f08a79) and use it. Then add an unrouted <spec-triage> to tests/fixtures/all-components.html so the sweep covers it.
color: var(--c-salmon); /* #e1624f — ~3:1 on light surface, ~3.3:1 on dark */ color: var(--c-danger); /* new token: light #b0392a / dark #f08a79 — AA in both modes */
Deep dive — none required

No cross-spec contract, no project-wide invariant, no deferred-scope promotion, no hotfix-before-amendment sequence. Self-contained colour + fixture fix under the existing NFR-003; not a spec change. Implement as a one-file just-do via /spectastic.implement.

spectastic-vivid doesn't match the reference design

Spec upstream

Debugging spectastic-vivid not resembling the reference (example.html), root cause was FR-007 enumerating only a narrow structural set (surfaces / radii / rule-weights / spacing) with no visual-parity criterion — pills, columns, boxes, and the header are never required to match; fixed by sharpening FR-007 to full component parity and adding a measurable parity success criterion, then re-planning; regeneration fails — another session follows the same thin spec/plan and reproduces the mismatch.

Expected
spectastic-vivid is visually faithful to the reference design (example.html) — pills, columns, boxes, surfaces, header, spacing and weights all match (FR-007).
Actual
Vivid changes only font-weights + four tokens (--card-radius, --rule-w, --accent-bar-w, --card-shadow); the reference's 5px pills, 12px carded boxes, sticky blurred header, 2-col goal grids and gauge cards are absent.
Diagnosis
FR-007 lists only "carded surfaces, border radii, rule weights, spacing" and no success criterion measures visual parity, so plan D-001 scoped a token-only theme that cannot express component-level styling; the implementation faithfully built that thin theme.
Fix
specs/016-theme-support/spec.html — 016 is Draft, so per P-6 sharpen FR-007 in place (re-entry via /spectastic.spec) to require full component-level parity with the reference (pills, columns, boxes, surfaces, header) and add a measurable visual-parity success criterion; then cascade /spectastic.plan → /spectastic.tasks → /spectastic.implement.
Deep dive — cascade required

Scope sharpening, surfaced not silently promoted. The user is widening "match the reference" beyond FR-007's current enumeration to full visual parity. Because 016 is in Draft, P-6 permits the FR-007 edit + new SC in place (no propose/apply cycle); the heavier ceremony isn't required until the spec leaves Draft.

Cascade: spec (sharpen FR-007 + add parity SC) → plan (D-001 must grow from token-only to per-theme component overrides, e.g. [data-theme="spectastic-vivid"] spec-status { … } and a sticky header, since pills / columns / header can't be reached by the current token set) → tasks → implement. The four passing contrast combinations (SC-003) and the no-flash / migration behaviour are unaffected and should stay green.

Principles watch: the reference is denser and adds chrome (sticky header). The amendment should confirm vivid still honours P-5 (calm density) — the reference reads as calm-but-dense, so this is a check, not a blocker.

Heading + inline-code line overlap (pre-existing, both themes)

Implementation code

Debugging a wrapped <h1> whose lines overlapped where inline <code> appeared, root cause was the tight heading line-height:1.05 plus inline code's padding/border/0.9em box exceeding the line box (≈73px vs 57px); fixed in base CSS by loosening h1 line-height to 1.14 and shrinking/flattening code inside headings; regeneration passes — a pure CSS implementation fix, no spec governs it.

Expected
A multi-line heading containing inline code reads cleanly, lines never overlap — in calm and vivid.
Actual
Inline <code> rendered ~73px tall inside a 57px h1 line box, so wrapped lines collided (visible long before themes; calm too).
Diagnosis
Base h1 { line-height: 1.05 } is too tight for wrapped headings, and inline code added vertical padding + border + 0.9em size on top — not a theme or spec issue, an old base-CSS gap.
Fix
assets/spec.css — h1 line-height 1.05→1.14; :is(h1..h6) code drops vertical padding/border, font-size:0.8em, line-height:inherit. Verified: code box 56.5px < 62px line box, +6px between lines. Guard: tests/heading-code.spec.ts.
Deep dive — none required

No cross-spec contract, invariant, or hotfix. Base fix benefits both themes; already applied and regression-guarded. Surfaced during the 016 vivid review but predates it.

Out-of-scope defer-to chip overlaps the item text (pre-existing, both themes)

Implementation code

Debugging the <spec-out-of-scope> list where a long defer-to chip overlapped the deferred-item text, root cause was the chip being absolutely positioned over a fixed 10rem text indent — long values overflowed the reserve; fixed by making the chip an inline-block at the start of a block list item; regeneration passes — a base-CSS layout fix, no spec governs it.

Expected
A deferred item's → defer-to chip sits beside its text, never overlapping — at any value length, in both themes.
Actual
Long values (e.g. TBD-github-releases) overflowed the absolute chip's 10rem reserve and printed over the item text (the first letters were hidden).
Diagnosis
Base spec-out-of-scope li reserved a fixed padding-left:10rem for a position:absolute chip; any wider defer-to spilled into the text. Pre-existing in calm; not a theme/spec issue.
Fix
assets/spec.css — the ::before chip is an inline-block at the start of a block list item (a grid/flex container would instead pull inline <code>/<a> from the description into the chip column — a first grid attempt did exactly that). The chip auto-sizes, so long values can't overflow. Guard: tests/heading-code.spec.ts asserts the item is not grid/flex and inline code stays in the text flow, both themes.
Deep dive — none required

No cross-spec contract, invariant, or hotfix. Base fix; benefits both themes; applied and guarded. Surfaced in the 016 review, predates it (same class as T-003).

Protocol

Five required Tier-1 fields, in order:

Each card MUST include a headline in Y-statement form: "Debugging X, root cause was Y; fixed by Z; regen pass|fail."

Each card MUST state Expected, Actual, and Diagnosis (one sentence — cause, not symptom).

Each card MUST declare a single layer attribute (spec | plan | implementation | cross-spec | principles | platform) and a regeneration test result (pass | fail).

Each card MUST include a concrete Fix — artifact path + one-line proposal. For implementation gaps, a <spec-diff> pointing at the offending line.

The deep-dive <details> block SHOULD be filled only when at least one of: cross-spec contract touched, project-wide invariant implicated, deferred scope exposed, or hotfix-before-amendment sequence required.

Cards MAY append a single <spec-question> if a decision is owed to the human before the fix lands.
