Change proposal · 016-theme-support

Amend the theme contract for Prose

Two narrow, load-bearing exceptions — opacity without colour, and a theme-scoped script without losing pure-CSS-by-default — so a third theme can exist without reopening the rest of this spec.

Status Applied Change ID 2026-08-19-amend-theme-contract-for-prose Spec 016-theme-support Source 109-prose-theme · FR-001 Author Brian Corbin · @briancorbin Created 19 Aug 2026 Targets 4 requirements (4 modified) Read time

FR-002 forbids a theme touching colour at all, and NFR-005 requires a theme be pure CSS with zero script. Both are must-tier, and 109-prose-theme collides with each on its own terms — not by wanting to relax discipline generally, but because its two load-bearing behaviours (recessed narration, a one-way reveal) sit exactly on these two lines. This change widens each requirement by the narrowest exception that unblocks 109: FR-002 permits opacity-only emphasis with no colour token touched; NFR-005 permits a theme-scoped script contribution that adds no markup requirement and never breaks the JS-off fallback. Neither existing theme (calm, vivid) uses either exception, so nothing about them changes. The adversarial pass then found the amendment incomplete: SC-004 promises a third theme needs “zero changes to the switch logic”, which the NFR-005 exception directly contradicts, and SC-003's “all four combinations” assumes exactly two themes. Both are retyped here, so the spec stays consistent with itself rather than shipping a contradiction.

Amend the theme contract for Prose

Applied

1 · Intent

109-prose-theme's own design process found two collisions with this spec, each grounded before being written down rather than argued from preference. First: Prose recesses narration to bring emphasis forward, which changes rendered colour without redefining any colour custom property — but FR-002's current text forbids a theme from touching colour in any form, drawn broadly enough to catch this too. Second, and more consequential: Prose's reveal was specified in pure CSS (animation-timeline: view()) specifically to satisfy NFR-005's pure-CSS rule — and a design-time spike then measured that mechanism scrubbing by scroll position, fading a revealed block back out on scroll-up. That is exactly the behaviour 109 exists to avoid. Reveal-once and a header scroll-up trigger both need remembered state, which CSS holds none of.

Both amendments are scoped to the narrowest exception that unblocks 109, not to a general loosening of either requirement. FR-002's colour prohibition survives intact; NFR-005's pure-CSS default survives intact. Per 109 FR-001, no other task in that spec may start until both land.

2 · Scope

In scope

  • MODIFY FR-002: permit a theme to modulate the rendered emphasis of existing text (e.g. via opacity), provided no colour custom property is touched and the WCAG floor in NFR-003 still holds.
  • MODIFY NFR-005: permit a theme to additionally contribute a small enhancement to the shared switcher script, scoped to that theme's own data-theme value, adding no markup requirement to any document and never breaking the JS-off fallback.
  • MODIFY SC-004: admit the NFR-005 script exception, so the criterion no longer promises the exact thing the amended NFR-005 permits.
  • MODIFY SC-003: generalise the AA check from “all four combinations” to every registered theme × mode, and extend it to each emphasis level a theme introduces under the amended FR-002 — so the new obligation is verified rather than merely stated.
  • Split the bundled out-of-scope entry in two: the third theme repoints to 109-prose-theme, while the user-authored/custom theme editor stays TBD. Folded as a §6 task, following the precedent of this spec's own sticky-header proposal, whose §6 carried its consequential prose edits the same way.

Out of scope

  • Relaxing FR-002's colour prohibition itself — the new clause is opacity-only and explicitly cannot become a route to a theme redefining a colour custom property.
  • A blanket permission for a theme to use JavaScript freely. The NFR-005 exception is narrow: theme-scoped, markup-free, and the JS-off fallback is unconditional — a future theme wanting more than this needs its own proposal.
  • Everything Prose itself builds — the token block, the reveal module, the divider, the header choreography. This proposal only widens what 016 permits; it builds nothing.

3 · Approach

The two permission amendments add one MAY clause to an existing requirement and leave every other clause untouched, so the post-state is the current text plus one narrowly-worded permission plus one appended Rationale paragraph naming why. Neither amendment references Prose's implementation details (its opacity floor, its reveal mechanism) — 016 states what a theme may do in general terms; 109's own design carries the specifics (D-002 through D-004). This keeps the two documents at the altitude each already owns: 016 is the contract every theme answers to, 109 is one theme's choices under it.

The two criterion amendments exist because a permission that contradicts a success criterion is not a permission — it is a spec at war with itself. SC-004 and SC-003 are retyped to stay true once a third theme exists and once emphasis becomes an axis, keeping their tiers and their verifiable-by-diff and automated-check character.

4 · Deltas

Two <spec-delta>, both op="modified", both must-tier. The post-state is rendered inline as it will appear when archived.

What changes: adds one permission — a theme may modulate rendered emphasis via opacity, provided no colour custom property is touched and the AA contrast floor holds. Every other clause is unchanged.

A theme MUST control the full visual identity — typography (font families and weights), structural treatment (surface/card elevation, border radii, border and rule weights, the spacing/density scale), and component-level styling (pill shape, card and admonition treatment, multi-column layouts) — MUST NOT redefine any colour custom property, and MAY modulate the rendered emphasis of existing text (for example via opacity), provided no colour custom property is touched and the WCAG floor in NFR-003 still holds at every emphasis level used.

Rationale

The split is identity (theme) versus lighting (mode). A theme owns the shape and weight of the page — type weight, card rounding, spacing density, and how components like pills and the goals grid are laid out; a mode owns every colour, including what colour a border or surface is. Holding colour out of the theme keeps the look-set a clean 2×2: any theme renders in either mode against the same palette. Broadened on re-entry (T-002) from "type + base structure" to include component styling, since per-theme component rules are what FR-007 parity requires.

Amended for 109-prose-theme: emphasis and colour are not the same axis. A theme recessing narration via opacity changes what a reader perceives without changing which token supplies the palette — the 2×2 stays intact, because every mode still renders correctly under the modulation, and the permission cannot become a route to a theme owning colour: it names opacity specifically, never a new custom property, and it is bounded by NFR-003's floor rather than left to the theme's judgment.

What changes: adds one permission — a theme may contribute a small, theme-scoped enhancement to the shared switcher script, on top of its CSS. The pure-CSS default, the no-added-markup rule, and the additive rule are all unchanged.

A theme MUST be pure CSS keyed on data-theme over the existing semantic vocabulary by default: it MUST NOT require any document to carry added markup, wrappers, classes, or data-attributes, and a document incurs a component's theming only by using that component (opt-in by usage). A theme MAY additionally contribute a small enhancement to the shared switcher script, provided it runs only while that theme's own data-theme value is active, adds no markup requirement to any document, and leaves every artifact fully readable with JavaScript disabled. Adding a theme MUST be additive — at most 1 new [data-theme] stylesheet section plus, where used, at most 1 theme-scoped script branch — with at most 0 changes to base CSS, to documents, or to other themes.

Rationale & hard-case fallback

Raised while reconsidering how themes 3/4/5 scale: rich styling must not tax documents that don't use a feature, and a new theme must never complicate existing ones. Where a reference layout can't be reached by CSS over the current DOM (e.g. side-by-side goals/non-goals needs a shared parent), prefer a CSS-only solution (:has(), grid on the existing parent); only if that is impossible may the supporting structure be added as an opt-in authoring-template hook — present for newly-scaffolded documents that use the feature, never forced on documents that don't. Parity (FR-007) stays non-negotiable; this constrains how it's reached.

Amended for 109-prose-theme: a design-time spike (109 D-002) found pure CSS cannot express a one-way reveal or a scroll-direction trigger — both are remembered state, and CSS scroll-driven animation is a pure function of scroll position, holding none. The structural escape hatch above already exists for the case where CSS alone can't reach a layout; this extends the same reasoning to behaviour, bounded the same way — scoped to the theme that needs it, adding nothing a document must carry, and never weakening the JS-off guarantee.

What changes: admits the NFR-005 script exception. Without this, the spec would simultaneously permit a theme-scoped script branch and promise a third theme requires zero switch-logic change. The no-markup-edit and no-cross-theme-impact guarantees are kept and sharpened.

Adding a third theme touches only the stylesheet (one theme block — its typography and structural tokens), the theme registry, and — where that theme reaches for NFR-005's script exception — one theme-scoped branch in the shared switcher script: zero edits to any artifact's markup, and zero change to the switch logic of any other theme (verifiable by diff).

Rationale

Retyped alongside the NFR-005 amendment for 109-prose-theme. The original wording — "zero changes to the switch logic" — was written when a theme was pure CSS by definition, and it named the mechanism rather than the property worth protecting. The property is that adding a theme costs no document edits and cannot disturb an existing theme; a theme-scoped branch satisfies both, and is still verifiable by diff.

What changes: generalises "all four combinations" — which assumed exactly two themes — to every registered theme × mode, and extends the check to each emphasis level the amended FR-002 permits, so the new permission ships with verification rather than only a promise.

Every registered theme × mode combination passes an automated WCAG AA contrast check (4.5:1 body, 3:1 large/UI) on a representative artifact, including at each emphasis level a theme introduces under FR-002.

Rationale

Retyped for 109-prose-theme. "All four" counted a fixed 2×2; a third theme makes it six, and a fourth would make it eight, so the criterion is stated over the registry rather than a frozen number. The emphasis clause closes the gap the FR-002 amendment would otherwise open: a permission to recess text toward the contrast floor needs the same automated check the base combinations already get, or the floor is only asserted.

4b · What this change removes

Each entry names one thing this change takes away — a clause dropped from a requirement it retypes, an obligation a sibling loses, a behaviour or affordance no requirement records.

NFR-005 loses one guarantee: that every theme is expressible in zero-script CSS, with no exception. Before this change, a reader of 016 could rely on "a theme is CSS, full stop"; after it, the honest claim is "a theme is CSS by default, with a narrow, theme-scoped, markup-free, JS-off-safe exception a theme may reach for." Calm and vivid do not use the exception and are unaffected; the guarantee that they specifically stay pure CSS is unchanged. What is lost is the ability to say the rule holds for every theme unconditionally, forever.

5 · Risk register

Adversarial pass triggered: both targets are priority="must". Statuses stay identified until the author commits them — apply refuses while any remain identified.

The new MAY clause requires the AA floor to hold “at every emphasis level used”, but no success criterion verifies emphasis levels — SC-003 covers only the base theme×mode combinations — so a later theme reaching for the same exception at a different opacity has nothing catching a silent AA regression.

FR-002 delta: “provided no colour custom property is touched and the WCAG floor in NFR-003 still holds at every emphasis level used”, against live SC-003, which checks “all four combinations” and no emphasis level.

Incorporated rather than argued: a fourth delta now MODIFIES SC-003 to run the automated check over every registered theme×mode and each emphasis level a theme introduces under FR-002. The obligation and its verification now ship together, which is what the finding asked for.

SC-004 promises that adding a third theme involves “zero changes to the switch logic (verifiable by diff)” — precisely what the NFR-005 delta authorises. As first drafted, this proposal would have applied cleanly and left the live spec permitting and forbidding the same act.

Live SC-004: “zero edits to any artifact's markup and zero changes to the switch logic (verifiable by diff)”, against the NFR-005 delta: “a theme MAY additionally contribute a small enhancement to the shared switcher script”.

The finding is correct and was a real defect in the proposal, not a difference of view. A third delta now MODIFIES SC-004 to admit the exception while keeping the two guarantees actually worth protecting: no artifact markup edits, and no change to any other theme's switch logic. Both remain verifiable by diff.

Routing the out-of-scope edit as a bare §6 task, justified by citing REQ-CHANGE-002's data/content-delta carve-out, stretched that carve-out past its worked example (a manifest key/path) onto prose inside a live spec.html, letting a substantive scope decision ride along without the scrutiny the requirement deltas get.

§2 in-scope item 3 as first drafted: “folded as a §6 task rather than a delta … per REQ-CHANGE-002's requirement-shaped-target test”.

The misapplied citation is withdrawn; the §6 routing now rests on this spec's own sticky-header precedent, whose §6 carried consequential prose edits the same way. Examining the entry under that scrutiny found a second defect the finding did not name: the line bundles two deferrals, and repointing it wholesale would have claimed 109 covers a user-authored theme editor it does not touch. The task now splits the entry, leaving the editor at TBD.

No committed corpus document supplies a domain fact these deltas could contradict.

The registry at knowledge/index.md holds two rows — KB-0001 (spectastic's own SDD methodology) and KB-0002 (settlement windows, a finance-domain reference) — and neither pack's subject matter overlaps this proposal's colour, opacity or script content.

Recorded rather than omitted, so a reader can see the corpus was checked and found not to bear, instead of inferring it was skipped.
