Specification · 044-verb-model-policy

Verb model policy

Assign each verb — and each verb's fan-out subagents — a Claude model tier, so cost tracks the work without dropping quality where reasoning pays off.

Status Accepted Spec ID 044-verb-model-policy Owner Brian Corbin (me@briancorbin.co.uk) Reviewers — Created 10 Jul 2026 Principlesv1.4.0 Smallest demoableRun /spectastic.implement and see it execute on Sonnet, then revert to the session model on the next prompt. Read time

Today every verb runs on whatever the Claude Code session model is (Opus), and the CLI hardcodes one model — so a mechanical apply costs the same as a reasoning-dense plan, and the read-heavy implement (19% of weekly usage) burns Opus tokens on work Sonnet handles well. This feature makes model tier a deliberate, per-verb choice across three surfaces: slash-command frontmatter (Tier A), isolated subagent pins (Tier C), and the headless CLI's provider config (Tier D). The single most important outcome: routine, single-turn, or fan-out work runs cheaper; reasoning-and-interview verbs stay on the strong model; and an escape hatch escalates a hard task on demand.

1 · Context

Spectastic's verbs run in two execution contexts. As slash commands inside the Claude Code host, a verb runs on the session model — today, uniformly Opus. As CLI commands (spectastic <verb>, for CI and headless automation), the verb's AIProvider is built with a hardcoded, now-stale model (claude-sonnet-4-6) and no way to change it. Neither context lets cost follow the shape of the work.

The weekly usage panel made the gap concrete: /spectastic.implement is 19% of usage and 83% comes from subagent-heavy sessions — yet implement is largely context-read and mechanical bookkeeping, and its fan-out subagents (and those of propose and triage) all inherit Opus. Meanwhile the reasoning-and-interview verbs (spec, plan, propose, triage) genuinely need the strong model — and their multi-turn chat interviews would leak a frontmatter downgrade anyway (a slash-command model: override is turn-scoped and reverts on the next prompt).

Stakeholders: the maintainer, who pays for the tokens; and every future contributor, who inherits whatever default tiering ships. This is the Claude case; the same policy shape is meant to generalise to the deferred cross-tool installers.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Cheap tier for the read-heavy and mechanical verbs P1

As the maintainer, I want implement, apply, and tasks to run on Sonnet so that the biggest cost line drops without me choosing a model each time.

Acceptance: invoking any of these verbs executes on Sonnet for that turn and reverts to the session model on the next prompt; the reasoning/interview verbs are untouched (inherit).

US2 · Escalate a hard task on demand P1

As the maintainer, I want /spectastic.implement --model opus to run the task on Opus so that a gnarly task isn't stuck on the cheaper default.

Acceptance: with the flag, the task's code authoring is done by an Opus-pinned subagent while the Sonnet main loop orchestrates; without it, authoring is inline on Sonnet.

US3 · Cheap fan-out subagents, strong adversary P2

As the maintainer, I want the triage list-intake classifiers and implement [P] workers pinned to Sonnet, but the propose critic left on Opus so that the 83% subagent line drops while adversarial risk-finding keeps its depth.

Acceptance: classifier and impl-task subagents run on Sonnet; the critic runs on the session model; the main loop stays on its own model throughout.

US4 · Configure the model for headless runs P2

As a CI author, I want SPECTASTIC_MODEL / --model to set the model for spectastic <verb> so that headless runs aren't frozen on a stale hardcoded default.

Acceptance: the override resolves through the same precedence as the decider config and flows into the provider; absent an override, a per-verb default applies; the resulting model appears in the commit's Assisted-by: trailer.

Edge cases

  • An availableModels allowlist excludes the requested tier — the session keeps its current model (documented Claude Code behaviour); the CLI path fails fast on an unknown alias.
  • A verb with model: inherit whose session is already Sonnet — no switch, no regression.
  • The .claude/commands/ (or .claude/agents/) sync copy drifts from source — the running command is stale; the drift-guard/validate rule must catch a mismatched model:.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional — Tier A (slash-command frontmatter)

Each verb's slash command MUST carry a model: frontmatter key: implement, apply, and tasks set sonnet; spec, plan, propose, triage, explain, principles, and explore set inherit.

Rationale

Single-turn autonomous verbs take a clean turn-scoped downgrade; the reasoning-and-interview verbs would leak the override across chat turns and want the strong model, so they self-select to inherit. Declaring inherit explicitly (rather than omitting the key) makes each command's model posture self-describing.

Frontmatter and agent-definition model values MUST use aliases drawn from a single legal set — opus, sonnet, haiku, inherit — defined once as a core constant (the single source of truth referenced by the policy map, the validator, and the meta-spec contract), never pinned full model IDs, so they track the latest model without edits.

/spectastic.implement --model opus MUST escalate by delegating the task's code authoring to an Opus-pinned subagent while the Sonnet main loop orchestrates (context read, checkbox tick, status-flip). Without the flag, authoring is inline on Sonnet.

Rationale

A frontmatter model: is fixed when the skill activates and a body argument cannot change the turn's model — so the only honest escape hatch is subagent delegation, which reuses the Tier C impl-task agent.

Functional — Tier C (subagent pins)

The fan-out subagents MUST declare model pins via agent definitions: spectastic-classifier (triage list-intake) and spectastic-impl-task (implement [P] + escape hatch) set sonnet; spectastic-critic (propose adversarial pass) sets inherit. Agent-definition sources MUST be tracked and synced to .claude/agents/, mirroring the commands/ → .claude/commands/ convention.

Rationale

Subagent model is isolated — the pinned tier runs independently while the main loop keeps its own model. The critic stays on the session model because adversarial risk-finding is where depth pays off and it runs rarely.

Functional — the frontmatter contract

The command-frontmatter contract (REQ-TOOL-004, meta-spec) MUST permit an optional model: key, and the skill-metadata-shape validate rule MUST accept it without warning. The enforcement that a declared tier is well-formed MUST live in that validate rule, not in command prose.

Rationale

Per P-8, a frontmatter model: is advisory — the harness can't be forced to honour it. The guarantee (the key is legal and well-formed) is a kernel/CI rule. Amends REQ-TOOL-004; landed as a companion delta on 000-spectastic.

Functional — Tier D (CLI model config)

For AI-coupled verbs run via the CLI, the model MUST be resolvable from a --model flag and a SPECTASTIC_MODEL environment variable, wired through to the ClaudeProvider; absent an override, a per-verb default from the model policy applies.

Model-tier resolution MUST use the same precedence path as the decider config (per-run override > project config > verb default), not a parallel resolver, and its project-config surface MUST reuse the decider loader's fail-fast validation.

Rationale

036 FR-006 established "one resolution path, not a parallel one." Model tier is an orthogonal axis to effort, but shares the resolver and config-loading discipline.

The deterministic model policy (the per-verb tier map and its resolver) MUST live in @spectastic/core; the CLI command layer stays thin. The stale DEFAULT_MODEL (claude-sonnet-4-6) MUST be refreshed to a current model and centralised as a single source of truth.

Rationale

Fat-core / thin-CLI (P-8, and the 000/T-016 convention): a second caller — another verb, a test, the frontmatter drift-guard — would want the policy map without the CLI.

A single per-verb policy map MUST be the source of truth for per-verb tiers, and a validate (drift-guard) rule MUST flag a command whose frontmatter model: value is either not a legal alias (well-formedness) or disagrees with the map (drift), so the frontmatter and the policy cannot silently diverge and a permitted model: key never lacks machine coverage.

Rationale

Promoted from should to must by the disposition of the 000-spectastic contract proposal's adversarial pass: the meta-spec permits the optional model: key (REQ-TOOL-004) but delegates its enforcement here, so this rule is the guarantee that keeps the permission from being a P-8 "permission without enforcement." It ships in the same increment as the permission.

Non-functional

Downgrading implement, apply, and tasks MUST preserve their existing behavioural and structural tests — the tier change introduces no regression in the deterministic paths (checkbox ticking, kernel delegation, task derivation).

Tier D tests SHOULD exercise model resolution with the stub provider in CI; any real-model assertion lives only in the local test:smoke tier.

Out of scope (deferred to other slices)

  • Whether the run-budget degrade phase should also step the model tier down (a second cost lever alongside lowering effort) — left to the budget spec's own interview.
  • Passing --model to the headless ClaudeCodeAgent subprocess that spectastic implement/run shell out to.
  • Model policy for the cross-tool installers (Cursor / Aider / Copilot) — this spec is the Claude case; the shape is meant to generalise.

4 · Data model

The feature introduces one policy map and one resolution precedence; it reuses the existing provider's per-call model? seams rather than adding new ones.

Entities

ModelTier
An alias: opus | sonnet | haiku | inherit. Resolves to the current concrete model at call time.
VERB_MODEL_POLICY
A frozen Record<verb, ModelTier> in @spectastic/core, alongside the DECISION_TAXONOMY map — the single source of truth for per-verb defaults.
Resolution precedence
per-run override (--model / SPECTASTIC_MODEL) → project config (spectastic.json) → verb default (the map). The same shape the decider uses.
Agent definition
A tracked markdown source with a model: pin, synced to .claude/agents/. New: spectastic-classifier, spectastic-impl-task, spectastic-critic.

Per-verb model flows into the spec-027 Assisted-by: trailer automatically via ai.model — the trailer value now varies by verb, and no 027 change is required.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

Invoking implement, apply, or tasks executes on Sonnet for that turn and reverts to the session model on the next prompt, while the reasoning/interview verbs remain on the session model — observable in each run and in the resulting Assisted-by: value.

/spectastic.implement --model opus completes the task with the authoring performed on Opus (visible as an Opus subagent), while an unescalated run performs it on Sonnet.

spectastic validate passes on every command file carrying a well-formed model: key (no skill-metadata-shape warning), and flags a command whose model: value is not a legal alias or disagrees with the policy map.

Across a representative week after adoption, the implement and subagent-heavy shares of usage measurably fall (re-read from the usage panel) with no rise in rework or defects attributable to those verbs.

6 · Assumptions

A slash-command model: override is turn-scoped and reverts to the session model on the next prompt (documented Claude Code semantics); a subagent model: pin is isolated and does not change the main loop.

Sonnet is a capable coder for routine implement tasks; the Opus escape hatch (US2) covers the exceptions, so the default downgrade does not degrade delivered quality on the mechanical paths.

Model aliases resolve to current models at call time, so alias-based config needs no edit when the model line advances.

7 · Open questions

None outstanding — the slice boundary, escape-hatch behaviour, and the apply and critic tiers were all anchored in the interview; the budget×tier and coding-runtime interactions are deferred as scoped out, not left open.
