Design contract section

The design doc gains a home for the physical data model and the interface contract — and the interview learns to ask which interface a feature actually exposes.

Read time

design.html has eleven sections and none of them holds a data model or an interface contract. The nearest thing is one interview prompt asking for persistence shape — storage class, not storage shape — whose answer lands as a row in the technical-context table. Meanwhile the contract-first enforcement category can already fail a project for lacking a contract, and the standard-tier seeded principle already promises one ships "before the code behind it." This spec closes that loop from the authoring side: the design template gains a Data model & contracts section, and the design interview learns to ask which interface this feature exposes — request/response, RPC, GraphQL, events, or none — before it asks anything about format. The contract itself stays a file; this section declares where it lives and argues about its boundaries. Format is seeded from the declared interface, never from a default, so the recommendation stays context-earned. For anyone whose design has to hand a shape to another team.

1 · Context

A feature's entities are captured as prose in spec.html §4 — a definition list of entity to sentence, used by sixty-seven of sixty-nine shipped specs. That is the right altitude for a conceptual model and the wrong one for field types and wire formats, which belong with the stack decision that constrains them. But design.html, the artifact that records that decision, has nowhere to put them: its eleven sections run principles check, technical context, grounding, approach, alternatives, decisions, project structure, risks, complexity, open questions, change log.

The consequence is a loop the tool leaves open. The contract-first enforcement category detects checked-in contracts and can fail a verified or enterprise project for not having one; the seeded principle tells that project a contract must ship before the code. Nothing in the lifecycle ever asks the author to produce one, records where it went, or argues about its boundaries. This spec is the authoring half of closing that loop, and the first of the three slices the data model and contract survey recommends.

Whose problem: any author whose feature exposes an interface — and, downstream of them, the team in another repository who needs the shape.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · The design declares its contract P1

As a backend author, I want to be asked what interface this feature exposes and where its contract lives so that the contract is a recorded decision rather than something remembered later.

Acceptance: A design run on a spec that exposes an interface produces a Data model & contracts section naming a contract file path; the path appears verbatim in the generated design.html.

US2 · A consumer can find the shape P1

As a UI-team engineer in another repository, I want the design doc to name the contract file so that I can generate a client without reading the service's source.

Acceptance: Opening the design in a browser, the declared path is visible and unambiguous, and the section links the spec's conceptual entities rather than restating field lists.

US3 · An event-driven feature is asked too P2

As an author of a service that publishes events, I want to be asked whether this feature publishes or consumes messages and on what transport so that an AsyncAPI contract is prompted the way an OpenAPI one is.

Acceptance: The interview offers an interface-shape choice that includes an event-driven option; choosing it seeds an event-shaped contract format rather than an HTTP one.

Edge cases

  • A feature that exposes no interface at all — a CLI flag, an internal refactor. The section must record that explicitly, so absence reads as a decision rather than an omission.
  • A feature with both an HTTP surface and a published event stream: two contracts, not a forced choice between them.
  • A feature that changes an existing contract rather than introducing one — the section declares the same effective path its predecessor did.
  • A project whose ecosystem has no conventional contract location, so the author must choose one and the design records it.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The design template MUST carry a Data model & contracts section holding the feature's physical or logical data shape and its interface contract declaration.

Rationale

The conceptual model belongs to the spec; the physical model and the consumer-facing contract are consequences of the stack choice, which the design owns. Today neither has a home.

The section MUST declare the effective contract path for every interface the feature exposes, as a project-relative path.

Rationale

A declaration is what makes the contract findable by a consumer and — per the sibling specs — checkable by the tool. Inference from the filesystem cannot distinguish a published contract from a vendored upstream one.

A feature that exposes no interface MUST record that explicitly rather than omitting the declaration.

Rationale

An empty section and a considered "no interface" are indistinguishable otherwise, which turns a silent omission into an apparent decision.

The design interview MUST ask the feature's interface shape — request/response, RPC, GraphQL, event-driven (publishing, consuming, or both), or none — before asking anything about contract format.

Rationale

Format is a consequence of shape. Asking about format first smuggles in the assumption that the interface is synchronous, which is the bias the companion survey documents.

The contract format offered MUST be seeded from the declared or detected interface, and MUST NOT come from a fixed default; where nothing decisively implies one, options MUST be presented without a recommendation.

Rationale

Honours 050 FR-002 — recommendations are context-seeded and crownless where context does not earn one. A house default for contract format would be the same error that requirement forbids for stacks.

The section SHOULD link the spec's conceptual entities rather than restating them, and SHOULD carry the reasoning about the contract — boundaries, error shape, what a consumer may rely on — rather than a copy of the schema.

A feature MAY declare more than one contract, and the section MAY record a different format per declared interface.

Non-functional

The added interview questions MUST respect the decision-phase limits already in force — at most 4 questions per call, each offering 2–4 options — and MUST be skipped when an upstream artifact or detection already answers them.

The section MUST render with JavaScript disabled: 100% of its authored content — the declaration, the path, and the reasoning — readable with scripting off.

Rationale

P-4 — progressive enhancement, never dependence.

Out of scope (deferred to other slices)

  • Where the contract file lives, and the check that a declared path resolves.
  • Promoting a proposed contract to the effective one when a change lands.
  • Rendering the contract's content inside the design artifact.
  • Teaching the enforcement gate to detect a message broker, so an event-driven project is asked for a contract by the floor as well as by the interview.
  • Scoping the spec's §4 to the conceptual model explicitly, so the altitude split is stated in the meta-spec and not only implied here.

4 · Data model

No persisted entity. This spec adds an authored artifact section and a set of interview answers that populate it.

Entities

Interface declaration
What a feature exposes: a shape (request/response, RPC, GraphQL, event-driven, none), a transport where relevant, and a direction for the event case (publishes, consumes, both).
Contract declaration
The effective contract for one declared interface: a project-relative path and a format. Zero or more per feature; explicitly empty when no interface is exposed.

The declaration is about a file; it never contains the file. The contract's own content stays in the contract, which is what makes it consumable by a generator, a linter, or another repository — and what keeps a single authoritative location.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

100% of designs generated for a feature that exposes an interface contain a contract declaration naming a project-relative path; 100% of designs for a feature exposing none contain an explicit no-interface record.

For each of the five interface shapes, the format offered by the interview matches the shape — an event-driven answer never yields only HTTP-shaped options, and no shape yields a crowned recommendation the context has not earned.

A reader who opens a generated design in a browser can state, without opening any other file, which interfaces the feature exposes and where each contract lives.

6 · Assumptions

Authors know, at design time, whether their feature exposes an interface. Where they do not, the answer is a genuine open question for that design rather than something this spec can resolve.

Declaring a path is cheap enough that authors will do it honestly rather than leaving it blank. If that proves false, the resolve check in 070 is the enforcement half.

7 · Open questions

None outstanding — the interface-shape taxonomy, the format-seeding rule, and the declaration-not-inference stance were all settled by the two considerations surveys that produced this slice.
