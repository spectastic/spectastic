Design · 069-design-contract-section

Design contract section

How we will build it.

Status Accepted Spec 069-design-contract-section Owner Brian Corbin · @briancorbinxyz Branch main Created 31 Jul 2026 Read time

Add one semantic element and one template section. <spec-contract> carries the interface shape, the format, and the project-relative path as attributes — rendered as a card by CSS attr() with no JavaScript, cloning <spec-slo>'s shipped pattern exactly — and lives in a new §3 Data model & contracts in templates/design.html. The design interview learns to ask the interface shape first and seed the format from the answer. The biggest risk is the one this slice cannot retire: nothing can force the model to ask the question, so the deterministic half is a shape rule over a declaration that is written, and the resolve check that makes a declared path a real promise belongs to 070.

3 · Data model & contracts

This design is written against the template shape it proposes — the section below is the section FR-001 asks for, filled in for this feature. Dogfooding it here means the first live example exists before the template ships, and the no-interface case in FR-003 is demonstrated rather than described. One consequence is visible on this page: the <spec-contract> below currently renders as plain prose, because the stylesheet block that turns it into a card is work this design is proposing, not work it has done.

There is no persisted entity and no storage. The spec's conceptual entities — interface declaration and contract declaration — land physically as attributes on a single custom element rather than as records, so the physical model is the element's attribute grammar.

Conceptual entityPhysical shapeNotes
Interface declaration shape= · direction= shape is one of request-response, rpc, graphql, event-driven, none — the five of FR-004, no more. direction is publishes, consumes or both, meaningful only when the shape is event-driven.
Contract declaration path= · format= Project-relative path and a format token (openapi, asyncapi, proto, graphql-sdl, json-schema, or free text where none fits). Both required unless the shape is none; FR-007's multi-contract case is simply more than one element.
Reasoning (FR-006) The element's own content Boundaries, error shape, what a consumer may rely on — prose, not a copy of the schema. Rendered below the header line.

The contract this feature itself exposes:

No interface. This slice changes an HTML template, a command markdown file, a stylesheet and a schema rule — all consumed by the tool's own authoring path, none of them a wire surface another repository calls. Recording the absence explicitly is FR-003 applied to itself.

5 · Approach

Four small edits, each cloning something already shipped. assets/spec.css gains a spec-contract block modelled line-for-line on the spec-slo card: a bordered surface, a ::before composing the shape, format and path into one uppercase header line, and an optional [direction] segment for the event case. Because every scalar is an attribute surfaced through attr(), the card is correct with scripting off without a single line of JavaScript — NFR-002 is satisfied by the mechanism, not by a test that happens to pass.

templates/design.html gains a new §3 Data model & contracts immediately after Technical context, pushing Grounding through Change log down by one. The section carries a placeholder physical-model table and one placeholder <spec-contract>, so the existing “replace every [PLACEHOLDER]” discipline covers it for free. commands/spectastic.design.md gains the interview half: an interface-shape question in the decision phase, placed before any format question, with the format seeded from the shape and left uncrowned where nothing decisive implies a winner. Finally packages/schema gains contract-declaration-shape, a rule that fires only when a <spec-contract> is present and malformed — so it is loud about a broken declaration and silent about every design that has none.

6 · Alternatives considered

The load-bearing choice is how the declaration is represented, since two sibling specs must read it. Scored 1–5, higher is better; economy scores cheapness of added vocabulary.

OptionParseable by 070/072Vocabulary economyMulti-contract fitTotal
A <dl> in the section, like §2's technical context2529
A sidecar declaration file the design points at51410
<spec-contract> element — chosen53513

The <dl> is cheapest and would have worked if this slice stood alone — but it forces 070 and 072 to read prose positionally, and FR-007's two-contracts case has no clean repeat unit in a definition list. The sidecar file scores well on parseability and badly on everything the project is: a second file per design contradicts “the artifact is the document, the document is the file”, and it would put the declaration somewhere a reader of the design cannot see it.

7 · Decisions

D-001 · The declaration is a <spec-contract> element

Status
Accepted
Context
Two siblings must read the declaration mechanically: specs/070-contract-sidecar-convention/spec.html:149-153 resolves the path, specs/072-contract-embedded-view/spec.html:130-156 materialises a view from it. P-2 asks for a tag when a concept exists, and assets/spec.css:1004-1039 shows the pattern already works with no JavaScript.
Decision drivers
Machine-readability for 070/072 · P-2 · FR-007's repeat unit · vocabulary cost
Considered options
  • A <dl> in the section — + no new vocabulary, no CSS. − Positional prose parsing for two siblings; no clean repeat unit for a second contract.
  • A sidecar declaration file — + trivially parseable. − A second file per design, contradicting the single-file bet, and invisible to a reader of the design.
  • <spec-contract> — chosen — + One element serves reader, rule and both siblings; repeats naturally. − One new element and one CSS block to maintain.
Decision
A custom element carrying shape, direction, format and path as attributes, with authored reasoning as its content. Styled as a card by CSS attr(), cloning <spec-slo>.
Consequences
+ 070's rule becomes a one-line findAll rather than a prose scraper. + 072 gets an unambiguous host. + A second contract is a second element. − The vocabulary grows by one, and the CSS block must be kept in step with the theme system like every other card.

D-002 · The section is a new §3, and the rest renumber

Status
Accepted

D-003 · Five shape tokens, with direction as its own attribute

Status
Accepted
Context
FR-004 names exactly five shapes. Folding the publish/consume axis into the token list would make seven, and packages/core/src/enforce/detect.ts:459-511 shows why the axis must stay separable: dependency matching cannot distinguish a publisher from a consumer, so direction is a fact only the author holds and only the artifact can record.
Decision
shape ∈ {request-response, rpc, graphql, event-driven, none}; direction ∈ {publishes, consumes, both}, meaningful only when the shape is event-driven.
Consequences
+ The attribute grammar and SC-002's five-shape check line up exactly. + 073 can later set direction from detection without disturbing the shape list. − A consumer must read two attributes to describe an event interface fully.

D-004 · The kernel's design renderer is out of scope

Status
Accepted
Context
packages/core/src/commands/design.ts:69 pins the AI contract to a fixed JSON schema with no field for a contract, and :137-177 renders its own reduced five-section HTML that never opens the template. packages/cli/test/design.stack-interview.test.ts:6-29 records 050 hitting this exact wall and choosing not to extend the kernel.
Decision
Change the template and the command markdown only. Leave designCommand and its JSON schema untouched.
Consequences
+ Follows the established precedent and keeps the blast radius off core types, the golden-snapshot prompt test and the stub provider. + Avoids half-building a surface the interview cannot drive anyway. − SC-001's “100% of designs generated” is true of the slash-command path and not the CLI one; recorded in §10 as a ceiling, not a gap awaiting work.

D-005 · A shape rule that fires only on a present-but-malformed declaration

Status
Accepted
Context
P-8 asks for the strongest available check. packages/schema/src/rules/no-placeholder-question.ts:44-65 is the shape: findAll over the element, early return when absent, status-dependent severity. A grep across specs/**/design.html found zero <spec-contract> elements, so a present-only rule is retroactively silent by construction.
Decision
Add contract-declaration-shape to @spectastic/schema. It errors when a <spec-contract> carries no shape, carries an unrecognised shape, or carries a shape other than none with no path. It never fires on a document with no such element. Whether a declaration is written at all remains the judgment step P-8 concedes cannot be forced.
Consequences
+ A malformed declaration is blocked at the git boundary from the day the element exists. + Zero findings across all sixty-eight existing designs, so no backfill is provoked. − A design that simply omits the section is not caught; the meaningful check on a declaration that is written arrives with 070's resolve rule.

D-006 · The shape-to-format map stays in the command markdown

Status
Accepted
Context
P-14's own test is whether a second caller — another verb, a workflow, a test — would want the logic without the CLI attached. For a four-row mapping consumed only by prompt text, the answer today is no. Pure judgment; no external fact decides it.
Decision
Write the seeding rule (request/response → OpenAPI, RPC → proto, GraphQL → SDL, event-driven → AsyncAPI, both surfaces → both) into commands/spectastic.design.md as instructions. Add no core module.
Consequences
+ No entry point exists that nothing imports. + The rule sits where the only reader — the interview — will encounter it. − If 073 or 074 later wants the same mapping in code, it gets extracted then, and briefly exists in two places during that move.

D-007 · The physical model is prose and a table, not a second element

Status
Accepted
Context
FR-001 gives the section two halves, but only the contract half has downstream machine consumers. A symmetric <spec-data-model> would double the vocabulary and the CSS for a half nothing parses, and the altitude question it would imply belongs to 075.
Decision
The section opens with prose plus an ordinary entity → physical shape → notes table, linking the spec's conceptual entities per FR-006, then carries the contract card or cards.
Consequences
+ One new element, not two. + The model half stays scannable without new chrome. − The physical model is not machine-readable; nothing today asks it to be.

D-008 · Forward-only — no backfill into existing designs

Status
Accepted
Context
No requirement in the spec asks for backfill; most existing designs are past-Draft, where P-6 routes any edit through propose and apply; and the grep behind D-005 confirms the new rule stays silent on every one of them.
Decision
The template governs designs authored from here on. Existing design.html artifacts are untouched.
Consequences
+ No invented contract declarations for features whose interviews never asked the question. + No P-6 violation. − Section numbering and the presence of §3 differ across the estate until designs are naturally rewritten.

10 · Complexity tracking

Where this design introduces complexity, or accepts a ceiling, the reasoning lives here.

The interview half has no deterministic guarantee, and that is P-8's sanctioned posture rather than a gap. FR-004 and FR-005 describe a judgment step: nothing can force the model to ask the interface-shape question, and a skipped question leaves no residue in the artifact to reject. P-8 addresses this directly — where a judgment step leaves detectable residue, a checkable rule must catch it; where it leaves none, the backstop is an independent review pass. So the deterministic half is scoped to what is checkable: the template carries the section (CI content test), the markdown carries the instruction (CI content test), and a declaration that is written is well-formed (D-005). The rest is review-caught, stated rather than dressed up.

The CLI path will not produce contract declarations. SC-001 reads “100% of designs generated”; per D-004 that holds for the slash-command path and not for spectastic design, whose renderer emits its own reduced HTML. This is the same boundary 050 accepted for the stack interview, recorded here so it is never mistaken for unfinished work.

The declared path is generated content, so it is announced but not selectable. Rendering scalars through CSS attr() is what keeps the card working with scripting off, and it is the shipped <spec-slo> posture — but generated content cannot be selected or copied. Judged an acceptable trade for consistency with the design system, given the path remains present in the source and 072 is the slice that makes contract content properly readable in the artifact.

The event-driven case is asked for but not yet detected. INTERFACE_SIGNALS holds no broker signal, so an author of a purely event-driven service is prompted by the interview and still passes the contract-first floor unwarned. 073 owns that half; this slice deliberately does not touch detect.ts.
