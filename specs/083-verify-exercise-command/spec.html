Specification · 083-verify-exercise-command

The exercise command

The verify view records how the project was built and how it was tested. It has no field for the one thing a reader actually wants: the entry point that makes this feature do something.

1 · Context

Spec 021 built the verify view to answer one question: "It's built. How do I run it, see it work, and what do I turn on?" Its first success criterion promises a reviewer can run, toggle, test and demo a feature using the view alone. An audit of all 61 views found that promise met on its literal terms — the test command is copy-pasteable in 60 of 61, the run command present and runnable in 58 — and still leaving readers asking what to type.

The reason is structural rather than a lapse in authoring. run is documented as "build/start command(s)", and in 53 of 58 populated cases it holds a build or an install: pnpm -r build, cd packages/core && npx tsup. For a library or a command-line tool that is the correct answer — building is what running means — but it leaves the command that actually exercises the feature homeless. It lands in demo, which 021 deliberately specifies as "a human demo path" and which therefore accepts prose. Twenty-four views bury a command mid-sentence; nine contain no command at all. None of them violates the format.

Users: the reviewer who opens specs/<id>/verify.html after a build and wants one line to paste, and the author who wants the view to keep itself honest without inventing ceremony for specs that have nothing to exercise. The full argument, including the alternatives rejected, is in the actionability survey (D-001, D-002).

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Reach the feature from one line P1

As a reviewer who has just pulled a finished spec, I want to find the single entry point that exercises the feature so that I can see it work without reading the source or asking the author.

Acceptance: Opening a verify view generated from a capture containing an exercise entry point shows it in its own labelled row, visually distinct from the build command; the value is reproduced verbatim, so a command can be selected and pasted without editing out surrounding prose.

US2 · See that nothing was recorded P2

As a reviewer, I want to see plainly when no entry point was captured so that I can tell an unrecorded field from a feature that genuinely has no entry point.

Acceptance: A capture omitting the field renders the same loud "not recorded" treatment the format already gives other omitted fields — never a silent blank and never a fabricated placeholder.

US3 · Inherit the commands already written down P3

As an author of the existing estate, I want to backfill the views whose demo already opens with a bare command so that the new field is inhabited rather than aspirational on the day it ships.

Acceptance: Every view whose demo begins with a command has that command lifted into the exercise field, with any remaining prose left in the demo; views whose command is buried in prose, or absent, are left untouched rather than guessed at.

Edge cases

  • A feature already served by run (a web application): the exercise field holds the address that reaches the feature, such as open http://localhost:3000/settings, not a duplicate of the server command.
  • A spec with genuinely nothing to exercise — a schema rule, a CI workflow, a documentation change: the field is omitted and gaps loudly. This is expected and MUST NOT be made to look like a defect.
  • A regeneration that supplies no capture at all must preserve an exercise entry point already present, exactly as it preserves the rest of the block.
  • An entry point that is an address rather than a shell command is still a value a reader acts on, but is not something a machine can execute the way a command is — a distinction that matters to the downstream execution slice, not here.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The captured run shape MUST carry an optional exercise field holding the feature's entry point, distinct from the existing build/start field.

Rationale

The gap is a missing field, not authoring laxity: 53 of 58 populated build fields hold a build, so the exercise command has no home and defaults into the prose field. Optional because a schema rule or a CI change has nothing to exercise, and a required field would be answered n/a.

The exercise field MUST hold the entry point that reaches this feature — a command where the feature is invoked directly, or an address where the build/start field already serves it.

Rationale

Framing the field as an entry point rather than a shell command covers a web application, whose exercise step genuinely is a URL, without forcing a duplicate of the server command into the row.

A verify view generated from a capture carrying an exercise entry point MUST render it in its own labelled row, reproducing the captured value verbatim.

A verify view generated from a capture omitting the exercise field MUST render the same loud "not recorded" treatment the format gives other omitted fields, and MUST NOT emit a silent blank or a placeholder value.

A regeneration performed without a capture MUST preserve an exercise entry point already present in the view, on the same terms as the rest of the block.

The implement-time capture prompt MUST ask for the exercise entry point alongside the existing fields, and MUST state that it is omitted rather than invented when the feature has none.

Rationale

The field exists to be filled by the verb that captures the run. Adding it to the type without adding it to the prompt would guarantee it stays empty — the failure this spec exists to correct, reproduced one level down.

Existing views whose demo field begins with a command SHOULD have that command lifted into the exercise field, leaving any remaining prose in the demo; views whose command is buried in prose or absent MUST NOT be backfilled.

Rationale

Lifting a leading command is mechanical and verifiable. Extracting one from mid-sentence is a judgment call, and authoring one where none exists is fabrication — which would put invented commands into an artifact whose whole purpose is grounded evidence.

The demo field SHOULD remain free prose and MUST NOT be constrained to command shape by this spec.

Rationale

A click-path, an import snippet and a browser check are all legitimate demo paths. Nine demos contain no command and every one is conformant; tightening the field would break the honest cases to discipline a gap that belongs to the new field.

Non-functional

All 61 existing verify views MUST survive this change — 100% continuing to validate cleanly, with no new spectastic validate finding attributable to it.

Rationale

The field is additive and optional, so a view that predates it must be unaffected. Stated as a whole-corpus proportion because a single broken view is a regression, not a rounding error.

100% of rendered exercise values SHOULD be inert text, carrying no executable and no navigable element, consistent with the deny-by-default posture the spec-family templates already carry.

Rationale

The field will frequently hold a URL once a web application records its entry point, and a URL in an artifact is the obvious thing to turn into a link. It must not become one: these documents are data, and a captured value is quoted evidence rather than an invitation to navigate.

Out of scope (deferred to other slices)

  • Executing any captured command to prove it still runs. This spec adds a field; verifying that the field's contents remain true is a separate mechanism with its own hazards.
  • Making the test command a durable selector rather than a file-path list. A sibling concern in the same block, argued separately.
  • Relaxing the required toggle field, which is the literal string none in 50 of 61 views. Raised by the same survey; a change to a shipped field needs its own justification.
  • Whether an elevated profile should seed a normalized project entry point, so the per-spec field carries only what is feature-specific.

4 · Data model

This feature owns one new concept and changes the meaning of no existing one.

Entities

Exercise entry point
The single address at which this feature can be made to do something, recorded as it was actually used. It is a command where the feature is invoked directly, and a location where the build/start step already serves it. It is optional — a feature with no runtime surface has none — and when present it is exactly one, because a reader asking "what do I type" is helped by one answer and not by a menu.
Captured run
The existing record of how a completed feature was built, toggled, tested and demonstrated. It gains the exercise entry point as a sibling of those fields, and every existing field keeps its current meaning. A captured run remains a record of what was actually done, so an entry point that was never used is not recorded.

The invariant that matters: an absent entry point and an empty one are the same state, and both mean not recorded. Nothing in this feature may distinguish "the author had none" from "the author did not say", because the format cannot know which is true and guessing would put a claim into an artifact whose value is that it only carries evidence.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For a spec whose feature has a runtime surface, a reader who has never seen it can reach a working invocation using only the verify view, without reading source or asking the author — and where the entry point is a command, it is usable exactly as written, with no editing and no substitution.

Every one of the estate's verify views remains valid, and the whole-corpus validate reports zero new findings attributable to this change.

On the day this ships, the exercise field is populated in at least the views whose demo already began with a command, and in none whose command was buried in prose or absent — so the field's first population contains no invented value.

6 · Assumptions

A single entry point is enough. A feature reachable several ways is served by recording the shortest one; if that proves wrong the field can hold a compound command before it needs to become a list.

Authors will fill a field that is visibly empty. The format's existing loud-gap treatment is taken to be sufficient pressure, and no validator is added on the strength of it — an assumption the toggle field's 50-of-61 none rate gives real reason to hold cautiously.
