Design · 083-verify-exercise-command

The exercise command

One optional field, four surfaces, and a duplicated renderer that has to be unified first — because adding a field to one of two copies is how the copies stop agreeing.

Status Accepted Spec 083-verify-exercise-command Owner Brian Corbin · @briancorbinxyz Created 02 Aug 2026 Principles v1.9.0 ArchitectureNo new structure — one field threaded through an existing generator, whose duplicate is collapsed into a shared unit first. Coverage Diff-aware: new lines covered by unit tests plus one browser assertion; a change never lowers coverage of what it touches. Read time

Adding exercise to the captured run touches four surfaces: the type, the renderer, the stylesheet that gives every field its label and its loud empty-state, and the capture prompt that asks for it. Grounding turned up a fifth thing first — the run block has two renderers, one in verify.ts and a byte-identical copy in explore.ts — so the first task is to collapse them into one shared unit, before a field is added to one and not the other. The rendered value stays inert text even when it is a URL, and the backfill lifts a leading command out of 27 demos and touches nothing else.

3 · Data model & contracts

This feature exposes no interface beyond the repository: it adds an optional property to a type consumed inside the kernel and one element to a generated document. No request/response surface, no RPC, no event, so no contract file is declared.

The physical shape of the spec's exercise entry point entity is a single optional string on CapturedRun, sitting beside run, toggle, tests and demo. It carries no citation array — unlike tests and demo, it makes no claim about which requirement it covers, so there is nothing to cite.

5 · Approach

Five steps, in dependency order. The first is not part of the feature and has to happen anyway.

  1. Collapse the duplicate renderer. Extract the run-block renderer to its own kernel module and have both verify.ts and explore.ts call it. Output is unchanged for every existing caller, so the whole existing suite is the regression test.
  2. Add the field to the type. One optional string on CapturedRun, documented as the entry point rather than as a command, so the web-application case reads as intended rather than as an abuse.
  3. Render it. One line in the now-shared renderer, positioned after toggle and before tests — build it, turn it on, invoke it, test it, see it — which is the order a reader walks.
  4. Style it. Add spec-exercise to the layout, label and empty-state selector lists in assets/spec.css. Verify the label fits its column in a real browser rather than by arithmetic.
  5. Ask for it, then backfill. Extend the implement-time capture prompt, then lift the leading command out of the 27 qualifying demos by script, leaving the other 33 untouched.

7 · Decisions

Status Accepted

Context The run block has two renderers: renderRunBlock (verify.ts:325) and renderExploreRunBlock (explore.ts:55), the second describing itself as "identical in shape". They differ only in the suggested-status branch, and explore.ts never sets verified, so their output is identical today.

Decision Extract the renderer to a shared kernel module and have both verbs call it, before adding the field. Keep renderExploreRunBlock as a delegating export so no caller or test changes.

Consequences
+ The field is added once. Adding it to one copy is exactly the drift the duplication was always going to cause, and this spec is the occasion it would have happened on.
+ P-14's own test — would a second caller want this logic? — is already answered yes by the existing copy.
− A refactor inside a feature spec, which widens the diff beyond "add a field".
− Explore now inherits the suggested-status branch it never exercises; harmless, but it is dead behaviour in that path until explore captures a verified flag.

Status Accepted

Context The block's fields render in source order, and a reader scans top to bottom. Placement is cosmetic to the machine and load-bearing to the reader — this field exists precisely because the wanted line was hard to find.

Decision Render exercise after toggle and before tests.

Consequences
+ Matches the order the reader acts in, and keeps the toggle adjacent to the run it modifies.
− Existing views gain a row in the middle of the block rather than at the end, so every regenerated view has a mid-block diff.

Status Accepted

Context The interview settled that where the build step already serves the feature, the field holds an address — so this field will hold URLs. The templates carry a deny-by-default policy and P-11 holds that artifacts are data.

Decision Render the captured value as escaped, inert text in every case. Do not detect URLs, do not linkify, do not add a copy affordance.

Consequences
+ A captured value is quoted evidence, and quoting a hostile string stays inert by construction rather than by a sanitiser someone has to keep correct.
+ NFR-002 is satisfied by doing nothing, which is the cheapest kind of compliance to keep true.
− A reader must select and paste a URL rather than click it, which is a small, deliberate friction.

Status Accepted

Context FR-007 permits backfill only where a demo already begins with a command. 27 of 60 demos qualify; 24 bury a command mid-sentence and 9 have none.

Decision Backfill by script, matching only a demo whose first token is a command, lifting that command and leaving the remainder as demo prose. Review the resulting diff by hand before committing it.

Consequences
+ Mechanical and reversible, and it cannot invent a value, because it only ever moves one.
− A demo whose leading command is followed by essential context could be split awkwardly, which is why the diff is reviewed rather than trusted.
− 33 views still show a loud gap after the backfill, which is the honest state and will look like an incomplete rollout to anyone who has not read this decision.

10 · Complexity tracking

No principle exceptions claimed. The one piece of added complexity — a new kernel module for a renderer that could have stayed inline — is the fat-core convention applied, and is justified by the second caller that already exists rather than by one that might.

11 · Open questions

None outstanding. Placement, inertness, the backfill boundary and the renderer unification were all settled here; the label-column fit is a spike run at task time rather than an open question.
