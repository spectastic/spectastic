Governance gates — plan constraint & coverage

Fail a plan that touches code governed by a decision it never acknowledges, and make visible how many active decisions have no executable check — the two pure, deterministic scans that turn a recorded decision into a gate.

1 · Context

Phase-1 gap G1's second half is that no gate fails when a plan ignores a governing decision, and gap G4 is that the blind spot — a decision with no executable check — is invisible. This slice closes both with pure scans. The plan-stage constraint is the one the Valmis scenario turns on: Priya's reconciliation plan touches the positions store, an accepted decision (authored two years earlier, in another feature) governs that path, and nothing surfaced it. Here, a design whose declared surface includes a governed path must acknowledge the decision that governs it, or the build fails.

Its users are the author of a plan (who is told, at plan time, which decisions their surface invokes) and the reviewer and CI (who get a hard signal instead of relying on someone remembering a two-year-old ADR).

2 · User scenarios & testing

An unacknowledged governing decision fails the plan. A design's project-structure tree lists src/**/persistence/**. Another spec's accepted decision governs that path. The design does not mention that decision. At the standard profile or above, spectastic validate fails, naming the decision id and the governed path — before the commit lands.

Acknowledging it clears the gate. The design references the decision's id in its constraints acknowledgment; the finding disappears. A design need not acknowledge its own decisions — only those authored elsewhere.

Coverage makes the blind spot visible. validate reports "4 of 5 active decisions carry an executable check (80%)" and warns on the one that has neither a rule nor an explicit unenforceable-with-reason, and on any decision past its review-by.

3 · Requirements

A design MUST be able to acknowledge a governing decision by referencing its id (D-NNN) or coordinate in a constraints acknowledgment. An acknowledgment discharges the plan-stage constraint for that decision. A profile-gated folded scan (the plan-stage constraint) MUST, at the standard profile and above, report an error when a design's declared surface includes a path governed by an active (status="accepted") decision authored in another spec that the design does not acknowledge. The finding MUST name the decision id and the governed path. The plan-stage constraint MUST read a design's declared surface from its §Project-structure tree — the paths a design already sketches — introducing no new required authoring field. A design's own decisions MUST NOT require acknowledgment by that same design — only in-scope decisions authored in other specs do (a plan does not acknowledge itself). A coverage report MUST state the proportion of active decisions that carry an executable check (at least one <spec-rule>), and MUST warn on an active decision that carries neither a rule nor an explicit <spec-none reason=>, and on any decision past its review-by date. Coverage MUST NOT block the build. Below the standard profile, or with no profile marker, the plan-stage constraint MUST NOT fire (it fails safe on the antecedent, like the enforce floor); coverage MAY still report. Both scans MUST carry no model client and no network access — a test MUST assert each scan's transitive imports include at most 0 model clients and at most 0 network modules. Both scans MUST be deterministic: the same corpus and profile yield the same findings on every run; the review-by comparison reads an injected clock so fixtures pin it (at most 1 repeated-run diff).
  • The merge-stage verdict — running native detectors and orchestrating ecosystem enforcers to check the actual diff. Its own slice (115), because executing a command from an artifact is a different risk class (P-11 / 085 guard-first).
  • Verifying a declared rule-id exists / passes in its tool — the merge verdict's resolvable check, not a plan-time scan.
  • Injecting the governing decisions into the agent before it writes — slice 4.

4 · Data model

Declared surface
The set of path globs a design sketches in its project-structure section — what this plan will touch.
In-scope decision
An active decision (from any spec) whose scope glob matches a path in a design's declared surface.
Acknowledgment
A reference (by decision id or coordinate) in a design to an in-scope decision authored elsewhere; discharges the constraint for that decision.
Coverage
Over all active decisions: the count carrying ≥1 executable rule, the count excused by a none-with-reason, and the count neither — the proportion and the warnings derive from these.

5 · Success criteria

Given a design whose project-structure tree includes a path an accepted decision in another spec governs, with no acknowledgment, the standard-profile scan reports exactly one error naming that decision id and the governed path; adding the acknowledgment clears it, and a design's own governing decision never triggers the error.

6 · Assumptions

  • Decisions carry the structured scope metadata (112) and are read from design.html files (113's loadDecisions).
  • The profile marker is read the way quantifiedNfrFindings reads it (.spectastic/profile.json); absent ⇒ the plan-constraint is a no-op.
  • "Acknowledged" means the design's text references the decision id/coordinate — no new required element, matching the reuse-what-exists decision.
