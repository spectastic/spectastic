Design · 037-hands-off-pipeline

Hands-off pipeline

How we will build it.

Status Accepted Spec 037-hands-off-pipeline Owner Brian Corbin · @briancorbinxyz Branch 037-hands-off-pipeline Created 09 Jul 2026 Read time

A core runPipeline(input, ctx) chains the verb kernels design → tasks → implement → verify, runs validate after each step, answers each generation verb's bounded decisions via answerDecisions (039) and threads them into the kernel, performs implement via drainTasks (038), and pauses at the checkpoint gate before implement (returning an escalation the caller resumes). The CLI run wires the stubs/reals; the Workflow home is a committed script convening the Decider. Everything is driven by injected seams, so CI runs it end-to-end with stubs. Biggest risk: the generation kernels don't consume decisions today — mitigated by an additive decisions? input field.

4 · Approach

A new packages/core/src/run/pipeline.ts holds runPipeline(input, ctx): a linear driver over an ordered STEPS list. Each generation step answers its decisions (answerDecisions), calls the verb kernel with the answers threaded in, writes the artifact, and runs validate — halting to an escalation on any validate error. Before implement (and, under --checkpoints=each, after every generative verb) it yields a checkpoint the caller resolves; implement runs drainTasks; verify writes verify.html. plan/tasks kernels gain an additive decisions? field folded into their generation prompt. The CLI run command wires the real/ stub seams and raises the escalation as an AskUserQuestion gate; the Workflow home is a script that convenes the Decider per decision and runs the same STEPS.

A core driver over injected seams runs end-to-end in CI with stubs (the AI-in-CI discipline) and reuses the verb kernels directly; shelling out to CLIs is opaque to tests and slow; a Workflow-only home can't be CI-tested at all. The CLI + Workflow homes both call the same core runPipeline.

6 · Decisions

D-001 · A core runPipeline over injected seams; CLI + Workflow are thin homes

Status
Accepted
Context
The verb kernels are pure (input, ctx) functions (commands/*.ts); 038/039 are injectable seams.
Decision
runPipeline(input, ctx) in core drives the steps over ctx = {ai, coding, sandbox, verify, escalate}; the CLI wires reals/stubs, the Workflow script convenes the Decider. Both call the same driver (FR-008 parity).
Consequences
+ full run tested in CI with stubs; + one code path for both homes. − the Workflow home's execution is smoke/local (harness-run).

D-002 · plan/tasks gain an additive decisions? input, threaded into generation

Status
Accepted
Context
DesignInput/TasksInput (types.ts) are generated from one ai.chat; they take no decisions today.
Decision
Add optional decisions?: Record<string,string>; the kernel folds it into the generation prompt ("Decisions already made: …"). Absent ⇒ today's behaviour byte-for-byte (regression guard).
Consequences
+ FR-005 made real, additively; − a second consumer of the decision copy (guarded by the 039 parity test + a plan/tasks parity test).

D-003 · Escalation is a yielded checkpoint the caller resolves

Status
Accepted
Context
The harness AskUserQuestion lives in the main loop, not the kernel; 033 FR-008 defines the irreversible trigger.
Decision
runPipeline calls ctx.escalate(checkpoint) at the gate (before implement by default; after each generative verb under --checkpoints=each); a caller that returns "stop" halts the run. Tests inject an escalate that records + approves; the CLI raises a real gate.
Consequences
+ pause/resume testable without the harness; + the human's word is a hard gate (NFR-002). − the CLI's non-TTY path must decide (auto-approve with --yes or refuse).

D-004 · validate between steps is in-process validateMany

Status
Accepted
Context
@spectastic/schema exposes validateMany(docs) — no subprocess needed.
Decision
After each step the run validates the just-written artifact within its bundle; any error-severity finding halts + escalates (FR-001). Reuses the same rule set the CLI validate runs.
Consequences
+ fast, deterministic gate; − must assemble the bundle docs in memory (small).

8 · Risks & mitigations

RiskLikelihoodImpactMitigation
Threading decisions regresses plan/tasks generationMMThe field is optional; a parity test asserts absent-decisions output is unchanged (D-002).
Workflow home un-testable in CI → drift from the CLI homeMMBoth call the same core runPipeline (D-001); the CLI home is CI-tested end-to-end, the script is structurally tested + smoke-run locally.
An autonomous run on decider=human loops on escalationsLMThe run refuses decider=human up front (spec edge case); the escalation gate is the only human touch-point.
validate between steps too strict (warns halt the run)LMOnly error-severity findings halt; warnings pass (matches the CLI validate exit convention).

9 · Complexity tracking

The one genuine addition beyond "call the kernels in order" is the checkpoint/escalation yield.

The Workflow home's execution is exercised locally, not in CI — the same should-tier smoke posture as 038's real adapter. Its structure (convenes the Decider, runs the shared STEPS) is asserted in CI.
