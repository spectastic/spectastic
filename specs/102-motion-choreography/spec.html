Specification · 102-motion-choreography

Motion is a sequence

A token can say a transition lasts 220 milliseconds. It cannot say that this element moves 180 milliseconds after that one, which is the only interesting thing about an entrance.

Read time

The annotation layer homes motion on the token format's duration, easing and transition types, and that is right for one element changing. An entrance is several elements moving in a declared order relative to a shared origin, and no token expresses an order. This adds the sequence: a timeline of offsets over declared elements, the origin they are measured from, and the rule that a choreography a user cannot skip is a defect rather than a preference.

1 · Context

Motion has a home in this family and it is the wrong size. The annotation layer maps a motion category onto the token format's duration, easing and transition types, which describes one element changing: a value fades over 220 milliseconds with a stated curve. That is a property, and properties compose badly into sequences. An entrance is an eyebrow at zero, a heading at 180, a mark at 1,080, and the interesting content is entirely in the ordering and the offsets.

Nothing in the estate can express that, so it is expressed nowhere and rebuilt from a recording each time. The cost is not only the rework: a sequence nobody wrote down cannot be reviewed, and the specific thing worth reviewing is whether two elements are far enough apart to read as separate rather than collapsing into a stagger.

The accessibility half is not decoration. An animation a user cannot turn off is a defect for people who get motion sick, and the platform already exposes the preference — so the question is only whether the declaration accounts for it, and a declaration silent about it is silent about the failure case.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · A sequence is declarable with an order and an origin P1

As an author, I want to declare which elements move, in what order, and how long after a shared starting point so that a developer builds the entrance from the declaration rather than from a screen recording.

Acceptance: A screen can declare a sequence of steps; each step names an offset from a declared origin; the order is unambiguous without any number that could disagree with the markup.

US2 · A sequence says what happens under reduced motion P1

As a reviewer, I want to see what a sequence does when a user has asked for less motion so that the answer is a decision rather than an omission.

Acceptance: A declared sequence records its reduced-motion behaviour; one that does not is reported.

US3 · A step names its value rather than restating it P2

As an author, I want to point a step's duration and easing at the token set so that a timing change happens in one place.

Acceptance: A step can reference a declared token for its duration or easing; a step that states a raw value instead stays valid, because not every project has the token for it yet.

Edge cases

  • Two steps at the same offset, which is deliberate simultaneity rather than an error.
  • A sequence whose origin is not first paint — a response arriving, or a user action.
  • A single-step sequence, which is a transition and arguably belongs to the component that owns it.
  • A step whose element is one the screen does not declare.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A choreography MUST be a declared element with a stable identifier, and its steps MUST be declared elements belonging to it in the order they occur.

Rationale

Order is the content. Source order carries it here for the same reason it carries a grid's resolution order: an ordering attribute is a second ordering able to disagree with the first.

A choreography MUST declare the origin its offsets are measured from.

Rationale

An offset without an origin is a number. First paint is the common case and not the only one — a sequence may start when a response arrives or when a control is pressed, and those are different clocks.

A step MUST name the element it moves and its offset from the origin.

Two steps sharing an offset MUST NOT be reported.

Rationale

Simultaneity is a choice an author makes, and the shape must not push them into inventing a one-millisecond difference to express it.

A choreography MUST record what it does when a user has asked for reduced motion, and one that records nothing MUST be reported.

Rationale

The one place this family requires an answer rather than permitting silence, and the exception is deliberate: elsewhere an absent record means "nobody asked", which is a tolerable state for a coverage claim and an intolerable one for an accessibility preference the platform already exposes. A sequence that cannot be skipped harms a specific group of people, so silence here is not neutral.

A step MUST be able to reference a declared token for its duration or its easing rather than restating the value.

Rationale

The rule the annotation already follows: a copy is a second thing to drift, and the token set is where a timing decision lives.

A referenced token MUST NOT be resolved at validate time.

Rationale

Consistent with every other reference in this family. The token file is declared by the design, not by this vocabulary, and reaching for it here would make a screen only as valid as a path in another artifact.

A step SHOULD be able to state a raw duration or easing where no token exists for it.

Rationale

Requiring a token would make the vocabulary unusable by a project that has not built its motion scale yet, which is most of them. The reference is the better path and not the only one.

A step naming an element the screen does not declare SHOULD be reported.

A screen MAY declare several choreographies, and a screen MAY declare none without that being reported.

Non-functional

Every declared choreography, step, offset and reduced-motion record MUST render with scripting disabled: 100% of the authored content readable with JavaScript off.

Reading a choreography MUST be deterministic and side-effect free: byte-identical output across at least 3 runs, with 0 reads of clock, network or environment.

Out of scope (deferred to other slices)

  • A single control moving between two of its own states, which belongs to the component rather than to a sequence over a screen.
  • Rendering a timeline inside the design.
  • Measuring a running build against a declared sequence, which needs a clock the check deliberately does not have.
  • Importing keyframes and easing from a design tool that exposes them.

4 · Data model

One sequence, its origin, and an ordered set of steps over elements the screen already declares.

Entities

Choreography
An ordered set of steps sharing one origin, with a stable identifier. Order is source order. Belongs to a screen; a screen may have any number, including none.
Origin
The moment offsets are measured from. First paint is the common case, not the definition.
Step
An element, an offset from the origin, and optionally a duration and easing — each either a token reference or a raw value. Two steps may share an offset.
Reduced-motion record
What the choreography does when the user has asked for less motion. Required, unlike every other record in this family.

The asymmetry worth stating: an offset is relative to the origin and never to the previous step. Relative-to-previous reads more naturally and makes every step depend on the one before it, so inserting a step silently moves everything after it — which is exactly the edit somebody makes late and does not re-review.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For a declared choreography, a developer can state which elements move, in what order, and at what offset, from the declaration alone — opening 0 recordings and 0 design-tool files.

Declared choreographies with no reduced-motion record number 0, or each produces exactly 1 finding.

Screens declaring no choreography produce 0 findings about its absence, counted across every screen in the project.

Steps naming an element their screen does not declare number 0, or each produces exactly 1 finding.

6 · Assumptions

A sequence is short — a handful of steps over a couple of seconds. Assumed from what entrances look like rather than measured. A long timeline would want a different shape, and if one appears the flat step list is the thing that breaks first.

Requiring a reduced-motion record will be accepted rather than worked around. It is the only required record in the family, so it is also the most likely to be satisfied with a token answer; whether authors write something meaningful there is not something the check can see.

7 · Open questions

None outstanding. The decision worth recording is that offsets are measured from a shared origin rather than from the preceding step: relative-to-previous reads more naturally and makes inserting a step silently move everything after it, which is exactly the late edit nobody re-reviews.
