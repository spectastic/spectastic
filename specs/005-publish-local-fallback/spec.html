1 · Context

Publishing spectastic to npm runs through GitHub Actions on a v* tag push (the contract owned by 004's FR-001). CI is the default path because it bundles every release gate — typecheck, tests, build, version-verify, provenance attestation — into one trigger the maintainer can't forget.

CI is not available 100% of the time. GitHub Actions can be down. The OIDC issuer can be rate-limiting. The maintainer can need to ship a hotfix from a network where their CI secrets are unreachable. The carve-out's job is to make that day non-existential: the same maintainer can authenticate to npm directly and run pnpm publish -r from their laptop, accepting the loss of the provenance badge as the cost of the escape hatch.

2 · User scenarios & testing

US1 · Maintainer publishes from a laptop without CI P2

As a maintainer with no working CI, I want to follow a documented two-command sequence to publish both packages so that I can ship a release on a day when GitHub Actions is unavailable.

Acceptance: Following the README's Emergency local fallback section verbatim — npm login (one-time per laptop), pnpm publish -r --access public from a clean checkout at the tagged commit — produces a published version on npm with the correct dist-tag (per 004's FR-006 derivation rules). The published tarball is byte-identical to what CI would have shipped.

Edge cases

  • Maintainer's local ~/.npmrc already authenticated — npm login is a no-op; pnpm publish -r proceeds directly.
  • Local _bundled/ is stale — pnpm publish -r picks up whatever the maintainer's working tree has. The README's fallback section MUST name pnpm --filter @spectastic/cli build as a prerequisite step so the bundle is fresh.
  • No --provenance badge appears — expected. Provenance requires an npm trusted-publisher configuration that isn't present on a local machine without setup. The README documents this as a known cost of the fallback.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The root README.md MUST document a local maintainer fallback for publishing both @spectastic/cli and @spectastic/schema to npm without going through GitHub Actions. The documentation MUST name the two-command sequence (npm login followed by pnpm publish -r --access public), the prerequisite pnpm --filter @spectastic/cli build step to refresh _bundled/, and the known cost (no provenance badge without an npm trusted-publisher configuration).

This FR was originally FR-009 of 004; carved out into this sibling slice via 2026-06-16-carve-out-local-fallback.

Out of scope (deferred to other slices)

  • Configuring an npm trusted-publisher for the maintainer's local machine so the fallback path also gets a provenance badge. Useful but not blocking; the badge gap is a known cost.
  • Automated CI alternative providers (CircleCI, GitLab) as further fallbacks. Single CI provider stays the default; this slice is the human-in-the-loop alternative, not a CI-on-CI redundancy play.

5 · Success criteria

An outsider reading the README's fallback section can run the documented two-command sequence and reach a working spectastic install on npm without further explanation. The section is self-contained — it does not assume the reader has read 004's CI-driven section first.

This SC was originally SC-004 of 004; carved out via the same proposal.

6 · Assumptions

The maintainer has a working ~/.npmrc with access to publish under the @spectastic organization. The auth mechanism is npm's standard interactive flow; no spectastic-specific tooling is involved.
