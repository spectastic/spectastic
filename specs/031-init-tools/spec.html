Specification · 031-init-tools

The guarantee-layer installer — init --tools

An explicit, idempotent installer that moves mandatory workflow steps out of advisory command markdown and into git — a pre-commit validate gate and drift-proof command adapters — so a guarantee is enforced, not asked for.

Status Accepted Spec ID 031-init-tools Owner Brian Corbin · @briancorbinxyz Reviewers — Created 07 Jul 2026 Principlesv1.3.0 Smallest demoableRun spectastic init --tools, then a commit that includes a validate-erroring artifact is rejected. Read time

Today spectastic's mandatory steps are advisory: the installed Claude Code commands are one-time copies that drift from source (the T-006 footgun that made T-004 reproduce live), and nothing stops a malformed or unresolved artifact from being committed. P-8 says a guarantee must live in the kernel or CI, never in the prompt. spectastic init --tools is that mechanism: it installs a git pre-commit gate that rejects a commit when spectastic validate finds an error (or an open question in an Accepted spec), and it installs the Claude Code command adapters so they cannot drift from source. For spectastic maintainers working in a Claude Code project.

1 · Context

spectastic's source of truth for its verbs is commands/*.md. The harness, however, loads gitignored copies at .claude/commands/*.md, and nothing keeps them current — the manual cp commands/*.md .claude/commands/ re-sync is a footgun (T-006) that already shipped a real defect: a stale apply copy skipped the §6 fold and reproduced T-004 live. Separately, the steps whose omission is a defect — the decision-phase interview, the post-verb commit — are instructions in advisory markdown an LLM can skip; the skill-trigger baseline confirmed even invocation itself can't be guaranteed by description.

P-8 settled where the guarantee must live: the kernel or CI, never the prompt. T-009 landed the principle and named the mechanism as the follow-on (TBD-guarantee-layer-spec). This spec is that mechanism, scoped to its keystone: an installer that makes the guarantees real at the one portable, unbypassable boundary a project already has — a git commit. The users are spectastic maintainers running the lifecycle inside a Claude Code project.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP — the guarantee gate.

US1 · Pre-commit validate gate P1

As a spectastic maintainer, I want init --tools to install a git pre-commit hook that validates the project's artifacts so that a malformed or unresolved artifact cannot be committed — the guarantee holds without my remembering to run anything.

Acceptance: after spectastic init --tools, a git commit whose artifact set contains a validate error exits non-zero with a message naming the file and finding; a commit of a clean set succeeds; git commit --no-verify is the only path that bypasses the gate.

US2 · Drift-proof command adapters P2

As a spectastic maintainer, I want init --tools to install the Claude Code command adapters from source so they cannot go stale so that I never hand-run the cp re-sync again and a stale verb can't silently skip a step (closing T-006).

Acceptance: after init --tools, an edit to a commands/*.md source is reflected in the installed .claude/commands/ adapter with no manual copy; an installed adapter is never observed stale against its source.

Edge cases

  • Not a git repo (or git disabled) — the command-adapter half installs; the hook is skipped with a loud warning that the gate needs git (FR-009), never a silent no-op.
  • A pre-commit hook already exists — it is preserved and chained, never overwritten (FR-006).
  • A Draft spec carries open questions — this does not block commits; the open-question gate applies only to Accepted specs (FR-004), so active drafting is unimpeded.
  • A pre-existing error elsewhere in the repo — because the gate validates the whole artifact set, an unrelated error blocks the commit; the accepted contract is that the corpus stays clean, and the message names the offending file.
  • Re-running init --tools — idempotent: it reconciles to the same state and reports no spurious changes (SC-004).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

spectastic init --tools MUST be an explicit, idempotent command that installs the guarantee-layer tooling into the current spectastic project and MUST report what it installed or changed; re-running it MUST reconcile to the same state without duplicating what is already present.

Rationale

Opt-in and idempotent so it is safe to run in CI, in a fresh clone, or after an upgrade. The report is the audit trail P-8's "deterministic, inspectable" bar implies.

init --tools MUST install a git pre-commit hook that runs spectastic validate over the project's whole artifact set on each commit.

The pre-commit hook MUST fail the commit — non-zero exit, a message naming the offending file and finding — when validate reports any error anywhere in the artifact set, regardless of the artifact's lifecycle status.

The hook MUST additionally fail the commit when an artifact whose status is Accepted carries an unresolved <spec-question>. Open questions in a Draft or In Review artifact MUST NOT block the commit.

Rationale

An open question in a finished artifact is the signal that the interview failed (the discipline behind REQ-AUTHOR-005); an open question in a Draft is normal work in progress. Gating only Accepted specs makes the guarantee real without taxing active drafting.

The gate SHOULD NOT be bypassable except through git's standard --no-verify escape hatch, so the gate holds on the normal commit path and any bypass is an explicit, auditable author choice rather than a silent skip.

When a pre-commit hook already exists, init --tools MUST preserve it — chaining the spectastic gate alongside the existing hook — and MUST NOT overwrite or discard the prior hook.

init --tools MUST install the Claude Code command adapters (.claude/commands/spectastic.*.md) from the commands/*.md source such that an installed adapter cannot drift from its source — a stale installed copy MUST be structurally impossible (generated or linked on demand, not a one-time copy).

Rationale

The direct fix for T-006: the class of bug is "installed copy diverged from source"; removing the copy removes the class.

The installed adapters SHOULD present the committed, skill-tuned description from source verbatim — not regenerated at install — so the string the harness router evaluates is the one that shipped (REQ-TOOL-004).

In a project that is not a git repository (or with git disabled), init --tools SHOULD install the command-adapter half and skip the hook with a clear warning that the pre-commit gate requires git — a partial install, not a refusal.

init --tools MAY support selective install and removal (e.g. --hooks-only, --commands-only, --uninstall) so the tooling is reversible and composable; the default installs both halves.

The guarantee layer SHOULD be discoverable at init, not flag-only: an interactive (TTY) init SHOULD offer to install it, and a non-interactive run SHOULD print a one-line tip that it exists — so a user never silently ends up with no gate (and no auto-commit) simply because they didn't know the flag.

Rationale

Dogfooding T-001: auto-commits never occurred on a project because --tools was never set, and — unlike the profile prompt (041) — nothing surfaced it during interactive init. The asymmetry (profiles discoverable, tools not) was the defect.

Non-functional

The pre-commit gate MUST add ≤ 1 s to commit time at p95 on a project of ≤ 200 artifacts.

init --tools and the installed hook MUST be deterministic and keyless — no ANTHROPIC_API_KEY — matching the kernel verbs (apply, validate); they are tooling, not AI-coupled.

The installed hook SHOULD be portable across the macOS and Linux shells spectastic targets; Windows support is deferred.

Out of scope (deferred to other slices)

  • A general spectastic validate --strict flag + CI recipes for pipeline use (GitHub Actions, etc.). This spec applies the errors + Accepted-open-question rejection at the pre-commit gate; the standalone strict flag for non-hook CI is the sibling.
  • Adapters for other harnesses (Cursor / Aider / Copilot), and Windows hook support. v1 targets Claude Code on macOS/Linux only.
  • Forcing a judgment step to happen (e.g. making the decision-phase interview run). Unenforceable by construction (T-009) — this spec rejects the artifact that shows a skipped interview (open questions in an Accepted spec), it does not force the interview.

4 · Data model

The feature owns a small amount of install-time state; it changes no spec-artifact schema.

Entities

Pre-commit gate
The installed git hook that runs validate — its presence, and the chaining wrapper that preserves any prior hook (FR-006).
Command adapter link
The drift-proof binding from each commands/spectastic.*.md source to its .claude/commands/ adapter (FR-007) — a link/generation, not a copy.
Install record
What init --tools installed, sufficient to reconcile idempotently (FR-001) and to reverse via --uninstall (FR-010).

Lifecycle of an install: absent → installed → (re-run) reconciled → (uninstall) removed. The gate and the adapters install and uninstall independently, so --hooks-only / --commands-only are coherent partial states, not half-broken ones.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

After spectastic init --tools, a git commit whose artifact set contains a validate error is rejected (non-zero exit, message naming the finding); a commit of a clean artifact set succeeds.

After init --tools, a commit that includes an Accepted spec carrying an open <spec-question> is rejected; the same open question in a Draft spec does not block the commit.

After init --tools, editing a commands/*.md source is reflected in the installed Claude Code adapter with no manual copy step, and an installed adapter is never observed stale against its source.

spectastic init --tools run twice in succession produces identical installed state and reports no changes on the second run.

The pre-commit gate adds ≤ 1 s to commit time at p95 on a ≤ 200-artifact project.

With a pre-existing pre-commit hook present, after init --tools both the prior hook and the spectastic gate run on commit, and the prior hook's behavior is unchanged.

6 · Assumptions

The target is a spectastic project (has specs/ + spectastic.json) and, for the gate, a git repository — consistent with the existing git layer (026).

spectastic validate's exit code already distinguishes an error-bearing run from a clean one, and its findings carry file + rule + severity (per 002) — the gate consumes that contract rather than re-deriving it.

Contributors commit through git; --no-verify is an occasional, deliberate escape, not the default path. A contributor who routinely bypasses the gate is outside the guarantee by choice.
