Specification · 066-corpus-single-layer-retire

Retire single-layer corpus support

Stop producing legacy single-layer packs and give existing ones a migration path — the non-breaking first phase of retiring the pre-062 shape.

1 · Context

The two-layer identity migration (062) moved the corpus onto a durable shape: the KB-NNNN lives in the project's root knowledge/index.md registry, and each document carries a pack-local slug:. But the pre-062 single-layer shape — id: KB-NNN in the document itself, plus a pack-local index.md, and no registry row — is still produced by corpus-writing verbs and still accepted everywhere. A single-layer document resolves only through the resolver's deprecated pack-scan fallback, at best; an edition-pinned citation to it never resolves via the registry.

065 fixed one producer: convert now registers two-layer. The other, adaptCorpus, still emits single-layer — and there is no command to bring an existing single-layer pack forward. This spec closes both gaps and opens a deprecation window, without breaking anything yet: single-layer stays accepted (the validator warns, doesn't reject; the resolver's fallback stays). A later spec lands the breaking retirement.

Who it's for: anyone curating a corpus — a spectastic project or a standalone spectastic-corpus user — who has adapted a markdown folder or inherited a pre-062 pack.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP (no verb produces single-layer any more).

US1 · adapt produces two-layer P1

As a corpus curator, I want adapt to file two-layer documents so that the markdown folder I shape becomes a registry-cited pack, not a legacy single-layer one.

Acceptance: adapt <folder> writes each document with a slug: (never a document id:) at references/<NNN-slug>.md, a repo-unique KB-NNNN row in the root registry, and a SKILL.md — and no pack-local index.md. Same terminal shape as convert (065) and import.

US2 · migrate an existing single-layer pack P1

As a curator with a pre-062 pack, I want one command that converts it to two-layer in place so that my existing references become registry-cited without hand-editing every file.

Acceptance: corpus migrate <pack> rewrites each id: document to slug:, allocates a repo-unique KB-NNNN registry row per document, ensures a SKILL.md, and removes the pack-local index.md. Running it again is a no-op; running it on an already-two-layer pack changes nothing.

US3 · single-layer is flagged deprecated P2

As a corpus maintainer, I want validate to tell me a pack is still single-layer so that I know to migrate it before the shape is retired.

Acceptance: validating a project whose loaded knowledge/ pack contains a single-layer document (an id: frontmatter or a pack-local index.md) yields a warning (not an error) naming corpus migrate as the fix. A two-layer pack yields no such warning.

Edge cases

  • A pack with mixed shapes (some id:, some slug:) — migrate converts the single-layer documents and leaves the two-layer ones untouched.
  • A pack-local id: KB-001 is not repo-unique (every pack starts at KB-001) — migrate MUST allocate a fresh repo-unique KB-NNNN, never reuse the pack-local number.
  • A prior pack-scan citation to a document's old id: stops resolving by that id after migration — the document is now cited by its registry KB-NNNN / marketplace·plugin·slug coordinate.
  • A hand-edited title/description/edition in the pack survives migration (non-destructive).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

adaptCorpus MUST produce two-layer documents — a slug: frontmatter (never a document id:), a repo-unique KB-NNNN row in the root registry, and a pack SKILL.md — and MUST NOT write a pack-local index.md.

Rationale

The same re-base 065 applied to convert: a corpus-writing verb must produce the durable two-layer shape, not the pre-062 legacy one. Reuses the registerDocument backbone.

The corpus tool MUST provide a migrate <pack> verb that converts a single-layer pack to two-layer in place: each id: document becomes a slug: document, gains a repo-unique KB-NNNN registry row, the pack gains a SKILL.md, and the pack-local index.md is removed. It MUST be idempotent — a second run, or a run on an already-two-layer pack, makes no change.

migrate MUST allocate a fresh, repo-unique KB-NNNN for each migrated document and MUST NOT reuse the document's old pack-local id: number (which is not repo-unique — every pack numbers from KB-001). The document's pack-local identity becomes its slug:.

spectastic validate / corpus validate SHOULD emit a warning (never an error, this phase) for a loaded knowledge/ pack that still carries a single-layer document (an id: frontmatter or a pack-local index.md), naming corpus migrate as the remedy.

Rationale

The "deprecate first, reject later" window: downstream corpora get notice and a migration path before any hard break. Warning severity mirrors the orphan/fragmentation findings, not the well-formed errors.

Non-functional

Both adapt and migrate MUST be idempotent and non-destructive: re-running never duplicates a registry row or document, and a hand-corrected title/description/edition MUST survive a re-run (carrying forward 056 NFR-001 / 061 NFR-003).

The deprecation warning (FR-004) MUST NOT fire on a two-layer pack (no false positives), and MUST be scoped to loaded knowledge/ packs — a project's own corpus — never to raw fixtures held outside a corpus root.

Out of scope (deferred to other slices)

  • Flipping single-layer from a warning to a validate error — the breaking phase-2 retirement, gated on a deprecation window.
  • Removing the resolver's pack-scan fallback (the registry becoming the sole authority) — its own breaking concern, unchanged here.
  • Migrating examples/knowledge/finance-settlement — it exists deliberately as pre-062 raw input for 057's portable-skill test; it stays single-layer.

4 · Data model

No new persisted entity — the target is the existing two-layer document (051/062): a slug: reference file, a KB-NNNN root-registry row, and a pack SKILL.md. This spec adds a transformation and a classification, not a new shape.

Entities

Single-layer pack
The pre-062 shape being retired: documents carrying id: KB-NNN frontmatter + a pack-local index.md, absent from the root registry. The input to migrate and the subject of the deprecation warning.
Migration
An in-place transformation of a single-layer pack into a two-layer one — re-keying each document's identity from a pack-local id: to a slug: + a repo-unique registry KB-NNNN, and dropping the pack-local index.

Invariant: migration is identity-preserving at the slug layer, re-keying at the registry layer — the document's pack-local name (its slug:) is stable, but its repo-wide id is freshly allocated because a pack-local id: can collide across packs.

5 · Success criteria

Technology-agnostic, measurable outcomes.

After corpus migrate <pack> on a single-layer pack, every document carries a slug: (no id:), the root registry holds one repo-unique KB-NNNN row per document, a SKILL.md exists, and no pack-local index.md remains — verifiable by reading the pack and the registry.

adapt <folder> on raw markdown produces a pack of the same two-layer shape (slug documents + registry rows + SKILL.md, no pack-index) — the same terminal state a migrate would reach.

Both migrate and adapt are idempotent: a second run leaves the pack and registry byte-for-byte unchanged (a hand-edited cell excepted, which survives).

Validating a project whose knowledge/ pack is single-layer yields a deprecation warning naming corpus migrate; validating a two-layer corpus yields no such warning and no new error.

6 · Assumptions

The two-layer registerDocument backbone (065) is the reuse target for both adapt's new output and migrate's per-document filing; neither invents a parallel filing path.

Single-layer packs are resolved today only via the resolver's pack-scan fallback, so re-keying a document's id during migration breaks no registry citation (there were none) — only an id-based pack-scan lookup, which is itself deprecated.

7 · Open questions

None outstanding — the scope (adapt + migrate + deprecation warning), the phasing (warning now, reject later), the resolver-fallback deferral, the legacy-fixture carve-out, story priorities, and the in-place idempotent migrate shape were all anchored in the interview.
