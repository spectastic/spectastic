1 · Context

The apply kernel (010-core-apply, REQ-CHANGE-008) deterministically folds an approved proposal's deltas into a live spec, appends the changelog, folds §6 into the tasks tracker, flips the proposal to applied, and archives it. But it is spec-scoped: packages/core/src/commands/apply.ts hardcodes specs/<specId>/spec.html, specs/<specId>/changes/, and specs/<specId>/tasks.html.

A principles amendment lives at repo root: its proposal is changes/<slug>/proposal.html and its target is principles.html. The kernel has no path for this, so every principle change — P-6, P-7, and P-8 — was applied by hand. That is precisely the defect P-8 names: a mandatory step (applying the amendment) whose guarantee lives in hand-execution, not deterministic code. The guarantee-layer survey ranks "own the loop" (the kernel) as the strongest enforcement; this slice extends that ownership to the one artifact it doesn't yet cover.

2 · User scenarios & testing

Each story is independently testable: US1 alone is a viable MVP.

US1 · Apply a principles amendment via the kernel P1

As a spectastic author, I want to run spectastic apply principles <slug> on an approved principles proposal so that the amendment lands deterministically with no hand-editing of the ratified principles.html.

Acceptance: given an approved proposal at changes/<slug>/ with one ADD delta targeting P-N, a declared target version, and declared replacement tagline + TL;DR fields — running the command inserts P-N after the last existing principle, updates the version in all three places, substitutes the tagline + TL;DR, appends a changelog entry, flips the proposal to applied, archives it with deepened paths, and commits. git diff principles.html touches only those regions.

US2 · Refuse an unsafe or stale apply P2

As a spectastic author, I want principles apply to refuse when the proposal is unsafe so that I can't silently corrupt the ratified constitution.

Acceptance: apply exits non-zero and mutates nothing if any <spec-risk status="identified"> remains (same gate as spec apply), if the proposal's declared from-version does not match the live principles.html version (stale guard), or if a required replacement field (tagline / TL;DR) is absent.

Edge cases

  • Root changes/archive/ does not exist on the first principles apply — the move MUST create it (the REQ-CHANGE-007 mkdir-before-rename discipline, applied at root depth).
  • The ADD delta's P-N already exists in principles.html — refuse (an ADD target must not pre-exist), same as spec apply.
  • A MODIFY delta on an existing principle (not just ADD) — the fold MUST replace the principle body in place, mirroring spec-apply MODIFY semantics.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

spectastic apply MUST accept principles as a reserved <spec-id> that resolves the proposal to changes/<slug>/proposal.html and the target to principles.html, both at repo root — applying the same approval-status and risk-gate preconditions as a spec apply.

Rationale

Keeps the existing apply <spec-id> <slug> arity verbatim; no new flag or second code path. principles is the only root-level artifact with a proposal lifecycle.

The kernel MUST fold the proposal's delta into principles.html — inserting an ADD'd principle after the last principle in the Core principles section, or replacing a MODIFY'd principle's body in place — and MUST NOT create or require a tasks tracker: a principles proposal's §6 is the apply mechanics the kernel performs, and stays frozen in the archived proposal.

The kernel MUST update principles.html's version in all three places it appears (the small-caps pill, the <spec-meta> Version, the footer) to the proposal's declared target version, set the "Last amended" date to today, and append a <spec-changelog> entry naming the archived proposal.

The kernel MUST substitute principles.html's tagline and TL;DR from explicit replacement fields the proposal declares, and MUST NOT infer or rewrite that prose itself. If a required replacement field is absent, apply MUST refuse with a clear error and mutate nothing.

Rationale

Structural edits are deterministic; the tagline count ("Seven" → "Eight") and the TL;DR sentence are content the author writes. The kernel substitutes author-written prose; it never guesses prose (brittle, and it would put a guarantee's content outside the author's control).

Principles apply MUST refuse — non-zero exit, no mutation — if any <spec-risk status="identified"> remains, or if the proposal's declared from-version does not match the live principles.html version (a stale-proposal guard).

On success the kernel MUST flip the archived proposal to applied, move the folder to changes/archive/<slug>/ (creating the parent if absent, per the REQ-CHANGE-007 mkdir-before-rename discipline), deepen its relative paths for the new depth, and commit per the git layer — the same archive semantics as spec apply, and keeping principles.html schema-valid.

The /spectastic.apply slash command SHOULD pass the principles sentinel automatically when the proposal targets principles.html, so the author types the same verb regardless of target.

Non-functional

Principles apply MUST be keyless (no ANTHROPIC_API_KEY) and deterministic — the same input proposal yields byte-identical output — matching spec apply.

The principles-apply path SHOULD reuse the existing spec-apply machinery (delta fold, risk gate, archive move, path rewrite) rather than a parallel copy, so the two cannot drift.

Out of scope (deferred to other slices)

  • spectastic validate --strict as an unbypassable CI gate (guarantee-layer slice 2). Plain validate already errors on open <spec-question>s; strict promotes advisory rules and is spec'd separately.
  • spectastic init --tools — the per-harness hook adapters + a git pre-commit calling spectastic validate (guarantee-layer slice 3).
  • Updating /spectastic.propose to auto-emit the replacement tagline + TL;DR fields for principles proposals. For this slice they are authored in the proposal (authoring — not hand-editing the applied artifact).
  • Generalizing apply to arbitrary non-spec targets via auto-detection. principles is the only root-level target today; a reserved sentinel is enough (YAGNI).

4 · Data model

This slice adds no persistent entities; it introduces one reserved identifier and one proposal-side field group.

Entities

Reserved spec-id principles
A sentinel <spec-id> that resolves to root changes/<slug>/ + principles.html. It has no spec.html and no tasks.html; the kernel branches on it.
Proposal replacement fields
The declared target version (already in the proposal's <spec-meta> / §Targets) plus a new tagline and new TL;DR the kernel substitutes verbatim. Field shape (attributes vs a structured block) is a plan decision.

The kernel already has FileSystem.mkdir + mkdir-before-rename (from the archive-dir-creation fix, REQ-CHANGE-007); the root changes/archive/ case reuses it. This is P-8 in miniature: the guarantee (a principle lands correctly) moves from a human's hands into a deterministic function.

5 · Success criteria

Technology-agnostic, measurable outcomes.

Running spectastic apply principles <slug> on an approved principles proposal produces a principles.html that contains the new/updated principle, shows the declared version in all three places, shows the substituted tagline + TL;DR, and carries a new changelog entry — with a git diff that touches only those regions; the proposal is archived and the run is committed. Zero hand-edits.

A principles proposal with an identified risk, a stale declared from-version, or a missing replacement field is refused with a non-zero exit and principles.html left byte-identical.

A principles apply creates no principles-tasks.html and folds no §6 phase.

After a successful apply, spectastic validate principles.html reports zero findings (the P-7 done-means-verified bar).

6 · Assumptions

principles.html is the only root-level artifact with a change-proposal lifecycle; the meta-spec (000-spectastic) and every feature spec live under specs/ and are already handled by spec apply.

Principles proposals carry a single ADD or MODIFY delta targeting a principle ID (P-N), matching the P-6 / P-7 / P-8 precedent. Multi-delta or REMOVE principle proposals are rare and can extend this path later.
