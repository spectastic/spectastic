Spectastic CLI — spectastic init

One command turns any directory into a spec-driven project.

spectastic init is a Python 3 single-file CLI that bootstraps any directory into a spectastic project. Zero arguments by default; writes .claude/commands/spectastic.*.md (8 slash commands), copies assets/spec.css and assets/spec.js, copies templates/ (5 scaffolds). Prompts before overwriting any existing file. Claude Code is the only supported tool in v1; cross-tool installers are deferred to a future slice.

1 · Context

Today, adopting spectastic means cloning the repo and copying directories — friction enough to lose marginal users. A one-command installer reduces adoption to a single gesture, in exchange for owning a Python entry point.

2 · User scenarios & testing

US1 · Bootstrap an empty directory P1

As a developer adopting spectastic, I want to run spectastic init in an empty project directory so that the eight slash commands, the design system, and the templates appear without any copy-paste from the repository.

Acceptance: after spectastic init in an empty directory, the cwd contains .claude/commands/spectastic.*.md (8 files), assets/spec.css, assets/spec.js, and templates/ with all five scaffolds. The exit code is 0. A one-paragraph "next step" message points the user at /spectastic.principles.

US2 · Bootstrap a directory with existing assets P1

As a developer re-running init after a spectastic upgrade, I want to be prompted before any existing file is overwritten so that my hand-edits and project state never silently disappear.

Acceptance: when any target path already exists, the CLI lists all conflicting paths and prompts [y/N/a(ll)/s(kip-all)] per file. Default (no input) is No. A skipped file is not written; an overwritten file is. The summary report breaks out written / skipped / overwritten counts.

US3 · Force-overwrite all P2

As an experienced spectastic user, I want to run spectastic init --force so that conflicts are silently overwritten and the prompt is skipped.

Acceptance: with --force, no prompts. All target paths written unconditionally. Summary still reports the overwritten count.

US4 · Non-Claude environment P3

As a non-Claude user, I want the next-step message to name /spectastic.principles as a Claude Code slash command, so I don't expect the infra to work in my editor. Folded into FR-004.

Edge cases

  • Read-only filesystem → exit non-zero; no partial state.
  • Python below minimum → exit with a message naming the minimum.
  • cwd is a symlink → resolve it; write to the resolved location.
  • cwd is a git working tree with staged changes → no special handling; user reviews via git status.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Behaviour

Zero-argument spectastic init MUST write the lifecycle infrastructure to the current working directory: .claude/commands/spectastic.*.md (all eight slash commands), assets/spec.css, assets/spec.js, and templates/ (the five scaffolds).

Before overwriting any existing file, init MUST list the conflicting paths and prompt the user with [y/N/a(ll)/s(kip-all)]. The default (empty input) MUST be No.

Rationale

Hand-edits and project state must never silently disappear; safe-by-default is the only acceptable posture for a tool that operates on the user's filesystem.

Init MAY accept a --force flag that skips the conflict prompt and overwrites all conflicting paths.

On completion, init SHOULD print a summary listing the count of files written, skipped, and overwritten, plus a next-step suggestion naming /spectastic.principles as a Claude Code slash command.

Safety

On any error during execution, init MUST exit non-zero and MUST NOT leave the cwd in a partially-written state. Writes MUST be all-or-nothing per file: either the file lands fully or it does not exist after exit.

Init MUST NOT write outside the cwd. No global config writes, no home-directory writes, no parent-directory writes.

Non-functional

In an empty directory on a modern macOS or Linux machine, init MUST complete in under 2 seconds wall-clock (file IO dominates; no network calls).

The CLI MUST run on Python 3.9 or later using standard library only — no third-party packages, no pip install step.

The CLI binary SHOULD ship as a single executable file at scripts/spectastic with a #!/usr/bin/env python3 shebang and no external imports beyond the standard library.

Out of scope (deferred to other slices)

  • Cross-tool installers for Cursor, Aider, GitHub Copilot. v1 is Claude-only; multi-tool support gets its own spec.
  • spectastic validate. Same Python file; different subcommand; its own spec (002-validate-cli).
  • A spectastic doctor diagnostics subcommand.
  • Self-update (spectastic update) and version-bumping policy across upstream changes.
  • Package-manager publication (homebrew tap, PyPI). v1 installs via chmod +x on a downloaded file.
  • Detection of the user's editor (auto-pick Claude vs Cursor vs Aider). Out for v1; user names the tool implicitly by what they install.

4 · Data model

None. The CLI is stateless: it reads from a known asset layout in its package, writes to the cwd, and exits. No database, no config files, no per-user state.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

A new user MUST go from "I want to try this" to running /spectastic.principles in their own project in under 5 minutes wall-clock.

Zero silent data losses MUST occur. Every overwrite MUST result from explicit user yes-or-force.

Init SHOULD complete in under 2 seconds for the empty-directory case at p95.

6 · Assumptions

Python 3.9+ is available (macOS ships 3.9+ since 12.3; modern Linux similarly). Windows is out of scope for v1.

Distribution is by direct download (curl … && chmod +x); no package manager in v1.

The user runs Claude Code in the cwd. The CLI doesn't detect this; it writes .claude/ unconditionally.
