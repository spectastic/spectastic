Design · 108-success-criteria

Success criteria

How we will build it.

Status Accepted Spec 108-success-criteria Owner Brian Corbin · @briancorbinxyz Branch spec/success-criteria-108 Created 19 Aug 2026 Read time

Six pure per-file rules over a document the parser has already read, one element with its own card, and four consumers taught what a conformance-bearing element is. The whole contract is decidable inside one document — validates= points at requirements in the same file — so unlike the coverage check next door this needs no cross-file scan and no filesystem read. The risk that matters is not the rules; it is that four readers of <spec-requirement> fail silently when a criterion stops being one.

2 · Technical context

Language / runtime
TypeScript on Node for the rules; plain browser JavaScript for the two assets/spec.js sites, which belong to no package.
Architecture
Per-file schema rules, the shape ~40 existing rules already use. No new module boundary, no port, no package (D-001).
Test framework
Vitest, tests written failing first. Each rule is a pure function over a parsed document, so a fixture is a string.
Coverage
Patch target: every new rule branch covered, and a change never lowers coverage of what it touches. The refusal paths matter more than the happy ones here — a rule that never fires is the defect this spec is about.
Persistence
None. Every slot is an attribute or element content in the document already in memory.
Perf
NFR-001: 0 model calls in the six gating rules. NFR-002: 0 filesystem reads beyond those existing rules already perform — achievable because validates= resolves within the same document (D-002).

Toolchain / enforcement

The enterprise floor is already covered — 8 categories covered, observability relaxed under a waiver with an owner and expiry, 0 missing. This design adds no workspace member and no gap, so there is nothing to bring under a gate that is not already under one.

3 · Data model & contracts

No consumer-facing interface. The rules run inside spectastic validate; nothing calls them over a wire. The one thing that is a contract — which elements count as conformance-bearing — is settled by D-005 and expressed as a single exported predicate rather than a document.

6 · Approach

Three pieces, and only one of them is interesting. The rules are six pure PerFileRules in @spectastic/schema, each reading attributes and element content from a document the parser has already produced — the shape ~40 existing rules use, added by writing a file and two lines in the registry. The rendering is a CSS card cloning spec-requirement’s: a grid, an id chip from attr(id), and the actor and thresholds visible without opening a slot.

The consumers are the part that can go wrong quietly. Four places read <spec-requirement> and each would disagree with a criterion in its own way, none of them loudly. Four are settled by a single exported predicate naming what counts as conformance-bearing, which the two TypeScript readers call; assets/spec.js belongs to no package and cannot import it, so its two sites are updated directly and a test pins that the two definitions agree. That divergence — a sixth element added to the predicate and not to the browser copy — is the one failure this design expects to outlive it.

The obvious alternative was to keep <spec-requirement id="SC-*"> and add the slots as attributes. It has near-zero blast radius and every rule still works, because they key on the id rather than the tag. It was rejected for the reason the spec exists: the conflation of an obligation with a measured observation is the root cause, and preserving the element preserves it.

7 · Alternatives considered

How a criterion is expressed. Scored 1–5, higher better.

OptionSeparates observation from obligationBlast radiusRules expressibleMigration costTotal
Keep <spec-requirement id="SC-*">, add attributes154515
A kind="criterion" attribute on the existing element244414
A distinct <spec-criterion> element — chosen525416

The winner is the worst option on blast radius and wins anyway, which is worth stating plainly: it scores 2 because four consumers must be taught, and every one of them fails silently. What buys it back is the first column. The conflation of an obligation with a measured observation is the defect the spec exists to remove, and both alternatives preserve it — the attribute variant most deceptively, since it looks like a separation while leaving every consumer treating a criterion as a requirement.

Migration cost is near-identical across all three, which is the column people expect to decide it and does not: FR-013’s forward-only binding means no existing criterion is rewritten under any option.

8 · Decisions

D-001 · Six per-file schema rules, no new module

Status
Accepted
Context
A rule is an id, a scope, a severity, a description and a check(ctx), plus two registry lines (requirement-id-required.ts; rules/index.ts:43,76). ~40 already exist in that shape.
Decision
The six gating checks are PerFileRules in @spectastic/schema. No new package, port or kernel scan.
Consequences
+ The pre-commit gate picks them up with no wiring.
+ A fixture is a string, so the refusal paths are cheap to test.
− Six more files in a directory already holding ~40, discoverable only by reading the registry.

D-002 · Per-file, not a kernel scan — the neighbouring precedent does not apply

Status
Accepted
Context
The obvious model is visualCoverageFindings, which had to leave the schema engine because the grid it resolves against is a separate file. A criterion’s validates= targets are requirement ids in the same spec.html.
Decision
Resolve entirely within the document. No filesystem access in any of the six.
Consequences
+ NFR-002’s zero-read budget holds by construction rather than by discipline.
+ The orphan check (a requirement no criterion validates) is a single pass over one tree.
− A future cross-spec criterion — one validating a requirement in another spec — would not fit and would need the kernel-scan shape after all.

D-003 · The four consumers are verified by opening a page

Status
Accepted
Context
All four failure modes are silent: the trace empties, the drift rule stops joining, the index drops rows, the gauge undercounts. 048 shipped exactly this class once — typed elements with render logic and no CSS — and every structural and headless check passed.
Decision
FR-012 is closed by a browser check on a real spec plus a byte comparison of a regenerated verify.html, not by asserting a rule ran.
Consequences
+ The one requirement whose failure is invisible gets the one verification that can see it.
− A manual step in the drain, which is what SC-003 makes explicit rather than leaving to memory.

D-004 · The card clones the requirement card; the slots stay <details>

Status
Accepted
Context
spec-requirement carries 34 stylesheet references — grid, an id chip from attr(id), a priority pill. The print block already ships details:not([open]) > *:not(summary) { display: block }.
Decision
Clone the card, adding an actor chip and the threshold pair. Meter and falsifying observation stay in <details>.
Consequences
+ 091 REQ-RENDER-001 and REQ-RENDER-002 are inherited, not restated — no print CSS to write.
+ A criterion costs roughly a requirement’s height in the flow (P-5).
− Two cards to keep visually in step; a change to one silently leaves the other behind.

D-005 · One predicate for the readers it can reach, a pinned copy for the one it cannot

Status
Accepted
Context
Two of the four consumers are TypeScript (verify.ts:138, verify-view-stale.ts:84) and can import a shared predicate. The other two are in assets/spec.js (:52, :97), plain browser JavaScript belonging to no package and importable by nothing.
Decision
Export one predicate naming the conformance-bearing elements; the TypeScript readers call it. The two browser sites are updated directly, with a test asserting the two lists agree.
Consequences
+ A sixth such element is added in one place for every reader that can import.
+ The copy that cannot import is guarded rather than trusted.
− Two definitions of one fact exist, and the test is the only thing preventing them diverging — a weaker guarantee than a single source, chosen because the asset has no module system to share one.

D-006 · Criteria are indexed and counted, like requirements

Status
Accepted
Context
No existing spec carries a criterion, so either choice satisfies FR-012. The size gauge exists to make authored bulk visible (091 REQ-FORMAT-004).
Decision
The conformance index lists criteria in their own group; the gauge counts them toward reqs=.
Consequences
+ A spec cannot grow unbounded criteria while the gauge reports green.
+ A reader scanning the index sees what the spec claims as well as what it obliges.
− 108’s own budget must be authored once with criteria counted, and the number moves under it as they are written.

D-007 · Tests written failing first

Status
Accepted
Context
Pure judgment. Each rule is a pure function over a parsed document and a fixture is a string, so the cost of a test is near zero.
Decision
Each rule opens with a failing test asserting the refusal, then the pass case.
Consequences
+ A rule that never fires is this spec’s own subject matter; red-first is what proves it fires.
− Says nothing about whether the slots change what authors write, which only SC-001 answers over time.

10 · Risks & mitigations

RiskLikelihoodImpactMitigation
A sixth conformance-bearing element is added to the predicate and not to spec.js, and the index quietly stops listing it. MM The parity test (D-005) fails when the lists diverge. It is the only guard, and it is named as such rather than presented as a single source of truth.
Authors fill every slot and still write a criterion that restates its requirement. HM Not preventable by the deterministic six — it is precisely what FR-014’s graded rules exist for, and they are advisory. The honest ceiling, stated in the spec’s own assumptions.
The panel’s verdict on criterion quality is too noisy to act on. ML The one assumed row in §5. Should-tier and advisory by design, so a noisy verdict degrades to ignorable rather than blocking a commit — and SC-004 measures it against what reviewers actually object to.
The actor denylist rejects a legitimate actor, or passes an artifact it does not know. ML A denylist fails open by construction, which is the right direction: a missed artifact is one bad criterion, a false rejection is a blocked commit. Its contents are data, editable without touching the rule.
Forward-only binding means the 382 existing criteria are never revisited. HL Accepted, not mitigated. That is what forward-only means, and the alternative — rewriting criteria for work already delivered, from reconstructed intent — is how fiction gets committed. Deferred explicitly as TBD-criteria-estate-migration.

11 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here. A reviewer should be able to point at any non-trivial choice and find its rationale in this section.

Two definitions of one fact

D-005 leaves the conformance-bearing element list stated twice: once as an exported predicate, once inline in assets/spec.js. That is a genuine duplication and the design does not pretend otherwise. The asset is loaded directly by every artifact as a plain script and belongs to no package, so there is nothing to import from; the alternatives were to give the asset a build step, or to move the index and gauge server-side, both of which are larger changes than this spec justifies. The parity test is the compensating control.

A denylist of artifact nouns is sufficient to catch the actor mistake in practice. The estate’s failures are the verb, an image, the number captured — the tool’s own vocabulary, which is a small closed set. An author determined to name something obscure will pass, and that is the ceiling FR-014’s graded rule exists to reach past.

Counting criteria toward the requirement budget will not push existing specs over. No spec in the estate has a criterion element, so today the count is unchanged everywhere; only specs authored under this contract see the number move. Checked rather than assumed for the estate, assumed for what people write next.
