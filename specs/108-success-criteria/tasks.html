Tasks · 108-success-criteria

Success criteria

Ordered, parallelizable work. Tests precede implementation. Drive through with /spectastic.implement — one task per invocation.

Status Draft Spec 108-success-criteria Design design Branch spec/success-criteria-108 Created 19 Aug 2026 Read time

30 tasks across five phases. Foundational carries the one thing every story needs — the shared predicate naming what counts as conformance-bearing — and nothing else; Setup is empty and says why. US1 is the six rules, US2 the four silent consumers, US3 the forward-only binding. The six rules are genuinely independent of one another, so US1 fans out wider than any story in this estate so far. Tests for a story MUST be written and failing before its implementation tasks start.

1 · Execution strategy

Foundational, then US1 alone: six rules that refuse a bad criterion. That is the whole value proposition and it ships without US2 or US3 — the element renders as plain prose and the estate is unbound, but a new criterion can no longer be unfalsifiable.

Foundational → US1 → US2 → US3 → Polish. Each story closes its conformance before the next opens. The natural order here, since US2 depends on Foundational’s predicate and US3 depends on nothing.

After Foundational, all three stories are independent. US1’s six rules are themselves independent of each other — six files, six fixtures, no shared state — so this story parallelises further than the usual one-team-per-story split.

2 · Phase 1 — Setup

Empty, deliberately. No new package, no new dependency, no CI change: six rule files land beside ~40 siblings in a directory that already builds and runs, and the pre-commit gate picks them up from the registry with no wiring (D-001).

3 · Phase 2 — Foundational

One thing every story reads, and the element it all hangs off.

Export the conformance-bearing predicate — the single list naming which elements carry conformance, which US1’s orphan check and US2’s two TypeScript readers both consume (D-005). packages/schema/src/conformance.ts

4 · Phase 3a — US1 · A criterion that can fail

Tests (write & fail first)

One file per rule, so six agents can write six fixtures without touching each other — the split that a shared test file cost this estate once already.

Assert an artifact actor is refused — a criterion declaring actor="the verb" is reported and one declaring actor="reviewer" is not; a criterion declaring no actor at all is reported (FR-002). packages/schema/test/criterion-actor.test.ts
Assert an unobservable criterion is refused — a human-observed criterion carrying no meter is reported; a mechanically-observed one carrying an observation point and no sampling frame is not, which is the shape gate rather than a blanket requirement (FR-005). packages/schema/test/criterion-observable.test.ts
Assert a conjoined outcome is refused — a criterion joining two outcomes is reported; one whose prose merely contains the word “and” inside a single outcome is not (FR-008). packages/schema/test/criterion-single.test.ts
Assert an RFC 2119 keyword is refused — a criterion containing MUST, SHOULD or MAY is reported, including inside a nested <spec-rule> (FR-009). packages/schema/test/criterion-indicative.test.ts
Assert both directions of the validates relation — a criterion with empty or absent validates is reported, and separately a requirement in the same document that no criterion validates is reported (FR-007, SC-002). packages/schema/test/criterion-validates.test.ts
Assert an unjustified extreme threshold is refused — a criterion asserting 0, 100% or two equal thresholds without a justification is reported; the same criterion carrying one is not (FR-011). packages/schema/test/criterion-threshold-justified.test.ts
Assert the six rules reach a verdict with no model and no filesystem — a structural scan of the six rule sources for a model client, a fetch, or any fs/readFile call, the same shape as 106’s no-comparison guard (NFR-001, NFR-002). packages/schema/test/criterion-rules.pure.test.ts

Implementation

Implement the actor rule — presence, plus a denylist of the tool’s own vocabulary; fails open on an unknown noun, per the design’s recorded assumption. packages/schema/src/rules/criterion-actor.ts
Implement the observability rule — gated on whether the observation is mechanical, not on whether the actor is human. packages/schema/src/rules/criterion-observable.ts
Implement the single-outcome rule packages/schema/src/rules/criterion-single.ts
Implement the indicative-mood rule packages/schema/src/rules/criterion-indicative.ts
Implement the validates rule — both the empty-target refusal and the orphan-requirement report, resolving entirely within the document (D-002). packages/schema/src/rules/criterion-validates.ts
Implement the threshold-justification rule packages/schema/src/rules/criterion-threshold-justified.ts
Register the six rules — one import and one array entry each; the last task in the story because it is the one file all six touch. packages/schema/src/rules/index.ts
Exercise the rules against a deliberately bad criterion — spectastic validate over a fixture spec whose criterion names an artifact actor, joins two outcomes and asserts a bare zero, confirming three findings naming three different slots. Entry point for this story’s path.

Closes FR-002, FR-005, FR-007, FR-008, FR-009, FR-011, NFR-001, NFR-002, SC-001, SC-002. The slot requirements FR-003, FR-004, FR-006 and FR-010 are closed here too, by the element shape the rules read rather than by a rule each — a criterion without two thresholds cannot satisfy T-105, and one without a baseline or a falsifying observation is caught at authoring by the template rather than at the gate. Deliberate: gating every slot would make the six rules twelve for no additional defect caught, since FR-011 already forces the threshold pair to be real.

5 · Phase 3b — US2 · What would prove this wrong

Tests (write & fail first)

Assert the verify trace still finds its criteria — generating a verify view for a spec whose criteria are <spec-criterion> produces the same trace rows it produced when they were requirements, rather than an empty section (FR-012). packages/core/test/verify.criterion-trace.test.ts
Assert the drift rule still joins on criteria — a verify view that has fallen out of step with a spec’s criteria is reported stale, which it cannot be if the rule stops seeing them (FR-012). packages/schema/test/verify-view-stale.criterion.test.ts
Assert the two element lists agree — the predicate’s list and the copy inlined in assets/spec.js name the same elements; the only guard against the duplication D-005 accepts (D-005). packages/schema/test/conformance-parity.test.ts

Implementation

Teach the verify generator — extractScIds reads the predicate instead of matching spec-requirement. packages/core/src/commands/verify.ts
Teach the drift rule — the same predicate, at its spec-requirement scan. packages/schema/src/rules/verify-view-stale.ts
Teach the conformance index and the size gauge — both call sites read criteria as well as requirements; the index groups them separately and the gauge counts them toward reqs= (D-006). assets/spec.js
Confirm the four consumers by opening a page — open 108’s own spec in a browser and read the four observables directly: the index lists its criteria, the gauge counts them, and a regenerated verify.html is byte-identical for a spec that has none. The one requirement whose failure is invisible to every structural check (D-003). Entry point for this story’s path.

Closes FR-012, SC-003. Also closes FR-001 in the only way it can be observed — the element is distinct precisely when these four consumers treat it as its own thing rather than as a requirement.

6 · Phase 3c — US3 · The estate does not fall over

Tests (write & fail first)

Assert a pre-binding spec is left alone — a spec authored before the stated version reports 0 criterion findings even when its criteria would fail every rule, and one authored after reports them (FR-013). packages/schema/test/criterion-binding.test.ts

Implementation

Implement the forward-only binding — the six rules stand down for a spec authored before the stated version, following the mechanism principles.html already uses rather than inventing a second one. packages/schema/src/rules/criterion-binding.ts
Confirm the estate is unmoved — run spectastic validate over all 102 specs and confirm 0 new findings against the 382 pre-existing criteria. Entry point for this story’s path, and the check that decides whether the gate is something people fix forward through or switch off.

Closes FR-013.

7 · Phase 4 — Polish

Give the criterion element its card — clone the requirement card’s grid and id chip, add an actor chip and the threshold pair; the meter and falsifying observation stay behind their summaries. Verified by opening a page in both modes, not by asserting the CSS parsed (FR-015, D-004). assets/spec.css
Scaffold the criterion into the spec template — replace the two placeholder <spec-requirement id="SC-*"> blocks with a filled criterion showing every slot, so the next author copies the shape rather than reading about it. templates/spec.html
Update the authoring guidance — the two sentences that were the entire contract now point at the element and its slots, and say which checks gate a commit. commands/spectastic.spec.md
Wire the two graded judgments into the critic panel — stakeholder vocabulary and test-suite-satisfiability, as advisory findings that inform an author and gate nothing (FR-014). packages/core/src/decider/panel.ts

Closes FR-015, FR-014, SC-004. FR-015 sits in Polish rather than a story because no story depends on it — the rules gate and the consumers read regardless of how a criterion looks. That is also the argument for doing it: a slot nobody can see is one nobody fills, which is why it is the first Polish task rather than the last.
