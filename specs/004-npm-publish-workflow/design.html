Design · 004-npm-publish-workflow

npm publish workflow for @spectastic/cli and @spectastic/schema

How we will build it.

Status Accepted Spec 004-npm-publish-workflow Owner Brian Corbin · @briancorbinxyz Branch 004-npm-publish-workflow Created 15 Jun 2026 Read time

A single GitHub Actions workflow at .github/workflows/publish.yml with two jobs sharing the gate logic: a dry-run job runs on PRs touching the workflow file itself (catches YAML errors and broken gates before any tag exists), and a publish job runs on v* tag pushes (does the real publish). Both jobs use major-version-tag-pinned third-party Actions for ergonomic Dependabot updates. The release procedure is hand-written in README.md — no helper script. Biggest risk: a stale _bundled/ at publish time would ship the wrong templates; mitigated by re-running prebuild inside the workflow before publish.

3 · Approach

One workflow file, two jobs sharing a YAML anchor for the install + gates. The dry-run job triggers on pull-requests that touch .github/workflows/publish.yml; it installs, typechecks, tests, builds, and runs pnpm publish --dry-run -r — the dry-run flag validates the publish would succeed (resolves workspace:*, checks package contents, etc.) without actually pushing a tarball to npm. The publish job triggers on tag pushes matching v*; it runs the same gates, additionally verifies the tag-derived version matches all three packages' package.json, and then publishes for real with --provenance --access public and the derived dist-tag set.

The dist-tag set is computed by scripts/derive-dist-tag.mjs (D-006, superseding D-005's inline bash). It keys on whether a stable release exists rather than on the version string: while no bare-semver version has ever been published, a pre-release moves both next and latest, so the documented bare install resolves to the newest build; once a stable exists the guard engages and pre-releases go to next only. The workflow passes the primary tag to pnpm publish --tag and applies any extra tag with npm dist-tag add across all three packages; an undeterminable registry state fails the run rather than guessing. Provenance flows through GitHub's OIDC sidecar — the workflow job declares permissions: { id-token: write, contents: read }, npm picks up the short-lived OIDC token at publish time, and the resulting attestation links the tarball back to this specific commit and Actions run.

4 · Alternatives considered

The foundational pick: how to pin third-party Actions. Scored 1–5 (higher is better).

Major-version tags win on the qualities that matter for a small public repo: Dependabot keeps them current; readers don't squint at 40-char hashes; maintenance is near-zero. The security delta vs SHA pins is real but bounded (the actions we use are first-party GitHub or pnpm; the attack surface is supply-chain compromise of those orgs, not the pin style we choose).

5 · Decisions

D-001 · Single workflow file with two jobs (dry-run on PRs + publish on tags)

Status
Accepted
Context
Two jobs share most of the gate logic (install + typecheck + tests + build). Splitting into two files would duplicate the gates or introduce composite-action complexity.
Decision
One file at .github/workflows/publish.yml; two jobs (dry-run, publish) gated by different on: triggers (pull_request with path filter; push: tags: ['v*']). YAML anchors share the gate steps.
Consequences
+ Single source of truth for gate logic; no drift risk. + Dry-run catches YAML errors before any tag exists. − Slightly larger YAML file than a publish-only workflow; the path filter on the dry-run job needs to stay aligned with the workflow filename if either ever renames.

D-002 · Major-version tag pins for third-party Actions

Status
Accepted
Context
NFR-003 SHOULDs pinning to SHAs or major-version tags. The repo is small, public, and uses only first-party GitHub Actions plus pnpm/action-setup; supply-chain risk is bounded.
Decision
actions/checkout@v4, actions/setup-node@v4, pnpm/action-setup@v4. Dependabot enabled for the github-actions ecosystem to bump major-version tags as they ship.
Consequences
+ Readable YAML. + Dependabot auto-updates with minimal review burden. − Marginal supply-chain exposure if an upstream org gets compromised and force-pushes a tag. Accepted; this is a public docs-site-style repo, not a banking app.

D-003 · PR-time dry-run job for workflow self-testing

Status
Accepted
Context
Workflows that only run on production triggers (tag pushes) get debugged in production. A dry-run job lets us catch YAML syntax errors, missing secrets, broken gates, and pnpm-publish issues before the first real release.
Decision
The dry-run job triggers on pull_request events whose changeset includes .github/workflows/publish.yml. It runs the same gates + pnpm publish --dry-run -r --provenance --access public. The dry-run flag exercises the publish path (workspace:* rewriting, package-contents check, manifest validation) without writing to npm.
Consequences
+ Workflow errors surface in PR review, not in the release. + No extra cost when the workflow file isn't being edited. − One extra job to maintain; the path filter must include any related files (e.g. if we add a scripts/publish-helpers.mjs later, the filter widens).

D-004 · README documentation only; no release-helper script

Status
Accepted
Context
The release procedure is four commands (edit × 2 → commit → tag → push). A helper script saves typing but adds a maintained file and an indirection layer.
Decision
Document the procedure in README.md under a "Releasing" section. Show both the tag-push path (primary) and the local-emergency-fallback (npm login + pnpm publish -r --provenance --access public).
Consequences
+ No new code to maintain; the README is the source of truth. + Maintainer learns the underlying commands rather than abstracting over them. − Four commands per release vs one. Trade is acceptable; releases are not frequent enough to amortise a helper.

D-005 · Bash conditional for dist-tag derivation

Status
Superseded by D-006
Context
FR-006 requires the dist-tag to derive from the version string: pre-releases on next, bare semver on latest. Options: a custom Action, a Node script, or an inline bash conditional.
Decision
Inline bash in the workflow: if [[ "$VERSION" == *-* ]]; then DIST_TAG=next; else DIST_TAG=latest; fi. No dependency; readable in the YAML; easy to extend if the rule grows.
Consequences
+ Zero dependencies; works on the default ubuntu-latest shell. + One line of logic, one line of test (the dry-run job covers it). − If the rule grows beyond "contains a hyphen → next," promote to a small scripts/derive-dist-tag.mjs. Not anticipated.

D-006 · Promote the dist-tag derivation to a tested script

Status
Accepted
Context
The rule D-005 implemented has grown exactly as D-005 anticipated. Applying 2026-07-23-prerelease-latest-dist-tag, FR-006 now keys on whether a stable release exists rather than on the version string, moves two tags across three packages, and must fail rather than guess when the registry state can't be determined. That is four branches, a network call and a failure path — no longer "one line of logic".
Decision
Take D-005's own escape hatch: move the derivation into scripts/derive-dist-tag.mjs, splitting a pure deriveDistTags(version, publishedVersions) from the one function that touches the network. The workflow calls the script and reads back a primary tag (passed to pnpm publish --tag) plus any extra tags applied with npm dist-tag add. Kept as repo release tooling rather than moved into @spectastic/core — it is infrastructure, not product domain, and should not ship in a published package.
Consequences
+ Every branch is unit-tested (scripts/derive-dist-tag.test.ts, 11 cases) instead of executing for the first time during a live publish — the riskiest place to be wrong. + The RC-window case (1.0.0-rc.* before any stable) is pinned by a test, not just prose. + vitest.config.ts's include widens to scripts/**/*.test.ts, so release tooling is covered by the normal suite. − A release now depends on registry availability, not just registry writes; an undeterminable state fails the run deliberately, and the README rollback runbook covers recovering from a bad tag. − One more file outside packages/.

7 · Risks & mitigations

RiskLikelihoodImpactMitigation
Stale _bundled/ ships the wrong templatesLHWorkflow runs node packages/cli/scripts/prebuild.mjs as a dedicated step before publish, on top of the build job's prebuild. Any drift would also fail the test suite since the smoke test reads _bundled/.
Partial publish (one package succeeds, the other fails)LMpnpm publish -r publishes both in one operation; npm publishes both before returning. If atomicity fails (network blip), the maintainer can npm unpublish within 72 hours per npm policy and re-tag with the next version.
Tag pushed but package.json versions don't matchMLVerify-versions step exits non-zero before any publish step runs; FR-003. The README's "Releasing" section emphasises bumping before tagging.
NPM_TOKEN leaks via workflow logsLHGitHub Actions auto-masks secrets in logs. NFR-002 requires granular-access scope, limiting blast radius if the token leaks anyway.
Provenance generation fails silentlyLMnpm errors out with a clear message if --provenance can't get an OIDC token. The dry-run job exercises the same code path on PRs touching the workflow.
Pre-release lands on latest dist-tagLMD-005's bash conditional is unit-tested via the dry-run job. If it ever misclassifies, npm dist-tag rm @spectastic/cli latest recovers in one command.

8 · Complexity tracking

One complexity addition worth justifying.

Two jobs in one workflow file. A simpler shape would be a publish-only workflow that runs on tag push. Adding the dry-run job doubles the YAML and adds a second trigger. Justified by D-003: workflows that only run on production triggers get debugged in production, and the cost of a release-day mistake is higher than the cost of a few extra YAML lines.
