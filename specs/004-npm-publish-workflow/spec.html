Specification · 004-npm-publish-workflow

npm publish workflow for @spectastic/cli and @spectastic/schema

Tagged-commit CI workflow that publishes both packages to npm with synced versions and provenance attestation. Make the binary one npm i -g away for anyone.

Status Draft Spec ID 004-npm-publish-workflow Owner Brian Corbin · @briancorbinxyz Reviewers — Created 15 Jun 2026 Principles v1.0.1 Smallest demoableA tag push (e.g. git tag v0.1.0-pre.3 && git push --tags) drives a GitHub Actions workflow that runs tests, builds, and publishes both packages to npm with provenance; an outsider can then npm i -g @spectastic/cli and run spectastic init + spectastic validate. Read time

Both @spectastic/cli and @spectastic/schema exist locally and are workspace-linked, but neither has been published to the npm registry — so the install story today is "clone the repo and npm link." This spec adds a GitHub Actions workflow at .github/workflows/publish.yml that fires on v* tag pushes, runs the full test + build gate, verifies the tag matches the version in both packages' package.json, then publishes both with synced versions, --provenance via OIDC, and the right dist-tag (next for pre-releases, latest for stable). A documented local fallback (npm login + pnpm publish -r) covers the case where CI is unavailable. Out of scope: GitHub Release automation, package signing beyond provenance, autogenerated changelogs.

1 · Context

Tier 1 shipped @spectastic/cli and @spectastic/schema as Node packages. They work for the maintainer because npm link from a clone makes the spectastic binary global on the local machine. They do not work for anyone else: npm view @spectastic/cli returns 404 because nothing has ever been published. Spec 003 explicitly deferred the publish workflow to a follow-up slice (TBD-npm-publish in §3 Out of scope); this spec is that follow-up.

The trigger for picking this up now is distribution. Tier 3 (VS Code extension) will tell users "install @spectastic/cli via npm." That instruction needs to actually work. Until then, sharing spectastic with someone outside the repo means walking them through cloning, installing pnpm, building, and npm link-ing — high friction that masks the actual quality of the tooling. Publishing closes that gap.

2 · User scenarios & testing

Each story is independently testable.

US1 · Outside user installs spectastic P1

As a developer with Node 20+ and no clone of spectastic, I want to run npm i -g @spectastic/cli so that I get a working spectastic binary that I can use against my own projects without cloning the source.

Acceptance: After the install, which spectastic resolves; spectastic init in an empty directory writes the canonical 16-file lifecycle; spectastic validate <some-file.html> works against any spec-html the user produces. Output matches the local-clone install byte-for-byte.

US2 · Maintainer releases a new version P1

As a maintainer, I want to release a new version by editing both packages' version fields, committing, tagging, and pushing so that I never run npm publish manually under release-day pressure and I never have to remember which gates to run by hand.

Acceptance: The sequence edit package.json × 2 → commit → git tag v0.1.0-pre.3 → git push --tags drives a GitHub Actions workflow that runs typecheck + tests + build, verifies the tag matches both package.json versions, then publishes both packages with --provenance. On any gate failure (test red, version mismatch, build error) the publish is blocked and the failure is visible in the Actions tab.

US3 · Sceptical consumer verifies provenance P2

As a downstream user evaluating supply-chain risk, I want to see a verified-source badge on npmjs.com for @spectastic/cli so that I can confirm the tarball was built from a specific commit in the public repo without trusting my eyes or downloading the source.

Acceptance: The npmjs.com page for each published version shows the provenance attestation linking back to a specific spectastic/spectastic commit and GitHub Actions run.

Edge cases

  • Tag pushed but package.json versions don't match the tag — workflow exits non-zero before any publish step; no npm tarball produced.
  • One package publishes; the second fails — pnpm publish -r publishes both in one operation; on partial failure, the maintainer can npm unpublish within 72 hours per npm policy or bump the next version and re-tag.
  • Same version re-tagged — npm rejects republish of the same version; the workflow surfaces npm's error and exits non-zero.
  • Pre-release accidentally hits latest dist-tag — the workflow inspects the version string: if it matches X.Y.Z-pre.N (or contains a dash before the digits), it publishes with --tag next; only bare X.Y.Z goes to latest.
  • Maintainer pushes a tag with no prior commit — npm requires the build artifacts; the workflow does a fresh checkout + prebuild + build, so the published tarball is always derived from the tagged commit.
  • CI is unavailable — the README documents the local fallback (npm login + pnpm publish -r); maintainer can publish from a laptop in an emergency.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional — the workflow

A GitHub Actions workflow at .github/workflows/publish.yml MUST trigger on push of any git tag matching the pattern v* (e.g. v0.1.0-pre.3, v0.1.0). The workflow MUST NOT trigger on branch pushes or pull requests.

Before any publish step runs, the workflow MUST install dependencies, typecheck both packages, run the full test suite, and build both packages. Any non-zero exit from these gates MUST halt the workflow before pnpm publish is invoked.

The workflow MUST extract the version from the git tag (strip the leading v) and verify it matches the version field in both packages/cli/package.json and packages/schema/package.json. On mismatch (either package, or the two packages out of sync), the workflow MUST exit non-zero with a clear error naming the expected and observed values.

The workflow MUST publish both @spectastic/cli and @spectastic/schema in one pnpm publish -r invocation so the two packages ship atomically when possible. The publish step MUST pass --provenance and --access public; authentication uses an NPM_TOKEN secret with granular-access scope limited to the @spectastic org.

Provenance attestation MUST be generated via GitHub Actions OIDC (the workflow job declares permissions: { id-token: write, contents: read }). Each published version appears on npmjs.com with a verified-source badge linking to the originating commit and workflow run.

The dist-tag MUST be derived from the version: if the version contains a hyphen (matching X.Y.Z-*, the pre-release pattern), publish with --tag next. If the version is bare semver (X.Y.Z), publish with --tag latest. This keeps npm i @spectastic/cli (no tag) from accidentally pulling pre-releases.

The workflow MUST re-run the prebuild step (refreshing packages/cli/_bundled/) before publish, so the shipped @spectastic/cli tarball includes a bundle generated from the tagged commit's commands/, assets/, and templates/. A stale or missing _bundled/ MUST halt the publish.

After a successful publish, the workflow SHOULD emit a workflow-summary block (visible in the Actions tab) listing the two published versions with links to their npmjs.com pages.

The root README.md MUST document both the CI-driven release path (tag push) AND a local fallback (npm login + pnpm publish -r --provenance --access public) so the maintainer can release from a laptop if CI is unavailable.

Non-functional

The workflow MUST complete in under 5 minutes p95 on GitHub-hosted ubuntu-latest runners. The bulk of the time is dependency install (~30 s with cache), typecheck + tests (~30 s), build (~10 s), and publish (~20 s); 5 minutes leaves slack.

The NPM_TOKEN secret MUST be a granular access token scoped to publishing the @spectastic npm organization only (not a classic token; not org-admin-scoped). The token MUST be stored as a GitHub Actions repository secret and MUST NOT appear in any committed file, including the workflow YAML.

The workflow SHOULD pin all third-party Actions (actions/checkout, actions/setup-node, pnpm/action-setup) to specific SHAs or major-version tags to reduce supply-chain drift from upstream Action changes.

Out of scope (deferred to other slices)

  • GitHub Releases automation — generating a Release object on github.com with release notes synced from the CHANGELOG. The tag IS the release record for v1; richer Releases land later.
  • Package signing via sigstore beyond what --provenance already provides. Provenance attestation is enough for v1 supply-chain hygiene.
  • Autogenerated changelogs (semantic-release, changesets, conventional-commits). Manual CHANGELOG.md entries stay the practice; automation can come later if release cadence warrants.
  • Snapshot/canary publishes from main on every push (e.g. 0.0.0-canary.<sha>). Not a v0.1 concern; release-from-tag is enough.
  • Per-package independent versioning. This spec commits to synced versions; if independent versioning becomes necessary later, it's a different spec, not a re-entry on this one.
  • A spectastic deprecate workflow for retiring a published version. Out for v1; npm deprecate manually if needed.

4 · Data model

The slice owns one data shape: the release event.

Entities

Release
Fields: tag (string, e.g. v0.1.0-pre.3), version (string derived from tag), commit (SHA), distTag ("next" | "latest" derived from version), packages (array of {name, publishedAt, provenanceUrl}). The Release is implicit — it lives in the workflow run output, not in a committed file. Captured here so the plan can model what the workflow logs.

The package.json version fields are the single source of truth for what a release ships. The git tag is a verification mechanism (it MUST match) and a trigger; it does not define the version. This separation matters: if the tag drifts from package.json, the workflow refuses rather than silently publishing whichever interpretation it picks.

5 · Success criteria

Technology-agnostic, measurable outcomes.

After the first publish lands, an outside user with Node 20+ and no clone of the spectastic repo can run npm i -g @spectastic/cli and then spectastic init in an empty directory; the resulting 16-file tree is byte-identical to the local-clone install. The same user can run spectastic validate against a sample spec.html file and get correct findings or a clean pass.

Each published version on npmjs.com displays a provenance attestation linking to a specific commit on github.com/spectastic/spectastic and a specific workflow run. The link resolves to a non-404 GitHub URL.

A test scenario with a deliberately-failing test in the workflow run produces a workflow failure before any pnpm publish step executes. npm view @spectastic/cli versions shows no new entry from that workflow run.

The README's install section includes both the npm-i-g instruction (US1's path) and the local-fallback documentation (US2's escape hatch). A reader following either path lands on a working install.

6 · Assumptions

The @spectastic npm organization exists (or the maintainer creates it as a one-time setup before the first publish). The maintainer also adds an NPM_TOKEN granular-access-token secret to the GitHub repo's Actions secrets, scoped to publishing the @spectastic org only. These are one-time bootstrapping steps captured as preconditions, not implementation tasks.

Both packages/cli/package.json and packages/schema/package.json already carry "publishConfig": {"access": "public"} from Tier 1; the workflow doesn't need to override access at publish time. The workspace:* dependency from @spectastic/cli to @spectastic/schema is rewritten by pnpm-publish to the matching synced version range.

npm provenance via GitHub OIDC remains available and free for public packages through the planning horizon. If npm changes the policy materially, the --provenance flag falls back to no-op on publish and the workflow still succeeds; the npmjs.com badge would be the visible loss.
