Change proposal · 004-npm-publish-workflow

OIDC trusted publishing

Retire the long-lived npm token: publish via OIDC trusted publishing, on pnpm 11.

Status Proposed Change ID 2026-09-14-oidc-trusted-publishing Spec 004-npm-publish-workflow Author Brian Corbin · @briancorbinxyz Created 14 Sep 2026 Targets 4 requirements (FR-003, FR-004, FR-006, NFR-002) Read time

The pre.28 publish failed on a 404 PUT — a token problem — and npm is deprecating 2FA-bypass granular tokens for direct publishing (Phase 2 ~Jan 2027). Trusted publishers are now configured on npmjs.com for all five @spectastic/* packages, so this change makes the workflow use them: authentication moves to OIDC trusted publishing (no stored token), on pnpm 11.27.0 — the CLI that performs the npm OIDC exchange. It touches four requirements: FR-003 (version check), FR-004 (auth), FR-006 (dist-tag), NFR-002 (the token requirement). No gate or exit-code changes.

OIDC trusted publishing

Proposed

1 · Intent

The v0.1.0-pre.28 publish failed twice at the npm step with 404 Not Found - PUT …/@spectastic%2frender — a credential failure, not a code one (every gate passed). The same-night pattern (pre.27 published at 00:14, pre.28 failed at 02:39) points at the NPM_TOKEN expiring, rotating, or losing scope. Separately, npm is deprecating 2FA-bypass granular tokens for direct publishing — Phase 2 (~Jan 2027) restricts them to staged publishes needing human approval — so a token-based flow is on a clock regardless.

The durable answer npm steers everyone toward is OIDC trusted publishing: the workflow mints a short-lived, run-scoped token via GitHub OIDC, and no long-lived secret exists to expire, rotate, or be restricted. The trusted publishers are already configured on npmjs.com for all five packages; this change makes the workflow authenticate through them. The one hard requirement it forces is a toolchain bump — pnpm performs the OIDC exchange natively only from pnpm 10, and pnpm 11.1.3 fixed the exact 404 class we would otherwise hit (the unresolved ${NODE_AUTH_TOKEN} placeholder actions/setup-node writes into .npmrc). The repo is on pnpm 9.15.0.

2 · Scope

In scope

  • Authentication via OIDC trusted publishing; remove the NPM_TOKEN secret entirely (FR-004, NFR-002).
  • Pin pnpm 11.27.0 (latest 11.x, past the 11.1.3 OIDC fix) — the CLI that does the npm OIDC exchange (FR-004).
  • Publish pre-releases directly to --tag latest and retire the unauthenticated npm dist-tag add mirror (FR-006).
  • Keep --provenance, --access public, the atomic pnpm publish -r, and every existing gate (FR-002, FR-005) unchanged.

Out of scope

  • The manual OIDC token exchange needed to set a second dist-tag (next) once a stable release exists — deferred to TBD-oidc-dist-tag; not needed while pre-stable (next ≡ latest ≡ newest).
  • Any change to ci.yml's browser-tests job beyond confirming Playwright browsers still install under pnpm 11 — an implementation check, not a spec change.
  • Migrating off pnpm 9 for reasons other than OIDC (lockfile format is unchanged — v9.0 spans pnpm 9–11).

3 · Approach

OIDC trusted publishing needs the publishing CLI to perform the OIDC token exchange. pnpm does this natively from pnpm 10, and pnpm 11.1.3 dropped the unresolved ${NODE_AUTH_TOKEN} placeholder that actions/setup-node's .npmrc writes (otherwise sent verbatim as a bearer token → the 404). So the workflow pins pnpm 11.27.0 via the packageManager field (which pnpm/action-setup reads), removes NODE_AUTH_TOKEN from the publish step, and lets OIDC authenticate. A local spike de-risked the bump: a fresh pnpm@11.27.0 install --frozen-lockfile works on the existing lockfile v9.0 unchanged, and pnpm -r build passes cleanly — the pnpm-10 build-script-approval change never touches the build (esbuild ships platform binaries as optional deps, no postinstall). The only ignored build script is Playwright's browser download, which the publish job does not need.

The dist-tag wrinkle is real but small: OIDC authenticates npm publish but not npm dist-tag add, so the current "move both next and latest" cannot run tokenless. Because no stable release exists, next and latest already name the same version every release — so publishing pre-releases straight to --tag latest preserves the load-bearing property (bare npm i resolves to the newest build) with no second, unauthenticated dist-tag write. The next alias simply stops updating while pre-stable; the stable-release branch's next-only path is deferred until a stable version exists.

4 · Deltas

Four MODIFY deltas; each embeds the full post-state.

What changes: the version-vs-tag check covers all five published packages, not just cli + schema — so FR-003 agrees with FR-004's corrected enumeration and the check the workflow already runs.

The workflow MUST extract the version from the git tag (strip the leading v) and verify it matches the version field in every published @spectastic/* package's package.json (cli, core, schema, corpus, render). On mismatch (any package, or the packages out of sync), the workflow MUST exit non-zero with a clear error naming the expected and observed values.

Rationale

The two-package enumeration predated core/corpus/render; the workflow's version check already covers all five, so this closes a spec-vs-code drift surfaced by FR-004's correction — a new package could otherwise ship at a stale version with the spec silent.

What changes: authentication moves from a stored NPM_TOKEN to OIDC trusted publishing, requiring pnpm ≥ 11.1.3; the package enumeration is corrected to all five published packages.

The workflow MUST publish every published @spectastic/* package (cli, core, schema, corpus, render) in one pnpm publish -r invocation so they ship atomically when possible. The publish step MUST pass --provenance and --access public. Authentication MUST use OIDC trusted publishing — no long-lived token — and the publishing CLI MUST be pnpm ≥ 11.1.3 (pinned to a specific version), the version that performs the npm OIDC token exchange and does not forward an unresolved ${NODE_AUTH_TOKEN} placeholder as a bearer token.

Rationale

pnpm performs the OIDC exchange natively from pnpm 10; 11.1.3 fixed the setup-node .npmrc placeholder 404 (pnpm issue #11513). The two-package enumeration predated core/corpus/render and is corrected here.

What changes: while no stable release exists, a pre-release publishes directly with --tag latest via OIDC, instead of publishing to next and mirroring latest via npm dist-tag add — which OIDC does not authenticate. The live rationale's two arguments are consciously kept: the freeze-avoidance argument (a bare npm i must not serve a stale build, once frozen at pre.3) is preserved by publishing to latest directly, and the stable-existence keying (covering the RC window) is retained in the stable-release branch; only the "mirror latest via a second dist-tag write" mechanism is retired, because OIDC cannot authenticate it.

The dist-tag MUST be derived from the version being published together with the package's existing release history on the registry.

While no stable release exists — no bare-semver (X.Y.Z) version has ever been published — a pre-release MUST publish directly with --tag latest, so the documented bare install (npm i -g @spectastic/cli) resolves to the newest published build. It MUST NOT rely on a second dist-tag write (npm dist-tag add) to mirror latest: OIDC authenticates npm publish but not dist-tag, and while no stable exists next and latest name the same version — so publishing straight to latest preserves the property with no unauthenticated write.

Once a stable release exists, the guard applies: a pre-release (a version matching X.Y.Z-*) MUST publish with --tag next only, and a bare semver MUST publish with --tag latest — keeping a bare npm i off pre-releases. Setting the next tag under OIDC then needs a manual OIDC token exchange for dist-tag (TBD-oidc-dist-tag), deferred until a stable version exists.

If the registry query that determines whether a stable release exists cannot be completed, the workflow MUST fail rather than guess a dist-tag.

Rationale

Carried from the live requirement: the load-bearing concern of the 2026-07-23 rule stands — a bare npm i must never serve a stale build (it once "froze at 0.1.0-pre.3 while next reached pre.18"). That property is preserved here by publishing pre-releases to latest directly, so latest tracks the newest build without a second tag write. The stable-existence keying (which also covers the release-candidate window, e.g. 1.0.0-rc.1) is retained in the stable-release branch above.

Retired: only the mechanism — "move latest via a second npm dist-tag add" — because OIDC authenticates npm publish but not dist-tag. Near-no-op today (next ≡ latest while pre-stable); the next alias stops updating until TBD-oidc-dist-tag.

What changes: the granular-NPM_TOKEN-secret requirement is replaced by the OIDC trust-relationship requirement — per-package trusted publishers, no stored credential.

Publishing MUST authenticate via OIDC trusted publishing, not a long-lived npm token. Each published @spectastic/* package MUST have a trusted publisher configured on npmjs.com naming the GitHub organization/user, the repository, and the workflow filename (publish.yml); the publish job MUST declare permissions: { id-token: write, contents: read } (the same block FR-005 requires — id-token: write for OIDC, contents: read for actions/checkout). No NPM_TOKEN (or any publish credential) MUST NOT be stored as a GitHub Actions secret or appear in any committed file, including the workflow YAML: at most 0 long-lived publish credentials exist in the repo or its Actions secrets, so there is nothing to expire, rotate, or be restricted by npm's 2FA-bypass-token deprecation.

4b · What this change removes

Each entry names one thing this change takes away that no delta fully expresses.

  • The token-based publish path as an affordance — publishing by supplying a stored NPM_TOKEN. It is replaced wholesale by OIDC; a maintainer can no longer publish this repo with a personal npm token in CI, only through the trusted-publisher trust relationship.
  • The next dist-tag no longer tracks pre-releases while pre-stable. Bare install (which reads latest) is unaffected, but npm i @spectastic/cli@next stops resolving to the newest build — it freezes at its last value until the stable-release next path is built (TBD-oidc-dist-tag).
