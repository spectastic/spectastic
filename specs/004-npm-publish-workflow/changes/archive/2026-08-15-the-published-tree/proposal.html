The published tree

Applied

1 · Intent

003's sibling proposal decides that init installs the bundle's installable trees, which brings in the three subagent definitions bundled since spec 044 and never written. The default scaffold goes from 29 files to 32.

SC-001 states that number, deliberately: a test reads it out of this requirement and fails when it disagrees with the scaffold. That guard exists because these counts drifted three ways at once — "spec said 16, the init docblock said 17, the tests asserted 20, the real tree was 21" — and it is doing its job now, holding the suite red until this lands.

FR-007 has to move with it. It requires the tarball carry "a bundle generated from the tagged commit's commands/, assets/, and templates/" — three trees producing 27 installed files and a 29-file tree. The 32 SC-001 would assert is reachable only via the agents/ tree FR-007 does not authorise. That staleness has been inert while the agents were bundled and dropped; this change makes it load-bearing, so shipping the count without it would land a contradiction and file the resolution.

And US1's acceptance prose repeats the count. Two earlier proposals against this spec carried a second delta for it, and this spec's archived risk register names the failure in almost these words. It is handled here.

2 · Scope

In scope

  • SC-001's tree count, 29 → 32.
  • FR-007's bundle enumeration, which cannot produce that tree.
  • US1's acceptance prose, which states the count and carries no requirement id — a pre-apply hand edit, named in §6 rather than left to a task that drains afterwards.

Out of scope

  • Extending the drift guard's regex to cover US1's prose as well as SC-001's body — roughly two lines in plan.test.ts. This is the option the adversarial pass named and it is the right long-term answer: the guarded number has never rotted silently, while the unguarded US1 copy has been hand-corrected on 25 Jul, on 13 Aug, missed this morning, and is scheduled for a third hand edit below. A manual control with a one-in-four failure rate. Deferred rather than taken only because it is a test change with its own design question — which prose sites deserve guarding — and this proposal is already carrying three sites. defer-to=TBD-scaffold-count-guard-widening.
  • Whether a count belongs in a success criterion at all. It has moved seven times in eight weeks, which is a real argument for stating the property and not the number — but the number is what the drift guard reads, and replacing that mechanism is a larger change than the one making the number wrong today. defer-to=TBD-scaffold-count-mechanism.
  • Everything in 003. Its four deltas are the sibling propose; the kernel folds same-spec deltas only. defer-to=003-init-node-port.

4 · Deltas

What changes: the stated tree count, 29 → 32. Every other clause untouched.

Post-publish, an outside user with Node 20+ and no clone runs npm i -g @spectastic/cli, then spectastic init in an empty directory yields a 32-file tree byte-identical to the local-clone install; spectastic validate against a sample spec.html produces correct findings or a clean pass.

Rationale

Unchanged in substance: an outside user with no clone gets the same tree a contributor does, which is the property publishing exists to deliver, and "byte-identical to the local-clone install" is the clause that has never once been wrong.

The count moved because 003 FR-002 now has init install the bundle's installable trees, which includes the three subagent definitions bundled since spec 044 and never written — so every scaffolded project ran the propose verb with no spectastic-critic and its adversarial pass silently absent (T-026).

The number stays here while the sibling's 003 SC-001 drops its own count, which looks contradictory and is not: this number is machine-read by the drift guard, and 003's was read by nothing. A count with a guard is a checked fact; a count without one is a comment that rots. The two proposals take opposite actions on the same word for that reason, and it is worth saying rather than leaving a reader to reconcile them.

The number stays stated rather than derived because a test reads it out of this requirement and fails when the scaffold disagrees. That is worth keeping even though the number has moved seven times: it is the reason this change is a red test rather than a silent rot, and the alternative — stating the property and deleting the guard — is a larger change than the one making the number wrong.

What changes: the bundle's source trees, so the rule can produce the tree SC-001 asserts. Nothing else — the stale-bundle publish gate is carried through verbatim. An earlier draft of this delta dropped it silently, which the adversarial pass caught; it is the only requirement making bundle contents a release gate.

The workflow MUST re-run the prebuild step (refreshing packages/cli/_bundled/) before publish, so the shipped @spectastic/cli tarball includes a bundle generated from the tagged commit's installable trees and the manifests the installer reads. A stale or missing _bundled/ MUST halt the publish.

Rationale

Regenerating at the tagged commit is unchanged and is the point: a bundle built from an earlier tree ships a package whose contents no commit produced.

The enumeration widens because it could not produce the tree SC-001 now asserts. "commands/, assets/, and templates/" yields 27 installed files against a 32-file tree, and the difference is the agents/ tree this rule did not authorise — inert while those files were bundled and dropped, load-bearing the moment they install. The manifests are named too because prebuild has always carried them and the installer reads them to decide which verbs are opt-in; a bundle without them changes what a default scaffold contains.

Named by role rather than by directory list, matching 003 FR-009's wording, so the two specs describe one bundle in one vocabulary rather than two lists that drift apart — which is what happened here.

5 · Risk register

Findings from the adversarial pass. Statuses stay identified until the author dispositions them.

The FR-007 delta dropped the stale-bundle publish gate without saying so

The live FR-007 ends "A stale or missing _bundled/ MUST halt the publish". The first draft of this delta rewrote the requirement to widen its enumeration and did not carry that sentence, while the What-changes line described only the widening — so a must-tier gate would have been deleted by a delta whose stated purpose was additive. It is the gate that stops a publish shipping a bundle built from an older tree, which is exactly the failure mode this pair of proposals makes more likely by moving the tree.

Restored verbatim, with a "nothing else" note on the What-changes line. The same defect was caught in the sibling proposal against 003 in the same pass. Two silent must-tier deletions in one sitting is a drafting failure rather than a coincidence: when a MODIFY post-state is retyped rather than edited, whatever is not consciously carried is silently dropped, and the What-changes line records intent rather than diff.

The pair leaves a window in which CI is red and no task owns it

The drift guard reads 004's SC-001 off disk and compares it to SCAFFOLD_TREE_FILE_COUNT. Both sides move, in different proposals — so from the moment either side of the pair lands until both have, the suite is red, and FR-002 halts the publish workflow on any non-zero gate. Correct behaviour, and no requirement, task or note acknowledged that it happens.

Named and bounded rather than removed. It cannot be removed: no ordering of the two applies closes it, because the code and the two specs cannot move atomically. §6 now carries the window explicitly with the instruction not to publish while the pair is in flight and to drain it in one sitting. This spec's own 25 Jul proposal met the same situation and resolved it by landing the code first.

Rows stamped verified are projections contingent on the sibling's unlanded tasks

The claim that the tree is 32 files was stamped verified against the bundle. It is verified as arithmetic and not as behaviour: SCAFFOLD_FILE_COUNT is 27 today and inventoryAt does not walk .claude/agents at all, both of which are tasks in the 003 proposal. So the number is a projection of what the code will do after work that has not happened.

Split into two rows. The arithmetic keeps its verified stamp; a second row records, as assumed, that the code does not yet produce it — stated as the contingency rather than left inside a stamp that reads as a checked fact. Also settled while here: 003's SC-001 drops its count while this one keeps it, which looks contradictory and is not — this number is machine-read by the guard and 003's was read by nothing. That distinction is now written into the delta rather than left for a reader to reconcile.

The obvious durable fix was neither taken nor deferred

Extending the drift guard's regex to cover US1's prose as well as SC-001's body is roughly two lines, and the evidence for it is in this proposal's own history: the guarded number has never rotted silently, while the unguarded US1 copy was hand-corrected on 25 Jul, again on 13 Aug, missed this morning, and is scheduled for a third hand edit here. A manual control with a one-in-four failure rate, left unmentioned.

Deferred explicitly as TBD-scaffold-count-guard-widening rather than silently omitted. Not taken here because it is a test change carrying its own design question — which prose sites deserve guarding — and this proposal already moves three sites. The deferral is the honest state; leaving it unnamed was not.
