Applied

1 · Intent

Spectastic has documented the parent / child slicing pattern since the meta-spec landed but has never shipped a worked example of it. The vocabulary exists (<spec-parent specid="…"> in templates/spec.html; <spec-out-of-scope defer-to="…"> enforced by assets/spec.js), the command prose exists (/spectastic.spec line 18; /spectastic.propose lines 105–106 budget-aware splitting nudge), and the inspiration log (CLAUDE.md) ties it back to Larson's 1,500-word threshold and Mike Cohn's vertical slicing. What has been missing is one real spec demonstrating the carve-out.

An audit on 16 Jun 2026 found four feature specs over their declared budget. Three (002, 003, 004) are within a disciplined-editing pass of being healthy; the meta-spec itself is at 166% and is a system-of-record artifact exempt from slicing per a separate principle. 004 was picked as the cleanest worked example. The local-fallback path is the smallest viable carve-out: one FR + one SC, both already-satisfied by existing README content, and topically independent from the CI-driven workflow that the parent retains. The narrowness is deliberate — a 2-requirement child is easier to inspect than an 8-requirement child, which makes it the better demonstration of the recipe.

2 · Scope

In scope

  • REMOVE FR-009 from 004 with reason ("Carved out to sibling slice 005-publish-local-fallback") and migration ("Tracked at 005#FR-001").
  • MODIFY SC-004 in 004 to narrow it to the npm i -g clause only — the local-fallback clause migrates to 005#SC-001. (Was originally drafted as a wholesale REMOVE; R-002 of the adversarial pass surfaced that the wholesale removal would strip 004's only testability hook for US1's npm-i-g documentation path. Narrowed in place instead.)
  • Editorial: append two <li defer-to="005-publish-local-fallback"> entries to 004 §3 Out of scope, naming the carved-out requirements explicitly so the audit trail is visible inside 004 itself. Not a delta — this is an inline edit on a list, not a requirement change. Captured in §6 Tasks.
  • Author the child spec 005-publish-local-fallback/spec.html with <spec-parent specid="004-npm-publish-workflow"> in the header and the migrated FR + SC bodies preserved verbatim. (Already done as a precondition to this proposal — the file exists; this proposal records the apply gesture that makes it official.)

Out of scope

  • Modifying any other requirement in 004. FR-001..FR-008, NFR-001..NFR-003, SC-001..SC-003 stay verbatim. The carve is surgical.
  • Adding a validator rule for parent / child reciprocity. Worth doing eventually; tracked under the slicing-gaps register. This proposal is the worked example, not the enforcement.
  • Resolving 004's overall over-budget condition. 004 at 129% drops to ~125% after this carve — the budget arithmetic is not the point. The point is the recipe.
  • Introducing a new op="carved" delta type for lossless requirement migration. Discussed in the slicing audit as a worthwhile follow-up; not in scope here. op="removed" with substantive reason + migration carries the lineage in the current vocabulary.
  • The child slice 005 lifecycle. 005 ships at Draft; whether it earns Accepted (via a tasks.html drain) or sits as a documentation-only contract is a separate decision for the child's own changelog.

3 · Approach

Two REMOVE deltas, no MODIFY deltas. Each REMOVE carries a substantive .reason-block and a .migration-block pointing at the child slice's matching requirement. The reason / migration pair is the lineage record — future readers can trace where a removed requirement went without walking git history.

The proposal targets are FR-009 (priority="must") and SC-004 (priority="should"). Verified both exist in the current live spec; no hallucinated targets. The adversarial pass auto-fires per the propose-time heuristic (any op="removed"); findings will be embedded into §5 below.

The editorial update to 004 §3 Out of scope is captured in §6 Tasks rather than as a delta. <spec-out-of-scope> items are list entries, not requirements with IDs; the delta vocabulary doesn't extend to list edits, and there is no need to invent one — the apply gesture handles the inline edit alongside the two REMOVE deltas.

4 · Deltas

What's removed: 004's requirement that the README document a local-fallback publish path. Migrated, not deleted — the contract continues to hold under the child slice's name.

Reason. Topical independence from the CI-driven workflow. FR-001..FR-008 all describe the same CI machinery (trigger, gates, version-verify, atomic publish, dist-tag derivation, prebuild, workflow summary). FR-009 describes the human-in-the-loop alternative — a different actor, a different trigger (no tag push), a different acceptance shape. Pulling it into a sibling slice keeps the parent's narrative coherent ("how does CI publish?") and gives the fallback its own self-contained contract.

Migration. The requirement body is preserved verbatim at 005-publish-local-fallback#FR-001, with two additions: an explicit named prerequisite (pnpm --filter @spectastic/cli build to refresh _bundled/) and an explicit known-cost statement (no provenance badge without trusted-publisher config). Both additions surfaced during the propose-time review and were folded into the child rather than the parent.

What changes: 004's SC-004 narrows from "both npm-i-g and local-fallback documented" to "npm-i-g documented." The local-fallback clause migrates to the child slice; the parent retains its US1 readme-contract.

The README's install section SHOULD document the npm i -g @spectastic/cli instruction (US1's path); a reader following that instruction lands on a working install. The local-fallback documentation that lived alongside it before the carve is now owned by 005-publish-local-fallback#SC-001; together, the two specs cover both install paths.

5 · Risk register

Adversarial pass auto-fires per the propose-time heuristic (any op="removed" delta). Findings to be embedded below; status starts at identified and transitions on author commitment.

"Already done as a precondition to this proposal" inverts the propose-then-apply gate

Concern. §2 Scope's fourth bullet states that 005's spec.html is "Already done as a precondition to this proposal — the file exists; this proposal records the apply gesture that makes it official." That ordering creates a live 005-publish-local-fallback/spec.html on main while the proposal is still status="review" — a reader following the parent's links lands in a sibling slice whose existence has not yet been ratified by the lifecycle that is supposed to authorize it. The first worked example of the slicing recipe thus also teaches that the recipe's gate (propose → apply) can be inverted when the author finds it convenient.

30-day frame. In 30 days, the second carve-out cites this one as precedent for authoring child specs before the parent's proposal lands, and the propose→apply gate quietly stops being load-bearing for slicing.

Author response — mitigated. The framing "gate inversion" is too strong: the slicing recipe inherently requires the child to exist before the parent's REMOVE/MODIFY deltas can cite migration targets. A REMOVE delta whose .migration-block points to 005#FR-001 demands that 005-publish-local-fallback/spec.html#FR-001 resolve — which in turn demands the file exist on disk. Hand-waving past this with "it'll exist after apply" would publish a proposal whose migration links 404 in the interim.

The recipe carries these four steps, to be codified in a slicing-gaps-and-recipe register surfaced by this worked example: (a) author the child spec at status="draft"; (b) author the parent's REMOVE/MODIFY deltas referencing the child; (c) the child carries an explicit lineage statement in its TL;DR or changelog naming the parent's pending proposal; (d) if the proposal is withdrawn (REQ-CHANGE-005), the child is withdrawn alongside — author retains the right to delete or de-spec the pre-authored child. This is a documented sequencing pattern, not a gate inversion.

Migrating an unsatisfied SHOULD weakens 004's own readme-completeness contract

Concern. 004's SC-004 reads "The README's install section includes both the npm-i-g instruction (US1's path) and the local-fallback documentation (US2's escape hatch). A reader following either path lands on a working install." It is the only success criterion in 004 testing the npm-i-g documentation path — US1's outsider-install story. After the carve, 004 retains SC-001 (the install works) but loses the criterion that the README documents US1's path at all. The proposal frames SC-004 as "the testability hook for FR-009," but its first half is the testability hook for US1, which 004 keeps.

30-day frame. In 30 days, 004 ships with a README that quietly drops the npm i -g instruction and no requirement in 004 catches it — because the SC that bound the README to US1's path got migrated to 005, which only tests the fallback path.

Author response — mitigated. Proposal amended in place. The SC-004 delta is now op="modified" (was op="removed"); the post-state SC-004 (still in 004, still SHOULD) narrows to the npm-i-g clause only: "The README's install section SHOULD document the npm i -g @spectastic/cli instruction (US1's path); a reader following that instruction lands on a working install." The local-fallback clause migrates to 005#SC-001. The two specs together cover both install paths; neither spec loses its testability hook for its own US. The §2 in-scope bullet, the §4 delta itself, and the §6 task list all updated to reflect the MODIFY.

A 1-FR / 1-SC documentation-only sibling spec fails INVEST-V and inverts the slicing rationale

Concern. §2 Scope concedes "Worked-example value > budget-recovery value here" and "004 at 129% drops to ~125% after this carve — the budget arithmetic is not the point. The point is the recipe." The slicing vocabulary in CLAUDE.md cites Larson's 1,500-word threshold and Cohn's vertical slicing — both are sizing tools. Using them to author a child whose only justification is demonstrating the recipe creates a sibling that fails INVEST-V on its own terms: 005's "value" reduces to "exists as an example," and its lifecycle (Draft, possibly never earning Accepted per §2 bullet 5) accretes governance overhead — a separate changelog, separate budget, separate conformance index — for a single documentation requirement already satisfied by README content.

30-day frame. In 30 days, 005 sits at Draft with no tasks drained, future contributors see "child spec authored to demo the pattern" as legitimate precedent, and the repo grows a class of tiny sibling specs whose existence justification is recursive rather than user-facing.

Author response — accepted. The framing is correct and the cost is owned, not denied. 005's user-facing value is small; its project-facing value (the first witness for a recipe that has been documented-but-undemonstrated since 2026-06-12) is the proposal's actual ask. The proposal does not propose to fix this; it proposes to ship it knowingly. Three guardrails against the "future contributors see this as legitimate precedent for tiny specs" 30-day frame: (a) 005's TL;DR explicitly names itself as the first worked example, not a template for narrow real slices; (b) the slicing-gaps register (separate work) will codify "deliberate worked-example slice" as a distinct category from "vertical slice of real work" so the precedent is bounded; (c) if 005 sits at Draft for an extended period with no real implementation work surfacing, it is a candidate for being merged back into 004 via /spectastic.apply --withdraw on a future proposal — the path back exists.
