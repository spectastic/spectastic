The tree grew by the skills

Move the guarded scaffold count 32 → 40 and FR-007's enumeration with it, tracking the portable Agent-Skills tree the default scaffold now writes.

Status Applied Change ID 2026-09-12-skills-grow-the-tree Spec 004-npm-publish-workflow Author Brian Corbin (@briancorbinxyz) Created 12 Sep 2026 Targets 2 requirements Read time

The default spectastic init now writes the portable Agent-Skills tree (003 FR-002, just amended; the 2026-09-12-claude-installs-skills change), so the scaffold is 40 files, not 32. SC-001's drift-guarded count and FR-007's enumeration rationale both say 32 and are stale — this moves them together to 40, per this spec's own rule that the count's copies move in one change.

The tree grew by the skills

Applied

1 · Intent

The portable Agent-Skills tree (.agents/skills, one SKILL.md per core verb) now ships in the default scaffold: 003 FR-002 authorises it (just amended by 2026-09-12-installable-trees-by-target) and the 111 2026-09-12-claude-installs-skills change has init write it. That adds eight files, so the scaffold tree is 40.

SC-001 states a 32-file tree — the copy a drift-guard test reads and fails on when the scaffold disagrees, which it now does (the guard is red). FR-007's rationale carries the same 32 and the enumeration arithmetic behind it. This change moves both to 40 in one proposal, because this spec's own history is emphatic that the count's copies must move together: "taking only the count has failed twice." US1 deliberately carries no number and needs no touch.

2 · Scope

In scope

  • SC-001's guarded tree count: 32 → 40.
  • FR-007's rationale: de-conflate the bundle count from the on-disk tree count, and name the portable Agent-Skills tree in the enumeration.
  • A committed guard for the render equivalence SC-001's "byte-identical to the local-clone install" now rests on — the dev-rendered skills must match the prebuilt bundle's byte-for-byte (verified today: all 8 match).

Out of scope

  • Changing SC-001's "byte-identical to the local-clone install" clause — it stays; only the count moves. (The equivalence it now depends on is brought in-scope as the guard above, rather than asserted as an aside.)
  • US1's acceptance prose — it states no number by design (the count lives once, in SC-001), so it is not touched.
  • Authorising the skills tree — that is 003 FR-002's job, landed in the companion propose applied just before this one.

3 · Approach

Two MODIFYs, both on <spec-requirement> elements the apply kernel folds. SC-001's normative count moves 32 → 40, its rationale carried verbatim (it argues why the number is stated-and-guarded, which is value-independent) plus one new sentence naming the skills driver. FR-007's normative text is unchanged — it names "installable trees" by role, which already covers the skills tree — and only its rationale's illustrative arithmetic updates: the tree is 40, and the difference above the 27 commands/assets/templates files is now the subagent tree and the portable Agent-Skills tree. The "byte-identical to local-clone" guarantee survives because dev renders the same skills the bundle copies.

4 · Deltas

One <spec-delta> per requirement touched.

What changes: the guarded tree count moves 32 → 40 (eight portable skill files). The "byte-identical to the local-clone install" clause is unchanged; the rationale is carried whole, with one sentence added for the skills driver.

Post-publish, an outside user with Node 20+ and no clone runs npm i -g @spectastic/cli, then spectastic init in an empty directory yields a 40-file tree byte-identical to the local-clone install; spectastic validate against a sample spec.html produces correct findings or a clean pass.

Rationale

Unchanged in substance: an outside user with no clone gets the same tree a contributor does, which is the property publishing exists to deliver, and "byte-identical to the local-clone install" is the clause that has never once been wrong.

The count moved because 003 FR-002 now has init install the bundle's installable trees, which includes the three subagent definitions bundled since spec 044 and never written — so every scaffolded project ran the propose verb with no spectastic-critic and its adversarial pass silently absent (T-026).

It moves again, to 40, because 003 FR-002 now also authorises the portable Agent-Skills tree the default scaffold writes (111, the 2026-09-12-claude-installs-skills change): eight SKILL.md files, one per core verb, carried into every project so any Agent-Skills host can run the lifecycle.

The number stays here while the sibling's 003 SC-001 drops its own count, which looks contradictory and is not: this number is machine-read by the drift guard, and 003's was read by nothing. A count with a guard is a checked fact; a count without one is a comment that rots. The two proposals take opposite actions on the same word for that reason, and it is worth saying rather than leaving a reader to reconcile them.

The number stays stated rather than derived because a test reads it out of this requirement and fails when the scaffold disagrees. That is worth keeping even though the number has moved eight times: it is the reason this change is a red test rather than a silent rot, and the alternative — stating the property and deleting the guard — is a larger change than the one making the number wrong.

What changes: the rationale only — the normative text (role-named "installable trees") already covers the skills tree. The rationale retires the "27-installed-files-against-an-N-file-tree" arithmetic: it conflated the bundle's installable count (38) with SC-001's on-disk tree count (40, which includes the two files init generates and never bundles), and that bundle-vs-tree conflation is exactly what this spec's changelog (24 Jul 2026) names as the cause of the count's drift. The qualitative point is kept and extended to name the skills tree.

The workflow MUST re-run the prebuild step (refreshing packages/cli/_bundled/) before publish, so the shipped @spectastic/cli tarball includes a bundle generated from the tagged commit's installable trees and the manifests the installer reads. A stale or missing _bundled/ MUST halt the publish.

Rationale

Regenerating at the tagged commit is unchanged and is the point: a bundle built from an earlier tree ships a package whose contents no commit produced.

The enumeration widens because it could not produce the tree SC-001 asserts. Enumerating only "commands/, assets/, and templates/" omits the agents/ subagent tree and the .agents/skills portable-skills tree — each inert while bundled-and-dropped, load-bearing the moment it installs — so a bundle naming only the first three cannot install what a default scaffold contains. (An earlier draft of this rationale counted bundle files against SC-001's on-disk tree to make the point; that conflated two different totals and is dropped, keeping the enumeration qualitative.) The manifests are named too because prebuild has always carried them and the installer reads them to decide which verbs are opt-in; a bundle without them changes what a default scaffold contains.

Named by role rather than by directory list, matching 003 FR-009's wording, so the two specs describe one bundle in one vocabulary rather than two lists that drift apart — which is what happened here.

4b · What this change removes

Nothing. Both MODIFYs move a count and carry their rationale whole; no clause, obligation, or affordance is dropped.

5 · Risk register

Populated by the adversarial risk pass (touches must-tier requirements). One <spec-risk> per finding; apply refuses until each is accepted, mitigated, or rejected.

The FR-007 rationale re-commits the bundle-count-vs-tree-count conflation this spec's own history names as the original cause of the drift — its arithmetic does not sum (27 + subagents 3 + skills 8 = 38, the bundle count, not SC-001's 40-file on-disk tree, whose extra 2 are generated and never bundled).

The first-draft delta: "'commands/, assets/, and templates/' yields 27 installed files against a 40-file tree." Against plan.ts (SCAFFOLD_FILE_COUNT = 38) and 004's 24 Jul 2026 changelog: "Conflating the bundle count with the tree count is what let this number drift in the first place."

Mitigated — and the pass turned it into an improvement. FR-007 is about the tarball (the bundle's installable trees = 38), so pinning its rationale to SC-001's on-disk tree (40) was the latent conflation — present in the original too. The rationale now drops the count arithmetic entirely and makes the point qualitatively: enumerating only commands/assets/templates omits the subagent and skills trees, so such a bundle cannot install what a default scaffold contains. The retirement is called out in the What-changes line, per the rationale-carry discipline.

SC-001's surviving "byte-identical to the local-clone install" clause now silently rests on the dev renderer and the prebuild renderer agreeing byte-for-byte — the precise equivalence sibling 003 SC-001 deliberately refused to assert, re-referencing itself to "its bundled source" because a clone referent is inexpressible for npx/global installs.

004 SC-001 "byte-identical to the local-clone install"; 003 SC-001 "each byte-identical … to its bundled source," because a no-clone install "has no repository." With skills, dev renders (bundle.ts renderDevSkills→translateToSkill) while the package copies pre-rendered files.

Mitigated — and verified, not assumed. The equivalence holds by construction — dev and prebuild call the one deterministic translateToSkill from the same core build — and is confirmed empirically: all 8 dev-rendered skills are byte-identical to the prebuilt bundle today. 004's "local-clone" framing is its own deliberate claim (publishing delivers a contributor's exact tree) and legitimately differs from 003's general "bundled source" framing; they are not in contradiction. The equivalence is no longer an assumption — it is brought in-scope as a committed guard (see §6 / §2).

The proposal put the one property this change makes fragile — the runtime-rendered-vs-prebuilt skill equivalence — out of scope and declared it "still true" without verifying it, the same unverified-claim pattern this spec has been burned by three times.

First-draft §Scope out-of-scope: "The 'byte-identical to the local-clone install' property — unchanged and still true … a no-clone install still matches a contributor's."

Mitigated by moving it in-scope and guarding it. The render equivalence is now an in-scope goal with a committed test task (§6): each dev-rendered skill must equal the prebuilt bundle's byte-for-byte. It is verified today (all 8 match), and the guard makes a future divergence (e.g. a core/prebuild version skew) a red test rather than a silent break of SC-001's post-publish smoke claim.
