Change proposal · 004-npm-publish-workflow

Visual authoring templates bump the init tree count

The drift guard catching its third scaffold change, which is the third time it has paid for itself.

Status Applied Change ID 2026-08-12-visual-templates-scaffold-count Spec 004-npm-publish-workflow Author Brian Corbin · @briancorbinxyz Created 12 Aug 2026 Targets 2 modified deltas (SC-001 + US1 tree counts) Read time

The visual slice (095–098) adds three authoring templates — a screen, a variant grid and a token set — and templates are always installed, so SCAFFOLD_FILE_COUNT moves 24 → 27 and SCAFFOLD_TREE_FILE_COUNT 26 → 29. That leaves SC-001's stated "26-file tree" stale, and US1's acceptance states the identical fact in a second place, so both move together rather than leaving one known-wrong number behind. Verified rather than projected: the code landed first and the drift-guard test was run before either number was written here, which is the sequencing the previous correction of this same criterion established.

1 · Intent

SC-001 asserts that a fresh spectastic init yields a 26-file tree, single-sourced as SCAFFOLD_TREE_FILE_COUNT in packages/cli/src/commands/init/plan.ts (SCAFFOLD_FILE_COUNT for bundle files, plus two for the generated .gitignore and the spectastic.json corpus config).

The visual slice adds three authoring templates to templates/: screen.html (095), variants.html (096) and tokens.html (098). The bundle plan installs assets and templates unconditionally — "assets, templates — always installed" — so all three ship, and the counts move to 27 and 29.

This is the drift guard (T-1005) doing its job for the third time. It exists because the scaffold size once drifted three ways at once — 16 in the spec, 17 in a comment, 20 in the tests, 21 on disk — and it has now caught the corpus scaffold, the course payload, and this. A failing guard here is the mechanism working, not a false positive.

2 · Scope

In scope. Two numbers in the live spec, both stating the same underlying fact: the size of the tree a fresh install produces.

Out of scope. Whether the three templates should ship to every downstream project, including those with no user interface. They should, and the reasoning is 093's: templates/ is copied verbatim and cannot vary per project, which is exactly why 093 made the design's visual section a checked property of the authored artifact rather than a template-level condition. A project with no interface deletes what it does not need; the templates being present costs it three files and no obligation.

Also out of scope: the historical counts in this spec's own change log (16, 21, 24, 25). Those are frozen records of what was true when written, and correcting them would falsify the history rather than repair it.

3 · Approach

Land the code, run the guard, then write the numbers the guard reports. That ordering is not ceremony — the previous correction of this same criterion recorded it as a lesson, having first drafted numbers ahead of the implementation and had an adversarial pass flag the sequencing risk. Both values below were read out of a failing drift-guard message ("SC-001 says 26-file tree but the scaffold produces 29"), not computed by hand.

4 · Deltas

What changes: the asserted tree size is corrected from 26 files to 29 — the count spectastic init writes now the visual slice's three authoring templates are in the bundle.

Post-publish, an outside user with Node 20+ and no clone runs npm i -g @spectastic/cli, then spectastic init in an empty directory yields a 29-file tree byte-identical to the local-clone install; spectastic validate against a sample spec.html produces correct findings or a clean pass.

Rationale

The criterion's shape is unchanged — a published install must match a local-clone install exactly. Only the count moved: the visual slice adds three authoring templates (screen.html, variants.html, tokens.html) to the bundle inventory init writes by default, growing SCAFFOLD_FILE_COUNT from 24 to 27 and, once the generated .gitignore and spectastic.json are counted, SCAFFOLD_TREE_FILE_COUNT from 26 to 29. Both remain single-sourced in packages/cli/src/commands/init/plan.ts and asserted in packages/cli/test/init/plan.test.ts, write.test.ts and smoke.test.ts. Verified: the code landed and the drift-guard test was run before this number was written here.

What changes: US1's acceptance criterion is corrected from "26-file lifecycle" to "29-file lifecycle" — the identical fact SC-001 states, in a second location.

Acceptance: Post-install, spectastic init in an empty dir writes the canonical 29-file lifecycle byte-identical to a local-clone install; spectastic validate works against any spec-html.

Rationale

US1 and SC-001 assert the same underlying fact about the same command, so correcting one and not the other would leave the live document stating two different numbers — the exact internal contradiction the previous correction of this criterion had to clean up after it had survived two earlier tree-count changes. Mechanical note: unlike SC-001, this acceptance sentence is plain prose inside an <h3> scenario rather than a <spec-requirement id="…"> anchor, and the apply kernel folds MODIFY deltas only against stable requirement IDs. This delta therefore needs a manual text edit at apply time — the same pattern the previous correction used.

5 · Risk register

The number will go stale again. This is the third correction of the same criterion, and nothing stops a fourth: any spec that adds a bundle file moves it. Accepted rather than mitigated, because the guard already converts a silent staleness into a failing test at the moment it happens — which is the strongest available position short of removing the number from the spec entirely, and the number is what SC-001 is for.

Numbers written ahead of the code. The previous correction was drafted with projected values and an adversarial pass caught the sequencing risk. Mitigated the same way it resolved: the constant was changed and the drift guard run first, and both values here were read out of its failure message rather than computed.

Correcting one of two copies. The identical fact appears in US1 and SC-001, and the last correction found US1 had been missed twice in a row. Mitigated by moving both in this proposal, and by the mechanical note recording that US1 is not kernel-foldable so its edit is manual and easy to skip.
