Knowledge-corpus scaffold bumps the init tree count

Applied

1 · Intent

SC-001 asserts that a fresh spectastic init yields a 21-file tree, single-sourced as SCAFFOLD_TREE_FILE_COUNT in packages/cli/src/commands/init/plan.ts (SCAFFOLD_FILE_COUNT [bundle files] + 1 for the generated .gitignore). 051-knowledge-corpus's FR-006 corpus scaffold — a SKILL.md, a curated index.md, and one worked reference document under templates/knowledge/, remapped at write time to land as a real, immediately usable knowledge/ directory at project root — has now landed in code and is verified: SCAFFOLD_FILE_COUNT is 23, SCAFFOLD_TREE_FILE_COUNT is 24 (both confirmed by running packages/cli/test/init/plan.test.ts's own drift-guard, not projected ahead of the implementation — the sequencing risk an adversarial pass on an earlier draft of this proposal flagged, resolved by landing the code first).

The mechanism that would otherwise let this drift silently is exactly what the last stale-count bug (16 in the spec, 17 in a comment, 20 in the tests, 21 on disk) produced the T-1005 drift-guard test to prevent. That test now correctly fails the moment 051's scaffold lands, because the on-disk tree really does change — this is the guard doing its job, not a false positive. The same adversarial pass surfaced a second, independent staleness the guard doesn't cover: US1's acceptance criterion (§2) still asserts a "16-file lifecycle" — never updated across either of the two prior tree-count corrections (16→20→21). Both SC-001 and US1 state the identical underlying fact (the post-init tree size); this proposal corrects both, rather than repeating the earlier scope-too-narrow failure mode at proposal-authoring time.

2 · Scope

In scope

  • MODIFY SC-001 — correct the stated tree size from 21 files to 24, matching the now-landed SCAFFOLD_TREE_FILE_COUNT (SCAFFOLD_FILE_COUNT 20 → 23, plus the generated .gitignore).
  • MODIFY US1's acceptance criterion — correct the same, independently stale "16-file lifecycle" assertion to 24, so the live document doesn't state two different tree counts for the identical spectastic init behavior (adversarial-pass Finding 2/3).

Out of scope

  • The code change itself (the corpus scaffold, the bundle-destination remap, the SCAFFOLD_FILE_COUNT/SCAFFOLD_TREE_FILE_COUNT bump) — that landed as 051-knowledge-corpus's own T-210/T-211, verified by its own drift-guard test, before this proposal's numbers were finalised. defer-to=never (it's the sibling spec's work, already done, not this one's).
  • Any change to the dist-tag rule, the publish workflow, or the byte-identical-install claim (FR-004–FR-008) — defer-to=never.
  • Re-verifying SC-001's byte-identical-tree claim end-to-end against a real npm install — already deferred as TBD-1-0-release by the prior 2026-07-23-prerelease-latest-dist-tag proposal.

3 · Approach

A pure stated-number correction, tracking the single source of truth (SCAFFOLD_FILE_COUNT/SCAFFOLD_TREE_FILE_COUNT in packages/cli/src/commands/init/plan.ts), landed and verified in 051's own tasks before this proposal was finalised — closing the spec-ahead-of-code sequencing risk an earlier draft carried. This proposal keeps the live spec's prose in sync with that already-landed code change, and — per the adversarial pass — corrects the one other place in the same document stating the identical fact, rather than leaving a second stale number for a future audit to rediscover.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec. op= is one of added | modified | removed | renamed; a missing or invalid op renders visibly broken.

What changes: the asserted tree size is corrected from 21 files to 24 — the count spectastic init writes once the 051-knowledge-corpus scaffold lands.

Post-publish, an outside user with Node 20+ and no clone runs npm i -g @spectastic/cli, then spectastic init in an empty directory yields a 24-file tree byte-identical to the local-clone install; spectastic validate against a sample spec.html produces correct findings or a clean pass.

Rationale

The criterion's shape is unchanged — a published install must match a local-clone install exactly. Only the count moved: 051-knowledge-corpus's FR-006 adds a corpus scaffold (3 files) to the bundle inventory that init writes by default, growing SCAFFOLD_FILE_COUNT from 20 to 23 and, once the generated .gitignore is counted, SCAFFOLD_TREE_FILE_COUNT from 21 to 24. Both remain single-sourced in packages/cli/src/commands/init/plan.ts and asserted in packages/cli/test/init/plan.test.ts, write.test.ts and smoke.test.ts — the same drift guard (T-1005) that caught the prior 16/17/20 mismatch is what caught this one, working as designed. Verified: the code landed and the drift-guard test was run before this number was written here.

What changes: US1's acceptance criterion is corrected from "16-file lifecycle" to "24-file lifecycle" — the identical fact SC-001 states, independently stale in this second location.

Acceptance: Post-install, spectastic init in an empty dir writes the canonical 24-file lifecycle byte-identical to a local-clone install; spectastic validate works against any spec-html.

Rationale

Adversarial-pass Finding 2/3: this acceptance text was never updated across either of the two prior tree-count corrections (16→20→21), so the live document currently asserts two different numbers for the same spectastic init behavior — SC-001 says 21 (soon 24), US1 says 16. Left alone, that internal contradiction would survive this proposal's own "single source of truth" argument. Mechanical note: unlike SC-001, this acceptance sentence is plain prose inside an <h3> scenario heading, not a <spec-requirement id="…"> anchor — the apply kernel folds MODIFY deltas only against stable requirement IDs (packages/core/src/commands/apply.ts). This delta therefore requires a manual text edit at apply time, the same "applied by hand" pattern already used for principles proposals whose target isn't kernel-foldable.
