Pre-1.0 pre-releases move latest too

The guard that stops a bare npm i pulling a pre-release has, pre-1.0, frozen the documented install command on a months-old build.

Pre-1.0 pre-releases move latest too

Approved

1 · Intent

FR-006 derives the dist-tag from the version: a pre-release publishes with --tag next, a bare semver with --tag latest. Its stated rationale is explicit — “this keeps npm i @spectastic/cli (no tag) from accidentally pulling pre-releases.” That is correct reasoning for a project that has a stable release to fall back to.

Pre-1.0, every release is a pre-release, so the rule's premise never holds: latest has never advanced past 0.1.0-pre.3 (@spectastic/core: 0.1.0-pre.8) while next reached 0.1.0-pre.18. Meanwhile SC-001 and SC-004 both describe the bare npm i -g @spectastic/cli path as the user install route, with SC-004 requiring that a reader following it “lands on a working install”. So pre-1.0 the guard in FR-006 defeats two of its own spec's success criteria: users following the documented command receive a build months behind HEAD, missing every fix shipped since.

This change makes the rule conditional on the major version rather than flat, so the guard applies exactly when it is meaningful — once a stable release exists — and not before.

3 · Approach

Key the rule on the version's major component rather than adding a manual switch. While the major is 0, a pre-release publish moves both tags; from 1.0.0 onward FR-006's original behaviour resumes with no further edit. Version-keyed rather than a flag or a reminder because the failure being fixed is a forgetting: nobody remembered to move latest for eighteen pre-releases, and a rule that needs remembering at 1.0 would fail the same way.

Pre-releases keep moving next as well as latest, so anyone already installing @spectastic/cli@next — or pinning it in CI — is unaffected. In workflow terms that is the existing pnpm publish --tag next followed by a npm dist-tag add per package, rather than flipping the single derived tag; the derivation step keeps one line of logic and the dry-run job still covers it.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec. op= is one of added | modified | removed | renamed; a missing or invalid op renders visibly broken.

What changes: the dist-tag rule becomes conditional on the major version — pre-1.0 a pre-release moves next and latest; from 1.0.0 the original stable-only rule resumes.

The dist-tag MUST be derived from the version being published.

While the project is pre-1.0 (the version's major component is 0), a pre-release publish MUST move both next and latest, so the documented bare install (npm i -g @spectastic/cli) resolves to the newest published build.

From 1.0.0 onward the guard applies: a pre-release (a version containing a hyphen, matching X.Y.Z-*) MUST publish with --tag next only, and a bare semver version (X.Y.Z) MUST publish with --tag latest — keeping npm i @spectastic/cli (no tag) from pulling a pre-release once a stable release exists to fall back to.

Rationale

The original rule reserved latest for bare semver so a bare npm i could never land on a pre-release. Sound, but it presumes a stable release exists. Pre-1.0 every release is a pre-release, so latest froze at 0.1.0-pre.3 while next reached 0.1.0-pre.18 — and the install path named by SC-001 and SC-004 served a build months behind. Keying the rule to the major version applies the guard exactly when it protects something real, and restores it automatically at 1.0 rather than relying on anyone remembering.

What changes: the asserted tree size is corrected from 16 files to 20 — the count spectastic init actually writes.

Post-publish, an outside user with Node 20+ and no clone runs npm i -g @spectastic/cli, then spectastic init in an empty directory yields a 20-file tree byte-identical to the local-clone install; spectastic validate against a sample spec.html produces correct findings or a clean pass.

Rationale

The criterion's shape is unchanged — a published install must match a local-clone install exactly. Only the count was stale: the scaffold has grown to 20 files (asserted in packages/cli/test/init/plan.test.ts, write.test.ts and smoke.test.ts), so the written 16 would fail a literal reading of its own success criterion.

5 · Risk register

Populated by the adversarial risk pass (this proposal touches must-tier requirements). One <spec-risk> per finding. status= is identified until the author dispositions it; /spectastic.apply refuses while any remain identified, and each transition must record by=.

Pointing latest at a pre-release means every new user's default install is software the project itself labels unstable — so a single bad pre-release reaches all of them immediately, with no stable version to fall back to. This is precisely the hazard the clause being removed was written to prevent.

Removed rationale: “This keeps npm i @spectastic/cli (no tag) from accidentally pulling pre-releases.”

Draft response (author to confirm): accepted rather than eliminated. Pre-1.0 there is no stable release to fall back to, so the protection was theoretical — the real-world effect was serving a months-old build to everyone. The exposure is real but bounded by the pre-1.0 contract; the mitigation is that next keeps moving, so a burned user can pin an older exact version, and the rule self-reverts at 1.0 when a stable fallback finally exists.

The workflow summary is specified around a single derived dist-tag and prints one install line (npm i -g @spectastic/cli@$DIST_TAG). Once a pre-1.0 pre-release moves two tags, that summary reports only one of them and will misdescribe what actually shipped.

FR-008 — the workflow summary block listing published versions and install instructions.

Draft response (author to confirm): mitigated in the task list rather than by a further delta — the summary step is updated to print both tags when two were moved. FR-008's wording ("listing published versions + links") does not itself name a single tag, so no requirement text needs to change; only the step's output does.

The proposal carries two unrelated intents: a dist-tag policy change and a stale assertion fix. They share only the words “install path”. If the policy delta is ever reverted, the SC-001 correction rides along with it, and the change's title under-describes half its deltas.

§2 In scope — “MODIFY SC-001 — correct the stale 16-file tree assertion to 20”.

Draft response (author to confirm): accepted as a deliberate call made during the interview — the SC-001 drift was surfaced while verifying this proposal's own claims about the published install path, it is a one-word correction with no behavioural coupling to FR-006, and splitting it would cost a second full propose/apply cycle for a typo. Revert-coupling is the honest cost; it is recorded here rather than hidden.
