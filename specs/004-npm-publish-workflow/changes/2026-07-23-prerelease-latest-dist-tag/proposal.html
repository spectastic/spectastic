Pre-stable pre-releases move latest too

The guard that stops a bare npm i pulling a pre-release has, with no stable release to guard, frozen the documented install command on a months-old build.

Status Approved Change ID 2026-07-23-prerelease-latest-dist-tag Spec 004-npm-publish-workflow Author Brian Corbin · @briancorbinxyz Created 23 Jul 2026 Targets 2 modified deltas (FR-006 dist-tag rule, SC-001 stale file count) Read time

Make the dist-tag rule conditional on whether a stable release exists, not on the version string. Pre-stable pre-releases move latest too

Approved

1 · Intent

FR-006 derives the dist-tag from the version: a pre-release publishes with --tag next, a bare semver with --tag latest. Its stated rationale is explicit — “this keeps npm i @spectastic/cli (no tag) from accidentally pulling pre-releases.” That is correct reasoning for a project that has a stable release to fall back to.

No stable release exists, so the rule's premise never holds: latest has never advanced past 0.1.0-pre.3 (@spectastic/core: 0.1.0-pre.8) while next reached 0.1.0-pre.18. Meanwhile SC-001 and SC-004 both describe the bare npm i -g @spectastic/cli path as the user install route, with SC-004 requiring that a reader following it “lands on a working install”. So the guard in FR-006 defeats two of its own spec's success criteria: users following the documented command receive a build months behind HEAD, missing every fix shipped since.

The fix keys the rule on whether a stable release exists rather than on the shape of the version string, so the guard applies exactly when it protects something real — and not before.

2 · Scope

In scope

  • MODIFY FR-006 — registry-keyed dist-tag rule: while no stable release exists a pre-release moves both next and latest; once one exists the original guard resumes. An undeterminable registry state fails the run rather than guessing.
  • MODIFY SC-001 — correct the stale 16-file tree assertion to 20, the count init actually writes.
  • Promote the tag derivation from D-005's inline bash to a unit-tested scripts/derive-dist-tag.mjs, and wire .github/workflows/publish.yml to it (both tags, all three packages, fail-loud).
  • A rollback runbook in the README's release section — how to demote latest to the last good version.
  • A single source of truth for the scaffold file count plus a drift-guard test; fix the stale canonical 17-file comment in packages/cli/src/commands/init.ts.

Out of scope

  • The one-off operational fix for already-published versions (moving latest to 0.1.0-pre.18 by hand). Operational, not a requirement — defer-to=never.
  • Any change to the provenance / OIDC publish mechanism (FR-004, FR-005, NFR-002) — defer-to=never.
  • Deciding when 1.0 is cut, or what gates it — defer-to=TBD-1-0-release.
  • Re-verifying SC-001's byte-identical-tree claim end-to-end against a real npm install — defer-to=TBD-1-0-release.

3 · Approach

Key the rule on the registry's release history rather than the version string. An earlier draft keyed on “the major component is 0”, but that reintroduces the same bug one version later: the moment 1.0.0-rc.1 is cut it has major 1 and a hyphen, so it would publish to next only and latest would re-freeze on the last 0.x pre-release for the whole release-candidate period. Asking “has a bare-semver version ever been published?” covers the 0.y.z and 1.0.0-rc.* cases with one condition, and the guard engages by itself the moment 1.0.0 final ships — no one has to remember, which matters because the failure being fixed is a forgetting.

Pre-releases keep moving next as well as latest, so anyone already installing @spectastic/cli@next — or pinning it in CI — is unaffected. Mechanically that is the existing pnpm publish --tag next followed by an npm dist-tag add per package for all three (cli, core, schema, whose latest values have already drifted apart at pre.3 and pre.8).

The rule has outgrown D-005's inline bash — it now spans a registry query, two tags, three packages and a failure path. D-005 pre-authorised exactly this trigger (“if the rule grows … promote to a small scripts/derive-dist-tag.mjs”), so the logic moves to a script whose branches are unit-tested rather than exercised for the first time during a live publish.

This makes a release depend on registry availability, not just registry writes. If the query cannot be completed the workflow fails rather than guessing a tag — a failed run after a successful publish is recoverable via the rollback runbook, whereas a silently wrong latest is the exact failure this change exists to end.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec. op= is one of added | modified | removed | renamed; a missing or invalid op renders visibly broken.

What changes: the dist-tag rule becomes conditional on whether a stable release exists — while none does, a pre-release moves next and latest; once one exists the original guard resumes. An undeterminable registry state fails the run.

The dist-tag MUST be derived from the version being published together with the package's existing release history on the registry.

While no stable release exists — no bare-semver (X.Y.Z) version of the package has ever been published — a pre-release publish MUST move both next and latest, so the documented bare install (npm i -g @spectastic/cli) resolves to the newest published build. This holds for 0.y.z pre-releases and 1.0.0-rc.* alike: until a stable version exists there is nothing safer for latest to point at.

Once a stable release exists, the guard applies: a pre-release (a version containing a hyphen, matching X.Y.Z-*) MUST publish with --tag next only, and a bare semver version MUST publish with --tag latest — keeping npm i @spectastic/cli (no tag) from pulling a pre-release once there is a stable version to fall back to.

If the registry query that determines whether a stable release exists cannot be completed, the workflow MUST fail rather than guess a dist-tag.

Rationale

The original rule reserved latest for bare semver so a bare npm i could never land on a pre-release. Sound, but it presumes a stable release exists. None does, so latest froze at 0.1.0-pre.3 while next reached 0.1.0-pre.18 — and the install path named by SC-001 and SC-004 served a build months behind. Keying on the existence of a stable release rather than the version string also covers the release-candidate window: a version-string rule would send 1.0.0-rc.1 to next only and re-freeze latest on the last 0.x pre-release until 1.0.0 final.

What changes: the asserted tree size is corrected from 16 files to 20 — the count spectastic init actually writes.

Post-publish, an outside user with Node 20+ and no clone runs npm i -g @spectastic/cli, then spectastic init in an empty directory yields a 20-file tree byte-identical to the local-clone install; spectastic validate against a sample spec.html produces correct findings or a clean pass.

Rationale

The criterion's shape is unchanged — a published install must match a local-clone install exactly. Only the count was stale: the scaffold has grown to 20 files (asserted in packages/cli/test/init/plan.test.ts, write.test.ts and smoke.test.ts), so the written 16 would fail a literal reading of its own success criterion. The number is stated in three places that had already drifted apart (spec 16, init.ts comment 17, tests 20), so a single source of truth and a drift-guard test land with it.

5 · Risk register

Populated by the adversarial risk pass (this proposal touches must-tier requirements). One <spec-risk> per finding. All three were dispositioned by the author in the decision interview; by= records who committed each.

Pointing latest at a pre-release means every new user's default install is software the project itself labels unstable — so a single bad pre-release reaches all of them immediately, with no stable version to fall back to. This is precisely the hazard the clause being removed was written to prevent.

Removed rationale: “This keeps npm i @spectastic/cli (no tag) from accidentally pulling pre-releases.”

Accepted. The exposure is real but the protection was theoretical: with no stable release to fall back to, the guard's only practical effect was serving a months-old build to everyone. Three things bound it — next keeps moving, so a burned user can pin an exact earlier version; a rollback runbook now ships in the README so demoting latest is a documented one-liner rather than improvised under pressure; and the rule reverts by itself the moment a stable release exists, including across the 1.0.0-rc.* window.

The workflow summary is specified around a single derived dist-tag and prints one install line (npm i -g @spectastic/cli@$DIST_TAG). Once a pre-stable pre-release moves two tags, that summary reports only one of them and will misdescribe what actually shipped.

FR-008 — the workflow summary block listing published versions and install instructions.

Mitigated in the task list rather than by a further delta: the summary step is updated to print every tag that was moved. FR-008's wording (“listing published versions + links”) does not itself name a single tag, so no requirement text needs to change — only the step's output.

The proposal carries two unrelated intents: a dist-tag policy change and a stale assertion fix. They share only the words “install path”. If the policy delta is ever reverted, the SC-001 correction rides along with it, and the change's title under-describes half its deltas.

§2 In scope — “MODIFY SC-001 — correct the stale 16-file tree assertion to 20”.

Accepted, and deliberately re-tested: the splitting question was asked again after the decision interview grew the change to eight tasks, and the answer held. The delta count is still 2 — under the >5 threshold — and the added work is implementation of one intent (“the published install path is correct and stays correct”), not extra deltas. Splitting would cost a second full propose/apply cycle for one corrected number. The revert-coupling is the honest price and is recorded here rather than hidden.

6 · Tasks

Scoped to this change only. On /spectastic.apply these fold into the target's tasks.html as a new provenance-linked phase (per REQ-CHANGE-006) that /spectastic.implement drains — this list is then the frozen intent record.

  • Add the tag-derivation script — scripts/derive-dist-tag.mjs resolves the tag set from the version plus the package's registry history, and exits non-zero if the registry state can't be determined.
  • Unit-test every branch — pre-stable pre-release (both tags), 1.0.0-rc.* before any stable (both tags), pre-release after a stable exists (next only), bare semver (latest), and the query-failure path. These branches currently only ever run during a live publish.
  • Wire the workflow to the script — .github/workflows/publish.yml: replace the inline Derive dist-tag bash, then after Publish to npm run npm dist-tag add for cli, core and schema when the two-tag branch is taken. Any dist-tag failure fails the run.
  • Report every moved tag in the run summary — update the Workflow summary step so a two-tag publish prints both, resolving the FR-008 risk.
  • Record the promotion in the plan — specs/004-npm-publish-workflow/plan.html D-005: the bash conditional is superseded by the script, which D-005 itself pre-authorised.
  • Single-source the scaffold count — one exported canonical count consumed by the init tests, plus a drift-guard test asserting SC-001's stated number matches it (the same posture that guards the assets/spec.js band value against REQ-FORMAT-004).
  • Fix the stale count comment — packages/cli/src/commands/init.ts still says “canonical 17-file”; correct it to the single source.
  • Document the rollback runbook — README release section: demote latest to the last good version across all three packages, for when a bad pre-release becomes the default install.
  • Verify end-to-end — after the next tagged release, assert npm view <pkg> dist-tags reports the new version on both latest and next for all three packages.

7 · Open questions

None outstanding — the rule's key (registry history vs version string), the registry-failure behaviour, which packages move latest, the promotion of D-005's bash to a tested script, the rollback runbook and its home, the count drift guard, the ship status, and whether to split the change were each anchored in the decision interview.
