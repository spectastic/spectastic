Cards

@spectastic/render is published but never dist-tagged, so its latest serves an old build

Implementation code

Debugging why npm view @spectastic/render version reported 0.1.0-pre.25 minutes after a successful pre.26 publish, root cause was the dist-tag loop enumerating four packages by name and omitting render, which spec 106 added after the loop was written; fixed by adding it to that loop and to the tag/version check beside it; regeneration passes — nothing upstream says which packages exist, so a new one has to be added to a list either way.

Expected
Every published package moves onto the same dist-tags together, so a bare npm i @spectastic/render serves the build just released.
Actual
render@0.1.0-pre.26 published correctly and its next moved, but latest stayed on pre.25. The other four packages moved both tags. The publish job reported success, because nothing in it looks at render.
Diagnosis
Two steps in .github/workflows/publish.yml enumerate packages by name — the tag/version check and the “Move additional dist-tags” loop — and both list cli, core, schema, corpus. render is published by pnpm publish -r, which walks the workspace and needs no list, so it ships on every release while being invisible to both checks. The workflow’s own comment records this exact failure happening before: “All three packages move together — their latest values had already drifted apart at pre.3 / pre.8”, with a set -e added so “a half-tagged release goes red rather than reporting success while the install command still serves an old build.” That is precisely what happened, to the one package the guard does not cover.
Fix
.github/workflows/publish.yml — add @spectastic/render to the dist-tag loop and a RENDER_VERSION arm to the tag/version check, so the package is covered by the same two guards as its siblings. The already-published pre.26 needs its latest moved by hand once, since a workflow fix cannot retroactively tag a release that already happened.
Deep dive — a list that has to be maintained, and the second one this session

No cross-spec contract and no principles amendment. Worth recording is the shape, which is the same one 110/T-002 hit hours earlier: a hand-maintained list in CI that a new thing must be added to, where forgetting produces silence rather than a failure. There the list was which tests need a browser; here it is which packages get tagged. Both were correct when written and both went stale the moment something was added elsewhere.

Whether the list should be derived rather than maintained — pnpm publish -r already knows every non-private workspace package, and pnpm -r --json list could supply the same set to both steps — is a real question and is surfaced rather than folded in. It would remove the failure mode instead of fixing this instance of it, which is the P-8 shape; it is also a larger change to a workflow that just published, so it belongs to its own pass rather than a hotfix.
