Design · 120-ownership-aware-verdict-output

Ownership-aware verdict output

How we will build it.

Status Draft Spec 120-ownership-aware-verdict-output Owner Brian Corbin · @briancorbinxyz Branch main Created 14 Sep 2026 Read time

The verdict already computes isOwner (119); it just discards the distinction after choosing the allowed zone. Carry it forward: at the moment it pushes a violation, record cause (path or ownership) and, for ownership, the store's owner + coordinate. Then explain (118) and shifu (117) branch on cause — they read it, never recompute ownership. One field on the violation, set in one place, read in two. The only real risk is mechanical: cause is now required on every Violation, so existing test fixtures and committed demo verdicts gain the field.

6 · Approach

Four edits over code that exists. In types.ts: add cause: 'path' | 'ownership' (required) and optional owner/storeCoordinate to Violation. In verdict.ts: at each push, set cause — 'ownership' only when the decision is resource-scoped and the current project is not the owner (carrying owner + storeCoordinate from decision.resource), else 'path' (a path-scoped decision, an owner writing outside allowed-in, a deny match, an enforcer finding). In explain.ts: branch on v.cause — an ownership violation renders "the store <coordinate> is owned by <owner> — route the change through that service" in place of the sanctioned-path line, and shows the store coordinate, not the decision coordinate; a path violation is unchanged. In shifu.ts: an ownership violation gets an ownership-grounded question. The owner comparison is read, never recomputed — the single-source guarantee, asserted by a code-structure test.

Governing decision acknowledged. This touches packages/core/src/guardrail/**, governed by 113-guardrail-retrieval/D-001 ("no model or network on the retrieval path"). This design adds no import there — a field, a string branch, a template — so the purity holds unchanged.

7 · Alternatives considered

The real design fork is how cause sits on the violation (the spec's decision-phase question, recorded here with its scored tradeoff).

OptionSelf-describingHook-friendlyByte-compatTotal
Always present (path|ownership)55212
Optional, ownership-only33511

The always-present form was chosen in the interview: a symmetric field a consumer can switch on unconditionally, at the cost of an additive change to existing verdict.json (path violations gain cause: "path"). Byte-identical would have preserved old artifacts exactly but left readers to treat "absent" as a third state.

8 · Decisions

D-001 · cause + authority as fields on Violation, set in the verdict

Status
Accepted
Decision drivers
Self-describing · hook-friendly · single-source
Considered options
  • Always present cause (chosen) — + symmetric, a hook switches on it unconditionally. − existing verdict.json gains a field.
  • Optional, ownership-only — + byte-identical for path. − readers treat "absent" as a third state.
Context
verdict.ts's push() takes an extra: Partial<Violation>; types.ts Violation extends additively.
Decision
cause: 'path' | 'ownership' (required) + optional owner/storeCoordinate, set at push time from the owner-aware branch (FR-001, FR-002).
Consequences
+ Any verdict.json consumer renders the cause without the decision. − Every Violation literal (test fixtures, committed demo verdicts) gains the field.

D-002 · Ownership is decided once; renderers read it

Status
Accepted
Context
explain.ts and shifu.ts today read rule/reason; the owner comparison lives only in verdict.ts (119).
Decision
The renderers branch on v.cause and read v.owner/v.storeCoordinate; they perform no owner comparison and read no current-project identity (NFR-001). A code-structure test asserts it (SC-004).
Consequences
+ One comparison, one site; no drift. − The renderers depend on the verdict having set the fields (it always does).

D-003 · An ownership explanation names the store's authority, not the copied decision

Status
Accepted
Context
Today --explain prints the sanctioned path (explain.ts:49) and the decision coordinate — for an ownership violation both are wrong (the file's own directory; the consumer's copy).
Decision
For cause === 'ownership', replace the sanctioned-path line with "owned by <owner> at <storeCoordinate> — route through that service" and show the store coordinate, not the decision coordinate (FR-003). A path violation is unchanged.
Consequences
+ The non-owner is directed to the right place. − Two render branches to keep tested.

D-004 · TDD with ownership/path fixtures on the demo-8 reproduction

Status
Accepted
Context
The guardrail layer is tests-first; the reproduction is committed.
Decision
Write the cause fixtures, the two renderer assertions, and the single-source structure check red first, then wire.
Consequences
+ The SCs become the tests. − Updating existing Violation-literal fixtures is part of the first red step.

11 · Complexity tracking

No complexity beyond the spec: a field, a push-time assignment, two render branches, one structure test. The largest line item is mechanical fixture churn, not design risk.
