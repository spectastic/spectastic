Ownership-aware verdict output

The owner-aware verdict exits correctly — but tells a non-owner the sanctioned path is exactly where their file already sits. Record why a touch was disallowed, so the output can say what to do instead.

Status Accepted Spec ID 120-ownership-aware-verdict-output Owner Brian Corbin · @briancorbinxyz Reviewers Guardrail layer (115 · 117 · 118 · 119) Created 14 Sep 2026 Principlesv1.9.0 Smallest demoableOn the demo-8 reproduction, a non-owner's verdict --explain says "the store … is owned by … — route through that service" instead of pointing at the file's own directory. Read time

Spec 119's owner-aware verdict blocks a non-owner's write to a store it doesn't own — the right exit code — but the 115/117/118 output layer can't tell that violation from a layering one, so it misdirects: it prints a "sanctioned path" that is exactly where the offending file sits, shows the consumer's copied decision coordinate rather than the store's authority, and templates --teach from a layering-case reason. The fix records why on the violation — a cause of path or ownership, plus the store's owner and coordinate when it's ownership — decided once, in the verdict and read by the renderers; the owner comparison never moves into them. An ownership violation then reads: "the store … is owned by … — route the change through that service." Path violations keep their exit code and detection; the artifact gains cause on every violation (a deliberate additive change, not byte-identical). No exit code changes.

1 · Context

Spec 119 made the merge verdict owner-aware: a decision can govern a data store by a federation-unique coordinate and an owner, and a write by any project other than the owner is a violation — even a write cleanly layered in the non-owner's own persistence adapter, because the defect is ownership, not layering. The exit code is right, proven by the resource integration test and the position-keeper reproduction (demonstrations/8-consumer-service/).

But the output layer built for the single-repo case (115's Violation, 118's --explain, 117's --teach) predates that semantics and cannot see it: for an ownership violation it prints src/**/persistence/** as the sanctioned path — where the offending file already sits — shows the consumer's copied decision coordinate, and teaches from the layering reason. The verdict is right; what it says misdirects the one person it is trying to help. This spec makes the output know the difference.

2 · User scenarios & testing

Each story is independently testable on the demo-8 reproduction.

US1 · A non-owner is told where the change belongs P1

As a reviewer in a consuming service, I want verdict --explain on an ownership violation to name the store's owner and coordinate and point me at that service — not at my own directory — so that I route the change to the team that owns the data instead of merging a cross-service reach.

Acceptance: for the demo-8 violation, the explanation states the store is owned by briancorbin/position-keeper-guardrails at its coordinate and directs the author there; it does not print the offending file's own directory as "sanctioned", nor the consumer's copied decision coordinate.

US2 · A verdict.json consumer can act on the cause P1

As an operator wiring a CI hook, I want the persisted verdict to record why each touch was disallowed and, for an ownership violation, the store's authority, so that a hook can route or annotate without re-deriving ownership or loading the decision.

Acceptance: verdict.json records cause on every violation; an ownership violation also carries the owner and store coordinate. A path violation records cause: "path" with unchanged exit code and detected file.

US3 · The teaching question fits the failure P2

As a reviewer in a consuming service, I want --teach on an ownership violation to ask about ownership, not layering, so that the Socratic prompt makes me reason about the right thing.

Acceptance: for an ownership violation the teach question names the store/owner and asks why this service should hold the data; for a path violation it is unchanged.

Edge cases

  • A path violation (no resource scope) — cause: "path", no authority carried; explanation and teach unchanged.
  • The owner's own verdict — an owner writing outside allowed-in is still a path violation, not ownership; the owner is never told to route through their own service.
  • An ownership violation whose decision carries no store coordinate (a malformed resource that slipped the validate rule) — the explanation degrades to naming the owner alone rather than fabricating a coordinate.
  • A verdict.json written before this spec (no cause) read by a new consumer — absent is read as path.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

Every Violation MUST record a cause — path (the change is outside the sanctioned location) or ownership (the current project is not the store's owner) — set by the verdict, which is the one place the owner comparison happens.

An ownership violation MUST additionally carry the store's authority — the owner (project identity) and the store coordinate — on the violation itself, so a verdict.json consumer renders it without loading the decision.

verdict --explain MUST render an ownership violation by naming the store's owner and coordinate and directing the author to route through that service — never printing the offending file's own location as a sanctioned path, nor the consumer's copied decision coordinate. A path violation's explanation is unchanged.

verdict --teach SHOULD ask an ownership-appropriate Socratic question for an ownership violation — grounded in the store and owner, distinct from the layering question — and be unchanged for a path violation.

A path violation's exit code and detection MUST be unchanged, and the owner's own verdict output MUST be unchanged. The persisted artifact gains cause on every violation — a deliberate, additive contract change, not byte-identical to a pre-120 verdict.json.

Rationale

The 119 triage floated a byte-identical floor; the decision phase chose a symmetric always-present cause over back-compat of the exact bytes. This requirement records that choice: semantics are preserved, the artifact is not frozen.

Non-functional

Ownership MUST be decided in exactly 1 place — the verdict; the explain and teach renderers read the recorded cause and authority and contain at most 0 owner comparisons (no read of the current project identity, no recomputation of owner-vs-current). Single-source-of-ownership.

Out of scope (deferred to other slices)

  • Reading the authoritative decision across repos — the consumer still carries a copied decision; resolving the real authority by reading the owner's repo is the federation slice.
  • Better cross-service touch detection — the content pattern still under-detects an API call / topic / migration; unchanged here.

4 · Data model

One classification added to an existing entity, and the authority it points at.

Entities

Violation cause
Why a change was disallowed: path (outside the sanctioned location) or ownership (the current project is not the store's owner). Invariant: every violation has exactly one cause; a pre-120 record with no cause is read as path.
Ownership authority
For an ownership violation: the store's owner (a project identity) and its coordinate. Invariant: an ownership violation carries an authority (owner always; coordinate when the decision declares one); a path violation carries none.

The load-bearing invariant is single-source-of-ownership: the cause is decided where the owner comparison already lives (the verdict) and flows outward as data. A renderer that recomputed ownership would be a second, driftable copy of the one comparison 119 was careful to place once.

5 · Success criteria

An operator reading verdict.json can tell why each violation was disallowed — the cause on every violation, with the store authority on every ownership one — correct across both fixture cases (target 2 of 2; any miss fails), from no established baseline. A path violation's exit code and detected file are unchanged.

Observed at

The guardrail verdict test suite on the demo-8 reproduction: an ownership violation records cause: "ownership" + owner + coordinate; a path violation records cause: "path", same exit code and file as before.

Falsified by

A violation with no cause, an ownership violation missing its authority, or a path violation whose exit code or detected file changed.

A reviewer in a consuming service running --explain on the demo-8 ownership violation is directed to the owner's service rather than to their own directory — the output names the store's authority (owner, coordinate), never the offending file's location or the consumer's copied decision coordinate. Correct on the reproduction (target: authority named with both misdirections gone; failing: either misdirection present), from no established baseline.

Falsified by

--explain printing the offending file's own directory as the sanctioned path, or the consumer's decision coordinate, for an ownership violation.

A reviewer sees a teaching question that names the store/owner for an ownership violation, distinct from the layering question — correct on the reproduction (target: ownership-grounded question), from no established baseline.

Observed at

Falsified by

The teach question for an ownership violation reading identically to the layering-case question.

A maintainer auditing the code finds the owner comparison in exactly 1 module — the verdict — and 0 occurrences in the explain and teach renderers (target 1 site, 0 in renderers), from no established baseline.

Observed at

A code-structure test: the explain and teach modules read no current-project identity and perform no owner-vs-current comparison.

Falsified by

The explain or teach module reading the current project identity or recomputing whether the current project is the owner.

6 · Assumptions

The verdict already knows, at the moment it flags an ownership violation, everything the authority needs — the decision's resource owner and coordinate are in hand (119). Recording them on the violation is a copy, not a new lookup.

A verdict.json consumer treats an absent cause (a pre-120 artifact) as path — the historical single-repo meaning — so old artifacts stay readable.

7 · Open questions

None outstanding — scope (verdict + explain + teach), the cause encoding (always present, symmetric), and where the authority lives (on the violation) were all anchored in the interview.
