Init project config — ignore files

A bootstrapped project should not commit build output and tool noise on day one.

spectastic init scaffolds commands, assets, templates, and (with a profile) principles + agent guidance — but no .gitignore, so a freshly-bootstrapped project commits spectastic's own ephemera and the stack's build output by default (dogfooding T-015). This spec adds ignore-file scaffolding in two phases, mirroring the 041→042 pattern: init writes a base .gitignore (spectastic's ephemeral outputs — deterministic, no stack knowledge), and the profile-aware plan verb appends stack-specific entries resolved from the detected ecosystem (reusing 042's detection). All spectastic-managed lines live in a marked block, so a brownfield .gitignore is appended to, never clobbered, and re-runs are idempotent.

1 · Context

init writes a project's lifecycle files but never a .gitignore. A scoped precedent exists — course.ts maintains .spectastic/.gitignore for ephemeral courses — but nothing covers the project as a whole, so spectastic's generated ephemera and the stack's build artifacts are committable from the first commit (T-015).

The shape follows the established lineage: an ignore policy that init can seed deterministically (spectastic's own ephemera — known without the stack), and stack-specific entries the profile-aware plan verb resolves once the ecosystem is known — exactly how 041 carries a policy that 042 resolves at plan time.

Users: developers bootstrapping a new project (greenfield) or retrofitting spectastic onto an existing one (brownfield).

2 · User scenarios & testing

Each story MUST be independently testable: US1 alone is a viable MVP.

US1 · Base ignore at init P1

As a developer bootstrapping a project, I want init to write a base .gitignore so that spectastic's own ephemeral output isn't committed by accident.

Acceptance: init on an empty directory writes a .gitignore whose spectastic block ignores spectastic's ephemeral outputs (e.g. generated courses) but not its tracked config (the profile marker). No model call.

US2 · Stack ignores at plan P2

As a developer, I want the plan verb to append my stack's build-artifact ignores so that I don't hand-maintain node_modules/, __pycache__/, target/, and friends.

Acceptance: plan on a project of a detected ecosystem appends that ecosystem's ignore entries to the spectastic block, reusing 042's detection.

US3 · Brownfield append, never clobber P2

As a developer with an existing .gitignore, I want spectastic to add only its missing entries under a marked block so that my own rules are never touched and re-runs don't churn.

Acceptance: against a hand-written .gitignore, every existing line is preserved and only absent spectastic entries are added inside the marked block; a second run changes nothing.

Edge cases

  • An existing spectastic block → new entries union into it (one block, never a duplicate). The block is spectastic-managed; hand-edits inside it aren't preserved — user rules belong outside it.
  • Undetectable / polyglot stack at plan → the base block stands; stack entries are skipped with a note, never guessed.
  • Non-git project → the file is still written (it's harmless), consistent with init writing files regardless of VCS.
  • --no-gitignore → opt out of the write entirely.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

init MUST write a project .gitignore containing spectastic's base ephemera entries, deterministically and with no model call.

All spectastic-managed entries MUST live inside a marked block (sentinel-delimited) so the managed region is bounded, mergeable, and idempotent — distinct from any lines the user authored.

The base block MUST ignore spectastic's ephemeral outputs (e.g. generated courses) and MUST NOT ignore its tracked config (the .spectastic/profile.json marker, 041).

On a project that already has a .gitignore, the writer MUST append only missing entries into the spectastic block and MUST NOT modify or reorder any line outside it — never a blind overwrite (parallels 041 amend).

The /spectastic.plan verb SHOULD detect the project's ecosystem (reusing 042's detection) and append the stack's build-artifact ignore entries to the spectastic block.

The ecosystem → ignore-entries mapping SHOULD be data (a table alongside 042's detection signals), so adding a stack's ignores is a data edit, not code.

init MAY accept --no-gitignore to skip the write.

Non-functional

Writing and merging MUST be deterministic and filesystem-only — no network, no model — so CI drives it with fixtures.

The write MUST be idempotent: re-running init/plan adds no duplicate entries and leaves an already-current block byte-unchanged.

Out of scope (deferred)

  • Other bootstrap config — .gitattributes, .editorconfig. A later slice if wanted.
  • Recommended harness/agent config (.claude/settings.json, effort/subagent defaults) — a separate, contested capability (the item-2 concern from the same dogfooding pass).
  • Non-git VCS ignore files (.hgignore, …) — spectastic assumes git (031).

4 · Data model

Entities

Spectastic ignore block
A sentinel-delimited region of .gitignore (a start/end marker pair) that spectastic owns and merges into; everything outside it is the user's.
Base entries
Spectastic's stack-agnostic ephemera to ignore — known at init, excluding tracked config.
Stack ignore map
Data mapping a detected ecosystem to its build-artifact ignore entries; consumed by plan (FR-005/006).

Invariant: spectastic only ever reads/writes inside its marked block; a user line outside it is never touched. Merges are set-union within the block (idempotent), never a rewrite of the whole file.

5 · Success criteria

init on an empty directory produces a .gitignore whose spectastic block ignores the ephemeral outputs and leaves the profile marker trackable; git check-ignore confirms the ephemera are ignored and the marker is not. (The smallest demoable base.)

plan on a fixture project of a detected ecosystem appends that ecosystem's build-artifact ignores to the spectastic block (e.g. Node → node_modules/, Python → __pycache__/).

Against a hand-written .gitignore, every pre-existing line survives and only missing spectastic entries are added inside the block; a second run is a no-op (idempotent).

The whole path runs green in CI with no model invoked.

6 · Assumptions

The two-phase split (base at init, stack at plan) is the right shape, matching 041→042; the base is knowable without the stack, the stack only at plan time.

042's detection (config-signal table) is a good enough ecosystem oracle to key stack ignores off, as it is for enforcement.

7 · Open questions

None outstanding — smallest demoable, scope (ignore files only), stack-resolution home (plan-time), and the brownfield strategy (append-only, marked block) were anchored in the interview.
