The value-ranked slicer

One oversized spec, proposed as many. The slicer reads an over-budget spec and appends a split proposal — covering child slices, RICE-ranked and dependency-ordered — that a human reviews before anything is minted. The nudges flag "too big"; this does the split, on paper first.

1 · Context

spectastic ships nudges that flag an oversized spec — the smallest-demoable prompt, the amber/red budget band, the propose-time splitting nudge. None of them do the split; the author still has to decompose by hand, decide the build order, and convince themselves nothing was dropped. That is exactly the work an agent can do — and the work this slice automates.

Two foundations the slicer needed now exist. R-002 supplies the dependency-respecting, value-ranked ordering (the slicer consumes it rather than inventing sequencing from scores), and the opt-in git layer (026/027) ships the branch/PR guardrails the eventual mint will fan out onto. This slice is the build-side complement to the nudges: it produces the split, as a reviewable proposal, before anything irreversible happens.

Who it's for: a spec author holding an over-budget spec who wants a defensible decomposition; and a maintainer who needs proof the split loses nothing.

2 · User scenarios & testing

Each story MUST be independently testable. US1 + US2 are the MVP: a covering, ranked proposal you can trust. US3 and US4 sharpen it.

US1 · The split proposal P1

As a spec author with an over-budget spec, I want to run /spectastic.spec and get a proposed decomposition into ranked, dependency-ordered child slices appended to my spec so that I can see how to split it without minting or branching anything yet.

Acceptance: a <spec-split> section is appended naming ≥2 candidate children, each with a title, scope, assigned parent-requirement IDs, and a reciprocal stub; the children are presented in R-002's order. No new files; no branches.

US2 · Coverage proof P1

As a maintainer, I want the proposal to prove the children cover the parent — nothing dropped, nothing duplicated so that I can trust the split instead of re-checking it by hand.

Acceptance: a coverage report shows every parent FR/NFR/SC mapped to exactly one child (a total, disjoint partition); any unassigned or duplicated requirement is flagged; a semantic pass confirms each child is a real vertical slice.

US3 · Rival-decomposition panel P2

As a spec author, I want a judge panel to weigh more than one way to slice and pick the best so that the proposed split is defensible, not the first arbitrary cut.

Acceptance: the panel scores up to N rival decompositions (N from the effort level; default ≤2) and selects one; the ranking is produced by multiple independent scorers, not a single judge, to resist LLM-as-judge bias.

US4 · Auto-offer on the red band P3

As a spec author, I want the slicer offered automatically when my spec crosses the red budget band so that I'm prompted to split at the moment the spec is demonstrably too big.

Acceptance: crossing the red band surfaces the split offer (extending the propose-time splitting nudge); the author still confirms — nothing runs unprompted.

Edge cases

  • The parent is Accepted, not Draft — the proposal must not be appended in place (FR-008); it routes through /spectastic.propose.
  • No clean split — the spec is cohesive, or every candidate leaves a child still over budget — W-2 returns a "don't split" verdict, not a forced cut (FR-007).
  • A proposed child is itself over budget — flagged as a recursive-split risk, not silently recommended (FR-007).
  • The parent has 0–1 requirements — too small to partition; W-2 returns the don't-split verdict.
  • RICE estimates are unconfirmed — the ranking is presented as provisional until the human confirms (FR-004).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

Run against an over-budget spec, the slicer MUST produce a split proposal — a decomposition into at least two candidate child slices — as a <spec-split> section appended to the parent. It MUST run as a workflow initiated by /spectastic.spec, not a new slash command, and MUST NOT mint child files or create branches in this slice.

Rationale

The dry-run boundary is what keeps the slicer in budget and revert-safe; the irreversible half (mint + git) is deferred. Keeping it inside spec preserves the eight-verb surface.

Each candidate child MUST carry a proposed reciprocal stub — a <spec-parent> plus the parent's reciprocal defer-to, and any inter-child reciprocity — so that R-002's existing inference orders the children unchanged.

Rationale

The children are hypothetical, so the slicer emits the exact link shape R-002 already reads, rather than a parallel edge format.

The proposal MUST rank the candidate children by RICE and present them in R-002's dependency-respecting order.

RICE inputs for candidate children MUST be agent-estimated and surfaced for human confirmation; the ranking MUST be presented as provisional until the inputs are confirmed.

The proposal MUST include a coverage report mapping every parent requirement (FR/NFR/SC) to exactly one child — a total, disjoint partition — and MUST flag any unassigned or duplicated requirement.

The coverage report SHOULD add a semantic critic pass asserting that nothing meaningful is dropped and each child is a genuine vertical slice (the smallest-demoable bar, per child).

When no candidate decomposition both covers the parent and leaves every child within budget, the slicer MUST emit an explicit "don't split" verdict with reasons rather than a forced split, and MUST flag any proposed child that itself exceeds budget.

The slicer MUST append the proposal in place only to a Draft parent (adding a <spec-changelog> entry, per P-6) and MUST NOT mutate a terminal-state (Accepted/Superseded/Deprecated) parent in place; against such a parent it SHOULD author the split through /spectastic.propose so it lands via change-management.

The ranking MUST be produced by a judge panel of independent scorers, not a single scorer, to counter LLM-as-judge bias (position, verbosity, self-preference). The slicer SHOULD weigh up to N rival decompositions (N governed by an effort level; default medium = ≤ 2) and have the panel select the best.

When a spec crosses the red budget band, the slicer SHOULD offer itself (extending the propose-time splitting nudge); the author still confirms — it MUST NOT run unprompted.

Non-functional

The ranking panel SHOULD use at least three independent scorers (or an equivalent structured anti-bias protocol), so a single biased judgment cannot decide the order.

Appending the <spec-split> section MUST be additive: existing parent requirements and their stable IDs are left untouched; only the section and one changelog line are added.

Out of scope (deferred to other slices)

  • Minting the proposed children as real spec.html files and superseding the parent (reciprocal defer-to / <spec-parent>) — the confirmed second step after the dry-run proposal.
  • The git fan-out (G-005): a branch per child off main and the topological merge sequence. Rides the 026/027 layer; speced when minting lands.
  • A general agent RICE-estimation primitive. W-2 estimates inline for its own children (FR-004); the reusable primitive is its own slice.
  • The effort-level primitive that governs the rival-decomposition count (FR-009); until it lands, the default ≤ 2 holds.

4 · Data model

One new element; three derived concepts it carries.

Entities

<spec-split> (new)
The appended proposal section: the candidate children, their ranking + R-002 order, the coverage report, and the verdict. Additive to the parent (NFR-002); reviewed, then a later slice mints from it.
Candidate child slice
A proposed child: title, scope, the parent-requirement IDs assigned to it, its reciprocal stub (FR-002), and its estimated RICE (FR-004). Hypothetical — no file exists yet.
Coverage report
The requirement → child partition table (FR-005) plus the semantic critic's verdict (FR-006).
Decomposition
A full candidate set of children covering the parent. The panel weighs rivals (FR-009) and selects one.

The slicer reuses the existing disciplines rather than inventing parallel ones: the per-child INVEST self-check and smallest-demoable bar judge a slice; R-002 orders; the <spec-budget> bands decide "still too big". The only genuinely new machinery is the two agentic pieces — the ranking panel and the coverage critic.

5 · Success criteria

Technology-agnostic, measurable outcomes.

For a parent with K requirements, the proposal's coverage partition assigns 100% of the K to exactly one child each — 0 unassigned, 0 duplicated — verifiable mechanically against the parent's requirement IDs.

Every candidate child in an accepted proposal passes the smallest-demoable / INVEST bar (independently demoable); any child that does not is flagged, never silently recommended.

The proposed child order satisfies 100% of the proposed reciprocal precedence edges (R-002's invariant) — re-checking the order against the stubs finds zero violations.

On a cohesive spec that should not be split, the slicer returns a "don't split" verdict with reasons rather than a forced decomposition, and a reviewer agrees the verdict is reasonable.

6 · Assumptions

R-002 is the ordering engine W-2 consumes. The reciprocal-stub shape (FR-002) feeds R-002's existing inference unchanged — the slicer produces links, R-002 sequences them.

The effort-level primitive that bounds the rival-decomposition count is not yet built; W-2's rival-weighing (FR-009, a P2 SHOULD) references it and defaults to ≤ 2 until it lands. This does not block the P1 estimate.

Specs needing a split are usually Draft (an over-budget spec is typically still being authored); the Accepted-parent → propose path (FR-008) is the lawful exception, not the common case.

The panel's bias resistance follows the LLM-as-judge literature (position/verbosity/self-preference effects); the concrete panel structure is the plan's to design.
