Run budget

A per-run cost ceiling for the hands-off pipeline that degrades gracefully — shallower decisions as it nears the limit — rather than dying mid-phase.

1 · Context

A hands-off run (037) answers every decision through the Decider, which at higher effort convenes a panel of voters — each a model call. Over a full plan→tasks→implement→verify run that is a lot of spend, and today the run has no ceiling: it either completes at full effort or a provider limit kills it mid-phase. The 037 interview peeled this cost story to keep that slice estimable; it is this slice.

This is for the operator running unattended who wants a predictable cost and a run that degrades — finishing at shallower Decider depth — rather than one that overspends or dies halfway.

2 · User scenarios & testing

Each story MUST be independently testable: US1 alone is a viable MVP.

US1 · The run degrades before it dies P1

As an operator, I want the run to lower its Decider effort as it nears the budget so that a long run finishes shallower instead of overspending or halting mid-phase.

Acceptance: with a ceiling set, once estimated spend crosses 80% the effort the run passes to the Decider drops one band (fewer voters via the 034 dial); the run keeps going.

US2 · The hard ceiling halts and hands back P1

As an operator, I want the run to stop and escalate at 100% of the budget so that it never silently overspends.

Acceptance: when estimated spend reaches the ceiling the run halts before the next decision and escalates to a human, reporting the spend.

Edge cases

  • No budget set (--budget unset): the tracker is unbounded and never degrades or halts — the run behaves exactly as 037 does today (parity).
  • Already past 80% at the first decision (a tiny budget): the first decision is already degraded; the run doesn't need to cross the band mid-run to degrade.
  • Effort already at the floor when degrading: it stays at the floor (can't go lower) rather than erroring.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A BudgetTracker MUST accumulate the run's estimated output-token spend and expose its phase: normal below 80% of the ceiling, degrade at ≥ 80%, halt at ≥ 100%. With no ceiling it is always normal.

Rationale

The 80% band is the established amber "approaching limit" threshold (REQ-FORMAT-004), reused so the run's cost warn point matches the project's convention.

When the tracker is in degrade, the run MUST lower the effort it passes to the Decider by one band (via the 034 effort order), clamped at the floor — so decisions convene fewer voters.

When the tracker reaches halt, the run MUST stop before the next decision and escalate to a human (the 037 escalation gate), reporting the spend — it MUST NOT silently exceed the ceiling.

The budget integration MUST be additive to 037's runPipeline: a run with no budget behaves byte-for-byte as today (the tracker's normal phase changes nothing).

spectastic run --budget <output-tokens> (default 1000000) SHOULD set the ceiling; the run records each model response's estimated tokens against it.

Non-functional

Spend accounting MUST be deterministic given the same responses — the estimate is a pure function of output length, so tests and reruns agree.

Out of scope (deferred to other slices)

  • Exact token accounting from provider usage reports — this slice estimates from output length; a real usage field on the AIProvider is a follow-up.
  • Degrading fan-out width (concurrency) — this slice degrades Decider depth (voters); width is 032's.
  • Persisting spend across a halted-then-resumed run — a fresh run starts the tracker at zero.

4 · Data model

One tracker; it holds the only new state (transient, per run).

Entities

BudgetTracker
{ ceiling?: number, spent: number, record(text): void, phase(): 'normal'|'degrade'|'halt' } — accumulates estimated output tokens; phase is derived from spent / ceiling against the 80% / 100% bands.
Degraded effort
The effort the run passes to the Decider = the base effort lowered one band when phase()==='degrade', clamped at the floor (FR-002).

Invariant: with no ceiling, phase() is always normal and the run is unchanged (FR-004) — the guardrail is opt-in.

5 · Success criteria

Technology-agnostic, measurable outcomes.

A run under a ceiling degrades the Decider effort by one band once estimated spend crosses 80% — observable by the effort passed to the Decider dropping (fewer voters) after the threshold, with the run continuing.

A run halts and escalates when estimated spend reaches 100% of the ceiling — observable by the run stopping before the next decision with a spend-reporting escalation, never exceeding the ceiling.

A run with no budget is byte-for-byte identical to a 037 run — observable by the tracker staying normal and the effort/decisions matching an un-budgeted run (parity, FR-004).

6 · Assumptions

The AIProvider does not report token usage today (verified in 037's grounding — chat/subagent return only text), so spend is estimated from output length (≈ chars ÷ 4). A real usage field is deferred (TBD-provider-usage); the estimate is enough to bound and degrade a run.

The 034 effort order (low < medium < high < xhigh < max) is the band ladder degradation steps down; the floor is the run's configured floor (default low).

7 · Open questions

None outstanding — the policy (degrade at 80, halt at 100), the default ceiling (1M output tokens), and the estimate-from-length method (with exact provider accounting deferred) were all settled in the 037 interview and this draft.
