Design · 057-portable-domain-skill

Portable domain skill

Portability and discoverability are the same coin: a pack that carries no host coupling and a description that any agent can find — checked where the tool can see it, honest about where it can't.

Status Accepted Spec 057-portable-domain-skill Owner Brian Corbin · @briancorbinxyz Branch main Created 25 Jul 2026 Read time

A domain pack is a distributable Agent Skill, and its discovery surface is the SKILL.md description the agent's router reads at startup (progressive disclosure). So this slice ships three things: a folded validate scan (packAgnosticismFindings in core) that flags spectastic vocabulary in a pack declared distributable by a marketplace.json — and verifies that same pack carries a present, non-trivial discovery description; a marketplace.json bundle shape; and a clean finance-settlement demo pack under examples/ that carries zero spectastic tokens, a rich multi-phase description, and 051 corpus metadata so the same unedited pack is a plain skill outside spectastic and citable inside it. Biggest risk: false-positiving spectastic's own dogfood/scaffold packs; mitigated by only ever checking marketplace-listed packs.

4 · Approach

Three deliverables, one coherent split. The check (FR-001/FR-003/SC-003): a pure core packAgnosticismFindings(packs) takes packs a marketplace.json declares distributable and, per pack, (a) scans its SKILL.md + references/*.md for spectastic vocabulary — the <spec-*> artifact tags, grounding=, /spectastic. verb names, the literal word spectastic — emitting a pack-not-portable finding per leak; and (b) verifies the SKILL.md carries a present, non-trivial description, emitting a pack-not-discoverable finding when it doesn't. The token set deliberately excludes KB-NNN ids and provenance frontmatter — those are the *portable* corpus convention (051), shared with Agent Skills, not spectastic coupling. A thin scanPackAgnosticism(cwd) locates any marketplace.json, resolves the listed pack dirs, and delegates — a no-op when no manifest exists.

The distribution shape (FR-002): a marketplace.json bundling packs by path, the same shape any skills-compatible client installs. The demo (FR-004 + your discoverability steer): a finance-settlement pack at examples/knowledge/ — a plain SKILL.md + references/ Agent Skill with zero spectastic tokens and a rich, multi-phase description written to trigger across software-development, learning, and knowledge-share tasks (the discovery surface), plus 051 KB-NNN metadata so the same unedited pack is a plain skill outside spectastic and citable inside it. The pack proves the split end-to-end; the check guards it.

6 · Decisions

D-001 · A folded validate scan backed by a pure core finding-fn

Status
Accepted
Context
scanCorpusWellFormed (validate.ts:236) is the established shape for a filesystem check: a thin CLI scan lazy-importing a pure core finding-fn, a no-op on absence.
Decision
Add packAgnosticismFindings(packs) to @spectastic/core/knowledge and scanPackAgnosticism(cwd) to validate.ts. Runs on every spectastic validate; [] when no marketplace.json exists.
Consequences
+ Reuses a proven, tested pattern; the check is unit-testable in-process. + FR-003's "wherever the tool can inspect" is satisfied by every validate run. − One more folded scan in the validate pipeline (bounded, no-op when absent).

D-002 · A pack is "distributable" iff a marketplace.json lists it — the check's scope

Status
Accepted
Context
The dogfood/scaffold packs legitimately name spectastic (knowledge/spectastic-concepts/SKILL.md); checking every pack reproduces 052's SC-003 false-positive. A marketplace.json is precisely the "packaged for distribution" declaration (FR-002).
Decision
The agnosticism check inspects only packs a marketplace.json resolves. spectastic's own un-listed packs are never checked.
Consequences
+ No false-positive on spectastic-domain packs; ties FR-002 and FR-003 into one signal. − A pack a user forgets to list is unchecked — acceptable, and exactly the NFR-001 ceiling (the tool checks what it can see).

D-003 · Token set = spectastic vocabulary, not the portable corpus convention

Status
Accepted
Context
052's BINDING_TOKENS flagged <spec-decision/grounding=; FR-001 widens this to "spectastic artifact vocabulary". But KB-NNN ids + provenance are 051's corpus convention, shared with Agent Skills — the pack needs them to be citable in a spectastic repo (US3).
Decision
Flag: <spec-*> tags, grounding=, /spectastic. verb names, the literal spectastic. Do not flag: KB-NNN ids, provenance frontmatter, index.md — those are portable data, not coupling.
Consequences
+ A clean finance pack keeps its citable KB metadata and still passes. + Matches 052's precedent, widened deliberately. − A pack could still couple in prose the token list doesn't name — the honest ceiling of a mechanical check (NFR-001), recorded.

D-004 · Discoverability = the SKILL.md description; check presence, author quality

Status
Accepted
Context
Agent Skills discovery is progressive disclosure over the SKILL.md name+description (considerations.html:154); a pack with no description is undiscoverable and so not "functioning as a plain Agent Skill" (FR-004). The steer: discoverable across dev/learning/knowledge-share phases.
Decision
The check verifies each distributable pack's SKILL.md has a present, non-trivial description (pack-not-discoverable otherwise). The demo pack models a rich, multi-phase description; the *quality* of triggering stays authored + review-caught (semantic, unenforceable) — no spec change, this rides inside FR-004.
Consequences
+ Honours the discoverability steer with a real checked floor + a worked example. + No requirement invented; interprets FR-004's "plain Agent Skill" honestly. − Presence ≠ good triggering; the semantic quality is review-caught (the whole family's presence-vs-quality line).

D-005 · The finance-settlement demo pack under examples/knowledge/

Status
Accepted
Context
The smallest-demoable names a finance-settlement pack; none exists. examples/ is the established home for illustrative artifacts (not knowledge/, the repo's own corpus, nor templates/, the init scaffold).
Decision
Build examples/knowledge/finance-settlement/ (SKILL.md + references/ + index.md) — zero spectastic tokens, a multi-phase description, 051 metadata — and examples/knowledge/marketplace.json listing it. It is both the demo and the check's own fixture.
Consequences
+ One artifact proves the whole split (plain skill outside, citable inside) and exercises both check legs. − A settlement-domain doc needs plausible content; kept small and clearly illustrative (not authoritative), with honest TODO/illustrative provenance.

D-006 · TDD, tests written red-first

Status
Accepted
Context
The check is deterministic core: fixtures in, findings out. Every SC is cheaply assertable first (clean pack passes; a token leak flags; a missing description flags; the demo pack passes both).
Decision
Write the failing unit tests before packAgnosticismFindings; the demo pack doubles as a real-fixture green case.
Consequences
+ Two MUSTs + the discovery floor get red-first coverage. − None material for a deterministic scan.

9 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here.

Discoverability is treated as an aspect of FR-004 ("function as a plain Agent Skill"), realised through the SKILL.md description — not a new requirement. This honours the author's steer without a spec re-entry: an Agent Skill's discovery surface *is* its description, so a present, non-trivial description is part of functioning as one. Should a first-class, separately-tested discoverability requirement later prove wanted, that is a clean /spectastic.propose against 057 — recorded, not pre-built.
