Portable domain skill

A domain pack that carries zero spectastic knowledge is a clean, publishable unit — equally useful in a spectastic repo and a plain agent project.

Status Accepted Spec ID 057-portable-domain-skill Owner Brian Corbin · @briancorbinxyz Reviewers — Created 25 Jul 2026 Principlesv1.8.0 Smallest demoableA finance-settlement pack with zero spectastic references + a marketplace.json installs into a plain Claude Code project as an Agent Skill. Read time

A domain pack is a distributable unit — Agent Skills ship as marketplace plugins installable into ~40 skills-compatible clients. So a finance-settlement pack must carry zero spectastic knowledge: the moment it embeds "cite this in a <spec-decision grounding>" it stops being a clean, publishable domain skill (a coupling the prototype's first SKILL.md got wrong). This spec defines the spectastic-agnostic pack shape and its distribution as a marketplace Agent Skill, and pairs it with the other half of the split: the citation binding lives in the harness (052 FR-004), never in the pack. A pack must function as a plain Agent Skill with no spectastic present — and, dropped into a spectastic repo, be citable via the harness binding with no pack edit. Portability across a third-party pack is a discipline the tool can encourage but not enforce; that ceiling is recorded.

1 · Context

The corpus convention began by adopting the Agent Skills folder shape precisely because it is portable across a wide field of agents — the direct answer to "what if I'm not using the model that authored the corpus". That portability is only real if a domain pack stays a clean skill. Agent Skills ship as marketplace plugins (a marketplace.json-style bundle installable by path), so a pack has a natural distribution path if it carries no host-specific coupling.

The prototype's first SKILL.md got this wrong: it baked in "cite this in a <spec-decision grounding>" — spectastic knowledge that has no business in a finance skill. The fix is an architectural split: the pack carries the domain knowledge and nothing else; the citation binding lives one level up, in the harness (052 FR-004). This spec owns the pack half of that split — the shape and the distribution — so the same pack is equally useful in a spectastic repo and in a plain Claude Code project.

2 · User scenarios & testing

Each story MUST be independently testable.

US1 · A clean, publishable pack P1

As a domain-pack author, I want a pack shape that carries zero spectastic-specific instructions so that my pack is a clean, publishable marketplace unit rather than something coupled to one host tool.

Acceptance: a domain pack contains no spectastic tokens (no <spec-decision>, no "cite in a grounding" text) and passes an agnosticism check.

US2 · Install into any skills-compatible agent P2

As a user of any skills-compatible agent, I want to install a domain pack via a marketplace so that it is useful outside spectastic — in a plain Claude Code, Codex, or Cursor project.

Acceptance: the pack is describable as a marketplace Agent Skill (a marketplace.json-style bundle) and installs into a project with no spectastic present, functioning as a plain SKILL.md + references/ skill.

US3 · The same pack is citable in a spectastic repo P3

As a maintainer, I want the citation binding kept in the harness so that the same, unedited pack is citable via a <spec-decision grounding> the moment it sits in a spectastic repo.

Acceptance: the pack, dropped into a spectastic repo, is citable through the harness binding with no edit to the pack.

Edge cases

  • A third-party pack that does embed spectastic instructions — flagged by the agnosticism check where spectastic can see it, but not enforceable on a pack it never inspects (NFR-001, a recorded ceiling).
  • A pack installed with no corpus convention present — still works as a plain Agent Skill; the corpus family is not a prerequisite for the skill itself (FR-004).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A domain pack MUST carry zero spectastic-specific instructions — no "cite in a <spec-decision grounding>" text, no spectastic artifact vocabulary; embedding one MUST be treated as a portability defect — unless the pack self-declares tool-specific (tool-specific: true in its SKILL.md), in which case its domain is that tool and the portability check MUST be skipped for it. A pack that does not so declare (i.e. claims general portability) still gets the hard check (063-corpus-discoverability FR-005).

Rationale

The moment a pack embeds host-specific citation instructions it stops being a clean, publishable domain skill — if it claims to be domain-neutral. A pack whose declared subject IS a specific tool is a different, legitimate case: listed and discoverable, but honestly non-portable. The self-declaration makes that distinction explicit and machine-readable rather than exempt-by-omission, which is what forced 062's consumer-only retreat.

A distributable pack MUST be describable as a marketplace Agent Skill — a marketplace.json-style bundle — installable into any skills-compatible client.

The pack shape SHOULD be validated for spectastic-agnosticism — a check that flags spectastic tokens in a pack meant to be portable — acknowledged as review-caught for third-party packs the tool never inspects.

Rationale

The tool can encourage agnosticism on packs it can see (its own, a repo's committed ones); it cannot enforce it on a pack published elsewhere. Naming that limit rather than pretending to a guarantee it can't hold.

A pack MUST function as a plain Agent Skill (SKILL.md + references/) with no spectastic present; the corpus convention and its citation binding MUST NOT be prerequisites for the pack to work.

Non-functional

Portability across third-party packs MUST be treated as a discipline the tool encourages, not a property it enforces on a pack it never inspects; this ceiling MUST be recorded, not hidden.

Out of scope (deferred to other slices)

  • The citation binding itself — the harness half of the split that keeps the pack clean.
  • The corpus convention (layout, IDs, index) a pack conforms to when used as a corpus.
  • Redistribution terms of the material a pack bundles when it is published.

4 · Data model

The entities this feature owns or substantially changes.

Entities

Domain pack
A self-contained Agent Skill: SKILL.md + references/, carrying domain knowledge and no spectastic instructions. The distributable unit.
Marketplace entry
A marketplace.json-style record bundling the pack into an installable plugin by path, for any skills-compatible client.

Invariant: the pack and the citation binding are on opposite sides of the split — the pack never names spectastic; the harness never lives in the pack. This is what makes one artifact serve two contexts unedited.

5 · Success criteria

Technology-agnostic, measurable outcomes.

A domain pack passes a spectastic-agnosticism check (no spectastic tokens) and installs as an Agent Skill in a project with no spectastic present.

The same, unedited pack, dropped into a spectastic repo, is citable via the harness binding — no edit to the pack required.

A pack that embeds a spectastic instruction is flagged by the agnosticism check wherever the tool can inspect it.

6 · Assumptions

The Agent Skills marketplace/plugin mechanism (a marketplace.json bundling skills by path) remains the distribution path; a public searchable registry with per-skill semver is reported by secondary coverage but not depended on here.

"Spectastic tokens" are recognisable enough (artifact vocabulary like <spec-decision>, KB-NNN@ citation syntax, verb names) that a mechanical agnosticism check can flag them without heavy semantic analysis.
