Tool-specific exemption for pack-not-portable

Applied

1 · Intent

057's pack-not-portable rule (FR-001) originally treated any spectastic vocabulary in a marketplace-listed pack as a portability defect — because it conflated "listed in a marketplace" with "portable to any domain". A pack whose subject is a specific tool (the meta-repo's own spectastic-concepts) is legitimately both listed and non-portable. 062 hit exactly this and retreated to consumer-only (FR-009); 063 resolved it instead — a pack self-declares tool-specific: true and the rule spares it, while a pack claiming real portability still gets the hard check.

The behaviour is built and dogfooded (063 T-310, T-300, T-312). This proposal only aligns 057's spec text with it, so the two stop disagreeing — the doc-sync half of the cross-spec cascade 063 FR-005 named.

2 · Scope

In scope

  • MODIFY FR-001 to carve out a self-declared tool-specific pack.

Out of scope

  • The exemption's implementation + test — already landed in 063 (T-310/T-300); this is prose-only.

3 · Approach

A single MODIFY on FR-001: keep the rule as the default, append the explicit self-declaration carve-out and the "a pack claiming portability still gets the hard check" clause. No code or task change — the behaviour predates this proposal by one spec.

4 · Deltas

One <spec-delta>.

What changes: the zero-spectastic-instructions rule now carves out a pack that self-declares tool-specific: true in its SKILL.md.

A domain pack MUST carry zero spectastic-specific instructions — no "cite in a <spec-decision grounding>" text, no spectastic artifact vocabulary; embedding one MUST be treated as a portability defect — unless the pack self-declares tool-specific (tool-specific: true in its SKILL.md), in which case its domain is that tool and the portability check MUST be skipped for it. A pack that does not so declare (i.e. claims general portability) still gets the hard check (063-corpus-discoverability FR-005).

Rationale

The moment a pack embeds host-specific citation instructions it stops being a clean, publishable domain skill — if it claims to be domain-neutral. A pack whose declared subject IS a specific tool is a different, legitimate case: listed and discoverable, but honestly non-portable. The self-declaration makes that distinction explicit and machine-readable rather than exempt-by-omission, which is what forced 062's consumer-only retreat.

5 · Risk register

Adversarial pass ran (touches must-tier FR-001). All findings dispositioned by the author.

The change most likely to be regretted: tool-specific: true becomes an escape hatch — a genuinely-non-portable domain pack (not tool-specific at all) sets the flag to silence a real portability defect and ships a spectastic-coupled pack into a marketplace others rely on.

MODIFY FR-001: "the portability check MUST be skipped for it".

Accepted. The flag is a visible, machine-readable, self-authored claim in the pack's own SKILL.md, not a silent skip — a reviewer sees "this pack declares its domain IS a tool" and can judge it, exactly as they judge any other SKILL.md metadata. The residual (someone lies in their own manifest) is the same trust boundary every self-declared field has; P-9 holds because a pack that omits the flag still fails hard.

The requirement this most likely contradicts is FR-003 ("a check that flags spectastic tokens in a pack meant to be portable") — the modified FR-001 could read as weakening the very check FR-003 describes.

FR-003 vs. the FR-001 carve-out.

Mitigated — no contradiction, and the wording already resolves it. FR-003 checks a pack "meant to be portable"; a tool-specific pack is by its own declaration NOT meant to be portable, so it falls outside FR-003's scope exactly as the carve-out intends. FR-003 is untouched and stays true.

Scope concern: prose-only proposes that trail their implementation by a spec can rot — if 063's code and this text ever diverge, the doc is authoritative-looking but stale.

§2: "already landed in 063 (T-310/T-300); this is prose-only".

Accepted (deliberate, tracked). The divergence risk is real for any doc-sync, but the alternative — 063 silently reversing an Accepted sibling's requirement with no propose — is worse (P-6). The behaviour's guarantee lives in 063's test (P-8), and this text points at it, so a future reader is sent to the enforcing code, not left trusting prose.

No corpus domain-fact contradiction: the repo's knowledge/ corpus commits facts about SDD/RFC 2119 and securities settlement, orthogonal to a portability-rule carve-out.
