Decision index federation

An owner publishes its scoped decisions as a pinned index; a consumer vendors it; the verdict enforces ownership across the repo boundary, from disk.

Status Draft Spec ID 122-decision-index-federation Owner Brian Corbin · @briancorbinxyz Reviewers Guardrail layer (115 · 119 · 120 · 121) Created 19 Sep 2026 Principlesv1.9.0 Smallest demoabledecisions export in an owner repo; decisions sync in a consumer repo pointed at it by path; a write to the owner's store fails verdict with cause: ownership, scope: federated, one source recorded — no MCP involved. Read time

119/120 let a decision claim a data store and let verdict flag a non-owner's write — but only for a decision present in the consumer's checkout, which today means a pasted copy. This spec makes the claim travel: the owner exports its scoped decisions to a hashed specs/decisions.json, kept honest by validate; a consumer declares its sources, vendors a pinned copy, and verdict evaluates the foreign resource-scoped decisions beside its own, still entirely from disk. The file contract is shared with the MCP server that serves the same index to agents.

1 · Context

The verdict is honestly repo-local: "a decision not present in this checkout is not evaluated". The one worked example of cross-repo ownership works only because the consumer carries a verbatim copy of the owner's decision — a copy nothing keeps current and nothing signed. The cross-repo survey named the missing legs: a claim that travels, and a way to reach it.

Checking out each owner in CI and hosting an MCP server were both declined — a live git dependency per run, or a service to operate. The knowledge corpus was the first instinct and is the right discipline (provenance, hash, drift) but the wrong store — placement D-004 and cross-repo D-006 already say so. So: a published index with the corpus's honesty and none of its documents. And because 115 FR-002 says a verdict reconstructs entirely from disk, the index is vendored into the consumer and refreshed by a separate verb — which is what "pinned" means concretely.

2 · User scenarios & testing

Each story is independently testable; US1 alone publishes something a human can check.

US1 · Publish the claim P1

As an owner of a data store, I want to export my accepted, scoped decisions as a committed index so that any consumer can enforce my ownership claim without reading my repository.

Acceptance: decisions export writes specs/decisions.json from the accepted, scoped decisions; a design edit without a re-export fails validate; a bare project is refused; two exports are byte-identical.

US3 · Enforce across the boundary P1

As a reviewer on a consuming service, I want a write to a store another repository owns flagged as an ownership violation with its authority named so that the change is routed to the owner instead of merged.

Acceptance: with a vendored owner index, a change touching the owner's store fails verdict with cause: ownership, the authority, scope: federated and a sources entry; local decisions behave as before; a missing or invalid copy stops the verdict naming the source.

US2 · Vendor a pinned copy P2

As a maintainer of a consuming service, I want to declare where each owner's index comes from and fetch a pinned copy so that my verdict runs from disk, offline, and an upstream change is a reviewable diff.

Acceptance: decisions sync fetches each source into .spectastic/decisions/, records its hash as the pin, reports what moved; a copy disagreeing with its pin fails validate; a source with no unit edge is warned about.

US4 · The gate carries it P2

As a downstream maintainer, I want the installed CI gate to enforce federated decisions with no change to its rendered line so that an owner's claim holds on every pull request, not only on a developer's machine.

Acceptance: the gate's verdict step is byte-identical to 121's; on a consumer with a vendored source it fails a violating pull request; the template carries a commented token line.

Edge cases

  • An index claiming a store for a project other than its own: rejected whole — an index makes claims only for itself.
  • A foreign decision with only path or module scope: ignored and counted; its globs mean nothing in the consumer's tree.
  • A foreign rule whose pattern exceeds the cap or fails to compile: counted on its source, never executed.
  • A source naming the consumer's own project: refused — a project does not federate with itself.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

decisions export MUST write specs/decisions.json containing every accepted decision that carries a path, module or resource scope — each with its coordinate, minus its prose and any rule's run — sorted by spec then id, with the project identity and a content hash over the decisions; it MUST refuse when the project identity is not owner-qualified.

Rationale

Prose is the design, already served by anchor; a run string is an instruction, and artifacts are data (P-11). A bare identity cannot be a federation key.

validate MUST report an error when a committed index's hash disagrees with the hash recomputed from the current designs, and MUST report a warning when an accepted resource-scoped decision exists and no index does.

A consumer MUST declare each owner it federates with as a source — the owner's project identity and where its index is fetched from, a URL or a repository-relative path — under a decisions section of its configuration, distinct from its unit edges; a source naming the consumer's own project MUST be refused.

Rationale

An edge and a locator are different facts, and 079's unit-edge list is a string array — an object there would silently vanish.

decisions sync MUST fetch each source's index, validate it, write it verbatim under .spectastic/decisions/, record the copy's hash as that source's pin, and report per source whether it was fetched, unchanged, moved or refused; a source that cannot be fetched MUST leave its copy and pin untouched and make the verb exit non-zero; a bearer token from the environment SHOULD be sent for a private owner and MUST NOT be written to any output.

An index MUST be rejected whole, with the reason named, when: its schema is unknown; its project is absent, not owner-qualified, or not the one the source was declared for; its hash is missing or disagrees with the content; any decision is not accepted, lacks an id, spec id or coordinate, or carries a coordinate that disagrees with them; or any resource owner is not the index's own project.

verdict MUST read each declared source's vendored copy, validate it, and evaluate its resource-scoped decisions beside the local ones; foreign decisions without a resource scope MUST be ignored and counted; local decisions MUST be evaluated as before.

When any source is declared, the verdict MUST carry scope: federated and one entry per source — project, origin, hash, and the counts evaluated, ignored and refused; the existing total MUST keep its meaning.

A declared source whose vendored copy is missing, fails validation, or disagrees with its pin MUST stop the verdict with the source named, never a green verdict that silently skipped it; validate MUST report the same three conditions.

Rationale

With vendoring there is no "unreachable" at verdict time — only "never synced" or "tampered". A verdict that skipped an owner's decisions is the silent-miss class 121 exists to close; no flag softens it.

A foreign rule's pattern MUST be at most 1024 characters and compile under the platform's regular-expression engine before it is run; a rule failing either MUST be counted on its source and never executed.

The verbs MUST land as one group, decisions {for, coverage, export, sync}, where for and coverage are today's adrs; adrs MUST keep working as an alias hidden from help.

A declared source whose project has no matching unit edge SHOULD be warned about by validate, since reach is declared, never inferred.

Non-functional

Export and verdict MUST be deterministic — repeated runs over one estate differ by at most 0 bytes, the verdict kernel performs 0 network reads — and the hash MUST be pinned by 1 literal test vector the sibling MCP repository mirrors, so two implementations cannot silently disagree.

A rejected index MUST contribute at most 0 decisions to any verdict — partial acceptance is never permitted.

The rendered CI gate's verdict line MUST differ from 121's by at most 0 bytes; sources come from configuration, not from the gate.

Out of scope (deferred)

  • Regrouping the other verbs under themes — direction in verb-grouping-considerations; decisions is the first done deliberately.
  • Reading an index over the network at verdict time — contradicts 115 FR-002 and the kernel's no-network guarantee.
  • Evaluating a foreign decision's path or module scope in the consumer's tree.
  • A design-time "this belongs to service X" suggestion — gated on placement.
  • Serving indexes to agents across checkouts — the sibling MCP repository's spec on the same contract.
  • A second ownership field — the resource scope is already the claim; the index makes it travel.

4 · Data model

The decision itself is unchanged from 119.

Entities

Decision index
An owner's published set of accepted, scoped decisions, identified by the owner's project and a content hash over exactly those decisions. A copy of the designs at a moment; the hash makes staleness detectable. At most 1 per repository.
Source
A consumer's declaration that it federates with an owner: the owner's project, where its index comes from, and the pin — the hash last synced. Never names the consumer itself.
Vendored copy
The owner's index bytes as last synced, held in the consumer's repository. Valid only while its hash equals the pin and it passes the rejection rules.
Foreign decision
A decision read from a vendored copy. Only its resource scope is evaluated; its path and module scopes are inert in the consumer's tree.

Transitions: an index is exported → committed → superseded by the next export. A source is declared → synced (pin set) → re-synced (pin moved, a reviewable diff). A vendored copy is valid ⇔ hash = pin ∧ passes rejection; there is no partially valid copy.

5 · Success criteria

A reviewer on a consuming service sees a write to another repository's store blocked with the owner named, from a decision never pasted into their repository — 1 of 1 violating changes fails with cause: ownership under scope: federated (target: a clean change passes too), from 0 today (a foreign decision is invisible unless copied).

Observed at

Two scratch repositories: owner exports, consumer syncs by path; verdict --changed on a write to the store exits 1 with the authority and one source in the artifact; a change outside it exits 0.

Falsified by

The violating change passing, or the verdict carrying no source.

An owner who edits a scoped decision without re-exporting is stopped at their next commit — 100% of stale indexes are reported (target 100%, with 0 unscoped decisions leaking into the file), from no established baseline.

Observed at

The validate integration test: export, edit a scope, validate exits 1; re-export clears it; an unscoped decision is absent from the file.

Falsified by

A stale index passing validate.

A maintainer whose vendored copy is missing, tampered with, or from the wrong project never gets a green verdict that skipped it — 3 of 3 conditions stop the verdict naming the source (target 3 of 3), from no established baseline.

Observed at

The verdict integration test: no copy, one byte changed, wrong project — each exits 2 naming the source.

Falsified by

Any of the three producing exit 0.

A maintainer declaring a source without the matching unit edge is told so — 1 of 1 such configurations warns (target 1 of 1, with a private-owner token never appearing in any output), from no established baseline.

Observed at

The validate unit test on a configuration with a source and no consumes entry; the sync test asserting the token is absent from stdout, stderr and the written copy.

Falsified by

Silence.

A downstream maintainer's installed CI gate enforces a federated decision with 0 bytes of change to its rendered verdict line (target 0), from no established baseline.

Observed at

The renderer's docs-equality and byte-determinism tests remain green after this spec; the gate integration test fails a violating pull request on a consumer with a vendored source.

Falsified by

A changed verdict line in the rendered workflow.

A maintainer of spectastic can trust the boundary without reading foreign patterns — 4 of 4 properties hold: the shared vector digests identically, an over-long or non-compiling pattern is counted and never run, a rejected index contributes 0 decisions, the kernel performs 0 network reads (target 4 of 4), from no established baseline.

Observed at

The unit tests plus the existing guardrail no-network import scan.

Falsified by

Any of the four assertions failing.

6 · Assumptions

The file contract is the one frozen in the sibling MCP repository's handover on 18 Sep 2026; a change to it lands in both places or not at all.

115's scope type and 121's template are Accepted; the federated value and the commented token line are proposed after this lands, never edited silently.

The owner's <spec-resource owner=…> is already the machine-readable claim the cross-repo survey asked for; this spec makes it travel.
