Design · 122-decision-index-federation

Decision index federation

How we will build it.

Status Draft Spec 122-decision-index-federation Owner Brian Corbin · @briancorbinxyz Branch main Created 19 Sep 2026 Read time

One new core module, decisions/, owns the index (build, canonical hash, validate, merge) and is pure: the CLI resolves config and injects sources as data, the kernel reads vendored copies through its filesystem port, and the only network call lives in an edge-side fetcher the verdict graph never imports — so the existing no-network scan proves the invariant rather than a comment asserting it. The verbs land as one decisions group with adrs hidden behind it. Biggest risk: two canonicalisers (this repo's and the MCP server's) disagreeing silently — held by a literal vector minted with a third implementation.

5 · Approach

A new core module packages/core/src/decisions/ holds everything pure: canonical.ts (canonical JSON + sha256), index.ts (build an index from loaded decisions; validate one against the reject list and an expected project), merge.ts (reconstitute foreign decisions, keep only those with a resource, count the rest), and sync.ts (plan a sync from sources + fetched bytes: fetched / unchanged / moved / refused; the pin update as data). verdictCommand gains an optional sources input and, when present, reads each vendored copy through ctx.fs, validates it, merges, and sets scope: 'federated' with sources[] on the verdict — the regex compile at verdict.ts:141 is preceded by the length cap and a try/catch so a rejected rule is counted on its source.

The CLI's adrs.ts becomes decisions.ts: a group with for, coverage, export, sync; a hidden adrs command maps its flags onto for/coverage. The fetcher is a port (DecisionIndexFetcher { fetch(location): Promise<string> }) with two edge implementations — path and HTTPS — so core's sync.ts never imports network code and the no-network scan keeps its meaning. Validate gains four findings folded beside scanCiDrift.

The thing nearly done instead: loading foreign decisions at the edge and passing them through the existing decisions?: seam. It would have worked and put the validation and merge logic in the CLI — the exact drift 041–043 paid for. The seam is kept; what flows through it is data the kernel validated.

7 · Decisions

D-001 · Pure decisions/ core module; the verdict seam widened; adapters at the edge

Status
Accepted
Context
verdictCommand already takes decisions and the current project as injected data (commands/verdict.ts:23-34) and reads nothing itself (119 D-004); the no-network test walks its import graph (guardrail.no-network.test.ts:11-19). P-14 asks the same question the alternatives matrix answers.
Decision drivers
reconstruct-from-disk · no-network by construction · second-caller test (the MCP repo and the validate scans both want validate/merge without the CLI)
Considered options
  • Core reads vendored copies via ctx.fs — chosen — + one validator, three callers; + the scan proves the invariant. − a new core module and subpath export.
  • Edge loads and injects — + thinner core. − validation and merge in the CLI; a second validator for the MCP repo to mirror.
  • Fetch at verdict time — + no sync verb. − contradicts 115 FR-002 and the scan.
Decision
packages/core/src/decisions/{canonical,index,merge,sync}.ts, exported as @spectastic/core/decisions. VerdictCommandInput.sources?: DecisionSource[]; when present the kernel reads .spectastic/decisions/*.json via ctx.fs, validates, merges, and emits scope: 'federated' + sources[]. The CLI resolves decisions.sources from config and passes it as data.
Consequences
+ the no-network scan covers the federated path with no edit. − Verdict gains an optional field and VerdictScope a value — 115's type is amended by propose after landing.

D-002 · The fetcher is a port; HTTPS and path adapters live in providers/, imported only by the CLI

Status
Accepted
Context
The scan also greps for a bare fetch( (guardrail.no-network.test.ts:19); the visual slice already models a fetcher as a port with a providers/ adapter (visual/source-fetcher.ts, providers/local-source-fetcher.ts). Node ≥ 20 has global fetch and AbortSignal.timeout (grounding row).
Decision
DecisionIndexFetcher { fetch(from: string): Promise<{ text: string; from: string }> } in decisions/sync.ts; providers/decision-index-fetcher.ts implements path (repo-relative, containment-checked) and https: (30 s AbortSignal.timeout, 1 MiB cap read via the body stream, redirect: 'manual' with same-host follow only, Authorization: Bearer $SPECTASTIC_SOURCE_TOKEN when set, never logged). http: is refused.
Consequences
+ sync is testable with a stub fetcher; the network code is one file. − a private owner needs the token in CI; the gate template carries it commented.

D-003 · Canonical JSON + sha256, pinned by a vector minted with a third implementation

Status
Accepted
Context
Two TS canonicalisers (this repo, the MCP repo) can agree with each other and both be wrong; the spike minted the vector with python's json.dumps(sort_keys, compact, ensure_ascii=False) and recorded its digest (grounding row). Keys sort identically in both languages only because every key is ASCII — recorded as a constraint.
Decision
canonicalJson: recursively sort object keys with the default comparator, drop undefined, no whitespace, otherwise JSON.stringify. contentHash = 'sha256:' + hex(sha256(utf8(canonicalJson(decisions)))). The vector (array + digest) lives in packages/core/test/fixtures/decision-index-vector.ts with a comment naming the MCP repo's mirror; the test asserts the digest byte-for-byte.
Consequences
+ a canonicaliser drift on either side fails a test, not a production sync. − adding a non-ASCII key to the decision shape would need a re-minted vector and an ordering note.

D-004 · Sources are a config section with the pin inline; the vendored copy is the bytes verbatim

Status
Accepted
Context
The registry models sections as frozen key maps and the unknown-key scan reads it (registry.ts:135-176); the writer preserves order and indent and refuses an unparseable file (config/edit.ts:46-80); consumes[] drops non-strings (units/read.ts:29-33).
Decision
Registry section decisions: { sources: object[] }; each entry { project, from, pin? }. config/edit.ts gains setDecisionSourcePin(cwd, project, pin) on the existing load/persist. Vendored copy at .spectastic/decisions/<project with / → -->.json, the fetched bytes unmodified, so its own hash can be recomputed against the pin. The pin is the hash string only — no syncedAt, so a re-sync that fetched identical bytes is a zero-line diff.
Consequences
+ a moved pin is a reviewable one-line change. − the pin and the copy can be edited independently by hand; validate's decision-source-unpinned and the verdict's refusal are what catch it.

D-005 · One decisions group; adrs a hidden command that forwards

Status
Accepted
Context
corpus is the grouped precedent (corpus.ts:37); commander 15 has { hidden: true } (typings/index.d.ts:1095); the impl-task agent definition and 112–114's tests call adrs. Direction recorded in docs/verb-grouping-considerations.html.
Decision
registerDecisions(program): decisions for <paths...> (with --log, --json), decisions coverage, decisions export [--out], decisions sync. program.command('adrs', { hidden: true }) keeps today's flags and forwards to the same action functions — byte-identical output, so 112–114's tests pass unchanged. Help copy carries no internal ids.
Consequences
+ one fewer visible verb; the first deliberate group. − two spellings coexist until TBD-verb-grouping decides the alias policy.

D-006 · Foreign patterns: cap, compile-check, count — before the existing compile site

Status
Accepted
Context
The one compile site is verdict.ts:141; a foreign decision's owner can never be the consumer (spec FR-005), so the owner branch above it is unreachable for foreign rules. The spec fixed 1024 characters and a compile check (FR-009).
Decision
In merge.ts, each foreign rule is checked before it reaches the kernel: length ≤ 1024 and new RegExp(pattern) inside try/catch; a failing rule is removed from the merged decision and tallied as refused on its source. Local rules are untouched — the check is on the boundary, not the kernel.
Consequences
+ the kernel's compile site stays as it is. − a pathological-but-compiling pattern is still run; recorded as the ceiling the 1024-character choice accepted.

D-007 · TDD, medium risk; the two-repo loop is the acceptance run

Status
Accepted
Context
Anchored in the interview. Medium because the nested config write and HTTPS fetching are new to this codebase; each gets a red-first test before its implementation.
Decision
Unit tests per module red-first; one integration test builds an owner and a consumer scratch repository, exports, syncs by path, and runs the built verdict; a stub fetcher exercises the HTTPS branch's cap, timeout and redirect rules without a network.
Consequences
+ SC-001 is a real run. − the HTTPS adapter's live path is exercised only by a local http.createServer fixture, not a public host.

10 · Complexity tracking

A separate decisions/ module rather than growing guardrail/: the index is consumed by validate, by sync and by the MCP repo's mirror, and only one of those is the verdict. Four small files beat one large one here.

P-11 tension, recorded: a foreign pattern is compiled and matched. It is never evaluated as code, run is stripped at export, and the boundary check (D-006) precedes the compile site — the residual (a compiling but slow pattern) is stated, not hidden.

A hidden alias instead of a clean rename: cheaper than a propose on 112/113 and a bundle re-sync today; the alias policy is TBD-verb-grouping's to settle.
