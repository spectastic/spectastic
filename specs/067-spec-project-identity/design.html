Design · 067-spec-project-identity

Spec project identity

How we will build it.

Status Accepted Spec 067-spec-project-identity Owner Brian Corbin · @briancorbinxyz Branch 067-spec-project-identity Created 29 Jul 2026 Read time

Split the identity across the layer it belongs to: the pure grammar — the project-id shape and the spectastic://<owner>/<repo>/spec/<id> URI composer — lands in @spectastic/schema (the dependency-free floor, beside the citation grammar); the fs reader (resolveProjectConfig) joins @spectastic/corpus's config.ts, and project folds into resolveCorpusConfig's marketplace precedence so every caller gets the unified derivation free; the engine + CLI for spectastic id is fat-core, thin-CLI; and the owner-qualified git derivation is confined to init's write path in the CLI. Biggest risk: git-remote → owner/repo parsing across hosts — mitigated by treating a non-confidently-parsed remote as not resolved, leaving the identity provisional rather than persisting a wrong value.

2 · Technical context

Language(s)
TypeScript, ESM; Node ≥ 20.
Frameworks
commander (CLI). No new dependency — git via node:child_process.execFile, the same shape GitRunner already uses (no git library).
Architecture
Layered-by-purity across the existing package graph (D-001): pure grammar → schema; fs config reader → corpus; engine → core; dispatch + git derivation → cli. No new package.
Storage
Filesystem — the top-level project field in the root spectastic.json. No new store, no schema migration.
Testing
Vitest, TDD red-first (D-005), against fixture configs + an injected GitExec / a temp git repo for the derivation.
Coverage
Not in scope — no coverage enforce floor (no profile marker present).
Perf targets
None — the only latency is a bounded, init-time git remote shell-out; read-path resolution is pure fs + string.
Constraints
Deterministic read (NFR-001 — no live git/clock/env at read time); non-breaking (NFR-002); the @spectastic/corpus → @spectastic/core boundary (never crossed).

4 · Approach

One identity, placed by purity across the layers that already exist. @spectastic/schema gains the two pure primitives — a project-id well-formedness predicate and specResourceUri(project, specId, anchor?) that composes spectastic://<owner>/<repo>/spec/<id>#<anchor> (owner-as-authority, D-004) — beside the citation grammar it already hosts. @spectastic/corpus's config.ts gains loadProjectConfig (raw) / resolveProjectConfig (basename fallback), mirroring its own corpus-config split, and resolveCorpusConfig inserts the raw project as a new marketplace tier (FR-006) — so all ~15 callers, standalone binary included, unify for free. @spectastic/core holds the id engine: resolve the project, confirm specs/<id> exists, render the URI. The CLI adds a thin registerId, a remoteOwnerRepo() method on GitRunner, and a writeProjectConfig in init that persists the owner-qualified id only when the remote confidently resolves one (FR-002) — otherwise leaving it absent for a later firm-up. The validate finding wraps schema's predicate in corpus (beside corpusRegistryFindings), so the standalone binary checks it too.

6 · Decisions

D-001 · Place the identity by purity: grammar+URI in schema, fs reader in corpus

Status
Accepted
Decision drivers
the corpus↛core boundary · FR-006 unified derivation with zero threading · "shared, not corpus-specific" semantics · new-package overhead
Considered options
  • Split — grammar+URI → schema, fs reader → corpus/config.ts (chosen) — + the shared concept lives in the shared floor beside the citation-grammar precedent; + FR-006 folds into resolveCorpusConfig free; + no new package. − the concept spans two files.
  • New @spectastic/model package — + cleanest naming/home for future identity primitives. − a 5th workspace (package.json/tsup/tsconfig/exports/CI/dependency-cruiser + release bump) for one field today.
  • All in corpus/config.ts — + zero overhead. − the spec-identity concept nesting inside the corpus package (the smell the interview flagged).
  • All in core — − corpus can't import core, so FR-006 needs per-call threading and the standalone binary loses unified derivation.
Context
Boundary + graph verified (.dependency-cruiser.cjs:15-22, package deps); schema is pure/fs-free (packages/schema, only parse5); resolveCorpusConfig is called from ~15 sites incl. the standalone binary (corpus/config.ts:119).
Decision
The pure project-id predicate + specResourceUri go in @spectastic/schema; loadProjectConfig/resolveProjectConfig go in corpus/config.ts, and resolveCorpusConfig gains a raw-project marketplace tier. Extracting a dedicated @spectastic/identity package is deferred until the surface (owner-config, federation URIs) proves the coupling.
Consequences
+ Every corpus-config caller unifies for free; + no new-package cost; + the shared primitive is reusable by the deferred MCP/federation specs. − The identity spans schema + corpus rather than one module (documented here).

D-002 · Derivation is write-time only; absence is the provisional state that firms up

Status
Accepted
Context
The common fresh-repo flow has no remote at init time; writeCorpusConfig already models create-or-merge / never-overwrite (init.ts:66-80), and GitRunner already bounds a git shell-out via injectable execFile (git/run.ts).
Decision
init's writeProjectConfig persists the owner-qualified id only when remoteOwnerRepo() confidently resolves one; otherwise it leaves project absent. resolveProjectConfig reads the persisted value and never re-derives live, falling back to basename(cwd) when absent (FR-003, NFR-001). A re-run after the remote appears firms it up, guarded by never-overwrite.
Consequences
+ No federation-fragile bare-dir value is ever locked in; + the read path is pure and deterministic; + firm-up needs no new command (a re-run of init). − An owner who never re-runs init stays on the provisional bare-dir coordinate (the collision warning is the nudge). − "Confidently resolves" must be defined narrowly (see the parser spike + §8 R1).

D-003 · spectastic id is a fat-core engine + thin CLI, main-CLI-only

Status
Accepted
Context
verify is the precedent: a deterministic command whose engine lives in @spectastic/core/commands with a thin register* wrapper (verify.ts:16-45). The standalone corpus binary has no specs/.
Decision
The id engine (resolve project → confirm specs/<id> exists → render the URI, erroring on an unknown spec, appending an optional anchor mechanically) lives in core; the CLI is a thin registerId. It registers only on the main CLI, not the standalone binary.
Consequences
+ Testable without spawning a binary; + consistent with every other deterministic verb. − One more core command module + one CLI registration (trivial).

D-004 · URI grammar: owner-as-authority

Status
Accepted
Context
A design choice, not an external fact — the spec left the <owner>/<repo> → URI mapping to the plan. MCP aggregators namespace resources by source; a DOI names a registrant authority.
Decision
The owner is the URI authority; repo + spec are the path: spectastic://<owner>/<repo>/spec/<id>#<anchor>. No percent-encoding, reads naturally, and composes with a future corpus URI (spectastic://<owner>/<repo>/corpus/…).
Consequences
+ Clean, extensible, encoding-free. − A project identity with no owner segment (the provisional bare-dir fallback) yields a single-segment authority with an empty repo path — acceptable for the warned provisional state, and the reason the collision warning exists.

D-005 · TDD, red-first

Status
Accepted
Context
The whole surface is deterministic fs/string logic over fixtures — the house discipline (047/048/065/066).
Decision
Write each requirement's test failing first, then implement. Fixtures: configs with/without project, an injected GitExec for the derivation, temp specs/ dirs for the id engine.
Consequences
+ The determinism (NFR-001) and precedence (FR-006) edges are pinned before the code. − None material.

8 · Risks & mitigations

RiskLikelihoodImpactMitigation
R1 · git-remote → owner/repo parsing is wrong for some hosts (Azure DevOps /_git/, GitLab subgroups) — the spike confirmed both.MLDefine "confidently resolves" narrowly (a clean host…/owner/repo(.git) shape); anything else counts as not resolved → leave project absent/provisional (D-002), never persist a wrong value. The owner can always set project by hand. Secure-by-default.
R2 · The provisional state is sticky — an owner never re-runs init, so the identity stays a bare-dir coordinate.MLThe validate warning (FR-007) is the standing nudge; the coordinate still works (degraded, unambiguous within the repo). A dedicated firm-up prompt is a possible fast-follow, not required for this slice.
R3 · Folding project into resolveCorpusConfig shifts an existing project's marketplace.LMproject slots below explicit marketplace/namespace in precedence, so any repo that set either is unaffected; only a repo relying on the bare-dir default AND with project set changes — the intended unification. A test pins the precedence.
R4 · The spectastic:// scheme defined here diverges from what the deferred MCP serving spec needs.LMOwner-as-authority (D-004) matches the MCP source-namespacing convention the survey grounded; the scheme is additive and the serving spec consumes it. Recorded as the identity/transport split in the spec's out-of-scope.

9 · Complexity tracking

The only non-obvious mechanic is the two-file placement of one concept (schema grammar + corpus reader). It is justified by the corpus↛core boundary and schema's purity (D-001): neither the pure grammar nor the fs reader can live in a single existing package that serves all consumers, and a new package for one field is not yet earned. Everything else clones an in-repo precedent (resolveCorpusConfig, verify, writeCorpusConfig, GitRunner).

"Confidently resolves a remote" is treated as a clean <host>[:/]<owner>/<repo>(.git)? match; atypical shapes (Azure /_git/, GitLab subgroups, self-hosted paths) are deliberately treated as unresolved and left provisional rather than guessed — a false provisional is cheap (a warning + a hand-set value), a wrong persisted identity is not.
