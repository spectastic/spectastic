Status Accepted Spec 067-spec-project-identity Plan plan Branch 067-spec-project-identity Created 29 Jul 2026 Read time

30 tasks across five phases. Setup → Foundational → User stories (US1 · US2 · US3) → Polish. Tasks marked [P] can run in parallel — different files, no dependency. Tests for a story MUST be written and failing before its implementation tasks start. The identity is placed by purity (plan D-001): pure grammar in @spectastic/schema, the fs reader in @spectastic/corpus, the id engine in @spectastic/core, git derivation confined to the CLI.

1 · Execution strategy

Story IDs follow the spec's numbering (T-1xx = US1, T-2xx = US2, T-3xx = US3) regardless of build order. Priorities are US1 = P1, US2 = P1, US3 = P2 — the recommended order below runs both P1 stories before the P2 validate story.

Setup → Foundational → US1 (declare identity, P1) → US2 (resolve coordinate + spectastic id, P1) → US3 (validate, P2) → Polish. US2 depends on US1's resolver existing (the id engine calls resolveProjectConfig), so this is the natural build order even though both are P1.

Setup → Foundational → US1 only → ship. A project can already declare and resolve its identity (in code, via resolveProjectConfig) — a viable substrate on its own. Add US2 (the visible spectastic id demo surface) and US3 (validate) as fast-follows.

Foundational must land first (both stories depend on the schema primitives). After that, US1 (init writer + GitRunner + corpus/config.ts) and US3 (the validate rule, which only needs schema's predicate, not US1's resolver) can run in parallel; US2 waits on US1's resolveProjectConfig landing.

The pure grammar + URI composer every story depends on: US1's resolver needs nothing from here directly, but US2's id engine and US3's validate rule both consume it — and per plan D-001 it is the one shared, reusable primitive (the citation-grammar precedent), so it is built once, first.

Write failing tests for the project-id grammar and URI composer — well-formed vs. malformed project ids (illegal characters, wrong shape), a bare-default (no owner segment) classified distinctly from an owner-qualified one, and specResourceUri composing spectastic://<owner>/<repo>/spec/<id> with and without a #<anchor>. packages/schema/test/project-shared.test.ts
Implement classifyProjectId and specResourceUri — the project-id shape classifier (a 3-way owner-qualified | bare | malformed, not a boolean — US3 needs the full split) and the owner-as-authority URI composer (plan D-004). packages/schema/src/project-shared.ts

No barrel re-export — ./project is the sole consumption path, exactly like ./citation/./slo/./fence (none of which are re-exported from schema's top-level index.ts either).
