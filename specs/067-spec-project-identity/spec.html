Spec project identity

Give a project a stable identity so a repo-local spec id becomes a federation-unique coordinate — the prefix specs lack that the corpus already has.

Status Accepted Spec ID 067-spec-project-identity Owner Brian Corbin · @briancorbinxyz Reviewers — Created 29 Jul 2026 Principlesv1.8.0 Smallest demoableA project identity in spectastic.json + spectastic id <spec> printing that spec's federation-unique spectastic:// resource URI. Read time

Spec ids are purely repo-local — every spectastic project starts at 000 and reuses the same 042 / REQ-* / T-* grammar, so across a multi-repo estate they collide with nothing to tell them apart. The corpus already solved this with a DOI-shaped prefix (corpus.marketplace); specs have no prefix at all. This spec gives a project a stable identity in spectastic.json, owner-qualified by default (derived once from the git remote), and resolves any spec to a canonical, federation-unique spectastic://<project>/spec/<id> resource URI via a new deterministic spectastic id command. The identity is unified — one coordinate qualifies both specs and the corpus. It is additive and non-breaking: repo-local ids are unchanged, and a project that sets nothing still works exactly as today. For anyone federating more than one spectastic repo behind a single index or orchestrator.

1 · Context

The corpus-extraction survey (docs/corpus-extraction-considerations.html, §5) surfaced a collision that only appears once a server or index fronts more than one repo: identity collides on two axes at once. Every spectastic repo has a spec 042, a REQ-FORMAT-004, a T-017; across repos they are not the same thing and there is nothing to distinguish them. Spec ids are purely repo-local — there is no namespace layer at all, and spectastic.json carries no project identity.

The corpus does not have this problem. It adopted the identifier world's canonical answer — a DOI: a namespace prefix plus a local suffix. Spectastic's corpus prefix is the marketplace; the durable cross-repo key is marketplace · plugin · slug @ edition, and KB-NNNN is only the repo-local suffix. So the corpus can be federated today with care. Specs cannot — because they carry no prefix at all. That missing prefix is this spec's entire subject: apply the same DOI move to the spec side.

Who it's for: anyone federating more than one spectastic repo — a multi-service estate served behind one query index or MCP surface, and (downstream, gated on this) an orchestrator that routes a new requirement to the service whose specs and corpus it most resembles. That federation surface is deferred; this spec builds the identity substrate it must stand on.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1 you would still have a viable MVP — a project that carries a stable, owner-qualified identity, even before anything resolves a coordinate from it.

US1 · A project declares its identity P1

As a maintainer of a spectastic repo, I want my project to carry a stable, owner-qualified identity so that its specs are distinguishable from an identically-numbered spec in any other repo.

Acceptance: spectastic init writes a top-level project field to spectastic.json, derived once from the git remote as an owner-qualified id (<owner>/<repo>); with no remote it falls back to the bare directory name. A single-source-of-truth resolver returns exactly that persisted value and never re-derives it live. An existing project value is never overwritten.

US2 · A spec resolves to a federation-unique coordinate P1

As a consumer federating several repos, I want each spec to resolve to a globally-unambiguous resource URI so that I can address 042 in one repo without it colliding with 042 in another.

Acceptance: spectastic id 042 prints the canonical spectastic://<project>/spec/042 resource URI; an optional requirement/task anchor appends as spectastic://<project>/spec/042#REQ-FORMAT-004. The command errors on a spec id that does not exist under specs/. Re-running yields byte-identical output. The repo-local id (042) is unchanged everywhere it is used today — the coordinate is additive.

US3 · The identity is validated P2

As a maintainer preparing to federate, I want validate to catch a broken or collision-prone identity so that a typo'd or bare-default project id doesn't silently mint a wrong or ambiguous coordinate.

Acceptance: a malformed project (illegal characters / wrong shape) is a validate error; a bare, unqualified default (no owner segment — the no-remote fallback) is a warning naming the fix; an absent project is neither (single-repo back-compat). A well-formed owner-qualified identity yields no finding.

Edge cases

  • A repo with no git remote at init time (the common fresh-repo case) — init leaves project absent (provisional); coordinates degrade to the bare directory name and validate warns it is collision-prone (never blocks). Adding the remote and re-running init firms up the owner-qualified identity.
  • A repo whose remote is renamed or forked after the identity is firmed up — the persisted project is unchanged, so a spec's coordinate never silently shifts (the reason derivation is write-time, not read-time).
  • A project that publishes a corpus pack under a marketplace name that genuinely differs from its project identity — an explicit corpus.marketplace still wins over the unified default.
  • A repo that sets nothing (project absent) — every verb behaves exactly as today; a coordinate degrades to the bare id with the collision warning, never a crash.
  • An anchor that names a requirement/task not present in the spec — the coordinate is still emitted (mechanical append); anchor-existence checking is out of scope.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

spectastic.json MUST support a top-level project identity field, and a single single-source-of-truth resolver MUST be the only path any consumer reads it through — so no two callers can derive a different value.

Rationale

The DOI prefix specs lack. Mirrors 063's resolveCorpusConfig single-authority pattern exactly, so config identity is never re-derived independently.

spectastic init MUST persist an owner-qualified identity (<owner>/<repo>) to spectastic.json only when the git remote resolves one; when no remote is available it MUST leave project absent (provisional) rather than persist a bare directory name. Re-running init after a remote becomes available MUST firm up the identity — deriving and persisting it — and MUST NOT overwrite a project value already set (by a person or a prior firm-up).

Rationale

The common fresh-repo flow is git init → spectastic init → remote added later, so a remote is usually absent at init time. Persisting a bare dir name then would lock in a federation-fragile value and fire the collision warning on nearly every new repo; leaving it absent keeps the door open to firm up an owner-qualified identity once the remote exists — without ever clobbering a deliberate value. Create-or-merge, never-overwrite mirrors writeCorpusConfig.

The resolver MUST read the persisted project value and MUST NOT re-derive it from the git remote (or any other live environment source) at read time. When project is absent (the provisional state), it MUST fall back deterministically to the bare directory name.

Rationale

A federation key must be stable. Live re-derivation would let a fork, a remote rename, or a missing remote silently shift a spec's coordinate — the determinism hazard NFR-001 forbids. Derivation is confined to init's write path (FR-002); read is pure.

A spec MUST resolve to a canonical, federation-unique resource URI of the form spectastic://<project>/spec/<spec-id>, qualified by the project identity and the repo-local spec id, with an optional #<anchor> fragment for a requirement or task. The repo-local spec id MUST remain unchanged everywhere it is used today (additive, non-breaking).

Rationale

The spectastic:// scheme is defined here; the MCP server that serves these URIs as resources — and cross-repo aggregation — is the deferred transport concern. The precise owner/repo → authority/path encoding is the plan's (D-002 open detail).

A deterministic spectastic id <spec> command MUST print the qualified resource URI for a given spec, MUST accept an optional anchor and append it mechanically, and MUST error on a spec id absent from specs/. It is a read-only utility, not a lifecycle verb — the eight AI lifecycle commands are unchanged.

The identity MUST be unified: when corpus.marketplace is unset it MUST derive from project, so a single coordinate qualifies both specs and the corpus. An explicit corpus.marketplace (or the deprecated corpus.namespace alias) MUST still take precedence, preserving the publish-identity-differs-from-project escape hatch.

Rationale

Survey D-002's "leaning unified": one thing for an orchestrator to route to, and the owner-qualified prefix becomes the single load-bearing primitive. The escape hatch keeps 062/063's "published pack ≠ this repo" fidelity intact. Resolution precedence: explicit corpus.marketplace → corpus.namespace → project → bare dir name.

spectastic validate SHOULD emit a validate error for a malformed project (illegal characters or wrong shape) and a warning for a bare, unqualified default (no owner segment) that is collision-prone; an absent project SHOULD yield no finding.

Rationale

Malformed-errors mirrors the corpus id-shape rules; the collision warning mirrors 061's identity-fragmentation posture. The true cross-repo collision check needs the whole estate and is deferred to the federation surface.

Non-functional

Coordinate resolution MUST be deterministic: given a fixed spectastic.json, the resolver and spectastic id MUST return byte-identical output across runs, with no dependency on the live git remote, the clock, or environment state at read time. Git-remote derivation happens only at init/write time.

The change MUST be non-breaking: no existing spec.html/design.html/tasks.html artifact and no repo-local id changes, and a project with no project field MUST behave exactly as it does today (graceful absence — every verb unchanged, no crash).

The command's --help and any diagnostic copy SHOULD carry no internal artifact id (P-10) — say what the command does, not which spec added it.

Out of scope (deferred to other slices)

  • The MCP server that serves these spectastic:// URIs as resources, and cross-repo aggregation / multiplexing. This spec defines the URI scheme; that spec owns the transport.
  • Exposing the specs/ estate over MCP (the specs half of the read-path). Consumes this spec's coordinate; does not define it.
  • The requirement→owning-service router (semantic CODEOWNERS). The forward-look this identity substrate exists for; gated behind the whole federation surface, human-confirmed.
  • Explicit owner/org config fields and org-level identity policy beyond the git-remote-derived default. This spec provides the owner-qualified default; the fuller owner/org surface remains its own concern.
  • Rendering corpus resources as spectastic:// URIs. This spec unifies the identity at the config layer (FR-006); the corpus resource-URI form ships with the serving surface.
  • Anchor-existence checking (that #REQ-* names a real requirement). The coordinate appends the anchor mechanically; validating it belongs with the query/read path.

4 · Data model

No new persisted store — one new config field and one derived value. The change is a coordinate and its derivation, not a new entity.

Entities

Project identity
The top-level project string in spectastic.json — an owner-qualified id (<owner>/<repo> by default), persisted once at init. The DOI-style prefix that qualifies every spec (and, unified, the corpus) in this repo.
Spec resource URI
The federation-unique coordinate a spec resolves to: spectastic://<project>/spec/<spec-id>, with an optional #<anchor>. Composed from the persisted project identity and the unchanged repo-local spec id — never stored in the artifact, always derived.

Invariant: the coordinate is identity-prefixed, id-preserving — the repo-local spec id is stable and untouched; the project identity is the only thing that makes it globally unambiguous, and it is resolved deterministically from persisted config, never from live environment state.

5 · Success criteria

Technology-agnostic, measurable outcomes.

Two repos with distinct owner-qualified project identities each carrying a spec 042 resolve to two distinct spectastic:// resource URIs — no collision — verifiable by resolving both against their fixture configs.

spectastic id 042 in a configured repo prints a stable, federation-unique resource URI; re-running yields byte-identical output and consults no live git remote or clock (determinism, NFR-001).

A repo with no project set authors, validates, and implements specs exactly as before (no behavioural change); a resolved coordinate degrades to the bare directory name and validate warns it is collision-prone — never an error, never a crash.

With project set and corpus.marketplace unset, a corpus citation coordinate and a spec resource URI share the same project authority (unified); setting an explicit corpus.marketplace overrides it for the corpus while the spec coordinate keeps the project identity.

Validating a project whose project is malformed yields a validate error; one whose project is a bare unqualified default yields a warning; a well-formed owner-qualified identity yields neither — all observable against fixture configs.

6 · Assumptions

The git remote is readable at init time for the common case; when it is not, the bare-directory-name fallback plus the collision warning is an acceptable degraded default (the owner can set project by hand). Derivation is a bounded shell-out, never a network call.

resolveCorpusConfig (063) is the pattern the project-identity resolver clones, and the corpus config's marketplace precedence can absorb project as a new fallback tier without disturbing the existing marketplace → namespace chain.

The exact encoding of an owner-qualified <owner>/<repo> identity into the spectastic:// URI's authority-versus-path components is a plan-level decision; the spec fixes only that the coordinate is canonical, federation-unique, and project-qualified.

7 · Open questions

None outstanding — the smallest demoable (field + resolver + spectastic id CLI), the unified-vs-parallel fork (unified, marketplace derives from project), the owner-qualified git-remote default, the persist-at-init determinism model, the additive non-breaking migration, the full-spectastic://-URI scope, and the validation severities were all anchored in the interview. The corpus resource-URI form and the MCP serving surface are deferred, not undecided.
