Cards

FR-002's identity firm-up is specified and unreachable

Implementation code

Debugging why a project stayed unidentified after its remote was added, root cause was that init refuses to run on a populated directory without a TTY, so the firm-up path FR-002 requires can never be taken; fixed in the command's re-run guard, not in the requirement; regeneration passes, because the requirement already says plainly what should happen.

Expected
FR-002: "Re-running init after a remote becomes available MUST firm up the identity — deriving and persisting it."
Actual
Re-running it prints init: 30 existing file(s) in destination but no TTY for prompts; pass --force to overwrite or remove the files first. and exits without writing. --force is not a fix — it overwrites the scaffold. No other command writes the value: spectastic owner answers a different question and spectastic id only reads. The user must hand-edit spectastic.json.
Diagnosis
The re-run guard exists to protect a scaffold from being clobbered and cannot distinguish "re-scaffold everything" from "firm up one config value". The requirement is right; the only path to it is gated behind a prompt that a scripted or non-interactive run never gets. Observed end-to-end while scaffolding a real downstream project: git init → spectastic init → remote added → firm-up impossible, which is the exact sequence FR-002's own rationale calls "the common fresh-repo flow".
Fix
packages/cli/src/commands/init.ts — let the identity firm-up run without the full scaffold, or give it a path of its own that is not gated on the overwrite prompt. The never-overwrite guard on the value itself already exists and is unaffected.
Deep dive — why this is implementation and not spec

The ladder stops here. Changing only the requirement would not help — it already mandates the behaviour. Changing only the resolver would not help — it reads correctly. The gap is that the one writer is unreachable in the flow the requirement was written for, which is a code fix that passes the regeneration test: an implementer reading FR-002 today would build the firm-up, and would then have to notice the guard swallows it.

A bare marketplace is persisted on the very path FR-002 avoids persisting a bare project

Design upstream

Debugging why a freshly scaffolded project fails its own first validate, root cause was that writeCorpusConfig falls back to the bare directory name when no project exists — persisting exactly the federation-fragile value FR-002 refuses to persist, one function later; fixed by leaving the marketplace absent when the identity is absent; regeneration fails, because the two writers' interaction is not described anywhere.

Expected
A freshly scaffolded project validates clean, and a later identity firm-up takes effect.
Actual
spectastic init on a repo with no remote leaves project absent, correctly — and then writes corpus.marketplace: "<dir-name>". The first validate reports "The resolved corpus marketplace has no owner segment — a bare, collision-prone default". Reproduced on a real scaffold; the warning is the new project's first output.
Diagnosis
FR-002's rationale says persisting a bare name "would lock in a federation-fragile value and fire the collision warning on nearly every new repo" — and that is precisely what happens, through the other writer. Worse, writeCorpusConfig's own docstring records that an explicit corpus.marketplace "ALWAYS wins in resolveCorpusConfig's precedence chain", so the bare value permanently shadows any identity a later firm-up would set. That docstring names this exact bug — it was found and fixed for the has-a-remote case, and the no-remote path still does it.
Fix
packages/cli/src/commands/init.ts — when resolveProjectConfig yields no project, omit marketplace and let resolveCorpusConfig's derivation supply it later, rather than freezing a directory name into the file. Pairs with T-001: firm-up is worthless while a bare marketplace outranks it.
Deep dive — cross-spec

Two specs' writers disagree about the same identity. 067 owns project and refuses a bare value; the corpus config owns marketplace and supplies one. Unifying them was 067's stated purpose, so this belongs to 067's design rather than to the corpus slice — the unification is incomplete in exactly the case 067 called common.
