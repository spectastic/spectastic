Change proposal · 082-placement-verdict

Structural evidence is relative, not a popularity count

The most-depended-upon unit won every placement, for every requirement. And nothing could have caught it, because there was no command to run.

Status Applied Change ID 2026-08-02-structural-evidence-is-relative Spec 082-placement-verdict Source Dogfooding 082 against this repository, 02 Aug 2026 Author Brian Corbin · @briancorbinxyz Created 02 Aug 2026 Targets 2 added (FR-010, FR-011) Read time

Dogfooding 082 on this repository produced the same answer for every requirement tried — a CLI bug, a corpus bug, a styling bug — all placed at @spectastic/schema, scoring an identical 40.0 on structural evidence alone. The cause is that structural evidence was gathered as one finding per inbound edge, so the most-depended-upon unit accumulates the most points regardless of what the requirement says. That is a popularity count, not a placement signal, and it defeats the property the whole slice exists for: structural evidence was so mis-measured that it swamped resemblance in every case — the inverse of the failure the survey warned about, arriving through the same door. This adds FR-010, making structural evidence relative to the candidates a requirement actually implicates rather than an absolute measure, and FR-011, a read-only command — because the reason this survived the test suite is that there was nothing to run.

Structural evidence is relative, not a popularity count

Applied

1 · Intent

082 shipped with 16 passing tests, including the headline case: a requirement in a consumer's vocabulary, with a structural edge to the producer, ranks the producer first. Run against this repository, it produces this — four times, for four unrelated requirements:

requirement: "the units command prints edges without their verification marks"
   40.0  @spectastic/schema     structural

requirement: "corpus citation provenance is not resolving edition pins"
   40.0  @spectastic/schema     structural

requirement: "the init command bootstraps the wrong profile"
   40.0  @spectastic/schema     structural

requirement: "typography and colour tokens in the canvas are cropped"
   40.0  @spectastic/schema     structural

The score is identical because the requirement is not an input to it. Evidence gathering pushes one structural finding per inbound edge: @spectastic/schema has four dependants, so it accumulates four findings at full strength and wins permanently. The comment justifying it read "a unit others are built on is a likelier owner of a shared change" — defensible for a change already known to be shared, and simply wrong as a general prior, because it never consults the requirement.

Two things make this worth a requirement rather than a quiet patch. First, the regeneration test fails: nothing in 082 says structural evidence is relative, so a future session reading the spec would implement the same absolute count again. Second, it inverts the slice's own purpose. FR-003 requires structural evidence to be able to outrank resemblance; here it outranks everything unconditionally, which is not the guarantee FR-003 wanted but its caricature.

The reason it survived is separable and worth naming. Every test used a hand-built two-candidate fixture in which the producer had exactly one inbound edge. The asymmetry only appears at real fan-in, and there was no way to reach real fan-in, because 082 shipped no command. Its verify.html records the demo as "rankPlacement on the producer/consumer fixture" — a description of a function, not something a person can run. A slice whose only entry point is its own test suite cannot be dogfooded, and this defect is what that costs.

2 · Scope

In scope

  • Structural evidence stated as a relation between candidates the requirement implicates, not an absolute property of a unit.
  • A read-only command, so the engine can be run against a real estate rather than only its fixtures.
  • A fixture with realistic fan-in, since the two-candidate shape is what hid this.

Out of scope

  • Re-weighting the classes. The weights are not the defect — the measurement was. Tuning stays TBD-placement-calibration.
  • The optional model refinement. Unchanged, and still opt-in.
  • Any change to the two refusals, the bands, or the evidence vocabulary.
  • Whether a verify.html demo should be required to be executable at all — the general question this defect is one instance of. Its own survey.

3 · Approach

The fix follows from what structural evidence can honestly know. Gathering sees a requirement as prose and a graph of units. It cannot tell from the graph alone which units a requirement concerns — only the other evidence classes can implicate a candidate. So structural evidence is not an independent score at all: it is a re-ranking signal over candidates something else has implicated, answering "of the units this requirement might touch, which sits upstream of the others?"

That reading preserves the headline case exactly. The requirement resembles the consumer, so the consumer is implicated by domain evidence; the producer is upstream of an implicated candidate, so the producer earns structural evidence and outranks. And it fixes the repository case: @spectastic/schema has four dependants, but for "typography and colour tokens in the canvas" none of them is implicated, so it earns nothing.

One finding per unit rather than per edge, with strength scaled by how many implicated candidates it is upstream of. A unit upstream of every implicated candidate is a stronger signal than one upstream of a single candidate — but the difference is bounded, rather than growing without limit as a project's fan-in grows.

4 · Deltas

Two additions. FR-003 is unchanged: its precedence claim was right, and it was the measurement beneath it that was wrong.

Structural evidence MUST be relative to the candidates a requirement implicates, never an absolute property of a unit: a unit earns it only where it stands upstream of another candidate that other evidence has implicated, and earns at most one finding regardless of how many edges point at it.

Rationale

Gathered as one finding per inbound edge, structural evidence became a popularity count: the most-depended-upon unit accumulated the most points and won every placement identically, for every requirement — verified against four unrelated requirements on this repository, all scoring 40.0 at the same unit. That inverts FR-003, which requires structural evidence to be able to outrank resemblance rather than to outrank everything unconditionally. The requirement is stated rather than left to the design because the regeneration test fails without it: nothing in this spec said the signal was relative, so the same absolute count would be implemented again.

A read-only command SHOULD produce a verdict for a requirement against the current project, printing each ranked candidate with its evidence classes, the confidence band, any hedge, and any conflict.

Rationale

The defect FR-010 corrects survived a full test suite because every fixture was a hand-built two-candidate case where the producer had exactly one inbound edge — and real fan-in was unreachable, because the slice had no entry point. Its verify.html recorded the demo as a function name and a fixture, which is grounded and unrunnable. A slice whose only caller is its own tests cannot be dogfooded, and a command is what makes the difference between a passing suite and a checked answer.

5 · Risk register

The proposal adds a must-tier requirement, so the adversarial pass applies. Three findings.

Making structural evidence depend on other classes means a project with no domain or declared evidence gets no structural evidence either — so a requirement whose words match nothing produces no candidates at all, and the engine abstains where it previously answered.

"a unit earns it only where it stands upstream of another candidate that other evidence has implicated"

Correct, and the right outcome. Previously it "answered" by naming whichever unit was most depended upon, which was not an answer at all. Abstention with reasons is FR-005's first-class state and exists precisely so the engine is never forced to name a plausible-but-wrong unit. Accepted knowingly: the abstention rate becoming visible is a feature of the fix, and the spec already records that watching it needs real use.

The same two-candidate fixtures that hid the defect would pass unchanged after the fix, so nothing stops it recurring.

"earns at most one finding regardless of how many edges point at it"

The sharpest finding, because it is about the test suite rather than the code. Mitigated by a fixture with realistic fan-in — several units depending on one — asserting that the shared dependency does not win a requirement unrelated to any of them. That case is the whole defect, and no test expressed it.

A command over a signal whose weights are admittedly uncalibrated invites a reader to trust output that has never been measured against a confirmed placement.

"printing each ranked candidate with its evidence classes, the confidence band, any hedge, and any conflict"

Real, and the reason the output prints classes, band, hedge and conflict rather than a bare winner. A reader shown "structural, domain — medium, hedged, and these two disagree" is being handed a case to check, which is what FR-001 requires and what P-14 says is the most this can honestly be. Accepted: the alternative — no command — is what produced this proposal.

None outstanding. The verb's name was anchored by the author — owner, because the command and the verdict's own no confident owner state share a vocabulary, and because asking who owns something invites "nobody confidently" in a way that place or route do not.
