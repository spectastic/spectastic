Specification · 103-content-budgets

Copy is part of the spec

A layout survives a heading of four words and breaks at fourteen, and nothing anywhere records which it was designed for.

Status Accepted Spec ID 103-content-budgets Owner Brian Corbin · @briancorbinxyz Reviewers — Created 13 Aug 2026 Principlesv1.9.0 Smallest demoableOne screen declaring a character budget for its heading and its error line, and the strings the product refuses to ship. Read time

The annotation vocabulary names content as a category with no accessibility analogue and homes it nowhere — an honest gap, planted with no slug and left. But copy is the input a layout is most sensitive to and the one most often supplied last, by someone who never saw the design. This gives it a home: a budget per element class, the voice rules a product holds itself to, the strings it refuses to ship, and the shape of an error message. All of it prose-typed and unchecked against a running build, because that is the honest ceiling.

1 · Context

The annotation layer maps eight categories onto existing vocabulary and finds a home for six. Two are recorded as genuine gaps, and content is the one that was then planted nowhere — no slug, no spec, no follow-up. It has stayed a gap by omission rather than by decision.

What is missing is not decoration. A layout is designed against copy of a particular length, and the copy usually arrives later from someone who never saw the layout. A heading budgeted at forty characters and supplied at ninety does not degrade — it wraps, pushes, and breaks the thing beneath it. The number is a real design decision and it is currently held in one person's head.

The other half is what a product refuses to say. Every team has strings it will not ship — a raw error code shown to a user, an apology that explains nothing — and that list is enforced by whoever happens to review the pull request. Writing it down does not enforce it either, but it makes the review possible.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · An element carries a budget P1

As a writer, I want to know the character budget of the thing I am writing into so that I find the limit before the layout does.

Acceptance: A screen can declare a budget for a class of element; the budget is a number with a unit; a declared budget carrying no number is reported.

US2 · A product records what it will not say P2

As a reviewer, I want to see the strings this product refuses to ship so that the rule is reviewable rather than remembered.

Acceptance: A project can declare refused strings with a reason; the list is readable without running anything.

US3 · An error message has a declared shape P3

As an author, I want to state what an error message must contain so that "something went wrong" is visibly not the shape.

Acceptance: A project can declare the parts an error message carries; a screen's error state can reference that shape rather than restating it.

Edge cases

  • A language where a character count is the wrong unit, and a product that will be translated.
  • A budget on an element that legitimately varies — a list item, a user-supplied name.
  • A refused string that is legitimate in one context and not another.
  • A project with no copy decisions worth recording at all.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A budget MUST be declarable for a class of element rather than for one instance, and MUST carry a number and the unit it counts.

Rationale

Per class because the decision is "a card title is short", not "this card title is short" — an instance budget would be a hundred copies of one rule. The unit is required because characters and words give different answers and a bare number silently picks one.

A declared budget with no number, or with no unit, MUST be reported.

Rationale

A budget that says "short" records an opinion and constrains nothing. This is the same rule the size gauge already applies to itself.

A budget MUST be treated as a design constraint and MUST NOT be checked against any running text.

Rationale

The honest ceiling, stated rather than discovered. The copy this constrains lives in a localisation system, a database or a person's draft, none of which this vocabulary can see — and a check that read only the strings it could reach would report a clean result while the real copy overflowed.

A budget MUST be able to record that it applies to a source language only.

Rationale

A German translation runs a third longer than English and a character budget that ignores that is wrong in the language nobody checked. Recording the scope does not solve translation; it stops the number claiming more than it means.

A project MUST be able to declare strings it refuses to ship, each with a reason.

Rationale

A refusal without a reason is a list somebody will delete the first time it is inconvenient. The reason is what survives a change of team.

A refused string MUST be able to record the context it is refused in, rather than being refused everywhere by default.

Rationale

"Error" is unacceptable to a user and perfectly fine in a log line. A blanket refusal would be either wrong or ignored, and ignored is the likelier of the two.

A project SHOULD be able to declare the parts an error message carries, and a screen's state SHOULD be able to reference that shape rather than restating it.

Rationale

The reference rule the annotation already follows. A shape restated per screen is a shape that diverges per screen.

Voice guidance SHOULD be declarable as prose and SHOULD NOT be given a structured form.

Rationale

The part of this that genuinely is not machine-readable. "Plain, never chirpy" resists structure, and inventing one would produce a schema nobody can satisfy and a check nobody can write — the tenth-taxonomy mistake this family has already refused once.

A project MAY declare no budgets, refusals or voice at all, and that MAY NOT be reported.

Rationale

Most projects have no copy decisions worth recording, and this family has already paid once for seeding a vocabulary into a population that could not answer it.

A budget MAY be declared on an element whose content varies beyond the project's control, and such a budget MAY record that it is a design target rather than a limit.

Non-functional

Every declared budget, refusal and voice note MUST render with scripting disabled: 100% of the authored content readable with JavaScript off.

The shape check MUST be pure: at most 1 pass over the document, 0 filesystem reads, and byte-identical findings across at least 3 runs.

Out of scope (deferred to other slices)

  • Checking real copy against a declared budget. It needs a source of strings this vocabulary cannot see, and the check would report clean on the strings it could reach while the rest overflowed.
  • Measuring rendered text against a budget in a running build, which is a different instrument.
  • Rendering budgets inside the design.
  • Importing copy decks from a design tool.

4 · Data model

Three declarations, none persisted, none checked against running text.

Entities

Budget
A number and a unit, for a class of element rather than an instance. Optionally scoped to a source language. A budget with no number is invalid — "short" is an opinion.
Refusal
A string the product will not ship, with a reason and optionally the context it is refused in. Refused everywhere is a choice, not the default.
Message shape
The parts an error message carries. Declared once at project scope, referenced by the states that use it.

The ceiling, stated here rather than left to be discovered: none of this is checked against real copy. The strings live in a localisation system or a person's draft, and a check that read only what it could reach would report clean while the rest overflowed — a false negative that reads as diligence.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For a screen declaring budgets, a writer can state the limit for each budgeted element class from the declaration alone, opening 0 other files.

Declared budgets carrying no number or no unit number 0, or each produces exactly 1 finding.

Projects declaring no copy decisions produce 0 findings about their absence, counted across every project artifact.

Refusals carrying no reason number 0.

6 · Assumptions

Characters are the useful unit for most budgets. Assumed from how design tools express them rather than measured, and FR-001 requires the unit precisely so a project that disagrees can say words instead without the number changing meaning silently.

A written refusal list changes reviews even though nothing enforces it. Unverified, and the honest counter-argument is that an unenforced list decays. FR-005's required reason is the hedge: a rule with a reason survives the review where a bare list does not.

7 · Open questions

None outstanding. The decision worth recording is that voice guidance stays prose. It is the part of this that genuinely resists structure, and giving it a schema would produce one nobody can satisfy and a check nobody can write — the tenth-taxonomy mistake this family already refused once.
