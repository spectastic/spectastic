corpus convert — document conversion into the corpus

A converter-agnostic corpus convert that shells out to a user-installed tool, turning a PDF (or any format the converter handles) into a provenance-stamped corpus document — no bundled runtime.

1 · Context

Curated corpora start as documents, and documents arrive as PDFs. The spectastic kernel descoped PDF conversion permanently (TBD-never, specs 051/056) for a single principled reason: the kernel stays Node-only, and every serious PDF-to-markdown converter is a Python or GPU tool. That ground disappears once the corpus is its own package — 064 extracted @spectastic/corpus with a standalone spectastic-corpus binary, usable with no SDD lifecycle present. A standalone curation tool that cannot ingest a PDF is missing the front door.

The 2026 landscape has three de-facto open-source converters and no universal winner — MarkItDown (fast, shallow, no GPU), Docling (structure-preserving), Marker (highest fidelity, GPU). That variance is the design cue: the tool must not marry one converter. The corpus-extraction survey (§6, D-003) landed the shape this spec builds — a convert subcommand that shells out to whichever converter the user installed and feeds the markdown into the provenance-stamping adapt path. It serves anyone building a corpus from source documents — a spectastic project or a standalone spectastic-corpus user with no specs/ at all.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Convert a PDF into a pack P1

As a corpus curator, I want to run one command that turns a PDF into a filed, cited corpus document so that a document that arrived as a PDF is usable knowledge without hand-transcription.

Acceptance: with MarkItDown on PATH, corpus convert paper.pdf --pack research converts the PDF, files the markdown under knowledge/research/references/ with allocated KB-NNN id and full frontmatter, and reports the written id — the same terminal state as an adapt of that markdown, reached in one step.

US2 · Choose the converter P2

As a curator with structure-heavy or scanned sources, I want to select Docling or Marker instead of the default so that I can trade speed for fidelity when the source demands it.

Acceptance: --converter docling and --converter marker invoke the named binary; the recorded provenance names the converter actually used. An unrecognised --converter value is rejected before any conversion runs.

US3 · Attributable provenance P1

As a reviewer citing a converted document, I want the provenance to record which converter ran and to pin the original source so that a bad or disputed conversion is attributable to its source and tool.

Acceptance: a converted document's frontmatter carries converter (tool + version), origin (the source filename), and a content-hash that is the SHA-256 of the original source file's bytes — so re-converting the same PDF is detectable, and a converter upgrade that changes the markdown never silently rewrites what the hash pinned.

Edge cases

  • The chosen converter isn't installed → non-zero exit with a copy-paste install line; nothing written to the pack.
  • The converter runs but exits non-zero (corrupt/encrypted PDF) → its stderr is surfaced; no partial document is filed.
  • The source file has already been converted into the pack (same filename) → idempotent, per adapt's non-destructive rule; the existing document is left untouched.
  • A non-derivable provenance field (edition, license) stays the literal TODO — conversion never fabricates it.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The corpus tool MUST provide a convert <file> verb that converts a source document to markdown via an external converter and, given a target pack, registers the result through the two-layer corpus backbone — the same path import/interview/source use. It MUST allocate a repo-unique KB-NNNN row in the root knowledge/index.md registry, write the document at references/<NNN-slug>.md carrying a slug: (never a document id:), create or extend the pack's SKILL.md, and keep marketplace.json in sync — never the legacy single-layer pack-index shape. The backbone MUST carry convert's own provenance per FR-004 (converter, source-bytes content-hash, not-yet-spot-checked status).

Rationale

A converted document must be a first-class, registry-cited artifact — resolvable by the registry (062 FR-006), not only via the deprecated pack-scan fallback. The prior "adapt provenance path … pack index" wording produced a single-layer, registry-invisible pack (T-001).

The verb MUST default to the MarkItDown converter and MUST accept a --converter <name> option selecting one of a documented set (MarkItDown, Docling, Marker); an unrecognised name MUST be rejected before any conversion runs.

The tool MUST NOT bundle or install a converter. It MUST invoke a user-installed binary found on PATH; when the chosen converter is absent, it MUST exit non-zero with an actionable install hint and MUST NOT write any partial output to the pack.

Rationale

Per D-003 — closes TBD-never without a Python/GPU runtime, keeps the Node-only spirit of distribution, and stays converter-agnostic so the tool tracks the field instead of betting on one binary.

A filed converted document's provenance MUST record the converter used (tool and version) and set content-hash to the SHA-256 of the original source file's bytes, not the converted markdown; origin MUST record the source filename. Fields not derivable from the source MUST remain the literal TODO (056's never-fabricate rule).

The verb SHOULD support a --no-adapt mode that emits the converted markdown (to a file or stdout) without filing it into a pack, for users who want to inspect or hand-place the output. In this mode no pack is required and none is modified.

The verb SHOULD accept any source format the chosen converter supports (e.g. PDF, DOCX, PPTX, XLSX, HTML, images for MarkItDown), delegating format capability to the converter and surfacing the converter's own error when a format is unsupported.

The convert verb SHOULD accept optional --title and --description options that set the registered document's title and description directly. Absent a --title and a derivable heading, it SHOULD fall back to the humanised source-filename stem (e.g. dodbook.pdf → "Dodbook") rather than a fixed "Converted: <stem>" placeholder.

Rationale

Auto-deriving a title/description from converted PDF text (first heading + first paragraph) is frequently a cover-page artifact or a page number; the author needs an override, and the filename is a better default than a fixed placeholder (T-002).

Non-functional

The shell-out MUST be injection-safe: converter and source arguments are passed as an argv array to a non-shell process spawn, never interpolated into a shell command string. Given identical converter output, the filed result MUST be deterministic.

The feature SHOULD add no Python, GPU, or non-Node runtime dependency to the tool's own distribution; the converter is a documented user prerequisite, surfaced in --help and the missing-binary hint.

Out of scope (deferred to other slices)

  • Batch/directory conversion — converting a folder of PDFs in one invocation. The first slice is one file per call.
  • Conversion-quality scoring or OCR-confidence surfacing — the tool records which converter ran, not how well it did.
  • Serving converted documents over the MCP read path — unrelated retrieval surface.

4 · Data model

This feature adds no new persisted entity — a converted document is a corpus document (051/056's frontmatter + index shape). It introduces two conceptual roles at conversion time.

Entities

Converted document
The derived markdown filed into a pack, plus its provenance: origin = source filename, converter = tool + version, content-hash = SHA-256 of the source bytes, status = TODO until spot-checked. Otherwise identical to any adapted document.
Converter adapter
A named external binary (MarkItDown / Docling / Marker) the tool invokes as an argv process and does not own. Identified by name, resolved on PATH, its version captured for provenance.

Invariant: content-hash pins the input, not the stored output. This is a deliberate departure from plain adapt (which hashes the markdown it stores) — for a converted document the markdown is derived and converter-version-dependent, so hashing the immutable source is the faithful provenance.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

With a converter installed, a single corpus convert <file> --pack <name> invocation leaves the pack containing a new cited document whose content-hash equals the SHA-256 of the source file and whose converter field names the tool used — verifiable by re-hashing the source and reading the frontmatter.

Running convert with the chosen converter not installed exits non-zero, prints an install command for that converter, and leaves the pack byte-for-byte unchanged (no partial write).

--converter docling and --converter marker route to their respective binaries and the filed provenance records which converter ran; an unrecognised converter name is rejected with a non-zero exit before any binary is invoked.

--no-adapt produces converted markdown output identical to what would have been filed, without creating or modifying any pack or index.

6 · Assumptions

Each documented converter (MarkItDown, Docling, Marker) exposes a command-line invocation that reads a source file and emits markdown to a file or stdout — confirmed for MarkItDown (markitdown <file>) and the plan will verify the Docling/Marker invocation shapes as a grounding step.

A converter's version is capturable via its --version (or equivalent); where a converter offers none, the converter field records the name and the literal TODO for the version rather than fabricating one. The existing free-form content-hash field carries the source-bytes hash with no schema change (no consumer asserts it hashes the stored file specifically).

7 · Open questions

None outstanding — the smallest-demoable boundary (full multi-converter slice with auto-adapt), format scope (any the converter handles), hash target (source bytes), converter selection (explicit --converter flag, MarkItDown default, hard-fail on absence), and the --no-adapt raw-emit mode were all anchored in the interview.
