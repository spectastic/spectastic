Defects against the 065-corpus-pdf-convert spec. Cards append-only; IDs stable.

Spec 065-corpus-pdf-convert Created 27 Jul 2026 Read time

Dogfooding corpus convert on a real PDF (in a freshly-inited project) surfaced that it files a legacy, registry-invisible document rather than a well-formed two-layer pack. Three cards: T-001 the root cause (spec-layer — FR-001 named the wrong filing primitive), T-002 weak title/description on converted docs, T-003 the corpus validator's blind spot that let the malformed pack ship clean. See examples/triage-log.html for the format.

Cards

convert files a legacy single-layer document via the adapt path, never registering it in the two-layer corpus

Spec upstream

Debugging a converted PDF that produced an incomplete pack, root cause was a spec-layer contract error — FR-001 specified "the existing adapt provenance path — allocating a KB-NNN id, writing frontmatter, and updating the pack index," which is the pre-062 single-layer 056-era primitive, so fileConvertedDocument faithfully produced a legacy pack (id-in-frontmatter, no root-registry row, no SKILL.md, no slug, a stray pack index); fixed by respecifying FR-001 to register through the two-layer registerDocument backbone; regeneration fails at implementation and plan (both correctly carried out FR-001) — only a spec change makes a faithful build produce a citable two-layer document.

Expected
convert yields the same well-formed two-layer artifact as import/interview/source: a slug: NNN-name document at references/NNN-slug.md, a KB-NNNN row in the root knowledge/index.md registry, a pack SKILL.md with the slug-map, and marketplace.json synced.
Actual
The 056-era legacy shape: doc frontmatter carries id: KB-001 (single-layer), the file is references/dodbook.md (no NNN- slug), a stray pack-local index.md is written, no SKILL.md is created, and the root registry is left empty. get KB-001 resolves only via the deprecated pack-scan fallback (052 FR-003) and only at @TODO edition — an edition-pinned citation never resolves, and the doc vanishes once TBD-resolver-registry-only deletes the fallback.
Diagnosis
fileConvertedDocument (packages/corpus/src/knowledge/adapt.ts) was built on adaptFolder's legacy helpers (renderDocument + pack-index + id: frontmatter) instead of registerDocument's two-layer backbone (renderTwoLayerDocument + root-registry row + SKILL.md + slug + 063 marketplace sync). The plan (D-003) and the implementation both faithfully executed FR-001's "adapt provenance path" wording — so the error is the contract, not the code.
Fix
MODIFY FR-001: register a converted document through the two-layer registerDocument backbone (root-registry row + slug: NNN-name doc + SKILL.md + marketplace sync + NNN-slug.md filename; drop the pack-local index), and extend that backbone to carry convert's own provenance (converter, source-bytes content-hash, not-yet-spot-checked status), which registerDocument's deriveProvenance(body, {origin, status}) does not set today. Cascade: spec → design (D-003) → tasks → re-implement.
Deep dive — cross-spec cascade + a shipped-in-a-release note (no silent hotfix)

Cross-spec. The shared contract is 062's two-layer identity (the KB-NNNN lives in the root registry; the document carries the slug). convert never joined that model — it still writes the 056 single-layer shape, which is exactly what 062 migrated the corpus away from. So the converted doc is invisible to registry-authoritative resolution and survives only on 052's back-compat pack scan, slated for removal (TBD-resolver-registry-only).

Maps every dogfooding observation to this one root cause: "index inside the pack" + "root index not populated" = the pack-local index.md written instead of a root-registry row; "no NNN- prefix" = ${stem}.md vs registerDocument's ${slug}.md; "no SKILL.md" = the backbone step convert skips. All resolve by re-basing on registerDocument.

Scope note — it's live. convert shipped in the 0.1.0-pre.22 release, so this malformed output is reaching users now. No hotfix is meaningful (the fix is a re-spec + re-implement, not a one-liner), but the amended spec should land and ship in the next release rather than waiting; flagged here, not buried.

Converted-document title and description are derived from noisy PDF text, with no override

Spec upstream

Debugging a converted book whose registry title/description read as junk, root cause was a missing capability — convert derives both from deriveTitleAndDescription (first # heading + next paragraph) over raw converter output, which for a PDF is often a cover-page artifact or a page number, and there is no way to supply a better one; fixed by adding optional --title/--description overrides (and a filename-stem title fallback); regeneration passes at implementation — the heuristic is doing exactly what it was built to do, the gap is that convert offers no better source.

Expected
A converted book lands with a sensible title (e.g. the book's name) and a description that summarises it — or a way to provide them when the auto-derivation is poor.
Actual
Title and description come only from the converter's first heading/paragraph, which for real PDFs is frequently a cover fragment, a running header, or a page number; there is no --title/--description flag to correct it, and the value is what gets written into the registry row and (post-T-001) the SKILL.md slug-map.
Diagnosis
convert reuses deriveTitleAndDescription unconditionally. It has richer signal it ignores — the source filename (a good title fallback) — and no author override. This is independent of T-001: re-basing on registerDocument keeps the same weak derivation (it also uses firstBodyParagraph).
Fix
ADD optional --title and --description options to the convert verb (both CLIs), threaded into the filing call; when a title isn't derivable from a heading, fall back to the humanised source filename stem rather than "Converted: <stem>". Should-tier.
Deep dive — no cross-spec contract, no invariant, no hotfix

Partly inherent to lossy PDF conversion — the tool can't manufacture a good description from bad text, which is why the not-yet-spot-checked status and the "review before citing" nudge exist. The actionable gap is only the missing override + the poor filename-stem fallback. Best folded into the same slice as T-001's re-spec, since both touch FR-001 and the filing call.

The corpus validator doesn't catch a malformed pack — missing SKILL.md, single-layer doc, unregistered reference

Cross-spec upstream

Debugging why the malformed convert output shipped without a gate catching it, root cause was a coverage gap in the corpus validator — spectastic-corpus validate reports only the license warning on T-001's output, silently passing a pack with no SKILL.md, a id:-frontmatter (single-layer) reference, a reference absent from the root registry, and a stray pack-local index; fixed by adding those checks to the corpus validate rules; regeneration fails upstream — the rules never asserted these invariants, so no faithful re-implementation of the validator would have caught it.

Expected
spectastic-corpus validate flags a pack that (a) has no SKILL.md, (b) contains a references/ document using id: instead of the two-layer slug:, (c) has a document not registered in the root knowledge/index.md, and (d) carries an unexpected pack-local index.md.
Actual
All four pass clean — the only finding on the malformed pack is the (correct) corpus-license warning. The validator is blind to structural malformation, so a bad producer (convert today, a bad hand-edit tomorrow) ships an unusable pack with a green check.
Diagnosis
The corpus validate rules (corpusWellFormedFindings/corpusRegistryFindings, owned by 064 / the corpus-validate line) never grew a SKILL-presence check. This is why T-001 reached a release: the guarantee that should live in the validator (P-8) isn't there.
Fix
Done (SKILL-presence gate). Added missingSkillFileFindings to corpusWellFormedFindings (error severity): a pack with reference documents but no SKILL.md now fails validate, enforcing 057's existing "a pack MUST function as a plain Agent Skill (SKILL.md + references/)". It catches T-001's output. The other three checks first proposed here — reject a bare id: reference, require root-registry membership, flag a pack-local index.md — were re-scoped out: the validator deliberately supports single-layer packs (062 D-003 retains id: + pack-index for unmigrated downstream packs), so those would fight intended back-compat and need a separate "deprecate single-layer" decision, not a bug-fix gate.
Deep dive — the corrected scope + a second verb caught (adapt)

Corrected scope. Of the four checks first proposed, only SKILL-presence is a clean gate — it enforces an existing requirement (057) with no conflict, so it landed as an implementation fix, not a new proposal. The single-layer-vs-two-layer question is real but belongs to convert's own T-001 (converted docs should be two-layer) and to a future decision about retiring single-layer support corpus-wide — the validator can't reject single-layer-ness today without breaking packs it's meant to accept.

Second verb caught. The new gate immediately flagged that adaptCorpus (056 folder mode) also emitted SKILL-less packs — a latent defect in a shipped verb, surfaced by an adapt test that had (wrongly) asserted a SKILL-less pack was clean. Fixed in the same change: adapt now writes a minimal SKILL.md (name + description) when absent, mirroring registerDocument. convert was deliberately left failing the gate — its full fix is the two-layer re-spec in T-001, and the gate correctly holds the line until then.
