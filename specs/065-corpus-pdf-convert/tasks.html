27 tasks across five phases. Setup → Foundational → User stories (US1 · US2 · US3) → Polish. Tasks marked [P] can run in parallel — different files, no dependency. Tests for a story MUST be written and failing before its implementation tasks start.

1 · Execution strategy

Story IDs follow the spec's numbering (T-1xx = US1, T-2xx = US2, T-3xx = US3) regardless of build order. Priorities are US1 = P1, US2 = P2, US3 = P1 — the recommended build order below runs both P1 stories before the P2 one.

Setup → Foundational → US1 (core convert + file into a pack, P1) → US3 (source-bytes provenance, P1) → Polish. US2 (multi-converter selection, P2) is the deferrable increment — build it next, or ship without it and land it as a fast-follow; the default MarkItDown path is fully usable without it.

Setup → Foundational → US1 → US2 → US3 → Polish, in document order. Each story closes its conformance before the next opens.

One contributor per story after Foundational lands — US1 and US3 share convert.ts closely enough (the orchestrator + the source-hash it stamps) that they're better run in sequence by the same person; US2 (a different axis — converter selection) is the one story that genuinely parallelizes against the other two.
