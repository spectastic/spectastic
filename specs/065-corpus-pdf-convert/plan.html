Implementation plan · 065-corpus-pdf-convert

corpus convert — document conversion into the corpus

How we will build it.

Status Accepted Spec 065-corpus-pdf-convert Owner Brian Corbin · @briancorbinxyz Branch 065-corpus-pdf-convert Created 27 Jul 2026 Read time

Add convert to @spectastic/corpus as a fat-core orchestrator behind a ConverterRunner port (the same injectable-execFile seam as claude-cli/pack-fetcher/git): a per-converter registry adapts the three heterogeneous CLI shapes, the orchestrator runs the chosen binary, computes a hash of the source bytes, and files the markdown through a new fileConvertedDocument helper that reuses the adapt primitives. Both CLIs (standalone binary + the main CLI's corpus group) are thin dispatch. Biggest risk: the converters' CLI flags drift across versions — isolated per-converter in the registry and pinned by an integration test against a fixture binary.

2 · Technical context

Language(s)
TypeScript, ESM; Node ≥ 20 (verified on v25).
Frameworks
commander@^12.1.0, yaml@^2.9.0 (both already in @spectastic/corpus); node:child_process (built-in). No new runtime dependency.
Architecture
Hexagonal ports-and-adapters at the ConverterRunner seam (D-001) — mirrors the AIProvider/GitRunner/PackFetcher seams.
Storage
Filesystem — the existing knowledge/<pack>/references/ + index.md convention. No schema change.
Testing
Vitest, TDD red-first. A stub ConverterRunner (canned markdown + version) runs the whole path with no converter installed — the CI-stub pattern the corpus already uses for PackFetcher. One integration test drives a fixture converter shim on PATH.
Coverage
Not in scope — no coverage enforce floor (no profile marker in this repo).
Perf targets
No latency target (conversion time is the converter's). A bounded child-process timeout, default 120 s, --timeout <sec> override (D-005).
Constraints
Node-only distribution — no bundled Python/GPU (NFR-002); injection-safe argv (NFR-001, P-12); the one-way corpus ↛ core boundary stays intact (this is all corpus-internal).

4 · Approach

Convert is orchestration in front of the existing adapt machinery. A new knowledge/convert.ts owns a convertDocument() orchestrator: it validates the --converter name against a CONVERTERS registry (rejecting an unknown one before any process runs), invokes the chosen binary through a ConverterRunner port, collects the markdown (however that converter delivers it — stdout, -o file, or an output folder for Marker), and then either emits it (--no-adapt → stdout or --out) or files it into the target pack. Filing goes through a new fileConvertedDocument in adapt.ts, which reuses the adapt sub-helpers (allocateIds, deriveTitleAndDescription, the private renderDocument/index merge) but stamps convert's own provenance: content-hash = SHA-256 of the source bytes, converter = tool (+ version when probeable), origin = the source filename. Both CLI surfaces register a thin convert that parses args and delegates.

6 · Decisions

D-001 · Shell out through an injectable ConverterRunner port

Status
Accepted
Context
The codebase already shells out via execFile with an argv array behind an injectable runner (providers/claude-cli.ts:123, providers/pack-fetcher.ts GitRunner). Convert needs the same testability and the same injection-safety.
Decision
A ConverterRunner interface — real impl execFile(bin, argv, { timeout }), stub impl returning canned markdown + version. Arguments are always an argv array, never interpolated into a shell string.
Consequences
+ Injection-safe by construction (NFR-001, P-12). + The whole path is testable with no converter installed. + Reuses a proven seam. − A stub/fixture converter is needed for tests (cheap).

D-002 · A per-converter adapter registry for the heterogeneous CLI shapes

Status
Accepted
Context
The spike found three different shapes: MarkItDown emits to stdout or -o; Docling takes format flags; marker_single writes a .md into an output folder (marker-pdf).
Decision
A CONVERTERS map: name → { bin, buildArgs(file, tmpDir), collectOutput(tmpDir|stdout), versionArgs, installHint } for markitdown/docling/marker. The orchestrator validates the name against the map (unknown → non-zero, pre-run) and normalises every shape to "markdown text".
Consequences
+ Converter-agnostic — a new converter is one registry entry. + Each shape's quirks are isolated. − Marker's output-folder needs a managed temp dir the orchestrator creates and cleans in a finally.

D-003 · A co-located fileConvertedDocument stamps source-bytes hash + converter

Status
Accepted
Context
deriveProvenance always hashes the body and injects only origin/status (adapt.ts:40-50); renderDocument/mergeIndexRows are private to the module. Convert must pin the source, not the derived markdown (FR-004).
Decision
A new fileConvertedDocument in adapt.ts (so it reaches the private render/merge helpers), reusing allocateIds/deriveTitleAndDescription but stamping content-hash = SHA-256(source bytes), converter = tool(+version), origin = filename, status = the not-yet-spot-checked sentinel. deriveProvenance is left untouched.
Consequences
+ Convert's distinct hash rule is explicit, not a hidden override of a widely-reused primitive. + Full adapt reuse (id allocation, idempotency, index merge). − A second filing path beside adaptFolder/adaptLlmsTxt, mitigated by sharing every sub-helper.

D-004 · Orchestrator in core; thin convert on both CLI surfaces

Status
Accepted
Context
Fat-core/thin-CLI (P-8); every corpus verb registers on both the standalone binary (cli/curate.ts) and the main CLI's corpus group (cli/src/commands/corpus.ts).
Decision
convertDocument() owns validate-name → run → hash → file/emit. A registerConvert in the corpus binary and a convert subcommand in the main CLI's corpus group are thin dispatch, each resolving root/marketplace from resolveCorpusConfig.
Consequences
+ One tested code path, two entry points. + Matches the existing verb-mirroring exactly. − Two registration sites to keep in sync (true of every corpus verb already).

D-005 · --no-adapt emits to stdout (--out redirects); bounded timeout default

Status
Accepted
Context
MarkItDown's own default is stdout; a pipe-friendly raw emit composes with the corpus read path. A converter can hang on an encrypted/huge source.
Decision
--no-adapt writes markdown to stdout, --out <path> to a file; no file is created unless asked, and no pack is touched. The child process runs under a default 120 s timeout, overridable with --timeout <sec>; a timeout kills the child, exits non-zero, and writes nothing.
Consequences
+ Unix-filter composability; + a hung convert can't wedge a script forever. − A very large legitimate scan may need --timeout raised (documented in --help).

9 · Complexity tracking

The one non-obvious choice is a second filing path (fileConvertedDocument) rather than bending deriveProvenance. Justified in D-003: the source-bytes hash is a genuinely different provenance rule, and hiding it as an override on a primitive six other call sites use would make every caller's hash silently overridable. The helper shares all adapt sub-logic, so the duplication is a thin wrapper, not a fork.

Users install their chosen converter themselves (documented prerequisite, surfaced in --help and the missing-binary hint); the tool's own distribution stays pure-Node with no Python/GPU dependency (NFR-002).
