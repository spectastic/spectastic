Convert registers a two-layer corpus document

Applied

1 · Intent

Running convert on a real book PDF in a fresh project produced an incomplete, registry-invisible pack (065 triage T-001): the document carried id: KB-001 (the pre-062 single-layer shape), was never written into the root knowledge/index.md registry, had no SKILL.md, and used a bare <stem>.md filename. Consequences: get KB-001 resolves only through the deprecated pack-scan fallback and only at @TODO edition, so an edition-pinned citation never resolves and every converted document disappears once TBD-resolver-registry-only deletes that fallback.

The root cause is FR-001 itself, which specified "the existing adapt provenance path — allocating a KB-NNN id, writing frontmatter, and updating the pack index" — the legacy 056-era primitive. This change re-points FR-001 at the two-layer registerDocument backbone that import/interview/source already share, so a converted document is a first-class, registry-cited, two-layer artifact. It also adds optional title/description overrides (T-002), because auto-deriving both from noisy converted-PDF text yields poor metadata and there is currently no way to correct it.

2 · Scope

In scope

  • Re-base convert's filing on the two-layer registration backbone: a repo-unique KB-NNNN row in the root knowledge/index.md, a slug: document at references/<NNN-slug>.md, a created/extended pack SKILL.md, and marketplace.json kept in sync.
  • Extend that backbone to carry convert's own provenance — converter, the source-bytes content-hash, and the not-yet-spot-checked status — preserving FR-004.
  • Optional --title/--description overrides, with a humanised source-filename-stem title fallback.

Out of scope

  • Retiring single-layer support corpus-wide — the validator deliberately still accepts id: + pack-index packs for unmigrated downstream corpora (062 D-003).
  • Migrating adaptCorpus's own document shape to two-layer — a separate verb with its own single-layer output.

3 · Approach

convert stops filing through fileConvertedDocument (the adapt-legacy path that writes an id: document + a pack-local index) and instead registers through the two-layer backbone. The orchestrator derives the backbone's inputs from what it already has: plugin = the --pack value, marketplace = the resolved corpus.marketplace (pinned at convert time, as installPack pins a marketplace-less import), slug = an allocated NNN- prefix + the slugified filename stem, and title/description from the overrides or the derivation.

The one real seam: registerDocument's deriveProvenance(body, {origin, status}) hashes the markdown body and sets only origin/status. convert needs content-hash = the source bytes and a converter field, so the backbone is extended to accept an optional provenance override. SC-001 (content-hash equals the source SHA-256, readable from frontmatter) and FR-004 hold unchanged; the document simply also gains a root-registry row and a slug:. --no-adapt (FR-005) is untouched — it never files, so it never touches the backbone.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec.

What changes: convert registers through the two-layer backbone (root-registry row + slug: document + SKILL.md + marketplace sync), not the legacy adapt path + pack-index.

The corpus tool MUST provide a convert <file> verb that converts a source document to markdown via an external converter and, given a target pack, registers the result through the two-layer corpus backbone — the same path import/interview/source use. It MUST allocate a repo-unique KB-NNNN row in the root knowledge/index.md registry, write the document at references/<NNN-slug>.md carrying a slug: (never a document id:), create or extend the pack's SKILL.md, and keep marketplace.json in sync — never the legacy single-layer pack-index shape. The backbone MUST carry convert's own provenance per FR-004 (converter, source-bytes content-hash, not-yet-spot-checked status).

Rationale

A converted document must be a first-class, registry-cited artifact — resolvable by the registry (062 FR-006), not only via the deprecated pack-scan fallback. The prior "adapt provenance path … pack index" wording produced a single-layer, registry-invisible pack (T-001).

The convert verb SHOULD accept optional --title and --description options that set the registered document's title and description directly. Absent a --title and a derivable heading, it SHOULD fall back to the humanised source-filename stem (e.g. dodbook.pdf → "Dodbook") rather than a fixed "Converted: <stem>" placeholder.

Rationale

Auto-deriving a title/description from converted PDF text (first heading + first paragraph) is frequently a cover-page artifact or a page number; the author needs an override, and the filename is a better default than a fixed placeholder (T-002).

5 · Risk register

Adversarial risk pass (run this session — the proposal touches must-tier FR-001). One <spec-risk> per finding, each dispositioned by the author (recorded in by=): two mitigated, one accepted. No finding is left open.

Making convert MUST-register through the backbone hard-couples it to corpus.marketplace config it never depended on before — and when that's unset (repo-dir-name default or the local sentinel), a later corpus.marketplace change re-keys the pack and mints a second KB-NNNN, the identity fragmentation 061 Phase 8 exists to warn about.

MODIFY FR-001 — "allocate a repo-unique KB-NNNN row … keep marketplace.json in sync".

Mitigated: convert pins the converted row to the resolved corpus.marketplace at convert time, exactly as installPack pins a marketplace-less import (061 Phase 8 T-1002), so a later config change can't silently re-key it; the existing identity-fragmentation validate warning is the belt-and-braces guard. Captured as an implementation constraint on §6 task 2.

The two-layer backbone's default provenance contradicts FR-004: registerDocument's deriveProvenance hashes the markdown body and sets only origin/status, so re-basing convert onto it as-is would set content-hash to the converted markdown, not the source bytes — silently reverting the very guarantee FR-004 (and SC-001) make.

Live FR-004 — "set content-hash to the SHA-256 of the original source file's bytes, not the converted markdown".

Mitigated: the MODIFY makes "the backbone MUST carry convert's own provenance per FR-004" load-bearing, and §6 task 1 (extend the backbone to accept a provenance override) plus §6 task 5 (a regression test asserting the source-bytes hash survives) are the concrete guards. The contradiction only arises if the extension is skipped — which the tasks and the FR-004 test prevent.

Bundling the title/description overrides (FR-007, should) with the must-tier two-layer re-base risks holding the load-bearing fix behind a cosmetic feature — two intents in one proposal.

§2 In scope — the third bullet (--title/--description) versus the first two (the re-base).

Accepted (keep together): they share one code path (the filing call's title/description arguments) and one release, and were triaged together (T-001 folds T-002). The should-tier keeps FR-007 non-blocking, so it never gates the must-tier work at apply — the bundling carries no scheduling risk.
