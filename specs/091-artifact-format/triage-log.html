Cards

A mismatched closing tag passes validate silently

Spec upstream

Debugging a design authored with </spike> where </spec-status> was meant, root cause was a missing format requirement — no spec asks that an artifact's source nesting be well-formed, so no rule checks it and every rule reads a tree the parser has already silently repaired; fixed by stating well-formedness as a floor property of the artifact format; regeneration fails — with nothing requiring it, a fresh session rebuilds the same silence.

Expected
A close tag matching no open element is reported, with a line and column.
Actual
spectastic validate prints no findings. The document renders, and the typo is invisible to every check.
Diagnosis
Not a parser defect — HTML5 parsing is defined to repair rather than reject, so a conforming parser must accept this. parse5's onParseError surfaces tokenizer errors only (eof-in-tag, bad attribute names, doctype problems), and reports nothing for tree-construction errors: verified this session, a stray </div> with no open <div> yields 0 errors. 002-validate-cli enumerates every rule the schema must carry and none of them is a well-formedness check, so the gap is a missing requirement rather than a missing implementation.
Fix
specs/091-artifact-format/spec.html — propose a requirement that an artifact's source nesting be well-formed, with a validate rule at error severity. A stack scan over the source is enough and needs no parser change: the tool's own vocabulary is custom elements, which no tree-construction rule ever repairs or clones.
Fixed
Shipped as REQ-FORMAT-008 plus the spec-element-nesting rule — a source scan, since the parser repairs a mismatch before any rule sees it. Scoped to <spec-*>, because a check over every element would have declared the whole estate defective on void tags and inlined SVG. Found three real defects on its first corpus run: one false positive inside a <pre> (fixed in the rule), and two genuine unescaped <spec-id>/<spec-note> in prose, which the browser was turning into phantom elements.
Deep dive — scope-deferred, and the evidence it is not hypothetical

Four documents in the live corpus already carry malformed nesting, found by parsing all 513 artifacts with two independent parsers and diffing their element counts. The parsers agree everywhere except where the source is already broken:

  • specs/000-spectastic/changes/archive/2026-07-06-task-row-emphasis-scope/proposal.html — a genuine authoring bug: a literal unescaped <strong> in prose that should have been escaped. It has been in the archive since 6 Jul and validate has never mentioned it.
  • specs/050-stack-selection/design.html and specs/013-core-propose/tasks.html — improperly nested formatting elements inside a code listing, which the HTML5 adoption-agency algorithm repairs by cloning the element (one source offset yielding four elements in 050).
  • docs/vscode-lifecycle-brief/references/03-lifecycle-canvas.html — a generated 1.8 MB artifact, not hand-authored.

Why the fix is small. Across the same 513 files the two parsers agreed on 4617 of 4617 counts of this project's own spec-* elements. Every divergence was in presentational HTML (code, strong, div, style), because the repair rules that clone elements apply to formatting elements, which custom elements are not. So a well-formedness check does not need a stricter parser — it needs a scan the tool does not currently run.

Deferred, deliberately. Whether to change parser at all is a separate and larger question (parser-selection considerations): a swap buys roughly 925 ms of the ~1192 ms currently spent parsing, but puts a non-spec-compliant tree model under every rule. This card does not depend on that answer, and should not wait for it.

The nesting rule skips <pre>, where an unescaped element is still a phantom

Implementation code

Debugging why an unescaped <spec-id> in a shipped design silently deleted a command argument from the rendered page, root cause was spec-element-nesting suppressing <pre>/<code> content on the reasoning that a tag shown there is being named rather than opened — which the browser does not agree with; fixed by escaping the one occurrence, with the suppression itself left open; regeneration passes, since REQ-FORMAT-008 already requires well-formed nesting and only the rule's scope is wrong.

Expected
An unescaped spec-* tag anywhere in an artifact is reported, because the browser will open an element for it wherever it appears.
Actual
Inside <pre> or <code> it is not reported. specs/037-hands-off-pipeline/design.html carried spectastic run <spec-id> unescaped in a project-structure block; the browser created a phantom SPEC-ID element which swallowed 251 characters — the whole remainder of the block — and rendered the line as spectastic run  — wires seams, with the argument the block exists to document simply gone.
Diagnosis
The suppression is deliberate and its stated reason is wrong. packages/schema/src/rules/spec-element-nesting.ts’s own docstring names this case: “a <pre> block showing spectastic run <spec-id> is naming the element rather than opening one.” Authorial intent is not what the HTML parser reads; <pre> and <code> are not raw-text elements, so a tag inside them is parsed exactly as it would be anywhere else. T-001’s Fixed row records this same occurrence being classified as “one false positive inside a <pre> (fixed in the rule)” — so the true positive was suppressed at the moment the rule was taught, and the defect it was reporting shipped.
Fix
Narrow the suppression: keep skipping <style> and <script>, which genuinely are raw-text, and stop skipping <pre>/<code> for spec-* tags. Escaping is already the estate’s convention — the meta-spec’s own example block escapes &lt;spec-requirement&gt; — so the corrected rule should report 0 findings on the corpus today. packages/schema/src/rules/spec-element-nesting.ts
Fixed
Partially, 19 Aug 2026: the one live occurrence is escaped and the page now renders the argument, verified in a browser (0 phantom elements, line restored). A corpus scan confirms it was the only one. The suppression itself is unchanged, so a future unescaped element in a code block is still invisible — which is why this card stays open rather than closing on the symptom.
Deep dive — why this is not scope-deferred to a vocabulary allowlist

A neighbouring gap was found in the same pass and is genuinely separate: nothing validates the spec- vocabulary at all, so an unknown or misspelled element name passes silently (deferred from 108 as TBD-criterion-element-allowlist). That would catch a typo; it would not catch this, because spec-id is not a typo — it is a placeholder the author never intended to be an element. The two checks answer different questions and neither substitutes for the other.
