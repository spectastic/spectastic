Change proposal · 091-artifact-format

Floor properties of an artifact

Two things every artifact is assumed to be, that nothing checks and one parser silently repairs.

Status Applied Change ID 2026-08-18-floor-properties-of-an-artifact Spec 091-artifact-format Author Brian Corbin · @briancorbinxyz Created 18 Aug 2026 Targets 2 added Read time

An artifact is assumed to be well-formed and to carry no leftover template placeholders. Neither is stated, so neither is checked — and the first is worse than unchecked, because every rule in the engine reads a tree the parser has already silently repaired. Two added requirements, both checkable, both error severity.

Floor properties of an artifact

Applied

1 · Intent

Two triage cards, filed months apart against different specs, turn out to be the same defect: a property every artifact is assumed to have, which nothing states and therefore nothing checks.

091/T-001 was found when a design was authored with </spike> where </spec-status> was meant, and validate said nothing. 000/T-027 is the same shape one level up: the authoring commands all say “replace every placeholder, never leave one”, which is guidance in markdown and therefore not a guarantee.

The well-formedness one is the more serious, because it is not merely unchecked. Every rule in the engine reads a parsed tree, and the parser repairs a mismatched tag before any rule sees it — so the artifact a rule validates is not the artifact on disk, and a whole class of authoring error is invisible by construction.

2 · Scope

In scope

  • Stating source well-formedness as a floor property, with a rule that reads the source rather than the tree.
  • Stating that an artifact carries no unreplaced template placeholder outside quoted context.
  • A spec that is complete and still reads Draft. The same family — a property expressed as a moment rather than as something checkable — but it belongs to the spec that owns the lifecycle, not the one that owns the format.
  • Requiring every §4 invariant to be reachable from a success criterion. Filed as 000/T-030 and deliberately not brought here: an invariant is prose, so the coupling is reviewable rather than checkable, and putting an uncheckable obligation beside two checkable ones would blur what this proposal is for.
  • Validating the nesting of ordinary HTML. The boundary is the element set, not the file set: <spec-*> elements always carry explicit closing tags, which is what makes a source scan tractable, while the void elements and self-closing SVG in the same file do not and are outside the requirement by construction.

3 · Approach

Both rules read the source, not the parsed tree, which is the whole point: a rule that reads the tree cannot see either defect, because the parser has already repaired the first and the second is ordinary text once parsed.

Well-formedness needs no parser change. A stack scan over the source is enough, because the vocabulary is custom elements that always carry explicit closing tags — the void-element and optional-closing-tag cases that make general HTML hard do not arise for <spec-*>.

The placeholder census was wrong the first time and is restated here. The draft reported nineteen occurrences, all quotation, from a scan that stripped <code> and <pre> and looked no further. The audit finds 43 occurrences, 11 outside quotation, 9 of them genuine unreplaced placeholders in artifacts already committed. Those nine are fixed as part of this change; the remaining two are quotation inside a <spec-diff>, which is why the exemption names diffs as well as code.

The correction matters beyond the number. A rule justified by “this reports nothing today” is a different rule from one justified by “this catches nine live defects”, and only the second tells you what severity it needs.

4 · Deltas

One <spec-delta> per requirement touched.

Every <spec-*> element in an artifact's source MUST close, matched and in order, and a mismatched or unclosed one MUST be reported rather than repaired silently.

Rationale

This is the floor the rest of the format rests on, and it is the one property no rule can currently observe. Validation parses before it checks, and the parser repairs a mismatched tag on the way in — so every rule reads a document that differs from the file, and the difference is exactly where the defect is. A design authored with </spike> closing a <spec-status> validated clean.

Scoped to <spec-*> rather than to every element, because that is the set a source scan can actually decide. An artifact is mostly ordinary HTML — <meta>, <link> and <input> never close, and REQ-FORMAT-001 mandates inlined SVG whose <path/> is self-closing — so a requirement over every element would declare the entire estate defective on day one. The first draft did exactly that, and disclaimed the problem on the vocabulary while the rule read the file.

The scan must also skip raw-text elements: a <style> selector and an inlined script's a < b both look like tags to a naive stack.

Error severity, and this half earns it on its own grounds: a repaired tree makes every other finding suspect, so a rule reporting clean may have been reading a document nobody wrote. This is engine integrity rather than authoring hygiene, which is why it does not share the other requirement's severity argument.

An artifact that has reached accepted MUST NOT carry an unreplaced template placeholder, and a placeholder inside quoted context — a code block, a preformatted block, or a diff — MUST NOT be reported, since quoting a template is how templates are documented.

Rationale

Every authoring command already says to replace them all. That instruction lives in command markdown, which triage T-009 and P-8 both exclude as a place a guarantee may live — it is a nudge, and an artifact that ships with [FEATURE_NAME] in its title is broken in a way a reader sees before anyone else does.

The exemption and the severity are both drawn from an audit that had to be run twice. The first census reported nineteen occurrences, all quotation. The real figures are 43 occurrences, 11 outside quotation, and 9 genuine unreplaced placeholders — including three in a proposal applied the same day this was drafted. The rule catches real defects, which is a better argument than the one first made for it.

Every one of the nine sat in the <title>, the <spec-change> wrapper or the footer — the chrome outside the sections an author writes. Nobody misses a scope item, because writing scope is the task; everybody misses the title. That is the pattern this requirement exists to catch.

Severity is status-dependent rather than flat, cloning no-placeholder-question.ts: error once accepted, warning while draft or review, skipped otherwise. That is what keeps an archived or withdrawn proposal — which 088 calls a stable fact — from failing a gate it can never be edited to satisfy. REQ-FORMAT-005 set the same precedent when it shipped date-format at warning as a migration-scoped choice.

The diff exemption was found, not guessed: the last two unexplained hits were <del> lines inside a <spec-diff> quoting template markup. Chasing why the count disagreed is what produced it.

5 · Risk register

Populated by the adversarial risk pass. This proposal adds two must-tier requirements.

The corpus census the exemption was designed from is wrong, and the error severity it justifies would block the next commit on artifacts that are supposed to be frozen.

§3 claims “All nineteen placeholder-shaped strings in the estate today are quotation”. An independent scan finds 43 occurrences, 11 outside quotation — including three in the proposal applied earlier today and six in a withdrawn one.

Verified and upheld; the count was re-run independently and the classification is false. Two consequences. The corpus is not clean when the rule lands, so the pre-commit hook and the CI dogfood both block on archived artifacts 088 calls stable facts — leaving a choice between editing an archive and blinding the gate permanently. And the honest finding is a better argument than the false one: the rule catches eleven live defects on day one. Recommend cloning the status-dependent ladder no-placeholder-question.ts already ships — error once accepted, warning while draft or review, skipped otherwise — so frozen archives never fire, and restating §3 with the real numbers.

REQ-FORMAT-008 is false of every artifact REQ-FORMAT-001 mandates: a must-tier requirement nothing in the corpus satisfies.

Proposed: “every element that opens MUST close, in order”. Against a single spec carrying three <meta> and two <link>, and 79 artifacts carrying inline SVG with self-closing <path/> — which REQ-FORMAT-001 requires by mandating inlined SVG.

Upheld. §3 disclaims the void-element case as not arising “for <spec-*>”, which is true of that vocabulary and irrelevant to a rule that scans the file. A scan must also special-case raw-text elements, since a <style> selector and an inlined script's a < b both look like tags to a naive stack. Recommend scoping the requirement to <spec-*> elements so the requirement and the rule describe one property, and rewording “published artifact” in REQ-FORMAT-009, which collides with REQ-FORMAT-001's established sense of the published build.

The scope boundary is drawn on the wrong axis, and it is the axis the approach rests on.

The item locates tractability in which files are scanned — “anything but spectastic's own artifacts” — when it lives in which elements inside a file are scanned. Restricting the file set buys nothing; spectastic's own artifacts are full of ordinary HTML.

Upheld. Secondary and also right: the two deltas are one origin story but two topic groups. REQ-FORMAT-008 is engine integrity, where a repaired tree makes every other finding suspect; REQ-FORMAT-009 is authoring hygiene with a migration cost and a live precedent for warn — REQ-FORMAT-005 ships date-format at warning explicitly as a migration-scoped choice. One severity argument was made to cover both. Recommend restating the boundary as the element set, and giving the placeholder delta its own severity argument.

Two must-tier requirements rest on facts presented as verified that are false, with an empty risk log — the state KB-0001@2026-07-25 forbids.

KB-0001: a must-tier decision may not rest on an assumed fact without an explicit accepted risk, where verified means the source was opened this turn. §3 says “derived from the corpus, not assumed” of a census that is wrong, and “a stack scan over the source is enough” with no spike run.

Upheld, and it is the finding that explains the other three: the census was run with a regex that stripped code and pre and nothing else, and its output was reported as though it were an audit. KB-0001's second half applies too — it defines a MUST as one whose absence is a defect, and REQ-FORMAT-008 as drafted declares the entire estate defective, which means its scope was never written down. Recommend re-grounding both claims rather than accepting the gap: the numbers are cheap to get right and the spike is one afternoon.

7 · Open questions

None outstanding. The adjacent question — whether a §4 invariant can be mechanically coupled to a success criterion — is answered in §2 as out of scope, because it cannot. The two questions this proposal got wrong first time, its census and its scope, are settled in §5 rather than left open.
