Specification · 091-artifact-format Spectastic

Artifact format and authoring

What a spectastic artifact is on disk, how it must render, and the conventions that keep its source editable.

Status Accepted Spec ID 091-artifact-format Owner Brian Corbin · @briancorbinxyz Reviewers Brian Corbin · @briancorbinxyz Created 11 Aug 2026 Principlesv1.9.0 Smallest demoableOne artifact that opens from file://, renders fully with JavaScript disabled, and validates clean. Read time

The floor every artifact stands on: a single self-contained HTML file that opens from the local filesystem, renders completely without JavaScript, carries a live size gauge and correctly-marked dates, and is authored in semantic custom elements with rationale tucked out of the reading path. Includes the copy rule that keeps internal ids off user-facing surfaces.

1 · Context

Everything else in the lifecycle assumes the artifact is a durable, self-contained, hand-editable file. These requirements are what make that assumption true — and they are the ones a downstream project feels first, because they govern every file the tool writes.

This spec is a slice of the spectastic meta-spec. Its requirements were authored there and moved here intact, keeping their stable ids: a requirement that was REQ-FORMAT-001 in the parent is REQ-FORMAT-001 here, so every existing citation still names the same contract. The parent keeps the project’s context, architecture, decisions and history; this file carries one family of requirements and nothing else.

2 · Requirements

Normative keywords follow RFC 2119.

A spectastic artifact MUST be a single .html file. All CSS, JavaScript, and SVG MUST be inlined in the published build.

Rationale

Single-file is the entire shape of the offer: emailable, archivable, runnable from file://. Linked assets re-introduce the build-and-deploy concerns we are trying to escape.

The file MUST open and render correctly when loaded from the local filesystem, with no required network round-trip beyond Google Fonts (which itself SHOULD degrade to system fonts on failure).

Source files SHOULD stay under 200 KB before font assets. Past that, hand-editing in common editors gets sluggish.

A spec.html artifact MUST carry a <spec-budget> size gauge. The gauge's Words row MUST count authored prose only — the auto-built <spec-conformance> index is excluded, since it is generated rather than written. The gauge MUST band each metric against its declared budget as green ≤ 80%, amber > 80–100%, red > 100%, taking the worst row as the overall band. The default budget for a feature spec SHOULD be 1,500 words / 20 requirements / 12-minute read; tool-shape specs SHOULD declare a higher budget (e.g. 2,500 words), and system-of-record artifacts (this meta-spec, principles.html) are exempt. The amber band is advisory — a nudge to consider slicing, never a hard gate.

Rationale

The budget is small-batch pressure made visible, but its numbers were unowned and partly invented. 80% amber is the industry-standard "approaching limit" warn point (AWS CloudWatch sets capacity alarms at 80%; queueing theory puts the knee there) and avoids the alert fatigue a 70% band caused — 67% of our specs breached it, so it was overridden as routine (AHRQ on warnings that fire too often). RAG cut points are conventions, not canon (PRINCE2), so we pick the evidenced one. Authored-words stops the ~430-word conformance index from counting against the author. The brevity principle is real and is Larson's ("most people don't read long documents") — but the "1,500 words" figure was never his, so the gauge stops attributing it to him.

Every date in an artifact MUST be wrapped in a <time> element whose datetime= attribute is a valid ISO 8601 date (YYYY-MM-DD, or a fuller ISO timestamp where a time-of-day is meaningful) and whose visible text renders in the canonical human form DD Mon YYYY — a zero-padded two-digit day, a three-letter title-case month, and a four-digit year, e.g. <time datetime="2026-07-06">06 Jul 2026</time> (not 6 Jul 2026). This holds uniformly across <spec-meta> Created/Updated rows, <spec-changelog> entries, and inline dates. A date-format validate rule SHOULD warn (not error) when a <time>'s display text departs from DD Mon YYYY or its datetime= is not ISO 8601.

Rationale

The datetime= attribute was ISO 8601 only by habit and the visible text was unowned, so the two forms drifted side by side — 2026-06-29 in one row, 29 Jun 2026 in the next (T-011). DD Mon YYYY is the corpus majority (375 vs 215) and the changelog convention, so it is the least-migration canonical choice (zero-padded day, e.g. 06 Jul 2026); ISO stays in datetime= for machines. The requirement is a genuine MUST; the rule's warn severity is a migration-scoped choice — it avoids breaking the SC-001 integration gate on the ~215 not-yet-normalized displays before the cleanup drains — not a softening of the mandate.

Copy that is the tool talking — text spectastic emits or writes for a user to read — MUST NOT surface spectastic's own internal artifact ids (spec numbers and slugs, REQ-*, FR-*, NFR-*, SC-*, T-*, P-*, D-*). The dividing line is the contract: a spec or plan artifact citing its own governing ids as anchors is legitimate provenance per P-3, not a leak — this explicitly includes a generated <spec-changelog> entry and the author-supplied apply summary the kernel writes (REQ-CHANGE-008), which are the human's voice. What the tool itself says — CLI --help text, error and diagnostic messages, and tool-managed markers (a pre-commit hook stamp, a managed-file marker) — carries no internal id; its provenance lives in code comments and the artifact trail.

A no-internal-id-in-copy validate rule MUST enforce, at error severity folded into every validate run and blocked by the pre-commit gate, the one tool-talking surface spectastic can see and judge without ambiguity: the string arguments of its own CLI .description/.option/.argument help calls, where an illustrative argument slug uses the sanctioned neutral placeholder 001-auth-service. This is a floor, not a cap — the rule MUST cover at least that surface. The remaining tool-talking surfaces (runtime finding messages, tool-managed markers) stay review-caught, permanently and by design: a rule scanning finding message: copy would false-positive on a finding legitimately naming the requirement it enforces, so that surface is judged by review, not linted. This ceiling MUST be recorded, not hidden — the honest P-8 posture — and is not a deferred check awaiting a future rule. The invariant binds spectastic's own tooling and every downstream project alike (P-10); a downstream project's application copy is unseeable by spectastic, so there it is review-caught too.

Rationale

Sourced from P-10 and meta-spec triage T-017 — spectastic --help shipped the tool's own spec numbers ((037), (spec 042), Spec 043.) across 30 sites. The requirement is a genuine MUST descending from a MUST-NOT invariant; the rule's error severity matches. It is stated as an abstract invariant with the enforced surface named separately as a floor, rather than an enumerated list of forbidden surfaces, so it neither freezes commander method names into a contract nor collides with REQ-CHANGE-008's id-citing author summaries — the two seams the adversarial pass surfaced (§5, R-001/R-002). The tool-talking-vs-artifact line is the same P-8 honesty the fat-core/thin-CLI convention carries (T-016). Parallels REQ-FORMAT-005's MUST-plus-named-rule shape and REQ-TOOL-004's "a rule gives the MUST teeth" pattern.

An artifact SHOULD contain its own wide content: at a 390 px viewport the page SHOULD scroll vertically only, with tables, code blocks, diagrams and definition lists scrolling or reflowing inside their own bounds.

Rationale

Measured at 390 px, 154 of 227 artifacts scrolled sideways, worst at 752 px — a document that cannot be read on a phone without panning. The tier is should because verifying it needs layout, which no static check has; the estate meets it at 219 of 227 today, so the rule records a standard already kept rather than one aspired to.

Components MUST be expressed as custom elements (<spec-requirement>, <spec-decision>, etc.) — never as <div> + class names. Tag name is schema.

Every requirement MUST carry a stable id attribute of the form REQ-<TOPIC>-<NNN> and a priority attribute of must | should | may.

Authors SHOULD place rationale, derivations, and long examples inside <details> blocks so the requirement reads as a single sentence at default zoom level.

Authors MAY use <spec-sidenote> inline for marginalia that would interrupt the reading flow but is too small for a callout.

A <spec-questions> register with no open questions MUST contain no <li> items. Each <li> in the register counts as exactly one open question to every consumer — health extraction, the lifecycle needs-attention signal, validators — so an absence of <li> is the single unambiguous representation of zero. Resolved-with-rationale prose (e.g. "None outstanding — every decision was anchored in the interview") SHOULD live in a <p> inside the register, and MUST NOT be written as a placeholder or "None" <li>.

Rationale

The register is a counter to machines and a decision trail to humans; both are served by reserving <li> for an actual open question and putting prose in a <p>. 016-theme-support already does this; the <ol><li>None at write time…</li></ol> form used by the core specs is what trips the false count fixed here (T-005). Complements REQ-AUTHOR-001 (tag name is schema): the tag you choose inside the register is the meaning.

With JavaScript disabled, every section, requirement, tab panel, and details block MUST remain readable. JavaScript provides convenience (tabs, copy-link, conformance index, dark mode) but never content.

Print stylesheet MUST expand collapsed details, unhide tab panels, and remove interactive chrome. A printed spec is a complete spec.

The default theme SHOULD support a dark-mode toggle that flips a single html.dark class — no per-element overrides required.

The dark-mode palette MUST honor the warm-tone principle established by the light palette. Concretely: surface and background tokens MUST use warm dark greys (warm hue, brightness in the #1c–#28 range) and never pure black; border tokens MUST sit 4–8 luminance steps above their adjacent surface token and never be desaturated neutrals.

Rationale

The light palette intentionally rejects pure white and pure black for the same reason: warmth reads as considered, neutral tones read as undesigned. Dark mode should follow the same discipline, not stumble into cold defaults when a fresh contributor tweaks a token.

A spectastic artifact MUST be a single .html file.

Rationale

Single-file is the entire shape of the offer.
