SLO-from-NFR artifact model

A quantified NFR is an SLO in prose. This gives that SLO a first-class shape linked to its NFR — and makes an unquantified NFR fail at the tiers that promise reliability.

Read time

A customer-facing "p95 < 200 ms" is an SLO in prose, but spectastic captures the NFR and consumes the number nowhere. This spec adds the artifact model, representation-first: a first-class <spec-slo target="NFR-NNN"> element (OpenSLO-shaped — SLI, objective, window, budgeting method; error budget derived), mirroring <spec-risk target>, with an optional golden-signal tag and an optional light slo= annotation on the NFR for simple cases; two shape rules keep it well-formed. As a should-tier follow-in, a profile-gated rule errors on a verified/enterprise NFR that is neither inline-quantified nor SLO-linked — the "verified NFRs are quantified" check. The verify.html trace that would prove the SLO at runtime stays the sibling TBD-verify-slo-trace.

1 · Context

The reliability chain is NFR → SLO → SLI → instrumentation. A research pass found spectastic owns the first rung and drops the chain: NFRs are <spec-requirement id="NFR-NNN"> and the template prompts "p95 < 200 ms, not 'fast'", but nothing represents the latent SLO and no rule requires the number to exist.

Two of that doc's four moves have landed — the tiered observability/SLO principle and the observability enforce category. This spec is the third: the SLO-from-NFR artifact model, which the research doc left for "the follow-on spec to pick." The fourth — a verify.html trace that proves the SLO at runtime — stays a sibling.

2 · User scenarios & testing

US1 · An SLO has a first-class shape linked to its NFR P1

As a spec author, I want to attach a structured SLO to an NFR so the reliability promise is a reviewable artifact, not prose a reader must infer.

Acceptance: a <spec-slo target="NFR-001"> carrying SLI, objective, window, and budgeting method renders linked to its NFR with click-through; a malformed one (no target=, a target that resolves to no NFR, or a missing required field) fails validate.

US2 · A verified NFR must be quantified P2

As a reviewer on a verified/enterprise project, I want an NFR with no measurable target to fail so a vague "fast" can't ship where reliability is promised.

Acceptance: at the verified/enterprise profile, an NFR that carries neither an inline measurable target (a number+unit, percentile, or threshold — in its prose or its slo= attribute) nor a linked <spec-slo> produces an error; below verified it is silent; a quantified or SLO-linked NFR passes at every tier.

US3 · The simple case stays light P3

As a spec author, I want a compact way to note a simple SLO without the full element so trivial targets don't demand ceremony.

Acceptance: an optional slo= attribute on <spec-requirement id="NFR-NNN"> carries a single-string SLO (e.g. "99% < 200ms / 28d"); it satisfies US2's quantified check and is machine-readable for the future verify trace.

Edge cases

  • No profile marker. The quantified rule reads .spectastic/profile.json; with no marker it is a no-op — fail-safe (advisory, never a false hard-fail).
  • Multiple SLOs per NFR. An NFR may carry several <spec-slo> (e.g. a latency and an availability objective); each is independently well-formed and linked.
  • Legitimately-qualitative NFRs. Where an NFR isn't a single number (accessibility, a security posture), the quantified rule accepts a threshold, ratio, or conformance level, and an SLO link satisfies it — an escape hatch that isn't "fast".

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A first-class <spec-slo> element MUST represent an SLO refining an NFR. It MUST carry a target= attribute naming the NFR id it refines, and MUST model the OpenSLO shape: an SLI (what is measured), an objective (the target, e.g. 99% < 200 ms), a time window, and a budgeting method; the error budget (1 − objective) MUST be derived, never authored. It MAY carry an optional signal= attribute tagging the SLO by a Four Golden Signals value (latency / traffic / errors / saturation). It MUST render linked to its NFR with click-through (mirroring <spec-risk target>) and MUST degrade gracefully with JS disabled (P-4).

Canonical shape 
<spec-slo target="NFR-001" signal="latency" window="28d" budgeting="occurrences">
  <dt>SLI</dt><dd>fraction of requests served in < 200 ms (good ÷ valid)</dd>
  <dt>Objective</dt><dd>99% (error budget 1% = derived)</dd>
</spec-slo>

Attribute-vs-content split (which fields are attributes, which are content) is a plan decision; the required information is fixed here.

Two schema validate rules MUST keep a <spec-slo> well-formed, at error severity: slo-target-required (a <spec-slo> that omits target= is flagged, mirroring risk-target-required), and slo-well-formed (its target= MUST resolve to an NFR-* requirement in the same document, and the required OpenSLO fields — SLI, objective, window, budgeting method — MUST be present; an unknown signal= value is flagged).

An optional slo= attribute on a <spec-requirement id="NFR-NNN"> SHOULD carry a compact single-string SLO (e.g. "99% < 200ms / 28d") for the simple case, machine-readable so a downstream consumer (the verify observables trace) can read either the attribute or the full element.

A profile-gated quantified-NFR rule SHOULD resolve the project's profile from .spectastic/profile.json and, at the verified/enterprise tiers, flag at error severity any NFR-* requirement that is neither inline-quantified (a number+unit, percentile, or threshold in its prose or its slo= attribute) nor refined by a linked <spec-slo>. Below verified, or with no profile marker, it MUST be a no-op (fail safe in the advisory direction, mirroring the enforce-waiver scan).

Rationale

Tier-gating needs the profile, which the schema engine never sees — so this is a folded CLI scan (like enforce-waiver-well-formed), not a schema PerFileRule. The inline-OR-linked acceptance keeps the heuristic from false-failing a legitimately SLO-linked or thresholded NFR.

Non-functional

The element and rules MUST be deterministic and add no runtime dependency, and MUST NOT break the rendering of any existing spec-family artifact — a document with no <spec-slo> renders and validates exactly as before.

The <spec-slo> element SHOULD render legibly in both themes and both light/dark modes (calm and vivid), consistent with the existing typed blocks (<spec-risk>, <spec-decision>).

Out of scope (deferred)

  • The verify.html observables trace (SLO → SLI → instrumentation) + a CapturedRun instrumentation field that proves the SLO at runtime (does /metrics exist? are the golden-signal SLIs emitted?). The sibling that gives NFRs a runtime proof leg (extends P-7).
  • Requiring an SLO on every verified NFR, or enforcing golden-signal coverage — advisory here; this spec only requires an NFR be quantified, not that it carry a full SLO.
  • Runtime probing of a live metrics endpoint, or OTLP-push detection — a runtime/config concern, not artifact shape (belongs to the verify trace).

4 · Data model

One new artifact element and one optional attribute; no persistent entities.

<spec-slo>
An SLO refining an NFR — the fields per FR-001, error budget derived.
slo= on <spec-requirement>
The optional light single-string SLO (FR-003).
Golden signal
The signal= enum: latency, traffic, errors, saturation (RED/USE are lenses onto these four).

5 · Success criteria

A <spec-slo target="NFR-001"> with the full OpenSLO fields renders linked to its NFR (click-through to the requirement), and a malformed SLO — missing target=, a target= resolving to no NFR in the document, or a missing required field — fails spectastic validate at error severity.

On a verified/enterprise project, an NFR carrying neither an inline measurable target nor a linked <spec-slo> fails validate (error); the same NFR passes below verified, passes with no profile marker, and passes once given an inline target, an slo= attribute, or a linked <spec-slo>.

6 · Assumptions

The profile marker (.spectastic/profile.json) and loadProfiles resolution used by the enforce-waiver scan are the same path FR-004 reads — a proven, existing mechanism, not new profile plumbing.

The observability enforce category and the tiered SLO principle already shipped (042/041, 11 Jul 2026), so this spec adds only the artifact model + the quantified check, not the principle or the metrics-stack detection.

7 · Open questions

None outstanding — the representation (hybrid: a first-class <spec-slo> element plus an optional light slo= annotation), the full OpenSLO field set, the optional golden-signal tag, the rule's profile-gated error gating, and the inline-OR-linked quantified definition were all anchored in the interview.
