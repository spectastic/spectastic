Design · 047-slo-nfr-artifact

SLO-from-NFR artifact model

Three loci, every one a copy of a shipped pattern: a typed element like <spec-risk>, two shape rules like risk-target-required, and a profile-gated scan like the enforce-waiver fold.

Status Draft Spec 047-slo-nfr-artifact Owner Brian Corbin · @briancorbinxyz Branch slo-nfr-artifact Created 12 Jul 2026 Read time

Slice 1 (the representation) is a first-class <spec-slo> element — scalars as attributes, SLI as content — rendered and click-through-linked to its NFR by spec.js/spec.css (copying the spec-delta[target] block), plus two schema shape rules copying risk-target-required. The should-tier FR-004 quantified-NFR check is a folded CLI scan (not a schema rule) so it can read the profile tier — mirroring scanEnforceWaivers. Biggest risk: the quantification heuristic mis-firing — mitigated by the liberal inline-OR-linked acceptance and should-tier gating. All grounding verified; no spikes.

4 · Approach

Three independent loci, each a copy of shipped code. (A) The element — <spec-slo> is a typed block: spec.css gets a card style (mirroring spec-decision) and spec.js gets a spec-slo[target] click-through block (mirroring spec-delta[target]). Fields are scalars-as-attributes (target, objective, window, budgeting, signal) with the SLI as content (D-003). (B) The shape rules — two schema PerFileRules (slo-target-required, slo-well-formed) copying risk-target-required, registered in the rule index, with fixture pairs. (C) The quantified-NFR check — a folded CLI scan (scanQuantifiedNfr) that reads the profile marker and, only at verified/enterprise, flags an unquantified NFR; its pure core (quantifiedNfrFindings) lives in @spectastic/core/commands/validate beside enforceWaiverFindings.

6 · Decisions

D-001 · A first-class <spec-slo> element, mirroring <spec-risk target>

Status
Accepted
Context
The spec's hybrid model needs a rich SLO shape; risk-target-required.ts + assets/spec.js:171 show a typed, target-linked, click-through element is a copyable pattern.
Decision
Add <spec-slo> as a typed block: a spec.css card + a spec.js spec-slo[target] click-through, both cloned from existing code. The light slo= NFR attribute (FR-003) rides alongside.
Consequences
+ Zero new concepts; degrades with JS off (P-4). + Consistent with spec-risk/spec-delta. − One more typed block to keep in the shared style lists.

D-002 · FR-004 is a folded CLI scan, not a schema rule

Status
Accepted
Context
The quantified-NFR check must gate by profile tier, but the schema engine never sees project state. packages/cli/src/commands/validate.ts:164 (scanEnforceWaivers) is the exact precedent: read the marker, resolve the profile, fold findings.
Decision
Core quantifiedNfrFindings(docs, {tier, now}) in @spectastic/core/commands/validate; CLI scanQuantifiedNfr(files, cwd) reads the marker, parses the files, calls core, folds into the findings array. No-op below verified / with no marker.
Consequences
+ Tier-accurate; keeps the schema engine profile-agnostic (the invariant). + Reuses the waiver-scan shape wholesale. − Re-parses the validated files a second time (cheap; noted in §9).

D-003 · Scalars as attributes, SLI as content

Status
Accepted
Context
The spec left the attribute-vs-content split to the plan; parser.ts validates attributes trivially with getAttr, while content needs a childNodes walk.
Decision
target, objective, window, budgeting, signal are attributes; the SLI description is element content. slo-well-formed checks required attrs via getAttr + non-empty SLI content + a known signal value.
Consequences
+ Scalars are greppable (P-2) and validate simply; the prose SLI reads naturally. − Two field homes (attrs + content) the rule must check.

D-004 · The quantification heuristic (should-tier)

Status
Accepted
Context
"Quantified" is judged from prose; no external fact settles the exact regex — pure judgment (grounding="n-a"), on a should-tier requirement so it does not block the gate.
Decision
An NFR is quantified if its prose or its slo= attribute carries a number with a unit / percentile / comparison-threshold, or a <spec-slo target=this-NFR> refines it. Liberal by design.
Consequences
+ The inline-OR-linked escape hatch avoids false-failing a legitimately SLO-linked or thresholded NFR. − Heuristic false-pos/neg is a recorded ceiling (§8); tune from real use, not up front.

D-005 · Structural fixtures + behavioral Playwright

Status
Accepted
Context
The element is positioned/rendered; the verification discipline (CLAUDE.md, "presence is not containment") says a structural check can't prove click-through works.
Decision
Fixture pairs + vitest for the two rules and the quantified scan; a Playwright spec drives a page and asserts <spec-slo> renders and click-through scrolls to the NFR.
Consequences
+ Proves behaviour, not just presence. − One browser spec to maintain (the course.gate / theme precedent).

8 · Risks & mitigations

RiskLikelihoodImpactMitigation
Quantification heuristic mis-fires (a real target read as vague, or vice-versa)MMLiberal inline-OR-linked acceptance (D-004); should-tier only; recorded ceiling; tune from use.
The slo= attribute and a full <spec-slo> on the same NFR disagreeLLIndependent by design — the quantified rule accepts either; no v1 cross-check.
Folded scan re-parses validated files (double parse)LLparse5 is fast, corpus small; acceptable — a later optimization can share parsed docs.

9 · Complexity tracking

FR-004 lives in the CLI as a folded scan rather than a schema rule — the one deviation from "all validation is a schema rule." It is forced by the schema-engine-stays-profile-agnostic invariant (D-002) and is not new complexity: it copies the shipped scanEnforceWaivers shape one-for-one.
