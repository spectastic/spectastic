Reconcile the SLO authoring surface with slo-well-formed

Applied

1 · Intent

Landing a valid <spec-slo> took three validate round-trips because 047's documented authoring surface contradicts the contract 047 itself defines. This is friction, not a blocker — the error messages are excellent — but it is exactly the trip-wire a first-time enterprise author hits, and the source of truth doing the tripping is the spec's own canonical example.

Two root causes, both in the spec's prose rather than the code. First, FR-001's "Canonical shape" <details> predates plan D-003's resolution that scalars are attributes; the example still shows the objective in <dt>/<dd> content, so it fails the very rule 047 ships. Second, the signal= enum (the Four Golden Signals) is deliberate and correct, but it is stated only in the §4 data model, while §2 refers to an "availability objective" — so an author reasonably writes signal="availability" and is rejected with no in-spec account of why. The fix teaches, at the requirement level, what the validator already enforces.

2 · Scope

In scope

  • Correct FR-001's canonical-shape example to the attribute form (objective/window/budgeting/signal as attributes; SLI as content) so it validates when copied, and update its note to point at the resolved plan D-003 shape.
  • State FR-002's signal= vocabulary explicitly (the Four Golden Signals) and teach the availability→errors / throughput→traffic mapping so intuitive-but-rejected terms have an in-spec answer.
  • Carry the same mapping into the §4 data-model note and into slo-well-formed's signal fixHint, so the failure message teaches the fix at the point of failure.
  • Reword §2's "an availability objective" edge-case prose so the phrase that literally triggers signal="availability" no longer reads as a signal (the tripwire T-001 names).

Out of scope

  • Widening the signal= enum to accept availability/throughput — the Four Golden Signals taxonomy is deliberate; these terms are objectives/SLIs, not signals. (Considered and declined in the interview.)
  • Any change to slo-well-formed's or slo-target-required's enforcement behaviour — the validator is correct; only its advisory fixHint text gains the mapping.
  • The verify.html observables trace and runtime SLO proof — unchanged (already shipped as 048).

3 · Approach

Two MODIFY deltas, no ADD/REMOVE, no code-behaviour change — the smallest reconciliation that makes the spec honest about its own contract. The normative bodies of FR-001 and FR-002 are preserved verbatim; the edits are surgical: FR-001 swaps its stale example for a valid one and refreshes the attribute-vs-content note now that D-003 has resolved it; FR-002 appends one sentence naming the legal signals and the two mappings. Neither delta changes what validate does — they change what the spec says so that following it produces a valid artifact on the first pass.

The non-requirement surfaces (the §2 edge-case prose, the §4 data-model "Golden signal" entry, and the validator's fixHint) carry the same mapping and fold in as §6 tasks. Keeping the fixHint as the belt-and-braces channel matters: markdown and spec prose are advisory to an author who skims, but the error message fires exactly when they're stuck — so the mapping lives in both places. The adversarial pass reshaped the draft: it caught a semantic regression in the first example (a merged objective that broke the derivation clause), softened the mapping from a closed rule to illustrative, and widened scope to the §2 tripwire — see §5.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec. op= is one of added | modified | removed | renamed; a missing or invalid op renders visibly broken.

What changes: the "Canonical shape" example is corrected to the attribute form (it currently fails slo-well-formed), and the attribute-vs-content note is updated to reflect plan D-003's resolution. The normative body is unchanged.

A first-class <spec-slo> element MUST represent an SLO refining an NFR. It MUST carry a target= attribute naming the NFR id it refines, and MUST model the OpenSLO shape: an SLI (what is measured), an objective (the target, e.g. 99% < 200 ms), a time window, and a budgeting method; the error budget (1 − objective) MUST be derived, never authored. It MAY carry an optional signal= attribute tagging the SLO by a Four Golden Signals value (latency / traffic / errors / saturation). It MUST render linked to its NFR with click-through (mirroring <spec-risk target>) and MUST degrade gracefully with JS disabled (P-4).

Canonical shape 
<spec-slo target="NFR-001" signal="latency" objective="99%" window="28d" budgeting="occurrences">
  fraction of requests served in < 200 ms (good ÷ valid)
</spec-slo>

The attribute-vs-content split is resolved in plan D-003: the scalars — objective, window, budgeting, and the optional signal — are attributes (so they render via CSS attr() with no JS, per P-4), and the SLI description is the element's content. The error budget (1 − objective) is derived, never authored.

What changes: one sentence is appended naming the legal signal= values and the availability→errors / throughput→traffic mapping. The two-rule enforcement description is unchanged; the enum itself is not widened.

Two schema validate rules MUST keep a <spec-slo> well-formed, at error severity: slo-target-required (a <spec-slo> that omits target= is flagged, mirroring risk-target-required), and slo-well-formed (its target= MUST resolve to an NFR-* requirement in the same document, and the required OpenSLO fields — SLI, objective, window, budgeting method — MUST be present; an unknown signal= value is flagged). The signal= value, when present, MUST be one of the Four Golden Signals (latency, traffic, errors, saturation). Broader reliability terms are expressed through the objective and SLI rather than the signal — for example, an availability objective is typically measured on the errors signal, and throughput on traffic.

5 · Risk register

Populated by the adversarial risk pass (the proposal touches the must-tier FR-001 and FR-002). One <spec-risk> per finding. target= is required; status= defaults to identified — apply refuses until each transitions to accepted, mitigated, or rejected, recorded by= the human who dispositions it.

The first-draft corrected example authored objective="99% < 200ms", merging a ratio and a latency threshold into one attribute — which makes FR-001's retained "error budget (1 − objective) MUST be derived" clause uncomputable, a semantic regression the validator can't catch (slo-well-formed only checks objective is present).

Delta op="modified" target="FR-001", the canonical-shape example vs. FR-001's clause "the error budget (1 − objective) MUST be derived, never authored".

Mitigated: the example now reads objective="99%" with the < 200 ms threshold kept in the SLI content ("fraction of requests served in < 200 ms (good ÷ valid)"), so 1 − 0.99 = 1% stays computable — the semantics the pre-D-003 example had right, now in the correct attribute shape. Confirmed by a live-markup validate round-trip; the §6 verification task pins it. Dispositioned mitigated in the propose interview.

Baking the two-term availability→errors / throughput→traffic mapping into a MUST-tier requirement body elevates a debatable, incomplete editorial claim to normative status, and adds a third un-guarded copy of the golden-signal enum (FR-002 body, §4 data model, GOLDEN_SIGNALS) that can silently diverge.

Delta op="modified" target="FR-002", the appended mapping sentence; enum also duplicated in §4 and packages/schema/src/slo-shared.ts.

Mitigated: the mapping is reworded from a closed normative rule to an illustrative "for example…" so it no longer reads as an exhaustive MUST, while the enumeration of the four signals stays normative (matching the validator). A §6 task adds a drift-guard test tying the documented set to GOLDEN_SIGNALS, closing the divergence surface the finding names. Dispositioned mitigated in the propose interview.

The proposal was too narrow against its own originating card: it taught the vocabulary in FR-001/FR-002/§4/fixHint but left §2's "an availability objective" prose — the exact phrase T-001 names as the tripwire — untouched, so a skimming author still meets the confusing term before reaching the new guidance.

§Scope in-scope list vs. spec.html §2 ("An NFR may carry several <spec-slo> (e.g. a latency and an availability objective)"), the trip T-001's diagnosis pins.

Mitigated: a fourth in-scope item and a §6 task now reword §2 to read as two SLOs ("a latency SLO and an availability SLO (measured on the errors signal)"), closing the confusion at the point an author first meets it — making the reconciliation complete against the card. Dispositioned mitigated in the propose interview.
