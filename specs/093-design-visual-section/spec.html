Design visual section

The design doc gains a home for what a feature looks like — the token set, the screens it touches, and where the design came from.

Status Accepted Spec ID 093-design-visual-section Owner Brian Corbin · @briancorbinxyz Reviewers — Created 12 Aug 2026 Principlesv1.9.0 Smallest demoableRunning /spectastic.design on a spec in a project with a detected UI produces a Visual surface section naming the token file. Read time

The design template has twelve sections and not one says what a feature looks like — the word screen occurs twice across all eight templates and both times means a screenful of prose. A designer's decisions have nowhere to land except a design tool the repository cannot read. This spec closes that from the authoring side, and only from there: the design gains a Visual surface section declaring the token set, the screens the feature touches and where the design came from — and the interview learns to ask. The declaration is about files; it never contains them, which is what keeps one authoritative copy and lets a design tool be a source rather than an authority. Two things make it safe to land ahead of the rest: it appears only where a UI is actually detected, so a CLI or a library never sees it, and a malformed or unresolvable declaration is an error rather than prose nobody checks. For anyone who has watched a review approve a mockup nobody could later prove was built: this is the first artifact that can be contradicted.

1 · Context

The design template's twelve sections cover principles, context, contracts, grounding, approach, alternatives, decisions, structure, risks, complexity and questions. None is about appearance, so a feature with a user interface records its stack and its API and says nothing about what it looks like — leaving the only statement of that in a design tool the repository cannot read and a reviewer may not hold a seat for.

069's contract declaration is the right shape: declare where the real thing lives, keep it a file, let a check confirm the two agree. This applies that shape to the visual surface. It serves the author, who has nowhere to put the decision; the implementer, who reconstructs it from a picture; and the reviewer, who cannot tell a considered visual decision from an unasked question.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · The design declares its visual surface P1

As a design author on a project with a user interface, I want to be asked what this feature looks like and where the token set and screens live so that the appearance is a recorded decision rather than something held in a design tool.

Acceptance: A design run on a spec in a project with a detected UI produces a Visual surface section naming a project-relative token path; the path appears verbatim in the generated design.html.

US2 · A project with no interface is never asked P1

As an author of a CLI or a library, I want to see no visual section at all so that my design is not carrying an empty question I could never answer.

Acceptance: A design run on a project with no UI signal produces no Visual surface section — not an empty one, not one reporting a gap. Nothing is scaffolded and nothing is reported.

Edge cases

  • A project with a user interface that no signal detects — a hand-rolled surface with no framework dependency. The declaration must be authorable anyway, and outrank the absent signal.
  • A project with a UI where this particular feature touches none of it — a caching change behind an existing screen. The section is scaffolded and the honest answer is an explicit none.
  • A feature that changes an existing screen rather than adding one. It declares the same screens, and the change is the design's prose, not a second declaration.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The design template MUST carry a Visual surface section holding the feature's visual declaration.

Rationale

The conceptual model belongs to the spec and the physical shape to the design; a screen is physical. Today it has no home in either.

A design in a project with no detected and no declared user interface MUST NOT carry a populated Visual surface section, and that absence MUST NOT be reported as a gap. The constraint MUST be enforced by a check over the authored artifact rather than by the template, which is a static file and cannot vary per project. Detection MUST key on a declared user-interface dependency or a conventional project file, and MUST fail safe on the antecedent — a project it cannot classify is treated as having no interface.

Rationale

Seeding visual vocabulary everywhere reproduces a failure already paid for: 37 of 61 verify views carry an observables section, every row is a gap, and no SLO was ever authored. Absence, not emptiness. It binds the artifact rather than the template because templates/ is copied verbatim — a template-level "must not scaffold" would leave a model reading markdown as its only owner, which P-8 excludes. verify-view-missing is the precedent for conditional presence as a rule.

Detection MUST consider conventional project files and not only manifest dependencies, so that a project whose user-interface framework ships inside its platform SDK — and is therefore undeclarable — is still seen.

Rationale

A dependency list cannot see SwiftUI, UIKit or AppKit — none is a dependency. A manifest-only heuristic classifies a native Apple app as having no interface, which is the population this spec exists to serve.

An author's declaration MUST outrank detection in both directions: a declared surface stands where nothing was detected, and a declared none stands where something was. Detection MUST continue to run and MUST NOT be switchable off.

Rationale

073 FR-003 settles this for interfaces on identical reasoning: inference cannot see intent, a declaration can. Detection stays on so a project cannot go quiet by forgetting.

The declaration MUST name the project-relative path of the project's token set and of the screens this feature touches. Either MAY resolve to a file or to a directory, since a token set is routinely more than one file. Where the token set extends an external one, the declaration MUST be able to record that the base is external and that the declared path holds only this project's overrides.

Rationale

Different cardinalities, and the one part of the contract chassis that does not transfer: a contract has one owning feature, a design system has none. N designs naming one shared token set would be N declarations of a single thing with no rule for disagreement — the sibling bug declaredInterfaceState already fixes. The directory allowance stops a set split by mode from failing FR-010.

The declaration MUST record where the design came from, as provenance rather than as an authority — the named source MUST NOT be read at validate time, and a project whose source is no longer available MUST remain valid.

Rationale

Five design tools with five incompatible models, two of them with no persistent document to read. Depending on any at check time makes a spec only as portable as somebody's seat.

A feature with no visual surface MUST record that explicitly rather than omitting the declaration — within a section the gate admits, per FR-002.

Rationale

Inside the gate, an empty section and a considered "this feature touches no screen" are indistinguishable. Outside it, there is nothing to distinguish.

The design interview MUST ask whether the feature has a visual surface before asking anything about tokens or screens, and MUST skip those questions entirely where FR-002's antecedent does not hold.

A declaration that is present but malformed — an unrecognised value, or a required attribute absent — MUST be an error. A document carrying no declaration MUST NOT be flagged by that check.

A declared path that resolves to neither a file nor a directory in the project MUST be an error, and one that escapes the project directory MUST be rejected rather than followed.

Rationale

A declaration nothing checks is prose. This catches a token file that moved, which is the likeliest way the declaration goes quietly wrong.

The section SHOULD link the spec's scenarios rather than restating them, and SHOULD carry the reasoning about the surface — what varies, what does not, what a build may rely on — rather than a copy of the token values.

Non-functional

The added interview questions MUST respect the decision-phase limits already in force — at most 4 questions per call, each offering 2–4 options — and MUST be skipped when an upstream artifact or detection already answers them.

The section MUST render with JavaScript disabled: 100% of its authored content — the declaration, every declared path and the reasoning — readable with scripting off.

Rationale

P-4 — progressive enhancement, never dependence.

Detection MUST read only project-root manifests and conventional project files, from a hand-enumerated list of at most 20 paths, none deeper than 4 segments, containing 0 globs, and MUST NOT walk the tree. Its signal list MUST be hand-enumerated too, and every signal MUST be attributable to a named platform or framework rather than matched heuristically. Both bounds MUST be asserted by a test rather than trusted.

Rationale

The path bound is the contract search's, asserted the same way. Alone it would bound the wrong dimension: the sibling INTERFACE_SIGNALS is 43 substring signals over about ten files, so the risk lives in the signal list, not the path count.

Out of scope (deferred to other slices)

  • Where the declared files live, what may be in that directory, and its name.
  • The element family for screens, states and compositions, and their loud gaps. This spec declares that screens exist and where; it does not describe one.
  • Annotations typed by role and state, and the mapping from design-tool categories.
  • The axes a surface varies across — mode, platform, size class — with their contexts, defaults, and a context declined with a reason. Absorbed into this spec at interview time and taken out again: it was the only part resting on a draft module that says not to implement it, and the size gauge called this spec over budget three times running with it in.
  • The operating-system version each platform context was designed and last verified against. This spec declares the platform axis; the baseline on it is a separate decision.
  • Measuring a build against the declared token set.
  • Versioning the declared token set, and what binds forward from a bump.
  • Replacing this spec's detection heuristic with a declared project shape, at which point FR-002's signals become the fallback rather than the gate.
  • Importing a token set from a design tool rather than committing one by hand.

4 · Data model

No persisted entity. This spec adds an authored artifact section and a set of interview answers that populate it.

Entities

Surface declaration
Whether a feature has a visual surface, the project-relative path of its token set, the screens it touches, and the design's provenance. Zero or one per feature; explicitly empty when it touches no screen.
Interface signal
Evidence a project has a user interface: a declared dependency or conventional file, matched within a bounded set of root paths. Never authoritative — a declaration outranks it both ways.

The declaration is about files; it never contains them. That keeps one authoritative copy, lets a design tool be a source rather than an authority, and makes a moved token file a check failure rather than a silent divergence.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For a project with a detected interface, 100% of designs authored through the slash-command path carry a surface declaration naming a project-relative token path, or an explicit no-surface record. Measured on that path only — the deterministic CLI renderer emits its own reduced document and is out of scope here, as it was for 069.

For projects with no detected and no declared interface, the count of designs carrying a populated Visual surface section is 0, the count of reported visual gaps is 0, and each of those counts is produced by a check rather than asserted.

Every declared path either resolves to a file in the project or produces exactly one error finding. The count of declared paths that neither resolve nor report is 0.

A reader who opens a generated design in a browser can state, without opening any other file, whether the feature has a visual surface, where its token set lives, and which contexts it deliberately does not support.

6 · Assumptions

A dependency or a project file is an adequate proxy for "this project has a user interface" until a declared project shape exists. It will produce false negatives — a hand-rolled surface with no framework dependency is invisible — and FR-004's declaration is the escape hatch rather than a wider heuristic.

Authors know, at design time, which screens a feature touches. Where they do not, that is a genuine open question for that design rather than something this spec can resolve.

Declaring a path is cheap enough that authors do it honestly. If not, FR-010 is the enforcement half — and it catches only a wrong path, never a missing declaration inside a scaffolded section.

7 · Open questions

One outstanding, and it does not block estimation — it is bounded by a sibling slug and changes nothing this spec builds. The gate, the explicit-none boundary, the scope against the siblings and the decision to carry both checks were anchored in the interview. The project-shape axis is settled rather than deferred: when it lands, a declared shape outranks these signals and the signals keep running, per FR-004.

  1. Where a local component wraps an external one, does the external origin, version and licence chain onto the wrapper or stay at the import? Recorded twice, the copies can disagree; recorded once, the wrapper looks locally owned when it is not. Bounded by 097-visual-component-lifecycle, which owns origin as a property.
