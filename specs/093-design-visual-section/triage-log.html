Cards

FR-014 makes the filesystem the authority, which 094 exists to deny — and breaks its NFR doing it

Cross-spec upstream

Debugging which set of screens a design owes an introduction to, root cause was that the check derives it by enumerating a directory the neighbouring spec says nothing may enumerate; fixed by deriving the set from the declaration; regeneration fails, because no requirement records the reversal and 094 still says the opposite.

Expected
094 §4, verbatim: "Neither directory is a registry. Nothing enumerates their contents, and a file present but undeclared is invisible to every check here — … the reason the declaration rather than the filesystem is the authority."
Actual
FR-014 obliges a design to introduce each screen that surface addresses, and its check derives that set by enumerating the declared path. Where the path is a directory — the normal case, since 094 puts a feature's screens in one and permits subdividing it — the declared set and the enumerated set are different sets. The declared set is what the author claimed; the enumerated set is whatever is on disk.

It also breaks 094 NFR-001 outright: "at most 1 filesystem call per declaration, and at most 0 directory walks". The check needs a walk and then must read and parse every file it finds to recover the ids. Today's resolve check honours that budget by stat-ing and never reading.

Diagnosis
My register raised the cross-file reach and accepted it as "the intended behaviour". The half it never examined is which set is authoritative. Accepting a drift check assumes the enumerated set is the addressed set — which FR-005 does not say and 094 §4 denies by name. 094's changelog carefully records the one place 093 took over a check it had specified; this reversal is recorded nowhere.
Fix
specs/093-design-visual-section/spec.html — a propose. Derive the obligation from what the design declares rather than from disk, so declaration stays the authority and the NFR holds. If enumeration is genuinely wanted, it is a MODIFY on 094 §4 and NFR-001, argued there.
Fixed
Applied 2026-08-14-declaration-is-the-authority. The check now reads what the design declares rather than walking the directory, which restores 094 §4's authority rule and keeps NFR-001's zero-directory-walks budget. It also dissolves the exclusion-zone hazard: reading declarations never searches text the generated view writes into the element being scanned. Severity is stated as an error, matching both siblings.
Deep dive — three more from the same pass

The check must exclude a region the tool generates into the element it scans. 099 materialises a table of exactly these identifiers inside the declaration. So the scan needs an exclusion zone around generated content — the shape this estate already paid for once, when 048's verify-view-stale counted a gap row's own anchor as evidence of the link it was reporting missing. A task names the hazard; the requirement does not, so a correct-looking implementation can be wrong.

No severity. FR-014 says a missing introduction "MUST be reported". Its siblings FR-009 and FR-010 both say "MUST be an error". At error severity this blocks the pre-commit gate on missing prose; at warning it is the advisory the proposal explicitly refuses to ship. Nobody chose, and whoever writes the rule will.

The boundary reads differently from each side. 093's own out-of-scope defers the screen element family and their loud gaps to 095 by name — "this spec declares that screens exist and where; it does not describe one" — and FR-014 takes both back without amending the deferral. The requirement leg belongs here; the enumerate-and-report leg belongs beside 095's other screen checks.

An assumed fact made load-bearing. 093 §6 assumes "authors know, at design time, which screens a feature touches", with an open question as the stated escape. FR-014 makes that assumption load-bearing and removes the escape in one move — an open question does not clear a set comparison. KB-0001@2026-07-25 requires an explicit accepted risk naming who accepted such a gap; none was recorded.

The correction repeals the requirement it corrects, and its central fact is false

Specupstream

Debugging what the corrected FR-014 actually checks, root cause was that a design declares a path and no screens, so the quantifier ranges over the empty set; and the NFR the reversal was justified by is already broken elsewhere in the same pass.

Expected
Per the correction: "the obligation stays exactly as strong for the case that motivated it — a design that names a path and describes nothing still fails."
Actual
It does not. The design the whole thing was written from declares a screens path and introduces zero screens by name — its prose says "One screen, ten states" while the generated view below it projects three. Under the enumerating version that fails, which is why the change existed. Under the correction the declaration declares no screens, nothing is introduced, nothing can fail to resolve, and it passes silently — including the one-versus-three drift. Not a correction of the check's authority; a repeal of its only effect, now recorded in the live spec as a deliberate refusal a future author must argue past.
Diagnosis
"Each screen it declares that surface addresses" has no referent. <spec-visual> is attributes and free prose; the only per-screen structure that has ever existed inside it is the generated view. All three implementations available are wrong: read the generated view and the tool's own output becomes evidence the author authored; scan prose and it is the text scan the correction claims to dissolve; add per-screen declarations and it duplicates the sidecar against FR-005.

And the load-bearing fact is false. materialiseVisualViews already does fs.readdir on the declared screens path and parses every file it finds, unconditionally, in the same validate pass. So the zero-directory-walks budget the reversal was justified by is already spent — the capability given up was traded for nothing, and the task asserting no walk occurs cannot hold.

Fix
Stop. Decide what a design structurally declares about screens before writing any requirement over it.
Re-grounded — 14 Aug, every claim checked against source
Verified true. <spec-visual> carries a screens path and no per-screen structure, so the quantifier has no referent. And the concrete charge holds exactly: in examples/currency-converter/…/design.html the two distinctive screen ids pairs and convert-unmapped occur zero times outside the generated <spec-visual-view> — they exist only in the tool's own output — while the authored prose says "One screen, ten states" three times and the view projects three. materialiseVisualViews does readdir the declared path and read every file, unconditionally, in the validate pass.

Wrong in two places, both already corrected elsewhere. The NFR claim: 094 NFR-001 governs path resolution, and materialisation is bounded separately by 099 NFR-003, which explicitly permits reading up to 20 screens — so the budget was never exceeded and no capability was traded to protect it (see 094/T-005). And the third rejected option: adding per-screen declarations does not offend FR-005, which requires the declaration to name paths and prohibits nothing about naming screens.

And the finding neither the card nor the correction it indicts ever made: FR-014 has never been implemented. No rule in packages/schema/src/rules/, no scan in validate.ts, and git log -S"introduce each screen" returns nothing. Validating the exemplar fires exactly three rules — visual-resolve, visual-section-gated, visual-view-drift — and none of them is a screen-introduction check.

So this card's headline is the wrong shape. The correction did not repeal an effect; there was never an effect to repeal, in either wording. Two rounds of proposals argued over the phrasing of a must-tier requirement that nothing has ever enforced — which is the more useful defect, and the one that survives. The referent question is real and still open; it is now plainly a build question rather than a wording one, and any propose that only restates FR-014 will change nothing observable.
