Change proposal · 093-design-visual-section

Declare the variant grid

The declaration names the token set and the screens, and has no word for the grid they vary across — so the one requirement that asks a feature to declare its coverage has no way to be met.

Status Applied Change ID 2026-08-13-declare-the-variant-grid Spec 093-design-visual-section Author Brian Corbin · @briancorbinxyz Created 13 Aug 2026 Targets 4 requirements Read time

Widens the surface declaration to name the project's variant grid and the contexts this feature addresses on it. Modifies FR-005 (what the declaration names) and FR-010 (what resolution means for the new path), and adds two requirements for the coverage half — the optional record, and the check that it is not wrong. No behaviour is removed, and a design that declares no grid stays valid.

Declare the variant grid

Applied

1 · Intent

096 FR-008 says the grid "SHOULD be project-scoped, with a feature declaring which of the project's contexts it addresses rather than inventing its own set." There is no mechanism for either half. <spec-visual> carries shape, tokens, tokens-external, screens and source, and nothing for the grid — so a project has one project-scoped artifact it cannot point at.

The consequence is not only that the requirement is unmet. The grid falls outside every check the other two declarations get: FR-010's resolve-and-contain check cannot see a path it is never given, and 094 FR-004's disagreement check — which exists precisely because a project-scoped artifact named by N designs needs a rule for when they disagree — cannot see it either. The grid is the third project-scoped thing and the only one with no rule for disagreement. The worked example shows what that looks like in practice: it names visual/variants.html in a prose table cell, where a rename would break it silently, and where it already did — three stale filenames in that exemplar were found and fixed by hand this week (I-060), two of them inside files nobody reads as prose.

2 · Scope

In scope

  • An attribute on the surface declaration naming the project's variant grid, resolved and contained exactly as the token set and the screens are.
  • An attribute declaring which of the grid's contexts this feature addresses, in the axis-and-context grammar the grid already uses.
  • A resolution rule for the new path: unlike a token set, a grid resolving to a directory is an error.
  • The reader half — both attributes are read and surfaced, and a malformed declaration is reported. An absent grid or coverage declaration is not a finding.
  • A third cross-file check in the kernel, beside the existing resolve and disagreement checks: a declared context is compared against the project's grid, which means reading a second file and therefore cannot live in the pure schema rules.

Out of scope

  • What a grid contains — axes, contexts, defaults, resolution order, declines and baselines. This change points at the file; 096 describes it.
  • Rendering the addressed contexts anywhere. This change makes the coverage declarable and checkable; showing it to a reader belongs to the embedded view.
  • Resolving a context to concrete values and measuring a build against that cell.

3 · Approach

Two attributes, no new element. The grid path joins tokens and screens as a sibling attribute, so it inherits the reader, the resolve check, the containment check and the disagreement check without any of them learning a new shape. The coverage declaration borrows the axis=context grammar <spec-same axes="…"> already uses, so a reader meets one syntax rather than two.

Both attributes have to render with scripting off, and the element has two pseudo-elements already spoken for. spec-visual::before composes tokens · screens, with a same-specificity [tokens-external] variant decided by source order, and ::after carries source. NFR-002 requires 100% of the authored content readable without scripting, so the two new attributes compose into those same two slots rather than asking for a third — the grid path into the header line, coverage alongside the provenance chip. That roughly doubles the selector count on each, which is a cost worth naming here so it is not rediscovered as a surprise; the existing block already carries the same source-order technique and a comment explaining it.

A grid resolving to a directory is an error, and a token set is not. That divergence is deliberate and worth stating plainly, because the two rules now sit side by side. A token set split one file per mode is the normal case, which is why the existing check is silent for it. A grid is a single declaration of axes in an explicit resolution order — 096 FR-001 requires that order be explicit, and 096's design deliberately took the order from source position rather than an attribute so a number could never disagree with the markup. Splitting a grid across files would split the order and put it back in exactly the ambiguity that decision avoided. The constraint is on the declared path, not on how a project lays out its directories — 094 FR-008's freedom to subdivide either sidecar directory is untouched, because a grid file may sit at any depth inside visual/.

Declaring a grid is not obliged, and declaring coverage is not either. No requirement anywhere makes a project have a variant grid — 096 FR-008 governs the grid's scope, not its existence — so the declaration must be able to name one without demanding it. A single-axis project that had to author a fictional grid to clear an error would be doing the busywork 096 FR-006 exists to refuse. The same reasoning applies one level down to coverage, and harder: recording nothing means nobody asked, never everything. The tempting shortcut — absence reads as full coverage — would make silence carry two meanings at once, which is the failure 096 FR-006 and this spec's own FR-007 both exist to prevent, and it would have a design silently claim coverage of a context the project has explicitly declined.

The unknown-context check is a new cross-file scan, and saying so is the point. The grid's own <spec-same> resolution cannot be reused: that rule is per-file and returns at its first line when the document carries no grid element, and a design never carries one — the grid is a separate file at project scope. So checking a declared context against the grid means reading another file, which puts it in the kernel beside the resolve and disagreement checks rather than in the schema package, whose rules are pure and read nothing. What is reusable is the grammar, not the resolution: the axis=context pair syntax is the same one a reader already knows, so nothing new has to be learned even though something new has to be built.

4 · Deltas

What changes: the declaration gains the ability to name the project's variant grid, and the directory allowance is stated per-path rather than granted to every path. Naming a grid is a capability, not an obligation — the token set and the screens stay required, the grid does not.

The declaration MUST name the project-relative path of the project's token set and of the screens this feature touches, and MUST be able to name the path of the project's variant grid. The token set and the screens MAY resolve to a file or to a directory, since a token set is routinely more than one file. Where the token set extends an external one, the declaration MUST be able to record that the base is external and that the declared path holds only this project's overrides.

Rationale

Different cardinalities, and the one part of the contract chassis that does not transfer: a contract has one owning feature, a design system has none. N designs naming one shared token set would be N declarations of a single thing with no rule for disagreement — the sibling bug declaredInterfaceState already fixes. The grid is the third project-scoped artifact and was the only one the declaration had no word for, so it alone fell outside FR-010's resolve check and 094 FR-004's disagreement check. It is a capability rather than an obligation because nothing anywhere requires a project to have a grid — 096 FR-008 governs the grid's scope, not its existence — and a single-axis project forced to author a fictional one to clear an error would be doing exactly the busywork 096 FR-006 refuses. The directory allowance is stated per-path rather than blanket because a grid must not take it.

What changes: adds the grid's resolution rule — a path to a single declaration whose order is positional cannot be a directory — and requires the finding to say why.

A declared path that resolves to neither a file nor a directory in the project MUST be an error, and one that escapes the project directory MUST be rejected rather than followed. A declared variant grid path resolving to a directory MUST also be an error, and the finding MUST say why rather than reporting only a type mismatch.

Rationale

A declaration nothing checks is prose. This catches a token file that moved, which is the likeliest way the declaration goes quietly wrong. The grid diverges from the token set deliberately: a set split one file per mode is normal, but a grid is one declaration of axes in an explicit resolution order, and 096 FR-001 requires that order be explicit. 096's design took the order from source position precisely so a number could never disagree with the markup; a grid spread across a directory would have no source position and would reintroduce that ambiguity. This constrains the declared path and not a project's directory layout, so 094 FR-008's freedom to subdivide either sidecar directory is untouched. The finding names the reason because "expected a file" does not tell an author what they have actually broken.

The declaration SHOULD be able to record which of the project's declared contexts this feature addresses, naming them in the same axis-and-context grammar the grid itself uses, and SHOULD be able to record that it addresses all of them. An absent coverage record SHOULD read as not recorded — neither a claim of full coverage nor a claim of none.

Rationale

The second half of 096 FR-008, which had no mechanism: a feature supporting fewer contexts is expressing coverage, not a different grid. Borrowing the grammar <spec-same axes="…"> already uses means a reader meets one syntax rather than two. The silence rule is the load-bearing half and it took two attempts to get right: reading an absent record as full coverage would make silence mean both "answered: everything" and "nobody asked", which is precisely what 096 FR-006 and this spec's FR-007 exist to prevent, and it would have a design silently claim coverage of a context the project has explicitly declined with a reason. Reading it as none would be worse — every design in the estate would declare zero coverage the day this lands, the failure the observables trace already paid for once. So absence is a third value, and a feature that wants to claim the whole grid says so. Should-tier because it mirrors the should-tier requirement it realises.

Where a coverage record is present, a named context the project's grid does not declare MUST be an error, and so MUST a named context the grid declares as declined.

Rationale

Recording coverage is optional; recording it wrongly is not. Split from FR-012 rather than embedded in it, because a should-tier requirement whose body carries absolute obligations is unreadable to anyone — human or tool — filtering by conformance level, and every should-tier requirement across this family uses the should form throughout. The declined case is the one worth stating separately: an unknown context is a typo, while claiming a context the project has deliberately refused is a disagreement, and both should stop the build for the same reason the grid records a decline with a reason at all. This check cannot be a schema rule — it must read the grid, which is a different file at project scope — so it lands in the kernel beside the resolve and disagreement checks.

Accepted in full and the delta was rewritten before this register was written. The finding also caught the estate impact: exactly one authored design declares shape="screens" today, plus two fixture declarations the task list had not mentioned updating, and all three would have started reporting on the day this landed.

FR-012's silence rule makes an absent contexts= a positive claim of full coverage, so a design nobody ever asked the coverage question of is indistinguishable from one that answered "every context" — the precise two-meanings-for-one-absence failure 093 FR-007 and 096 FR-006 both exist to prevent, and it asserts coverage even of contexts the project-scoped grid has declined with a reason.

Live 093 FR-007 — "A feature with no visual surface MUST record that explicitly rather than omitting the declaration" — against the added FR-012: "Recording nothing MUST mean the feature addresses the grid as declared, never that it addresses no context."

Accepted; the rule was inverted. The original wording cited 096 FR-006 approvingly in its own rationale while breaking it, which is the worst version of this mistake. Absence is now a third value — not recorded, neither full coverage nor none — and a feature claiming the whole grid says so explicitly. The declined half became its own obligation in the new FR-013: claiming a context the project has refused is a disagreement, not a typo, and reads differently.

The scope is too narrow for what FR-012 commits: the unknown-context check cannot come from the shape rule or from reusing 096's resolution, because variantSameResolvesRule is scope: 'per-file' and returns at its first line when the document carries no <spec-variant-grid> — and a design never carries one, since the grid is a separate project-scoped file — so the slice silently commits a new cross-file, filesystem-reading core scan (the third such check, alongside resolve and disagreement) that no scope item names.

§2 In scope, item 4: "The reader half — both attributes surface in the shape check, so a malformed declaration is reported rather than ignored." Contradicted by packages/schema/src/rules/variant-same-resolves.ts:27 — if (findAll(doc.ast, GRID_ELEMENT).length === 0) return findings; — and by task 6's instruction to "reuse the axis-and-context resolution in variant-same-resolves.ts".

Accepted, and this one was a factual error rather than a judgment call — the reuse claim was made without reading the rule's first line. §2 now names the third cross-file kernel scan as its own scope item, §3 states plainly that the grammar is reusable and the resolution is not, and the task list moves the check to the kernel. The slice is genuinely larger than it read; that is the honest size.

FR-012 is authored at priority="should" while its body carries two bare <spec-rule>MUST</spec-rule> obligations, which contradicts the committed conformance-keyword fact that MUST is absolute and its absence a defect while SHOULD is a strong recommendation one may document a deviation from — and defeats the same document's stated purpose for the wrapper, since a tool grepping must-tier requirements would miss both absolute clauses; every should-tier requirement across 093/094/095/096/097/098 uses level="should" exclusively.

Its absence is a defect… makes the conformance level machine-greppable". Contradicted by the added FR-012: <spec-requirement id="FR-012" priority="should"> containing "A named context the grid does not declare MUST be an error."

Accepted. The mixed-tier requirement was split: FR-012 is should-tier throughout and describes an optional capability; the absolute clauses became must-tier FR-013. Recording coverage is optional, recording it wrongly is not, and those are two requirements rather than one sentence pretending to be both.

None outstanding.
