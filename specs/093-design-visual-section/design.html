Design · 093-design-visual-section

Design visual section

How we will build it.

Status Accepted Spec 093-design-visual-section Owner Brian Corbin · @briancorbinxyz Branch spec/093-design-visual-section Created 12 Aug 2026 Read time

One <spec-visual> element in a new section of the design template, checked by two rules split along the boundary the rule engine already forces — shape is pure-AST and lives in @spectastic/schema, path resolution touches the filesystem and lives in @spectastic/core as a folded scan. Detection gains a user-interface signal list plus one read of the project root, because the marker for a native Apple app is a directory whose name the project chooses. The biggest risk is not technical: this spec and 094 state the same resolve requirement, so the check must land here once and be inherited there rather than built twice.

3 · Data model & contracts

The spec's two conceptual entities land as authored markup and a hand-enumerated table. Neither is persisted; both are read at check time and discarded.

Conceptual entityPhysical shapeNotes
Surface declaration <spec-visual shape tokens screens source> — one element, three optional attributes beside the required shape. Zero or one per design. shape="none" carries no path and is the explicit-empty form FR-007 requires.
Interface signal readonly FileSignal[] beside the existing INTERFACE_SIGNALS, plus a suffix list matched against one read of the project root. Held separate from the web/RPC signals, exactly as EVENT_INTERFACE_SIGNALS is, because a caller needs to know which kind fired.

This feature exposes no interface. It adds an authored section, two checks over it, and a widening of an existing detector — all consumed inside the tool. The <spec-visual> element is a vocabulary for artifacts, not a wire format: nothing serialises it, nothing transmits it, and no consumer outside this repository reads it.

5 · Approach

The work divides into four pieces that follow existing seams rather than cutting new ones. A new section in the design template scaffolds one <spec-visual> element. A reader in @spectastic/core extracts declarations from a design's HTML by attribute, degrading to "declares nothing" on anything malformed, and accumulates across specs the way declaredInterfaceState does. A shape rule in @spectastic/schema fires only on a declaration that is present and malformed. A pair of scans in @spectastic/core, folded into validate by a thin CLI wrapper, checks that each declared path stays inside the project and points at something real, and that no project without an interface is carrying a populated section. Detection widens with a user-interface signal list and one read of the project root.

Nothing here is novel; all four pieces have a working sibling in the contract chassis, and the value of going first is finding out where the clone is not verbatim. Two places it is not: a declared token-set path may resolve to a directory, where a contract path may not; and the presence check is conditional on a project property rather than on a document's own status, which is what pushes it out of the rule engine altogether — it borrows verify-view-missing's shape but not its home.

This design carries no Visual surface section, and that is the requirement working rather than an omission. spectastic is a CLI and three libraries: no user-interface dependency, no conventional project file, so FR-002's antecedent does not hold and the section must be absent rather than empty. The first artifact to exercise the section is the currency-converter exemplar under examples/, which is why that bundle exists.

6 · Alternatives considered

7 · Decisions

D-001 · Shape is a schema rule; resolution is a core scan folded into validate

Status
Accepted
Context
The rule engine is pure-AST with no filesystem imports — contract-declaration-shape.ts states this in its own header and its imports confirm it. FR-009 checks markup and FR-010 checks the filesystem, so they cannot live in one place.
Decision
Clone the contract chassis exactly: visual-declaration-shape as a per-file schema rule, and visualResolveFindings in core taking an injected FileSystem port, folded in by a thin scanVisualResolve in the CLI.
Consequences
+ Two testable units, both importable without a binary. + The split is forced by an existing constraint, so it cannot drift. − Two files and two test suites for what reads like one check, and a reader has to know which half reports a given finding.

D-002 · The section goes at slot 4, and the numeric cross-references become named ones

Status
Accepted
Context
Grouping the three physical-shape declarations — data, interface, surface — puts the section at 4. But FR-002 makes it conditional, so with it at 4 every later number is right for interface projects and wrong for everything else. 21 numeric references point at those sections: 7 in templates/design.html, 14 in commands/spectastic.design.md. The spec template already carries the fix as an instruction — "referred to by name rather than number so a renumber cannot break the pointer" — and applies it to itself.
Decision
Place the section at slot 4 and convert all 21 numeric references to named links in the same change. A number that cannot be correct for both populations is not a number worth keeping.
Consequences
+ The next insertion breaks nothing. + Both populations read a correct document. − Touches two files this spec would otherwise not open, and the diff is larger than the feature. − Section numbers still differ between projects; only the references are immunised, so a human citing "§7" in review is on their own.

D-003 · Absence is checked on the artifact, never instructed in the template

Status
Accepted
Context
templates/ is copied verbatim, so a template cannot vary per project and a template comment saying "delete this section if you have no interface" is advisory — the exact thing P-8 and triage T-009 exclude as a home for a must-tier guarantee. verify-view-missing is the precedent for conditional presence — but only for its shape, not its home: it derives its condition from the documents it is handed, whereas this condition is filesystem state, which the rule engine cannot read.
Decision
The template scaffolds the section unconditionally; a second core scan, folded in beside the resolve one, reports a populated section in a project with no detected and no declared interface, and reports nothing at all when the section is absent. The template comment explains, it does not guarantee.
Consequences
+ The guarantee is machine-checked at the git boundary. + A non-interface project deletes one section once and is never nagged. − Both visual checks now live in core rather than one in each package, so @spectastic/schema owns only the markup half. − A freshly scaffolded non-interface design is momentarily non-conformant, which is a worse first impression than a template that had simply omitted it — mitigated by the finding naming the deletion as its fix.

D-004 · One read of the project root, matched against hand-enumerated suffixes

Status
Accepted
Context
FR-003 exists because SwiftUI, UIKit and AppKit ship in the platform SDK and appear in no manifest. The spike enumerated every fixed-name candidate: Package.swift is SwiftPM-only and names no UI framework, Info.plist and Assets.xcassets are conventionally nested, and project.pbxproj lives inside a directory the project names. The only root-level marker is the .xcodeproj / .xcworkspace suffix.
Decision
Read the project root's own entries once and match them against a hand-enumerated suffix list, alongside the existing fixed-name signals. Depth 1, no glob engine, no tree walk.
Consequences
+ The population FR-003 was written for is actually seen. + The suffix list is as auditable as the filename list beside it. − NFR-003 says detection reads "from a hand-enumerated list of at most 20 paths", and a directory read is not on that list; this design takes the bound to mean no tree walk and no glob, which the mechanism honours, and states the reading rather than assuming it. − The test must assert a fourth bound — at most 1 directory read — or the loosening is unbounded.

D-005 · A declared token-set path may resolve to a directory; a contract path may not

Status
Accepted
Context
contractResolveFindings flags a directory as "names a directory, not a readable file", because a contract is one file. FR-005 says the opposite for a token set: it is routinely split by mode, so a directory is the normal case.
Decision
Clone the containment and stat sequence verbatim and invert the directory branch — silent for a visual path, where it is an error for a contract. Keep the absent and unreadable branches identical.
Consequences
+ Containment logic, the security-relevant half, stays byte-identical to a reviewed implementation. − Two nearly-identical functions that differ in one branch, which invites a later "refactor" that reintroduces the wrong behaviour; the test names the difference so the invariant is legible.

D-006 · The resolve check lands here once, and 094 inherits it

Status
Accepted
Context
FR-010 and 094's FR-003 state the same requirement in almost the same words. 093 cannot defer it — a declaration nothing checks is prose, which is its own stated rationale — and 094 cannot drop it, because it is the convention document.
Decision
Build it here. 094's implementation adds only what is genuinely its own: the two directory names, the disagreement check across designs, and the image rules. Its changelog records the inheritance so the duplication reads as deliberate.
Consequences
+ One implementation, one test suite, no divergence. + 094 gets smaller, which suits a convention slice. − Two specs describe one check, so a reader of 094 alone will look for code that is not there; only the changelog note prevents that.

10 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here.

The 21-reference sweep in D-002 is not required by any requirement in the spec. It is required by the section's conditionality: placing a conditional section anywhere but last makes every later number ambiguous, and the alternative — a slot near the end — was weighed and lost on the grouping argument. Doing the sweep in the same change is what keeps the choice honest, since a follow-up "we should fix the references" is the kind of task that never gets drained.

D-004 reads NFR-003's path bound as prohibiting tree walks and globs rather than prohibiting a single read of the project's own root. That reading is stated rather than assumed, and the mechanism is bounded by a test. If a reviewer disagrees, the fix is a one-line MODIFY to NFR-003 while the spec is still Draft, not a redesign.
