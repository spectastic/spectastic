Design · 074-contract-checked-tier

Contract-checked tier

How we will build it.

Status Accepted Spec 074-contract-checked-tier Owner Brian Corbin · @briancorbinxyz Branch main Created 01 Aug 2026 Read time

Tighten the existing contract-first category rather than adding a tenth: at verified and above, holding a contract also requires a configured linter and a configured differ. Detection follows the coverage precedent exactly — match a declared configuration (a ruleset file, a CI invocation), never a bare dependency, so presence never falsely certifies the floor. AsyncAPI's thinner tooling is handled by the same per-capability advisory mechanism 073 uses, and the no-predecessor case resolves as configured is enough, which the spec's own register now records.

3 · Data model & contracts

No persisted entity. Two lookup tables and one per-contract verdict, all derived per run.

Conceptual entityPhysical shapeNotes
Configured check A signal entry — a ruleset filename, or a manifest/CI string Two kinds, linter and differ. Matches a declared configuration, never a bare dependency (D-002).
Format capability Partial<Record<format, readonly ('linter'|'differ')[]> Which halves have no mainstream tool for a given contract format — today AsyncAPI's differ. Clones STRUCTURALLY_UNDETECTABLE's shape (D-003).
Per-contract verdict Derived — { path, format, linter, differ } with each half covered, missing or advisory FR-004 requires the report distinguish which half and which contract, so the verdict cannot collapse to one boolean.

No interface. This slice reads configuration files and reports; it exposes no endpoint, event or schema. Worth stating plainly given the subject matter — spectastic checks contracts, it does not publish one.

5 · Approach

No tenth category. contract-first gains a second, tier-gated condition: at verified and above, a project that holds a contract must also show a configured linter and a configured differ. Detection is a signal table in the coverage mould — a Spectral ruleset file, an oasdiff or buf invocation in CI, a buf.yaml with a breaking stanza — matching declared configuration rather than a dependency, so a project that merely installed a tool is not certified.

Two carve-outs keep it honest. Where a contract's format has no mainstream tool for one half — AsyncAPI diffing today — that half reports at advisory strength with the limitation stated, using the same per-capability map shape STRUCTURALLY_UNDETECTABLE already established. And a first contract with no predecessor satisfies the differ half provided a differ is configured: the category asserts a check is configured, never that it has run or passed, which FR-005 requires the copy to say out loud. Reporting is per contract and per half, so a project with a linted OpenAPI file and an unlinted proto sees exactly which one is short.

6 · Alternatives considered

The load-bearing choice is where the rung lives. Scored 1–5, higher is better.

OptionFits the axis ladderReuses machineryReport clarityTotal

Tighten contract-first at verified+ — chosen55414

A tenth category is the obvious shape and the wrong one: contracts is a posture ladder (informal → contract-first → contract-checked → versioned+governed), and a rung on a ladder is a tightening of the rung below, not a parallel category that could be satisfied independently. Axis-only scores well on cost and fails the spec — an advisory vocabulary is what exists today, and FR-001 asks for teeth.

7 · Decisions

D-001 · Tighten contract-first; do not add a category

Status
Accepted
Context
The contracts profile axis ladders informal → contract-first → contract-checked → versioned+governed. detect.ts:415-417 shows contract-first is interface-gated and fails safe on the antecedent, which is exactly the property a tightening must inherit.
Decision drivers
Fidelity to the posture ladder · reuse of the interface gate · clarity of the gap report
Considered options
  • A tenth contract-checked category — + a clean separate tally. − Breaks the ladder metaphor; two categories could disagree about the same contract.
  • Axis value only, no check — + zero cost. − Leaves the rung advisory, which is what already exists.
  • Tighten contract-first at verified+ — chosen — + inherits the interface gate and the ladder. − One category now means two things by tier.
Decision
A second tier-gated condition inside contract-first: at verified and above, holding a contract also requires a configured linter and differ.
Consequences
+ Inherits the fail-safe antecedent for free, so a project with no interface is untouched. + The ladder stays honest. − The category's meaning is now tier-dependent; the report must say which condition failed, which FR-004 requires anyway.

D-002 · Detect declared configuration, never a bare dependency

Status
Accepted
Context
FR-002 is explicit. The coverage category set the precedent for the identical problem: it matches a declared threshold, never a coverage library, because presence must never falsely certify a floor.
Decision
Signals match a configuration artifact — a Spectral ruleset file, a buf.yaml breaking stanza, an oasdiff or buf invocation in a CI workflow — not a package-manifest entry.
Consequences
+ A project that installed a linter but never configured it is correctly reported short. + Same shape as coverage, so a reader who knows one knows the other. − A team configuring a tool in an unrecognised way is a false negative; recorded as a ceiling, consistent with the other categories.

D-003 · Capability limits are a per-format map cloning the existing mechanism

Status
Accepted
Context
FR-003 requires a half with no mainstream tool to report advisory and not hard-fail. policy.ts:36,124 already carries STRUCTURALLY_UNDETECTABLE as an injectable per-category map, twice extended. The event-driven survey establishes AsyncAPI diffing as today's real gap.
Decision
A sibling map keyed by contract format rather than ecosystem, listing which halves are capability-limited; the affected half reports advisory with the limitation stated.
Consequences
+ Reuses a proven shape and an injectable-for-tests pattern. + The rung never promises parity it cannot deliver, which the survey warned against. − Two similar maps now exist (by ecosystem, by format); named distinctly and documented so they are not conflated.

D-004 · Detection reads config files and never invokes a tool

Status
Accepted
Context
NFR-001 caps detection at 0 network calls and 0 tool invocations — unusually explicit, and a direct P-12 capability bound. Running spectral --version to prove configuration would breach both determinism and that bound.
Decision
Pattern-match configuration files and CI definitions as text. No subprocess is spawned under any circumstance.
Consequences
+ Deterministic, fast, and safe to run against an untrusted checkout. + No dependency on the tool being installed. − Cannot tell a valid ruleset from a malformed one; the category claims configured, never working — the ceiling FR-005 already requires be stated in copy.

D-005 · A first contract satisfies the differ half when a differ is configured

Status
Accepted
Context
The spec's register carried this as its one open question; it was settled in the design interview and the register now records the resolution. FR-002 defines detection as recognising declared configuration, and FR-005 forbids claiming a check passes.
Decision
A configured differ satisfies the half regardless of whether a predecessor exists. No configured-but-not-yet-exercised state is introduced.
Consequences
+ A project's first interface can reach the rung, which the alternative would have made impossible. + No third state for consumers to handle, and no other category carries one. − The rung says nothing about whether a diff has ever run; precisely what FR-005 requires the copy to admit.

9 · Risks & mitigations

RiskLikelihoodImpactMitigation
A verified project that was passing suddenly fails, reading as a surprise regressionHMIntended by FR-001 — but only for projects that hold a contract, and the antecedent gate means no interface-free project is touched. The gap names both halves so the fix is obvious, and the waiver mechanism remains available for a justified delay.
The signal set misses a legitimate configuration and false-fails a well-run projectMHThe worst outcome here, since this is a hard floor at verified. Signals are drawn from the mainstream tools named in the survey, each with a fixture; the waiver path exists; and the ceiling is recorded rather than pretended away.
Reading CI workflow files to find an invocation is brittle across CI systemsMMMatching is a filename-plus-substring test over known workflow locations, the same shallow technique the other categories use — not YAML semantics. A miss is a false negative, which fails safe.

10 · Complexity tracking

The advisory carve-out is not a P-9 relaxation. P-9 forbids lowering a floor because it is inconvenient. D-003 lowers nothing: it declines to raise a floor for a format where the ecosystem has no tool to satisfy it, which is the same reasoning STRUCTURALLY_UNDETECTABLE already encodes for Go coverage and Swift observability. The carve-out is keyed to a named capability gap, not to a project's preference, and no project can opt into it. Stated here because "advisory" and "relaxed" look alike from a distance.

Configured is not passing, and the copy must say so. Detection proves a ruleset exists, not that it is valid, runs, or blocks a merge. FR-005 makes that an explicit copy requirement rather than an implicit ceiling, which is the honest form — the same posture the security and observability categories already take about present-versus-wired.

Requiring a differ to actually block is out of scope and stays so. The spec lists it, and this design does not smuggle it in. Detecting that a CI step is required rather than merely present means reading branch-protection settings, which is a network call and a different capability entirely.
