Specification · 074-contract-checked-tier

Contract-checked tier

Give the contract-checked rung mechanical meaning — a linted contract and a breaking-change diff — without promising for events what the tooling only delivers for REST.

Status Accepted Spec ID 074-contract-checked-tier Owner Brian Corbin · @briancorbinxyz Reviewers — Created 31 Jul 2026 Principlesv1.9.0 Smallest demoableAt the verified tier, spectastic enforce reports a gap when a project has a contract but no configured contract linter or breaking-change differ. Read time

The contracts profile axis already ladders informal → contract-first → contract-checked → versioned+governed, and nothing reads any rung of it. contract-first now has teeth; this spec gives the next rung the same. Checked means two commodity things a project either wired up or did not: the contract is linted against a style ruleset, and it is diffed against its predecessor for breaking changes. Both are mature, permissively-licensed tools with CI actions, so the enforcement engine's job is to detect that they are configured — the same posture the coverage category takes toward a declared threshold rather than a coverage library. The honest complication is that this parity does not hold across formats: linting and diffing are commodity for OpenAPI and thinner for AsyncAPI, thinner still for its current major version. So the rung is defined per format, with the gap reported at the strength the tooling actually supports rather than at the strength the ladder implies. Runtime compatibility testing stays out — it needs both sides of an integration running and belongs to the testing categories.

1 · Context

A checked-in contract proves someone wrote one. It does not prove the contract is consistent, house-styled, or that the change about to land will not break every consumer. The gap between those is where most real interface pain lives, and it is exactly the distance between the contract-first and contract-checked rungs of a profile axis that currently has no mechanical meaning at any rung.

The industry answer to this rung is settled and unglamorous: a linter with a ruleset, and a differ that classifies changes as breaking or not, both wired into CI. Maturity models put automated linting one level above written convention for exactly this reason. Spectastic should not build either — it should detect that a project has them, which is the posture the enforcement engine already takes everywhere else.

What makes this more than a copy of the coverage category is an asymmetry worth stating before it becomes a broken promise: this tooling is commodity for OpenAPI and materially thinner for event-driven formats, where the mainstream ruleset trails the current specification version. A rung that demands equal rigour of both would either fail honest projects or be quietly waived into meaninglessness. Whose problem: verified and enterprise projects, and anyone consuming an interface that changes under them.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · An unchecked contract is a gap at verified P1

As a platform reviewer, I want a verified project with a contract but no linting or diffing to be reported as a gap so that "has a contract" cannot be mistaken for "honours a contract".

Acceptance: A verified-profile fixture with a contract and no configured linter or differ reports a contract-first gap naming what is missing; adding either configuration changes the report accordingly.

US2 · A configured project passes without extra ceremony P1

As an engineer who already lints and diffs my OpenAPI, I want my existing configuration to satisfy the rung so that I am not asked to adopt a spectastic-specific mechanism for work I already do.

Acceptance: A project with a recognised linter ruleset and a recognised differ in CI is reported covered, with at most 0 new files required.

US3 · An event-driven project is not held to a promise the tooling cannot keep P2

As an author of an AsyncAPI-described service, I want the rung to demand what is actually available for my format so that I am neither failed for a gap I cannot close nor told I am checked when I am not.

Acceptance: Where a format has no mainstream differ, the missing half is reported at advisory strength and the limitation is stated, rather than hard-failing or silently passing.

Edge cases

  • A project holding several contracts in different formats, with tooling configured for only one.
  • A linter present as a dependency but never invoked in CI — installed is not wired.
  • A differ that runs but never blocks, so a breaking change is reported and merged anyway.
  • A project whose contract is generated from an upstream DSL, where linting the generated artifact is the wrong target.
  • The very first contract, which has no predecessor to diff against.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

At the verified tier and above, a project holding a contract MUST also have a configured contract linter and a configured breaking-change differ, or be reported as a gap.

Rationale

Gives the contract-checked rung the mechanical meaning it has never had, and closes the distance between holding a contract and honouring one.

Detection MUST recognise a declared configuration — a ruleset file, a CI invocation — and MUST NOT treat the mere presence of a tool as a dependency as sufficient.

Rationale

Mirrors the coverage category, which counts a declared threshold rather than a coverage library, for the same reason: an installed tool that never runs certifies nothing.

Where a contract's format has no mainstream tool for one half of the check, that half MUST be reported at advisory strength with the limitation stated, and MUST NOT hard-fail the floor.

Rationale

Honest asymmetry. Failing a project for tooling that does not exist is the warn-washing the enforcement design exists to avoid, and passing it silently would overstate what the rung means.

The gap report MUST distinguish which half is missing — linting, diffing, or both — and for which contract.

The enforcement copy SHOULD state that detection proves a check is configured, not that it passes or that it blocks a merge.

Rationale

The same recorded ceiling the security and observability categories carry. Overstating it in generated documentation is how a floor loses credibility.

A project MAY satisfy the rung with a single tool performing both checks, and MAY configure different tooling per contract format.

Non-functional

Detection MUST remain config-file-only and bounded — completing in under 500 ms on a typical project with at most 0 network calls and at most 0 tool invocations.

Rationale

The engine detects configuration; it does not run linters. Running them would make enforce as slow and as failure-prone as the tools it inspects.

The new requirement MUST NOT change the verdict below the verified tier: at most 0 lean- or standard-profile projects may gain a gap from this spec.

Out of scope (deferred to other slices)

  • Payload compatibility over time for events, where replay makes the problem different in kind.
  • The rung above — versioning policy, deprecation windows, and an approval path for breaking changes.
  • Consumer-driven contract testing, which needs both sides of an integration running and belongs to the testing categories.
  • Requiring that a differ actually blocks rather than merely reports — the same reported-versus-enforced ceiling the other categories carry.

4 · Data model

No persisted entity. This spec adds detection state and one per-format capability judgment.

Entities

Check configuration
Evidence that a contract linter or breaking-change differ is wired up: a ruleset file, a CI step, or an equivalent declaration. Detected per contract format.
Format capability
Whether a mainstream linter and differ exist for a given contract format. Decides whether a missing half is a gap or an advisory limitation under FR-003.

Format capability is a claim about the world that will age. It should be data the project can read and revise, not a judgment baked into control flow — otherwise the rung silently misreports as the ecosystem catches up.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

A verified fixture with a contract and no configured checks reports a gap naming both missing halves; configuring each in turn reduces the report to 1 missing half, then to 0.

A fixture whose format lacks a mainstream differ reports that half at advisory strength and does not hard-fail — verified across 100% of formats marked capability-limited.

At most 0 lean- or standard-profile fixtures change verdict, and at most 0 verified fixtures already configured with recognised tooling gain a gap.

Detection adds under 100 ms to an enforce run on a project holding at least 5 contracts.

6 · Assumptions

A configured check correlates well enough with a running one to be worth detecting. The gap between configured and enforced is recorded as a ceiling rather than closed here.

Projects at verified and above already run CI, so "configured in CI" is a reachable bar rather than a new obligation.

7 · Open questions

None outstanding. The no-predecessor fork — whether a first contract satisfies the differ half — was settled in the design interview in favour of yes, a configured differ satisfies it: FR-002 defines detection as recognising a declared configuration, and FR-005 already forbids claiming a check passes. A differ with nothing yet to compare against is configured; introducing a third configured-but-not-yet-exercised state would contradict both and add a case every consumer must handle, which no other enforcement category carries.
