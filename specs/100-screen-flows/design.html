Design · 100-screen-flows

Where a screen sits

How we will build it.

Status Draft Spec 100-screen-flows Owner Brian Corbin · @briancorbinxyz Branch spec/visual-slice-095-098 Created 13 Aug 2026 Read time

A journey is an ordered list of steps, each referencing a screen the feature already declares, with a branch recording what happens when a step cannot complete. Pure and per-file — everything it references lives in the same sidecar — which is what keeps it a schema rule rather than the cross-file kernel scan the coverage check needed. The biggest risk is that authors record the happy path and leave every branch unwritten, which the vocabulary can surface and cannot prevent.

TypeScript, Node 20 target. Settled by the repository.

None new. The schema package's parser.

n/a — one reader and one rule, both pure. A journey references only what its own document declares, so no port is needed.

None.

Tests-first per piece, plus a browser pass on the rendered chain — a flow is the one element here whose value is visual.
Coverage
Every new branch covered by a red-first test; a change never lowers coverage of what it touches.
Perf targets
NFR-002 — byte-identical findings across at least 3 runs, 0 reads of clock, network or environment.

Per-file only. The moment a journey could reference a screen in another spec, the rule stops being expressible here — which is why FR-006 makes leaving the feature explicit rather than resolvable.

6 · Approach

Two elements and one rule. A journey holds ordered steps; a step references a screen by id and may name the state it arrives in; a branch hangs off a step and records what happens when it cannot complete. Reading is a pure function over the parsed document, in the shape the grid reader already uses, and the check resolves each reference against the screens declared in the same file.

The constraint that shapes everything is that this stays per-file. The coverage check built two days ago had to become a cross-file kernel scan because it resolves against the grid, which lives elsewhere; a journey resolves against screens in its own sidecar, so it can be a schema rule and stay pure. FR-006 is what protects that: a step leaving the feature is declared as leaving rather than resolved, so the rule never has to open a second file to decide whether a reference is legitimately outward.

The thing nearly done instead was resolving outward steps against other specs' sidecars, which would make the boundary checkable — and would turn a pure rule into a project-wide scan, and would make declaring a screen in another feature a prerequisite for describing a route through it.

8 · Decisions

D-001 · Order is source order, and there is no order attribute

Status
Accepted
Context
The variant grid faced the identical question and answered it in packages/schema/src/variant-grid.ts, whose header records the reasoning: an order= attribute would be explicit too, and would create a second ordering able to disagree with the first.
Decision
Steps resolve in the order they are written. No ordering attribute exists to disagree with the markup.
Consequences
+ One ordering, so there is nothing to reconcile. + P-1 already guarantees source order is reading order, so this reuses an invariant rather than adding one. − Reordering a journey means moving markup, which a naive edit can get wrong without any check noticing.

D-002 · A per-file rule, not a kernel scan

Status
Accepted
Context
The coverage check two days ago had to leave the schema package because it resolves a claim against the grid, a different file at project scope. variantSameResolvesRule shows the per-file shape a journey needs, and returns immediately on a document that declares nothing relevant.
Decision
Reader and rule both live in the schema package and stay pure. A step resolves against screens declared in the same document.
Consequences
+ No filesystem, so NFR-002's determinism is true by construction rather than by discipline. + Costs nothing on the overwhelming majority of documents, which declare no journey. − A journey crossing to another feature's screen cannot be checked, which FR-006 turns from a hole into a declared boundary.

D-003 · A cycle is legal, and is not the cycle the ordering graph refuses

Status
Accepted
Context
This project already ships cycle detection in packages/core/src/ordering/graph.ts, where a cycle means two specs each claim precedence over the other — a contradiction.
Decision
A journey returning to a screen it has already visited is reported by nothing.
Consequences
+ A converter that clears and is used again is ordinary, and the vocabulary must not call it an error. − The two meanings of "cycle" now live in one codebase, so this decision is written down to stop a future reader importing the wrong intuition.

D-004 · A missing branch reads as not recorded, and nothing forces one

Status
Accepted
Context
Whether authors will record failure branches is unknown — nothing has ever asked them to. The family's standing rule is that silence carries one meaning, and a sibling got this wrong once already by reading an absent record as a positive claim.
Decision
An absent branch means not recorded. It is not required, and it is not read as "no failure is possible".
Consequences
+ Silence keeps exactly one meaning. + Nothing manufactures a finding on every journey in a project that has not thought about failure yet. − The most valuable half of the vocabulary is the half nothing compels, so it may go unused — which is visible in the artifact rather than hidden, and is carried as an accepted risk.

10 · Risks & mitigations

RiskLikelihoodImpactMitigation
Authors record the happy path and leave every branch unwritten — the one assumed fact hereMMAccepted rather than mitigated. The vocabulary can surface the gap and cannot compel it; requiring a branch would manufacture an empty declaration on every journey.
A journey crossing into another feature's screens is unresolvableHLTurned into a declared boundary by FR-006 rather than left as a hole. The alternative makes this a project-wide scan.
The two meanings of "cycle" get conflated by a later readerLMD-003 exists mostly to prevent this, and the rule has a test asserting a cycle reports nothing.
The rendered chain is drawn but unreadable to a screen readerMMP-13. The browser pass asserts text content, not only that the chain rendered.

11 · Complexity tracking

An outward step is a declared kind rather than an inferred one. The tool could try to resolve a reference and treat a failure as "it must be outward", which needs no new vocabulary. It would also make a typo indistinguishable from a boundary — the two most common cases, collapsed into one silent outcome.

12 · Open questions

None outstanding. Four decisions were anchored: order comes from source position, the rule stays per-file and pure, a cycle is legal, and an absent branch means not recorded. The one assumed fact — that authors will record a branch when the vocabulary offers one — is carried as an accepted risk rather than left unremarked in the grounding table.

13 · Change log

  1. 13 Aug 2026Initial design. The shape is the variant grid's, deliberately: source order rather than an ordering attribute, a pure per-file reader, and a resolution check that returns immediately on a document declaring nothing relevant. The one place it diverges is the boundary — a step leaving the feature is declared outward rather than inferred from a failed resolution, because inferring it would make a typo and a boundary the same silent outcome.
