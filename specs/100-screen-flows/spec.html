Where a screen sits

A screen inventory says what exists. It says nothing about how anyone gets there, or what happens when the thing they came for is unavailable.

Status Accepted Spec ID 100-screen-flows Owner Brian Corbin · @briancorbinxyz Reviewers — Created 13 Aug 2026 Principlesv1.9.0 Smallest demoableA feature declaring one journey through two screens, with the branch taken when the call it depends on fails. Read time

The visual vocabulary describes screens one at a time and has no word for the path between two. A product is not a set of screens — it is the routes through them, and the branches taken when something the route depends on is not there. This adds the relation: a journey over declared screens, the route a screen answers to, and the failure branch. It is the one part of the visual survey that was never considered at all, rather than considered and deferred.

1 · Context

A feature's screens are declared and each carries its states. Nothing anywhere says a user reaches the second screen from the first, or which screen a route resolves to, or what the product does when the step a journey depends on cannot complete. The visual survey reasoned about one screen and about the grid over it, and never about the path between two — this is the only gap in the family that was never considered rather than considered and deferred.

The omission has a cost the state vocabulary makes visible. States are recorded per screen, and a great many of them exist because of a journey: a screen shows a cold start because the user arrived without a cache, or an error because the step before it failed. Recording the state without the route records the symptom without the cause, and leaves a reviewer unable to tell whether a state is reachable at all.

The reader is a developer deciding what to build first, and a reviewer asking whether a flow has a hole in it. Both questions are about edges, and there are currently no edges.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · A journey is declarable over screens that already exist P1

As an author, I want to declare the route a user takes through this feature's screens so that a reader can follow it without inferring it from names.

Acceptance: A feature declaring two screens can declare one journey through them; every step resolves to a declared screen; a step naming no screen is reported.

US2 · A journey records what happens when it fails P1

As a reviewer, I want to see the branch a journey takes when a step cannot complete so that an unhandled failure is visible as an omission rather than hidden as a happy path.

Acceptance: A journey can declare a branch from any step, naming the state or screen it leads to; a journey with no branch declared reads as not recorded rather than as having none.

US3 · A screen says what route reaches it P2

As a developer, I want to know which address a screen answers to so that I can find the screen from a URL and the URL from the screen.

Acceptance: A screen may declare its route; two screens declaring the same route are reported; a screen declaring none stays valid.

Edge cases

  • A journey that leaves this feature — the next screen belongs to another spec, or to no spec at all.
  • A journey whose steps form a cycle, which is ordinary rather than an error: a converter returns to its own entry state.
  • A screen reachable by more than one route, and a route resolving to more than one screen by context.
  • A feature with exactly one screen and no journey worth declaring.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A journey MUST be a declared element with a stable identifier, and its steps MUST be declared elements belonging to it in the order they occur.

Rationale

Order is the whole content of a journey, and source order already carries it everywhere else in this vocabulary — 096 took a grid's resolution order from source position precisely so a number could never disagree with the markup.

A step MUST reference a declared screen rather than naming one inline, and a reference that resolves to no declared screen MUST be reported.

Rationale

094's data model is explicit that neither sidecar directory is a registry — nothing enumerates their contents. So a journey references and never enumerates, and the reference is checked because a dangling one reads as a route and records nothing.

A step MUST be able to name the state of that screen it arrives in.

Rationale

A route to a screen is under-specified: arriving at a converter with a warm cache and arriving cold are different steps to the same screen, and the states already exist to say which.

A journey MUST be able to declare a branch from any step, naming what the journey does when that step cannot complete.

Rationale

The half every flow diagram omits. A journey recording only its happy path is a claim that nothing can go wrong, made silently.

A journey with no branch declared MUST read as not recorded, never as having none.

Rationale

The rule this family keeps having to restate, and it has been got wrong once already in a sibling. Silence must carry one meaning; "nobody asked" and "there is no failure path" are different claims and only one of them is ever likely to be true.

A step MUST be able to leave the feature — naming a destination this spec does not declare — and such a step MUST NOT be reported as unresolvable.

Rationale

A journey that stops at the feature boundary is the normal case and the boundary is exactly where a reviewer looks. Reporting it would push authors to declare screens they do not own, which is worse than an unchecked edge.

A cycle in a journey MUST NOT be reported.

Rationale

Returning to where you started is ordinary — a converter clears and is used again. The precedence graph this project already ships detects cycles because a cycle there is a contradiction; here it is a loop, and the two must not be confused.

A screen SHOULD be able to declare the route that reaches it, and two screens declaring the same route SHOULD be reported.

A declared route SHOULD be treated as provenance and SHOULD NOT be resolved against anything outside the declaration.

Rationale

The same posture the design source and the annotation target already take. A route is a string the build owns; checking it here would make a screen only as valid as a router this vocabulary cannot see.

A feature MAY declare several journeys, and a screen MAY appear in more than one.

A feature MAY declare no journey at all, and that MAY NOT be reported.

Rationale

A single-screen feature has no route worth writing down, and the estate is mostly single-screen features. Requiring one would manufacture an empty declaration in every one of them.

Non-functional

Every declared journey, step and branch MUST render with scripting disabled: 100% of the authored content readable with JavaScript off.

Resolving a step's reference MUST be deterministic and side-effect free: identical input produces byte-identical findings across at least 3 runs, with 0 reads of clock, network or environment.

Out of scope (deferred to other slices)

  • Rendering a journey inside the design. This spec declares one; the view shows it.
  • The states a component moves between, which are transitions inside one screen rather than between two.
  • Walking a journey against a running build.
  • What a step emits, as opposed to where it goes.

4 · Data model

One relation and two supporting shapes. Nothing here is persisted; the journey is authored beside the screens it references.

Entities

Journey
An ordered sequence of steps through declared screens, with a stable identifier. Order is source order. A cycle is legal. A feature may have any number, including none.
Step
A reference to a declared screen, optionally naming the state it arrives in, and optionally leaving the feature. A step that references nothing declared and does not leave the feature is invalid.
Branch
What a journey does when a step cannot complete. Belongs to a step. Absent means not recorded, never that no failure is possible.

The invariant: a step either resolves to a declared screen or is explicitly outward. There is no third case, which is what lets an unresolvable reference be an error without forcing an author to declare screens they do not own.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For a feature declaring a journey, a reader can state the order of its screens and the failure branch of each step from the declaration alone, opening 0 other files.

Steps referencing a screen that does not exist number 0, or each produces exactly 1 finding. Steps that leave the feature produce 0 findings.

Features declaring no journey produce 0 findings about its absence, counted across every feature in the project.

For a journey of 2 or more steps, every step is either branch-recorded or visibly not-recorded — steps where the two are indistinguishable number 0.

6 · Assumptions

Journeys are short. The shape assumes a handful of steps rather than a state machine with dozens, because that is what a feature-scoped flow looks like. A product-wide map is a different artifact and this is not it.

Authors will declare the failure branch if the vocabulary asks for it. They have not before, but nothing has ever asked — the same reasoning that turned out to be right for a state's source and wrong for nothing so far.

7 · Open questions

None outstanding. The two that could have been left open are settled by precedent rather than by preference: a cycle is legal, because the precedence graph this project already ships treats a cycle as a contradiction and a journey must not inherit that reading; and a step may leave the feature, because the alternative pushes an author to declare screens they do not own.
