17 tasks across five phases. Setup → Foundational → User stories (US1·US2·US3) → Polish. Tasks marked [P] can run in parallel — different files, no dependency. Tests for a story MUST be written and failing before its implementation tasks start.

1 · Execution strategy

Implement US1 end-to-end. Ship. Iterate to US2 and US3 only after US1 is verified.

Setup → Foundational → US1 → US2 → US3 → Polish. Each story closes its conformance before the next opens.

One team on each user story after Foundational. Coordinate at shared seams (data model, API contracts) via the spec, not Slack.

2 · Phase 1 — Setup

Name the journey elements — journey, step and branch, in the drift-guarded vocabulary table, so the names are contracts before anything reads them. packages/schema/src/visual-vocabulary.ts
Add the build entry and export subpath — a new schema module is invisible to its callers without both. packages/schema/tsup.config.ts

3 · Phase 2 — Foundational

The reader every story reads through. Pure, so it needs no port and no fixture project.

Write the reader's tests red — steps come back in source order; a branch belongs to its step; a document declaring no journey costs nothing. packages/schema/test/screen-flow.test.ts
Read journeys, steps and branches — order from source position, never an attribute. Order-preserving, and a test asserts it, because that is a contract rather than an implementation detail. packages/schema/src/screen-flow.ts

7 · Phase 4 — Polish

Drive the chain in a browser — both themes, and assert text rather than geometry: a flow drawn only as arrows is unreadable to a screen reader. tests/visual-flow.spec.ts
