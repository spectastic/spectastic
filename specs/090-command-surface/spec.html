The command surface

What spectastic surfaces to an agent host: the verb set, the one-task default, and the invocation metadata a skill carries.

1 · Context

A verb surface is a vocabulary, and vocabularies get worse as they grow. Keeping the set small is a deliberate constraint, not an accident of scope — so what the surface contains, and what metadata each entry carries, is specified rather than left to whoever adds the next command.

This spec is a slice of the spectastic meta-spec. Its requirements were authored there and moved here intact, keeping their stable ids: a requirement that was REQ-TOOL-001 in the parent is REQ-TOOL-001 here, so every existing citation still names the same contract. The parent keeps the project’s context, architecture, decisions and history; this file carries one family of requirements and nothing else.

2 · Requirements

Normative keywords follow RFC 2119.

Spectastic MUST ship eight Claude Code slash commands across the lifecycle — /spectastic.principles, /spectastic.spec, /spectastic.design, /spectastic.tasks, /spectastic.implement, /spectastic.propose, /spectastic.apply, /spectastic.triage — that drive the templates without introducing a separate CLI. It MAY additionally ship extended, opt-in verbs upstream of or alongside the lifecycle (e.g. /spectastic.explain, /spectastic.explore); extended verbs are not required to ship, but any command spectastic does surface as a skill is bound by REQ-TOOL-004.

The implement verb MUST drain the queue by default, stopping on the first failure, and MUST offer an explicit single-step mode. A project MAY set its preferred default in configuration, and precedence MUST run command-line flag over configuration over the compiled default.

Rationale

The former default stopped after one task so a human could notice a wrong plan between them. That interruption is worth keeping and is not worth paying on every task: a drain that halts on the first failure preserves it exactly where it earns its keep, and removes a re-invocation that carried no judgment. Single-step remains available for the case the old default was built for.

Every command spectastic surfaces to an agent host as a skill — the lifecycle commands enumerated in REQ-TOOL-001 and any extended verb it ships (e.g. /spectastic.explain, /spectastic.explore) — MUST declare structured invocation metadata in its source frontmatter as the source of truth for how the skill router selects it. The metadata MUST comprise three keys:

  • triggers — the intents and phrasings that should invoke the command;
  • use-when — a one-line framing of when to reach for it;
  • sibling-boundary — what disambiguates it from adjacent verbs (e.g. propose vs plan, spec vs explore).

The metadata MAY additionally carry an optional model: key declaring the model tier the command runs on — an alias (never a pinned model ID) drawn from the legal set that 044-verb-model-policy owns as a single source of truth. It is advisory to the host and is not one of the three required keys; a command that omits it is fully conformant. The per-verb tier assignments and their enforcement are owned by 044-verb-model-policy.

The harness router reads only the frontmatter description. That description MUST be a fixed, committed output tuned against /skill-creator's eval — the same string the router loads and the eval measures — and MUST NOT be generated from the keys at sync time (a generated description makes the evaluated artifact a moving target that never lives in the repo). The structured keys are the machine-checkable contract and the input skill-creator tunes from; the description is the resulting trigger surface. Where a key and the description diverge, the description is authoritative. spectastic validate MUST carry a skill-metadata-shape rule that flags a command whose source frontmatter is missing any of the three required keys; the rule ships at warning severity. That rule checks only the three required keys for presence and MUST NOT flag a command merely for omitting the optional model: key. The well-formedness of a present model: value — that it is a legal alias — is enforced by the drift-guard rule that 044-verb-model-policy requires, so a permitted key never ships without a machine-checkable guarantee.

Command descriptions SHOULD be validated with /skill-creator's eval against a ≥90% trigger-accuracy default target (the command fires correctly on ≥90% of its intent cases) whenever the metadata changes; a command measured below the target SHOULD be re-tuned before it ships. The target is a SHOULD, not a hard gate — the first eval run establishes the baseline it is checked against — until spectastic ships a harness that can run the eval automatically (deferred to init --tools), at which point the check MAY be promoted to a gated must by a future change.

Rationale

Commands load as skills but invoke unreliably because their frontmatter is authored for a human reader, and no requirement encodes a triggering bar (triage T-008, spec layer, regen fail). Structured keys make the bar machine-checkable; the description stays a fixed, tuned output so the exact string skill-creator evaluates is the one committed and loaded — generating it at sync would break that eval loop. The validate rule gives the must teeth (starting as a warning so the ten existing commands can be brought up to the bar without a red build); the eval should makes "reliable" measurable rather than asserted, baselined on first run so the ≥90% figure is checked against reality before it ever hardens into a gate. The optional model: key is an orthogonal, advisory knob (spec 044): permitting it in the contract keeps a cost-tiering choice from ever reading as a metadata violation, while its well-formedness is guaranteed by 044's drift-guard (a MUST) — so the permission never ships without an enforcement, honouring P-8.
