Change proposal · 090-command-surface

Dispatch a triage card, and disambiguate its id

Give the triage log the consumer its own contract implies, and stop a copied identifier from silently naming something else.

Status Applied Change ID 2026-08-20-triage-dispatch-and-ids Spec 090-command-surface Source 000 · T-035 Author Brian Corbin · @briancorbin Created 20 Aug 2026 Targets 2 requirements (2 added) Read time

REQ-CHANGE-009 makes a diagnostic triage card a record of whether it is still owed work, and states that an unmarked card must be read as still open. Nothing then reads that backlog. This change adds the missing consumer — REQ-TOOL-005, under which implement dispatches a card that is safe to fix in code, once the scope's tasks are drained, and closes it when the fix lands — and forecloses a latent trap beside it: REQ-TOOL-006, under which a T-NNN that names both an unchecked task and an open card is refused rather than silently resolved. That condition holds zero times today, and the requirement is preventive on purpose; the adversarial pass is what narrowed it from a far broader refusal that would have fired on 81 harmless collisions.

Dispatch a triage card, and disambiguate its id

Applied

1 · Intent

Two contracts compose into a gap neither made. REQ-CHANGE-009 defines a per-spec triage log as a backlog: a card records “whether it is still owed work”, and one carrying no data-status must be read as still open. REQ-TOOL-003 defines implement as draining a queue. Neither says the owed work reaches the queue, so it does not: implement accepts a tasks.html task id, an inbox I-NNN, or a spec id resolving to the next unchecked task, and a triage card is none of those. Running /spectastic.implement 016 reported nothing to do while 016/T-006 sat open, because that spec's tasks are 52/52 complete.

The identifier makes the quiet failure a loud one waiting to happen. 025-id-uniqueness scoped T-NNN to within a file — correct for a spec-local id, but a spec is a bundle, and tasks.html and triage-log.html mint from the same sequence. 81 ids across the estate name both a task and a card, and the kernel's classifyTarget maps any T-NNN to 'task' unconditionally.

How dangerous that is was overstated in this proposal's first draft, and the correction is worth keeping. The kernel already throws when a bare T-NNN is not an unchecked task (task … not found (or already ticked)), so a stale collision fails loudly rather than misrouting. Silent misresolution needs the number to name an unchecked task and a card at once — which, measured across the estate, is true of 0 ids today. The trap is real but latent: it opens the first time a spec carries unchecked tasks and an open card together, which is an ordinary mid-drain state.

2 · Scope

In scope

  • ADD REQ-TOOL-005: an open card carrying layer="implementation" and a passing regeneration result is dispatchable work, picked up once the resolved scope has no unchecked tasks left; landing its fix closes the card.
  • ADD REQ-TOOL-006: a bare T-NNN naming both an unchecked task and an open card is refused with both candidates named; task:T-NNN and triage:T-NNN resolve unambiguously.
  • A card that is not dispatchable is reported with the routing its layer implies, rather than the scope reporting no work at all.

Out of scope

  • Widening 025-id-uniqueness so T-NNN is unique across a spec's bundle rather than within a file. Deferred, not refused: 025 FR-002 names “T-NNN on <spec-task>” as its own subject, so the identifier space is that spec's topic group, and this change binds only the implement verb — a human reading a log, or apply, verify and propose, still treat a colliding id as unambiguous. Renumbering would churn stable anchors, which P-3 treats as forever contracts, so it needs its own change rather than riding along here.
  • Dispatching upstream-layer cards. Ten of the thirteen open cards are spec, cross-spec or design at regen-fail; they route through propose or a new spec by design, and machinery that mostly declines is machinery nobody trusts.
  • A dedicated verb that drains a triage log the way implement drains a task list. Worth considering only if the dispatch path proves too narrow in practice; the verb count is deliberately eight.

3 · Approach

Two requirements rather than one, because these are two obligations that fail independently: a correct queue with an ambiguous identifier is still a trap, and an unambiguous identifier pointing at work no verb dispatches is still a dead end. Splitting them also keeps each independently testable, which a single requirement carrying two bare MUSTs would not be.

Neither modifies REQ-TOOL-003 — its subject is drain mode, not what the queue contains or how a target resolves, and folding dispatch into it would give one requirement two unrelated jobs. But they do interact with it, which an earlier draft of this section wrongly denied. REQ-TOOL-003 halts a drain on first failure, so gating card pickup purely on “no unchecked task remaining” would strand a spec's cards behind one blocked task forever. REQ-TOOL-005 therefore makes the task-exhaustion gate govern only the automatic sweep: a card named explicitly is always reachable, and single-step dispatches at most one card, matching the mode's own contract.

The dispatch condition names both axes deliberately. A survey of all 142 cards found layer and regen are independent: two implementation cards carry regen fail (019/T-001 and T-002), and three spec cards carry regen pass. A regen-fail implementation card records that the defect would return from spec and design, so landing a code fix there ships work that regenerates away — the outcome the root-cause ladder exists to prevent.

4 · Deltas

Two <spec-delta>, both op="added". REQ-TOOL-002 is retired and its number is never reused, so the next free ids are 005 and 006. The post-state is rendered inline as it will appear when archived.

The implement verb MUST treat an open <spec-triage> card in a spec's triage-log.html as dispatchable work when it carries both layer="implementation" and a passing regeneration result; a card whose regeneration result is absent or unrecognised MUST NOT be treated as passing. A card that does not meet both conditions MUST NOT be dispatched however it is named — naming one explicitly reaches it, and the verb then MUST refuse it and report the routing its layer implies.

Cards MUST be considered only within a scope the invocation resolved, never swept across the project. When selecting automatically the verb MUST pick a card up only once that scope has no unchecked task remaining; a card named explicitly MUST remain reachable whatever the state of the task queue, so a blocked task cannot strand it. Single-step mode MUST dispatch at most one card, and a dispatched card MUST NOT be fanned out to a parallel agent, no card having declared independence.

When it lands a dispatched card's fix the verb MUST close that card, recording what actually shipped; where the fix is only partly landed it MUST leave the card open and report what remains. Closing the card MUST be the whole record — no task is written into tasks.html for dispatched work. Where a scope yields no work, the verb MUST report any open cards it found and their routing, rather than reporting that there is nothing to do.

Rationale

REQ-CHANGE-009 made a triage log a backlog — an unmarked card “MUST be read as still open” — without giving it a consumer, so owed work accumulated where no verb looked. /spectastic.implement 016 reported nothing to do while a card sat open.

Both conditions are named because they are independent axes, not one signal twice: across 142 cards, two implementation cards carry regen fail and three spec cards carry regen pass. A regen-fail card records that the defect would return from spec and design, so a code fix there is work that regenerates away. Tasks keep priority so no existing drain changes behaviour until its queue empties — but only for the automatic sweep, because REQ-TOOL-003 halts on first failure and a gate that waited for an empty queue would strand every card behind one blocked task. The closure obligation is stated at must on this path — stronger than REQ-CHANGE-009's authoring should — because a verb that dispatched the card knows it landed the fix, and leaving it open is a false backlog the verb created itself.

Four boundaries are drawn deliberately. Location: per-spec logs only, because inbox.html uses the same element for routing exits with different semantics and already dispatches its own just-do cards — widening here would silently change a file this change never analysed. Fail-safe: an absent regeneration result is not a passing one, matching how a malformed enforce waiver fails closed rather than open. No bypass: explicit naming reaches a card but never overrides the gate, or the verb could be talked into building upstream work the ladder says regenerates away. Partial fixes mirror the tick-once discipline exactly — an open card means work is owed, so closing a half-fixed one puts a false “done” into the record the card exists to keep honest.

Where a bare T-NNN target names both an unchecked task and an open triage card within the resolved scope, the implement verb MUST refuse it and name both candidates, rather than resolving to either; and it MUST accept the qualified forms task:T-NNN and triage:T-NNN, which resolve unambiguously and are never refused on this ground. Where only one of the two is actionable, the target MUST resolve to it as it does today. A refusal MUST be reported as a failure to do the requested work, never as a successful no-op.

Rationale

025-id-uniqueness scoped T-NNN uniqueness to within a file, on the reasoning that a spec-local id numbers per spec. But a spec is a bundle, and two files inside it mint from the same sequence: 35 of 36 specs carry at least one T-NNN naming both a task and a card, and the meta-spec has 18. Today the kernel's classifyTarget maps any T-NNN to a task unconditionally, so an author copying an id off a card gets different work with no warning.

Refusal rather than a precedence rule, because any precedence is silently wrong half the time and the author cannot tell which half they are in. Refusing makes the ambiguity visible at the moment it matters and costs one retyped prefix; it also leaves which ids are legal untouched, so no stable anchor moves.

Both conditions are narrow deliberately, and the narrowing was earned. An earlier draft refused on any id naming a task and a card at all — 81 ids, of which the kernel already handles every stale one by throwing (task … not found (or already ticked)), so that refusal would have been friction on 81 cases to prevent 0. Scoped to an unchecked task and an open card, it fires exactly when both candidates are live work. That is true of 0 ids in the estate today: this requirement is preventive, guarding an ordinary mid-drain state rather than remedying an observed failure, and it is stated at must because a safety property that costs nothing while nothing is ambiguous is cheap to hold and expensive to retrofit.

The failure clause exists so automation cannot swallow it: a refusal that exited successfully would let a scripted or CI invocation report success having done nothing — the same silent-skip class this change exists to close.

4b · What this change removes

Each entry names one thing this change takes away — a clause dropped from a requirement it retypes, an obligation a sibling loses, a behaviour or affordance no requirement records.

Authors lose the ability to resolve a bare T-NNN in the one case where an unchecked task and an open card share it. The work stays reachable as task:T-NNN, and the loss is 0 ids today — it costs nothing until a spec next carries unchecked tasks and an open card at once. The first draft of this register claimed a far larger loss (“at least one id in 35 of 36 specs”); that was measured against the wrong condition and is corrected here rather than quietly dropped, because the register is meant to state what a change costs, and overstating it is its own kind of wrong.
