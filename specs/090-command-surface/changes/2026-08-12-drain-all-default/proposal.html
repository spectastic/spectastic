Change proposal · 090-command-surface

Draining should be the default, not the flag

The common case is emptying the queue; the rare case is stopping after one.

Status Proposed Change ID 2026-08-12-drain-all-default Spec 090-command-surface Author Brian Corbin · @briancorbinxyz Created 12 Aug 2026 Targets 1 requirement(s) Read time

REQ-TOOL-003 makes one task per invocation the default, on the reasoning that a per-task pause keeps a human in the loop. In practice the pause is spent typing the same command again. This proposes flipping the default to draining, keeping single-step as an explicit flag, and — because the existing rationale is deliberate rather than accidental — rebutting it rather than deleting it. A configuration key sets the project's preference, with the flag winning over the config and the config over the compiled default.

Draining should be the default, not the flag

Proposed

1 · Intent

The single-task default was reasoned, not incidental: a stop between tasks is a chance to notice that the plan is wrong. That value is real and it is not free — it is paid on every task, including the many where nothing is wrong, and the cost is a re-invocation that carries no judgment at all.

The judgment worth keeping is available more cheaply. A drain that stops on failure preserves the interruption where it matters and removes it where it does not.

2 · Scope

In scope

  • Flipping the default from one task per invocation to draining the queue.
  • An explicit single-step flag, and a configuration key setting the project default.
  • Precedence: flag over configuration over compiled default.

Out of scope

  • Parallel task execution, which is a separate capability.
  • What counts as a failure worth stopping on — the existing behaviour is inherited unchanged.

3 · Approach

Modify the requirement rather than adding a sibling, since the default is the requirement. The old rationale is answered in the new one rather than dropped: a reader who wants to know why the default flipped should find the argument that was overturned, not its absence.

4 · Deltas

What changes: the default becomes draining; single-step becomes an explicit choice; a configuration key and its precedence are defined.

The implement verb MUST drain the queue by default, stopping on the first failure, and MUST offer an explicit single-step mode. A project MAY set its preferred default in configuration, and precedence MUST run command-line flag over configuration over the compiled default.

Rationale

The former default stopped after one task so a human could notice a wrong plan between them. That interruption is worth keeping and is not worth paying on every task: a drain that halts on the first failure preserves it exactly where it earns its keep, and removes a re-invocation that carried no judgment. Single-step remains available for the case the old default was built for.

5 · Risk register

The adversarial pass triggered on a must-tier requirement being modified. Two findings, recorded and answered.

Draining by default means a wrong plan produces many wrong tasks before anyone looks, and "stop on first failure" only helps when the work fails loudly — a task that succeeds at the wrong thing does not.

"MUST drain the queue by default, stopping on the first failure"

The strongest objection to this change and it is not fully answered. A drain trades early detection for throughput, and the trade is only sound where tasks fail visibly. Left identified deliberately: the owner should accept this consciously rather than have it argued away.

Adding a configuration key repeats the defect that design.stackInterview just had to be withdrawn for — a documented switch nothing reads.

"A project MAY set its preferred default in configuration"

Mitigated by ordering: the key is only worth declaring once the kernel reads it, so the task list puts the reader before the documentation, and the configuration registry will not advertise it until then.

One outstanding, and it is deliberately left for the owner: the first risk above. Draining trades early detection of a wrong plan for throughput, and that trade is only sound where a wrong task fails loudly rather than succeeding at the wrong thing. It should be accepted knowingly rather than reasoned away in the proposal that benefits from it.
