Unit edge authoring

A relation nothing writes is a relation that will not exist. This is the surface that writes one.

Status Draft Spec ID 080-unit-edge-authoring Owner Brian Corbin · @briancorbinxyz Reviewers — Created 02 Aug 2026 Principlesv1.9.0 Smallest demoableA maintainer runs one command and the edge is in spectastic.json, correctly shaped, with the rest of the file untouched. Read time

079 defines the edge and reads it. Nothing writes one. That is exactly how 076's consumes key arrived at zero entries across the whole estate including this repository — a config key with no authoring surface is a key nobody fills in. This adds two: a command that writes a declared edge idempotently while leaving the rest of the configuration alone, and a decision-phase question in the design interview that asks about dependencies where a project plausibly has them. A validate rule completes it, so a malformed or self-referential declaration is caught at the boundary rather than discovered by whatever reads it next.

1 · Context

The estate has a worked example of what happens when a config key ships without a way to fill it in. 076 added consumes as a should-tier routing list; a year later it has no CLI surface, no interview question, no caller outside its own tests, and not one entry in this project's own configuration. The mechanism is sound and unused, and the reason is that nothing ever asks.

079 makes inference the safety net so the relation is useful regardless. But inference sees only that a dependency exists — never which side of it a change belongs on, and never a relationship the manifests do not express. Those are the cases a declaration exists for, and they arrive only if something writes one.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Record a dependency without hand-editing config P1

As a maintainer, I want to declare an edge with one command so that the relation is recorded correctly without me learning the config shape.

Acceptance: running the command adds the edge to spectastic.json; every unrelated key, and the file's existing formatting, survives unchanged. Running it twice leaves one edge.

US2 · Be asked, at the moment it is knowable P2

As a designer, I want to be asked what this work depends on while I am deciding the design so that the relation is captured when I know it rather than reconstructed later.

Acceptance: a design for a project with more than one unit, or one declaring a contract, reaches a dependency question in its decision phase. A single-unit project with no contract is not asked.

US3 · Catch a bad declaration at the boundary P2

As a reviewer, I want a malformed or self-referential edge reported by validate so that it fails where every other artifact defect fails, not somewhere downstream.

Acceptance: a declared edge whose coordinate is not well-formed is an error; an edge naming its own declaring unit is an error; a well-formed edge naming a unit absent from this checkout is not.

Edge cases

  • No spectastic.json at all — the command creates a minimal one rather than refusing.
  • A hand-edited config with comments or unusual formatting; the write must not reformat what it did not change.
  • An edge that duplicates one inference already finds. Declaring it is legitimate and makes it authoritative per 079.
  • A design interview in a project whose unit count cannot be determined — the question is skipped rather than asked speculatively.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A command MUST write a declared edge into the project's configuration, and re-running it with the same edge MUST leave the configuration unchanged.

Rationale

Idempotence is what makes the command safe to put in a script or re-run after an interrupted session, and it is the property a hand-edit cannot promise.

The write MUST preserve every key it did not change, and MUST NOT reformat regions of the file it did not touch.

Rationale

The configuration is hand-authored and hand-reviewed. A verb that reformats it makes its own diff unreadable and discourages the very authoring this spec exists to encourage.

The command MUST refuse an edge whose declared target is the declaring unit itself, and MUST refuse a target that is not a well-formed coordinate.

Where no project configuration exists, the command MUST create a minimal one rather than failing.

The design verb's decision phase SHOULD ask what the work depends on when the project has more than one unit or declares a contract, and SHOULD skip the question otherwise.

Rationale

Asking a single-module project with no interface what it depends on trains authors to dismiss the question, which is how a prompt stops being read. The trigger is the same shape as the architecture-pattern prompt's "more than one moving part".

A confirmed answer to that question SHOULD be written through the same command path as FR-001, not by a second writer.

Rationale

Two writers for one key drift. The interview is a caller of the command, not a parallel implementation of it.

Validation MUST report a declared edge whose target is malformed, or which names its own declaring unit, at error severity.

Validation MUST NOT report a well-formed edge whose target is merely absent from this checkout.

Rationale

Parsing a coordinate never dereferences it, and most consumers do not have their providers checked out. Erroring on absence would make the ordinary federated case unvalidatable; 079 already reports it as unverified, which is the honest treatment.

Non-functional

The command MUST make at most 0 network calls and MUST write at most 1 file.

A failed or refused write MUST leave the configuration byte-identical: at most 0 partial writes are permitted.

Rationale

A half-written config is worse than no write at all, because the next read sees something that parses but is wrong.

Out of scope (deferred to other slices)

  • Editing or removing a declared edge. Hand-editing remains available; a verb for it waits for evidence that edges churn.
  • Presenting inferred edges for confirmation into declarations — deliberately not in v1, since rubber-stamping would convert a weak signal into a strong-looking one without thought.
  • Reading a project's declared boundary map as a source of intra-repo structure.

4 · Data model

This slice introduces no new entity. It writes the Edge that 079 defines, into the project configuration that already exists.

Entities

Declared edge
An Edge (079) whose existence is asserted by the depending unit's own configuration rather than inferred. The declaring unit is always the project being configured — a configuration file can only speak for its own project, which is what makes conscription structurally impossible rather than merely forbidden.

The set of declared edges is a set, not a list: the same target declared twice is one edge. That is what makes FR-001's idempotence a property of the data rather than a behaviour of the writer.

5 · Success criteria

Technology-agnostic, measurable outcomes.

A maintainer records a dependency in a single command, and running that command a second time changes at most 0 bytes of the configuration.

Across a fixture configuration carrying unrelated keys and hand formatting, a write alters at most 0 of them.

A malformed or self-referential declared edge produces a validate error, and a well-formed edge naming an absent unit produces at most 0 findings.

A design for a single-unit project with no declared contract reaches the dependency question at most 0 times.

6 · Assumptions

The project configuration remains a hand-authored file that a person reads and reviews, so a machine write must behave like a careful editor rather than a serialiser.

A project's unit count is determinable from the same workspace signals 079's inference already reads. Where it is not, the interview trigger fails closed and the question is skipped.

7 · Open questions

None outstanding. The authoring surface's aggressiveness — write on command, prompt in design, and deliberately not offer inferred edges for bulk confirmation — was anchored in the interview, along with the prompt's trigger condition.
