5 · Approach

The interesting part is the order of operations, not the write. Every way this verb can refuse — a self-edge, a malformed coordinate, an unparseable config — is decidable before a single byte is emitted. So the whole thing is: read, decide, and only then write once. NFR-002's byte-identical guarantee falls out of that arrangement rather than being defended by a temp file and a cleanup path; there is no window in which a partial write could exist.

The write itself needs one piece of care. Re-emitting parsed JSON normalises indentation, which is invisible here — this repository's config is already 2-space, exactly what the existing writers emit — and would rewrite every line of a project using tabs. Detecting the file's own indentation and re-emitting with it costs a few lines and removes the whole class. What it cannot preserve is comments or unusual spacing inside a line; JSON has no comments, and the rest is a recorded ceiling rather than a solved problem.

The shared editor needs two policies, because its callers genuinely differ. init sets a key only if absent and never overwrites an owner's value; this verb adds to a set, so re-running is a no-op rather than a duplicate. Those are different enough to be separate functions over one implementation, and conflating them would give init an append it must never do.

7 · Decisions

D-001 · Round-trip the config, re-emitting with its own detected indentation

Status
Accepted
Context
FR-002 forbids reformatting untouched regions. The two existing writers re-emit everything at 2-space, which is lossless in this repository only because its config already is 2-space — verified byte-wise. A project using tabs would have every line rewritten by a one-key change, making the verb's own diff unreadable.
Decision
Parse, mutate, and re-emit — but detect the file's existing indentation from its first indented line and re-emit with it. Preserve nothing else: JSON has no comments, and unusual intra-line spacing is a recorded ceiling.
Consequences
+ A one-key change produces a one-line diff in any project, not just this one. + Keeps the simplicity of the existing precedent rather than trading it for string surgery. + The ceiling is stated rather than implied. − Key order within an object is preserved but a hand-arranged blank line is not. − Detection is a heuristic: a file whose first indented line is unusual gets a reasonable guess, not a guarantee.

D-002 · Decide every refusal before writing anything

Status
Accepted
Context
NFR-002 requires a refused or failed write to leave the file byte-identical. Every refusal this verb can make — self-edge, malformed coordinate, unparseable config — is decidable from inputs already in hand. An atomic rename is available in the IO port if a swap were wanted.
Decision
Validate fully, then perform exactly one write as the last action. No temp file, no rename, no cleanup path.
Consequences
+ The guarantee is structural: there is no code path on which a partial write exists to clean up. + One fewer lifecycle to get wrong for a file of a few hundred bytes. − Does not protect against a crash during the single write, which a temp-and-swap would; accepted as out of proportion to the file's size and the verb's blast radius.

D-003 · Extract one config editor into core and migrate init's two writers onto it

Status
Accepted
Context
init carries two near-identical writers and this slice would be the third. P-14's test — would a second caller want this without the CLI attached — is plainly yes. Both existing writers have dedicated test files, so a behaviour change during migration fails an existing test rather than escaping unnoticed.
Decision
One editor in core exposing two policies over one implementation: set-if-absent (init's never-overwrite semantics) and add-to-set (this verb's idempotent append). Migrate both init writers onto it in this slice rather than leaving a third copy behind.
Consequences
+ Three copies of the parse-mutate-write dance become one, and the indentation fix in D-001 reaches init for free. + Both policies are named, so a caller cannot accidentally get an append where it wanted never-overwrite. − Widens this slice into a verb it does not own; mitigated by the existing tests and by the migration being behaviour-preserving by construction. − Two policies on one editor is a small API surface to get right early, since init binds to it immediately.

D-004 · Extend 079's arrangement rather than introduce a pattern

Status
Accepted
Context
REQ-LIFECYCLE-008 asks for a deliberate architecture choice where a feature has more than one moving part, and this one spans a core editor, a CLI verb, a schema rule and an interview prompt. 079 already established ports-and-adapters over a pure core for this module.
Decision
No new pattern. The config editor is a filesystem-side capability alongside the existing workspace port; the refusal rules stay pure and testable without a directory; the CLI stays thin. The deliberate choice here is not to introduce a second arrangement in one module.
Consequences
+ One module, one arrangement, so a reader who has understood 079 has understood this. + The refusal rules inherit 079's fixture-free testability. − Records a decision whose content is "keep going", which is only worth writing down because the requirement asks the question be answered rather than skipped.

D-005 · Tests red before implementation

Status
Accepted
Context
Consistent with 079 D-005. A judgment about method with no external fact to verify. The idempotence and byte-identical properties are both easy to assert after the fact in a way that merely restates the implementation.
Decision
Each requirement's test is written and seen failing first. The migration in D-003 is the exception by nature: its tests already exist and must stay green throughout, which is the point of migrating rather than rewriting.
Consequences
+ Idempotence and byte-identity are specified rather than observed. + The migration has a pre-existing red line it must not cross. − Slower per cycle.

9 · Risks & mitigations

RiskLikelihoodImpactMitigation
Migrating init changes its never-overwrite behaviour and a fresh init silently starts clobbering an owner's config LowHigh The highest-impact risk here, and the reason D-003 names the existing test files as its safety net. The two policies are separate functions precisely so init cannot accidentally receive an append.
Indent detection guesses wrong on an unusual file and reformats after all MediumLow Falls back to the file's existing behaviour (2-space), which is no worse than today. Asserted against tab, 2-space and 4-space fixtures.
The design-interview question is added and never fires, or fires everywhere MediumLow It is command markdown and therefore advisory — stated in the principles check rather than claimed. The trigger condition is asserted where it is checkable: the unit count the prompt keys on.
The validate rule errors on a well-formed coordinate whose target is merely absent LowMedium FR-008 forbids it explicitly, and it gets its own test — the federated common case is a provider that is not checked out.
