Specification · 106-visual-render

Visual render capture

A design artboard becomes a picture a reviewer can look at — and a byte survives the journey.

Status Accepted Spec ID 106-visual-render Owner Brian Corbin · @briancorbinxyz Reviewers Unassigned Created 18 Aug 2026 Principlesv1.9.0 Smallest demoableOne artboard is executed in a browser and one image lands beside the screens it documents, named from the artboard’s own label. Read time

A design tool draws a screen, but the export carries only source and a runtime — so nothing here has ever seen the picture. This adds one verb that executes a design source in a browser and writes each artboard as an image beside the screens it documents, over a byte-faithful file port, because today an image read through that port is corrupted rather than refused. The picture is evidence for a person to look at, never something a machine compares against.

1 · Context

A design drawing eleven screen states in light and dark was imported. No images landed, and the manifest reported two files as not landed “because these carry a runtime” — as though a safety rule had discarded them. That reading points the fix at the wrong file.

There were four causes and the refusal rule was none of them. No export examined contains rendered images of its own artboards — an artboard is source plus a runtime, and becomes a picture only once a browser executes it. This project has no render capability. The file port is text-only, so an image read through it arrives mangled with no exception and no manifest entry. And the one tool-made image is filtered as a dotfile before it is read, making it the single file neither landed nor reported.

The cost is not hypothetical: rendering an export by hand caught a refusal in a consuming project forbidding a dash the design legitimately draws — invisible in the source, obvious in the picture.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · A design becomes a picture P1

As a spec author, I want to capture a design artboard as an image beside the screens it documents so that a reviewer judges what the design draws rather than reading its source.

Acceptance: Against an unmodified export declaring at least one labelled artboard, the verb writes one openable image per artboard into the owning spec’s render directory, named from its own label.

US2 · A byte survives the port P2

As a kernel consumer, I want to read and write a binary file through the file port so that an image is either landed correctly or refused, and never silently corrupted.

Acceptance: An image written through the port and read back is byte-identical, and two files differing only outside the text-representable range hash differently.

US3 · An absent picture is accounted for P3

As a reviewer, I want to see which artboards were not captured and why so that a missing picture is a reported outcome rather than an invisible one.

Acceptance: For an export declaring N artboards the manifest accounts for all N, each captured or named with a reason; one that logged a console error is captured and carries it.

Edge cases

  • The network is unavailable, so the verb refuses with a stated reason rather than failing inside the runtime.
  • Two artboards declare the same label and collide — distinct from re-capturing one, which legitimately replaces its own file.
  • A label carries spaces, separators, or characters a filesystem rejects.
  • An artboard renders visibly but logs an error, producing evidence that may be half-drawn.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The file port MUST carry file contents without transformation: a file written through it and read back MUST be byte-identical to its source.

Rationale

The current port reads every file as a UTF-8 string, so an image through it is mangled and nothing errors — the only one of the four causes that destroys data, and it does so silently. Everything else here is blocked on it.

A content hash recorded for a landed file MUST be computed over its bytes, and two files differing only in bytes outside the text-representable range MUST hash differently.

Rationale

The existing hash reads character codes, so it is text-shaped by construction. Left alone it would report two different images as identical — a provenance record making a false claim, which is worse than no hash.

The render capability MUST be supplied to the kernel as a port on the invocation context, and the kernel MUST NOT depend on any particular browser.

Rationale

The shape the file and model ports already use; it keeps a browser out of the package every consumer installs.

Rendering MUST be a separate verb from the design import, and the import MUST continue to execute nothing and require no network.

Rationale

Import advertises that it needs no network, no account and no design-tool licence; rendering requires a browser and egress. Folding one into the other would silently void a property the import promises today. The load-bearing separation in this spec.

The verb MUST declare that it requires network egress, and when egress is unavailable it MUST refuse with a stated reason before executing any artboard.

Rationale

Offline, the runtime throws from inside itself, which reads as a defect in the design rather than a missing prerequisite. Refusing first makes the error answerable.

Each capture MUST be of one artboard’s own bounds rather than of the page containing it, and MUST be named from that artboard’s declared label, reduced to a name the filesystem accepts.

Rationale

Artboards carry their own identity in the markup, so twenty-two hand-authored names would be twenty-two chances to disagree with the design. The bounds clause is what this spec nearly left ambiguous: a source file draws many artboards on one page, and a whole-page image is evidence of nothing in particular — a render is nested in the single state it documents, so a picture of eleven states makes no claim about any of them.

Two artboards in one run whose labels reduce to the same name MUST be reported as a collision rather than one silently overwriting the other.

Rationale

Two pictures claiming one name means whichever ran last masquerades as evidence of the other, and a wrong picture is worse than a missing one.

Captures MUST be written inside the visual directory of the spec that owns the screens, and MUST NOT be placed behind a path segment beginning with a dot.

Rationale

A capture is evidence of one feature’s screens, not material every feature shares, so it belongs at the feature scope 094 FR-002 defines. The dot prohibition is the same trap 094 FR-006 names — an ignore rule silently excluding images — and it is not hypothetical: a dotfile filter is precisely why the one tool-made image was invisible rather than refused.

A console error raised while an artboard renders MUST be recorded against that artboard’s capture in the run’s manifest, and MUST NOT be discarded.

Rationale

A silently half-rendered artboard is worse evidence than none, because a reader cannot tell by looking. Recording rather than refusing keeps the picture a human can judge, which a refusal would throw away.

The verb MUST NOT compare a capture against a previous capture, against another image, or against a running implementation.

Rationale

The refusal that keeps this verb from becoming something else. Comparing a render against a stored render is pixel diffing with extra steps and inherits every failure mode: font rendering, anti-aliasing, a baseline re-approved on every legitimate change. Fidelity is measured against declared tokens as numbers, never as images. Written as a requirement because a capability this close to the wrong one drifts into it unless something says no.

Re-running the verb SHOULD replace an existing capture of the same artboard without requiring a flag, and every artboard found MUST be accounted for in the run’s manifest as either captured or not captured with a reason.

Rationale

Guarding a capture is machinery a compared baseline needs, and FR-010 says nothing compares these — so the guard buys nothing and costs a flag on every honest re-run. Ratifying evidence stays a human act; the commit is that gesture. The accounting clause closes the gap the dotfile filter left: a file neither landed nor reported is invisible, which is a different thing from refused.

Non-functional

A run over a single design source MUST launch at most 1 browser process and MUST capture every artboard in that one session.

Rationale

A session per artboard turns a twenty-two-state gallery into twenty-two cold starts.

At most 1 verb — the render verb — MUST be able to reach the render port, so no network access or code execution can occur as a side effect of a verb that promises neither.

Rationale

The enforcement half of FR-004: a promise resting on nobody wiring the port into a second verb is a convention, not a guarantee.

Out of scope (deferred to other slices)

  • Measuring an implementation against the design. This spec captures evidence; it never judges with it.
  • Landing renders through the design import — speculative until an export carries one, though the port fix here unblocks it.
  • Reporting the tool-made canvas thumbnail rather than dropping it unread; it belongs to the importer.
  • Vendoring the runtime’s libraries to render offline, which trades the egress requirement for pinning versions the design tool controls.
  • Exports from design tools other than the one examined.
  • Opening an archive. 105 FR-013 already requires an import to materialise one, so a render reads a materialised source and there is one expander, not two.

4 · Data model

Three entities, none of them persisted beyond files on disk.

Entities

Artboard
One labelled region of a design source — the unit a person would call a screen. A single source file commonly draws many, so an artboard is never the file. One with no label cannot be captured, because its capture would have no name.
Capture
An image file that is evidence of exactly 1 artboard in a stated set of contexts, named from that artboard’s label. Never load-bearing: nothing may depend on one existing.
Render run
One execution over one design source. Produces zero or more captures and exactly 1 manifest.

Two invariants, both counts of 0: no artboard goes unaccounted for, and no two resolve to one capture name.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

An image written through the file port and read back differs from its source by 0 bytes.

Against an export declaring N labelled artboards, the number captured plus the number reported as not captured equals N, and each captured file opens as a viewable image.

With the network unavailable, the verb exits with a stated reason and writes 0 capture files.

Run against a source declaring two artboards whose labels reduce to one name, the number of capture files written for them is 1 fewer than requested and the collision is reported.

Validating a project after a render run reports 0 findings it did not report before — landing images trips no existing scan or content policy.

6 · Assumptions

A capture is not byte-reproducible: it depends on the browser build, the fonts available, and libraries fetched at load time, so two runs may differ without anything being wrong. FR-010 keeps that from mattering — a picture nothing compares against need not be stable. The accuracy worth pursuing is token accuracy, and that belongs to the measurement slice.

The design source declares its own identity in its markup, so a name and grid context can be derived rather than authored. Verified against one tool’s export; a source declaring nothing would need names supplied some other way.

7 · Open questions

None outstanding. The one that looked open — where a capture lives — was settled by a spike: the convention is already in use and committed in the exemplar, so this spec ratifies it rather than inventing one.
