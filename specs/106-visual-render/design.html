Design · 106-visual-render

Visual render capture

How we will build it.

Status Draft Spec 106-visual-render Owner Brian Corbin · @briancorbinxyz Branch spec/visual-render-106 Created 18 Aug 2026 Read time

A Renderer port on the kernel context, a Playwright adapter in its own package so no browser reaches @spectastic/core, and a byte-faithful pair of methods on the file port. The verb loads a design source once, captures each labelled artboard at its own bounds, and writes a run manifest accounting for every one. Egress is checked before the browser opens — a blocked CDN produces four plausible-looking artboards rather than none.

2 · Technical context

Language / runtime
TypeScript on Node, unchanged — the workspace's existing stack.
Architecture
Ports and adapters, extending the shape already shipping: core declares the port, a package outside it supplies the implementation (D-003).
Browser driver
Playwright 1.62.1 — already resolved and installed in the workspace.
Test framework
Vitest for the deterministic half; a real Chromium for the capture path (D-007).
Coverage
Patch target: every new line in the deterministic core covered, and a change never lowers coverage of what it touches. The adapter's browser-driving lines are exercised by the real-browser test rather than counted.
Persistence
Files only — captures and one manifest, under the owning spec's visual/renders/.
Perf
NFR-001: at most 1 browser process per run, every artboard in that session. Measured on the real export at 22 artboards.

Toolchain / enforcement

The enterprise floor is already fully covered — 8 categories covered, observability relaxed under a waiver with an owner and expiry, 0 missing. This design adds no gap and resolves none.

What it does add is a package, and a new workspace member is outside every gate until it is brought under one. So the work is wiring, not selection: the formatter, linter and type-checker configs extend to it, its tests join the run, and a dependency-cruiser rule forbids @spectastic/core importing it — the same rule shape that already guards the corpus boundary, and which was proven there against a planted edge before being trusted.

3 · Data model & contracts

No consumer-facing interface. The verb is invoked from a terminal and writes files; nothing calls it over a wire, and nothing outside the project depends on its output shape. The one thing that is a contract — what a capture is called — is settled by D-004 and read by the existing <spec-render src=> attribute rather than by anything new.

6 · Approach

Three pieces, each answering one requirement group. A byte path on the file port so an image survives being written (FR-001). A render port the kernel declares and does not implement (FR-003). And a verb that composes them: preflight, load once, capture each artboard, account for all of them.

The deterministic half — slugging a label, detecting a collision, accounting for every artboard, writing the manifest — lives in core and is testable with a stub renderer. The browser is behind the port, so the only thing that needs a real Chromium is the adapter.

The dashed box is the only thing that knows what a browser is, and nothing in core may import it.

8 · Decisions

Check egress before the browser opens, and guard against unexpanded templates

Status
Accepted
Context
The spike aborted unpkg.com and reloaded the real export: the page yielded 4 unexpanded template labels ({{ s.id }} · light) rather than zero, with 3 console errors. The offline failure is not a crash — it is four plausible-looking artboards.
Decision
Reach the runtime's CDN before launching the browser; refuse with a stated reason if unreachable. Then, after load, refuse any label still carrying template syntax.
Consequences
+ Satisfies FR-005 literally — nothing is executed before the refusal — and makes SC-003's "writes 0 capture files" achievable rather than aspirational.
+ The template guard catches what a preflight cannot: a CDN that answers but serves something broken.
− Two checks to maintain, and the preflight hard-codes knowledge of which host the runtime needs, which is the design tool's business and could change.

Add readBinary and writeBinary rather than overloading readFile

Status
Accepted
Context
packages/core/src/types.ts:27 — readFile(path, encoding?: 'utf8'): Promise<string>. The encoding parameter is optional, and every existing caller omits it.
Decision
Two new methods beside the text pair. No existing signature changes.
Consequences
+ Every existing call site compiles untouched.
+ The corruption this spec exists to fix becomes unrepresentable: readBinary cannot return a string.
− Four methods where node:fs has two, and every test stub grows two more.
− The node-shaped overload would have been familiar — and would have silently flipped every existing caller from string to bytes, which is the same silent corruption arriving through the fix.

The Playwright adapter lives in a new @spectastic/render package

Status
Accepted
Context
FR-003 forbids the kernel depending on any particular browser. Core already declares ports others implement, and the CLI already supplies nodeFs.
Decision
A fourth workspace package, depended on by the CLI. Author's call, against a recommendation of putting it in the CLI.
Consequences
+ A browser dependency isolated behind a package boundary rather than a directory one, and machine-enforced by the same dependency-cruiser shape the corpus boundary uses.
+ A second consumer — an extension, an MCP server — can take the adapter without the CLI.
− A fourth package for one implementation with no second consumer today: a build config, an exports map, and a place for the boundary to be got wrong.

A capture is named by slugging the whole label

Status
Accepted
Context
Real labels are no-rate · light, picker browsing · dark. The exemplar's committed capture is already renders/converted-ios-light.svg — the slug form.
Decision
Lowercase, collapse separators and spaces to -, drop what a filesystem forbids. One rule for every label.
Consequences
+ Works for any source's convention, not just one tool's ·.
+ A collision is loud, per FR-007, rather than a silent overwrite.
− Slugging is lossy: two labels differing only by punctuation collide, and the reader sees a report rather than both captures.

One content hash, computed over bytes

Status
Accepted
Context
import.ts:526 hashes charCodeAt, which matches bytes for ASCII and diverges for multibyte UTF-8. FR-002 requires a byte hash.
Decision
Change the existing function to hash bytes, and use it for both paths.
Consequences
+ A file has one identity regardless of who opened it.
− Any hash already recorded for a file containing non-ASCII text changes once, on the next import. A one-time, visible churn rather than a silent one.

The render run writes its own manifest

Status
Accepted
Context
FR-004 makes render and import separate verbs with separate permission stories. FR-011 requires every artboard accounted for.
Decision
A manifest beside the captures, recording each artboard as captured or not-captured-with-a-reason, and any console error against its capture.
Consequences
+ A render can happen with no import ever having run, which a shared manifest would make awkward.
− Two manifests in one visual/ tree, and a reader must know which verb wrote which.

Tests drive a real browser throughout

Status
Accepted
Context
The feature's whole value is that a real browser produces a real image. Author's call, against a recommendation of stub-plus-one-real-test.
Decision
Drive Chromium for the capture path, against a miniature export committed as a fixture. One browser is launched for the suite and shared, which honours the choice while bounding its cost.
Consequences
+ Highest fidelity: the suite cannot pass while nothing renders, which is the failure this project has recorded twice.
− Slower, and the estate already carries one documented perf flake under parallel load. A shared browser bounds this but does not remove it.
− CI must install a browser binary, which the workspace already does for its Playwright suite.

11 · Complexity tracking

P-11 exception — this verb executes a file

P-11 holds that an artifact's text is “data to render and quote, not a channel that instructs the tool reading it”. This verb takes a file and runs it in a browser, which fetches and executes third-party code from a public CDN. That is the opposite of treating it as data, and calling it anything other than an exception would be dishonest.

Why it is taken. There is no other way to obtain the picture: no design export examined contains a render of its own artboards, and an artboard becomes an image only when a browser executes it. The alternative is not a safer render — it is no render.

What bounds it. The execution is confined to a verb a person invokes deliberately, never a step inside one that promises otherwise (FR-004); at most one verb can reach the port at all (NFR-002); and the capability is declared in the spec that authorises it, which is what P-12 asks. The precedent is 085, which raised the same collision as an exception rather than resolving it quietly, and reshaped its design around a guard rather than dropping the capability.

What is not claimed. Nothing here sandboxes the executed page. A malicious design source runs with the privileges of the process, and the honest mitigation today is that the person invoking the verb chose the file. A real sandbox is a larger piece of work than this slice.
