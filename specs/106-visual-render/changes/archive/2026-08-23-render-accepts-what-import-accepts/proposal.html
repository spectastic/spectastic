Change proposal · 106-visual-render

Render accepts what import accepts

A real design export is an archive of files. Import takes one; render takes a page. So no single source satisfies both verbs, and the one-step flag that passes one value to both captures nothing.

Status Applied Change ID 2026-08-23-render-accepts-what-import-accepts Spec 106-visual-render Author Brian Corbin · @briancorbinxyz Created 23 Aug 2026 Targets 2 requirements Read time

Nothing in this spec says what the verb’s source may be, so it grew a page-only implementation while 105’s import grew a folder-and-archive one. Reproduced against a real 4-file design export: pointed at the archive the verb fails (the browser downloads it); pointed at the extracted folder it captures 0, silently; pointed at the one artboard file inside it captures 22. Two ADDs — the verb states the source shapes it accepts, and a resolved source yielding no artboards is reported rather than silent. The adversarial pass reshaped both before they were written.

Render accepts what import accepts

Applied

1 · Intent

Found by asking a simple question of the newly-shipped one-step flag (110): if the artboard HTML is refused at import for carrying a runtime, where do the renders come from? The answer turned out to be that they do not come at all, and the reason has nothing to do with that refusal.

Reproduced end to end against a real design export — a 4-file archive containing one artboard document, a 69 KB runtime and an uploaded spec:

  • Pointed at the archive — what the one-step flag passes — the verb fails outright: page.goto: Download is starting. The browser downloads the file rather than rendering it. No captures, no renders/ directory.
  • Pointed at the extracted folder, the verb reports 0 written, 0 refused and exits successfully. Navigating a browser to a directory finds no artboards, so there is nothing to report and nothing is reported.
  • Pointed at the one artboard file inside it, the verb captures 22 screens correctly.

So the capability works; only the way in does not. Import resolves an archive or a folder because 105 gave it a fetcher that does; this verb navigates whatever string it is handed. Neither spec ever wrote down what a source may be, so the two answers drifted apart without either being wrong on its own terms.

The consequence is not confined to the flag. Anyone running the three verbs by hand over an extracted export hits the same silent zero — including 110’s SC-001, whose comparison currently holds because both sides render a directory and both therefore capture nothing. The criterion passes on two empty results. That is why this change belongs here rather than in 110: fixing only the orchestrator would leave the hand-run broken and the criterion still vacuous.

P-11 is not implicated, and the first reading of this defect blamed it. Refusing to land the artboard costs the render nothing: this verb never reads the sidecar, it navigates the source. And derivation already mines refused material — all 73 token candidates from the real export came out of the two files import declined to land. The refusal is the artifact rule working exactly as intended.

2 · Scope

In scope

  • Stating what the verb’s source may be, enumerated here rather than by reference to another spec’s implementation, so a single value can serve both verbs and a future edit to 105 cannot retype a must-tier requirement of this one without a delta.
  • Making a source that resolved but yielded no artboards reported rather than silent, so the difference between “this declares none” and “you pointed at the wrong thing” is visible.

Out of scope

  • Relaxing the import’s in-project containment so an export in ~/Downloads can be used directly. Decided, and being authored as its own proposal against 105 rather than folded in here, since the apply kernel folds same-spec deltas only and the two land independently.
  • Whether 110 needs its own amendment once this lands — its one-value design becomes correct, but its SC-001 currently passes on two empty results and the task list below budgets a re-check rather than assuming the answer , so the question stays attached.
  • Whether a rendered artboard should also be landed as design material rather than only captured — a larger question about what the sidecar is for.

3 · Approach

The verb keeps one notion of a source and gains the ability to resolve it. Where the source is already a page or a URL, nothing changes. Where it is an archive or a directory, it resolves to the page or pages inside that declare artboards.

The port widens rather than the budget. NFR-001 bounds a run over one source at a single browser process and requires every artboard be captured in that one session, and today chromium.launch() sits inside the port’s per-location call — so rendering several pages the naive way would be several launches and a broken must-tier bound. The port therefore takes a set of locations and navigates them in one session, which is the reading of NFR-001 that survives a multi-page export rather than the one that quietly exceeds it. Caught by the adversarial pass, before a task list that never touched packages/render would have made the contradiction somebody else’s to find.

The second delta is narrow but load-bearing, and it is a separate requirement rather than a clause bolted onto FR-011. FR-011 already requires every artboard found to be accounted for — which is exactly why a directory is silent: zero are found, so the accounting has nothing to say and says it correctly. Widening the subject from the artboards to the source is a genuinely absolute obligation, and FR-011 is should-tier, so folding it in would have buried a MUST inside a SHOULD where nothing enumerating must-tier requirements would find it. The same split 093 made, for the same reason.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec. op= is one of added | modified | removed | renamed; a missing or invalid op renders visibly broken.

The verb MUST accept a source that is a page, a URL, a directory, or an archive. A directory or an archive MUST be resolved to the page or pages within it that declare artboards, and every resolved page MUST be rendered within the single session NFR-001 permits. A source that resolves to no page at all MUST be refused with a stated reason rather than navigated as-is.

Rationale

Neither this spec nor 105 ever stated what a source may be, so import grew a fetcher that resolves archives and directories while this verb navigated whatever string it was handed — and a real export is an archive. Measured on one: the archive fails outright (the browser downloads it), the extracted directory captures 0, and the artboard file inside captures 22. The cost is not confined to the one-step flag that passes a single value to both verbs; anyone running the verbs by hand over an extracted export gets the same silent nothing. The shapes are enumerated here rather than defined as “whatever the import accepts”: that phrasing would have silently subtracted the URL this verb has always taken, imported the import’s in-project containment onto the one verb whose purpose is browser navigation, and let a future edit to another spec retype this requirement without a delta.

A source that resolved but yielded no artboards MUST be reported with that fact stated — not as a refusal, since a source may legitimately declare none, but never as silence.

Rationale

FR-011’s accounting takes the artboards as its subject, so pointing the verb at a directory finds none, and a run that captured nothing reports nothing and exits successfully. Correct by the letter and useless in practice: it is how a source-shape mismatch survived a full lifecycle pass with a green suite, and it is the one signal that would have named the defect. Stated as its own must-tier requirement rather than appended to FR-011, which is should-tier — an absolute obligation buried inside a recommendation is invisible to anything enumerating what this spec actually requires.

4b · What this change removes

Each entry names one thing this change takes away — a clause dropped from a requirement it retypes, an obligation a sibling loses, a behaviour or affordance no requirement records. An empty register is the answer “this removes nothing”, so the common case needs no editing.

Where a delta removes something itself, its own reason and migration stay authoritative — this register is for what no delta can express.

  • The indistinguishability of a zero-capture run from a successful one. Today a run that captures nothing exits successfully and says nothing, so a caller checking only the exit code cannot tell the two apart. After this change it can. That is the point, but it is a real behavioural guarantee being removed, and a script written against the current silence would begin seeing output it did not before.
  • The render port’s single-location signature. Widening it to a set is not additive for anyone who has implemented the port: an existing implementation stops satisfying it. No requirement names the port’s shape, so no delta records this — which is precisely why it belongs here. The shipped Playwright adapter is the only implementation in this repository, but the port exists to admit others, and FR-003 says so.
  • The freedom to point the verb at something that is not a page and get a browser error. An unresolvable source is now refused with a stated reason, so the raw navigation failure — page.goto: Download is starting was the one that started this — stops reaching the caller. That message was useless as a diagnostic, but it was the truth about what happened, and a refusal is this spec’s account of it rather than the runtime’s.

5 · Risk register

Populated by the adversarial risk pass when the proposal triggers the heuristic (touches a must-tier requirement, contains an op="removed" delta, or spans ≥2 topic prefixes). One <spec-risk> per finding. target= is required (missing renders broken). status= defaults to identified; apply refuses until each transitions to accepted, mitigated, or rejected.

The requirement defined its own scope by reference to another spec’s implementation rather than by enumeration, and the set it pointed at is deliberately narrower than what this verb ships today. Import is local, in-project and network-free on purpose: localSourceFetcher throws SourceOutsideProjectError on an absolute path and on anything resolving outside cwd. visual:render’s help says --from <location> is “a local file path or a URL”, and renderVisualExport passes a scheme-bearing string through unchanged — on a verb that requires egress by FR-005. So the phrase silently subtracted the URL shape and imported in-project containment onto the one verb whose reason to exist is a browser navigation. The reproduction that motivated this change points --from at an export that, if it lives outside the project (the normal place a design tool drops a download), would be newly refused by the very clause added to fix it.

Original delta wording: “MUST accept the same source shapes the design import accepts”. Against packages/core/src/providers/local-source-fetcher.ts, packages/cli/src/commands/visual.ts:373, and live FR-005.

Draft response (author to disposition). Accepted; the delta was rewritten before it shipped. FR-012 now enumerates its own shapes — page, URL, directory, archive — so the URL survives explicitly, no containment is inherited, and a future edit to 105 cannot retype this requirement without a delta. Verified in source rather than taken on trust: the absolute-path and outside-project throws are both real, and the reproduction masked the problem because the export was copied into the project first. The containment question is genuine and now has its own proposal against 105, named in §2 — the write side was checked first and stands on its own, since destinations derive from readdir entries that can never be ...

NFR-001 bounds a run over a single design source at 1 browser process and requires every artboard be captured “in that one session”. FR-012 makes a directory or an archive a single source that may resolve to many pages, and each is rendered. The render port takes one location per call — Renderer.render(location) — and the shipped adapter launches Chromium inside it, whose own docstring cites NFR-001 as “render() launches Chromium exactly once”. Rendering N pages is therefore N launches, breaking a must-tier quantified bound. Satisfying both needs a port-shape change, and the original task list touched neither packages/render nor the port. A second-order effect also goes unaddressed: FR-007/SC-005 make two labels reducing to one name a reported collision, and widening a run from one page to a whole export makes cross-page collisions the common case.

Live NFR-001: “A run over a single design source MUST launch at most 1 browser process and MUST capture every artboard in that one session.” Against packages/render/src/index.ts:75’s per-call chromium.launch().

Draft response (author to disposition). Accepted, and the sharpest finding of the pass. Verified in source: chromium.launch() is inside render(location), so the contradiction is real rather than theoretical. Resolved by widening the port rather than the budget — it takes a set of locations and navigates them in one session, which keeps NFR-001 exactly as written instead of redefining it per page. FR-012 now says so in its own text, §3 records the reasoning, §4b records that this breaks any existing port implementation, and the task list gains the packages/render work it was missing. The cross-page collision effect is real and is carried as its own task rather than assumed away: FR-007 already reports collisions, so the behaviour is correct — what changes is how often it fires, which the task checks against the real export.

The out-of-scope item asserted a sibling spec’s correctness and then foreclosed revisiting it, from inside a proposal that admits it does not yet know. §6 budgets work to re-check 110’s SC-001; §1 argues that criterion currently compares two paths that both produce nothing. That is an open must-tier question about another spec, and defer-to="never" left no slug to carry it if the answer is no. The premise was also stated imprecisely: SC-001’s Observed at already scopes around the design --visuals path deliberately, comparing the three CLI entry points over a hand-authored design instead.

Original §2: “Changing 110. Its design is correct once this lands, and needs no amendment to become so” with defer-to="never". Against §6 task 5 and 110 SC-001’s Observed at.

Draft response (author to disposition). Accepted on the disposition, and the citation is half right in a way worth recording. The never is replaced with a real slug, which was the substantive point: a question §6 budgets work for cannot be closed in §2. On the premise — SC-001 does scope around the --visuals path, but its hand-run leg renders a directory, so both sides still capture nothing and the criterion still passes on two empty results. §1 now says that precisely rather than by implication, which is a better sentence than either version.

The corpus states the conformance level is what makes obligation machine-discoverable, and FR-011 already strains that: priority="should" while carrying an absolute “every artboard found MUST be accounted for”. The original delta re-typed the requirement and added a second absolute clause while leaving the level at should. A tool enumerating must-tier requirements would miss two genuine obligations, and the one the proposal calls load-bearing would be the less greppable of the pair. This repo has the precedent: 093’s proposal split a should-tier requirement carrying bare MUSTs into a must-tier requirement for exactly this reason.

KB-0001@2026-07-25 (spectastic/spectastic · spectastic-concepts · 001-foundations): “makes the conformance level machine-greppable as well as human-readable — a validate rule or a downstream tool can find every must-tier requirement without parsing prose.” Against the original op="modified" target="FR-011" delta.

Draft response (author to disposition). Accepted, and it removed a delta rather than adding one. The zero-artboard clause is now its own must-tier FR-013, and FR-011 is not touched at all — so the obligation is greppable, the should-tier re-run clause stays where it belongs, and the rationale-carrying problem that came with retyping FR-011 disappears with it. FR-011’s own pre-existing should-with-a-MUST tension is left alone deliberately: it predates this change, and fixing it here would be scope this proposal did not earn.

6 · Tasks

Scoped to this change only. On /spectastic.apply these fold into the target's tasks.html as a new provenance-linked phase (per REQ-CHANGE-006) that /spectastic.implement drains — this list is then the frozen intent record.

  • Write failing tests for the four source shapes against a fixture export — a page, a URL, a directory, and an archive — asserting each resolves and captures the same artboards, and that a source resolving to no page is refused with a stated reason. packages/core/test/render-capture.test.ts
  • Widen the render port to take a set of locations and navigate them in one browser session, so a multi-page source still satisfies NFR-001's single-process bound. packages/render/src/index.ts
  • Assert the single-session bound directly — a multi-page source launches exactly one browser process, the property NFR-001 states and the previous per-call shape could not hold. packages/render/test/single-session.test.ts
  • Resolve the source before navigating, selecting the page(s) declaring artboards from what the fetcher returns. packages/core/src/visual/render-capture.ts
  • Report a resolved source that yielded no artboards in the run manifest, distinct from both a refusal and a successful capture (FR-013). packages/core/src/visual/render-manifest.ts
  • Check cross-page label collisions against the real export — FR-007 already reports them, but a whole-export run makes them common rather than rare, so confirm the report is usable at that volume rather than a wall. packages/core/test/render-naming.test.ts
  • Add an end-to-end test that the one-step flag produces captures from a single --visuals value pointed at an archive — the case that produced an empty renders/ directory and reported success. packages/cli/test/design-visuals.test.ts
  • Re-check 110's SC-001 byte-equality test once both paths capture real artboards, since it currently passes on two empty results; if it needs amending, that is a propose against 110 rather than an edit here. packages/cli/test/design-visuals.test.ts

7 · Open questions

None outstanding. Five decisions were anchored: where the fix belongs (here rather than in 110, because the hand-run is broken the same way), whether a zero-artboard run should stay silent (no — that silence is what hid this), how the source shapes are stated (enumerated here, keeping the URL, inheriting no containment), how a multi-page source meets the single-process bound (the port widens to a set of locations rather than the budget widening per page), and the status to ship at. The import's in-project containment is decided but deliberately carried by its own proposal against 105, since apply folds same-spec deltas only.
