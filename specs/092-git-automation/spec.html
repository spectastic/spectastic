What the verbs do with git when a project opts in — branch model, commit contract, and default-off delivery.

1 · Context

Driving git on someone else’s behalf is the most intrusive thing the tool can do, so it is off unless asked for and narrow when granted. These requirements bound it: what gets branched, what a generated commit message may claim, and the guarantee that the feature stays opt-in.

This spec is a slice of the spectastic meta-spec. Its requirements were authored there and moved here intact, keeping their stable ids: a requirement that was REQ-GIT-001 in the parent is REQ-GIT-001 here, so every existing citation still names the same contract. The parent keeps the project’s context, architecture, decisions and history; this file carries one family of requirements and nothing else.

2 · Requirements

Normative keywords follow RFC 2119.

Branch model. Under branch-based automation (git.auto=branch+commit), spec MUST create the slice's branch named NNN-slug off the default branch when it opens the slice. Small, revert-safe work — just-do cards, triage list-intake, one-file hotfixes — MUST stay on the current branch (no branch created), reusing the existing just-do boundary.

This family binds spectastic's own git automation — what the verbs do when a developer opts in. A consuming project's hand-commits and its PR-merge strategy are its own; REQ-GIT does not govern them.
Rationale

The slice is the natural unit of review; the latent 018-explain pattern proved the shape. Branch creation + the small-work exception are implemented by 026 FR-003 / FR-005 (git-strategy G-002). Two parts of the model are described, not mandated, because nothing automates them today: the slice branch merges to the default branch when the spec flips Accepted, and proposals are intended to live on change/NNN-<date>-<slug> branches. Both are the developer's action (or a PR) — the intended workflow, not a conformance MUST — and stay descriptive until a future slice implements them.

Commit message contract (subject + attribution). An auto-commit's subject MUST follow <verb>(NNN): <subject> (Conventional Commits — the lifecycle verb as type, the spec id as scope) whenever a spec id is in play, and the unscoped <verb>: <subject> form when it isn't (triage list-intake, principles, an implement run draining an inbox just-do card). implement MUST emit one commit per drain invocation, not one per ticked task. Authorship of record is human only: when attribution trailers are written, spectastic MUST NOT emit an AI identity as Author, Co-authored-by, Reviewed-by, or Acked-by — the assisting model is acknowledged distinctly, and only, as Assisted-by: <model>. (Which trailers are emitted, and when, is the delivery concern of REQ-GIT-003 + git.trailers.)

Rationale

The grammar already speaks in the history; the unscoped form and the Assisted-by stance were settled in 027. Conventional Commits explicitly permits types beyond feat/fix — here the lifecycle verb is the (custom, permitted) type, the spec id the scope. Implemented by 026 FR-002/FR-007 + 027 FR-005/FR-006 (git-strategy G-003 + G-004).

Opt-in, default-off delivery. Git automation MUST be opt-in and default off: git.auto and git.trailers both default off, every verb MUST accept --commit/--no-commit, and with automation off no verb performs any git action. An auto-commit MUST be gated on a clean spectastic validate and compose after the P-6 state-gate and the explore quarantine (never around them). The git layer itself MUST NOT introduce squash-on-merge as a default, nor rewrite or squash existing default-branch history — per-verb commits are the legible record. This binds the layer, not the consuming project: how a project merges its own PRs (squash or not) is its choice; the contract is only that spectastic's automation doesn't squash for it.

Rationale

The house enforcement stance (opt-in, default off, documented loudly); per-verb commits are the legible record. Implemented by 026 FR-001/FR-004/NFR-002 (git-strategy G-003 §7 guardrails).
