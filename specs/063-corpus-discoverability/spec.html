Specification · 063-corpus-discoverability

Corpus discoverability

A corpus describes itself and is discoverable by default — carrying a marketplace.json kept in sync with its registry, configured at init, published on demand — reversing the consumer-only stance once the portability rule learns to spare a tool's own pack.

1 · Context

062 settled the meta-repo's corpus as consumer-only — FR-009 forbids a distributable root marketplace.json — because 057's pack-not-portable rule (error severity) fires on any marketplace-listed pack embedding <spec-*> tags or verb names, and spectastic-concepts legitimately carries them. That decision made a corpus invisible: nothing describes it, nothing else can find or install it, and a downstream project migrating its own in-repo pack hit exactly this wall — "we have no marketplace.json" — with no first-class way to become discoverable.

The pivot: a corpus should be a self-describing, discoverable unit by default, the way an Agent Skill marketplace already is. The blocker was never discoverability itself — it was that pack-not-portable conflated "listed in a marketplace" with "portable to any other domain". A pack whose domain is a specific tool is legitimately both listed and non-portable. Once a pack can self-declare tool-specific and the rule spares it, discoverability and the portability guarantee stop fighting, and 062 FR-009's consumer-only default can be retracted. This is the TBD-corpus-publish follow-on 062 named.

2 · User scenarios & testing

Each story MUST be independently testable. US1 (config at init) stands alone as a viable first increment even before a manifest is generated.

US1 · Configure the corpus at init P1

As a project author running spectastic init, I want a corpus section written to spectastic.json — the marketplace name defaulting to my repo name, and the corpus root directory so that every corpus verb has one source of truth for what my corpus is called and where it lives.

Acceptance: after spectastic init, spectastic.json carries corpus.marketplace (defaulting to basename(cwd)) and corpus.root (defaulting to knowledge); a marketplace-less local corpus import files under corpus.marketplace (folding 061's interim corpus.namespace into this single key).

US2 · A corpus carries a synced marketplace.json P1

As a corpus maintainer, I want my corpus to carry a marketplace.json generated from my registry and kept in sync by the corpus verbs, with corpus publish generating a missing one so that the corpus is self-describing and installable without a hand-written manifest.

Acceptance: corpus publish writes <root>/marketplace.json (name from corpus.marketplace, one plugins[] entry per pack derived from index.md + each pack's SKILL.md); a subsequent corpus write verb (import / register / adapt / interview / source) keeps it in sync as packs change; and a pack self-declared tool-specific is listed without tripping pack-not-portable.

US3 · Discoverable-by-default supersedes consumer-only P2

As a maintainer of the meta-repo (and any spectastic project), I want discoverable-by-default to become the stance, retracting 062's consumer-only clause and publishing the meta-repo's own corpus so that the tool dogfoods the discoverability it now offers downstream.

Acceptance: the meta-repo's knowledge/ gains a marketplace.json listing spectastic-concepts (tool-specific) and finance-settlement; 062 FR-009 is retracted via a MODIFY propose (named, not silent); and full-corpus validate stays at its prior error baseline.

Edge cases

  • marketplace.json already hand-edited. Sync + publish preserve hand-edited cells the way the registry merge does (non-destructive), rather than clobbering an owner/description a human tuned.
  • A pack with no SKILL.md description. The plugin entry's description falls back rather than fabricating (NFR-002); 057 already warns on a missing discovery description.
  • A corpus with zero packs. publish writes a manifest with an empty plugins[] (a valid, discoverable-but-empty marketplace), never an error.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

spectastic init MUST write a corpus section to spectastic.json with marketplace (defaulting to the repo directory name, basename(cwd)) and root (defaulting to knowledge).

A corpus MUST be describable by a marketplace.json at its corpus.root, carrying the marketplace name (from corpus.marketplace), an owner, and one plugins[] entry per pack (name, relative source, description) — the discoverable, self-describing manifest a consuming project installs from.

The corpus write verbs (import, register via interview/source, adapt) MUST keep marketplace.json in sync with the root index.md registry — adding, updating, or reflecting a pack's plugins[] entry as the registry changes — non-destructively, preserving hand-edited cells (mirroring the registry merge).

A corpus publish subcommand MUST generate a marketplace.json for a corpus that lacks one — from corpus.marketplace plus the packs in index.md — and MUST be idempotent (a re-run against an in-sync corpus changes nothing).

A pack MUST be able to self-declare tool-specific (in its own SKILL.md), and 057's pack-not-portable rule MUST skip a self-declared tool-specific pack — so a corpus listing an inherently tool-specific pack (the meta-repo's spectastic-concepts) is discoverable without a false portability error, while a pack meant for cross-domain reuse still gets the hard check.

Rationale

pack-not-portable conflated "listed in a marketplace" with "portable to any domain". A pack whose subject is a specific tool is legitimately both. The self-declaration makes the distinction explicit and machine-readable rather than exempt-by-omission (057 D-002), which is what required consumer-only in the first place.

The corpus's marketplace name MUST be the single canonical source for both the marketplace.json name and the default namespace a marketplace-less local import files under (061 FR-008). The interim corpus.namespace key (061) SHOULD be retained only as a deprecated read-alias resolving to corpus.marketplace, so the manifest name and the registry namespace can never drift apart.

Discoverable-by-default SHOULD supersede 062 FR-009's consumer-only default; landing this MUST retract that clause via a MODIFY-FR-009 propose on 062 (recorded, never a silent contradiction), and the meta-repo MUST publish its own corpus as the dogfood.

Non-functional

Manifest generation and sync MUST be deterministic: regenerating marketplace.json from the same index.md + config yields byte-identical output, with no clock or network read.

Generation MUST NOT fabricate: a plugin's description is derived from the pack's SKILL.md (falling back, never inventing), and source is the pack's real relative path — the same never-fabricate discipline the registry already holds (061 FR-009).

Out of scope (deferred to other slices)

  • The spec-text amendment to 057's pack-not-portable requirement recording the tool-specific exemption — a MODIFY propose on 057 (this spec owns the behaviour + code; 057's prose catches up).
  • The MODIFY-FR-009 propose retracting 062's consumer-only clause — FR-007 requires it as a cascade; the propose itself lands against 062.
  • Rewriting a pack's source to a remote git URL for cross-repo distribution — publish emits relative-path sources (marketplace-is-the-repo); a remote-source rewrite is a later concern.
  • A configurable owner block beyond a sensible default — the manifest's owner is defaulted for now.

4 · Data model

Three artifacts at a corpus root, now kept mutually consistent:

Entities

spectastic.json · corpus
New config object: marketplace (string, the name + local namespace; default basename(cwd)) and root (string, the corpus base directory; default knowledge). Set at init (FR-001); root is the overridable base 062 T-002 made corpus-root-relative.
<root>/marketplace.json
The discoverable manifest: { name, owner, plugins:[{ name, source, description }] }. Generated + synced from the registry + config (FR-002/003/004); never hand-authored, but hand-edited cells survive a re-sync.
<root>/index.md
The KB-NNNN registry (062), unchanged — the source of truth the manifest's plugins[] is derived from.
Pack SKILL.md · tool-specific flag
A pack self-declares tool-specific here (FR-005); pack-not-portable reads it to decide whether to enforce portability. The exact field name is a plan choice.

Invariant: corpus.marketplace is the one name — the manifest's name and the local-import namespace are always the same value (FR-006), so the discoverable identity and the resolution identity never diverge.

5 · Success criteria

Technology-agnostic, measurable outcomes.

After spectastic init, spectastic.json contains corpus.marketplace equal to the repo directory name and corpus.root equal to knowledge.

corpus publish on the meta-repo writes knowledge/marketplace.json listing both packs (spectastic-concepts marked tool-specific, finance-settlement), and full-corpus spectastic validate stays at its prior error baseline — no new pack-not-portable error.

Registering a new pack through any corpus write verb updates marketplace.json to include it, matching index.md, with no manual edit — and a re-run of corpus publish changes nothing (idempotent).

A marketplace-less local corpus import <plugin> --from … files the pack under the corpus.marketplace name; corpus.namespace, if present, resolves to it as a deprecated read-alias (never a second independent value).
