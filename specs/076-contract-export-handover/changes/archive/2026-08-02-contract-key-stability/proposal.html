A contract's federation key should be authored, not inherited from a filename

The escape hatch exists and nothing asks for it, so everyone lands on the fallback — and the fallback is a filename.

Status Applied Change ID 2026-08-02-contract-key-stability Spec 076-contract-export-handover Source Considerations: orchestrator-placement; resolves TBD-contract-key-stability Author Brian Corbin · @briancorbinxyz Created 02 Aug 2026 Targets 1 added (FR-007) Read time

A contract's coordinate name resolves from its declared name= and falls back to the file's basename. The fallback is doing all the work: templates/design.html's <spec-contract> scaffold does not include name=, and neither does the design command's contract question — so a coordinate that is meant to be a stable federation key is, in practice, always a filename. Two consequences follow. Renaming or reformatting a contract silently re-keys it, breaking every downstream reference with no rename detection anywhere. And two contracts in one project must have distinct basenames regardless of directory, since the directory is discarded before the key is formed. Neither is a defect in the resolution logic, which is correct; both come from an escape hatch nothing prompts for. This requires the key to be authored where a contract is expected to be referenced, and makes a collision an error rather than a silent overwrite.

A contract's federation key should be authored, not inherited from a filename

Applied

1 · Intent

076 made a contract addressable so a consumer in another repository can name it. The name resolves through contractCoordinateName, which prefers an explicitly declared name= and otherwise derives one from the path's basename. That design is right: an author who cares can pin the key, and one who does not gets something reasonable.

What was missed is that nothing ever asks. The design template's <spec-contract> scaffold carries shape, path and format and no name; the design command's contract questions fill exactly those three. So the deliberate escape hatch is unreachable by anyone following the documented path, and every contract in practice is keyed by its filename.

A filename is a poor federation key for two specific reasons. It is editable for reasons unrelated to identity — renaming openapi.yaml to payments-api.yaml, or switching format extension, silently mints a different coordinate while every downstream reference keeps pointing at the old one, and nothing detects a rename. And it is not unique within a project: the directory is discarded before the key is formed, so api/v1/openapi.yaml and api/v2/openapi.yaml collide on one key. Both are latent today because the estate has one contract; both become live the moment a project has two, which is the ordinary case for anything versioned.

2 · Scope

In scope

  • A requirement that the coordinate name is authored where a contract is expected to be referenced across a repository boundary.
  • A collision between two declarations resolving to the same key becoming an error rather than a silent last-one-wins.
  • Prompting for the key where contracts are authored, so the escape hatch is reachable by the documented path.

Out of scope

  • Rename detection. Recording that a key moved needs a history the estate does not keep; the fix here is to stop tying the key to something that moves.
  • Changing contractCoordinateName's resolution order. Declared-then-basename is correct and stays.
  • Making name= unconditionally mandatory. A single-contract project with no cross-repo consumer is well served by the fallback, and requiring ceremony there would be noise.

3 · Approach

Require the key conditionally rather than universally — at the point where it actually becomes load-bearing, which is when a contract is expected to be referenced from outside its own project, or when a project holds more than one contract. That keeps the simple case simple and closes the case where a filename cannot carry the weight being put on it.

The collision check is the part with real teeth and it is cheap: two declarations in one project resolving to the same coordinate name is unambiguously wrong, detectable from the declarations alone, and today would silently resolve to whichever was read last. Making it an error costs nothing and removes a class of failure that would otherwise surface as a downstream reference quietly pointing at the wrong document.

4 · Deltas

One delta.

A contract's coordinate name SHOULD be explicitly declared where the contract is expected to be referenced from outside its own project, or where the project declares more than one contract, rather than left to the basename fallback. Two declarations within one project that resolve to the same coordinate name MUST be reported as an error.

Rationale

The name resolves from a declared name= and falls back to the path's basename, but nothing prompts for the attribute — not the design template's scaffold, not the design command's contract questions — so in practice every key is a filename. A filename is editable for reasons unrelated to identity, so a rename silently mints a new coordinate while downstream references keep pointing at the old one, and no rename detection exists anywhere. It is also not unique within a project, since the directory is discarded before the key is formed: two versioned contracts under different directories collide on one key and resolve to whichever was read last. Conditional rather than universal because a single-contract project with no external consumer is well served by the fallback; the collision half is unconditional because it is unambiguously an error and free to detect.

5 · Risk register
