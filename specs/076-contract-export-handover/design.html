Design · 076-contract-export-handover

Contract export handover

How we will build it.

Status Accepted Spec 076-contract-export-handover Owner Brian Corbin · @briancorbinxyz Branch main Created 01 Aug 2026 Read time

Generalise one function and add two artifacts. specResourceUri() already composes spectastic://<owner>/<repo…>/spec/<id> with spec/ hardcoded as the kind segment — so a contract coordinate is that same function with the kind lifted to a parameter, which is exactly the "sibling resource kind" 067's design anticipated. On top of it: a change notification emitted at promotion, and an optional consumer dependency record so notification can be routed rather than broadcast. The distribution mechanism is deliberately absent — descoped, not undecided, because FR-004 forbids the surface requiring one.

3 · Data model & contracts

The coordinate is the load-bearing entity — a mechanism can be swapped, but a coordinate consumers have written down cannot.

Conceptual entityPhysical shapeNotes
Contract coordinate spectastic://<owner>/<repo…>/contract/<name> The same composition specResourceUri performs, with the kind segment lifted from a hardcoded spec to a parameter. The name is declaration-derived, never path-derived (D-002).
Change notification A file emitted at promotion — coordinate, change class, and a reason for the withdrawal subtype Breaking / non-breaking is the required split; withdrawn is a reason on a breaking change, not a third class (D-003).
Consumer declaration An optional array of coordinates in spectastic.json Configuration, not artifact markup — it is a project-level fact, and spectastic.json already holds exactly that kind (D-004).

No interface of its own. The irony is worth naming: this slice is about making other projects' contracts travel, and it exposes none itself. It emits a file and prints a string; whatever carries them is the consuming project's choice, which is precisely what FR-004 protects.

5 · Approach

The coordinate comes first and is the smallest change: specResourceUri() becomes resourceUri(project, kind, name, anchor?) with specResourceUri kept as a thin wrapper so no existing caller moves, and contractResourceUri() added beside it. The kind segment was already the only difference between a spec address and a contract address, which is why 067's design called sibling kinds out in advance.

Stability under a file move (FR-002) forces one real decision: the coordinate's name segment must come from the declaration, not the path. A design declaring path="api/openapi.yaml" today and path="openapi/service.yaml" tomorrow must keep one address, so the name is a stable identifier carried alongside the declaration rather than the file's basename. Then promotion emits a notification naming the coordinate and the change class, and an optional consumes array in spectastic.json lets a consuming project record which coordinates it depends on so notification can be routed. Finally a read-only spectastic contract command prints the contract at a coordinate, cloning spectastic id's shape.

6 · Alternatives considered

The load-bearing choice is what the coordinate's name segment derives from, since FR-002 requires it survive a file move. Scored 1–5, higher is better.

OptionSurvives a moveNo new stateReadable to a consumerTotal
The contract file's basename15410
An opaque generated identifier5218
A stable name on the declaration — chosen53513

The basename is what everyone reaches for and it fails the one requirement that matters: rename api/openapi.yaml to openapi/service.yaml and every consumer's written-down address breaks — the precise failure SC-002 forbids. An opaque identifier survives anything and is unreadable, which for an address humans paste into issues and configs is a real cost.

7 · Decisions

D-001 · Generalise specResourceUri; add no scheme

Status
Accepted
Context
packages/schema/src/project-shared.ts:54-61 composes `${rest}/spec/${specId}` with spec/ literal, and its doc comment describes the form as federation-unique. FR-001 forbids a contract-specific naming scheme.
Decision
Lift the kind to a parameter — resourceUri(project, kind, name, anchor?) — keep specResourceUri as a wrapper so no caller changes, and add contractResourceUri.
Consequences
+ One composer, one authority rule, one degradation path for bare projects. + Existing callers untouched. + A third kind later is a parameter, not a design. − project-shared.ts now serves more than specs; its name becomes slightly narrow for what it holds, noted rather than renamed mid-cohort.

D-002 · The coordinate's name is declaration-derived, never path-derived

Status
Accepted
Context
FR-002 requires the coordinate survive a file-path change, and SC-002 permits 0 exceptions. A basename cannot: it changes by definition when the file moves. P-3 makes this sharper — a coordinate is an id that has left the repository, so it is a contract with people the tool cannot see.
Decision drivers
Survives a move · avoids new state · readable when pasted into an issue
Considered options
  • The file's basename — + zero new state. − Breaks on rename, which is the one thing FR-002 forbids.
  • An opaque generated id — + immune to everything. − Unreadable in an issue or a config file.
  • A stable declared name — chosen — + survives moves and stays readable. − One more attribute to author.
Decision
The name segment comes from a stable identifier carried with the declaration, defaulting to the basename at first authoring and thereafter independent of it.
Consequences
+ A file move never breaks a published address. + The address stays human-readable. − An author can rename the identifier and break consumers; that is a semantic act the tool should not silently prevent, and it is visible in the diff.

D-003 · A withdrawal is a breaking change with a reason, not a third class

Status
Accepted
Context
The spec's register carried this as an open fork, with the stated objection that a separate kind "adds a state that every consumer must handle". FR-003 requires only that breaking be distinguishable from non-breaking. Pure judgment; no external fact decides it.
Decision
Model withdrawal as a subtype: the change class stays breaking, and a reason field carries withdrawn.
Consequences
+ A consumer branching only on breaking-versus-non-breaking is still correct, since a withdrawal is unambiguously breaking — the objection disappears rather than being traded off. + A consumer that cares learns there is no successor shape to migrate to. − The distinction is a field rather than a type, so a careless consumer can ignore it; acceptable, because ignoring it still yields the safe behaviour.

D-004 · The consumer declaration is configuration, not artifact markup

Status
Accepted
Context
FR-005 asks a project to record the coordinates it depends on. That is a project-level fact, not a statement any single design makes, and spectastic.json already carries exactly this kind of section (git, validate, enforce).
Decision
An optional consumes array of coordinates in spectastic.json. No new element, no new file.
Consequences
+ Lives where project-level facts already live, and is readable without parsing HTML. + Absent by default, so NFR-002's monorepo-costs-nothing holds. − A consuming project that uses no spectastic artifacts still needs a spectastic.json to participate; a one-line file, and the feature is optional.

D-005 · Two mechanisms are demonstrated as recipes, not built

Status
Accepted
Context
SC-004 requires at least 2 distinct distribution mechanisms demonstrated over the same coordinate with 0 changes to this spec's guarantees. FR-004 forbids requiring any particular one, and the spec's out-of-scope list excludes SDK generation and registry operation.
Decision
Demonstrate by documented recipe — vendoring, and a published artifact — each exercised in a test that consumes the emitted notification. The recipes ship as documentation; neither mechanism is implemented in the tool.
Consequences
+ Proves the surface really is mechanism-agnostic rather than asserting it, which is the whole point of the criterion. + Adds no dependency. − A recipe can rot as external tooling moves; it is documentation, reviewed like documentation, and the guarantee it evidences is the tool's own surface.

10 · Complexity tracking

The mechanism question was descoped, not answered. The spec's register originally treated it as blocking. Read against FR-004 — which forbids the export surface requiring any particular registry, generator or package manager — it was asking whether to bless something the requirements already forbid the surface from depending on, and no requirement here needs the answer. It is re-deferred as TBD-contract-distribution-tier, a profile-catalog question, rather than left blocking a slice that is complete without it. Recorded because "we dropped the hard question" and "the hard question was not in scope" look identical from outside.

A coordinate is a promise the tool cannot keep alone. Once an address leaves the repository, its stability depends on humans not renaming it. D-002 removes the accidental breakage — a file move no longer breaks the address — but a deliberate rename still can. That residual is inherent to any naming scheme that stays human-readable, and the alternative (an opaque id) trades a real usability cost for it.

Breaking-versus-non-breaking is classified by the producer, not detected. The spec's out-of-scope list is explicit that deciding whether a change is breaking belongs to another slice; this one reports what it is told. So the notification carries a claim, and the copy should say so — the same posture 077 takes about compatibility stances.
