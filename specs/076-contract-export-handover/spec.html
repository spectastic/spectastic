Specification · 076-contract-export-handover

Contract export handover

Make the effective contract addressable and consumable from another repository — the original motivating problem, and the one with the most left to decide.

Status Accepted Spec ID 076-contract-export-handover Owner Brian Corbin · @briancorbinxyz Reviewers — Created 31 Jul 2026 Principlesv1.9.0 Smallest demoableA backend repository's effective contract is addressable by a stable coordinate that a UI repository can resolve and consume. Read time

This is the problem the whole line of work started from: a backend project's design produces a contract, and a UI team in a different repository needs it. Everything before this slice makes the contract exist, live somewhere findable, and stay honest. This slice makes it leave. The identity half is already solved — 067 landed an owner-qualified project identity and a spectastic:// resource URI whose design explicitly anticipates sibling resource kinds, so an exported contract inherits that coordinate rather than minting a scheme of its own. What is not settled is the mechanism: vendoring, a generated SDK published to a package registry, or a schema registry are three genuinely different answers with different operational costs, and the right one depends on organisational maturity rather than on anything the tool can detect. This spec therefore fixes the addressing and the change-notification obligation, and records the mechanism choice as an open question the design must settle with the profile tier in hand. Deliberately last: it is the highest-value slice and the one most likely to be built wrong if built early.

1 · Context

A spectastic project is a backend service. Its design settles what a settlement looks like on the wire, and a different team, in a different repository, is building the UI against it. They need the shape in a form their generator, type-checker and mock server can read. That scenario is what the data-model and contract survey set out to answer, and every slice before this one is groundwork: the contract now exists, is declared, lives somewhere findable, and is checked. It still does not travel.

One half of travelling is already solved. Spec 067 gave the estate an owner-qualified project identity behind a single-source-of-truth resolver and a federation-unique spectastic:// URI, whose design anticipated sibling resource kinds. An exported contract should be one of those kinds, not a new naming scheme — the alternative is two coordinate systems to reconcile the first time anything federates.

The other half is genuinely open. Every distribution mechanism consumes a checked-in contract, but they differ enormously: vendoring costs nothing and diverges silently; a generated SDK published to a package registry costs a CI job and a versioning policy; a schema registry costs infrastructure and organisational buy-in and repays it at scale. Which is right is an organisational judgment, not a detectable property — which is precisely the kind of decision the profile tier exists to carry, and precisely the kind this spec should not pre-empt.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · A consuming repository can name the contract P1

As a UI engineer in another repository, I want a stable coordinate for the backend's contract so that I can depend on it by name rather than by a path that moves.

Acceptance: The effective contract is addressable by a coordinate that survives a change of file path, and resolving it yields the contract.

US2 · A consumer learns the contract changed P1

As a consuming team, I want to be told when the interface I depend on changes so that I discover it from a signal rather than from a production failure.

Acceptance: A promoted contract change produces a notification artifact identifying what changed and at which coordinate; a change with no consumers produces at most 0 spurious signals.

US3 · The producer does not adopt someone else's toolchain P2

As a backend author, I want the export to work with whatever distribution my organisation already uses so that adopting spectastic does not mean adopting a package registry I did not choose.

Acceptance: The coordinate and notification are mechanism-agnostic; at least 2 distribution mechanisms can be layered on without changing the spec's guarantees.

Edge cases

  • A consumer pinned to an older contract version while the producer moves on.
  • A contract that moves path within the producer repository — the coordinate must not move with it.
  • A producer whose repository is private and a consumer who cannot read it.
  • Several consumers on different versions at once.
  • A contract withdrawn entirely because the interface was retired.
  • A monorepo where producer and consumer are the same repository and no export is needed at all.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

An effective contract MUST be addressable as a resource kind under the existing project coordinate, and MUST NOT introduce a contract-specific naming scheme.

Rationale

The identity question is solved. Minting a second scheme guarantees a reconciliation the first time the estate federates.

The coordinate MUST be stable across a change of the contract's file path within the producing repository.

Rationale

A coordinate that moves with the file is a path with extra steps, and gives a consumer nothing to depend on.

A change to an effective contract MUST produce a notification artifact identifying the coordinate and the nature of the change, distinguishing breaking from non-breaking.

The export surface MUST be mechanism-agnostic: it MUST NOT require any particular package registry, schema registry, or generator.

Rationale

The tool's job is to produce a correctly-located, addressable, honest contract. Publishing and registry operation are solved by tools whose whole purpose that is, and absorbing them would repeat a category error the project has refused before.

A consuming project SHOULD be able to record which coordinates it depends on, so a change notification can be routed rather than broadcast.

The tool MAY provide a read-only resolution command that prints the contract at a given coordinate.

A contract's coordinate name SHOULD be explicitly declared where the contract is expected to be referenced from outside its own project, or where the project declares more than one contract, rather than left to the basename fallback. Two declarations within one project that resolve to the same coordinate name MUST be reported as an error.

Rationale

The name resolves from a declared name= and falls back to the path's basename, but nothing prompts for the attribute — not the design template's scaffold, not the design command's contract questions — so in practice every key is a filename. A filename is editable for reasons unrelated to identity, so a rename silently mints a new coordinate while downstream references keep pointing at the old one, and no rename detection exists anywhere. It is also not unique within a project, since the directory is discarded before the key is formed: two versioned contracts under different directories collide on one key and resolve to whichever was read last. Conditional rather than universal because a single-contract project with no external consumer is well served by the fallback; the collision half is unconditional because it is unambiguously an error and free to detect.

Non-functional

Resolution and notification MUST be deterministic — the same inputs yield the same output, with at most 0 dependencies on wall-clock time.

A monorepo in which producer and consumer coexist SHOULD incur at most 0 additional steps, since the export problem does not arise there.

Out of scope (deferred to other slices)

  • Generating client SDKs from an exported contract — mature external tooling.
  • Operating or integrating a schema registry.
  • Version pinning and migration windows for consumers, which follow the mechanism choice.
  • Deciding whether a change is breaking — this slice reports it, that one detects it.

4 · Data model

No persisted entity beyond what the coordinate scheme already carries.

Entities

Contract coordinate
A stable, federation-unique address for an effective contract, qualified by the existing project identity and independent of the contract's file path.
Change notification
A record that a contract at a coordinate changed, carrying whether the change was breaking. Produced on promotion; consumed by whatever distribution mechanism a project chose.
Consumer declaration
Optional, per FR-005: the coordinates a project depends on, so notification can be routed.

The coordinate is the whole point of the slice and the only part that must be got right first: a mechanism can be swapped, but a coordinate that consumers have written down cannot.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

A consuming repository resolves a producer's contract by coordinate and generates from it, with at most 0 knowledge of the producer's internal file layout.

Moving the contract's file path within the producing repository changes the coordinate in at most 0 cases.

A promoted breaking change produces exactly 1 notification identifying the coordinate and its breaking nature; a non-breaking change is distinguishable from it.

At least 2 distinct distribution mechanisms are demonstrated over the same coordinate and notification, with at most 0 changes to this spec's guarantees.

6 · Assumptions

The project identity landed by 067 is stable enough to hang consumer-visible coordinates from. If it is not, this slice inherits that instability rather than causing it.

Consumers are willing to record their dependencies for routed notification. Where they are not, broadcast remains the fallback and the routing requirement stays a SHOULD.

7 · Open questions

None outstanding. Both were resolved on 01 Aug 2026, one by descoping and one in the design interview.

The distribution mechanism is out of scope, not undecided. Re-reading it against FR-004 — which requires the export surface be mechanism-agnostic and forbids requiring any particular package registry, schema registry or generator — showed the question was asking whether to bless a mechanism the requirements already forbid the surface from requiring. Every requirement here (FR-001–FR-007) is mechanism-neutral and implementable without it. A per-tier recommendation would be an addition to the profile catalog rather than part of this surface, so it is re-deferred as TBD-contract-distribution-tier rather than left blocking a slice that does not depend on it.

A withdrawal is a breaking change carrying a distinct reason, not a sibling notification kind. Modelling it as a separate top-level kind was the concern — every consumer would gain a state to handle. Modelling it as a subtype removes that cost: a consumer branching only on breaking-versus-non-breaking still handles a withdrawal correctly, because a withdrawal is unambiguously breaking, while a consumer that cares can read the reason and know there is no successor shape to migrate to. FR-003's breaking/non-breaking split is a floor, not a cap.
