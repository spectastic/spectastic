1 · Context

/spectastic.propose is the most architecturally-complex slash verb after implement. The canonical procedure at commands/spectastic.propose.md drives a two-phase interview (chat for narrative; AskUserQuestion for change shape, status, per-delta op, defer-to targets), then optionally fires an adversarial risk pass (per REQ-CHANGE-004) that spawns a critic sub-agent and embeds three findings as <spec-risk status="identified"> in §5.

Today the verb is markdown executed by the LLM; Tier 2 MCP and Tier 3 VS Code can't reach it. This slice extracts both layers into @spectastic/core/commands/propose following 006's contract, exercised by 007 (foundation) and 011 / 012 (interview shape). The adversarial pass introduces the first kernel requirement for sub-agent semantics on AIProvider.

2 · User scenarios & testing

Each story is independently testable; US1 alone is a viable MVP.

US1 · Maintainer authors a proposal via CLI P1

As a maintainer with a change to propose, I want to run spectastic propose <spec-id> "<description>" and get an interview-driven proposal.html under specs/<spec-id>/changes/<date>-<slug>/ so that the flow is reachable without a slash command and shared with future MCP / VS Code surfaces.

Acceptance: The CLI runs the kernel function with captured input; the kernel drives a two-phase interview via ctx.ai.ask<T>() (decisions) and ctx.io.prompt() (narrative); the proposal's deltas all carry valid op + target, verified against the live spec.

US2 · Adversarial pass fires automatically P1

As the same maintainer, I want the adversarial risk pass to fire automatically when the heuristic triggers so that the strongest counter-argument lands in the artifact without me asking for it.

Acceptance: On a must-tier-touching fixture, the kernel calls ctx.ai.subagent() with the critic prompt, receives exactly three RiskFinding objects, and embeds them as <spec-risk target="…" status="identified"> blocks in §5. --no-adversarial skips; --adversarial forces.

US3 · Downstream consumer invokes the kernel directly P2

As a future MCP or VS Code consumer, I want to import proposeCommand and invoke it with a typed input + stub AIProvider so that the verb works without re-implementing the interview, heuristic, or sub-agent spawn.

Acceptance: A test under packages/core/test/ calls proposeCommand(input, ctx) with a stub ai.subagent returning three canned findings; the returned ProposeResult contains the rendered HTML, deltas count, and the three risks. No process spawn.

Edge cases

Failure modes the extraction handles
  • Missing op or target on a delta — kernel renders the visible MISSING OP / MISSING TARGET labels per the canonical procedure rather than silently dropping the delta.
  • Hallucinated target ID — kernel verifies every modified | removed | renamed target exists in the live spec and every added target doesn't; mismatch raises a typed error before write.
  • Adversarial agent returns fewer than three findings — the kernel demands exactly three; the critic prompt forbids empties and requires <spec-risk status="no-value-found"> when no risk passes the "regret in 30 days" test.
  • Concurrent proposals on the same target — kernel scans specs/<spec-id>/changes/ for sibling proposals touching the same IDs and reports them; the user resolves sequencing before write.
  • Author-response status drift — kernel MAY draft initial responses into <div class="response"> per risk, but MUST leave status="identified". Status transitions to accepted / mitigated / rejected are author commitment, never kernel inference.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The kernel function MUST conform to 006's KernelContext shape: single async function, all IO / AI access flow through ctx, no module-level side effects, no implicit process.cwd() / process.env / console usage inside the function body.

proposeCommand MUST be implemented at packages/core/src/commands/propose.ts and exported via the @spectastic/core/commands/propose subpath per 006 FR-002's per-verb subpath rule.

The CLI MUST expose spectastic propose <spec-id> "<description>" with flags --no-adversarial (skip the adversarial pass even when the heuristic fires) and --adversarial (force the pass even when it doesn't). The subcommand wires the kernel function and translates a structured ProposeResult into stdout + on-disk artifact.

The kernel MUST read the target spec.html via ctx.fs, parse its <spec-requirement> IDs, and verify every delta target: modified | removed | renamed targets MUST exist; added targets MUST NOT exist. Hallucinated or duplicated IDs raise a typed error before write.

Every <spec-delta> the kernel emits MUST carry both op (one of added | modified | removed | renamed) and target (a requirement ID). Missing values MUST render as visible MISSING OP / MISSING TARGET labels rather than silent omission, matching the canonical procedure's "no silent failure" discipline.

The kernel MUST run a two-phase interview matching 011-core-spec's pattern: narrative chat via ctx.io.prompt() for intent / approach / reason / migration prose, and ctx.ai.ask<T>() for bounded decisions (change shape, status pill, per-delta op, defer-to targets). Skip any question whose answer is already in the input, the live spec, or sibling proposal folders.

The kernel MUST apply the budget-aware splitting nudge: if the proposal contains more than five deltas OR touches deltas across more than two topic prefixes, prompt the user via ctx.io.prompt() with "Would these read better as two or three smaller proposals?" The default answer is "yes, split."

The kernel MUST evaluate the adversarial-pass heuristic per REQ-CHANGE-004: fire if the proposal touches a priority="must" requirement, OR contains an op="removed" delta, OR spans two or more topic prefixes. --no-adversarial overrides to skip; --adversarial overrides to force.

When the adversarial pass fires, the kernel MUST spawn a critic sub-agent via ctx.ai.subagent(prompt, opts) with the canonical three-finding critic prompt from commands/spectastic.propose.md §8, receive an array of RiskFinding, and embed each as a <spec-risk target="…" status="identified"> block under §5 of the rendered proposal. The kernel MUST demand exactly three findings; the critic prompt's "empty findings forbidden" clause is reproduced verbatim.

This slice MUST introduce a subagent(prompt: string, opts?: SubagentOpts): Promise<unknown> method on the AIProvider interface defined in @spectastic/core's main entry, extending the foundation in 007. This is the first kernel function that requires sub-agent semantics; the method lands here for the first time.

Author-response discipline: the kernel MAY draft an initial response into <div class="response"> per risk, but MUST leave status="identified". Status transitions to accepted | mitigated | rejected are author commitment; the kernel MUST NOT infer or emit them.

Before write, the kernel SHOULD scan specs/<spec-id>/changes/ for sibling proposals whose deltas target any of the same IDs and report them via ctx.io.prompt() so the user can resolve sequencing. The scan MUST NOT auto-block the write — concurrent proposals are surfaced, not rejected.

The kernel MUST return a structured ProposeResult shape (rendered HTML, deltas count, risks array, resolved output path). The caller (CLI today; MCP / VS Code later) MUST own writing the result HTML to disk. The kernel MUST NOT mutate the filesystem directly.

The kernel function MUST be unit-tested at packages/core/test/propose.test.ts as a pure function using a stub AIProvider (including a stub subagent() returning canned RiskFinding arrays) and an in-memory ctx.fs. A CLI integration test MUST exercise the end-to-end flow against a fixture under packages/cli/test/.

commands/spectastic.propose.md MUST be updated with a MAY-Bash-to-CLI note per 006 FR-009: the slash-command LLM MAY invoke spectastic propose via Bash for deterministic operations but MUST NOT be required to. The markdown remains the canonical procedure source.

The kernel function's docblock MUST link to commands/spectastic.propose.md as the canonical procedure per 006 FR-008. No auto-generation in either direction.

Non-functional

The extraction MUST NOT regress any scenario in bench/baselines.json past its declared budget. In particular, the init-help-cold-start scenario MUST stay within ±20% of today's baseline — the kernel's main entry MUST NOT eagerly load propose's command module.

Out of scope (deferred to other slices)

  • Cross-spec proposals — a single proposal touching deltas across multiple specs. Today's procedure assumes one spec per proposal; lift later if usage demands it.
  • Proposal amendments — editing a proposal after it's been authored but before apply. Today the workflow rewrites the file; a structured amend mode is future work.
  • Inbox-card source detection — the canonical procedure references an "originating inbox card path" passed to the critic; today the kernel takes it as an optional input rather than auto-detecting it from the spec ID.
  • All cross-cutting kernel concerns (subpath exports, lazy-loading discipline, version policy, README) — owned by 006.

4 · Data model

Four types this slice owns: ProposeInput, ProposeResult, Delta, RiskFinding. Plus the new subagent() method on AIProvider.

Entities

ProposeInput
{ specId: string, description: string, adversarial?: boolean }. specId resolves to specs/<specId>/spec.html via ctx.fs. description is the one-line change name from the CLI's positional argument. adversarial is the tri-state flag: true forces the pass, false skips it, undefined lets the heuristic decide.
ProposeResult
{ html: string, deltasCount: number, risks: RiskFinding[], outputPath: string }. html is the fully-rendered proposal artifact ready to write. outputPath is the resolved specs/<specId>/changes/<date>-<slug>/proposal.html the caller writes. risks is empty when the adversarial pass didn't fire.
Delta
{ op: 'added' | 'modified' | 'removed' | 'renamed', target: string, postState?: string, reason?: string, migration?: string }. postState is the full <spec-requirement> HTML embedded for ADD / MODIFY. reason + migration are required for REMOVE; the kernel refuses to write a REMOVE delta with either missing.
RiskFinding
{ target: string, status: 'identified' | 'accepted' | 'mitigated' | 'rejected' | 'no-value-found', concern: string, response?: string }. target is a delta ID, requirement ID, or §<n> anchor. response is the kernel's optional draft into <div class="response">. The kernel only emits status: 'identified' (or 'no-value-found' when the critic self-reports nothing of value); all other statuses are author-set.
AIProvider.subagent()
New method introduced this slice: subagent(prompt: string, opts?: SubagentOpts): Promise<unknown>. Spawns a fresh agent context with the provided prompt; the caller parses the structured response. opts carries the agent name and any attachment paths (e.g. the spec, the principles, the draft proposal). The Claude adapter (lands here or in a follow-up extension to 007 — implementation detail for the plan) wires this to a sub-agent invocation.

The kernel emits RiskFinding objects with status: 'identified' only. The author's commitment — flipping a status to accepted / mitigated / rejected — happens in the rendered artifact after the kernel returns. This invariant is what makes the apply-time gate in REQ-CHANGE-004 meaningful: apply refuses on status="identified", so the kernel-emitted defaults force an author touch before archive.

5 · Success criteria

Technology-agnostic, measurable outcomes.

Running spectastic propose <spec-id> "<description>" against a fixture spec with a stub AIProvider (canned interview answers + canned three-finding sub-agent response) produces a proposal.html whose content is byte-identical (modulo trivial whitespace normalisation) across runs. Reproducibility is the harness for everything else.

On a fixture proposal that satisfies the heuristic (must-tier touched OR removed op OR ≥2 topic prefixes), the adversarial pass fires automatically and embeds three <spec-risk target="…" status="identified"> blocks under §5. On a fixture that doesn't satisfy the heuristic, the pass doesn't fire and §5 is empty (or contains only the <spec-risk-log> shell). --no-adversarial + --adversarial overrides verified.

A test file under packages/core/test/ imports proposeCommand from @spectastic/core/commands/propose and invokes it with a stub ctx whose ai.subagent() returns three canned RiskFinding objects. The returned ProposeResult.risks.length is exactly 3; the rendered html contains all three <spec-risk> blocks. No process spawn.

pnpm bench passes all scenarios within their declared budgets. The init-help-cold-start scenario stays within ±20% of today's baseline, confirming propose's command module isn't eagerly loaded by the kernel's main entry.
