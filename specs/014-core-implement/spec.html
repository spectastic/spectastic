1 · Context

Today's /spectastic.implement is the most-used verb — every spec slice drains through it; the small-batch loop routes through it. Procedure lives entirely in commands/spectastic.implement.md; nothing is reachable from MCP, VS Code, or scripted-CI consumers.

The verb is also the heaviest of the eight: estimability gate, task-tick, inbox just-do tick, verification, three drain modes, parallel agent fan-out, plus the bundled flip prompt mandated by REQ-LIFECYCLE-004 and REQ-LIFECYCLE-005. Bundling all of that violates small-batches. Split: single-task is the smallest demoable; drain modes warrant their own slice. This spec ships single-task; TBD-core-implement-drain picks up the rest.

2 · User scenarios & testing

Each story is independently testable: if you implemented only US1, you would still have a viable MVP that proves the shape.

US1 · Maintainer drives one task via CLI P1

As a maintainer outside Claude Code, I want to run spectastic implement T-014 and have one task driven end-to-end so that implementation doesn't require a Claude Code session.

Acceptance: CLI loads spec + plan + tasks, applies the gate, does the work, runs verification, ticks the matching checkbox, prints a one-line summary. Exit 0 on success, 1 on verification failure, 2 on blocked estimability.

US2 · Maintainer drains a single inbox just-do card P1

As a maintainer with an unfinished just-do card in inbox.html, I want to run spectastic implement I-013 and drive that card to completion so that the small-batch loop works the same from CLI as from slash command.

Acceptance: CLI locates the matching <spec-triage layer="just-do">, does the work, runs verification, writes data-status="done" to that single card. Other cards untouched; card stays as history.

US3 · Last-tick fires the bundled flip prompt P1

As a maintainer ticking the final unchecked task in a Draft spec, I want to see an explicit bundled flip prompt covering the three siblings so that REQ-LIFECYCLE-005 is enforced deterministically.

Acceptance: When remaining unchecked count hits zero, kernel calls ctx.ai.ask<T>() with a confirmation naming spec, transition, and three siblings; reminds author to verify SC integration tests pass. Kernel never auto-flips; only on confirmation does it write value="accepted" to all three pills and append matching changelog entries.

US4 · Future MCP / VS Code consumer invokes the kernel directly P2

As a future MCP / VS Code author, I want to import implementCommand, inject my own AIProvider + fs, and drive a single task programmatically so that I can render the flip-prompt UI in my own surface.

Acceptance: A test passes stubs, asserts ImplementResult shape, verifies the bundled flip prompt fires on last-tick + Draft. No process spawn; no real model or fs call.

Edge cases

Five tracked failure modes the extraction handles
  • Estimability gate trips — open <spec-question> in the task's section, [NEEDS CLARIFICATION] marker referenced by the task, missing defer-to= on a <spec-out-of-scope> item the task touches. Kernel surfaces a typed error naming the blocker; CLI exits 2.
  • Task already ticked — caller passed T-NNN for a task whose checkbox already has checked. Kernel surfaces a typed result; CLI reports and exits 0 without re-ticking.
  • Spec status past Draft — last-tick on an Accepted / In Review / Superseded spec must not re-fire the bundled flip prompt (per REQ-LIFECYCLE-005 Draft-scoping). Kernel checks status before evaluating the predicate.
  • Author declines the flip prompt — all three sibling statuses stay Draft; kernel reports the declined flip in ImplementResult.flipConfirmed: false; tick still landed.
  • Verification fails — kernel runs the scoped check, surfaces the failure, does not tick the checkbox. CLI exits 1. Author re-invokes after fixing.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional — the verb

implementCommand MUST conform to the kernel contract from 006 FR-003: signature (input: ImplementInput, ctx: KernelContext) => Promise<ImplementResult>; pure with respect to arguments; no module-level side effects; all IO and AI access flows through ctx.

The function MUST live at packages/core/src/commands/implement.ts and be exposed via subpath @spectastic/core/commands/implement per 006 FR-002. The umbrella entry MUST NOT eagerly load it.

@spectastic/cli MUST add an implement subcommand accepting a single positional target: a task ID (T-NNN), inbox card ID (I-NNN), or spec ID. v1 MUST NOT accept --all, --phase=<id>, or --parallel — drain modes carve out to TBD-core-implement-drain.

The kernel MUST resolve the target to a specific task (T-NNN directly, or the next unchecked task in a spec ID's tasks.html) or a specific inbox just-do card (I-NNN). It MUST read spec / plan / tasks via ctx.fs — never via direct node:fs.

Before any work, the kernel MUST apply the estimability gate: open <spec-question> in the task's section, [NEEDS CLARIFICATION] referenced by the task, or missing defer-to= on a touched <spec-out-of-scope> item MUST halt with a typed error naming the blocker. CLI exits 2.

After successful work + verification, the kernel MUST write the checked attribute to the single targeted <input type="checkbox"> in tasks.html via ctx.fs. Other tasks MUST remain untouched; document order MUST NOT change.

For inbox just-do targets, the kernel MUST write data-status="done" to the single targeted <spec-triage> in inbox.html via ctx.fs. The card MUST NOT be removed or moved; other cards untouched.

After every tick taken while the spec's status is Draft, the kernel MUST count remaining unchecked <input type="checkbox"> in the spec's tasks.html. If exactly zero, the kernel MUST surface a Draft → Accepted bundled flip prompt via ctx.ai.ask<T>() naming the spec, the transition, and the three siblings (spec.html, design.html, tasks.html) per REQ-LIFECYCLE-005. Skip when status is past Draft.

The flip prompt MUST remind the author to verify integration tests covering the spec's Success Criteria pass before confirming. The confirmation gesture absorbs the test-pass discipline; author judgment is the gate.

The kernel MUST NOT auto-flip status. On explicit confirmation, the kernel MUST write value="accepted" to the <spec-status> pill in all three siblings and append a matching one-line <spec-changelog> entry to each (old state, new state, date, trigger). Partial bundle flips are forbidden.

The kernel MUST run the smallest scoped verification the task admits (scoped tests, smoke check, build) before ticking. The verification runner (kernel shells via ctx.shell, reads test output via ctx.fs, or accepts a caller-supplied callback) defers to the plan. Failing verification MUST halt without writing the tick.

The kernel MUST be unit-tested at packages/core/test/implement.test.ts with stub ai + stub fs (no process spawn, no real model call, no real fs write). The CLI subcommand MUST have an integration test under packages/cli/test/ exercising task and inbox-card paths.

commands/spectastic.implement.md MUST be updated to (a) note the slash command MAY shell out to spectastic implement for deterministic single-task execution (per 006 FR-009), and (b) reference the drain-modes carve-out — the CLI does not yet support --all / --phase=<id> / --parallel; drain invocations stay on the markdown procedure.

The implementCommand docblock MUST link to commands/spectastic.implement.md as the canonical procedure per 006 FR-008. Markdown MUST NOT be auto-generated from the docblock.

Non-functional

The extraction MUST NOT regress any scenario in bench/baselines.json past its declared budget. Importing @spectastic/core/commands/implement MUST NOT eagerly load parse5, the Claude provider, or any other heavy dependency onto the CLI init path.

Out of scope (deferred to other slices)

Drain modes carved out to TBD-core-implement-drain; seven sibling kernel-verb extractions linked.

4 · Data model

Three types this slice owns: ImplementInput, ImplementResult, TaskTickResult. Reuses KernelContext and AIProvider from 006.

Entities

ImplementInput
Fields: target: string — the single positional argument, matching one of: a task ID (T-NNN), an inbox card ID (I-NNN), or a spec ID (e.g. 014-core-implement) which resolves to the next unchecked task in that spec's tasks.html. No flags in v1; drain-mode fields carved out to the sibling slice.
ImplementResult
Fields: ticked: { kind: 'task' | 'just-do'; id: string } (which item was ticked and its ID), filesChanged: string[] (every file the kernel wrote to, including the tasks.html or inbox.html and any work-product files), verified: boolean (did scoped verification pass), flipPromptFired?: boolean (was the bundled flip prompt surfaced — true on last-tick + Draft), flipConfirmed?: boolean (did the author confirm the flip — undefined when the prompt didn't fire).
TaskTickResult
Fields: taskId: string, file: string (absolute or workspace-relative path to the tasks.html that was modified), remainingUnchecked: number (count of unchecked <input type="checkbox"> elements still present after the tick — the predicate input for FR-008's bundled flip check). Used internally and surfaced for callers that want to render their own progress UI.

The kernel never owns the spec status pill's mutation autonomously — the bundled flip is gated on explicit author confirmation via ctx.ai.ask<T>(). On confirmation the kernel writes to all three siblings; on decline it writes nothing. The contract: one tick per invocation, one optional bundled flip per last-tick on Draft.

5 · Success criteria

Technology-agnostic, measurable outcomes.

For a representative single-task invocation against a fixture spec, the resulting tasks.html is byte-identical (modulo trivial whitespace normalisation) to the file produced by today's slash-command flow against the same inputs.

A unit test drives the last-tick path with a Draft fixture, asserts ctx.ai.ask<T>() is called exactly once with a payload naming the three siblings, and verifies that on stub-confirmation all three pills are written and three matching <spec-changelog> entries land. The same test with a non-Draft fixture asserts the prompt does not fire.

A test imports implementCommand from @spectastic/core/commands/implement, passes a stub AIProvider + stub fs, and asserts the returned ImplementResult shape matches expectations. No process spawn; no real model call; no real fs write.

6 · Assumptions

Two preconditions: 006's kernel scaffolding is shipped; the bundled flip prompt's UX renders acceptably in a CLI context via the same ask<T>() shape Claude Code uses.

006-kernel-extraction has shipped: @spectastic/core package exists with KernelContext + AIProvider interfaces, per-verb subpath exports are wired, and the bench scaffold gates regression. This slice extends the contract; it does not reinvent it.

The bundled flip prompt's confirmation gesture rendered via ctx.ai.ask<T>() is acceptable UX in both the CLI (where the user sees terminal-rendered options) and the future MCP / VS Code consumers (where the caller renders the prompt in its own surface). The interface is shape-stable; the rendering is caller-side.
