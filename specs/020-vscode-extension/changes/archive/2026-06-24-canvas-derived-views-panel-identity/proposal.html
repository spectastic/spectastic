Canvas: derived-view nodes + artifact-panel identity

Teach the lifecycle canvas about derived views (verify.html) and make every opened artifact say which spec it belongs to.

Status Applied Change ID 2026-06-24-canvas-derived-views-panel-identity Spec 020-vscode-extension Source T-006 · T-007 Author Brian Corbin · @briancorbinxyz Created 2026-06-24 Targets 4 requirements — 1 added, 3 modified Read time

The canvas was specified before two things existed: the verify.html derived view (spec 021) and the lived reality of switching between specs with artifacts open. So it omits verify nodes entirely (T-006), and its artifact panels — titled by bare verb with no spec id and never reused — make a leftover panel from one spec read as if it belongs to the spec currently on the canvas (T-007). This change updates the canvas's spec/artifact model: MODIFY FR-001 to include derived views in the node set, ADD FR-014 naming a statusless derived-view node category (with MODIFY FR-002 scoping its fixed-colour mandate to verb nodes), and MODIFY FR-003 so every opened panel identifies its spec and reuses one panel per artifact.

Canvas: derived-view nodes + artifact-panel identity

Applied

1 · Intent

020 shipped a canvas that draws one node per lifecycle artifact and opens each on click. Two gaps surfaced once it ran against a real, evolving project. First, spec 021 introduced verify.html — a derived view that is regenerated, not authored, and carries no status of its own. FR-001's node set and the scanner's hardcoded artifact list predate it, so a spec's verify.html is invisible on the canvas (T-006). Second, opened artifact panels are titled by bare verb basename (spec/plan/tasks) with no spec id and are never reused, so after the canvas defaults to one spec and you switch to another, the first spec's panels linger and read as if they belong to the spec now shown (T-007).

Both are spec-layer gaps — the implementation faithfully built what the spec said; the spec simply didn't anticipate derived views or multi-spec panel use. This proposal closes both by extending the canvas's spec/artifact model rather than patching the symptoms in code.

2 · Scope

In scope

  • Broaden FR-001's node set to include derived-view artifacts (e.g. verify.html).
  • Add FR-014: a statusless derived-view node category — no status pill, a freshness/coverage metric, visually distinct from the verb-coloured spine.
  • Amend FR-003: an opened panel identifies its spec (title carries the spec id) and reuses one panel per artifact path; panels from other specs stay open across a spec switch.

Out of scope

  • Auto-closing other specs' artifact panels when the canvas spec changes — deliberately rejected so cross-spec comparison stays possible; disambiguation is by title instead.
  • A richer derived-view metric (e.g. a trace-coverage percentage) beyond FR-014's required binary stale indicator — deferred; the MUST is already satisfied by the stale signal 021 emits.
  • Building verify.html itself — shipped by 021; this change only teaches the canvas to render it.

3 · Approach

Two seams, each isolated. Node model: FR-001 gains "plus derived views"; new FR-014 names the category so FR-002's verb-node contract (icon, title, status pill, one metric, fixed 017 colours) stays intact rather than absorbing a special case. In code the scanner gains a verify candidate and a derived-view node kind, and the webview renders it without a status pill and with a freshness metric, attached adjacent to its source. Artifact panels: FR-003 gains identity + reuse — openArtifact titles each panel <spec-id> · <verb> and keys a reuse map by artifact path so re-opening reveals the existing panel; cross-spec panels are left open. Touches scanner.ts, messaging.ts, the webview node renderer, and open-artifact.ts/extension.ts.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec; op= is one of added | modified | removed | renamed.

What changes: the node set now also includes any derived-view artifacts the bundle carries (e.g. verify.html), rendered per FR-014 and associated with the spec rather than placed inline in the verb sequence.

The panel MUST render the selected spec's lifecycle as a canvas of nodes — one node per existing artifact file — ordered along the lifecycle sequence principles → spec → plan → tasks → implement → propose → apply → triage (laid out in the orientation set by FR-004), plus any derived-view artifacts the bundle carries (e.g. verify.html), rendered per FR-014 and associated with the spec rather than placed inline in the verb sequence. A missing artifact simply has no node, which is itself information.

What changes: scope FR-002's fixed-colour mandate to lifecycle-verb nodes, so derived-view nodes (FR-014) sitting outside the 017 verb palette don't read as a contradiction of "MUST NOT be recoloured".

Each minimal node MUST show a verb icon, a title (spec id / name), a status pill, and exactly one key metric, colour-coded by node type using the fixed per-verb colour order of 017-brand-logo — which MUST NOT be shuffled, recoloured, or dropped. This fixed-colour mandate binds lifecycle-verb nodes; derived-view nodes (FR-014) sit outside the verb palette and take a deliberately distinct, non-verb treatment.

A derived-view artifact — a regenerated, statusless view of the bundle such as verify.html — MUST render as a distinct node category. It MUST NOT carry a status pill (it has no own lifecycle status; per 021-verify-view FR-007 it derives the spec bundle's), MUST show, in place of a verb metric, a freshness indicator — at minimum a binary stale flag derived from the verify-view-stale signal (021 FR-008), a value the bundle genuinely exposes — and MUST be visually distinguishable from the verb-coloured lifecycle spine (FR-002, as scoped by this change). A richer measure (e.g. trace coverage) MAY follow. The node SHOULD attach adjacent to its source rather than inline in the verb sequence.

Rationale

verify.html is the first derived view; naming the category keeps FR-002's verb-node contract intact (now explicitly verb-scoped by this change) and lets future derived views (e.g. a conformance index) reuse the treatment. The metric is pinned to a signal 021 actually emits (the stale rule), so the MUST is testable rather than aspirational.

What changes: an opened artifact panel must identify its spec (title carries the spec id) and reuse one panel per artifact path; panels from other specs stay open across a spec switch (no auto-close).

Clicking a node MUST open that artifact's full rendered document in spectastic's existing design system, in no more than one click. The opened panel MUST identify its spec — its title MUST lead with the spec id (e.g. 020-vscode-extension · spec) so identity survives tab truncation, reinforced by the rendered artifact's own header which already carries the spec id — and re-opening the same artifact MUST reuse its existing panel rather than stacking a duplicate. Panels opened from other specs remain open across a spec switch (the canvas MUST NOT auto-close them); disambiguation is by title, so artifacts from different specs can be compared side by side.

5 · Risk register

Adversarial pass fired (two must-tier requirements touched — FR-001, FR-003 — across two topic areas: the node model and the artifact-panel model). Three findings below; status="identified" until the author commits each to mitigated / accepted / rejected. Apply refuses while any remain identified.

Never auto-closing cross-spec panels while resting identity on a tab title will, within 30 days of multi-spec use, pile up near-identical webview tabs that truncation makes indistinguishable — recreating the very confusion T-007 set out to kill.

"Panels opened from other specs remain open across a spec switch (the canvas MUST NOT auto-close them); disambiguation is by title".

Author draft (recommend mitigated). The no-auto-close decision is kept — cross-spec comparison is a real need — but the identity signal was strengthened in place: FR-003 now requires the spec id to lead the title (so it survives VS Code's middle-out truncation) and notes the rendered artifact's own header independently carries the spec id, so identity no longer depends on an untruncated tab. A stronger affordance (a spec-id chip in the panel body) MAY follow if pile-up still bites. Committed mitigated.

FR-014's "visually distinguishable from the verb-coloured lifecycle spine" sits in direct tension with live FR-002's absolute "the per-verb colour order MUST NOT be shuffled, recoloured, or dropped", and the original draft asserted reconciliation without making it.

FR-002: "MUST NOT be shuffled, recoloured, or dropped" vs FR-014: "visually distinguishable from the verb-coloured lifecycle spine".

Author draft (recommend mitigated). Reconciled by adding a MODIFY FR-002 delta that scopes the fixed-colour mandate explicitly to lifecycle-verb nodes; derived-view nodes (FR-014) are stated to sit outside the verb palette with a distinct, non-verb treatment. The two MUSTs no longer overlap. (This is the same conflicting-MUSTs shape the 16/22 Jun adversarial passes caught — closed by construction here.) Committed mitigated.

FR-014 made "show a freshness/coverage metric" a MUST while §2 deferred what the metric is — an untestable MUST pointed at a TBD, worsened by 021 not exposing a trace-coverage percentage as a first-class field.

§2 Out of scope: "the exact derived-view metric semantics … a plan/implementation detail" vs FR-014: "MUST show a freshness/coverage metric".

Author draft (recommend mitigated). FR-014's MUST was pinned to a concrete, derivable signal: a binary stale flag off 021's verify-view-stale rule (021 FR-008) — something the bundle genuinely emits and a test can assert. The richer trace-coverage percentage was demoted to a MAY and the §2 deferral reframed to cover only that richer measure, so no MUST points at a TBD. Committed mitigated.
