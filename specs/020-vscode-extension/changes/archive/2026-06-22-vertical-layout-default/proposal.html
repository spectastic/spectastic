Change proposal · 020-vscode-extension

Vertical layout, default

Support a top-to-bottom orientation and make it the default, so the canvas fits the tall, narrow editor side-panel.

Status Applied Change ID 2026-06-22-vertical-layout-default Spec 020-vscode-extension Author Brian Corbin · @briancorbinxyz Created 2026-06-22 Targets 3 requirements (2 modified, 1 added) Read time

The canvas lays out left-to-right (FR-004), but it lives in the VS Code side-panel — tall and narrow — where a horizontal spine wastes vertical space and forces sideways scrolling. This change generalises the layout to two orientations, makes vertical (top-to-bottom) the default, and adds a toggle (FR-013, new) so authors can flip to horizontal for wide / bottom-panel layouts. The choice persists per workspace. The adversarial pass added an FR-001 delta so the spine's direction lives only in FR-004.

Vertical layout, default

Applied

1 · Intent

The lifecycle canvas renders in a VS Code view — by default an Activity-Bar side panel that is much taller than it is wide. The original layout (FR-004) runs the spine left-to-right, which suits a wide editor pane but fights the side-panel's aspect ratio: a six-to-eight-node lifecycle overflows horizontally and the author scrolls sideways to see tasks or triage, while most of the panel's height sits empty.

A top-to-bottom spine matches the panel's shape — more nodes are visible without scrolling, and a pipeline reads naturally downward. We keep horizontal available (the editor area, or a docked bottom panel, is wide) but make vertical the default because that is where the canvas actually lives most of the time. Maximising the common surface is the whole point.

2 · Scope

In scope

  • Vertical (top-to-bottom) deterministic auto-layout as the new default orientation.
  • Horizontal (left-to-right) retained as the alternative orientation.
  • Lanes for child slices / proposals branch perpendicular to the spine; edges adapt their curve direction.
  • A view title-bar toggle (and a command) to switch orientation.
  • Per-workspace persistence of the chosen orientation (survives reload).

Out of scope

  • Animated transition between orientations — an instant re-layout is fine.
  • Per-spec orientation memory — the choice is per workspace, not per selected spec.
  • Free / manual node arranging — already out of scope in the live spec, unchanged here.
  • Any non-orthogonal layout (radial, diagonal, force-directed).

3 · Approach

Generalise the pure layout function with an orientation: 'vertical' | 'horizontal' parameter (default 'vertical'). The spine advances along the primary axis — y per verb for vertical, x per verb for horizontal — and slice / proposal lanes offset along the perpendicular axis (vertical spine → lanes to the right; horizontal spine → lanes below). edges.ts picks its curve direction from the same flag. Node and card rendering are unaffected.

The host owns the choice: a spectastic.toggleOrientation command (surfaced as a view title-bar button) flips it and writes to workspaceState; the value rides in the graph message to the webview. No new layout engine, no framework — the hand-rolled layout (plan D-003) simply takes one more argument.

Vertical is strictly better for the default surface but taller graphs scroll vertically, which the panel already supports. Containment / viewport bounds (NFR-004) must hold in both orientations — the new layout tests assert it for each.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec; op= is one of added | modified | removed | renamed.

What changes: the spine is ordered by lifecycle sequence, not a hard-coded left-to-right direction — direction is owned by FR-004. (Caught by the adversarial pass: FR-001 and FR-004 would otherwise both MUST a direction, and disagree.)

The panel MUST render the selected spec's lifecycle as a canvas of nodes — one node per existing artifact file — ordered along the lifecycle sequence principles → spec → plan → tasks → implement → propose → apply → triage (laid out in the orientation set by FR-004). A missing artifact simply has no node, which is itself information.

What changes: the layout is no longer fixed left-to-right; it supports two orientations and defaults to vertical (top-to-bottom).

The canvas MUST position nodes by deterministic auto-layout in the active orientation — vertical (top-to-bottom) by default, or horizontal (left-to-right) — with lanes for child slices and proposals branching perpendicular to the spine, and draw edges along the flow including branch points (parent↔child, propose→apply / →withdraw). Manual arranging is out of scope for this slice.

The canvas SHOULD expose an orientation toggle — a view title-bar control and a command — that switches the layout between vertical and horizontal, and SHOULD remember the chosen orientation per workspace so it survives a reload.

Rationale

Vertical is the default, so horizontal needs a discoverable way back; persistence keeps a deliberate choice from resetting on every reload. Mirrors the spec-picker affordance (FR-008).
