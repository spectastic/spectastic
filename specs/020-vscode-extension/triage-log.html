Minimal node crops / overspills its content (fixed height)

Implementation code

Debugging a node whose title + pill + metric spilled past its border in the live canvas, root cause was implementation drift — the node used a fixed height instead of growing to fit; fixed by switching to min-height + a flex content column with title ellipsis; regeneration passes (FR-002/FR-005 never mandated a fixed height).

Expected
The minimal node (FR-002) contains its verb label, title, status pill and metric inside its border.
Actual
With a wrapping title (001-game-ui), the stacked content exceeded the fixed 64 px box and spilled below the border; the attention ring was clipped at the canvas edge.
Diagnosis
updateNode set el.style.height = pos.h (a hard height), so taller content overflowed; the grid also let label+title wrap together.
Fix
packages/vscode/src/webview/node.ts + webview/canvas.css: min-height floor, flex .ncontent column, title nowrap+ellipsis; larger node in webview/layout.ts. Guarded by a Playwright assertion that scrollHeight ≤ clientHeight for every node.
el.style.height = `${pos.h}px`; // fixed → content overspills el.style.minHeight = `${pos.h}px`; // floor → box grows to fit
Deep dive — none required

No cross-spec contract, no invariant, no hotfix sequence. Pure rendering correctness; spec + plan unchanged.

Compact-card popover clipped near panel edges

Implementation code

Debugging a hover card that was cut off, root cause was implementation drift — the card was appended inside the canvas surface, which the scroll container clips with overflow:auto; fixed by rendering it on <body> with position:fixed, viewport clamping, and flip-above; regeneration passes (FR-005 specifies the card, not its stacking context).

Expected
The hover/select compact card (FR-005) is fully visible wherever its node sits.
Actual
For nodes low/right in the panel the card extended past the surface and was clipped by #canvas-root { overflow:auto }.
Diagnosis
The card was a child of .canvas-surface with position:absolute, so it lived inside the clipped, scrollable region.
Fix
packages/vscode/src/webview/card.ts + webview/canvas.css: append to document.body, position:fixed from the node's getBoundingClientRect(), flip above when no room below, clamp within the viewport. Regression test shrinks the panel and asserts the card stays on-screen.
Deep dive — none required

No cross-spec contract, no invariant, no hotfix. Positioning-context fix only.

Plan node falsely flagged needs-attention by a "None outstanding" open-questions placeholder

Cross-spec upstream

Debugging a red needs-attention border on a plan whose only "open question" was the prose "None outstanding — everything resolved in the interview", root cause was a cross-spec format gap: <spec-questions> has no unambiguous "zero" representation, so spec/plan generation writes a freeform placeholder <li> indistinguishable from a real question; fixed by defining a canonical empty representation at the generating side; regeneration fails — any consumer of the artifact reproduces the false count.

Expected
A plan/spec with no open questions does not trigger the canvas needs-attention state (FR-006).
Actual
A plan whose <spec-questions> holds a single "None outstanding…" <li> renders red — the placeholder counts as one open question.
Diagnosis
The <spec-questions> contract has no canonical "zero open questions" form: generation writes a prose "None" <li> that reads identically to a real question, so extractHealth (correctly counting <li>, feeding FR-006) over-counts. The reader is fine; the generated format is ambiguous.
Fix
Define an unambiguous empty form at the generating side — when there are no open questions, /spectastic.spec + /spectastic.plan leave <spec-questions> empty (no <li>), not a "None" placeholder; codify in the meta-spec format + templates/{spec,plan}.html. No 020 code change — extractHealth then reads zero.
Deep dive — cross-spec contract

Shared contract: the <spec-questions> "no open questions" representation. It is consumed by 020 (extractHealth → FR-006) and produced by every authoring verb — so the fix is upstream of 020, not in it. The user's call: "no room for ambiguity" — fix where questions are generated, don't patch the reader.

Cascade (a candidate change-proposal against the meta-spec, not 020): (1) the meta-spec format defines "zero open questions = empty <spec-questions>" (or a resolved marker); (2) commands/spectastic.spec.md + commands/spectastic.plan.md emit the empty form; (3) templates/{spec,plan}.html drop the placeholder <li>; (4) existing specs carrying a "None" <li> migrate to the empty form. extractHealth is unchanged.

Scope note (not promoted): a stricter option — a validate rule rejecting a placeholder/prose-"None" <li> inside <spec-questions> — is surfaced here, not adopted. Filed against 020 because that's where it manifested; the fix lands in the meta-spec/format.

Canvas omits the verify.html artifact — no verify node in the lifecycle

Spec upstream

Debugging the absence of a verify node on the canvas for a spec that carries a verify.html, root cause was a spec gap: FR-001's lifecycle node set (principles → spec → plan → tasks → … → triage) and the scanner's hardcoded artifact list (packages/vscode/src/host/scanner.ts: principles / spec / plan / tasks / propose / triage) predate the verify.html derived view introduced by spec 021-verify-view; fixed by amending 020 to place verify in the node set; regeneration fails — 020's spec never names verify, so any rebuild reproduces the omission.

Expected
With a spec selected, the canvas shows one node per existing artifact file (FR-001); a spec carrying a verify.html shows a verify node.
Actual
verify.html exists in specs/<id>/ (e.g. spec-tictactoe's 001/002) but no node renders — the scanner enumerates a fixed set that omits it.
Diagnosis
FR-001's lifecycle sequence and scanner.ts's artifact list were authored before 021 added verify.html — a derived view, not a lifecycle verb — so the canvas has no representation for it. Needs a spec decision: where verify sits (adjacent to tasks/implement, as a derived-view node), its verb colour, and its one key metric (e.g. trace coverage / stale).
Fix
specs/020-vscode-extension/spec.html — amend FR-001 (and the node-type/colour requirement) to include verify.html as a derived-view node; cascade to scanner.ts + the graph types + the webview. Author via /spectastic.propose against 020.
Deep dive — cross-spec / structural

Shared contract. The lifecycle artifact set is effectively a contract between 020 (which renders it) and the lifecycle itself (which defines it). 021 extended the lifecycle with a new artifact; 020 didn't learn it. Rather than hardcode each new artifact, the fix should consider deriving the node set from the canonical lifecycle so future artifacts (e.g. a conformance index) don't each require a 020 amendment.

Derived-view category. verify.html is not a lifecycle verb — it carries no own status (021 FR-007) and is regenerated, not authored. 020 likely needs a distinct "derived-view node" treatment (no status pill; a freshness / trace-coverage metric) rather than forcing it into the verb-coloured flow. That's the spec decision the proposal must make — hence spec, not a code-only patch.

Opened artifact panels don't identify their spec — 020's canvas appears to "show 021's artifacts"

Spec upstream

Debugging the canvas (correctly on 020 — the spec node reads 21 reqs, matching 020) appearing to "show 021's artifacts", root cause is a spec gap, not a path bug: clicking a node opens the right file, but openArtifact (packages/vscode/src/host/open-artifact.ts:21) titles every panel by the bare verb basename (path.basename(path,'.html') → "spec"/"plan"/"tasks"), carries no spec id, and createWebviewPanel runs per-click with no per-artifact reuse or cross-spec reconciliation — so the 021 panels opened when the canvas first defaulted to 021 (the most-recently-modified spec, via defaultSpec()) stay open and indistinguishable from 020's after switching; regeneration fails — 020's spec never constrains panel identity, so any rebuild reproduces the ambiguity.

Expected
With the canvas on 020, opened artifacts are identifiably 020's; re-opening or switching specs does not leave indistinguishable panels (FR-003).
Actual
Panels are titled "spec"/"plan"/"tasks" with no spec id; each click stacks a new panel; switching the canvas spec leaves prior specs' panels open — so a leftover 021 "tasks" panel reads as if the 020 view opened it.
Diagnosis
FR-003 mandates "open the artifact on click" but is silent on panel identity and reuse; open-artifact.ts titles by bare basename and never reuses/reconciles. Amplified by defaultSpec() opening the most-recently-modified spec (021) first.
Fix
specs/020-vscode-extension/spec.html — amend FR-003 (or add an FR) requiring an opened artifact to identify its spec (title carries the spec id) and to reuse a single panel per artifact path; then update open-artifact.ts + extension.ts. Author via /spectastic.propose against 020. (Minimal mitigation — title = <spec-id> · <verb> — is a one-line impl change, but the requirement is the upstream gap a regen reproduces.)
Deep dive — spec gap, defaultSpec interaction

Not a path bug. Node→file resolution is correct (scanner.ts builds each path from ctx.specDir); a 020 node opens a 020 file. The confusion is purely panel identity + persistence.

Scope of the requirement (surfaced, not pre-decided). The FR should mandate (1) the panel identifies its spec and (2) re-opening the same artifact reuses its panel. Whether switching the canvas spec should auto-close other specs' panels is a separate design choice — some authors want several artifacts open at once — so the proposal should decide it explicitly rather than assume.

After switching specs, clicking a node opens the previous spec's artifact (stale click closure)

Implementation code

Debugging the canvas correctly showing 002-validate-cli but clicking any node opening the 020-vscode-extension artifact, root cause was a stale closure: the webview reconciles nodes by id (spec/plan/tasks are identical ids for every spec, main.ts), so a spec switch reuses the DOM node and updateNode refreshes its text — but the click handler set in renderNode still closed over the first render's node.path; fixed by reading the live path from el.dataset.path (refreshed every reconcile) at click time; regeneration passes — FR-003 is correct, the gap was code-only (the closure-over-reused-DOM family of 019's quiz-gate bug).

Expected
With a spec selected, clicking a node opens that spec's artifact (FR-003).
Actual
After switching to another spec, clicking a reused node (spec/plan/tasks) opened the previous spec's file — the click handler's path was frozen at first render.
Diagnosis
renderNode bound () => onOpen(node.path), closing over the render-time node; updateNode reconciled content by id but never rebound the handler, so reused nodes kept the old path. Not a path-derivation bug in the scanner (paths are correct per spec); a webview reconciliation slip.
Fix
packages/vscode/src/webview/node.ts — updateNode writes el.dataset.path = node.path; the click/Enter handler reads el.dataset.path at invocation. Regression: tests/vscode/canvas-open.spec.ts switches specs and asserts the open targets the new path (32/32 Playwright).
const open = (): void => onOpen(node.path); // frozen at first render const open = (): void => { const p = el.dataset.path; if (p) onOpen(p); }; // live
Deep dive — none required

No cross-spec contract, no invariant, no hotfix-before-amendment. Distinct from T-007 (panel identity/reuse): that was about which panel a correct path opens into; this is the path itself being stale. Both surfaced from the same multi-spec-switch session; T-007 is spec-layer (panel identity), T-008 is implementation (stale handler).

Reclicking an already-open artifact reveals stale content — the panel never re-reads the file

Implementation code

Debugging an open tasks.html panel still showing pre-edit content after the file changed, root cause was an implementation gap — openArtifact reveals an already-open panel without re-reading the file, and watchLifecycle only rebuilds the canvas graph (never the artifact panels), so a reclick reveals frozen HTML; fixed by re-reading and re-rendering on the reveal path; regeneration passes — FR-003's reveal-don't-duplicate is correct, the refresh step was simply never wired.

Expected
Reopening (reclicking) an artifact whose file changed shows the current content — the revealed panel reflects the live file.
Actual
The panel keeps the HTML from first open; the tab must be closed and reopened to see updates. Observed live while reviewing the task-row re-authoring edits.
Diagnosis
open-artifact.ts:38–42 — the existing-panel branch calls existing.reveal() and returns, never reassigning panel.webview.html. watcher.ts (watchLifecycle) watches *.html but only posts a rebuilt graph to the canvas webview (FR-009 freshness is canvas-scoped); nothing repaints an open artifact panel. So reveal-of-a-stale-panel is a code omission, not a wrong contract.
Fix
packages/vscode/src/host/open-artifact.ts — on the existing-panel branch, re-read the file and reassign webview.html via rewriteForWebview (reveal + refresh), reusing the initial open's read-error handling. Regression: tests/vscode/ — open, mutate the file, reveal, assert the webview HTML reflects the change.
Fixed
Factored a shared paint(panel, artifactPath) that both the first open and the reuse-reveal path call, so a reopen repaints from the current file. Regression added in packages/vscode/src/host/open-artifact.test.ts (temp file, mutate between opens, assert the reused panel shows VERSION_TWO not VERSION_ONE); 9/9 host tests green.
if (existing) { existing.reveal(); return; } if (existing) { existing.reveal(); await repaint(existing, artifactPath); return; } // re-read + re-render
Deep dive — none required

No cross-spec contract, no invariant, no hotfix-before-amendment. Distinct from T-008 (stale click path into a reused node) and T-007 (panel identity/tab title): this is the panel content going stale after a file edit.

Artifact sticky header reads index.html in the webview instead of the spec-relative path

Implementation code

Debugging the in-artifact sticky header showing index.html rather than e.g. 027-git-trailers/tasks.html in the VS Code view, root cause was an implementation gap — the shared sticky-header JS derives its label from location.pathname (correct in a browser), but a webview loads the artifact as a string via panel.webview.html, so location.pathname is the webview's synthetic URL ending in index.html; fixed by having the host convey the artifact's real path to the page; regeneration passes — the header derivation is browser-correct, the webview integration just never passes the path.

Expected
In the VS Code artifact view the sticky header shows the artifact's real spec-relative path (e.g. 027-git-trailers/tasks.html), matching the browser.
Actual
It always reads index.html. The webview has no real document URL, so the header's last-two-segments derivation resolves against the webview's synthetic origin.
Diagnosis
assets/spec.js:262 builds the header label from location.pathname.split('/').filter(Boolean).slice(-2).join('/') — valid under file:/http, wrong in a webview where the document has no real path. open-artifact.ts assigns panel.webview.html but conveys nothing about the artifact's identity to the page, so the header falls back to the webview's index.html. Cross-component (host ↔ shared asset), code-only.
Fix
packages/vscode/src/host/open-artifact.ts — inject the artifact's real spec-relative path before assigning webview.html (a <meta name="spectastic-path"> or a page global); assets/spec.js — prefer that host-provided path (or the artifact <title>) over location.pathname when present. Add a webview assertion that the header shows the spec-relative path.
Fixed
Host-side only, as it turned out — assets/spec.js already prefers document.body.dataset.docPath over location.pathname. rewriteForWebview now stamps <body data-doc-path="<spec-id>/<file>"> (e.g. 027-git-trailers/tasks.html), so the header shows the real path; no spec.js change needed. Unit test asserts the stamp; 9/9 host tests green.
Deep dive — cross-component, no contract change

Distinct from T-007, which fixed the VS Code tab title (specId · verb via artifactPanelTitle) — this is the in-page sticky header rendered by assets/spec.js. The fix straddles the host (open-artifact.ts) and the shared design-system asset (spec.js) but adds no requirement: the host owes the page its identity, and spec.js should degrade gracefully when location is synthetic. No cross-spec contract; no invariant.

Cross-artifact anchor links escape the webview and open as external vscode-resource URLs

Spec upstream

Debugging a dead SC link in tasks.html opened inside the extension, root cause was a spec gap — 020 never specified how an intra-corpus link (spec.html#SC-002) resolves within the webview; fixed by a requirement that the host intercepts same-corpus links (open the target artifact panel, scroll to the anchor); regeneration fails at implementation — nothing tells the webview to intercept, so the default file+ resource escape recurs.

Expected
Clicking an #SC-002 link in the tasks panel opens the corresponding spec.html artifact in the extension and scrolls to the SC-002 entry.
Actual
The link resolved to https://file+.vscode-resource.vscode-cdn.net/…/spec.html%23SC-002 and launched externally (broken), because relative anchors resolve against the webview resource origin, not the corpus.
Diagnosis
020's navigation contract (cf. FR-003, which governs panel identity/reuse) is silent on intra-corpus link interception — a <a href="../…/spec.html#SC-002"> clicked inside a webview has no handler, so VS Code treats it as an external resource URI.
Fix
specs/020-vscode-extension/spec.html — add a requirement (via /spectastic.propose) that the host intercepts same-corpus artifact links and routes them through the existing open-artifact path with an anchor to scroll to; then plan/tasks re-run.
Deep dive — sibling of T-006/T-007 (also spec-level nav gaps)

No cross-spec contract, no invariant. This joins the family of 020 navigation gaps (T-006 missing verify node, T-007 panel identity) where FR-003's node/panel model predates a richer navigation need and requires a propose, not a code patch. The webview needs a link router: a message from a clicked corpus link → host resolves the artifact path + anchor → open-artifact reveals/paints and posts the anchor for spec.js to scroll to. No deferred scope promoted.
