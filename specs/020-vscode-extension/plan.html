Implementation plan · 020-vscode-extension

Lifecycle canvas (VS Code)

How we will build it.

Status Accepted Spec 020-vscode-extension Owner Brian Corbin · @briancorbinxyz Branch 020-vscode-extension Created 21 Jun 2026 Read time

A new packages/vscode workspace package consumes @spectastic/schema to scan a selected spec's specs/<id>/ artifacts, extract their health, and post a LifecycleGraph to a vanilla-TS webview that draws the calm canvas; a file-watcher keeps it live and clicking a node opens the rendered artifact in a second webview. Biggest risk: webview CSP + asWebviewUri asset-rewriting must reproduce spectastic's design system faithfully — spiked first.

Verify this plan respects every principle in v1.2.0. Any violation requires either a principles amendment or a deliberate exception logged in §8.

The .html artifacts still ship as source.

2 · Technical context

Language(s)
TypeScript 5.7, ESM. Extension host targets Node ≥ 20 (VS Code runtime); webview targets browser ES2022.
Frameworks
None (vanilla TS + DOM/SVG — honours the no-framework non-goal). VS Code Extension API ^1.90. Bundled by tsup/esbuild with two entries: a CommonJS host bundle and a browser IIFE webview bundle.
Storage
None. The LifecycleGraph is transient in-memory, re-derived from disk; nothing is persisted (no positions, no index).
Testing
Behaviour-first. vitest for pure extraction in @spectastic/schema; Playwright drives the webview and asserts render + click + attention state; @vscode/test-electron smoke-tests activation + the file-watcher. Positioned elements (nodes, overlays) carry containment + viewport-bounds assertions (scrollHeight ≤ clientHeight; rect inside the viewport), not just presence — see NFR-004 and T-001/T-002.
Perf targets
NFR-001 < 300 ms p95 panel paint (≤ 8 nodes); NFR-002 node update < 500 ms after save.
Constraints
No JS framework; reuse spec.css tokens + the fixed 017 per-verb colours; strict webview CSP; read-only (never writes artifacts); sideload/dev-host only (no marketplace).

3 · Approach

Add packages/vscode to the pnpm workspace, consuming @spectastic/schema (and @spectastic/core where useful). On activation the host registers a webview view and a "select spec" command (a native QuickPick — FR-008). For the selected spec it scans specs/<id>/, runs an extended extractHealth() over each artifact, assembles a LifecycleGraph (nodes + typed edges), and postMessages it to the webview. A createFileSystemWatcher('**/specs/<id>/*.html') re-extracts only the touched file and posts a node-level patch (FR-009, NFR-002).

The webview is vanilla TS. A pure, deterministic layout function places the linear spine on a row with offset lanes for child slices and proposals (D-003); edges are inline SVG; nodes and the hover/select compact card are DOM that consumes spec.css custom properties, with a small theme layer mapping --vscode-* surface variables onto our tokens while keeping spectastic accents, brand colours, and pills (FR-012, D-007). Clicking a node posts open; the host opens a WebviewPanel that loads the artifact's own HTML with asset links rewritten via asWebviewUri under a strict CSP (D-005). Staleness is an mtime comparison against upstream artifacts (D-006).

5 · Decisions

D-001 · New packages/vscode package consuming the kernel

Status
Accepted
Context
@spectastic/core and @spectastic/schema already name "the future VS Code extension" as a consumer; the repo is a pnpm monorepo.
Decision
A new workspace package @spectastic/vscode with a host entry and a webview entry, bundled by tsup (CJS host, IIFE webview). Depends on @spectastic/schema via workspace:*.
Consequences
+ Reuses the grammar + kernel; the extension stays thin. − First dual-bundle-target package and first VSIX in the repo.

D-002 · Vanilla TS + DOM/SVG for the webview (no framework)

Status
Accepted
Context
The principles' Scope non-goal forbids JS frameworks; the canvas shows ≤ 8 nodes for one spec.
Decision
Hand-written render: cards as DOM, edges as inline SVG, state via a tiny message-driven update loop. No Preact/Svelte/Lit.
Consequences
+ Principle-compliant, near-zero runtime, fits the single-file ethos. − More hand-written render/state code than a reactive lib would need.

D-003 · Hand-rolled deterministic L→R layout

Status
Accepted
Context
FR-004 wants deterministic auto-layout with lanes; the graph is linear-ish; calm spacing must be controllable.
Decision
A pure function places the spine on one row and offsets child-slice / proposal nodes onto lanes. No layout dependency.
Consequences
+ Zero deps, fully predictable, trivial to test. − We maintain it; it is not built for the deferred whole-project overview.

D-004 · Health extraction extends @spectastic/schema

Status
Accepted
Context
FR-010 derives node state by parsing artifact HTML; schema already has a parse5 AST, findAll/getAttr, and extractSpecMetadata.
Decision
Add extractHealth() returning an ArtifactHealth (status, req counts, budget band, open-question count, regen pass/fail) beside extractSpecMetadata, including a static re-computation of the budget band.
Consequences
+ One tested source of truth; the extension stays thin; validate can reuse it. − Pre-1.0 minor bump of schema; consumers pin tightly.

D-005 · Open the artifact in a WebviewPanel with asWebviewUri + CSP

Status
Accepted
Context
FR-003 requires the artifact rendered in spectastic's design system; webviews sandbox local resources.
Decision
Load the artifact HTML into a panel; rewrite its ../../assets/* links via asWebviewUri; serve under a strict CSP scoped to the extension's localResourceRoots (repo assets/ + the spec folder).
Consequences
+ Faithful, in-editor "the document is the artifact". − CSP + URI-rewrite work; must permit spec.js; the riskiest single piece (spiked first).

D-006 · Staleness by file mtime comparison

Status
Accepted
Context
Resolves the spec's one open question (§7) for FR-007: how "predates an upstream change" is computed.
Decision
A node is stale when its file mtime is older than the newest upstream artifact's mtime. No parsing; the watcher already surfaces mtimes.
Consequences
+ Simple, robust, fits "no build step". − Coarse: a no-op save bumps mtime. Revisit with a changelog-date hybrid only if it proves noisy.

D-007 · Theme by mapping --vscode-* onto spectastic tokens

Status
Accepted
Context
FR-012: follow the active VS Code theme for surfaces, keep spectastic accents / brand / pills.
Decision
A small theme layer assigns VS Code surface variables (--vscode-editor-background, etc.) to our surface tokens at runtime; accent, per-verb brand, and pill tokens stay spectastic's own.
Consequences
+ Sits natively in any editor theme; brand intact. − A token-mapping layer to maintain; contrast must be re-checked per theme (NFR-003).

D-008 · Derived-view node category for verify.html

Status
Accepted
Context
Spec 021 added verify.html — a regenerated, statusless view. FR-014 names a derived-view node category that sits outside FR-002's fixed verb palette.
Decision
Tag the node with a derived-view kind. The scanner adds a verify candidate (specs/<id>/verify.html) and emits a node with no status pill; its metric is a binary stale flag from 021's verify-view-stale rule (021 FR-008) — a different signal from D-006's node-mtime staleness. The webview renders it visually distinct from the verb spine, attached adjacent to its source.
Consequences
+ Future derived views (e.g. a conformance index) reuse the category; FR-002's verb-node contract stays intact. − A new node kind plus a second, distinct staleness signal to keep separate from D-006; the metric couples 020 to 021's rule.

D-009 · Artifact-panel identity + reuse map

Status
Accepted
Context
T-007: open-artifact.ts titled panels by bare verb with no spec id and created a fresh panel per click, so a leftover panel from one spec read as the spec now on the canvas. FR-003 now requires identity + reuse.
Decision
The view provider holds a Map<artifactPath, WebviewPanel>. openArtifact titles each panel <spec-id> · <verb> (spec id leads, surviving tab truncation), reveals the existing panel on re-open instead of stacking a duplicate, and clears the entry on onDidDispose. Cross-spec panels stay open — auto-close was deliberately rejected (the proposal's §2) to preserve cross-spec comparison.
Consequences
+ Identity + no duplicate panels; cross-spec comparison preserved. − The provider gains panel-lifecycle state (it was stateless); panels can accumulate across many specs (accepted, bounded by the leading-id disambiguation).

8 · Complexity tracking

Where this plan adds complexity beyond the spec's literal text, the justification lives here.

P-4 exception. The canvas webview is JS-dependent and does not degrade to a static document. Justified: it is editor tooling, not a shipped spec artifact, and the artifacts it opens still honour P-4 (FR-003). Mirrors the spec's <spec-warning>; not a precedent for JS-dependent artifacts.

Static budget-band recomputation. spec.js computes the budget band at render time; the extension must reproduce it statically because FR-010 forbids a build step or index. Justified by FR-010; mitigated by centralising the logic in @spectastic/schema with parity tests so the two never silently diverge.

Token-mapping theme layer. Mapping --vscode-* onto our tokens is more surface than hardcoding spectastic light/dark. Justified by FR-012 (native fit was the decided theming approach) and bounded by NFR-003 contrast checks.

9 · Open questions

None outstanding — the canvas surface was settled during implementation: a dedicated Activity Bar view container (contributes.viewsContainers.activitybar), not the bottom Panel; both used the same WebviewView, so the choice was non-blocking as anticipated.
