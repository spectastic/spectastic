Lifecycle canvas (VS Code)

An in-editor canvas that shows one spec's whole principles → … → triage flow at a glance — and opens any artifact in a click.

1 · Context

spectastic artifacts are self-contained .html files at specs/<id>/{spec,plan,tasks,…}.html. Today an author moves through a lifecycle by opening files in the VS Code tree — there is no at-a-glance view of where a spec stands: which artifacts exist, their status, whether the spec is over budget or carries open questions or a blocked plan. That state is already encoded in the artifacts; nothing surfaces it together.

A design brief proposes an in-editor canvas of connected cards translating the lifecycle into spectastic's calm, editorial voice. This spec scopes its first shippable slice: a read-only canvas for one selected spec, two card fidelities (minimal node, compact card), and a one-click affordance into the full rendered artifact. Users: authors working a spec through its lifecycle in VS Code.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · See the lifecycle at a glance P1

As an author, I want to open a panel that draws my selected spec's whole principles → … → triage flow as connected nodes so that I can see which artifacts exist and their status without opening each file.

Acceptance: with a spec selected, the panel shows one minimal node per existing artifact, ordered along the lifecycle (vertical by default) — verb icon, title, status pill, one metric — with edges along the flow.

US2 · Open any artifact in one click P1

As an author, I want to click a node and have its rendered artifact open so that the canvas is a launcher, not a dead picture.

Acceptance: clicking any node opens that artifact rendered in spectastic's design system, in no more than one click.

US3 · Read more health without leaving the canvas P2

As an author, I want to hover or select a node to reveal a compact card of 3–5 health rows so that I can judge a node's state before deciding to open it.

Acceptance: hover/select expands the node to a compact card of per-verb health fields; a node needing attention (over budget, open questions, blocked) is visibly distinct from a calm one before any card is opened.

Edge cases

  • No spec selected, or a workspace with no specs/ — the panel shows a calm empty / first-run state, not an error.
  • An artifact file is present but malformed or unparseable — its node renders in an unknown state; the panel never crashes.
  • An artifact is edited, added, or deleted on disk while the panel is open — the affected node updates without a manual refresh.
  • A spec has child slices or a proposal in flight — these appear as lanes branching off the linear spine.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The panel MUST render the selected spec's lifecycle as a canvas of nodes — one node per existing artifact file — ordered along the lifecycle sequence principles → spec → plan → tasks → implement → propose → apply → triage (laid out in the orientation set by FR-004), plus any derived-view artifacts the bundle carries (e.g. verify.html), rendered per FR-014 and associated with the spec rather than placed inline in the verb sequence. A missing artifact simply has no node, which is itself information.

Each minimal node MUST show a verb icon, a title (spec id / name), a status pill, and exactly one key metric, colour-coded by node type using the fixed per-verb colour order of 017-brand-logo — which MUST NOT be shuffled, recoloured, or dropped. This fixed-colour mandate binds lifecycle-verb nodes; derived-view nodes (FR-014) sit outside the verb palette and take a deliberately distinct, non-verb treatment.

Clicking a node MUST open that artifact's full rendered document in spectastic's existing design system, in no more than one click. The opened panel MUST identify its spec — its title MUST lead with the spec id (e.g. 020-vscode-extension · spec) so identity survives tab truncation, reinforced by the rendered artifact's own header which already carries the spec id — and re-opening the same artifact MUST reuse its existing panel rather than stacking a duplicate. Panels opened from other specs remain open across a spec switch (the canvas MUST NOT auto-close them); disambiguation is by title, so artifacts from different specs can be compared side by side.

The canvas MUST position nodes by deterministic auto-layout in the active orientation — vertical (top-to-bottom) by default, or horizontal (left-to-right) — with lanes for child slices and proposals branching perpendicular to the spine, and draw edges along the flow including branch points (parent↔child, propose→apply / →withdraw). Manual arranging is out of scope for this slice.

Hovering or selecting a node SHOULD reveal a compact card of 3–5 per-verb health rows. The ⋯ action menu (run / validate) is out of scope for this slice.

A node MUST enter a visible needs-attention state when any of its signals fire — budget red, an open <spec-question>, blocked status, an unresolved risk at identified, or a failing regen — and MUST stay quiet otherwise, so the cue earns its ink only when it means something (P-5).

A node SHOULD show a stale state when its artifact predates a change in an upstream artifact (e.g. a plan older than its spec's last edit).

The panel MUST provide a picker to choose which spec's lifecycle is shown, and render exactly one spec's lifecycle at a time.

The canvas MUST update live when artifacts in the selected spec are added, changed, or removed on disk, via a workspace file-watcher, without requiring a manual refresh.

Node state MUST be derived by scanning specs/<id>/ and parsing each artifact's HTML (status pills, counts, budget band, health fields); no separate index or build step MAY be required — the artifacts are the source of truth.

The panel SHOULD render a calm empty / first-run state when no spec is selectable, and MUST degrade a malformed or unparseable artifact to an unknown-state node rather than failing the whole panel.

Surfaces (page, card, inset) SHOULD follow the active VS Code theme so the panel sits naturally in the editor, while retaining spectastic's accent colours, per-verb brand colours, and status pills.

The canvas SHOULD expose an orientation toggle — a view title-bar control and a command — that switches the layout between vertical and horizontal, and SHOULD remember the chosen orientation per workspace so it survives a reload.

A derived-view artifact — a regenerated, statusless view of the bundle such as verify.html — MUST render as a distinct node category. It MUST NOT carry a status pill (it has no own lifecycle status; per 021-verify-view FR-007 it derives the spec bundle's), MUST show, in place of a verb metric, a freshness indicator — at minimum a binary stale flag derived from the verify-view-stale signal (021 FR-008), a value the bundle genuinely exposes — and MUST be visually distinguishable from the verb-coloured lifecycle spine (FR-002). A richer measure (e.g. trace coverage) MAY follow. The node SHOULD attach adjacent to its source rather than inline in the verb sequence.

Non-functional

On panel open for a typical single-spec lifecycle (≤ 8 nodes), the canvas MUST paint in under 300 ms at p95 on a developer-class machine.

After an artifact is saved, the affected node SHOULD reflect the change within 500 ms, with no full-canvas reload flicker.

Nodes and cards SHOULD stay legible at small editor sizes in both light and dark, meeting WCAG AA contrast for all text against its surface.

Every rendered node and overlay MUST contain its own content (no overspill past its border) and remain fully within the panel viewport (no clipping by an overflow ancestor or the editor edge), verified by containment and on-screen-bounds assertions — not merely "it rendered".

Rationale

Added after T-001/T-002: a fixed-height node and a hover card positioned inside a scroll container passed every presence test yet were visibly cropped. Presence is not containment.

Out of scope (deferred to other slices)

  • The ⋯ action menu — running the next verb or validating from a node (state-mutating; shells to the CLI).
  • Whole-project overview (every spec folder at once) and the inbox small-batch node.
  • Free / manual node positioning persisted per workspace.
  • Marketplace publishing, packaging, and signing — this slice is dev-host / VSIX sideload only.
  • The full rendered artifact's design — already shipped in assets/spec.css; reused read-only.
  • Validation squiggles / problems-panel integration — owned permanently by the native VS Code Diagnostics API, not this canvas.

4 · Data model

A transient, derived view model — it persists nothing; the artifacts on disk are the source of truth.

Entities

LifecycleGraph
The selected spec's ordered ArtifactNodes plus their Edges. Rebuilt from a filesystem scan; never written back.
ArtifactNode
One artifact file: verb type, spec id, path, status, its HealthSnapshot, fidelity (minimal / compact), and derived flags (attention, stale, unknown).
Edge
A directed link, kind flow (spine), slice (parent↔child), or proposal (propose→apply / →withdraw).
HealthSnapshot
Per-verb fields parsed from the artifact (for a spec: req count, budget band, open-question count) — the brief's appendix is the authoritative field list.
Selection
The currently-shown spec id, driven by the picker (FR-008).

Node state is a pure function of the artifacts on disk; the file-watcher (FR-009) re-derives the affected node on change. Nothing couples the canvas to a write path — it cannot corrupt a spec because it never writes one.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

From a cold panel open, an author can see the full lifecycle of a selected spec and open any one of its artifacts in a single click — with no use of the file tree.

Given a spec with one at-risk artifact (over budget, open questions, or blocked) among calm ones, a first-time viewer identifies the at-risk node unaided, without opening any card.

The canvas paints a single-spec lifecycle (≤ 8 nodes) in under 300 ms at p95 on panel open.

After an artifact is saved, its node reflects the new state within 500 ms without a manual refresh.

6 · Assumptions

Specs follow the specs/<id>/<verb>.html layout this repo uses; non-conforming layouts are out of scope.

Artifact HTML is stable enough to parse for state (status pills, budget gauge, counts) without a formal schema — the same structure spectastic validate already relies on.

P-4 exception. Principle P-4 requires spectastic artifacts to stay readable with JavaScript off. The canvas is a VS Code webview — editor tooling, not an artifact — and is inherently JS-driven, so it does not degrade to a static document. The artifacts it opens (FR-003) still honour P-4 unchanged. A deliberate, scoped exception; not a precedent for JS-dependent artifacts.

7 · Open questions

None outstanding — the one deferred item, FR-007's stale mechanism, was settled during implementation: an upstream change is a later file mtime (a downstream artifact older than its upstream's mtime is stale), implemented in the scanner's flagStale (stale.ts). Both the criterion and the mechanism are now fixed.
