What a component does

A component is declared, named, scoped and versioned — and nothing anywhere says what it does when you hover it, or what it looks like while it waits.

1 · Context

A component today declares what it is: a name, a scope, a maturity, an origin, and where it was vendored from. It declares nothing about what it does. A button has a resting appearance, a hover, a focus ring, a pressed state, a disabled state, a loading state, a success and an error — and the one that ships broken most often is the one nobody thought to ask about.

The screen vocabulary is close but is not this. A screen's states are the situations the screen is in, derived where possible from the responses of the contract it calls. A component's states are the situations a control is in, and they are driven by interaction rather than by a response — there is no status code for hover. Recording them on the screen would put a button's focus ring in ten places if ten screens use the button, which is the duplication the component scope exists to remove.

The completeness rule is the point rather than a detail. Listing the states a component has is easy and uninformative; the useful artifact is the list of states it should have with each one either designed or refused in writing. A blank is then a question, not a silence.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · A component declares the states it has P1

As a developer building a control, I want to see every interaction state it is meant to have so that I do not discover the focus ring was never designed at review.

Acceptance: A declared component can declare its interaction states; the set of states expected of it is derivable without reading the component's code.

US2 · A state that does not apply says why P1

As a reviewer, I want to tell a state nobody designed from one deliberately refused so that an omission and a decision do not look identical.

Acceptance: A component can mark an expected state not applicable with a reason; the reason is required; a state that is simply absent reads differently from one declined.

US3 · A transition is declarable, not only a state P2

As an author, I want to record what carries a component from one state to another so that a timed or conditional transition is written down rather than discovered in the implementation.

Acceptance: A component can declare a transition between two of its declared states; a transition naming a state the component does not declare is reported.

Edge cases

  • A non-interactive component — a card, a divider — for which most interaction states are meaningless.
  • A consumed component whose states belong to somebody else's library.
  • A component whose loading state is indistinguishable from its resting one by design.
  • A transition with no trigger a person controls, such as one driven by elapsed time.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A component MUST be able to declare the interaction states it has, each as a declared element belonging to it.

Rationale

On the component rather than the screen: a control used by ten screens has one focus ring, and recording it ten times is the duplication component scope exists to remove.

The set of interaction states a component is expected to account for MUST be defined as data rather than fixed by this requirement.

Rationale

It is a judgment about interface convention and it will age. A sibling has already been through this: a requirement naming a fixed count had to be reworded because the count moved, and the list belongs where it can change in one line.

An expected state a component does not declare MUST be reportable as unaccounted for, and a component MUST be able to mark such a state not applicable with a reason.

Rationale

The completeness rule, and the reason it earns its keep. Listing what a component has is uninformative; listing what it should have, each entry designed or refused in writing, turns a blank into a question.

A not-applicable mark with no reason MUST be reported.

Rationale

Exactly the rule the variant grid already applies to a declined context. A decline without a reason is indistinguishable from a shrug, and the whole value of recording it is that somebody thought about it.

A state that is absent MUST read differently from one marked not applicable.

Rationale

The family's standing rule, restated because this is the slice where it costs most: the difference between "nobody designed the disabled state" and "this control is never disabled" is the difference between a bug and a decision.

A component MUST be able to declare a transition between two of its declared states, naming what carries it.

A transition naming a state the component does not declare MUST be reported.

Rationale

The same reference discipline every other element in this family uses: a reference to nothing reads as diligence and records nothing at all.

A component declaring itself non-interactive MUST be exempt from the completeness check entirely, rather than being expected to decline every state individually.

Rationale

Failing safe on the antecedent, the posture the contract-first category already takes. A divider declining nine states one at a time is nine lines of noise saying one thing.

A consumed component — one the project declares but does not own — SHOULD be exempt from the completeness check.

Rationale

Its states belong to whoever wrote it, and demanding an account of them would have a project document a library rather than its own decisions. 097 already distinguishes consumed from authored, so the antecedent exists.

A state SHOULD be able to carry the same annotations a screen's state carries, rather than a parallel vocabulary.

A component MAY declare a state outside the expected set, and such a state MAY NOT be reported.

Non-functional

Every declared state, decline and transition MUST render with scripting disabled: 100% of the authored content readable with JavaScript off.

The completeness check MUST return before allocating on a document declaring no components: at most 1 scan of the document and 0 further work, adding under 1 ms to a document that declares none.

Out of scope (deferred to other slices)

  • What a transition looks like over time. This spec says a transition exists and what triggers it; the duration and easing of several elements moving together is a sequence, not a property of one control.
  • Movement between screens, which is a journey rather than a component transition.
  • Rendering any of this inside the design.
  • Driving a component through its states against a running build.

4 · Data model

Two additions to a component that already exists, and one relation between them.

Entities

Interaction state
A situation a control is in, driven by interaction rather than by a response — which is what distinguishes it from a screen's state, where the source is often a contract's status code. Belongs to exactly one component.
Expected set
The interaction states a component of a given kind should account for. Data, not a requirement, because it is a judgment about convention that will age.
Transition
A move between two of one component's declared states, with what carries it. Both ends must be states that component declares.

The invariant that makes the completeness rule work: every expected state is in exactly one of three conditions — declared, declined with a reason, or unaccounted for. There is no fourth, and the third is the only one that reports.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For an interactive component, the number of expected states that are neither declared nor declined is 0, or each produces exactly 1 finding.

Declines carrying no reason number 0. A reader can distinguish an absent state from a declined one in 100% of cases.

Non-interactive and consumed components produce 0 completeness findings, counted across every component in the project.

Transitions naming a state their component does not declare number 0, or each produces exactly 1 finding.

6 · Assumptions

The expected set is roughly the conventional one — resting, hover, focus, pressed, disabled, loading, success, error, empty. Assumed from interface convention rather than measured, which is precisely why FR-002 puts it in data where being wrong costs one line.

Authors will decline rather than ignore. If they ignore instead, the check reports and the finding is the mechanism working — but a project that finds the noise unbearable will reach for a blanket non-interactive declaration, and that failure mode is worth watching for.

7 · Open questions

None outstanding. The one genuinely open question was whether a component's states belong on the component or on each screen that uses it, and it is settled by the scope 097 already built: a control used by ten screens has one focus ring, and recording it ten times is the duplication component scope exists to remove.
