Verb decision taxonomy

Lift each generation verb's bounded decision-phase questions into a code registry the Decider can answer — so an unattended run decides them by role, not a human by hand.

Status Accepted Spec ID 039-verb-decision-taxonomy Owner Brian Corbin · @briancorbinxyz Reviewers — Created 09 Jul 2026 Principlesv1.3.0 Smallest demoableanswerDecisions('plan', {role:agent}, ai) returns a chosen test-style + risk-tolerance from the declared options via the Decider. Read time

Grounding for 037 found each verb's decision-phase questions live only in the slash-command markdown — unreachable by an injected Decider. This spec lifts the verb-generic, bounded ones into a code registry: plan's test-style and risk-tolerance, tasks' execution-strategy. An answerDecisions(verb, cfg, ai) helper answers a verb's questions through decideChoice (036), honouring the configured role (human / agent / panel). Context-dependent decisions (smallest-demoable framings, per-story priorities) are not liftable — they're generated from the artifact and stay the adaptive interview (deferred). This is the FR-005 primitive 037 consumes; it changes no existing verb's behaviour.

1 · Context

The grounding pass for 037 established that only three decisions are reachable in kernel code (propose's adversarial decide, the slicer's confirmRice, triage's escalateLayer) — all already Decider-answerable. Every other verb decision — plan's test-style, tasks' execution strategy — lives only in the slash-command markdown's AskUserQuestion passes, which a CLI/Workflow orchestrator cannot inject a Decider into. For a hands-off run to decide them by role, the bounded ones must exist in code.

This spec is for the orchestrator (037) that needs to answer those decisions unattended, and the maintainer who wants the code registry to stay faithful to the human interview it mirrors.

2 · User scenarios & testing

Each story MUST be independently testable: US1 alone is a viable MVP.

US1 · The generation verbs' bounded decisions live in code P1

As an orchestrator author, I want each generation verb's bounded decision-phase questions as a code registry answerable by the Decider so that an unattended run decides them by the configured role instead of prompting a person.

Acceptance: answerDecisions('plan', cfg, ai) answers plan's test-style + risk-tolerance and answerDecisions('tasks', cfg, ai) answers tasks' execution-strategy, each returning a chosen option label per question via decideChoice.

US2 · The answerer honours the configured role P1

As a maintainer, I want the answerer to route by the resolved Decider role so that human is the default (parity with the slash-command interview) and agent/panel answer unattended.

Acceptance: at role human the answerer calls ai.ask with the verb's questions; at agent/panel it convenes the Decider — the same dispatch decideChoice already guarantees.

Edge cases

  • A verb with no liftable bounded decisions (e.g. spec — its decisions are context-dependent): the registry has no entry, and answerDecisions returns an empty result rather than inventing questions.
  • An unknown verb name: the answerer returns empty (no throw) — the orchestrator simply has nothing to inject for it.
  • The Decider returns an out-of-range label: decideChoice already defaults to the first declared option (036 NFR-001) — inherited, not re-specified here.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A DECISION_TAXONOMY registry MUST map each generation verb to its bounded, verb-generic decision-phase questions as a Question[]: plan → test-style (TDD / integration-first / smoke-only) + risk-tolerance (Low / Medium / High); tasks → execution-strategy (MVP-first / Incremental / Parallel).

Rationale

These are the decisions a verb's slash-command decision phase asks that are the same regardless of the specific artifact — so they can be a fixed, reviewable code registry. The option copy mirrors the command markdown (FR-004).

answerDecisions(verb, cfg, ai) MUST answer that verb's registry questions by delegating to decideChoice(cfg, questions, ai) (036), returning the chosen option label per question keyed by its header.

answerDecisions MUST honour the resolved Decider role — human routes to ai.ask, agent/panel convene the Decider — inheriting decideChoice's dispatch and guardrails rather than re-implementing them.

The registry's questions and option labels MUST mirror the corresponding slash-command decision-phase options; a verb whose decisions are context-dependent (spec's smallest-demoable framings, per-story priorities) MUST NOT be given a fixed registry entry.

Rationale

Faithfulness to the human interview (the registry is not a new taxonomy, it's the same one in code); and honesty about what is liftable — a context-dependent decision has no fixed option set.

answerDecisions SHOULD return an empty result for a verb with no registry entry (including an unknown verb), never throwing — the orchestrator simply injects nothing for it.

Non-functional

This spec MUST NOT change any existing verb kernel's behaviour: the registry + answerer are additive; wiring the answers into a verb's generation is 037's integration, not this slice's.

Out of scope (deferred to other slices)

  • Context-dependent decisions (smallest-demoable framings, per-story priorities, quantified NFR targets) — generated from the artifact, they stay the adaptive interview.
  • Threading the answered decisions into each verb's generation prompt — the orchestrator that consumes this registry owns that.
  • Re-implementing role dispatch or panel voting — inherited wholesale from 036 decideChoice.

4 · Data model

One registry constant and one helper; both reuse the landed Question / DeciderConfig types.

Entities

DECISION_TAXONOMY
Record<VerbName, Question[]> — the bounded, verb-generic decision-phase questions per generation verb (only the liftable ones have an entry).
answerDecisions
(verb: string, cfg: DeciderConfig, ai: AIProvider) => Promise<Record<string,string>> — the registry lookup + decideChoice call; empty for an absent verb.

Invariant: the registry holds exactly the decisions that are the same across artifacts. A decision whose options depend on the artifact is definitionally not in the registry (FR-004).

5 · Success criteria

Technology-agnostic, measurable outcomes.

With role agent, answerDecisions('plan', cfg, ai) returns a chosen test-style and risk-tolerance — each a declared option label — via one subagent per question, and answerDecisions('tasks', …) returns a chosen execution-strategy; observable by the returned map and the subagent invocation count.

At role human, answerDecisions calls ai.ask with the verb's registry questions and returns its answer — parity with the slash-command interview shape; observable via a stub recording the ask call.

The registry's question headers and option labels match the corresponding slash-command decision-phase options exactly — observable by asserting the declared labels (no drift from the source markdown).

answerDecisions on a verb with no entry (e.g. spec or an unknown name) returns an empty map and makes no Decider call — observable via the stub.

6 · Assumptions

decideChoice (036) is a sufficient answerer for a batch of bounded Questions — verified during 037's grounding (it dispatches by role, sizes the panel by effort, and defaults out-of-range labels).

The three verb-generic decisions named (plan test-style + risk-tolerance, tasks execution-strategy) are the complete liftable set today; a future verb-generic decision is an additive registry entry, not a reshape.

7 · Open questions

None outstanding — the liftable/unliftable boundary is settled (verb-generic vs context-dependent), the answerer reuses decideChoice wholesale, and the option copy is a faithful mirror of the command markdown.
