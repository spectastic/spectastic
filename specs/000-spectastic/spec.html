Spectastic

A single-file HTML alternative to markdown-based spec tooling — rich, dense, hand-editable.

System-of-record budget. The meta-spec is the single authoritative document of the spectastic project itself; slicing it by topic group (e.g. carving the REQ-CHANGE-* family into a sibling) trades one search hit for two and weakens the "open one file, see the whole contract" property. By project convention — captured in the 16 Jun 2026 slicing audit — system-of-record specs (this meta-spec, principles.html) stay all-inclusive over budget rather than being sliced. The budget here was raised from 3,000 to 5,000 to reflect that the artifact has grown with the system; the per-feature 1,500–2,500-word threshold does not apply.

Markdown specs are quick to write but cramped to review. Spectastic runs a structured spec lifecycle — principles → spec → plan → tasks → implement → propose → apply → triage — and emits a single self-contained .html file per artifact. The file uses a small vocabulary of semantic custom elements (<spec-requirement>, <spec-decision>, <spec-diff>…) with a calm typographic system, so a spec reads like a quiet essay yet packs tables, diagrams, diffs, decision matrices, and progressive disclosure that markdown can't.

1 · Context

Spec-driven development treats the spec as the source of truth and code as its expression. The workflow is good. The artifact, when shaped as a stack of markdown files, is not. Independent benchmarks have measured markdown-spec workflows at roughly an order of magnitude slower than plain AI coding, largely from review burden. A typical markdown spec pipeline produces five or more files — principles, specification, plan, research, tasks — that share context, repeat each other, and ask a reviewer to hold the whole graph in their head. Three patterns recur in criticism:

  1. Review fatigue. Long undifferentiated prose; no progressive disclosure; every section reads at the same visual weight.
  2. Markdown is a thin format. No diagrams, fragile tables, no interactivity, no inline annotation, no semantic anchors beyond headings.
  3. "Waterfall in markdown." Multiple gated phases produce duplicated background context across artifacts because cross-linking is weak.

HTML solves these directly. A single file can hold semantic structure, tables that work, inline SVG, collapsible sections, tabs, badges, and a real typographic hierarchy — and still be read in any browser, attached to an email, or piped through cat. The challenge is keeping the source as editable as markdown for both humans and LLMs. That is the bet spectastic makes.

Branch model. Under branch-based automation (git.auto=branch+commit), spec MUST create the slice's branch named NNN-slug off the default branch when it opens the slice. Small, revert-safe work — just-do cards, triage list-intake, one-file hotfixes — MUST stay on the current branch (no branch created), reusing the existing just-do boundary.

This family binds spectastic's own git automation — what the verbs do when a developer opts in. A consuming project's hand-commits and its PR-merge strategy are its own; REQ-GIT does not govern them.
Rationale

The slice is the natural unit of review; the latent 018-explain pattern proved the shape. Branch creation + the small-work exception are implemented by 026 FR-003 / FR-005 (git-strategy G-002). Two parts of the model are described, not mandated, because nothing automates them today: the slice branch merges to the default branch when the spec flips Accepted, and proposals are intended to live on change/NNN-<date>-<slug> branches. Both are the developer's action (or a PR) — the intended workflow, not a conformance MUST — and stay descriptive until a future slice implements them.

Commit message contract (subject + attribution). An auto-commit's subject MUST follow <verb>(NNN): <subject> (Conventional Commits — the lifecycle verb as type, the spec id as scope) whenever a spec id is in play, and the unscoped <verb>: <subject> form when it isn't (triage list-intake, principles, an implement run draining an inbox just-do card). implement MUST emit one commit per drain invocation, not one per ticked task. Authorship of record is human only: when attribution trailers are written, spectastic MUST NOT emit an AI identity as Author, Co-authored-by, Reviewed-by, or Acked-by — the assisting model is acknowledged distinctly, and only, as Assisted-by: <model>. (Which trailers are emitted, and when, is the delivery concern of REQ-GIT-003 + git.trailers.)

Rationale

The grammar already speaks in the history; the unscoped form and the Assisted-by stance were settled in 027. Conventional Commits explicitly permits types beyond feat/fix — here the lifecycle verb is the (custom, permitted) type, the spec id the scope. Implemented by 026 FR-002/FR-007 + 027 FR-005/FR-006 (git-strategy G-003 + G-004).

Opt-in, default-off delivery. Git automation MUST be opt-in and default off: git.auto and git.trailers both default off, every verb MUST accept --commit/--no-commit, and with automation off no verb performs any git action. An auto-commit MUST be gated on a clean spectastic validate and compose after the P-6 state-gate and the explore quarantine (never around them). The git layer itself MUST NOT introduce squash-on-merge as a default, nor rewrite or squash existing default-branch history — per-verb commits are the legible record. This binds the layer, not the consuming project: how a project merges its own PRs (squash or not) is its choice; the contract is only that spectastic's automation doesn't squash for it.

Rationale

The house enforcement stance (opt-in, default off, documented loudly); per-verb commits are the legible record. Implemented by 026 FR-001/FR-004/NFR-002 (git-strategy G-003 §7 guardrails).

Every command spectastic surfaces to an agent host as a skill — the lifecycle commands enumerated in REQ-TOOL-001 and any extended verb it ships (e.g. /spectastic.explain, /spectastic.explore) — MUST declare structured invocation metadata in its source frontmatter as the source of truth for how the skill router selects it. The metadata MUST comprise three keys:

  • triggers — the intents and phrasings that should invoke the command;
  • use-when — a one-line framing of when to reach for it;
  • sibling-boundary — what disambiguates it from adjacent verbs (e.g. propose vs plan, spec vs explore).

The metadata MAY additionally carry an optional model: key declaring the model tier the command runs on — an alias (never a pinned model ID) drawn from the legal set that 044-verb-model-policy owns as a single source of truth. It is advisory to the host and is not one of the three required keys; a command that omits it is fully conformant. The per-verb tier assignments and their enforcement are owned by 044-verb-model-policy.

The harness router reads only the frontmatter description. That description MUST be a fixed, committed output tuned against /skill-creator's eval — the same string the router loads and the eval measures — and MUST NOT be generated from the keys at sync time (a generated description makes the evaluated artifact a moving target that never lives in the repo). The structured keys are the machine-checkable contract and the input skill-creator tunes from; the description is the resulting trigger surface. Where a key and the description diverge, the description is authoritative. spectastic validate MUST carry a skill-metadata-shape rule that flags a command whose source frontmatter is missing any of the three required keys; the rule ships at warning severity. That rule checks only the three required keys for presence and MUST NOT flag a command merely for omitting the optional model: key. The well-formedness of a present model: value — that it is a legal alias — is enforced by the drift-guard rule that 044-verb-model-policy requires, so a permitted key never ships without a machine-checkable guarantee.

Command descriptions SHOULD be validated with /skill-creator's eval against a ≥90% trigger-accuracy default target (the command fires correctly on ≥90% of its intent cases) whenever the metadata changes; a command measured below the target SHOULD be re-tuned before it ships. The target is a SHOULD, not a hard gate — the first eval run establishes the baseline it is checked against — until spectastic ships a harness that can run the eval automatically (deferred to init --tools), at which point the check MAY be promoted to a gated must by a future change.

Rationale

Commands load as skills but invoke unreliably because their frontmatter is authored for a human reader, and no requirement encodes a triggering bar (triage T-008, spec layer, regen fail). Structured keys make the bar machine-checkable; the description stays a fixed, tuned output so the exact string skill-creator evaluates is the one committed and loaded — generating it at sync would break that eval loop. The validate rule gives the must teeth (starting as a warning so the ten existing commands can be brought up to the bar without a red build); the eval should makes "reliable" measurable rather than asserted, baselined on first run so the ≥90% figure is checked against reality before it ever hardens into a gate. The optional model: key is an orthogonal, advisory knob (spec 044): permitting it in the contract keeps a cost-tiering choice from ever reading as a metadata violation, while its well-formedness is guaranteed by 044's drift-guard (a MUST) — so the permission never ships without an enforcement, honouring P-8.

Every date in an artifact MUST be wrapped in a <time> element whose datetime= attribute is a valid ISO 8601 date (YYYY-MM-DD, or a fuller ISO timestamp where a time-of-day is meaningful) and whose visible text renders in the canonical human form DD Mon YYYY — a zero-padded two-digit day, a three-letter title-case month, and a four-digit year, e.g. <time datetime="2026-07-06">06 Jul 2026</time> (not 6 Jul 2026). This holds uniformly across <spec-meta> Created/Updated rows, <spec-changelog> entries, and inline dates. A date-format validate rule SHOULD warn (not error) when a <time>'s display text departs from DD Mon YYYY or its datetime= is not ISO 8601.

Rationale

The datetime= attribute was ISO 8601 only by habit and the visible text was unowned, so the two forms drifted side by side — 2026-06-29 in one row, 29 Jun 2026 in the next (T-011). DD Mon YYYY is the corpus majority (375 vs 215) and the changelog convention, so it is the least-migration canonical choice (zero-padded day, e.g. 06 Jul 2026); ISO stays in datetime= for machines. The requirement is a genuine MUST; the rule's warn severity is a migration-scoped choice — it avoids breaking the SC-001 integration gate on the ~215 not-yet-normalized displays before the cleanup drains — not a softening of the mandate.

Copy that is the tool talking — text spectastic emits or writes for a user to read — MUST NOT surface spectastic's own internal artifact ids (spec numbers and slugs, REQ-*, FR-*, NFR-*, SC-*, T-*, P-*, D-*). The dividing line is the contract: a spec or plan artifact citing its own governing ids as anchors is legitimate provenance per P-3, not a leak — this explicitly includes a generated <spec-changelog> entry and the author-supplied apply summary the kernel writes (REQ-CHANGE-008), which are the human's voice. What the tool itself says — CLI --help text, error and diagnostic messages, and tool-managed markers (a pre-commit hook stamp, a managed-file marker) — carries no internal id; its provenance lives in code comments and the artifact trail.

A no-internal-id-in-copy validate rule MUST enforce, at error severity folded into every validate run and blocked by the pre-commit gate, the one tool-talking surface spectastic can see and judge without ambiguity: the string arguments of its own CLI .description/.option/.argument help calls, where an illustrative argument slug uses the sanctioned neutral placeholder 001-auth-service. This is a floor, not a cap — the rule MUST cover at least that surface. The remaining tool-talking surfaces (runtime finding messages, tool-managed markers) stay review-caught, permanently and by design: a rule scanning finding message: copy would false-positive on a finding legitimately naming the requirement it enforces, so that surface is judged by review, not linted. This ceiling MUST be recorded, not hidden — the honest P-8 posture — and is not a deferred check awaiting a future rule. The invariant binds spectastic's own tooling and every downstream project alike (P-10); a downstream project's application copy is unseeable by spectastic, so there it is review-caught too.

Rationale

Sourced from P-10 and meta-spec triage T-017 — spectastic --help shipped the tool's own spec numbers ((037), (spec 042), Spec 043.) across 30 sites. The requirement is a genuine MUST descending from a MUST-NOT invariant; the rule's error severity matches. It is stated as an abstract invariant with the enforced surface named separately as a floor, rather than an enumerated list of forbidden surfaces, so it neither freezes commander method names into a contract nor collides with REQ-CHANGE-008's id-citing author summaries — the two seams the adversarial pass surfaced (§5, R-001/R-002). The tool-talking-vs-artifact line is the same P-8 honesty the fat-core/thin-CLI convention carries (T-016). Parallels REQ-FORMAT-005's MUST-plus-named-rule shape and REQ-TOOL-004's "a rule gives the MUST teeth" pattern.

2 · Goals & Non-goals

Goals

  • Produce single-file .html artifacts that render in any modern browser, open from file://, and survive being emailed as an attachment.
  • Run a structured spec lifecycle: principles → spec → plan → tasks → implement → propose → apply → triage.
  • Match markdown's hand-editability: a human or LLM can open the source and make targeted edits without breaking layout.
  • Use a small, semantic component vocabulary (custom elements) — no class soup, no framework lock-in.
  • Provide a calm, information-dense default theme — readable at all sizes, never visually noisy.
  • Be diff-friendly under git: every component is a single semantic block; line edits are clean.

Non-goals (categorical — never in scope)

  • Not a wiki, CMS, or knowledge graph. One spec = one file.
  • No build step. Source .html is what ships.
  • No JavaScript framework. Progressive enhancement only; the spec is readable with JS off.
  • Not a replacement for ADR tooling, RFC publishing, or design-doc platforms. Spectastic sits next to them.
  • Not a markdown converter. The source is HTML by intent.

Out of scope (deferred to future slices)

  • A spectastic CLI with init --tools — now specced and built as 031-init-tools (the guarantee-layer installer: a pre-commit validate gate + drift-proof command adapters).
  • A spectastic validate command. Considered in C-004; needs its own proposal.
  • Cross-tool installers for Cursor, Aider, Copilot. Claude Code first.
  • An action-detecting /spectastic.next command piggybacking on a triage sniffer.

3 · Principles

The five non-negotiable principles every requirement in this spec is justified against live in the project's principles document:

  • P-1 · Source order is reading order
  • P-2 · Semantic tags over class soup
  • P-3 · IDs are contracts
  • P-4 · Progressive enhancement, never dependence
  • P-5 · Calm density

Each principle's full statement, rationale, and governance shape lives in principles.html. Downstream specs reference principles by ID (P-1… P-5); the principles document is the source of truth.

4 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Format

A spectastic artifact MUST be a single .html file. All CSS, JavaScript, and SVG MUST be inlined in the published build.

Rationale

Single-file is the entire shape of the offer: emailable, archivable, runnable from file://. Linked assets re-introduce the build-and-deploy concerns we are trying to escape.

The file MUST open and render correctly when loaded from the local filesystem, with no required network round-trip beyond Google Fonts (which itself SHOULD degrade to system fonts on failure).

Source files SHOULD stay under 200 KB before font assets. Past that, hand-editing in common editors gets sluggish.

A spec.html artifact MUST carry a <spec-budget> size gauge. The gauge's Words row MUST count authored prose only — the auto-built <spec-conformance> index is excluded, since it is generated rather than written. The gauge MUST band each metric against its declared budget as green ≤ 80%, amber > 80–100%, red > 100%, taking the worst row as the overall band. The default budget for a feature spec SHOULD be 1,500 words / 20 requirements / 12-minute read; tool-shape specs SHOULD declare a higher budget (e.g. 2,500 words), and system-of-record artifacts (this meta-spec, principles.html) are exempt. The amber band is advisory — a nudge to consider slicing, never a hard gate.

Rationale

The budget is small-batch pressure made visible, but its numbers were unowned and partly invented. 80% amber is the industry-standard "approaching limit" warn point (AWS CloudWatch sets capacity alarms at 80%; queueing theory puts the knee there) and avoids the alert fatigue a 70% band caused — 67% of our specs breached it, so it was overridden as routine (AHRQ on warnings that fire too often). RAG cut points are conventions, not canon (PRINCE2), so we pick the evidenced one. Authored-words stops the ~430-word conformance index from counting against the author. The brevity principle is real and is Larson's ("most people don't read long documents") — but the "1,500 words" figure was never his, so the gauge stops attributing it to him.

Authoring

Components MUST be expressed as custom elements (<spec-requirement>, <spec-decision>, etc.) — never as <div> + class names. Tag name is schema.

Every requirement MUST carry a stable id attribute of the form REQ-<TOPIC>-<NNN> and a priority attribute of must | should | may.

Authors SHOULD place rationale, derivations, and long examples inside <details> blocks so the requirement reads as a single sentence at default zoom level.

Authors MAY use <spec-sidenote> inline for marginalia that would interrupt the reading flow but is too small for a callout.

A <spec-questions> register with no open questions MUST contain no <li> items. Each <li> in the register counts as exactly one open question to every consumer — health extraction, the lifecycle needs-attention signal, validators — so an absence of <li> is the single unambiguous representation of zero. Resolved-with-rationale prose (e.g. "None outstanding — every decision was anchored in the interview") SHOULD live in a <p> inside the register, and MUST NOT be written as a placeholder or "None" <li>.

Rationale

The register is a counter to machines and a decision trail to humans; both are served by reserving <li> for an actual open question and putting prose in a <p>. 016-theme-support already does this; the <ol><li>None at write time…</li></ol> form used by the core specs is what trips the false count fixed here (T-005). Complements REQ-AUTHOR-001 (tag name is schema): the tag you choose inside the register is the meaning.

Lifecycle

The tooling MUST ship five lifecycle templates corresponding to the spec-driven lifecycle: principles.html, spec.html, plan.html, tasks.html, and proposal.html. Each MUST use the same design system.

Each template SHOULD include a <spec-status> in the header reflecting exactly one of: Draft, In Review, Accepted, Superseded, Deprecated, Blocked. Transitions between these values are governed by REQ-LIFECYCLE-004.

Each task entry in a tasks.html artifact MUST be a <spec-task> custom element. The element MUST carry:

  • id="T-NNN" — the stable task ID, matching the format defined for tasks elsewhere in the project.
  • parallel (boolean attribute) — present when the task can run alongside its in-flight peers (the existing [P] convention); omitted otherwise.
  • An inner <input type="checkbox"> — the completion state. checked means done. CSS MUST read the state via :has(input:checked) rather than a parallel data-status attribute, so the checkbox is the single source of truth.
  • A label child (a <div> or <p>) holding the task text. Its leading emphasis MUST be a single <strong> wrapping a short imperative task title only — not the full task sentence. Any supplementary detail MUST follow in plain-weight prose (conventionally after an em-dash), and the target file or directory SHOULD sit in a trailing <span class="path"> — where path is a layout/styling class exempt under P-2, not a semantic component subject to REQ-AUTHOR-001.

Styling for <spec-task> MUST live in assets/spec.css — not inline in the template. The generic <div class="task"> + class-span form is forbidden as a direct application of REQ-AUTHOR-001. A task-title-bold-scope validate rule SHOULD warn (not error) when a task row's leading <strong> both spans most of the row and the row carries supplementary detail beyond the title (bold continuing past the first em-dash, or the row exceeding a length floor) — the structural signature of a whole-line-bold row. A terse, detail-free title that legitimately fills its own row does not warn.

Rationale

The tasks artifact is regen-derived from a template, so the contract for its internal shape is worth being explicit about. Without a named element, a fresh authoring session falls back to whatever the template already shows — and a class-soup template propagates indefinitely. Codifying <spec-task> turns the implicit pattern into something a validator (or a careful reader) can check. The label-form clause is the same lesson one level down: the original requirement bounded the element's attributes but not its emphasis, so the template's <strong>[TASK]</strong> placeholder was read as "bold the whole task" and every tasks.html from 026 onward became a wall of bold (T-010). Bounding emphasis to a short title restores the title/detail scan the readable pre-026 rows had, and the warn-level rule keeps the drift from silently returning.

The lifecycle status of any artifact (spec, plan, tasks, principles, triage log, inbox) MUST evolve as a finite state machine over the six values named in REQ-LIFECYCLE-002. The allowed transitions are:

Draft → Accepted
Triggered when the last unchecked <input type="checkbox"> in the artifact's tasks.html is ticked and the author explicitly confirms the flip. /spectastic.implement MUST display a flip prompt at the last-tick that the author must explicitly confirm; the prompt MUST remind the author to verify the integration tests covering the Success Criteria pass before confirming. The command MUST NOT auto-flip status without explicit confirmation. The confirmation gesture absorbs the test-pass discipline; author judgment is the gate.
Draft → In Review
Author-initiated manual flip when soliciting reviewer feedback before the spec is locked. Reversible via In Review → Draft.
In Review → Accepted
Reviewer sign-off. The author flips after the review concludes, and MUST record the reviewer — a human — in the Reviewers field of the artifact's <spec-meta> and in the <spec-changelog> entry for this transition; the recorded identity is never an automated agent. The recording shape is the author's choice (a name, a handle, or both, the way Owner is written) — the contract is that a human reviewer is named, not the exact format. Artifacts that reach Accepted by author affirmation (the tasks-less path below) rather than through In Review have no separate reviewer, and this clause does not apply to them.
In Review → Draft
Author-initiated when revisions are needed in response to review.
Accepted → Superseded
Triggered when a successor artifact adds a <spec-note> in its header citing this artifact as the prior contract. The successor's author flips the predecessor's status to Superseded at the same time the forward-link lands. The predecessor's content is preserved as historical record.
Accepted → Deprecated
Terminal phase-out without a successor — the requirements described are being removed from the project's scope, not replaced. Manual flip; once Deprecated, no further transitions are allowed.
Any state → Blocked
Triggered by a triage card or an upstream-block signal (an external system down, a vendor bug, a contractual review pending). Reversible via Blocked → originating-state. The originating state is recorded in the artifact's <spec-changelog> at flip time.
Blocked → originating state
When the blocker resolves, the artifact returns to whatever state it was in when Blocked was entered. Recorded in <spec-changelog>.

For artifacts that are not a specs/<spec-id>/ spec slice (principles, the meta-spec itself, triage logs, inbox) — including when they carry an execution-only tasks.html tracker for folded change tasks per REQ-CHANGE-006 — the Draft → Accepted trigger is an explicit author affirmation that the artifact is the operative contract for the project; the execution tracker's checkboxes do not drive their status. The author records the affirmation as a one-line <spec-changelog> entry naming the date and the reason.

Transitions not in the list above are forbidden. In particular, a Superseded or Deprecated artifact MUST NOT transition to any other state — those are terminal. An Accepted artifact MUST NOT transition back to Draft or In Review; if amendments are needed, the path is /spectastic.propose against the live spec, not a status downgrade.

Every transition MUST append a one-line entry to the artifact's <spec-changelog> naming the old state, the new state, the date, and the triggering condition or gesture.

The three artifacts of a single spec slice — spec.html, plan.html, and tasks.html under specs/<spec-id>/ — MUST share a single bundled lifecycle status. When the spec.html status transitions per REQ-LIFECYCLE-004, the plan.html and tasks.html status MUST transition to the same value in the same gesture. One author confirmation per transition flips all three siblings; matching one-line <spec-changelog> entries MUST land on each artifact naming the old state, the new state, the date, and the triggering condition.

The bundle is the natural unit of "this spec slice." Splitting status across the three artifacts has no operational meaning — a spec.html cannot be Accepted while its plan.html is Draft without inviting drift. The bundle rule makes the natural relationship explicit and prevents the gap surfaced in T-002 of the meta-spec triage log, where nine sibling artifacts sat in Draft despite their parent specs being shipped.

The bundle status is a readiness affirmation, not a content lock. New ADRs, refined risks, additional tasks accrete inside the Accepted state without constituting a lifecycle transition — the bundle rule governs the status pill, not the artifact contents. A plan amendment that genuinely needs Accepted → In Review drags the whole bundle back to In Review, because the readiness affirmation no longer holds for any of the three siblings.

Cross-spec bundling is not implied: each spec slice has its own bundle; one slice's status never tracks another slice's. Artifacts outside a specs/<spec-id>/ slice — principles, the meta-spec, triage logs, inbox — keep their own author-affirmation trigger from REQ-LIFECYCLE-004 and are not part of any sibling bundle. Such an artifact MAY nonetheless carry a standalone tasks.html tracker for tasks folded from an applied proposal (per REQ-CHANGE-006); that tracker is execution-only — it does not pull the artifact into a status bundle.

/spectastic.implement's last-tick step MUST evaluate the bundle-trigger condition (zero remaining unchecked <input type="checkbox"> in the spec's tasks.html) after every tick taken while the spec's status is Draft, not only when the LLM heuristically recognizes "the last one." Scoping the predicate to the Draft state preserves REQ-LIFECYCLE-004's "last unchecked checkbox is ticked" transition semantics — once the bundle transitions out of Draft, a re-ticked box (a hotfix re-tick on an Accepted spec, an unticked-then-reticked manual gate) does not re-fire the bundled flip prompt. The deterministic evaluation closes the LLM-fragility failure mode where last-tick goes unnoticed when manual gates interleave with code tasks, without introducing a re-confirmation loop on already-flipped specs.

The /spectastic.plan procedure SHOULD ground every design-bearing fact against real source before its interview — opening the actual consuming code, the dependency's signature at the resolved lockfile version, and quantified platform constraints, not the file tree alone — and SHOULD record each fact in an evidence ledger as one of verified (opened this turn, with a cited source), spike (resolved by a time-boxed investigation run during planning, with its finding), or assumed (unverified).

Each <spec-decision> SHOULD declare its grounding and cite a verified or spike-resolved source in its Context; a decision that rests on an unverified assumption SHOULD render as a visible failure (the planning analogue of REQ-AUTHOR-001's render-broken-when-malformed discipline).

The gate is the binding clause: the plan MUST NOT be declared ready for /spectastic.tasks while a must-tier decision rests on an assumed or unresolved spike fact, unless the author has accepted it as a tracked <spec-risk> whose status the author commits (per REQ-CHANGE-004's author-owned-status model). This gate is a plan→tasks readiness affirmation, not a Draft content-lock — it mirrors the existing estimability gate, and pure-judgment decisions with no external fact are exempt.

Implementation surprises come from planning under unverified assumption. The grounding discipline ships as SHOULD — mirroring REQ-CHANGE-004, which shipped the adversarial pass as guidance from one data point rather than a blanket MUST that hollows into theater. The gate is the MUST that actually stops an ungrounded assumption from reaching implementation silently; lifting the /spectastic.explain "cite only confirmed source" discipline into planning makes "what the plan knows vs. assumes" structurally legible.

Before committing a diagnostic layer, /spectastic.triage SHOULD ladder the root cause against the regeneration test: starting from the candidate (lowest plausible) layer, ask "if I changed only this layer, would the regeneration test still fail?" — if the bug would recur, the owner is upstream, so step up (implementation → spec → cross-spec → principles) and re-ask. The ladder reuses the existing regeneration test — one probe, not a second analysis pass — so the card still reads in under 30 seconds.

The gate is the binding clause: a card MUST be classified at the lowest layer whose fix makes the regeneration test pass — neither lower (a fix that would recur — the symptom layer) nor higher (an honest implementation drift inflated past its real owner, against the No spec inflation discipline). That lowest-passing layer is "the highest layer that needed to change," stated as a procedure: the gate is bidirectional, so the ladder is not a one-way escalator. just-do and defer intake items skip the regeneration test and are exempt.

Rationale

The maxim had no step, so triage defaulted to the convenient layer: the no-open-questions defect (020 T-005) was classed at the presentation layer and reached cross-spec only on author pushback. The laddering discipline ships SHOULD — codifying from one data point, mirroring REQ-LIFECYCLE-006 / REQ-CHANGE-004 rather than a blanket MUST that hollows into theater. The gate is the MUST, and it is bidirectional: it stops under-classification (T-005) and over-escalation (spec inflation) with the same rule — stop at the lowest layer that holds.

Change management

Spec evolution MUST happen via change-proposal artifacts at specs/<spec-id>/changes/<YYYY-MM-DD>-<slug>/proposal.html. Each artifact MUST use the <spec-change> wrapper and contain at least one <spec-delta>.

Rationale

One proposal per discrete change, reviewable as a single file. The PR-shaped folder structure scopes review cleanly; folding intent / scope / approach / deltas / tasks into one document preserves spectastic's single-file principle.

Each <spec-delta> MUST carry an op attribute equal to one of added | modified | removed | renamed, and a target attribute naming the requirement ID it touches. For op="removed", the delta MUST also carry reason and migration fields — empty or missing renders visibly broken.

After /spectastic.apply lands a change, the command SHOULD surface the post-apply routing rule — where the user drives the follow-up implementation work — in both its documented output and its per-apply console report:

  • Small change (one or two requirements, behavioural addition, no new ADRs): the §6 tasks have been folded into the target's tasks.html as a new phase (per REQ-CHANGE-006); drive them with /spectastic.implement.
  • Large change (multi-requirement, architectural shift, new topic group): re-run /spectastic.plan against the updated spec to revisit ADRs, then /spectastic.tasks to derive a fresh breakdown — which regenerates tasks.html and supersedes the folded phase — then /spectastic.implement to drain it.

The boundary is fuzzy by design: if more than one new ADR would land, the change is large enough to warrant plan + tasks; otherwise the proposal's inline tasks are the breakdown. The rule is guidance, not a guardrail — apply MUST NOT refuse or auto-trigger plan/tasks based on its own classification.

Rationale

The propose template already encodes the small-change shortcut by hosting tasks inside the proposal artifact. The apply command's prose never names the resulting routing rule, so a fresh reader hits the fork unsignposted. Surfacing the rule turns implicit design into explicit guidance and prevents the lifecycle's reading order from leaving a hole between apply and the next implement.

Non-trivial proposals — those that touch a priority="must" requirement, contain an op="removed" delta, OR span two or more topic prefixes — SHOULD carry a <spec-risk-log> populated by an adversarial risk pass run during /spectastic.propose.

Each <spec-risk> MUST carry:

  • target= — a delta ID, requirement ID, or §<n> section anchor. Missing renders the visible label MISSING TARGET.
  • status= — one of identified | accepted | mitigated | rejected (or no-value-found when the critic agent self-reports nothing of value). Default identified.
  • by= — when status is accepted | mitigated | rejected, the human who dispositioned the finding (name · handle, the recording shape the author's choice); never an automated agent. It stays empty while identified. This is the source the Acked-by trailer reads (spec 027).

/spectastic.apply SHOULD refuse if any <spec-risk> has status="identified" — gating on the user-confirmed status field only. Apply MUST NOT re-run the heuristic, re-spawn the critic Agent, or transition statuses on its own; the status field is the user's commitment, and apply reads it. This is what distinguishes the gate from REQ-CHANGE-003's "apply MUST NOT refuse based on its own classification" — the risk-register gate refuses on user input, not apply-side judgment. The heuristic, the three-finding agent prompt, and the response discipline are owned by commands/spectastic.propose.md §8; the apply gate by commands/spectastic.apply.md's Preconditions.

Rationale

Spectastic's lifecycle had no step that forced the strongest counter-argument into the artifact, so first-draft proposals shipped without critical pushback. The risk pass closes that loop. The vocabulary borrows from ISO 31000's risk register — same lineage habit as ADR, INVEST, RFC 2119, and DORA already in the project. Priority should rather than must because we're codifying from one data point; re-evaluate after ≥5 worked applications. The by= dispositioner record makes design-time sign-off attributable and gives the Acked-by trailer a human source.

Items considered but decided against MUST be preserved as history, not deleted. The lifecycle SHOULD support rejection at both surfaces:

Surface A — Inbox cards (pre-propose). A <spec-triage> card in inbox.html MAY carry data-status="rejected" and a <dt>Rejected because</dt> row inside its <dl>. The card stays in inbox.html (mirrors the existing data-status="done" convention for just-do cards). CSS renders a REJECTED pill, muted body, and strikethrough title.

Surface B — Authored proposals (post-propose). /spectastic.apply SHOULD accept a withdrawal mode invoked as --withdraw <YYYY-MM-DD>-<slug> --reason="<one-line>". The mode:

  • Refuses if the proposal status is already applied or withdrawn.
  • Refuses if --reason is empty.
  • Flips status to withdrawn.
  • Moves the folder from specs/000-spectastic/changes/<YYYY-MM-DD>-<slug>/ to specs/000-spectastic/changes/withdrawn/<YYYY-MM-DD>-<slug>/ (a sibling of archive/, not nested), MUST creating changes/withdrawn/ if it does not yet exist (mirroring the archive-move obligation, REQ-CHANGE-007, so a spec's first withdraw does not ENOENT at the move step). The date-prefixed folder name is preserved in both terminal states (applied and withdrawn) per REQ-CHANGE-001.
  • Appends a <spec-changelog> entry to the live spec it targeted: "Considered <YYYY-MM-DD>-<slug>, withdrew on <DD Mon YYYY> because <reason>."
  • Appends a changelog entry to the moved proposal recording the withdrawal date and reason verbatim.

Withdraw is intended as terminal: there is no --unwithdraw command. If you withdrew by accident or under time pressure, restoring the folder and status manually is unsupported but not forbidden — git-revert the move and flip the status field. If your thinking has actually updated since the withdrawal, author a new proposal instead so the lineage stays legible. Implementation ownership: Surface A in commands/spectastic.triage.md; Surface B's procedure in commands/spectastic.apply.md's Withdraw procedure section.

Rationale

The <spec-status value="withdrawn"> vocabulary has existed since v0.1 but has had no workflow behind it — an authored proposal the author decided against would either sit in changes/<YYYY-MM-DD>-<slug>/ indefinitely or get manually deleted. Inbox cards had no terminal-rejected state for routed layers. The lifecycle had no way to record "considered, decided against." This requirement closes both gaps with one discipline — preserve, don't delete — and one apply-mode extension. The withdrawn-folder mkdir-if-absent (added here) is the create-the-destination-if-absent obligation REQ-CHANGE-006 (tracker) and REQ-CHANGE-007 (archive) also carry — placed with the operation it governs. Priority should rather than must because we're codifying from zero applications; re-evaluate after ≥3 worked rejections.

On /spectastic.apply, a proposal's §6 tasks MUST be folded into the target's tasks.html — specs/<id>/tasks.html for a spec, or the artifact's sibling tracker for the meta-spec / principles, created from templates/tasks.html if absent — as a new provenance-linked <spec-task> phase whose IDs continue the target's sequence. The provenance MUST link the archived proposal.

/spectastic.apply MUST NOT itself implement the tasks; /spectastic.implement drains the folded phase. The archived proposal §6 remains the frozen intent record and MUST NOT be ticked in place. This makes apply a uniform accept-and-route step for every target — never context-dependent about whether it implements.

Acceptance ≠ execution (a merge is not a deploy); a command must behave consistently (least astonishment); and accepted work belongs in a project's tracked task list, not the triage inbox. One execution surface per target, no hand-copy, archive intact.

The §6 task-fold mandated by REQ-CHANGE-006 MUST have a deterministic implementation in the apply kernel (it has none today). The fold MUST run on the §6 content apply has already read, before the archive-folder move, so a fold or fidelity failure leaves the proposal in changes/ for a clean retry rather than a half-applied state. The archive-folder move MUST create its destination parent (changes/archive/) if it does not yet exist, so a spec's first apply does not ENOENT at the move step — the same create-the-destination-if-absent obligation REQ-CHANGE-006 places on the tracker and REQ-CHANGE-005 on the withdrawn-folder move. When the kernel folds, it MUST confirm the resulting phase faithfully carries the §6 work — a <spec-task> for every §6 item, carrying over each item's <span class="path"> and, where the §6 item declares it (the [P] convention), its parallel marker, in the <spec-task> shape REQ-LIFECYCLE-003 defines — before reporting success. Mere presence of a phase is insufficient (presence is not containment). A missing or incomplete phase MUST be completed, not returned as success. An empty §6 owes no phase and is skipped per REQ-CHANGE-006.

This adds a kernel capability; it does not change which path performs the fold. The CLI apply path, which already calls the kernel, folds deterministically as a result. Bringing the slash-command path onto the kernel fold is a separate change (it re-architects the markdown-canonical boundary and has an API-key wiring question), tracked as TBD-route-fold-through-kernel and dependent on this one.

Rationale

REQ-CHANGE-006 specifies the fold as an action but defines no post-condition, and the action lives only in slash-command prose — apply.ts has no tasks.html code at all. So the one step that orphans real work when skipped is the one with no deterministic implementation: the 2026-06-25-spec-budget-bands failure (triage T-004). A fidelity check (not mere presence) is required because the fold is real format work and a present-but-wrong phase would otherwise pass — the project's own presence-is-not-containment lesson. A validate backstop was evaluated across three passes and rejected (it cannot know a fold was owed without the archived §6 it ignores). The move-creates-parent clause codifies triage T-007: the kernel's bare fs.rename ENOENT'd on 023's first apply (changes/archive/ absent), failing after the deltas, fold, and proposal-flip had committed — the one path that breaks the fold-before-move atomicity this requirement promises. Priority should, codifying from incidents, matching REQ-CHANGE-004 / REQ-CHANGE-005; re-evaluate after a few real applies.

The mechanical steps of /spectastic.apply — applying each <spec-delta>, the live-spec <spec-changelog> entry (the kernel MUST accept an author-supplied one-line summary, so the changelog's human voice is preserved rather than reduced to a delta count), the archive-folder move, the proposal status flip to applied, and the §6 task-fold (per REQ-CHANGE-006 / REQ-CHANGE-007) — MUST be performed by the apply kernel (spectastic apply, which is deterministic and requires no ANTHROPIC_API_KEY), not re-implemented in the slash-command markdown. The apply markdown MUST run the preconditions — including the REQ-CHANGE-004 risk gate, listing any status="identified" risks by target= — and surface failures before invoking the kernel; the kernel's own gate is a deterministic backstop, not the user-facing refusal. It MUST also confirm spectastic apply resolves before invoking it, surfacing a missing or stale binary clearly rather than failing silently. Beyond the preconditions, the markdown owns only the post-apply routing nudge (REQ-CHANGE-003) and the inbox-card nudge.

This is a deliberate, named exception to 006 FR-008 ("the markdown procedure remains the source of truth") and FR-009 ("slash commands MAY invoke the CLI but MUST NOT be required to") for apply: its mechanical steps are pure and deterministic, and their prose-only form was the T-004 failure. Those general rules continue to govern the six verbs that need LLM judgment.

The obligation is scoped to same-spec applies. A cross-spec delta (whose target is a requirement in another spec) is the one mechanical step the kernel does not yet perform and MAY remain markdown-handled until it does (TBD-kernel-cross-spec-apply).

Rationale

Apply's mechanical steps need no AI and the CLI runs key-free, so making the kernel authoritative for them removes the whole class of skipped-step bugs on the in-host path (T-004) without touching the verbs that need judgment. Hosted as a meta-spec requirement — not a MODIFY of 006 FR-009 — because a cross-spec delta could not be applied by the kernel this very requirement mandates, and because apply's contract already lives in REQ-CHANGE-*. Priority should: codifying apply's kernel-authoritative path from one incident, matching REQ-CHANGE-004 / REQ-CHANGE-007; re-evaluate after a few real applies.

Rendering

With JavaScript disabled, every section, requirement, tab panel, and details block MUST remain readable. JavaScript provides convenience (tabs, copy-link, conformance index, dark mode) but never content.

Print stylesheet MUST expand collapsed details, unhide tab panels, and remove interactive chrome. A printed spec is a complete spec.

Theming

The default theme SHOULD support a dark-mode toggle that flips a single html.dark class — no per-element overrides required.

The dark-mode palette MUST honor the warm-tone principle established by the light palette. Concretely: surface and background tokens MUST use warm dark greys (warm hue, brightness in the #1c–#28 range) and never pure black; border tokens MUST sit 4–8 luminance steps above their adjacent surface token and never be desaturated neutrals.

Rationale

The light palette intentionally rejects pure white and pure black for the same reason: warmth reads as considered, neutral tones read as undesigned. Dark mode should follow the same discipline, not stumble into cold defaults when a fresh contributor tweaks a token.

Tooling

Spectastic MUST ship eight Claude Code slash commands across the lifecycle — /spectastic.principles, /spectastic.spec, /spectastic.plan, /spectastic.tasks, /spectastic.implement, /spectastic.propose, /spectastic.apply, /spectastic.triage — that drive the templates without introducing a separate CLI. It MAY additionally ship extended, opt-in verbs upstream of or alongside the lifecycle (e.g. /spectastic.explain, /spectastic.explore); extended verbs are not required to ship, but any command spectastic does surface as a skill is bound by REQ-TOOL-004.

The /spectastic.implement command MUST default to one task per invocation. It MAY accept three opt-in drain modes that the user must type explicitly:

  • --all — drain every unchecked task in the resolved scope sequentially, pausing on first failure.
  • --phase=<id> — drain every unchecked task inside the named phase section (setup, foundation, us1, us2, us3, polish).
  • --parallel — within the resolved scope (default scope = one task; combinable with --all or --phase), spawn one Agent tool call per [P]-marked task; run non-[P] tasks in the main session.

Drain modes MUST NOT silently chain — failure pauses the drain and re-invocation is explicit. Each completed task MUST be reported individually (one line per ticked checkbox) so progress is visible mid-drain.

Rationale

One-per-invocation is the right default for contested or cross-spec work where each step is a judgment call. MVP-first solo drains do not match that shape — the user typed /goal as a workaround on 001-cli's 33-task list because the existing discipline rejected the obvious move. Making the drain opt-in preserves the default while removing the workaround.

6 · Decisions

Each card uses the ADR shape: status, context, decision, consequences. New decisions append; superseded decisions stay visible and link forward.

D-001 · Custom elements over <div class="…">

Status
Accepted
Context
Specs need a vocabulary. Class-based components (<div class="requirement">) require the reader to map invisible CSS rules to meaning. Custom elements (<spec-requirement>) put the schema in the tag.
Decision
Adopt custom elements as the canonical authoring surface for every spectastic component. Style them via element selectors only.
Consequences
+ Source is self-describing. + LLM edits target tags, not classes. + No naming collisions with host-page CSS. − Slightly higher floor for users who have only seen Bootstrap-style HTML.

D-002 · Inline assets at publish, link during dev

Status
Accepted
Context
Single-file is the goal. But during authoring, a 25 KB <style> block at the top of every file is annoying to scroll past.
Decision
Source files link to ../assets/spec.css and ../assets/spec.js. A trivial inliner produces the standalone artifact for publish, archive, or attach.
Consequences
+ Author experience stays clean. + DRY: one design system. − Two flavours of the same file exist; users must understand which to ship.

D-003 · Calm typographic defaults

Status
Accepted
Context
The default look matters more than any individual feature; it sets the tone of the whole spec ecosystem.
Decision
Adopt a warm cream surface (never pure white), crimson links, sea-blue accents, a serif / sans-serif / monospace trio (Fraunces, Source Serif 4, Lato, IBM Plex Mono), an 8 px spacing grid, and small-caps section labels. Optimise for long-form prose readability over decorative chrome.
Consequences
+ Out-of-box specs feel like considered documents, not Bootstrap pages. + Generous typography invites long-form prose. − Fonts pull from Google Fonts; offline use falls back to system serifs.

8 · Migrating a markdown spec

What changes in a typical spec.md → spec.html transition:

@@ Functional Requirements @@ ### FR-001 Users MUST be able to register with email + password. ### FR-002 Sessions MUST expire after 24h. <spec-requirement id="FR-001" priority="must"> <p>Users <spec-rule>MUST</spec-rule> be able to register with email + password.</p> </spec-requirement> <spec-requirement id="FR-002" priority="must"> <p>Sessions <spec-rule>MUST</spec-rule> expire after 24h.</p> </spec-requirement>

The diff is mechanical: heading + paragraph → component with stable ID and priority. A future /spectastic.migrate command can do this in bulk; v0.1 expects authors to do it once per spec by hand and amortize.

Keep the markdown spec next to the HTML one during transition. Both can be valid for a quarter while the team adapts.

9 · Open questions

  1. Inline-or-link. Is a single command (spectastic build) enough to manage the link/inline duality, or should the source files inline a smaller "boot" stylesheet that imports the full one — keeping single-file truly single?
  2. Versioning the design system. If the CSS changes, do old specs need re-inlining? Adopt semver on the design system and lock per-spec via a header attribute?
  3. Bidirectional spec ⇄ tasks. Should completing a task automatically tick its source requirement, or stay a one-way link? Spec-kit's gap.
  4. Diagrams. Mermaid? Excalidraw export? Or stick to hand-written SVG and a prompt that produces it well?
  5. Collab. What's the review surface — GitHub PR with a rendered preview, or a dedicated viewer that supports inline comments anchored to id attributes?
