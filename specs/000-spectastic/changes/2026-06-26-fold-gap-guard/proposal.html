Make the task-fold deterministic

Under review

1 · Intent

REQ-CHANGE-006 makes /spectastic.apply fold a proposal's §6 tasks into the target's tasks.html as a provenance-linked phase. But it specifies the fold only as something apply does, with no post-condition — and crucially, the fold today is implemented only in the slash-command markdown (step 8). The apply kernel folds the <spec-delta> blocks, writes the changelog, and archives the folder, but has zero code touching tasks.html. So the one mechanical step that orphans real work when skipped is exactly the step with no deterministic implementation.

That is why 2026-06-25-spec-budget-bands failed (triage T-004): an LLM apply run skipped a prose step, the deltas folded, the folder archived, the status read applied, and eight tasks were orphaned with a fabricated citation still shipping — nothing detectably wrong. A self-check written into the same prose would be no stronger: the run that skips the fold is the run that skips checking it (the point an adversarial pass made against three earlier drafts of this change).

The durable fix is to stop depending on prose adherence for a mechanical step. The fold needs no AI judgment — it transcribes §6 list items into <spec-task> elements. So put it in the kernel, make the kernel verify the phase landed, and route both apply paths through it. The guarantee then holds by construction, on the path that actually failed.

2 · Scope

In scope

  • ADD REQ-CHANGE-007: the §6 fold MUST be performed by the apply kernel (deterministic code), the kernel MUST confirm the new provenance-linked phase is present before returning success, and both the slash-command and CLI apply paths MUST route the fold through the kernel.
  • Implementing the fold in packages/core/src/commands/apply.ts (it does not exist there today), and narrowing the slash-command step 8 to invoke it rather than transcribe §6 in prose.

Out of scope

  • A spectastic validate "fold-gap" rule. Evaluated across three adversarial passes and rejected as unsound: a validate rule reads only in-set artifacts, but the "a fold was owed" signal lives in the archived §6 that validate ignores — so it can only check self-consistency, which misses a wholesale skip and risks false-positives. Recorded so it is not re-proposed.
  • Moving the interactive parts of apply into the kernel. Precondition and risk-gate decisions, and the apply report, stay in the markdown procedure; only the mechanical §6 fold becomes kernel-authoritative.
  • Verifying other apply steps. Only the fold has a checkable present/absent artifact; the archive move and status flip are self-evident from the folder location and the status pill.

3 · Approach

Move the fold into the kernel. Today apply.ts handles deltas, changelog, and the archive move, but nothing for tasks.html; the §6 fold is hand-described in spectastic.apply.md step 8. This change adds a deterministic fold to the kernel: parse the applied proposal's §6 list, resolve-or-create the target tracker from templates/tasks.html, append a provenance-linked <spec-task> phase with ID-continuation per REQ-CHANGE-006, and — the post-condition — re-read the tracker to confirm the phase is present before returning success, completing it if absent. Because the fold is now code, the verify is trivially deterministic in the same function.

Route both paths through it. The CLI path already calls the kernel, so it inherits the fold and its check for free. The slash-command path is narrowed: step 8 stops transcribing §6 in prose and instead invokes the kernel fold (directly, or via spectastic apply), then reports the verified result. This closes the T-004 path — the guarantee no longer rides on the LLM executing a prose step.

The one tension, named. REQ-CHANGE-006's lineage (006) holds that "the markdown procedure remains the source of truth the LLM reads." Making the kernel authoritative for the fold is a deliberate, narrow exception: the fold is purely mechanical (no AI judgment), and its prose-only form is precisely what a non-deterministic run skipped. The markdown stays canonical for everything that needs judgment (preconditions, the risk gate, the report); only this one transcription step moves to code, where it belongs. The §6 task list owns reconciling the docblock/canonical note accordingly.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec; op= is one of added | modified | removed | renamed.

The §6 task-fold mandated by REQ-CHANGE-006 MUST be performed by the apply kernel as deterministic code — not by LLM-authored prose alone — and the kernel MUST confirm the new provenance-linked phase is present in the target tracker before returning the apply successful. When §6 carries tasks and the phase is absent, the kernel MUST complete the fold rather than return success; it MUST NOT leave a half-applied state. An empty §6 owes no phase and is skipped per REQ-CHANGE-006.

Both apply paths MUST route the §6 fold through the kernel: the CLI already calls it, and the slash-command procedure MUST invoke the kernel fold rather than transcribe §6 in prose — so the post-condition holds regardless of LLM adherence (the path that failed in T-004).

This is a deliberate, narrow exception to the rule that the markdown procedure is the LLM's source of truth (006): the fold is purely mechanical and needs no AI judgment, so it is kernel-authoritative; the interactive parts of apply (preconditions, risk gate, report) remain markdown-canonical.

Rationale

REQ-CHANGE-006 specifies the fold as an action but defines no post-condition, and the action lives only in slash-command prose — apply.ts has no tasks.html code at all. So the one step that orphans real work when skipped is the one with no deterministic implementation, which is the 2026-06-25-spec-budget-bands failure (triage T-004). A self-check in the same prose is no stronger — the run that skips the fold skips the check. Putting the fold (and thus its verify) in the kernel makes the guarantee hold by construction on both paths. A validate backstop was evaluated across three passes and rejected: it cannot know a fold was owed without the archived §6 it ignores. Priority should, codifying from one incident, matching REQ-CHANGE-004 / REQ-CHANGE-005; re-evaluate after a few real applies.

5 · Risk register

The adversarial pass ran (opt-in --adversarial; the change touches the must-tier change-management family REQ-CHANGE-006 governs). Findings below; each MUST reach accepted, mitigated, or rejected before apply.

Too broad for one should requirement: REQ-CHANGE-007 fuses three independently-contestable commitments — build the kernel fold, make it self-verify, and re-route both apply paths through it — so the clearly-correct half (kernel owns + verifies the fold, which closes T-004 alone) is held hostage to the contestable half (re-architecting the slash command's relationship to the kernel).

"the §6 fold MUST be performed by the apply kernel … and both the slash-command and CLI apply paths MUST route the fold through the kernel."

Draft (status is the author's to set). The strongest structural critique, and it lands. Recommend splitting: land "the kernel owns and verifies the §6 fold" as REQ-CHANGE-007 now (deterministic, closes T-004 on the CLI path and gives the slash path something real to call); track "route the slash-command fold through the kernel" as a sibling change. The split also isolates a genuine wiring question that deserves its own review: the slash command runs in-host with no API key, while the AI-coupled spectastic apply CLI requires ANTHROPIC_API_KEY — so the slash path needs a non-AI way to invoke the kernel fold, which the current draft waves at ("directly, or via spectastic apply"). Disposition: split, or accept the broader scope knowingly.

A should-tier requirement carves a piece of a must-tier action (REQ-CHANGE-006's indivisible fold) into code and leaves the rest prose-owned, but records the new boundary only by asserting a "narrow exception" and deferring reconciliation to an implementation task — so ownership of the fold's contract becomes split and undefined.

"This is a deliberate, narrow exception to the rule that the markdown procedure is the LLM's source of truth (006)" + §3's "The §6 task list owns reconciling the docblock/canonical note accordingly."

Draft (status is the author's to set). Fair — the seam can't live in a task checkbox. Fix: REQ-CHANGE-007 must state the boundary in the requirement (kernel owns the mechanical fold; markdown owns preconditions, risk gate, and the report), not defer it. Whether to additionally MODIFY REQ-CHANGE-006 / 006 FR-008 to record the carve-out (a second delta) or let -007 own it explicitly is a disposition choice; recommend -007 owns it with the boundary named, avoiding a second delta. Either way the "defer to a task" language goes.

The premise that the fold "needs no AI judgment" and is "purely mechanical" is overstated, and the post-condition only checks a phase is present, not that it faithfully transcribes §6 — the project's own "presence is not containment" trap (CLAUDE.md, P-7).

"the fold is purely mechanical (no AI judgment) … re-read the tracker to confirm the phase is present."

Draft (status is the author's to set). Partly. The decision-making is mechanical (which items, ID continuation, tracker location — and the tracker-location worry the critic raised is resolved by the meta-spec migration: it is now the normal specs/000-spectastic/tasks.html). But the format work is real (parse free-form §6 <li>, preserve parallel + path spans, create-from-template, hundred-range IDs), and a present-but-wrong phase satisfies "a phase is present." Fix folded into the contract: the post-condition MUST confirm the phase carries a <spec-task> for every §6 item (fidelity, not presence), and the kernel fold MUST be tested for transcription fidelity — not assumed mechanical.

7 · Open questions

  1. Split this change, or land it whole? The fifth adversarial pass (§5) argues REQ-CHANGE-007 bundles two things: the safe, clearly-correct "kernel owns and verifies the §6 fold" (closes T-004 by itself) and the contestable "route the slash-command fold through the kernel" (re-architects a must-tier action's ownership, and carries a real API-key wiring question — the in-host slash path has no key, the AI-coupled CLI needs one). Decide: split (land the kernel-fold half now, track routing separately) or keep whole. Two refinements apply in either shape and are not in question — the post-condition checks fidelity not just presence (§5 R-3), and the kernel/markdown boundary is stated in the requirement rather than deferred to a task (§5 R-2). The validate backstop stays rejected and recorded (§2); priority should; empty-§6 carve-out inherited from REQ-CHANGE-006.
