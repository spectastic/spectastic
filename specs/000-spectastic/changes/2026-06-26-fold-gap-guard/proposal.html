Fold §6 in the apply kernel

Under review

1 · Intent

REQ-CHANGE-006 makes /spectastic.apply fold a proposal's §6 tasks into the target's tasks.html as a provenance-linked phase. But it specifies the fold only as an action, and that action is implemented only in the slash-command markdown (step 8). The apply kernel folds the <spec-delta> blocks, writes the changelog, and archives the folder, but has zero code touching tasks.html. So the one mechanical step that orphans real work when skipped is exactly the step with no deterministic implementation — which is why 2026-06-25-spec-budget-bands failed (triage T-004): an LLM run skipped a prose step, and nothing was detectably wrong.

The foundation for fixing that is a deterministic fold. The §6 fold needs no AI judgment — which items, ID continuation, where the tracker lives are all determined — but it is real format work (parse free-form §6 <li>, preserve parallel markers and path spans, create-the-tracker-from-template, continue IDs in a fresh hundred-range). So it belongs in code, with a post-condition that checks the result is faithful, not merely present. This change builds and verifies that kernel fold; the CLI apply path picks it up at once. Routing the in-host slash-command path through it — the path that actually failed — is the natural next step, but it re-architects how the slash command relates to the kernel and carries its own wiring question (the in-host path has no API key; the AI-coupled CLI requires one), so it is a separate, sibling change rather than riding this one.

2 · Scope

In scope

  • ADD REQ-CHANGE-007: the §6 fold MUST be implemented in the apply kernel as deterministic code, and the kernel MUST confirm the folded phase faithfully carries the §6 work (a <spec-task> for every item, preserving parallel markers and paths) before returning success.
  • The kernel implementation in packages/core/src/commands/apply.ts (none exists today) and its tests. The CLI apply path, which already calls the kernel, thereby folds deterministically.

Out of scope

  • Routing the slash-command apply path through the kernel fold (so it stops transcribing §6 in prose). That re-architects a must-tier action's ownership and carries an API-key wiring question (in-host slash path has no key; the AI-coupled CLI requires one) — it gets its own proposal (scaffolded), which depends on the kernel fold this change builds.
  • A spectastic validate "fold-gap" rule. Evaluated across three adversarial passes and rejected as unsound: a validate rule reads only in-set artifacts, but the "a fold was owed" signal lives in the archived §6 that validate ignores. Recorded so it is not re-proposed.
  • Verifying other apply steps. Only the fold has a checkable present/absent artifact; the archive move and status flip are self-evident from the folder location and the status pill.

3 · Approach

Add the fold to the kernel, checked for fidelity. Today apply.ts handles deltas, changelog, and the archive move; the §6 fold is hand-described in spectastic.apply.md step 8. This change adds a deterministic kernel fold: parse the applied proposal's §6 list, resolve-or-create the target tracker from templates/tasks.html (strip placeholder phases, rewrite asset paths for depth), append a provenance-linked <spec-task> phase with ID-continuation per REQ-CHANGE-006, and — the post-condition — confirm the phase carries a <spec-task> for every §6 item (presence is not containment, per CLAUDE.md and P-7), completing it if any are missing before returning success.

Why this is the safe half to land first. The fifth adversarial pass on the bundled version showed it was really two changes; this is the half with no contestable boundary: it only adds a kernel capability, so the CLI apply path (which already calls the kernel) folds correctly for the first time, and the slash command is untouched — it keeps its prose fold until the sibling change routes it onto this kernel one. No ownership seam is opened here (REQ-CHANGE-006's "markdown is canonical" rule still holds for the slash path); that question moves with the routing change. The transitional cost is that the two paths fold via different code for one cycle — acceptable, because the kernel fold is tested for fidelity against the same shape the prose produces.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec; op= is one of added | modified | removed | renamed.

The §6 task-fold mandated by REQ-CHANGE-006 MUST have a deterministic implementation in the apply kernel (it has none today). The fold MUST run on the §6 content apply has already read, before the archive-folder move, so a fold or fidelity failure leaves the proposal in changes/ for a clean retry rather than a half-applied state. When the kernel folds, it MUST confirm the resulting phase faithfully carries the §6 work — a <spec-task> for every §6 item, carrying over each item's <span class="path"> and, where the §6 item declares it (the [P] convention), its parallel marker, in the <spec-task> shape REQ-LIFECYCLE-003 defines — before reporting success. Mere presence of a phase is insufficient (presence is not containment). A missing or incomplete phase MUST be completed, not returned as success. An empty §6 owes no phase and is skipped per REQ-CHANGE-006.

This adds a kernel capability; it does not change which path performs the fold. The CLI apply path, which already calls the kernel, folds deterministically as a result. Bringing the slash-command path onto the kernel fold is a separate change (it re-architects the markdown-canonical boundary and has an API-key wiring question), tracked as TBD-route-fold-through-kernel and dependent on this one.

Rationale

REQ-CHANGE-006 specifies the fold as an action but defines no post-condition, and the action lives only in slash-command prose — apply.ts has no tasks.html code at all. So the one step that orphans real work when skipped is the one with no deterministic implementation: the 2026-06-25-spec-budget-bands failure (triage T-004). A fidelity check (not mere presence) is required because the fold is real format work and a present-but-wrong phase would otherwise pass — the project's own presence-is-not-containment lesson. A validate backstop was evaluated across three passes and rejected (it cannot know a fold was owed without the archived §6 it ignores). Priority should, codifying from one incident, matching REQ-CHANGE-004 / REQ-CHANGE-005; re-evaluate after a few real applies.

5 · Risk register

The adversarial pass ran (opt-in --adversarial; the change touches the must-tier change-management family REQ-CHANGE-006 governs). Findings below; each MUST reach accepted, mitigated, or rejected before apply.

The kernel today archives the proposal folder (fs.rename) and returns with no tasks.html work, so a fold-and-verify bolted on "before returning success" would run after the irreversible archive move — the opposite of the "no half-applied state" the requirement promises, and it can't re-read §6 from changes/ because the proposal is already in archive/.

apply.ts: "await fs.rename(proposalDir, archiveDir); return {…}" vs the delta's "MUST NOT leave a half-applied state".

Draft (status is the author's to set). Caught a real sequencing gap. The requirement now states it: the fold runs on the §6 apply has already read (in memory) and is sequenced before the archive fs.rename, so a fold/fidelity failure leaves the proposal in changes/ for a clean retry — atomic, no archived-but-unfolded state. §6 task 1 names the sequencing. This is a small re-order of the existing flow, not the must-tier boundary change the split deferred.

"Preserving each item's parallel marker" presumes §6 items already carry one, but proposal §6 lists are bare <li> with no parallel attribute — so a "parallel preserved" check passes trivially (none→none) while the fold may never emit a parallel task, under-honouring REQ-LIFECYCLE-003's required <spec-task> shape.

"preserving each item's parallel marker" vs REQ-LIFECYCLE-003: "parallel (boolean attribute) — present when the task can run alongside its in-flight peers (the existing [P] convention)".

Draft (status is the author's to set). Right — parallel is carried over from the §6 author's [P] marking, not transcribed from an attribute. Reworded: the fidelity check confirms a <spec-task> per §6 item carrying its path and, where the §6 item declares [P], its parallel marker, in the shape REQ-LIFECYCLE-003 defines. The fold transcribes the author's parallelism call; it does not invent it. Testable on count, path, and [P]-carry.

The kernel fold ships exercised only by the CLI path and its own tests, while T-004's actual path (the in-host slash command) keeps prose-folding — so the change risks reading as "T-004 fixed" when the failing path is untouched, and the two fold implementations could drift with no test asserting they agree.

In-scope "the CLI apply path … thereby folds deterministically" paired with out-of-scope defer-to="TBD-route-fold-through-kernel".

Draft (status is the author's to set). Honest and now reflected in the copy: the tldr and changelog say foundation, not fix — this builds the deterministic fold the fix depends on and does not by itself prevent T-004's in-host path. The drift concern is real for one cycle; the sibling change retires the prose fold entirely, and until then the kernel fold's fidelity tests pin it to the same shape the prose produces. Accepted as the cost of small-batching; the alternative (the bundled version) is what the fifth pass rejected.
