Closes meta-spec triage T-005. REQ-CHANGE-006 mandates that apply fold a proposal's §6 into the target's tasks.html, but defines the fold as an action with no checkable post-condition. When the 2026-06-25-spec-budget-bands apply skipped it (triage T-004), eight tasks were orphaned and a fabricated citation kept shipping — nothing was in a detectably-wrong state. Detect a skipped task-fold

Under review

1 · Intent

REQ-CHANGE-006 makes /spectastic.apply a uniform accept-and-route step: it folds a proposal's §6 tasks into the target's tasks.html as a provenance-linked phase, and /spectastic.implement drains them. But the requirement specifies the fold only as something apply does — there is no post-condition a later check can test. So when an apply run omits the fold, the corpus contains no malformed artifact: the deltas are in the spec, the folder is in archive/, the status reads applied. Everything looks done.

That is exactly what happened on 26 Jun 2026 with 2026-06-25-spec-budget-bands (meta-spec triage T-004): the deltas folded, the folder archived, but the §6 task-fold was skipped. Eight implementation tasks were orphaned and a fabricated "Larson" citation kept shipping in assets/spec.js until a human asked where the work went. The failure was invisible because nothing verifies that an applied proposal was actually folded.

The verification must work within the engine as it really is: spectastic validate default-ignores **/archive/** and **/withdrawn/** (archived proposals copy stable IDs and would trip no-duplicate-ids), so a guard cannot inspect the archived proposal at all. The signal it can reach is the pair already in the validated set: the live spec's <spec-changelog> and its tracker.

2 · Scope

In scope

  • ADD REQ-CHANGE-007 — a checkable post-condition for the REQ-CHANGE-006 fold, enforced at two points: (a) apply confirms the folded phase is present before reporting success and records the fold (or explicit no-fold) in the target spec's <spec-changelog>; (b) spectastic validate raises an error when a recorded fold has no matching tracker phase.
  • The requirement contract for both points. The apply-command change, the fold-gap validate rule, its fixtures, and a docs cross-reference are the §6 tasks, drained by /spectastic.implement.

Out of scope

  • Inspecting the archived proposal. validate ignores **/archive/** by design; the guard reads only the live spec changelog and the tracker, both already in the validated set.
  • Generalising to "verify every apply step". Only the fold has a checkable present/absent artifact (a phase in the tracker); the archive move and the status flip are self-evident from the folder location and the status pill.

3 · Approach

Record, then verify. The reason a skipped fold is silent is that no in-set artifact claims the fold should exist. So apply gains a small obligation: when it folds, it appends the fold to the target spec's <spec-changelog> (naming the tracker phase it wrote); when a proposal legitimately produces no fold — an empty §6, or a large change whose re-plan regenerated tasks.html and superseded the phase (REQ-CHANGE-003) — it records that no phase was folded. Either way the changelog now states the expected post-condition, in the validated set, in plain sight.

Two enforcement points, defense in depth. Point (a) is an apply-time self-check: apply confirms the phase landed before declaring success, catching the omission the moment it would happen. But the T-004 failure mode is precisely that the apply run itself skipped a step — a self-check the same run also skips is no guarantee. So point (b) is the after-the-fact backstop: a fold-gap cross-file validate rule that, for each fold a live spec's changelog records, asserts the target tracker carries the matching phase — and never flags an apply that recorded no fold. It is the same live-comparison shape as verify-view-stale (re-derive the expected set from one in-set artifact, compare to another; no stored fingerprint, no archived input). One delta (REQ-CHANGE-007, priority should, matching REQ-CHANGE-004 / REQ-CHANGE-005); the mechanics are §6 tasks.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec; op= is one of added | modified | removed | renamed.

The fold mandated by REQ-CHANGE-006 MUST carry a checkable post-condition, enforced at two points — neither of which reads the archived proposal (spectastic validate default-ignores changes/archive/), so both operate only on artifacts in the validated set.

(a) At apply time. When /spectastic.apply folds a proposal's §6, it MUST confirm the new provenance-linked phase is present in the target tracker before reporting success, and MUST record the fold in the target spec's <spec-changelog>, naming the tracker phase it wrote. A proposal that legitimately produces no fold — an empty §6, or a large change whose re-plan regenerated tasks.html and superseded the phase per REQ-CHANGE-003 — MUST instead record that no phase was folded, so the absence is intentional and legible.

(b) After the fact. spectastic validate SHOULD enforce the post-condition: it MUST raise an error-severity finding when a live spec's <spec-changelog> records a fold for which the target tracker carries no matching folded phase (a fold-gap cross-file check over the live spec + its tracker, both in the validated set). The check MUST NOT depend on the archived proposal, and MUST NOT flag an apply that recorded no fold.

The post-condition is scoped to the fold alone: it MUST NOT attempt to verify other apply steps (the archive move and the status flip are self-evident from the folder location and the status pill).

Rationale

REQ-CHANGE-006 specifies the fold as an action but defines no checkable post-condition, so a skipped fold leaves the corpus looking complete while the work is orphaned — the 2026-06-25-spec-budget-bands failure (triage T-004). The two points are deliberate defense in depth: apply's self-check catches the common case at write time, and the validate backstop catches the case that actually bit — an apply run that skipped the step (and would skip its own self-check too). Both read only the live spec changelog and the tracker, because validate cannot see the archived proposal. Recording the fold in the changelog is what lets the rule tell a skipped fold from a legitimate no-fold apply without false positives. Error severity (not warning) because an unrecorded-but-expected fold means real work was silently dropped — a correctness gap like verify-view-stale. Priority should because we codify from one incident; re-evaluate after it has proven itself against a few real applies.

5 · Risk register

The adversarial pass ran (opt-in --adversarial; the change touches the must-tier change-management family REQ-CHANGE-006 governs). Three findings; each MUST reach accepted, mitigated, or rejected before apply.

Decisive feasibility gap: the canonical validated set contains specs/000-spectastic/spec.html but not specs/000-spectastic/tasks.html (no glob matches it), so the rule's two inputs never co-occur for the meta-spec — the exact spec where T-004 happened. The "no glob change needed" claim is wrong.

§6 task 3: "the live spec and its tracker are normally both validated, so no glob change is needed" — vs integration.test.ts PATTERNS = [principles.html, plan.html, inbox.html, index.html, specs/000-spectastic/spec.html, examples/triage-log.html, specs/**/*.html] — none match specs/000-spectastic/tasks.html.

Draft (status is the author's to set). Confirmed on disk. verify-view-stale only works because specs/**/*.html sweeps each slice's spec+tasks together; the meta-spec's tracker sits outside specs/, so the analogy breaks for 000 specifically. Concrete fix: add examples/*-tasks.html (and principles-tasks.html) to the canonical set — safe, since trackers don't copy stable IDs, so no no-duplicate-ids interaction. But that is the glob change the scope ruled out; it must move into scope and §6. Same infeasibility shape as the withdrawn first draft, re-expressed against the tracker.

The "record an explicit no-fold line" obligation is itself an unverifiable honor-system step: an apply run that skips writing any changelog line is indistinguishable from a legitimate no-fold to the rule, so the silent gap is moved one level up rather than closed.

"A proposal that legitimately produces no fold … MUST instead record that no phase was folded" — the rule fires only on recorded folds, so a missing record (the T-004 failure mode) yields zero findings.

Draft (status is the author's to set). Real, and partly inherent. After-the-fact detection needs an independent signal that "a fold was owed" — but the only artifact that knows §6 was non-empty is the proposal, which validate ignores. So a guard that reads only in-set artifacts cannot catch a wholesale skip (no phase, no line); it can only catch a recorded-but-unfulfilled fold and apply's own self-check (point a). That is a bounded guarantee, strictly better than today but not the "fully detectable" the intent implies. The requirement should state the bound honestly, or accept that apply-time self-verify (point a) is the real guarantee and validate is a secondary net.

The rule raises a hard error on the large-change path REQ-CHANGE-003 blesses: apply folds a phase (writes a fold line), then a later /plan+/tasks regenerates the tracker and supersedes that phase — leaving a fold line whose phase no longer exists, which fold-gap flags as error.

REQ-CHANGE-003: "regenerates tasks.html and supersedes the folded phase" — the no-fold escape hatch only covers "apply produced no fold", not "a later re-plan removed a real fold".

Draft (status is the author's to set). Genuine false-positive path. Apply can't know at fold-time that a change will later be re-planned, so it correctly writes a fold line; the supersession happens later and decoupled. Mitigation: the contract must cover the re-plan path too — /spectastic.tasks regeneration MUST append a "superseded fold <slug>" changelog line that the rule treats as clearing the obligation. That widens the change beyond apply, into the tasks verb — a real scope question, currently unaddressed.

7 · Open questions

  1. What does REQ-CHANGE-007 actually promise — full or bounded detection? The adversarial pass (§5) shows a validate guard reading only in-set artifacts cannot catch a wholesale skip (no phase + no changelog line), because the only artifact that knows a fold was owed is the archived proposal, which validate ignores. So the achievable guarantee is bounded: apply-time self-verify (point a) catches the common case; validate catches recorded-but-unfulfilled folds, not silent skips. Decide whether to (i) ship the bounded guarantee and state it honestly, (ii) make apply-time self-verify the primary guarantee and demote validate to a secondary net, or (iii) reconsider whether validate is the right enforcement layer at all.
  2. Does the change extend beyond apply? Closing the §5 risks pulls in scope the current draft excludes: adding examples/*-tasks.html to the canonical validated set (R-1), and a "superseded fold" changelog line written by /spectastic.tasks regeneration to avoid false-positives on the REQ-CHANGE-003 large-change path (R-3). Confirm whether REQ-CHANGE-007 should own those, or whether they split into sibling changes.
