Change proposal · 000-spectastic

Verify the task-fold at apply time

REQ-CHANGE-006 makes apply fold a proposal's §6 tasks, but never says apply must check it did. Make apply confirm the phase landed before it reports success — the one place that knows a fold is owed.

Status Under review Change ID 2026-06-26-fold-gap-guard Spec 000-spectastic (meta-spec) Author Brian Corbin · @briancorbinxyz Created 2026-06-26 Targets 1 requirement (1 added) Read time

Closes meta-spec triage T-005. REQ-CHANGE-006 mandates the fold as an action with no checkable post-condition, so when the 2026-06-25-spec-budget-bands apply skipped it (triage T-004), nothing was detectably wrong. This change ADDs REQ-CHANGE-007: when apply folds a proposal's §6, it MUST confirm the phase is present in the target tracker before reporting success. Apply is the only actor that can see §6, so it is the only one that can know a fold is owed — which is exactly why the guarantee lives at apply time and not in validate (see §3; a validate backstop was evaluated and rejected as unsound). One requirement, one verb, no new validate machinery.

Verify the task-fold at apply time

Under review

1 · Intent

REQ-CHANGE-006 makes /spectastic.apply a uniform accept-and-route step: it folds a proposal's §6 tasks into the target's tasks.html as a provenance-linked phase, and /spectastic.implement drains them. But the requirement specifies the fold only as something apply does — there is no post-condition a later step can test. So when an apply run omits the fold, the corpus contains no malformed artifact: the deltas are in the spec, the folder is in archive/, the status reads applied. Everything looks done.

That is exactly what happened on 26 Jun 2026 with 2026-06-25-spec-budget-bands (meta-spec triage T-004): the deltas folded, the folder archived, but the §6 task-fold was skipped. Eight implementation tasks were orphaned and a fabricated "Larson" citation kept shipping in assets/spec.js until a human asked where the work went.

The fix has to live where the knowledge is. The fact that a fold is owed exists in exactly one place: the proposal's §6 — which only /spectastic.apply reads, and only while it applies. So apply is the sole actor that can verify the fold against ground truth. An after-the-fact check cannot: spectastic validate default-ignores changes/archive/, so it can never see the §6 that would tell it a fold was due (§3 records why a validate backstop was tried and dropped).

2 · Scope

In scope

  • ADD REQ-CHANGE-007: when apply folds a proposal's §6, it MUST confirm the new provenance-linked phase is present in the target tracker before reporting the apply successful; a missing phase when §6 carried tasks MUST fail loudly rather than report success.
  • The apply implementation of that post-condition (the verify sub-step and its failure surface).

Out of scope

  • A spectastic validate "fold-gap" rule. Evaluated across three adversarial passes and rejected as unsound (§3): a validate rule reads only in-set artifacts, and the "a fold was owed" signal lives in the archived §6 that validate ignores — so any such rule either misses the real skip or false-positives on legitimate no-fold applies. Recorded here so it is not re-proposed.
  • Changing when apply folds. REQ-CHANGE-006 already governs that (always, except an empty §6); this change only makes apply check the fold it was already required to perform.
  • Verifying other apply steps. Only the fold has a checkable present/absent artifact; the archive move and the status flip are self-evident from the folder location and the status pill.

3 · Approach

Put the guarantee where the knowledge is. When apply folds, it is holding the proposal's §6 — so it knows, with no inference, whether a fold is owed and what phase it just wrote. The post-condition is therefore a self-check apply performs at the end of its fold step: re-read the target tracker, confirm the new phase (the one it just appended, linking this proposal) is present, and only then report success — completing the fold if its first attempt left the phase absent. In the apply kernel (apply.ts) this is a deterministic guarantee. On the LLM-driven slash-command path — the one that actually failed in T-004 — it is a self-check by the same run that did the fold, so it is only as strong as that run's adherence; the honest read (§5) is that the durable hardening for that path is to perform the fold through the kernel, so the same deterministic check covers it. This proposal documents and enforces the post-condition; routing the slash path through the kernel is the recommended follow-up.

Why not a validate backstop (the part that was cut). The first three drafts of this change each tried to add an after-the-fact fold-gap validate rule; each failed an adversarial pass for the same underlying reason, worth recording so it is not retried: (1) keying on the archived proposal — validate default-ignores changes/archive/; (2) keying on the meta-spec tracker — at the time it was in no validated glob; (3) keying on a tracker "fold announcement" in its changelog — apply (spectastic.apply.md step 8) writes only the phase <section>, never a tracker changelog entry, so the rule had no producer. The root cause is invariant: a validate rule cannot know a fold was owed without the archived §6, so it can only ever check self-consistency — which misses a wholesale skip (the actual T-004 case) and risks false-positives. Apply self-verify has none of these problems, so it is the whole change.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec; op= is one of added | modified | removed | renamed.

When /spectastic.apply folds a proposal's §6 into the target's tasks.html (per REQ-CHANGE-006), it MUST confirm the new provenance-linked phase is present in the target tracker before reporting the apply successful. Because apply holds the §6 it is applying, it knows whether a fold is owed: when §6 carries tasks, apply MUST NOT report success until the phase is present — completing the fold itself if a missing phase is detected (it still holds §6), rather than aborting after the deltas, archive move, and status flip have already committed (apply steps 4–7). The remedy for a missing fold is to finish it, not to fail into a half-applied state. An empty §6 owes no phase and is already skipped by REQ-CHANGE-006.

This is a post-condition on a step REQ-CHANGE-006 already requires — it does not change when apply folds, only that apply verifies it folded. It is owned at apply time by design: the signal that a fold is owed (the proposal's §6) is visible only to apply, so an after-the-fact spectastic validate rule MUST NOT be relied on for this guarantee (it cannot read the archived §6).

Rationale

REQ-CHANGE-006 specifies the fold as an action but defines no checkable post-condition, so a skipped fold leaves the corpus looking complete while the work is orphaned — the 2026-06-25-spec-budget-bands failure (triage T-004). The guarantee belongs at apply time because apply is the only actor that can see §6 and thus know a fold is owed; a validate backstop was evaluated and rejected as unsound (§3 — it cannot know "owed" without the archived §6 that validate ignores). Priority should rather than must, codifying from one incident, matching REQ-CHANGE-004 / REQ-CHANGE-005; re-evaluate after a few real applies.

5 · Risk register

The adversarial pass ran (opt-in --adversarial; the change touches the must-tier change-management family REQ-CHANGE-006 governs). Findings below; each MUST reach accepted, mitigated, or rejected before apply.

A self-check by the same run that performed the fold is not an independent check: the LLM slash-command run that skips the fold (the T-004 failure) is the same run most likely to skip verifying the fold — so on the path that actually broke, this "adds a line, not an actor".

"a self-check apply performs at the end of its fold step … re-read the target tracker, confirm the new phase … is present".

Draft (status is the author's to set). True and the honest core limit. The kernel (apply.ts) check IS independent and deterministic — but it guards the CLI path, not the slash path that failed. Real independence on the slash path requires it to perform the fold through the kernel, so the deterministic check runs regardless of LLM adherence. That hardening is the recommended follow-up (and is why §3 no longer claims the slash path is "deterministic"). As written, this proposal makes the post-condition explicit and enforces it deterministically in the kernel; it should be accepted as the necessary first step, with the route-through-kernel change tracked next — or this risk justifies pulling that change into scope now.

Apply folds at step 8, after the deltas (4), spec changelog (5), archive move (6) and status flip (7) have committed — so an abort-on-missing-phase would leave a half-applied state (artifacts say applied+archived, command errored) with no recovery path, puncturing REQ-CHANGE-006's "uniform … never context-dependent" framing.

REQ-CHANGE-006: "a uniform accept-and-route step for every target — never context-dependent about whether it implements"; vs an apply that fails at step 8.

Draft (status is the author's to set). Caught a real flaw in the first wording ("fail loudly"). The delta was revised: the remedy for a missing phase is to complete the fold (apply still holds §6), not abort — apply MUST NOT report success until the phase is present, and never fails into a half-applied state. With that change the post-condition strengthens REQ-CHANGE-006's atomicity rather than contradicting it. (Considered: moving the fold ahead of the irreversible steps; rejected as a larger reorder than this change warrants — self-completion achieves the same end-state.)

The requirement lands in two unsynchronised surfaces — the LLM slash-command procedure and the deterministic kernel — and only the kernel one is enforceable, so the requirement can read "done" while the path that demonstrably failed (slash command) stays exactly as trustworthy as before.

§6 task: "Implement the same check in the apply kernel so the CLI path enforces it too (not just the slash-command procedure)".

Draft (status is the author's to set). Related to R-1 and the same fix applies: the kernel is the deterministic enforcer, and the slash path is hardened by routing its fold through the kernel rather than re-implementing it in prose. Until then, the slash-command self-verify is a documented reminder, honestly weaker than the kernel guarantee — the proposal should say so (it now does, §3), not imply parity. Disposition turns on whether to pull the route-through-kernel change into this proposal or track it as the immediate follow-up.

7 · Open questions

  1. Pull the route-through-kernel hardening into this change, or track it as the immediate follow-up? The adversarial pass (§5 R-1/R-3) is right that the slash-command self-verify is only as strong as LLM adherence — the deterministic guarantee is the kernel's. Making the slash apply perform its fold through the kernel is what closes that gap on the path that actually failed (T-004). It is a larger change (the slash command's relationship to apply.ts), so it is held as a decision: include it in REQ-CHANGE-007 now, or land this post-condition first and the routing next. Everything else is settled — apply self-verify is the mechanism (the validate backstop was evaluated across three passes and rejected, recorded in §2/§3 so it is not re-proposed), the remedy is self-completion not abort (§5 R-2), priority is should (one data point), and the empty-§6 carve-out is inherited from REQ-CHANGE-006.
