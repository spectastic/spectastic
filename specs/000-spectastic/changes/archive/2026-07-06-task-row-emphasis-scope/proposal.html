Task-row emphasis is a short title, not the whole line

Every tasks.html since 026 renders as a wall of bold because the task-row contract never bounds the <strong> to a title. Pin it to a short imperative title with detail in plain-weight prose.

Status Applied Change ID 2026-07-06-task-row-emphasis-scope Spec 000-spectastic (meta-spec) Author Brian Corbin · @briancorbinxyz Created 2026-07-06 Targets 1 requirement (1 modified) Read time

Closes meta-spec triage T-010. REQ-LIFECYCLE-003 fixes the <spec-task> element shape — id, parallel, checkbox — but stops at the checkbox and never specifies the inner label. So the template's <strong>[TASK]</strong> placeholder gets read literally: a richly-detailed task line is bolded end-to-end. Five consecutive specs (026–030) drifted identically — the signature of a contract gap, not one-off drift. This change MODIFYs REQ-LIFECYCLE-003 to bound <strong> to a short imperative task title, with any supplementary detail in plain-weight prose (the readable pre-026 pattern), backed by a warn-level task-title-bold-scope validate rule. §6 re-authors 026–030 to the split form.

Task-row emphasis is a short title, not the whole line

Applied

1 · Intent

Task lists are the artifact a reader scans most mechanically — one row after another, looking for the next unchecked box. When every row is fully bold, that scan loses its only visual affordance: there is no title to catch, no detail to skim past, just an undifferentiated block of heavy text. Since spec 026, every generated tasks.html has read this way.

The cause is a gap in the format contract, not author carelessness. REQ-LIFECYCLE-003 pins the <spec-task> element's structural attributes but says nothing about the emphasis inside its label. The template placeholder (<strong>[SETUP_TASK_1]</strong>) reads as "wrap the task in strong", so a detailed task sentence comes out entirely bold. Pre-026 authoring used a readable split — a short bold imperative, then an em-dash and plain-weight detail — but nothing in the contract required it, and once the drift started it propagated through five specs. Fixing only the drifted files would leave the next /spectastic.tasks run free to reproduce it; the fix has to land in the contract.

2 · Scope

In scope

  • Modify REQ-LIFECYCLE-003 to specify the task-row label form: a single short-title <strong>, detail in plain-weight prose, path in <span class="path">.
  • A warn-level task-title-bold-scope validate rule + fixtures that flags a <strong> spanning most of a task row.
  • Update commands/spectastic.tasks.md and templates/tasks.html to model the title/detail split, then re-sync .claude/commands/.
  • Re-author 026–030 tasks.html to the split form.

Out of scope

  • Restyling the <spec-task> CSS in assets/spec.css — the rendering already dims completed rows and shows a title/detail contrast; only the authored markup drifted. defer-to=never
  • Re-authoring tasks.html for specs 000–025 — those predate the drift and use the readable form already; the rule will flag any that don't, cleaned up as they surface. defer-to=never
  • Promoting the rule to an error/CI hard-fail — it is heuristic and ships at warn; a strict-CI gate is the deferred guarantee-layer work. defer-to=TBD-guarantee-layer-spec

3 · Approach

The change is one MODIFY delta. REQ-LIFECYCLE-003 already enumerates the element's required attributes as a list; we extend it with the label contract as one more clause and one more list item, keeping the requirement a single readable unit. The rule is named inline in the requirement body — the same pattern REQ-FORMAT-004 uses to name its band drift-guard — so the contract and its enforcement live together.

The task-title-bold-scope rule is deliberately a heuristic warning, not a hard parse: it flags a <spec-task> whose leading <strong> spans most of the row's text and whose row carries detail beyond the title (bold running past the first em-dash, or the row over a length floor) — what "the whole line is bold" looks like structurally. The conjunction is load-bearing: a terse, detail-free title that legitimately fills its row is left alone, and a bare colon or semicolon in a title is not a signal (titles carry them routinely). Warn, not error, because even the narrowed heuristic should not fail CI — this mirrors the false-positive caution behind REQ-FORMAT-004's move off the alert-fatiguing 70% band. The cleanup of 026–030 is ordinary re-authoring folded into §6 so /spectastic.implement drains it against the now-active rule.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec. op= is one of added | modified | removed | renamed; a missing or invalid op renders visibly broken.

What changes: adds a label-form clause — <strong> wraps a short imperative title only, detail in plain-weight prose — and names the task-title-bold-scope validate rule. The existing element-shape rules are unchanged.

Each task entry in a tasks.html artifact MUST be a <spec-task> custom element. The element MUST carry:

  • id="T-NNN" — the stable task ID, matching the format defined for tasks elsewhere in the project.
  • parallel (boolean attribute) — present when the task can run alongside its in-flight peers (the existing [P] convention); omitted otherwise.
  • An inner <input type="checkbox"> — the completion state. checked means done. CSS MUST read the state via :has(input:checked) rather than a parallel data-status attribute, so the checkbox is the single source of truth.
  • A label child (a <div> or <p>) holding the task text. Its leading emphasis MUST be a single <strong> wrapping a short imperative task title only — not the full task sentence. Any supplementary detail MUST follow in plain-weight prose (conventionally after an em-dash), and the target file or directory SHOULD sit in a trailing <span class="path"> — where path is a layout/styling class exempt under P-2, not a semantic component subject to REQ-AUTHOR-001.

Styling for <spec-task> MUST live in assets/spec.css — not inline in the template. The generic <div class="task"> + class-span form is forbidden as a direct application of REQ-AUTHOR-001. A task-title-bold-scope validate rule SHOULD warn (not error) when a task row's leading <strong> both spans most of the row and the row carries supplementary detail beyond the title (bold continuing past the first em-dash, or the row exceeding a length floor) — the structural signature of a whole-line-bold row. A terse, detail-free title that legitimately fills its own row does not warn.

Rationale

The tasks artifact is regen-derived from a template, so the contract for its internal shape is worth being explicit about. Without a named element, a fresh authoring session falls back to whatever the template already shows — and a class-soup template propagates indefinitely. Codifying <spec-task> turns the implicit pattern into something a validator (or a careful reader) can check. The label-form clause is the same lesson one level down: the original requirement bounded the element's attributes but not its emphasis, so the template's <strong>[TASK]</strong> placeholder was read as "bold the whole task" and every tasks.html from 026 onward became a wall of bold (T-010). Bounding emphasis to a short title restores the title/detail scan the readable pre-026 rows had, and the warn-level rule keeps the drift from silently returning.

5 · Risk register

Populated by the adversarial risk pass (this proposal touches a must-tier requirement, REQ-LIFECYCLE-003). One <spec-risk> per finding. status= defaults to identified; apply refuses until each transitions to accepted, mitigated, or rejected, recording the dispositioner in by=.

The task-title-bold-scope heuristic will false-positive on the rows it means to preserve: a legitimately terse, detail-free task ("Wire up the CLI flag") is a short title that fills 100% of its row and is correctly all-bold, yet trips the "spans most of the row" arm; and an ordinary title carrying a colon ("Add REQ-TOOL-004: triggering metadata") trips the punctuation arm — so the rule nags correct rows, gets muted as noise, and the drift it was meant to stop quietly returns.

§3 / delta body — "flags a <spec-task> whose leading <strong> spans most of the row's text or contains sentence-ending punctuation (. ; : mid-clause)".

Mitigated. The heuristic is narrowed to a conjunction: it warns only when the leading <strong> spans most of the row and the row carries detail beyond the title (bold past the first em-dash, or the row over a length floor). The bare-colon/semicolon signal is dropped — titles carry them routinely. §3 Approach, the delta body, and the §6 rule task now carry the narrowed spec, and the §6 fixture task adds a terse detail-free negative fixture that pins the boundary. Warn-severity bounds the blast radius even if the length floor needs tuning.

The new SHOULD clause routes a semantic value (the target path) through a class-named <span class="path">, which reads as contradicting REQ-AUTHOR-001 ("tag name is schema — never <div> + class names") — doubly so because REQ-LIFECYCLE-003 forbids "the generic <div class="task"> + class-span form" one paragraph up.

delta body — "the target file or directory SHOULD sit in a trailing <span class="path">" vs REQ-AUTHOR-001 "never as <div> + class names. Tag name is schema."

Mitigated. <span class="path"> stays — it is the established convention across every shipped tasks.html and is styled by assets/spec.css. The delta body now carries one clause scoping path as a layout/styling class exempt under P-2, not a semantic component subject to REQ-AUTHOR-001, so the contract no longer reads as self-contradicting. The heavier <spec-path> custom-element option (CSS + every existing row) was not taken.

Emphasis/prose-weight is an authoring-format concern, yet the whole label-form contract is housed in a LIFECYCLE requirement whose subject is the element's structural shape and state — so a future reader looking for a bolding convention will not think to look under "Lifecycle"; T-010 itself named REQ-LIFECYCLE-003 and REQ-AUTHOR-001 jointly as the locus.

§2 in-scope item 1 — "Modify REQ-LIFECYCLE-003 to specify the task-row label form"; T-010 Diagnosis names "REQ-LIFECYCLE-003 / REQ-AUTHOR-001" jointly.

Rejected. The label form is specific to the <spec-task> element, not a general authoring convention, so it belongs with the element it shapes — the way REQ-FORMAT-004 owns its own band drift-guard rather than deferring to a generic format REQ. Single-delta economy was the interview decision and §3 Approach records the placement rationale; a reader finding <spec-task> under Lifecycle finds its full contract in one place. The Mixed two-delta split (ADD REQ-AUTHOR-006) was considered and not taken.
