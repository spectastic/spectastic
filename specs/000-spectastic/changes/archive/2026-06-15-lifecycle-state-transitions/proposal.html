Define the full set of <spec-status> state transitions

The meta-spec names the lifecycle status values but never says when a spec moves between them. Pin down the state machine so shipped specs stop drifting in Draft.

Status Applied Change ID 2026-06-15-lifecycle-state-transitions Spec spectastic-spec Source T-001 · meta-spec triage log Author Brian Corbin · @briancorbinxyz Created 15 Jun 2026 Targets 1 modification (REQ-LIFECYCLE-002) + 1 addition (REQ-LIFECYCLE-004) Read time

REQ-LIFECYCLE-002 names the status values (Draft / In Review / Accepted / Superseded / Deprecated) but no requirement defines when a spec moves between them. Specs 002-validate-cli and 003-init-node-port shipped end-to-end while still marked Draft; both were hotfixed today (catch-up flip) ahead of this amendment. This proposal adds Blocked to the value set on REQ-LIFECYCLE-002 and adds REQ-LIFECYCLE-004 pinning the full state machine: who moves what, when, and by what gesture. A follow-on task updates commands/spectastic.implement.md so the last-task tick surfaces the Draft → Accepted flip.

Define the full set of <spec-status> state transitions

Applied

1 · Intent

The lifecycle status pill in every artifact carries one of six values (Draft, In Review, Accepted, Superseded, Deprecated, Blocked), but the meta-spec only names five of them in REQ-LIFECYCLE-002 and doesn't say how an artifact moves between values. The result is the drift documented in T-001: spec 002-validate-cli (50/50 tasks, 58/58 tests, shipped end-to-end) and spec 003-init-node-port (29/29 tasks, byte-identity verified vs the retired Python script) both carried Draft until manual catch-up this morning. The regeneration test for T-001 fails — nothing in the current artifacts tells the next LLM session to flip status, so the bug recurs for every future spec. The fix is upstream: define the state machine explicitly so subsequent specs cannot drift.

Adding the machine doesn't just close the gap that surfaced today; it also pins the transitions we've been performing implicitly. We flipped 001-cli to Superseded when 003 forward-linked it. We've never had a spec move into Blocked, but the value exists in implementations and the rule ought to be written down before the first one needs it. This proposal makes the implicit explicit.

2 · Scope

In scope

  • Modify REQ-LIFECYCLE-002 to add Blocked to the named value set (six values, not five) and to point forward at REQ-LIFECYCLE-004 for transition semantics.
  • Add REQ-LIFECYCLE-004 defining the finite state machine: every allowed transition with its trigger condition, and the terminal states.
  • Update commands/spectastic.implement.md so the tick-step on the last unchecked checkbox in any tasks.html surfaces the Draft → Accepted flip (prompt-or-perform).

Out of scope

  • Auto-running tests as part of the Draft → Accepted detection. The implement command will surface the flip; verifying tests are green stays an author judgment. Test-gate automation is a separate slice (TBD).
  • Touching the proposal lifecycle (proposed → under-review → approved → applied → withdrawn). Those are <spec-change> status values, distinct from the artifact-status values this proposal pins. They live under REQ-CHANGE-* and stay as-is.
  • Defining the principles' own status semantics differently. Principles inherit the same six values and the same FSM.
  • Migrating existing specs other than the two hotfixed today (002, 003). 001-cli is already Superseded; the meta-spec is left for the author to flip when ready, since "meta-spec is shipped" is a judgment call this proposal explicitly doesn't make.

3 · Approach

Two deltas. The MODIFY on REQ-LIFECYCLE-002 keeps its SHOULD strength on presence (templates SHOULD include a status pill) but extends the named value set and forward-links to the new requirement for transitions. The ADD of REQ-LIFECYCLE-004 declares MUST on transition correctness — once a spec ships, the state machine governs its movement.

The state machine itself is small. Most transitions are author-initiated; two are surfaced by tooling: Draft → Accepted by /spectastic.implement at last-tick, and Accepted → Superseded indirectly via the forward-link pattern (a successor spec adds a <spec-note> in its header citing the predecessor; the author of the predecessor flips status to match). Blocked is symmetric — any state can enter Blocked when an upstream issue is detected, and Blocked returns to the originating state when the blocker resolves. Superseded and Deprecated are terminal.

The command-prose update lives outside the spec deltas (it's a markdown file under commands/, not a meta-spec requirement). It's captured as a task in §6.

4 · Deltas

What changes: Extend the named value set to six (adding Blocked) and forward-link to the new REQ-LIFECYCLE-004 for transition semantics. The conformance strength stays SHOULD on presence — this requirement is about the pill appearing in the header, not about how it moves.

Each template SHOULD include a <spec-status> in the header reflecting exactly one of: Draft, In Review, Accepted, Superseded, Deprecated, Blocked. Transitions between these values are governed by REQ-LIFECYCLE-004.

What changes: A new MUST requirement pinning the finite state machine. Every allowed transition has a named trigger; transitions not listed are forbidden. The terminal states (Superseded, Deprecated) admit no further moves.

The lifecycle status of any artifact (spec, plan, tasks, principles, triage log, inbox) MUST evolve as a finite state machine over the six values named in REQ-LIFECYCLE-002. The allowed transitions are:

Draft → Accepted
Triggered when the last unchecked <input type="checkbox"> in the artifact's tasks.html is ticked and the author explicitly confirms the flip. /spectastic.implement MUST display a flip prompt at the last-tick that the author must explicitly confirm; the prompt MUST remind the author to verify the integration tests covering the Success Criteria pass before confirming. The command MUST NOT auto-flip status without explicit confirmation. The confirmation gesture absorbs the test-pass discipline; author judgment is the gate.
Draft → In Review
Author-initiated manual flip when soliciting reviewer feedback before the spec is locked. Reversible via In Review → Draft.
In Review → Accepted
Reviewer sign-off. Author flips after the review concludes.
In Review → Draft
Author-initiated when revisions are needed in response to review.
Accepted → Superseded
Triggered when a successor artifact adds a <spec-note> in its header citing this artifact as the prior contract. The successor's author flips the predecessor's status to Superseded at the same time the forward-link lands. The predecessor's content is preserved as historical record.
Accepted → Deprecated
Terminal phase-out without a successor — the requirements described are being removed from the project's scope, not replaced. Manual flip; once Deprecated, no further transitions are allowed.
Any state → Blocked
Triggered by a triage card or an upstream-block signal (an external system down, a vendor bug, a contractual review pending). Reversible via Blocked → originating-state. The originating state is recorded in the artifact's <spec-changelog> at flip time.
Blocked → originating state
When the blocker resolves, the artifact returns to whatever state it was in when Blocked was entered. Recorded in <spec-changelog>.

For artifacts without a tasks.html (principles, the meta-spec itself, triage logs, inbox), the Draft → Accepted trigger is an explicit author affirmation that the artifact is the operative contract for the project. The author records the affirmation as a one-line <spec-changelog> entry naming the date and the reason.

Transitions not in the list above are forbidden. In particular, a Superseded or Deprecated artifact MUST NOT transition to any other state — those are terminal. An Accepted artifact MUST NOT transition back to Draft or In Review; if amendments are needed, the path is /spectastic.propose against the live spec, not a status downgrade.

Every transition MUST append a one-line entry to the artifact's <spec-changelog> naming the old state, the new state, the date, and the triggering condition or gesture.

5 · Risk register

Adversarial pass auto-fires per the heuristic (must-tier touched: ADD declares priority="must"). Three findings embedded below; status starts at identified and transitions on author commitment.

The Draft → Accepted transition permits tooling to "prompt-or-perform" the flip without author confirmation in the margin, creating silent status changes that override explicit author intent.

"Surfaced by /spectastic.implement at the tick-step (prompt-or-perform; author confirms before the flip lands)."

Mitigated. Rewrote the Draft → Accepted bullet in REQ-LIFECYCLE-004: the command MUST display a flip prompt the author must explicitly confirm; MUST NOT auto-flip without confirmation. The ambiguous "prompt-or-perform" phrase is gone; the requirement now names the confirmation as mandatory in three explicit clauses.

REQ-LIFECYCLE-004 requires integration tests covering Success Criteria to pass as a precondition for Draft → Accepted, but REQ-LIFECYCLE-003 says every task entry MUST be a <spec-task> with a checkbox, leaving no way to represent a task whose completion depends on test results not yet known at tick time.

REQ-LIFECYCLE-003 requires "An inner <input type='checkbox'> — the completion state" but REQ-LIFECYCLE-004 conditions the transition on "the integration tests covering its Success Criteria pass." A task can be checked without tests passing, but the status machine forbids the transition.

Mitigated. Replaced the formal "tests pass" precondition with "author explicitly confirms the flip." The prompt MUST remind the author to verify tests pass before confirming, but the confirmation gesture itself is the gate — author judgment absorbs the test-pass discipline. REQ-LIFECYCLE-003's checkbox-only model is now compatible with REQ-LIFECYCLE-004; no schema change to tasks.html needed.

The proposal's scope excludes migrating existing specs other than 002 and 003, and explicitly leaves the meta-spec itself for "the author to flip when ready." This creates a meta-spec that prescribes a rule it doesn't follow, damaging credibility and inviting the next author to skip the step again.

"Migrating existing specs other than the two hotfixed today (002, 003). 001-cli is already Superseded; the meta-spec is left for the author to flip when ready, since 'meta-spec is shipped' is a judgment call this proposal explicitly doesn't make."

Mitigated in two parts. (a) Added a clause to REQ-LIFECYCLE-004 covering tasks-less artifacts (principles, meta-spec, triage logs, inbox): the Draft → Accepted trigger is an explicit author affirmation that the artifact is the operative contract — recorded as a <spec-changelog> entry. (b) Added a task to §6 to flip the meta-spec's status simultaneously with apply, so the proposal lands as Accepted alongside the rule it defines. "Rules for thee" trap closed.
