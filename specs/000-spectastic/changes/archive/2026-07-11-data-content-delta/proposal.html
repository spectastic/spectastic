Recognise a data/content delta in the change-proposal contract

A delta that carries no requirement carries no requirement. Apply should fold and archive it — not fabricate one into the spec.

Status Applied Change ID 2026-07-11-data-content-delta Spec 000-spectastic Source triage 000/T-018 (live on 041's profile-principle-catalog apply) Author Brian Corbin · @briancorbinxyz Created 11 Jul 2026 Targets 2 modified (REQ-CHANGE-002, REQ-CHANGE-008) Read time

The change-proposal contract assumes every <spec-delta> touches a numbered requirement: REQ-CHANGE-002 says target names "the requirement ID it touches," and REQ-CHANGE-008's kernel fabricates a <spec-requirement> from any op="added" delta that embeds none (apply.ts:75-86). But 041 and 042 legitimately propose changes to profile-manifest data (spectastic-profiles.json), whose deltas name a JSON key and carry a <spec-diff>, not a requirement. Applying one injects proposal prose into the live spec (triage T-018, hit live on 041). This change teaches the contract the distinction: a delta with an embedded <spec-requirement> is a requirement delta (apply to spec.html); a delta without one is a data/content delta (fold §6 tasks + changelog + archive, making no change to the requirements body). A shape guard gate-blocks the one ambiguous case — a requirement-shaped target that forgot to embed its requirement — and a data-delta-shape validate rule catches the same slip at authoring time.

Recognise a data/content delta in the change-proposal contract

Applied

1 · Intent

The change-proposal lifecycle was designed around requirement deltas — the whole point of a typed <spec-delta> is to fold a requirement's post-state into spec.html. But two specs (041 init-profiles, 042 profile-enforcement) govern behaviour that lives as data in a JSON manifest, not as numbered requirements. A proposal that seeds a profile principle or an enforce category legitimately targets a manifest key (standard/shape-of-system-principles) and shows the change as a <spec-diff>. The contract has no word for that, so the kernel does the only thing it knows: it wraps the whole delta body in a fabricated <spec-requirement id="{target}" priority="must"> and injects it into the live spec — silent corruption, caught live on 041 (triage T-018; hotfixed, apply commit amended).

This is upstream of the code. REQ-CHANGE-002 mandates target = "the requirement ID it touches," and REQ-CHANGE-008 mandates the kernel apply each delta into spec.html — neither contemplates a data delta. So a code-only patch would drift back on the next regeneration. The fix is to name the data/content delta in the contract and give the kernel a deterministic branch, so every downstream data-proposal (041's remaining principle rows, 042's whole enforce-category cluster) applies cleanly instead of needing a manual scrub each time.

2 · Scope

In scope

  • MODIFY REQ-CHANGE-002: a delta target MAY name manifest data (a JSON key/path), not only a requirement ID; a requirement delta embeds a <spec-requirement>, a data/content delta does not.
  • MODIFY REQ-CHANGE-008: the kernel branches on the embedded <spec-requirement> — present → apply to spec.html; absent → data/content delta, make no change to the requirements body (still fold §6 + changelog + archive), never fabricate one; and gate-block the shape guard (requirement-shaped target with no embedded requirement).
  • ADD a data-delta-shape validate rule (the authoring-time half of the guard, pulled in from the adversarial pass): a <spec-delta> whose target is requirement-ID-shaped (^[A-Z]+-) but embeds no <spec-requirement> is an error. REQ-CHANGE-002 names it as the enforcement.
  • Folded tasks: the apply.ts branch, the validate rule, and a kernel test proving a data delta leaves the requirements body unchanged (only the changelog append lands) while the fold and archive still run.

Out of scope

  • Cross-spec delta application — already the kernel's one unhandled mechanical step per REQ-CHANGE-008; unchanged by this proposal.
  • Re-expressing 041's already-applied profile-principle-catalog. It was hotfixed in place (phantom removed, apply commit amended); no rework needed.

3 · Approach

The distinguishing signal is content, not a new attribute: a delta that embeds a <spec-requirement> is a requirement delta; one that doesn't is data/content. This reuses the structure the template already prescribes (ADD/MODIFY embed the post-state) rather than adding a surface="data" marker authors must remember. The kernel's current fallback — extractInner(body,'spec-requirement') ?? body.trim() — is exactly the bug: the ?? body.trim() is what fabricates a requirement. The fix replaces it with an explicit branch.

One guard closes the opposite footgun: a requirement delta that forgot to embed its <spec-requirement> must not silently become a no-op. So when the target matches a requirement-ID shape (^[A-Z]+-…) but no requirement is embedded, the kernel gate-blocks it as malformed — the author sees a clear failure, not a silent skip. A slash-bearing or lowercase target with no embedded requirement is unambiguously a data delta and applies as a spec-noop + fold.

The data delta's real effect is its §6 tasks: /spectastic.implement edits the manifest (spectastic-profiles.json) during the drain. Apply's job for a data delta is purely to fold those tasks, append the changelog, and archive — the same lifecycle every proposal gets, minus the requirements-body mutation a data change never wanted (the changelog append still lands, as on every apply).

4 · Deltas

Two MODIFY deltas on the change-proposal contract. Both embed the full post-state.

What changes: a delta target may name manifest data, not only a requirement ID, and the embedded-<spec-requirement> presence is what marks the two kinds apart.

Each <spec-delta> MUST carry an op attribute equal to one of added | modified | removed | renamed, and a target attribute naming what it touches: a requirement ID (FR-*, REQ-*, NFR-*, SC-*, D-*) for a requirement delta, or a manifest data key/path (e.g. standard/shape-of-system-principles in spectastic-profiles.json) for a data/content delta. A requirement delta MUST embed a <spec-requirement> showing the post-state; a data/content delta MUST NOT — its post-state is the §6 tasks that edit the manifest, and apply makes no change to the requirements body for it (the <spec-changelog> append still lands, as on every apply; see REQ-CHANGE-008). The data-delta-shape validate rule enforces the pairing: a target of requirement-ID shape (^[A-Z]+-) with no embedded <spec-requirement> is an error. For op="removed", the delta MUST also carry reason and migration fields — empty or missing renders visibly broken.

What changes: a new paragraph gives the kernel a deterministic branch on the embedded <spec-requirement> — present → inject; absent → data delta, no spec.html mutation, never fabricate; requirement-shaped-but-unembedded → gate-block. The rest of the requirement is unchanged.

The mechanical steps of /spectastic.apply — applying each <spec-delta>, the live-spec <spec-changelog> entry (the kernel MUST accept an author-supplied one-line summary, so the changelog's human voice is preserved rather than reduced to a delta count), the archive-folder move, the proposal status flip to applied, and the §6 task-fold (per REQ-CHANGE-006 / REQ-CHANGE-007) — MUST be performed by the apply kernel (spectastic apply, which is deterministic and requires no ANTHROPIC_API_KEY), not re-implemented in the slash-command markdown. The apply markdown MUST run the preconditions — including the REQ-CHANGE-004 risk gate, listing any status="identified" risks by target= — and surface failures before invoking the kernel; the kernel's own gate is a deterministic backstop, not the user-facing refusal. It MUST also confirm spectastic apply resolves before invoking it, surfacing a missing or stale binary clearly rather than failing silently. Beyond the preconditions, the markdown owns only the post-apply routing nudge (REQ-CHANGE-003) and the inbox-card nudge.

When applying each <spec-delta>, the kernel MUST branch on whether the delta embeds a <spec-requirement>. Present — it is a requirement delta: apply the post-state into spec.html (insert for added; replace the id-matched requirement for modified | removed | renamed). Absent — it is a data/content delta whose target names manifest data: the kernel MUST make no change to the requirements body (the mandated <spec-changelog> append still lands) and let the §6 task-fold carry the change; it MUST NOT fabricate a <spec-requirement> from the delta body. As a guard, if a delta's target matches a requirement-ID shape (^[A-Z]+-…) yet embeds no <spec-requirement>, the kernel MUST gate-block it as malformed rather than silently skip — a requirement delta that forgot its post-state is an error, not a no-op.

This is a deliberate, named exception to 006 FR-008 ("the markdown procedure remains the source of truth") and FR-009 ("slash commands MAY invoke the CLI but MUST NOT be required to") for apply: its mechanical steps are pure and deterministic, and their prose-only form was the T-004 failure. Those general rules continue to govern the six verbs that need LLM judgment.

The obligation is scoped to same-spec applies. A cross-spec delta (whose target is a requirement in another spec) is the one mechanical step the kernel does not yet perform and MAY remain markdown-handled until it does (TBD-kernel-cross-spec-apply).

Rationale

Apply's mechanical steps need no AI and the CLI runs key-free, so making the kernel authoritative for them removes the whole class of skipped-step bugs on the in-host path (T-004) without touching the verbs that need judgment. The data/content branch (T-018) extends the same principle: the kernel, not a fabrication fallback, decides what a delta means, so a manifest-data proposal (041 principles, 042 enforce categories) folds and archives without corrupting spec.html. Hosted as a meta-spec requirement — not a MODIFY of 006 FR-009 — because a cross-spec delta could not be applied by the kernel this very requirement mandates, and because apply's contract already lives in REQ-CHANGE-*. Priority should: codifying apply's kernel-authoritative path from incident, matching REQ-CHANGE-004 / REQ-CHANGE-007; re-evaluate after a few real applies.

5 · Risk register

Populated by the adversarial risk pass (auto-fired: REQ-CHANGE-002 is must-tier, and this touches the meta-spec's core change contract). One <spec-risk> per finding; status="identified" until the author dispositions each. Apply refuses while any remains identified.

The proposal's claim that a data/content delta leaves spec.html "byte-identical" contradicts REQ-CHANGE-008's own retained MUST that the kernel append the live-spec <spec-changelog> entry — which apply.ts:128-130 writes into spec.html unconditionally for every apply.

§6 task 2: "leaves spec.html byte-identical" and REQ-CHANGE-002 rewrite "apply leaves spec.html untouched for it" — versus REQ-CHANGE-008: "the live-spec <spec-changelog> entry … MUST be performed by the apply kernel" (appendChangelogEntry → unconditional fs.writeFile(specPath, …)).

Mitigated. Confirmed against the kernel: the changelog line always lands. The invariant is narrowed throughout (REQ-CHANGE-002, REQ-CHANGE-008, §3, §6 task 2) to "the kernel makes no change to the requirements body — the mandated changelog append still lands, as on every apply." The test asserts the requirements body is unchanged, not the whole file. The changelog write is correct and stays.

Discriminating requirement-vs-data deltas by the absence of an embedded <spec-requirement> — rather than an explicit marker — turns an authoring slip that drops or mis-nests the post-state into a silently-accepted "data delta" whenever the target isn't requirement-ID-shaped, re-introducing a symmetric silent failure on the branch opposite the one T-018 closed.

§3 Approach: "reuses the structure the template already prescribes … rather than adding a surface="data" marker"; and "A slash-bearing or lowercase target with no embedded requirement is unambiguously a data delta".

Accepted. The residual gap is narrow: a requirement-ID-shaped target that forgets its post-state IS caught by the shape guard; only a lowercase/slash target secretly meant as a requirement slips through — two mistakes at once. Content + shape guard was chosen over an explicit marker (extra authoring burden) in the decision interview, and the residual is now closed at authoring time by the data-delta-shape validate rule pulled in-scope (next risk). No explicit marker.

Deferring the authoring-time validate rule to TBD-data-delta-validate ships a contract whose only guard against a forgotten post-state is a regex-based apply gate with a known blind spot, so the new silent-no-op class has zero detection at propose/validate time — the earliest, cheapest checkpoint (P-8).

§2 Out of scope (draft): An authoring-time validate rule that flags a requirement-shaped target with no embedded <spec-requirement> before apply … a cheap follow-on.

Mitigated. The data-delta-shape validate rule is pulled in-scope (§2, §6): a <spec-delta> whose target is requirement-ID-shaped (^[A-Z]+-) but embeds no <spec-requirement> is an error, and REQ-CHANGE-002 names it as the enforcement. The propose/validate gate now catches the forgotten post-state before apply, closing the residual from the prior risk. The TBD-data-delta-validate defer is removed.
