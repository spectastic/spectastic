Change proposal · 000-spectastic

Extract five slices

The meta-spec has grown past the point where its own gates pass on it. Move all 39 requirements into five child slices and leave the umbrella holding context, architecture and history.

Status Applied Target spec000-spectastic Author Brian Corbin · @briancorbinxyz Created 11 Aug 2026 Read time

The meta-spec is 118 KB and breaches its own NFR-001 validation budget on continuous integration hardware, and its size gauge has been red for some time. This proposal removes all 39 requirements from it, each having been moved verbatim — stable id intact — into one of five child slices, and records the five carve-outs so the parent and its children point at each other.

1 · Intent

One file has been carrying the whole contract. At 118 KB the meta-spec takes about 28 ms to validate on a developer machine and roughly 140 ms on a continuous-integration runner, against a budget of 100 ms per file — so the project's own performance requirement fails on the project's own flagship artifact. Its size gauge tells the same story in the header of every render: 9,638 words against a 5,000 budget, 39 requirements against 20, banded red with the tool's own advice to split.

The advice is right, and this is the mechanism the lifecycle already provides for taking it. Nothing about the contract changes here. Thirty-nine requirements move house; not one word of requirement text is edited, and not one id changes.

What this fixes is the validation breach. It does not make the size gauge green: with every requirement gone the file still holds about 4,300 authored words against a 5,000 target — inside the budget, but in the amber band, because what remains is change-log history and context prose rather than requirements. Bringing that down wants its own decision — see §5.

2 · Scope

In scope. Removing all 39 requirements from the parent; recording the five carve-outs in its out-of-scope register so parent and child reciprocate; repointing inbound anchors across the repository.

Out of scope. Any change to requirement text, priority or id. The parent's context, architecture, decisions, alternatives, glossary and change log all stay where they are — this proposal moves requirements, not prose. Six requirements had drifted into §1 Context and one into §5 Architecture rather than living in §4; they move into their child's requirements section, which is the only structural correction here.

3 · Approach

The partition cuts on concern, and it is a partition in the strict sense: every requirement lands in exactly one child, none is duplicated, and none is dropped. That was checked mechanically against the parent before the children were written.

The parent drops from 118 KB to roughly 64 KB, which measures at about 13 ms locally and a projected 61 ms on a runner — inside the budget with room to spare. Each child is between 10 and 30 KB and validates well under it.

Ids are contracts, so they survive the move untouched. What does not survive is the path: 117 anchors across the repository point at 000-spectastic/spec.html#REQ-…, and each must be repointed at the child that now holds the requirement. That is mechanical, and its completeness is checkable — no anchor into the parent may resolve to a moved requirement afterwards.

5 · Risk register

A missed anchor rewrite fails silently, and nothing catches it. Moving a requirement keeps its id but changes its address, so all 117 anchors of the form 000-spectastic/spec.html#REQ-… must be repointed. A missed one still resolves to a real file and simply lands nowhere — no browser error, no build failure. And there is no gate: no validate rule checks that an href anchor resolves. The evidence is in this very spec, which carries six broken relative links today while spectastic validate reports no findings on it.

Mitigation. Completeness is asserted mechanically rather than trusted: after the rewrite, no anchor anywhere in the repository may point at 000-spectastic/spec.html#REQ-… for any moved id, and every rewritten anchor must resolve to a heading that exists in the named child. Both are checks with a definite answer, and both run as part of §6. That the gate does not exist in the tool is a separate gap, recorded here rather than fixed under cover of this change.

The children ship a spec with no design or tasks sibling. REQ-LIFECYCLE-005 makes the three artifacts of a slice a single bundled unit that transitions together. Each of the five children is created with only a spec.html, and marked Accepted at birth — a bundle missing two of its three members.

Disposition — accepted, with the reading recorded. The requirement governs status transitions: when a spec's status moves, its siblings move in the same gesture. These children are not making a transition. They hold requirements that were ratified in the parent years of commits ago and whose implementations already shipped; authoring a design doc and a task list for them would be fabricated ceremony describing work that is long finished, which is a worse artifact than none. If a child later changes, it changes through a proposal like any other spec, and a bundle can be created then if the change warrants one.

This fixes the performance breach, not the size gauge. The intent section cites both the failing validation budget and the red size gauge, which invites the reading that the split resolves both. It does not. Measured after removing all 39 requirements, the parent holds 5,990 authored words against a 5,000 budget — still over, because the weight that remains is the 22.6 KB change log and the 17.8 KB context section, neither of which is a requirement and neither of which this proposal touches.

Disposition — accepted, and the claim narrowed. The performance breach is the problem being solved, and it is solved with room to spare. The word budget stays amber and wants a separate decision about archiving change-log history, which is a different change with different consequences. Better to say so than to let a reader infer the gauge goes green.

Outcome — the 5,990 figure above was wrong, and is left in place rather than quietly corrected. It came from a simulation that removed only §4's requirements. The applied change also moved the seven requirements that had drifted into §1 and §5, so the parent settled at 4,306 words — inside the 5,000 budget at 86%, still amber but no longer over. The band this risk predicted is right; the number it predicted is not.
