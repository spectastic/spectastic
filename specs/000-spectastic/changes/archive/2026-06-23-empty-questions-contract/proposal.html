Unambiguous zero for the open-questions register

"No open questions" gets one canonical form — no counted <li> — so a resolved register never reads as an open question. Rationale prose stays, in a <p>.

Status Applied Change ID 2026-06-23-empty-questions-contract Spec spectastic-spec Source 020 · T-005 Author Brian Corbin · @briancorbinxyz Created 2026-06-23 Targets 1 requirement (1 added) Read time

A <spec-questions> register has no canonical "zero" form. Some artifacts write the resolved state as a <p> (016 — "None outstanding because…"), which reads as zero; others write an <ol><li>None at write time…</li></ol>, which every <li>-counting consumer reads as one open question. That false count lit a red needs-attention border on a fully-resolved plan (T-005). This change fixes it at the generating side: REQ-AUTHOR-005 (new) makes "no open questions" = a register with no <li>, with rationale kept in a <p> (the 016 pattern). The reader (extractHealth) is already correct; the 29 live artifacts on the <li>-form migrate, and a validate rule gives the contract teeth.

Unambiguous zero for the open-questions register

Applied

1 · Intent

The lifecycle canvas (020 FR-006) flags a node for attention when it has an open question. It counts open questions the only way a machine can — one per <li> in the <spec-questions> register. But the register has no agreed representation for zero open questions: authors variously write a <p> saying "None outstanding…" (which carries no <li> and so correctly reads as zero) or an <ol><li>None at write time…</li></ol> (which reads as one). The second form lit a red needs-attention border on a plan whose questions were all resolved — triaged as T-005, classified cross-spec because the defect is the shared format contract, not any one consumer.

The reader is fine; the generated format is ambiguous. The fix belongs where questions are written. There should be no room for ambiguity about what "resolved" looks like.

2 · Scope

In scope

  • Define the zero-questions contract as a new requirement: no open questions ⇒ no <li> in the register; rationale prose lives in a <p>.
  • Migrate the 29 live artifacts (15 specs × spec + plan) carrying the <li>-"None" form to the <p> form, preserving the rationale text verbatim.
  • Update the authoring verbs (spec, plan, propose) to emit the <p>/empty form when nothing is unresolved — never a "None" <li>.
  • Document the convention in templates/{spec,plan,proposal}.html.
  • Add a no-placeholder-question validate rule (a sentinel "None" <li> in a register is non-conformant), status-keyed so frozen archives don't fail CI.

Out of scope

  • Archived and withdrawn proposals, and the schema test fixtures — preserved verbatim / intentionally non-conformant; never migrated.
  • Extending the same "rationale-in-<p>, items-in-<li>" discipline to other registers (<spec-risk-log>, <spec-out-of-scope>).

3 · Approach

The canonical zero form already exists in the codebase: 016-theme-support writes <spec-questions><p>None outstanding. Every decision was anchored in the interview…</p></spec-questions> — full rationale, zero <li>, reads as zero. We make that the rule rather than inventing a new marker. The distinction is simple and machine-legible: a <li> is an open question; a <p> is prose. Count the <li>.

Because the rule matches what extractHealth already does (counts <li>), no consumer code changes. Migration is a mechanical move of rationale text from an <li> into a <p>. The validate rule is status-keyed (like the existing no-unresolved-question rule it sits beside) so it does not fire on applied / withdrawn archives, and it lands after the migration task so it can never red-CI an un-migrated file.

This proposal was reframed by its own adversarial pass (§5). The first draft mandated an empty register; the critic showed that deletes load-bearing "resolved because…" rationale and collides with the structural-legibility principle. The shipped contract preserves the prose — it only forbids the counted <li> placeholder.

4 · Deltas

One <spec-delta> — a new authoring requirement. target= links to the live spec; op="added" embeds the post-state inline.

A <spec-questions> register with no open questions MUST contain no <li> items. Each <li> in the register counts as exactly one open question to every consumer — health extraction, the lifecycle needs-attention signal, validators — so an absence of <li> is the single unambiguous representation of zero. Resolved-with-rationale prose (e.g. "None outstanding — every decision was anchored in the interview") SHOULD live in a <p> inside the register, and MUST NOT be written as a placeholder or "None" <li>.

Rationale

The register is a counter to machines and a decision trail to humans; both are served by reserving <li> for an actual open question and putting prose in a <p>. 016-theme-support already does this; the <ol><li>None at write time…</li></ol> form used by the core specs is what trips the false count fixed here (T-005). Complements REQ-AUTHOR-001 (tag name is schema): the tag you choose inside the register is the meaning.

5 · Risk register

Adversarial pass per REQ-CHANGE-004 (triggered: the delta is priority="must"). Three findings; each materially shaped the proposal. Statuses stay identified until the author commits them — apply refuses while any remain identified.

Mandating an empty register would delete the load-bearing "resolved because…" rationale authors rely on, and make "deliberately resolved" indistinguishable from "never filled in".

Draft phrasing "MUST be empty"; real prose in 016-theme-support ("None outstanding. Every scope and mechanism decision was anchored…").

Accepted and incorporated before shipping: the requirement no longer mandates emptiness. It forbids only the counted <li> placeholder and explicitly keeps rationale in a <p> (the 016 pattern). The empty case and the prose case both read as zero.

An empty register collides with the structural-legibility principle — it erases the decision-path affordance that no-unresolved-question presumes the register carries.

REQ-LIFECYCLE-006 (make "what the plan knows vs assumes" structurally legible); no-unresolved-question.ts treats <spec-questions> as a register that routes resolved questions in "with a tracked decision path".

Reconciled: keeping rationale in a <p> preserves — and makes uniform — the tracked-decision-path prose; the change only stops miscounting it. Legibility improves rather than regresses.

The migration scope rested on an unverified premise; shipping the validate rule in the same batch risks red-CI on un-migrated or frozen files.

§2 in-scope items — "migrate the artifacts" and "add a validate rule". Initial guess was unmeasured.

Re-measured before scoping: 29 live <li>-form artifacts (archives, withdrawn, and fixtures explicitly excluded — see §2 out-of-scope); 016 already conformant via <p>. The rule is status-keyed (skips applied/withdrawn) and §6 orders it after migration, so it cannot red-CI a frozen archive or an un-migrated file.
