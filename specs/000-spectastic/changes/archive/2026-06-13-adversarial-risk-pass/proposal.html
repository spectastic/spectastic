Adversarial risk pass for /spectastic.propose

Applied

1 · Intent

The I-008 propose → apply → wire-up cycle landed without critical pushback at any stage. The result was mostly right, but a careful reviewer could have caught a naming inconsistency (<spec-task> inside tasks.html), an undefended must-vs-should priority call, a missing :has() browser-support footnote, and an undersized risk note for the 33-entry migration. Nothing in the propose → apply lifecycle forces the strongest counter-argument into the artifact, so first-draft proposals ship.

The fix is to spawn an independent critic Agent during propose for non-trivial proposals, embed the findings as statused artifacts inside the proposal, and gate apply on the user's status transitions. The artifact carries both the challenge and the defense; the reviewer evaluates instead of trusting the author's silence.

2 · Scope

In scope

  • One new requirement (REQ-CHANGE-004) codifying the risk pass.
  • Heuristic (must-tier touched OR op=removed OR ≥2 topic prefixes) with --adversarial / --no-adversarial flag overrides.
  • Spawned-Agent critic with a concrete three-finding prompt (regret-in-30-days, contradiction-with-live-spec, scope concern).
  • New <spec-risk> / <spec-risk-log> element vocabulary; new §5 Risk register section in the proposal template.
  • /spectastic.apply gate refusing on any <spec-risk status="identified">; "carry the risk register verbatim" discipline.

Out of scope

  • A separate /spectastic.risk <slug> command for post-hoc invocation on already-drafted proposals. Re-running propose is the supported path; capture if friction surfaces.
  • Multi-round adversarial passes (critic → revise → critic again). One pass per propose invocation; the author owns whether to re-run.
  • Severity grades (critical / major / minor). The four-value status enum carries enough signal; severity adds vocabulary cost.
  • Automatic propagation of risk findings into the changelog or inbox. Findings stay inside the proposal; the user routes manually if a finding becomes its own work.
  • Recording the critic Agent's full I/O transcript inside the artifact. The artifact carries findings + responses; provenance lives in the propose command's run log.
  • A rejection workflow for proposals the critic convinces the author to abandon. Captured as inbox card I-011 and slated as a sibling design pass once the risk pass has a few worked examples.

3 · Approach

The vocabulary borrows from ISO 31000's risk register. "Risk-accept" is canonical parlance; the four-status enum (identified | accepted | mitigated | rejected) maps cleanly onto how proposal-time concerns actually resolve. A fifth value, no-value-found, exists so the Agent can self-report when no risk passes the "would I regret in 30 days?" test — three of those in a row escalates to the user before archive.

The Agent's prompt is concrete by construction: "Identify exactly three risks. Cite the delta target, REQ ID, or §Scope item." Open-ended adversarial framing produces sycophancy; bounded asks produce specific findings the author can address or accept. The author-response discipline concedes a real point from the Plan-agent pressure-test: the propose-session LLM MAY draft a response, but MUST leave status="identified". Status transitions are the user's commitment; LLM drafts are starting points.

The section sits after Deltas, before Tasks. Reviewers' freshest attention lands on what's actually changing; meta-discourse before deltas burns that attention. Apply gates on identified only — the four other status values all allow apply to proceed, including rejected (the author disagrees the risk is real).

Vocabulary budget. This proposal adds two new custom elements — <spec-risk> and <spec-risk-log> — to a design system that the README and the meta-spec both describe as shipping "twelve elements total — that's the budget." That language predates several additions (<spec-budget>, <spec-out-of-scope>, <spec-parent>, the new <spec-task> from REQ-LIFECYCLE-003); the count is closer to fifteen. The two new elements ship coupled to the requirement they encode — splitting them into a sibling vocabulary proposal would create an artifact-ordering trap (apply REQ-CHANGE-004 first and the elements don't exist; apply elements first and they're undocumented). The honest move is to ship them here and retire the stale twelve-element ceiling in a follow-up commit that updates the README and the relevant meta-spec prose. Flagged as a follow-up; not blocking.

4 · Deltas

One <spec-delta>. target= links to the live spec. op= is added.

Non-trivial proposals — those that touch a priority="must" requirement, contain an op="removed" delta, OR span two or more topic prefixes — SHOULD carry a <spec-risk-log> populated by an adversarial risk pass run during /spectastic.propose.

Each <spec-risk> MUST carry:

  • target= — a delta ID, requirement ID, or §<n> section anchor. Missing renders the visible label MISSING TARGET.
  • status= — one of identified | accepted | mitigated | rejected (or no-value-found when the critic agent self-reports nothing of value). Default identified.

/spectastic.apply SHOULD refuse if any <spec-risk> has status="identified" — gating on the user-confirmed status field only. Apply MUST NOT re-run the heuristic, re-spawn the critic Agent, or transition statuses on its own; the status field is the user's commitment, and apply reads it. This is what distinguishes the gate from REQ-CHANGE-003's "apply MUST NOT refuse based on its own classification" — the risk-register gate refuses on user input, not apply-side judgment. The heuristic, the three-finding agent prompt, and the response discipline are owned by commands/spectastic.propose.md §8; the apply gate by commands/spectastic.apply.md's Preconditions.

Rationale

Spectastic's lifecycle had no step that forced the strongest counter-argument into the artifact, so first-draft proposals shipped without critical pushback. The risk pass closes that loop. The vocabulary borrows from ISO 31000's risk register — same lineage habit as ADR, INVEST, RFC 2119, and DORA already in the project. Priority should rather than must because we're codifying from one data point; re-evaluate after ≥5 worked applications.

5 · Risk register

Populated by the adversarial risk pass forced via --adversarial (the heuristic doesn't trigger automatically here: the proposal touches a single should-tier requirement under a single topic prefix). Self-application — the proposal that introduces the risk pass MUST itself carry one. Three findings expected; statuses default to identified until the user transitions them.

The three-clause heuristic for auto-firing the adversarial pass is codified from zero applications and will be wrong in one direction or the other within a month.

The §4 delta defines the trigger as "touch a priority="must" requirement, contain an op="removed" delta, OR span two or more topic prefixes", then admits in the rationale that priority is "should rather than must because we're codifying from one data point; re-evaluate after ≥5 worked applications." The same one-data-point caveat applies to the heuristic shape itself, not just its conformance level — a single-topic should-tier change that is architecturally deep (the exact shape of this proposal, which only fires under --adversarial) misses every clause, while a one-line wording tweak to any must fires the full ceremony.

Acknowledged in full. The flag overrides (--adversarial / --no-adversarial) are the explicit safety valve: when the heuristic mis-fires in either direction the author can force or skip. The heuristic itself is should-tier on purpose so it can be tuned after the ≥5-application sample window without re-doing the lifecycle. The "this proposal needs --adversarial to fire" admission is the precise data point that proves the heuristic isn't a guardrail — it's a default. Proposed transition: accepted — the risk is real but the design already absorbs it via the flag escape hatch.

The apply-refuses-on-identified gate contradicts the live spec's explicit "apply MUST NOT refuse based on its own classification" guardrail.

REQ-CHANGE-003 carries: "The rule is guidance, not a guardrail — apply MUST NOT refuse or auto-trigger plan/tasks based on its own classification." REQ-CHANGE-004 then directs "/spectastic.apply SHOULD refuse if any <spec-risk> has status="identified"" — a new refusal path keyed off a heuristic-driven classification (must-tier / removed / ≥2 prefixes) that apply itself can re-check. The two requirements pull in opposite directions on whether apply is allowed to gate on the proposal's self-classification; the live spec's MUST NOT outranks the new SHOULD.

Sharpest of the three. The REQ-CHANGE-003 MUST NOT is about apply's routing classification (small vs. large) which is a pure judgment call apply must not enforce. REQ-CHANGE-004's gate is structurally different: apply refuses on a user-confirmed status field, not on apply's own re-classification. The propose command writes identified; only the user transitions to accepted | mitigated | rejected; apply then reads the user's confirmed commitment. So apply is gating on user input, not its own judgment. Mitigation: the REQ-CHANGE-004 body should explicitly say "apply gates on the user-confirmed status field — never re-runs the heuristic or re-spawns the critic at apply-time." That phrasing closes the contradiction. Proposed transition: mitigated — but only after the requirement body is revised to carry the clarification, which is a delta change worth the user's eye.

Scope bundles new design-system vocabulary (two custom elements) with a workflow requirement, silently consuming budget from the spec's explicit twelve-element ceiling without acknowledgement.

§2 in-scope bullet 4: "New <spec-risk> / <spec-risk-log> element vocabulary; new §5 Risk register section in the proposal template." The live spec's §7 carries the standing warning "v0.1 ships twelve elements total — that's the budget" and REQ-AUTHOR-001 makes custom elements the canonical authoring surface — both signals that new elements are a governed resource, not a free byproduct. The proposal neither counts the elements it adds against the budget nor argues for raising the ceiling, conflating a Change-management requirement with an Authoring-vocabulary change that arguably wants its own proposal.

Genuine scope concern. The vocabulary additions are coupled to the requirement: <spec-risk> is what REQ-CHANGE-004 says the proposal MUST carry; splitting them into two proposals creates an artifact-ordering trap (apply REQ-CHANGE-004 first, then the elements don't exist; apply elements first, then they're undocumented). The honest fix is to acknowledge the budget cost and argue for it explicitly. The current spec ships ~14 named elements already (the original "twelve" warning predates several additions including <spec-budget> and <spec-out-of-scope>); the warning is stale. Mitigation: extend the §3 Approach with one paragraph naming the budget concern explicitly and recommending the README's element-count warning be retired in a sibling commit. Proposed transition: mitigated — after the §3 paragraph lands.
