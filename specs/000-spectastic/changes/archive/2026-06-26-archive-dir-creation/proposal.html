The kernel's archive + withdraw moves create their parent dir

A spec's first apply ENOENTs: the kernel's fs.rename can't move into a changes/archive/ that doesn't exist yet — and fails after the deltas already committed.

Status Applied Change ID 2026-06-26-archive-dir-creation Spec 000-spectastic Author Brian Corbin · @briancorbinxyz Created 2026-06-26 Targets 2 requirements Read time

Two MODIFY deltas making the kernel's folder-moves create their parent dir if absent: REQ-CHANGE-007 for the archive move (changes/archive/) and REQ-CHANGE-005 for the withdraw move (changes/withdrawn/). Today a spec's first apply ENOENTs on fs.rename (the dir doesn't exist yet) — and, as the last kernel step, fails after the deltas already committed. Surfaced live by triage T-007 applying 023's grounding-in-plan; the adversarial pass then split the withdraw clause onto its proper requirement and trimmed an atomicity overclaim.

The kernel's archive + withdraw moves create their parent dir

Applied

1 · Intent

Applying 023-explore-graduation's first proposal threw ENOENT: rename …/changes/<slug> → …/changes/archive/<slug>: fs.rename cannot move a folder into a parent that does not exist, and changes/archive/ is created lazily — it is absent until a spec's first apply. The meta-spec never reproduced this because its changes/archive/ has existed for dozens of applies.

The damage is worse than a clean failure. The rename is the last kernel step, so it threw after the deltas, changelog, §6 fold, and proposal status-flip had all committed — a half-applied state recovered only by hand (mkdir archive + mv). REQ-CHANGE-007 promises the fold-before-move ordering yields "a clean retry rather than a half-applied state" — but that guarantee only holds if the move itself cannot fail. A move that ENOENTs on a missing parent is exactly the hole. Triage T-007 classified this spec-layer (regen fails: another LLM implementing the current wording writes the same bare rename).

2 · Scope

In scope

  • Amend REQ-CHANGE-007 (archive move → changes/archive/) and REQ-CHANGE-005 (withdraw move → changes/withdrawn/): each MUST create its destination parent if absent.
  • The hotfix (§6): add FileSystem.mkdir + nodeFs impl; mkdir-before-rename at both move sites; a kernel test for the first-archive case.

Out of scope

  • Full transactional apply (true all-or-nothing rollback) — this closes the one missing-dir failure path, not every conceivable mid-sequence failure.
  • Routing the slash apply through the kernel — already landed (REQ-CHANGE-008).

3 · Approach

A sentence each on REQ-CHANGE-007 (archive move) and REQ-CHANGE-005 (withdraw move) — both stating the move creates its destination parent if absent, cross-referencing the shared create-the-destination-if-absent pattern REQ-CHANGE-006 already carries for the tracker. The kernel gains a mkdir primitive — the third the FileSystem abstraction has needed, after rename (apply) and rm (023 graduation rollback) — and both move sites ensure their parent before renaming. A recursive, force mkdir is idempotent, so it's safe whether or not the dir already exists (the common case).

4 · Deltas

Two <spec-delta>s. target= links to the live spec.

What changes: add one sentence — the archive-folder move MUST create changes/archive/ if absent. (The withdraw move's mkdir lands on REQ-CHANGE-005, its proper home — see the 2nd delta.) The rest of REQ-CHANGE-007 (the deterministic fold + fidelity) is unchanged.

The §6 task-fold mandated by REQ-CHANGE-006 MUST have a deterministic implementation in the apply kernel (it has none today). The fold MUST run on the §6 content apply has already read, before the archive-folder move, so a fold or fidelity failure leaves the proposal in changes/ for a clean retry rather than a half-applied state. The archive-folder move MUST create its destination parent (changes/archive/) if it does not yet exist, so a spec's first apply does not ENOENT at the move step — the same create-the-destination-if-absent obligation REQ-CHANGE-006 places on the tracker and REQ-CHANGE-005 on the withdrawn-folder move. When the kernel folds, it MUST confirm the resulting phase faithfully carries the §6 work — a <spec-task> for every §6 item, carrying over each item's <span class="path"> and, where the §6 item declares it (the [P] convention), its parallel marker, in the <spec-task> shape REQ-LIFECYCLE-003 defines — before reporting success. Mere presence of a phase is insufficient (presence is not containment). A missing or incomplete phase MUST be completed, not returned as success. An empty §6 owes no phase and is skipped per REQ-CHANGE-006.

This adds a kernel capability; it does not change which path performs the fold. The CLI apply path, which already calls the kernel, folds deterministically as a result. Bringing the slash-command path onto the kernel fold is a separate change (it re-architects the markdown-canonical boundary and has an API-key wiring question), tracked as TBD-route-fold-through-kernel and dependent on this one.

Rationale

REQ-CHANGE-006 specifies the fold as an action but defines no post-condition, and the action lives only in slash-command prose — apply.ts has no tasks.html code at all. So the one step that orphans real work when skipped is the one with no deterministic implementation: the 2026-06-25-spec-budget-bands failure (triage T-004). A fidelity check (not mere presence) is required because the fold is real format work and a present-but-wrong phase would otherwise pass — the project's own presence-is-not-containment lesson. A validate backstop was evaluated across three passes and rejected (it cannot know a fold was owed without the archived §6 it ignores). The move-creates-parent clause codifies triage T-007: the kernel's bare fs.rename ENOENT'd on 023's first apply (changes/archive/ absent), failing after the deltas, fold, and proposal-flip had committed — the one path that breaks the fold-before-move atomicity this requirement promises. Priority should, codifying from incidents, matching REQ-CHANGE-004 / REQ-CHANGE-005; re-evaluate after a few real applies.

What changes: the withdraw move MUST create changes/withdrawn/ if absent — the withdraw counterpart of the archive-move clause, placed on the requirement that owns withdraw (the adversarial pass's topic-group catch). Only the folder-move bullet changes.

Items considered but decided against MUST be preserved as history, not deleted. The lifecycle SHOULD support rejection at both surfaces:

Surface A — Inbox cards (pre-propose). A <spec-triage> card in inbox.html MAY carry data-status="rejected" and a <dt>Rejected because</dt> row inside its <dl>. The card stays in inbox.html (mirrors the existing data-status="done" convention for just-do cards). CSS renders a REJECTED pill, muted body, and strikethrough title.

Surface B — Authored proposals (post-propose). /spectastic.apply SHOULD accept a withdrawal mode invoked as --withdraw <YYYY-MM-DD>-<slug> --reason="<one-line>". The mode:

  • Refuses if the proposal status is already applied or withdrawn.
  • Refuses if --reason is empty.
  • Flips status to withdrawn.
  • Moves the folder from specs/000-spectastic/changes/<YYYY-MM-DD>-<slug>/ to specs/000-spectastic/changes/withdrawn/<YYYY-MM-DD>-<slug>/ (a sibling of archive/, not nested), MUST creating changes/withdrawn/ if it does not yet exist (mirroring the archive-move obligation, REQ-CHANGE-007, so a spec's first withdraw does not ENOENT at the move step). The date-prefixed folder name is preserved in both terminal states (applied and withdrawn) per REQ-CHANGE-001.
  • Appends a <spec-changelog> entry to the live spec it targeted: "Considered <YYYY-MM-DD>-<slug>, withdrew on <DD Mon YYYY> because <reason>."
  • Appends a changelog entry to the moved proposal recording the withdrawal date and reason verbatim.

Withdraw is intended as terminal: there is no --unwithdraw command. If you withdrew by accident or under time pressure, restoring the folder and status manually is unsupported but not forbidden — git-revert the move and flip the status field. If your thinking has actually updated since the withdrawal, author a new proposal instead so the lineage stays legible. Implementation ownership: Surface A in commands/spectastic.triage.md; Surface B's procedure in commands/spectastic.apply.md's Withdraw procedure section.

Rationale

The <spec-status value="withdrawn"> vocabulary has existed since v0.1 but has had no workflow behind it — an authored proposal the author decided against would either sit in changes/<YYYY-MM-DD>-<slug>/ indefinitely or get manually deleted. Inbox cards had no terminal-rejected state for routed layers. The lifecycle had no way to record "considered, decided against." This requirement closes both gaps with one discipline — preserve, don't delete — and one apply-mode extension. The withdrawn-folder mkdir-if-absent (added here) is the create-the-destination-if-absent obligation REQ-CHANGE-006 (tracker) and REQ-CHANGE-007 (archive) also carry — placed with the operation it governs. Priority should rather than must because we're codifying from zero applications; re-evaluate after ≥3 worked rejections.

5 · Risk register

Adversarial pass ran (opt-in --adversarial; REQ-CHANGE-007 is should-tier so the heuristic wouldn't auto-trigger). One <spec-risk> per finding; status= defaults to identified; apply refuses until each transitions to accepted, mitigated, or rejected.

The clause overstates atomicity: mkdir-before-rename closes only the ENOENT-at-the-move hole, but apply.ts:123 writes the live spec before the fold (:128), proposal-flip (:141), and rename (:145) — so a fold-fidelity throw still leaves the spec mutated and the proposal un-archived, a half-applied state the wording implies is now gone.

"so a spec's first apply or withdraw cannot fail mid-sequence on a missing directory; the fold-before-move ordering only guarantees a clean retry when the move itself cannot ENOENT on an absent parent".

Mitigated — reworded: the clause now claims only that the move "does not ENOENT at the move step," and cross-references the create-if-absent pattern (006 tracker / 005 withdrawn). Full transactional apply stays explicitly out of scope (§2); the clause no longer implies it.

REQ-CHANGE-007 is exclusively about the §6 task-fold (its title, body, and rationale never mention withdraw); withdraw has no fold and no fold-before-move atomicity promise to repair. Welding withdraw's changes/withdrawn/ mkdir onto 007 is the wrong topic group — the obligation belongs on REQ-CHANGE-005, which created changes/withdrawn/.

§2 In scope — "the archive and withdraw moves MUST create their destination parent if absent".

Mitigated — split done: the withdraw-move mkdir is now a 2nd MODIFY delta on REQ-CHANGE-005 (which owns withdraw and created changes/withdrawn/); REQ-CHANGE-007 covers the archive move only. The proposal grew from 1 to 2 MODIFY deltas to place each obligation correctly.

REQ-CHANGE-006 already mandates the tracker be "created from templates/tasks.html if absent" — the same create-the-destination-if-absent obligation. Spelling mkdir-before-rename as a separate MUST on 007 fragments one principle across requirements; a future reader may treat archive-dir creation and tracker creation as unrelated guarantees.

REQ-CHANGE-006 — "created from templates/tasks.html if absent".

Mitigated — the reworded 007 clause and the new 005 delta both cross-reference the shared create-the-destination-if-absent pattern (006 tracker, 007 archive, 005 withdrawn), so the three read as one principle placed with each operation rather than three unrelated guarantees.
