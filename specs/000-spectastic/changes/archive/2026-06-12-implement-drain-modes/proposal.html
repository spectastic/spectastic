Drain modes for /spectastic.implement

Keep one-task-per-invocation as the default. Add --all, --phase, and --parallel as opt-in drains.

Status Applied Change ID 2026-06-12-implement-drain-modes Spec spectastic meta-spec Source I-009 Author Brian Corbin · brian@example.com Created 12 Jun 2026 Targets 1 requirement (added) Read time

Add REQ-TOOL-003 to the meta-spec (skipping REQ-TOOL-002, historically used for the deferred-CLI requirement that was removed in 2026-06-12-add-change-proposal — stable IDs are not reused) stating that /spectastic.implement defaults to one task per invocation and accepts three opt-in drain modes: --all (drain unchecked sequentially), --phase=<id> (drain a phase block), and --parallel (spawn one Agent per [P]-marked task within the chosen scope). The one-per-invocation default and every existing discipline rule stay unchanged.

Drain modes for /spectastic.implement

Applied

1 · Intent

One full cycle through 001-cli exposed the cost of the one-task-per-invocation discipline at MVP-first scale: a 33-task drain meant 33 invocations and a /goal session hook to keep them in motion. The current rule is correct for risky, contested, or cross-spec work — silent chaining there hides judgment calls the user should be making. It is the wrong default for the common shape of a solo drain where every task carries the same low risk.

The fix is not to relax the rule, but to make it opt-in: keep one-per-invocation as the default; add three named modes that explicitly elect the relaxation. The user types the mode; nothing chains silently.

2 · Scope

In scope

  • One new requirement (REQ-TOOL-003) defining the three drain modes and the default.
  • Behavioural prose in commands/spectastic.implement.md describing each mode and its termination conditions.
  • An Agent spawn convention for --parallel: one agent per [P]-marked task within the resolved scope; sequential tasks remain in the main session.

Out of scope

  • Drain modes for other verbs (/spectastic.tasks, /spectastic.triage). The shape would be similar but the parallelism semantics differ; capture later.
  • A formal specification of the Agent spawn strategy beyond the per-[P] convention. Concurrency limits, error aggregation, and partial-failure semantics warrant their own pass.
  • Removing the default. One-per-invocation stays the default precisely because the existing discipline is right for the uncommon case where every invocation deserves a fresh judgment call.

3 · Approach

The drain modes are resolution rules in the same family as the existing no-argument resolution (drain inbox, then most-recent tasks.html). Each mode resolves $ARGUMENTS to a list of one or more target tasks before the implement loop runs. The body of the implement command (load context, do the work, tick the checkbox, verify) is unchanged.

--parallel requires one extra step: after scope resolution, partition the target list by the [P] marker. Sequential tasks run in the main session as today. [P] tasks each fork to an Agent tool call with the same context. The main session collects results and ticks the boxes only when each agent reports success — no silent half-state.

The "no silent chaining" rule still bites: when --all is in flight, the implement loop reports progress per task and pauses on the first failure. The user must re-invoke with --all after fixing the failure; failure does not silently skip.

4 · Deltas

One <spec-delta>. target= links to the live spec. op= is added; a missing or invalid op renders visibly broken.

The /spectastic.implement command MUST default to one task per invocation. It MAY accept three opt-in drain modes that the user must type explicitly:

  • --all — drain every unchecked task in the resolved scope sequentially, pausing on first failure.
  • --phase=<id> — drain every unchecked task inside the named phase section (setup, foundation, us1, us2, us3, polish).
  • --parallel — within the resolved scope (default scope = one task; combinable with --all or --phase), spawn one Agent tool call per [P]-marked task; run non-[P] tasks in the main session.

Drain modes MUST NOT silently chain — failure pauses the drain and re-invocation is explicit. Each completed task MUST be reported individually (one line per ticked checkbox) so progress is visible mid-drain.

Rationale

One-per-invocation is the right default for contested or cross-spec work where each step is a judgment call. MVP-first solo drains do not match that shape — the user typed /goal as a workaround on 001-cli's 33-task list because the existing discipline rejected the obvious move. Making the drain opt-in preserves the default while removing the workaround.
