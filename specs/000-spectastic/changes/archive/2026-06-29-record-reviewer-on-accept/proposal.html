Change proposal · 000-spectastic

Record the reviewer on In Review → Accepted

Review is status-driven but person-blind: the In Review → Accepted transition records that a review happened, never who did it. Make it record the reviewer.

Status Applied Change ID 2026-06-29-record-reviewer-on-accept Spec 000-spectastic Author Brian Corbin · @briancorbinxyz Created 2026-06-29 Targets 1 requirement (REQ-LIFECYCLE-004) Read time

A single MODIFY on REQ-LIFECYCLE-004. Its In Review → Accepted transition currently reads "Reviewer sign-off. Author flips after the review concludes." — it records that a review happened but not who reviewed, so the Reviewers <spec-meta> field sits empty in every live spec and the changelog names the condition, not the person. This amendment makes the transition record the reviewer's identity — filling the Reviewers field and naming the reviewer in the changelog entry, human only. The rest of the FSM is reproduced verbatim. It is the prerequisite for an honest Reviewed-by trailer (git-strategy brief ③ / G-004).

Record the reviewer on In Review → Accepted

Applied

1 · Intent

spectastic already produces a review signal — the In Review → Accepted transition is a human sign-off — but it never records who gave it. REQ-LIFECYCLE-004 says only "Reviewer sign-off. Author flips after the review concludes." The Reviewers field exists in every <spec-meta> header but is empty across all live specs, and the changelog entry names the triggering condition, not the person. Review is status-driven, not person-driven.

That gap is worth closing on its own merits — "who reviewed this" is a question the lifecycle should be able to answer from its own record. It is also the one thing standing between spectastic and an honest Reviewed-by: git trailer: the git layer (026) can derive Author/Acked-by/ Refs from existing fields today, but it omits Reviewed-by precisely because no field carries the reviewer yet. This amendment fills that field.

2 · Scope

In scope

  • Amend the In Review → Accepted transition in REQ-LIFECYCLE-004 to MUST record the reviewer's identity — the Reviewers <spec-meta> field plus the changelog entry, human only (never an automated agent).
  • Reproduce the rest of the FSM verbatim — no other transition changes.

Out of scope

  • The Draft → Accepted bundled flip. That path is the author confirming their own completed work — there is no separate reviewer to record, so it is untouched.
  • A validate rule enforcing a non-empty Reviewers field. Whether a spec went through In Review isn't statically knowable; enforcement stays author discipline for now. Deferred. The honesty of the eventual Reviewed-by: trailer does not depend on this: per G-004 the trailer is derived only from a populated Reviewers field and omitted otherwise — never faked — so an unfilled field yields no trailer rather than a false one.
  • Emitting the Reviewed-by: trailer. That is the git-trailers sibling slice (G-004); this amendment only makes the data exist.

3 · Approach

One MODIFY delta. The post-state is REQ-LIFECYCLE-004 reproduced in full, with exactly one change: the In Review → Accepted definition gains a sentence requiring the reviewer's identity to be recorded in the Reviewers field (as name · handle, the shape Owner already uses) and named in the changelog entry, with an explicit human-only clause that mirrors the project's no-AI-attribution stance. The general "every transition appends a changelog entry" closing rule is unchanged — the reviewer's name simply becomes part of that entry for this one transition.

The amendment is a contract/process rule, not new automation: In Review → Accepted is a manual author flip (no verb performs it), so the requirement is enforced by author discipline — the same way the tasks-less "author affirmation" clause already in REQ-LIFECYCLE-004 is. A future validate assist is left out of scope above.

4 · Deltas

One <spec-delta>, targeting the live REQ-LIFECYCLE-004.

What changes: only the In Review → Accepted definition — it now MUST record the reviewer's identity (Reviewers field + changelog, human only). Every other transition and clause is reproduced unchanged.

The lifecycle status of any artifact (spec, plan, tasks, principles, triage log, inbox) MUST evolve as a finite state machine over the six values named in REQ-LIFECYCLE-002. The allowed transitions are:

Draft → Accepted
Triggered when the last unchecked <input type="checkbox"> in the artifact's tasks.html is ticked and the author explicitly confirms the flip. /spectastic.implement MUST display a flip prompt at the last-tick that the author must explicitly confirm; the prompt MUST remind the author to verify the integration tests covering the Success Criteria pass before confirming. The command MUST NOT auto-flip status without explicit confirmation. The confirmation gesture absorbs the test-pass discipline; author judgment is the gate.
Draft → In Review
Author-initiated manual flip when soliciting reviewer feedback before the spec is locked. Reversible via In Review → Draft.
In Review → Accepted
Reviewer sign-off. The author flips after the review concludes, and MUST record the reviewer — a human — in the Reviewers field of the artifact's <spec-meta> and in the <spec-changelog> entry for this transition; the recorded identity is never an automated agent. The recording shape is the author's choice (a name, a handle, or both, the way Owner is written) — the contract is that a human reviewer is named, not the exact format. Artifacts that reach Accepted by author affirmation (the tasks-less path below) rather than through In Review have no separate reviewer, and this clause does not apply to them.
In Review → Draft
Author-initiated when revisions are needed in response to review.
Accepted → Superseded
Triggered when a successor artifact adds a <spec-note> in its header citing this artifact as the prior contract. The successor's author flips the predecessor's status to Superseded at the same time the forward-link lands. The predecessor's content is preserved as historical record.
Accepted → Deprecated
Terminal phase-out without a successor — the requirements described are being removed from the project's scope, not replaced. Manual flip; once Deprecated, no further transitions are allowed.
Any state → Blocked
Triggered by a triage card or an upstream-block signal (an external system down, a vendor bug, a contractual review pending). Reversible via Blocked → originating-state. The originating state is recorded in the artifact's <spec-changelog> at flip time.
Blocked → originating state
When the blocker resolves, the artifact returns to whatever state it was in when Blocked was entered. Recorded in <spec-changelog>.

For artifacts that are not a specs/<spec-id>/ spec slice (principles, the meta-spec itself, triage logs, inbox) — including when they carry an execution-only tasks.html tracker for folded change tasks per REQ-CHANGE-006 — the Draft → Accepted trigger is an explicit author affirmation that the artifact is the operative contract for the project; the execution tracker's checkboxes do not drive their status. The author records the affirmation as a one-line <spec-changelog> entry naming the date and the reason.

Transitions not in the list above are forbidden. In particular, a Superseded or Deprecated artifact MUST NOT transition to any other state — those are terminal. An Accepted artifact MUST NOT transition back to Draft or In Review; if amendments are needed, the path is /spectastic.propose against the live spec, not a status downgrade.

Every transition MUST append a one-line entry to the artifact's <spec-changelog> naming the old state, the new state, the date, and the triggering condition or gesture.

5 · Risk register

REQ-LIFECYCLE-004 is a must-tier requirement, so the adversarial pass fired. One <spec-risk> per finding; status= stays identified until the author dispositions it. /spectastic.apply refuses while any risk is identified.

Hard-coding the recorded reviewer's shape as "name · handle, the same shape as Owner" elevates a cosmetic format to MUST where no requirement defines the Reviewers format — so the first reviewer recorded by email, a GitHub URL, or as a two-person panel violates the literal MUST and triggers a needless re-propose.

Delta op="modified" target="REQ-LIFECYCLE-004", the In Review → Accepted clause: "filling the Reviewers field … (as name · handle, the same shape as Owner)".

Mitigated — the post-state was softened: the MUST is now "a human reviewer is named," with the recording shape explicitly the author's choice (name, handle, or both). The format is illustrative, not binding.

The rule reads against "any artifact," but REQ-LIFECYCLE-004's own tasks-less clause routes the meta-spec / principles / triage / inbox through an author-affirmation Draft → Accepted path with no reviewer — so on those artifacts the new MUST is either dead or invites a future reader to demand a reviewer on a solo affirmation flip.

REQ-LIFECYCLE-004 tasks-less clause ("the Draft → Accepted trigger is an explicit author affirmation … checkboxes do not drive their status") vs. the amended MUST.

Mitigated — the clause now lives entirely inside the In Review → Accepted definition and adds an explicit carve-out: artifacts that reach Accepted by author affirmation rather than through In Review have no separate reviewer and the clause does not apply. The rule simply never fires on the author-affirmation path.

Deferring the non-empty-Reviewers validate rule leaves the MUST enforced only by author discipline — the same slot the proposal admits sits empty across all live specs — so a Reviewed-by trailer named "honest" could inherit a field nothing guarantees was filled.

§2 Out-of-scope: "A validate rule enforcing a non-empty Reviewers field … enforcement stays author discipline for now. Deferred."

Addressed — the out-of-scope item now states the trailer's honesty does not rest on this rule: G-004 derives Reviewed-by only from a populated field and omits it otherwise (never faked), so an unfilled field yields no trailer, not a false one. The validate assist remains a worthwhile-but-separate hardening.
