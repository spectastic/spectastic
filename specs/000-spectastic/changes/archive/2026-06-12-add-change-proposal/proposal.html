Add change-proposal workflow

Introduce a PR-shaped change-proposal artifact and the two slash commands that drive it.

Status Applied Change ID 2026-06-12-add-change-proposal Spec 000-spectastic v0.1 Targets 4 requirements (1 modified, 1 removed, 1 renamed) + 2 added Author Brian Corbin · brian@example.com Created 12 Jun 2026 Read time

Today, evolving a spectastic spec means editing spec.html in place and writing a free-form note in the changelog. Fine for solo work, fragile under review. This proposal introduces a structured change-proposal artifact: a folder (specs/<id>/changes/<date>-<slug>/) containing one proposal.html with intent, scope, approach, deltas, and tasks. Deltas are typed via the op attribute on a new <spec-delta> element, machine-readable and unambiguous. The post-state of every changed requirement renders inline so reviewers see what they're approving without consulting git diff.

Add change-proposal workflow

Applied

1 · Intent

Spec-driven projects evolve in increments. Today, evolving a spectastic spec means editing spec.html in place and writing a free-form note in the <spec-changelog>. That's fine for solo work but doesn't survive review: a PR mixes "what's the new spec" with "why we changed it" and forces reviewers to reconstruct intent from a diff.

A structured change-proposal artifact fixes this. The proposal lives next to the spec it modifies, declares its intent, and ships its deltas in a typed form. On apply, the deltas fold into the live spec; the proposal folder is preserved verbatim under changes/archive/ so future readers can see why a requirement is shaped the way it is.

2 · Scope

In scope

  • A new <spec-change> wrapper element and a typed <spec-delta op="…"> with four ops: added | modified | removed | renamed.
  • A templates/proposal.html scaffold and one worked examples/proposal.html.
  • Two new slash commands: /spectastic.propose and /spectastic.apply.
  • Required reason and migration as HTML attributes on REMOVE deltas. Visible failure on omission; no silent fallback.

Out of scope

  • A spectastic validate CLI. Deferred to a separate proposal; this one relies on CSS-visible failure (e.g. missing op shows MISSING OP) until a validator ships.
  • A spectastic init installer. Separate proposal.
  • Detect-and-pick / unified /spectastic.next action command. Out for now; revisit alongside a lightweight triage-style sniffer.
  • Enforcement hooks. Future work.

3 · Approach

Each change lives at specs/<spec-id>/changes/<YYYY-MM-DD>-<slug>/proposal.html. The file uses the same design system as every other spectastic artifact, with two new elements:

<spec-change>
Wrapper. Holds the proposal's intent, scope, approach, deltas, tasks. Status pill at the top reflects proposal lifecycle: proposed → under-review → approved → applied → withdrawn.
<spec-delta op="…" target="…">
One per requirement touched. op is the schema: added | modified | removed | renamed. target is the requirement ID and renders as a clickable badge that scrolls (in-page) or navigates (cross-page) to the target in the live spec.

Three load-bearing design choices:

  1. Typed ops, not hash counts. An unknown or missing op renders the visible label MISSING OP — failure is loud, not silent.
  2. Inline rendered preview. ADD and MODIFY deltas embed a full <spec-requirement> showing the post-state exactly as it'll appear when archived.
  3. RENAME is rare by construction. Spectastic requirements are identified by stable id= attributes; renaming the human-readable name is just a content edit. The RENAME op only handles changes to the ID itself.

On /spectastic.apply, deltas fold into the live spec.html: ADD appends the embedded <spec-requirement> in the right section; MODIFY replaces the matching ID's body; REMOVE deletes the requirement (preserving the proposal as history); RENAME swaps the ID across the spec. The change folder moves to specs/<id>/changes/archive/<date>-<slug>/ preserved verbatim; the spec's <spec-changelog> gets an entry pointing at the archived proposal.

4 · Deltas

Four deltas, one per op. Click any target badge to jump to the live spec.

Add a new requirement to the Format section establishing the change-proposal artifact.

Spec evolution MUST happen via change-proposal artifacts at specs/<spec-id>/changes/<YYYY-MM-DD>-<slug>/proposal.html. Each artifact MUST use the <spec-change> wrapper and contain at least one <spec-delta>.

Rationale

One proposal per discrete change, reviewable as a single file. The PR-shaped folder structure scopes review cleanly, and folding intent, scope, approach, deltas, and tasks into one document preserves spectastic's single-file principle.

Add a second requirement codifying the delta schema.

Each <spec-delta> MUST carry an op attribute equal to one of added | modified | removed | renamed, and a target attribute naming the requirement ID it touches. For op="removed", the delta MUST also carry reason and migration fields — empty or missing renders visibly broken.

What changes: add the change-proposal phase alongside the original four templates. The change is additive — no existing template is removed.

The tooling MUST ship five templates corresponding to the spec-driven lifecycle: principles.html, spec.html, design.html, tasks.html, and proposal.html. Each MUST use the same design system.

Remove the deferred standalone-CLI requirement REQ-TOOL-002.

Reason
The deferred CLI was reserved for editors that don't host Claude Code. With the change-proposal workflow now in scope, the two operations that mattered (propose, apply) ship as slash commands. A future spectastic CLI may still arrive — it should not be back-blocked by a placeholder requirement.
Migration
If you were waiting on a CLI as described in REQ-TOOL-002, use /spectastic.propose and /spectastic.apply from Claude Code today. A standalone CLI, if proposed later, will get its own requirement ID under a fresh topic prefix.

Rename REQ-RENDER-003→REQ-THEME-001. The dark-mode requirement is the seed of a "theme" topic; future theme requirements (light/dark token contracts, print stylesheet rules, accessibility modes) belong under the same prefix.

Reason
Topic-grouping IDs is how spectastic keeps requirements discoverable. Theming has grown beyond a single rendering concern.

The default theme SHOULD support a dark-mode toggle that flips a single html.dark class — no per-element overrides required.

6 · Open questions

  1. Cross-file target navigation. Clicking a delta target inside a proposal scrolls within the page if the requirement is embedded inline (ADD / MODIFY), or navigates to ../spec.html#<id> if not. Acceptable, or do we want proposals to always link forward to ../spec.html for consistency?
  2. Archived proposals' link integrity. When an archived proposal references a now-renamed ID, do we rewrite the archive on rename (breaking "preserved verbatim") or accept that archive links may point at the new ID via redirect? Lean toward preserving verbatim; a future validator surfaces the breakage instead of silently rewriting.
  3. RENAMED scope. Currently only an ID rename. Should it also handle topic-prefix migrations (e.g. moving 20 requirements from REQ-RENDER-* to REQ-THEME-*)? Probably yes; design TBD.
