Sibling-bundling rule: spec.html, plan.html, tasks.html share one status

Applied

1 · Intent

The lifecycle FSM we landed yesterday (2026-06-15-lifecycle-state-transitions) closed T-001 on spec.html status drift, but left a structural gap on the sibling artifacts. REQ-LIFECYCLE-004's Draft → Accepted trigger names "the last unchecked <input type='checkbox'> in the artifact's tasks.html" — which only fits when the artifact is the spec.html. The tasks-less clause that follows ("for artifacts without a tasks.html...") explicitly handles principles, the meta-spec, triage logs, and inbox. plan.html and tasks.html sit between: they belong to a spec that does have a tasks.html, but it's not their tasks.html.

The audit in T-002 exposes the consequence: nine sibling artifacts across specs 002 / 003 / 004 stuck in Draft after their parent specs shipped end-to-end. Two reinforcing failures. First, the FSM never describes a path for plan/tasks to transition. Second, even on spec.html the LLM-driven last-tick prompt is fragile when manual user gates interleave with code tasks — spec 004 drained to T-907 without the flip prompt firing because remaining tasks (T-310, T-905) were manual gates that paused the drain before "the last one" was reached.

2 · Scope

In scope

  • Add REQ-LIFECYCLE-005 declaring that for any spec slice, the spec.html, plan.html, and tasks.html artifacts share a single bundled status — one author confirmation per transition flips all three siblings, with matching one-line <spec-changelog> entries landing on each.
  • Update commands/spectastic.implement.md step 8 so the bundle-trigger condition (zero remaining unchecked <input type="checkbox"> in tasks.html) is evaluated after every tick rather than asking the LLM to recognize "the last one." Makes the trigger deterministic.
  • Hotfix the four stuck artifacts at apply time whose bundles are legitimately drainable today: 002 plan + tasks → Accepted; 003 plan + tasks → Accepted. (Each spec.html in 002 / 003 is already Accepted from the T-001 hotfix; the plan + tasks pair simply catches up.) Each gets the matching changelog entry per REQ-LIFECYCLE-004's last-paragraph requirement.

Out of scope

  • Modifying REQ-LIFECYCLE-004 itself. The new rule operates on top of -004; the existing transitions and trigger semantics for spec.html stay as written.
  • Bundling non-task artifacts (principles, meta-spec, triage logs, inbox). They keep their own author-affirmation trigger from -004's tasks-less clause.
  • Cross-spec bundling. Each spec slice has its own bundle; one slice's status never tracks another slice's status.
  • Touching <spec-change> proposal status values (proposed → under-review → approved → applied → withdrawn). Those are a different lifecycle owned by REQ-CHANGE-*.
  • Flipping the 004-npm-publish-workflow bundle. T-905 (manual PR smoke for SC-003 — open a test PR that breaks a test, verify the dry-run job fails before publish-dry-run, close without merging) is still unchecked. Under REQ-LIFECYCLE-004's trigger semantics, the 004 bundle cannot legitimately flip Accepted while a task remains unchecked; this proposal honours that. 004's spec + plan + tasks stay Draft until T-905 is verified and ticked, at which point the bundle flip fires via REQ-LIFECYCLE-005 as designed.
  • The proposal triggers a 0.1.0-pre.5 publish (since updating commands/spectastic.implement.md changes the bundled CLI templates). That republish happens as a follow-up commit; it's not part of this proposal's apply step.

3 · Approach

Single ADD delta. REQ-LIFECYCLE-005 is a small bundling rule that defers to -004 for the trigger (last-tick in tasks.html, plus explicit author confirmation) and just says "when the spec.html flip happens, the plan.html and tasks.html flip with it." No new state semantics; no new trigger mechanics; one new invariant.

The command-prose update lives outside the spec delta — it's a markdown edit under commands/. Captured as a task in §6. The change is: replace step 8's narrative-driven "check whether this was the last tick" with a deterministic "count remaining unchecked checkboxes after this tick; if zero, fire the bundled flip prompt." Same UX from the author's perspective; reliable trigger from the LLM's perspective.

The nine-artifact hotfix lands in the apply step. The proposal's narrative is the affirmation gesture for these specs catching up — 002 and 003 shipped before the FSM existed; 004 shipped this session. All three sets of plan / tasks artifacts (and 004's spec.html) flip Draft → Accepted at apply time, each with a matching changelog entry citing this proposal.

4 · Deltas

What changes: A new MUST requirement establishing sibling bundling for the spec / plan / tasks artifact trio. Operates on top of REQ-LIFECYCLE-004 (same trigger, same affirmation gesture); just states that the flip propagates to siblings.

The three artifacts of a single spec slice — spec.html, plan.html, and tasks.html under specs/<spec-id>/ — MUST share a single bundled lifecycle status. When the spec.html status transitions per REQ-LIFECYCLE-004, the plan.html and tasks.html status MUST transition to the same value in the same gesture. One author confirmation per transition flips all three siblings; matching one-line <spec-changelog> entries MUST land on each artifact naming the old state, the new state, the date, and the triggering condition.

The bundle is the natural unit of "this spec slice." Splitting status across the three artifacts has no operational meaning — a spec.html cannot be Accepted while its plan.html is Draft without inviting drift. The bundle rule makes the natural relationship explicit and prevents the gap surfaced in T-002.

Cross-spec bundling is not implied: each spec slice has its own bundle; one slice's status never tracks another slice's. Non-task artifacts (principles, the meta-spec, triage logs, inbox) keep their own author-affirmation trigger from REQ-LIFECYCLE-004's tasks-less clause — they are not part of any sibling bundle.

/spectastic.implement's last-tick step MUST evaluate the bundle-trigger condition (zero remaining unchecked <input type="checkbox"> in the spec's tasks.html) after every tick taken while the spec's status is Draft, not only when the LLM heuristically recognizes "the last one." Scoping the predicate to the Draft state preserves REQ-LIFECYCLE-004's "last unchecked checkbox is ticked" transition semantics — once the bundle transitions out of Draft, a re-ticked box (a hotfix re-tick on an Accepted spec, an unticked-then-reticked manual gate) does not re-fire the bundled flip prompt. The deterministic evaluation closes the LLM-fragility failure mode where last-tick goes unnoticed when manual gates interleave with code tasks, without introducing a re-confirmation loop on already-flipped specs.

5 · Risk register

Adversarial pass auto-fires per the heuristic (must-tier added: REQ-LIFECYCLE-005 declares priority="must"). Three findings to be embedded below; status starts at identified and transitions on author commitment.

Bundle invariant collapses the moment a plan amendment needs its own review cycle

Concern. REQ-LIFECYCLE-005's "one author confirmation per transition flips all three siblings" forbids a plan.html or tasks.html from ever holding a state its spec.html doesn't share. The proposal's Out-of-scope explicitly rules out "Modifying REQ-LIFECYCLE-004 itself" — but -004 already lists Accepted → In Review as a Draft-only path, so the day someone needs to flip an Accepted plan back to In Review for a re-plan (without dragging spec.html with it), the bundle rule and -004's terminal-Accepted rule jointly leave no legal move except authoring a new spec slice.

30-day frame. In 30 days the first plan-only revision will arrive (a new ADR, a vendor swap) and the author will quietly violate -005 with a solo plan flip rather than re-spec the whole slice, normalising the bundle as theatre.

Author response — mitigated. The bundle status is a readiness affirmation, not a content lock. New ADRs, refined risks, additional tasks accrete inside the Accepted state without constituting a lifecycle transition — the bundle rule governs the status pill, not the artifact contents (mirroring how <spec-changelog> already works). A plan amendment that genuinely needs Accepted → In Review (a fundamental ADR being reconsidered) drags the spec back to In Review too, because the readiness affirmation no longer holds for any of the three siblings. The intended semantics are preserved without further -004 modification; -005's third paragraph already carries the cross-spec carve-out and the non-task-artifact carve-out that anchor this reading.

"After every tick" deterministic re-evaluation contradicts -004's last-tick trigger wording

Concern. REQ-LIFECYCLE-004 names the trigger as "when the last unchecked <input type='checkbox'> in the artifact's tasks.html is ticked" — a transition event, not a steady-state predicate. REQ-LIFECYCLE-005's fourth paragraph re-defines the implement trigger as "zero remaining unchecked checkboxes after every tick", which fires identically on the genuine last tick and on every tick taken in a tasks.html that was already drained (e.g. a re-opened-then-re-closed box, a hotfix re-tick). The proposal claims to "operate on top of -004" but is silently redefining -004's trigger semantics inside a -005 paragraph.

30-day frame. Within a month a re-ticked box on an already-Accepted spec will re-fire the bundled flip prompt, and the team will discover the "deterministic" rule is actually a re-confirmation loop that -004 never authorised.

Author response — mitigated. Proposal amended in place. REQ-LIFECYCLE-005's fourth paragraph now scopes the post-tick predicate to "after every tick taken while the spec's status is Draft", with an explicit clarification that hotfix re-ticks on already-flipped Accepted specs do not re-fire the bundled flip prompt. This preserves -004's transition-event semantics while still closing the LLM-fragility failure mode — which only matters in the Draft phase, when the bundle has not yet flipped.

Nine-artifact retroactive hotfix is smuggled in under a forward-looking rule change

Concern. §2 Scope's third in-scope bullet — "Hotfix the nine stuck artifacts at apply time: 002 plan + tasks → Accepted; 003 plan + tasks → Accepted; 004 spec + plan + tasks → Accepted" — bundles a multi-spec data migration into a meta-spec rule proposal. 004's spec.html has never had its own last-tick confirmation gesture (per T-002 the drain stopped at T-907 with manual gates outstanding), so its inclusion isn't a -005 consequence but a separate author judgement being smuggled through the apply step. Mixing the forward rule with backfill of three other specs' lifecycle records means a future reviewer can't tell whether the rule itself was approved or just the convenient cleanup.

30-day frame. In 30 days, when someone audits why 004's spec.html flipped Accepted without satisfying -004's stated trigger, the answer will be "the -005 proposal did it as a side effect" — and the meta-spec's lifecycle audit trail will have its first asterisked entry.

Author response — mitigated. Verified empirically: 004's tasks.html has T-905 (manual PR-breaking smoke for SC-003) still unchecked. Proposal amended — §2 now scopes the hotfix to four artifacts (002 plan + tasks, 003 plan + tasks), with an explicit Out-of-scope bullet naming T-905 as the gating condition for 004's bundle. §6 Tasks updated to match. The remaining four-artifact hotfix is a legitimate REQ-LIFECYCLE-005 consequence: each pair's parent spec.html is already Accepted from the T-001 hotfix; the siblings catch up under the new bundle rule. 004's bundle flips later, when T-905 verifies and ticks, under the same rule.
