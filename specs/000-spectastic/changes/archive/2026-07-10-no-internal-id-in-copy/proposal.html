A requirement owner for the no-internal-id-in-copy rule

Applied

1 · Intent

Every folded source-scan rule in spectastic validate traces to a meta-spec requirement: skill-metadata-shape to REQ-TOOL-004, date-format to REQ-FORMAT-005, the quarantine and drift gates to their FRs. The new no-internal-id-in-copy rule — which landed this session to fix the copy-leak defect in triage T-017 — is the one exception: it rests on the principle (P-10) alone, with no requirement of its own. That is a deliberate temporary state, recorded in T-017's Closed-by, because the meta-spec is Accepted and P-6 locks it: a new requirement must arrive through this proposal cycle, not a hand-edit.

This change closes that loop. It ADDs REQ-FORMAT-006, binding the P-10 invariant to a checkable rule on the meta-spec — the P-8 "guarantees live in the kernel/CI" shape made contractual. The rule, its test, and the 30-site scrub already exist; this proposal gives them the requirement they should have traced to from the start.

2 · Scope

In scope

  • Add REQ-FORMAT-006 to the REQ-FORMAT-* group: "the tool talking" (CLI help, error/diagnostic messages, tool-managed markers) MUST NOT surface spectastic's internal ids, while a spec/plan artifact citing its own governing ids is legitimate provenance per P-3. Enforced at error severity over the CLI's .description/.option/.argument help strings — a floor, not a cap; the message surface is permanently review-caught (the honest P-8 ceiling).
  • The requirement owns the no-internal-id-in-copy rule (copyLeakFindings + the CLI's scanCopyLeak) landed under T-017 and refined this session — widened to scan .argument with the sanctioned 001-auth-service placeholder allowlisted — plus its test. Verified in §6.
  • Trace the requirement to its source invariant (P-10) and its originating triage (T-017).

Out of scope

  • Linting a downstream project's application copy — spectastic cannot see it, and a spec artifact legitimately cites its own ids as anchors per P-3. The invariant binds downstream via P-10; enforcement there is review-caught. defer-to=never
  • Extending the rule to scan runtime finding message:/fixHint: fields — permanently review-caught by design, not a deferred check: a rule citing the requirement it enforces would false-positive, so that surface is judged by review, not linted. defer-to=never
  • Re-authoring the rule or the scrub from scratch — landed under T-017 and refined this session (rule widened to .argument; three artifact-copy scrubs reverted as legitimate provenance). §6 verifies, it does not re-author. defer-to=never

3 · Approach

One ADD delta, sited in the REQ-FORMAT-* group beside the siblings it most resembles — REQ-FORMAT-005 (a format contract that names its own validate rule inline) and REQ-FORMAT-004. The requirement fixes the contract the rule already enforces: no internal artifact id on any surface a user reads.

The requirement is a genuine must: it descends directly from P-10, a MUST-NOT invariant, and the rule ships at error severity behind the pre-commit gate. Crucially — and exactly as REQ-FORMAT-005 separated its MUST from its rule's warn severity — the MUST is not weakened by the rule's bounded reach. The rule mechanically covers only the one surface spectastic can see and judge without ambiguity: its own CLI .description/.option help strings. It deliberately does not scan finding messages (where citing the enforced requirement is legitimate) or a downstream project's application copy (unseeable). Those remain review-caught — the honest P-8 ceiling, recorded not hidden, the same posture as the fat-core/thin-CLI convention (T-016). The requirement states both the mandate and the ceiling so neither is mistaken for the other.

This proposal is retroactive by design: the rule, the test, and the scrub landed under T-017 before this requirement is written, because the fix could not wait on the Accepted meta-spec's change cycle and P-10 was sufficient to ship against. The adversarial pass (§5) then sharpened both the requirement and the shipped rule in the same session — the wording moved from an enumerated list of forbidden surfaces to the abstract tool-talking-vs-artifact line, the rule gained .argument coverage, and three over-scrubbed artifact-provenance ids were restored. §6 verifies the landed work matches that final wording.

4 · Deltas

One <spec-delta> for the requirement added. target= links to the live spec. op="added"; the target ID does not yet exist in the live spec.

Copy that is the tool talking — text spectastic emits or writes for a user to read — MUST NOT surface spectastic's own internal artifact ids (spec numbers and slugs, REQ-*, FR-*, NFR-*, SC-*, T-*, P-*, D-*). The dividing line is the contract: a spec or plan artifact citing its own governing ids as anchors is legitimate provenance per P-3, not a leak — this explicitly includes a generated <spec-changelog> entry and the author-supplied apply summary the kernel writes (REQ-CHANGE-008), which are the human's voice. What the tool itself says — CLI --help text, error and diagnostic messages, and tool-managed markers (a pre-commit hook stamp, a managed-file marker) — carries no internal id; its provenance lives in code comments and the artifact trail.

A no-internal-id-in-copy validate rule MUST enforce, at error severity folded into every validate run and blocked by the pre-commit gate, the one tool-talking surface spectastic can see and judge without ambiguity: the string arguments of its own CLI .description/.option/.argument help calls, where an illustrative argument slug uses the sanctioned neutral placeholder 001-auth-service. This is a floor, not a cap — the rule MUST cover at least that surface. The remaining tool-talking surfaces (runtime finding messages, tool-managed markers) stay review-caught, permanently and by design: a rule scanning finding message: copy would false-positive on a finding legitimately naming the requirement it enforces, so that surface is judged by review, not linted. This ceiling MUST be recorded, not hidden — the honest P-8 posture — and is not a deferred check awaiting a future rule. The invariant binds spectastic's own tooling and every downstream project alike (P-10); a downstream project's application copy is unseeable by spectastic, so there it is review-caught too.

Rationale

Sourced from P-10 and meta-spec triage T-017 — spectastic --help shipped the tool's own spec numbers ((037), (spec 042), Spec 043.) across 30 sites. The requirement is a genuine MUST descending from a MUST-NOT invariant; the rule's error severity matches. It is stated as an abstract invariant with the enforced surface named separately as a floor, rather than an enumerated list of forbidden surfaces, so it neither freezes commander method names into a contract nor collides with REQ-CHANGE-008's id-citing author summaries — the two seams the adversarial pass surfaced (§5, R-001/R-002). The tool-talking-vs-artifact line is the same P-8 honesty the fat-core/thin-CLI convention carries (T-016). Parallels REQ-FORMAT-005's MUST-plus-named-rule shape and REQ-TOOL-004's "a rule gives the MUST teeth" pattern.

5 · Risk register

Populated by the adversarial risk pass (this proposal's ADD post-state declares priority="must"). One <spec-risk> per finding. status= defaults to identified; apply refuses until each transitions to accepted, mitigated, or rejected, recording the dispositioner in by=.

The MUST-tier requirement pins its mechanically-enforced surface to specific commander method names — "its own CLI .description/.option help strings" — freezing a mutable implementation detail into a permanent contract. Worse, the gap is live on day 0: T-017's own Actual record lists two .argument-example slugs that leaked (verify.ts's 021-verify-view, run.ts's 041-foo), and this proposal's §6 T-002 codifies that "an out-of-scope .argument example passes." So the requirement asserts a broad MUST-NOT while its named enforcement surface knowingly excludes a documented leak class — the next .argument spec-slug ships green under a requirement that claims to forbid it.

Delta op="added" target="REQ-FORMAT-006": "the machine-visible surface spectastic can judge without ambiguity — its own CLI .description/.option help strings." Cross-cite T-017 Actual: "2 argument-example slugs (verify.ts's own 021-verify-view, run.ts's 041-foo)."

Mitigated. Two moves. (1) The requirement was reworded to state the invariant abstractly — "the tool talking" vs an artifact citing its own anchors — with the enforced surface named separately as a floor, so it no longer freezes commander method names into the contract. (2) The gap is closed mechanically, not just contractually: the rule now scans .argument help too, with the sanctioned neutral placeholder 001-auth-service allowlisted (indistinct from a real slug by pattern), so a genuine slug like 021-verify-view in argument help now trips the rule while the placeholder passes — verified by a CLI-level planted-leak check and a unit test. The day-0 leak class is enforced, not merely documented.

REQ-FORMAT-006's normative MUST-NOT enumerates "generated changelog lines" among the surfaces on which an internal artifact id must never appear. REQ-CHANGE-008 requires the apply kernel to write the live-spec <spec-changelog> entry from an author-supplied one-line summary — and those summaries legitimately and routinely cite REQ-*, T-*, and proposal slugs (the meta-spec changelog is wall-to-wall ids; the apply line for this proposal will itself cite REQ-FORMAT-006 and T-017). The P-3 carve-out lives only in §Scope/Rationale prose, not in the MUST-NOT sentence, so read as a checkable contract the prohibition contradicts REQ-CHANGE-008's MUST.

REQ-FORMAT-006: "…or the copy written into files a user reads or commits (hook markers, managed-file stamps, generated changelog lines)." Live spec REQ-CHANGE-008: the kernel MUST accept an author-supplied one-line summary for the live-spec <spec-changelog> entry, "so the changelog's human voice is preserved."

Mitigated. The contradiction is removed at the source: a spec/plan artifact citing its own governing ids as anchors is legitimate provenance per P-3, not a leak — so "generated changelog lines" was dropped from the forbidden surfaces entirely, and the normative sentence now explicitly names the generated <spec-changelog> entry and the author-supplied apply summary (REQ-CHANGE-008) as the human's voice. Consistent with that, the three artifact-copy scrubs T-017 had made were reverted: implement.ts's bundle-flip changelog line (REQ-LIFECYCLE-005), graduate.ts's generated spec changelog (023-explore-graduation) and plan grounding prose (REQ-LIFECYCLE-006) keep their provenance ids. The MUST-NOT now binds only "the tool talking," which never contradicts REQ-CHANGE-008.

The §Scope out-of-scope item defers scanning runtime messages and generated-artifact prose to TBD-copy-leak-message-scan — an explicit "not yet" that anticipates a future in-scope extension. But the in-scope requirement text does not merely defer that surface; it codifies its non-enforcement as a normative clause ("runtime messages and generated-artifact copy are review-caught, not linted"). That bakes a temporary enforcement ceiling into a MUST-tier contract: the day TBD-copy-leak-message-scan lands, it contradicts the requirement it was meant to extend, forcing a re-amendment through the full propose/apply cycle against the P-6-locked spec.

§2 out-of-scope[2]: "Extending the rule to scan runtime finding message:/fixHint: fields and generated-artifact prose … defer-to=TBD-copy-leak-message-scan" — set against the delta clause "so runtime messages and generated-artifact copy are review-caught, not linted — the honest P-8 enforcement ceiling."

Mitigated. The premise — that the ceiling is temporary — is what drove the contradiction, and it is false: a rule scanning finding message: copy would false-positive on a finding legitimately naming the requirement it enforces, so that surface is review-caught permanently and by design, not awaiting a future check. The TBD-copy-leak-message-scan deferral was therefore removed (defer-to=never), so no future extension exists to contradict the requirement. The requirement is also reframed as a floor, not a cap (the rule MUST cover at least the CLI help surface), so tightening it later never needs a re-amendment either.
