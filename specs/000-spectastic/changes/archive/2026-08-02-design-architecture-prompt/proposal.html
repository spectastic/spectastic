The architecture-pattern prompt gets a requirement

Applied

1 · Intent

The agent-architecture survey found that the spec-driven leaders prompt for architecture per project and never prescribe a house pattern, and recommended pattern-awareness at design time: a bounded decision-phase question landing an ADR. Its TBD-plan-architecture-prompt named three deliverables — a requirement on the verb, a command-markdown step, and a template cue.

Checking what actually shipped: commands/spectastic.design.md carries the step, and templates/design.html carries the Architecture row in its technical-context summary. The requirement does not exist. The meta-spec has no REQ-* mentioning an architecture pattern at all.

That gap is not cosmetic, and this project has already written down why. Triage T-009 records that a command's markdown is advisory to the model — two pilots confirmed descriptions cannot force invocation — and concludes that guarantees for mandatory steps live in the kernel or CI, never in command markdown. P-8 says the same at principle level. A behaviour that exists only in markdown, with no requirement behind it, is one edit away from silently disappearing, and nothing in the estate would record that it was ever intended.

The requirement does not make the prompt a guarantee — nothing here can, and pretending otherwise would be the exact overclaim P-8 exists to prevent. What it does is make the intent durable and reviewable: the behaviour becomes something the estate asserts and a reviewer can hold the command markdown to, rather than an unwritten habit that happens to be implemented today.

2 · Scope

In scope

  • One requirement on the /spectastic.design procedure covering the architecture-pattern prompt, what it records, and where standing cross-feature rules belong instead.
  • Its ceiling stated in the requirement itself: the prompt is advisory, and enforcing a chosen pattern is a separate effort.
  • Correcting three stale section cross-references found while verifying the landed halves.

Out of scope

  • An architecture fitness function. That is TBD-architecture-fitness-function, planted by the same survey as the heavier P-8 guarantee half, and the requirement below explicitly declines to imply it.
  • A house catalog of patterns. The survey's D-001 is prompt, don't prescribe, and 050 FR-002 independently forbids recommending from a maintained catalog.
  • Making the pattern machine-readable. Today it is prose in a summary row and prose in a decision; giving it an attribute is a detection concern, deferred as TBD-boundary-map-detection.
  • Any change to the command markdown's substance. Its step already says what the requirement asks; only stale section numbers are corrected.

3 · Approach

Add the requirement under the LIFECYCLE prefix, where the other design-verb procedure requirements already sit — REQ-LIFECYCLE-006 (the grounding ledger) and REQ-LIFECYCLE-007 (the triage root-cause ladder). Both are phrased SHOULD, because both describe what a verb's procedure ought to do rather than a property a validator can check, and this one is the same shape. Matching them keeps the meta-spec's register consistent rather than introducing a stricter-sounding MUST that nothing could enforce.

No code changes. The behaviour is already implemented; what is missing is the record that it is required. The tasks are limited to the three stale section cross-references, which are wrong today regardless of this proposal and were found by reading the landed halves closely enough to confirm they matched.

4 · Deltas

One delta.

The /spectastic.design procedure SHOULD anchor an architecture pattern in its decision phase whenever the feature has more than one moving part, offering domain- and stack-appropriate contenders rather than a fixed house pattern, and a trivial single-module feature SHOULD skip the question. The chosen pattern SHOULD land as a <spec-decision> carrying grounding=, with its one-line summary filling the design's technical-context Architecture row, so the arrangement of the pieces is recorded before the stack picks that depend on it. Standing, cross-feature rules — dependency direction, keeping a framework out of a domain core — MUST NOT be recorded in a single design; they belong in the project's principles. This prompt is advisory: it nudges a deliberate, grounded choice and provides no enforcement that the chosen pattern is followed.

Rationale

The behaviour shipped in commands/spectastic.design.md and templates/design.html without a requirement behind it, leaving it resting entirely on command markdown — which triage T-009 establishes is advisory to the model and which P-8 excludes as a place guarantees may live. A behaviour with no requirement can be edited away with nothing recording that it was intended. Phrased SHOULD to match REQ-LIFECYCLE-006 and REQ-LIFECYCLE-007, the other design- and triage-procedure requirements, since a validator cannot check that an interview happened. The final sentence is deliberate: naming the ceiling inside the requirement stops a reader inferring that a recorded pattern is an enforced one, and keeps the honest split between this prompt and the fitness function that would actually hold a design to it.

5 · Risk register

The adversarial pass does not trigger: one should-tier addition, no removed delta, a single topic prefix. Recorded rather than skipped silently, since the heuristic's not firing is itself a judgment worth showing.

6 · Tasks

Scoped to this change only. All three are stale cross-references that are wrong independently of the requirement.

  • Correct the Architecture row's section references — it cites "the §6 decision that shapes §7"; decisions are §7 and project structure is §8 templates/design.html
  • Correct two stale section references in the design command — Complexity tracking is §10 not §8, and the architecture sketch sits in §5 not §7 commands/spectastic.design.md
  • Re-sync the command copies the harness actually loads, since a source under commands/ changed .claude/commands/

7 · Open questions

None outstanding. The requirement restates behaviour that already shipped and was reviewed when it did; the only judgment call — SHOULD rather than MUST — follows the two sibling verb-procedure requirements and the reasoning T-009 already recorded.
