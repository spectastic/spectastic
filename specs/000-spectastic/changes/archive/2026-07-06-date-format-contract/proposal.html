One date format — ISO in the attribute, DD Mon YYYY on the page

Applied

1 · Intent

Dates appear in nearly every artifact — <spec-meta> Created/Updated rows, <spec-changelog> entries, inline references. They are always wrapped in a <time> element and the datetime= attribute is, in practice, always ISO 8601. But the visible text is unowned: some rows render 2026-06-29, others 29 Jun 2026. The two forms sit side by side even within one spec (026's Created row vs its changelog), which reads as sloppiness in a tool whose whole point is calm, consistent artifacts.

The cause is a format-contract gap, not per-artifact carelessness. No requirement names the canonical display form, so each template and authoring session picks one. Normalizing the existing dates without fixing the contract would let the drift return on the next generated artifact — so the fix has to be a requirement plus an enforcing rule, with the corpus cleanup riding behind it.

2 · Scope

In scope

  • Add REQ-FORMAT-005: <time> datetime= is ISO 8601; visible text is DD Mon YYYY; enforced by a warn-level date-format validate rule.
  • The date-format rule + positive/negative fixtures.
  • Normalize the off-form date displays to DD Mon YYYY, per-file with a validate re-check gate — the deterministic display-equals-ISO rewrite and a residual pass for any other shape the rule flags; "done" is zero date-format warnings, not a fixed count.
  • Align the lifecycle templates so newly-generated artifacts emit the canonical form.

Out of scope

  • Localised or alternate date formats (locale-aware rendering, relative "3 days ago") — one canonical form, full stop. defer-to=never
  • Timestamps with a time-of-day component — the contract covers calendar dates; a fuller ISO timestamp is permitted in datetime= where a time is meaningful, but no artifact needs one today. defer-to=TBD-time-of-day-stamps
  • Promoting the rule to an error / CI hard-fail — it ships at warn (the ~215 drifted displays would otherwise break the SC-001 integration gate before cleanup drains). defer-to=TBD-guarantee-layer-spec

3 · Approach

One ADD delta, sited in the REQ-FORMAT-* group beside the sibling it most resembles — REQ-FORMAT-004, which likewise owns a format contract and names its own validate rule inline. The requirement fixes both halves of a date: the machine-readable datetime= attribute (ISO 8601, which consumers like reading-time and lifecycle sorting depend on) and the human-readable text (DD Mon YYYY).

DD Mon YYYY (zero-padded day) is chosen because it is already the corpus majority (375 occurrences vs 215 ISO) and the established changelog convention — the smallest-migration, least-surprising choice.

The requirement itself is a genuine must: a consumer that reads a date should be able to rely on both halves of the contract. That is a stronger commitment than REQ-FORMAT-004's advisory band, and this proposal does not borrow FORMAT-004's advisory authority for it. The rule's warn severity is a separate, migration-scoped choice, not a softening of the mandate: the ~215 drifted displays exist right now, so an error-level rule would break the SC-001 "zero error findings" integration gate before §6's normalization drains. Once the corpus is clean, the severity can be revisited (a candidate for the deferred strict-CI gate) — the MUST stands regardless.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec. op= is one of added | modified | removed | renamed; a missing or invalid op renders visibly broken.

Every date in an artifact MUST be wrapped in a <time> element whose datetime= attribute is a valid ISO 8601 date (YYYY-MM-DD, or a fuller ISO timestamp where a time-of-day is meaningful) and whose visible text renders in the canonical human form DD Mon YYYY — a zero-padded two-digit day, a three-letter title-case month, and a four-digit year, e.g. <time datetime="2026-07-06">06 Jul 2026</time> (not 6 Jul 2026). This holds uniformly across <spec-meta> Created/Updated rows, <spec-changelog> entries, and inline dates. A date-format validate rule SHOULD warn (not error) when a <time>'s display text departs from DD Mon YYYY or its datetime= is not ISO 8601.

Rationale

The datetime= attribute was ISO 8601 only by habit and the visible text was unowned, so the two forms drifted side by side — 2026-06-29 in one row, 29 Jun 2026 in the next (T-011). DD Mon YYYY is the corpus majority (375 vs 215) and the changelog convention, so it is the least-migration canonical choice (zero-padded day, e.g. 06 Jul 2026); ISO stays in datetime= for machines. The requirement is a genuine MUST; the rule's warn severity is a migration-scoped choice — it avoids breaking the SC-001 integration gate on the ~215 not-yet-normalized displays before the cleanup drains — not a softening of the mandate.

5 · Risk register

Populated by the adversarial risk pass (this proposal's ADD post-state declares priority="must"). One <spec-risk> per finding. status= defaults to identified; apply refuses until each transitions to accepted, mitigated, or rejected, recording the dispositioner in by=.

The canonical form DD Mon YYYY never resolves day-padding, and the corpus is already split — so within 30 days the date-format rule either warns on roughly half of every artifact's dates or the normalization script silently rewrites the established convention.

Delta body — "DD Mon YYYY — e.g. 29 Jun 2026"; yet this proposal's own Created row is 6 Jul 2026 (unpadded), principles.html uses 2 Jul 2026 (unpadded), and T-011 uses 06 Jul 2026 (padded). Every day 1–9 is ambiguous.

Mitigated. Padding is now pinned: DD is a zero-padded two-digit day — the delta states it explicitly (06 Jul 2026, not 6 Jul 2026), the §6 rule task warns on unpadded days, and the fixtures carry a single-digit-day boundary (6 Jul 2026 warns / 06 Jul 2026 clean). The zero-padded form was chosen over non-padded so days column-align. The normalization zero-pads days 1–9, and this proposal's own Created/changelog/footer stamps were corrected to 06 Jul 2026 to conform.

The proposal grounds REQ-FORMAT-005 by invoking REQ-FORMAT-004's "advisory posture" as precedent, but FORMAT-004 makes its whole contract advisory while FORMAT-005 elevates the display form to a hard priority="must" — so the sibling parallel it leans on is false.

§3 / rationale — "mirroring REQ-FORMAT-004's advisory stance" / "to match REQ-FORMAT-004's advisory posture" — but FORMAT-004 says "the amber band is advisory … never a hard gate," whereas FORMAT-005 is a MUST.

Mitigated. §3 and the delta rationale were reworded to own the MUST: the requirement is a genuine mandate; the rule's warn severity is a separate, migration-scoped choice (so the ~215 pre-cleanup displays don't break the SC-001 gate, revisitable once clean), not a softening. The FORMAT-004 advisory-band citation is no longer used as authority for the mandate — only for the sibling shape (a format contract that names its own rule).

The cleanup is scoped strictly narrower than the requirement it satisfies — the transform only rewrites <time> whose display already equals the ISO attribute, so any date in a third shape (bare-text footer dates, Jun 29 2026, padding variants) is untouched, leaving warn residue the proposal claims it drains; and one blunt pass sweeps 67 files including system-of-record principles.html/index.html.

§2 in-scope bullet 3 + §6 task — "Normalize the ~215 off-form date displays … a mechanical, scriptable pass" whose precondition (display == ISO) is a strict subset of the delta's universal "Every date … MUST be wrapped in a <time> … canonical human form."

Mitigated. The universal MUST stands; §2 bullet 3 and the §6 task were re-scoped to run the normalization per-file with a validate re-check gate — the deterministic display==ISO rewrite plus a residual pass for any other shape the rule flags (unpadded days, bare-text dates) — with "done" defined as zero date-format warnings, not a fixed count. The dropped "~215" figure no longer overpromises. System-of-record files (principles.html, index.html) run the same per-file gate, so a mis-rewrite of non-date <time> content is caught before commit.
