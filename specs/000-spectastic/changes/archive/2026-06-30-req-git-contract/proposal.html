The REQ-GIT contract

The git model is built and shipped (026 + 027) but unwritten as house law. Ratify it — the branch model, the commit grammar, and the opt-in default-off delivery — as a REQ-GIT-* family on the meta-spec.

Status Applied Change ID 2026-06-30-req-git-contract Spec 000-spectastic Author Brian Corbin · @briancorbinxyz Created 2026-06-30 Targets 3 new requirements (REQ-GIT-001..003) Read time

Three ADD deltas creating the REQ-GIT-* family: REQ-GIT-001 the branch model (the slice is the branch, NNN-slug; small revert-safe work stays on the current branch), REQ-GIT-002 the commit grammar (<verb>(NNN): scoped, unscoped <verb>: for spec-less verbs; humans-only authorship + a distinct Assisted-by for the AI), and REQ-GIT-003 the opt-in default-off delivery (config-gated, --commit/ --no-commit, validate-gated, no squash). This is the contract version of what 026 + 027 already implement — the git-strategy brief's downstream slice ②.

The REQ-GIT contract

Applied

1 · Intent

spectastic was already using a git grammar before anyone designed it — its history reads spec(NNN): / plan(NNN):, its branches matched their spec dirs. The git-strategy brief formalized that into slices; 026 built the opt-in git layer and 027 the attribution trailers. Both are Accepted and shipping.

But the model lives only in those feature specs and the code. The meta-spec — spectastic's operative contract — says nothing about it, so the grammar is convention-by-implementation: a new contributor or a future verb has no rule to honor. This change writes the model into the house spec as REQ-GIT-001..003, closing the "built but not ratified" gap. The deltas describe shipped behavior; nothing new is built.

2 · Scope

In scope

  • Add REQ-GIT-001 (branch model — creation + small-work exception), REQ-GIT-002 (the commit message contract — subject grammar + the humans-only / Assisted-by attribution rule), and REQ-GIT-003 (opt-in default-off delivery + the validate-gate + the layer-scoped no-squash guardrail).
  • Cite 026 / 027 as the implementing slices in each rationale.

Out of scope

  • The spectastic init --tools installer (brief ④) — the delivery installer, still deferred.
  • Splitting under the branch model (brief G-005) — owned by the W-2 slicer / /spectastic.split spec, blocked on the dependency layer.
  • Any change to the git layer's behavior — this is a contract that describes 026/027, not a modification of them.

3 · Approach

Three ADD deltas, one topic prefix. Each requirement states the rule and cites the 026/027 FR that implements it, so the contract and the code stay traceable. The seam is branch / message / delivery: REQ-GIT-002 owns the whole commit message contract — subject grammar (026) and attribution (027), since both govern what one commit says — keeping the verb→git map and the humans-only rule under the requirement they belong to rather than a fourth ID.

Priority must: the grammar, default-off, and validate-gate are hard rules, matching 026/027's already-shipped must-tier FRs. "You may use git automation" is optional; "if you do, it MUST be default-off and follow this grammar" is not.

4 · Deltas

Three new requirements. op="added" — none of these IDs exists in the live spec.

Branch model. Under branch-based automation (git.auto=branch+commit), spec MUST create the slice's branch named NNN-slug off the default branch when it opens the slice. Small, revert-safe work — just-do cards, triage list-intake, one-file hotfixes — MUST stay on the current branch (no branch created), reusing the existing just-do boundary.

This family binds spectastic's own git automation — what the verbs do when a developer opts in. A consuming project's hand-commits and its PR-merge strategy are its own; REQ-GIT does not govern them.
Rationale

The slice is the natural unit of review; the latent 018-explain pattern proved the shape. Branch creation + the small-work exception are implemented by 026 FR-003 / FR-005 (git-strategy G-002). Two parts of the model are described, not mandated, because nothing automates them today: the slice branch merges to the default branch when the spec flips Accepted, and proposals are intended to live on change/NNN-<date>-<slug> branches. Both are the developer's action (or a PR) — the intended workflow, not a conformance MUST — and stay descriptive until a future slice implements them.

Commit message contract (subject + attribution). An auto-commit's subject MUST follow <verb>(NNN): <subject> (Conventional Commits — the lifecycle verb as type, the spec id as scope) whenever a spec id is in play, and the unscoped <verb>: <subject> form when it isn't (triage list-intake, principles, an implement run draining an inbox just-do card). implement MUST emit one commit per drain invocation, not one per ticked task. Authorship of record is human only: when attribution trailers are written, spectastic MUST NOT emit an AI identity as Author, Co-authored-by, Reviewed-by, or Acked-by — the assisting model is acknowledged distinctly, and only, as Assisted-by: <model>. (Which trailers are emitted, and when, is the delivery concern of REQ-GIT-003 + git.trailers.)

Rationale

The grammar already speaks in the history; the unscoped form and the Assisted-by stance were settled in 027. Conventional Commits explicitly permits types beyond feat/fix — here the lifecycle verb is the (custom, permitted) type, the spec id the scope. Implemented by 026 FR-002/FR-007 + 027 FR-005/FR-006 (git-strategy G-003 + G-004).

Opt-in, default-off delivery. Git automation MUST be opt-in and default off: git.auto and git.trailers both default off, every verb MUST accept --commit/--no-commit, and with automation off no verb performs any git action. An auto-commit MUST be gated on a clean spectastic validate and compose after the P-6 state-gate and the explore quarantine (never around them). The git layer itself MUST NOT introduce squash-on-merge as a default, nor rewrite or squash existing default-branch history — per-verb commits are the legible record. This binds the layer, not the consuming project: how a project merges its own PRs (squash or not) is its choice; the contract is only that spectastic's automation doesn't squash for it.

Rationale

The house enforcement stance (opt-in, default off, documented loudly); per-verb commits are the legible record. Implemented by 026 FR-001/FR-004/NFR-002 (git-strategy G-003 §7 guardrails).

5 · Risk register

REQ-GIT-001..003 are must-tier, so the adversarial pass fired. One <spec-risk> per finding; status= stays identified until the author dispositions it (recording the by= dispositioner per the just-added REQ-CHANGE-004 rule).

As first drafted, REQ-GIT-001 mandated a branch merge trigger ("the slice merges to the default branch when its spec flips Accepted") as a MUST — but no 026 FR implements it (FR-003 governs branch creation only), so the contract claimed to "describe shipped behavior" while inventing an unimplemented rule. Day one, any Accepted-but-unmerged spec is silently non-conformant.

Delta op="added" target="REQ-GIT-001" — "the slice merges to the default branch when its spec flips Accepted (a proposal's change branch merges when Applied)".

Mitigated — the merge clause was removed from the MUST. REQ-GIT-001 now mandates only branch creation + the small-work exception (both shipped by 026 FR-003/FR-005); the merge-on-Accepted is described in the rationale as the intended developer/PR workflow, not an automated conformance MUST.

REQ-GIT-003's "no rewriting of default-branch history" globalized 026 NFR-002 (a MUST scoped to "the layer MUST NOT introduce…") into a project-wide mandate — over-constraining a consuming project that legitimately squash-merges its PRs into non-conformance with spectastic's meta-spec, and breaking the house pattern (REQ-CHANGE-004/005/006/008 ship should until incidents justify must).

REQ-CHANGE-004 (line 500) and siblings — all priority="should" with "re-evaluate after ≥N applications" — vs. the proposal's blanket global MUST.

Mitigated on the scope half — REQ-GIT-003 now binds the git layer ("the layer MUST NOT introduce squash-on-merge as a default, nor rewrite…"), with a sidenote that a project's own PR-merge strategy is its choice; the rule no longer reaches the consuming project. On priority: kept must — unlike the REQ-CHANGE rules codified "from one/zero data points," this ratifies behavior already shipped and test-proven by 026 + 027, whose implementing FRs are themselves must. (Author left identified to confirm the must call.)

Folding the humans-only / Assisted-by rule (027 attribution policy) into a requirement titled "commit grammar" (026 subject shape) mixed two slices' contracts under one ID, muddying the 026-vs-027 trace and implying authorship is a sub-topic of grammar rather than its own concern.

§2 In-scope item 1 — "REQ-GIT-002 (commit grammar, incl. the humans-only / Assisted-by rule)"; the delta's rationale then had to cite both 026 and 027.

Mitigated — REQ-GIT-002 is reframed as the commit message contract (subject + attribution), which coherently spans 026 (grammar) and 027 (attribution) since both govern what one commit says; the humans-only rule is also clarified as conditional on trailer emission (it doesn't mandate Acked-by, which stays 027's should-tier emission). A fourth requirement was considered and rejected — the author chose the three-way decomposition; "the commit message" is one coherent owner.
