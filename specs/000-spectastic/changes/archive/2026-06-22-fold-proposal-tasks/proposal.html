Fold applied-proposal tasks into the target's tasks.html

Apply accepts-and-routes; it never implements. A proposal's §6 tasks fold into the target's tasks.html, and /implement drains them.

Status Applied Change ID 2026-06-22-fold-proposal-tasks Spec spectastic-spec Author Brian Corbin · @briancorbinxyz Created 2026-06-22 Targets 4 requirements (1 added, 3 modified) Read time

Tasks from an accepted proposal have no formal execution home — REQ-CHANGE-003 even says /implement can drive the proposal's checkboxes directly, which is impossible (proposal §6 tasks are id-less and freeze on archive). This change makes the rule consistent and Linear-shaped: apply never implements — it folds §6 into the target's tasks.html (creating one if absent) as a provenance-linked <spec-task> phase, and /implement drains it. REQ-CHANGE-006 (new) states the rule; REQ-CHANGE-003 is fixed to point at the folded phase; REQ-LIFECYCLE-005 is amended so the meta-spec / principles may hold an execution-only tasks.html tracker.

Fold applied-proposal tasks into the target's tasks.html

Applied

1 · Intent

The lifecycle's promise is that each phase hands clean work to the next. It breaks at apply→implement: a proposal carries a §6 task list, but /spectastic.apply archives the proposal (frozen) and touches no execution queue, while /spectastic.implement only drains <spec-task id="T-NNN"> from a tasks.html. Proposal §6 tasks are plain id-less <li> that freeze on archive, so REQ-CHANGE-003's "/implement can target those tasks directly" is mechanically impossible. The work gets hand-copied or forgotten.

The fix is a single consistent rule grounded in how acceptance and execution separate everywhere: merging/accepting a change is not the same as doing it (CI/CD); a command should behave the same every time (least astonishment); and Linear — the inbox's inspiration — turns accepted action items into tracked issues in a project's list, never back into the triage inbox. So apply accepts-and-routes; /implement executes — uniformly, for every target.

2 · Scope

In scope

  • Apply folds a proposal's §6 tasks into the target's tasks.html as a new provenance-linked <spec-task> phase; it implements nothing.
  • Every target gets one: the meta-spec and principles may hold an execution-only tasks.html tracker, created on first fold.
  • The archived proposal §6 stays the frozen intent record; /implement drains the folded phase.
  • /implement's empty-drain discovery finds those trackers (specs/000-spectastic/tasks.html, principles-tasks.html).

Out of scope

  • The inbox / just-do — untouched; just-do keeps its crisp "small, no-proposal, revert-safe" meaning.
  • Routing deferred out-of-scope items into a roadmap / parking lot — a distinct Initiative-level slice, deferred.
  • Any new verb or custom element.

3 · Approach

On apply, after the proposal is archived, resolve the target's tasks.html (create it from templates/tasks.html if absent) and append a <section class="phase"> transcribing each §6 <li> to a <spec-task id="T-NNN"> (IDs continuing in a fresh hundred-range), with an inline provenance link to the archived proposal and a closing <spec-note> — the shape already demonstrated by Phase 5 of specs/020-vscode-extension/tasks.html. Apply executes none of it; /implement pulls the phase like any other.

This proposal is itself the first live case: the meta-spec has no tasks.html, so applying it creates specs/000-spectastic/tasks.html and folds the §6 below — the model demonstrating itself.

4 · Deltas

target= links the live meta-spec; op= is added | modified.

On /spectastic.apply, a proposal's §6 tasks MUST be folded into the target's tasks.html — specs/<id>/tasks.html for a spec, or the artifact's sibling tracker for the meta-spec / principles, created from templates/tasks.html if absent — as a new provenance-linked <spec-task> phase whose IDs continue the target's sequence. The provenance MUST link the archived proposal.

/spectastic.apply MUST NOT itself implement the tasks; /spectastic.implement drains the folded phase. The archived proposal §6 remains the frozen intent record and MUST NOT be ticked in place. This makes apply a uniform accept-and-route step for every target — never context-dependent about whether it implements.

Rationale

Acceptance ≠ execution (CI/CD); a command must behave consistently (least astonishment); Linear turns accepted action items into tracked issues in a project's list, not the triage inbox. One execution surface per target, no hand-copy, archive intact.

What changes: the small-change bullet no longer claims /implement can drive the archived proposal's checkboxes (impossible) — it points at the folded tasks.html phase.

After /spectastic.apply lands a change, the command SHOULD surface the post-apply routing rule — where the user drives the follow-up implementation work — in both its documented output and its per-apply console report:

  • Small change (one or two requirements, behavioural addition, no new ADRs): the §6 tasks have been folded into the target's tasks.html as a new phase (per REQ-CHANGE-006); drive them with /spectastic.implement.
  • Large change (multi-requirement, architectural shift, new topic group): re-run /spectastic.design against the updated spec to revisit ADRs, then /spectastic.tasks to derive a fresh breakdown — which regenerates tasks.html and supersedes the folded phase — then /spectastic.implement to drain it.

The boundary is fuzzy by design: if more than one new ADR would land, the change is large enough to warrant plan + tasks; otherwise the proposal's inline tasks are the breakdown. The rule is guidance, not a guardrail — apply MUST NOT refuse or auto-trigger plan/tasks based on its own classification.

What changes: one clause — the author-affirmation trigger is re-keyed from "artifacts without a tasks.html" to "artifacts that are not a spec slice", so an execution-only tracker (per REQ-CHANGE-006) does not flip these artifacts into the spec-slice last-tick status path. (Caught by the adversarial pass.)

The lifecycle status of any artifact (spec, plan, tasks, principles, triage log, inbox) MUST evolve as a finite state machine over the six values named in REQ-LIFECYCLE-002. The allowed transitions are:

Draft → Accepted
Triggered when the last unchecked <input type="checkbox"> in the artifact's tasks.html is ticked and the author explicitly confirms the flip. /spectastic.implement MUST display a flip prompt at the last-tick that the author must explicitly confirm; the prompt MUST remind the author to verify the integration tests covering the Success Criteria pass before confirming. The command MUST NOT auto-flip status without explicit confirmation. The confirmation gesture absorbs the test-pass discipline; author judgment is the gate.
Draft → In Review
Author-initiated manual flip when soliciting reviewer feedback before the spec is locked. Reversible via In Review → Draft.
In Review → Accepted
Reviewer sign-off. Author flips after the review concludes.
In Review → Draft
Author-initiated when revisions are needed in response to review.
Accepted → Superseded
Triggered when a successor artifact adds a <spec-note> in its header citing this artifact as the prior contract. The successor's author flips the predecessor's status to Superseded at the same time the forward-link lands. The predecessor's content is preserved as historical record.
Accepted → Deprecated
Terminal phase-out without a successor — the requirements described are being removed from the project's scope, not replaced. Manual flip; once Deprecated, no further transitions are allowed.
Any state → Blocked
Triggered by a triage card or an upstream-block signal (an external system down, a vendor bug, a contractual review pending). Reversible via Blocked → originating-state. The originating state is recorded in the artifact's <spec-changelog> at flip time.
Blocked → originating state
When the blocker resolves, the artifact returns to whatever state it was in when Blocked was entered. Recorded in <spec-changelog>.

For artifacts that are not a specs/<spec-id>/ spec slice (principles, the meta-spec itself, triage logs, inbox) — including when they carry an execution-only tasks.html tracker for folded change tasks per REQ-CHANGE-006 — the Draft → Accepted trigger is an explicit author affirmation that the artifact is the operative contract for the project; the execution tracker's checkboxes do not drive their status. The author records the affirmation as a one-line <spec-changelog> entry naming the date and the reason.

Transitions not in the list above are forbidden. In particular, a Superseded or Deprecated artifact MUST NOT transition to any other state — those are terminal. An Accepted artifact MUST NOT transition back to Draft or In Review; if amendments are needed, the path is /spectastic.propose against the live spec, not a status downgrade.

Every transition MUST append a one-line entry to the artifact's <spec-changelog> naming the old state, the new state, the date, and the triggering condition or gesture.

What changes: one clause — the "Non-task artifacts" paragraph — now allows the meta-spec / principles to carry an execution-only tasks.html tracker (per REQ-CHANGE-006) without entering a status bundle.

The three artifacts of a single spec slice — spec.html, design.html, and tasks.html under specs/<spec-id>/ — MUST share a single bundled lifecycle status. When the spec.html status transitions per REQ-LIFECYCLE-004, the design.html and tasks.html status MUST transition to the same value in the same gesture. One author confirmation per transition flips all three siblings; matching one-line <spec-changelog> entries MUST land on each artifact naming the old state, the new state, the date, and the triggering condition.

The bundle is the natural unit of "this spec slice." Splitting status across the three artifacts has no operational meaning — a spec.html cannot be Accepted while its design.html is Draft without inviting drift. The bundle rule makes the natural relationship explicit and prevents the gap surfaced in T-002 of the meta-spec triage log, where nine sibling artifacts sat in Draft despite their parent specs being shipped.

The bundle status is a readiness affirmation, not a content lock. New ADRs, refined risks, additional tasks accrete inside the Accepted state without constituting a lifecycle transition — the bundle rule governs the status pill, not the artifact contents. A plan amendment that genuinely needs Accepted → In Review drags the whole bundle back to In Review, because the readiness affirmation no longer holds for any of the three siblings.

Cross-spec bundling is not implied: each spec slice has its own bundle; one slice's status never tracks another slice's. Artifacts outside a specs/<spec-id>/ slice — principles, the meta-spec, triage logs, inbox — keep their own author-affirmation trigger from REQ-LIFECYCLE-004's tasks-less clause and are not part of any sibling bundle. Such an artifact MAY nonetheless carry a standalone tasks.html tracker for tasks folded from an applied proposal (per REQ-CHANGE-006); that tracker is execution-only — it does not pull the artifact into a status bundle.

/spectastic.implement's last-tick step MUST evaluate the bundle-trigger condition (zero remaining unchecked <input type="checkbox"> in the spec's tasks.html) after every tick taken while the spec's status is Draft, not only when the LLM heuristically recognizes "the last one." Scoping the predicate to the Draft state preserves REQ-LIFECYCLE-004's "last unchecked checkbox is ticked" transition semantics — once the bundle transitions out of Draft, a re-ticked box (a hotfix re-tick on an Accepted spec, an unticked-then-reticked manual gate) does not re-fire the bundled flip prompt. The deterministic evaluation closes the LLM-fragility failure mode where last-tick goes unnoticed when manual gates interleave with code tasks, without introducing a re-confirmation loop on already-flipped specs.

5 · Risk register

Populated by the adversarial pass (a must-tier ADD spanning two topic prefixes — the heuristic fires). Each <spec-risk> stays status="identified" until the author commits a transition; /spectastic.apply refuses while any remain identified.

Making apply a file-creating, tasks.html-writing command is the change most likely to be regretted: every prior apply was a pure spec-patch-plus-archive, and the new "create from template if absent" side effect means apply now silently materializes a fresh tracked artifact on a command whose only job was to land deltas — a class of write that's hard to undo cleanly and easy to fire on the wrong target.

REQ-CHANGE-006: "folded into the target's tasks.html … created from templates/tasks.html if absent … as a new provenance-linked <spec-task> phase"

The write is bounded and revert-safe: apply only appends a phase or creates a file from the template — never edits or deletes existing tasks — so a stray fold is one git revert. Apply already has a filesystem side effect (it moves the proposal folder into archive/); folding tasks is in keeping, not a new class. The "wrong target" is not possible: the target is the proposal's own declared spec (<spec-change> / Spec meta), unambiguous. Proposed transition: mitigated.

REQ-CHANGE-006 gives the meta-spec and principles a sibling tasks.html that lives outside any specs/<spec-id>/ slice, so the "without a tasks.html" predicate in REQ-LIFECYCLE-004 and the "tasks-less" framing in REQ-LIFECYCLE-005 would misclassify a tracker-bearing meta-spec into the spec-slice last-tick status path — a latent contradiction a reader must reconcile against the frozen archived §6.

REQ-LIFECYCLE-004: "For artifacts without a tasks.html (principles, the meta-spec itself …)"

Conceded — the critic caught a real predicate collision (the FR-001-shaped omission). Resolved by adding the REQ-LIFECYCLE-004 delta above, which re-keys the trigger from "without a tasks.html" to "not a specs/<id>/ spec slice" and states the execution tracker's checkboxes do not drive status; the REQ-LIFECYCLE-005 amendment scopes the tracker execution-only. The tracker reuses templates/tasks.html — no sixth template — so REQ-LIFECYCLE-001's five-template contract is intact. Proposed transition: mitigated.

Scope is too broad in its "every target, always fold" stance: REQ-CHANGE-006 mandates the fold even for large changes, while the same proposal's REQ-CHANGE-003 says a large change should re-run /plan + /tasks which "regenerates tasks.html and supersedes the folded phase" — so it guarantees a duplicated/immediately-superseded phase for exactly the changes the routing rule tells you to regenerate.

§Scope "Apply folds … for every target" vs. REQ-CHANGE-003 "regenerates tasks.html and supersedes the folded phase"

Deliberate, per the author's "always fold + nudge" decision: apply must not self-classify small vs. large (REQ-CHANGE-003 forbids it), so it always folds — correct for the common small case (kept small by the budget-splitting nudge). For the rare large change the author chooses to re-run /tasks, regenerating tasks.html and superseding the folded phase — an explicit author gesture, not silent waste. The folded phase is correct-but-superseded, never wrong. Proposed transition: mitigated.
