Status Applied Change ID 2026-07-02-skill-invocation-metadata Spec 000-spectastic Author Brian Corbin Created 2026-07-02 Targets 2 requirements (1 added, 1 modified) Read time

Spectastic's verbs load into Claude Code as skills, but their frontmatter descriptions are written as human documentation, so the skill router fires them unreliably. This change adds REQ-TOOL-004: every command surfaced as a skill MUST declare structured invocation metadata (triggers, use-when, sibling-boundary) in its frontmatter as a machine-checkable contract, alongside a fixed, /skill-creator-tuned description that is the trigger surface the router reads and the eval measures — no generation at sync, so the committed output is exactly what gets evaluated. spectastic validate gains a skill-metadata-shape rule (warning) that flags a command missing the keys, and descriptions SHOULD clear a ≥90% /skill-creator eval (a default target, baselined on first run). It also modifies REQ-TOOL-001 to correct the command count (eight lifecycle commands MUST, extended verbs MAY). From meta-spec triage T-008.

Skill-optimized command invocation metadata

Applied

1 · Intent

Claude Code loads spectastic's ten verbs as skills, and the harness selects a skill from its frontmatter — the description and argument-hint lines. Those lines were authored as prose for a human reader ("Write a feature specification — what to build, for whom, and how we know it worked."), not as router-matchable signal: no explicit trigger cues, no "use when" framing, no boundary against sibling verbs. The result, reported in triage T-008, is that the verbs "do not invoke reliably enough" — a user's intent frequently fails to fire the command that owns it.

The regeneration test on T-008 fails at the code layer: rewriting the ten descriptions by hand fixes today's copies but recurs on the next regeneration, because no requirement encodes a triggering bar. This proposal closes that gap at the layer T-008 laddered to — a central meta-spec requirement that every command owns, parallel to how REQ-FORMAT-004 owns the sizing bands centrally rather than per-spec.

2 · Scope

In scope

  • Add REQ-TOOL-004: structured invocation metadata (triggers, use-when, sibling-boundary) is a must in the frontmatter of every command spectastic surfaces as a skill — a machine-checkable contract and the input skill-creator tunes from.
  • The frontmatter description is the fixed, /skill-creator-tuned output: the trigger surface the router reads and the eval measures. It is not generated at sync — the committed description is exactly what gets evaluated. Keys and description coexist; the description is authoritative on conflict.
  • A spectastic validate rule (skill-metadata-shape, warning severity) that flags a command missing the required keys — the enforcement mechanism for the must.
  • A measurable definition of "reliable": a /skill-creator eval with a ≥90% trigger-accuracy default target, as a should, baselined on the first run; the hard gate waits on CI tooling.
  • Modify REQ-TOOL-001: correct the stale "eight commands" enumeration — eight lifecycle commands must ship, extended verbs (explain, explore) may.
  • Task list: the structured-key authoring + /skill-creator tuning of the fixed descriptions across all ten commands/*.md, the eval baseline, the validate rule, and the .claude/commands/ re-sync.

Out of scope

  • An automated harness that runs the /skill-creator eval in CI. The eval floor ships as a should precisely because this harness does not exist yet. defer-to init --tools (meta-spec §2 Out of scope).
  • Promoting the skill-metadata-shape rule from warning to a hard error, or the eval floor to a gated must. Both wait on the ten commands being brought up to the bar first. defer-to TBD-skill-metadata-gate.

3 · Approach

Two deltas, single REQ-TOOL-* topic: an additive REQ-TOOL-004 for the metadata contract, and a corrective REQ-TOOL-001 to fix its stale command count (folded in per the risk pass rather than left as a dangling contradiction the new requirement leans on).

The load-bearing choice is that the description is a fixed, committed, skill-creator-tuned output — not generated from the keys at sync time. Composing it downstream was rejected: the whole point of /skill-creator is to tune a description against its eval and iterate, so the artifact that gets evaluated must be the artifact that is committed and shipped. Generating it at sync would make the evaluated string a moving target that never lives in the repo. So the structured keys (triggers / use-when / sibling-boundary) are the machine-checkable contract and skill-creator's inputs; the tuned description is the fixed output that the router reads and the eval measures. Keys and description coexist in the frontmatter; where they diverge, the description — the thing actually evaluated and loaded — is authoritative. spectastic validate's new skill-metadata-shape rule checks the keys are present.

The requirement is deliberately two-tier on enforcement. The metadata shape is a hard MUST backed by the validate rule (at warning severity while the ten commands are brought up to the bar). The eval floor is a SHOULD with a ≥90% default target — honest about tooling, since spectastic has no harness to run a /skill-creator eval in CI; the first eval run establishes the baseline the number is checked against before any future promotion to a gate.

The tuned description is inert until .claude/commands/ is re-synced: the harness loads the installed copies, which drift from commands/*.md source (triage T-006). The sync stays a plain cp commands/*.md .claude/commands/ (no generation) — the task list makes that re-sync an explicit step, not an afterthought.

4 · Deltas

Two deltas — one ADD, one MODIFY, both on REQ-TOOL-*. REQ-TOOL-002 is burnt per the stable-IDs invariant, so the next free ID is REQ-TOOL-004.

Every command spectastic surfaces to an agent host as a skill — the lifecycle commands enumerated in REQ-TOOL-001 and any extended verb it ships (e.g. /spectastic.explain, /spectastic.explore) — MUST declare structured invocation metadata in its source frontmatter as the source of truth for how the skill router selects it. The metadata MUST comprise three keys:

  • triggers — the intents and phrasings that should invoke the command;
  • use-when — a one-line framing of when to reach for it;
  • sibling-boundary — what disambiguates it from adjacent verbs (e.g. propose vs plan, spec vs explore).

The harness router reads only the frontmatter description. That description MUST be a fixed, committed output tuned against /skill-creator's eval — the same string the router loads and the eval measures — and MUST NOT be generated from the keys at sync time (a generated description makes the evaluated artifact a moving target that never lives in the repo). The structured keys are the machine-checkable contract and the input skill-creator tunes from; the description is the resulting trigger surface. Where a key and the description diverge, the description is authoritative. spectastic validate MUST carry a skill-metadata-shape rule that flags a command whose source frontmatter is missing any of the three keys; the rule ships at warning severity.

Command descriptions SHOULD be validated with /skill-creator's eval against a ≥90% trigger-accuracy default target (the command fires correctly on ≥90% of its intent cases) whenever the metadata changes; a command measured below the target SHOULD be re-tuned before it ships. The target is a SHOULD, not a hard gate — the first eval run establishes the baseline it is checked against — until spectastic ships a harness that can run the eval automatically (deferred to init --tools), at which point the check MAY be promoted to a gated must by a future change.

Rationale

Commands load as skills but invoke unreliably because their frontmatter is authored for a human reader, and no requirement encodes a triggering bar (triage T-008, spec layer, regen fail). Structured keys make the bar machine-checkable; the description stays a fixed, tuned output so the exact string skill-creator evaluates is the one committed and loaded — generating it at sync would break that eval loop. The validate rule gives the must teeth (starting as a warning so the ten existing commands can be brought up to the bar without a red build); the eval should makes "reliable" measurable rather than asserted, baselined on first run so the ≥90% figure is checked against reality before it ever hardens into a gate.

What changes: the enumeration said spectastic ships "eight" commands and named only the eight lifecycle verbs; it now ships extended verbs too. Correct the count so REQ-TOOL-004 doesn't lean on a stale inventory — eight lifecycle commands must ship; extended verbs may.

Spectastic MUST ship eight Claude Code slash commands across the lifecycle — /spectastic.principles, /spectastic.spec, /spectastic.plan, /spectastic.tasks, /spectastic.implement, /spectastic.propose, /spectastic.apply, /spectastic.triage — that drive the templates without introducing a separate CLI. It MAY additionally ship extended, opt-in verbs upstream of or alongside the lifecycle (e.g. /spectastic.explain, /spectastic.explore); extended verbs are not required to ship, but any command spectastic does surface as a skill is bound by REQ-TOOL-004.

5 · Risk register

Populated by the adversarial risk pass — the proposal's ADD post-state declares priority="must", which fires the REQ-CHANGE-004 heuristic. One <spec-risk> per finding; status="identified" until the author commits a transition.

The ≥90% floor is baked into the spec body as the definition of "reliable" with no measured baseline of what the ten verbs score today, so in 30 days it reads as invented precision — trivially cleared or unreachable — the same unenforceable-magic-number class this project already paid for (the fabricated Larson "1,500-word" citation; the 70%→80% alert-fatigue band).

"validated with /skill-creator's eval against a trigger-accuracy floor of ≥90%" — a number chosen without a baseline, shipped as a SHOULD nothing can yet run.

Mitigated (user-committed). The requirement body now frames ≥90% as a default target, not a measured fact, and states explicitly that the first eval run establishes the baseline it is checked against before any promotion to a gate. The eval task is the baseline run. The number is a SHOULD default, so the magic-number failure mode doesn't apply.

REQ-TOOL-004's scope premise cites REQ-TOOL-001 — the only requirement that enumerates the command surface — yet REQ-TOOL-001 says spectastic MUST ship eight commands and names neither explain nor explore, so the new requirement leans on an inventory contract the proposal itself concedes is stale.

Live spec REQ-TOOL-001 (spec.html:655–661): "Spectastic MUST ship eight Claude Code slash commands … principles, spec, plan, tasks, implement, propose, apply, triage" — no extended verbs.

Mitigated (user-committed). Fixed at the source rather than deferred: this proposal now carries a MODIFY delta on REQ-TOOL-001 that keeps the eight lifecycle commands as must and adds that extended verbs (explain, explore) may ship — with any surfaced command bound by REQ-TOOL-004. No residual contradiction; the TBD-tool-001-command-count defer is dropped.

Too narrow — the proposal defers the one enforcement mechanism (a validate rule for the metadata shape) that would give the MUST teeth, so REQ-TOOL-004 lands with both halves unenforced: no harness for the eval SHOULD, no validator for the shape MUST — reproducing the T-005 lesson that a requirement with no checkable post-condition drifts silently, the exact regen-fail T-008 laddered to the spec layer to prevent.

§2 out-of-scope: "A spectastic validate rule that checks the metadata shape is present … defer-to TBD-skill-metadata-validate-rule" — deferred despite the Approach section justifying the shape as a MUST "precisely because a validator can enforce it once written".

Mitigated (user-committed). The skill-metadata-shape validate rule is pulled into scope (§2 in-scope, Task list) and named in REQ-TOOL-004 as a must, at warning severity so the ten commands can be brought up to the bar without a red build. The keys are structured (not prose) so the rule checks presence rather than guessing intent — sidestepping the REQ-CHANGE-007 "a rule can't know intent" failure mode. The keys are a machine-checkable contract; the fixed description (not a sync-generated one) carries the tuned trigger surface skill-creator evaluates. The shape MUST is machine-enforced, not review-only.

6 · Tasks

Scoped to this change. On /spectastic.apply these fold into tasks.html as a new provenance-linked phase (per REQ-CHANGE-006) that /spectastic.implement drains.

  • Add the structured triggers / use-when / sibling-boundary keys to the source frontmatter of all ten commands/*.md.
  • Tune each command's description via /skill-creator into a fixed, committed trigger surface; commit the keys and the tuned description together.
  • Add the skill-metadata-shape rule to spectastic validate (in packages/core) — warning severity, flags a command whose source frontmatter is missing any of the three keys; add a vitest covering present/missing cases.
  • Run /skill-creator eval per command against the committed description; record the first-run scores as the baseline; re-tune any command below the ≥90% default target.
  • Re-sync installed copies: cp commands/*.md .claude/commands/ (plain copy, no generation); confirm the router fires each verb from intent (closes the T-006 drift for this change).
  • Document the structured-metadata contract (the three keys + the fixed skill-creator-tuned description) in the command-authoring notes so future verbs inherit the bar.

7 · Open questions

None outstanding — every decision was anchored across two interview passes: eval force (two-tier), the ≥90% default target (baselined on first run), structured keys as a parallel contract with a fixed skill-creator-tuned description (no sync composition), the validate rule and its warning severity, the REQ-TOOL-001 count fix (eight must + extended may), and the ship status. All three risk-pass findings resolved to mitigated.
