Add REQ-LIFECYCLE-003 formalising the <spec-task> custom element — its id, optional parallel boolean attribute, and inner <input type="checkbox"> for completion state. The <div class="task"> + class-span pattern currently used in tasks.html already violates REQ-AUTHOR-001 ("never as <div> + class names"); this delta closes the application gap by naming the right element instead.

Semantic <spec-task> element

Applied

1 · Intent

When templates/tasks.html was first authored, the component vocabulary did not yet have a task element. The styling was solved with a one-off <div class="task"> + class-span block and an inline <style> in the template. The shortcut shipped, then stayed.

The result is a visible inconsistency between tasks.html (class-soup) and every other lifecycle artifact (semantic custom elements), and a quieter problem: every new tasks.html derived from the template inherits the violation, since /spectastic.tasks copies the template verbatim. The fix is structural — add the vocabulary entry, migrate the template, and bring the existing 001-cli tasks artifact along in the same change.

2 · Scope

In scope

  • One new requirement (REQ-LIFECYCLE-003) defining the <spec-task> element, its attributes, and where its styling lives.
  • Migration of the lifecycle template (templates/tasks.html) and the existing specs/001-cli/tasks.html in the same delta — preserve the 33 ticked checkboxes verbatim.
  • Move the inline <style> block from the template into assets/spec.css so the design system stays the single source of truth.
  • README's component-vocabulary table grows by one row.

Out of scope

  • A formal catalog of every custom element as enumerated requirements. REQ-AUTHOR-001 still covers the vocabulary aggregately; REQ-LIFECYCLE-003 is justified by the tasks artifact's reach (one file per spec, regen-derived from a template) — not by a precedent for per-element requirements.
  • Backwards-compatible support for both <div class="task"> and <spec-task>. The class-soup form is a REQ-AUTHOR-001 violation; we don't ship dual contracts.
  • JavaScript-driven persistence of checkbox state across page reloads. Out of scope here; the checkbox state lives in the HTML and is mutated by /spectastic.implement editing the file.

3 · Approach

Three design choices worth naming:

  • Boolean parallel attribute rather than data-p="1" or a class. Boolean HTML attributes are the canonical pattern (hidden, open, required); they read naturally in source and select cleanly in CSS via [parallel].
  • Inner <input type="checkbox"> stays. The checkbox is what /spectastic.implement mutates and what gives the artifact at-a-glance "what's left" visibility. CSS reads the state via :has(input:checked) for the done-style; no data-status needed.
  • Styling moves to assets/spec.css. The current template carries an inline <style> block. Pulling it into the shared stylesheet keeps the design system the single source of truth and shrinks the template.

REQ-AUTHOR-001 already forbids <div> + class names. REQ-LIFECYCLE-003 is the concrete application: this element, these attributes, for this artifact. The author-time test for whether to add a per-artifact requirement is whether the artifact is regen-derived; tasks.html is, so the contract is worth being explicit about.

4 · Deltas

One <spec-delta>. target= links to the live spec. op= is added.

Each task entry in a tasks.html artifact MUST be a <spec-task> custom element. The element MUST carry:

  • id="T-NNN" — the stable task ID, matching the format defined for tasks elsewhere in the project.
  • parallel (boolean attribute) — present when the task can run alongside its in-flight peers (the existing [P] convention); omitted otherwise.
  • An inner <input type="checkbox"> — the completion state. checked means done. CSS MUST read the state via :has(input:checked) rather than a parallel data-status attribute, so the checkbox is the single source of truth.

Styling for <spec-task> MUST live in assets/spec.css — not inline in the template. The generic <div class="task"> + class-span form is forbidden as a direct application of REQ-AUTHOR-001.

Rationale

The tasks artifact is regen-derived from a template, so the contract for its internal shape is worth being explicit about. Without a named element, a fresh authoring session falls back to whatever the template already shows — and a class-soup template propagates indefinitely. Codifying <spec-task> turns the implicit pattern into something a validator (or a careful reader) can check.
