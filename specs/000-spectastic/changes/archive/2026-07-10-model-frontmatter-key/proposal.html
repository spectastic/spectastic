Change proposal · 000-spectastic

Permit an optional model: frontmatter key

Let a command declare which model tier it runs on, as an optional key the metadata contract recognises and the validator never flags.

Status Applied Change ID 2026-07-10-model-frontmatter-key Spec 000-spectastic Author Brian Corbin · me@briancorbin.co.uk Created 10 Jul 2026 Targets 1 requirement Read time

Spec 044-verb-model-policy assigns each verb a model tier via a model: frontmatter key. That key needs a home in the frontmatter contract. This change modifies REQ-TOOL-004 to permit an optional model: key alongside the three required invocation-metadata keys, and locks in that skill-metadata-shape — which today only checks for missing required keys — MUST NOT flag its presence or absence. One MODIFY delta; no new required keys.

Permit an optional model: frontmatter key

Applied

1 · Intent

The command-frontmatter contract (REQ-TOOL-004) fixes the source-of-truth keys for how the skill router selects a command: triggers, use-when, sibling-boundary, and the tuned description. Spec 044 introduces a new, orthogonal knob — which Claude model tier a verb runs on — expressed as a model: key in the same frontmatter. Before 044 can add that key to the command sources, the contract must recognise it as legal.

The change is deliberately minimal. model: is optional and does not join the three required keys, so no existing command becomes non-conformant. The validator already tolerates it (it only reports missing required keys), so this makes an incidental tolerance an explicit, guaranteed part of the contract — closing the door on a future rule change silently rejecting it.

2 · Scope

In scope

  • Modify REQ-TOOL-004 to permit an optional model: key (alias value: opus / sonnet / haiku / inherit).
  • State that skill-metadata-shape checks only the three required keys and MUST NOT flag the presence or absence of model:.

Out of scope

  • The per-verb tier assignments, the escape hatch, subagent pins, and the CLI model config — all owned by 044-verb-model-policy.
  • The drift-guard rule that flags a command whose declared model: disagrees with the core policy map — owned by 044 FR-009 (one rule, one owner).

3 · Approach

A single MODIFY delta on REQ-TOOL-004. The requirement's existing body is preserved verbatim; two clauses are added — one permitting the optional key in the keys paragraph, one scoping the validate rule so its acceptance of model: is a contract guarantee (per P-8, the guarantee is the rule, not the prose). No change to REQUIRED_SKILL_KEYS is needed, because skillMetadataFinding already filters only the required set; the contract text now makes that behaviour load-bearing rather than incidental.

4 · Deltas

One <spec-delta>, targeting the live REQ-TOOL-004.

What changes: add an optional model: key to the permitted frontmatter metadata, and scope skill-metadata-shape so it never flags that key. The three required keys and the description discipline are unchanged.

Every command spectastic surfaces to an agent host as a skill — the lifecycle commands enumerated in REQ-TOOL-001 and any extended verb it ships (e.g. /spectastic.explain, /spectastic.explore) — MUST declare structured invocation metadata in its source frontmatter as the source of truth for how the skill router selects it. The metadata MUST comprise three keys:

  • triggers — the intents and phrasings that should invoke the command;
  • use-when — a one-line framing of when to reach for it;
  • sibling-boundary — what disambiguates it from adjacent verbs (e.g. propose vs plan, spec vs explore).

The metadata MAY additionally carry an optional model: key declaring the model tier the command runs on — an alias (never a pinned model ID) drawn from the legal set that 044-verb-model-policy owns as a single source of truth. It is advisory to the host and is not one of the three required keys; a command that omits it is fully conformant. The per-verb tier assignments and their enforcement are owned by 044-verb-model-policy.

The harness router reads only the frontmatter description. That description MUST be a fixed, committed output tuned against /skill-creator's eval — the same string the router loads and the eval measures — and MUST NOT be generated from the keys at sync time (a generated description makes the evaluated artifact a moving target that never lives in the repo). The structured keys are the machine-checkable contract and the input skill-creator tunes from; the description is the resulting trigger surface. Where a key and the description diverge, the description is authoritative. spectastic validate MUST carry a skill-metadata-shape rule that flags a command whose source frontmatter is missing any of the three required keys; the rule ships at warning severity. That rule checks only the three required keys for presence and MUST NOT flag a command merely for omitting the optional model: key. The well-formedness of a present model: value — that it is a legal alias — is enforced by the drift-guard rule that 044-verb-model-policy requires, so a permitted key never ships without a machine-checkable guarantee.

Command descriptions SHOULD be validated with /skill-creator's eval against a ≥90% trigger-accuracy default target (the command fires correctly on ≥90% of its intent cases) whenever the metadata changes; a command measured below the target SHOULD be re-tuned before it ships. The target is a SHOULD, not a hard gate — the first eval run establishes the baseline it is checked against — until spectastic ships a harness that can run the eval automatically (deferred to init --tools), at which point the check MAY be promoted to a gated must by a future change.

Rationale

Commands load as skills but invoke unreliably because their frontmatter is authored for a human reader, and no requirement encodes a triggering bar (triage T-008, spec layer, regen fail). Structured keys make the bar machine-checkable; the description stays a fixed, tuned output so the exact string skill-creator evaluates is the one committed and loaded — generating it at sync would break that eval loop. The validate rule gives the must teeth (starting as a warning so the ten existing commands can be brought up to the bar without a red build); the eval should makes "reliable" measurable rather than asserted, baselined on first run so the ≥90% figure is checked against reality before it ever hardens into a gate. The optional model: key is an orthogonal, advisory knob (spec 044): permitting it in the contract keeps a cost-tiering choice from ever reading as a metadata violation, while its well-formedness is guaranteed by 044's drift-guard (a MUST) — so the permission never ships without an enforcement, honouring P-8.

5 · Risk register

Populated by the adversarial risk pass (REQ-TOOL-004 is a must-tier requirement, so the heuristic fires). One <spec-risk> per finding. status= defaults to identified; apply refuses until each transitions to accepted, mitigated, or rejected, with a by= naming the human dispositioner.

The delta hardcoded the alias enum (opus/sonnet/haiku/inherit) into meta-spec prose, which already disagreed with 044's own FR-002 — two enumerations that would silently drift the moment the alias set changed.

"an alias (opus, sonnet, haiku, or inherit), never a pinned model ID"

Mitigated: the concrete enum is removed from REQ-TOOL-004's prose. The legal alias set lives once as a core constant that 044-verb-model-policy owns and the validator references; 044's FR-002 and Data model are harmonised to the same set. No value list can go stale in meta-spec prose.

Legalising model: while forbidding the validate rule from ever inspecting it left a permitted contract element with zero machine coverage — a typo'd value (model: sonet) would be fully conformant.

"The rule checks only those three required keys and MUST NOT flag the presence or absence of the optional model: key."

Mitigated via 044: the "MUST NOT flag" clause is narrowed to omission only (the key stays optional). Well-formedness of a present value is enforced by 044's drift-guard, promoted from SHOULD to MUST so it ships in the same increment. The permitted key now always carries a machine-checkable guarantee.

Shipping the permission now while deferring every check to 044 FR-009 — a SHOULD in a still-Draft sibling — is the P-8 permission-without-enforcement anti-pattern the proposal claims to honour.

"The drift-guard rule that flags a command whose declared model: disagrees with the core policy map — owned by 044 FR-009 (one rule, one owner)."

Mitigated: 044 FR-009 is promoted SHOULD→MUST, and this increment's completion is gated on the drift-guard shipping. Permission (000) and guarantee (044) land together, so "legal but unchecked" is never a durable state.
