Apply kernel: place ADD deltas by kind, re-base embedded links

The durable fix for triage T-019/T-020 — make the apply kernel put an ADD requirement in the section its id names, and re-base an embedded requirement's links to the live spec's depth on fold.

Status Applied Change ID 2026-07-26-apply-add-delta-placement-and-paths Spec 000-spectastic Author Brian Corbin · @briancorbinxyz Created 26 Jul 2026 Targets 1 requirement Read time

The apply kernel drops every op="added" requirement at the document's first </section> and splices an embedded requirement's relative links in verbatim — so an ADD lands in the wrong section and its cross-file links point above the repository root (triage T-019 / T-020, both hand-fixed while applying 019's NFR-003). This MODIFIES REQ-CHANGE-008 to require kind-matched placement and proposal→live-spec link re-basing, then implements both in apply.ts. One MODIFY delta; the adversarial pass ran.

Apply kernel: place ADD deltas by kind, re-base embedded links

Applied

1 · Intent

Applying 019's NFR-003 ADD delta surfaced two defects in the apply kernel's requirement-delta path, both hand-fixed in 019's spec.html and logged as triage T-019 and T-020. First, the ADD insertion anchors on the document's first </section> (apply.ts:104-112), so NFR-003 landed inside §1 Context instead of §3 Non-functional — placement ignores the requirement's kind entirely. Second, the embedded post-state is spliced in verbatim; the kernel deepens the archived proposal's paths but never re-bases the folded requirement's own links, so proposal-depth hrefs (four levels deep) land in a two-levels-deep spec and point above the repository root.

Both are spec-layer, regen-fail defects: REQ-CHANGE-008 says the kernel applies each delta "into spec.html (insert for added)" but constrains neither where the insert lands nor how the embedded links are depth-adjusted — so a faithful re-implementation reproduces both. This change closes the contract gap and lands the kernel fix, so the hand-fixes 019 needed become unnecessary for the next ADD.

2 · Scope

In scope

  • MODIFY REQ-CHANGE-008 to require family-prefix placement for an op="added" requirement — insert after the last existing sibling sharing its id prefix (NFR- beside the non-functional requirements, REQ-CHANGE- beside the change-management ones), covering both the downstream FR/NFR/SC vocabulary and the meta-spec's own REQ-<TOPIC> vocabulary — never the document's first </section>.
  • MODIFY the same requirement to require the kernel re-base an embedded <spec-requirement>'s relative links from proposal depth to the live spec's depth on fold — for both added and modified — the mirror of the archive-path deepening it already performs.
  • Implement both in the apply kernel (apply.ts): a kind-routed section lookup and an inverse-of-deepenArchivePaths re-base helper, with unit coverage.

Out of scope

  • Retro-cleaning the meta-spec's own historically-spliced proposal-depth links (a pre-existing symptom of the same bug, in text this change doesn't touch) — defer-to=TBD-metaspec-link-depth-cleanup.
  • Cross-spec apply, still kernel-unhandled — defer-to=TBD-kernel-cross-spec-apply.

3 · Approach

Placement. Replace the first-</section> anchor with a rule that keys on the requirement's own family, not on a fixed section vocabulary: strip the trailing number from the new id to get its family prefix (NFR-003→NFR-, REQ-CHANGE-009→REQ-CHANGE-), find the last existing <spec-requirement> sharing that prefix, and insert immediately after it — so the requirement joins its own group (an NFR-* beside the other non-functional requirements, a REQ-CHANGE-* beside the other change-management ones). This is vocabulary-agnostic by construction: it works for a downstream spec's FR/NFR/SC groups — which the templates keep as sibling <h3> inside one <section id="requirements">, so keying on the enclosing <section> would fail — and for the meta-spec's own REQ-<TOPIC> groups, without hard-coding either heading. When no existing requirement shares the prefix (the first of its kind), append after the last <spec-requirement> in the document rather than gate-block — a legitimate first-of-kind ADD should land, not fail.

Path re-basing. Add the inverse of the existing deepenArchivePaths (archive-paths.ts) — a function that rewrites a fragment's relative href/src values from the proposal's four-levels-deep folder to the live spec's two-levels-deep location — and apply it to the embedded requirement HTML before it is written into spec.html, on both the added and modified branches. Same-document anchors (#ID) are already depth-independent and pass through untouched. The two directions (deepen the archived copy, shallow the folded body) then live side by side in one module, tested together.

4 · Deltas

One <spec-delta>, MODIFYing REQ-CHANGE-008. The post-state preserves the existing body verbatim and adds the placement + re-basing clauses to its second paragraph (and a rationale line); priority stays should.

What changes: the "when applying each delta" paragraph gains two clauses — (a) an added requirement is inserted into the section matching its id kind, before that section's close, not the document's first </section>; and (b) an embedded <spec-requirement>'s relative links are re-based from proposal depth to live-spec depth on fold (both added and modified). Existing text and the priority (should) are unchanged; the new clauses' own same-spec references use depth-independent intra-doc anchors.

The mechanical steps of /spectastic.apply — applying each <spec-delta>, the live-spec <spec-changelog> entry (the kernel MUST accept an author-supplied one-line summary, so the changelog's human voice is preserved rather than reduced to a delta count), the archive-folder move, the proposal status flip to applied, and the §6 task-fold (per REQ-CHANGE-006 / REQ-CHANGE-007) — MUST be performed by the apply kernel (spectastic apply, which is deterministic and requires no ANTHROPIC_API_KEY), not re-implemented in the slash-command markdown. The apply markdown MUST run the preconditions — including the REQ-CHANGE-004 risk gate, listing any status="identified" risks by target= — and surface failures before invoking the kernel; the kernel's own gate is a deterministic backstop, not the user-facing refusal. It MUST also confirm spectastic apply resolves before invoking it, surfacing a missing or stale binary clearly rather than failing silently. Beyond the preconditions, the markdown owns only the post-apply routing nudge (REQ-CHANGE-003) and the inbox-card nudge.

When applying each <spec-delta>, the kernel MUST branch on whether the delta embeds a <spec-requirement>. Present — it is a requirement delta: apply the post-state into spec.html. For added, the kernel MUST insert the requirement immediately after the last existing <spec-requirement> whose id shares its family prefix (the id with its trailing number stripped — e.g. NFR-, SC-, REQ-CHANGE-), so it joins its own group beside its siblings, never the document's first </section>. Keying on the sibling requirements already present makes this work for both a downstream spec's FR/NFR/SC groups (kept as sibling <h3> within one requirements <section>) and the meta-spec's REQ-<TOPIC> groups, with no hard-coded section heading. When no existing requirement shares the prefix (the first of its kind), the kernel MUST append it after the last <spec-requirement> in the document rather than at an arbitrary position. For modified | removed | renamed, replace the id-matched requirement in place. Whenever the kernel writes an embedded <spec-requirement> into spec.html (both added and modified), it MUST re-base that requirement's relative links from the proposal's folder depth to the live spec's depth — the mirror of the path-deepening it already applies to the archived proposal — so a same-spec link, a principles.html link, or a sibling-spec link resolves from the live spec instead of pointing above the repository root; a same-document anchor (#ID) is depth-independent and passes through unchanged. Absent — it is a data/content delta whose target names manifest data: the kernel MUST make no change to the requirements body (the mandated <spec-changelog> append still lands) and let the §6 task-fold carry the change; it MUST NOT fabricate a <spec-requirement> from the delta body. As a guard, if a delta's target matches a requirement-ID shape (^[A-Z]+-…) yet embeds no <spec-requirement>, the kernel MUST gate-block it as malformed rather than silently skip — a requirement delta that forgot its post-state is an error, not a no-op.

This is a deliberate, named exception to 006 FR-008 ("the markdown procedure remains the source of truth") and FR-009 ("slash commands MAY invoke the CLI but MUST NOT be required to") for apply: its mechanical steps are pure and deterministic, and their prose-only form was the T-004 failure. Those general rules continue to govern the six verbs that need LLM judgment.

The obligation is scoped to same-spec applies. A cross-spec delta (whose target is a requirement in another spec) is the one mechanical step the kernel does not yet perform and MAY remain markdown-handled until it does (TBD-kernel-cross-spec-apply).

Rationale

Apply's mechanical steps need no AI and the CLI runs key-free, so making the kernel authoritative for them removes the whole class of skipped-step bugs on the in-host path (T-004) without touching the verbs that need judgment. The data/content branch (T-018) extends the same principle: the kernel, not a fabrication fallback, decides what a delta means, so a manifest-data proposal (041 principles, 042 enforce categories) folds and archives without corrupting spec.html. The placement and link-rebasing clauses codify triage T-019 / T-020: applying 019's NFR-003 ADD delta, the kernel dropped the new requirement at the document's first </section> (§1 Context, not §3 Non-functional) and spliced its embedded links in verbatim at proposal depth, so every cross-file reference pointed above the repository root — both hand-fixed in 019, both certain to recur without a contract that constrains placement and link depth. Hosted as a meta-spec requirement — not a MODIFY of 006 FR-009 — because a cross-spec delta could not be applied by the kernel this very requirement mandates, and because apply's contract already lives in REQ-CHANGE-*. Priority should: codifying apply's kernel-authoritative path from incident, matching REQ-CHANGE-004 / REQ-CHANGE-007; re-evaluate after a few real applies.

5 · Risk register

The adversarial risk pass ran (opt-in — the heuristic did not auto-fire, but this rewrites how the kernel places and re-links every future ADD delta, and a knowledge/ corpus is present). One <spec-risk> per finding; status="identified" until the author dispositions each. Apply refuses while any remain identified.

The original placement rule routed on a per-kind <section> and gate-blocked on no match — but the templates keep Functional and Non-functional as sibling <h3> inside one <section id="requirements">, so an NFR-* ADD would gate-block or land at the section's very end, reproducing a milder T-019 (right section, wrong group) that the hand-fix explicitly rejected by placing NFR-003 beside NFR-001/002.

Objected phrase (pre-revision): "insert the requirement into the section whose kind its id names … immediately before that section's closing </section>."

Mitigated by revision. The placement clause was re-keyed on the requirement's family prefix — insert immediately after the last existing <spec-requirement> sharing the id prefix — which is <h3>/<section>-layout-agnostic and reproduces the hand-fix's beside-siblings placement exactly. A test fixture mirroring the 019 shared-<section> layout is the first §6 task.

The FR/NFR/SC-only routing would gate-block every ADD to the meta-spec, whose ids are REQ-<TOPIC>-<NNN> per REQ-AUTHOR-002 — so the most-amended spec could not self-apply an ADD through the very kernel REQ-CHANGE-008 mandates.

REQ-AUTHOR-002 mandates REQ-<TOPIC>-<NNN>; the pre-revision delta routed only on FR/NFR/SC and gate-blocked on no match.

Mitigated by revision. The family-prefix rule covers REQ-<TOPIC> ids natively (a REQ-CHANGE-* lands beside the other change-management requirements), and gate-block-on-no-match was replaced with append-after-last, so a legitimate first-of-kind ADD to the meta-spec still lands. A meta-spec topic-grouped fixture is in the §6 tests.

The in-scope item enumerated only the downstream FR/NFR/SC vocabulary and silently omitted the REQ-<TOPIC> family the host spec of this very contract uses — shipping a placement rule the meta-spec's own future ADDs fall outside of.

§Scope, in-scope item 1 (pre-revision): "(FR-*→functional, NFR-*→non-functional, SC-*→success-criteria section)."

Mitigated by revision. §2 in-scope item 1 now describes the family-prefix rule and names both vocabularies explicitly (downstream FR/NFR/SC and the meta-spec's REQ-<TOPIC>).

No requirement in the live spec contradicts a domain fact committed under knowledge/.

KB-001-foundations.md@2026-07-25 (the pack's only reference, read in full) commits facts only about SDD framing, the RFC 2119 MUST/SHOULD/MAY definitions, and the verified/spike/assumed grounding states — all orthogonal to ADD-placement and link-rebasing mechanics; the change's should tier is itself consistent with KB-001's definition of SHOULD.
