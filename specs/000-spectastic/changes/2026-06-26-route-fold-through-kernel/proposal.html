Route the slash-command fold through the kernel

Proposed (draft)

1 · Intent

T-004 (meta-spec triage) occurred on the in-host /spectastic.apply slash-command run, which transcribes §6 into a tracker phase in LLM prose (step 8). The sibling foundation (REQ-CHANGE-007) gives the apply kernel a deterministic, fidelity-checked fold, but only the CLI path calls it; the slash path still folds in prose, so an LLM run can still skip it. This change finishes the fix: route the slash-command fold through the kernel, so the deterministic check runs no matter what the LLM does.

This is the contestable half the foundation's adversarial pass asked to review on its own, for two reasons it must resolve: it makes the mechanical fold kernel-authoritative (a narrow exception to the rule that the markdown procedure is the LLM's source of truth, per 006), and it has to invoke kernel code from a context that — unlike the CLI — has no ANTHROPIC_API_KEY (§7).

2 · Scope

In scope (candidate — finalised when authored)

  • Narrow slash-command apply step 8: invoke the kernel fold instead of transcribing §6 in prose, then report the verified result.
  • Record the kernel-authoritative-fold boundary in the meta-spec (which mechanical sub-step of apply is code vs prose) — see the candidate delta in §4.
  • A non-AI way for the in-host path to run the kernel fold without requiring ANTHROPIC_API_KEY.

Out of scope

  • The kernel fold itself and its fidelity post-condition — built by the foundation (REQ-CHANGE-007).
  • Moving the interactive parts of apply (preconditions, risk gate, report) into the kernel; those stay markdown-canonical.

3 · Approach

Sketch (to be grounded when authored): the slash-command procedure stops describing the §6 transcription and instead calls the kernel fold the foundation built — directly via a fold-only entry, or via a spectastic apply path that does not gate the (non-AI) fold on an API key. The markdown keeps owning the steps that need judgment (preconditions, the risk gate, the apply report); only the transcription moves to code. The boundary — which apply sub-steps are kernel-authoritative — is recorded in the meta-spec so it is not folklore.

4 · Deltas

Candidate, not finalised. Most likely one MODIFY recording the boundary — either REQ-CHANGE-006 (the fold is performed by the kernel; the slash command invokes it rather than hand-transcribing) or the 006 "markdown is canonical" requirement (a named exception for the mechanical fold). The exact target is an open question (§7); deltas are written when this change is authored, after the foundation lands.

5 · Risk register

The adversarial pass has not run yet — it runs when this change is authored (it will fire: it touches the must-tier change-management family and re-architects an ownership boundary). The foundation's fifth and sixth passes already flagged the two issues this change owns: the markdown-canonical boundary (state it in a delta, not folklore) and the API-key wiring (§7).

6 · Tasks

Derived when authored (after the foundation lands and §7 is decided). Expected shape: narrow commands/spectastic.apply.md step 8 to invoke the kernel fold; add the non-AI fold entry/path; record the boundary delta; a test that the slash path and the kernel produce the same phase (retiring the prose fold).

7 · Open questions

  1. API-key wiring. The in-host slash path has no ANTHROPIC_API_KEY; the AI-coupled spectastic apply CLI requires one. How does the in-host path invoke the (non-AI) kernel fold — a fold-only kernel entry with no key requirement, a non-AI CLI subcommand, or splitting the key gate so the mechanical fold runs keyless? Resolve before authoring.
  2. Which requirement records the boundary? MODIFY REQ-CHANGE-006, modify the 006 markdown-canonical requirement with a named exception, or extend REQ-CHANGE-007. Decides the §4 delta.
  3. Transitional dual-fold. Until this lands, the kernel (CLI) and prose (slash) fold via different code; should a test assert they produce the same phase, and does that test live here or in the foundation?
