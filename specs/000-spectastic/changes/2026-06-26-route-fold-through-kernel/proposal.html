Route the slash apply through the kernel

Approved

1 · Intent

T-004 happened on the in-host /spectastic.apply run: the LLM, following the slash-command markdown, skipped a mechanical step (the §6 fold). The sibling REQ-CHANGE-007 fixed that step in the kernel — the apply kernel now folds §6 deterministically and fidelity-checks it — but only the CLI path calls the kernel. The slash path still re-implements the entire mechanical apply (apply each delta, append the changelog, move the folder to archive, flip the proposal status, fold §6) in prose the LLM can under-execute. So the path that actually failed is still as fragile as it was.

The fix is now unblocked and simpler than it first looked. The whole mechanical apply already lives in the kernel (applyCommand: risk gate, deltas, changelog, archive, and — since REQ-CHANGE-007 — the fold), and apply is deterministic and key-free — the CLI invokes applyCommand with no AI provider and gates on no ANTHROPIC_API_KEY (unlike spec/plan). So the slash command can simply invoke spectastic apply for the mechanical work instead of doing it by hand. The earlier worry — that the in-host path (no key) couldn't call the AI-coupled CLI — does not apply to apply.

2 · Scope

In scope

  • ADD REQ-CHANGE-008 to the meta-spec: /spectastic.apply's mechanical steps MUST run via the kernel, not be re-implemented in the slash markdown — a named exception to 006 FR-008/FR-009 for apply.
  • Close the kernel gaps so the routed apply does everything the prose did — the proposal status flip to applied and its apply changelog entry — first, before the markdown is reduced to invoking it.
  • Rewrite commands/spectastic.apply.md so the mechanical apply is one kernel invocation; the markdown keeps preconditions-surfacing, the post-apply routing nudge, and the inbox-card nudge; then re-sync .claude/commands/ (per triage T-006).

Out of scope

  • Cross-spec deltas. The kernel applyCommand applies deltas to a single spec (its own); a delta targeting another spec's requirement is the one mechanical step the kernel does not yet perform, so it stays markdown-handled. Teaching the kernel multi-spec application is a separate change — and is why this proposal ADDs a meta-spec requirement rather than MODIFYing 006 FR-009 (a cross-spec delta the kernel could not itself apply).
  • Routing the other six slash verbs through the kernel. They keep 006 FR-009's "MAY"; only apply — whose mechanical steps are pure, deterministic, and were the T-004 failure — becomes a MUST.
  • Editing 006 FR-008/FR-009. REQ-CHANGE-008 names the apply exception; 006's general rules stand for the other verbs. A back-reference note in 006 is optional polish, not required here.

3 · Approach

Invoke, don't re-implement. The slash-command apply procedure stops describing the mechanical steps and instead runs spectastic apply <spec-id> <slug> (key-free), which performs the risk gate, delta-fold, changelog, archive move, status flip, and §6 fold deterministically in one call. The markdown keeps the parts that need judgment or are human-facing: surfacing precondition failures, the post-apply small-vs-large routing nudge (REQ-CHANGE-003), and the inbox-card nudge. Every mechanical apply step becomes deterministic on the in-host path — the LLM can no longer skip one, which is the entire T-004 class.

A meta-spec requirement, not a 006 edit. Apply's contract already lives in the meta-spec (REQ-CHANGE-003/004/006/007), so REQ-CHANGE-008 belongs there too — and as a same-spec ADD it is itself kernel-applicable, unlike a cross-spec MODIFY of 006 FR-009 (which the kernel could not apply — it would gate-block on a target in another spec, half-applying the very change that mandates kernel-routing). The requirement names the apply carve-out from 006 FR-008's "markdown is the source of truth" and FR-009's "MAY invoke the CLI" in one place, so there is no silent contradiction; those general rules keep governing the six judgment-bearing verbs.

Ordering. The kernel does not today flip the proposal's status to applied (only withdraw flips) or append the proposal's apply changelog entry — the markdown's old step 7. Those kernel gaps MUST close and be tested before the markdown is reduced to invoke-only, or the MUST would mandate a routing that drops a step (the T-004 shape inverted). §6 orders the kernel work first.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec; op= is one of added | modified | removed | renamed.

The mechanical steps of /spectastic.apply — applying each <spec-delta>, the live-spec <spec-changelog> entry (the kernel MUST accept an author-supplied one-line summary, so the changelog's human voice is preserved rather than reduced to a delta count), the archive-folder move, the proposal status flip to applied, and the §6 task-fold (per REQ-CHANGE-006 / REQ-CHANGE-007) — MUST be performed by the apply kernel (spectastic apply, which is deterministic and requires no ANTHROPIC_API_KEY), not re-implemented in the slash-command markdown. The apply markdown MUST run the preconditions — including the REQ-CHANGE-004 risk gate, listing any status="identified" risks by target= — and surface failures before invoking the kernel; the kernel's own gate is a deterministic backstop, not the user-facing refusal. It MUST also confirm spectastic apply resolves before invoking it, surfacing a missing or stale binary clearly rather than failing silently. Beyond the preconditions, the markdown owns only the post-apply routing nudge (REQ-CHANGE-003) and the inbox-card nudge.

This is a deliberate, named exception to 006 FR-008 ("the markdown procedure remains the source of truth") and FR-009 ("slash commands MAY invoke the CLI but MUST NOT be required to") for apply: its mechanical steps are pure and deterministic, and their prose-only form was the T-004 failure. Those general rules continue to govern the six verbs that need LLM judgment.

The obligation is scoped to same-spec applies. A cross-spec delta (whose target is a requirement in another spec) is the one mechanical step the kernel does not yet perform and MAY remain markdown-handled until it does (TBD-kernel-cross-spec-apply).

Rationale

Apply's mechanical steps need no AI and the CLI runs key-free, so making the kernel authoritative for them removes the whole class of skipped-step bugs on the in-host path (T-004) without touching the verbs that need judgment. Hosted as a meta-spec requirement — not a MODIFY of 006 FR-009 — because a cross-spec delta could not be applied by the kernel this very requirement mandates, and because apply's contract already lives in REQ-CHANGE-*. Priority should: codifying apply's kernel-authoritative path from one incident, matching REQ-CHANGE-004 / REQ-CHANGE-007; re-evaluate after a few real applies.

5 · Risk register

The adversarial pass ran (opt-in --adversarial; the change re-architects must-tier apply behaviour). Findings below; each MUST reach accepted, mitigated, or rejected before apply.

REQ-CHANGE-004 puts the risk-gate refusal (list identified risks "by target= value") in the apply markdown's Preconditions, but the kernel also gates by throwing a generic error string — so reducing the markdown to "invoke the kernel" would replace the specified refusal surface with an exception message.

REQ-CHANGE-004: "refuse and list them by target= value … the apply gate by commands/spectastic.apply.md's Preconditions" vs apply.ts:53's IDENTIFIED_RISK_RE throw.

Draft (status is the author's to set). Caught a real ownership collision. Resolved in the requirement: the markdown MUST run the preconditions (including the REQ-CHANGE-004 risk gate, listing by target=) and surface failures before invoking the kernel; the kernel's gate is a deterministic backstop, not the user-facing refusal. So the REQ-CHANGE-004 reporting contract stays in the markdown; routing doesn't replace it.

Routing the live-spec changelog through the kernel would replace every future apply's rich, hand-authored one-line summary with the kernel's hardcoded "Applied <slug>: N deltas (M successful)", silently downgrading the spec's richest provenance surface.

The live changelog's dense per-apply paragraphs vs apply.ts:114 Applied … ${deltas.length} delta(s) (N successful).

Draft (status is the author's to set). Right — the changelog voice is load-bearing. Resolved by binding it in the requirement and §6: the kernel MUST accept an author-supplied one-line summary (defaulting to the terse line), and the slash command passes the rich one-liner — so routing preserves the human voice rather than collapsing it. A delta-count default is the fallback only when no summary is supplied (e.g. raw CLI use).

REQ-CHANGE-008 makes the most basic lifecycle verb depend on spectastic apply being a built, available CLI in-host — a dependency the slash path doesn't have today (self-contained prose) — and the scope owns only the command-copy re-sync, not the binary's availability, so a fresh checkout or drifted install (per T-006) could invoke a stale/absent CLI.

§2 in-scope: "then re-sync .claude/commands/ (per triage T-006)" + §1: "the slash command can simply invoke spectastic apply".

Draft (status is the author's to set). Real new dependency. Resolved by adding a precondition: the markdown MUST confirm spectastic apply resolves (built/available) before invoking it and surface a missing/stale binary clearly, never fail silently (requirement + §6 task 3). The deeper "guarantee the binary is built in a fresh checkout" is install-tooling territory (the deferred init --tools, T-006's durable owner) — named, not silently assumed.
