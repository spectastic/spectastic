Route the slash apply through the kernel

Approved

1 · Intent

T-004 happened on the in-host /spectastic.apply run: the LLM, following the slash-command markdown, skipped a mechanical step (the §6 fold). The sibling REQ-CHANGE-007 fixed that step in the kernel — the apply kernel now folds §6 deterministically and fidelity-checks it — but only the CLI path calls the kernel. The slash path still re-implements the entire mechanical apply (apply each delta, append the changelog, move the folder to archive, fold §6) in prose the LLM can under-execute. So the path that actually failed is still as fragile as it was.

The fix is now unblocked and simpler than it first looked. The whole mechanical apply already lives in the kernel (applyCommand: risk gate, deltas, changelog, archive, and — since REQ-CHANGE-007 — the fold), and apply is deterministic and key-free — the CLI invokes applyCommand with no AI provider and gates on no ANTHROPIC_API_KEY (unlike spec/plan). So the slash command can simply invoke spectastic apply for the mechanical work, instead of doing it by hand. The earlier worry — that the in-host path (which has no key) couldn't call the AI-coupled CLI — does not apply to apply.

2 · Scope

In scope

  • MODIFY 006 FR-009 (cross-spec): carve /spectastic.apply out of the "MAY invoke the CLI" rule — its mechanical steps MUST run via the kernel, not be re-implemented in the slash markdown.
  • Rewrite commands/spectastic.apply.md so the mechanical apply is one kernel invocation; the markdown keeps preconditions-surfacing, the post-apply routing nudge, and the inbox-card nudge.
  • Close the small gaps so the kernel-routed apply does everything the prose did (e.g. flip the archived proposal's status to applied).

Out of scope

  • Cross-spec deltas. The kernel applyCommand applies deltas to a single spec (its own); a delta targeting another spec's requirement — like this proposal's own MODIFY of 006 FR-009 — is the one mechanical step the kernel does not yet perform, so it stays markdown-handled. Teaching the kernel multi-spec application is a separate change.
  • Routing the other six slash verbs through the kernel. They keep 006 FR-009's "MAY"; only apply (whose mechanical steps are pure, deterministic, and were the T-004 failure) becomes a MUST.

3 · Approach

Invoke, don't re-implement. The slash-command apply procedure stops describing the mechanical steps and instead runs spectastic apply <spec-id> <slug> (key-free), which performs the risk gate, delta-fold, changelog, archive move, and §6 fold deterministically in one call, returning a structured result. The markdown keeps the parts that need judgment or are human-facing: surfacing precondition failures, the post-apply small-vs-large routing nudge (REQ-CHANGE-003), and the inbox-card nudge. This makes every mechanical apply step deterministic on the in-host path — the LLM can no longer skip one, which is the entire T-004 class.

The one honest boundary. The kernel applies deltas to one spec. A cross-spec delta — one whose target lives in another spec — is not something applyCommand does, so the requirement scopes the MUST to the same-spec mechanical apply and names cross-spec as the documented exception the markdown still performs (rare; the budget-bands and this very proposal are the examples). The deferred TBD-kernel-cross-spec-apply would remove even that exception later. The MODIFY also bumps FR-009 to must, since it now carries a hard obligation for apply rather than a pure permission.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec; op= is one of added | modified | removed | renamed.

What changes: 006 FR-009 carves /spectastic.apply out of the optional-CLI rule — its mechanical steps MUST run via the kernel — and bumps to must. (Cross-spec delta: FR-009 lives in 006-kernel-extraction.)

Slash commands MAY instruct the LLM to invoke spectastic <verb> via Bash for deterministic operations, and for most verbs the kernel remains an alternate code path, not a hard dependency. /spectastic.apply is the exception: its mechanical steps — applying each <spec-delta>, the live-spec <spec-changelog> entry, the archive-folder move, and the §6 task-fold (per REQ-CHANGE-006 / REQ-CHANGE-007) — MUST be performed by the kernel (spectastic apply, which is deterministic and requires no ANTHROPIC_API_KEY), not re-implemented in the slash-command markdown. The apply markdown MUST invoke the kernel for those steps and owns only the surrounding judgment and reporting (precondition surfacing, the post-apply routing and inbox-card nudges). This obligation is scoped to same-spec applies; a cross-spec delta (whose target is a requirement in another spec) is the one apply step the kernel does not yet perform and MAY remain markdown-handled until it does.

Rationale

FR-009 originally kept the kernel a pure alternate so the markdown stayed canonical (006 FR-008). T-004 showed that for apply's purely-mechanical steps, prose-only is the failure mode: the LLM skipped one. Since those steps need no AI and the CLI runs key-free, making the kernel authoritative for them removes the whole class of skipped-step bugs on the in-host path without touching the verbs that genuinely need LLM judgment. Scoped to apply and to same-spec deltas to stay honest about what the kernel actually does today.

5 · Risk register

The clean fix the pass points to (and which also dissolves R-2): reshape the delta from MODIFY 006 FR-009 to ADD a meta-spec REQ-CHANGE-008 — a same-spec delta under 000-spectastic (where apply's contract already lives, REQ-CHANGE-003/004/006/007), kernel-applicable, that states the apply-routing obligation and explicitly carves apply out of 006 FR-008/FR-009 rather than editing a general all-verbs rule in another spec. Cross-spec application stays a real kernel limitation (deferred TBD-kernel-cross-spec-apply) but is no longer this proposal's blocker.
