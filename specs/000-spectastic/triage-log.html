Closed specs never flip Draft → Accepted

Spec upstream

Debugging shipped specs (002-validate-cli, 003-init-node-port) still showing "Draft" after end-to-end completion; root cause was the meta-spec's lifecycle is missing a requirement that names when a spec transitions Draft → Accepted; fixed by adding a status-transition requirement and a corresponding step in /spectastic.implement for the last-task tick; regeneration fails because nothing in the current artifacts tells the next LLM session to flip status when tasks drain.

Expected
A spec whose tasks.html has every <input type="checkbox"> ticked and whose tests pass should carry <spec-status value="accepted">Accepted</spec-status>.
Actual
Both 002-validate-cli (50/50 tasks, 58/58 tests, Tier 1 shipped 14 Jun 2026) and 003-init-node-port (29/29 tasks, 58/58 tests, Python retired 15 Jun 2026) still carry <spec-status value="draft">Draft</spec-status>.
Diagnosis
The meta-spec names the lifecycle status values via REQ-LIFECYCLE-002 ("Each template SHOULD include a <spec-status> reflecting Draft / In Review / Accepted / Superseded / Deprecated") but no requirement defines when a spec transitions between those states, and no slash command in the lifecycle flips the status. Author memory is the only mechanism; it fails silently.
Fix
Add a new requirement (provisionally REQ-LIFECYCLE-004) to specs/000-spectastic/spec.html: "Spec status MUST transition from Draft to Accepted when the last unchecked <input type='checkbox'> in the spec's tasks.html is ticked, and the integration tests pass." Update commands/spectastic.implement.md's tick-step to detect last-tick and prompt-or-perform the status flip. Hotfix: flip 002 and 003 to Accepted now (catch-up) before the amendment lands.
Closed by

(b) Applied 2026-06-15-lifecycle-state-transitions: modified REQ-LIFECYCLE-002 + added REQ-LIFECYCLE-004 (finite state machine for artifact lifecycle, with tasks-less-artifact clause). Adversarial pass produced 3 findings, all mitigated. Meta-spec status flipped Draft → Accepted at apply time. (c) Updated commands/spectastic.implement.md step 8 — last-tick detection surfaces an explicit Draft → Accepted confirmation prompt that reminds the author to verify tests pass.

The proposed REQ-LIFECYCLE-004 won't retroactively affect specs whose last-task moment has already passed. Two specs need an immediate hotfix before the upstream change lands:

plan.html and tasks.html statuses never transition; spec.html flip is unreliable in practice

Spec upstream

Debugging shipped specs (002, 003) whose sibling plan.html + tasks.html stay in Draft after the spec.html itself is Accepted, plus spec 004 whose all three artifacts are still Draft despite a successful first npm publish; root cause was REQ-LIFECYCLE-004 covers spec.html via the tasks-driven last-tick trigger and covers tasks-less artifacts (principles, meta-spec, triage logs, inbox) via author affirmation but leaves plan.html and tasks.html in a gap — they belong to a spec that has a tasks.html so the tasks-less clause doesn't apply, but they don't have their own tasks.html to drive the last-tick trigger; fixed by extending REQ-LIFECYCLE-004 so plan/tasks status bundles with the parent spec (one author confirmation flips all three siblings) and tightening /spectastic.implement's last-tick step to always perform the bundled flip; regeneration fails because the next LLM session will keep ticking boxes without flipping any pills.

Expected
Shipped specs have all three artifacts (spec.html, plan.html, tasks.html) at Accepted. In-progress specs have all three at Draft. The three siblings move together as one logical lifecycle unit.
Actual
Audit of the live repo: specs/002-validate-cli/{plan,tasks}.html Draft (spec is Accepted from the T-001 hotfix); specs/003-init-node-port/{plan,tasks}.html Draft (spec is Accepted from the same hotfix); specs/004-npm-publish-workflow/{spec,plan,tasks}.html all three Draft despite the first npm publish landing successfully this session. Three specs, nine artifacts, only two are Accepted.
Diagnosis
Two reinforcing gaps. (a) REQ-LIFECYCLE-004's Draft→Accepted trigger ("last unchecked checkbox in the artifact's tasks.html") only fits the spec.html artifact. The tasks-less clause that follows ("for artifacts without a tasks.html...") covers principles, meta-spec, triage, and inbox — but explicitly assumes the artifact has no associated tasks.html. plan.html and tasks.html fall outside both clauses: they have a tasks.html (the same one), but it's not theirs. (b) Even for spec.html, the LLM-driven last-tick prompt is unreliable: spec 004 drained to T-907 without ever surfacing the flip prompt, because the remaining tasks (T-310, T-905) were manual user gates that paused the drain before the LLM could detect last-tick. Fix
Extend REQ-LIFECYCLE-004 with a bundling clause: a spec's plan.html and tasks.html status MUST track the parent spec.html status — they move together as one logical unit. The same author confirmation that flips spec.html flips all three siblings (and appends matching <spec-changelog> entries to each). Tighten commands/spectastic.implement.md step 8 to always check the bundle-trigger condition after each tick: count remaining unchecked boxes in tasks.html; if zero, prompt the bundled flip even when the current invocation just ticked a non-final box in a partial drain. Hotfix: catch-up flip 002/003 plan + tasks to Accepted; flip 004's spec/plan/tasks to Accepted as part of this triage's fix landing.
Closed by

Spec upstream

Cascade

Kernel apply ENOENTs on a spec's first archive (changes/archive/ missing)

Spec upstream

Debugging a partial apply on 023's first proposal, root cause was a spec gap — REQ-CHANGE-007 mandates the kernel's archive-folder move but never requires it to create changes/archive/ if absent, so a bare fs.rename ENOENTs on a spec's first apply; fixed by a spec clause + a code hotfix (FileSystem.mkdir + mkdir-before-rename); regeneration fails — another LLM implementing the current wording writes the same bare rename.

Expected
A spec's first /spectastic.apply archives the proposal cleanly — creating specs/<id>/changes/archive/ as needed and moving the folder atomically (REQ-CHANGE-007).
Actual
ENOENT: rename …/changes/<slug> → …/changes/archive/<slug> — fs.rename can't move into a missing parent. It threw after applying deltas + folding §6 + flipping the proposal to applied + deepening paths, leaving a partial state (recovered by hand: mkdir archive + mv). Hit on 023-explore-graduation's first proposal; the meta-spec never reproduced it because changes/archive/ always existed.
Diagnosis
REQ-CHANGE-007 specifies "before the archive-folder move" but not that the kernel MUST create the destination parent; the FileSystem abstraction also has no mkdir; apply.ts does a bare fs.rename at the archive (:145) and withdraw (:318) moves.
Fix
/spectastic.propose against specs/000-spectastic/spec.html: amend REQ-CHANGE-007 so the kernel's archive (and withdraw) move MUST create changes/archive|withdrawn/ if absent. Hotfix: add FileSystem.mkdir + nodeFs impl, and mkdir-before-rename at packages/core/src/commands/apply.ts:145 & :318.
Deep dive — hotfix-now + atomicity note
Hotfix now?
Yes — the code hotfix (mkdir-before-rename for both moves) can land immediately; it's safe and unblocks every future first-apply. The spec amendment formalises the requirement via /propose.
Atomicity
The failure exposed a gap in REQ-CHANGE-007's fold-before-rename atomicity: deltas, changelog, §6 fold, and the proposal-flip all committed before the rename, so a rename failure leaves a half-applied state — not the intended "proposal stays in changes/ for a clean retry." Making the move robust (it can't fail on a missing dir) closes the one path that breaks the guarantee.
Infra
FileSystem.mkdir is the third primitive this domain has needed — after rename (apply) and rm (023 graduation rollback). The abstraction grows one method per genuinely-new fs need; the right cadence.

Commands load as skills but don't invoke reliably — descriptions aren't tuned for the skill router

Spec upstream

Debugging the ten verbs firing inconsistently when Claude Code loads them as skills, root cause was a spec gap — REQ-TOOL-001 mandates the markdown procedure but nothing requires the frontmatter to carry skill-invocation metadata (explicit trigger cues / "use when…" phrasing the router keys on), so the human-facing description lines give the skill router too little signal; fixed by a new REQ-TOOL-* clause plus a /skill-creator sweep of all ten commands; regeneration fails — another LLM regenerating commands from their specs writes reader-facing prose again.

Expected
The ten spectastic verbs, loaded by the Claude Code harness as skills, fire reliably — both on an explicit /spectastic.<verb> and when user intent matches the verb's job — because each command's frontmatter gives the skill router strong, unambiguous triggering signal.
Actual
Commands load as skills but "do not invoke reliably enough." Command frontmatter is authored for a human reader, not for skill-invocation matching, and no requirement encodes a triggering bar. Deep dive — cross-spec cascade + T-006 sync dependency
Cross-spec cascade
The individual verbs are owned by their own specs (007-core-triage … 014-core-implement, plus 011-core-spec, 018-explain, 022-explore). Mandatory workflow steps live in command markdown, so nothing guarantees they run

Principles upstream

Debugging why pre-verb steps (the interview) and post-verb steps (git commit) can silently not happen, root cause was a missing principle — a step written into commands/*.md is advisory prose an LLM can skip; a guarantee for an LLM-executed workflow must live in deterministic code (the kernel) or CI, never in the prompt; fixed by stating that invariant and reframing init --tools + validate --strict as the guarantee layer; regeneration fails — absent the principle, another session keeps writing mandatory steps into markdown.

Expected
A step whose omission is a defect — the decision-phase interview before a spec/propose write, a git commit after apply/implement — reliably runs, or its absence is rejected.
Actual
Those steps are instructions in the verb's markdown, loaded as a skill; the LLM can skip, reorder, or half-satisfy them. Zero enforcement by construction. Evidenced by the reliability arc (T-004 skipped fold, T-006 stale installed copies, T-008 unreliable invocation) and by two run_loop pilots (T-603) showing descriptions can't carry the guarantee.
Diagnosis
No principle states where a guarantee must live. Research (guarantee-layer considerations, ~20 primary sources) confirms: across every agent tool, a step is guaranteed only when harness-invoked deterministic code can say deny; markdown/rules/MCP are all advisory. The one portable, unbypassable layer is VCS/CI; the strongest is owning the loop — which spectastic already does via the kernel.
Fix
Amend principles.html: "a mandatory step's guarantee MUST live in the kernel or CI, never in command markdown; markdown is advisory." Then a spec that pulls the two deferred items forward as the guarantee layer — init --tools (per-harness hook adapters + a git pre-commit calling spectastic validate) and validate --strict (the CI gate that rejects an artifact with open <spec-question>s or a wrong commit/fold shape). REQ-TOOL-004 descriptions stay as the UX nudge on top.
Closed by
The root cause — the missing invariant — is landed as P-8 · Guarantees live in the kernel or CI (principles v1.3.0, applied 2026-07-02-p8-guarantees-in-kernel-or-ci, 3 adversarial risks mitigated). The mechanism half (the strict-CI gate, the hook/pre-commit installer, and — surfaced by P-8's own hand-apply — moving the principles-apply path into the kernel) is the named follow-on: TBD-guarantee-layer-spec. Survey: guarantee-layer-considerations.html.
Deep dive — principles cascade + reframes two deferred items
Invariant implicated
Proposed principle: guarantees live in the kernel/CI, not the prompt. Cascades to how every verb is authored (its mandatory steps must have a deterministic owner or a checkable post-condition) and reframes the OKR of init --tools and validate --strict from "convenience" to "enforcement".
The interview is special
A judgment step can't be hook-gated (a marker the LLM writes fakes it). The guarantee is post-hoc: reject the artifact that shows a skipped interview (an open <spec-question>). Spectastic already has the no-unresolved-question rule; the fix makes it an unbypassable CI gate, not advisory.
Not spec inflation
This isn't a code drift patchable at implementation — no kernel change makes markdown steps enforceable. The lowest rung whose fix passes the regen test is the principle: state where guarantees live, then the spec follows. Scope surfaced, not silently promoted.
