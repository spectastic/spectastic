Closed specs never flip Draft → Accepted

Spec upstream

Debugging shipped specs (002-validate-cli, 003-init-node-port) still showing "Draft" after end-to-end completion; root cause was the meta-spec's lifecycle is missing a requirement that names when a spec transitions Draft → Accepted; fixed by adding a status-transition requirement and a corresponding step in /spectastic.implement for the last-task tick; regeneration fails because nothing in the current artifacts tells the next LLM session to flip status when tasks drain.

Expected
A spec whose tasks.html has every <input type="checkbox"> ticked and whose tests pass should carry <spec-status value="accepted">Accepted</spec-status>.
Actual
Both 002-validate-cli (50/50 tasks, 58/58 tests, Tier 1 shipped 14 Jun 2026) and 003-init-node-port (29/29 tasks, 58/58 tests, Python retired 15 Jun 2026) still carry <spec-status value="draft">Draft</spec-status>.
Diagnosis
The meta-spec names the lifecycle status values via REQ-LIFECYCLE-002 ("Each template SHOULD include a <spec-status> reflecting Draft / In Review / Accepted / Superseded / Deprecated") but no requirement defines when a spec transitions between those states, and no slash command in the lifecycle flips the status. Author memory is the only mechanism; it fails silently.
Fix
Add a new requirement (provisionally REQ-LIFECYCLE-004) to specs/000-spectastic/spec.html: "Spec status MUST transition from Draft to Accepted when the last unchecked <input type='checkbox'> in the spec's tasks.html is ticked, and the integration tests pass." Update commands/spectastic.implement.md's tick-step to detect last-tick and prompt-or-perform the status flip. Hotfix: flip 002 and 003 to Accepted now (catch-up) before the amendment lands.
Closed by
(a) Hotfix 15 Jun 2026 — flipped 002-validate-cli and 003-init-node-port to Accepted. (b) Applied 2026-06-15-lifecycle-state-transitions: modified REQ-LIFECYCLE-002 + added REQ-LIFECYCLE-004 (finite state machine for artifact lifecycle, with tasks-less-artifact clause). Adversarial pass produced 3 findings, all mitigated. Meta-spec status flipped Draft → Accepted at apply time. (c) Updated commands/spectastic.implement.md step 8 — last-tick detection surfaces an explicit Draft → Accepted confirmation prompt that reminds the author to verify tests pass.
Deep dive — hotfix required before amendment

The proposed REQ-LIFECYCLE-004 won't retroactively affect specs whose last-task moment has already passed. Two specs need an immediate hotfix before the upstream change lands:

  • 002-validate-cli — flip Draft → Accepted; FR-011 alignment proposal already applied; integration test (SC-001) verified.
  • 003-init-node-port — flip Draft → Accepted; byte-identity parity with Python verified via diff -r; Python script and 001-cli supersession both landed.

The upstream amendment lands via /spectastic.propose against specs/000-spectastic/spec.html adding REQ-LIFECYCLE-004 and updating commands/spectastic.implement.md prose. After the amendment, future specs will not exhibit this drift — the tick-step of the last task in any tasks.html will surface the status flip as part of the standard implement flow.

No cross-spec contract is touched (the meta-spec stands alone for the lifecycle protocol). No project-wide principle is violated — P-1..P-5 are about HTML format, IDs, and typography, not status semantics. No deferred functionality is exposed.

plan.html and tasks.html statuses never transition; spec.html flip is unreliable in practice

Spec upstream

Debugging shipped specs (002, 003) whose sibling plan.html + tasks.html stay in Draft after the spec.html itself is Accepted, plus spec 004 whose all three artifacts are still Draft despite a successful first npm publish; root cause was REQ-LIFECYCLE-004 covers spec.html via the tasks-driven last-tick trigger and covers tasks-less artifacts (principles, meta-spec, triage logs, inbox) via author affirmation but leaves plan.html and tasks.html in a gap — they belong to a spec that has a tasks.html so the tasks-less clause doesn't apply, but they don't have their own tasks.html to drive the last-tick trigger; fixed by extending REQ-LIFECYCLE-004 so plan/tasks status bundles with the parent spec (one author confirmation flips all three siblings) and tightening /spectastic.implement's last-tick step to always perform the bundled flip; regeneration fails because the next LLM session will keep ticking boxes without flipping any pills.

Expected
Shipped specs have all three artifacts (spec.html, plan.html, tasks.html) at Accepted. In-progress specs have all three at Draft. The three siblings move together as one logical lifecycle unit.
Actual
Audit of the live repo: specs/002-validate-cli/{plan,tasks}.html Draft (spec is Accepted from the T-001 hotfix); specs/003-init-node-port/{plan,tasks}.html Draft (spec is Accepted from the same hotfix); specs/004-npm-publish-workflow/{spec,plan,tasks}.html all three Draft despite the first npm publish landing successfully this session. Three specs, nine artifacts, only two are Accepted.
Diagnosis
Two reinforcing gaps. (a) REQ-LIFECYCLE-004's Draft→Accepted trigger ("last unchecked checkbox in the artifact's tasks.html") only fits the spec.html artifact. The tasks-less clause that follows ("for artifacts without a tasks.html...") covers principles, meta-spec, triage, and inbox — but explicitly assumes the artifact has no associated tasks.html. plan.html and tasks.html fall outside both clauses: they have a tasks.html (the same one), but it's not theirs. (b) Even for spec.html, the LLM-driven last-tick prompt is unreliable: spec 004 drained to T-907 without ever surfacing the flip prompt, because the remaining tasks (T-310, T-905) were manual user gates that paused the drain before the LLM could detect last-tick. The discipline that's supposed to surface the flip is fragile when manual gates are interleaved with code tasks.
Fix
Extend REQ-LIFECYCLE-004 with a bundling clause: a spec's plan.html and tasks.html status MUST track the parent spec.html status — they move together as one logical unit. The same author confirmation that flips spec.html flips all three siblings (and appends matching <spec-changelog> entries to each). Tighten commands/spectastic.implement.md step 8 to always check the bundle-trigger condition after each tick: count remaining unchecked boxes in tasks.html; if zero, prompt the bundled flip even when the current invocation just ticked a non-final box in a partial drain. Hotfix: catch-up flip 002/003 plan + tasks to Accepted; flip 004's spec/plan/tasks to Accepted as part of this triage's fix landing.
Closed by
2026-06-16-lifecycle-sibling-bundling applied on 16 Jun 2026. Landed REQ-LIFECYCLE-005 as a separate requirement (not an extension of -004 as originally proposed in this card — separating preserves -004's transition-event semantics and lets -005 carry the readiness-vs-immutability clarification). Adversarial pass forced two scope refinements: the implement-step predicate is scoped to Draft state (preventing re-confirmation loops on already-Accepted specs), and the hotfix shrunk from 9 artifacts to 4 (002 plan + tasks; 003 plan + tasks). 004's bundle stays Draft pending T-905 (manual PR-breaking smoke for SC-003) — the same predicate that forbids re-confirmation loops also forbids smuggling 004's flip through the apply step before its trigger has legitimately fired.
Deep dive — hotfix list + cascade through the implement command

The hotfix lands in two strokes:

  • 002-validate-cli/plan.html + tasks.html — flip Draft → Accepted; append a one-line changelog entry citing this card.
  • 003-init-node-port/plan.html + tasks.html — same.
  • 004-npm-publish-workflow/spec.html + plan.html + tasks.html — all three; the first npm publish (v0.1.0-pre.3 + .4) is the affirmation; the spec is the operative contract for the publish workflow.

The upstream amendment lands via /spectastic.propose against specs/000-spectastic/spec.html. The proposal adds the bundling clause to REQ-LIFECYCLE-004 and tightens the implement command prose. After the amendment, the next session's drain reliably flips all three siblings on the last tick — no more nine-artifact lag.

Cascade vs T-001: T-001 closed the spec.html-only flip protocol; T-002 closes the plan + tasks coverage gap that T-001's fix didn't address. The two amendments are sequential refinements of the same REQ.

Triage defaults to the symptom/presentation layer instead of laddering to the highest layer that must change

Spec upstream

The no-open-questions case (020 T-005) was first classified at the presentation layer (a 020 reader bug) and only reached the correct cross-spec root cause — the <spec-questions> format contract — after author pushback. Triage's speed-optimised procedure carries "fix at the highest layer that needed to change" as a discipline line but no explicit root-cause-laddering step that forces probing upstream before classifying. Regeneration fails — another session reproduces the easy-layer default.

Expected
Triage proactively tests whether the symptom's true owner is upstream (spec / cross-spec / principles) before settling on the convenient layer.
Actual
Optimised for speed, it lands on the presentation/implementation layer first; the deeper layer surfaced only after the user pushed back (T-005).
Diagnosis
The triage command (commands/spectastic.triage.md) states the highest-layer discipline but lacks a procedural step that ladders the root cause ("if only the symptom layer changed, would the regen test recur?") before the layer is committed.
Fix
/spectastic.propose against the meta-spec — add a root-cause-laddering step/gate to the triage procedure (a single "is the owner actually upstream?" probe wired into the regeneration test), without losing the <30-second-card ergonomics. Touches commands/spectastic.triage.md + likely a REQ-TOOL-* clause.
Closed by
Applied 2026-06-23-triage-root-cause-laddering — added REQ-LIFECYCLE-007 (the bidirectional laddering gate; landed under REQ-LIFECYCLE-*, not REQ-TOOL-*); implemented in commands/spectastic.triage.md.
Deep dive — self-referential; speed-vs-depth tension

Worked example: 020 T-005 (presentation-first → cross-spec after pushback). The fix must add depth without killing the format's deliberate speed (a card reads in <30s): a single laddering prompt tied to the existing regeneration test, not a heavy analysis pass. The discipline already says "fix at the highest layer"; this makes it a step, not just a maxim. No cross-spec contract beyond the triage command; no new principle.

No guard detects a skipped task-fold — a silent apply step 8 is undetectable

Spec upstream

Debugging how the budget-bands fold (T-004) went unnoticed until a human asked; root cause was a spec gap — REQ-CHANGE-006 mandates the fold but no requirement makes its omission detectable, so a skipped step 8 leaves no failing signal; fixed by adding a validate rule (and its owning requirement) that flags an applied proposal whose §6 has no matching folded phase; regeneration fails — given the current meta-spec, the next session has no contract telling it the guard should exist, so the blind spot persists.

Expected
spectastic validate flags an applied/archived proposal whose §6 tasks have no matching provenance-linked phase in the target's tasks.html — the same way verify-view-stale flags a drifted verify view — so a skipped fold fails loudly instead of silently.
Actual
No such rule and no requirement mandating one. The fold is governed only by REQ-CHANGE-006's procedural step; when an apply run skips it, nothing in the corpus is in a detectably-wrong state, so the gap surfaces only by a human noticing the implementation never landed (here, weeks could have passed with the fabricated Larson citation shipping).
Diagnosis
REQ-CHANGE-006 specifies the fold as an action but defines no checkable post-condition; the enforcement requirement (a validate rule asserting fold-completeness) is genuinely missing, so this is a spec gap, not the implementation drift of T-004.
Fix
/spectastic.propose against the meta-spec — add REQ-CHANGE-007: an applied proposal's §6 tasks MUST appear as a provenance-linked folded phase in the target tracker, enforced by a fold-gap validate rule. Implement as packages/schema/src/rules/proposal-tasks-unfolded.ts + one registry entry, modelled on packages/schema/src/rules/verify-view-stale.ts.
Deep dive — cascade + relationship to T-004
Cascade
/spectastic.propose → /spectastic.apply folds the rule's own implementation tasks → /spectastic.implement drains them (the new rule + fixture + registry entry).
vs T-004
T-004 is the one-off execution miss (regen passes — the contract was correct); T-005 is the structural prevention for its whole class (regen fails — the detectability contract is missing). Fixing T-004 alone lets the next skipped fold recur unseen; T-005 makes the omission self-evident.
Scope
Scoped to the fold post-condition. Do not over-generalise to "validate every apply step" — the fold is the step with a checkable artifact (a phase that is present or absent); other apply steps (archive move, status flip) already have their own guards or are self-evident.
Principles
No new principle — this is the format/change-management contract, not a project-wide invariant. It does instantiate the existing drift-guard pattern (verify-view-stale) one more time.

Installed .claude/commands/ are stale copies — the executed slash command isn't the source of truth

Spec upstream

Debugging an apply that skipped the §6 fold, root cause was a spec/process gap — installed commands are one-time copies with no sync mechanism, so the /spectastic.apply the harness executed was a 13 Jun copy predating REQ-CHANGE-006's step-8 fold; fixed by re-syncing now (hotfix), with the durable owner being the deferred init --tools; regeneration fails — the copies drift again on any source update.

Expected
The slash command the LLM executes matches commands/<verb>.md, the canonical procedure (REQ-TOOL-001; 006's "markdown is the source of truth").
Actual
.claude/commands/spectastic.apply.md is a 13 Jun 2026 copy with no step-8 fold (predates REQ-CHANGE-006); all four checked .claude/commands/*.md (apply, implement, propose, spec) differ from commands/ source. The 26 Jun apply of 2026-06-26-fold-gap-guard followed the stale copy and skipped the fold — T-004 reproduced live.
Diagnosis
.claude/commands/ holds one-time copies (not symlinks) of the commands/*.md source, and nothing re-syncs them; the installer that would (spectastic init --tools) is deferred (meta-spec §2 Out of scope, defer-to="TBD"). So source updates never reach the executed command.
Fix
Hotfix: re-sync .claude/commands/ from commands/ now. Durable: fold install/sync into the deferred init --tools — symlink installed commands to source, or a drift check, so they cannot go stale. Surface into that deferred work; no new requirement here.
Deep dive — scope-deferred + hotfix-now
Hotfix now?
Yes — re-sync .claude/commands/*.md from commands/*.md so the next apply/implement runs current procedures; the stale apply copy is actively dangerous (it skips the fold). Trivial copy, reversible.
Scope
Deferred. The durable sync mechanism belongs to spectastic init --tools (meta-spec §2, defer-to="TBD"). Surfaced here as the install-tooling requirement to fold in when that lands — not promoted to a new requirement now (no spec inflation).
vs T-004 / T-005 / REQ-CHANGE-007
Distinct root cause. Those harden the apply procedure (skippable prose → deterministic kernel fold); this is the installed artifact drifting from source, so even a correct procedure isn't the one executed. Note REQ-CHANGE-007 mitigates this for the fold specifically — a kernel-side fold runs regardless of which markdown copy the LLM read — a further argument for routing apply through the kernel (sibling TBD-route-fold-through-kernel).

Kernel apply ENOENTs on a spec's first archive (changes/archive/ missing)

Spec upstream

Debugging a partial apply on 023's first proposal, root cause was a spec gap — REQ-CHANGE-007 mandates the kernel's archive-folder move but never requires it to create changes/archive/ if absent, so a bare fs.rename ENOENTs on a spec's first apply; fixed by a spec clause + a code hotfix (FileSystem.mkdir + mkdir-before-rename); regeneration fails — another LLM implementing the current wording writes the same bare rename.

Expected
A spec's first /spectastic.apply archives the proposal cleanly — creating specs/<id>/changes/archive/ as needed and moving the folder atomically (REQ-CHANGE-007).
Actual
ENOENT: rename …/changes/<slug> → …/changes/archive/<slug> — fs.rename can't move into a missing parent. It threw after applying deltas + folding §6 + flipping the proposal to applied + deepening paths, leaving a partial state (recovered by hand: mkdir archive + mv). Hit on 023-explore-graduation's first proposal; the meta-spec never reproduced it because changes/archive/ always existed.
Diagnosis
REQ-CHANGE-007 specifies "before the archive-folder move" but not that the kernel MUST create the destination parent; the FileSystem abstraction also has no mkdir; apply.ts does a bare fs.rename at the archive (:145) and withdraw (:318) moves.
Fix
/spectastic.propose against specs/000-spectastic/spec.html: amend REQ-CHANGE-007 so the kernel's archive (and withdraw) move MUST create changes/archive|withdrawn/ if absent. Hotfix: add FileSystem.mkdir + nodeFs impl, and mkdir-before-rename at packages/core/src/commands/apply.ts:145 & :318.
Deep dive — hotfix-now + atomicity note
Hotfix now?
Yes — the code hotfix (mkdir-before-rename for both moves) can land immediately; it's safe and unblocks every future first-apply. The spec amendment formalises the requirement via /propose.
Atomicity
The failure exposed a gap in REQ-CHANGE-007's fold-before-rename atomicity: deltas, changelog, §6 fold, and the proposal-flip all committed before the rename, so a rename failure leaves a half-applied state — not the intended "proposal stays in changes/ for a clean retry." Making the move robust (it can't fail on a missing dir) closes the one path that breaks the guarantee.
Infra
FileSystem.mkdir is the third primitive this domain has needed — after rename (apply) and rm (023 graduation rollback). The abstraction grows one method per genuinely-new fs need; the right cadence.
