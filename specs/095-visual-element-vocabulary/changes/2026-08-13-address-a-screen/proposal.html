Address a screen

Approved

1 · Intent

A screen declares id= and no consumer resolves it. A design points at a whole file, the materialised view lists screens as plain headings, and a reader who wants to know which screen a decision concerns opens the file and searches. Every other relation in the estate is addressable — a requirement is FR-003, a decision is D-002, a risk carries target=, a contract has a full coordinate — and the screen, which is the thing a design conversation is most often about, has nothing.

The mechanism already exists and needs one more kind rather than an invention. 067 established the owner-qualified spectastic://<project>/… scheme, and 076 extended it to contracts in both the proposed and effective forms. A screen sits at the same altitude as a proposed contract — it belongs to one spec, it is named, and it is referenced from outside the file that declares it.

Found by reading a real design against its screens: the design's own prose could not name what it was describing, so it described the file instead.

2 · Scope

In scope

  • A screen coordinate kind, resolvable to a declared <spec-screen>.
  • The materialised view linking each screen to its declaration rather than printing a bare heading.

Out of scope

  • A state coordinate. A state is addressable within its screen and nothing outside has asked to reach one; adding a second kind speculatively is how a grammar acquires rungs nobody climbs. defer-to=TBD-state-coordinate.
  • Serving screens over the external read surface. That belongs to the repository which owns that surface, not here. defer-to=never.

3 · Approach

One kind, and deliberately no second mechanism. The alternative — a local cites-screen= attribute resolved within the project — is smaller and would land sooner, and it would create a second way to refer to the same thing that a coordinate would later have to absorb. The estate already carries more of those than it wants.

The shape follows the contract precedent exactly rather than reasoning afresh: spectastic://<project>/spec/<spec-id>/screen/<name>, where the name is the screen's declared id. A screen has only one location — unlike a contract, which is proposed and then effective — so it needs only the spec-scoped form, and the effective-form question does not arise.

Resolution is local and reads declarations only, like every other coordinate here. Nothing fetches, and a coordinate naming a project that is not this one resolves to nothing rather than reaching for it.

4 · Deltas

A declared screen MUST be addressable by a coordinate of the kind the project already uses for its other addressable artifacts, and resolving one MUST NOT require a network.

Rationale

A screen is the thing a design conversation is most often about and the one thing it cannot name. Every neighbouring relation is addressable; the screen carries an id that no consumer resolves, so a design points at a file and a reader searches it.

Deliberately one mechanism. A local citation attribute would be smaller and would be a second way to say the same thing, which a coordinate would then have to absorb — the estate already carries more duplicate referencing than it wants.

Only the spec-scoped form is needed. A contract has two locations across its lifecycle and therefore two coordinate shapes; a screen has one, so the effective-form question does not arise and no rung is added for it.

5 · Risk register

Self-run rather than delegated, as with this session's earlier pass — weaker independence than the register usually assumes, and recorded rather than glossed.

A coordinate for a thing with one location may not have earned a coordinate

The contract precedent this borrows from exists because a contract genuinely moves — proposed, then effective — and needs an unambiguous name at each. A screen does not move. So the strongest argument for the mechanism does not apply here, and what is left is consistency, which is a weaker reason to add a grammar rung.

Mitigated. The requirement is written to the capability rather than to a syntax, so the resolution can be the minimum that satisfies it. And the demand is real rather than anticipated: it came from a design that could not name what it was describing, not from symmetry.

Screen ids are unique per file, and a coordinate implies uniqueness per spec

The existing shape rule enforces uniqueness within a document. A spec may hold several screen files in its visual/ directory, so two files could each declare converter and both resolve from the same spec-scoped coordinate.

Accepted, with the reason recorded. Real and not yet reachable: no project in the estate has more than one screens file. Closing it now would mean choosing between a cross-file uniqueness scan and a file segment in the coordinate, on no evidence. The implementing task carries a note to report a collision rather than pick a winner silently, which is the behaviour that keeps the choice open.

The view-linking half could be its own change

Two things are in scope: the coordinate, and the generated view using it. The second is a rendering change that could ship separately.

Accepted. A coordinate with no consumer is exactly the speculative-vocabulary failure this proposal argues against elsewhere. The view is its first consumer and lands with it.

6 · Tasks

  • Add the screen kind to the coordinate grammar and its resolver, beside the contract kind.
  • Resolve a screen coordinate to its declaration; report an ambiguous name across two screens files rather than choosing one.
  • Link each screen in the materialised view to its declaration.
  • Tests: resolves; refuses a network; reports a collision; a coordinate for an absent screen resolves to nothing rather than erroring.

7 · Open questions

None outstanding. The uniqueness question is a recorded risk with a chosen behaviour rather than an open decision.
