Change proposal · 095-visual-element-vocabulary

Annotate the element

An annotation can say what a screen is doing and not which control it is about — so the one thing a measurement could be snapped to has no way to be written down.

Status Applied Change ID 2026-08-13-annotate-the-element Spec 095-visual-element-vocabulary Author Brian Corbin · @briancorbinxyz Created 13 Aug 2026 Targets 2 requirements Read time

Adds two capabilities to the annotation: the element it is about, and the layer it belongs to. Both are additions — nothing existing changes, and every annotation authored today stays valid.

Annotate the element

Applied

1 · Intent

An annotation belongs to a state, and a state belongs to a screen. Nowhere in that chain is there a word for the control the annotation is about. The worked example lost real content to this when it was migrated onto the vocabulary: it had annotated amount-field, convert-button, rate-line and staleness-badge by name, and afterwards every one of those rows had become an unattributed note on a state. Three of them said something measurable — a minimum tap target, a transition duration — and a measurable claim about nothing in particular cannot be checked by anything.

The second gap is the layer axis. The survey's §4 held the exemplar's seven layers up and ruled "keep the axis, not the number", and D-005 chose to express that axis as a grouping over the accessibility type system rather than as a tenth taxonomy. The grouping half was never built: nothing anywhere records which layer an annotation belongs to. For five of the eight categories that turns out not to matter, because the type already answers it — a role is structure, an accessibility state is behaviour, a citation is a requirement. For the three with no accessibility analogue it matters completely, because there is nothing to derive from and the vocabulary currently has no way to say which of them an annotation is.

2 · Scope

In scope

  • Naming the element an annotation is about, as provenance that nothing resolves.
  • Declaring the layer an annotation belongs to, and reporting a declared layer that disagrees with the one its accessibility typing implies.
  • The rendering half — both surface with scripting off, per this spec's existing NFR-001. This is more work than it sounds: the element has two content slots and they are both already spoken for.

Out of scope

  • Matching a named element against a rendered accessibility tree — and naming the token a measurable value comes from, which was in this proposal and came out: its only consumer is the measurement slice, so the shape should be chosen by whoever builds the thing that reads it rather than guessed a slice early.
  • What a tracking annotation should contain. This change gives the category a name; it says nothing about event payloads or consent.
  • The same, for content budgets.
  • Importing annotations from a design tool into these attributes.
  • Rendering annotations anywhere outside the sidecar that holds them.

3 · Approach

The element name is provenance, not a selector. Nothing declares an element inventory for a screen, and this change deliberately does not add one — the design tools disagree about what an element even is, and inventing a registry here would put a third naming scheme beside the two the corpus and the contract convention already own. So a target names something in the implementation and nothing resolves it at validate time, which is the posture 093 FR-006 already takes for source=. The check that a target matches a real control is a measurement, and measurement is a different slice.

The layer is declarable, and a disagreement is reported rather than resolved. The first draft derived it and forbade an authored one, on the reading that a grouping over a type system is read off rather than written down. That was wrong, and the way it was wrong is worth keeping: the deferred design-tool import is committed to landing any annotations a source carries, and those arrive with a category their author stated, so a vocabulary with no word for it would force the importer to throw that word away and re-derive — inference beating declaration, which 073 FR-003 settled against in both directions. Where both exist and disagree, neither is reliably right: an author who typed a control as a textbox and labelled the annotation behaviour may have mistyped either. So it is reported, on the same reasoning that makes the token-set disagreement across designs a finding rather than a precedence rule.

Which categories have no accessibility analogue is deliberately not fixed here. It is a judgment about other people's products, it will age, and T-001 has already found the current transcription wrong in both directions — four categories the survey homed fall through as unknown, and one in the map is not in the survey's table at all. A requirement that named a count would have to be amended every time that judgment moved. The list stays in the data FR-006 already owns.

4 · Deltas

An annotation MUST be able to name the element it is about. That name MUST be treated as provenance and MUST NOT be resolved at validate time, and an annotation naming no element MUST remain valid, reading as a statement about the state it belongs to.

Rationale

An annotation currently belongs to a state, and a state to a screen, so there is no word anywhere for the control an annotation is about — which is how the worked example lost four named targets and three measurable claims when it was migrated onto this vocabulary. A measurable claim about nothing in particular cannot be checked by anything. It is provenance rather than a reference because nothing declares an element inventory for a screen and this change deliberately does not add one: the design tools disagree about what an element is, and a registry here would be a third naming scheme beside the two the corpus and the contract convention already own. The same posture 093 FR-006 takes for a design source. Naming nothing stays valid because most annotations are about the screen rather than a control, and requiring a target would push authors to invent one.

An annotation MUST be able to declare the layer it belongs to. Where the annotation is also typed by the accessibility tree and the declared layer disagrees with the layer that typing implies, the disagreement MUST be reported rather than resolved. An annotation in a category with no accessibility analogue MUST be able to declare that category, and the set of such categories MUST NOT be fixed by this requirement.

Rationale

The survey held the exemplar's seven layers against its own bar and kept the axis rather than the number; D-005 then chose to express that axis as a grouping over the accessibility type system rather than as a tenth taxonomy. Deriving the layer and forbidding an authored one was the first draft and was wrong in a way worth recording: 073 FR-003 settles declaration over inference in both directions, and the deferred design-tool import is committed to landing any annotations a source carries — annotations that arrive with a category their author stated. A vocabulary with no word for it would force the importer to discard that word and re-derive, which is inference beating declaration. So the layer is declarable, and the disagreement is reported rather than silently resolved, because neither the author's word nor the implied one is reliably right and picking one would hide the case worth looking at. The set of analogue-less categories is deliberately left open: it is a judgment about other people's products, it will age, and T-001 has already found the current transcription wrong in both directions — so it belongs in the data FR-006 owns, not fixed inside a requirement.

5 · Risk register

Populated by the adversarial risk pass when the proposal triggers the heuristic (touches a must-tier requirement, contains an op="removed" delta, or spans ≥2 topic prefixes). One <spec-risk> per finding. target= is required (missing renders broken). status= defaults to identified; apply refuses until each transitions to accepted, mitigated, or rejected.

Forbidding the vocabulary from ever carrying an authored layer makes derivation beat declaration, so the design-tool importer this spec explicitly defers has nowhere to put the category its source actually stated and must silently discard it — the very loss FR-006 exists to prevent, and unwinding it later costs a MODIFY on a must-tier requirement.

"the vocabulary MUST NOT carry an authored layer for such an annotation" (delta FR-012), against TBD-design-source-adapters' commitment to land "any annotations the source carries" and 073 FR-003's settled rule that a declaration takes precedence over inference "in both directions".

Accepted, and this one reversed a recommendation made earlier in the same session. The counter-argument — that FR-006's category map is itself the landing place, so an imported label is translated rather than discarded — was considered and rejected: translation loses the author's own word, and a rule that can only be satisfied by discarding a declaration is the shape 073 FR-003 rules out. FR-012 now makes the layer declarable and reports a disagreement with the implied one rather than resolving it, on the same reasoning that makes a token-set disagreement across designs a finding rather than a precedence rule.

The proposal promises three new attributes will surface with scripting off, but spec-annotation has exactly two content slots — ::before held by role/aria-state, ::after by cites — and the new FR-008 broken-label for the category-plus-type collision must occupy ::after alongside cites, so at least one of target, token, cites or the broken label renders nothing and the "100% readable" claim quietly stops being true.

NFR-001 — "at least 100% of the declaration, its states and its annotations readable with JavaScript off" — versus §2 Scope's "The rendering half — all three surface with scripting off, per this spec's existing NFR-001" and the single assets/spec.css task line covering it.

Accepted. Dropping the token attribute removes one claimant on the two slots, which helps but does not settle it — target, layer, cites and the new broken label still share two pseudo-elements. §2 now says plainly that this is more work than it sounds, and the task list carries the mechanism (a combination selector per attribute, because attr() on an absent attribute yields an empty string so separators cannot be shared) plus an explicit screenshot step. The block's own comment records this exact trap costing a real bug that every structural assertion missed.

The token capability is the one in-scope item with no consumer inside this change — its only user is deferred in the same section — yet it lands a must-tier prohibition on resolution that the consuming slice will have to unwind, and it is the increment that takes the artifact past its declared 1,900-word budget.

In scope: "Naming the token a measurable value comes from, so a later measurement has something to snap to" — deferred in the same section as defer-to="TBD-fidelity-measurement": "snapping a measured value to the token this change lets an annotation name".

Accepted and the delta was dropped. Building a capability whose only consumer is a slice that does not exist means guessing the shape that slice will want, and the guess arrives already must-tier. It moves to TBD-fidelity-measurement's scope, named explicitly there rather than silently removed. The exemplar's three measurable claims stay unrestored until it lands — which is the honest cost and is recorded in the task list rather than glossed.

FR-012's operative content — that exactly three categories have no accessibility analogue, hence which values the authored category attribute may take — rests entirely on the design's grounding row marked assumed, with no accepted risk recording the gap, and T-001 has already proven that transcription wrong in both directions (four homed categories fall through as unknown; emphasis is in the map and not in the survey table).

KB-0001@2026-07-25 — "A must-tier decision may not rest on an assumed or unresolved-spike fact without an explicit <spec-risk status="accepted"> recording who accepted the gap and why" — against design.html's grounding row "The categories the common design tools use, and which have no accessibility analogue … assumed".

Accepted, and resolved by removing the dependency rather than by recording it. FR-012 no longer asserts how many such categories there are or names them — it says the set is not fixed by the requirement. The judgment stays in the data FR-006 already owns, where T-001 is correcting it, so the requirement no longer rests on an assumed fact at all and the corpus rule stops applying.

6 · Tasks

Scoped to this change only. On /spectastic.apply these fold into the target's tasks.html as a new provenance-linked phase (per REQ-CHANGE-006) that /spectastic.implement drains — this list is then the frozen intent record.

  • packages/schema/src/visual-vocabulary.ts — the annotation gains two attributes in the drift-guarded vocabulary table; tests first, red.
  • packages/schema/src/rules/annotation-typed.ts — a declared layer that disagrees with the one the annotation's accessibility typing implies is reported; a target naming anything is never resolved.
  • packages/core/src/visual/annotation-categories.ts — the unmapped category values come from this map, so the authored attribute and the import landing-place stay one list. Closes T-001's type-widening half.
  • assets/spec.css — surface both with attr() so NFR-001 holds with scripting off. Budget this properly: ::before is held by [role]/[role][aria-state] and ::after by [cites], so every new attribute needs its own combination selector or it silently loses the cascade — attr() on an absent attribute yields an empty string, which is why separators cannot be shared. The block already documents this trap costing a real bug, caught by screenshotting a fixture rather than by a test.
  • assets/spec.css — the visibly-broken half of FR-008 for a layer that disagrees with its typing, following the MISSING SOURCE pattern already in the block, and sharing ::after with [cites] without colliding.
  • Screenshot the fixture in both themes at two widths before believing any of the above — the one prior bug in this block was invisible to every structural assertion.
  • templates/screen.html — scaffold a targeted annotation and an unmapped one, so both shapes are offered rather than only described.
  • Fixtures under packages/schema/fixtures/annotation-typed/ — positive for both attributes, negative for a declared layer disagreeing with its typing.
  • examples/currency-converter/specs/001-currency-conversion/visual/converter.screen.html — restore the four named targets the migration dropped. The three measurable claims wait for the token attribute, which this proposal deferred.

7 · Open questions

None outstanding. Three decisions were anchored in the interview and one of them reversed a recommendation made earlier in the same session: an element name is provenance that nothing resolves rather than a reference into an inventory this change declines to invent; the layer is declarable with a disagreement reported, not derived-only, because forbidding an authored layer would make inference beat declaration at import time; and the set of categories with no accessibility analogue is left to the data rather than fixed in a requirement, because a requirement resting on a count would need amending every time that judgment moved.
