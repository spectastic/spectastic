Use the anchor that already exists

Applied

1 · Intent

An independent pass found that FR-013 is unbuildable as intended and unfalsifiable as written.

The proposal that added it described spectastic://<project>/spec/<spec-id>/screen/<name> and asserted this "follows the contract precedent exactly". It does not. resourceUri composes spectastic://<owner>/<repo>/<kind>/<name> with the kind as a single segment; the nested form no kind uses cannot be composed by it and would parse back as a spec coordinate whose name contains slashes.

The requirement itself carries no shape at all — the grammar lived only in the proposal's prose. That is the mitigation and the second defect in one: nothing wrong reached the spec, and nothing usable did either. "Addressable by a coordinate of the kind the project already uses" names no conformance condition, and the local attribute the rationale rejects reads as satisfying it.

The correction is smaller than the original. 067 FR-004 already ships spectastic://<project>/spec/<spec-id>#<anchor> "for a requirement or task" — a screen is the same kind of thing, something named inside a spec. So no new kind, no widening of the union the code warns must move together, no parse change.

2 · Scope

In scope

  • Naming the mechanism: the existing anchor form, not a new coordinate kind.
  • Inheriting 076 FR-007's collision rule instead of restating the problem.

Out of scope

  • A consumer. The obligation on the generated view to use this belongs to 099, and shipping it as a task with no delta is one of the defects being corrected. defer-to=099-visual-embedded-view.
  • A state coordinate. Still nothing outside has asked to reach one. defer-to=TBD-state-coordinate.

3 · Approach

Use what exists. 067 established an anchor fragment for naming a requirement or a task inside a spec, and a screen is that same shape of thing — declared in a spec's own material, unique to it, referenced from outside. Widening what an anchor may name costs nothing structural: ResourceKind and KNOWN_KINDS stay closed, and their docstring's warning that widening one alone "yields a kind that composes and then fails to parse — a coordinate that looks minted and is not" never comes into play.

The uniqueness question is not new either, and the original was wrong to treat it as such. 076 FR-007 settled it for contracts with two halves — a declared name is preferred over an inferred one, and two declarations resolving to one coordinate name are an error. The first proposal cited that precedent while inheriting neither half, and filed its own uniqueness risk against the wrong requirement, so the recorded acceptance was invisible from the requirement it concerned.

The original's mitigation put the collision guarantee in an unchecked task checkbox. P-8 excludes that as a place a guarantee may live, which is why the rule is in the requirement here rather than in §6.

4 · Deltas

What changes: the mechanism is named rather than gestured at, and the collision rule is inherited rather than left to an implementing task.

A declared screen MUST be addressable as an anchor within its owning spec's resource URI, resolving MUST NOT require a network, and two screens within one spec that resolve to the same anchor MUST be reported as an error.

Rationale

A screen is the thing a design conversation is most often about and was the one thing it could not name. Every neighbouring relation is addressable; a screen carried an identifier no consumer resolved.

The anchor form 067 FR-004 already ships — spectastic://<project>/spec/<spec-id>#<anchor>, for a requirement or a task — is the mechanism, and a screen is the same shape of thing: named inside a spec, referenced from outside it. The first version of this requirement described a nested sub-resource instead, which the composer cannot build and the parser would read back as a spec coordinate with slashes in its name. Reusing the anchor keeps the kind union closed, which its own code comment warns must be widened in step or not at all.

The collision clause is 076 FR-007's, inherited rather than restated. Screen identifiers are unique per document and a spec may hold several screens files, so two can collide — and the first version left that to a task checkbox, which P-8 excludes as a place a guarantee may live.

5 · Risk register

The findings this corrects came from an independent critic; no second independent pass was run on the correction. Self-authored, and weaker for it.

An anchor is weaker than a kind, and that may be the wrong trade

A first-class kind would let a screen be listed, enumerated and served as a resource in its own right. An anchor is a fragment on a spec coordinate — it addresses, and it does not make a screen a thing the estate can enumerate. If an external read surface ever wants to list screens, this will need revisiting and the revision will be a grammar change after all.

Accepted. The demand on record is addressing, not enumeration — a design that could not name what it was describing. Building the stronger mechanism for a use nobody has asked for is the speculative-vocabulary failure the first version was already criticised for.

Filed against the right requirement this time, and still not fully resolved

FR-001 requires a stable identifier and the shape rule enforces uniqueness only within a document. The new clause makes a cross-file collision an error, which closes the hole — but it means a project that today holds two screens files each declaring converter becomes non-conformant on apply, with no migration beyond renaming one.

Accepted. No project in the estate has more than one screens file, so the population affected is empty. Recording it against FR-001 rather than against the state-source requirement, which is where the first version filed it — that mis-filing is why the original acceptance was invisible to anyone reading the requirement it concerned.

Still no consumer, now deliberately

The first version shipped its consumer as a task with no delta, leaving 099 with a behavioural obligation no requirement recorded. This one defers the consumer explicitly — which is more honest and leaves the coordinate unused in the meantime.

Accepted. An unused mechanism is a smaller problem than an obligation nothing records. The deferral names 099 rather than a slug, so it is a sequencing note rather than a backlog entry.

6 · Tasks

  • Resolve a screen anchor against its owning spec's declared screens; no network.
  • Report two screens in one spec resolving to the same anchor, as an error, naming both files.
  • Tests: resolves; refuses a network; reports a collision naming both; an anchor for an absent screen resolves to nothing rather than throwing.
  • Leave ResourceKind and KNOWN_KINDS untouched — a test asserting no new kind was added is the cheapest guard that this stayed an anchor.

None outstanding.
