Cards

Annotation category map homes four of the eight rows FR-006 requires

Implementation code

Debugging why an imported annotation category resolves as unknown when the survey found it a home, root cause was an unfinished transcription of an already-cited source plus a type that cannot represent two of the answers; fixed in annotation-categories.ts; regeneration passes, because the design already names the audit to transcribe and a careful implementer following that citation would not stop halfway.

Expected
Every category in the survey's annotation table resolves to a named home or to an explicit unmapped entry carrying its reason — FR-006: the vocabulary "MUST define where each design-tool category lands and MUST name the categories with no home."
Actual
ANNOTATION_CATEGORY_MAP enumerates role, landmark, heading, order, behaviour, state, tracking, content and emphasis. motion, data, requirement and accessibility fall through to {kind:'unknown'}, though the table homes all four — motion on the token format's duration, easing and transition types; data on <spec-contract>; requirement on a citation by id; accessibility on the tree itself. emphasis is in the map and not in the table, so the drift runs both ways.
Diagnosis
An incomplete build against fully specified guidance, not a gap in it: FR-006 and this spec's D-005 both name the audit as the source and the design's grounding row links it. The CategoryEntry union — role, aria-state, unmapped — was also never widened to admit "lives in the token file" or "lives in the contract declaration", so it structurally cannot express two of the four, which is why this is not the one-line data change the module's own docstring promises.
Fix
packages/core/src/visual/annotation-categories.ts — add the four entries, widen CategoryEntry with a variant for a home that is neither a role, a state, nor nothing, correct the docstring's one-line-change claim (true for the unmapped reasons, false for these), and reconcile emphasis against the table it claims to transcribe.
Fixed
All four entries added, plus structure and interaction as the names the two tools actually export. The union gained a fourth variant, elsewhere, carrying where: motion lands on the token format's transition types and data on the contract declaration, neither of which is the accessibility tree, and neither of which the original three-variant union could express — which is why this was never the one-line data change the module's docstring promised. Three outcomes are now distinct where two were: elsewhere (a home exists, outside the tree), unmapped (no home anywhere) and unknown (never heard of it), because an importer acts differently on each. Two things beyond the card: the docstring's "ageing is a one-line change" claim was narrowed to say a new reason is one line and a new kind of home is a type change; and emphasis was reconciled rather than removed — it is a real category in both tools with a genuine absence of analogue, and the survey's table was a summary of where things land rather than a list of everything the tools emit. A property test now asserts that every layer the vocabulary offers resolves to something other than unknown, which is the assertion that would have caught this on the day it shipped.
Deep dive — none required

No cross-spec contract disagreement: this spec only needs to name homes owned by the token format and by the contract declaration, not modify either. No principles invariant, no hotfix sequence.

FR-013 names a coordinate the grammar cannot express, and the requirement does not say so

Spec upstream

Debugging what an implementer would build from FR-013, root cause was that the shape its proposal described is not the one the coordinate grammar composes — and the requirement carries no shape at all, so the mistake is invisible from the spec; fixed by a MODIFY naming the mechanism; regeneration fails, because a must-tier requirement whose conformance condition cannot be determined is not a MUST.

Expected
A screen is addressable the way a contract is, by the mechanism 067 established.
Actual
Three separate problems, found by an independent adversarial pass and each verified against the code.

The shape is wrong. resourceUri composes spectastic://<owner>/<repo>/<kind>/<name> — the kind is a single segment directly after the authority. The proposal's …/spec/<spec-id>/screen/<name> is a nested sub-resource no existing kind uses; resourceUri cannot compose it and parseResourceUri would read it back as a spec coordinate whose name contains slashes. Meanwhile 067 FR-004 already ships #<anchor> for addressing something inside a spec. Two mechanisms existed, neither was used, and the proposal's §3 asserts it "follows the contract precedent exactly".

The requirement carries no shape. The URI form appears only in the archived proposal's prose. FR-013 says "addressable by a coordinate of the kind the project already uses", which does not name a determinate conformance condition — and the local cites-screen= attribute the rationale rejects reads as conformant against it, since target= and defer-to= are mechanisms the project already uses. KB-0001@2026-07-25 commits "MUST — an absolute requirement. Its absence is a defect", and an absence nobody can identify is not one.

The collision rule was already solved and not inherited. 076 FR-007 settled this exact problem for contracts: a declared name= is preferred, and two declarations resolving to one coordinate name MUST be reported as an error. FR-013 took neither half while claiming that precedent.

Diagnosis
My own risk pass raised the collision hazard and then filed it against FR-002 — which is the state source requirement and has nothing to do with identifiers. The requirement actually in tension is FR-001 ("a stable identifier", unique only within a document). So the one recorded acceptance is invisible to anyone reading the requirement it concerns, and its mitigation put the guarantee in an unchecked task checkbox, which P-8 excludes as a place a guarantee may live. A self-run pass found the hazard and mis-filed it; an independent one found the mis-filing.
Fix
specs/095-visual-element-vocabulary/spec.html — a propose. MODIFY FR-013 to name the mechanism (a flat screen kind, or the existing anchor form — the choice is the decision, and the nested form is ruled out), and inherit 076 FR-007's two halves rather than restating the problem.
Fixed
Applied 2026-08-14-use-the-anchor. The correction is smaller than what it replaced: 067 FR-004 already ships #<anchor> for naming a requirement or task inside a spec, and a screen is the same shape of thing — so no new kind, no widening of the union whose own comment warns it must move in step. The collision rule is now inherited from 076 FR-007 and lives in the requirement rather than a task checkbox.
Deep dive — cross-spec, and what did not ship

The bad grammar never reached the live spec, because FR-013 carries no grammar. That is the mitigation and the defect in one: nothing wrong shipped, and nothing usable did either.

ResourceKind and KNOWN_KINDS carry a docstring warning that widening either alone "yields a kind that composes and then fails to parse — a coordinate that looks minted and is not". Any fix moves both.

Also recorded rather than fixed: the archived proposal shipped with its <spec-tldr> still holding the literal template placeholder. Archives are preserved verbatim, so it stays — but a placeholder surviving into an applied artifact means nothing checks for one at propose time, which is its own gap and worth a card if it recurs.

The coordinate has no requirement-level consumer, and the surface that motivated it got no delta

Cross-spec upstream

Debugging which spec obliges anything to use a screen coordinate, root cause was that the mechanism landed split across three specs with nothing binding them; fixed by an amendment to the spec that owns the view; regeneration fails, because no requirement anywhere records the obligation.

Expected
A landing spec amends the upstream spec whose recorded behaviour it changes — the convention 073→042 and the 057/062/063 syncs already follow.
Actual
The proposal put "the materialised view linking each screen to its declaration" in scope and shipped it as a task with no delta. That view belongs to 099, which therefore acquires a behavioural obligation no requirement records. The result is a mechanism in three parts, none load-bearing: 093 FR-014 obliges a design to "refer to the screen" and names no mechanism; 095 FR-013 defines an address and names no consumer; 099 renders and is obliged to do nothing.
Diagnosis
My own scope risk accepted the view-linking half on the ground that "a coordinate with no consumer is exactly the speculative-vocabulary failure this proposal argues against" — which was the right instinct and the wrong conclusion, because shipping the consumer as a task rather than a requirement leaves the coordinate with no consumer at the level that matters. Card I-065 asked for a propose against 093 and 099; 099 got none.
Fix
specs/099-visual-embedded-view/spec.html — a propose adding the linking obligation, sequenced after T-002 settles what a screen coordinate actually is. Fixing the consumer before the mechanism would bake in the shape T-002 rules out.

The corrected coordinate is wrong too, and fails more quietly than the one it replaced

Spec upstream

Debugging what spectastic://…/spec/095#converter actually opens, root cause was that an anchor names something inside spec.html and a screen is not in spec.html; fixed by giving a screen a coordinate that denotes the document it lives in; regeneration fails, because the requirement asserts the mechanism ships when the half it depends on does not.

Expected
FR-013's premise: the anchor form 067 FR-004 ships is the mechanism, and a screen is "the same shape of thing: named inside a spec, referenced from outside it."
Actual
The analogy fails in the one respect that makes an anchor work. 067's anchor names a requirement or a task — both are elements inside spec.html, which is the document a spec coordinate denotes, so the fragment dereferences. A screen is not in that document: 094 FR-002 puts it in a sidecar beside the spec.

And nothing resolves an anchor anywhere. The whole surface is three call sites: id.ts composes one, the CLI passes it through, and the VS Code host resolves one by scrolling the addressed artifact to a matching element id. 067 FR-005 says the command "MUST accept an optional anchor and append it mechanically" — composition ships, resolution does not.

So the coordinate composes cleanly, parses cleanly, and opens spec.html to scroll to an element that is in another file.

Diagnosis
My third instance of one error: asserting a mechanism exists without opening the half that mattered — after 098's missing writer, and after the first version of this same requirement. Worse than what it replaced: the nested form failed loudly, at the parser. This one succeeds at every layer and is wrong only at dereference, which no check performs. The code's own docstring names the failure — "a coordinate that looks minted and is not" — one level up and now silent.

The collision clause repeats the other half of the same mistake. 076 FR-007 has two halves and I inherited the error half again; the dropped half — a name SHOULD be explicitly declared rather than left to a fallback — is the escape hatch that resolves a collision without a rename. Which matters, because FR-001 requires a stable identifier and the shipped rule's own fixHint says renaming one breaks the annotations and traces that reference it. A must-tier requirement whose only remedy is breaking a must-tier stability contract.

Fix
specs/095-visual-element-vocabulary/spec.html — a propose, and this time decide what document the coordinate denotes before choosing its syntax. A screen lives in a sidecar, so either the sidecar is addressable and the screen is an anchor within it, or a screen is a kind in its own right. Take both halves of 076 FR-007 with it.
Deep dive — what the scope claimed

§2 framed this as pure nomenclature — "Use what exists" — while FR-013's "resolving MUST NOT require a network" presumes a resolver that exists for nothing, and the collision clause is inherently cross-file so it cannot live in the per-file shape rule and needs a kernel scan. Two new mechanisms presented as reuse, which is the criticism T-002 made of the version being corrected, relocated from the grammar to the resolver.

No accepted-gap risk was recorded for any of it, which KB-0001@2026-07-25 requires for a must-tier requirement resting on an assumed fact. All three of my self-authored risks covered something else.
