Design · 095-visual-element-vocabulary

Visual element vocabulary

How we will build it.

Status Accepted Spec 095-visual-element-vocabulary Owner Brian Corbin · @briancorbinxyz Branch spec/visual-slice-095-098 Created 12 Aug 2026 Read time

Three elements — <spec-screen>, <spec-state>, <spec-annotation> — authored in an HTML artifact per screen under the feature's 094 directory, because a declaration that must render with scripting off cannot be JSON. A state carries two attributes rather than one: what kind of thing it came from, and which thing — so a many-to-one collapse is recorded by from holding more than one value, and needs no third attribute to notice. Annotations are typed by accessibility role and state, which is not a taste call: toMatchAriaSnapshot and getByRole({checked}) both ship in the Playwright already installed here, so a declared annotation is an assertion in vocabulary the test framework reads today. Guarded twice, per the project's standing posture — the stylesheet catches a reader's eye, the rule catches a pipeline.

3 · Data model & contracts

Three conceptual entities, three elements. None is persisted; all are authored and read.

Conceptual entityPhysical shapeNotes
Screen <spec-screen id serves> — root of one artifact. serves links the scenarios it answers (FR-009), by reference rather than restatement.
State <spec-state id source from> — child of a screen. Two attributes, not one: source is the kind, from is what it came from. A collapse is from with more than one value.
Annotation <spec-annotation role aria-state cites>. cites references a requirement instead of restating it (FR-007). An annotation with no accessibility analogue carries neither role nor state and stays prose.

This feature exposes no interface. It adds an authored vocabulary and the checks over it, consumed entirely inside the tool.

5 · Approach

One artifact per screen, authored under the feature's visual/ directory, carrying a <spec-screen> root with <spec-state> and <spec-annotation> children. Three schema rules check the shape; one stylesheet block makes a missing or unrecognised attribute visible without any of them running; one hand-enumerated map in core says where each design-tool annotation category lands and which have nowhere to go.

Nothing here is a new mechanism. The elements clone spec-contract's attribute style, the rules clone visual-declaration-shape's scope discipline, and the broken-state affordance clones spec-delta's MISSING OP. What is new is the claim: that a design annotation and a test assertion can be the same statement, which is true only because the accessibility tree is a type system both sides already speak.

The derived-state floor has a ceiling worth stating before the design rests on it. Nothing in this slice parses a contract file's own responses — readContractDeclarations reads the declaration, not the OpenAPI document behind it. So FR-004's "derived is a floor" is enforced as a property of how a state is recorded, not by cross-checking the contract. US1's acceptance is met by the author accounting for each response; the tool checks that each state says where it came from, and cannot yet check that none was forgotten. Recorded in D-006 rather than left for a reader to discover.

6 · Alternatives considered

The load-bearing choice was the authoring format. Scored on whether it satisfies NFR-001 directly, whether it reuses tooling that exists, and how much new machinery it needs. 5 is best.

OptionRenders with JS offReuses existing toolingNew machineryTotal
JSON sidecar + generated view1214

An HTML artifact per screen — chosen55515

The JSON option loses on the requirement rather than on taste: the authored form would not render at all, and NFR-001 would be satisfied only by a derived copy — which means a generator, a drift check, and a second thing to keep true. Inlining scores well and still loses, because 093 declares a path and a feature with ten screens would swamp the design it lives in. That is the argument that moved contracts out to sidecar files, and it applies here unchanged.

7 · Decisions

D-001 · One HTML artifact per screen, under the feature's visual directory

Status
Accepted
Context
NFR-001 requires 100% of a declaration readable with scripting off, which JSON cannot satisfy without a generated copy. 094 already fixes the directory, and 093 already permits a declared path to name one.
Decision
specs/<spec-id>/visual/<name>.screen.html, one <spec-screen> per file. The exemplar's speculative .json is converted rather than kept.
Consequences
+ Renders, validates, diffs and reviews with the tooling that already exists — no generator, no drift check. + A ten-screen feature is ten short files rather than one long one. − A new artifact kind to learn, and one more thing the sidecar directory can contain. − Nothing yet generates these from a design tool, so the first ones are hand-authored.

D-002 · A state carries its kind and its origin as two attributes, and a collapse needs no third

Status
Accepted
Context
FR-002 wants the source recorded, FR-003 wants a many-to-one collapse recorded rather than implied. The spec's own data model insists source is a string and not a flag, because a state derived from a field is neither derived-from-response nor authored.
Decision
source= names the kind (derived, field, authored); from= names what it came from, space-separated. A collapse is from holding more than one value, and is therefore recorded by construction rather than by an author remembering a third attribute.
Consequences
+ The collapse cannot be forgotten separately from the origin — they are the same field. + A missing from on a derived state is a missing attribute, which both guards already catch. − from is a space-separated list, so a value containing a space cannot be expressed; acceptable for status codes and dotted field paths, and stated rather than discovered.

D-003 · Annotations are typed by the accessibility tree, because that is what makes them assertions

Status
Accepted
Context
FR-005 forbids inventing a vocabulary here. The reason it can is verified rather than assumed: the Playwright installed in this repository ships toMatchAriaSnapshot and a getByRole that takes state options, so a declared role and state is already a sentence the test framework reads.
Decision
role= and aria-state= on <spec-annotation>. An annotation with no accessibility analogue carries neither and stays prose — visibly unchecked rather than pretended-checked.
Consequences
+ The design's intent and the test are one statement, on web and on native. + No tenth taxonomy to maintain. − Ties the vocabulary to a standard this project does not control. − Roles are not validated against the ARIA set in this slice, so a typo in role= is caught only by a human or by the test failing later.

D-004 · Two guards for one gap, and neither is a fallback for the other

Status
Accepted
Context
FR-008 asks for both halves explicitly, and the spec's own rationale gives the reason: the stylesheet catches a reader's eye, the rule catches a pipeline. They fail at different moments for different people.
Decision
A stylesheet block cloning spec-delta's MISSING OP, plus three per-file schema rules. The stylesheet is authoritative for nothing and advisory for everything; the rule is the P-8 guarantee.
Consequences
+ A malformed screen is obvious in a browser before any tool runs. + The gate still holds in CI where nobody is looking. − The same vocabulary is expressed twice, in CSS selectors and in rule code, and they can drift; a test asserts the recognised-value lists agree.

D-005 · The category map is kernel data, so an unmapped category is named rather than dropped

Status
Accepted
Context
FR-006 asks for two things: where each design-tool category lands, and which have no home. A table in a document answers the first and cannot answer the second, because nothing reads a table.
Decision
A hand-enumerated map in @spectastic/core, with the unmapped categories present as explicit entries rather than absent. An imported annotation of an unmapped category is reported by name.
Consequences
+ "Has no home" becomes a value the tool can say out loud, which is what stops it being a silent drop. + Greppable and testable. − The map is a judgment about other people's products and will age; it is data precisely so ageing is a one-line change.

D-006 · The derived-state floor is checked as a recording discipline, not against the contract file

Status
Accepted
Context
FR-004 says derived states are a floor and not a ceiling, and US1's acceptance talks about six documented error responses. But nothing in this codebase parses a contract file's responses — readContractDeclarations reads the declaration, and stops at the path.
Decision
Check what can be checked: that every state says where it came from, that a derived one names its origin, and that the vocabulary can express a state no response implies. Do not claim to verify that no response was forgotten.
Consequences
+ The tool never asserts completeness it cannot establish, which is the failure the whole visual survey was written to avoid. − US1's acceptance is therefore met by the author, with the tool checking form rather than coverage; a reader could mistake a clean validate for a complete state set, so the spec's own wording and the finding copy both avoid the word "complete". − A real cross-check needs a contract-response reader, deferred rather than faked.

10 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here.

Converting the exemplar's .json is not required by any requirement. It is done because the exemplar is the only project in this repository with an interface, and therefore the only place the vocabulary can be exercised end to end — leaving it in a format this spec rejects would mean shipping a demonstration of the thing the spec decided against.

Three rules rather than one. A single "screen well-formed" rule would be cheaper to write and worse to read: a finding that says which of the three obligations was missed is actionable, and one that says "malformed screen" is not. It follows slo-well-formed's precedent of reporting granularly.
