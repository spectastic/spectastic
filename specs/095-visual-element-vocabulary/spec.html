Specification · 095-visual-element-vocabulary

Visual element vocabulary

Screens, states and annotations as declared elements — typed by the accessibility tree rather than by a tenth taxonomy.

Status Accepted Spec ID 095-visual-element-vocabulary Owner Brian Corbin · @briancorbinxyz Reviewers — Created 12 Aug 2026 Principlesv1.9.0 Smallest demoableA screen declaring one state and one annotation renders as a card, and a state with no source renders visibly broken. Read time

094 gives the files a home; this says what is in them. A screen, the states it can be in, and the annotations attached to its parts — expressed as declared elements so a reader and a check see the same thing. Two decisions do most of the work. States carry where they came from, because a state derived from a declared contract's error response and one a person thought of are different kinds of claim, and a derivation that collapses several responses into one state has to say so or an omission and a decision become indistinguishable. And annotations are typed with ARIA roles and states rather than a new vocabulary, which means a declared annotation is directly assertable on a web surface and on a native one, and an annotation imported from a design tool has somewhere defined to land. Missing attributes render visibly broken, following the pattern the change-proposal elements already set.

1 · Context

093 declares that a feature touches screens and 094 says where they live, but nothing says what a screen is as a declared thing. Without that, the file is prose in a directory: a reader can follow it and no check can, which is the condition the survey set out to leave.

Two industry facts shape the answer. The categories designers already use for annotations — behaviour, requirement, animation, API, tracking, accessibility, content — are broadly agreed and exist nowhere as a schema; the accessibility annotation kits that are the de facto standard ship as design-tool component libraries with no machine-readable form at all. And most of those categories map onto vocabulary this project can already express.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Every state the contract implies is accounted for P1

As an implementer, I want the states a screen can be in to be enumerated, with each one saying where it came from so that the error responses nobody drew are visible before they are shipped.

Acceptance: A screen whose feature declares a contract with six documented error responses accounts for all six — designed, or collapsed into another state with the collapse recorded, or explicitly dismissed.

US2 · An annotation is assertable, not just readable P1

As a developer, I want an annotation to name a role and a state in vocabulary my test framework already understands so that the design's intent and the test are the same statement.

Acceptance: An annotation declaring a role and a state can be read out as an assertion without translation, on a web surface and on a native one.

Edge cases

  • Several contract responses that are one situation to a user — the collapse must be expressible and recorded, not implied by absence.
  • A state no contract implies and no user reaches, such as an expired credential. Unreachable is not a reason to leave it undrawn.
  • An annotation with no accessibility analogue — visual emphasis, brand rationale. It stays prose and stays unchecked, and the vocabulary must not pretend otherwise.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A screen MUST be a declared element carrying a stable identifier, and its states MUST be declared elements belonging to it.

Every state MUST record its source, distinguishing one derived from a declared contract from one a person authored. A state with no source MUST render visibly broken.

Rationale

The two are different claims. A derived state is owed by the contract and can be checked against it; an authored one exists because somebody thought of it, and nothing can tell whether the thinking was complete.

Where several contract responses map to one state, the collapse MUST be recorded on the state rather than left implicit.

Rationale

An unrecorded collapse and a forgotten response look identical to a reviewer. Recording it makes the judgment reviewable and disagreeable.

Contract-derived states MUST be treated as a floor and not a ceiling: the vocabulary MUST express states no response implies, and MUST NOT present a derived set as complete.

An annotation MUST be typed with an accessibility role and, where applicable, an accessibility state, rather than with a vocabulary invented here.

Rationale

It is the only widely implemented type system for "what is this element and what is it currently doing", it is what browser and native test tooling already serialises, and it makes a declared annotation an assertion rather than a note.

The vocabulary MUST define where each category used by the common design tools lands, and MUST name the categories that have no home rather than silently dropping them.

Rationale

Tracking plans and content budgets have no accessibility analogue. An imported annotation of a category with nowhere to go must be visibly unhandled, not quietly lost.

An annotation that restates a requirement MUST NOT be permitted: it MUST reference the requirement by identifier instead.

Rationale

A copy is a second thing to drift. The trace mechanism already aggregates by reference and copies no prose.

A required attribute that is absent or carries an unrecognised value MUST render visibly broken without scripting, and MUST additionally be reported by a check.

Rationale

Two guards for the same gap, which is this project's standing posture: the stylesheet catches a reader's eye, the rule catches a pipeline.

A screen SHOULD reference the scenarios it serves rather than restating them.

A feature MAY declare several screens, and a screen MAY carry states no other screen shares.

An annotation MUST be able to name the element it is about. That name MUST be treated as provenance and MUST NOT be resolved at validate time, and an annotation naming no element MUST remain valid, reading as a statement about the state it belongs to.

Rationale

An annotation currently belongs to a state, and a state to a screen, so there is no word anywhere for the control an annotation is about — which is how the worked example lost four named targets and three measurable claims when it was migrated onto this vocabulary. A measurable claim about nothing in particular cannot be checked by anything. It is provenance rather than a reference because nothing declares an element inventory for a screen and this change deliberately does not add one: the design tools disagree about what an element is, and a registry here would be a third naming scheme beside the two the corpus and the contract convention already own. The same posture 093 FR-006 takes for a design source. Naming nothing stays valid because most annotations are about the screen rather than a control, and requiring a target would push authors to invent one.

An annotation MUST be able to declare the layer it belongs to. Where the annotation is also typed by the accessibility tree and the declared layer disagrees with the layer that typing implies, the disagreement MUST be reported rather than resolved. An annotation in a category with no accessibility analogue MUST be able to declare that category, and the set of such categories MUST NOT be fixed by this requirement.

Rationale

The survey held the exemplar's seven layers against its own bar and kept the axis rather than the number; D-005 then chose to express that axis as a grouping over the accessibility type system rather than as a tenth taxonomy. Deriving the layer and forbidding an authored one was the first draft and was wrong in a way worth recording: 073 FR-003 settles declaration over inference in both directions, and the deferred design-tool import is committed to landing any annotations a source carries — annotations that arrive with a category their author stated. A vocabulary with no word for it would force the importer to discard that word and re-derive, which is inference beating declaration. So the layer is declarable, and the disagreement is reported rather than silently resolved, because neither the author's word nor the implied one is reliably right and picking one would hide the case worth looking at. The set of analogue-less categories is deliberately left open: it is a judgment about other people's products, it will age, and T-001 has already found the current transcription wrong in both directions — so it belongs in the data FR-006 owns, not fixed inside a requirement.

A declared screen MUST be addressable by a resource coordinate of its own kind, qualified by the spec that owns it; a screen MUST declare the name it is addressed by, and two screens within one spec resolving to the same name MUST be reported as an error.

Rationale

A screen is the thing a design conversation is most often about and was the one thing it could not name, while a contract has had a coordinate since 076.

A kind, not a fragment. An anchor names something inside the document its coordinate denotes — a requirement or a task inside spec.html — and a screen is declared in a sidecar, so an anchor coordinate composes, parses, and points at nothing. A kind denotes the screen itself. The name spans two segments, the owning spec and the screen, which is the shape the corpus kind already ships as plugin/slug: name is everything after the kind, and the composer interpolates it verbatim.

The declared name is 076 FR-007's first half, taken this time rather than dropped — and strengthened past its tier, deliberately. 076 is should-tier and its own follow-up found that should-tier plus no prompt produced filenames-as-keys for every contract in the estate. Requiring it here means one identity is authoritative for addressing, a collision cannot silently arise, and the rename screen-shape warns against is never the remedy. The cost is an attribute on every screen, which the authoring prompt supplies. The first draft of this correction wrote MAY while claiming to inherit both halves; under the committed conformance vocabulary an author who never declares one would then be fully conforming, leaving the rename that screen-shape warns against as the unremarked default. Without it the only cure for a collision is renaming a screen — and FR-001 requires that identifier to be stable precisely because annotations, traces and reviews reference it. A requirement whose sole remedy breaks its neighbour is not a remedy.

Non-functional

Every declared element MUST render with scripting disabled: at least 100% of the declaration, its states and its annotations readable with JavaScript off.

Rationale

P-4 — progressive enhancement, never dependence.

The shape check MUST return before allocating on a document declaring no screens, adding at most 0 measurable cost to a project that has none.

Out of scope (deferred to other slices)

  • Components as declared things, and the states they move between.
  • The axes a screen varies across, and which context is the default.
  • Reading these declarations to check a build against them.
  • Whether the tracking category belongs in this vocabulary at all, which the survey leaves open.
  • Importing annotations from a design tool into this vocabulary.

4 · Data model

No persisted entity. This spec adds declared elements and the rules governing them.

Entities

Screen
A named surface a feature touches, with a stable identifier and zero or more states. Belongs to exactly one feature.
State
One condition a screen can be in, carrying its source — derived from a named contract response, or authored — and, where several responses collapse into it, which ones.
Annotation
A statement about one part of a screen, typed by accessibility role and state, or referencing a requirement by identifier. Zero or more per screen.

A state's source is a string rather than a flag because the middle case is real: a state derived from a field of a contract rather than from a response is neither purely derived nor purely authored, and a boolean would force it to lie in one direction.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For a feature declaring a contract, the count of documented error responses that are neither designed as a state, recorded as collapsed into one, nor explicitly dismissed is 0.

The count of declared states carrying no source is 0, and each one that is missing renders visibly broken in a browser as well as reporting.

For each annotation category used by the two most common design tools, the vocabulary states where it lands or names it as unhandled — 0 categories silently unaccounted for.

6 · Assumptions

Accessibility roles and states are close enough to native platform traits to be usable on both. The mapping is close but not exact, and a spec that pretended otherwise would encode a falsehood about focus behaviour in particular.

Authors will record a collapse rather than quietly designing one state for three responses. Nothing can detect the difference between a recorded collapse and a considered omission, which is why the requirement is on recording rather than on completeness.

7 · Open questions

None outstanding. The annotation type system, the derived-is-a-floor rule and the loud-gap posture were settled by the survey; the tracking category is deferred rather than open, because the survey states plainly that whether it belongs here at all is a question it declines to close.
