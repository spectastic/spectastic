Corpus retrieval at scale

The exception, not the design centre — characterised now so a future slice doesn't reinvent it, and deliberately not built until a real corpus earns it.

Below that, the shipping behaviour is agentic search only (051 FR-008). Read time

This spec is authored deferred on purpose. Its entry condition is a real in-repo corpus crossing the ~200,000-token (~500-page) threshold; until then, building any of it is the most expensive mistake available in this family (a synchronisation problem, an infra dependency, an opaque retrieval step — to solve a problem most projects do not have). It is written now so the ladder is characterised and a future slice doesn't reinvent it, not because it is next to build.

Anthropic's own retrieval guidance draws the line explicitly: for a knowledge base under roughly 200,000 tokens — about 500 pages — skip retrieval entirely and put the whole thing in the prompt (with prompt caching for cost). That threshold covers most of what a project would curate, so agentic search over the committed corpus (051) is the answer for the common case. This spec governs the exception: above the threshold, the known ladder is contextual embeddings, then contextual BM25, then reranking — reported to cut retrieval failures by roughly a third, a half, and two-thirds respectively. The binding constraints: this is not built or activated below the threshold; any retrieval index is a second copy of the truth with a staleness cost; and the index never becomes the cited source of record — the committed document remains the archive.

1 · Context

The instinct on hearing "knowledge base" is to build a vector database. The evidence points the other way from two independent directions. First, the tools that tried are walking it back: Claude Code removed vector search in favour of agentic search — the reported reasons are simplicity, security, privacy, reliability, and above all staleness (an index is a second copy of the truth that must be kept in sync). Second, most corpora are too small to need it: below the ~200k-token / ~500-page threshold, put the whole corpus in the prompt.

So retrieval at scale is the exception, and the corpus convention (051) deliberately requires no index to be usable. This spec exists to characterise the ladder for the rare corpus that genuinely exceeds the threshold — and, just as importantly, to hold the line that it must not be built before then. The known technique is real and useful; it is simply not the first thing to build.

2 · User scenarios & testing

Each story MUST be independently testable.

US1 · Retrieval for a very large corpus P1

As a user with a corpus above ~200k tokens, I want retrieval over it so that the model isn't asked to hold the whole corpus in context on every turn.

Acceptance (entry-gated): once a corpus exceeds the threshold, retrieval via the characterised ladder returns the relevant documents for a query and measurably reduces retrieval failure versus naive search.

US2 · The ladder is characterised, not reinvented P2

As a maintainer, I want the retrieval ladder named and ordered so that a future slice builds contextual embeddings → contextual BM25 → reranking in the known-good order rather than rediscovering it.

Acceptance: the spec records the ladder and its reported failure-reduction figures as the reference for a future implementation.

US3 · The index never becomes the source of record P3

As a reviewer, I want any retrieval index to stay strictly derived so that a citation still resolves to the committed document, never to an opaque index entry.

Acceptance: a citation resolves against the committed corpus document (051 / 052), and the index is a performance layer only, rebuildable and discardable.

Edge cases

  • A corpus just under the threshold — no index; agentic search (051 FR-008) resolves everything (FR-001).
  • An index that has drifted from the corpus — a staleness cost that must be justified before adopting an index at all (FR-003).
  • Pressure to build retrieval "to be safe" before any corpus is large — refused; the entry condition is the guard (FR-004).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

Retrieval MUST NOT be built or activated while a corpus fits under the ~200k-token threshold; agentic search over the committed corpus (051 FR-008) MUST be the sole mechanism below it.

Rationale

Below the threshold the whole corpus fits in the prompt; an index buys a synchronisation problem, an infra dependency and an opaque step to solve a problem the project does not have.

Above the threshold, retrieval SHOULD follow the known ladder — contextual embeddings, then contextual BM25, then reranking — in that order.

Rationale

The ladder is characterised: the three stages cut retrieval failures by roughly a third, a half, and two-thirds respectively. Recording the order means a future slice does not rediscover it.

Any retrieval index MUST be treated as a second copy of the truth carrying a staleness cost; adopting one SHOULD be justified against that cost rather than adopted by default.

This spec MUST remain deferred — not implemented — until a real in-repo corpus crosses the ~200k-token threshold; that crossing is its entry condition.

Rationale

The deferral is itself a requirement, not an accident of prioritisation. The entry condition is what makes the whole corpus family able to promise "no vector database" honestly.

Non-functional

A retrieval index, if built, MUST NOT become the cited source of record — the committed corpus document remains the archive a citation resolves to; the index is a rebuildable, discardable performance layer.

Out of scope (deferred to other slices)

  • Everything below the threshold — agentic search over the committed corpus, the common case.
  • Injecting the corpus index (not the documents) into the prompt — the below-threshold placement strategy.
  • A hosted vector-database service or an external retrieval runtime — the opaque, stale-prone dependency the whole family refuses.

4 · Data model

The entities this feature would own if and when triggered.

Entities

Retrieval index
A derived, rebuildable structure over the committed corpus (embeddings + BM25 postings + a reranking stage). Never the source of record.
Corpus-size measurement
The token/page count of the committed corpus, evaluated against the ~200k-token threshold to determine whether retrieval is even in scope.

Invariant: the index derives entirely from the committed corpus and can be deleted and rebuilt with no loss. A citation (052) resolves against the document, never the index — so the index's staleness can never corrupt a cited source.

5 · Success criteria

Technology-agnostic, measurable outcomes.

Entry-gated: when a corpus exceeds ~200k tokens, retrieval via the characterised ladder measurably reduces retrieval failure versus naive search, for a representative query set.

While a corpus is under the threshold, no retrieval index exists and agentic search resolves every citation.

A citation always resolves to a committed corpus document, never to an index entry — verifiable by deleting the index and re-resolving.

6 · Assumptions

The ~200k-token / ~500-page threshold from Anthropic's retrieval guidance remains a sound line for "put it all in the prompt vs retrieve"; the corpus convention's typical corpora fall below it.

The contextual-embeddings → contextual-BM25 → reranking ladder remains the state-of-practice for above-threshold retrieval; if it moves, this spec is re-characterised before any build, not built against a stale reference.
