Specification · 028-dependency-ordering

Order by dependency-respecting value

RICE and WSJF rank; they don't sequence. This is the foundation that does both — it infers a precedence graph from the links specs already carry, then emits a topological order that breaks ties by value and lifts cheap foundations above expensive leaves. The primitive the value-ranked slicer (W-2) will stand on.

Read time

The roadmap and the slicer both need to answer "what order do we build these in?" — and value alone can't, because a high-value leaf may depend on a cheap foundation that scores lower. This slice builds the dependency-ordering primitive: it infers a precedence DAG from the corpus, breaks ties among dependency-ready specs by RICE, lifts foundations by the value of the subtree they unblock, and refuses to emit anything when the graph contains a cycle — naming the offending nodes. It ships both a CLI order (for callers like W-2) and a self-contained roadmap view (the standalone value). It does not slice anything itself.

1 · Context

spectastic already nudges when a spec is too big — the smallest-demoable prompt, the amber/red budget band, the propose-time splitting nudge. What it cannot do is say what order a set of related specs should be built in. RICE and WSJF each collapse a spec to one number; a number ranks, but it cannot express "X must come before Y". A high-value leaf that depends on an unbuilt foundation will out-rank that foundation on score alone, and a naive value sort would schedule it first — to be blocked on day one.

The corpus already encodes the missing structure. Specs carry defer-to= on out-of-scope items and <spec-parent specid> on slices — a latent precedence graph nobody reads as one. This slice reads it, sequences it, and ranks the ties. It is the foundation the handover named: the value-ranked slicer (W-2) consumes this ordering rather than inventing sequencing from scores, and a roadmap maintainer gets a defensible build order out of the box.

Who it's for: the roadmap maintainer ordering a backlog, and — downstream — the W-2 slicer sequencing the children of one split.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · A dependency-respecting build order P1

As a roadmap maintainer, I want to point the tool at specs/ and get back a single ordered sequence so that I can build in an order where nothing is blocked by unbuilt work and ties go to the higher-value spec.

Acceptance: every inferred precedence edge is satisfied in the emitted order; among specs whose dependencies are all already placed, the next one out is the highest-RICE candidate. Re-checking the order against the graph finds zero violations.

US2 · A named cycle, not a wrong order P1

As a roadmap maintainer, I want a hard failure that names the specs in a precedence cycle so that I fix the offending link instead of trusting a silently-broken sequence.

Acceptance: a corpus containing A→B→A produces no order and a diagnostic listing exactly the nodes on the cycle; the message alone is enough to locate the bad link.

US3 · Foundations lifted above leaves P2

As a roadmap maintainer, I want a cheap foundation that unblocks a lot of value to rank ahead of a high-value leaf so that the order reflects leverage, not just a spec's own score.

Acceptance: given a low-RICE foundation whose unblocked subtree carries high total value, it appears ahead of a higher-RICE leaf that unlocks nothing; the elevation is visible and re-derivable from the scores.

Edge cases

  • A spec with no RICE block — placed by dependency, ordered after ranked ready peers, flagged unranked; never dropped (FR-006).
  • A defer-to / <spec-parent> pointing at a spec ID that does not exist — reported as a dangling edge; it must not crash the scan or silently vanish (FR-010).
  • Two ready specs with identical RICE scores — broken deterministically by spec ID so output is stable across runs (NFR-001).
  • A corpus with no edges at all — degenerates to a pure value ranking; still valid output.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The tool MUST infer a precedence DAG from the spec corpus by reading defer-to= and <spec-parent specid> reciprocity across specs/*/spec.html; nodes are specs and edges are those links. It MUST NOT require any separately-authored edge list.

Rationale

The structure already exists in the corpus; re-authoring it as a <spec-dag> would duplicate a source of truth and drift from it.

The tool MUST emit a priority-respecting topological order: no spec appears before a spec it depends on, and among dependency-ready specs the next emitted MUST be the one with the highest RICE score.

Each spec MUST be able to carry one authored RICE annotation (reach, impact, confidence, effort); the tool reads it and derives the value score as reach × impact × confidence ÷ effort.

The tool SHOULD elevate a spec by the critical-path value of the subtree it unblocks, so a low-scoring foundation that unlocks high total value ranks ahead of a higher-scoring leaf that unlocks nothing.

Rationale

This is the "dependency-respecting value" the handover names: leverage, not just a spec's own RICE. SHOULD (not MUST) so a simpler value-only fallback is still conformant if the subtree computation is deferred.

On any precedence cycle the tool MUST hard-error, name every spec on the cycle, and emit no order. It MUST NOT drop an edge to produce a best-effort sequence.

A spec lacking a RICE annotation MUST still appear in the order — placed consistent with its dependencies, after ranked ready peers — and be flagged unranked. It MUST NOT be silently dropped or silently treated as zero-value.

The tool MUST emit both forms of the result: a machine-readable ordered list of spec IDs (for callers such as W-2) and a self-contained HTML roadmap view rendering the sequence, the inferred edges, and any unranked flags.

The roadmap view SHOULD compute a WSJF cross-check alongside the RICE order and flag the specs where the two methods disagree on position.

Rationale

RICE is the primary ranking; WSJF is a portfolio sanity-check. Surfacing only the divergences keeps it a check, not a competing order.

The tool MUST be read-only over the corpus: it derives and emits the order and view, and MUST NOT modify any spec it reads.

A defer-to / <spec-parent> referencing a non-existent spec ID SHOULD be reported as a dangling edge and excluded from the graph, without aborting the scan.

Non-functional

Output MUST be deterministic: the same corpus yields an identical order and an identical view (modulo a generation timestamp). Residual ties after RICE break by spec ID ascending.

The tool SHOULD order the full live corpus (≥ 28 specs) and write both outputs in under 2 seconds on a developer machine.

The roadmap view SHOULD be a single self-contained HTML file using the shared design system, consistent with every other spectastic artifact.

Out of scope (deferred to other slices)

  • Slicing a parent spec into children, the ranking judge panel, and the coverage critic — W-2 consumes this ordering; it does not live here.
  • A mechanical "walking skeleton vs horizontal layer" gate. The vertical-slice expectation is a documented authoring guideline; acyclicity is the only hard structural gate here. The judgement, if automated, belongs to W-2's coverage critic.
  • Agent-estimated RICE inputs with a confirm gate. v1 reads authored RICE only.
  • Pulling defer-to edges from inbox cards and triage logs. v1's graph is specs-only.

4 · Data model

Three entities, one of them new to the design system.

Entities

Precedence DAG
Nodes are specs (specs/*/spec.html). Directed edges are inferred, not authored — see the edge semantics below. The graph is acyclic by contract; a cycle is an error (FR-005), not a state.
<spec-rice> (new)
An authored per-spec block carrying reach, impact, confidence, effort. The tool reads it for the value score (FR-003). Absent ⇒ the spec is unranked but still ordered (FR-006).
Ordering
The emitted result: a sequence of spec IDs, each tagged ranked, unranked, or elevated (lifted by subtree value). Rendered two ways — a list for callers, a view for humans (FR-007).

Edge semantics (the one correctness call — confirmed by the plan). A precedence edge P → C exists only where a defer-to and a <spec-parent> reciprocate: child C carries <spec-parent specid="P"> and parent P carries defer-to="C" — the relation the parent-child-reciprocity validate rule already enforces. The edge points parent → child (the parent is the established foundation; the child is the work that builds on it). A bare, unreciprocated defer-to (e.g. a sibling see-also) is not a precedence edge and is excluded.

This corrects an earlier draft that treated any defer-to as an edge: a grounding spike over the live corpus found sibling defer-tos are symmetric (007↔008) and children defer back to parents (012→006), so the naive read makes the corpus cyclic and FR-005 would refuse all output. See plan D-001.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For the live corpus, the emitted order satisfies 100% of inferred precedence edges — re-checking each edge against the order finds zero cases where a spec precedes one it depends on.

A corpus seeded with a precedence cycle produces no order and a diagnostic naming every spec on the cycle; a reviewer can identify the offending link from the message alone.

Among dependency-ready specs, the order is non-increasing in RICE score except where FR-004 elevation applies, and every position is re-derivable by a reviewer from the published scores.

Every spec in the corpus appears exactly once in the output — ranked specs in value order, unranked specs present and flagged — with zero specs dropped.

Two runs over an unchanged corpus produce byte-identical order and view (modulo the generation timestamp), verifiable by diff.

6 · Assumptions

The edge semantics in §4 hold: a precedence edge is a reciprocated defer-to↔<spec-parent> pair (parent → child); bare defer-tos are see-also, not edges. Verified against the live corpus by the plan's grounding spike (D-001) and aligned with the existing parent-child-reciprocity rule.

W-2 (the value-ranked slicer) is the downstream consumer of this ordering. Whether W-2 is a workflow initiated by an existing verb (e.g. /spectastic.spec owning splits) rather than a ninth slash command is W-2's decision to make — it does not constrain this foundation, which is callable from either shape.

RICE inputs authored on a spec are trusted as given. Validating or estimating them is out of scope (deferred to TBD-rice-estimation).
