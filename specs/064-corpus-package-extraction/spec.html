Corpus package extraction

1 · Context

Spectastic's corpus grew from a grounding aid into a full knowledge product — two-layer identity, an edition-pinned citation contract, integrity and licensing gates, an ingester, marketplace discoverability. None of it is about spec-driven development; it is about curating citable domain knowledge. Yet it lives in packages/core/src/knowledge/, and the only way knowledge comes out is the SDD verbs injecting a prompt block. The corpus-extraction survey found it couples to the lifecycle through only two thin seams (prompt injection + the scanCorpus* validate gates), with the file-IO port already built for a second surface — so extraction is a well-trodden move, not a leap.

This is Slice 1: make the corpus a package and binary in its own right, so someone who wants a cited knowledge base but never writes a spec can use it. The MCP surface, PDF conversion, and the eventual repo split sit downstream.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · The corpus becomes a clean package P1

As a spectastic maintainer, I want to lift the corpus logic into @spectastic/corpus and invert the two seams onto it so that the subsystem is a reusable package with a one-way boundary and every existing consumer behaves identically.

Acceptance: the AI verbs and the CLI validate scans import corpus logic from @spectastic/corpus; the @spectastic/core/knowledge subpath is gone; the full pre-extraction test suite passes with only import-path edits; a dependency check shows no edge from @spectastic/corpus back into @spectastic/core.

US2 · A corpus you can use without the lifecycle P1

As someone who wants a cited knowledge base but not SDD, I want a standalone spectastic-corpus binary so that I can curate, search, and validate a corpus with no @spectastic/core or specs/ present.

Acceptance: in a fresh environment carrying only @spectastic/corpus, spectastic-corpus runs the curation verbs (adapt/import/interview/source/publish), the read path (get/query/grep), and corpus-intrinsic validate (well-formed/registry/license) — each succeeding without the lifecycle installed.

US3 · Get cited knowledge out, deterministically P2

As a curator or agent, I want deterministic read verbs that return documents with their citation and provenance so that I can retrieve knowledge by id, by metadata, or by full text without a vector store.

Acceptance: get <id> resolves one document via the existing citation resolver; query <term> returns metadata-field substring matches; grep <pattern> returns document-body matches with context; every hit carries the document's coordinate and provenance, and the same inputs always return the same results.

Edge cases

  • Absent or empty corpus — every verb is a defined no-op or empty result (get → not-found, query/grep → no matches, validate → clean), never an error; graceful-absence is preserved.
  • Injection must not change — the AI verbs still inject from knowledge/ on disk; the read path is additive and never reroutes them.
  • Latent cycle — shared types (corpus domain types, the citation grammar, the IO port, Finding) drop to a lower package both depend on, so core ↔ corpus never forms a cycle.
  • Non-markdown files in a corpus folder — grep scans corpus documents only and skips anything it can't read as text.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The corpus curation, citation, provenance, and licensing logic (today packages/core/src/knowledge/ plus the schema corpus-citation rules) MUST live in a new standalone @spectastic/corpus package that owns it in full.

Rationale

The survey's core finding: the subsystem is cohesive and self-contained. A package makes that boundary real and reusable rather than an unwritten habit.

Shared foundational types both packages need — corpus domain types, the citation grammar, the IO port, and the Finding shape — MUST live in a lower package that both @spectastic/core and @spectastic/corpus depend on, so the dependency graph is acyclic.

Rationale

Core needs corpus (for injection) and corpus needs shared types core also uses; a lower types package is the only shape that severs the latent cycle without one package importing the other's edge.

The two lifecycle seams MUST depend on @spectastic/corpus: the AI verbs' prompt-injection loader and the CLI's corpus validate scans import from it. The @spectastic/core/knowledge subpath MUST be removed and every in-repo caller repointed.

A standalone spectastic-corpus binary MUST expose the curation verbs (adapt/import/interview/source/publish), the read path (get/query/grep), and corpus-intrinsic validate (well-formed / registry / license), runnable without @spectastic/core or the SDD lifecycle present.

Rationale

The grounding gate needs specs, so it stays a lifecycle/main-CLI concern; the well-formed, registry, and license scans are intrinsic to a corpus and belong on the standalone binary.

The read path MUST be deterministic with no embeddings or vector store: get <id> resolves one document via the existing citation resolver; query <term> matches a case-insensitive substring over metadata fields (id, slug, title, description); grep <pattern> matches over document bodies. Every result MUST carry the document's coordinate and provenance.

The AI verbs' prompt injection MUST continue to read directly from knowledge/ via the extracted loader, unchanged. The new read path is additive and MUST NOT reroute injection through query/get/grep or any server.

Every verb (curation, read, validate) on an absent or empty corpus SHOULD be a well-defined no-op or empty result, never an error — preserving today's with-or-without-corpus behaviour.

Non-functional

Behavioural parity: the pre-extraction corpus, validate, and AI-verb test suites MUST pass against the extracted packages with no changes beyond import paths — identical inputs producing identical outputs and findings.

The acyclic, one-way boundary MUST be machine-verified: an automated dependency check reports zero import edges from @spectastic/corpus (or the shared-types package) into @spectastic/core. The boundary is enforced, not conventional.

Out of scope (deferred to other slices)

  • The MCP serving surface for the corpus (query/get over MCP), and the specs-over-MCP half.
  • A corpus convert PDF wrapper — the read/curate/validate surface here consumes markdown only.
  • Full-text search over specs/ — grep here is scoped to corpus documents; searching the spec estate is a later, namespaced concern.
  • Semantic / vector retrieval and any export-to-RAG recipe — the read path stays deterministic exact/substring lookup.
  • Splitting @spectastic/corpus into its own repository — this slice is in-monorepo.

4 · Data model

This slice moves code across package boundaries; it introduces no new persisted artifact. The corpus document, registry, and index formats are unchanged — that invariance is exactly what parity guards.

Entities

@spectastic/corpus
The extracted package: curation verbs, the get/query/grep read path, corpus-intrinsic validate, and the spectastic-corpus binary.
Shared foundational types package
The lower package both core and corpus depend on: corpus domain types, the citation grammar, the IO port, Finding. Exact name/shape is a plan decision.
Read-path hit
A result from get/query/grep: the document's coordinate (marketplace · plugin · slug @ edition / KB-id), title, provenance, and — for grep — the matching context.

Invariant: for a fixed corpus, the prompt block the AI verbs inject is byte-identical before and after this slice (SC-004). The extraction is invisible to every existing consumer.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

Behavioural parity: running the full pre-064 test suite (unit, Playwright, and a full-corpus validate sweep) against the extracted packages yields identical results, with zero changed assertions except import paths.

One-way boundary: an automated dependency check reports zero import edges from @spectastic/corpus into @spectastic/core.

Standalone usability: in a fresh environment carrying @spectastic/corpus (or the spectastic-corpus binary) but without @spectastic/core or any specs/, a user can import/adapt a corpus, run get/query/grep returning cited results, and run corpus validate — all succeeding.

Injection unchanged: for a fixed corpus, the prompt corpus block the AI verbs inject is byte-identical before and after the extraction.

6 · Assumptions

The knowledge/ subsystem is genuinely self-contained at the two seams the survey audited; extraction will not surface a hidden third coupling. If one appears, it is captured and severed via the shared-types package.

Every consumer of @spectastic/core/knowledge is in-repo (a pnpm monorepo); no external package imports that subpath directly, so removing it breaks no published contract.

The existing vitest + Playwright coverage is sufficient to guard parity — a passing suite after the move is credible evidence of no regression.
