Specification · 118-verdict-explain

Reviewer-grade verdict explanation

A verdict a PR author or reviewer can act on without leaving the terminal — the offending code shown, the decision made readable, and the sanctioned path named. Triage's clarity, at the gate.

Status Accepted Spec ID 118-verdict-explain Owner Brian Corbin · @briancorbinxyz Reviewers — Created 13 Sep 2026 Principlesv1.9.0 Smallest demoablespectastic verdict --explain renders, per violation, the offending code in context, the governing decision's reason and consequences, and the location where the pattern is sanctioned. Read time

The 115 verdict carries everything a reviewer needs — decision id, rule, reason, file:line, source→target — but renders one line, so understanding the violation means leaving the diff to open the file and the ADR. This closes the gap to the clarity a <spec-triage> card gives: verdict --explain renders each violation in a fixed shape — Offending (the code shown in context), Why (the decision's reason and Context/Decision/Consequences, with the coordinate to open it), and Sanctioned path (where the pattern is allowed, from the rule's allowed-in). It is composed only from what the verdict already loads — the changed files and the decision record — so it adds no authoring and no model, and leaves the machine verdict and exit code untouched.

1 · Context

Dogfooding the position-keeper example surfaced this: the verdict is a machine verdict — correct, traceable, reconstructable — but the human reading it (the PR author, the reviewer) gets one line and must go find the code, the decision, and the right pattern themselves. That is precisely the trap the guardrail exists to close: if understanding the violation means leaving the diff, a busy reviewer approves. The brief's own bar for "a failure teaches" is language a reviewer who has never read the ADR can act on; the data meets it, the rendering does not.

The floor is set by spectastic's own <spec-triage> card: a plain-language header, then Expected / Actual / Diagnosis / Fix, with the offending thing shown and the governing rule linked. This feature brings the verdict to that floor. Its user is whoever is looking at a failed gate.

2 · User scenarios & testing

A reviewer understands without leaving the terminal. A verdict flags the reconciliation bypass. verdict --explain shows the offending SQL with its surrounding lines, the decision's reason and its Context/Decision/Consequences, the coordinate to open the full ADR, and that the pattern is sanctioned only under the persistence adapter path — so the reviewer sees what is wrong, why, and where the right code lives.

CI stays terse; the machine verdict is unchanged. Without --explain the output is the existing one-line-per-violation form; the persisted verdict.json and the exit code are byte-identical either way.

3 · Requirements

verdict --explain MUST render, for each violation, three labelled sections: Offending — the changed code at the violation's file:line shown with a few surrounding lines and the line marked; Why — the governing decision's reason and its Context/Decision/Consequences prose, plus the decision's coordinate and design-file location so it can be opened; and Sanctioned path — where the pattern is permitted (the rule's allowed-in, else the decision's scope) together with the decision's own guidance. The explanation MUST be composed only from data the verdict already loads — the changed files and the decision record — with no new authoring surface and no model. The decision parse MUST be extended to carry the decision's title and prose so the explanation can show them. --explain MUST enrich only human output: the persisted verdict.json and the process exit code MUST be identical whether or not it is given. --explain SHOULD compose with --teach: the Socratic follow-up (117) MAY appear after the explanation. When a violation's file:line cannot be read (a deleted file, an ingested SARIF location not on disk), the Offending section SHOULD state that plainly rather than omit the section or fail — the Why and Sanctioned-path sections still render. The explanation renderer MUST be pure and deterministic — the same verdict, decisions, and file contents yield a byte-identical explanation — with at most 0 model clients and 0 network modules on its path.
  • Pointing at a specific exemplar file (e.g. "see JdbcPositionRepositoryAdapter") — naming the one right file needs the decision to declare it; the allowed-in location is the honest v1.
  • A Markdown / PR-comment rendering for posting into a review UI — this slice is the terminal view.
  • Making the rich view the default (with a --quiet for CI) — opt-in first, non-breaking.

4 · Data model

Explained violation
A violation (115) joined to: the offending code snippet (from the changed file), the governing decision's title/reason/prose and coordinate (from the decision record), and the sanctioned location (the rule's allowed-in or the decision's scope).
Decision prose
The Context/Decision/Consequences text of a <spec-decision> — captured by the parse so the explanation can show it, not just the one-line reason.

6 · Assumptions

  • 115's Violation carries file, line, decisionId, specId, ruleId; the CLI already reads the changed files for content detection, so the snippet needs no new read.
  • The decision record (112) is parseable for its title and Context/Decision/Consequences prose — an additive parse extension.
  • The rule's allowed-in (or the decision's scope) is the honest "where is this permitted" answer; a specific exemplar file is deferred.

7 · Open questions

None outstanding — the triage-card shape sets the layout, opt-in --explain keeps CI terse, and the sanctioned-path answer (allowed-in, not a named exemplar) was settled before drafting.
