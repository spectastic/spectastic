Change proposal · 110-visual-one-step

A skipped step is not a divergence

Two must-tier requirements promise the one-step flow does everything the hand-run does; a third requires it to do nothing at all in one case. Scope the first two so the third is their exception, and widen the third so it covers the step the code already skips.

Status Applied Change ID 2026-08-23-a-skipped-step-is-not-a-divergence Spec 110-visual-one-step Author Brian Corbin · @briancorbinxyz Created 23 Aug 2026 Targets 3 requirements Read time

Implementing FR-008 made a must-tier test fail, and the test was right. FR-002 requires the flag’s output be indistinguishable from running the three verbs by hand; FR-008 requires the flag to import and materialise nothing where the design declares no visual surface. The delegated verbs carry no such gate, so in that case the two paths cannot agree — and must not, because FR-008 exists to stop material landing where 093’s own gate would report it as a defect. FR-001 is contradicted on the same axis. Both are scoped to name FR-008’s case as their exception. The adversarial pass then found a third contradiction the first draft missed: FR-008 names only import and materialise, while the shipped code also skips the render, resting on a requirement that does not cover it. FR-008 is widened to cover all three. Three MODIFY deltas; after them the implementation and the spec agree, which they did not before.

A skipped step is not a divergence

Applied

1 · Intent

This began as a failing test and turned out to be a contradiction between must-tier requirements. While draining 110’s T-311 — the task that implements FR-008 — the SC-001 byte-equality test went red. The obvious reading was that the new code was wrong. It was not: the test is asserting something the spec elsewhere forbids.

The two statements cannot both hold. FR-002 says the invocation’s result must be indistinguishable from running the same three verbs by hand. FR-008 says that where the design declares no visual surface, the invocation must import nothing and materialise nothing. The hand-run verbs (visual:import, visual:render, materialise) have no such gate — they are general-purpose verbs, and refusing to import because some design does not declare a surface would be the orchestrator’s policy leaking into a tool used directly. So the hand-run lands material and the one-step lands none. Demonstrated, not reasoned: the failing test’s two trees differed by exactly visual/a.html, visual/import-manifest.html and visual/renders/manifest.json — the hand-run’s output, against the flag’s correct nothing.

FR-001 is contradicted on the same axis, though more arguably: it says a single invocation must perform the import, the render and the view materialisation, which FR-008 forbids in the same case. Its own rationale reads as a claim about who orchestrates rather than about unconditional execution, so a generous reader resolves it. A must-tier requirement should not need a generous reader. Both are scoped here.

The adversarial pass found a third contradiction, and it is the one that mattered most. The first draft claimed the implementation already matched the corrected requirements. It did not. FR-008 governs only import and materialise — the render is not mentioned, and SC-005’s own methodology confirms the scope (“nothing was imported or materialised”). But the shipped orchestrator also reports the render as not-attempted in the no-surface case, citing FR-008 for a step FR-008 never covered. Worse, the first draft cited FR-004 as a second source of that permission; FR-004 says the opposite — where a step does not complete, the invocation MUST perform the steps that can still complete. It is an obligation to do more, triggered by incapacity, never a licence to skip. So the render skip rested on nothing, and one of the two requirements cited to excuse it in fact forbade it.

Skipping the render is nevertheless the right behaviour: a capture written under specs/<id>/visual/renders/ is visual material by exactly the argument FR-008’s own rationale makes. So FR-008 is widened rather than the code changed — the requirement’s text was too narrow, and the test already shipped for it (T-301 asserts all three steps report not-attempted), which is independent evidence of where the intent always was.

2 · Scope

In scope

  • Scoping FR-001’s three-step obligation so FR-008’s no-surface case and FR-004’s could-not-complete case are stated exceptions rather than contradictions — distinguishing the two, since one is a required skip and the other an incapacity.
  • Scoping FR-002’s indistinguishability claim the same way, covering both of its clauses — the comparison and the no-bytes-change-afterwards guarantee.
  • Widening FR-008 to govern the render alongside import and materialise, so the step the code already skips rests on a requirement that covers it.
  • Revising SC-001’s and SC-005’s Observed at methodologies to match (§6 tasks, since the apply kernel cannot target a <spec-criterion>).
  • Recording, in the design’s grounding table as a verified fact with its citation, that a design generated through spectastic design never declares a visual surface.

Out of scope

  • Pushing the visual-surface gate down into the delegated verbs so the hand-run agrees with the one-step. That would change 105 and 106, and would make a general-purpose verb refuse work on the strength of a declaration in a document it has no business reading — declined on the merits, not deferred.
  • The 105/106 orphan-scan collision that keeps FR-002’s second clause uncovered even in the surface-declaring case: 106’s render destination nests inside the directory 105’s import treats as its own managed landing zone, so a redundant re-import reports render’s output as “no longer in the export” and rewrites import-manifest.html. Reproducible with no involvement of 110’s code — two conventions disagreeing about who owns orphan-detection scope, which is neither verb’s defect alone.
  • Teaching designCommand’s kernel to author or preserve the decision-phase sections (Visual surface, Data model & contracts) that today exist only in the interactive slash-command’s own interview — a materially larger change, deserving its own spec.

3 · Approach

The two scoping deltas take the same shape: the requirement keeps its obligation and gains an antecedent naming the case in which another requirement governs instead. This is the pattern 070 already set — when its FR-004 gained a pending-promotion exception, the affected siblings were amended to match rather than left to be reconciled by whoever read them next. The alternative considered and rejected was declaring precedence on FR-008 alone; that is fewer edits, but the exception is then invisible to anyone who reads FR-001 or FR-002 first, which is everyone.

The exception clauses name FR-008 and FR-004 separately and differently, because they are not the same kind of thing. FR-008 requires a step not be performed. FR-004 governs a step that could not complete — an incapacity the invocation must work around by doing more, not less. The first draft collapsed both into “declines to perform”, which misread FR-004 as granting a permission it withholds; the adversarial pass caught it.

Three edits this change needs cannot be expressed as deltas. Every path in the apply kernel anchors on <spec-requirement id=…>, and 110 uses 108’s newer <spec-criterion> element for its success criteria — so a delta targeting SC-001 or SC-005 would come back gate-blocked / “target not found”. No spec using <spec-criterion> has ever had an SC- delta applied, so this would have been the first, and it would have failed silently against the wrong anchor. Those two revisions and the grounding-table row are carried as §6 tasks, applied by hand during the drain — the same route a data/content delta already takes. The kernel gap itself is a defect in shared lifecycle tooling affecting every spec authored on 108’s element, so it is filed as a triage card against the meta-spec rather than absorbed here.

SC-001’s claim survives the scoped FR-002 untouched — artifacts produced by the flag are still byte-identical to the hand-run wherever the steps run. Only its Observed at methodology changes, because that methodology reaches the comparison through spectastic design, and a design generated that way never declares a surface, so both trees fall into precisely the case the criterion cannot measure. The replacement compares runVisualOneStep against the three verb entry points the CLI subcommands themselves call — importVisualExport, renderVisualExport and materialiseVisualDesign in packages/cli/src/commands/visual.ts — not against the raw core kernels the orchestrator calls internally. That distinction is the whole value of the test: comparing the orchestrator against the same three functions it invokes would be near-tautological, and would stop exercising exactly the layer where divergence actually lives — the into/destDir prefix derivation, the file:// location rule the orchestrator re-implements with a comment saying it matches the render verb’s wrapper, and the contract-view materialisation the orchestrator performs and a three-kernel hand-run would omit. Caught by the adversarial pass, which is the second thing it found that would have shipped as a weaker gate wearing a green tick.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec. op= is one of added | modified | removed | renamed; a missing or invalid op renders visibly broken.

What changes: the three-step obligation gains an antecedent naming FR-008’s required skip and FR-004’s could-not-complete case as distinct exceptions. Nothing else — the MUST NOT clause is unchanged and both live rationale sentences carry through verbatim, with one appended stating the exception.

A single invocation of the design verb, given one design export, MUST perform the import, the render and the view materialisation — except where FR-008 requires that a step not be performed, or FR-004 governs a step that could not complete — and MUST NOT require the author to name or order those steps.

Rationale

The whole point. Three commands in a fixed order is a sequence to remember, and the step easiest to forget is the last one, whose omission leaves an artifact that looks finished. The two exceptions are stated rather than left to a generous reading, and stated separately because they differ in kind: FR-008 requires a step not happen, while FR-004 governs one that was attempted and could not finish — conflating them would read FR-004 as licensing a skip, which it explicitly does not.

What changes: both clauses — the comparison and the no-bytes-change guarantee — are scoped to the steps the invocation actually performs. Nothing else: both live rationale sentences carry through verbatim, and two are appended explaining why the scoping is not a weakening. The “caller, not a second implementation” intent is what the scoping preserves.

For each step the invocation performs, the result MUST be indistinguishable from running that same verb by hand in the same order, and running the performed steps by hand afterwards MUST change no bytes. A step that FR-008 requires not be performed, or that FR-004 governs because it could not complete, carries no such obligation.

Rationale

Keeps the flag a caller rather than a second implementation. Were the two paths able to diverge, every downstream check would need to know which produced the artifact — which is why the guarantee is kept in full wherever both paths do the same work, and narrowed only where one of them is required not to. The scoping is not a weakening: the delegated verbs are general-purpose and deliberately carry no visual-surface gate, so requiring the hand-run to agree in a case where the invocation is required to do nothing would make the two requirements unsatisfiable together. Discovered by SC-001’s own test going red against a correct FR-008 implementation.

What changes: the requirement gains the render alongside import and materialise. Nothing else — the reporting clause is unchanged and both live rationale sentences carry through verbatim, with two appended recording why the render was missing and what its absence rested on.

Where the spec’s design declares no visual surface, the invocation MUST import nothing, render nothing and materialise nothing, and MUST report that it did so.

Rationale

Landing visual material into a project with no interface creates exactly the artifact 093’s gate reports as a defect. A no-op nobody was told about is indistinguishable from a step that ran. The render is named because a capture written under specs/<id>/visual/renders/ is visual material by the same argument as the other two; the original text covered only import and materialise, which left the shipped skip of the render step resting on no requirement at all. The implementation and its test both already skip all three, so this widening records where the intent always was rather than changing behaviour.

4b · What this change removes

Each entry names one thing this change takes away — a clause dropped from a requirement it retypes, an obligation a sibling loses, a behaviour or affordance no requirement records. An empty register is the answer “this removes nothing”, so the common case needs no editing.

Where a delta removes something itself, its own reason and migration stay authoritative — this register is for what no delta can express.

  • The unconditional indistinguishability guarantee. Before this change FR-002 promised the flag and the hand-run agree, full stop; afterwards it promises that only for steps the invocation performs. Nothing now requires the two paths to agree in the no-surface case — deliberately, because they must not, but the guarantee is genuinely narrower than it read.
  • FR-001’s unconditional three-step obligation. A reader could previously cite FR-001 alone as requiring all three steps on every invocation. That reading is now closed off, which is the point, but it does remove a (contradictory) guarantee somebody might have been relying on.
  • End-to-end coverage of the flag itself for byte-equality. SC-001’s revised methodology calls the CLI verb kernels directly rather than spawning spectastic design --visuals, so after this change nothing exercises the real binary end-to-end for the byte-equality claim. It remains a genuine two-path comparison, which is what makes it worth keeping — but the process boundary, argument parsing and commit-path wiring fall out of its reach, and that is a real subtraction, not a wash. It is recoverable only when TBD-design-kernel-decision-sections is drained.
  • Any coverage at all for FR-002’s second clause. The no-bytes-change-afterwards guarantee is re-affirmed as a must, and its test stays skipped — blocked not by anything this change touches but by the 105/106 orphan-scan collision now named in §2. The clause is honest; it is simply unobserved, and this change does not fix that.

5 · Risk register

Populated by the adversarial risk pass when the proposal triggers the heuristic (touches a must-tier requirement, contains an op="removed" delta, or spans ≥2 topic prefixes). One <spec-risk> per finding. target= is required (missing renders broken). status= defaults to identified; apply refuses until each transitions to accepted, mitigated, or rejected.

The replacement methodology can no longer catch the defect the criterion exists for

SC-001’s revised Observed at compares runVisualOneStep against a direct hand-run of importDesignSource / renderDesign / materialiseVisualViews — but one-step.ts calls those three kernels itself, so the test compares a function against its own inlined body and is near-tautological. Every divergence FR-002 actually guards against lives in the layer the new methodology stops exercising: the CLI wiring in design.ts, the into/destDir prefix derivation, and the file:// location rule one-step.ts re-implements with the comment “the same rule visual:render’s own wrapper applies” — a second implementation of a delegate’s rule, invisible to a kernel-level comparison. The task’s own recipe already demonstrates the drift: it names three kernels, while the orchestrator and the real materialise verb both run materialiseContractViews then materialiseVisualViews. A test written to the letter of the task compares a hand-run missing a step against an orchestrator that performs it.

§2 Scope: “Revising SC-001’s Observed at methodology to one that can actually be written”; §6 task 1; the test it replaces calls itself “the one real end-to-end test D-004 names, because only a real comparison can prove two trees are byte-identical” (packages/cli/test/design-visuals.test.ts:9-12).

Draft response (author to disposition). Accepted and the proposal reshaped. The methodology now compares runVisualOneStep against the three CLI verb entry points (importVisualExport, renderVisualExport, materialiseVisualDesign) rather than the raw kernels the orchestrator calls internally — genuinely two code paths, so the prefix derivation, the file:// rule and the contract-view step all stay in reach. The contract-view omission in the first draft’s task recipe was real and is corrected. The residual loss — the process boundary and argument parsing fall out of scope until TBD-design-kernel-decision-sections is drained — is recorded in §4b rather than left implied. On the P-9 citation: P-9’s subject is enforcement gates and tool configuration, so it reads here as analogy rather than binding text; the finding stands on its own reasoning without it.

FR-004 is cited as granting an exception it does not grant, and the render step still has no cover

Both deltas name FR-004 as a requirement under which the invocation may decline a step. FR-004 says the opposite: where a step “does not complete”, the invocation “MUST perform the steps that can still complete”. It is an obligation to do more, triggered by incapacity — never a licence to skip. This is load-bearing, not pedantic, because it leaves the shipped behaviour uncovered: FR-008 governs only import and materialise (render is not mentioned, and SC-005’s own Observed at confirms the scope), yet the orchestrator pushes render: not-attempted citing (FR-008). In the no-surface case render can still complete, so FR-004 today requires it and the code skips it. After this change FR-001 reads “except where FR-008 or FR-004 governs a step” — neither governs the render skip — so the contradiction the proposal exists to remove survives in the third step, while the TL;DR asserts “no behaviour change”.

Live FR-004: “MUST perform the steps that can still complete”; first-draft FR-002 delta: “A step the invocation declines to perform under FR-008 or FR-004 carries no such obligation”; packages/core/src/visual/one-step.ts:108-111.

Draft response (author to disposition). Accepted in full; the most valuable finding of the pass. Verified against the live text before acting: FR-004 is indeed an obligation to perform more, not a permission to perform less. Three corrections followed. The exception clauses now name FR-008 and FR-004 separately and differently — a required skip versus an incapacity — rather than collapsing both into “declines to perform”. A third delta widens FR-008 to cover the render, so the step the code already skips rests on a requirement that covers it. And the TL;DR’s “no behaviour change” claim is withdrawn and replaced with the accurate one: after these deltas the implementation and the spec agree, which they did not before. Skipping the render remains the right behaviour — a capture under renders/ is visual material by FR-008’s own argument — and T-301’s shipped test already asserts all three steps skip, which is independent evidence of the original intent.

The scope claims both FR-002 clauses and carries work for only one

The in-scope bullet promises to cover “both of its clauses — the comparison and the no-bytes-change-afterwards guarantee”, and the delta duly re-states clause 2 as a must. But clause 2 has a second skipped test, and it was skipped for an entirely different, live cross-spec defect: 106’s render destination nests inside the directory 105’s import owns, so import’s orphan-scan reports render’s own output as “no longer in the export” and import-manifest.html’s bytes change on a redundant hand re-run — in exactly the surface-declaring case where the steps are performed, which the scoping does not rescue. The proposal never mentions it: not in §1, not in §6, not in §2’s out-of-scope list, and not in §4b. So a must-tier clause with a documented counterexample is re-affirmed with zero coverage and no assumption, risk, or deferral recording it — while §7 declares “None outstanding.”

§2 Scope: “covering both of its clauses — the comparison and the no-bytes-change-afterwards guarantee”; packages/cli/test/design-visuals.test.ts:121-134 — it.skip('running the three verbs by hand afterwards changes nothing (FR-002)').

Draft response (author to disposition). Accepted. The omission was real: the first draft re-affirmed a must-tier clause whose only test is skipped for a live defect, and said nothing about it anywhere. Now named in three places — §2’s out-of-scope list with the mechanism spelled out and a defer-to slug, §4b as a distinct subtraction (the clause is honest but unobserved), and §7, which no longer claims nothing is outstanding on this axis. The defect itself stays out of scope on the merits rather than by omission: it is two conventions disagreeing about who owns orphan-detection scope, reproducible with no involvement of 110’s code, and belongs to neither verb alone.

A verified fact is filed as an assumption, and two must-tier deltas rest on it

§6’s second task records “a design generated through spectastic design … never declares a visual surface” as a <spec-assumption>, and §3 makes it the sole justification for rewriting SC-001 (priority="must") and for scoping two must-tier requirements. KB-0001@2026-07-25 rules that “a must-tier decision may not rest on an assumed or unresolved-spike fact without an explicit <spec-risk status="accepted">”; the register was empty. The fact is in truth verified — T-001 names the source and two experiments — so filing it as an assumption understates evidence the project already paid for, and inverts the ledger’s stated purpose: “a reader can tell at a glance which decisions rest on something real and which rest on … best guess.”

KB-0001@2026-07-25 (knowledge/spectastic-concepts/references/001-foundations.md, “The grounding discipline”); first-draft §2 Scope: “Recording, as a <spec-assumption>, that a design generated through spectastic design never declares a visual surface”.

Draft response (author to disposition). Accepted; the citation was checked against the registry and the pack before acting (KB-0001 resolves to spectastic/spectastic · spectastic-concepts · 001-foundations at edition 2026-07-25, and the quoted rule is present). The fact is verified, not assumed: its source is renderDesignHtml’s fixed template with no preservation on re-entry, and two experiments recorded on T-001. It now lands as a verified row in the design’s grounding table with that citation, rather than as a <spec-assumption> in the spec — which is where a verified fact belongs and removes the KB-0001 conflict at source rather than papering it with an accepted risk.

7 · Open questions

None outstanding on this change. Six decisions were anchored: how to resolve the contradiction (scope both requirements rather than declare precedence on FR-008), how to treat FR-004 once the pass showed it grants no exception (name it separately, as an incapacity rather than a decline), whether to widen FR-008 or change the code (widen — skipping the render is correct, the text was narrow), how to carry the three edits the apply kernel cannot make (§6 tasks), what SC-001's replacement methodology should compare against (the CLI verb entry points, not the raw kernels), and where the <spec-criterion> kernel gap is recorded (a meta-spec triage card, filed separately — it is not 110's defect to own). Two known gaps are deferred rather than open: FR-002's second clause has no passing test until the 105/106 orphan-scan collision is resolved, and SC-001 loses end-to-end coverage until the design kernel can emit a visual-surface declaration. Both are named in §2 with defer-to targets and recorded in §4b.
