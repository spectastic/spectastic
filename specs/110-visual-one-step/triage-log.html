SC-001's own test methodology cannot exercise its happy path

Spec upstream

Debugging a regression in the SC-001 byte-equality test after landing T-311's FR-008 check, root cause was SC-001's “Observed at” methodology assuming a capability spectastic design's deterministic kernel does not have; fixed by (proposed) amending 110's own Assumptions and SC-001's methodology, not the implementation; regeneration fails — another session implementing FR-008 exactly as written from 110's spec+design alone would hit this identical wall.

Expected
Running spectastic design 001-x --visuals export (Tree A) and running spectastic design 001-x then the three verbs by hand (Tree B) over a fixture whose design declares a real visual surface produces byte-identical trees, per SC-001's stated methodology.
Actual
Both trees' design.html declare no visual surface, always — because designCommand's kernel never emits <spec-visual>, regardless of stub or real AI. FR-008 then (correctly) makes Tree A skip import/render/materialise entirely, while Tree B's hand-run bypasses that check (the individual verbs don't gate on a declaration), so the trees diverge.
Diagnosis
Corrected during the propose: the root cause is a must-vs-must contradiction in the live spec, not SC-001's methodology alone. FR-002 required the flag's result be indistinguishable from the hand-run, full stop; FR-008 required the invocation to import and materialise nothing where the design declares no visual surface. The delegated verbs carry no such gate, so the two paths could not agree in that case — and could not, deliberately, since FR-008 exists to stop material landing where 093's own gate would report it as a defect. FR-001 was contradicted on the same axis. The methodology gap this card originally centred on is real but secondary: packages/core/src/commands/design.ts's renderDesignHtml is a fixed v0.1-scope template with no <spec-visual> section and no preservation on re-entry — the 093 Visual-surface question lives only in the interactive slash-command's own interview, never in this kernel — so a live spectastic design --visuals invocation can never produce a declared surface for either tree, on either side of the AI/stub split. That gap made SC-001's original methodology untestable; the contradiction is why the requirements themselves needed to change, not only the test. A third, deeper issue surfaced only once the fix landed: FR-008 as originally worded covered only import and materialise, while the shipped code (correctly) also skipped the render — resting on a requirement that didn't cover it, and on a mis-cited FR-004 that in fact grants no such exception. Not a defect introduced by 110's implementation — FR-008's own behaviour was always correct; the text around it was too narrow and the sibling requirements didn't yet name it as an exception.
Fix
specs/110-visual-one-step/spec.html — via /spectastic.propose: add a <spec-assumption> recording that a design generated through spectastic design (stub or real AI) never declares a visual surface, so SC-001's happy path is unreachable through a live design-generation invocation for either tree; and revise SC-001's “Observed at” clause to a methodology this can actually prove — comparing runVisualOneStep against a hand-run sequence of importDesignSource / renderDesign / materialiseVisualViews called directly over a hand-authored design declaring a real surface, bypassing spectastic design's generation step for the comparison fixture entirely. Separately worth a TBD- or its own spec: whether designCommand's kernel should grow the decision-phase sections (Visual surface, Contract, …) that today exist only in the interactive procedure — out of scope for 110 and for this fix.
Fixed
Diverges from the plan above in three ways the adversarial pass found. Landed via 2026-08-23-a-skipped-step-is-not-a-divergence: FR-001 and FR-002 were MODIFIED — not given a new <spec-assumption> as first planned — to name FR-008's required-skip case and FR-004's could-not-complete case as distinct, stated exceptions (the FR-004 citation in the first draft was itself wrong — FR-004 grants no exception, it obliges the run to do more — which is what surfaced that FR-008 also needed widening to cover the render alongside import and materialise, since the shipped skip rested on no requirement at all). The design-kernel fact landed as a verified row in design.html's grounding table, not a <spec-assumption>, per KB-0001@2026-07-25. SC-001 and SC-005's methodologies were revised by hand (T-1000/T-1001 — the apply kernel cannot target a <spec-criterion>, filed separately against the meta-spec) to compare against the three CLI verb entry points rather than the raw core kernels the orchestrator calls itself, which the adversarial pass found the first draft's plan would have made near-tautological. T-1003 un-skips SC-001's test against that revised methodology, proving the real byte-equality claim for the first time. A fourth, unplanned fix landed alongside T-900 (bounded non-idempotence): the SAME orphan-scan defect a related test had separately deferred (106's renders/ nesting inside 105's own managed directory) was fixed at the source — RENDERS_SUBDIR excluded from 105's own orphan-scan — rather than tolerated a second time.
Deep dive — cascade required

Cross-spec-adjacent: the finding sits on the boundary 093 already drew (decision-phase sections are interactive-only) and a general, already-documented convention throughout this project (the CLI's AI-coupled verbs bypass “LLM-driven file handling,” per 006 FR-009) — 110 is the first spec whose success criterion's own test methodology collided with that boundary rather than merely being silent about it. No principles invariant implicated; no hotfix needed — the CLI test for SC-001's happy path is marked it.skip() with a citation of this card pending the propose, and the rest of 110's implementation drain continues unblocked (T-311/T-312's own tests, which don't depend on spectastic design's generation step, are unaffected and green).

A browser-dependent test was added to the job that installs no browser

Implementation code

Debugging a red build-and-test on the release commit, root cause was three vitest files that launch a real Chromium sitting in the unit tier, which deliberately installs no browsers; fixed by excluding them there and running them in browser-tests, the established convention the existing single-session.test.ts exclusion already documents; regeneration passes — the convention is written in the workflow’s own comment, so a session reading it would place a new browser test correctly.

Expected
A test that drives visual:render end to end runs in the job that has a browser, and the unit tier stays fast and browser-free.
Actual
build-and-test failed with “Executable doesn’t exist at …/chrome-headless-shell” on three tests. Two are new (design-visuals.test.ts, visual-kernels.test.ts); the second has never run in CI at all since it was authored this session, so its characterisation of the render verb was only ever checked locally.
Diagnosis
The convention exists and is documented in ci.yml’s own comment — “This job deliberately installs no browsers … the test is excluded here and runs in browser-tests, which has one” — and the new files simply were not added to it. Local runs hid it completely: a developer machine has Chromium, so all three passed every time, including the full pre-tag gate. The same exclusion is duplicated in publish.yml’s two jobs, so the tag push would have failed at the identical step after the tag existed.
Fix
.github/workflows/ci.yml and .github/workflows/publish.yml — exclude the two files from the unit tier alongside single-session.test.ts, and add them to the browser job’s explicit run list. Kept out rather than skipped, so they are verified rather than quietly not running.
Fixed
Shipped as proposed, across all three affected jobs (ci.yml’s unit tier, and both of publish.yml’s). The publish half is the part that mattered most: it was found only because the tag was held until CI reported, and tagging first would have produced a failed publish on an existing tag.
Deep dive — the failure mode is the one this project keeps paying for

No cross-spec contract and no principles amendment, but the shape is worth recording because it recurs: a check that silently does not run is indistinguishable from a check that passes. The estate already carries this lesson for artifacts (a structural test going green on behaviourally-broken JavaScript) and for the verify view (a command nobody executes). Here it is CI itself — a whole test file that never executed in the pipeline while reporting green locally on every run.

Whether the placement should be enforced rather than conventional — a check that a vitest file importing a browser driver appears in the browser job’s list — is a real question and is surfaced here rather than promoted into this card’s scope. It is exactly the kind of guarantee P-8 says belongs in the kernel or CI rather than in a comment, and the comment is currently the only thing holding the convention.
