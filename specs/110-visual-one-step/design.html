Design · 110-visual-one-step

Land the visuals in one step

How we will build it.

Status Draft Spec 110-visual-one-step Owner Brian Corbin · @briancorbin Branch spec/visual-slice-095-098 Created 23 Aug 2026 Read time

A core orchestrator sequences the three existing kernels — importDesignSource, renderDesign, materialise*Views — taking the renderer as an injected port, exactly as 037’s run already injects its coding and verify ports. visual.ts stays the one module that constructs playwrightRenderer(), and design.ts calls into it without ever holding a renderer, so 106’s capability bound is satisfied by construction rather than by convention. The biggest risk is not the wiring: it is that all four visual actions currently end in process.exit(), so each has to be split into a callable kernel and a thin exiting wrapper before anything can call them.

Perf targets

Constraints

3 · Data model & contracts

Nothing is persisted. The one thing this design gives physical shape to is the spec’s Run report — an in-memory value the orchestrator returns and the CLI prints, never a file.

Conceptual entityPhysical shapeNotes
Run reportA returned array of step records, one per step, each carrying the step’s name and its outcomeOrdered by execution. Every step attempted appears exactly once; a step not attempted appears with its reason, never absent.
Step outcomeA discriminated union: completed · completed-with-refusals (carrying the delegate’s own per-item refusals) · not-attempted (carrying a reason)A union rather than a boolean plus optional fields, so the middle case cannot be collapsed into either neighbour by a caller that forgets to check (FR-007).

This feature exposes no interface. It is a flag on an existing CLI verb, and the terminal output it adds is a human report rather than a consumed surface — nothing outside this process reads it, and no other project can depend on its shape. Recorded explicitly rather than omitted, per 069 FR-003.

6 · Approach

Three moves, in dependency order. First, split each visual action into a callable kernel and a thin exiting wrapper. Every one currently ends in process.exit(), which is why nothing can call them; the existing subcommands keep their exact behaviour by becoming wrappers that call the kernel and exit on its result. Second, add a core orchestrator that sequences the three kernels and returns the run report — pure, port-taking, and the only place that knows the refusal order. Third, wire the flag: design.ts gains --visuals <export> and --no-render, calls a single entry point exported from visual.ts, and adds whatever landed to the paths it already passes to commitVerbAndExit.

The renderer never crosses into design.ts. visual.ts is the one module that constructs playwrightRenderer(), and the entry it exports takes a boolean rather than a port, so the capability is acquired behind that boundary and nowhere else. That is what keeps the source scan reading exactly one module, and it is the literal shape 106 FR-004 now permits: invoke, never acquire.

Ordering follows from what each step needs. The export path is checked before anything — before the model call, which is the expensive one (FR-003). Import runs next, since render reads what it landed. Materialise runs last, because it writes into design.html, which does not exist until the design generation has finished.

Subprocess spawning ties on confinement and loses everything else: exit codes are the only channel back, so the per-step reporting FR-007 requires would have to be re-parsed from stdout, and three extra Node startups buy isolation the injected port already provides. 8 · Decisions

D-001 · A core orchestrator over injected ports, invoked through the module that holds the capability

Status
Accepted
Context
The flag must drive three verbs whose actions all end in process.exit() (visual.ts:250,256), while design.ts must never acquire the render capability (render.port-reach.test.ts:41,46). The codebase already answers the general form of this: run drives four verbs by calling their kernels directly with ports injected (core/run/steps.ts:38,66), and renderDesign already takes the renderer as a parameter (visual.ts:185-192).
Decision drivers
Capability confinement · testable without a browser · P-14 placement · cost
Considered options
  • Spawn three child processes — + perfect isolation; the import graph question disappears. − exit codes are the only channel, so per-step reporting must be re-parsed from stdout; three extra Node startups.
  • Orchestrate inside visual.ts — + smallest diff. − strands the refusal ordering in the CLI where no test reaches it without spawning; contradicts P-14.
  • Core orchestrator, port injected via visual.ts — chosen — + every requirement unit-testable with fakes; mirrors run exactly; the capability stays behind one boundary. − requires splitting four actions into kernel + wrapper first.
Decision
A core module sequences the three kernels and returns the run report, taking the renderer as an optional injected port. visual.ts exports the single entry that constructs playwrightRenderer() and calls it; design.ts calls that entry with a boolean and never holds a renderer.
Consequences
+ The source scan keeps reading exactly one module, so the guarantee needs no relaxation. + Refusal order, partial-chain handling and report shape are all unit-testable against an in-memory filesystem and a fake renderer. + A second caller — the unattended orchestrator, deferred as TBD-visual-one-step-run — gets the same entry for free. − Four existing actions must be split into kernel and wrapper before anything else can start, which is the bulk of the work and touches verbs this spec otherwise leaves alone. − design.ts importing ./visual.js is a new CLI-to-CLI edge; it is legal under the scan and under the amended FR-004, but it is the first of its kind and worth watching.

D-002 · The import identity is derived from the spec id

Status
Accepted
Context
visual:import needs --into and --identity. The first is derivable — conventionalVisualPrefix('screens', specId) gives specs/<id>/visual (core/visual/location.ts:43-46). The second has no derivation: it is the stable anchor a later re-import keys on, and a mismatch throws ImportIdentityError (core/visual/import.ts:200,248-250) — though only when the caller passes previousIdentity, which is an input rather than a disk read.
Decision
The flag derives the identity from the spec id and documents it. No second flag, and nothing is parsed back out of the manifest.
Consequences
+ The ask survives intact: one flag, one argument. + The spec that owns the material is a genuinely stable anchor, which is what the field is for. − A project that previously imported under a hand-chosen identity meets 105’s mismatch refusal the first time it uses the flag. That is loud, names both identities, and is fixable by re-importing once — it is not silent, which is the property that matters. − Reading the identity back from the import manifest was rejected: the manifest records it in prose HTML, and making a load-bearing key depend on parsing that would be the first code to treat the manifest as a data source.

D-003 · Refuse before the model call; continue past a step that cannot run

Status
Accepted
Context
Two failure postures, pulling opposite ways. FR-003 wants the cheap check first because the design generation is the expensive step and commitVerbAndExit ends the process (cli/src/git/index.ts:100,114). FR-004 wants the run to survive a step that cannot run, because 094 FR-005 forbids a render’s absence from failing a gate.
Decision
Preflight — export readable, egress reachable when rendering is on — runs before the model call and refuses the whole invocation. After that point nothing aborts the run: a step that cannot complete is recorded as not-attempted with its reason and the remaining steps proceed.
Consequences
+ A typo costs a second rather than a generation. + An author with no browser still gets the design and its embedded view. − Two different failure semantics in one command, split at the model call. The split is defensible but has to be documented in the flag’s help, or it reads as inconsistency. − Preflighting egress means a reachability probe before the model call, which is itself a network round trip on a verb that had none — bounded, but real.

D-004 · Tests-first against fakes for both ports

Status
Accepted
Context
A preference, not a fact — grounding="n-a". The orchestrator takes fs and render as ports, so nothing about the requirements needs a real browser to exercise.
Decision
Every requirement gets a unit test against an in-memory filesystem and a fake renderer, written before the implementation. SC-001’s byte-equality claim additionally gets one real end-to-end comparison, since a fake cannot prove two trees identical.
Consequences
+ The suite stays runnable in CI without Playwright browsers. + Matches how 105 and 106 are already tested. − A fake renderer can drift from the real one; the single end-to-end test is the only thing anchoring it, and it is the slowest test in the slice.

11 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here. A reviewer should be able to point at any non-trivial choice and find its rationale in this section.

P-12 exception — capability accountability. This is the one principle this design does not simply satisfy. design today reaches no network and executes no process; with --visuals it does both, via the browser. The widening is justified by being authorised, bounded and declared: the spec that authorises it says so in FR-005, the capability is acquired in exactly one module and asserted by a source scan, the reach is opt-in per invocation rather than a property of the verb, and --no-render exists so the default posture of a machine without egress is unchanged. What P-12 forbids is a footprint no spec accounts for; this one is accounted for in three places.

Four actions are refactored for a caller that does not exist yet. Splitting kernel from wrapper is most of the work and none of the feature, and it touches verbs this spec otherwise leaves alone. It is not incidental complexity: nothing can call an action that ends in process.exit(), so either the split happens or the orchestration becomes subprocess spawning, which the matrix scores lower on every axis but one. Recorded here because a reviewer seeing the diff will see four unrelated verbs change.

An inherited non-idempotence is carried, not fixed. Materialising twice over unchanged input changes one byte on the second run (measured: 29,123 → 29,122, stable after). The fix belongs to the verb that owns the defect, not to its first caller, so FR-009 is a SHOULD and this design inherits the behaviour rather than working around it.
