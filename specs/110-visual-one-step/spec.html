Specification · 110-visual-one-step

Land the visuals in one step

Three verbs a person has to remember, run in the right order, become one flag on the verb they were already running.

Status Draft Spec ID 110-visual-one-step Owner Brian Corbin · @briancorbin Reviewers — Created 22 Aug 2026 Principlesv1.9.0 Smallest demoablespectastic design 001-x --visuals ./export.html writes the design and lands its imported material, captures and embedded view in one run. Read time

Landing a design export today takes three commands in a fixed order — visual:import, visual:render, materialise — and getting the order wrong produces a design that looks finished and is not. This adds a single --visuals <export> flag to the verb an author is already running, which performs all three by delegation. The render port stays reachable from exactly one module, so 106’s NFR-002 keeps the guarantee it has today; what changes is who may call the verb, never what may reach the browser.

Depends on 105 (import) and 106 (render), both Accepted and drained. Orchestrates them; adds no behaviour of its own to either.
N Negotiable

1 · Context

Landing a design export is four commands, and only three of them are mechanical. 107’s visual:brief emits a document for a designer, so the export does not exist until a person has made one — that step cannot be folded into anything. The remaining three all operate on an export already on disk: 105’s visual:import lands its material, 106’s visual:render captures its artboards, and 099’s materialise writes the embedded view into design.html.

The failure is quiet rather than loud: skip materialise and the design carries a stub where a view should be. 099 exists because that had already happened — the contract view it clones had never once materialised on the canonical authoring path, unnoticed because an absent view was legal there. A pipeline whose last step is easy to forget, and whose omission looks like completion, is that defect one level up. Authors running design anyway should not need to know the pipeline exists to get its result.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · One command lands the export P1

As an author with a design export on disk, I want to land its material, its captures and its embedded view in the run I was already doing so that I never have to remember a pipeline or the order of its steps.

Acceptance: a single invocation naming the export produces the same imported material, the same captures and the same embedded view as running the three verbs by hand in the correct order; running the three verbs by hand afterwards changes nothing.

US2 · It refuses before it costs anything P2

As an author, I want a run that cannot succeed to say so before it spends tokens or writes files so that a typo in a path costs a second rather than a design generation.

Acceptance: with a non-existent export path, the run refuses naming the path, no model call is made, and no file is created or modified.

US3 · A missing browser does not cost the rest P3

As an author on a machine with no browser installed, or in a container without egress, I want the steps that can still run to run so that I get the design and its embedded view, and a stated gap where the captures would be.

Acceptance: with rendering unavailable, the import and the embedded view still land, the run reports which step did not complete and why, and the run does not fail.

Edge cases

  • The export resolves but declares no artboards — rendering completes having captured nothing, which is a legitimate outcome and not a refusal; the run says so rather than reporting a silent success.
  • The flag is passed for a spec whose design declares no visual surface at all — nothing is imported and nothing is embedded, and the run says which, rather than writing a visual section the gate would then flag.
  • The flag is passed twice in a row over an unchanged export — the second run changes no bytes.
  • Rendering refuses some artboards (a label collision) while capturing others — the run carries 106’s own per-artboard refusals through rather than flattening them into one outcome.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A single invocation of the design verb, given one design export, MUST perform the import, the render and the view materialisation, and MUST NOT require the author to name or order those steps.

Rationale

The whole point. Three commands in a fixed order is a sequence to remember, and the step easiest to forget is the last one, whose omission leaves an artifact that looks finished.

The result of that invocation MUST be indistinguishable from running the same three verbs by hand in order, and running them by hand afterwards MUST change no bytes.

Rationale

Keeps the flag a caller rather than a second implementation. Were the two paths able to diverge, every downstream check would need to know which produced the artifact.

Before making any model call and before writing any file, the invocation MUST refuse when the named export cannot be read, and MUST state which path it could not read.

Rationale

The design verb is the expensive step and the path check is the cheap one, so a run that cannot succeed should fail at the cheap end. This is 106 FR-005’s posture — refuse "before executing any artboard" — moved one stage earlier for the same reason.

Where a step other than the design generation itself does not complete, the invocation MUST perform the steps that can still complete, MUST report which did not and why, and MUST NOT fail on that ground alone.

Rationale

Settled by an existing requirement rather than decided here: 094 FR-005 makes a render evidence, not load-bearing — its absence may not fail a gate. Aborting the chain when rendering is unavailable would make captures load-bearing by the back door, on the path most likely to run in a container.

The invocation MUST reach the render capability only by invoking the verb that owns it, and MUST NOT acquire that capability itself.

Rationale

The load-bearing constraint. 106 NFR-002 confines the render capability to one verb so no network access or code execution occurs as a side effect of a verb promising neither, and enforces it mechanically. Delegation leaves that untouched: this spec adds a caller, never a second holder.

The invocation MUST offer a way to perform the import and the materialisation while skipping the render, and that way MUST require no browser and no network egress.

Rationale

Rendering is the only step needing either. Without an opt-out the flag is unusable in CI or offline, and an author in that position is pushed straight back to running the verbs by hand — which is the problem this spec exists to remove.

Where a delegated step refuses part of its own work while completing the rest, the invocation MUST carry those individual refusals through to its own report rather than reducing them to a single outcome.

Rationale

106 distinguishes a whole-run refusal from a per-artboard one; a label collision reported as “rendering failed” loses the only detail that makes it fixable. An orchestrator that flattens its delegates’ reporting is worse than the verbs it replaces.

Where the spec’s design declares no visual surface, the invocation MUST import nothing and materialise nothing, and MUST report that it did so.

Rationale

Landing visual material into a project with no interface creates exactly the artifact 093’s gate reports as a defect. A no-op nobody was told about is indistinguishable from a step that ran.

Re-running the invocation over an unchanged export SHOULD change no bytes in any artifact it writes.

Rationale

Every step it delegates already claims this, so the orchestration should not be the thing that breaks it. Written as a SHOULD rather than a MUST because it inherits whatever its delegates actually do, and one of them is known not to hold it today — see Assumptions.

Non-functional

A run that refuses under FR-003 MUST make 0 model calls and write 0 files.

Rationale

The quantities are the requirement. "Refuses early" is a description; 0 and 0 are checkable, and they are the two costs an author actually notices.

At most 1 command module MUST be able to acquire the render capability, unchanged by this spec.

Rationale

Restated here as a number so this spec cannot be read as relaxing it. The existing mechanical check is the guarantee; this requirement exists so that a reader of this spec finds the constraint rather than having to know 106 to spot that it applies.

Out of scope (deferred to other slices)

  • Generating the design brief. It emits a document for a person, and the export does not exist until that person has produced one — so it cannot be a step in a chain that consumes the export. This is the reason the flag covers three steps and not four.
  • Making the same one-step flow available from the unattended orchestrator, which drives a whole spec lifecycle rather than acting on an export somebody already has. A different trigger and a different failure surface; worth doing, not worth conflating.
  • Reading the export’s location from the design’s own declaration instead of the flag, so the path need not be repeated. The declaration records provenance today, not a resolvable path, and turning it into one is a change to that vocabulary rather than to this flow.

4 · Data model

This feature owns no persisted entity. It introduces one conceptual thing — the record of what a single invocation did — because FR-004 and FR-007 both turn on a reader being able to tell one step’s outcome from another’s.

Entities

Run report
What one invocation did, as one entry per delegated step. Every step attempted is present exactly once; a step not attempted is present with the reason it was skipped, never absent. Absence and "did not run" must not be the same reading — that conflation is the defect this whole family keeps paying for.
Step outcome
One of: completed, completed with individual refusals carried from the delegate, or not attempted with a stated reason. The middle case exists because a delegate may legitimately refuse part of its work while completing the rest.

One invariant carries the section: a design generation that succeeded is never undone by a later step failing. The steps run in dependency order — the view can only be embedded into a design that exists — so a failure late in the chain leaves earlier work standing. That is deliberate under FR-004, and it is why the run reports rather than rolls back.

5 · Success criteria

A criterion names who is better off, and what would prove it was not — see 108-success-criteria for the full contract.

Authors landing a design export do so in one command rather than three — invocations needed to land an export = 1, down from 3, with the artifacts produced byte-identical to the hand-run sequence.

Observed at

A test that runs the flag over a fixture export, runs the three verbs by hand over the same export into a separate tree, and compares the two trees byte for byte.

Falsified by

The two trees differing in any byte — which would mean the flag is a second implementation of the pipeline rather than a caller of it, and every downstream check would then have to know which path produced the artifact.

Authors who mistype an export path lose nothing — model calls made = 0 and files written = 0 on a run naming an unreadable export, from a design generation’s full cost today.

Observed at

A test invoking the flag with a non-existent path against a recording provider, asserting the provider was never called and the working tree is unchanged.

Falsified by

Any model call, or any file created or modified, before the path is checked.

Authors without a browser still get everything that does not need one — steps completed = 2 of 3 with rendering unavailable, and the run does not fail, from 0 of 3 today when the chain is run as written.

Observed at

A test running the flag with rendering made unavailable, asserting the imported material and the embedded view are both present, the report names the render step as not attempted with its reason, and the exit state is success.

Falsified by

The run failing, or the embedded view being absent, when only the render step could not run — either would make a capture load-bearing, which 094 FR-005 forbids.

Operators running any verb other than the render verb incur no network egress from it — command modules able to acquire the render capability = 1, unchanged, after this flag ships.

Observed at

The existing source scan over the closed set of command modules, run unchanged: it asserts exactly one module acquires the render capability and names which. This spec adds a caller and must not move that number.

Falsified by

The count reaching 2, or the scan being relaxed to an allowlist to accommodate this flag — either converts a one-module guarantee into a list that grows, which is how the convention it replaced got there.

Authors reading a run report can tell what happened to every step — steps unaccounted for = 0, and individual refusals lost to summarising = 0, across a run that skips a step, a run whose delegate partly refuses, and a repeat run over unchanged input.

Observed at

Three tests over one fixture: a spec declaring no visual surface (asserting the report says nothing was imported or materialised, rather than staying silent); an export with two artboards whose labels collide (asserting the individual refusal reaches the report by label); and the same invocation run twice (asserting the byte difference is confined to the delegate named in Assumptions).

Falsified by

A step absent from the report rather than present with a reason — the conflation between “did not happen” and “not recorded” this family has paid for repeatedly — or a delegate’s per-item refusal arriving as a single flattened outcome.

6 · Assumptions

The three delegated verbs are correct as they stand. This spec orchestrates them and changes none of their behaviour, so a defect in any one surfaces through the flag unchanged rather than being masked or fixed by it.

One delegate is known not to be idempotent today, which is why FR-009 is a SHOULD. Materialising twice over unchanged input changes one byte on the second run — a blank line inserted by the first pass and consumed by the second, then stable. It converges rather than diverges, so it does not threaten this flow, but the flag inherits it until fixed at source. Recorded rather than fixed in passing: the fix belongs to the verb that owns it, not its first caller.

An author passing the flag is understood to be accepting network egress for that run. The design verb needs none by itself, and rendering needs it always; making the flag the place that declares it keeps the plain verb as network-free as it is today.

7 · Open questions

None outstanding. Four decisions were anchored before writing: where the flow lives, when it refuses, what it does when one step cannot run, and whether the render step is separately skippable. A fifth — how the render verb’s own separation requirement should read once a caller exists — is settled as a MODIFY on 106 that permits delegation while confining the capability, authored alongside this spec rather than left implied by it.
