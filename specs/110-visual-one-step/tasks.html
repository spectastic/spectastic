Tasks · 110-visual-one-step

Land the visuals in one step

Ordered, parallelizable work. Tests precede implementation. Drive through with /spectastic.implement — one task per invocation.

Status Draft Spec 110-visual-one-step Design design Branch spec/visual-slice-095-098 Created 23 Aug 2026 Read time

22 tasks across five phases. Setup → Foundational → User stories (US1·US2·US3) → Polish. Tasks marked [P] can run in parallel — different files, no dependency. Tests for a story MUST be written and failing before its implementation tasks start. US2 and US3 both extend US1's orchestrator and wiring rather than standing independent of it — see Dependencies.

1 · Execution strategy

Fits this slice. The spec's own INVEST card names US1 a viable MVP on its own — one command performs the three steps, with no early-refusal or partial-chain hardening yet. US2 and US3 each hardens one property of that same orchestrator (P2 and P3), so shipping US1 first and verifying it is the natural order, not a simplification.

Setup → Foundational → US1 → US2 → US3 → Polish. Each story closes its conformance before the next opens.

One team on each user story after Foundational. Coordinate at shared seams (data model, API contracts) via the spec, not Slack.

2 · Phase 1 — Setup

No new package, dependency or CI wiring — everything the flag needs already exists. The one real setup task is a regression net for the refactor Foundational performs.

Characterise today's CLI behaviour before touching it — spawn the built binary against a fixture export and pin the exact stdout lines and exit code for visual:import, visual:render and materialise, one success case and one failure case each. These assertions must still pass unchanged once Foundational extracts each action into a kernel plus a thin wrapper. packages/cli/test/visual-kernels.test.ts

3 · Phase 2 — Foundational

Shared infrastructure no story can ship without. All three visual actions in scope end in process.exit() today, so nothing can call them until each becomes a kernel a caller can invoke and inspect. Sequential — same file, and each extraction must leave T-001's assertions green before the next begins. visual:brief is deliberately left untouched: no requirement in this spec invokes it, and splitting it would be scope this slice doesn't own.

Extract the import action into a kernel — pull visual:import's body into an exported importVisualExport function returning a result the wrapper turns into today's exact stdout and exit code; the subcommand becomes a thin wrapper calling it. No behaviour change. packages/cli/src/commands/visual.ts
Extract the render action into a kernel — pull visual:render's body into an exported renderVisualExport function that takes the renderer as an explicit parameter rather than constructing playwrightRenderer() inline; wrapper calls it and constructs the renderer itself. No behaviour change. packages/cli/src/commands/visual.ts
Extract the materialise action into a kernel — pull materialise's body into an exported materialiseVisualDesign function; wrapper calls it. No behaviour change. packages/cli/src/commands/visual.ts

4 · Phase 3a — US1 · One command lands the export

Tests (write & fail first)

Write a failing orchestrator-sequencing test — against an in-memory fs and a fake renderer, assert runVisualOneStep sequences import → render → materialise in that order over a fixture export and returns a run report with all three steps completed. packages/core/test/visual-one-step.test.ts
Write the SC-001 byte-equality end-to-end test — spawn the built binary as spectastic design <id> --visuals <export> against the two-artboard fixture into one tree, run visual:import → visual:render → materialise by hand into a second tree, and assert the two are byte-identical (D-004's one real end-to-end test — a fake renderer cannot prove this). This is US1's assembled-and-run entry point. packages/cli/test/design-visuals.test.ts

Implementation

Build the core orchestrator — runVisualOneStep sequences the three kernels (import, render, materialise, in that order — materialise last because it writes into a design that must already exist) and returns the run report; takes { fs, render? } as ports and holds no capability of its own. packages/core/src/visual/one-step.ts
Export the one-step CLI entry — a function that constructs playwrightRenderer() and calls runVisualOneStep. This module remains the only one importing @spectastic/render; the existing (now-recursive per 106 T-1001) render.port-reach.test.ts is the standing guard that design.ts never does — no new test needed for that half. packages/cli/src/commands/visual.ts
Wire --visuals onto the design command — derive --into and --identity from the spec id (D-002), call visual.ts's one-step entry after designCommand succeeds, and add whatever landed to the paths array already passed to commitVerbAndExit so the artifacts are committed. packages/cli/src/commands/design.ts

Closes FR-001, FR-002, FR-005, NFR-002 — the last two verified by the existing, already-recursive render.port-reach.test.ts rather than a new test. Validates SC-001, SC-004. Does not yet satisfy FR-003's refusal ordering (US2) or FR-004/006/007/008 (US3) — this phase ships the happy path only, which the spec's own INVEST card names a viable MVP.

6 · Phase 3c — US3 · A missing browser does not cost the rest

Extends US1's orchestrator with the not-attempted / partial-refusal branches; independent of US2.

Tests (write & fail first)

Write a failing render-unavailable test — with the fake renderer's reachability check returning false, assert the orchestrator still completes import and materialise, records render as not-attempted with a reason, and the overall result is success, not a refusal. packages/core/test/visual-one-step.test.ts
Write a failing no-visual-surface test — with the design declaring shape="none" or no visual surface at all, assert import and materialise are both recorded not-attempted with the stated reason, and neither is silently skipped — FR-008. packages/core/test/visual-one-step.test.ts
Write the SC-003 no-browser end-to-end test — spawn spectastic design <id> --visuals <export> --no-render, assert the design and its embedded view land, the report names rendering as not attempted with its reason, and the process exits successfully. This is US3's assembled-and-run entry point. packages/cli/test/design-visuals.test.ts
Write a failing partial-refusal carry-through test — with the fake renderer reporting one artboard captured and one refused (a label collision), assert the orchestrator's render step outcome is completed-with-refusals carrying that individual refusal, not a single flattened pass/fail — FR-007. packages/core/test/visual-one-step.test.ts

Implementation

Add --no-render and the egress preflight — a reachability check for rendering, skipped entirely under --no-render; on failure this produces a not-attempted outcome for the render step rather than aborting the run. packages/cli/src/commands/design.ts
Check the declared visual surface before importing or materialising — when it is absent or none, skip both steps and return them not-attempted with that reason — FR-008. packages/core/src/visual/one-step.ts
Carry a delegate's per-item refusals through the run report — surface 106's own per-artboard refusals (e.g. a label collision) on the render step's outcome rather than reducing them to a single pass/fail — FR-007. packages/core/src/visual/one-step.ts

Closes FR-004, FR-006, FR-007, FR-008. Validates SC-003, SC-005 (its remaining leg — a repeat run over unchanged input — closes in Polish, T-900).
