Implementation plan · 003-init-node-port

spectastic init — Node port

How we will build it.

Status Accepted Spec 003-init-node-port Owner Brian Corbin · @briancorbinxyz Branch 003-init-node-port Created 14 Jun 2026 Read time

Add an init subcommand to @spectastic/cli that ports the Python scripts/spectastic at parity. A small prebuild script copies templates/, assets/, and commands/ from the repo root into packages/cli/_bundled/ (gitignored); runtime resolves via import.meta.url with a dev-mode fallback up the workspace. Conflict UX uses @clack/prompts for a calmer feel than raw readline. Test style is unit-first (decision/planner/writer functions covered individually) with one smoke integration test spawning the CLI against a tmp dir. Biggest risk: byte-identity parity with the Python output across line endings and trailing-newline conventions.

Perf targets

3 · Approach

Five-stage pipeline, all in @spectastic/cli: the commander entry registers an init subcommand; the action handler builds a plan (a list of FileWriteDecisions) from the bundle inventory and a CWD scan; the prompt loop consults the plan to ask the user about each conflict (or applies --force / refuses on non-TTY); the writer executes the finalised plan in a single atomic pass; the summary printer reports counts and the next-step hint. The bundle resolver is a small helper that tries the production path first (_bundled/ next to the compiled binary) and falls back to the dev workspace path (../../ from the CLI package root) — so dev mode without a prebuild still works on a freshly-cloned repo.

The two-pass design (plan everything before writing anything) is the load-bearing invariant from FR-008 — Ctrl-C during the prompt loop must leave zero partial writes. Implementation: plan.ts returns FileWriteDecision[] with every entry marked "write" initially; prompt.ts mutates entries to "overwrite" or "skip" based on user choices; write.ts only runs after the loop returns cleanly. The writer itself doesn't need temp-file shuffling because conflicts are decided up front; it just does writeFile sequentially.

5 · Decisions

D-001 · init lives in @spectastic/cli as a second subcommand

Status
Accepted
Context
Single binary on PATH is the user-visible goal. validate already lives in @spectastic/cli; spinning up @spectastic/init as its own package would re-introduce the dual-binary problem this spec exists to retire.
Decision
Register init as a commander subcommand inside @spectastic/cli/src/commands/init.ts. Shared CLI shell, shared bin/spectastic.
Consequences
+ One binary. + Reuses commander setup and the picocolors output convention. − CLI package grows slightly (init logic ~200 LOC); acceptable.

D-002 · @clack/prompts for conflict UX

Status
Accepted
Context
Conflict prompts ([y/N/a/s]) are the only interactive moment in spectastic init. Built-in readline works but feels janky; the parity argument doesn't justify a worse user experience than competing CLIs (cargo new, vite create, etc.).
Decision
@clack/prompts for the conflict UX. Use its select primitive with four options matching the Python prompt's [y/N/a/s]. picocolors stays for non-interactive output.
Consequences
+ Calm, modern terminal UX that matches Tier 1's design sensibility. + Built-in Ctrl-C handling. − One new runtime dependency (~30 KB). − Output differs slightly from Python parity; SC-001 covers byte-identity of written files, not terminal output, so this is fine.

D-003 · Prebuild copy bundles templates; runtime falls back for dev

Status
Accepted
Context
Templates, assets, and slash-command files live at the repo root. The published npm package needs them too. Committing duplicates risks drift; inlining as JS strings makes the install opaque; symlinks don't survive npm pack.
Decision
packages/cli/scripts/prebuild.mjs copies ../../templates/, ../../assets/, and ../../commands/ into packages/cli/_bundled/ on every build. _bundled/ is gitignored but included in the files field of packages/cli/package.json. At runtime, bundle.ts resolves via import.meta.url to _bundled/; if missing (dev without prebuild), it falls back to the workspace root and warns.
Consequences
+ Single source of truth at repo root. + Published install is real files users can inspect. + Drift impossible at release time. − One extra build step. − Runtime fallback adds a few lines; cost is bounded.

D-004 · Unit-first testing; one smoke integration

Status
Accepted
Context
The planner, prompt-decision function, and writer are pure-ish functions amenable to fast unit tests. A heavy integration suite would re-validate the same logic at higher cost. Parity verification (SC-001) does need one real spawn-the-CLI test against a tmp directory.
Decision
Unit tests cover: plan.ts (given bundle inventory + cwd scan, produces correct FileWriteDecision[]); prompt.ts (given conflict + user answer, mutates plan correctly); write.ts (given plan, writes correct files to a tmp dir). One smoke integration test spawns the compiled binary against an empty tmp dir and asserts the 16-file structure.
Consequences
+ Fast feedback loop while iterating. + Surface for regression catch-rate is comprehensive (unit + smoke). − Slightly more test files to maintain than an integration-only approach.

D-005 · Two-pass atomic-plan-then-write (mandated by FR-008)

Status
Accepted
Context
FR-008 requires zero partial writes on Ctrl-C. Two designs satisfy this: temp-file-shuffle (write to .tmp + rename atomically) or plan-then-write (decide everything first, write in one pass at the end).
Decision
Plan-then-write. The first pass builds FileWriteDecision[] and runs the prompt loop. The writer only fires after the loop returns cleanly; Ctrl-C during the loop exits before any writeFile call.
Consequences
+ Simpler than tempfile shuffle; no orphaned .tmp files to clean up. + Single point of decision before any IO. − Doesn't protect against mid-write failure (e.g. disk full at file 12 of 16). Trade is acceptable: such failures are rare and partial state is recoverable via spectastic init --force on a re-run; FR-008 specifies the Ctrl-C case, not the disk-full case.

8 · Complexity tracking

Two complexity decisions worth justifying.

Submodule under src/commands/init/. The init subcommand splits into bundle / plan / prompt / write / summary — five files where a single 250-line file would also work. Justified by D-004: unit testing is much cleaner with separable functions. The split serves testability, not preemptive abstraction.

Runtime fallback path in bundle.ts. Dev-mode without prebuild is a real scenario (fresh clone, contributor explores the CLI before running pnpm build). The fallback adds ~15 LOC and one warning. The alternative — requiring prebuild before any node packages/cli/bin/spectastic init — would frustrate first-time contributors. Cost is minimal.
