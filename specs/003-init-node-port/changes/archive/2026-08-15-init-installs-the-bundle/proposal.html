init installs the bundle

Asked outright this time, and answered: yes. Two earlier attempts tried to discover this in a requirement that does not say it.

Status Applied Change ID 2026-08-15-init-installs-the-bundle Spec 003-init-node-port Author Brian Corbin · @briancorbinxyz Created 15 Aug 2026 Targets 4 requirements — 4 modified Read time

init should install the subagent definitions, and anything else the bundle carries for installation. That is a decision — no requirement obliges it today, and two withdrawn proposals failed by trying to find one. It is worth taking because the adversarial risk pass depends on spectastic-critic being present, and every downstream project has run /spectastic.propose without it since spec 044.

Taking it means correcting the requirement that forbids it — FR-002 enumerates sixteen files exhaustively — and three siblings the same edit exposes: a bundling rule naming only two of four trees, and two requirements still measured against a Python script this spec required be deleted.

Init installs the bundle

Applied

1 · Intent

Spec 044 introduced three subagent definitions and the build has bundled them ever since. init has never installed them, so every project scaffolded since then has run /spectastic.propose with no spectastic-critic — the adversarial risk pass silently absent rather than failing (meta-spec T-026).

Two proposals tried to fix that by arguing the install was already required, reading 044 FR-004 — "Agent-definition sources MUST be tracked and synced to .claude/agents/, mirroring the commands/ → .claude/commands/ convention" — in opposite directions and marking each reading verified. Both were withdrawn. CLAUDE.md documents that convention as the repo-local manual cp, so the sentence is about keeping a checkout in sync and not about what a scaffolded third-party project receives.

So this is a decision, taken here rather than found somewhere: yes, init should install them, along with anything else the bundle carries for installation. The argument is the evidence from using it — the one project where the definitions were hand-copied is the one where the risk pass has been catching defects all day, including in the two proposals this one replaces.

Taking the decision means correcting FR-002, which forbids it: it enumerates "the canonical 16-file lifecycle structure" exhaustively, against a scaffold that writes 27 and a bundle that carries a fourth tree it never mentions. The same edit exposes three siblings that cannot be left behind — FR-009 bundles only "Templates and assets", and SC-001 and FR-007 both measure against the Python script FR-010 required be deleted at this spec's own apply.

2 · Scope

In scope

  • Deciding that init installs the bundle's installable trees, which brings the subagent definitions in and anything a later tree adds.
  • FR-002's enumeration, replaced by the trees the installer walks — named concretely, because the previous two attempts both invented an abstraction ("marked", "designates") that exists nowhere in the code.
  • FR-009, which bundles "Templates and assets" and so omits the command adapters it has always shipped as well as the agents this adds.
  • SC-001 and FR-007, both measured against a deleted script. Not a separate concern: SC-001 has to move for the count anyway, and leaving FR-007 would keep a must-tier requirement naming that script as the authority for output.
  • Four prose sites repeating the 16-file count, and five more naming the deleted script as canonical — the preamble to §3, the first assumption in §6, the INVEST Estimable row, §1 Context, and the symlink edge case in §2. An earlier draft of this line named two of the five, which is the defect that withdrew the second attempt recurring inside the attempt whose changelog claims to have caught it. Prose, so no delta reaches them — they land as pre-apply edits, listed in §6.

Out of scope

  • Installing commands.json and spectastic-profiles.json. The bundle carries them and prebuild.mjs annotates both as never written to a project: they are install-time inputs the CLI reads from its own package. "Installable trees" excludes them by naming trees rather than the bundle root. defer-to=never.
  • 004's tree count, its US1 prose, and its FR-007 bundle enumeration. A different spec and the kernel folds same-spec deltas only, so it is the sibling propose 2026-08-15-the-published-tree, authored alongside and applied after this. defer-to=004-npm-publish-workflow.
  • Closing the fail-open path in the extended-verb manifest. loadManifest returns empty on a missing or malformed file, so every verb installs — deliberate, and the wording below states the exclusion as a property of the bundle rather than an absolute the code can silently breach. defer-to=TBD-manifest-fail-open.

4 · Deltas

What changes: the file enumeration becomes the trees the installer walks, which is what brings the subagent definitions in.

The subcommand MUST write the bundle's installable trees — the slash-command files, the subagent definitions, the assets and the templates — to the destination paths the installer derives for them, and MUST NOT write a command the bundle marks as an opt-in extended verb unless it was requested. Bundled material outside those trees MUST NOT be written.

Rationale

The subagent definitions are the change. Spec 044 introduced them and the build has bundled them since; nothing installed them, so the adversarial risk pass has been absent from every scaffolded project (T-026). This decides that it should not be, which no existing requirement says — two proposals were withdrawn for arguing otherwise.

Trees rather than files, and rather than an abstraction. The previous wording enumerated sixteen files against a scaffold of twenty-seven and named plan, a verb renamed to design; a list of files must be edited whenever any file ships, and is not. But the two withdrawn attempts replaced it with "marked" and "designates", neither of which exists — the installer walks named subdirectories and never reads the bundle root. Naming the trees is the honest middle: it matches the mechanism, and a tree is added about once a year rather than a file every release.

The last sentence is what keeps commands.json and spectastic-profiles.json out. Both are bundled and both are install-time inputs the CLI reads from its own package; writing them into a project would add files nothing consumes.

"Marks as an opt-in extended verb" describes the bundle's own manifest, which is how explain and explore stay out of a default scaffold. That manifest is deliberately fail-open — absent or malformed, every verb installs — so this is stated as what the bundle marks rather than as an absolute the loader can breach without anyone noticing.

What changes: the bundling rule covers every installable tree, not two of four. Nothing else — the install-parity sentence is carried through verbatim. An earlier draft dropped it silently, caught by the adversarial pass on the sibling proposal.

Everything the bundle carries — its installable trees and the manifests the CLI reads at install time — MUST ship inside the published @spectastic/cli npm package, under the package's own directory structure, and MUST resolve at runtime relative to the binary's installed location via import.meta.url — never via a CWD-relative path. The CLI MUST work identically whether invoked via npx, a global npm i -g install, or a workspace-symlinked dev install.

Rationale

Resolution via import.meta.url is unchanged and is the half that matters at runtime: a CWD-relative path breaks the moment the binary is invoked from anywhere but the package root, which is every real invocation.

The enumeration widens because it was already wrong. "Templates and assets" omitted the slash-command files this spec has shipped since it landed, and would omit the subagent definitions FR-002 now installs — a must-tier bundling rule describing less than the bundle has carried for months.

It deliberately does not reuse FR-002's "installable trees" alone. This requirement governs what ships in the tarball; FR-002 governs what lands in a project. Narrowing the first to the second would make a package conforming while omitting commands.json — which the CLI reads to decide which verbs are opt-in, and whose loader is fail-open, so a package without it installs every extended verb. Two scopes, stated separately, because collapsing them is how a packaging rule acquires an installer's blind spot.

What changes: the criterion stops measuring against a deleted script, and names the two files init generates itself so it is true rather than nearly true.

Running spectastic init with no arguments and no profile in an empty temporary directory MUST write every file in the bundle's installable trees except unrequested extended verbs, each byte-identical (modulo trailing-newline normalisation) to its bundled source, and MUST NOT write any other file from the bundle.

Rationale

The property is unchanged: a scaffolded project is exactly what the package ships, with nothing missing and nothing extra.

What changed is the referent. This measured byte-identity against "what the Python scripts/spectastic init produces", and FR-010 requires that script be deleted at this spec's apply — so it has never been satisfiable as written. Comparison against the bundled source is the same guarantee against something present in every install context, including npx and a global install where no repository exists. Whether the bundle matches the repository is a build-time property and belongs to 004 FR-007, which regenerates it at the tagged commit.

It no longer claims to describe the whole tree, and that is the third correction to this clause today. Two earlier drafts said the tree contains "nothing the bundle does not designate" and then "exactly" a named set; both were refuted by real behaviour, because what init emits depends on the run. Zero-arg in a TTY prompts for a profile and writes principles.html, AGENTS.md and CLAUDE.md as content with no on-disk source, plus a profile marker; --tools adds a hook and a managed-adapter stamp; and the .gitignore block and spectastic.json are generated outside the write plan in every run.

So the criterion states what it can check and scopes itself to the run it describes: the bundle's material all arrives, correctly, and no bundled file arrives that should not. Exhaustiveness over the whole directory is abandoned deliberately rather than narrowed again — it is not a closed set, and three attempts to write it as one have each been falsified by a path nobody had opened.

What changes: the summary format stays; the clause measuring it against the deleted script goes.

After completion, the subcommand MUST print a summary line in the form spectastic init — summary followed by wrote N, overwrote M, skipped K, then a next-step hint pointing at /spectastic.principles.

Rationale

The format is unchanged and is the whole requirement: three counts and a next step, so a reader can tell at a glance what happened and what to do.

"Matches the Python script's output verbatim" is removed because that script was deleted at this spec's own apply (FR-010). A must-tier clause whose conformance cannot be determined is not a MUST, and this one additionally named the deleted script as the authority for output — which would have reinstated, through a back door, the same enumeration authority FR-002 is transferring to the bundle.

5 · Risk register

Findings from the adversarial pass. Statuses stay identified until the author dispositions them.

The FR-009 rewrite narrowed a packaging rule into an installer's vocabulary, and dropped a must-tier clause without saying so

Two properties left the spec unannounced. The live FR-009's second sentence — the CLI must work identically via npx, a global install, or a workspace symlink — was absent from the replacement and mentioned nowhere; it is the only requirement covering resolveBundle's dev fallback, a second hand-maintained walk this proposal's own task 2 must edit in parallel, so the draft created a second code path to keep in step while deleting the rule obliging them to agree. And borrowing FR-002's "installable trees" narrowed a packaging obligation to an install one, excluding commands.json and spectastic-profiles.json — the first of which decides which verbs are opt-in and whose loader is fail-open, so a conforming package could omit it and install every extended verb.

Both fixed before disposition. The clause is restored verbatim and the post-state now reads "everything the bundle carries — its installable trees and the manifests the CLI reads at install time", with the two-scope distinction argued in the rationale rather than left for a reader to notice. This is the second silent must-tier deletion the pass has caught today, in two different proposals, which is a finding about my drafting and not about either requirement.

The "exactly" clause was false on the interactive path, and the two files it named are written outside the atomic two-pass FR-008 requires

The evidence cited — SCAFFOLD_TREE_FILE_COUNT = SCAFFOLD_FILE_COUNT + 2 — holds only for the non-TTY run the smoke test spawns. In a TTY, zero-arg init prompts for a profile; accepting one writes principles.html, AGENTS.md and CLAUDE.md as content with no on-disk source, plus a profile marker, and --tools adds two more. Separately, promoting .gitignore and spectastic.json into the spec's definition of the output tree makes them part of "the file set", which FR-008 requires be written in a scan-then-write pass — and both are written after executeWrites and after the summary has printed, with no conflict scan.

Fixed by abandoning exhaustiveness rather than narrowing it again. Three drafts of this clause have now been falsified by a path nobody had opened, which is the signal that the tree is not a closed set. It states the checkable property — every installable-tree file arrives byte-identical, and no other bundled file arrives — and scopes itself to the run it describes. The FR-008 tension dissolves with the generated files no longer named. That they are written outside the two-pass is a real and separate defect in the live behaviour, and belongs in triage rather than in this proposal — filed as 003/T-001, which found it is six writes rather than two, and that printSummary runs before all six so it undercounts its own run.

Three deleted-script referents survived the list, two of them asserting the exact authority FR-007's delta removes

The count half was complete; the script half named two of five. Missing were the INVEST Estimable row — which rests the spec's claim to have no open questions on the script being canonical — §1 Context, and the symlink edge case. So after apply the document would still name a deleted file as the authority for precisely what FR-007 stopped pointing at. This is the defect that withdrew the second attempt, recurring inside the attempt whose changelog claims to carry the sites both earlier attempts missed.

Fixed; all five now named in §Scope and owned by a §6 task. Worth stating plainly rather than filing: the mechanism failed three times because there is no mechanism. Prose referents are invisible to every delta and every validate rule, and the hand-edit list is the whole control. It has now been short on all three attempts.

A universal negative was stamped verified, which is not what the grounding vocabulary means

KB-0001@2026-07-25 defines verified as a state about a source that was opened this turn. Claim 1 — "nothing today requires the install" — quantifies over the whole spec estate, and two files cannot establish it. Three proposals have now marked three different readings of 044 FR-004's one sentence verified, in opposite directions, which inverts what the discipline exists for: a plan's confidence should be visible rather than uniform.

Restamped assumed, with the genuinely-verified narrower facts kept. The critic's alternative — close the ambiguity where it lives, with a delta on 044 FR-004 scoping the sentence — is the better long-term answer and is not taken here, because this proposal's whole point is that the question is a decision rather than a reading. Once it is decided, 044 FR-004 should say so. Filed as TBD-agent-sync-scope.
