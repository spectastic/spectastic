Change proposal · 003-init-node-port

Installable trees by host target

Make FR-002's installable-trees set depend on the host target, and authorise the portable Agent-Skills tree it has been writing without sanction.

Status Applied Change ID 2026-09-12-installable-trees-by-target Spec 003-init-node-port Author Brian Corbin (@briancorbinxyz) Created 12 Sep 2026 Targets 1 requirement Read time

FR-002 enumerates the installable trees init writes — slash commands, subagents, assets, templates — and forbids writing bundled material outside them. But the host-target feature (111) has init write a fifth tree, the portable Agent-Skills adapters (.agents/skills): for --target codex (already shipped) and, via the 2026-09-12-claude-installs-skills change, the default Claude scaffold. Both violate FR-002 as written. This makes FR-002 target-aware and authorises the skills tree, resolving the conflict — including the pre-existing one the codex target slipped past.

Installable trees by host target

Applied

1 · Intent

FR-002 was written when init produced exactly one scaffold shape — the four Claude trees (slash commands, subagent definitions, assets, templates) — and it is deliberately strict: it enumerates those trees and ends with "Bundled material outside those trees MUST NOT be written." That strictness is good and worth keeping; it is the clause that keeps commands.json and the profile manifest out of a scaffold.

But spec 111 introduced a host target, and with it a fifth installable tree: the portable Agent-Skills adapters at .agents/skills. init --target codex writes that tree instead of the Claude command and subagent trees; and the 2026-09-12-claude-installs-skills change has the default Claude scaffold write it alongside them. Under FR-002 as written, both are forbidden — .agents/skills is bundled material outside the four authorised trees, and the codex target additionally omits the two trees FR-002 says it MUST write.

So FR-002 has silently disagreed with shipped behaviour since the codex target landed — 111's design never checked this clause (worth a triage note in its own right). This change makes FR-002 describe what init actually does: the installable-trees set is a function of the selected target, and the portable skills tree is one of the trees it may write. The strict "nothing outside the authorised trees" guarantee is preserved, just made target-relative.

2 · Scope

In scope

  • Making FR-002's installable-trees set depend on the host target, and adding the portable Agent-Skills tree to the authorised set.
  • Preserving FR-002's two guarantees — no unrequested extended verb, and nothing bundled written outside the selected target's trees — scoped to the target.
  • The header's smallest-demoable enumeration, which lists the trees by hand and so cannot be reached by a delta (hand-edit, per the risk note).

Out of scope

  • The scaffold file count — owned and guarded by 004 SC-001; a companion propose against 004 moves it (32 → 40) and reconciles FR-007.
  • FR-009 (what the published package ships) — its normative text is role-named ("installable trees"), so the skills tree is already covered; only its illustrative rationale is now one tree short, which is not a normative change.
  • The opt-in extended-verb mechanism and the manifests-stay-out clause — unchanged.

3 · Approach

One MODIFY on FR-002. The normative sentence becomes target-relative: the Claude target writes the slash commands, the subagents, and the portable skills adapters plus the shared assets and templates; the Codex target writes the portable skills adapters plus those same shared assets and templates. The two MUST-level guarantees are kept verbatim in force but re-scoped to "the trees the selected target installs," so the strictness FR-002 exists for is unchanged — a scaffold still contains nothing the selected target does not authorise. The tree set is named by role (following the existing FR-002 / FR-009 discipline), so it does not drift into a file or directory list.

SC-001 and US1 already speak of "the bundle's installable trees" abstractly and carry no tree list of their own, so the MODIFY is enough for them. Only the header's smallest-demoable prose enumerates the trees literally; a delta cannot target <spec-meta>, so it is a hand-edit task — the same prose-copy hazard 004's history documents.

4 · Deltas

One <spec-delta>. target= links to the live spec.

What changes: the installable-trees set becomes a function of the host target, and the portable Agent-Skills tree joins the authorised set. The knowledge-corpus scaffold — written under both targets since 051 but never named here, only implicitly covered by "templates" — is now stated explicitly, so the MUST-NOT clause does not forbid a tree init actually writes. Both MUST-level guarantees (no unrequested extended verb; nothing bundled written outside the authorised trees) are preserved, re-scoped to the selected target.

The subcommand MUST write the installable trees the selected host target calls for — for the default Claude target, the slash-command files, the subagent definitions and the portable Agent-Skills adapters; for the Codex target, the portable Agent-Skills adapters — together with the shared assets, templates and knowledge-corpus scaffold every target installs, to the destination paths the installer derives for them. It MUST NOT write a command the bundle marks as an opt-in extended verb unless it was requested, and MUST NOT write bundled material outside the trees the selected target installs.

Rationale

The host target is the change. Spec 111 added a target, and the portable Agent-Skills adapters for non-Claude hosts — and, by the 2026-09-12-claude-installs-skills change, the default scaffold too — ship as the .agents/skills tree, which was being written with no requirement authorising it. So the authorised set is now a function of the target rather than one fixed shape, and "nothing outside the authorised trees" is scoped to the selected target so the guarantee stays exact under each. The codex target slipped past this clause at its own apply — worth a triage note.

The subagent definitions are the change. Spec 044 introduced them and the build has bundled them since; nothing installed them, so the adversarial risk pass has been absent from every scaffolded project (T-026). This decides that it should not be, which no existing requirement says — two proposals were withdrawn for arguing otherwise.

Trees rather than files, and rather than an abstraction. The previous wording enumerated sixteen files against a scaffold of twenty-seven and named plan, a verb renamed to design; a list of files must be edited whenever any file ships, and is not. But the two withdrawn attempts replaced it with "marked" and "designates", neither of which exists — the installer walks named subdirectories and never reads the bundle root. Naming the trees is the honest middle: it matches the mechanism, and a tree is added about once a year rather than a file every release.

The last sentence is what keeps commands.json and spectastic-profiles.json out. Both are bundled and both are install-time inputs the CLI reads from its own package; writing them into a project would add files nothing consumes.

"Marks as an opt-in extended verb" describes the bundle's own manifest, which is how explain and explore stay out of a default scaffold. That manifest is deliberately fail-open — absent or malformed, every verb installs — so this is stated as what the bundle marks rather than as an absolute the loader can breach without anyone noticing.

4b · What this change removes

The MODIFY on FR-002 states its own widening (reason + new post-state), so nothing further is owed here. Nothing is removed: the two MUST-level guarantees survive, re-scoped rather than relaxed.

5 · Risk register

Populated by the adversarial risk pass (touches a must-tier requirement). One <spec-risk> per finding; apply refuses until each is accepted, mitigated, or rejected.

The re-enumerated FR-002 omits the knowledge-corpus scaffold, so its own MUST-NOT clause forbids a tree init actually writes under both targets — reproducing, for a second tree, the very "spec silently disagrees with shipped behaviour" defect this change exists to kill.

The MODIFY's new text authorised only commands/subagents/skills + "the shared assets and templates," then said "MUST NOT write bundled material outside the trees the selected target installs" — but bundle.ts's remapKnowledgeScaffold writes templates/knowledge/** to knowledge/ under both targets, and 003's own smallest-demoable (spec.html:29) lists "the knowledge scaffold."

Mitigated — the sharpest catch of the pass, and fixed in the delta. FR-002 now names "the shared assets, templates and knowledge-corpus scaffold every target installs," so the MUST-NOT clause no longer forbids the knowledge/ tree. This also closes the pre-existing latent gap: knowledge was only ever implicitly covered by "templates," and the re-write is the right moment to state it rather than re-freeze it.

Applying this makes 003 FR-002 authorise a ~40-file scaffold while sibling 004 SC-001's drift-guarded count still reads 32, so the two specs disagree on what init writes.

004 SC-001 "yields a 32-file tree," machine-read by a guard; the applied 2026-09-12-claude-installs-skills change already added the 8 skill files, and this proposal's §Scope concedes the count must move 32 → 40.

Mitigated by sequencing, not deferral. The disagreement is pre-existing — 004's guard has been red since the skills landed in the 111 drain — and 003 repairs only its own half. The machinery forbids co-landing: a proposal targets one spec and apply folds same-spec deltas only, so 003 and 004 cannot land in one apply. The companion 004 propose (SC-001 32→40 + FR-007) is authored and applied immediately after this one, in the same session, closing the window; until both land the red guard is the honest "the pair is not done" signal.

Scoped too narrowly: pushing the 004 reconciliation to a separate propose is the SC-001-alone split 004's own history records as having failed twice.

§Scope out-of-scope "a companion propose against 004 moves it (32 → 40)," against 004's changelog (2026-08-15): "taking only the count has failed twice … a proposal scoped to SC-001 alone would leave US1's copy of the number wrong."

Mitigated. 004's "failed twice" scar is about intra-004 coupling — SC-001, US1's prose copy, and FR-007 must move together within 004 — which the companion 004 propose will honour by carrying all three in one change (SC-001 is delta-folded; US1/FR-007 handled as that proposal's deltas/tasks). The 003↔004 split is a different axis: it is across specs and unavoidable (one propose per spec), and is mitigated by landing the 004 propose now, back-to-back with this one, rather than leaving it uncommitted.
