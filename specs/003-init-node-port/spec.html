spectastic init — Node port

Bring init to parity in TypeScript on the same binary as validate, then retire the Python implementation. One CLI, one install, no PATH coexistence anxiety.

1 · Context

At authoring time, spectastic shipped two CLIs. The Python scripts/spectastic init bootstrapped a project (8 slash commands + 2 assets + 6 templates = 16 files); its spec at 001-cli is the behavioral contract. The Node spectastic validate shipped in 002-validate-cli as a subcommand of @spectastic/cli. Both want the same spectastic binary name on PATH — exactly one can own it. Spec 002 §6 Assumption #4 acknowledged this transition cost and named "retire Python once Node CLI reaches parity" as the resolution. This spec is that resolution.

Porting yields three immediate wins: one install story (npm i -g @spectastic/cli instead of chmod +x on a downloaded Python file), one binary on PATH (no spectastic-init renaming compromise), and shared lifecycle/test infrastructure across init and validate (and future subcommands like adopt, generate, doctor). The Python script's 1.0 behavior is the contract; the Node implementation is the new home.

2 · User scenarios & testing

Each story is independently testable.

US1 · New-project author bootstraps spectastic P1

As a developer starting a new spec-driven project, I want to run spectastic init in an empty directory so that I get a working spectastic project (slash commands, assets, templates) with one command, no clone required.

Acceptance: Empty directory + zero-arg invocation produces the full lifecycle structure — every file in the bundle's installable trees, byte-identical to its source — exits 0, prints a summary line of the form "wrote N, overwrote 0, skipped 0" where N is SCAFFOLD_FILE_COUNT, and a next-step hint pointing at /spectastic.principles. The count is deliberately not restated here: it has moved seven times, and the guarded copy lives in 004 SC-001.

US2 · Repeat-init author isn't surprised P1

As a developer re-initialising or updating an existing spectastic project, I want to be prompted before any existing file is overwritten so that I never lose work I forgot to commit.

Acceptance: Each conflict prompts [y/N/a/s] (default N); a overwrites all remaining; s skips all remaining. --force bypasses prompts entirely. Non-TTY context with any conflict refuses with exit 2 and a message naming --force.

US3 · CI script idempotently bootstraps a workspace P2

As a CI maintainer for a project template, I want to run spectastic init --force in a fresh workspace so that the build always starts from a known-good baseline without manual interaction.

Acceptance: --force mode in non-TTY context completes without prompting; exit 0 on success; exit 1 on any unrecoverable filesystem error.

Edge cases

  • Destination directory not writable — exit 1 with a clear message naming the path. No partial writes left behind.
  • Templates missing from the install (packaging bug) — exit 1 early with a message instructing reinstall.
  • Init in a directory that already has spectastic but is mid-edit — every existing file produces a conflict prompt; user can s-skip all to safely abort.
  • Init in the spectastic repo itself (self-init) — works; same conflict-prompt behavior applies to every templated file already present.
  • Symlinked destination files — prompts as normal; on overwrite, the existing symlink is replaced with a regular file (this was the Python script's behaviour and is carried forward deliberately).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119. The Python script (001-cli) is the canonical reference for any behavior not explicitly named here.

Functional — the subcommand

The spectastic init subcommand MUST accept zero positional arguments and write to the current working directory. With unexpected positional arguments, print usage and exit 2.

The subcommand MUST write the bundle's installable trees — the slash-command files, the subagent definitions, the assets and the templates — to the destination paths the installer derives for them, and MUST NOT write a command the bundle marks as an opt-in extended verb unless it was requested. Bundled material outside those trees MUST NOT be written.

Rationale

The subagent definitions are the change. Spec 044 introduced them and the build has bundled them since; nothing installed them, so the adversarial risk pass has been absent from every scaffolded project (T-026). This decides that it should not be, which no existing requirement says — two proposals were withdrawn for arguing otherwise.

Trees rather than files, and rather than an abstraction. The previous wording enumerated sixteen files against a scaffold of twenty-seven and named plan, a verb renamed to design; a list of files must be edited whenever any file ships, and is not. But the two withdrawn attempts replaced it with "marked" and "designates", neither of which exists — the installer walks named subdirectories and never reads the bundle root. Naming the trees is the honest middle: it matches the mechanism, and a tree is added about once a year rather than a file every release.

The last sentence is what keeps commands.json and spectastic-profiles.json out. Both are bundled and both are install-time inputs the CLI reads from its own package; writing them into a project would add files nothing consumes.

"Marks as an opt-in extended verb" describes the bundle's own manifest, which is how explain and explore stay out of a default scaffold. That manifest is deliberately fail-open — absent or malformed, every verb installs — so this is stated as what the bundle marks rather than as an absolute the loader can breach without anyone noticing.

The subcommand MUST detect conflicts (any destination file already existing) and prompt per-file in a TTY: [y/N/a/s] with default N (skip this file). y overwrites this file. a overwrites every remaining conflict without further prompting. s skips every remaining conflict without further prompting.

The subcommand MUST accept a --force flag that overwrites every conflict without prompting. --force in an empty directory (no conflicts) is a no-op flag.

In a non-TTY context (CI, piped input) with at least one conflict and without --force, the subcommand MUST refuse with exit code 2 and an error message that names --force as the resolution. The CLI MUST NOT hang on a prompt that can never be answered.

Exit codes MUST be: 0 on success (every file written or intentionally skipped); 1 on unrecoverable IO error (e.g. destination not writable, template missing from install); 2 on usage error or non-TTY-conflict-without-force.

After completion, the subcommand MUST print a summary line in the form spectastic init — summary followed by wrote N, overwrote M, skipped K, then a next-step hint pointing at /spectastic.principles.

Rationale

The format is unchanged and is the whole requirement: three counts and a next step, so a reader can tell at a glance what happened and what to do.

"Matches the Python script's output verbatim" is removed because that script was deleted at this spec's own apply (FR-010). A must-tier clause whose conformance cannot be determined is not a MUST, and this one additionally named the deleted script as the authority for output — which would have reinstated, through a back door, the same enumeration authority FR-002 is transferring to the bundle.

Writes MUST be atomic across the file set: a first pass scans every destination for conflicts and prompts for each (or applies --force); only after every decision is made does the second pass write any file. A user who aborts mid-prompt (Ctrl-C) leaves zero files written.

Everything the bundle carries — its installable trees and the manifests the CLI reads at install time — MUST ship inside the published @spectastic/cli npm package, under the package's own directory structure, and MUST resolve at runtime relative to the binary's installed location via import.meta.url — never via a CWD-relative path. The CLI MUST work identically whether invoked via npx, a global npm i -g install, or a workspace-symlinked dev install.

Rationale

Resolution via import.meta.url is unchanged and is the half that matters at runtime: a CWD-relative path breaks the moment the binary is invoked from anywhere but the package root, which is every real invocation.

The enumeration widens because it was already wrong. "Templates and assets" omitted the slash-command files this spec has shipped since it landed, and would omit the subagent definitions FR-002 now installs — a must-tier bundling rule describing less than the bundle has carried for months.

It deliberately does not reuse FR-002's "installable trees" alone. This requirement governs what ships in the tarball; FR-002 governs what lands in a project. Narrowing the first to the second would make a package conforming while omitting commands.json — which the CLI reads to decide which verbs are opt-in, and whose loader is fail-open, so a package without it installs every extended verb. Two scopes, stated separately, because collapsing them is how a packaging rule acquires an installer's blind spot.

At apply time for this spec: the Python script scripts/spectastic and its test file scripts/test_spectastic.py MUST be removed from the repository, and spec 001-cli's <spec-status> MUST flip to superseded with a forward link to this spec. The 001-cli artifact is preserved as historical record; the contract moves here.

Non-functional

Init MUST complete in under 500 ms p95 on a modern laptop (Apple M-series or comparable) in an empty directory. The work is pure filesystem (no network); the threshold is generous to absorb npm-install warm-up latency.

The subcommand MUST NOT alter anything outside the destination directory. No global config, no home-directory dotfiles, no logs in /tmp. Failure to write does not leave debris in the parent path.

Init SHOULD work cross-platform on macOS, Linux, and Windows under Node 20 LTS+. Path separators, line endings, and file-mode bits handled per Node's standard APIs; no shell-out to cp/mkdir.

Out of scope (deferred to other slices)

  • npm-publish workflow for @spectastic/cli and @spectastic/schema. Landed via spec 004-npm-publish-workflow; first publish at v0.1.0-pre.3 on 16 Jun 2026.
  • Cross-tool installers (--target cursor|aider|claude|copilot|generic). Tier 2 work; this spec stays Claude-only to match parity with the Python implementation.
  • spectastic doctor diagnostics subcommand.
  • spectastic update mode that refreshes templates without touching authored content.
  • Auto-detect editor (Claude vs Cursor vs Aider). Users name their tool implicitly by which init flavor they invoke.
  • A backwards-compatible Python shim. The Python script's lifetime ends with this spec's apply; users on a clone older than this slice keep working from that clone.

4 · Data model

One shape: FileWriteDecision (collected first, executed second — Ctrl-C-safe).
FileWriteDecision
Fields: source (bundled path inside @spectastic/cli), destination (CWD-relative), action ("write" | "overwrite" | "skip"). First pass builds the array; second pass executes. Abort between passes → zero files written.

The two-pass design is the only non-obvious invariant. A write-as-you-go loop partially-inits on Ctrl-C; two passes prevent that. The plan names the prompt mechanism; the data model is fixed.

5 · Success criteria

Technology-agnostic, measurable outcomes.

Running spectastic init with no arguments and no profile in an empty temporary directory MUST write every file in the bundle's installable trees except unrequested extended verbs, each byte-identical (modulo trailing-newline normalisation) to its bundled source, and MUST NOT write any other file from the bundle.

Rationale

The property is unchanged: a scaffolded project is exactly what the package ships, with nothing missing and nothing extra.

What changed is the referent. This measured byte-identity against "what the Python scripts/spectastic init produces", and FR-010 requires that script be deleted at this spec's apply — so it has never been satisfiable as written. Comparison against the bundled source is the same guarantee against something present in every install context, including npx and a global install where no repository exists. Whether the bundle matches the repository is a build-time property and belongs to 004 FR-007, which regenerates it at the tagged commit.

It no longer claims to describe the whole tree, and that is the third correction to this clause today. Two earlier drafts said the tree contains "nothing the bundle does not designate" and then "exactly" a named set; both were refuted by real behaviour, because what init emits depends on the run. Zero-arg in a TTY prompts for a profile and writes principles.html, AGENTS.md and CLAUDE.md as content with no on-disk source, plus a profile marker; --tools adds a hook and a managed-adapter stamp; and the .gitignore block and spectastic.json are generated outside the write plan in every run.

So the criterion states what it can check and scopes itself to the run it describes: the bundle's material all arrives, correctly, and no bundled file arrives that should not. Exhaustiveness over the whole directory is abandoned deliberately rather than narrowed again — it is not a closed set, and three attempts to write it as one have each been falsified by a path nobody had opened.

Integration tests cover every branch of the conflict matrix: empty-dir clean init; existing-file prompt with y/N/a/s; --force in TTY; --force in non-TTY; non-TTY with conflict and without --force (exit 2); unrecoverable IO error (destination not writable; exit 1).

After this spec is applied: the repository contains no Python implementation of spectastic (scripts/spectastic and scripts/test_spectastic.py deleted); which spectastic on a clean install resolves to the Node CLI only; spec 001-cli's status pill reads "Superseded" and links forward to this spec.

6 · Assumptions

Three preconditions: Python parity baseline, bundling via package.json files, npm publish is a follow-up.

Held at authoring time: the Python script at scripts/spectastic (commit f6107e2) was the canonical reference for every observable behaviour — file set, prompt UX, exit codes, summary format. The script was deleted at this spec's apply, so this spec is now that reference and divergence from it is a bug. The original wording survived three proposals that each set out to remove it, which is why the file set it once governed drifted without anything noticing.

Bundling templates inside @spectastic/cli via package.json files is the cleanest distribution; import.meta.url resolution survives npx, global install, and workspace-symlinked dev install without code change.

npm publish ships in a follow-up slice (TBD-npm-publish; now 004). Until then users npm link from a clone as the Tier 1 ship does. Python retirement doesn't block on publish.
