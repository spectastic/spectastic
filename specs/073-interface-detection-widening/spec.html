Specification · 073-interface-detection-widening

Interface detection widening

Teach the enforcement gate the two things it cannot currently see — an interface that isn't HTTP, and a contract that isn't in one of four directories.

Status Accepted Spec ID 073-interface-detection-widening Owner Brian Corbin · @briancorbinxyz Reviewers — Created 31 Jul 2026 Principlesv1.9.0 Smallest demoablespectastic enforce on a Kafka-only service reports contract-first as a gap instead of silently exempt, and finds a Gradle project's contract at src/main/proto/. Read time

The contract-first gate has two blind spots that point in opposite directions. It cannot see an interface that isn't HTTP, GraphQL or gRPC — the signal list contains no message broker of any kind, so a service whose entire public surface is published topics is marked covered at verified and enterprise on the grounds that it has nothing to contract. And it cannot find a contract outside the project root or four named directories, one level deep — so a Gradle project keeping its protos where the protobuf plugin puts them (src/main/proto/) can be failed for lacking a contract it has. This spec widens both, and adds the thing that makes widening safe: dependency presence cannot distinguish publishing a topic from consuming one, nor a contract a project publishes from one it vendored to generate a client, so a contract path declared by the design outranks anything inferred from the filesystem. Both widenings amend requirements that currently record these misses as accepted ceilings, so they land as changes to 042 rather than as new behaviour bolted beside it. Advisory first, promoted once the signals prove themselves.

1 · Context

The contract-first enforcement category is interface-gated: it is a gap only when a project exposes a detectable public interface and has no checked-in contract. Both halves of that test are narrower than the sentence suggests.

The antecedent matches roughly forty dependency names across six ecosystems, and every one is an HTTP framework, a GraphQL server, or a gRPC toolchain. A service built entirely on Kafka, AMQP, NATS, SQS or Pub/Sub fails the antecedent and is marked covered — no warning, because the gate deliberately fails safe there so CLIs and batch jobs are never false-failed. The oddity is that the answer is already recognised: an asyncapi document has always counted as a valid contract. The tool can accept an answer to a question it cannot ask.

The other half is the mirror. Contract detection lists the project root and reaches one level into four conventional directories, without recursion — so it misses the layouts most build tools actually produce: the protobuf plugin's src/main/proto/, nested module trees, and directory names outside its four. A project can hold a perfectly good contract and be failed for it.

Both misses are recorded in 042 as accepted ceilings, which is why this arrives as an amendment rather than a patch. Whose problem: every event-driven project silently exempted from a floor it should meet, and every JVM project asked to rearrange itself to be seen.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · An event-driven service is asked for a contract P1

As a platform reviewer, I want a service whose public surface is broker topics to be held to the contract floor so that its consumers get a payload contract instead of an undocumented message shape.

Acceptance: A project declaring a broker client and no contract is reported as a contract-first gap; the same project with an asyncapi document is reported as covered.

US2 · A conventional layout is found where it lives P1

As a JVM engineer, I want my protos found at src/main/proto/ so that I am not asked to move them into a tool-shaped directory to satisfy a gate.

Acceptance: A Gradle or Maven project with contracts only under src/main/proto/ is reported as covered.

US3 · A consumer is not mistaken for a publisher P2

As an author of a service that only consumes events, I want the gate not to demand a contract I have no business publishing so that widening the antecedent does not trade one wrong answer for another.

Acceptance: A project whose design declares that it publishes nothing is not reported as a gap, even when a broker dependency is present.

Edge cases

  • A broker client pulled in transitively by a framework the project never uses directly.
  • A project with both an HTTP surface and published events, holding only one of the two contracts.
  • A vendored upstream contract checked in to generate a client — present, but not published by this project.
  • A monorepo where one module publishes events and its siblings do not.
  • An ecosystem with no conventional contract location at all.
  • A declaration that contradicts inference in both directions — claims a contract the filesystem lacks, or disclaims one it has.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The interface antecedent MUST recognise event-driven interfaces — message-broker and managed-bus dependencies — as exposing a public interface.

Rationale

Closes the case where an entire architectural style is exempt from a floor at every tier, including enterprise.

Contract detection MUST find contracts at ecosystem-conventional locations beyond the current root-plus-four shallow scan, by named convention rather than unbounded recursion.

Rationale

A tool that makes projects rearrange themselves to be detectable has inverted its charter. Naming the conventions keeps the cost bounded, which unbounded recursion would not.

Where a design declares an interface or a contract path, that declaration MUST take precedence over inference from dependencies or the filesystem — in both directions, establishing that a contract is owed and that one is not.

Rationale

Inference cannot distinguish publishing from consuming, nor a published contract from a vendored one. Only a declaration carries intent, and both false directions have been observed.

A newly-recognised event-driven interface MUST first be reported at advisory severity, and MUST NOT hard-fail a profile floor until the signal set has been promoted deliberately.

Rationale

A broker client is a weaker declaration of public surface than a web framework. Landing hard would produce exactly the false failures the existing ceiling was written to prevent.

The seeded contract-first principle's copy MUST name every format the detector accepts, including AsyncAPI, Protobuf and GraphQL SDL.

Rationale

A project reading its own constitution should be able to learn which artifacts satisfy the rule. Today the copy names three formats and the detector accepts six.

Detection SHOULD prefer signals that indicate producing over mere client presence where the ecosystem makes that distinguishable.

The residual false-negative — an interface exposed through a mechanism outside the signal set — SHOULD remain recorded as an honest ceiling rather than closed by widening into false failures.

Non-functional

Detection MUST remain shallow and bounded: it MUST complete in under 500 ms on a typical project, and MUST make at most 0 network calls.

Rationale

Preserves the existing detection budget that the widened path list trades against.

The widening MUST NOT change the verdict for any project that passes today: at most 0 currently-covered projects may become gaps through path detection alone.

Rationale

Finding contracts in more places can only add coverage. Any regression here would be a defect, not a trade.

Out of scope (deferred to other slices)

  • What a detected contract must then satisfy — style linting and breaking-change detection.
  • Payload compatibility over time, which detection cannot speak to.
  • Promoting the event-driven signals from advisory to the hard floor once field evidence supports it.

4 · Data model

No persisted entity. This spec widens two signal sets and adds one precedence rule over existing derived state.

Entities

Interface signal
A dependency pattern indicating a project exposes a public interface. Gains an event-driven class alongside the existing HTTP, GraphQL and RPC ones.
Contract location
A conventional path where a checked-in contract may be found. Gains ecosystem-specific entries beyond the current shallow set.
Interface declaration
Authored, not inferred — from 069. When present it decides the question that inference would otherwise guess at.

The precedence order is the load-bearing part: declaration, then inference, then the fail-safe exemption. Reversing the first two would make a design's stated intent unable to correct a wrong guess, which is the only reason the declaration exists.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

A broker-only fixture with no contract is reported as a contract-first gap; the same fixture with an AsyncAPI document is reported covered — across 100% of the ecosystems given broker signals.

Fixtures placing contracts at each newly-recognised conventional location are reported covered, and at most 0 previously-covered fixtures regress to a gap.

A fixture declaring that it publishes nothing is not reported as a gap despite a broker dependency, and a fixture whose declaration names a contract the filesystem lacks is reported as a gap despite a vendored file being present.

Whole-project detection stays under 500 ms on a repository of at least 50 modules after the path list widens.

6 · Assumptions

Declaring a broker client in a manifest correlates well enough with using it that the signal is worth acting on — advisory first precisely because this is an assumption rather than a certainty.

Conventional contract locations are stable enough per ecosystem to enumerate. Where a project is unconventional, its design's declaration is the intended escape hatch.

7 · Open questions

None outstanding — the symmetry framing, advisory-first landing, and declaration-over-inference precedence were settled by the two considerations surveys that produced this slice. Which specific broker packages constitute the signal set per ecosystem is an implementation detail for the design, not an undecided requirement.
