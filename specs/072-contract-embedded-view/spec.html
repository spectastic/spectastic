Specification · 072-contract-embedded-view

Contract embedded view

A reviewer sees the agreed shape without leaving the page — bounded, labelled as a projection, and never silently stale.

Status Accepted Spec ID 072-contract-embedded-view Owner Brian Corbin · @briancorbinxyz Reviewers — Created 31 Jul 2026 Principlesv1.9.0 Smallest demoableA design's contract section renders a height-bounded, scrollable excerpt of the declared contract, labelled with the file it projects. Read time

Once a design declares a contract, a reviewer still has to open another file to see what shape was agreed. This slice closes that gap — carefully, because the obvious version is a trap. The templates ship a deny-by-default content policy with no include mechanism, so an embedded contract cannot be fetched at view time; it can only be materialised at generate time, which makes it a copy, which makes it a drift problem rather than a rendering one. The tool has solved this shape before: the verify view materialises links and a validate rule flags it when they drift from the bundle. This spec clones that discipline. It adds a view that is visibly a projection of a named file, never a source; the design system's first height-bounded scrolling container, so a large schema cannot run the page; an excerpt rather than a full paste when the contract is large; and a staleness finding when the projection no longer matches what it projects. Reviewer convenience, deliberately built last — after the authoritative path is proven, so a copy never precedes the original.
I Independent
Depends on 069 for the declaration and 070 for the resolving path. Promotion is not a prerequisite — a view can project a proposed contract as readily as an effective one.
N Negotiable

1 · Context

A design that declares a contract path tells a reviewer where the shape is, not what it is. For the argument the design is making — why these boundaries, why this error envelope, what a consumer may rely on — the shape is usually the thing under discussion, and sending the reader to another file to find it is exactly the friction the single-file artifact format exists to remove.

Two facts make the naive fix wrong. The spec-family templates ship a deny-by-default content-security policy and the element vocabulary contains no include mechanism, so nothing can load a contract at view time; an embed is necessarily a copy written when the artifact is generated. And no bounded-scroll container exists in the design system today — code blocks scroll horizontally and are vertically unbounded, so a few hundred lines of schema pasted into a design would simply run the document and take the calm reading measure with it.

Both problems have precedent. The verify view already materialises derived content and is policed by a staleness rule when it drifts from its bundle; the same shape of guard applies here. Whose problem: the reviewer deciding whether an interface is right, and the author who would otherwise be tempted to keep the shape in the artifact where it renders nicely — the failure this slice is built to prevent.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · The shape is visible in the design P1

As a reviewer, I want to see the declared contract's shape inside the design doc so that I can judge the argument being made about it without opening another file.

Acceptance: Opening a generated design in a browser, the contract's content is visible within the contract section and is legible as code.

US2 · A stale projection is caught P1

As a reviewer, I want validate to flag a view that no longer matches the file it projects so that I am never shown an out-of-date shape as though it were current.

Acceptance: Editing the contract file without regenerating the design produces a finding naming the design and the contract; regenerating clears it.

US3 · A large contract does not run the page P2

As a reader, I want a large schema shown as a bounded excerpt so that the design stays readable instead of becoming a schema dump with prose at either end.

Acceptance: A contract far exceeding the container height renders within a fixed-height scrolling region; the page itself does not grow with the contract, and the file remains one link away.

Edge cases

  • A declared path that resolves to nothing — the view must degrade to the declaration alone, not render an empty box that reads as "the contract is empty".
  • A binary or non-text contract.
  • A contract that is legitimately empty.
  • A design whose contract has since been promoted, so the projected file moved.
  • Printing the design, where a scrolling container can hide content that a reader on paper cannot reach.
  • A very wide schema line — horizontal containment matters as much as vertical.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The design artifact MUST be able to render the content of a declared contract as a view materialised at generate time.

Rationale

The content policy forbids loading it at view time, so materialisation is the only mechanism available — and naming it as such is what makes the drift guarantee necessary rather than optional.

The view MUST be visibly labelled as a projection of a named file — the file whose content it shows — and MUST NOT read as the contract itself.

Rationale

An unlabelled copy invites editing. The label is what keeps the file authoritative in the reader's mind as well as in the tool's.

Added by this change. "A named file" was unambiguous while one file could be projected. Once a view can show the proposed copy, the label must follow the content — today it renders Projection of ${declaredPath}, the effective path, so a view of the sidecar would be labelled with a path whose bytes it does not hold.

The view MUST be height-bounded and scroll within its own container, containing both vertical and horizontal overflow so the page never scrolls horizontally because of it.

Rationale

Presence is not containment. The design system has no such container today, and an unbounded one would break the calm-density property every other artifact depends on.

spectastic validate MUST emit a finding when a rendered view no longer matches the contract file it projects, and MUST emit one when a view marked provisional no longer has a proposed contract behind it.

Rationale

A materialised copy that nothing polices is a second source of truth with extra steps. This clones the guard the verify view already carries.

Added by this change. The second clause exists because the first cannot see the case. Promotion copies the proposed bytes verbatim to the effective path, so after it runs the view's text matches its new source exactly and the drift check is silent — while the marker still says provisional, in a design whose contract is now in force. An earlier draft deferred re-materialisation on the grounds that "staleness is already checked"; it is not, for this, and a marker nothing can falsify is the quiet inaccuracy this proposal refuses elsewhere.

The view MUST NOT be a source of truth: no tool MUST read it as the contract, and editing it MUST NOT change the contract.

For a contract exceeding the container's capacity, the view SHOULD render an excerpt and SHOULD state that it is one, keeping the file one link away.

Where the declared contract cannot be read at either its effective or its proposed location — absent, unreadable, or not text — the view SHOULD be omitted rather than rendered empty, leaving the declaration visible on its own. A design MAY render a view per declaration rather than for every contract it declares.

Rationale

Scoped rather than reversed. A pending contract is the "absent" case as this requirement was written, and the implementation reads it that way — catch { continue; } // absent — omit the view — so FR-009 would have obliged a view exactly where this obliges omission, leaving a must-tier and a should-tier requirement giving opposite instructions with nothing recording which won.

That is the collision 070 FR-004's own rationale names in writing — "stating the carve-out in the requirement it carves out of is the difference between an amendment and a collision" — and an earlier draft of this proposal reproduced it one spec over, hours later, by amending only FR-004. Caught by the adversarial pass.

A design MAY render a view per declared contract, and MAY omit the view entirely while still declaring the contract.

Where a proposed contract exists for a declaration, its view MUST project the proposed copy, and MUST record that the copy it shows is provisional.

Rationale

The antecedent is "a proposed contract exists", not "the contract is pending promotion", and an earlier draft had the narrower one. 070 FR-008 defines pending as the effective path not resolving — so an amendment, where both copies are readable and a baseline is captured, is not pending. Under the narrow wording a reviewer reading a design that proposes a change to an existing interface would see the old contract, unmarked and indistinguishable from a settled one, while the shape actually under discussion sat unrendered in the sidecar. The view would have shown the new shape only when there was no prior contract to compare it against — the case where seeing it matters least.

The marker is not decoration. The rendered bytes are identical whichever copy they came from, so without it a provisional view and a promoted one cannot be told apart — the reasoning that puts "suggested — not yet run" on a captured run block rather than trusting a reader to check. FR-004's second clause is what stops the marker outliving the state it describes.

Rendering a proposed contract is not treating it as effective. It satisfies no enforcement category and no effective declaration; what it does is show a reviewer the thing they are being asked to approve.

Non-functional

The view MUST render with JavaScript disabled: 100% of the projected content readable with scripting off.

Rationale

P-4 — progressive enhancement, never dependence. A schema hidden behind a script is worse than no view.

The view MUST NOT introduce executable content or any runtime fetch: at most 0 scripts, event-handler attributes, or external requests are added to the artifact by this feature.

Rationale

P-11 — artifacts are data, not instructions. A contract is untrusted text from the generator's point of view and must be rendered inert.

Materialising a view SHOULD add under 100 ms to a design generation, for a contract up to 5000 lines.

Out of scope (deferred to other slices)

  • Rendering the difference between a proposed contract and the effective one it would replace.
  • Syntax highlighting or schema-aware rendering of the projected content.
  • Validating the contract itself — this slice renders it, it does not judge it.
  • A print stylesheet that unrolls the bounded container so paper readers lose nothing.

4 · Data model

No persisted entity. The view is derived content plus the state needed to tell whether it has gone stale.

Entities

Projection
Materialised content from a declared contract, together with the path it came from and whether it is complete or an excerpt.
Projection fingerprint
Whatever the staleness check compares — enough to tell that the source changed since the view was written, and stable across regenerations that changed nothing.

The invariant: a projection is always downstream of exactly one file, and is never consulted by anything that wants the contract. If any consumer ever reads the projection instead of the file, the boundary this slice depends on has been lost.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

A reviewer opening a generated design in a browser can read the declared contract's shape without opening another file, in 100% of designs that declare a readable contract.

Editing a projected contract without regenerating produces exactly 1 staleness finding; regenerating clears it to 0.

For a contract of at least 2000 lines, the rendered page's own height and horizontal scroll extent are unchanged from the same design with no view — containment verified by computed style, not by presence.

A design generated with a view adds at most 0 scripts and at most 0 external requests to the artifact, verified by a scripting-off render and a network trace.

6 · Assumptions

Reviewers want the shape more often than they want the whole file — so an excerpt is usually the right default and a full paste usually is not.

Contracts are text. A binary interface definition is a case for the declaration alone, not for a rendering strategy.

Regeneration is cheap and routine enough that a staleness finding is an actionable prompt rather than a chronic warning people learn to ignore.

None outstanding — materialise-not-transclude, bound-and-scroll, and clone-the-verify-guard were all settled by the survey that produced this slice.
