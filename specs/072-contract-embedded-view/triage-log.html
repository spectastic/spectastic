Cards

Contract view never materialises on the canonical design path

Design upstream

Debugging why a design that declares a contract carries no embedded view, root cause was that this spec's design wired materialisation into designCommand only — the CLI dispatch path — while 006 FR-009 makes the markdown procedure canonical and the kernel path merely alternate; fixed by naming both surfaces in the design and adding the step to the command; regeneration fails, because an implementer following §8's project structure would wire exactly one file again.

Expected
A design authored through /spectastic.design that declares <spec-contract path=…> gets a materialised <spec-contract-view>, the same as one produced by the kernel verb.
Actual
materialiseContractViews has exactly one caller — packages/core/src/commands/design.ts:102, inside designCommand. The slash command copies templates/design.html and drives the rest by interview, never shelling into the verb, and renderDesignHtml emits no <spec-contract> at all. So on the path designs are actually authored, the view is never written.
Diagnosis
§5 and §8 of this spec's design scoped FR-001's capability to designCommand, on the implicit assumption that is how designs get generated — an assumption 006 FR-009 already contradicts in writing. Neither FR-001's wording nor 006 FR-009 needs to change; the design simply never crossed to the surface that matters.
Fix
specs/072-contract-embedded-view/design.html §5 and §8 — name both authoring surfaces. commands/spectastic.design.md — add a materialisation step near step 8, mirroring how 069, 070, 076, 077, 093 and 094 each extended that same file, instructing the author to read the declared path and write the same <spec-contract-view lines=… [excerpt=…]> markup the kernel produces.
Fixed
Closed by 099's entry point rather than by a fix of its own. 099 needed exactly the same thing — an obligation that holds on the authoring path the kernel verb never reaches — so it built one materialise command and made it cover both views. Scoping that command to the visual view would have left this defect exactly as it was and required a second command with the same shape, which is the duplication a shared entry point exists to avoid. Verified on a project whose contract path resolves: one invocation writes both views and a second changes no bytes. The proposed fix — a step in the command markdown — was deliberately not taken: P-8 and T-009 both exclude command markdown as a place a guarantee may live, and this is a must-tier obligation.
Deep dive — why nothing ever reported this

The drift check fires on staleness, never on absence. contractViewDriftFindings skips any declaration whose view is undefined (packages/core/src/commands/validate.ts:955, "no view — nothing to check"), and that is correct rather than a bug: FR-008 makes rendering a view a MAY and omitting one while still declaring the contract legal. So this is a silently missing feature on the common path, not a permanent false finding — a materially better position to be in, and also the reason it went unnoticed.

Consequence for the sibling work. The visual embedded view lands on this same chassis. If it copies the wiring as-is it inherits this gap, and if it copies FR-008's absence-is-legal rule it inherits the reason nobody would notice. Both decisions have to be made deliberately there rather than by clone.
