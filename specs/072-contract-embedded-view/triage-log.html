Cards

Contract view never materialises on the canonical design path

Design upstream

Debugging why a design that declares a contract carries no embedded view, root cause was that this spec's design wired materialisation into designCommand only — the CLI dispatch path — while 006 FR-009 makes the markdown procedure canonical and the kernel path merely alternate; fixed by naming both surfaces in the design and adding the step to the command; regeneration fails, because an implementer following §8's project structure would wire exactly one file again.

Expected
A design authored through /spectastic.design that declares <spec-contract path=…> gets a materialised <spec-contract-view>, the same as one produced by the kernel verb.
Actual
materialiseContractViews has exactly one caller — packages/core/src/commands/design.ts:102, inside designCommand. The slash command copies templates/design.html and drives the rest by interview, never shelling into the verb, and renderDesignHtml emits no <spec-contract> at all. So on the path designs are actually authored, the view is never written.
Diagnosis
§5 and §8 of this spec's design scoped FR-001's capability to designCommand, on the implicit assumption that is how designs get generated — an assumption 006 FR-009 already contradicts in writing. Neither FR-001's wording nor 006 FR-009 needs to change; the design simply never crossed to the surface that matters.
Fix
specs/072-contract-embedded-view/design.html §5 and §8 — name both authoring surfaces. commands/spectastic.design.md — add a materialisation step near step 8, mirroring how 069, 070, 076, 077, 093 and 094 each extended that same file, instructing the author to read the declared path and write the same <spec-contract-view lines=… [excerpt=…]> markup the kernel produces.
Fixed
Cause found and both halves fixed. The card recorded the symptom — never materialised on the canonical path — and the cause was that the matcher is a regex over raw HTML while templates/design.html explains the element by naming it: <!-- One <spec-contract> per interface … -->. It matched the comment's literal tag, found no path=, and skipped — and the match then ran on to the real closing tag, so one bogus match consumed the genuine declaration. Both materialisers now match against a comment-masked copy and slice the original. The visual one had the same latent bug and escaped only because its comment happens not to spell the element out, which is a property of the prose rather than of the code.

Fixing it exposed a second, worse bug that had been unreachable behind the first: the view is spliced in with String.replace and a replacement string, which treats $&, $' and $` as substitution patterns. A contract is exactly where those occur — an OpenAPI schema carries regex patterns like '^[A-Z]{3}$' routinely — and that $' spliced the entire rest of the document into the view, taking a 493-line design to 2,390 and duplicating every decision. Silent corruption of the artifact, in the one code path whose whole job is to copy somebody else's text. Both call sites now pass a replacer function.

Fixed
Closed by 099's entry point rather than by a fix of its own. 099 needed exactly the same thing — an obligation that holds on the authoring path the kernel verb never reaches — so it built one materialise command and made it cover both views. Scoping that command to the visual view would have left this defect exactly as it was and required a second command with the same shape, which is the duplication a shared entry point exists to avoid. Verified on a project whose contract path resolves: one invocation writes both views and a second changes no bytes. The proposed fix — a step in the command markdown — was deliberately not taken: P-8 and T-009 both exclude command markdown as a place a guarantee may live, and this is a must-tier obligation.
Deep dive — why nothing ever reported this

The drift check fires on staleness, never on absence. contractViewDriftFindings skips any declaration whose view is undefined (packages/core/src/commands/validate.ts:955, "no view — nothing to check"), and that is correct rather than a bug: FR-008 makes rendering a view a MAY and omitting one while still declaring the contract legal. So this is a silently missing feature on the common path, not a permanent false finding — a materially better position to be in, and also the reason it went unnoticed.

Consequence for the sibling work. The visual embedded view lands on this same chassis. If it copies the wiring as-is it inherits this gap, and if it copies FR-008's absence-is-legal rule it inherits the reason nobody would notice. Both decisions have to be made deliberately there rather than by clone.

A contract view reports stale for a contract that is correctly pending

Cross-spec upstream

Debugging an error that appeared the moment a project was brought into conformance, root cause was that contract-view-stale asks whether the projected file can be read and 070 FR-008 now makes unreadable-at-the- effective-path a legal state; fixed by teaching the view check the pending state, or by projecting the proposed copy; regeneration fails, because the interaction between the two requirements is described nowhere.

Expected
A design whose contract is pending promotion validates clean. 070 FR-008 says a pending contract must not be reported as a finding.
Actual
the projected view of "contracts/rates.openapi.yaml" … no longer matches — the file could not be read. Reproduced by doing exactly what 070's drain prescribes: removing a pre-copied effective contract from ~/Code/example-currency-converter so the contract becomes pending. The pre-copy error cleared and this one replaced it, so the project cannot reach zero findings by either route.
Diagnosis
Both checks are right about their own concern. The view is a materialised copy and staleness is real when its source moves. But "the file could not be read" is now ambiguous — it meant the declaration is broken and it also means promotion has not run yet, and only the first is a defect. This is the same shape as 099/T-001, where drift fired for a view that had never existed: a check that asks "does this still match" without first asking "is this supposed to exist yet".
Fixed
17 Aug — applied as 2026-08-17-a-view-of-the-authoritative-copy, then built. The view projects the proposed copy where one exists, marked provisional="true" and labelled with the file whose bytes it holds; the stale check compares against that copy, and a marker with no proposed contract behind it is itself an error.

Keyed on "a proposed contract exists" rather than on 070's "pending promotion" — the adversarial pass caught that the narrower predicate excludes every amendment after the first, which would have shown a reviewer the old contract during exactly the review that matters.
Fix
Two candidates, and the choice is a real one rather than an implementation detail. Either contract-view-stale stands down while the contract is pending — minimal, mirrors 099/T-001's fix, and leaves a view on screen that projects a file no longer at the declared path. Or the view projects the proposed copy while pending, which keeps it truthful but sits close to 070 FR-003's rule that a proposed contract must not be treated as effective. Wants an interview, not a patch.
Deep dive — surfaced by a fix, which is the useful part

This did not exist before today. 070 FR-008 created the pending state a few hours ago, and this error is the first thing that state touched. A project that had been passing by holding two copies now fails a different check for holding one — so the drain that was meant to bring the exemplar into conformance moved it from one error to another.

Worth stating plainly: the pre-copy workaround this all began with was, in a narrow sense, load-bearing. It kept the view's source readable. Nobody knew that, including whoever wrote it — but it means removing it is not purely a cleanup, and the cleanup task in 070's drain is left unticked rather than marked done against a project that still reports an error.

A view is never removed when its source disappears, and the fix hint tells you to do it anyway

Implementation code

Debugging why a design could not clear contract-view-stale by regenerating, root cause was that materialiseContractViews strips an existing view only inside its success branch, so an unreadable source takes the continue and leaves the orphan untouched; fixed by stripping before the read rather than after it; regeneration passes — FR-007 already says a view should be omitted when the contract cannot be read, and the code omits writing one without removing what is there.

Expected
The fix hint on contract-view-stale reads "Regenerate the design to refresh or remove the stale projection." Regenerating a design whose contract has gone should therefore leave no view.
Actual
The view stays. packages/core/src/contracts/materialise-view.ts does catch { continue; } // absent — omit the view (FR-007) before ever reaching the strip, which lives further down beside the write. So "omit" means do not write a new one, never remove the old one, and the remove half of the hint is unimplemented — the tool asks for something it cannot do.
Diagnosis
Not a specification gap: FR-007 says plainly that a view should be omitted where the contract cannot be read, and an orphaned view is not an omitted one. The code satisfies the requirement for a design being materialised the first time and misses it for one that already carries a view — the case that only arises once a contract moves, which is exactly what 070 FR-008 has just made routine.
Fixed
17 Aug — an omit() helper, called on all five declining paths, not just the absent one the card described: no declared path, absent, a directory, unreadable, and binary content. Each had its own bare continue, and the card only named the one that had bitten.

It strips before deciding rather than after, so a declaration whose contract has gone is left bare — which is what FR-007 asked for all along. Uses a replacer function for the same reason the write path does: a contract's own text carries $& and $', which a replacement string would treat as substitution patterns.

Verified end to end against the real failure: a design carrying a view for a contract that no longer exists went from 2 findings to 1 on regenerating, with the view gone and the remaining finding correctly the missing contract itself. Five tests cover the paths plus idempotence.
Fix
packages/core/src/contracts/materialise-view.ts — strip an existing view before deciding whether a new one can be written, so an unreadable source leaves the declaration bare rather than carrying a projection of a file that is gone. Worth a test that regenerating twice over a vanished contract is idempotent, since the strip and the write would then be on separate paths.
Deep dive — found by an adversarial pass on a different question

Surfaced while reviewing the pending-view proposal, and independent of it: this bites whatever that proposal decides, because it is about removing a view rather than about which copy a view shows. Filed separately rather than folded in, so a decision about projection is not entangled with a defect about deletion.

It also explains something the 070 drain could not: the exemplar could not clear its finding by regenerating. The advice was sound and the mechanism behind it was missing.
