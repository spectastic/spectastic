A view of the authoritative copy

A view of the authoritative copy

The view reads one location. A contract now lives in two, one at a time.

Status Applied Change ID 2026-08-17-a-view-of-the-authoritative-copy Spec 072-contract-embedded-view Author Brian Corbin · @briancorbinxyz Created 17 Aug 2026 Source 072/T-002 Targets 4 requirements — 1 added, 3 modified Read time

070 FR-008 made an empty effective path a legal state a few hours ago. The view check reads that path and reports "the file could not be read" — so bringing a project into conformance with 070 makes it fail 072.

The view should project whichever copy is authoritative: the proposed contract while pending, the effective one once promoted. And it should say which, because the rendered bytes look identical either way.

1 · Intent

Reproduced by doing exactly what 070's drain prescribes. Removing a pre-copied effective contract cleared the pre-copy error and produced this one instead, so the project could not reach zero findings by either route.

The two checks are each right about their own concern, and the ambiguity is in one phrase. "The file could not be read" meant the declaration is broken; since FR-008 it also means promotion has not run yet, and only the first is a defect. That is the same shape as 099/T-001, where drift fired for a view that had never existed — a check asking "does this still match" without first asking "is this supposed to exist yet".

Standing the check down while pending was the smaller fix and is not taken. It leaves a materialised view on screen projecting a file that is not at the declared path, with nothing telling a reader it is provisional — which trades a false error for a quiet inaccuracy, and the artifact's whole claim is that what you read is what is there.

2 · Scope

In scope

  • Which copy the view projects while a contract is pending promotion.
  • Saying so in the view, since the rendered content is identical either way.

Out of scope

  • Re-materialising the view automatically when promotion runs. An earlier draft deferred this on the grounds that "staleness is already checked" — false, and the adversarial pass showed why: promotion copies the proposed bytes verbatim, so afterwards the view's text matches its new source and the drift check is silent while the marker still says provisional. That gap is now closed inside FR-004 rather than deferred, and what remains deferred is only the convenience of regenerating automatically. defer-to=071-contract-promotion.
  • The nested-project path limitation, which is why this repo's own exemplar reaches neither check. defer-to=TBD-nested-project-paths.

4 · Deltas

What changes — the label names the file actually projected. Nothing else: both existing obligations are carried word for word, and the live rationale verbatim below.

The view MUST be visibly labelled as a projection of a named file — the file whose content it shows — and MUST NOT read as the contract itself.

Rationale

An unlabelled copy invites editing. The label is what keeps the file authoritative in the reader's mind as well as in the tool's.

Added by this change. "A named file" was unambiguous while one file could be projected. Once a view can show the proposed copy, the label must follow the content — today it renders Projection of ${declaredPath}, the effective path, so a view of the sidecar would be labelled with a path whose bytes it does not hold.

What changes — the finding is keyed to the projected copy, and a provisional marker that outlived promotion is itself staleness. Nothing else: the existing obligation and its rationale are carried verbatim.

spectastic validate MUST emit a finding when a rendered view no longer matches the contract file it projects, and MUST emit one when a view marked provisional no longer has a proposed contract behind it.

Rationale

A materialised copy that nothing polices is a second source of truth with extra steps. This clones the guard the verify view already carries.

Added by this change. The second clause exists because the first cannot see the case. Promotion copies the proposed bytes verbatim to the effective path, so after it runs the view's text matches its new source exactly and the drift check is silent — while the marker still says provisional, in a design whose contract is now in force. An earlier draft deferred re-materialisation on the grounds that "staleness is already checked"; it is not, for this, and a marker nothing can falsify is the quiet inaccuracy this proposal refuses elsewhere.

What changes — omission is scoped to the case where neither copy is readable. Nothing else: the omit-rather-than-render-empty rule and the per-declaration opt-out are carried word for word.

Where the declared contract cannot be read at either its effective or its proposed location — absent, unreadable, or not text — the view SHOULD be omitted rather than rendered empty, leaving the declaration visible on its own. A design MAY render a view per declaration rather than for every contract it declares.

Rationale

Scoped rather than reversed. A pending contract is the "absent" case as this requirement was written, and the implementation reads it that way — catch { continue; } // absent — omit the view — so FR-009 would have obliged a view exactly where this obliges omission, leaving a must-tier and a should-tier requirement giving opposite instructions with nothing recording which won.

That is the collision 070 FR-004's own rationale names in writing — "stating the carve-out in the requirement it carves out of is the difference between an amendment and a collision" — and an earlier draft of this proposal reproduced it one spec over, hours later, by amending only FR-004. Caught by the adversarial pass.

What changes — a view shows the copy under discussion whenever there is one, and says that it is provisional. New requirement.

Where a proposed contract exists for a declaration, its view MUST project the proposed copy, and MUST record that the copy it shows is provisional.

Rationale

The antecedent is "a proposed contract exists", not "the contract is pending promotion", and an earlier draft had the narrower one. 070 FR-008 defines pending as the effective path not resolving — so an amendment, where both copies are readable and a baseline is captured, is not pending. Under the narrow wording a reviewer reading a design that proposes a change to an existing interface would see the old contract, unmarked and indistinguishable from a settled one, while the shape actually under discussion sat unrendered in the sidecar. The view would have shown the new shape only when there was no prior contract to compare it against — the case where seeing it matters least.

The marker is not decoration. The rendered bytes are identical whichever copy they came from, so without it a provisional view and a promoted one cannot be told apart — the reasoning that puts "suggested — not yet run" on a captured run block rather than trusting a reader to check. FR-004's second clause is what stops the marker outliving the state it describes.

Rendering a proposed contract is not treating it as effective. It satisfies no enforcement category and no effective declaration; what it does is show a reviewer the thing they are being asked to approve.

5 · Risk register

"Pending promotion" excluded every amendment after the first, so the view would show the old contract during exactly the review it exists for

070 FR-008 defines pending as the effective path not resolving. An amendment — both copies readable, baseline captured — resolves, so it is not pending, and 070 FR-009's own rationale calls that "the ordinary state of every contract amendment after the first". Under the narrow wording a reviewer reading a design that proposes changing an existing interface would see the old contract, unmarked, while the shape under discussion sat unrendered in the sidecar. The view would have shown the new shape only where there was no prior contract to compare against.

Decisive; the antecedent is now "a proposed contract exists". I borrowed a term from an adjacent spec without restating it and inherited a boundary drawn for a different purpose — FR-008 defines pending to decide what validate reports, not what a view shows. The two questions have different right answers and I used one predicate for both.

A must-tier addition reversed a should-tier requirement in its own home case, and the proposal amended only FR-004

Live FR-007 says a contract that cannot be read — absent among them — SHOULD have its view omitted, and materialise-view.ts implements exactly that: catch { continue; } // absent — omit the view (FR-007). A pending contract is that case verbatim, so FR-009 obliged a view precisely where FR-007 obliges omission, leaving a MUST and a SHOULD in one spec giving opposite instructions with nothing recording which won. FR-002 was the second casualty: its label renders Projection of ${declaredPath}, so a view of the sidecar would carry a path whose bytes it does not hold.

Both now amended. FR-007 is scoped to "neither location readable" rather than reversed; FR-002's label follows the content.

Worth stating without softening: this is the exact failure 070 FR-004's rationale names in writing — "stating the carve-out in the requirement it carves out of is the difference between an amendment and a collision" — which I wrote this morning, after a critic caught me doing it, and then reproduced one spec over within hours. Knowing the failure was not enough to avoid it; the pass was.

The deferral's justification was false, and nothing could detect a provisional marker outliving promotion

It deferred re-materialisation because "staleness is already checked". The drift check compares text only, and promotion copies the proposed bytes verbatim — so after promotion the view matches its new source exactly, the check is silent, and the mandatory marker still says provisional in a design whose contract is now in force. A second requirement in the same proposal that no check could see.

Closed inside FR-004 rather than deferred. A view marked provisional with no proposed contract behind it is now itself a finding — which is checkable, unlike the text comparison, because the marker and the sidecar's existence are independent facts. What stays deferred is only the convenience of regenerating automatically.

An interpretation of an upstream must-tier requirement was stamped verified, with two must-tier deltas resting on it

KB-0001@2026-07-25 defines verified as a source opened this turn and forbids a must-tier decision resting on an assumed fact without an accepted risk. The row claimed 070 FR-003 "forbids two named things" — but it opens with a general prohibition against any consumer treating a proposed contract as effective, with the clauses as instances. More decisively it never cited FR-008's second clause, which is directly on point: a pending contract must not satisfy any check requiring an effective contract.

Accepted rather than argued away, and the row restated as assumed. The reading is that a view is a rendering rather than a consumer, and that contract-view-stale checks a projection rather than the presence of an effective contract. I still think it is right; it is an interpretation of somebody else's must-tier requirement and it was wearing a stamp that claims otherwise. If the reading is wrong the remedy is a delta on 070 saying so explicitly, not a quieter word here.
