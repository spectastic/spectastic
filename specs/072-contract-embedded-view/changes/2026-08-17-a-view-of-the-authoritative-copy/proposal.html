A view of the authoritative copy

A view of the authoritative copy

The view reads one location. A contract now lives in two, one at a time.

Status Proposed Change ID 2026-08-17-a-view-of-the-authoritative-copy Spec 072-contract-embedded-view Author Brian Corbin · @briancorbinxyz Created 17 Aug 2026 Source 072/T-002 Targets 2 requirements — 1 added, 1 modified Read time

070 FR-008 made an empty effective path a legal state a few hours ago. The view check reads that path and reports "the file could not be read" — so bringing a project into conformance with 070 makes it fail 072.

The view should project whichever copy is authoritative: the proposed contract while pending, the effective one once promoted. And it should say which, because the rendered bytes look identical either way.

1 · Intent

Reproduced by doing exactly what 070's drain prescribes. Removing a pre-copied effective contract cleared the pre-copy error and produced this one instead, so the project could not reach zero findings by either route.

The two checks are each right about their own concern, and the ambiguity is in one phrase. "The file could not be read" meant the declaration is broken; since FR-008 it also means promotion has not run yet, and only the first is a defect. That is the same shape as 099/T-001, where drift fired for a view that had never existed — a check asking "does this still match" without first asking "is this supposed to exist yet".

Standing the check down while pending was the smaller fix and is not taken. It leaves a materialised view on screen projecting a file that is not at the declared path, with nothing telling a reader it is provisional — which trades a false error for a quiet inaccuracy, and the artifact's whole claim is that what you read is what is there.

2 · Scope

In scope

  • Which copy the view projects while a contract is pending promotion.
  • Saying so in the view, since the rendered content is identical either way.

Out of scope

  • Re-materialising the view automatically when promotion runs. The view is generated and its staleness is already checked, so the existing mechanism reports it. defer-to=071-contract-promotion.
  • The nested-project path limitation, which is why this repo's own exemplar reaches neither check. defer-to=TBD-nested-project-paths.

4 · Deltas

What changes — the finding is keyed to the copy the view actually projects rather than to the effective path. Nothing else: the obligation to report a view that no longer matches is carried word for word, and the live rationale is carried verbatim below with the addition marked.

spectastic validate MUST emit a finding when a rendered view no longer matches the contract file it projects — the proposed contract while the contract is pending promotion, and the effective contract otherwise.

Rationale

A materialised copy that nothing polices is a second source of truth with extra steps. This clones the guard the verify view already carries.

Added by this change. The clause names which file "it projects" resolves to, because since 070 FR-008 that is two files at two points in a contract's life. Without it the check reads an effective path that is legitimately empty and reports a view as stale for the one reason that is not the view's fault.

What changes — a view of a pending contract projects the proposed copy and says so. New requirement.

While a contract is pending promotion, its view MUST project the proposed contract, and MUST record that the copy it shows is provisional.

Rationale

The alternative considered and rejected was to suppress the staleness check while pending. It is smaller and it mirrors 099/T-001's fix exactly, but it leaves a view rendering a file that is not at the declared path with nothing saying so — trading a false error for a quiet inaccuracy, in an artifact whose entire claim is that what you read is what is there.

The second clause is not decoration. The rendered bytes are identical whichever copy they came from, so without a marker a provisional view and a promoted one are indistinguishable at a glance — the same reasoning that puts "suggested — not yet run" on a captured run block rather than trusting a reader to check.

It also keeps 070 FR-003 honest in substance rather than on a technicality. Rendering a proposed contract is not treating it as effective, and the marker is what makes that visible instead of asking the reader to take it on trust.
