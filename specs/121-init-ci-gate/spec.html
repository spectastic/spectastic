Init CI gate

spectastic init --tools installs a marker-managed, drift-guarded CI gate — GitHub Actions and GitLab CI — that runs validate, enforce and the merge verdict on every pull request.

Read time

The guarantee layer exists as binaries — validate, enforce, verdict — but nothing installs it into a downstream project's CI; the hook runs locally and the docs recipes are hand-written, validate-only and advisory. This spec makes the CI gate a third half of init --tools: a file spectastic owns, pinned to the installing CLI's version, that validate reports as drifted the moment it stops matching. A downstream maintainer gets a blocking merge verdict on their first pull request without writing a workflow.

1 · Context

An audit of what init writes found nothing CI-shaped. --tools installs a pre-commit hook running validate and drift-proof command adapters; the merge verdict (115) was designed for CI — exit 1 on a violation, a JSON artifact "so CI can archive it" — yet its only caller is the CLI command, and 115 deferred the wiring to "the proving example". Three specs record the gap: 031's CI-recipe half of TBD-validate-strict, 115's TBD-guardrail-verdict-ci, and 042's unslugged CI-file item.

So a downstream project relies on a human — or an agent reading the advisory line in AGENTS.md — hand-writing the workflow: the shape the .claude/commands footgun had before 031. The guarantee exists; its installation is manual; and P-8 says a guarantee that lives in prose is a nudge. This spec is for the downstream maintainer who runs init --tools and the reviewer on their pull request.

The GitLab recipe ships allow_failure: true and the GitHub one filters to specs/** — a project that copied them still sees no verdict on a code change.

2 · User scenarios & testing

Each story is independently testable; US1 alone is a viable MVP.

US1 · Install the gate P1

As a downstream maintainer, I want to run init --tools and get a CI gate so that validate, enforce and the merge verdict run on every pull request without me writing a workflow.

Acceptance: on a project with .github/, init --tools writes one managed workflow; its steps against a pull request carrying a decision violation fail on the verdict step with a SARIF file produced; a clean request passes; a re-run reports the file unchanged.

US3 · Drift on upgrade P1

As a maintainer upgrading spectastic, I want validate to report the gate file as drifted so that CI never silently runs a different version than my hook.

Acceptance: a managed file hand-edited or rendered by an older CLI yields an error finding naming the file and the regenerate command; init --tools --ci-only clears it; no managed file, no finding.

US2 · Results on the pull request P2

As a reviewer on a downstream pull request, I want every gate result surfaced even when an earlier step failed so that a misplaced write is caught at merge time, not after.

Acceptance: with validate failing, enforce and verdict still run; findings reach code scanning as SARIF; the verdict artifact is retained.

US4 · GitLab parity P2

As a GitLab user, I want the same gate without spectastic editing my .gitlab-ci.yml so that my pipeline stays mine.

Acceptance: the gate lands under .gitlab/; an existing root file is byte-identical after install; the include snippet is printed with its presence reported; with no root file, a minimal bootstrap one is created.

Edge cases

  • Pre-release or unpublished CLI version: pinned anyway — CI fails honestly until published, and the summary says so.
  • A fresh verified project fails its first enforce step — the floor working as designed; the summary says so.
  • Both hosts detected: both installed; --uninstall removes both managed files and nothing else.
  • Changed paths containing whitespace are unsupported by the verdict step — a recorded ceiling.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

init --tools MUST install a CI gate as a third half beside the pre-commit gate and the command adapters — --ci-only selects it alone, --hooks-only / --commands-only exclude it — under 031's contract: idempotent, a per-file outcome of created, updated or unchanged, and --uninstall removing managed files only.

--ci github | gitlab | both MUST choose the host; absent, the host MUST be detected from .github/ or .gitlab-ci.yml / .gitlab/; with nothing detected a terminal MUST prompt, a headless run MUST skip with a note, and a headless --ci-only that would install nothing MUST exit with an error.

The rendered gate MUST run validate (findings as SARIF to code scanning or the SAST report), enforce, and verdict; the job MUST fail when any of the three exits non-zero; each step MUST run regardless of an earlier step's failure; and the gate MUST NOT soften any verb's exit semantics.

Rationale

The verbs already say what "fail" means; a CI-side allow_failure would be a second opinion their specs deliberately do not offer.

The gate MUST run on pull/merge request events and pushes to the default branch; the verdict step MUST run on pull/merge requests only, over the merge-base-to-head change set with full history, MUST pass on an empty change set, and its JSON artifact MUST be retained.

Every CLI invocation in a managed gate file MUST be pinned to the exact version of the CLI that installed it; the install summary MUST warn when that version carries a pre-release tag; the gate MUST NOT fall back to a floating version.

Rationale

Lockstep: CI runs exactly what the hook runs. Only a dev-from-source maintainer meets an unpublished pin; a red run until publication is the honest outcome.

A managed gate file MUST carry a marker on its first line; a file at a managed path without the marker MUST NOT be overwritten or removed unless --force, and the refusal MUST name the path.

On GitLab the gate MUST be a separate owned file under .gitlab/; an existing .gitlab-ci.yml MUST NOT be edited; the include snippet MUST be printed with its presence reported; absent a root file, a minimal bootstrap one holding only the include MUST be created.

The bootstrap root file MUST NOT be drift-checked; --uninstall MUST remove it only while it is byte-identical to what was written; and validate MUST report when a managed GitLab gate is no longer included from the root file.

Rationale

The root file will grow the user's own jobs; owning it then would make spectastic the pipeline. The one thing worth checking is that the gate is still reachable.

validate MUST report an error-severity finding when a managed gate file diverges from what the running CLI renders — including its version pin — naming the file and the regenerate command; it MUST report nothing when no managed gate file exists.

The interactive offer at plain init SHOULD install all three halves, with the CI host detected or prompted as in FR-002.

The recipes under docs/ci-examples/ SHOULD be the same renderer's output in an example mode — unpinned, unmarked, with a copy-or-run header — and a test SHOULD hold them byte-equal to it.

Non-functional

Rendering MUST be deterministic and well-formed: repeated renders of one host and version differ by at most 0 bytes, 100% of rendered files parse as YAML, and each of the 3 CLI steps carries the version pin.

Rendered gate content, install messages and option help MUST carry at most 0 internal artifact ids.

init --help cold start MUST stay within the existing 150 ms bench budget, the renderer adding 0 runtime dependencies.

Out of scope (deferred)

  • A validate --strict flag — this spec lands the CI-recipe half of that slug; the flag stays deferred.
  • Bitbucket, Azure Pipelines, CircleCI and other hosts.
  • A packaged GitHub Action or GitLab CI component in place of an npx step.
  • A decision-coverage step — the coverage report has no failing exit contract yet.
  • Passing the project's own enforcer output to the verdict step — a commented example line at most; no configuration key.
  • Running this gate on spectastic's own repository.
  • Editing an existing .gitlab-ci.yml — a user-owned file stays user-owned.

4 · Data model

One new kind of thing — a managed gate file — and one courtesy artefact beside it.

Entities

Managed gate file
A CI file spectastic owns at a fixed per-host path. Its content is a pure function of host and installing CLI version; line 1 is the marker; at most 1 per host per project.
Bootstrap root file
A GitLab root pipeline file created only because none existed. Marked but not managed thereafter: it may grow, is never drift-checked, and is removable only while identical to what was written.
Host selection
github, gitlab, both, or detect. Detection reads presence only, never the user's files.
Install outcome
Per managed file: created, updated, unchanged, or refused — a refusal names the path.

Transitions: absent → created → unchanged | updated → removed. An unmanaged file at a managed path has no transition unless forced. Drift is a relation to the running CLI, not a stored flag.

5 · Success criteria

A downstream maintainer who runs init --tools on a project with a .github/ directory has a pull request carrying a decision violation blocked, with no hand-written workflow — 3 of 3 gate steps execute and the violating request fails (target: and a clean request passes), from 0 steps today (no gate is installed).

Observed at

The rendered steps run against a scratch project — committed base, a branch adding a scoped decision plus a violating file, the built CLI standing in for the pinned package: verdict exits 1 listing 1 violation; the SARIF file exists; a clean branch exits 0.

Falsified by

Any step absent from the run, or a violating request that passes.

A maintainer who upgrades the CLI is stopped at their next commit by a finding naming the gate file — 100% of managed gate files that no longer match the running CLI are reported (target 100%), and 0 unmanaged files are ever reported, from no established baseline.

Observed at

The CLI integration test: a hand-edited managed file makes validate exit 1 with the drift rule; regeneration clears it; no managed file, no finding.

Falsified by

A managed file that differs from the render and passes validate, or a finding on a file without the marker.

A GitLab user's existing root pipeline file is untouched by the install — 0 bytes changed (target 0, with the include snippet printed alongside its reported presence), from no established baseline.

Observed at

The installer test: a pre-existing .gitlab-ci.yml is byte-identical after install; the summary carries the snippet and the state.

Falsified by

Any byte changed in a pre-existing root file.

A reader who copies a recipe from docs/ci-examples/ gets what init --tools writes, less the pin plus the marker — 2 of 2 recipes byte-equal to the renderer (target 2 of 2), from 0 of 2 today (hand-written, validate-only).

Observed at

The renderer's docs equality test.

Falsified by

Either recipe differing from the example-mode render.

A maintainer on a project with neither host present is never left with a silent no-op — 3 of 3 fallback paths behave as stated: a terminal asks which host, a headless run explains the skip, a headless request for the gate alone is refused (target 3 of 3), from no established baseline.

Observed at

The CLI integration test in an empty repository: headless --tools exits 0 with the note; headless --ci-only exits 2; the prompt is exercised under a pseudo-terminal.

Falsified by

A headless --ci-only that exits 0 having written nothing, or a plain --tools that omits the note.

A maintainer of spectastic can trust the renderer without reading its output — 4 of 4 properties hold in the suite: identical bytes across two renders, YAML parse with the pin on every step, 0 internal ids on any user surface, init --help inside its cold-start budget (target 4 of 4), from no established baseline.

Observed at

The renderer unit tests plus the existing cold-start bench.

Falsified by

Any of the four assertions failing, or the bench exceeding 150 ms.

6 · Assumptions

--tools output is not scaffold, so 003's list of what init writes and 004's scaffold count are untouched — the planner counts bundle entries only.

A downstream CI runner can reach the npm registry; the gate does not vendor the CLI.

The three upstream deferrals are redirected by change proposals applied after this spec lands, so no accepted spec claims a landing before it is real.
