Design · 121-init-ci-gate

Init CI gate

How we will build it.

Status Accepted Spec 121-init-ci-gate Owner Brian Corbin · @briancorbinxyz Branch main Created 16 Sep 2026 Read time

A pure, dependency-free renderer in @spectastic/core turns (host, CLI version) into a CI file; a CLI-local installer beside hook.ts and adapters.ts writes it as a third --tools half; and validate re-renders with the running CLI and reports any difference as drift. Every piece clones a seam that already exists. The biggest risk is the one no local test can retire: the rendered steps are proven by executing them by hand, not on a live GitHub or GitLab runner.

5 · Approach

Three new modules, each cloning a neighbour. Renderer — packages/core/src/ci/render.ts, a pure renderCiWorkflow(host, {cliVersion, mode}) built by joining a string array exactly as buildHookScript does: no YAML library, no I/O, so it can sit on the init cold path and be called by the docs script, the drift scan and the tests alike. It owns the marker, the file paths, the artifact globs (re-exported to hook.ts so both gates validate one list), the Node major and the action pins. Installer — packages/cli/src/commands/init/ci.ts, beside hook.ts and adapters.ts: host detection, the refuse-unless-forced write, the GitLab bootstrap root file, the include-state probe, and DriftPair production. tools.ts gains a third half (ci, ciHost, cliVersion; kinds install-ci/remove-ci) and init.ts the two options, the routing, and the host prompt when nothing is detected. Drift — a ciGateDriftFinding in core next to commandsDriftFinding, and a scanCiDrift in the CLI's validate folded beside scanSkillsDrift.

The workflow itself: checkout with full history → setup Node 22 → validate --format sarif (upload, run-regardless) → enforce (run-regardless) → on pull requests only, verdict --changed over the merge-base diff with an empty-diff guard, then upload the verdict artifact. GitLab mirrors it as one .pre-stage job whose script accumulates a failure flag across the three commands and exits with it, with reports: sarif and the verdict as artifacts.

The obvious shortcut — build the YAML as an object and stringify it — was rejected for the cold-start budget alone. The template is small enough that a string array is also easier to diff by eye.

Scored 1–5. The fenced splice scores on first-run convenience only; a YAML fence collides with the user's stages: and job names and cannot be spliced safely without a YAML-aware merge (the .gitignore writer gets away with it because that file is line-oriented). The bootstrap variant keeps every "never edit" property while giving a fresh GitLab project a working pipeline.

7 · Decisions

D-001 · Pure renderer in core; installer CLI-local

Status
Accepted
Context
Three callers need the rendered bytes — the installer, the drift scan, the docs script — and only the installer needs the filesystem or a prompt (tools.ts:24-49; validate.ts:110-138). P-14 asks the same question and answers it the same way; core's subpath-export shape is package.json:36-39.
Decision drivers
second-caller test · cold-start budget · the 041–043 drift scar
Considered options
  • Core renderer + CLI-local installer — chosen — + one pure function, three callers; fs/prompt scaffolding stays where hook.ts lives. − two packages touched.
  • Everything in core — + Workflow-reusable installer. − drags fs/prompt orchestration only init calls into the kernel.
  • Everything CLI-local — + one package. − docs script and drift scan import from the CLI, the drift 041–043 paid for.
Decision
packages/core/src/ci/render.ts exporting renderCiWorkflow, the marker, paths, globs and pins; packages/cli/src/commands/init/ci.ts for detection, writes, bootstrap and drift pairs; a new ./ci/render subpath export.
Consequences
+ the renderer is testable without a binary and reachable from a script. − hook.ts now imports its globs from core (a one-line re-export keeping its tests intact).

D-002 · Drift compares against the running CLI's render, version pin included

Status
Accepted
Context
The adapter drift check is "render(source) ≠ on-disk" (adapters.ts:17-21) and the CLI's version is a runtime read (index.ts:41-48). The interview chose lockstep — CI runs exactly what the hook runs — over treating the on-disk pin as user data.
Decision
scanCiDrift renders with cliVersion() and compares bytes; any managed file whose pin (or anything else) differs is an error-severity ci-gate-drift finding with the regenerate command as fix hint. A pre-release running version warns at install (FR-005) but drifts like any other.
Consequences
+ upgrading the CLI cannot leave CI on an older version silently; the pre-commit hook says "regenerate". − every CLI upgrade costs one init --tools --ci-only and a commit; a dev-from-source maintainer sees a pin that may not be published yet (accepted in the spec's edge cases).

D-003 · GitLab: owned sidecar, bootstrap root file, never a splice

Status
Accepted
Context
The only fenced-block precedent is line-oriented (gitignore/apply.ts:16-26); YAML is not. GitLab's include: local takes a root-relative path with a leading slash and .pre is usable without a stages: entry (spike row). The interview asked for a bootstrap root file when none exists.
Decision
Write .gitlab/ci/spectastic.yml (managed) with the job at stage: .pre; print include: - local: /.gitlab/ci/spectastic.yml and report whether the root file already contains that path; when no .gitlab-ci.yml exists, write one holding only the marker and the include. The root file is never drift-checked and is removed on uninstall only while byte-equal to its render; validate reports a managed sidecar the root file no longer includes.
Consequences
+ the user's pipeline stays theirs; a fresh project pipelines on first push. − a user who deletes the include silently disables the gate until validate runs — the check exists for exactly that.

D-004 · Workflow shape: run-regardless steps, PR-only verdict, SARIF via the host's SARIF channel

Status
Accepted
Context
Merge-base diffing needs full history (ci.yml:242-261); verdict --changed is variadic and needs ≥ 1 path (verdict.ts:21); GitHub's docs recommend !cancelled() over always(); GitLab ingests SARIF only through reports: sarif, not sast (both spike rows).
Decision
GitHub: on: pull_request (no paths filter) + push: branches: [main, master]; permissions: contents: read, security-events: write; every gate step if: ${{ !cancelled() }}, the verdict steps additionally && github.event_name == 'pull_request'; base ref via env: BASE_REF; an empty diff prints and exits 0; the verdict JSON uploaded with if-no-files-found: ignore; a commented --enforcer-output example line. GitLab: image: node:22 (the Debian default tag, which carries git — spike row), stage: .pre, GIT_DEPTH: "0", rules for merge-request events and the default branch, one script accumulating FAILED across the three commands, artifacts: when: always, reports: sarif:, paths: [spectastic.sarif, .spectastic/verdict.json].
Consequences
+ a reviewer sees all three results on one run; the SARIF lands where each host renders it. − paths containing whitespace are unsupported in the verdict step (recorded ceiling); the Debian image is larger than alpine.

D-005 · Pins are renderer constants matching this repo's CI, test-guarded, not configurable

Status
Accepted
Context
This repo runs checkout@v7, setup-node@v7, upload-sarif@v4, upload-artifact@v4 on Node 22 (ci.yml:16, 32, 127, 228); engines.node is >=20. The interview chose 22 and rejected a config key.
Decision
CI_NODE_VERSION = '22' and an ACTION_PINS map live in the renderer. Two tests hold them honest: the Node major satisfies engines.node, and each pin equals the major .github/workflows/ci.yml uses — so a bump here forces the renderer forward and downstream files drift on the next release. Stated fixity: these are not overridable, and the help text does not pretend otherwise.
Consequences
+ one place to bump; no undiscoverable default. − a downstream project cannot pin an older action major without leaving management.

D-006 · Proof by executing the rendered steps, not by a live runner

Status
Accepted
Context
act is not installed (spike row) and a live GitHub/GitLab run needs a throwaway remote. SC-001 is about the steps' behaviour, which the shell commands carry; the YAML wrapper is proven by parsing plus the pin/permission assertions.
Decision
The real-CI proof runs the rendered commands by hand in a scratch project (init, commit a base, branch with a scoped decision and a violating file, run validate/enforce/verdict exactly as rendered with the built CLI standing in for the pinned package) and records exit codes in verify.html. A live push to a throwaway repository is optional and, if skipped, is recorded as the P-8 ceiling.
Consequences
+ SC-001 is grounded in a real run, not a structural check. − the npx fetch and the hosts' SARIF ingestion are exercised only by a live run; both are named in Risks.

D-007 · TDD, tests-first per story

Status
Accepted
Context
A preference, anchored in the interview; the same discipline 083–085 and 099–105 drained under.
Decision
Renderer tests red before the renderer, installer tests red before ci.ts, drift tests red before the scan, the built-binary integration test last.
Consequences
+ every module lands with its test. − slower first phase.

10 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here.

A separate version.ts rather than reading program.version() everywhere: the validate drift scan runs in helper functions with no program in reach, and the docs script has no commander at all. One 8-line module beats threading the value through three call sites.

An example render mode exists only to keep docs/ci-examples/ honest (FR-012). It is one boolean branch in the renderer — no marker, @latest, a copy-or-run header — and its byte-equality test is what makes the docs a derived artifact rather than a third copy.
