Visual variant grid

One feature with four presentations is one decision — plus a baseline for every clock the project does not own.

Status Accepted Spec ID 096-visual-variant-grid Owner Brian Corbin · @briancorbinxyz Reviewers — Created 12 Aug 2026 Principlesv1.9.0 Smallest demoableA project declaring a light and a dark context, with one platform declined and the reason visible. Read time

A product that ships on several platforms in two modes at two size classes does not have many designs; it has one design with a grid over it. This declares that grid — named axes, named contexts, an explicit resolution order — and it carries two rules that stop the grid becoming busywork or fiction. A context the feature deliberately does not support is declined with a reason, so the grid records a decision where it would otherwise record an absence and nobody re-litigates it in six months. And every axis whose contexts are set by somebody else — the operating system, a component library — carries a declared baseline: what it was designed against, and what it was last verified against. That second rule is what lets a measured difference be attributed to a dependency that moved rather than blamed on the implementation or the design. The shape is borrowed from a draft specification module and the file format deliberately is not, so a divergence costs a serialisation change rather than a redesign.

1 · Context

Light and dark, compact and regular, phone and tablet and desktop and television — these are the same problem at different sizes. Each is a context that selects a different resolution of one design. Without a grid they become separate documents that agree by hand, which is as many chances to disagree as there are documents.

Platform is not merely another theme, and modelling it as one would be dishonest: a television has a focus engine and no pointer, a desktop has a menu bar. The axis has to be able to select structure and interaction, not only values. And every platform sits on a release schedule the project does not control.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · One decision, not four documents P1

As an author of a feature shipping on several platforms, I want to declare the axes it varies across once so that a reviewer reads one decision instead of comparing four documents.

Acceptance: A feature supporting three platforms in two modes declares two axes with their contexts and a resolution order, and the combinations it addresses are countable from that declaration.

US2 · A decline reads differently from an omission P1

As a reviewer, I want a context the team decided against to look different from one nobody considered so that I can tell a judgment from a gap.

Acceptance: A declined context carries a reason and renders distinguishably; a context absent from the declaration renders as neither supported nor declined.

US3 · A restyle is attributable P2

As an implementer, I want each platform context to record what it was designed and last verified against so that a difference caused by an operating-system release is not reported as my bug.

Acceptance: A platform context declares both baselines; one never verified records that explicitly rather than omitting the field.

Edge cases

  • A combination considered and found identical to another. Silence would mean two things, so it must be recordable as considered.
  • An axis only one feature uses. Permitted — the grid is not a fixed set.
  • A platform whose baseline has never been verified. The gap must be visible rather than absent.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The grid MUST declare named axes, the named contexts of each, which context is the default, and an explicit order in which axes resolve.

An axis MUST be able to select structure and interaction and not only values, so that a platform difference in input model is expressible.

Rationale

A focus-driven remote and a pointer are different interaction models. An axis restricted to values could describe the colours of a television interface and nothing about how it is operated.

A context the feature deliberately does not support MUST be declarable as declined with a reason, and a declined context MUST render distinguishably from an absent one.

Every axis whose contexts are determined outside the project MUST carry a baseline per context, recording what it was designed against and what it was last verified against.

Rationale

A platform can restyle every application on it in one release and keep adjusting through a beta cycle; a major version of an external component library is the same event at another altitude. Neither is caused by anything in the project.

A baseline that has never been verified MUST be recorded explicitly rather than omitted, so that the gap is visible instead of absent.

A combination considered and found not to differ MUST be recordable as such, so that the absence of an entry never means both "identical" and "not thought about".

Rationale

The grid is combinatorial and most cells are uninteresting. Without this, either every cell must be authored — which manufactures busywork at the rate the observables trace did — or silence carries two meanings.

The declaration MUST borrow only the conceptual shape of the design-token resolver draft — axes, contexts, resolution order — and MUST NOT depend on its file format while that module carries an instruction not to implement it.

The grid SHOULD be project-scoped, with a feature declaring which of the project's contexts it addresses rather than inventing its own set.

Rationale

Modes and platforms are properties of the product. A feature supporting fewer contexts is expressing coverage, not a different grid.

A project MAY declare an axis no other project uses, and MAY declare a context on one axis that is meaningless on another.

Non-functional

The declaration MUST render with scripting disabled: at least 100% of the axes, contexts, declines and baselines readable with JavaScript off.

Reading the grid MUST be deterministic and side-effect free: identical input produces byte-identical output across at least 3 consecutive runs, with at most 0 network reads.

Out of scope (deferred to other slices)

  • Resolving the grid to concrete values and measuring a build against a cell.
  • The token set the mode axis selects between, and its version.
  • Verifying a platform baseline on a native surface.
  • The baseline of an external component library, as distinct from a platform.

4 · Data model

No persisted entity. This spec adds a declaration and the rules governing it.

Entities

Axis
One dimension a design varies across — a name, its contexts, and its default. Ordered relative to other axes.
Context
One value on an axis. Either supported, or declined with a reason. A context may select values, structure or interaction.
Baseline
For a context determined outside the project: what it was designed against and what it was last verified against. The second may be explicitly none.

The grid is not a matrix of authored cells. It declares the dimensions and which combinations were addressed; combinations that resolve from defaults are not authored, and combinations considered and found identical are recorded so that silence keeps one meaning.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For a feature declaring 2 or more axes, every combination is either addressed, resolved from a default, recorded as considered-and-identical, or declined — with 0 combinations in none of those categories.

The count of declined contexts carrying no reason is 0, and the count of externally-determined contexts carrying no baseline is 0.

A reader can state, from the declaration alone, which platforms a feature supports and which it decided against — in under 60 seconds and without opening another file.

6 · Assumptions

The resolver draft's shape — axes, contexts, an explicit order — will survive stabilisation even if its serialisation changes. If the model itself changes, this is rework rather than a serialisation swap.

Authors will record a considered-and-identical combination rather than leaving it out. If they do not, the grid under-reports coverage, which is the safe direction to be wrong in.

7 · Open questions

None outstanding. The axis model, the decline-with-a-reason rule and the baseline requirement were settled by the survey; the decision to borrow the shape and not the format is recorded as an assumption rather than a question, because nothing here waits on that module stabilising.
