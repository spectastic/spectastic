Design · 096-visual-variant-grid

Visual variant grid

How we will build it.

Status Accepted Spec 096-visual-variant-grid Owner Brian Corbin · @briancorbinxyz Branch spec/visual-slice-095-098 Created 12 Aug 2026 Read time

A project-scoped artifact at the root visual/ declaring axes, their contexts, and which context is the default — with the resolution order carried by document order rather than a number, because P-1 already makes source order reading order and a second ordering could disagree with the first. The load-bearing element is the one that stops the grid becoming busywork: <spec-same> records a combination somebody checked and found identical, so an unwritten cell means nobody looked and never also means looked, no difference. Without it the grid manufactures work at the rate the observables trace did — 77 gap rows, none of them answerable. Baselines nest inside the context they describe, because iOS and macOS move on separate clocks, and a never-verified baseline is a visible verified="none" rather than an absent attribute.

3 · Data model & contracts

Three conceptual entities and one element that belongs to none of them, because the thing that stops the grid becoming busywork is a statement about a combination rather than about any single axis or context.

Conceptual entityPhysical shapeNotes
Axis <spec-axis name default selects> selects is what lets an axis carry structure and interaction rather than only values (FR-002). Order is position, not an attribute.
Context <spec-context name declined> A decline carries its reason as content, so it can never be a bare flag.
Baseline <spec-baseline designed verified>, nested in its context. verified="none" is a value, not an omission — FR-005 is explicit that the gap must be visible.
— (no conceptual sibling) <spec-same axes> A combination checked and found not to differ. Belongs to no single axis, which is why it is its own element rather than an attribute.

This feature exposes no interface. It adds a project-scoped declaration and the checks over it.

5 · Approach

One artifact at visual/variants.html, declaring axes in the order they resolve, each with its contexts and each context optionally declined or carrying a baseline. Alongside them, zero or more <spec-same> entries naming combinations somebody examined and found identical. Two schema rules check the shape and that every name a <spec-same> refers to actually exists; the stylesheet makes a decline read differently from a support, and a missing baseline read differently from a never-verified one.

The whole design turns on what an absent cell means. A combinatorial grid with three axes of three contexts is twenty-seven cells, and almost all of them are uninteresting. If silence meant only "not addressed", every project would either author twenty-seven cells or carry twenty-seven gaps — and this repository already knows where that ends, because the observables trace did exactly that and produced 77 gap rows nobody could answer. So absence is given one meaning and one only: nobody looked. Anything else is written down.

This design deliberately adds no check that the grid is complete, and no notion of a required combination. That is not an oversight to fix later — it is the mechanism. A completeness check would recreate the gap rows by another route, and the spec's own FR-006 rationale says so in as many words.

6 · Alternatives considered

The load-bearing choice was how a considered-and-identical combination is recorded — the thing standing between this grid and 77 unanswerable rows. Scored on whether it can express a combination at all, whether it keeps silence single-meaning, and how much is authored in the common case. 5 is best.

OptionExpresses a combinationSilence stays single-meaningLow authoring costTotal
An attribute on the context1359
A considered= list on the grid root44412
A <spec-same> entry — chosen55414

The context attribute fails on the first criterion outright and that decides it: a cell is a combination of contexts across axes, and a single context has no way to name one. The root list works and loses on proximity — it drifts from the contexts it names, and reads as bookkeeping rather than as a finding somebody made.

7 · Decisions

D-001 · Silence means nobody looked, and nothing else

Status
Accepted
Context
The grid is combinatorial and most cells are uninteresting. If an absent cell meant both "identical" and "not thought about", a project would have to author every cell or carry every gap. This repository has run that experiment: the observables trace produced 37 sections, 77 gap rows and zero authored objectives.
Decision
<spec-same axes="…"> records a combination examined and found not to differ. Absence means one thing. No completeness check is added, and none should be.
Consequences
+ A grid stays as small as the interesting cells, so it does not manufacture busywork. + "We checked and it is the same" becomes a finding rather than a silence. − A reader cannot tell how much of the grid was examined without counting, and the tool deliberately will not tell them — offering that number is how the gap rows come back.

D-002 · A baseline nests inside the context it describes, and never-verified is a value

Status
Accepted
Context
FR-004 makes the baseline per-context because contexts move independently — iOS and macOS are separate clocks even in the same release cycle. FR-005 then insists a never-verified baseline is recorded rather than omitted, so the gap is visible instead of absent.
Decision
A nested <spec-baseline designed verified>. verified="none" is a legal, rendered value; an absent verified attribute is an error.
Consequences
+ "Designed against this, never checked against anything" is sayable, and reads differently from a filled-in baseline. + The baseline sits beside what it describes. − One more nesting level for the rules to traverse. − Nothing checks that a version string is real or well-formed; it is provenance a human reads, and a typo survives.

D-003 · Resolution order is document order, because the project already guarantees that

Status
Accepted
Context
FR-001 requires an explicit order in which axes resolve. An order= number would be explicit and would introduce a second ordering that can disagree with the first — and then a reader has to know which wins.
Decision
Axes resolve in the order they are declared. The artifact says so in prose, and a test asserts the reader returns them in document order rather than sorted or keyed.
Consequences
+ One ordering, which cannot disagree with itself. + Reuses P-1 rather than adding a rule to keep two things consistent. − Reordering axes changes behaviour with no diff marker saying so, which is exactly what an order= attribute would have made loud. Accepted because the alternative failure — a number contradicting the markup — is silent in a worse way.

D-004 · A name referenced by a <spec-same> must resolve, and that is the second rule

Status
Accepted
Context
<spec-same axes="platform=tv mode=dark"> is a reference, and a reference to an axis or context that does not exist is a claim about nothing. It would read as diligence while recording nothing at all — the worst kind of failure for an element whose entire job is to make silence unambiguous.
Decision
A second rule resolves every axis and context named in a <spec-same> against the declared grid, at error severity.
Consequences
+ A renamed context breaks loudly rather than turning a recorded finding into a dangling one. + The names become contracts, per P-3. − A rule that must see the whole artifact rather than one element, so it walks the grid once per document; bounded and asserted.

D-005 · Borrow the resolver draft's shape, never its format

Status
Accepted
Context
FR-007 is unusually specific, and the reason is in the survey: the module this shape comes from carries an instruction not to implement it while it is a draft. Depending on its file format would tie this project's artifacts to something explicitly not ready.
Decision
Take axes, contexts and resolution order as concepts. Express them in this project's own vocabulary, in this project's own artifact format. Reference the draft in the spec as provenance and nowhere in code.
Consequences
+ The draft can change, or never land, without invalidating a single authored grid. + No parser for somebody else's evolving format. − If that draft does stabilise, interoperating means writing an adapter rather than already being compatible. Recorded as the price rather than discovered later.

9 · Risks & mitigations

RiskLikelihoodImpactMitigation
Somebody later adds a completeness check, and the gap rows come back.MHD-001 states the refusal as a decision rather than an omission, and the spec's FR-006 rationale gives the evidence. The risk is real precisely because a coverage number always looks like an improvement.
Reordering axes silently changes resolution.MMAccepted in D-003 as the lesser of two silences. The artifact states the rule in prose where an author will read it.
A baseline version string is meaningless or misspelt and nothing notices.MLStated in D-002. Validating a platform version against reality needs a source of truth this project does not have and should not invent.
The grid and a feature's screens disagree about which contexts exist.LMOut of scope here by FR-008 — a feature declares which of the project's contexts it addresses. Cross-checking that is a later slice, not a silent gap.

10 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here.

A second rule purely to resolve names is more machinery than FR-006 literally asks for. It is here because an unresolvable <spec-same> is worse than none: it reads as diligence and records nothing, which defeats the one thing the element exists to do.

Converting the exemplar's variants.json is not required by any requirement, and is done for the reason 095 converted the screen file: the exemplar is the only project here with an interface, so it is the only place the vocabulary can be exercised, and leaving it in a superseded format ships a demonstration of the thing this spec decided against.
