Change proposal · 078-federated-resource-uri

Kinds come from the closed set

Two requirements name the kinds by hand and are already one short. Naming them was the mistake, not the count.

Status Applied Change ID 2026-08-14-kinds-from-the-closed-set Spec 078-federated-resource-uri Author Brian Corbin · @briancorbinxyz Created 14 Aug 2026 Targets 4 requirements — 2 modified, 2 added Read time

FR-005 and SC-002 enumerate the resource kinds as "spec, contract and corpus" and "all three kinds". Four ship — 079 added unit — so both have been wrong since that landed. Both stop naming members and point at the closed set the parser already recognises, which is what the sibling FR-008 has always done correctly. Two further deltas close the hole that let the drift go unnoticed: the kinds are declared twice with nothing keeping the pair in step, and the round-trip coverage is a hand-listed fixture — so a kind can be added and the matrix stay silent rather than fail.

Kinds come from the closed set

Applied

1 · Intent

Two requirements in this spec list the resource kinds by name. FR-005 says a parser must accept "every spectastic:// resource kind — spec, contract and corpus"; SC-002 measures round-tripping "across all three kinds". The code ships four: ResourceKind and KNOWN_KINDS in packages/schema/src/project-shared.ts both carry unit, added by 079. Both sentences have been false since then.

The instinct is to add unit to each list. That is the wrong repair, and this spec already contains the right one: FR-008 states its round-trip guarantee "for every kind" and names none, so it did not go stale when the fourth arrived and will not when the fifth does. The defect is that FR-005 and SC-002 enumerate members where FR-008 names the set. A fifth kind is already drafted, so patching the count now would put both sentences one short again within the week.

Underneath the wording is the reason nobody noticed for two specs' worth of time — stated carefully, because the state changed yesterday. unit is in RESOURCE_URI_MATRIX now: it was added on 13 Aug precisely because this drift was found, and the fixture carries a comment saying so. What has not changed is the mechanism that let it go missing. The matrix is a hand-written array, and nothing structurally ties it to the kind declaration — so the next kind can be added and the matrix stay silent exactly as it did for unit, with the suite reporting success while FR-008's text claims a property it did not test.

The hole has a direction, and it is the opposite of the obvious one. The kinds are declared twice — ResourceKind as a union and KNOWN_KINDS as a runtime set, documented as "two declarations of one set" that "move together". Widening the set alone is already caught, since it is typed against the union and an unrecognised member does not compile. Widening the union alone is not caught at all, and that is what 079 did: it leaves a coordinate that composes and then fails to parse, the failure the docstring itself warns about. Any coverage keyed off the runtime set would guard the half that was never in danger.

So the two declarations are collapsed into one, and that is why the collapse belongs in this change rather than in the follow-on it was first deferred to. The comment says the pair moves together; it does not, and no mechanism makes it. With a single declaration and both forms derived from it, the asymmetry does not need guarding — it stops existing, and coverage keyed off that one declaration catches every widening because there is only one way to widen. A guarantee that depended on an author reading a comment is the kind P-8 says may not live in prose.

2 · Scope

In scope

  • Removing the by-name enumeration from FR-005, so the obligation is over the closed set the parser recognises rather than over a list that must be maintained in prose.
  • The same correction to SC-002, whose "all three kinds" carries the identical staleness and would contradict the amended FR-005 in the same file if left.
  • Collapsing the two kind declarations into one, so the pair that is documented as moving together actually does. This was first drafted as a deferred follow-on and is in scope on the adversarial pass's evidence: the only failure that has occurred here is widening the union without the set, and no coverage keyed off the set can see it. Collapsing removes the asymmetry rather than guarding it.
  • Two new requirements: the kinds are declared once, and a widening that does not extend the round-trip coverage fails rather than passing silently.
  • Adding the two unit fixtures the matrix is missing. They implement FR-008, which has always required them, so they land as ordinary work before this applies rather than as a delta — otherwise the amended SC-002 is false on the day it lands.

Out of scope

  • Adding screen as a fifth kind. That is 095's drafted change and is the reason this one lands first; sequencing them the other way is what puts a new kind on a stale enumeration. defer-to=095-visual-element-vocabulary. This proposal is the sibling 095 asked for. Its own text says amending 078 FR-005 needs "a sibling propose authored alongside this one — the apply kernel folds same-spec deltas only, so a cross-spec delta here would be silently skipped." One consequence worth naming: once the enumeration is gone, adding a fifth kind no longer touches 078's requirements at all — only the declaration and the coverage that now follows it.
  • Any change to the set of kinds, or to how a kind is composed, parsed, or rendered. Collapsing two declarations into one is a change of shape, not of behaviour: the same four kinds parse and compose identically before and after. defer-to=never. The boundary is behaviour, not the package surface — if the single declaration must be exported where the runtime set is module-private today, that is in scope and still moves no behaviour.
  • Correcting US2's acceptance prose is in scope as a task rather than a delta — see §6. It carries the same stale enumeration, but a user story's acceptance clause is not a <spec-requirement>, so the delta mechanism cannot carry it and a requirement-shaped target with no embedded post-state is rejected by the apply gate.

3 · Approach

Both MODIFYs point at the same referent FR-008 already uses: the closed set of kinds the parser recognises. The requirement stays checkable — arguably more so, because a test can iterate that set, where it could only ever compare prose against a list a reader assembled by eye.

The ADD states a property rather than a mechanism: coverage is derived from the closed set, and a kind absent from coverage is a failure. It deliberately does not say how — whether the fixture array is generated, whether a separate assertion compares the two, or whether the matrix is replaced by iteration is the design's call. Naming a mechanism in a requirement is how 105's FR-016 came to reference a writer that did not exist, and the correction there was to state properties and let the implementation follow.

This is an amendment to an accepted spec, which is ordinary rather than exceptional — the requirements were true when written and stopped being true when a sibling spec widened the set underneath them. The changelog entry records that, so a later reader does not read the amendment as a drafting error.

4 · Deltas

What changes: the parser's obligation stops naming members and names the set, so it cannot go stale when the set widens.

A single parser MUST accept every spectastic:// resource kind in the closed set of kinds it recognises, and MUST report the kind it found as part of its result.

Rationale

One parser, because a second would drift from the first — that half is unchanged.

The enumeration is removed rather than corrected. Naming "spec, contract and corpus" made this requirement false the moment 079 added unit, and correcting the list to four would make it false again when the fifth lands — which is already drafted. The sibling FR-008 has always said "for every kind" and never went stale, which is the shape to copy.

The set is not vague. It is the closed set the parser recognises, declared in code and already the thing an unknown-kind failure is judged against under FR-007 — so this requirement now points at the same referent its own error case does.

What changes: the same correction to the criterion that measures it. Left alone, it would contradict the amended FR-005 in the same document.

Every well-formed coordinate, across every kind in the closed set and all four combinations of edition pin and anchor, round-trips: compose → parse → compose returns the original string.

Rationale

A success criterion that counts the kinds is a success criterion that needs editing every time one is added, and this one was not edited. "All three kinds" has measured three of the four that ship since 079.

The "all four combinations of edition pin and anchor" clause is deliberately kept as a number: that set is genuinely closed at four — pin present or absent, anchor present or absent — and is a property of this spec's own grammar rather than of a list another spec can widen.

What changes: new requirement. The kinds are declared once, so there is a single thing to widen and a single thing for coverage to follow.

The recognised resource kinds MUST have exactly one declaration, and every derived form — the static type, any runtime set the parser consults — MUST be derived from it rather than restated. At most 1 place in the codebase may enumerate the kinds.

Rationale

Today there are two: a union and a runtime set, carrying a comment that says they "move together". Nothing makes them, and they did not — 079 widened the union, the set followed, and the coverage behind FR-008 did not.

This requirement exists because FR-014 is unstatable without it. "A widening" needs a referent, and with two declarations there are two widenings with different consequences: one fails to compile, the other ships a coordinate that composes and then fails to parse. Collapsing them is what makes the next requirement mean one thing.

Deliberately not a claim that the enumeration must live in any particular place or form. One declaration, everything else derived — where it sits and how it is written is the design's call.

What changes: new requirement. Widening the declaration without extending coverage fails, so the drift this proposal corrects cannot recur silently.

Widening the kind declaration without extending the round-trip coverage that proves FR-008 MUST fail, and that failure MUST be triggered by the widening itself rather than by a separate list being kept in step by hand. Coverage MUST span the same cross-product FR-008 states — every kind against every combination of edition pin and anchor — with at most 0 kind-and-combination pairs untested while the suite reports success.

Rationale

FR-008 is correctly worded and was never correctly guaranteed. unit was widened into the declaration by 079 and did not reach the matrix until it was found by hand two specs later; nothing failed in between, which is why it survived.

The cross-product clause is not redundant with the kind clause. At authoring time unit carries three fixtures covering the bare and anchor cases and neither edition case, so a rule counting only kinds would report it covered while SC-002 — amended in this same proposal to claim every kind against all four combinations — would be false. Measuring the pair is what makes the two agree.

A consequence worth stating rather than leaving to be discovered: the next kind cannot land until its coverage does. 095's screen is next in line and will meet this as a stated obligation rather than a surprising build failure. That friction is the guarantee — unit went missing precisely because nothing blocked.

Stated as a property, not a mechanism. Whether coverage is keyed by a type whose exhaustiveness the compiler checks, generated, or asserted some other way is the design's call; the obligation is only that the widening cannot pass unnoticed.

5 · Risk register

Findings from the adversarial pass. Statuses stay identified until the author dispositions them.

Run before apply, deliberately. I-074 records that the previous two rounds ran it after, and that the one proposal following the method caught four defects while they were still free. This pass found four, all confirmed against the code, and three changed the proposal before you read it — the drafted responses below say what changed rather than arguing the finding away.

The requirement named a set no test can reach, and would have guarded the safe direction

As first drafted, FR-013 required coverage "derived from the closed set of recognised kinds". KNOWN_KINDS is a module-private const imported by nothing, so satisfying it needed a package-surface change the proposal had put out of scope. Worse, it guards the wrong half: that set is typed Set<ResourceKind>, so widening it alone already fails to compile, while widening ResourceKind alone — what 079 did, and the only failure that has ever occurred here — would leave a set-derived matrix silent.

Draft response — the finding was taken further than its own remedy. The first fix reworded the requirement to guard the asymmetry. The interview reversed that in favour of removing it: the two declarations are collapsed into one (FR-013), so there is no longer a safe half and a dangerous half to distinguish — there is one declaration, one way to widen it, and coverage keyed off it (FR-014) sees every widening. The module-private half of the finding dissolves with it, and the scope note now states the boundary is behaviour rather than the package surface. Status left identified — the reader should confirm the collapse closes it rather than relocating it.

The bar measured kinds where FR-008 states a cross-product, and today's matrix already fails the difference

FR-008 requires round-tripping "for every kind and every combination of edition pin and anchor". The first FR-013 counted kinds only, so one fixture per kind would satisfy it while leaving FR-008 unmet. That is not hypothetical: unit has three fixtures covering bare, owner-qualified and anchor, and neither edition case, where spec, contract and corpus each have all four. So unit would read as covered while the amended SC-002 — claiming every kind against all four combinations — is false on the day it lands.

Draft response — requirement widened, and the sequence changed. FR-014 now measures kind-and-combination pairs. More importantly the fix moved ahead of apply rather than after it: the two missing fixtures implement FR-008, which has always required them, so they land as ordinary work before this proposal applies. That was the interview's call and it is the right one — a §6 task would have shipped a knowingly-false success criterion during a recovery whose cause was requirements that were not true.

Too narrow: a third stale enumeration was demoted to a sweep

§Scope argued SC-002 must move because it "would contradict the amended FR-005 in the same file". That reasoning applies verbatim to US2's acceptance clause, which reads "one parser accepts all three kinds — spec, contract, corpus" — and the first draft handled it as an open-ended "re-read for any other by-name enumeration" task, which is the guarantee-in-prose posture the proposal's own §1 rejects.

Draft response — partially accepted, and the limit stated. The task is now specific: the site, its line, and its current text. It cannot become a delta — a user story's acceptance prose is not a <spec-requirement>, and a requirement-shaped target carrying no embedded post-state is rejected by the apply gate — so a window does exist between apply and drain in which the spec contradicts itself. The reader's call is whether that window is acceptable or whether the enumeration should come out of US2 by hand before this applies.

The only new must-tier requirement was argued from a state that had already been fixed

Against KB-0001@2026-07-25, which commits that a fact is verified only when the source was opened this turn and that a must-tier decision may not rest on an assumed fact without an accepted risk: §1 claimed in the present tense that the suite "goes green having tested three of four kinds". It does not. unit reached the matrix on 13 Aug in commit bfb733e, which I-074 records as Done and which the authoring session had already read. The residual defect is real; the sentence justifying it was not.

Draft response — accepted, and the prose corrected. §1 now states that unit is in the matrix, that it arrived because this drift was found, and that what survives is the mechanism rather than the omission. Recorded rather than quietly fixed because it is I-074's own diagnosis — a requirement written from a description rather than from the code — reproducing itself in the first proposal of the recovery, which is evidence about the method and not just about this file.

6 · Tasks

Two edits must land by hand immediately before the kernel apply, and cannot be tasks. Both are prose rather than <spec-requirement>s, so no <spec-delta> can carry them — a requirement-shaped target= with no embedded post-state is rejected by the apply gate — and a §6 task drains after apply, leaving a window in which the spec contradicts itself.

  • Add the Resource kind entry to §4 Data model, defining the set that FR-005, SC-002, FR-013 and FR-014 all now point at. It must exist before the deltas land, or the amended requirements name a referent the spec does not define.
  • Correct US2's acceptance clause (spec.html line 111), which reads "one parser accepts all three kinds — spec, contract, corpus" — the third site of the same staleness.

And one piece of ordinary work before apply, needing no approval: fill unit's two missing combinations in packages/schema/test/fixtures/resource-uri-matrix.ts. It implements FR-008, which has always required them; without it the amended SC-002 is false on the day it lands.

  • Amend specs/078-federated-resource-uri/spec.html with the four deltas (kernel apply).
  • Collapse the two kind declarations in packages/schema/src/project-shared.ts — one enumeration, with the union and the runtime set both derived from it, replacing the comment that says they move together with a structure that makes them.
  • Key the round-trip coverage off that single declaration in packages/schema/test/fixtures/resource-uri-matrix.ts, so an unwidened matrix cannot pass.
  • Prove the guard in packages/schema/test/project-shared.test.ts: add a kind to the declaration without coverage and confirm it fails before trusting it green — the discipline the removed 105 arithmetic tests never got.

7 · Open questions

None outstanding. The one judgment worth recording is a deliberate asymmetry: the kind enumeration is removed while SC-002's "all four combinations of edition pin and anchor" is kept as a number, because that set is closed by this spec's own grammar and cannot be widened by a sibling.
