Design · 078-federated-resource-uri

Federated resource URI

How we will build it.

Status Accepted Spec 078-federated-resource-uri Owner Brian Corbin · @briancorbinxyz Branch 078-federated-resource-uri Created 01 Aug 2026 Read time

Add a third resource kind to the composer that already takes the kind as a parameter, add the reverse direction on top of the platform's own URL parser, and mirror the existing project-identity findings one axis over onto the marketplace. Almost nothing here is new machinery — the work is choosing the authority correctly and folding its case, which is what makes the dedupe guarantee structural rather than a convention. The biggest risk is the one the spike found: a non-special URI scheme does not normalise host case, so without a deliberate fold two repositories spelling their marketplace differently would silently fail to dedupe.

3 · Data model & contracts

The spec's three conceptual entities land as one string grammar and one parsed record — no storage, no wire format. The registry row is the physical source of a corpus coordinate's parts and already carries every one of them, so nothing new is persisted.

Conceptual entityPhysical shapeNotes
Resource coordinate A string when rendered; a discriminated record { kind, authority, name…, edition?, anchor? } when parsed. The parsed form is the parser's return type; the rendered form is canonical and the one that is compared.
Authority The URI host segment — marketplace for the corpus kind, project for spec and contract. Sourced from resolveCorpusConfig's existing precedence chain; lowercased for the corpus kind only (D-004).
Edition pin ?edition=<value> query parameter; the value is the registry row's edition field verbatim. Absent parameter means current. Query precedes fragment, fixed by URI syntax.

This feature exposes no request/response, RPC, GraphQL or event-driven interface. It ships a library grammar and a read-only CLI verb; every serving surface that would carry a contract — the corpus server, the specs server, cross-repository aggregation — is deferred by the spec's own out-of-scope block. The spectastic:// scheme it defines is an interoperability contract, but a naming one: it has no transport, no request shape and no error envelope to specify, so an OpenAPI or AsyncAPI document would have nothing to describe. The consumer-facing contract arrives with the server that serves these coordinates, in that repository.

5 · Approach

Three additions in three existing places, in dependency order. First, @spectastic/schema's shared project grammar grows a corpus kind, an optional edition parameter on the composer, and a new parser — the whole grammar, both directions, in the one module both packages already consume. Second, @spectastic/corpus gains the two things that need a corpus to answer: a function turning a registry row into a coordinate, and a marketplace-identity findings function cloned from the project-identity one beside it. Third, the spectastic-corpus binary gains an id verb alongside get/query/grep, and the marketplace findings are wired into both validate surfaces.

The parser is the only genuinely new unit, and the spike removed most of its risk: the platform's URL implementation already parses this scheme correctly and round-trips it byte-for-byte, so our code validates the kind and shape rather than re-implementing percent-encoding. The one piece of real design judgment is the authority: it is the marketplace rather than the project, and it is lowercased on the way out, because those two choices together are what make the dedupe guarantee hold structurally instead of by convention.

6 · Alternatives considered

Scored 1–5, higher is better. The criteria that mattered: whether the dedupe guarantee holds without anyone remembering a rule, whether the change is confined to additive code, and how much grammar we own versus borrow from the platform.

OptionDedupe holds structurallyAdditive onlyGrammar we don't ownTotal
Project authority, hand-rolled parser — one authority rule for all kinds1427
Marketplace authority, case-sensitive, hand-rolled parser2529
Marketplace authority, case-folded, hand-rolled parser55212
Marketplace authority, case-folded, platform URL parser — chosen55515

The first option scores worst on the criterion that matters most: keying on the project mints one coordinate per installing repository, which is the double-counting the whole substrate exists to prevent. The second and third differ only by the case fold — the spike is what separated them, and without it the third option would have looked identical to the second.

7 · Decisions

D-001 · The corpus kind joins the existing composer rather than getting its own

Status
Accepted
Context
packages/schema/src/project-shared.ts:68 takes the kind as a parameter precisely so a second kind needs no second composer, and a contract kind was added that way at :96. A third kind is the same move again.
Decision
Extend ResourceKind with 'corpus' and add a thin named wrapper beside the existing spec and contract wrappers. Add an optional edition parameter to the shared composer, emitted as ?edition= before any fragment.
Consequences
+ One authority-and-path rule, so a corpus coordinate cannot drift from a spec coordinate. + Existing call sites are untouched — the new parameter is optional. − The shared composer now carries a query concept only one kind uses today.

D-002 · Parse with the platform's URL implementation, not a hand-rolled grammar

Status
Accepted
Context
Spike (§4): new URL('spectastic://spectastic/corpus/pack/doc?edition=2026-07-26#anchor') yields the correct host, pathname, searchParams and hash, and href round-trips byte-identically. Percent-encoding is handled to spec.
Decision drivers
Correctness of encoding · FR-008 round-trip · FR-007 never-throws · amount of grammar we own
Considered options
  • Hand-rolled regex grammar — + total control, no throw path to wrap. − we re-implement percent-encoding and inherit its edge cases forever.
  • Platform URL — chosen — + spike-verified on the real runtime, encoding correct by construction. − lenient, so the kind and segment count must be validated by us; throws on malformed input, so FR-007's typed failure is a wrapper.
Decision
Parse via the platform URL, then validate the kind segment and arity ourselves, returning a typed result. Wrap construction so a malformed input becomes a failure value rather than a thrown error.
Consequences
+ Encoding correctness is the platform's problem, not ours. + The round-trip requirement is met by construction. − One assumed fact (runtime parity across supported majors) that §9 mitigates with a test assertion. − Parsing is lenient by default, so validation is explicit rather than implied by the grammar.

D-003 · The whole grammar lives in the shared schema package

Status
Accepted
Context
@spectastic/schema already publishes a ./project subpath holding the composer, and .dependency-cruiser.cjs:15 forbids only a corpus→core edge. Schema sits below both consumers, so it is the one place both can reach.
Decision
Composer, parser and kind union all live in the existing shared project grammar module. The corpus package holds only what needs a corpus to answer — turning a registry row into a coordinate, and the marketplace findings.
Consequences
+ Satisfies FR-010 and NFR-003 structurally: the standalone binary reaches the grammar without the kernel. + No new package, no new build target. − The schema package accumulates another responsibility, which is the trade it was already making.

D-004 · Lowercase the authority — for the corpus kind only

Status
Accepted
Context
Two facts collide. The spike (§4) found a non-special scheme preserves host case where https:// folds it, and project-shared.ts:31 permits mixed case — so casing can silently break dedupe. But FR-012 requires existing spec and contract coordinates to render exactly as today, which folding in the shared composer would violate.
Decision drivers
FR-009 dedupe must hold structurally · FR-012 additive-only · avoiding a convention nobody remembers
Considered options
  • Fold in the shared composer — + symmetric across kinds. − changes already-emitted spec and contract coordinates, so it needs a proposal against FR-012 first.
  • Warn instead of folding — + no behaviour change. − the headline guarantee then depends on someone heeding a warning.
  • Fold for the corpus kind only — chosen — + dedupe holds structurally, FR-012 intact. − casing becomes asymmetric between a project's spec and corpus coordinates.
Decision
The corpus composer lowercases the authority before rendering. The shared composer's behaviour for spec and contract is untouched.
Consequences
+ Two repositories spelling the marketplace differently still dedupe, with nothing to remember. + FR-012 holds, so no proposal blocks this design. − A project with a mixed-case identity renders a lowercase corpus authority and a mixed-case spec authority; recorded in §10 as deliberate, and a candidate for a later symmetry proposal.

D-005 · Tests red first, 100% patch coverage

Status
Accepted
Context
A judgment call with no external fact behind it. Every unit here is a pure function whose expected output is an exact string, and the estate has run tests-red-first on comparable specs.
Decision
Write the failing test before each unit. Patch target 100% of changed lines, plus the standing rule that a change never lowers coverage of what it touches. Table-driven cases over the coordinate matrix — every kind crossed with every combination of edition pin and anchor.
Consequences
+ The round-trip and dedupe requirements are literally test tables, so the criteria are executable. + Full patch coverage is realistic rather than aspirational for code with no environment branch. − Slower per unit than writing tests after.

D-006 · The marketplace warning fires on both validate surfaces

Status
Accepted
Context
packages/cli/src/commands/validate.ts:353 documents why the project-identity gate is not mirrored onto the standalone corpus binary: it "has no dependency on a knowledge/ corpus existing". That reasoning distinguishes rather than excludes a marketplace, which is corpus-intrinsic by definition.
Decision
Add marketplace findings beside the project ones in the corpus package, wire them into the main CLI as a sibling scan, and also into packages/corpus/src/cli/validate.ts. The project gate stays main-CLI-only, unchanged.
Consequences
+ A standalone corpus user hears about a collision-prone identity from the tool they actually run. + The existing scope docstring stays true — we follow its reasoning rather than contradicting it. − Two registration sites for one findings function; covered by asserting both surfaces emit it.

10 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here.

The casing asymmetry is deliberate. D-004 folds case for the corpus kind only, so a project with a mixed-case identity renders a lowercase corpus authority beside a mixed-case spec authority. The simpler, symmetric alternative — folding everywhere — would change coordinates already emitted for spec and contract kinds, which FR-012 forbids. The asymmetry is therefore the cheaper of the two, and it is confined to projects that chose a mixed-case identity. Making it symmetric later is a proposal against FR-012, not a redesign.

The shared composer gains a concept only one kind uses. The optional edition parameter is meaningless for spec and contract coordinates today. Keeping it on the shared composer rather than forking a corpus-only one preserves the single authority-and-path rule that stops the kinds drifting apart — the same trade an earlier spec made when it added the contract kind rather than a second composer.
