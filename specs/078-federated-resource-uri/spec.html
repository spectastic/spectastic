Specification · 078-federated-resource-uri

Federated resource URI

Give a corpus document the federation-unique coordinate specs already have — and make every spectastic:// URI readable in both directions.

Status Accepted Spec ID 078-federated-resource-uri Owner Brian Corbin · @briancorbinxyz Reviewers — Created 01 Aug 2026 Principlesv1.8.0 Smallest demoableA corpus document renders a spectastic:// coordinate, that coordinate parses back, and the same pack in two repos yields one identical URI. Read time

067 gave specs the namespace prefix they lacked and deferred one piece by name: rendering corpus resources as spectastic:// URIs. This spec closes it. A corpus document becomes spectastic://<marketplace>/corpus/<plugin>/<slug> — keyed on the marketplace rather than the repo-local KB-NNNN, so the same pack installed in ten repositories collapses to one coordinate. It also adds the reverse direction the estate has never had: a parser reading any spectastic:// URI back into the coordinate it names.

V Valuable

1 · Context

The corpus already knew the answer before the specs did. Facing "a globally-unique id without a global coordinator", 062 adopted the identifier world's canonical shape — a namespace prefix plus a local suffix, the way a DOI works. Spectastic's prefix is the marketplace; KB-NNNN is only the repo-local suffix.

067 applied that move to the spec side and built the machinery: a project identity, a spectastic://<project>/spec/<id> coordinate, and a composer taking the resource kind as a parameter — 076 then reused it for a second kind without writing a second composer. But 067 deferred one piece by name: Rendering corpus resources as spectastic:// URIs … ships with the serving surface. That is the gap here.

Two things make it worth closing on its own rather than inside a server. The corpus's coordinate is not the project's — a pack installed in ten repositories is one body of knowledge, and a coordinate saying otherwise turns a federated index into ten near-identical hits. And the estate can compose these URIs but has never been able to read one.

Who it's for: the read surfaces that come next, and equally someone using 064's corpus on its own — no lifecycle, no specs/ — who still deserves a citable global coordinate.

2 · User scenarios & testing

Each story MUST be independently testable: US1 alone is a viable MVP — a corpus document with a stable global coordinate, before anything can read one back.

US1 · A corpus document gets a global coordinate P1

As a corpus curator, I want to render any document's federation-unique resource URI so that I can cite it from outside the repository that happens to hold it.

Acceptance: a corpus document resolves to spectastic://<marketplace>/corpus/<plugin>/<slug>, with an edition pin appended as ?edition=… and an anchor as #…, in that order. It runs with the corpus package alone — no kernel, no specs/. Re-running yields byte-identical output.

US2 · A coordinate reads back P1

As a consumer receiving a coordinate from elsewhere, I want to parse any spectastic:// URI into the parts it names so that I can act on a coordinate I did not compose.

Acceptance: one parser accepts every kind in the closed set and reports which it found. A well-formed URI naming a marketplace this repository has never heard of parses successfully; only the separate act of resolving it locally reports "not present". A malformed URI yields a typed failure and never throws. Compose-then-parse returns the original coordinate.

US3 · One pack, one coordinate P1

As a maintainer of several repositories that share a pack, I want the same knowledge to carry the same coordinate everywhere so that an index over all of them shows one document, not one per repository.

Acceptance: the same pack in two repositories — different project identities, different KB-NNNN ids — yields byte-identical unpinned coordinates. Two repositories holding different editions still share that unpinned coordinate; their pinned coordinates differ, naming different content.

US4 · A collision-prone marketplace is called out P2

As a maintainer preparing to federate, I want validation to flag a marketplace name that cannot distinguish me from anyone else so that I find out before my coordinates collide, not after.

Acceptance: a marketplace that is not owner-qualified — the bare directory-name default — is a validate warning naming the fix; an owner-qualified one yields no finding. The warning never blocks.

Edge cases

  • An unset corpus.marketplace — 067's unified derivation supplies it from project. The authority is still the marketplace; that the two coincide here is derivation, not equivalence.
  • A marketplace deliberately different from the project identity — the explicit value wins and the corpus coordinate diverges from the spec coordinate. Correct, not a conflict: the pack is published by one identity and lives in another.
  • A superseded but retained edition — its pinned coordinate keeps resolving, matching 052's guarantee that a pinned citation survives supersession.
  • An anchor naming a heading that does not exist — the coordinate is emitted anyway, matching 067's treatment of a spec anchor.
  • An unknown kind segment — parses to a typed failure rather than a partial result, so a consumer rejects it cleanly instead of guessing.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A corpus document MUST resolve to a canonical resource URI of the form spectastic://<marketplace>/corpus/<plugin>/<slug>, and that URI MUST NOT incorporate the repo-local KB-NNNN id.

Rationale

The registry itself calls KB-NNNN "project-assigned and repo-unique" — a local convenience, never a federation key. The durable key is the coordinate the citation label already derives.

The authority of a corpus resource URI MUST be the marketplace — not the project identity — even where the two resolve to the same string.

Rationale

The whole dedupe mechanism, and the one place this spec departs from 067's project-as-authority rule. Keying a shared pack on the project would mint one coordinate per installing repository — the double-counting a federated index exists to avoid. 067's derivation makes the two values usually equal; this keeps the corpus case correct when they are not.

An edition pin MUST ride as a query parameter (?edition=<edition>), an absent parameter MUST mean the current edition, and where both a pin and an anchor are present the query MUST precede the fragment.

Rationale

Conventional URI syntax, so a generic client parses it with no special knowledge. A deliberate divergence from the citation grammar's KB-0001@2026-07-26 — the estate now carries two spellings for one concept — accepted because a URI is read by tools that know nothing of that grammar. Query-before-fragment is fixed by URI syntax, not preference.

A corpus resource URI MAY carry a fragment naming a heading slug within the document; it MUST be appended mechanically, and its existence MUST NOT be checked at composition time.

A single parser MUST accept every spectastic:// resource kind in the closed set of kinds it recognises, and MUST report the kind it found as part of its result.

Rationale

One parser, because a second would drift from the first — that half is unchanged.

The enumeration is removed rather than corrected. Naming "spec, contract and corpus" made this requirement false the moment 079 added unit, and correcting the list to four would make it false again when the fifth lands — which is already drafted. The sibling FR-008 has always said "for every kind" and never went stale, which is the shape to copy.

The set is not vague. It is the closed set the parser recognises, declared in code and already the thing an unknown-kind failure is judged against under FR-007 — so this requirement now points at the same referent its own error case does.

Parsing MUST succeed for any well-formed URI regardless of whether the marketplace or project it names is present locally; resolving a parsed coordinate to a local artifact MUST be a distinct operation that reports absence rather than failure.

Rationale

Keeps the parser pure grammar, with no knowledge of the repository around it. A read surface fronting several repositories parses foreign coordinates constantly; one that rejected them would need replacing immediately.

A malformed or unknown-kind URI MUST yield a typed failure result and MUST NOT throw, and MUST NOT return a partially-populated coordinate.

Composing a coordinate and then parsing the result MUST return a coordinate equal to the one composed, for every kind and every combination of edition pin and anchor.

The same pack installed in any number of repositories MUST yield byte-identical unpinned coordinates, irrespective of each repository's project identity or locally-assigned KB-NNNN ids. Coordinates pinned to different editions MUST remain distinct.

Rationale

Identity and versioning are separate axes: the unpinned coordinate answers "same document?", the pin answers "which edition?". Collapsing them would either double-count a shared pack or make two genuinely different editions indistinguishable.

Rendering and parsing a corpus coordinate MUST be available from the standalone corpus surface, with no lifecycle kernel installed and no specs/ directory present.

Rationale

064 made the corpus usable on its own; a coordinate needing the lifecycle to render would quietly retract that, and would breach the one-way package boundary.

Validation SHOULD emit a warning for a marketplace that is not owner-qualified, naming the fix; an owner-qualified marketplace SHOULD yield no finding. The warning MUST NOT block.

Rationale

Mirrors 067's bare-project warning, one axis over. The marketplace defaults to the repository's directory name, so two repositories with generic directory names collide in the very namespace meant to prevent collisions. A true cross-repository collision check needs the whole estate, and is deferred.

The change MUST be additive: existing spec and contract coordinates MUST render exactly as they do today, and KB-NNNN citations MUST keep their current form and behaviour everywhere they are used.

The recognised resource kinds MUST have exactly one declaration, and every derived form — the static type, any runtime set the parser consults — MUST be derived from it rather than restated. At most 1 place in the codebase may enumerate the kinds.

Rationale

Today there are two: a union and a runtime set, carrying a comment that says they "move together". Nothing makes them, and they did not — 079 widened the union, the set followed, and the coverage behind FR-008 did not.

This requirement exists because FR-014 is unstatable without it. "A widening" needs a referent, and with two declarations there are two widenings with different consequences: one fails to compile, the other ships a coordinate that composes and then fails to parse. Collapsing them is what makes the next requirement mean one thing.

Deliberately not a claim that the enumeration must live in any particular place or form. One declaration, everything else derived — where it sits and how it is written is the design's call.

Widening the kind declaration without extending the round-trip coverage that proves FR-008 MUST fail, and that failure MUST be triggered by the widening itself rather than by a separate list being kept in step by hand. Coverage MUST span the same cross-product FR-008 states — every kind against every combination of edition pin and anchor — with at most 0 kind-and-combination pairs untested while the suite reports success.

Rationale

FR-008 is correctly worded and was never correctly guaranteed. unit was widened into the declaration by 079 and did not reach the matrix until it was found by hand two specs later; nothing failed in between, which is why it survived.

The cross-product clause is not redundant with the kind clause. At authoring time unit carries three fixtures covering the bare and anchor cases and neither edition case, so a rule counting only kinds would report it covered while SC-002 — amended in this same proposal to claim every kind against all four combinations — would be false. Measuring the pair is what makes the two agree.

A consequence worth stating rather than leaving to be discovered: the next kind cannot land until its coverage does. 095's screen is next in line and will meet this as a stated obligation rather than a surprising build failure. That friction is the guarantee — unit went missing precisely because nothing blocked.

Stated as a property, not a mechanism. Whether coverage is keyed by a type whose exhaustiveness the compiler checks, generated, or asserted some other way is the design's call; the obligation is only that the widening cannot pass unnoticed.

Non-functional

Composition and parsing MUST be deterministic and pure: 100% identical output across repeated runs for identical input, with at most 0 reads of the filesystem, the clock, the network, or environment state.

Rationale

A federation key that shifted with its environment would not be a key. This restates 067's determinism constraint for the corpus kind and extends it to the new parsing direction.

A URI submitted for parsing MUST be treated as untrusted data: at most 0 dereferences, filesystem reads, or evaluations of any part of it occur during parsing.

Rationale

Coordinates will arrive from outside the repository once a read surface exists. Honours P-11 — artifacts are data, not instructions — at the point the estate first accepts an identifier it did not author.

The corpus package SHOULD gain at most 0 new dependencies on the lifecycle kernel in service of this spec; the shared URI grammar SHOULD stay upstream of both.

Out of scope (deferred to other slices)

  • The server serving these coordinates as corpus resources. This spec defines the addressing; that one owns the transport, in its own repository with its own lifecycle.
  • Exposing the specs/ estate over the same surface. Consumes these coordinates; does not define them.
  • Cross-repository aggregation — one endpoint fronting several checkouts. This spec fixes the rules making aggregation unambiguous; the first serving surface is deliberately single-repository.
  • Promoting the marketplace from a directory-name default to an owner-qualified identity. This spec warns about the fragile default; it does not fix it.
  • Verifying an anchor names a real heading. Belongs with the read path that would dereference it, matching 067's identical deferral.
  • Routing a requirement to its owning service by the spec-sensitive corpus. Gated behind the whole serving surface.

4 · Data model

Three concepts. The estate already has a resource coordinate; this spec adds the corpus kind and names the rule deciding its authority.

Entities

Resource coordinate
The federation-unique name of one addressable artifact: an authority, a kind, a name, and optionally an edition pin and an anchor. It names what a thing is, never where its file sits. Exactly one canonical rendering per coordinate, and every well-formed rendering parses back to exactly one.
Authority
The namespace prefix making a repo-local name globally unambiguous. Which identity serves depends on the kind: specs and contracts take the project, corpus documents the marketplace. It is owner-qualified when it carries more than one segment; a single-segment authority is valid but collision-prone.
Edition pin
An optional selector narrowing a coordinate to one edition; absent means current. A pin never changes which document is named — which is why the unpinned form is the identity.
Resource kind
The closed set of things a coordinate may name. One declaration; every requirement in this spec that refers to "every kind" or "the closed set" means this one. Widened only by the spec that adds a kind — this spec added corpus, 079 added unit — never by a requirement enumerating members, which is what let the set drift out of sync with its own description.

The invariant that carries this spec: a document's identity is a function of its publication coordinate alone — never of the repository holding it or the id assigned to it there. This is also where the estate gains a second authority rule. The asymmetry is deliberate: a spec belongs to one project, a pack is installed by many.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

The same pack installed in two repositories — different project identities, different locally-assigned ids — produces byte-identical unpinned coordinates for every document it contains.

Every well-formed coordinate, across every kind in the closed set and all four combinations of edition pin and anchor, round-trips: compose → parse → compose returns the original string.

Rationale

A success criterion that counts the kinds is a success criterion that needs editing every time one is added, and this one was not edited. "All three kinds" has measured three of the four that ship since 079.

The "all four combinations of edition pin and anchor" clause is deliberately kept as a number: that set is genuinely closed at four — pin present or absent, anchor present or absent — and is a property of this spec's own grammar rather than of a list another spec can widen.

A corpus coordinate renders in an environment containing only the corpus package and a corpus — no lifecycle kernel, no specs/ directory, no project identity configured.

A coordinate naming a marketplace absent from the local repository parses successfully and reports its parts; the separate attempt to resolve it locally reports absence, and neither operation raises an error.

A repository whose marketplace is the bare directory-name default produces exactly one validation warning naming the fix, and validation still exits successfully.

6 · Assumptions

Marketplace names are stable once published. A rename produces new coordinates rather than migrating old ones — the posture 067 takes toward a renamed project, and why both derive at write time.

A plugin and slug together identify a document within a marketplace. Already the registry's working assumption and the basis of the citation label; this spec relies on it rather than re-verifying it.

Two spellings for edition pinning — the citation grammar's @ and this URI's ?edition= — is an acceptable cost, accepted knowingly rather than overlooked. The audiences differ: a generic URI consumer should not have to learn a bespoke grammar to read a version selector.

7 · Open questions

None outstanding. The authority rule, the edition-pin spelling, the kind segment, the parse/resolve split, the dedupe semantics across differing editions, the standalone rendering surface and the validation severity were each anchored in the interview. The serving surfaces are deferred, not undecided — including where their specs live, which settled as their own repository's estate.
