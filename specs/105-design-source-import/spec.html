Specification · 105-design-source-import

Take the design in

Five design tools, five incompatible read paths, and one thing they all do: put files on a disk. Read those, once, and let the tool go out of business.

Status Draft Spec ID 105-design-source-import Owner Brian Corbin · @briancorbinxyz Reviewers — Created 13 Aug 2026 Principlesv1.9.0 Smallest demoableRunning an import against an exported folder lands a token file and its renders in the sidecar, marked not yet reviewed, and the design still validates after the folder is deleted. Read time

The design stage declares where a design came from and can do nothing with it — source= is provenance, never resolved, and that is enforced in code. This adds the other half: an import that reads an export already on disk, lands a token file, its renders and any annotations it carries into the sidecar, and then disappears. No live read path, no seat, no API. For the two sources that emit an artifact rather than design data, token candidates are derived from the emitted stylesheet and land marked as inferred, never silently promoted.

1 · Context

Everything on the receiving side is built. A design declares its token set, its grid and its screens; a convention says where they live; checks resolve the paths and report disagreement. Nothing on the producing side exists: no importer, no code anywhere that reads or writes a token file, no render capture. The one precedent in the repository is a designer's export committed by hand and its values transcribed into a table by a person reading it.

The constraint that shapes this is settled and worth restating, because it rules out the obvious architecture first. source= is provenance and is never resolved — a project whose design tool is gone stays valid. A live read path would make a spec only as available as somebody's seat and as portable as the tool it was written against, and two of the five sources have nothing persistent to query.

So an adapter's job is not to be queried. It lands files, once, as a commit, and is never consulted again — which is also what lets one code path serve five tools whose models agree about nothing except that they can put a folder on a disk.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · An export becomes committed material P1

As a developer, I want to point the tool at a folder a designer exported so that its tokens and renders land in the sidecar without anyone retyping them.

Acceptance: Running an import against a local export writes a token file and any renders into the conventional location; the design that declares them resolves; deleting the export folder afterwards changes nothing.

US2 · Re-importing does not destroy work P1

As a developer, I want to re-run an import when the designer sends a new export so that I get the update without losing what was edited by hand.

Acceptance: A second import over the same source is idempotent where nothing changed, reports what it replaced where something did, and removes nothing that the new export no longer contains.

US3 · An inferred value never passes for a declared one P1

As a reviewer, I want to tell a token the designer stated from one the tool guessed from a stylesheet so that a guess never quietly becomes the contract.

Acceptance: Values derived rather than read are marked as inferred and as not yet reviewed; a declared value always outranks an inferred one; nothing promotes itself.

Edge cases

  • An export carrying annotations in a category this vocabulary has no home for.
  • A source that emits an artifact rather than design data, so there is no token file to read at all.
  • An export whose licence forbids committing its contents.
  • An import interrupted halfway.
  • A re-import that would land under a different identity than the first, silently forking the material.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

An import MUST read from a location already on the local filesystem, and MUST NOT require a network, an account or a credential.

Rationale

What makes one code path serve five tools whose models agree about nothing else. It also removes the seat, the rate limit and the API version from the dependency graph of a spec — a spec that needs somebody's login to validate is not portable.

An import MUST be a discrete operation, and nothing in the ordinary lifecycle MUST invoke it.

Rationale

An adapter is an import-time producer and is never consulted at validate, measure or build time. Folding it into design generation would make every generation depend on an export folder somebody may have deleted.

After an import, the project MUST remain valid with the source location deleted.

Rationale

The property that proves FR-002 rather than asserting it. If deleting the export breaks validation, something is reading it at check time.

Every file an import reads MUST carry provenance — where it came from, what identified it there, and under what licence — and an unknown field MUST be recorded as unknown rather than guessed.

Rationale

The corpus importer's rule, transferred: a fabricated provenance field is worse than a missing one, because it looks like diligence. This project already forbids inventing an origin for a vendored component.

Scoped to landed files while landing and reading were the same act. FR-014 and FR-015 separate them, and the file contributing most of the derived colour is now precisely the one that is read and never copied — so the narrower wording left the material with the most influence over the output as the material with no record at all. The requirement exists so that nothing shapes the project without a record of where it came from; reading is the act that shapes it.

A value the import derived rather than read MUST be marked as inferred and MUST NOT outrank a declared value, and that mark MUST persist until the value is confirmed, after which the record that it was derived MUST remain.

Rationale

Declaration over inference, in both directions — settled elsewhere and unchanged here.

The original was unconditional, which made confirmation impossible to express: the state a confirmed candidate occupies had no wording, and the shipped types fix inferred true and confirmed false so it is inexpressible in code too. The first attempt to add confirmation asserted the transition in a rationale and shipped no delta, leaving the reconciliation inside the newer requirement's prose.

The last clause is the part worth keeping. A confirmed value stops being inferred, and if the record vanishes with the mark then the fact that it was ever observed rather than chosen vanishes too — a reader should be able to tell a token that arrived from a design tool from one somebody decided on.

Newly landed material MUST be marked as not yet reviewed, and that mark MUST be visible to a reader.

Rationale

The corpus does exactly this and says so at the command line. An import is a bulk arrival of somebody else's decisions, and the moment it looks identical to authored material is the moment nobody reviews it.

Re-importing MUST be non-destructive: material the new source no longer contains MUST be reported rather than deleted.

Rationale

An export is somebody's working state, and an element missing from it is as likely to be an export setting as a deletion. Reporting is recoverable; deleting is not.

Re-importing MUST land under the same identity as the first import, and a re-import that would land under a different one MUST be refused.

Rationale

The corpus has already paid for this: a changed configuration silently re-keyed material and minted a second identity for one thing. A fork that happens quietly is worse than a refusal that happens loudly.

A hand edit to landed material MUST survive a re-import, except where the field has a source of truth in the export.

Rationale

Both halves are load-bearing and the second was learned the hard way: protecting a field that does have a source of truth silently desynchronised the copy from the thing it copied.

Where a source emits an artifact rather than design data, the import MUST be able to derive token candidates from any text that artifact carries, and those candidates MUST be presented for confirmation rather than committed as read.

Rationale

Several of the sources emit code, not a token file — the design is what they emitted. Deriving is the only way to serve them, and confirmation is what keeps FR-005 true in practice rather than only in the file.

The original wording reasoned from a stylesheet, and a real export has none: every value is an inline style= attribute. Worse, the markup is a template — screens are produced by iterating over data, with the values computed in the document's own trailing script — so a static reader sees a placeholder where a figure should be. Reading that script as text is reading data, not executing it, and it is where the values are.

What follows is a bound worth stating rather than discovering: colour and spacing are recoverable, and screen and state identity may not be present at all. So this requirement is about values, and never about reconstructing the structure a designer drew. Turning a template's data into declarations is a separate question about who authors a screen.

An imported annotation whose category has no home in the vocabulary SHOULD be reported as unhandled rather than dropped.

Rationale

The category map exists precisely to name the categories with nowhere to go. Dropping one silently would waste the mechanism, and "we looked and there is no home" is a different statement from "we have never heard of this" — the map already distinguishes them.

An import SHOULD refuse to land material whose licence forbids it, and SHOULD say which licence and why.

An import MUST accept an archive as its source location and materialise it, and doing so MUST NOT require a network, an account or a credential.

Rationale

FR-001 requires the source to be on the local filesystem and assigns nobody the job of putting it there. In practice that step is unreachable through the documented path: reading a design tool programmatically returns file content with no way to write it, so material passes through a model's context and a large bundle cannot land at all.

The answer is narrower than a fetcher per tool, which would be the coupling FR-001 exists to prevent. Every one of these sources exports a zip; an archive on disk already satisfies FR-001 as written; and the fetcher seam already takes a location and returns a directory. So one archive fetcher serves every source, the rest of the import cannot tell the difference, and the no-network position is untouched — an archive is opened, never downloaded.

Material that cannot be landed without leaving the project in violation of its own artifact rules MUST NOT be landed, and MUST be reported rather than dropped.

Rationale

FR-003 makes remaining valid the property this slice exists to hold, and says nothing about the landed bytes — so a verbatim copier satisfies it on paper and breaks it in fact. A real export carries a runtime, and landing one produces an error-severity violation of P-11, which is a principle rather than a rule that can be relaxed for this case.

Reporting rather than dropping is not a new posture: FR-011 already establishes it for an annotation category the vocabulary has no home for. This is the same statement about a whole file, and the reason it is written down is that generalising a requirement quietly, in code, is how a distinction loses its argument.

A deliberate consequence: an import may complete having landed less than it read, and a caller must be told which files those were. Silence would look like success.

Reading source material and landing a copy of it MUST be treated as distinct permissions: material that is not landed MAY still be read to derive candidates, and material whose licence forbids a copy MUST NOT be read for that purpose either.

Rationale

Discovered by running a real import and watching it produce almost nothing useful. The file carrying the runtime is also the file carrying the design, so refusing to land it — correctly, per FR-014 — and then ignoring it discarded most of the colour in the export and left FR-010 deriving from whatever happened to be safe.

The two halves fail differently, which is why both are stated. Refusing to read what may not be copied is a permission question and the conservative answer is right. Refusing to read what merely cannot be copied is a safety question answered in the wrong place, and it costs the requirement its best input.

Visible in the output: a value appearing in both the stylesheet and the markup outranks one appearing in neither, which is the ordering a reviewer wants — and it only exists because the unlandable file still counted.

Confirming a derived candidate MUST write it into the project's token set under a name and a change class the confirmer supplies, the tool MUST NOT supply either, the write MUST move the set's version under the versioning policy and MUST refuse a set that has changed since it was read, and a token written this way MUST record that it was derived and confirmed rather than authored.

Rationale

FR-010 presents candidates for confirmation and nothing consumed a confirmation, so a project could declare a token path, validate clean, and hold no tokens.

This spec owns the write because 098 deferred "importing a token set from a design tool, and what its version means on arrival" here in writing, and because 098 ships a reader and a refusal rather than a writer. The first version named 098's mechanism as though it existed; stating the properties the write must satisfy is what an owner does, and leaves 098 free to grow a writer later without this requirement changing.

The change class is the confirmer's, not the tool's. 098 requires every surface to present a release's class as the producer's claim, and its own assumption is that authors classify honestly — so a tool that picks one asserts something its producer never said. That corrects "everything after the name is clerical", which was false: the clerical part is the file, the guard and the bookkeeping.

Non-functional

An interrupted import MUST leave the project in a state that still validates: at most 0 partially written files remain.

The import MUST be exercisable with no live model and no network in continuous integration: at least 1 test covers the derivation path against a stubbed provider, and 0 tests in that tier require a credential.

Rationale

The project's standing rule for anything model-coupled. A real model belongs in the local-only tier, and a check that cannot run without a key is a check that stops running.

Out of scope (deferred to other slices)

  • Querying a design tool over a protocol. Ruled out here rather than deferred reluctantly: it makes a spec as available as a seat, and two of five sources have nothing to query.
  • Deriving anything from an image. This slice reads an emitted stylesheet, which is text, so it needs no vision.
  • Producing renders by driving a build, as opposed to landing ones a designer exported.
  • Comparing anything landed against a running build.

4 · Data model

An import lands files and records where they came from. It owns no long-lived entity of its own.

Entities

Source location
A folder already on disk. Read once, never again, and deletable afterwards without consequence.
Landed material
A token file, renders, and any annotations the export carried, written to the conventional sidecar. Each carries provenance, and an unknown field is recorded as unknown.
Inferred value
A value derived from an emitted artifact rather than read from design data. Marked, never promoted, and presented for confirmation before it lands.
Import identity
What ties a re-import to the material it updates. Stable across runs; a re-import that would change it is refused rather than allowed to fork.

The invariant the whole slice rests on: after an import completes, nothing in the project refers to the source location. That is what makes the design tool replaceable, and it is testable by deleting the folder.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

After importing a local export, the declared paths resolve and the project validates with 0 findings — and still does with the source folder deleted.

Re-importing an unchanged source writes 0 changed bytes. Re-importing a changed one removes 0 files and reports each item the new source no longer contains.

Inferred values that are indistinguishable from declared ones number 0. Landed provenance fields carrying a fabricated value number 0.

A re-import that would land under a different identity is refused 100% of the time, naming both identities.

Imported annotation categories that are silently dropped number 0 — each is landed or reported unhandled.

6 · Assumptions

Designers can export a folder from all five tools. True today for each of them, and the assumption the whole slice rests on — if a tool removes export, this approach loses that tool entirely rather than degrading.

Token candidates derived from an emitted stylesheet are useful enough to confirm rather than rewrite. Not tested. If confirmation turns out to be slower than authoring by hand, FR-010 is the requirement that was wrong, and the fallback — landing the artifact and letting a person transcribe it — is what happens today.

7 · Open questions

None outstanding. The two decisions worth recording are refusals: no live protocol, because it makes a spec as available as somebody's seat and two of five sources have nothing to query; and no vision, because the sources that emit an artifact emit a stylesheet, which is text.
