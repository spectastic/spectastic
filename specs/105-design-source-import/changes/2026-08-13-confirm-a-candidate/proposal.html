Confirm a candidate

Candidates are presented for confirmation and confirmation has no destination. The naming stays human; everything after it is mechanical.

Confirm a candidate

Approved

1 · Intent

The import derives token candidates, marks them inferred and unconfirmed, and writes them where a reader will see them. That is FR-010 working as written — presented for confirmation rather than committed as read — and it stops one step short of anywhere. There is no command, prompt or check that turns a confirmed candidate into a token set.

So a project can declare a tokens= path, resolve it, validate clean, and contain no tokens. That is exactly the state the first real downstream project is in: six candidates in a manifest, a declared token path, and nothing a build could reach for. The declaration is honest and the lifecycle has nowhere to take it.

The reason it stopped there is sound and survives: a token's name is the part a human supplies. #f7f5f1 is a fact; color.surface is a decision about meaning, and a wrong name is worse than no name because it looks decided. That argues against automating the naming. It does not argue against automating anything else.

2 · Scope

In scope

  • A confirmation step that writes a valid token set from candidates a human has named.
  • Each written token recording that it was derived and then confirmed, rather than authored outright.

Out of scope

  • Naming a candidate. The one part that is a decision about meaning. defer-to=never.
  • Choosing which candidates matter. Occurrence counts are evidence, not a threshold. defer-to=never.
  • Pairing a light and a dark literal into one mode-aware token. A stronger signal than counting, needing structural comparison. defer-to=TBD-token-mode-pairing.

3 · Approach

Split the act. Naming is a decision and stays with the person; producing a well-formed, correctly-versioned token set from named rows is clerical and belongs to the tool. Today the split is in the wrong place — the human is left holding both halves, and the clerical half is the one they are most likely to get subtly wrong, since the token set carries a version whose bump policy is a whole spec.

Provenance is what makes this more than a file writer. A token that arrived through an import and was confirmed is a different thing from one somebody wrote, and a reader should be able to tell — the import already refuses to guess an unknown field and records it as unknown, and the same discipline applies to how a value came to be a token. That is also what keeps FR-005 true after confirmation: a confirmed value is no longer inferred, and the record of having been inferred should not vanish with the marker.

Deliberately not scaffolding a token set with placeholder names for a human to edit. A placeholder that ships is worse than an absent file, because it looks decided — the same reason the candidates carry no names in the first place.

4 · Deltas

Confirming a derived candidate MUST write it into the project's token set under a name the confirmer supplies, the tool MUST NOT supply or suggest that name, and a token written this way MUST record that it was derived and confirmed rather than authored.

Rationale

FR-010 presents candidates for confirmation and nothing consumes a confirmation, so a project can declare a token path, validate clean, and hold no tokens. The first real downstream project is in exactly that state.

The split is deliberate. A name is a decision about meaning and a wrong one is worse than none because it looks decided — so the tool never supplies one, which is the same reason a candidate is derived without a name. Everything after the name is clerical: a well-formed set, correctly versioned under a bump policy that is its own spec, is work a person should not be doing by hand.

The provenance clause is what keeps FR-005 true past confirmation. A confirmed value stops being inferred, and if the marker simply disappears the fact that it was ever observed rather than chosen disappears with it. A reader should be able to tell a token that arrived from a design tool from one somebody decided on.

5 · Risk register

Self-run rather than delegated. Recorded rather than glossed.

It writes into an artifact another spec owns, including its version

The token set is 098's, and 098 is unusually strict about it: a compare-and-swap guard, a bump policy classified at the highest tier of the change, forward-only binding so a bump does not reopen shipped screens. A writer in this spec that adds tokens is performing a versioned change to somebody else's artifact, and the obvious first implementation — append rows, leave the version alone — would be a silent policy violation.

Mitigated. The requirement says write into the token set without saying how, so the implementation must go through 098's own mechanism rather than around it. Named here as the primary constraint on the task, and the tasks are written so the writer is a caller of that mechanism rather than a second editor of the same file.

The confirmation surface could re-import the naming problem sideways

FR-010 forbids committing a candidate as read. A confirmation flow that lists candidates and takes names in bulk is one careless default — a pre-filled name field, an accept-all — away from doing exactly that while appearing to have asked. The corpus importer already learned the neighbouring lesson: offering inferred material for bulk confirmation converts a weak signal into a strong-looking one.

Mitigated. The requirement forbids the tool supplying or suggesting a name, which rules out the pre-filled field specifically rather than only the automatic one. A candidate with no name supplied is not confirmed and is not written.

Arguably 098's change, not 105's

The output is a token set. A reader looking for how tokens get authored would look in 098 and find nothing.

Accepted, with the reason recorded. The gap is in the import's own trail — FR-010 raises a candidate and abandons it — so the requirement to finish that trail belongs where the trail starts. 098 owns what a token set is and how it is versioned; this owns how imported material reaches one.

6 · Tasks

  • A confirmation step taking candidate and name; refuses a candidate with no name; never suggests one.
  • Write through 098's own token-set mechanism, so the version bump and its compare-and-swap guard apply — never as a second editor of that file.
  • Record derived-and-confirmed provenance on each written token.
  • Tests: a named candidate lands with provenance; an unnamed one is refused; nothing is suggested; the version moves per 098's policy; a stale token set is refused rather than clobbered.

7 · Open questions

None outstanding. Mode pairing is deferred as a named slug rather than left open.
