Own the write

FR-016 writes through a mechanism that does not exist, and 098 defers the question back here. One of the two must own it.

Own the write

Approved

1 · Intent

An independent pass found that FR-016 rests on something that is not there, and that the deferral chain is circular.

Its task says to write through "098's own token-set mechanism, so the version bump and its compare-and-swap guard apply". Opened: 098 ships readTokenSet — a reader — and assertTokenSetVersion, a guard that throws and returns nothing. Neither writes a token or bumps a version; both assume a caller that already authored the release. And 098's own out-of-scope defers "importing a token set from a design tool, and what its version means on arrival" to the slug this spec drains. 098 handed the question here; FR-016 handed it back.

The register dispositioned that mitigated because the requirement "says write into the token set without saying how". Silence is not a constraint on an implementation; it is the absence of one — and the corpus commits the rule that was broken: a must-tier decision resting on an unverified fact is accepted, naming who accepted it, never mitigated.

A second claim in the same change is also false. "Everything after the name is clerical" — but a release declares a change class, which 098 requires every surface to present as the producer's claim. A tool that classifies a bump asserts something its producer never said.

2 · Scope

In scope

  • Making this spec own the write, since 098 deferred it here and nothing else can.
  • Correcting the clerical claim: classification is the human's, alongside the name.
  • Giving FR-005's inferred mark a stated end, so a confirmed value is expressible.

Out of scope

  • Building 098 a writer. If the versioning surface should grow one, that is 098's change to argue. defer-to=098-token-set-versioning.
  • Suggesting a name the export itself declares. Real, and it is reading rather than inference, so it deserves its own argument. defer-to=TBD-declared-token-names.

3 · Approach

Stop passing the question. 098 deferred arrival-versioning to this slug in writing, so this spec owns it — and owning it means saying what the write must satisfy rather than naming a mechanism and hoping. The requirement now states the properties: the version moves under 098's policy, the guard refuses a stale set, and the change class comes from the person, not the tool.

The clerical framing was the error underneath. Splitting naming from everything else looked clean and put a claim on the tool's side of the line: 098 requires a release's class to be presented as the producer's claim, and its own stated assumption is that authors classify honestly. So the human supplies a name and a class; what is genuinely clerical is the file, the guard and the bookkeeping.

FR-005 needs the smaller fix to stop contradicting all this. It says unconditionally that a derived value must stay marked inferred and must not outrank a declared one — while confirmation exists precisely to end that state. The first change asserted the transition in a rationale and shipped no delta, so the reconciliation lived inside the newer requirement's prose. The conflict is already in code: the candidate type fixes inferred true and confirmed false, making a confirmed candidate literally inexpressible.

4 · Deltas

What changes: the write is owned here rather than delegated to a mechanism that does not exist, and the change class joins the name on the human's side.

Confirming a derived candidate MUST write it into the project's token set under a name and a change class the confirmer supplies, the tool MUST NOT supply either, the write MUST move the set's version under the versioning policy and MUST refuse a set that has changed since it was read, and a token written this way MUST record that it was derived and confirmed rather than authored.

Rationale

FR-010 presents candidates for confirmation and nothing consumed a confirmation, so a project could declare a token path, validate clean, and hold no tokens.

This spec owns the write because 098 deferred "importing a token set from a design tool, and what its version means on arrival" here in writing, and because 098 ships a reader and a refusal rather than a writer. The first version named 098's mechanism as though it existed; stating the properties the write must satisfy is what an owner does, and leaves 098 free to grow a writer later without this requirement changing.

The change class is the confirmer's, not the tool's. 098 requires every surface to present a release's class as the producer's claim, and its own assumption is that authors classify honestly — so a tool that picks one asserts something its producer never said. That corrects "everything after the name is clerical", which was false: the clerical part is the file, the guard and the bookkeeping.

What changes: the inferred mark gets a stated end, so a confirmed value can exist without contradicting the requirement that created it.

A value the import derived rather than read MUST be marked as inferred and MUST NOT outrank a declared value, and that mark MUST persist until the value is confirmed, after which the record that it was derived MUST remain.

Rationale

Declaration over inference, in both directions — settled elsewhere and unchanged here.

The original was unconditional, which made confirmation impossible to express: the state a confirmed candidate occupies had no wording, and the shipped types fix inferred true and confirmed false so it is inexpressible in code too. The first attempt to add confirmation asserted the transition in a rationale and shipped no delta, leaving the reconciliation inside the newer requirement's prose.

The last clause is the part worth keeping. A confirmed value stops being inferred, and if the record vanishes with the mark then the fact that it was ever observed rather than chosen vanishes too — a reader should be able to tell a token that arrived from a design tool from one somebody decided on.

5 · Risk register

The findings this corrects came from an independent critic; no second independent pass was run on the correction. Self-authored, and the dispositions below are deliberately accepted where nothing mechanically closes the gap — which is the lesson from the register this replaces.

Owning the write puts versioning logic in the spec that does not own versioning

098 owns what a token set is and how its version moves. This requirement now obliges a write that bumps under that policy and honours its guard — implemented here. Two specs will hold knowledge of the same policy, and the copy in this one can drift from the original without anything noticing.

Accepted. There is no mechanism preventing the drift, which is why this is accepted rather than mitigated. The alternative is worse and was just tried: naming a mechanism in another spec that does not exist, and calling the gap closed. If 098 later grows a writer, this requirement is already phrased as properties rather than as a call, so adopting it changes an implementation and not a requirement.

Requiring a class as well as a name raises the cost of confirming anything

A person confirming six candidates now supplies six names and a change class, and must know 098's bump policy to pick one. The likely outcome is that confirmation gets used rarely, or that a single class is chosen for everything without much thought — which is the honest-classification assumption 098 already rests on, now leaned on harder.

Accepted. The alternative is the tool asserting a producer's claim, which 098 forbids in substance. A class per release rather than per token is the obvious way to make the cost proportionate, and that is an implementation shape rather than a requirement change.

The name-suggestion prohibition survives unexamined, and it is probably wrong

FR-016 still forbids the tool to supply a name, and a design export commonly declares one — --color-surface: #f7f5f1. Carrying that forward is reading, which this spec says outranks inference in both directions, so the prohibition as written forces a human to retype a name the source supplied. It is deferred here rather than fixed.

Accepted, with the reason recorded. Fixing it means distinguishing a name the tool invented from one it read, which is a real requirement change and belongs in its own proposal rather than riding along in a correction. Named as a slug so it is findable. Also worth stating: "suggest" is not checkable at the P-8 bar, and the sibling clause — a candidate with no name supplied is not written — is what a gate can actually test.
