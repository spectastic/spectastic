A declared token is not a guess

The import protects a declaration from being overwritten by an inference. It has no way to recognise one.

Status Proposed Change ID 2026-08-17-a-declared-token-is-not-a-guess Spec 105-design-source-import Author Brian Corbin · @briancorbinxyz Created 17 Aug 2026 Source 105/T-019 Targets 2 requirements — 1 added, 1 modified Read time

A real import left 45 colour candidates unconfirmed beside an empty token set. FR-010 is written entirely in terms of derivation — candidates inferred from an artifact, presented never committed — which is right, and is what US3 protects. The gap is its mirror: a declared value has no path in either.

Sharper than the card recorded. The importer mines the declared token file itself: a named, typed DTCG token comes back INFERRED — UNCONFIRMED, asking a human to confirm a value that was already declared. That is US3 inverted — not an inference passing for a declaration, but a declaration presented as an inference.

1 · Intent

The importer has one mode where it needs two. Derivation is the careful path for a source that emits an artifact and nothing else, and every guarantee around it is sound. But a source that emits real design data gets the careful path too, so its declarations arrive as guesses.

Reproduced with a two-token export: design.tokens.json lands in the sidecar with provenance and a content hash — the verb's own --help promises it "lands its token file" — and nothing recognises it as the token set. It is not wired to <spec-visual tokens=>, its values are not reconciled against the derived ones, and its own colours are re-derived from it and reported unconfirmed.

What makes this worth a requirement rather than a patch: the fix has to say what happens when a declared token and a stylesheet value disagree, and neither silent answer is available. Preferring the token hides a design that drifted from its own system — the off-system case the measurement work exists to catch. Preferring the stylesheet lets an inference overwrite a declaration, which US3 forbids outright.

2 · Scope

In scope

  • Recognising a DTCG token file in an export as the declared token set.
  • Narrowing derivation so it never mines a declaration, and never re-offers what one already covers.

Out of scope

  • Asking a design tool for anything. 105's import is a local export read once and then forgotten, and reading a file the export already contains stays inside that boundary. defer-to=never.
  • What a disagreement between a declared token and a derived value means. Dropped from this proposal rather than answered, because its antecedent is not observable: a derived candidate carries a value and nothing else — deriveTokenCandidates is a colour regex, and the module states the omission is deliberate, since naming a candidate "would be the tool inventing the one thing the human is uniquely able to supply". So there is no role on which a declared token and a derived value could be compared, and a requirement keyed on one would ship as prose with no runtime. Reopening it needs a role-attribution mechanism first. defer-to=TBD-token-role-attribution.
  • Token kinds beyond colour for any future disagreement check. Colour is what derivation produces today; a dimension or duration candidate has no derivation path to disagree with. defer-to=TBD-token-kind-derivation.
  • Correcting the --help copy, which promises this today. A §6 task, not a requirement.

3 · Approach

Recognition by shape rather than filename: a JSON file whose entries carry $type and $value is a DTCG token file by construction, whatever the exporting tool named it.

4 · Deltas

What changes — a token file in an export is recognised as a declaration and landed as one. It is not written into the project's token set; adoption stays on the confirmed path FR-016 governs.

Where an export carries a token file in a recognised token format, the import MUST land it as a declared token source alongside the export's other material, and MUST NOT mark its values inferred or present them for confirmation. Landing a declared token source MUST NOT write the project's token set.

Rationale

Recognition is by shape, not by name: a token file is identifiable from its own contents, and depending on what a tool chose to call it would make the behaviour a lottery across sources. The project's own token set already uses that shape, so the test is verified against committed material.

The second clause is the point of the change. Asking a human to confirm a named, typed token is not caution — it is the tool failing to read what it was given, and it produced forty-five such requests in one real import.

The third clause is the one an earlier draft got wrong, and the correction matters more than the feature. That draft had the import write "the project's declared token set" directly, which would have performed a strictly larger write with strictly fewer guards than FR-016 demands for a single value — no confirmer, no change class, no version movement, no refusal on a set that moved underneath it — and would have routed around 098 entirely. It would also have overwritten hand-authored tokens on every subsequent import. Landing a declaration is not adopting it; the two are different acts and only the second touches the versioned artifact.

"Alongside the export's other material" rather than a named location, deliberately: the import writes where --into points, which is feature-scoped material under 094 FR-002. The project's token set lives at the root under FR-001 and is a different artifact with a different owner, which is precisely why this requirement must not reach it.

What changes — derivation gains a boundary: it never mines a declaration, and never re-offers a value one already carries. Nothing else — the ability to derive from an artifact, and the present-never-commit rule, are carried through word for word.

Where a source emits an artifact rather than design data, the import MUST be able to derive token candidates from any text that artifact carries, and those candidates MUST be presented for confirmation rather than committed as read. Derivation MUST NOT read a recognised token file as an artifact to mine, and MUST NOT present a candidate whose value the declared token set already carries.

Rationale

Several of the sources emit code, not a token file — the design is what they emitted. Deriving is the only way to serve them, and confirmation is what keeps FR-005 true in practice rather than only in the file.

The original wording reasoned from a stylesheet, and a real export has none: every value is an inline style= attribute. Worse, the markup is a template — screens are produced by iterating over data, with the values computed in the document's own trailing script — so a static reader sees a placeholder where a figure should be. Reading that script as text is reading data, not executing it, and it is where the values are.

What follows is a bound worth stating rather than discovering: colour and spacing are recoverable, and screen and state identity may not be present at all. So this requirement is about values, and never about reconstructing the structure a designer drew. Turning a template's data into declarations is a separate question about who authors a screen.

Added by this change. The two clauses above bound where derivation stops. The first fixes an inversion rather than a nuisance: a token file is text, so the pattern matched its declared values and returned them as guesses about themselves. The second is what the complaint was actually about — a project that supplies real tokens should be asked to confirm nothing about them, and suppressing only the token file while still offering every stylesheet colour that matches a declared token would leave the list nearly as long.

The three paragraphs above this one are carried verbatim from the live requirement, and saying so matters: a MODIFY replaces the whole <spec-requirement> element, rationale included, so an author who retypes only the normative sentence deletes everything else without the diff showing it. An earlier draft of this delta did exactly that and would have dropped the bound T-008 cost two real imports to establish.

This is the fifth silent narrowing this session and the second new mechanism: not a dropped conformance keyword but a dropped rationale, which the conformance-dropped guard cannot see because rationale carries no <spec-rule>.

Blast radius checked rather than assumed. Every MODIFY applied today was diffed against its pre-apply state at sentence level: 088 REQ-CHANGE-006 lost nothing, and 003 FR-009's one missing sentence is the enumeration it deliberately replaced. The mechanism was live all session and did not bite; it would have here.

FR-017 wrote the project's token set with fewer guards than FR-016 requires for a single value, and its target was undefined

FR-016 requires a name and change class the confirmer supplies, that the tool supply neither, that the write move the set's version, and that it refuse a set which changed since it was read. The draft FR-017 had the import write that same artifact — a whole set — with none of them, and forbade the confirmation gate FR-016 depends on. It also routed around 098 entirely, and would have overwritten hand-authored tokens on every later import. Compounding it, "the project's declared token set" had no referent: --into takes an arbitrary directory, while 094 puts the project set at the root and feature material beside the spec.

Decisive; FR-017 is narrowed to landing rather than adopting. A token file is now landed as a declared token source alongside the export's other material, with an explicit clause that it must not write the project's token set. Landing a declaration and adopting it are different acts and only the second touches the versioned artifact — so FR-016 keeps every guard it has, and the location question dissolves because the requirement no longer reaches the root.

It still fixes the complaint that started this: the forty-five candidates disappear through FR-010's boundary, not through writing anything.

The proposal scoped what a disagreement means while excluding any way to detect one, so FR-018 could never fire

FR-018 keyed on "the same role", and a derived candidate has no role: deriveTokenCandidates is a colour regex, and the module states the omission is deliberate — naming a candidate "would be the tool inventing the one thing the human is uniquely able to supply". Under that reading the antecedent is unsatisfiable and the requirement ships as prose with no runtime. Under the alternative — compare by value — FR-010's new clause suppresses every equal value, so what remains is every derived colour not in the declared set: the long list this proposal exists to shorten, re-emitted under a new name.

FR-018 is withdrawn from this proposal rather than reworded. Both readings fail, and that is a signal the question is upstream of the requirement: comparison needs role attribution, which nothing produces today. Deferred as TBD-token-role-attribution with the reasoning recorded, so a later slice starts from why it could not be written rather than rediscovering it.

Worth stating plainly: this was the part of the proposal I was most confident in, and it was the least buildable.

A must-tier requirement rests on an assumed fact with an empty risk register

KB-0001@2026-07-25 forbids a must-tier decision resting on an assumed fact without an explicit accepted risk naming who accepted the gap and why. §3's fourth row — that other tools' exports carry token files — is marked assumed and concedes that no observed export carried one; the file in the reproduction was authored by hand. FR-017 is must-tier and that fact is its antecedent. This spec has been bitten here before: T-011 cites the same edition and records that such a gap is accepted, never mitigated, which would assert it closed.

Correct, and this finding is the artifact the rule asks for — it exists to be dispositioned accepted with a by=, which is the recorded form the corpus requires. The gap is real and narrow: recognition is shape-based, so the requirement is correct whether or not a tool ever emits one, but its trigger has not been observed in the wild. Accepting names that honestly. Demoting to should-tier was considered and rejected — a should-tier obligation with no prompt is what produced filenames-as-keys for every contract in the estate, which 076 records.
