What the design tool actually is

Two refusals rest on claims that are false or untested, one workflow is unmodelled, and an export is an archive nothing agrees to open.

Status Applied Change ID 2026-08-18-what-the-design-tool-is Spec 105-design-source-import Author Brian Corbin · @briancorbinxyz Created 18 Aug 2026 Targets 5 content deltas — no requirement changes Read time

This spec models one design tool as an artifact emitter with nothing to query and no readable document. A live read path exists, its exports are archives rather than folders, and a design system can be pushed into it incrementally — a workflow the spec never mentions. Five corrections to prose that is false or untested. No requirement changes: the adversarial pass established that the one behaviour this proposal tried to add is already required by FR-013 and merely unbuilt.

What the design tool actually is

Applied

1 · Intent

Five triage cards on this spec say the same thing from different angles: the design tool it was written against is not the tool it describes. Two refusals rest on claims that turn out to be false or never checked, one first-class workflow is unmodelled, and the export shape the whole slice assumes is wrong.

They were deliberately batched. T-001 says so in its own Fix — “amended once rather than five times” — and defers until the experiment that motivated it has run. It has now run: a real design was imported into a real project, which produced a handover document and the findings this proposal carries.

The draft of this proposal contained the same class of defect it exists to remove. It added a requirement to accept an archive, arguing that “nothing agrees to open one” — while FR-013 has required exactly that since 13 August. And its correction to the no-vision refusal reinstated a stylesheet that FR-010's own rationale records as verified absent. Both were caught by the adversarial pass, both are recorded in §5, and what remains is prose corrections only.

2 · Scope

In scope

  • Correcting the live-protocol refusal, which is factually wrong.
  • Downgrading the no-vision refusal from a settled fact to what it actually is.
  • Naming the real export shape, and deciding who opens an archive.
  • Recording the design-system sync loop as out of scope, with the reason.
  • Recording the ecosystem's own default handoff, which bypasses this verb.
  • Correcting the source-reading seam's own comment, which still carries the false premise.

Out of scope

  • Building the sync loop. This proposal records that it exists and why it is not this spec's; the work is its own slice.
  • Producing renders. Unchanged by this proposal.
  • Building a live read path. The refusal is corrected on its real grounds — portability — which leaves the refusal standing and its stated reason honest.
  • Settling who supplies the version a token write produces. Split out after the adversarial pass observed it is a different investigation carrying a cross-spec obligation none of these five share — 098's out-of-scope still says the question lives elsewhere, and T-013's own diagnosis records that half as missing. It goes as its own proposal paired with the 098 amendment, so one topic carries its own obligation.
  • Implementing archive expansion, and bounding what an expansion may write. FR-013 already requires the behaviour and no code implements it, so that is an implementation card rather than a requirement.

3 · Approach

Every delta is content rather than a requirement change: they correct prose in §6 and §7 and add entries to the out-of-scope block, so each carries a <spec-diff> and no <spec-requirement>. Applying this changes no requirement body; the edits are §6 tasks.

Each refusal is stated twice. Both live in §7 Open questions and in the out-of-scope block, in nearly the same words. A correction that touches one leaves the spec disagreeing with itself, so D2 and D3 each edit both places. This is the kind of duplication that makes a correction look done when it is half done.

On the splitting nudge. The draft carried seven deltas and defended batching on the grounds that splitting would leave the spec calling an export a .zip while nothing agreed to open one. That defence was void — FR-013 agrees to open one — and the pass removed two deltas rather than splitting them. What remains is five corrections from one research pass, comfortably inside the nudge.

4 · Deltas

One <spec-delta> per requirement or content region touched. target= links to the live spec. op= is one of added | modified | removed | renamed; a missing or invalid op renders visibly broken.

What changes: the live-protocol refusal keeps its answer and loses its false reason. The refusal stands; the grounds move from absence to portability. Stated in §7 and again in the out-of-scope block, so both are edited.

no live protocol, because it makes a spec as available as somebody's seat and two of five sources have nothing to query no live protocol, because it makes a spec as available as somebody's seat — not because there is nothing to query, which is false for at least one source

The tool this spec was written against exposes project listing, file listing and file reading, and the editor ships a first-class client for them. An implementer reading the current wording would restate a claim that is checkably wrong, which is the whole cost: the decision was right and its stated reason was not, so nobody can re-derive it.

What changes: the no-vision refusal stops naming a stylesheet, because this spec has already established there isn't one, and rests on what a source actually emits: text. Stated in §7 and again in the out-of-scope block, so both are edited — two diffs, not one.

no vision, because the sources that emit an artifact emit a stylesheet, which is text no vision, because the sources examined emit their values as text — inline attributes and a template's own script — and where one does not, the fallback is to land the artifact and let a person transcribe it Deriving anything from an image. This slice reads an emitted stylesheet, which is text, so it needs no vision. Deriving anything from an image. This slice reads text the artifact carries, so it needs no vision.

The first draft of this correction said “the sources examined emit a stylesheet”, which FR-010's own rationale already falsifies: “a real export has none: every value is an inline style= attribute.” The refusal was always right; what it named was wrong, and naming it wrong twice would have been worse than leaving it. The residual — one source verified, four assumed — is recorded as an accepted risk in §5 rather than left in prose.

What changes: the assumption every part of this slice rests on names the wrong artifact. Exports are archives, not folders.

Designers can export a folder from all five tools. Designers can export from all five tools, as an archive or a folder depending on the tool.

The behaviour half of this correction is FR-018. Separating them would leave the spec saying an export is an archive while no requirement accepts one.

What changes: a new out-of-scope entry recording the design-system sync loop.

<li defer-to="TBD-design-system-sync">Pushing this project's own design system into a design tool. The tool this spec was written against supports it as a first-class, incremental, plan-then-write workflow with a dedicated project type — the opposite direction of travel from an import, and available whether or not anyone uses it.</li>

Out of scope rather than modelled, on three arguments that agree. 094 already splits project-scoped material — the design system — from feature-scoped, and this carries the former. This spec's D-001 chose portability, and a tool-specific write protocol is its opposite. And folding an outbound push into a spec named import makes its name lie.

The entry deliberately does not repeat T-004's suggestion that the loop may remove the need to infer. T-009 supersedes it on evidence: the real project attached no design system, and its export carried zero token references and roughly forty raw hex literals, so derivation is more load-bearing than T-004 supposed. Carrying the original wording would have left a future reader written grounds to reopen FR-010's necessity.

What changes: a new out-of-scope entry acknowledging the ecosystem's own handoff.

<li defer-to="never">Competing with the design tool's own handoff. It ships a first-class action that lands work in the working directory directly, which is what most people will reach for. This spec is the path for a source that arrives as files, not a replacement for that action.</li>

The spec is not wrong here, it is silent — and silence about a competing default is a different defect from a false claim, which is why this is the smallest of the five corrections.

5 · Risk register

Populated by the adversarial risk pass. This proposal triggers the heuristic on two counts: it modifies a must-tier requirement and adds another.

FR-018 re-states shipped must-tier FR-013 minus its no-network clause, on a premise that is false in the same way as the claims this proposal exists to correct.

Live FR-013: “An import MUST accept an archive as its source location and materialise it, and doing so MUST NOT require a network, an account or a credential.” — against FR-018's rationale, “nothing forbids one and nothing agrees to open one.”

Verified and upheld. FR-013 applied on 13 Aug and is T-010's recorded resolution; materialise and expand it itself are one act. The gap is real but is an implementation gap — no archive handling exists under packages/core/src/visual/, confirmed by reading source-fetcher.ts — so FR-013 is shipped and unbuilt, and a second requirement governing one behaviour reproduces the doubly-stated defect §3 complains about. Recommend withdrawing the FR-018 ADD, closing T-002 against FR-013, and re-filing expansion as an implementation card. Also unaddressed by either requirement: expanding somebody else's archive is a filesystem-reach change with no bound on traversal entries, symlinks or decompression ratio.

The MODIFY removes one undischargeable MUST and inserts another; the replacement needs an ordering a sibling spec forbids.

Proposed: “the write MUST refuse a version the versioning policy disallows” — against 098 NFR-001, “Version comparison MUST be equality only, with at most 0 orderings computed.”

Upheld. Deciding a version is disallowed relative to a class is a relation between two versions, which the strong reading makes an ordering. It also re-creates the substitution T-014 deleted bumpVersion to avoid, and would ship non-conformant on day one. Recommend bounding the clause to what is decidable without ordering — supplied, well-formed, and unequal to the from-version — and stating that agreement with the declared class is deliberately unchecked because the policy is prose.

Wrong topic group, and it closes T-013 while leaving the cross-spec half T-013 itself records as missing.

T-013's own diagnosis: “I dropped the second half of T-011's own stated fix: 098's out-of-scope is still unamended, so the circularity is only half broken.” This proposal carries no delta and no task against 098.

Upheld. Five deltas are one research pass about what the design tool is; this is a different investigation with a cross-spec obligation none of the others carry, and §3's batching defence never mentions it. Recommend splitting it into its own proposal paired with the 098 MODIFY, so one topic carries its own cross-spec obligation.

The corrected no-vision refusal re-asserts a stylesheet the spec has already recorded as verified absent — an assumed fact presented as verified, under a must-tier requirement with no accepted risk.

KB-0001@2026-07-25: a must-tier decision may not rest on an assumed fact without an explicit <spec-risk status="accepted">. Live FR-010 rationale: “a real export has none: every value is an inline style= attribute.”

Upheld and verified against the live requirement. The correction as drafted would reinstate a claim this spec already falsified and paid for. Recommend saying what FR-010 says — the sources examined emit text, inline attributes rather than a stylesheet — and recording the residual as one accepted risk naming verified-for-one-source and assumed-for-the-rest. The delta also claims to edit both §7 and the out-of-scope entry while supplying one diff; the second is required or the retired sentence survives.

The no-vision refusal is verified for one source of five and assumed for the rest.

KB-0001@2026-07-25 — a must-tier decision may not rest on an assumed fact without an explicit accepted risk naming who accepted the gap and why.

Accepted rather than mitigated, because the evidence cannot be manufactured: exports from one tool were opened and examined directly, and the remaining four have not been. The fallback if a source emits neither a stylesheet nor inline text is already named in the spec — land the artifact and let a person transcribe it — so the cost of being wrong is a slower path, not a broken one. Recorded here so the gap is bookkeeping rather than prose.
