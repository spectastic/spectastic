Change proposal · 105-design-source-import

Land what breaks nothing

The importer is a copier with one safety rule. Deciding what belongs in a project is a different job, and not this one's.

Status Applied Change ID 2026-08-15-land-what-breaks-nothing Spec 105-design-source-import Author Brian Corbin · @briancorbinxyz Created 15 Aug 2026 Targets 1 requirement — 1 modified Read time

A real import landed support.js — 68 KB of the design tool's own runtime — unexamined, because FR-014's safety check inspects only HTML-shaped files. Triage T-018 asked whether that is a bug. It is not: FR-014 governs the project staying valid, and a loose script breaks no artifact rule. What was wrong is that nobody chose it — the behaviour fell out of an extension list added for an unrelated reason. This closes one ground for withholding, deliberately and narrowly, so the next reader finds a decision rather than an accident.

Land what breaks nothing

Applied

1 · Intent

The first real import of a design export landed the design tool's viewer runtime into the project's visual sidecar: 68 KB of minified JavaScript, self-labelled "GENERATED from dc-runtime/src/*.ts — do not edit". It landed because landingWouldViolate only inspects .html, .htm, .xhtml and .svg, and a bare .js is none of those.

That reads like a hole, and the surface argument for closing it is strong: the import refuses the design file for carrying a runtime and then keeps the runtime for the file it refused. Stated that way the asymmetry looks absurd, and it is the reason this was raised.

It is still the wrong fix, because it misreads what FR-014 is for. That requirement exists to protect FR-003 — the project stays valid after an import — and it says so: material that cannot be landed "without leaving the project in violation of its own artifact rules." A loose script violates none. It is not parsed as an artifact, no rule reads it, and validate is clean with it on disk. The asymmetry is real and it is not FR-014's asymmetry: the design file is refused because landing it would break the rules, not because runtimes are unwelcome.

Refusing it would mean the importer deciding what belongs in a project rather than what is safe to copy — a judgement with no crisp test, which would need a heuristic, and which would put this verb in the business of curating somebody else's export. The importer is a copier with one safety rule. Every landed file already carries provenance and a not-yet-reviewed mark, which is the mechanism for "this arrived from elsewhere and nobody has vouched for it" — and it applies to a runtime exactly as it applies to a stylesheet.

So the behaviour stays and the requirement stops leaving it to inference. What was genuinely wrong is that the scope was an accident: the extension filter exists because a README.md describing a <script> was being refused, and the consequence for real scripts was never considered.

2 · Scope

In scope

  • Stating FR-014's scope in the requirement: it governs the project's artifact rules, so being executable is not on its own a ground to withhold. Bounded to that ground — the other grounds this spec establishes, notably FR-012's licence refusal, are untouched.
  • Recording why, so the asymmetry a reader will notice — a refused design file whose runtime is kept — is answered where they find it rather than re-raised.

Out of scope

  • Refusing scripts by extension, refusing a design tool's scaffolding generally, and whether a project wants a 68 KB runtime in its sidecar. These are one question at three sizes — a runtime is a script and scaffolding is both — so they get one deferral rather than two permanent closures and a slug for their own superset. Declined now, on the reasoning in §1: it would widen a safety rule into a curation rule and cost the requirement its crisp test. Reopening it needs a propose against FR-014, and the <spec-warning> below names what evidence would justify one. defer-to=TBD-import-material-curation.
  • The third option triage T-018 offered — land it, but record it as a tool runtime rather than design data. Not taken, and worth naming so a reader can see it was weighed: it needs a test for "is this a runtime" that the previous item just declined to invent, and the manifest already records what the import knows about the file. defer-to=TBD-import-material-curation.

4 · Deltas

What changes: the scope is stated rather than inferred. No behaviour moves — this makes an accident into a decision.

Material that cannot be landed without leaving the project in violation of its own artifact rules MUST NOT be landed, and MUST be reported rather than dropped. Material MUST NOT be withheld on the ground that it carries or is executable content when landing it breaks no such rule; withholding on other grounds this spec establishes is unaffected.

Rationale

FR-003 makes remaining valid the property this slice exists to hold, and says nothing about the landed bytes — so a verbatim copier satisfies it on paper and breaks it in fact. A real export carries a runtime, and landing one produces an error-severity violation of P-11, which is a principle rather than a rule that can be relaxed for this case. Reporting rather than dropping is not a new posture: FR-011 already establishes it for an annotation category the vocabulary has no home for.

The second sentence is new and is a boundary, not a permission. It is deliberately narrow: it closes one ground for withholding — this file is executable — and leaves every other ground this spec establishes untouched, including FR-012's licence refusal, which withholds on permission rather than on safety and is shipped behaviour. An earlier draft said material breaking no artifact rule must be landed regardless of what it is, which would have made that refusal non-conformant on the day this landed.

A first real import landed the design tool's own viewer runtime — a bare .js, which no rule parses and which validate is clean alongside. The reflex is to refuse it, and the asymmetry invites that: the design file is refused for carrying a runtime while its runtime is kept. Note the first paragraph's "landing one produces an error-severity violation of P-11" is about the HTML case that motivated it — P-11's deterministic half is scoped to an artifact, and a loose script is not one.

That asymmetry is not this requirement's. The design file is refused because landing it would break the artifact rules, not because runtimes are unwelcome; the two files differ in what they do to the project, not in what they are. Refusing by kind would turn a safety rule into a curation rule — deciding what belongs rather than what is safe — and that judgement has no crisp test, so it would need a heuristic and would put this verb in the business of editing somebody else's export.

What the import asserts about landed material is where it came from and that nobody has reviewed it — the mechanism for unvouched material, covering a runtime exactly as it covers a stylesheet. Stated as the reason rather than as a limit, because the manifest legitimately says more elsewhere: which files were not landed, and what the project holds that the export no longer does. A project that does not want the file removes it or does not commit it, which is a project's decision and not a copier's. Recorded because the scope was previously an accident — the extension filter that lets a script through exists to stop a README being refused for describing one (triage T-018).

5 · Risk register

Findings from the adversarial pass. Statuses stay identified until the author dispositions them.

Run before apply. The critic confirmed the proposal's central claim — a bare .js genuinely breaks no artifact rule, and no CI glob reaches one — and then found the argument was recorded with the wrong modal verbs. Three findings changed the artifact.

The draft carried a second MUST nobody needed, and it foreclosed the option T-018 recommended

The new sentence bundled two obligations, and the second — "its provenance and unreviewed state MUST be the whole of what the import asserts about it" — served nothing in the argument and was already false about shipped behaviour: renderManifest asserts "Not landed" and "No longer in the export", neither of which is provenance or review state. It also made T-018's middle option — land it but record it as a runtime — a must-tier violation, so the cheapest answer to a worse import would have needed another propose.

Draft response — clause removed. The requirement now closes one ground for withholding and asserts nothing about what the manifest may say. The middle option is named in §Scope as weighed-and-not-taken rather than foreclosed. Separately, the retained rationale's "landing one produces an error-severity violation of P-11" is now scoped to the HTML case it was written about — P-11's deterministic half applies to an artifact, and a loose script is not one, so carrying that sentence forward unqualified put the argument on both sides of the same word.

"MUST be landed regardless of what it is" would have made the shipped licence refusal non-conformant

FR-012 refuses material whose licence forbids landing, and that refusal ships: forbiddingLicence is checked and continues before landingWouldViolate is reached. A cc-by-nd file breaks no artifact rule, so under an unbounded obligation to land it MUST have been landed — converting deliberate, tested behaviour into a defect, and falsifying §4's claim that no behaviour moves. The must-tier casualty is FR-015, whose whole architecture is that permission and safety are two independent grounds for withholding.

Draft response — accepted in full; the obligation is now bounded to its ground. It reads "MUST NOT be withheld on the ground that it carries or is executable content", with withholding on other grounds explicitly unaffected. Verified against the source rather than taken on the finding's word: the licence check does precede the executable check. This is the finding that would have shipped a contradiction, and it came from asking what the sentence forbids rather than what it permits.

Two permanent closures and a deferral of their own superset, so the recorded escape hatch was already nailed shut

§Scope closed "refusing scripts by extension" and "whether a project wants a runtime in its sidecar" at defer-to=never, while deferring their superset — refusing tool scaffolding generally — to a slug. A runtime is a script and scaffolding is both, so the same question was answered never twice and later once. The <spec-warning> then named that slug as where contrary evidence goes, which draining would have required reversing two permanent closures and a must-tier MUST.

Draft response — consolidated to one deferral. The three are one question at three sizes and now carry a single defer-to, declined now on stated reasoning rather than forever. The warning's escape hatch is therefore real: evidence goes to the slug, and reopening needs a propose against FR-014, which is said plainly.

Against KB-0001@2026-07-25: an absolute keyword used to describe rather than to oblige

The corpus fixes this project's RFC 2119 semantics — MUST is "an absolute requirement. Its absence is a defect". The draft used one while the TL;DR and §4 described the change as merely stating scope with no behaviour moving. By the committed definition those cannot both be true: an absolute the shipped importer does not satisfy is a defect on arrival, not a description. And the deviation it tolerated was should-tier, which cannot license non-conformance with a MUST.

Draft response — the tension is real and the resolution is deliberate. The finding's own suggestion was to drop the conformance keyword entirely and state the scope as prose. That is rejected: an unenforceable scope note is what this spec already had, and inference rather than decision is the defect T-018 raised. Instead the keyword stays and the obligation is made true of the shipped importer by bounding it — nothing is withheld today on the ground of being executable, so the requirement lands satisfied. Left for the author to confirm that reading, since it is the one place the proposal keeps a must-tier obligation the finding argued against.

Dispositioned mitigated. The bounding is what closes it: nothing in the shipped importer is withheld on the ground of being executable, so the requirement lands satisfied rather than as a defect on arrival — which is precisely what KB-0001@2026-07-25 objects to. The keyword is kept because it still binds a future implementation that tries to refuse by kind, and that is the behaviour this change exists to prevent. Recorded rather than silent: this is the one finding where the critic's own remedy was declined.
