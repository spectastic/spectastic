Change proposal · 105-design-source-import

What a candidate is made of

A requirement that says what its input is and never what its output is made of, and two silent failures that grew in the gap.

Status Applied Change ID 2026-08-22-what-a-candidate-is-made-of Spec 105-design-source-import Author Brian Corbin · @briancorbin Created 22 Aug 2026 Targets 3 requirements Read time

Derivation has always been specified by its input — “any text that artifact carries” — and never by its output. Nothing says what a token candidate is made of, so the code chose: hex colours only, and no spacing at all. A real export using oklch() therefore derives nothing, and the empty result is indistinguishable from an export that genuinely has no colours. This change names the value kinds and their notations in FR-010, makes the write in FR-016 emit a token matching the kind rather than assuming an sRGB hex, and adds FR-018 so a derivation that finds nothing says which kind of nothing it found.

What a candidate is made of

Applied

1 · Intent

The reported symptom was one sentence with two unrelated causes in it: “it didn’t land the source HTML, which means it didn’t derive any tokens.” Not landing is FR-014 working exactly as designed, and it has no bearing on derivation — 2026-08-13-read-more-land-less deliberately made the import mine material it refuses to copy, and it does. The empty candidate list has its own cause, and the two have been read as one twice now.

That cause is a silence in this requirement. FR-010 bounds derivation’s input and says nothing about its output, so two answers were invented in code and recorded nowhere: the colour pattern is #[0-9a-fA-F]{3,8}, and spacing derivation has never existed. Both were reproduced against the built kernel — an export carrying oklch() and rgb() values returns zero candidates, while the byte-identical file with those two values rewritten as hex returns two.

The second cause is worse and was found while confirming the first. The write assumes an sRGB hex unconditionally: setTokenAtPath hardcodes $type: 'color' and parses the value as hex digits. Confirming a non-hex candidate today writes a corrupt DTCG token — "hex": "#oklch(" with components: [null, null, null] — raises no error, and bumps the token set’s version so the set records a release for it. So widening the grammar without fixing the write converts a silent no-op into a silent corruption, and the two halves must land together.

The third thing this change fixes is the one that made the same defect cost two investigations: an empty candidate table looks identical whether the export had no colours, or had colours the tool could not read. This estate has a name for that failure and a settled posture on it — recording nothing is a third value, and silence must not be readable as a claim nobody made.

2 · Scope

In scope

  • Naming, normatively, which colour notations derivation recognises — hex plus the CSS colour functions a real export actually emits.
  • Spacing derivation, bounded to lengths declared in a spacing property.
  • A candidate carrying which kind of value it is, so the manifest and the write can tell colour from spacing.
  • A write that emits the DTCG type matching the candidate’s kind, records a colour in the colour space the candidate declares, and refuses rather than writes a value it cannot represent.
  • A derivation that found nothing saying which kind of nothing it found.
  • Bumping this spec’s <spec-budget>, which has read red across seven applied changes without anyone touching it.

Out of scope

  • Every other DTCG value kind a real export carries — typography, radii, shadows, borders, durations. Colour and spacing are what this change can deliver alongside the write path it also has to fix; the rest is a list rather than a design problem, and is better taken once.
  • Converting a derived colour between colour spaces. The value written is the value the designer chose; converting it would need colour science this project has no other use for, would lose out-of-gamut values, and sits badly beside FR-005’s record that the value arrived derived rather than authored.
  • Reading a length that reaches a spacing property through a custom property. A static reader sees padding: var(--gap-2) and cannot resolve it without evaluating the cascade, which is a different capability from reading text.

3 · Approach

The grammar goes in the requirement, not the regex. The interview considered stating a property instead (“must not be limited to a single notation”) and chose an explicit list, accepting that CSS Color 5/6 will eventually need an amendment. The trade is deliberate: an enumerated list is checkable against the implementation by reading both, and the failure mode of the property form — everyone agrees the code is compliant and it still misses oklch() — is the failure this change exists to end.

Spacing is bounded by the declaring property, not by the length. A bare length pattern matches every width, font-size, border-radius and icon dimension in a document; one real import already produced 45 colour candidates alone, and a flood is not a list a human confirms. So a length counts only where it declares padding, margin, gap, inset or a longhand. That costs a property-aware read rather than a flat scan, and it misses a value reaching the property through a custom property — recorded above as out of scope rather than discovered later.

The write is in scope because the grammar cannot land without it. setTokenAtPath hardcodes $type: 'color' and parses the value as hex digits, so a non-hex candidate is written malformed with no error raised. Storing a colour as authored needs no conversion, because the token format carries an explicit colour space of its own; spacing takes its dimension type. A value the writer cannot represent is refused, which is the same posture FR-016 already takes towards a stale set and a version that does not move.

Two values are derivable and not representable, and that is deliberate rather than overlooked. The token format permits fourteen named colour spaces and no author-defined ones, so CSS color(--brand …) with a custom profile has no equivalent — it is a real notation an export can carry, so the grammar recognises it, and the write refuses it. The same holds for spacing: the dimension type permits only px and rem, so a length in em derives and then refuses. Naming both here is the point of the refusal clause; discovering them during a drain is what this proposal is trying to stop.

Grounding. The colour-space enumeration, the absence of custom spaces, and the optional 6-digit hex fallback are verified against the Design Tokens Color module; the px/rem restriction against the Format module. An earlier draft of this section asserted all of it from memory, which the risk pass caught as an assumed fact carrying a must-tier decision — see §5.

One authoring note for whoever drains this. Both MODIFY deltas carry their live rationale verbatim, including the paragraphs an earlier change marked Added by this change — those sentences are history and refer to 2026-08-17-a-declared-token-is-not-a-guess, not to this one. The paragraphs this change adds name their own change id instead, which is the better precedent: a MODIFY replaces the whole element, and an unqualified this change stops being true the moment a second one lands.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec. op= is one of added | modified | removed | renamed; a missing or invalid op renders visibly broken.

What changes: the requirement gains an output vocabulary — a candidate carries its kind, the recognised colour notations are named, and spacing derivation is defined and bounded to the property that declares it. The four rationale paragraphs are carried verbatim; three are appended.

Where a source emits an artifact rather than design data, the import MUST be able to derive token candidates from any text that artifact carries, and those candidates MUST be presented for confirmation rather than committed as read. Derivation MUST NOT read a recognised token file as an artifact to mine, and MUST NOT present a candidate whose value the declared token set already carries.

A candidate MUST carry which kind of value it is. Colour derivation MUST recognise hexadecimal notation and the functional notations rgb(), rgba(), hsl(), hsla(), hwb(), lab(), lch(), oklab(), oklch() and color(). Spacing derivation MUST recognise a length that declares a spacing property — padding, margin, gap, inset, and their longhands — and MUST NOT present a length declared anywhere else.

Suppression of an already-declared value MUST compare against the values the declared token set records, in every form that set may carry them, and MUST NOT attempt equality between values in different colour spaces.

Rationale

Several of the sources emit code, not a token file — the design is what they emitted. Deriving is the only way to serve them, and confirmation is what keeps FR-005 true in practice rather than only in the file.

The original wording reasoned from a stylesheet, and a real export has none: every value is an inline style= attribute. Worse, the markup is a template — screens are produced by iterating over data, with the values computed in the document's own trailing script — so a static reader sees a placeholder where a figure should be. Reading that script as text is reading data, not executing it, and it is where the values are.

What follows is a bound worth stating rather than discovering: colour and spacing are recoverable, and screen and state identity may not be present at all. So this requirement is about values, and never about reconstructing the structure a designer drew. Turning a template's data into declarations is a separate question about who authors a screen.

Added by this change. The two clauses above bound where derivation stops. The first fixes an inversion rather than a nuisance: a token file is text, so the pattern matched its declared values and returned them as guesses about themselves. The second is what the complaint was actually about — a project that supplies real tokens should be asked to confirm nothing about them, and suppressing only the token file while still offering every stylesheet colour that matches a declared token would leave the list nearly as long.

The three paragraphs above this one are carried verbatim from the live requirement, and saying so matters: a MODIFY replaces the whole <spec-requirement> element, rationale included, so an author who retypes only the normative sentence deletes everything else without the diff showing it. An earlier draft of this delta did exactly that and would have dropped the bound T-008 cost two real imports to establish.

Added by 2026-08-22-what-a-candidate-is-made-of. The three clauses above bound derivation’s input; nothing here has ever bounded its output, and two answers were invented in code as a result. The colour pattern was hex only, so an export using oklch() derived nothing at all — and the paragraph above claiming spacing is recoverable was true about the material and false about the tool, because no spacing derivation had ever existed. Stating the notations as a list rather than as a property is a deliberate trade: the list will need amending when CSS gains a colour function, and the property form’s failure mode is that everyone agrees the code complies while it still misses the notation a real export uses.

Spacing is bounded by the declaring property rather than by the length, because a bare length pattern matches every width, font size and radius in a document. One real import produced forty-five colour candidates on its own; a list nobody can read is not a list presented for confirmation. The cost is recorded rather than hidden: a length that reaches a spacing property through a custom property is not resolvable by reading text, and is out of scope.

The suppression clause is bounded rather than left to inference, because widening the grammar without bounding it would make an existing clause unsatisfiable: deciding that #f7f5f1 and an oklch() value are the same colour needs conversion this change deliberately refuses. Comparing every recorded form is achievable; comparing across spaces is not, and an unsuppressed duplicate is a longer list where a wrong match silently withholds a value the confirmer never saw.

The kind is on the candidate rather than inferred at the point of use, because two consumers need it and neither can recover it from the value. A manifest that cannot tell a colour from a length cannot present either honestly, and the write in FR-016 must choose a DTCG type before it can emit anything at all.

What changes: the write stops assuming its input. It must emit the DTCG type matching the candidate’s kind, record a colour in the colour space the candidate declares without converting it, and refuse a value it cannot represent rather than writing a malformed token. Six rationale paragraphs carried verbatim; two appended.

Confirming a derived candidate MUST write it into the project's token set under a name and a change class the confirmer supplies, and at a resulting version the confirmer supplies once per confirmation, which MAY cover many candidates. The tool MUST NOT supply any of the three. The write MUST refuse a version equal to the one being moved from, MUST refuse a set that has changed since it was read, and a token written this way MUST record that it was derived and confirmed rather than authored. An absent or unreadable version is already refused by 098's NFR-002 and is not restated here.

The write MUST emit a token whose type matches the kind the candidate carries, and MUST record a colour in the colour space that candidate declares rather than converting it. Where the value cannot be represented in the token format, the write MUST refuse it and MUST NOT write a token, move the version, or record a release. Where one confirmation covers many candidates, representability MUST be decided for all of them before any is written, and one unrepresentable value MUST refuse the whole confirmation, naming it.

Rationale

FR-010 presents candidates for confirmation and nothing consumed a confirmation, so a project could declare a token path, validate clean, and hold no tokens.

This spec owns the write because 098 deferred "importing a token set from a design tool, and what its version means on arrival" here in writing, and because 098 ships a reader and a refusal rather than a writer. The first version named 098's mechanism as though it existed; stating the properties the write must satisfy is what an owner does, and leaves 098 free to grow a writer later without this requirement changing.

The change class is the confirmer's, not the tool's. 098 requires every surface to present a release's class as the producer's claim, and its own assumption is that authors classify honestly — so a tool that picks one asserts something its producer never said. That corrects "everything after the name is clerical", which was false: the clerical part is the file, the guard and the bookkeeping.

The version is the confirmer's for the same reason, and the first version of this requirement missed it. A release declares a from and a to; naming the name and the class as human inputs while leaving the version to be moved under the versioning policy left the tool authoring half the claim it had just been forbidden from making.

The one refusal this requirement adds is an equality: the version must move. Checking that it moved correctly for the declared class would mean ordering two versions, which 098's NFR-001 forbids at must tier, and would reintroduce the substitution this correction exists to remove. Absent and unreadable are deliberately not restated — 098's NFR-002 already refuses both, and the first draft of this correction copied them into a second spec, where they could drift and where "malformed" would have quietly ratified a version format narrower than semver that no requirement states.

One version per confirmation rather than per candidate, decided rather than left implicit. A release is a claim about a set, and one real import produced forty-five candidates — forty-five releases would describe nothing a producer would recognise.

Added by 2026-08-22-what-a-candidate-is-made-of. The write assumed its input: it emitted $type: "color" unconditionally and parsed every value as hex digits. That was invisible while FR-010 derived nothing but hex, and becomes a corruption the moment it derives anything else — confirming an oklch() candidate produced a token reading "hex": "#oklch(" with null components, raised no error, and moved the set’s version so the release recorded it. A silent no-op became a silent corruption, which is why the grammar and the write are one change and not two.

A colour is recorded in the colour space the candidate declares, without conversion. DTCG’s colour type carries an explicit colour space already, so storing the authored value needs no colour science and loses no out-of-gamut value — and rewriting a designer’s chosen value would sit badly beside FR-005’s record that it arrived derived rather than authored. Refusing a value the writer cannot represent is the posture this requirement already takes towards a stale set and a version that does not move; the new part is only that a third thing can now be unrepresentable.

Where derivation read material and produced no candidates, the import MUST report that outcome rather than presenting an empty list, and MUST distinguish material carrying no values of a kind it derives from material carrying values in a notation it does not recognise.

Rationale

An empty candidate table is the same table whether the export had no colours or had colours the tool could not read, and the two call for opposite responses — accept the result, or report a gap in the grammar. The same defect was investigated twice because the artifact could not tell them apart, and the second investigation began from a reasonable but wrong inference drawn from an adjacent note about a file that was read and not landed.

This is the estate’s settled posture rather than a new one: recording nothing is a third value, and silence must not be readable as a claim nobody made. It is also why the second clause matters more than the first — reporting “no candidates” is easy and nearly useless; reporting which kind of nothing was found is what ends the investigation.

Deliberately not stated: how an unrecognised notation is detected. A tool that could reliably identify every value it does not understand would understand it. The obligation is that a notation the grammar names but cannot parse, and material whose text carries no derivable value at all, are reported differently — not that every unknown token in a document is classified.

4b · What this change removes

Each entry names one thing this change takes away — a clause dropped from a requirement it retypes, an obligation a sibling loses, a behaviour or affordance no requirement records. An empty register is the answer “this removes nothing”, so the common case needs no editing.

Where a delta removes something itself, its own reason and migration stay authoritative — this register is for what no delta can express.

  • FR-010 loses its open-endedness on value notation. The live requirement never said what a candidate is made of, which read as unbounded in principle even though the code was hex-only in fact. Naming the notations makes the bound real and explicit: a notation not on the list is now out by decision rather than by accident. That is the point of the change, but it is a genuine subtraction and a reader deserves to see it registered rather than inferred.
  • A confirmation can now fail where it previously always “succeeded”. Today every candidate writes something and moves the version. After this change a value the writer cannot represent is refused outright. Nothing of value is lost — what it wrote was malformed — but any caller assuming confirmation is total loses that assumption, and no requirement records it today.

5 · Risk register

Populated by the adversarial risk pass when the proposal triggers the heuristic (touches a must-tier requirement, contains an op="removed" delta, or spans ≥2 topic prefixes). One <spec-risk> per finding. target= is required (missing renders broken). status= defaults to identified; apply refuses until each transitions to accepted, mitigated, or rejected.

The new refusal is written per-value but sits in a requirement whose version is supplied once per confirmation covering many candidates, so it never says whether one unrepresentable value refuses the whole batch or is skipped while the batch’s version moves anyway — and the first 45-candidate confirmation containing a single color(--brand …) forces an implementer to invent the answer.

§4 delta op="modified" target="FR-016": Where the value cannot be represented in the token format, the write MUST refuse it and MUST NOT write a token, move the version, or record a release — read against the carried-verbatim at a resulting version the confirmer supplies once per confirmation, which MAY cover many candidates.

Accepted as a real gap, and the codebase already settles it. NFR-001’s two-phase discipline — decide everything first, write only once nothing can still fail — is the same shape, and was introduced because a partial write left material with no manifest beside it. The batch is therefore all-or-nothing: every candidate is checked for representability before anything is written, and one unrepresentable value refuses the confirmation with that value named. Now stated in the delta as a sentence on the new paragraph, rather than left as a fourth requirement.

Widening derivation to ten notations while FR-016 forbids conversion makes FR-010’s own carried-forward duplicate-suppression clause unsatisfiable: equality would have to be decided across colour spaces, and the only shipped mechanism is a string compare — so a token written as oklch() is invisible to the suppressor and the next import re-presents the colour the confirmer just declared.

Live FR-010, carried verbatim: MUST NOT present a candidate whose value the declared token set already carries, against the FR-016 delta’s MUST record a colour in the colour space that candidate declares rather than converting it. declaredColourValues collects only $value strings matching /^#[0-9a-fA-F]{3,8}$/.

Confirmed, and worse than the finding states. Run against the structured object setTokenAtPath itself writes, declaredColourValues returns the empty set — so suppression is already blind to every token this tool has ever confirmed, hex included, independent of this change. That half is a pre-existing defect and belongs in a triage card rather than here. The half this change owns is the cross-space one, and the answer is to state the bound rather than attempt colour equality: suppression compares recorded values, including the structured form, and does not attempt equality across colour spaces. An unsuppressed duplicate is a longer list; a wrong match silently withholds a real value. Now stated in the FR-010 delta as a third normative paragraph.

The scope register’s boundary half is unwritten — both out-of-scope entries are still template placeholders — while two deferrals the proposal treats as settled are asserted in prose to have been recorded there, so the change would apply with its stated bound existing nowhere.

§2 <spec-non-goals>: [OUT_OF_SCOPE_ITEM_1], [OUT_OF_SCOPE_ITEM_2] — against §3’s recorded above as out of scope rather than discovered later and §7’s the deferral target for the remaining DTCG types.

Correct, and already corrected. The authoring pass wrote the register against the wrong element name and the substitution silently matched nothing — the failure mode this proposal is itself about, one level up. §2 now carries three entries with defer-to=. Worth noting separately: the estimability gate refuses on a <spec-out-of-scope> item missing defer-to=, but the proposal template’s register is <spec-non-goals>, which nothing checked here.

The must-tier obligation to store a colour in its authored colour space rested on an ungrounded claim about the token format — nothing named the specification whose colorSpace enumeration was being relied on — and FR-010 mandates deriving color(), which admits custom profiles no closed enumeration carries, so the grammar is required to produce candidates the write is required to refuse.

KB-0001@2026-07-25: A must-tier decision may not rest on an assumed or unresolved-spike fact without an explicit <spec-risk status="accepted"> recording who accepted the gap and why. Contradicted by an earlier §3 asserting the format’s colour-space behaviour from memory.

Both halves correct. The fact has since been verified against the Design Tokens Color module — fourteen named colour spaces, no author-defined ones, hex optional and 6-digit — and the Format module, whose dimension type permits only px and rem. So it is no longer an assumed fact, and §3 now cites both. Both modules are drafts and can still move; that is recorded here rather than treated as closing the question, and is the reason the enumeration lives in a requirement a propose can amend rather than in a comment. The second half stands and is now stated deliberately: color(--brand …) and a length in em are both derivable and not representable, which is precisely what the refusal clause is for. Verification also found a third instance the proposal had not considered, which is the argument for having run it.
