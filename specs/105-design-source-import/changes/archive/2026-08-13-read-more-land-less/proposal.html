Change proposal · 105-design-source-import

Read more, land less

A real design handoff found the derivation premise false, the safe-to-land question unasked, and no owner for getting the export onto disk. Four deltas, all from running it.

Read more, land less

Applied

1 · Intent

The slice was built against synthetic fixtures and then run, for the first time, against a real design handoff: a spec was handed to a visual design tool, screens came back, and the export was imported. Three of its stated premises turned out to be wrong, and the run also surfaced a question the spec never asks — whether landed material is safe to land at all.

The premise that carries the most weight is FR-010's. Its rationale reasons that a source emitting an artifact emits a stylesheet, which is text, and that is what makes deriving possible without vision. The real export has no stylesheet — every value is an inline style= attribute — and the markup is a template: the screens are produced by iterating over data, with the values computed in the document's own trailing script. A reader parsing it statically sees a placeholder where a figure should be. So the conclusion survives and the reasoning does not, and a requirement resting on a false premise is one nobody can extend correctly.

The second is that nothing owns getting the export onto the filesystem FR-001 requires it to already be on. Reading the design tool programmatically returns file content with no way to write it, so material passes through a model's context and a large bundle cannot land at all. The answer is narrower and better than it first looked: every one of these tools exports a zip, an archive on disk is already a local filesystem location, and the fetcher seam already returns a directory — so one archive fetcher serves all five sources without touching FR-001 or admitting a network.

The third is a question the spec never asks. A real export carries a runtime, and the importer copied bytes, so landing one left the project failing its own artifact rules at error severity — contradicting FR-003, the property the slice exists to hold. Refusing to land it is right. But refusing to read it would throw away most of the colour in the export, because the file carrying the runtime is also the file carrying the design. Reading and copying are different permissions, and nothing said so.

Both of those last two are already built, which is the honest reason they are here: the behaviour shipped ahead of any requirement, and a later reader would find no record of why a file gets read and not copied.

One finding deliberately produces no delta. The assumption that a design project has a design system attached, and therefore an existing token file, was wrong — none was attached, and the export carries zero token references against forty-odd raw literals. That makes FR-010 more load-bearing rather than less, so the requirement stands as it is and only its reasoning changes.

2 · Scope

In scope

  • Correcting FR-010's premise: derive from whatever text the export emits, including inline style attributes and a template's own computed source.
  • An archive as a source location, materialised without a network, an account or a credential.
  • Material that cannot be safely landed is reported rather than dropped — the posture FR-011 establishes for an annotation category, said about a whole file.
  • Reading and landing as distinct permissions.

Out of scope

  • A live read path against a design tool's API — the no-network position stands, and the archive route makes it unnecessary. defer-to=never.
  • Translating an export into the screen and state vocabulary. The values a template computes are reachable as text, but turning them into declarations is a separate question about who authors a screen. defer-to=TBD-visual-import-translation.
  • Pairing a light and a dark literal into one mode-aware token. A stronger signal than counting, and it needs structural comparison rather than a tally. defer-to=TBD-token-mode-pairing.

3 · Approach

The shape of all four deltas is the same: widen what may be read, narrow what may be written. The slice was drafted as though those were one decision, and running it showed they are two.

Reading a file is not executing it, and a template's computed source is text like any other. P-11 forbids an artifact instructing the tool that reads it — it has never forbidden the tool from reading. So derivation may look at everything it can open. Landing is the narrow half: material that would leave the project failing its own rules does not get copied, and a licence that forbids a copy stops it before anything is written. A licence refusal is the one case that excludes material from both, because that one really is about permission to use it at all.

The archive delta deliberately does not touch FR-001. A zip on disk is a local filesystem location, so the existing requirement is already true of it — what was missing is the obligation to accept one. The fetcher seam is already shaped for this: it takes a location and returns a directory, so an archive fetcher expands and returns, and the rest of the pass cannot tell the difference. That is one adapter for every source rather than one per tool, which is what FR-001 was protecting in the first place.

Two of these four are already implemented. That is the wrong order and the reason they are in this proposal rather than left alone: the behaviour is live, and without a requirement a later reader finds a distinction with no argument behind it and no reason not to simplify it away.

4 · Deltas

What changes: provenance is owed for every file the import reads, not only for the ones it lands. Raised by this proposal's own risk pass and dispositioned as a widening rather than a recorded gap.

Every file an import reads MUST carry provenance — where it came from, what identified it there, and under what licence — and an unknown field MUST be recorded as unknown rather than guessed.

Rationale

The corpus importer's rule, transferred: a fabricated provenance field is worse than a missing one, because it looks like diligence. This project already forbids inventing an origin for a vendored component.

Scoped to landed files while landing and reading were the same act. FR-014 and FR-015 separate them, and the file contributing most of the derived colour is now precisely the one that is read and never copied — so the narrower wording left the material with the most influence over the output as the material with no record at all. The requirement exists so that nothing shapes the project without a record of where it came from; reading is the act that shapes it.

What changes: the requirement stands; its premise is corrected. Derivation reads whatever text the export emits — not a stylesheet, which a real export may not have — and the requirement now states what a source artifact may not statically contain.

Where a source emits an artifact rather than design data, the import MUST be able to derive token candidates from any text that artifact carries, and those candidates MUST be presented for confirmation rather than committed as read.

Rationale

Several of the sources emit code, not a token file — the design is what they emitted. Deriving is the only way to serve them, and confirmation is what keeps FR-005 true in practice rather than only in the file.

The original wording reasoned from a stylesheet, and a real export has none: every value is an inline style= attribute. Worse, the markup is a template — screens are produced by iterating over data, with the values computed in the document's own trailing script — so a static reader sees a placeholder where a figure should be. Reading that script as text is reading data, not executing it, and it is where the values are.

What follows is a bound worth stating rather than discovering: colour and spacing are recoverable, and screen and state identity may not be present at all. So this requirement is about values, and never about reconstructing the structure a designer drew. Turning a template's data into declarations is a separate question about who authors a screen.

An import MUST accept an archive as its source location and materialise it, and doing so MUST NOT require a network, an account or a credential.

Rationale

FR-001 requires the source to be on the local filesystem and assigns nobody the job of putting it there. In practice that step is unreachable through the documented path: reading a design tool programmatically returns file content with no way to write it, so material passes through a model's context and a large bundle cannot land at all.

The answer is narrower than a fetcher per tool, which would be the coupling FR-001 exists to prevent. Every one of these sources exports a zip; an archive on disk already satisfies FR-001 as written; and the fetcher seam already takes a location and returns a directory. So one archive fetcher serves every source, the rest of the import cannot tell the difference, and the no-network position is untouched — an archive is opened, never downloaded.

Material that cannot be landed without leaving the project in violation of its own artifact rules MUST NOT be landed, and MUST be reported rather than dropped.

Rationale

FR-003 makes remaining valid the property this slice exists to hold, and says nothing about the landed bytes — so a verbatim copier satisfies it on paper and breaks it in fact. A real export carries a runtime, and landing one produces an error-severity violation of P-11, which is a principle rather than a rule that can be relaxed for this case.

Reporting rather than dropping is not a new posture: FR-011 already establishes it for an annotation category the vocabulary has no home for. This is the same statement about a whole file, and the reason it is written down is that generalising a requirement quietly, in code, is how a distinction loses its argument.

A deliberate consequence: an import may complete having landed less than it read, and a caller must be told which files those were. Silence would look like success.

Reading source material and landing a copy of it MUST be treated as distinct permissions: material that is not landed MAY still be read to derive candidates, and material whose licence forbids a copy MUST NOT be read for that purpose either.

Rationale

Discovered by running a real import and watching it produce almost nothing useful. The file carrying the runtime is also the file carrying the design, so refusing to land it — correctly, per FR-014 — and then ignoring it discarded most of the colour in the export and left FR-010 deriving from whatever happened to be safe.

The two halves fail differently, which is why both are stated. Refusing to read what may not be copied is a permission question and the conservative answer is right. Refusing to read what merely cannot be copied is a safety question answered in the wrong place, and it costs the requirement its best input.

Visible in the output: a value appearing in both the stylesheet and the markup outranks one appearing in neither, which is the ordering a reviewer wants — and it only exists because the unlandable file still counted.

5 · Risk register

This pass was run by the authoring session rather than delegated to an independent reviewer, so its independence is weaker than the register's usual guarantee. Recorded rather than glossed: a second pass on the three findings below is worth having before they are dispositioned.

A candidate can cite evidence that no longer exists anywhere

The change most likely to be regretted. FR-015 lets material that was not landed shape the derived candidates — and FR-003 actively encourages deleting the source once the import is done, because surviving that deletion is how the slice proves the adapter disappeared. Put together, a reviewer opening the manifest sees a candidate whose sources column names a file that is not in the repository and, if the export has been cleaned up, is not anywhere. The provenance trail breaks at precisely the point someone would follow it.

It is not hypothetical: the run that motivated this proposal produced exactly that shape — four of six candidates cite a file the import deliberately refused to land.

Mitigated. Make the asymmetry visible where it is read: a candidate derived wholly or partly from material that was not landed says so, next to the source name, so "go and look" is never silent advice about a file that is gone. That is a rendering change to the manifest plus a field on the candidate, not a change to the requirement's substance. The alternative — refusing to derive from unlanded material — is the thing this proposal exists to reject.

Material with no provenance at all now influences the output

The live requirement most likely contradicted. FR-004 is scoped to "every landed file", which was exhaustive when landing and reading were the same act. FR-014 and FR-015 together create a second class — read, never landed — that FR-004 does not reach and nothing else covers. So the file contributing most of the derived colour is the one file whose origin, edition, licence and hash are recorded nowhere.

The contradiction is with FR-004's intent rather than its letter: it exists so that nothing shapes the project without a record of where it came from, and that is now false.

Mitigated. Widened rather than recorded as a ceiling: FR-004 now reads every file an import reads, which is faithful to why it exists. Costs a fifth delta on a must-tier requirement, and takes the proposal past the shape the interview settled — accepted deliberately, because the alternative leaves the requirement saying something narrower than what the code must do, which is the drift this proposal is fixing three requirements away.

The archive delta is the one item here that did not come from running the import

The scope concern. Three of the four in-scope items were found by executing a real import and watching it misbehave; FR-013 was found by discovering that the import could not be reached. It is also the only item requiring code that does not exist, the only one whose motivation is a particular tool's API rather than the import's own behaviour, and the only one that could ship on its own without leaving the other three incoherent.

Bundling it risks the proposal being reviewed as one thing when it is two: a correction of what the slice believed, and a new capability.

Accepted, with the reason recorded. Splitting would leave FR-010's corrected premise landing while the verb it governs stays unreachable by any documented path, which is a worse state to pause in than a slightly mixed proposal. Four deltas is inside the splitting threshold and the topic prefix is single. The concern is real and the answer is sequencing, not separation.

  • Build the archive fetcher in packages/core/src/providers/ — expands an archive to a directory and returns it, behind the existing DesignSourceFetcher seam so the import cannot tell the difference. No network, no credential.

  • Cite FR-014 and FR-015 in the docstrings of carriesExecutableContent and the read-versus-land split in packages/core/src/visual/import.ts — both shipped ahead of a requirement and currently argue for themselves.
  • Mark a candidate derived wholly or partly from unlanded material, and render that beside its source name in the manifest (FR-015 risk, mitigated).
  • Record provenance for every file read, not only for the ones landed (FR-004 widening).
