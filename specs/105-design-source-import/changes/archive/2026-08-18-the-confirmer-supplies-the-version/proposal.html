The confirmer supplies the version

A requirement forbids the tool from authoring two parts of a claim, then has it author the third.

Status Applied Change ID 2026-08-18-the-confirmer-supplies-the-version Spec 105-design-source-import Author Brian Corbin · @briancorbinxyz Created 18 Aug 2026 Targets 2 modified Read time

FR-016 makes the name and the change class the confirmer's and says the tool must supply neither — then requires the write to move the version under the versioning policy, which has the tool authoring the third part of a claim 098 treats as the producer's. Split out of an earlier proposal after the adversarial pass observed it is a different investigation carrying a cross-spec obligation, which lands beside it.

The confirmer supplies the version

Applied

1 · Intent

FR-016 is careful about two of three inputs and silent about the third. It requires a confirmed token to be written “under a name and a change class the confirmer supplies”, says “the tool MUST NOT supply either”, and then requires the write to “move the set's version under the versioning policy”. A release declares a from and a to, so the version is part of the same claim — and by omission the tool authors half of it.

This was drafted once already, inside 2026-08-18-what-the-design-tool-is, and split out when the adversarial pass observed it is a different investigation from that one's five corrections and carries a cross-spec obligation none of them share. That obligation lands with it here: T-013's own diagnosis records that 098's out-of-scope still says this question lives elsewhere, which is the half of T-011's fix that was dropped.

2 · Scope

In scope

  • Making the produced version a confirmer input, like the name and the class beside it.
  • Bounding what the write may refuse to what is decidable without ordering two versions.
  • The paired amendment to 098's out-of-scope, so one spec owns the question and the other says so.
  • Computing a version for the confirmer. That is the defect, not the shortfall — a tool that picks one asserts something its producer never said.
  • Checking that a supplied version agrees with the declared change class. Deciding that is an ordering, which 098's NFR-001 forbids at must tier, and it would need 098 to grow a machine-readable policy rather than the prose one it deliberately keeps. It carries its own slug rather than deferring to 098, because deferring a question to the spec being amended to disown it is the circularity T-011 exists to break, with an extra step.

3 · Approach

One modified requirement, and a separate proposal against 098 amending the out-of-scope entry that still points here. Two applies rather than one, because a proposal folds into the spec it targets.

The refusal is bounded by what a check can decide. The earlier draft said the write “MUST refuse a version the versioning policy disallows”, which reads as the same substitution inverted: deciding that 2.1.0 plus minor should not be 3.5.7 means comparing two versions, and 098's NFR-001 requires “equality only, with at most 0 orderings computed”. So the refusal is limited to what equality settles: supplied, well-formed, and not equal to the version being moved from.

4 · Deltas

One <spec-delta> per requirement touched.

What changes: the produced version joins the name and the change class as a confirmer input. One MUST is deliberately removed — “the write MUST move the set's version under the versioning policy” — because it is the defect: it has the tool authoring the third part of a claim the same sentence forbids it from making. It is replaced by a bounded refusal rather than dropped, and all three existing rationale paragraphs are carried through unchanged.

Confirming a derived candidate MUST write it into the project's token set under a name and a change class the confirmer supplies, and at a resulting version the confirmer supplies once per confirmation, which MAY cover many candidates. The tool MUST NOT supply any of the three. The write MUST refuse a version equal to the one being moved from, MUST refuse a set that has changed since it was read, and a token written this way MUST record that it was derived and confirmed rather than authored. An absent or unreadable version is already refused by 098's NFR-002 and is not restated here.

Rationale

FR-010 presents candidates for confirmation and nothing consumed a confirmation, so a project could declare a token path, validate clean, and hold no tokens.

This spec owns the write because 098 deferred "importing a token set from a design tool, and what its version means on arrival" here in writing, and because 098 ships a reader and a refusal rather than a writer. The first version named 098's mechanism as though it existed; stating the properties the write must satisfy is what an owner does, and leaves 098 free to grow a writer later without this requirement changing.

The change class is the confirmer's, not the tool's. 098 requires every surface to present a release's class as the producer's claim, and its own assumption is that authors classify honestly — so a tool that picks one asserts something its producer never said. That corrects "everything after the name is clerical", which was false: the clerical part is the file, the guard and the bookkeeping.

The version is the confirmer's for the same reason, and the first version of this requirement missed it. A release declares a from and a to; naming the name and the class as human inputs while leaving the version to be moved under the versioning policy left the tool authoring half the claim it had just been forbidden from making.

The one refusal this requirement adds is an equality: the version must move. Checking that it moved correctly for the declared class would mean ordering two versions, which 098's NFR-001 forbids at must tier, and would reintroduce the substitution this correction exists to remove. Absent and unreadable are deliberately not restated — 098's NFR-002 already refuses both, and the first draft of this correction copied them into a second spec, where they could drift and where "malformed" would have quietly ratified a version format narrower than semver that no requirement states.

One version per confirmation rather than per candidate, decided rather than left implicit. A release is a claim about a set, and one real import produced forty-five candidates — forty-five releases would describe nothing a producer would recognise.

What changes: the precedence prohibition gains the termination the mark already has. Nothing else changes: the inferred mark, its persistence to confirmation, and the permanent record that a value was derived are all carried through unchanged.

A value the import derived rather than read MUST be marked as inferred and MUST NOT outrank a declared value, and both the mark and that precedence rule MUST persist until the value is confirmed, after which the record that it was derived MUST remain.

Rationale

Declaration over inference, in both directions — settled elsewhere and unchanged here.

The original was unconditional, which made confirmation impossible to express: the state a confirmed candidate occupies had no wording, and the shipped types fix inferred true and confirmed false so it is inexpressible in code too. The first attempt to add confirmation asserted the transition in a rationale and shipped no delta, leaving the reconciliation inside the newer requirement's prose.

The last clause is the part worth keeping. A confirmed value stops being inferred, and if the record vanishes with the mark then the fact that it was ever observed rather than chosen vanishes too — a reader should be able to tell a token that arrived from a design tool from one somebody decided on.

The termination was then bound to the wrong clause, which is what this amendment fixes. “That mark MUST persist until the value is confirmed” ends the mark and leaves “MUST NOT outrank a declared value” with no end condition at all — so a confirmed value stayed permanently barred from outranking a declared one, while FR-016 requires exactly that write. Two must-tier requirements disagreed about whether a confirmation is allowed to take effect, which is the second time this requirement's confirmation story has been half-expressed.

FR-006 was checked on the same suspicion, since its mark has no termination either. It does not share the defect: an unreviewed mark that never ends costs a reader nothing and blocks no write, so it is left alone rather than swept into a correction it does not need.

5 · Risk register

Populated by the adversarial risk pass. This proposal modifies a must-tier requirement.

Two of the three refusal grounds are already owned by 098 at must tier, the word “malformed” ratifies a format contract 098 declined to state, and the equality check makes a real import unaffordable.

098 NFR-002: “on a malformed or absent version it MUST refuse the amendment”. The only implementation of “malformed” is /^\d+\.\d+\.\d+$/, narrower than semver — a project on 2.1.0-rc.1 could never confirm. And one real import produced 45 candidates, so one release per candidate is 45 hand-typed versions.

Upheld on all three, each verified by reading the sibling requirement and the shipped code. Absent and malformed are removed and cited to 098 NFR-002 rather than restated, which leaves one owner and drops the accidental sub-semver contract. The equality check stays — it is the genuinely new content and is decidable without ordering.

The batch question is decided rather than left: a confirmation supplies one version and may cover many candidates, so an import of 45 is one release. Forty-five releases for one arrival would not describe anything a producer would claim.

FR-005 still forbids the write this requirement mandates, so closing T-013 here would leave the half that card names as its own diagnosis.

Live FR-005: “MUST be marked as inferred and MUST NOT outrank a declared value, and that mark MUST persist until the value is confirmed” — the termination binds to the mark, not to the precedence prohibition, which therefore never ends.

Upheld and verified. A second delta ends the precedence clause at confirmation, which is what makes FR-016's write legal. FR-006 was checked on the same suspicion and does not share the defect — its mark has no termination at all, which is a different and benign shape, so it is left alone rather than swept in. T-013's closure is narrowed to the halves that actually landed.

The scope block re-creates the circularity T-011 exists to break, and ships the cross-spec half as a checkbox rather than a delta — the same form that failed once already.

Out of scope defers the agreement check to 098, while the amendment being authored makes 098 say the question is 105's. T-011: “Not both, and not neither.” And the pass that authorised this split asked for it “paired with the 098 MODIFY”.

Upheld, and the sharper half is that deferring to the spec being amended to disown the question is the circularity with an extra step. The agreement check now carries its own slug, TBD-version-class-agreement, so it has an owner that is not either spec. The 098 amendment is authored and applied in the same session rather than left as a task — two applies, because a proposal folds into the spec it targets, and the pairing is what T-011 asked for.

A must-tier requirement rests on the assumption that a confirmer supplies an honest version, and nothing catches one who does not.

KB-0001@2026-07-25: a must-tier decision may not rest on an assumed fact without an explicit accepted risk naming who accepted the gap and why. 098's own assumption is that “authors will classify a release honestly”, now extended to the number beside the class.

Accepted rather than mitigated, because the alternative is worse than the gap. Catching a dishonest version means deciding whether it agrees with its class, which is an ordering — and 098 NFR-001 forbids one at must tier, deliberately, so that no format contract is taken on beyond what the policy states. Closing this would mean 098 growing a machine-readable policy in place of the prose one it chose. The gap is one a reviewer can see in the diff, which is where 098 already puts this class of trust.
