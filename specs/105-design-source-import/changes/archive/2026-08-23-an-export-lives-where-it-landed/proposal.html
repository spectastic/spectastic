Change proposal · 105-design-source-import

An export lives where it landed

A design tool drops its export in Downloads. The import refuses to read it there — a containment this spec never asked for, on the one path where containment protects nothing.

Status Applied Change ID 2026-08-23-an-export-lives-where-it-landed Spec 105-design-source-import Author Brian Corbin · @briancorbinxyz Created 23 Aug 2026 Targets 2 requirements Read time

FR-001 says an import reads from “a location already on the local filesystem” and says nothing about where on it. Both fetchers nonetheless refuse an absolute path and anything resolving outside the working directory, so --from ~/Downloads/export.zip — where every design tool actually puts one — is rejected with a message telling the author to move it. One MODIFY makes the read path’s scope explicit and the write path’s containment explicit alongside it; one ADD gives the two source shapes a single symlink posture, which the adversarial pass showed they do not have.

An export lives where it landed

Applied

1 · Intent

Surfaced while reproducing a sibling defect in 106 against a real design export. The export was a .zip in ~/Downloads, which is where the tool that produced it put it — and the reproduction only worked because it was copied into the project first. That copy was not a convenience; without it the import refuses outright: “is an absolute path; give a location inside the project.”

No requirement asks for that. FR-001 constrains the source to be already on the local filesystem, and constrains the import to need no network, account or credential. It says nothing about which part of the filesystem. The containment is an implementation decision that exceeds its own spec, and it is the kind that is invisible until somebody uses the tool the way the ecosystem actually works.

It was deliberate rather than accidental — the local fetcher’s comment says “Containment first … so a traversal is rejected rather than stat-ed.” That reasoning is sound for a path check in general and misapplied here, because it conflates two paths. --from is a location the author names, on their own machine, pointing at material they already have. --into is where the tool writes. Only the second is derived from anything the author did not type, and only the second is where a traversal could do harm.

Two things the adversarial pass corrected, both of which would have shipped. First, the containment is not in one fetcher but two: archiveSourceFetcher carries its own absolute and outside-project refusals, and looksLikeArchive routes every .zip there. A first draft of this proposal touched only the local fetcher, so its own headline case would still have failed after every task was drained. Second, the two source shapes do not share a symlink posture: the archive path refuses a symlink entry outright, while the folder path walks with a stat that follows them — so widening the read location alone would mean an export is refused as an archive and accepted once a person unzips it. That asymmetry is not something to inherit while relaxing the boundary around it.

What does hold up, checked in source: destinations are never built from author-supplied or archive-supplied strings. Every landed file’s name comes from collectExportFiles walking the resolved source with readdir, which cannot return .., and dot entries are filtered at every level. The write side stands on its own — which is why the read-side path check was never load-bearing, even though the read-side symlink question turns out to be.

2 · Scope

In scope

  • Making the read path’s scope explicit — an export may live anywhere the author can read — so the shipped refusals stop exceeding the requirement they implement. Both fetchers, since both carry the check and a .zip is routed to the one a first draft overlooked.
  • Making the write path’s containment explicit in the same requirement, so removing the read-side check does not read as removing containment altogether. It states what was actually doing the protecting.
  • Giving both source shapes one symlink posture, so widening the boundary does not make an export’s safety depend on whether the author unzipped it first.

Out of scope

  • Anything about what the import lands once it has read. The refusal of executable content, the runtime decision settled by this spec’s own T-018, and the review marks are all untouched by a change to where reading may begin.
  • Reading from a network location, an account, or behind a credential. FR-001’s other clause is the load-bearing one and is not weakened here — local means local.
  • Per-entry traversal, entry-size and expansion-ratio bounds inside an archive. Already shipped by this spec’s own T-020 and unchanged here — a first draft deferred these to a slug, which would have planted a backlog item for a closed concern.

3 · Approach

One MODIFY on FR-001, carrying both existing clauses through unchanged and adding the two that were left implicit: the source need not sit inside the project, and everything the import writes stays under the destination it was given. One ADD stating the symlink posture both source shapes must share.

The relaxation is worded as need not be inside the project rather than must not be constrained. The difference matters: the second is an unbounded prohibition, and it would mean any future read-side bound — including the symlink refusal added here, which has nothing to do with the project directory — needed a fresh proposal amending a must-tier requirement before it could be written. A requirement that forbids its own siblings is a trap for whoever writes the next one.

Stating the write-side containment is not padding either. Deleting a check named SourceOutsideProjectError without recording what containment survives would leave the next reader to work out from the code whether this spec still has any. It does, it always did, and it is the half that matters.

This lands independently of the 106 change it was surfaced by. That one makes a single --from value serve both verbs; this one widens where that value may point. Either is useful alone: 106 alone fixes an export already inside the project, this alone fixes nothing about rendering. Together they make --visuals ~/Downloads/export.zip work, which is the shape a person actually has.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec. op= is one of added | modified | removed | renamed; a missing or invalid op renders visibly broken.

What changes: two clauses are added — the source need not sit inside the project directory, and everything written stays under the given destination. Nothing else: both existing clauses and the whole live rationale carry through verbatim, with two sentences appended.

An import MUST read from a location already on the local filesystem, and MUST NOT require a network, an account or a credential. That location MUST NOT be required to sit inside the project directory — an export may live anywhere on the local filesystem the author can read. Everything the import writes MUST remain under the destination it was given.

Rationale

What makes one code path serve five tools whose models agree about nothing else. It also removes the seat, the rate limit and the API version from the dependency graph of a spec — a spec that needs somebody's login to validate is not portable. The two added clauses separate a conflation the implementation made and this requirement did not: a read location is named by the author and points at material they already have, while a write destination is where the tool acts. Refusing an absolute --from protected nothing — every landed name comes from walking the resolved source with readdir, which cannot produce a traversal — and it rejected the one place a design tool actually puts an export. Worded as need not rather than must not be constrained so that a bound unrelated to the project directory, such as FR-019's, does not require amending this requirement before it can exist.

An import MUST refuse to follow a symbolic link when reading a source, and MUST apply that refusal identically whatever shape the source takes.

Rationale

The archive path already refuses a symlink entry, on the stated grounds that its target “is chosen by whoever built the archive, not by the project expanding it”. The directory path does not: it walks with a stat that follows links, so a folder carrying a link to somewhere else on the machine is read through, landed, hashed into the manifest and committed. While both paths refused anything outside the project the gap was bounded by accident; widening the boundary is exactly when it stops being. Stated as one requirement over both shapes rather than a second clause on the archive rule, because the defect is the asymmetry — the same export refused as a .zip and accepted once unzipped is worse than either answer applied consistently.

4b · What this change removes

Each entry names one thing this change takes away — a clause dropped from a requirement it retypes, an obligation a sibling loses, a behaviour or affordance no requirement records. An empty register is the answer “this removes nothing”, so the common case needs no editing.

Where a delta removes something itself, its own reason and migration stay authoritative — this register is for what no delta can express.

  • A refusal that was doing real work in one narrow case. Rejecting the declared string before resolving it meant a traversal was never stat-ed — the source was never touched at all. After this change an out-of-project path is resolved and stat-ed, so the tool reads where it previously refused to look. That is the intent, and it is still a capability the tool did not have a moment ago.
  • A uniformity this codebase relied on without stating it. Both fetchers’ comments claim the containment order is “the same order every path check in this codebase uses”. After this change two path checks deliberately differ from the others, so the sentence that made them obviously correct no longer applies and a reader must know why.
  • The ability to read an export through a symbolic link. Nothing depended on it and no requirement offered it, but a directory export containing a link to material elsewhere on the machine is imported today and will be refused after FR-019. A person who had arranged an export that way — a shared assets folder linked into a per-feature export, say — loses a working arrangement and gets a refusal rather than silence.

5 · Risk register

Populated by the adversarial risk pass when the proposal triggers the heuristic (touches a must-tier requirement, contains an op="removed" delta, or spans ≥2 topic prefixes). One <spec-risk> per finding. target= is required (missing renders broken). status= defaults to identified; apply refuses until each transitions to accepted, mitigated, or rejected.

The delta widens the read location at must tier while the safety argument offered for it reasons only about destination names, never about what the walk may reach. collectExportFiles recurses on fs.stat, and nodeFs.stat is node:fs/promises’ stat, which follows symlinks — so an export folder carrying a symlinked directory is walked, its contents read, landed under --into, hashed into the manifest as “NOT REVIEWED”, and committed. That is exactly the capability the archive path already refuses by type, so after this change the same untrusted export is refused as a .zip and accepted once a person unzips it into Downloads. The 30-day regret is the wording as much as the hole: “MUST NOT be constrained to the project directory” is an unbounded must-tier prohibition, so reintroducing any read-side bound — including a symlink refusal that has nothing to do with the project directory — needs a second proposal amending a must requirement rather than a patch.

Original delta: “That location MUST NOT be constrained to the project directory”. Against packages/core/src/visual/import.ts:230-239, packages/core/src/providers/node-fs.ts:37 (stat, not lstat), and packages/core/src/providers/archive-source-fetcher.ts:105 (S_IFLNK refused).

Accepted in full; the sharpest finding of the pass and it changed both the wording and the scope. Verified in source before acting: nodeFs.stat is stat and does follow links, and the archive path does refuse them — so the asymmetry is real, not theoretical. Two corrections followed. The prohibition is now bounded (“MUST NOT be required to sit inside”), so a future read-side bound does not need a proposal against a must requirement before it can be written — and FR-019, added in this same change, is the first thing that would have hit that trap. And the symlink gap is closed here rather than inherited: FR-019 gives both shapes one posture, since the same export refused as an archive and accepted once unzipped is worse than either answer applied consistently. The subtraction register records what that costs someone.

Live FR-013 is must-tier and says an import “MUST accept an archive as its source location”; the amended FR-001 says that location must not be constrained to the project directory. Read together, the two oblige the archive path to accept ~/Downloads/export.zip — but archiveSourceFetcher carries its own, independent absolute-path and outside-project refusals, looksLikeArchive routes every .zip there from all three call sites, and no delta, scope item or task in this proposal touches that file. So the change as written makes the shipped archive path non-conformant with two must-tier requirements on the day it applies, and the proposal’s own headline case still fails after every listed task is drained.

Live FR-013; against packages/core/src/providers/archive-source-fetcher.ts:151-158 and the original §6, which named only local-source-fetcher.ts while its last task asserted an archive outside the project is exercised end to end.

Accepted; this one was fatal and the proposal would have shipped claiming a fix it did not deliver. Confirmed in source: the archive fetcher throws ArchiveEntryOutsideError on both an absolute path and an outside-project resolution, entirely independently of the local fetcher, and looksLikeArchive sends every .zip to it. The headline case is the archive path, not the folder path. §2 now says both fetchers explicitly, the task list covers archive-source-fetcher.ts, and the end-to-end task that asserts the real shape is kept precisely because it is what would have caught this had the tasks been drained rather than read.

The scope register is mis-drawn on the one axis that decides whether this change works. Its third out-of-scope item is the only place archives are mentioned, and it defers work that already ships — per-entry traversal containment, symlink refusal and expansion ratio/size bounds are all live in the expander (T-020) — so the slug plants a phantom backlog item for a closed concern. Meanwhile the archive edit the change genuinely needs is excluded by implication, because the item asserts archives are “unchanged by this proposal”. The scope is too narrow, and narrow in a way that reads as deliberate: a reviewer sees archives considered and set aside, rather than a gap.

Original §2 item 3, deferring archive expansion safety to TBD-archive-expansion-containment. Already implemented at packages/core/src/providers/archive-source-fetcher.ts:107-121 and :170-178, with tests at packages/core/test/archive-bounds.test.ts.

Accepted, and the phantom slug is the part worth recording. A TBD- for something already shipped is worse than no entry: it manufactures backlog, and the estate has a whole considerations document about exactly that failure. The item now states that those bounds ship and are unchanged, with defer-to="never" rather than a slug. The genuine archive edit moved from excluded-by-implication into scope, which is the substantive half of this finding and is handled alongside the FR-013 one above.

The corpus commits a must-tier grounding rule, and this must-tier delta breaches it: two facts §1 and §6 present as verified are contradicted by the source they name. §1 says the read side “was never load-bearing” having been “checked before proposing, not assumed”, but the check reached one of the two fetchers — the archive fetcher carries the same containment refusal and is unmentioned. §6 task 3 states “the one-step preflight catches it by type today”; checkVisualsExport catches nothing at all, and the only by-type catch is in the CLI, which the task does not name.

Contradicts KB-0001@2026-07-25: “A must-tier decision may not rest on an assumed or unresolved-spike fact without an explicit <spec-risk status="accepted">.” Refuted by packages/core/src/visual/one-step.ts:82-85 (no catch) and packages/cli/src/commands/visual.ts:355 (the actual catch site).

Accepted; both claims were wrong and both are corrected rather than softened. The grounding claim in §1 now says what was actually checked — that destinations derive from readdir names, which is true and holds — and no longer generalises from it to “the read side was never load-bearing”, which the symlink finding disproves. The task naming the preflight is rewritten against the real catch site in the CLI; I wrote checkVisualsExport earlier in the same session and still mis-stated its behaviour, which is a good argument for the pass reading source rather than prose. The citation is verified: KB-0001 resolves to spectastic/spectastic · spectastic-concepts · 001-foundations at edition 2026-07-25 and carries that rule.

None outstanding. The adversarial pass then settled two more by disproving the first draft: the containment lives in both fetchers rather than one, and the two source shapes disagree about symbolic links — closed here by FR-019 rather than inherited, since widening the boundary is precisely when that asymmetry stops being bounded by accident.
