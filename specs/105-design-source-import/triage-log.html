Cards

Claude Design has a persistent, readable design document — the refusal's stated reason is wrong

Design upstream

Debugging why this spec's alternatives table scores a live read path so low, root cause was a survey claim that is factually false — Claude Design exposes get_project, list_files and read_file, and Claude Code ships a /design import that uses them; fixed by re-grounding D-001 on portability rather than on absence, and correcting the survey; regeneration fails, because an implementer reading the survey would restate the same false premise.

Expected
The reason for refusing a live read path is one that survives checking.
Actual
The survey's D-002 says "Claude Design and Stitch have no persistent design document to read", and this spec's alternatives rationale leans on it: "Two of the five sources have nothing persistent to query at all." Both are wrong for Claude Design. Its projects are addressable at claude.ai/design/p/<projectId>, and the file API is already wired into this very session's tool surface.
Diagnosis
The survey's own §13 records that "the design tools were read, not exercised" — and Claude Design is not even named in that hedge, which makes its row the least-evidenced of the five. The decision is unaffected: /design import needs a login, a subscription and a consent grant, which is exactly the "only as available as somebody's seat" failure D-001 rejects. Only the justification has to change, from there is nothing to query to querying it costs portability.
Fix
A propose against this spec correcting D-001's Context and the alternatives rationale, plus a §13 correction and a §1 table fix in the survey. Deliberately not yet: the same research surfaced four more findings (T-002 to T-005) and the experiment that motivated it will likely surface more, so this is amended once rather than five times.
Deep dive — cross-spec, and a scoring consequence

The alternatives table scores "A live protocol client" 6 against "Local export only" 15, and part of that gap is the false premise. Re-scored honestly the winner does not change — portability, cost and five-sources-one-path all still favour the local export — but the margin is smaller and the table should say so rather than carry a number nobody can reproduce.

The survey is the upstream artifact here, so correcting only this spec would leave the false claim sitting where the next reader finds it first.

The export is an archive, and nothing says who expands it

Spec upstream

Debugging what a user actually hands the importer, root cause was that Claude Design's user-facing exports are Download as .zip and Export as standalone HTML rather than a folder; fixed by naming the export shape in the assumption and saying whether the fetcher seam expands an archive; regeneration fails, because the spec as written implies a directory appears by itself.

Expected
FR-001's "a location already on the local filesystem" describes something a user can actually produce.
Actual
They produce a .zip. It is not a location on the filesystem until somebody expands it, and the spec never mentions archives — §6's assumption says only "designers can export a folder from all five tools".
Diagnosis
The assumption was written from the shape the design wanted rather than the shape the tools emit. FR-001 survives unchanged — unzip and point at the folder — but the step is invisible, so the first person to run this hits it.
Fix
Name the export shape in §6, and decide explicitly whether DesignSourceFetcher expands an archive or that is the user's job. Batched with T-001.

The no-vision refusal rests on an unverified claim about what Claude Design emits

Spec upstream

Debugging whether token derivation has anything to derive from, root cause was that "the sources that emit an artifact emit a stylesheet, which is text" was asserted for Claude Design and never checked; fixed by downgrading it from a settled refusal to a tested assumption, or by verifying it against a real export; regeneration fails, because the claim reads as established in the spec's own open-questions register.

Expected
A refusal stated in §7 as settled is one that was checked.
Actual
It holds for Stitch, which emits HTML and CSS. For Claude Design it is unverified: the output is React-rendered, and the design-sync skill's own conventions enumerate design systems that carry no stylesheet at all — a Grommet-style kit uses props and a theme provider, a Chakra-style one uses token strings. If an export carries that idiom, FR-010 has nothing to derive from.
Diagnosis
This is the single most load-bearing unverified assumption in the slice: the whole no-vision decision rests on it, and vision is the fallback it forecloses.
Fix
Verify against a real export — which the experiment this triage precedes will produce — then either keep the refusal with evidence or move it to a tested assumption with the fallback named. Batched with T-001.

The attached-design-system loop is unmodelled, and it may remove the need to infer at all

Spec upstream

Debugging why derivation is needed for a source that can be given the project's own components, root cause was that the spec models Claude Design only as an artifact emitter and never as a tool a design system is pushed into; fixed by modelling the loop; regeneration fails, because nothing in the spec suggests the second path exists.

Expected
The cheapest correct path for each source is the one specced.
Actual
Claude Design projects attach a design system, and Claude Code ships a skill whose entire purpose is pushing a repository's real components up so that "the design agent builds with the customer's actual components". In that loop the design already speaks the project's token vocabulary, so there is nothing to infer and nothing to confirm.
Diagnosis
A materially better path than AI extraction, and it may take Claude Design out of FR-010's scope entirely — which would make FR-010 a Stitch-only requirement and worth saying so.
Fix
Model the loop, or record deliberately that it is out of scope and why. Batched with T-001.

The ecosystem's default handoff bypasses the import verb

Spec code

Debugging what a user will actually reach for, root cause was that Claude Design ships a first-class Send to Claude Code handoff that lands work in the working directory directly; fixed by acknowledging it in the alternatives or out-of-scope block; regeneration passes, because nothing in the spec is wrong — it is silent, and silence about a competing default is a different defect from a false claim.

Expected
A spec that chooses an import mechanism acknowledges the mechanism its users already have.
Actual
Send to Claude Code is listed as a primary developer handoff. It is agent-mediated rather than a folder import, so it does not violate FR-002 — but it means the default path most users take never reaches this verb.
Diagnosis
Not a contradiction, an omission. Worth a line so the choice reads as considered rather than unaware.
Fix
One entry in §5 out of scope or the alternatives table. Lowest priority of the five; batched with T-001.

Four must-tier requirements have a type and no runtime, and every task is checked

Implementation code

Debugging why a real import landed no provenance, root cause was that six of twelve requirements — four of them must-tier — exist only as exported type declarations that nothing constructs; fixed by building them; regeneration passes, because the requirements say plainly what to build and the drain simply did not.

Expected
18 of 18 tasks checked means the twelve requirements are built.
Actual
importDesignSource reads a directory, copies each file byte-for-byte, and returns a ledger. That is FR-001, FR-002, FR-007, FR-008 and FR-009. Nothing else runs. No provenance is written (FR-004, must), nothing is marked inferred (FR-005, must), nothing is marked unreviewed (FR-006, must), no token candidates are derived (FR-010, must), no annotation category is reported unhandled (FR-011), no licence is checked (FR-012).
Diagnosis
The vocabulary was built and mistaken for the behaviour. Provenance, ImportedFile, EXPORT_OWNED_FIELDS and UNKNOWN are all exported and all consumed by nothing outside their own module — a repo-wide search finds importers only in the generated .d.ts. ImportLedger.unhandled is initialised on one line and never pushed to on any other, so it is structurally always empty. Every one of these reads as done: the type is there, the name is right, the doc comment explains the rationale at length, and the unit tests exercise the copier that was built. This is the project's own "presence is not containment" discipline one level up — a declared type passes every structural check a built feature would.
Fix
packages/core/src/visual/import.ts — construct an ImportedFile per landed file and write its provenance, inferred and reviewed marks somewhere a reader sees them; push to unhandled; build the token derivation. Then re-open the six tasks. Until then the checkboxes are wrong and should be un-checked rather than left claiming coverage.
Fixed
All six built and verified end-to-end against a real-shaped export. Provenance is written per file with an unknown field recorded rather than guessed; landed material is marked not-yet-reviewed in an artifact a reader opens, not only in a ledger a command discards; token candidates are derived, counted and left unnamed, because naming one is the decision a human is uniquely able to make; a file carrying a runtime is reported rather than landed; a forbidding licence stops the file before anything is written. 19 tests added, every one asserting behaviour reachable from importDesignSource — never the presence of a type, since a type is exactly what passed last time. The 18 task checkboxes are now honest rather than newly ticked.
Deep dive — why this is implementation and not spec

The requirements are unusually specific and would regenerate correctly: FR-004 names the three provenance fields and says an unknown one is recorded as unknown; FR-006 says the mark must be visible to a reader. An implementer reading them would build the behaviour. So the ladder stops at implementation.

What it says about the drain is the more useful finding, and it is not this spec's to fix: nothing checks that a requirement has a runtime, only that a task is ticked. Worth raising separately rather than folding in here.

Importing a real export makes the project invalid, which FR-003 forbids

Spec upstream

Debugging a validate failure straight after an import, root cause was that the importer copies verbatim while a real design export carries a <script> the artifact rules reject at error severity; fixed by deciding what an import does with executable content; regeneration fails, because nothing in the spec says the landed bytes must satisfy the project's own rules.

Expected
FR-003: "After an import, the project MUST remain valid with the source location deleted."
Actual
A Claude Design export is a .dc.html carrying <script type="text/x-dc" data-dc-script>. Landing it produces error no-executable-content — <script> (inline) in a spec — a spec carries no executable content (P-11). Reproduced against a real export from a real project, reduced to a three-line probe to confirm the rule is categorical.
Diagnosis
FR-003 was written about reference — that nothing points at the source once the import is done — and reads naturally as being about links. It is silent on whether the landed material itself must be valid, and the copier makes that the load-bearing question: the two most likely export formats in the field are HTML, and one of them is a runtime that needs its script to mean anything. So the requirement most likely to fail is the one the slice named as its central property. Note the collision is with P-11, which is a principle rather than a rule that can be relaxed for this case.
Fix
specs/105-design-source-import/spec.html — a propose. FR-003 needs a second clause about the landed bytes, and the slice needs a decision on executable content: strip it, refuse the file, or land it somewhere the artifact rules do not reach. The third is not obviously available, since the sidecar convention puts it inside the project.
Fixed
Resolved as a refusal to land rather than a propose, which the card had not offered as an option and which turns out to need no requirement change: FR-011 already establishes reporting as the posture for material the vocabulary cannot take, and this is the same statement one level up, about a whole file. So the import reads the file, derives what it can from it, and declines to copy it — which keeps FR-003 true as written. Confirmed by deleting the export folder and revalidating clean.
Deep dive — cross-spec and principles

Touches 045's no-executable-content and P-11 directly. Worth noting that stripping the script from a .dc.html does not degrade it gracefully — see T-008, where the script is what produces the values. So "strip it" and "land something useful" may be in tension, which is the decision the propose has to make rather than assume.

The export is a template, not a rendering — the values are not in the file

Spec upstream

Debugging what FR-010 would derive token candidates from, root cause was that the export interpolates every value at runtime rather than emitting it; fixed by stating what an import may assume about a source artifact; regeneration fails, because the spec's stated premise about these artifacts is wrong.

Expected
FR-010: derive token candidates from an emitted artifact. The refusal to use vision rests on the reasoning that an artifact-emitting source emits a stylesheet, which is text.
Actual
Neither half holds for the real export. There is no stylesheet — every value is an inline style= attribute. And the markup is a template: <sc-for list="{{ states }}"> repeated over data, with {{ s.figure }}, {{ s.rateLine }} and {{ s.id }} throughout. The eleven states are produced by a renderVals() method in the trailing script. A reader parsing the file statically sees {{ s.figure }}, never a figure. The per-screen identity is interpolated too — data-screen-label="{{ s.id }} · light".
Diagnosis
Two different claims fail together. Colour and spacing are statically present, so token derivation is still possible — from inline attributes rather than a stylesheet, which is a mechanism change. But screen and state identity are not present at all, which is a capability change: the material the vocabulary most wants is exactly the material the export computes. Recorded honestly, this weakens the vision refusal's justification without overturning it — the file is still text, and the script is still readable text describing the data.
Fix
specs/105-design-source-import/spec.html — fold into T-007's propose. State what a source artifact may be assumed to contain, and correct the alternatives rationale that names a stylesheet. Whether an importer may read the data out of a template's own script is the real open question, and it should be asked rather than assumed either way.
Deep dive — supersedes an earlier finding

This refines T-003, which recorded the stylesheet claim as unverified. It is now verified and false. T-003 stays as the record of the doubt; this card carries the answer.

A design project attaches no design system by default, so there is nothing to inherit

Spec upstream

Debugging why the imported design carried no tokens, root cause was the assumption that a design project has a design system attached; fixed by correcting the assumption; regeneration fails, because it is recorded as a finding rather than a guess.

Expected
Per T-004: design projects attach a design system, so the token file already exists and needs no inferring.
Actual
The real project attached none. The export carries zero token references and roughly forty distinct raw hex literals, hand-duplicated across a light and a dark copy of the same markup — #F7F5F1/#161310, #1C1914/#F1EDE3, and so on down the file. The two copies are structurally identical and differ only in those literals.
Diagnosis
T-004 generalised from the presence of the feature to its use. Attaching a design system is available and optional, and a designer asked to produce screens from a spec has no reason to reach for it first. So FR-010's derivation is more load-bearing than T-004 suggested, not less — and the light/dark duplication is a strong signal for it, since a literal appearing in exactly two positions across two otherwise-identical subtrees is a mode pair rather than a coincidence.
Fix
specs/105-design-source-import/spec.html — supersede T-004's note in the same propose. FR-010 stays in scope for this source and its derivation has a usable signal.
Deep dive — none required

No cross-spec contract, no invariant. It corrects an earlier card of this log and widens FR-010's applicability rather than narrowing it.

There is no way to get an export onto the filesystem that FR-001 requires it to already be on

Spec upstream

Debugging how to hand the importer a directory, root cause was that the only read path returns file contents into a model's context with no way to write them to disk; fixed by naming who is responsible for landing the export; regeneration fails, because the spec assumes a step it never assigns.

Expected
FR-001: "An import MUST read from a location already on the local filesystem." Something has to put it there.
Actual
For this source there are two routes and neither is specified. A human exports a .zip by hand and unzips it — noted as T-002 and still unassigned. Or the design tool is read programmatically, which returns each file's content and offers no write-to-disk: every byte must pass through the model's context and be re-emitted to land, so a bundle is read twice and a large one cannot be landed at all. Confirmed against the real project.
Diagnosis
FR-001's "already on the local filesystem" is what makes one code path serve five tools, and it is right. But the slice treats getting it there as somebody else's problem without ever saying whose, so in practice the verb cannot be reached without a manual step nothing documents. Related and worth recording beside it: a project of the screen-carrying type resolves fine when its id is known but does not appear in a project listing, which filters to the design-system type — so the read path works and is undiscoverable, and an id must come from a human.
Fix
specs/105-design-source-import/spec.html — fold into the same propose. Either name the manual export-and-unzip as the supported path and document it, or add a requirement for a fetch step that writes to disk. Do not leave it implied.
Deep dive — bears on the whole slice's premise

Taken with T-005, the ecosystem's own handoff bypasses this verb entirely — so the honest question the propose should ask is not only how material lands but whether the import verb is the path anyone takes. That is a scope question and it should be asked, not settled here.
