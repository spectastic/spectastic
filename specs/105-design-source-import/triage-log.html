Cards

Claude Design has a persistent, readable design document — the refusal's stated reason is wrong

Design upstream

Debugging why this spec's alternatives table scores a live read path so low, root cause was a survey claim that is factually false — Claude Design exposes get_project, list_files and read_file, and Claude Code ships a /design import that uses them; fixed by re-grounding D-001 on portability rather than on absence, and correcting the survey; regeneration fails, because an implementer reading the survey would restate the same false premise.

Expected
The reason for refusing a live read path is one that survives checking.
Actual
The survey's D-002 says "Claude Design and Stitch have no persistent design document to read", and this spec's alternatives rationale leans on it: "Two of the five sources have nothing persistent to query at all." Both are wrong for Claude Design. Its projects are addressable at claude.ai/design/p/<projectId>, and the file API is already wired into this very session's tool surface.
Diagnosis
The survey's own §13 records that "the design tools were read, not exercised" — and Claude Design is not even named in that hedge, which makes its row the least-evidenced of the five. The decision is unaffected: /design import needs a login, a subscription and a consent grant, which is exactly the "only as available as somebody's seat" failure D-001 rejects. Only the justification has to change, from there is nothing to query to querying it costs portability.
Fix
A propose against this spec correcting D-001's Context and the alternatives rationale, plus a §13 correction and a §1 table fix in the survey. Deliberately not yet: the same research surfaced four more findings (T-002 to T-005) and the experiment that motivated it will likely surface more, so this is amended once rather than five times.
Deep dive — cross-spec, and a scoring consequence

The alternatives table scores "A live protocol client" 6 against "Local export only" 15, and part of that gap is the false premise. Re-scored honestly the winner does not change — portability, cost and five-sources-one-path all still favour the local export — but the margin is smaller and the table should say so rather than carry a number nobody can reproduce.

The survey is the upstream artifact here, so correcting only this spec would leave the false claim sitting where the next reader finds it first.

Four must-tier requirements have a type and no runtime, and every task is checked

Implementation code

Debugging why a real import landed no provenance, root cause was that six of twelve requirements — four of them must-tier — exist only as exported type declarations that nothing constructs; fixed by building them; regeneration passes, because the requirements say plainly what to build and the drain simply did not.

Expected
18 of 18 tasks checked means the twelve requirements are built.
Actual
importDesignSource reads a directory, copies each file byte-for-byte, and returns a ledger. That is FR-001, FR-002, FR-007, FR-008 and FR-009. Nothing else runs. No provenance is written (FR-004, must), nothing is marked inferred (FR-005, must), nothing is marked unreviewed (FR-006, must), no token candidates are derived (FR-010, must), no annotation category is reported unhandled (FR-011), no licence is checked (FR-012).
Diagnosis
The vocabulary was built and mistaken for the behaviour. Provenance, ImportedFile, EXPORT_OWNED_FIELDS and UNKNOWN are all exported and all consumed by nothing outside their own module — a repo-wide search finds importers only in the generated .d.ts. ImportLedger.unhandled is initialised on one line and never pushed to on any other, so it is structurally always empty. Every one of these reads as done: the type is there, the name is right, the doc comment explains the rationale at length, and the unit tests exercise the copier that was built. This is the project's own "presence is not containment" discipline one level up — a declared type passes every structural check a built feature would.
Fix
packages/core/src/visual/import.ts — construct an ImportedFile per landed file and write its provenance, inferred and reviewed marks somewhere a reader sees them; push to unhandled; build the token derivation. Then re-open the six tasks. Until then the checkboxes are wrong and should be un-checked rather than left claiming coverage.
Fixed
All six built and verified end-to-end against a real-shaped export. Provenance is written per file with an unknown field recorded rather than guessed; landed material is marked not-yet-reviewed in an artifact a reader opens, not only in a ledger a command discards; token candidates are derived, counted and left unnamed, because naming one is the decision a human is uniquely able to make; a file carrying a runtime is reported rather than landed; a forbidding licence stops the file before anything is written. 19 tests added, every one asserting behaviour reachable from importDesignSource — never the presence of a type, since a type is exactly what passed last time. The 18 task checkboxes are now honest rather than newly ticked.
Deep dive — why this is implementation and not spec

The requirements are unusually specific and would regenerate correctly: FR-004 names the three provenance fields and says an unknown one is recorded as unknown; FR-006 says the mark must be visible to a reader. An implementer reading them would build the behaviour. So the ladder stops at implementation.

What it says about the drain is the more useful finding, and it is not this spec's to fix: nothing checks that a requirement has a runtime, only that a task is ticked. Worth raising separately rather than folding in here.

Importing a real export makes the project invalid, which FR-003 forbids

Spec upstream

Debugging a validate failure straight after an import, root cause was that the importer copies verbatim while a real design export carries a <script> the artifact rules reject at error severity; fixed by deciding what an import does with executable content; regeneration fails, because nothing in the spec says the landed bytes must satisfy the project's own rules.

Expected
FR-003: "After an import, the project MUST remain valid with the source location deleted."
Actual
A Claude Design export is a .dc.html carrying <script type="text/x-dc" data-dc-script>. Landing it produces error no-executable-content — <script> (inline) in a spec — a spec carries no executable content (P-11). Reproduced against a real export from a real project, reduced to a three-line probe to confirm the rule is categorical.
Diagnosis
FR-003 was written about reference — that nothing points at the source once the import is done — and reads naturally as being about links. It is silent on whether the landed material itself must be valid, and the copier makes that the load-bearing question: the two most likely export formats in the field are HTML, and one of them is a runtime that needs its script to mean anything. So the requirement most likely to fail is the one the slice named as its central property. Note the collision is with P-11, which is a principle rather than a rule that can be relaxed for this case.
Fix
specs/105-design-source-import/spec.html — a propose. FR-003 needs a second clause about the landed bytes, and the slice needs a decision on executable content: strip it, refuse the file, or land it somewhere the artifact rules do not reach. The third is not obviously available, since the sidecar convention puts it inside the project.
Fixed
Resolved as a refusal to land rather than a propose, which the card had not offered as an option and which turns out to need no requirement change: FR-011 already establishes reporting as the posture for material the vocabulary cannot take, and this is the same statement one level up, about a whole file. So the import reads the file, derives what it can from it, and declines to copy it — which keeps FR-003 true as written. Confirmed by deleting the export folder and revalidating clean.
Deep dive — cross-spec and principles

Touches 045's no-executable-content and P-11 directly. Worth noting that stripping the script from a .dc.html does not degrade it gracefully — see T-008, where the script is what produces the values. So "strip it" and "land something useful" may be in tension, which is the decision the propose has to make rather than assume.

The export is a template, not a rendering — the values are not in the file

Spec upstream

Debugging what FR-010 would derive token candidates from, root cause was that the export interpolates every value at runtime rather than emitting it; fixed by stating what an import may assume about a source artifact; regeneration fails, because the spec's stated premise about these artifacts is wrong.

Expected
FR-010: derive token candidates from an emitted artifact. The refusal to use vision rests on the reasoning that an artifact-emitting source emits a stylesheet, which is text.
Actual
Neither half holds for the real export. There is no stylesheet — every value is an inline style= attribute. And the markup is a template: <sc-for list="{{ states }}"> repeated over data, with {{ s.figure }}, {{ s.rateLine }} and {{ s.id }} throughout. The eleven states are produced by a renderVals() method in the trailing script. A reader parsing the file statically sees {{ s.figure }}, never a figure. The per-screen identity is interpolated too — data-screen-label="{{ s.id }} · light".
Diagnosis
Two different claims fail together. Colour and spacing are statically present, so token derivation is still possible — from inline attributes rather than a stylesheet, which is a mechanism change. But screen and state identity are not present at all, which is a capability change: the material the vocabulary most wants is exactly the material the export computes. Recorded honestly, this weakens the vision refusal's justification without overturning it — the file is still text, and the script is still readable text describing the data.
Fix
specs/105-design-source-import/spec.html — fold into T-007's propose. State what a source artifact may be assumed to contain, and correct the alternatives rationale that names a stylesheet. Whether an importer may read the data out of a template's own script is the real open question, and it should be asked rather than assumed either way.
Fixed
Applied change 2026-08-13-read-more-land-less. FR-010's premise is replaced — derivation reads whatever text the artifact carries, not a stylesheet it may not have — and the open question was asked and answered: reading a template's script is reading data, not executing it, so it is permitted. The bound is now stated in the requirement rather than discovered later: colour is recoverable, screen and state identity may not be present at all. Turning a template's data into declarations was deferred as TBD-visual-import-translation rather than left implied.
Deep dive — supersedes an earlier finding

This refines T-003, which recorded the stylesheet claim as unverified. It is now verified and false. T-003 stays as the record of the doubt; this card carries the answer.

There is no way to get an export onto the filesystem that FR-001 requires it to already be on

Spec upstream

Debugging how to hand the importer a directory, root cause was that the only read path returns file contents into a model's context with no way to write them to disk; fixed by naming who is responsible for landing the export; regeneration fails, because the spec assumes a step it never assigns.

Expected
FR-001: "An import MUST read from a location already on the local filesystem." Something has to put it there.
Actual
For this source there are two routes and neither is specified. A human exports a .zip by hand and unzips it — noted as T-002 and still unassigned. Or the design tool is read programmatically, which returns each file's content and offers no write-to-disk: every byte must pass through the model's context and be re-emitted to land, so a bundle is read twice and a large one cannot be landed at all. Confirmed against the real project.
Diagnosis
FR-001's "already on the local filesystem" is what makes one code path serve five tools, and it is right. But the slice treats getting it there as somebody else's problem without ever saying whose, so in practice the verb cannot be reached without a manual step nothing documents. Related and worth recording beside it: a project of the screen-carrying type resolves fine when its id is known but does not appear in a project listing, which filters to the design-system type — so the read path works and is undiscoverable, and an id must come from a human.
Fix
specs/105-design-source-import/spec.html — fold into the same propose. Either name the manual export-and-unzip as the supported path and document it, or add a requirement for a fetch step that writes to disk. Do not leave it implied.
Fixed
Neither, as it turned out — a third answer the card had not seen. New FR-013 admits an archive as a source. A zip on disk already satisfies FR-001 as written, so nothing needed relaxing, and the fetcher seam already returns a directory — so one archive fetcher serves every source rather than one adapter per tool, which is the coupling FR-001 exists to prevent. The no-network position is untouched: an archive is opened, never downloaded. The programmatic read path's inability to write to disk stops being load-bearing, because every one of these tools exports a zip.
Deep dive — bears on the whole slice's premise

Taken with T-005, the ecosystem's own handoff bypasses this verb entirely — so the honest question the propose should ask is not only how material lands but whether the import verb is the path anyone takes. That is a scope question and it should be asked, not settled here.

FR-016 writes through a mechanism that does not exist, and the deferral is circular

Cross-spec upstream

Debugging how a confirmed candidate reaches the token set, root cause was that the named mechanism ships a reader and a refusal but no writer — and the question of what a version means on arrival was deferred to this spec by the spec this defers it to; fixed by one of the two owning it; regeneration fails, because both point at each other.

Expected
The task says "write through 098's own token-set mechanism, so the version bump and its compare-and-swap guard apply".
Actual
Verified in code: 098 ships readTokenSet (a reader) and assertTokenSetVersion (a guard that throws and returns nothing). Neither writes a token or bumps a version; both assume a caller that already authored the release.

And 098's own out-of-scope defers "Importing a token set from a design tool, and what its version means on arrival" — to the slug this spec drains. 098 handed the question here, FR-016 hands it back, and nobody owns it.

Diagnosis
My register raised this as the primary constraint and dispositioned it mitigated on the ground that the requirement "says write into the token set without saying how". Silence is not a constraint on an implementation; it is the absence of one. Under KB-0001@2026-07-25's grounding discipline a must-tier decision resting on an unverified fact is accepted, naming who accepted it and why — never mitigated, which asserts the gap is closed. I named no file and no symbol, and when the sources are opened they disagree.

The framing failed too: "everything after the name is clerical" is false. A release must declare a change class, which 098 requires every surface to present as the producer's claim. A tool that classifies a bump asserts a claim its producer never made. The human part is naming and classifying.

Fix
A propose. Either 098 grows a writer and 105 calls it, or 105 owns the write and 098's out-of-scope is amended to say so. Not both, and not neither.
Fixed
Applied 2026-08-14-own-the-write. This spec now owns the write, since 098 deferred arrival-versioning here in writing and ships a reader and a refusal rather than a writer. The requirement states the properties the write must satisfy rather than naming a mechanism, so 098 growing one later changes an implementation and not a requirement. The clerical claim is corrected too — the change class is the confirmer's, because 098 requires it presented as the producer's claim.

Specupstream

Debugging what the write actually produces, root cause was that a release must declare from= and to= and the requirement names two human inputs, neither of which is a version — so by omission the tool authors one.

The write shipped anyway, and invented the bump policy it claimed to follow

Implementation code

Debugging what T-1201 actually landed, root cause was that bumpVersion hardcodes standard semantic-version increments while FR-016 requires the move happen under the versioning policy — a policy 098 FR-001 deliberately keeps as the element's own prose, which this code never reads; fixed by refusing to author a version rather than assuming one; regeneration passes, because the requirement said "under the versioning policy" and the implementation substituted a different policy without checking they agreed.

Expected
A version moves under the policy the project stated, or the write refuses.
Actual
bumpVersion('2.1.0', 'minor') returns 2.2.0 by arithmetic alone. It never opens the <spec-token-set> prose that governs it, so a project whose stated policy differs — and the currency-converter exemplar's does say something specific: "MAJOR when a token is removed or its meaning is redefined; MINOR when a token is added or deprecated; PATCH for a value change that alters no binding" — gets a number the tool chose and the producer never declared. The tests I wrote pin the arithmetic, so they confirm the assumption rather than catch it.
Diagnosis
Implementation drift against a requirement that was clear enough. T-013 had already named this exact hazard the day before and said "decide who supplies the produced version before writing any obligation to move it"; the obligation was implemented while the card sat open. Two halves are worth separating: the ownership question (who authors to=) is T-013's and is still undecided, while silently substituting a policy for the one the artifact states is drift no spec decision excuses. Only the second half is this card's.
Fix
packages/core/src/visual/import.ts — stop deriving to=. Either take it from the confirmer alongside the name and the class (the shape FR-016 already uses for both other human inputs), or refuse the write when the declared policy cannot be discharged mechanically. Which of the two is right is T-013's to settle; until it does, the honest interim is to refuse rather than assume. The three tests asserting the arithmetic go with it — they encode the defect.
Fixed
Both, as it turned out, and they were the same change. bumpVersion is deleted; the produced version is now a required confirmer input alongside the name and the class, validated for presence and readable shape only — never for agreement with the declared tier, since checking that would be the same substitution one step removed. A missing or malformed version is refused with a message naming the reason (the policy is prose; read it and state the version). The refusal is the interim: nothing can be written without a human having read the policy, and if T-013 later finds a policy that can be discharged mechanically, deriving becomes additive rather than a correction. The arithmetic tests are gone, and the one that replaced them asserts a version standard arithmetic could never produce (2.1.0 + minor → 3.5.7) — verified to fail against the old implementation before being trusted, which is the check the deep dive says the originals never got.
const major = Number(m[1]); switch (tier) { case 'major': return `${major + 1}.0.0`; case 'minor': return `${major}.${minor + 1}.0`; case 'patch': return `${major}.${minor}.${patch + 1}`; } // The policy is prose by design (098 FR-001), so it cannot be // discharged mechanically. The produced version is an input. throw new Error('token-set write: the produced version must be supplied…');
Deep dive — hotfix-before-amendment, and what the tests were worth

Sequence. This is the hotfix half of an amendment that has not happened. T-013 owns the requirement question and is open; this card owns the code that ran ahead of it. Landing the refusal first is safe in the direction that matters — nothing currently calls writeConfirmedToken outside its own tests, so no caller loses a working path, and a refusal cannot write a wrong version into a token set.

The tests confirmed the assumption rather than catching it. Worth recording plainly, because the suite went green and that greenness was evidence of nothing. moves the version under the declared tier asserts 2.1.0 + minor === 2.2.0 — which is true of standard semver and true of the exemplar's stated policy, so the one case that would have exposed the gap (a project whose policy diverges) was never written. A test written from the implementation agrees with the implementation. The guard tests are unaffected and still earn their keep: the stale-set refusal is real, and declaredFrom is a caller input, so the read-then-pass-own-read failure T-013 also warned about was avoided.

Not promoted. Whether a validate rule could catch "code claims to follow a prose policy it never reads" is not a question this card answers — it is close to undecidable in general, and naming it here is only so the next reader sees it was considered.

A first import always fails: the destination sidecar is never created

Implementation code

Debugging ENOENT: no such file or directory, open 'visual/support.js' on a real import, root cause was that importDesignSource writes three times and never creates --into; regeneration passes, because the corpus importer this spec transfers its properties from does mkdirSync before writing and the FileSystem port already carries mkdir.

Expected
Importing into a sidecar that does not exist yet creates it. That is the ordinary case — a project's first import, which is the one US1 describes.
Actual
Exit code 2, nothing written, no visual/. importDesignSource (packages/core/src/visual/import.ts) calls fs.writeFile at three sites — the landed file, the replaced file, and the manifest — and never fs.mkdir. The CLI registrar does not create it either.
Diagnosis
An omission, not a design choice. FileSystem.mkdir exists on the port and is documented as "recursive, idempotent directory create", added for exactly this class of failure when the apply kernel hit it (meta-spec T-007 — the archive move ENOENTing on a spec's first archive). The same bug, in a different verb, two months later.

It survived because every previous run of this import wrote into a visual/ that already existed. The failure needs a genuinely fresh project to surface, and the only downstream project had been imported into before. Rolling that repo back to its handoff tag reproduced a real first-run and it failed immediately.
Fix
packages/core/src/visual/import.ts — await fs.mkdir(input.into) before the write loop. Mirrors the corpus importer's mkdirSync(referencesDir, {recursive:true}) and the apply kernel's mkdir-before-rename. A test importing into a non-existent directory is what keeps it fixed; every existing test seeds the destination.
Fixed
await fs.mkdir(input.into) before the write loop, mirroring the corpus importer and the apply kernel's mkdir-before-rename. Two tests, both confirmed red first. Deep dive — what it says about the test suite, and about the exemplar

Implementation code

Debugging who expands a design export, root cause was not a missing requirement but a missing implementation — FR-013 has required an import to accept an archive and materialise it since 13 August, and the source-reading seam is one method that takes a directory; fixed by implementing expansion with a bound on what it may write; regeneration passes, because the requirement is right and only the code is absent.

Expected
Handing the importer a .zip works, since every user-facing export from the tool is one.
Actual

Diagnosis
Found while drafting 2026-08-18-what-the-design-tool-is, which tried to add this as a new requirement on the premise that nothing agreed to open an archive. The adversarial pass showed FR-013 already agrees, at must tier, with a no-network clause the new requirement had dropped. Fix
packages/core/src/visual/source-fetcher.ts: accept a directory or a single archive, expanding the latter. Bound what an expansion may write — an entry resolving outside the destination, a symlink entry, and an unreasonable decompression ratio are each refused rather than written. Neither FR-013 nor the withdrawn requirement mentions those bounds, and expanding somebody else's archive is a filesystem-reach change; NFR-001's at-most-0-partially-written-files also applies, since expansion writes before the read-then-plan phase.
Fixed
The card's premise was wrong, and the correction is the useful part. FR-013's archive expansion has been implemented all along, in packages/core/src/providers/archive-source-fetcher.ts — 149 lines, a central-directory walk over inflateRawSync, wired into the CLI behind looksLikeArchive. Three separate reads concluded it was missing (the handover document, an adversarial pass, and this card) because all three searched packages/core/src/visual/, and a provider lives in providers/.

What was missing is two of the three bounds. Traversal was guarded from the start; a symlink entry and a decompression bomb were both expanded happily — the reader never read the external attributes or the uncompressed size. Both now refuse, naming the entry, with tests built against archives the system zip produces rather than hand-rolled bytes.

A duplicate reader was written before the existing one was found, and deleted. The lesson is the one this session keeps paying for: a negative asserted about a package after searching one directory of it is not a finding.
