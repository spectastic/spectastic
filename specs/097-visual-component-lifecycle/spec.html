Visual component lifecycle

The one thing that migrates — born inside a feature, promoted when a second reaches for it, and often not written here at all.

Status Accepted Spec ID 097-visual-component-lifecycle Owner Brian Corbin · @briancorbinxyz Reviewers — Created 12 Aug 2026 Principlesv1.9.0 Smallest demoableA component declared local to one feature, promoted by proposal, with its origin and licence intact after the move. Read time

Tokens are project-scoped and screens are feature-scoped. A component is neither for its whole life: it is born inside one feature and may become shared, which makes it the only declared thing that migrates between scopes. Promotion is not a file move — it is a change of which clock governs the component, from the feature's change log to the design system's version, and from one consumer to many. It is therefore a proposal, decided by a person, never automatic. Two further properties are orthogonal to that scope: a maturity, which reuses the six-value status vocabulary this project already has rather than minting the experimental-beta-stable ladder a seventh time, and an origin, because on the dominant model today most components are not authored here at all. A vendored component carries the provenance the knowledge corpus already requires — where it came from, which version, under what licence — and a pin to a version that has moved on is a warning rather than a failure.

1 · Context

The scope split that works for tokens and screens has no home for a component, because a component changes scope during its life. Promoting one early is the classic design-system failure — the cost of a wrong abstraction exceeds the cost of temporary duplication, which is why the long-standing advice is to build directly on the first use, tolerate duplication on the second, and abstract on the third.

And most components are not authored by the project at all. The fastest-growing model copies a component's source into the consuming repository, where the consumer owns it from that moment — including, explicitly, responsibility for keeping it current. That is a different thing from importing a package, and both are different from authoring. A lifecycle that assumes authorship describes a minority of real projects.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · A component becomes shared deliberately P1

As an author whose feature needs something another feature already built, I want to promote it into the design system by proposal so that the moment it stopped belonging to one feature is recorded rather than assumed.

Acceptance: Promoting a local component writes it to the project location, updates the declarations that referenced it, and refuses if the destination changed since the proposal was raised.

US2 · A vendored component remembers where it came from P1

As a maintainer, I want a component copied in from elsewhere to carry its origin, version and licence so that I can tell what is ours, what is borrowed, and what has moved on upstream.

Acceptance: A vendored component declares its provenance; a pin to a version that has since been superseded reports a warning, and a reference to a version that never existed reports an error.

US3 · Maturity is legible without a new vocabulary P2

As a consumer, I want to see how settled a shared component is so that I can judge whether to build on it.

Acceptance: A promoted component carries a status from the vocabulary already used across this project's artifacts, and a deprecated one names its replacement.

Edge cases

  • A component consumed from a package rather than copied in. There is no file to move, so promotion means declaring shared use rather than relocating anything.
  • A local component wrapping an external one — locally owned on the outside, borrowed on the inside.
  • A project that authors nothing, whose project-scoped component set is legitimately empty.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A component MUST be declarable at feature scope, and MUST be promotable to project scope. Scope, maturity and origin MUST be independent properties.

Rationale

A vendored component can be local or shared; an authored one can be either; maturity varies across all of them. Collapsing three properties into one state machine would make most real combinations inexpressible.

Promotion MUST be initiated by a person through a change proposal and MUST NOT occur automatically on detected reuse.

Rationale

Promoting automatically converts a weak signal — two things that resemble each other — into a strong-looking one, which is the refusal this project has already made about inferred relationships. It also promotes on the second use, which is a use too early.

Promotion MUST be planned before any write, MUST abort entirely if any part conflicts, and MUST refuse when the destination has changed since the proposal recorded it.

Rationale

The same three properties the contract promotion already holds, and for the same reason: a conflict discovered on the tenth write must not leave nine applied.

Promotion MUST update every declaration that referenced the component at its former scope, so that no declaration is left pointing at a location the component has left.

A promoted component MUST carry a maturity drawn from the status vocabulary already used by this project's artifacts, and MUST NOT introduce a parallel one.

A component MUST declare its origin as authored, vendored or consumed.

A vendored component MUST carry provenance — where it came from, its address, the version taken, and its licence — and that provenance MUST survive promotion unchanged.

Rationale

Copying a component into a repository is a licensing event as much as an engineering one, and nothing in design tooling records it. The field set is the one the knowledge corpus already requires of a document taken from elsewhere.

A reference to an origin version that has been superseded MUST report a warning, and a reference to one that cannot be resolved at all MUST report an error.

Rationale

Being behind upstream should nag; pointing at nothing should fail. The same severity split the corpus makes between a stale pin and a dead reference.

A consumed component MUST be declarable without a file in the project, and its promotion MUST mean declaring shared use rather than relocating anything.

An empty project-scoped component set MUST NOT be reported as a gap.

Rationale

A project consuming everything from a library legitimately authors none. Reporting that as incomplete would reproduce the failure where a section was seeded into a population that could never fill it.

A deprecated component SHOULD name its replacement, and SHOULD NOT be removed in the same change that deprecates it.

A component MAY be demoted from project scope back to a single feature, by the same proposal route as promotion.

Non-functional

Promotion MUST be atomic: on any conflict, at most 0 files are written and at most 0 declarations are modified.

Provenance MUST NOT be fabricated: a field whose value is unknown MUST be recorded as unknown, with at most 0 invented origins, versions or licences.

Out of scope (deferred to other slices)

  • The version a promotion bumps, and what binds forward from it.
  • Measuring a component's rendered result, and the question of which parts of a screen the project owns.
  • Importing a component from a design tool, as opposed to from a code library.
  • The element a component is declared with, which the vocabulary slice owns.

4 · Data model

No persisted entity beyond the component's own files. This spec adds properties and a transition between two of their values.

Entities

Component
A named, reusable part of a surface. Carries a scope, a maturity and an origin, which vary independently. Belongs to one feature or to the project.
Promotion
A planned, human-initiated transition of one component from feature scope to project scope, together with the updates to every declaration that referenced it. Atomic.
Provenance
For a component not authored here: its origin, address, version taken and licence. Never fabricated; unknown is a recordable value.

Promotion changes which clock governs the component — from the owning feature's change log to the design system's version, and from one consumer to many. The file moving is a consequence, not the point; for a consumed component nothing moves at all and the promotion is still real.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

After a promotion, the count of declarations still pointing at the component's former scope is 0, and the count of promotions that occurred without a proposal is 0.

The count of vendored components missing any provenance field is 0, and the count of fabricated provenance values is 0.

A promotion interrupted by a conflict leaves at most 0 files written, verified by attempting one against a destination that has changed.

A project that authors no components reports 0 gaps about its empty component set.

6 · Assumptions

A person will notice they have built the same thing twice. Because a feature-scoped component is deliberately invisible to other features, nothing can detect the second use, so the workflow rests on human attention. That is consistent with the advice to tolerate the second duplication rather than abstract on it, and it is still a dependency on someone paying attention.

Upstream versions are comparable enough to tell superseded from unresolvable. The corpus makes the same assumption and compares by equality rather than order, which is the weaker and safer reading.

7 · Open questions

None outstanding. Both questions carried from drafting were decided at design time and are recorded in the design's decisions rather than left here. A wrapper references what it wraps rather than copying its provenance: one record of origin, version and licence, at the import, resolved through the reference — so the two can never disagree and a wrapper never reads as locally owned. Scope stays binary, and a component records which features use it: the rule of three then becomes visible evidence a person reads before proposing promotion, without the tool inventing a third state whose transition nothing could decide.
