Visual component lifecycle

Ordered, parallelizable work. Tests precede implementation. Drive through with /spectastic.implement — one task per invocation.

Status Accepted Spec 097-visual-component-lifecycle Design design Branch spec/visual-slice-095-098 Created 12 Aug 2026 Read time

23 tasks across four phases. Setup → Foundational → User stories (US1·US2·US3) → Polish. Tasks marked [P] can run in parallel. Tests for a story MUST be written and failing before its implementation tasks start.

1 · Execution strategy

Setup → Foundational → US1 → US2 → US3 → Polish. US1 is promotion, which is the only task with a write; US2 is provenance; US3 is maturity, which is almost entirely a matter of not inventing a vocabulary.

US2 alone is defensible as a first ship: recording where a vendored component came from is useful even before anything can be promoted, and it is the half with a licensing consequence.

Not applicable. One element, two rules, one kernel operation.

Extend the shared vocabulary — the component element, the two scopes, the three origins, and the maturity values re-exported from the project's existing status set rather than redeclared. packages/schema/src/visual-vocabulary.ts

3 · Phase 2 — Foundational

The reader both rules and the promotion operation share.

Implement the component reader — pure, no filesystem, and treating scope, maturity and origin as orthogonal rather than as one state. packages/schema/src/component.ts

Closes part of FR-001 — the independence of the three properties.

4 · Phase 3a — US1 · A component becomes shared deliberately

Tests (write & fail first)

Write the promotion plan's tests red — a plan reads and writes nothing, and a conflict anywhere aborts the whole plan rather than applying the writes before it. packages/core/test/promote-component.test.ts
Write the moved-destination refusal red — comparing baseline against current, never incoming against current, because the incoming component is expected to differ. packages/core/test/promote-component.test.ts
Write the consumed-component case red — promotion declares shared use and relocates nothing, which is the case an implementation assuming a file move will break on. packages/core/test/promote-component.test.ts

Assert promotion is never automatic — nothing in the module detects reuse or initiates anything; the entry point takes an already-decided proposal. packages/core/test/promote-component.test.ts

Closes FR-001, FR-002, FR-003, FR-004, FR-010, FR-012, SC-001.

5 · Phase 3b — US2 · A vendored component remembers where it came from

Tests (write & fail first)

Write the provenance tests red — a vendored component missing its origin, version or licence errors; an authored one is not asked for any of them. packages/schema/test/component-provenance.test.ts
Write the severity-split tests red — a superseded reference warns and an unresolvable one errors, the same split the corpus makes between a stale pin and a dead reference. packages/schema/test/component-provenance.test.ts
Write the wrapper tests red — a wrapper carries no copied provenance, its wraps= must resolve, and the wrapped component's origin is readable through the reference. packages/schema/test/component-provenance.test.ts

Implementation

Implement the provenance rule — the corpus's field set, and nothing fetched: unresolvable means undeclared in this project, not unreachable over a network. packages/schema/src/rules/component-provenance.ts
Preserve provenance across promotion — a promoted vendored component carries the same origin, version and licence it had before. packages/core/src/visual/promote-component.ts

Closes FR-007, FR-008, FR-009, SC-002.

6 · Phase 3c — US3 · Maturity is legible without a new vocabulary
