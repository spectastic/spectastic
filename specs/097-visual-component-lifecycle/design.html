Design · 097-visual-component-lifecycle

Visual component lifecycle

How we will build it.

Status Accepted Spec 097-visual-component-lifecycle Owner Brian Corbin · @briancorbinxyz Branch spec/visual-slice-095-098 Created 12 Aug 2026 Read time

One element with three independent properties — scope, maturity, origin — because collapsing them into a state machine makes most real combinations inexpressible: a vendored component can be local or shared, an authored one either, and maturity varies across all of them. Promotion reuses 071's machinery rather than a second implementation: plan then execute, abort entirely on any conflict, refuse when the destination moved since the proposal recorded it. Maturity draws on the six status values this project already has — draft, review, accepted, superseded, deprecated, blocked — so there is no seventh vocabulary. Provenance is the corpus's field set with the corpus's severity split: a superseded version nags, an unresolvable one fails. And the two questions carried from drafting are settled — a wrapper references what it wraps rather than copying its provenance, and scope stays binary with the second use recorded as evidence a person reads.

3 · Data model & contracts

One element carrying three independent properties, plus two references. The independence is the design: a vendored component can be local or shared, an authored one either, and maturity varies across all of them.

Conceptual entityPhysical shapeNotes
Component <spec-component name scope maturity origin> Three orthogonal attributes. scope is binary; maturity is one of the project's six status values; origin is authored, vendored or consumed.
Provenance origin-url edition license on a vendored component. The corpus's field set, because copying a component in is the same act as taking a document in, and the corpus already decided what must be recorded.
Wrapping wraps="<name>" A reference, not a copy. One record of origin exists and the wrapper reads through it — see D-001.

This feature exposes no interface. It adds a declaration, checks over it, and a promotion operation, all consumed inside the tool.

5 · Approach

One element, three independent attributes, two references. A shape rule checks the attributes; a provenance rule checks that a vendored component records where it came from and that its reference resolves; a promotion operation in core plans every write before making any, and refuses when the destination has moved.

The two questions this spec carried from drafting are answered the same way, and it is worth naming the shared reasoning: reference rather than copy. A wrapper points at the component it wraps instead of repeating its provenance, so one record exists and the copies cannot disagree. A component records the features that use it instead of the tool inferring shared use, so the evidence is visible and the judgment stays human. Both are the same refusal the corpus makes when it cites a document rather than duplicating it.

Promotion is not a file move for every origin. A consumed component has no file in the project at all, so promoting it means declaring shared use and relocating nothing — FR-010 says so explicitly, and it is the case most likely to be missed by an implementation that assumes promotion means copying bytes. The plan therefore describes declaration updates and, only where a file exists, a move.

6 · Alternatives considered

The choice with real alternatives was how a wrapper records what it wraps. Scored on whether the two records can disagree, whether a wrapper is visibly not locally owned, and whether it can be read without following a reference. 5 is best.

OptionCannot disagreeWrapper is visibly not localReadable standaloneTotal
Provenance stays at the import only5139
Provenance chains onto the wrapper15511
wraps= reference — chosen55313

Chaining scores perfectly on the two criteria a reader notices and worst on the one that bites later: two copies of a licence and a version will diverge, and a diverged licence record is worse than none because it looks authoritative. The reference loses only on standalone readability, which a rendered view can recover and a divergence cannot.

7 · Decisions

D-001 · A wrapper references what it wraps; provenance is recorded once

Status
Accepted
Context
The spec's first open question: recorded twice the copies can disagree, recorded once the wrapper looks locally owned. Both halves are real, and the corpus already resolved the same tension for documents by citing rather than duplicating.
Decision
wraps="<name>" on the wrapper. Origin, version and licence live once, on the component being wrapped. A wrapper declaring origin="authored" with a wraps= is visibly resting on somebody else's work, and the reference must resolve or it is an error.
Consequences
+ One record, so a licence and a version cannot diverge. + The wrapper never reads as locally owned. − Reading a wrapper's licensing position means following one reference; a rendered view can compose it, but the raw artifact does not. − A wrapping chain deeper than one is unaddressed here — resolvable, and not something this slice needs.

D-002 · Scope stays binary, and the second use is evidence rather than a trigger

Status
Accepted
Context
The spec's second open question. The rule of three implies a real gap between the second use and the third, and a third scope value would name it — but nothing could decide when that scope becomes project, so the tool would have added a state it cannot transition. Meanwhile FR-002 already forbids acting on detected reuse.
Decision
Two scopes. used-by= records the features that use a component, so a second entry is visible to a person deciding whether to propose promotion. The tool never proposes it.
Consequences
+ The rule of three becomes legible without the tool inventing a rung. + Consistent with the refusal already made about inferred relationships. − used-by is hand-maintained and will go stale; it is evidence a human weighs, not a fact anything depends on, and the design says so rather than pretending it is authoritative. − A component genuinely shared by two features sits at feature scope, which reads as understating it.

D-003 · Promotion reuses 071's machinery rather than a second implementation

Status
Accepted
Context
FR-003 asks for three properties — planned before any write, aborts entirely on conflict, refuses on a moved destination — and states they are "the same three the contract promotion already holds". Reading promote.ts confirms it, including the baseline-versus-current insight recorded there as its headline risk.
Decision
Clone the plan/execute split and the conflict shape. A component promotion plans declaration updates and, where a file exists, a move; a consumed component's promotion relocates nothing.
Consequences
+ Atomicity and the refusal come from a reviewed implementation rather than a fresh one. + The two promotions stay legible as the same operation. − Two similar modules that could drift; the shared property is stated in both headers rather than extracted, because a premature abstraction over two callers is its own cost.

D-004 · Maturity is the project's existing status vocabulary, unmapped

Status
Accepted
Context
FR-005 forbids a parallel vocabulary. The field's usual ladder — experimental, beta, stable, deprecated — maps onto draft, review, accepted, deprecated, and this project already styles all six values.
Decision
Use the six directly. No mapping table, no aliases, no seventh value.
Consequences
+ A reader who knows what Draft means on a spec knows what it means on a component. + The stylesheet already renders every value. − "Accepted" is a slightly odd word for a stable component, and an author arriving from a design-system background will look for "stable"; accepted deliberately, because a synonym is the parallel vocabulary the requirement forbids.

D-005 · Provenance is recorded, never resolved

Status
Accepted
Context
FR-009 wants a superseded version to warn and an unresolvable one to error — which sounds like fetching. It is not: the corpus makes the same split without a network call, by resolving a reference against what the project has committed.
Decision
origin-url is provenance a human reads and nothing fetches. "Unresolvable" means the referenced component is not declared in this project; "superseded" means the declaration says so. No network access, consistent with P-11.
Consequences
+ Deterministic, offline, and no supply-chain surface. + A dead wraps= fails loudly. − The tool cannot tell you that upstream has moved on, only that your own records disagree; that is a real ceiling and is stated rather than implied.

D-006 · An empty component set is never a gap

Status
Accepted
Context
FR-010, and the evidence behind it: a project consuming everything from a library legitimately authors no components. This repository has already shipped the opposite — a section seeded into a population that could never fill it, producing 77 unanswerable gap rows.
Decision
No check reports the absence of components. The rules fire only on a component that is present and malformed, which is the same scope discipline every rule in this slice holds.
Consequences
+ A consuming project is not told it is incomplete for being what it is. − No coverage signal exists, so nothing notices a project that should have declared a component and did not; that is deliberate, and the same trade 096 made.

9 · Risks & mitigations

RiskLikelihoodImpactMitigation
An implementation assumes promotion moves a file, and breaks for a consumed component.MMCalled out in §5 and given its own test. It is the case most easily missed, because every other origin does involve a file.
used-by goes stale and somebody treats it as authoritative.HLStated in D-002 as evidence rather than fact. Nothing computes from it, so a stale entry misleads a reader and breaks no check.
The two promotion modules drift.MMAccepted in D-003. Both headers state the shared property; extracting a common abstraction over two callers is the larger risk.
A partial promotion leaves declarations pointing at a location the component has left.LHThe whole reason for plan-then-execute. Tested by forcing a conflict mid-plan and asserting nothing was written.

10 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here.

Two rules rather than one. Shape and provenance are separable obligations with different audiences — an author gets the first wrong while writing, a reviewer cares about the second at licence-audit time — and a finding that names which was missed is actionable where "malformed component" is not. It follows the same reasoning 095 used for splitting three.

No exemplar component is authored in this slice. The currency-converter is a single-feature project, so every component in it would sit at feature scope and promotion could not be demonstrated — a fixture project in the tests exercises it honestly, and inventing a second exemplar feature to show promotion would be building a demonstration rather than a demonstration of something.

11 · Open questions

None outstanding. The spec's two carried questions were the substance of this design's first two decisions, and both resolve the same way — reference rather than copy. The promotion machinery, the maturity vocabulary and the provenance severity split were all settled by reading code that already exists rather than by asking.
