Governing-decision injection

Put the decisions that govern the code being touched in front of the agent before it writes — fenced as data, so the output accounts for them rather than being caught afterwards. A happy-path aid, never the guarantee.

1 · Context

The research pass on the corpus found that its injection reaches five authoring verbs but is undifferentiated (the whole index), and that implement — the verb at the code-writing moment — has no injection at all. The 114 plan-constraint and 115 verdict catch an unacknowledged or violated decision after the fact; rubric item 3 asks for the governing decisions to reach the agent before it writes, so the happy path is right the first time. This slice adds a path-selective injection of exactly the decisions that govern the surface being worked.

Its user is the agent authoring tasks or code, and the human reading a prompt that now names the relevant decisions. It is deliberately an aid: the guarantee lives in the gates (P-8 / T-009 — an advisory prompt cannot force compliance, as spec 111's cross-tool spike showed), and this slice must not pretend otherwise.

2 · User scenarios & testing

Governing decisions surface at tasks time. A design's project-structure tree touches src/**/persistence/**, governed by an accepted decision. When tasks assembles its prompt, that decision's id and reason appear in a block fenced as untrusted data — so the task breakdown accounts for it.

Nothing governs → nothing injected. A surface no decision governs (or a design with no §Project-structure yet) yields an empty block — no noise.

The code-writing nudge is advisory. implement has no kernel prompt, so the command and the impl-task agent instruct running spectastic adrs --for <task-path> and accounting for the result — a nudge, honestly labelled, not a gate.

3 · Requirements

A pure buildGoverningDecisionsBlock(paths, decisions) MUST render the active decisions governing the given paths (via 113's retrieval) as a prompt block fenced as untrusted data — carrying each decision's id, coordinate, and reason — and MUST return an empty string when no path is given or no decision governs. The block MUST be injected into the tasks kernel prompt, computed over the design's declared project-structure surface, so the task breakdown sees the decisions governing the code area. The block MUST be injected into the design kernel prompt over whatever surface the design declares; on a first authoring (no project-structure yet) it renders empty, and on re-entry (a surface exists) it populates — no separate code path. The implement command and the spectastic-impl-task agent SHOULD instruct consulting spectastic adrs --for <task-path> and accounting for the governing decisions before authoring. This is an advisory markdown nudge — implement has no kernel prompt to inject into — and provides no enforcement. The injection MUST be advisory only: the block is fenced as data the agent accounts for, never an instruction the tool obeys, and the 114/115 gate verdicts MUST be identical whether or not the block was injected (injection is not a gate input). The block builder MUST be pure and deterministic — the same paths and decisions yield a byte-identical block on every run — with at most 0 model clients and 0 network modules on its path.
  • Making the corpus's own injection path-selective — the corpus (054) still injects its whole index; narrowing that is a separate corpus concern.
  • The Socratic teaching layer — slice 5.
  • Any gate behaviour — the guarantee is the verdict/constraint; this slice only surfaces context.

4 · Data model

Governing set
The active decisions whose scope matches a surface's paths (113's retrieval), the payload of the block.
Injection block
A fenced-as-data prompt fragment listing each governing decision's id, coordinate, and reason; empty when the governing set is empty.
Surface
The paths a design declares (its project-structure tree) or a task names — what the injection is computed over.

6 · Assumptions

  • 113's decisionsForPaths and loadDecisions supply the governing set; the fencing primitive is @spectastic/schema/fence, as the corpus uses.
  • The design's declared surface is read the same way 114 reads it (the project-structure tree extractor).
  • A markdown nudge cannot be guaranteed to change agent behaviour (T-009); its value is a UX prompt, and the gates are the guarantee.

7 · Open questions

None outstanding — the scope (builder + design/tasks wiring + advisory implement nudge), the honesty framing (aid not guarantee), and the empty-on-first-authoring behaviour were all anchored before drafting.
