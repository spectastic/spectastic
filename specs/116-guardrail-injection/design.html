Governing-decision injection

How we will build it.

Status Accepted Spec 116-guardrail-injection Owner Brian Corbin · @briancorbinxyz Branch main Created 13 Sep 2026 Read time

A pure buildGoverningDecisionsBlock(paths, decisions) that reuses 113's retrieval and the corpus's fenceArtifactText, wired into the design and tasks kernel prompts exactly where buildCorpusPromptBlock already injects, plus an advisory markdown nudge in the implement command + agent. Biggest risk: reading as a guarantee when it is an aid — mitigated by a gate-independence test.

1 · Principles check

P-8 / T-009 — OK: the injection is explicitly an aid, not a guarantee; a gate-independence test proves the verdict ignores it. P-14 — OK: the builder is kernel logic; the verbs just inject it. No exceptions logged.

Governing decisions acknowledged

Floor already wired; this adds a builder + two injection lines + markdown. No new toolchain.

No external interface. buildGoverningDecisionsBlock(paths: string[], decisions: GovernanceDecision[]): string returns a fenced-as-data block (a directive line + a fenced list of governing decisions' id/coordinate/reason) or ''. The verbs compute paths via 114's extractDeclaredSurface over the relevant design.html.

6 · Approach

Add buildGoverningDecisionsBlock to the guardrail module, mirroring buildCorpusPromptBlock: run 113's decisionsForPaths over the given paths, and if any govern, render a directive + a fenceArtifactText block listing each decision's id, coordinate, and reason; else return ''. Wire it into design.ts and tasks.ts beside the corpus block, computing paths via 114's extractDeclaredSurface over the relevant design.html (empty for a design being authored fresh, populated once §project-structure exists). Add the advisory nudge to the implement command and the impl-task agent. A gate-independence test proves the 114/115 verdicts never read the block.

8 · Decisions

D-001 · buildGoverningDecisionsBlock mirrors buildCorpusPromptBlock

Context. The corpus already ships the fence-and-directive shape (prompt.ts:97, fence.ts:146). Decision. Same shape — directive + fenceArtifactText — over 113's governing set; '' when empty. Consequences. + P-11 fencing for free; familiar to a reader. − Two similar builders (corpus + governing) — acceptable, they carry different payloads.

D-002 · Wire into design + tasks at the corpus injection point

Context. design.ts:139-148 and tasks.ts:38 already inject the corpus block. Decision. Compute the governing block via 114's extractDeclaredSurface and join it beside the corpus block. Consequences. + One obvious insertion point per verb. − design's first-authoring block is empty (no §structure yet) — intended (FR-003), not a bug.

D-003 · implement's injection is an advisory markdown nudge

Context. implement.ts has no ctx.ai prompt (grounding row 5). Decision. The command markdown + the impl-task agent instruct running adrs --for <task-path> before authoring, flagged advisory. Consequences. + Honest about where the guarantee is (the gates). − Cannot be enforced (T-009) — recorded, not hidden.

D-004 · Test-first, low risk

Context. A pure builder + two injection lines on a proven pattern. Decision. TDD; low risk. A gate-independence test guards the aid-not-guarantee property. Consequences. + Regression-guarded. − None material.

10 · Risks & mitigations

Injection read as a guarantee

Likelihood medium, impact medium. Mitigation: the gate-independence test proves the 114/115 verdicts ignore the block; the spec + design state "aid, not guarantee" throughout.

The markdown nudge doesn't change behaviour (T-009)

Likelihood high, impact low. Mitigation: this is expected — the nudge is a UX prompt; the guarantee is the gates. Recorded as the ceiling, not treated as a defect.
