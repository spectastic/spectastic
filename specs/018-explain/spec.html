explain — the grounded coach

A first extended verb: explain <target> gives an ephemeral, in-chat, just-in-time explanation of a real spec, decision, or file — grounded in source, never invented, pulled on demand.

The eight lifecycle verbs are the core / hero set. explain is the first extended, opt-in verb. In this slice it ships in one form only: explain <target>, an ephemeral in-chat coach that explains a named spec, requirement, decision, or file grounded in real repository source. It writes no artifact, mutates nothing, and runs only when pulled. The richer explain --course mode is deferred to a sibling spec; this slice reserves the two migration-sensitive seams (--proficiency flag, extended-verb packaging) so the deferral never forces a later breaking change.

1 · Context

Spectastic ships eight lifecycle verbs — principles · spec · plan · tasks · implement · propose · apply · triage — installed by default. A junior engineer or product reviewer who lands on a finished spec has no in-tool way to understand it: they leave for a chat window, where any explanation is ungrounded and free to invent APIs and requirements that don't exist. That detachment is the documented failure mode of code-grounded learning.

The handover at docs/explain.html settled the frame: a new verb explain in the extended (opt-in) tier, in two depths — an ephemeral coach and a persistent --course — built coach-first, course once grounding is proven. This spec is the coach. Stakeholders: the learner pulling an explanation, and the maintainer adding an extended verb without bloating the default surface.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Grounded explanation on demand P1

As a reviewer new to a spec, I want to run explain <target> and read an explanation grounded in its actual content so that I understand it without leaving for an ungrounded chat that might invent details.

Acceptance: on a real ID or path, an in-chat explanation returns; every cited ID, symbol, and path resolves to a real artifact; the working tree is unchanged (FR-001–FR-003).

US2 · Band-aware coaching depth P2

As a learner of known competence, I want to set --proficiency so that the explanation matches my level — full scaffolding when new, terse when independent.

Acceptance: the band is accepted and changes depth; absent it defaults to wheels; an invalid value is rejected (FR-006–FR-007).

US3 · Opt-in extended verb P2

As a project maintainer, I want to enable explain deliberately rather than ship it in the default eight so that the day-to-day verb surface stays minimal.

Acceptance: a default install omits explain; the installer distinguishes core from extended verbs; explain enables via a documented opt-in step (FR-009).

Edge cases

  • Target resolves to nothing → the coach reports the miss and stops (FR-004), never fabricating.
  • Target is ambiguous (an ID present in several specs) → one clarifying question, then proceed (FR-005).
  • Several targets passed at once → each is explained, each independently grounded.
  • An ad-hoc topic with no repo anchor → rejected as out of scope for this slice (belongs to the course sibling).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A /spectastic.explain <target> command MUST produce an ephemeral, in-chat explanation of the named target and MUST NOT write any artifact file or otherwise modify the repository.

Rationale

A course is the persistent sibling (D-008); the coach is deliberately ephemeral — the explanation is the chat, regenerated on the next pull, so nothing goes stale on disk.

The command MUST accept a repo-anchored <target> — a spec ID, a requirement / decision / success-criterion ID, or a file or directory path (one or several) — and MUST resolve each against real repository source before explaining it.

Rationale

Ad-hoc topics with no repo anchor are the weakest, least-grounded mode and are deferred to the course sibling; this slice keeps the grounding guarantee clean.

Every symbol, path, or ID the explanation cites MUST resolve to a real artifact in the repository; the coach MUST NOT reference anything it has not confirmed exists.

Rationale

D-010: confident-but-wrong content is the dominant failure mode of code-grounded learning; retrieval-grounding is the best-supported mitigation. A coach that cites a hallucinated symbol is worse than no coach.

If a target does not resolve to real source, the command MUST report the miss and stop, rather than synthesizing an explanation from generic knowledge.

When a target resolves ambiguously (to more than one artifact), the command MUST ask a single clarifying question; otherwise it MUST proceed one-shot without an interview.

Rationale

The coach's value is low-friction, just-in-time pull. A full two-phase interview every invocation would defeat that; a single disambiguation only when genuinely needed preserves it.

The command MUST accept a --proficiency flag with the fixed vocabulary wheels | completion | independent, defaulting to wheels when unset and while no persisted state exists.

Rationale

D-012 seam: the CLI surface must be stable from v1, so adding personalization later is purely additive. Defaulting to wheels fails safe — more scaffold, never less.

Coaching depth SHOULD fade by band: independent yields a terse, skippable explanation; wheels yields the fullest scaffolded one.

Rationale

Expertise reversal (D-001/D-009): guidance that helps novices degrades experts. The band is the fading lever.

Coaching MUST be pull-only: the coach runs only when explicitly invoked and MUST NOT be auto-injected into any other command's output.

explain MUST be packaged as an opt-in extended verb: it MUST NOT be part of the default-installed hero set, and the installer MUST distinguish core from extended verbs.

Rationale

D-007/D-011 seam: explain is the first extended verb. If it ships with no notion of tiers, formalizing the split later forces a file-move/manifest migration for every installed project. The exact mechanism (manifest flag vs separate install path) is a plan decision; the distinction must exist now.

explain SHOULD reuse the existing command-file shape (front-matter description + argument-hint; Inputs; Procedure; Output style) and existing grounding machinery; no new <spec-*> elements are required to ship it.

Non-functional

Invoking explain MUST be read-only with respect to the repository: no tracked or untracked file is created, modified, or deleted, and git state is unchanged. The working tree MUST be byte-identical before and after.

The v1 coach SHOULD add no new persistent state or storage; the --proficiency band is supplied per-invocation.

Rationale

D-001's storage question (per-author state in a single-file world) is a real open question, deferred cleanly. The flag ships now; defaulting from stored state arrives additively later.

Out of scope (deferred to other slices)

  • The explain --course mode and all course machinery — objectives, mastery ledger, Bloom-driven modality, verified exercises, the course.html artifact. Specced as the sibling 019-explain-course (design in docs/explain.html).
  • Persistent storage of the band and per-objective mastery state (D-001). Until it lands, the flag is passed explicitly (NFR-002).
  • Ad-hoc topic mode (a target with no repo anchor) — the weakest, ungrounded mode; belongs to the course sibling.
  • Graded teach-back (D-005), <spec-signoff> (D-002), JSON-LD emitter (D-004), reading-lens toggle (D-003) — all deferred per handover §5; cleanly additive.

4 · Data model

This slice owns no persisted entity — by design (NFR-002). It works with three transient inputs.

Entities

Target reference
A user-supplied token resolved to real source: a spec ID, a requirement / decision / success-criterion ID, or a file/dir path. May be plural. Resolution is the gate before any explanation (FR-002).
Proficiency band
An enum, wheels | completion | independent, supplied per-invocation via --proficiency (default wheels). The entire learner model in this slice; tunes depth only (FR-006/FR-007).
Explanation
The ephemeral in-chat output. Not persisted; every cited reference is repo-resolved (FR-003). No ID of its own — it references the stable IDs it teaches.

The absence of persisted state is the invariant worth guarding: if a later change needs to remember a band or a mastery flag, that is the storage seam (D-001) — deferred, additive, and explicitly not this slice.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

Across a sample of explanations over real targets, 100% of the symbol, path, and ID references they cite resolve to artifacts that exist in the repository — zero hallucinated references.

Every invocation against an unresolvable target stops with a reported miss; none produce a fabricated explanation.

A user can obtain a grounded explanation of a repo target in a single command invocation, with no separate tool launched and no file generated.

6 · Assumptions

The coach runs inside an existing session whose model can read local repository source; explain rides that session rather than standing up new retrieval infrastructure.

The eight hero verbs and their command-file conventions exist and are stable; explain follows the same shape (FR-010).

No per-author proficiency/mastery state exists yet; the band is supplied per-invocation until the storage seam (D-001) is specified in a later slice.

7 · Open questions

No open question blocks this slice — every decidable question was anchored during the interview. Two forward dependencies are resolved by deferral, not left open here: the exact extended-verb packaging mechanism (manifest flag vs install path) is a plan decision under FR-009; the proficiency/mastery storage location is owned by the deferred course sibling (see §3 Out of scope). Both are tracked, neither is undecided.
