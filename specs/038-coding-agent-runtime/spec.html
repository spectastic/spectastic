Coding-agent runtime

Make implement actually code: a runtime that drains tasks through an injectable coding-agent seam, sandboxed in a worktree, ticking only past the verify gate.

Status Accepted Spec ID 038-coding-agent-runtime Owner Brian Corbin · @briancorbinxyz Reviewers — Created 09 Jul 2026 Principlesv1.3.0 Smallest demoableA stub coding-agent performs one fixture task end-to-end (perform → tests pass → tick); a failing outcome halts the drain with the box unticked. Read time

The implement kernel only ticks a checkbox — the actual coding lives outside the kernel, in the harness agent following markdown. That is why a hands-off run (037) can't implement on its own. This spec adds a coding-agent seam: an injectable CodingAgent the runtime hands one task at a time, which performs the edits and runs the task's tests and reports a verifiable outcome. The runtime ticks a task only when its tests pass (P-7). The coding runs in an isolated git worktree, so a failed run never touches the primary tree. CI runs a deterministic stub agent (the AI-in-CI discipline); the real tool-using adapter is a local-only smoke tier.

1 · Context

The implement kernel (014) is a checkbox-ticker: it regex-ticks a <spec-task> and reports the flip prompt — it never writes code (the ctx is unused). The real "read the task, write the code, run the tests" work lives in the slash-command markdown, performed by the tool-using harness agent. Grounding for 037 (the hands-off pipeline) surfaced the consequence: a pure spectastic run can generate plan/tasks/verify but cannot perform the implement step — the kernel's AIProvider is text-only (no tools, no file edits).

This spec closes that gap for the operator who wants run to code unattended, and for the maintainer who needs that coding to be trustworthy: sandboxed so a bad run can't corrupt the tree, and never marked done until its tests actually pass.

2 · User scenarios & testing

Each story MUST be independently testable: US1 alone is a viable MVP.

US1 · Drain a task list into tested code P1

As an operator, I want the runtime to perform each unchecked task through a coding-agent and tick only the ones whose tests pass so that a task list becomes real, verified code without my keystrokes.

Acceptance: given a fixture bundle and a stub coding-agent, the runtime performs each task in order, runs its verify, ticks a task iff its outcome passes, and halts + escalates on the first failing outcome (box left unticked).

US2 · A bad run can't corrupt the tree P1

As a maintainer, I want the coding to run in an isolated git worktree, accepted only after the verify gate so that a failed or abandoned run leaves the primary working tree untouched.

Acceptance: a run whose task fails verify leaves the primary tree byte-for-byte unchanged; a passing task's changes are surfaced for acceptance (merge) only after its tests pass.

US3 · The real agent behind the seam P1

As a Claude-surface user, I want a real tool-using coding-agent adapter so that the runtime performs actual edits and tests, not just orchestrates a stub.

Acceptance: the real adapter performs a genuine edit on a fixture task and its tests pass — exercised by a local-only smoke tier; CI always uses the deterministic stub.

Edge cases

  • The coding-agent returns "done" but the tests fail: the runtime treats it as a failure — no tick, halt + escalate (P-7; the agent's word is not trusted).
  • A task is already ticked: skipped; the drain resumes at the first unchecked task (idempotent).
  • The worktree can't be created (dirty index, not a git repo): the runtime refuses up front rather than editing the primary tree.
  • The agent produces no changes: treated as a blocked outcome — halt + escalate, not a silent pass.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

The runtime MUST define an injectable CodingAgent seam — a perform(task) operation returning a typed outcome (status, changed files, the verify command it ran and its result) — selected the same way the AIProvider is (a stub when a SPECTASTIC_* env var points at a script, else the real adapter).

Rationale

Mirrors the AIProvider/stub seam (007) so CI stays deterministic and offline (the AI-in-CI discipline), and the real agent is one swappable boundary.

For each unchecked <spec-task> in tasks.html, in document order, the runtime MUST invoke the CodingAgent, run the task's verify, and tick the task (via the existing 014 tick) only when the verify passes.

On a failed or blocked outcome (including "done but tests fail" and "no changes produced") the runtime MUST stop the drain and escalate — no tick, no further tasks, no silent skip.

The coding MUST run in an isolated git worktree; a task's changes MUST be surfaced for acceptance only after its verify passes, and a failed or abandoned run MUST leave the primary working tree byte-for-byte unchanged.

Rationale

The W-1 guardrail: an autonomous coding run ships sandboxed and gated or not at all. A worktree isolates edits without a bespoke sandbox and reverts for free.

The runtime MUST be idempotent: re-running after a partial drain resumes at the first unchecked task (the P-6 Draft in-place path) — the ticked tasks.html is the state, no separate run-state machine.

A real tool-using CodingAgent adapter SHOULD perform actual edits + tests behind the seam; it is exercised by a local-only smoke tier, never in CI. The adapter's concrete mechanism (subprocess to a headless agent vs an in-process tool-use loop) is a plan decision.

Non-functional

The real coding-agent adapter MUST NOT run in CI; CI MUST use the deterministic stub, so the suite is offline and reproducible.

No coding-agent output MUST be trusted without the verify gate: a task is ticked only when its tests pass (P-7) — the agent's self-reported "done" is necessary but not sufficient.

Out of scope (deferred to other slices)

  • Parallel workers draining multiple tasks at once — this slice is a single-agent, single-worktree drain.
  • A per-run cost ceiling on the coding agent's token spend — owned by the run-budget sibling.
  • A richer agent protocol (multi-turn negotiation, partial-task handback) beyond perform → verifiable outcome.

4 · Data model

The ticked tasks.html is the durable state (FR-005); the runtime adds two transient shapes.

Entities

TaskWork
{ taskId, title, path, specHtml, planHtml, tasksHtml, cwd } — the one task handed to the CodingAgent, with the bundle context it needs to do the work.
TaskOutcome
{ status: 'done' | 'failed' | 'blocked', filesChanged: string[], verifyCommand?, verifyPassed: boolean, summary } — the verifiable result the runtime gates the tick on.
CodingAgent
The injected seam: perform(work: TaskWork): Promise<TaskOutcome>. Stub (CI) replays a script; real adapter does tool-using work in the worktree.

Invariant: a task is ticked ⟺ its TaskOutcome.verifyPassed is true. The tick and the pass are one gate, never two (NFR-002).

5 · Success criteria

Technology-agnostic, measurable outcomes.

With the stub agent on a fixture bundle, the runtime ticks exactly the tasks whose outcome verifies and halts the drain (box unticked) on the first failing task — observable by the resulting tasks.html tick state.

A coding run whose task fails verify leaves the primary working tree byte-for-byte unchanged — observable by a clean git status / unchanged file hashes after the failed run.

An agent that self-reports "done" while its tests fail results in no tick and an escalation — observable proof the verify gate, not the agent's word, drives the tick (NFR-002).

The real adapter performs a genuine edit on a fixture task and its tests pass — observable in the local-only smoke tier (never CI).

6 · Assumptions

A tool-using coding agent can be invoked from a Node CLI process — whether as a subprocess (a headless agent binary) or an in-process SDK tool-use loop — and confined to a worktree. The concrete mechanism is a plan spike; this spec assumes at least one viable path exists.

The project runs under git (a worktree is creatable). The runtime refuses rather than degrades when it is not (edge case), so no non-git fallback is specified.

7 · Open questions

None outstanding — the seam, the sandbox (worktree), the verify-before-tick gate, the CI-stub discipline, and the single-agent scope were all settled. The real adapter's mechanism is deliberately a plan-time spike (recorded as an assumption), not an open spec decision.
