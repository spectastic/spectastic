No decision on publishing the corpus — is spectastic-concepts meant to be externally importable?

Spec upstream

During US1 the concepts marketplace.json was removed to clear four pack-not-portable errors; that fixed the consumer role but silently skipped the publisher role — whether the repo should offer its corpus for external corpus import was never a requirement. Regeneration fails: another session reading only 062's spec would hit the same clash and make the same undocumented call.

Expected
062 states whether the meta-repo publishes its corpus (a root knowledge/marketplace.json others import from), or deliberately does not — a decided requirement, not a side effect of dodging a lint error.
Actual
062 only ever framed knowledge/ as a consumer corpus root. FR-002 was amended to say "no distributable manifest" purely to clear the portability errors — the publish/don't-publish question was never asked.
Diagnosis
A pack whose domain is spectastic itself is simultaneously distributable (someone learning spectastic might want it) and inherently non-portable (it carries <spec-*> tags and verb names). 057's pack-not-portable rule assumes distributable ⟹ domain-neutral (validate.ts:310: "spectastic's own dogfood … never listed"), so it has no vocabulary for a legitimately tool-specific published pack. The two specs never reconciled this.
Fix
Decide intent first (open question below). If publish: a 062 requirement for a root knowledge/marketplace.json + a 057 amendment carving out a self-declared tool-specific pack from pack-not-portable. If don't publish: keep the current state and add a 062 requirement recording the consumer-only decision + the export path as a TBD. Either way the resolution is a /spectastic.propose on 062, so 062 stays Draft until it lands.
Fixed
Decided and reversed by 063: a corpus is discoverable by default. knowledge/marketplace.json is committed, and the pack-not-portable collision is resolved by a pack self-declaring tool-specific: true in its own SKILL.md.
Deep dive — cross-spec (057) + open scope question

Cross-spec contract. The shared contract is "a pack listed in a marketplace.json must be portable" (057 FR-001, its D-002 exemption-by-omission). Publishing spectastic-concepts would require 057 to gain a first-class notion of an intentionally tool-specific pack (e.g. a manifest/SKILL flag that opts a pack out of the token check, or a rule that a pack whose declared subject IS the tool is exempt) — not the current exempt-because-never-listed posture.

Open scope question (the intent to settle before proposing). Is the meta-repo a corpus publisher (others should be able to corpus import spectastic-concepts@spectastic from it), or purely a consumer that dogfoods the convention in-repo? The demo marketplace under examples/knowledge/ already covers "here is how an external marketplace looks", which weakens the case for also publishing the dogfood pack — but it is a product decision, not a technical one.

No hotfix needed. Current state is internally consistent and error-free; this is a missing requirement, not a live defect. 062 holds at Draft pending the decision.

Resolved (26 Jul 2026): decided consumer-only. Recorded directly on the Draft spec (P-6) as FR-009 — no distributable root marketplace.json, no external publication in this slice — with the publisher role (root manifest + the 057 tool-specific carve-out) deferred to TBD-corpus-publish. No propose cycle needed: the spec had not yet ratified.

Root registry Path column carries the knowledge/ prefix — unspecified relative-to convention

Spec upstream

The root knowledge/index.md Path column reads knowledge/<plugin>/references/<file> (repo-relative) while the pack SKILL.md slug map reads references/<file> (relative to its own file) — a real asymmetry that reads as a bug. It is actually deliberate (the registry path must match loadCorpus's repo-relative doc.filePath so resolveCitation returns one consistent base from both routes), but the convention was never written down. Regeneration fails: the spec says only "path", so another session could pick either base.

Expected
Either the registry Path is relative to the registry's own location (<plugin>/references/<file>, matching the SKILL map), or the repo-relative form is a written, justified convention — not an unstated implementer's choice.
Actual
installPack/registerDocument write path: knowledge/<plugin>/references/<file> (ingest.ts:268, :402); the SKILL map writes references/<file>. 051 FR-009 and 062 only say "path", pinning neither base.
Diagnosis
Not a code defect in isolation: loadCorpus sets doc.filePath = relative(cwd, …) (index.ts:85,108), so the pack-scan half of resolveCitation returns repo-relative paths; the registry's knowledge/ prefix keeps a registry hit's filePath on the same base. Dropping the prefix in isolation would make a current-edition (registry) hit and a superseded (pack) hit return different bases. The gap is the unspecified convention, not the value.
Fix
Pin the convention in the data model (051 FR-009 / 062 §4). Two coherent ends — decision below; either way, both resolver routes must return the same base, so the registry Path and loadCorpus's doc.filePath move together.
Fixed
Registry paths are corpus-root-relative (<plugin>/references/<file>, no knowledge/ prefix), matching installPack and loadCorpus, with a regression test. Pinned in 063 and the code rather than in the artifacts this card named — the convention is stated, just not where the Fix field predicted.
Deep dive — cross-spec (051/061) + the base-consistency constraint

Cross-spec contract. The Path base is a shared contract between the ingester that writes it (061 installPack) and the resolver that returns it (052 resolveCitation, which also returns loadCorpus's repo-relative doc.filePath). The invariant to preserve: ResolvedCitation.filePath means the same thing whether resolution went via the registry or the pack scan. Any convention change touches both writer and reader together, plus the resolver test fixtures and knowledge.migration.test.ts (which opens join(REPO_ROOT, row.path)).

The intentional asymmetry to document. The SKILL map is pack-relative by necessity — it is a portable, pack-local artifact that must read the same in or out of any repo (057). The root registry is a project-local resolution table, so a repo-root base is defensible. The confusion T-002 records is that this was never stated.

No hotfix needed. Current state resolves correctly and validates clean; this is an unspecified-convention gap, not a live defect.

Resolved (26 Jul 2026): paths are now corpus-root-relative — the base (knowledge/) is no longer hard-coded into any stored path, so a configured base can be overridden without rewriting index.md. installPack/registerDocument write <plugin>/references/<file> (ingest.ts); loadCorpus now takes doc.filePath/dirPath relative(knowledgeDir, …) instead of relative(cwd, …) (index.ts), so both resolveCitation routes still return one consistent base. The registry was regenerated by re-running the ingester (not hand-edited). Pinned by test, not spec prose (P-8): knowledge.migration.test.ts asserts no stored path hard-codes the base — since 051/062 never made the base a spec contract, the kernel+test guarantee is the fix, no propose against the Accepted specs needed. Full corpus suite (136 core + 18 CLI) green; validate at the 8-error baseline.
