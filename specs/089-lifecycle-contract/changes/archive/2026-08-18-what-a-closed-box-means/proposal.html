What a closed box means

The element says a tick means done, and the sibling change makes it mean closed.

Status Applied Change ID 2026-08-18-what-a-closed-box-means Spec 089-lifecycle-contract Author Brian Corbin · @briancorbinxyz Created 18 Aug 2026 Targets 1 modified Read time

REQ-LIFECYCLE-003 says a checked box means done and that CSS must never key on a parallel status attribute. The sibling change applied beside this one makes a checked box mean closed and needs exactly that attribute for the retirement pill. Two clauses amended, and the flip predicate's unchanged wording given the meaning it now has.

What a closed box means

Applied

1 · Intent

The sibling change applied beside this one makes a task's checkbox answer open or closed, with a mark saying how it closed. REQ-LIFECYCLE-003 currently contradicts that twice in one bullet: “checked means done”, and “CSS MUST read the state via :has(input:checked) rather than a parallel data-status attribute, so the checkbox is the single source of truth” — which is exactly what the retirement pill needs.

Both clauses were right when written. The checkbox was the single source of truth, because it carried both facts. Splitting the facts is what makes a second source necessary, and pretending otherwise would leave the pill keying on an attribute a must-tier requirement forbids it to read.

2 · Scope

In scope

  • What a checked box asserts, and what may carry the rest.
  • Permitting CSS to read the closure mark, which the retirement pill requires.
  • Saying plainly that the flip predicate's meaning changed even though its wording did not.
  • The semantics themselves, and the migration of the sixteen unclosed retired tasks. 088 owns supersession; this is the element learning what that requires of it.
  • Widening the closure vocabulary. The estate has one non-done closure and this proposal adds none.

3 · Approach

One modified requirement, applied in the same session as its sibling. A cross-spec obligation split across sessions is how the last one landed half-done, and the card recording that is three days old.

The single-source-of-truth clause is narrowed, not deleted. Its purpose was to stop two attributes disagreeing about one fact. After the split there are two facts, so the rule becomes: the box is the sole authority on whether a task is closed, and the mark is the sole authority on how. Neither may restate the other, which preserves exactly what the original was protecting.

The flip predicate is addressed in prose rather than by a delta. REQ-LIFECYCLE-004 and -005 say “the last unchecked checkbox” and “zero remaining unchecked”; that wording stays correct and its meaning changes underneath it, because a retirement now counts toward zero. Verified latent rather than live: the only specs holding retired tasks are 093, 095 and 105, all accepted, so no Draft spec is currently one supersession away from a false completion prompt.

4 · Deltas

One <spec-delta>.

What changes: the checkbox bullet. checked now means closed rather than done, and CSS may read a closure mark for what the box does not carry. The single-source-of-truth rule is narrowed rather than removed — it now applies per fact instead of per element, which is what it was protecting all along. Every other bullet, the styling clause, the forbidden div-form, the title-emphasis rule and the whole rationale are carried through unchanged, with one paragraph appended recording why the clause moved.

Each task entry in a tasks.html artifact MUST be a <spec-task> custom element. The element MUST carry:

  • id="T-NNN" — the stable task ID, matching the format defined for tasks elsewhere in the project.
  • parallel (boolean attribute) — present when the task can run alongside its in-flight peers (the existing [P] convention); omitted otherwise.
  • An inner <input type="checkbox"> — the settlement state. checked means closed: the task is not owed. It does NOT assert that work was performed — a task closed because it was retired is closed too, and carries a data-status mark saying so. The box MUST be the sole authority on whether a task is closed and the mark the sole authority on how: a mark MUST NOT restate closure, and the box MUST NOT encode the manner of it. CSS MUST read closure via :has(input:checked), and MAY read the mark for what the box does not carry.
  • A label child (a <div> or <p>) holding the task text. Its leading emphasis MUST be a single <strong> wrapping a short imperative task title only — not the full task sentence. Any supplementary detail MUST follow in plain-weight prose (conventionally after an em-dash), and the target file or directory SHOULD sit in a trailing <span class="path"> — where path is a layout/styling class exempt under P-2, not a semantic component subject to REQ-AUTHOR-001.

Styling for <spec-task> MUST live in assets/spec.css — not inline in the template. The generic <div class="task"> + class-span form is forbidden as a direct application of REQ-AUTHOR-001. A task-title-bold-scope validate rule SHOULD warn (not error) when a task row's leading <strong> both spans most of the row and the row carries supplementary detail beyond the title (bold continuing past the first em-dash, or the row exceeding a length floor) — the structural signature of a whole-line-bold row. A terse, detail-free title that legitimately fills its own row does not warn.

Rationale

The tasks artifact is regen-derived from a template, so the contract for its internal shape is worth being explicit about. Without a named element, a fresh authoring session falls back to whatever the template already shows — and a class-soup template propagates indefinitely. Codifying <spec-task> turns the implicit pattern into something a validator (or a careful reader) can check. The label-form clause is the same lesson one level down: the original requirement bounded the element's attributes but not its emphasis, so the template's <strong>[TASK]</strong> placeholder was read as "bold the whole task" and every tasks.html from 026 onward became a wall of bold (T-010). Bounding emphasis to a short title restores the title/detail scan the readable pre-026 rows had, and the warn-level rule keeps the drift from silently returning.

The box carried two facts and now carries one. “Checked means done” was true while every closed task was a completed one, and the single-source-of-truth clause was right for the same reason — one fact, one carrier, nothing to disagree. Supersession introduced a task that is closed and not done, and forbidding its box to be ticked kept the tick honest at the cost of making an untick ambiguous, which every consumer then had to special-case and one got wrong. Splitting the facts is what makes a second carrier necessary; the rule survives per fact rather than per element, so the two still cannot contradict each other. The prohibition on restating is what keeps that true — a mark that also encoded closure would recreate the disagreement this clause exists to prevent.

4b · What this change removes

Each entry names one thing this change takes away. An empty register is the answer “nothing”.

  • The assertion that a checked box means work was performed. The same removal the sibling proposal records, restated here because this is the requirement that actually said it — a reader looking for where the invariant lived will find it in this bullet, not in 088.
  • The prohibition on CSS reading a parallel attribute. Narrowed rather than dropped: CSS may now read the closure mark, and may still not read a second opinion about closure itself. Any stylesheet that took the original as “never key on data-status” is now wrong, and the retirement pill is the first thing to rely on that.
