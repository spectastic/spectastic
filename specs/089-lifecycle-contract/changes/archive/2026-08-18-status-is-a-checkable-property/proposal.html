Change proposal · 089-lifecycle-contract

Status is a checkable property

A status that disagrees with the work it describes is detectable, and nothing looks.

Status Applied Change ID 2026-08-18-status-is-a-checkable-property Spec 089-lifecycle-contract Author Brian Corbin · @briancorbinxyz Created 18 Aug 2026 Targets 1 added Read time

The Draft-to-Accepted transition is defined as something that happens at an instant, with the obligation on a command to prompt. A slice finished outside that instant stays Draft with nothing able to notice, and a bundle flipped incompletely stays split the same way. One added requirement making the disagreement detectable — carefully, because the obvious version of this check fires on every spec that has ever received a proposal.

Status is a checkable property

Applied

1 · Intent

REQ-LIFECYCLE-004 defines the transition as “triggered when the last unchecked checkbox is ticked and the author explicitly confirms”, and places the obligation on /spectastic.implement to display the prompt. That is a moment. A slice that reaches completion any other way — a drain that ended in a different session, a flip declined and never revisited — stays Draft, and nothing in the system can notice, because nothing describes what the status should be.

Ten specs were found advertising themselves as Draft while finished, and swept by hand earlier today. Sweeping them is not a fix: the next one is created the same way, by the same gap.

2 · Scope

In scope

  • Making a status that disagrees with the work it describes reportable.
  • Naming the two disagreements that are decidable, and the exemptions that keep them honest.
  • Flipping a status automatically. REQ-LIFECYCLE-004 requires an author's confirmation and this proposal does not touch that: the finding tells a human that the artifact and the work disagree, and the human decides which is wrong.
  • Coupling a §4 invariant to a success criterion — the fourth card in this family, and the one that cannot be made checkable because an invariant is prose.

3 · Approach

The check compares two files, so it is a kernel scan rather than a schema rule — a per-file rule sees a spec.html and cannot see the tasks.html it disagrees with.

The obvious version of this check is wrong, and the census is what showed it. Reading “status should match completion” symmetrically would flag an accepted spec that still has unchecked tasks — and that state is not merely common, it is produced by design: every apply folds its proposal's tasks into the target's tasks.html as a fresh phase, so a spec is normally accepted with open work. 047 is exactly this, with one open task in a folded range. The symmetric check would fire on it, and on every spec that has ever received a proposal.

So the requirement names only the two decidable disagreements, and bounds itself by naming what it reads: three filenames, their header status, and only a slice that has a tasks.html. The meta-spec's execution-only tracker carries no status element and four slices have no tracker at all — both fall outside by construction rather than by exemption.

Current corpus: zero Draft-but-finished, after this morning's sweep; one genuine bundle disagreement — 047, whose spec reads accepted while its design and tasks still read draft.

4 · Deltas

One <spec-delta> per requirement touched.

A lifecycle status that disagrees with the artifacts it describes MUST be reportable. The check applies to exactly two disagreements, and to nothing else. First: a spec.html at draft whose tasks.html carries at least one checkbox and none unchecked MUST be reported, at warning. Second: where a specs/<spec-id>/ slice holds more than one of spec.html, design.html and tasks.html each carrying a status element, those statuses MUST agree, and a disagreement MUST be reported at error. The check reads only those three filenames, only their header status, and only a slice that has a tasks.html.

Rationale

REQ-LIFECYCLE-004 describes an instant and assigns the obligation to a command; REQ-LIFECYCLE-005 requires three siblings to move in one gesture. Both are correct and neither is observable after the fact, so a slice that missed the moment looks exactly like one that never reached it. This states what the status should be, which is the thing a later session can check.

The asymmetry is load-bearing. Reading this symmetrically — status should track completion in both directions — would report every spec that has ever received a proposal, because the apply kernel folds tasks into completed specs in a fresh hundred-range on purpose. Eight accepted specs carry unchecked work today and every one of those tasks sits in a folded phase; unchecked work outside a folded phase totals zero. So the asymmetry is a consequence of how change lands rather than an exception to the rule.

It is stated as a scope limit rather than a prohibition, deliberately. A negation here would need MUST NOT, which the conformance markup cannot distinguish from MUST — the element carries a level for should and may and nothing else, so a consumer reading the level off the element would see the exemption as an obligation and invert it. Saying what the check applies to leaves nothing to misread.

The two severities differ because the two disagreements do. A finished slice still reading draft is bookkeeping — a reader is misinformed while the artifact stays sound — so it warns, like REQ-FORMAT-009. A split bundle is a violated MUST: REQ-LIFECYCLE-005 says three siblings share one status and transition in one gesture, so reporting its breach as advice would say the requirement is optional. Both severities are in the requirement rather than left to the implementation, since an implementer choosing either would otherwise still conform.

Restricting the check to the three named filenames is what keeps it honest. A slice directory also holds archived proposals carrying applied — not one of the six lifecycle values — and a triage log that can carry a status element inside a sentence. Naming the three puts both out of scope by construction rather than by an exemption list that has to anticipate them.

Reporting, never flipping. The disagreement has two possible resolutions — the status is stale, or the work is not really done — and only a person knows which.

5 · Risk register

Populated by the adversarial risk pass. This proposal adds a must-tier requirement.

The blanket past-draft exemption hides four accepted specs holding roughly ninety never-started authored tasks.

Cited: 079 (29), 080 (21), 081 (16), 082 (24) as “unchecked” with no folded phase.

Rejected — the evidence is false, checked twice. All four specs have zero unchecked tasks; the figures quoted are their total checkbox counts, and 29+21+16+24 is exactly the “roughly ninety” claimed. The pattern <input type="checkbox"> was counted without excluding the ones carrying checked — the same blind spot that produced a false “90 owed tasks” earlier in this session, on these files, reaching the same number.

Independently re-run: across the whole estate, unchecked tasks outside a folded phase total 0. The eight accepted specs that do carry unchecked work carry it entirely in folded phases, which is the state the exemption exists for.

What survives, recorded rather than acted on: folded work is mechanically distinguishable — apply writes a phase-<slug> section carrying an archive anchor — so a narrower exemption is available whenever it earns its keep. It does not today, and narrowing on false evidence would have been the worse error.

“Sibling artifacts of one slice” is broader than the bundle REQ-LIFECYCLE-005 defines, and reports its MUST violation as advisory.

REQ-LIFECYCLE-005 names exactly “spec.html, design.html, and tasks.html”. A slice directory also holds archived proposals carrying value="applied" — not one of the six lifecycle values — and a triage log carrying <spec-status> in prose.

Upheld and verified: 047's archive carries applied, and 016's triage log uses a status element inside a sentence. Both confirmed by reading the files. Adopting REQ-LIFECYCLE-005's own three names puts each out of scope by construction rather than by an exemption list that has to anticipate them. Severity split accordingly and moved into the normative text: a split bundle violates a MUST and is reported at error; a finished slice still reading draft is bookkeeping and is reported at warning.

The proposal closes T-001 while addressing part of it, and does not record the remainder.

T-001 names three false-backlog mechanisms; this addresses one and a half.

Upheld on the record-keeping, not on the diagnosis. The “done but unticked” symptom is an accepted spec carrying unchecked boxes, and every instance in the estate today is legitimate folded work — so there is nothing to catch, rather than something being hidden. Task 4 now closes T-001 partially and names what remains, which is the honest state either way.

The three load-bearing exemptions use MUST NOT, a keyword the corpus does not admit, in a form a machine cannot distinguish from its opposite.

KB-0001@2026-07-25 commits three keywords and says the markup makes the level readable “without parsing prose”. <spec-rule>MUST NOT</spec-rule> is byte-identical in attributes to <spec-rule>MUST</spec-rule>.

Upheld and verified: only level="should" and level="may" exist in the estate, and the schema package contains zero references to spec-rule — nothing reads it today, which is what makes this the cheap moment rather than an urgent one. Rather than invent a fourth level here, the three exemptions are restated as affirmative scope limits: the requirement says what the check applies to, so there is no negation to misread. Whether the vocabulary needs a must-not level, and the corpus edition bump that would follow, is a separate question this proposal does not settle.
