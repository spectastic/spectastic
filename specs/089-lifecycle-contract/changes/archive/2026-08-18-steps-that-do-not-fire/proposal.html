Change proposal · 089-lifecycle-contract

Steps that do not fire

Three obligations the lifecycle assumes happen, and the work that gets repeated or stranded when they do not.

Status Applied Change ID 2026-08-18-steps-that-do-not-fire Spec 089-lifecycle-contract Author Brian Corbin · @briancorbinxyz Created 18 Aug 2026 Targets 3 added Read time

A generated task list never exercises the assembled thing, so a project can reach 90% unit coverage and not start. A task waiting on a person blocks two completion mechanisms that have nothing to do with it. And nothing asks whether a task's work already exists, so a wrong card produces a confident reimplementation. Three added requirements, each from a failure that happened rather than one imagined.

Steps that do not fire

Applied

1 · Intent

Three obligations the lifecycle assumes will happen, and does not require. Each has a failure behind it.

A downstream project reached 90% unit coverage and could not be started. Nothing in the generated task list ever assembled the thing and ran it: REQ-LIFECYCLE-003 gives a story failing tests and then implementation tasks, both naturally unit-level, and anything integration-flavoured drifts to Polish, which is last and is what gets cut. The “Done means verified” principle seeded at verified and enterprise already requires “a behavioral check that exercises the running code” — and nothing turns a principle into a task, so the guarantee sits in prose exactly where P-8 says it cannot.

A slice finished its work and never reached completion, because a task gated on a person counts toward the same zero remaining unchecked condition that fires the status flip and materialises the verify view. One waiting gesture blocks two mechanisms, silently.

And a triage card asked for a capability that already shipped. Three separate readers — a handover document, an adversarial pass, and the card itself — concluded a feature was missing because all three searched the directory the card named. It was one directory over, and a duplicate implementation was written before the original was found. REQ-LIFECYCLE-003's procedure loads “any source files the task explicitly names” and then does the work; nothing between those two steps asks whether the work is already done.

2 · Scope

In scope

  • A per-story task that exercises the assembled artifact, inside the story rather than in Polish — owed only where there is something to assemble.
  • A completion condition that reports what is outstanding rather than stalling silently.
  • An obligation to establish that a task's work is not already built, before building it.
  • Deciding what “exercise it” means per project shape. A CLI is an invocation, a library an import-and-call, a service a request, and a schema change none of those. The requirement names the obligation; the shape question has its own slug and a mandatory task half of all projects could not satisfy would be worse than the gap.
  • Automating the human gesture a gated task waits for. The point is that it is a person's; the defect is that waiting for one strands two unrelated mechanisms.

3 · Approach

All three are obligations on the verbs 089 already governs, so they land as requirements rather than as command markdown — which is the whole point. Every one of these failures happened while guidance describing the right behaviour existed somewhere: in a seeded principle, in a command's procedure, in a triage card's own instructions.

The first two must move together. A per-story exercise task is exactly the kind of task that may need a person to drive it — so adding it without fixing the completion condition would hand the second defect a fresh instance in every story of every downstream project.

The third obliges a search and a record, not a correct answer. It cannot prevent a wrong conclusion — only make the basis for one visible, and leave an artifact behind when the search is skipped. That ceiling is stated inside the requirement rather than only here, following the precedent its gate-less sibling set.

4 · Deltas

One <spec-delta> per requirement touched.

Where a project has an artifact that can be assembled and run, a generated task list MUST give each user story at least one task that exercises that artifact along the story's path, and that task MUST sit inside the story's own phase rather than in a later polish phase. Where no such artifact exists, no task is owed. An exercise task names an entry point rather than a file, so the trailing-path convention does not apply to it.

Rationale

Without it a story is complete when its units pass, and the composition is never run. A downstream project reached 90% unit coverage and would not start; the failure was in no unit, and nothing assembled them.

Placement is half the requirement. Anything integration-flavoured currently drifts into Polish because that is the only phase that will take it, and Polish is last — so the task that would have caught the failure is structurally where work goes when time runs out.

Gated on the antecedent rather than owed by everyone, the way the Visual surface section and the contract-first floor are gated: a schema change or a config-only slice has nothing to assemble, and a mandatory task half of all projects cannot satisfy trains people to tick boxes. That also leaves the project-shape axis free to demote the heuristic later rather than replace a requirement.

What “exercise” means is shape-sensitive and deliberately not settled here: an entry point is a command for a library or CLI and an address where a server already serves the feature. Across this estate 67 of 72 recorded run commands are a build or an install, which is the gap. The verify view's field for this is not unused — 20 of 83 views populate it, up from 9 when it landed — so the requirement follows a practice that is already spreading rather than creating one.

Where a completion condition does not fire because work remains, the verb evaluating it MUST report what is outstanding rather than staying silent.

Rationale

Zero remaining unchecked is stated once and consumed twice — by the status flip and by the verify view. A task waiting on a person is indistinguishable from work not done, so one waiting gesture blocks two mechanisms that have nothing to do with it, and both are silent about why.

Reporting rather than excluding, deliberately. REQ-LIFECYCLE-005 already considered this exact case — its body names “an unticked-then-reticked manual gate” — and chose a deterministic count precisely to remove per-task judgment. Excluding a task would put that judgment back and answer a settled question from a third place; reporting leaves the predicate exactly as 005 defines it and fixes what actually cost something, which was the silence rather than the block.

Paired with REQ-LIFECYCLE-010 on purpose. An exercise task is a strong candidate for needing a person, so landing that one without this would multiply this defect rather than leave it where it is.

Before implementing a task, the implementer SHOULD establish that the capability it asks for is not already present, searching by capability across the project rather than only in the files the task names, and SHOULD record what was searched — whether or not anything was found. This obliges the search and the record, not a correct answer: it cannot prevent a wrong conclusion, only make the basis for one visible.

Rationale

A complete duplicate implementation was written before the original was found one directory over, where a provider belongs — after three independent readers, working from a card that named the wrong directory, each searched it and agreed the capability was missing.

The procedure makes this easy to get wrong rather than hard: it loads the files a task names, then does the work. A task naming the wrong file produces a clean search and a confident wrong conclusion, and a clean search reads like proof.

Should rather than must, in this project's committed sense: a deviation needs a reason that exists and is written down, which belongs in the task's own completion note. That is a real obligation, not an advisory one — an implementer who skips the search owes an explanation.

The record is unconditional because the conditional version fires on the rare branch. A search that finds nothing is the case worth recording: it is the one that precedes a duplicate.

5 · Risk register

Populated by the adversarial risk pass. This proposal adds two must-tier requirements.

The requirement is derived from a misreading of its source card, and the record clause is conditioned on the branch that rarely fires.

Proposed: record what was searched “when the task turns out to be already satisfied” — against 105/T-020, whose headline says the root cause was a missing implementation.

Upheld on substance, with one correction to the finding: the card's headline is its original diagnosis and its Fixed row records the opposite — the capability had shipped, in providers/ rather than the visual/ the card searched. The card is genuinely self-contradictory now, because closure annotates rather than rewrites, and the critic read the older half.

The substance stands regardless, and the critic names it: the real evidence is the duplicate reader written before the original was found. The rationale is re-narrated to that, the record is made unconditional so a skipped search leaves an absent artifact rather than a silent one, and the ceiling is stated inside the requirement body following REQ-LIFECYCLE-008's precedent — its two SHOULD-tier siblings each carry a gate half and this one has none.

The exclude branch silently overrides a predicate REQ-LIFECYCLE-005 already settled, for this exact scenario, the other way.

REQ-LIFECYCLE-005's body names “an unticked-then-reticked manual gate” and chooses deterministic evaluation to close the fragility it causes. A third location answering the same question differently would leave the spec self-contradictory after apply.

Upheld and verified by reading 005 in full. Resolved by taking the critic's own preferred branch: the exclude half is dropped and the requirement obliges only the report. Reporting leaves the raw predicate exactly as 005 defines it, so there is nothing to contradict and no MODIFY on a six-paragraph requirement — and it removes the disjunctive MUST, which had no single absence to call a defect.

The scope boundary runs through the middle of the requirement: the obligation is in scope while its operative verb is deferred out.

§2 commits to a mandatory per-story task and defers what “exercise it” means, saying in the same section that “a mandatory task half of all projects could not satisfy would be worse than the gap” — then ships it unconditionally at must tier.

Upheld; the proposal diagnosed the failure and then did not gate against it. Resolved by interface-gating the requirement the way 093 gates its Visual surface section and contract-first gates on a detected interface: a project with no assemblable artifact is exempt on the antecedent rather than obliged to invent ceremony, which also lets the shape axis later demote the heuristic rather than replace a requirement. The path-convention collision is resolved explicitly in the requirement, since an exercise task names no file.

One motivating claim was false and is corrected: “the recording surface is fed by nothing”. Verified independently — 20 of 83 verify views carry a populated <spec-exercise>, up from 9 when 083 landed, so it is feeding itself at a growing rate with no requirement behind it. That weakens the motivation rather than strengthening it, and saying so is the honest version.

The proposal treats SHOULD as the weak tier, contradicting the project's committed definition of the keyword.

KB-0001@2026-07-25: “SHOULD — a strong recommendation; a reason to deviate must exist and should be documented.” Against §3's “deliberately weak” and the rationale's “weak on purpose”.

Upheld. SHOULD is the right tier and the framing was wrong: an obligation whose deviation needs a documented reason is exactly what this requirement wants, and calling it weak misdescribes what the project has committed the keyword to. The framing is removed from both places and the requirement says where a deviation reason goes.
