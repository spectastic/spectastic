The lifecycle contract

The artifacts the lifecycle ships, the states they move through, and the grounding each transition owes.

1 · Context

The lifecycle’s value is not that it has phases but that each phase leaves a checkable artifact behind. These requirements fix what those artifacts are and what a transition between them costs — the part a downstream project inherits whether or not it uses any particular verb.

This spec is a slice of the spectastic meta-spec. Its requirements were authored there and moved here intact, keeping their stable ids: a requirement that was REQ-LIFECYCLE-001 in the parent is REQ-LIFECYCLE-001 here, so every existing citation still names the same contract. The parent keeps the project’s context, architecture, decisions and history; this file carries one family of requirements and nothing else.

2 · Requirements

Normative keywords follow RFC 2119.

The tooling MUST ship five lifecycle templates corresponding to the spec-driven lifecycle: principles.html, spec.html, design.html, tasks.html, and proposal.html. Each MUST use the same design system.

Each template SHOULD include a <spec-status> in the header reflecting exactly one of: Draft, In Review, Accepted, Superseded, Deprecated, Blocked. Transitions between these values are governed by REQ-LIFECYCLE-004.

Each task entry in a tasks.html artifact MUST be a <spec-task> custom element. The element MUST carry:

  • id="T-NNN" — the stable task ID, matching the format defined for tasks elsewhere in the project.
  • parallel (boolean attribute) — present when the task can run alongside its in-flight peers (the existing [P] convention); omitted otherwise.
  • An inner <input type="checkbox"> — the completion state. checked means done. CSS MUST read the state via :has(input:checked) rather than a parallel data-status attribute, so the checkbox is the single source of truth.
  • A label child (a <div> or <p>) holding the task text. Its leading emphasis MUST be a single <strong> wrapping a short imperative task title only — not the full task sentence. Any supplementary detail MUST follow in plain-weight prose (conventionally after an em-dash), and the target file or directory SHOULD sit in a trailing <span class="path"> — where path is a layout/styling class exempt under P-2, not a semantic component subject to REQ-AUTHOR-001.

Styling for <spec-task> MUST live in assets/spec.css — not inline in the template. The generic <div class="task"> + class-span form is forbidden as a direct application of REQ-AUTHOR-001. A task-title-bold-scope validate rule SHOULD warn (not error) when a task row's leading <strong> both spans most of the row and the row carries supplementary detail beyond the title (bold continuing past the first em-dash, or the row exceeding a length floor) — the structural signature of a whole-line-bold row. A terse, detail-free title that legitimately fills its own row does not warn.

Rationale

The tasks artifact is regen-derived from a template, so the contract for its internal shape is worth being explicit about. Without a named element, a fresh authoring session falls back to whatever the template already shows — and a class-soup template propagates indefinitely. Codifying <spec-task> turns the implicit pattern into something a validator (or a careful reader) can check. The label-form clause is the same lesson one level down: the original requirement bounded the element's attributes but not its emphasis, so the template's <strong>[TASK]</strong> placeholder was read as "bold the whole task" and every tasks.html from 026 onward became a wall of bold (T-010). Bounding emphasis to a short title restores the title/detail scan the readable pre-026 rows had, and the warn-level rule keeps the drift from silently returning.

The lifecycle status of any artifact (spec, plan, tasks, principles, triage log, inbox) MUST evolve as a finite state machine over the six values named in REQ-LIFECYCLE-002. The allowed transitions are:

Draft → Accepted
Triggered when the last unchecked <input type="checkbox"> in the artifact's tasks.html is ticked and the author explicitly confirms the flip. /spectastic.implement MUST display a flip prompt at the last-tick that the author must explicitly confirm; the prompt MUST remind the author to verify the integration tests covering the Success Criteria pass before confirming. The command MUST NOT auto-flip status without explicit confirmation. The confirmation gesture absorbs the test-pass discipline; author judgment is the gate.
Draft → In Review
Author-initiated manual flip when soliciting reviewer feedback before the spec is locked. Reversible via In Review → Draft.
In Review → Accepted
Reviewer sign-off. The author flips after the review concludes, and MUST record the reviewer — a human — in the Reviewers field of the artifact's <spec-meta> and in the <spec-changelog> entry for this transition; the recorded identity is never an automated agent. The recording shape is the author's choice (a name, a handle, or both, the way Owner is written) — the contract is that a human reviewer is named, not the exact format. Artifacts that reach Accepted by author affirmation (the tasks-less path below) rather than through In Review have no separate reviewer, and this clause does not apply to them.
In Review → Draft
Author-initiated when revisions are needed in response to review.
Accepted → Superseded
Triggered when a successor artifact adds a <spec-note> in its header citing this artifact as the prior contract. The successor's author flips the predecessor's status to Superseded at the same time the forward-link lands. The predecessor's content is preserved as historical record.
Accepted → Deprecated
Terminal phase-out without a successor — the requirements described are being removed from the project's scope, not replaced. Manual flip; once Deprecated, no further transitions are allowed.
Any state → Blocked
Triggered by a triage card or an upstream-block signal (an external system down, a vendor bug, a contractual review pending). Reversible via Blocked → originating-state. The originating state is recorded in the artifact's <spec-changelog> at flip time.
Blocked → originating state
When the blocker resolves, the artifact returns to whatever state it was in when Blocked was entered. Recorded in <spec-changelog>.

For artifacts that are not a specs/<spec-id>/ spec slice (principles, the meta-spec itself, triage logs, inbox) — including when they carry an execution-only tasks.html tracker for folded change tasks per REQ-CHANGE-006 — the Draft → Accepted trigger is an explicit author affirmation that the artifact is the operative contract for the project; the execution tracker's checkboxes do not drive their status. The author records the affirmation as a one-line <spec-changelog> entry naming the date and the reason.

Transitions not in the list above are forbidden. In particular, a Superseded or Deprecated artifact MUST NOT transition to any other state — those are terminal. An Accepted artifact MUST NOT transition back to Draft or In Review; if amendments are needed, the path is /spectastic.propose against the live spec, not a status downgrade.

Every transition MUST append a one-line entry to the artifact's <spec-changelog> naming the old state, the new state, the date, and the triggering condition or gesture.

The three artifacts of a single spec slice — spec.html, design.html, and tasks.html under specs/<spec-id>/ — MUST share a single bundled lifecycle status. When the spec.html status transitions per REQ-LIFECYCLE-004, the design.html and tasks.html status MUST transition to the same value in the same gesture. One author confirmation per transition flips all three siblings; matching one-line <spec-changelog> entries MUST land on each artifact naming the old state, the new state, the date, and the triggering condition.

The bundle is the natural unit of "this spec slice." Splitting status across the three artifacts has no operational meaning — a spec.html cannot be Accepted while its design.html is Draft without inviting drift. The bundle rule makes the natural relationship explicit and prevents the gap surfaced in T-002 of the meta-spec triage log, where nine sibling artifacts sat in Draft despite their parent specs being shipped.

The bundle status is a readiness affirmation, not a content lock. New ADRs, refined risks, additional tasks accrete inside the Accepted state without constituting a lifecycle transition — the bundle rule governs the status pill, not the artifact contents. A plan amendment that genuinely needs Accepted → In Review drags the whole bundle back to In Review, because the readiness affirmation no longer holds for any of the three siblings.

Cross-spec bundling is not implied: each spec slice has its own bundle; one slice's status never tracks another slice's. Artifacts outside a specs/<spec-id>/ slice — principles, the meta-spec, triage logs, inbox — keep their own author-affirmation trigger from REQ-LIFECYCLE-004 and are not part of any sibling bundle. Such an artifact MAY nonetheless carry a standalone tasks.html tracker for tasks folded from an applied proposal (per REQ-CHANGE-006); that tracker is execution-only — it does not pull the artifact into a status bundle.

/spectastic.implement's last-tick step MUST evaluate the bundle-trigger condition (zero remaining unchecked <input type="checkbox"> in the spec's tasks.html) after every tick taken while the spec's status is Draft, not only when the LLM heuristically recognizes "the last one." Scoping the predicate to the Draft state preserves REQ-LIFECYCLE-004's "last unchecked checkbox is ticked" transition semantics — once the bundle transitions out of Draft, a re-ticked box (a hotfix re-tick on an Accepted spec, an unticked-then-reticked manual gate) does not re-fire the bundled flip prompt. The deterministic evaluation closes the LLM-fragility failure mode where last-tick goes unnoticed when manual gates interleave with code tasks, without introducing a re-confirmation loop on already-flipped specs.

The /spectastic.design procedure SHOULD ground every design-bearing fact against real source before its interview — opening the actual consuming code, the dependency's signature at the resolved lockfile version, quantified platform constraints, and — where a knowledge corpus is present — a corpus document cited by its edition-pinned id, not the file tree alone — and SHOULD record each fact in an evidence ledger as one of verified (opened this turn, with a cited source), spike (resolved by a time-boxed investigation run during planning, with its finding), or assumed (unverified).

Each <spec-decision> SHOULD declare its grounding and cite a verified or spike-resolved source in its Context; a decision that rests on an unverified assumption SHOULD render as a visible failure (the planning analogue of REQ-AUTHOR-001's render-broken-when-malformed discipline).

The gate is the binding clause: the plan MUST NOT be declared ready for /spectastic.tasks while a must-tier decision rests on an assumed or unresolved spike fact, unless the author has accepted it as a tracked <spec-risk> whose status the author commits (per REQ-CHANGE-004's author-owned-status model). This gate is a design→tasks readiness affirmation, not a Draft content-lock — it mirrors the existing estimability gate, and pure-judgment decisions with no external fact are exempt.

Implementation surprises come from planning under unverified assumption. The grounding discipline ships as SHOULD — mirroring REQ-CHANGE-004, which shipped the adversarial pass as guidance from one data point rather than a blanket MUST that hollows into theater. The gate is the MUST that actually stops an ungrounded assumption from reaching implementation silently; lifting the /spectastic.explain "cite only confirmed source" discipline into planning makes "what the plan knows vs. assumes" structurally legible.

Before committing a diagnostic layer, /spectastic.triage SHOULD ladder the root cause against the regeneration test: starting from the candidate (lowest plausible) layer, ask "if I changed only this layer, would the regeneration test still fail?" — if the bug would recur, the owner is upstream, so step up (implementation → spec → cross-spec → principles) and re-ask. The ladder reuses the existing regeneration test — one probe, not a second analysis pass — so the card still reads in under 30 seconds.

The gate is the binding clause: a card MUST be classified at the lowest layer whose fix makes the regeneration test pass — neither lower (a fix that would recur — the symptom layer) nor higher (an honest implementation drift inflated past its real owner, against the No spec inflation discipline). That lowest-passing layer is "the highest layer that needed to change," stated as a procedure: the gate is bidirectional, so the ladder is not a one-way escalator. just-do and defer intake items skip the regeneration test and are exempt.

Rationale

The maxim had no step, so triage defaulted to the convenient layer: the no-open-questions defect (020 T-005) was classed at the presentation layer and reached cross-spec only on author pushback. The laddering discipline ships SHOULD — codifying from one data point, mirroring REQ-LIFECYCLE-006 / REQ-CHANGE-004 rather than a blanket MUST that hollows into theater. The gate is the MUST, and it is bidirectional: it stops under-classification (T-005) and over-escalation (spec inflation) with the same rule — stop at the lowest layer that holds.

The /spectastic.design procedure SHOULD anchor an architecture pattern in its decision phase whenever the feature has more than one moving part, offering domain- and stack-appropriate contenders rather than a fixed house pattern, and a trivial single-module feature SHOULD skip the question. The chosen pattern SHOULD land as a <spec-decision> carrying grounding=, with its one-line summary filling the design's technical-context Architecture row, so the arrangement of the pieces is recorded before the stack picks that depend on it. Standing, cross-feature rules — dependency direction, keeping a framework out of a domain core — MUST NOT be recorded in a single design; they belong in the project's principles. This prompt is advisory: it nudges a deliberate, grounded choice and provides no enforcement that the chosen pattern is followed.

Rationale

The behaviour shipped in commands/spectastic.design.md and templates/design.html without a requirement behind it, leaving it resting entirely on command markdown — which triage T-009 establishes is advisory to the model and which P-8 excludes as a place guarantees may live. A behaviour with no requirement can be edited away with nothing recording that it was intended. Phrased SHOULD to match REQ-LIFECYCLE-006 and REQ-LIFECYCLE-007, the other design- and triage-procedure requirements, since a validator cannot check that an interview happened. The final sentence is deliberate: naming the ceiling inside the requirement stops a reader inferring that a recorded pattern is an enforced one, and keeps the honest split between this prompt and the fitness function that would actually hold a design to it.

A lifecycle status that disagrees with the artifacts it describes MUST be reportable. The check applies to exactly two disagreements, and to nothing else. First: a spec.html at draft whose tasks.html carries at least one checkbox and none unchecked MUST be reported, at warning. Second: where a specs/<spec-id>/ slice holds more than one of spec.html, design.html and tasks.html each carrying a status element, those statuses MUST agree, and a disagreement MUST be reported at error. The check reads only those three filenames, only their header status, and only a slice that has a tasks.html.

Rationale

REQ-LIFECYCLE-004 describes an instant and assigns the obligation to a command; REQ-LIFECYCLE-005 requires three siblings to move in one gesture. Both are correct and neither is observable after the fact, so a slice that missed the moment looks exactly like one that never reached it. This states what the status should be, which is the thing a later session can check.

The asymmetry is load-bearing. Reading this symmetrically — status should track completion in both directions — would report every spec that has ever received a proposal, because the apply kernel folds tasks into completed specs in a fresh hundred-range on purpose. Eight accepted specs carry unchecked work today and every one of those tasks sits in a folded phase; unchecked work outside a folded phase totals zero. So the asymmetry is a consequence of how change lands rather than an exception to the rule.

It is stated as a scope limit rather than a prohibition, deliberately. A negation here would need MUST NOT, which the conformance markup cannot distinguish from MUST — the element carries a level for should and may and nothing else, so a consumer reading the level off the element would see the exemption as an obligation and invert it. Saying what the check applies to leaves nothing to misread.

The two severities differ because the two disagreements do. A finished slice still reading draft is bookkeeping — a reader is misinformed while the artifact stays sound — so it warns, like REQ-FORMAT-009. A split bundle is a violated MUST: REQ-LIFECYCLE-005 says three siblings share one status and transition in one gesture, so reporting its breach as advice would say the requirement is optional. Both severities are in the requirement rather than left to the implementation, since an implementer choosing either would otherwise still conform.

Restricting the check to the three named filenames is what keeps it honest. A slice directory also holds archived proposals carrying applied — not one of the six lifecycle values — and a triage log that can carry a status element inside a sentence. Naming the three puts both out of scope by construction rather than by an exemption list that has to anticipate them.

Reporting, never flipping. The disagreement has two possible resolutions — the status is stale, or the work is not really done — and only a person knows which.

Where a project has an artifact that can be assembled and run, a generated task list MUST give each user story at least one task that exercises that artifact along the story's path, and that task MUST sit inside the story's own phase rather than in a later polish phase. Where no such artifact exists, no task is owed. An exercise task names an entry point rather than a file, so the trailing-path convention does not apply to it.

Rationale

Without it a story is complete when its units pass, and the composition is never run. A downstream project reached 90% unit coverage and would not start; the failure was in no unit, and nothing assembled them.

Placement is half the requirement. Anything integration-flavoured currently drifts into Polish because that is the only phase that will take it, and Polish is last — so the task that would have caught the failure is structurally where work goes when time runs out.

Gated on the antecedent rather than owed by everyone, the way the Visual surface section and the contract-first floor are gated: a schema change or a config-only slice has nothing to assemble, and a mandatory task half of all projects cannot satisfy trains people to tick boxes. That also leaves the project-shape axis free to demote the heuristic later rather than replace a requirement.

What “exercise” means is shape-sensitive and deliberately not settled here: an entry point is a command for a library or CLI and an address where a server already serves the feature. Across this estate 67 of 72 recorded run commands are a build or an install, which is the gap. The verify view's field for this is not unused — 20 of 83 views populate it, up from 9 when it landed — so the requirement follows a practice that is already spreading rather than creating one.

Where a completion condition does not fire because work remains, the verb evaluating it MUST report what is outstanding rather than staying silent.

Rationale

Zero remaining unchecked is stated once and consumed twice — by the status flip and by the verify view. A task waiting on a person is indistinguishable from work not done, so one waiting gesture blocks two mechanisms that have nothing to do with it, and both are silent about why.

Reporting rather than excluding, deliberately. REQ-LIFECYCLE-005 already considered this exact case — its body names “an unticked-then-reticked manual gate” — and chose a deterministic count precisely to remove per-task judgment. Excluding a task would put that judgment back and answer a settled question from a third place; reporting leaves the predicate exactly as 005 defines it and fixes what actually cost something, which was the silence rather than the block.

Paired with REQ-LIFECYCLE-010 on purpose. An exercise task is a strong candidate for needing a person, so landing that one without this would multiply this defect rather than leave it where it is.

Before implementing a task, the implementer SHOULD establish that the capability it asks for is not already present, searching by capability across the project rather than only in the files the task names, and SHOULD record what was searched — whether or not anything was found. This obliges the search and the record, not a correct answer: it cannot prevent a wrong conclusion, only make the basis for one visible.

Rationale

A complete duplicate implementation was written before the original was found one directory over, where a provider belongs — after three independent readers, working from a card that named the wrong directory, each searched it and agreed the capability was missing.

The procedure makes this easy to get wrong rather than hard: it loads the files a task names, then does the work. A task naming the wrong file produces a clean search and a confident wrong conclusion, and a clean search reads like proof.

Should rather than must, in this project's committed sense: a deviation needs a reason that exists and is written down, which belongs in the task's own completion note. That is a real obligation, not an advisory one — an implementer who skips the search owes an explanation.

The record is unconditional because the conditional version fires on the rare branch. A search that finds nothing is the case worth recording: it is the one that precedes a duplicate.
