Design · 107-visual-design-brief

Design brief

How we will build it.

Status Accepted Spec 107-visual-design-brief Owner Brian Corbin · @briancorbinxyz Branch spec/visual-design-brief-107 Created 19 Aug 2026 Read time

A pure reader over a feature’s own declarations, a Markdown renderer, and a write. The brief is a dated file under the spec’s visual/briefs/ and never an embedded view — a materialised view is replaced on regeneration, which is the exact opposite of what FR-009 requires. The load-bearing output is one line per state naming the exact label its artboard must carry. A separate pure comparator answers the returning question — which observed labels match no declared state — and is called from the render path, because that is the only place real labels exist.

2 · Technical context

Language / runtime
TypeScript on Node, unchanged — the workspace’s existing stack.
Architecture
A pipeline of pure functions with I/O only at the edges: read → model → render → write. No new package and no new port — nothing here reaches outside the process.
Output format
Markdown (D-001). Not a design-system artifact, because the reader is outside this project.
Test framework
Vitest, tests written failing first. Every requirement is observable in the emitted string, so the suite needs no fixture project per assertion.
Coverage
Patch target: every new line in the generator covered, and a change never lowers coverage of what it touches.
Persistence
Files only — one dated Markdown file per run under specs/<id>/visual/briefs/.
Perf
NFR-001: 0 network calls. NFR-002: two runs over unchanged inputs differ by 0 bytes, the date excepted — achieved by taking the date from the caller (D-003) rather than reading a clock.

Toolchain / enforcement

The enterprise floor is already covered — 8 categories covered, observability relaxed under a waiver with an owner and expiry, 0 missing. This design adds no gap and resolves none, and unlike its predecessor adds no workspace member, so there is nothing to bring under a gate that is not already under one.

3 · Data model & contracts

No consumer-facing interface. The generator is invoked from a terminal and writes a file; nothing calls it over a wire. The brief’s own text is emphatically not a contract — it is addressed to a person and a design tool, and FR-011 forbids any verb reading it back, which is what stops its shape becoming one by accident.

6 · Approach

Two capabilities that share one fact and nothing else. Outbound is a three-step pipeline with I/O only at the ends: a reader walks the feature’s declared screens and returns a complete model (every state, every refusal, every annotation, the addressed contexts), a renderer turns that model into Markdown, and a write puts it at a dated path. Nothing in the middle touches a filesystem, a clock or a network, which is what makes NFR-002’s byte-identity a property of the code rather than a hope.

Inbound is a single pure comparator: given the declared state ids and the labels actually observed on a returned design, which labels correspond to no declared state? It writes nothing and decides nothing — it returns a report. It lives in core rather than in either caller because two callers are plausible and only one exists today: the render path has real labels now, and a static importer could call the identical function the day a design tool exports labels that are true before execution. The fact both halves share is the label grammar — the outbound side states the label, the inbound side reads it, and if those two ever disagreed the feature would be silently useless, so they are one module.

The brief is the first thing this project emits that is meant to be read as an instruction by a model. That sounds like a P-11 problem and is not: P-11 governs what the tool reads, and the risk it names — an artifact steering the tool that processes it — runs the other way. What does cross the boundary is artifact prose being carried into the brief, and that is fenced (D-005). Worth stating rather than leaving a reader to wonder why the principle table says OK.

7 · Alternatives considered

Where the brief lives, which settles its format too. Scored 1–5, higher better. The first two criteria are pass/fail dressed as scores — a 1 in either is disqualifying, because both are requirements rather than preferences.

OptionSurvives regeneration (FR-009)Unreadable as a declaration (FR-011)Pasteable into a design toolFollows existing precedentTotal
Embedded view in design.html142411
HTML artifact outside visual/542314
Markdown outside visual/555217
Markdown at visual/briefs/ — chosen545519

The embedded view scores 1 on the first criterion and is therefore out regardless of its total: a materialised view is replaced on regeneration, and materialise is now a required step in the design procedure, so the brief would not survive its own slice. That is a contradiction, not a tradeoff.

The two Markdown rows differ by one point in each direction, and the choice is honest about what it buys. Outside visual/ scores 5 on unreadability because no visual reader can reach it however it globs; inside scores 4 because the guarantee rests on readers filtering by extension, as both current ones do. Inside wins on precedent because 106 already puts generated non-HTML output at visual/renders/ under exactly that assumption — so the alternative would not remove the risk from the project, only from this one file, while splitting feature-scoped material across two directories.

8 · Decisions

D-001 · A dated Markdown file, never an embedded view

Status
Accepted
Context
The chassis for feature-scoped material is declare → sidecar → embedded view, so an embedded brief was the expected answer. materialise-view.ts:152 rules it out: “a regeneration REPLACES any existing view rather than appending”, and FR-009 requires a brief never be rewritten. Format follows the reader, who is outside this project.
Decision drivers
Survives regeneration · not readable as a declaration · pasteable by a person · consistent with what already ships
Considered options
  • Embedded view in design.html — + one artifact, the established chassis. − destroyed by the next materialise; disqualified.
  • HTML artifact outside visual/ — + themed, opens in a browser. − awkward to paste into a design tool, which is the entire purpose.
  • Markdown at visual/briefs/ — chosen — + immutable by construction; + the format design tools read. − not viewable in the design system’s own chrome.
Decision
A brief is Markdown at specs/<id>/visual/briefs/<date>.md, written once.
Consequences
+ FR-009 holds without a guard, because nothing regenerates the path.
+ Corroborated externally: Stitch’s DESIGN.md is Markdown for the adjacent payload.
− A brief is the one feature-scoped artifact a reader cannot open in the design system’s chrome.
− Immutability costs convenience: a wrong brief is superseded by a new one, never corrected in place.

D-002 · It sits under visual/, and that rests on an extension filter

Status
Accepted
Context
Both screen readers glob endsWith('.html') (materialise-view.ts:192, screen-naming.ts:73), so a .md is invisible to them. 106 already places generated PNGs at visual/renders/ under the identical assumption.
Decision
Briefs live at visual/briefs/, beside renders/.
Consequences
+ All feature-scoped visual material stays in one place, and the directory says what it holds.
− FR-011’s guarantee is conventional rather than structural: a future reader globbing * would reach it. Recorded rather than mitigated, because the same exposure already exists for the renders and fixing it for one file would not fix it for the project.

D-003 · The date is supplied by the caller

Status
Accepted
Context
NFR-002 and SC-003 want two runs to differ by 0 bytes with the date excepted, which is unachievable if the generator reads a clock. The convention is already written down twice: types.ts:868 and :931 — “supplied by the caller so the kernel stays deterministic”.
Decision
The generator takes an ISO YYYY-MM-DD string. Only the CLI reads a clock.
Consequences
+ Byte-identity becomes testable with no clock injection or freezing.
+ Matches two existing verbs rather than inventing a third habit.
− One more required argument, and a caller passing a wrong date gets a wrongly-named file with no complaint.

D-004 · Its own complete reader, not the view’s model

Status
Accepted
Context
projectScreens is budget-truncating by design (materialise-view.ts:59, :69–72) and its model carries no refusal, no prose and no aria-state. FR-001 requires every declared state. screen-naming.ts:83–85 already met this and chose to read directly rather than widen the model.
Decision
A reader owned by this slice, returning a complete model. projectScreens is untouched.
Consequences
+ A truncated brief becomes inexpressible rather than merely unlikely.
+ The view’s shape stays owned by the view, as the precedent intends.
− A second parser over the same vocabulary; a new element added to a screen must be taught to both.

D-005 · Artifact text is fenced with the existing primitive

Status
Accepted
Context
FR-005 requires artifact prose to be fenced as data. fence.ts:146 already sanitises and wraps with an explicit guard, and six core verbs plus the corpus call it.
Decision
Call fenceArtifactText. Author no second mechanism.
Consequences
+ Hidden-element, comment and data: stripping plus NFKC normalisation arrive for free.
− The guard text is written for a model reading a prompt, and a brief is also read by a person, so a fenced quotation reads more heavily on the page than a plain one would.

D-006 · The returning check is a pure comparator called from the render path

Status
Accepted
Context
The claim tested before choosing: can a returned design’s real artboard labels be read without executing it? 106’s spike answers no — 4 template labels statically, 22 after execution. The importer also has no notion of a state (import.ts). So a static check would report {{ s.id }} as a discovered state, which is worse than not checking.
Decision
A pure function in core taking declared ids and observed labels and returning a report, called from the render path. It writes nothing.
Consequences
+ FR-004’s “never written on its behalf” is structural: the function has no writer to call.
+ A static importer can call the identical function if a tool ever exports true labels.
− The check only runs where a render runs, so a design reviewed without one is not checked at all — the honest limit, and why SC-004 is should-tier.

D-007 · Tests written failing first

Status
Accepted
Context
Pure judgment, no external fact. Every requirement here is observable in a returned string, so the cost of a test is low and the cost of asserting the wrong thing is the usual one.
Decision
Each story opens with failing tests, as 106 did.
Consequences
+ SC-003 is naturally a test rather than a manual comparison.
− Says nothing about whether the brief is useful, which only a real round-trip answers.

9 · Project structure

Only the new or changed paths. No new package and no new port — the pipeline is pure functions in core with the CLI at the edge, which is P-14 applied rather than extended.

10 · Risks & mitigations

RiskLikelihoodImpactMitigation
The brief is faithful and still not useful — a designer reads it and works from the picture in their head anyway. MH Not mitigable by any test here, and named rather than hidden: SC-002 is deliberately written about what binds rather than what is drawn. One real round-trip settles it and nothing else does.
A future reader globs visual/ without an extension filter and reads a brief as a declaration. LH Accepted in D-002 rather than mitigated. The identical exposure already exists for 106’s renders, so a per-file fix would leave the project no safer.
Two parsers over one vocabulary drift — a new screen element is taught to the view and not to the brief. MM The consequence is a quiet omission from a brief, not a failure. D-004 takes it knowingly; the alternative was a truncating brief, which is worse and silent in the same way.
The label the brief states and the label the comparator expects diverge, making the round-trip silently useless. LH Structural: both sides read one grammar in one module (§6). A test asserts a label the renderer emits is one the comparator matches, so the two cannot be changed apart.
An immutable brief written with a mistake cannot be corrected. ML By design. A wrong brief is superseded by a dated successor, which is what makes the record trustworthy; the cost is convenience, and it is the recognised cost of append-only records generally.

11 · Complexity tracking

Anywhere this plan introduces complexity not strictly required by the spec, justify it here. A reviewer should be able to point at any non-trivial choice and find its rationale in this section.

P-10 exception — the brief names internal ids deliberately

P-10 keeps internal artifact ids out of user-facing copy, and the brief breaks that on purpose. A state’s id is the artboard label (D-004) — that is the whole mechanism — and an annotation citing NFR-001 or a screen serving US1 carries that citation so a designer can ask what it refers to.

The exception is narrow and consistent with how P-10 is already read here: the rule’s line is tool-talking versus artifact-provenance, and it explicitly permits an artifact citing its own governing ids. A brief is an artifact of this project quoting its own declarations, not the tool describing itself. What stays clean is the generator’s own surface — its help text and its refusals say what they do and name no spec.

A person reading the brief can act on a state id as a label without knowing this project’s conventions. The ids in the worked example (empty, loading, rate-limited) read as plain English, which is what makes the assumption reasonable rather than lucky — a project naming states s1…s12 would get a faithful and useless brief, and nothing here detects that.

Emitting one file per run will not become a directory nobody prunes. Briefs are written when a design is commissioned, not on every build, so the volume is the number of times a person asked for a design. No retention rule is designed, and if that assumption fails the answer is a retention decision rather than mutability.

12 · Open questions

None outstanding. The two that mattered were settled by reading the code rather than by discussion: whether the brief could be an embedded view (it cannot — a regeneration replaces it) and where the returning check belongs (not the import path — a static read cannot see a real label). Both findings are in §5 with their citations, and both changed the design from what was first proposed.
