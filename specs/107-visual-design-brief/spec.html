Ask for the design you specified, in the words the specification already uses.

1 · Context

A feature declares its screens, its states and the contract responses each derives from, the copy it forbids, and the behaviour a picture cannot show. None of it reaches the person drawing it.

On the one worked example the cost is measurable: the design drew eleven states, the screen file declares twelve, and only four match by name. Some are the same thing named twice — the design’s fetching is the spec’s loading. The rest is worse both ways: eight declared states nobody drew, seven drawn states nobody declared.

The response is not a matching engine. It is to ask in the words the specification already uses, so what comes back binds by exact match and there is nothing to reconcile.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Ask in the specification’s own words P1

As a spec author, I want to generate a brief from what the feature already declares so that the person drawing it knows the states, the forbidden copy and the exact label each artboard must carry.

Acceptance: For a feature declaring at least one screen, the brief names every state it declares, the exact label for each, every refusal it carries, and the axes addressed. No label is invented.

US2 · A discovered state arrives identifiable P2

As a designer, I want to draw a state the specification missed and have it come back recognisable so that what I found is visible to the author rather than lost or mistaken for drift.

Acceptance: The brief states the labelling convention for a state the feature does not declare. A design returned with such a state is reported as undeclared and attributed to the design, and no declaration is written on its behalf.

US3 · What was asked for is still readable later P3

As a reviewer, I want to read the brief that was actually issued so that when a design comes back missing something, the question of whether we asked for it has an answer.

Acceptance: A brief is written once and never rewritten; a later run produces a new dated brief and leaves earlier ones byte-identical.

Edge cases

  • A state’s prose contains text that reads as an instruction to a model.
  • A feature declares axes but addresses only some contexts — a declined one must carry its reason.
  • A screen declares no states at all, so there is nothing to ask for.
  • A design returns a state the feature does not declare — the case that must not be silently dropped or silently adopted.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A brief MUST be generated only from what the feature declares, and MUST NOT introduce a screen, state, context or constraint that no artifact carries.

Rationale

The claim being tested is that the lifecycle already holds enough to brief a design. A generator permitted to invent would make that claim unfalsifiable, and would put requirements into a designer’s hands that no reviewer ever saw.

The brief MUST state the exact label each artboard is to carry, and each label MUST correspond to exactly one state the feature declares.

Rationale

The load-bearing requirement. Naming is the whole difference between a design that binds on import and one that needs a translator: on the worked example four of twelve states matched, and the mismatches were not random — unavailable matched while loading/fetching did not, so the confident guesses and the correct ones are not the same set. Stating the label converts an inference problem into an instruction.

The brief MUST state the labelling convention for a state the feature does not declare, so that a state discovered while designing arrives identifiable rather than anonymous.

Rationale

The label contract binds naming, not completeness. A specification is not the ceiling on what states exist — the worked example’s design drew same-currency, which is a real case a spec author forgets and a person drawing the screen cannot. Without this, a discovered state comes back unlabelled or labelled ad hoc, and the most valuable thing a designer produces is the thing the pipeline is worst at carrying.

A returned design MUST NOT be treated as authority to add a state to a feature: an undeclared state MUST be reported and attributed to the design, and a declaration MUST NOT be written on its behalf.

Rationale

Propose, never mint. A design tool is a source and never the authority, and a state is a requirement-shaped thing a human accepts — adopting one automatically would let an external tool write into the artifact that governs the build. The symmetric failure is just as real and is what this requirement guards against: dropping the discovery because adopting it was the only alternative on the menu.

Text taken from an artifact MUST be fenced as data in the emitted brief, and MUST NOT be emitted where it would read as an instruction.

Rationale

The brief is the first surface that deliberately turns artifact prose into prompt text, which is exactly the channel P-11 names. The fencing primitive already exists and six of the AI verbs use it; not reusing it here would make a spec’s body a way to instruct an external tool.

The brief MUST carry every refusal the feature declares as copy that must not appear.

Rationale

The highest-value lines in the brief. A refusal is a decision already taken — the worked example forbids the word “Error” in anything a user reads — and it is precisely what a design tool supplies by default from its own house style. No tool infers a prohibition.

The brief MUST carry the feature’s declared annotations, so behaviour a picture cannot show is stated rather than left to be inferred from one.

Rationale

An annotation is typed by the accessibility tree, so a declaration is already an assertion: that the rate line is a live region spoken without moving focus is not visible in any drawing of it, and a design returned without it looks correct.

The brief MUST name the axes the feature addresses and the subset of contexts to be drawn, and a declined context MUST carry the reason the feature declined it.

Rationale

The worked example addresses seven contexts across three axes, which against twelve states is up to eighty-four artboards — more drawing than any release needs. Naming the subset makes what is missing a decision rather than an oversight, which is the distinction the variant grid was built to hold.

A brief MUST be written to a dated file and MUST NOT be rewritten; a later run MUST write a new one and leave earlier briefs unchanged.

Rationale

A brief is a record of what was asked, not a view of what is currently true. Regenerating it would destroy the only evidence of the request at the moment a design comes back wrong, which is the moment the evidence is wanted. Captured evidence is a dated baseline superseded rather than incremented.

The brief MUST NOT name a design tool, and generating one MUST NOT require a network connection, an account, or a design-tool licence.

Rationale

A design tool is a source and never the authority, which is what makes five tools interchangeable rather than five integrations. Tool-specific tuning is unowned work that decays, and the tools differ in licence and API access rather than in what a screen is.

A brief MUST be an output only, and MUST NOT be read back by any verb as a source of declarations.

Rationale

A generated file re-read as input becomes a second place a state can be declared, and then two files disagree about what the feature is. The declaration stays in the artifacts; the brief is a rendering of them.

Non-functional

Generating a brief MUST make at most 0 network calls.

Two runs over unchanged inputs MUST produce briefs differing by at most 0 bytes, the date excepted.

Rationale

Deterministic because it can be, and worth stating because the sibling that captures renders explicitly cannot promise this — a brief is text assembled from files, with no browser, fonts or fetched libraries in the path.

Out of scope (deferred to other slices)

  • Briefing an existing design toward a specification. The undecided part is who yields when the two disagree on vocabulary, and one real greenfield run settles more of that than reasoning about it now.
  • The path by which a discovered state becomes a declared one. FR-004 settles that it is never automatic; the shape of the human step is left open, and this project’s existing triage card is the obvious candidate before any new mechanism.
  • Capturing what comes back as images.
  • Checking a returned design against the brief that asked for it.
  • Delivering the project’s design system to the tool. A brief carries feature-scoped intent; the token set and components are project-scoped and travel by a sync path. The split is 094’s, not a new one.

4 · Data model

Two entities, both derived and neither persisted beyond a file.

Entities

Brief
A dated document derived from a feature’s declarations and addressed to a person. Written once. A later brief is a new document, never an edit of an earlier one.
Label contract
The set of exact artboard labels a brief states, plus the convention for labelling a state the feature does not declare. Each stated label corresponds to exactly 1 declared state in 1 context.

Two invariants, both counts of 0: a brief states no label that does not correspond to a declared state, and no brief is ever rewritten.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

Of the labels a brief states, the number not corresponding to a declared state is 0.

For a design returned against a brief, every artboard drawn for a declared state binds to that state by exact match, with 0 requiring a mapping or an inference.

Two runs over unchanged inputs produce briefs differing by 0 bytes apart from the date, and an earlier brief is unchanged by a later run.

A design returned with a state the feature does not declare produces 1 report of it and 0 changes to the feature’s declarations.

6 · Assumptions

A brief is advisory. Nothing in prompt text can compel a design tool, so this makes the ask explicit and reviewable and guarantees nothing about what returns — which is why SC-002 is written about what binds rather than what is drawn.

The specification is not the ceiling on what states exist. A person drawing a screen sees cases a spec author does not, so a brief that treated its state list as exhaustive would suppress the most valuable thing the exercise produces. A discovery is not drift, and what it produces is a question for a person rather than an amendment the exercise makes for itself — which follows from a design tool being a source and never the authority, not from any practice outside this project.

7 · Open questions

None outstanding. The one that arose late — what happens when a design yields states the specification does not have — is answered in part here (FR-003 makes it arrive identifiable, FR-004 forbids adopting it automatically) and deferred in part, as TBD-visual-state-discovery, since the shape of the human step is a separate decision.
