Specification · 112-guardrail-decision-record

Governance decision record

Give an architectural decision the structured, machine-readable shape a retrieval and a gate can operate on — the scope it governs, the checks that enforce it, the posture it carries — without moving it out of the spec that produced it.

Status Accepted Spec ID 112-guardrail-decision-record Owner Brian Corbin · @briancorbinxyz Reviewers — Created 13 Sep 2026 Principlesv1.9.0 Smallest demoableAuthor a decision with a malformed enforcement block; spectastic validate fails naming the problem; fix it and it passes. Read time

Slice 1 of the architectural-guardrails design brief (design, §3.1–3.2). It extends the existing <spec-decision> card with structured governance metadata — a status lifecycle, a posture, the scope it governs (path globs as the universal floor), the enforcement rule-ids that check it, and the human reason that teaches on failure — enforced by a new decision-well-formed validate rule. It adds a decision resource kind so a decision is federation-addressable at spectastic://<project>/decision/<spec-id>/<D-NNN>. Everything the retrieval, the gates, and the coverage lint need to exist rests on this record.

1 · Context

The architectural-guardrails assessment (Phase 1) scored spectastic strong on what the governance layer must not be and weak on what it must have. The root cause is gap G3: a <spec-decision> carries an id, a free-text status pill, and a grounding tag, but no scope, no precedence, and no enforcement link. So nothing can retrieve "the decisions governing this path" or check "was this decision honoured." The dogfood repo spec-tictactoe-2 shows a real decision→check link (D-008 ↔ NoWallClockRule) — but as a hand-repeated string across four files, un-guarded against drift.

This slice promotes that prose convention to structure. Its user is the person authoring a governing decision and the tooling (later slices) that must read it. It is the foundation every downstream slice rests on.

2 · User scenarios & testing

Author a governing decision. A designer records that only the persistence adapter may touch data-access APIs. They write a <spec-decision> with status="accepted", a <spec-scope> naming the paths, a <spec-enforcement> naming the ArchUnit rule that checks it, and a <spec-reason>. spectastic validate passes.

Malformed enforcement is caught. They forget the reason on a <none> enforcement, or use an illegal status. validate fails at error severity, naming the exact problem and how to fix it — before the commit lands.

The decision is addressable. A later slice composes the decision's coordinate spectastic://acme/pk/decision/002-downstream/D-007 and parses it back to the same kind, spec, and id.

3 · Requirements

The <spec-decision> element MUST accept structured governance metadata: a status from {proposed, accepted, superseded, retired}, an optional posture from {warn, block}, an optional supersedes naming another decision id, an optional review-by date, a <spec-scope> holding one or more <path> globs (and optional ecosystem <module> selectors), a <spec-enforcement>, and a <spec-reason>. Absent metadata leaves a decision exactly as it renders today (backward compatible). A new decision-well-formed validate rule (per-file, error) MUST reject: an illegal status or posture value; an accepted decision whose posture is not warn-only but that declares no <spec-scope> with at least one <path>; and a <spec-enforcement> that is neither "at least one <rule> with a tool and an id" nor "exactly one <none> carrying a non-empty reason". Each problem is reported granularly. The reason that teaches on failure MUST live once, in <spec-reason> on the decision. The schema MUST NOT require it to be duplicated into any enforcement tool's own message channel. A decision resource kind MUST be added to the resource-URI grammar, yielding a project-scoped coordinate spectastic://<project>/decision/<spec-id>/<D-NNN> that composes and parses back to the same kind, spec id, and decision id — mirroring the two-segment screen coordinate, authority the project (not a marketplace). An overlap check SHOULD report (not silently pick) two active decisions whose scopes overlap the same path with no supersedes relation between them, so precedence is always explicit. The validate path exercising decision-well-formed MUST carry no model client and no network access — a test MUST assert the rule module's transitive imports contain at most 0 model clients and at most 0 network modules. Rule evaluation and coordinate composition MUST be deterministic: the same document yields the same findings, and the same inputs yield the same coordinate, on every run (no clock, no ordering nondeterminism) — asserted with at most 1 repeated-run diff.
  • Path-scoped retrieval (spectastic adrs --for) — Slice 2.
  • The plan-stage and merge-stage gates — Slice 3.
  • The decision registry file + corpus id-allocation reuse — deferred to Slice 1b once the record is proven.
  • Verifying a declared rule-id exists in the named tool — the merge gate's resolvable check, not this schema rule.

4 · Data model

Decision (extended <spec-decision>)
The Nygard card, plus status/posture/supersedes/review-by attributes and <spec-scope>/<spec-enforcement>/<spec-reason> children.
Enforcement rule
A <rule tool="…" id="…" run="…"?/>, or a single <none reason="…"/>.
Decision coordinate
spectastic://<project>/decision/<spec-id>/<D-NNN> — project-authority, two-segment name.

5 · Success criteria

Given a <spec-decision> with an illegal status and a <none> enforcement missing its reason, spectastic validate reports at least two decision-well-formed error findings naming both problems; correcting them yields zero findings on that rule.

6 · Assumptions

  • The <spec-decision> element already parses via the schema parser and appears in design.html; adding children/attributes is additive (unknown attributes are tolerated today).
  • RESOURCE_KINDS is the blessed single-declaration extension point (its docstring records a prior drift bug).

7 · Open questions
