Design · 112-guardrail-decision-record

Governance decision record

How we will build it.

Status Accepted Spec 112-guardrail-decision-record Owner Brian Corbin · @briancorbinxyz Branch main Created 13 Sep 2026 Read time

Extend <spec-decision> with structured governance metadata and enforce its shape with one per-file schema rule, and add a project-scoped decision resource kind — all additive over the existing parser and the RESOURCE_KINDS extension point. Biggest risk: false-firing on the existing estate's bare decisions, mitigated by making every check conditional on the new metadata being present.

1 · Principles check

The record is a schema artifact; the guarantee is the validate rule (P-8). The rule is pure kernel logic in @spectastic/schema with no CLI-side branching (P-14 — fat schema, thin CLI). A decision carries its teaching reason once, in the artifact; it is not restated in any enforcer's message channel (the drift P-8/T-009 warns against). No executable content is added; the record is data (P-11).

2 · Technical context

Where the rule lives
packages/schema/src/rules/decision-well-formed.ts, registered in rules/index.ts, run by the same validate engine as every other rule.
Parser
Reuses findAll/getAttr/getLocation from @spectastic/schema/parser — the exact primitives slo-well-formed uses.
Resource kind
Added to RESOURCE_KINDS in packages/schema/src/project-shared.ts; the generic parseResourceUri already handles a two-segment name, so only a composer is new.

3 · Data model & contracts

The extended <spec-decision>: attributes status ∈ {proposed, accepted, superseded, retired}, posture ∈ {warn, block}, supersedes, review-by; children <spec-scope> (holding <spec-path> globs + optional <spec-module>), <spec-enforcement> (holding <spec-rule tool= id= run=> or one <spec-none reason=>), and <spec-reason>. All optional — a bare decision is unchanged. The coordinate is spectastic://<project>/decision/<spec-id>/<D-NNN>.

5 · Grounding & evidence

Two deep-research passes over packages/corpus/ (13 Sep 2026) settled the hybrid: the corpus's identity / coordinate / edition machinery hosts a decision gracefully (RESOURCE_KINDS is the blessed extension point; the screen kind already ships the two-segment coordinate), but its document model is a forced fit — no structured-metadata parsing, a "cited-against, never enforced-from" data-flow a decision reverses, and no lifecycle status any code respects. So the decision is authored in <spec-decision> (this slice) and only its addressing reuses the corpus. The dogfood evidence is spec-tictactoe-2's D-008 ↔ NoWallClockRule link — real, but a hand-repeated string; this record makes it structural.

6 · Approach

  1. Add the decision-well-formed per-file rule (error), modelled on slo-well-formed: granular findings, an early return when no <spec-decision> is present, conditional checks so a bare decision is untouched.
  2. Add decision to RESOURCE_KINDS and a decisionResourceUri composer; extend the round-trip coverage matrix.
  3. Prove backward-compatibility by running the whole-estate integration validate — the existing bare decisions must stay clean.

7 · Alternatives considered

  • Decisions as full corpus documents (kind: decision markdown files). Rejected: reverses the corpus's cited-against→enforced-from data-flow and bolts structured policy onto a deliberately-minimal domain-fact model — the research's four forced-fits.
  • A standalone decision index with no corpus reuse. Rejected: re-invents identity, federation and editions the corpus already solved.

8 · Decisions

packages/schema/src/rules/decision-well-formed.ts The decision record's own well-formedness is a guarantee (P-8), so it must be enforced by a test and the validate rule, not by convention.

D-001 · The record's shape is machine-enforced, dogfooded here

Context. This is the first decision authored in the new structured form. Decision. Use the extended <spec-decision> shape in this very design, scoped to the rule + coordinate files and enforced by the rule's own test. Consequences. spectastic adrs --for packages/schema/src/rules/decision-well-formed.ts (Slice 2) returns this decision — the first end-to-end proof that authoring and retrieval agree.

 Existing specs carry bare <spec-decision> cards with no metadata; the rule must leave them untouched or it breaks the whole estate.

D-002 · Every new check is conditional on the metadata being present

Context. 70+ specs carry bare decisions. Decision. The rule early-returns on no decisions, and each check fires only when its attribute/child is present; scope is required only once status="accepted" and posture is not warn-only. Consequences. The whole-estate integration validate stays green — proven, not assumed. (Warn posture here because this is a methodology decision with no single code scope to block on.)

10 · Risks & mitigations

False-firing on the existing estate

Mitigation: every check is conditional (D-002); the whole-estate integration validate is the gate — it passed.

A model or network creeping onto the rule's path

Mitigation: a transitive-import test asserts 0 model-client and 0 network references (NFR-001).

11 · Complexity tracking

None. One rule, one composer, one enum widening — all additive, all modelled on shipping precedent.

12 · Open questions

Attribute vs child spelling for scope/enforcement — settled here as children (a scope holds multiple paths; a child list is the natural shape). The decision index/registry file is deferred to Slice 1b (TBD-guardrail-decision-index).
