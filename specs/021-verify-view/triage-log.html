verify.html trace empty for fixture-driven tests

Spec upstream

Debugging an empty verification trace in 025-id-uniqueness's verify.html, root cause was the 021 spec identifying a "test task" only by path (tests/ or .test.); fixed by broadening the heuristic to recognise the story's Tests subsection / fixtures/ paths; regeneration fails — any fixture-driven feature recurs.

Expected
Each success criterion traced to the test task that proves it (P-7's artifact form; 021 · FR-002/FR-003).
Actual
All three SCs in specs/025-id-uniqueness/verify.html §2 render "— no test task cites this SC —"; the proof trace is empty though the feature is thoroughly tested (the registry fixture harness, 40/40).
Diagnosis
021's test-task heuristic is path-only — TEST_PATH = /(?:(?:^|\/)tests?\/)|(?:\.(?:test|spec)\.[tj]sx?$)/ at packages/core/src/commands/verify.ts:62 and (identically) packages/schema/src/rules/verify-view-stale.ts:25. Fixture-driven test tasks (paths under fixtures/, the way every schema rule is tested) never match, so the SC→test join finds nothing. validate stays silent because verify-view-stale only checks consistency (empty == empty), not completeness.
Fix
specs/021-verify-view/ — /spectastic.propose to broaden "test task" beyond the path regex (recognise the structural <h3>Tests (write & fail first)</h3> subsection present in every tasks.html, and/or fixtures/ paths) across both the generator and the stale rule; optionally add a completeness check that fails loudly on an empty trace when SCs + a Tests subsection exist.
Resolved
Fixed by 2026-06-27-trace-by-tests-section — applied + implemented (subsection-based identification across both impls, per-SC join, the completeness check; all five extant verify.html regenerated). 025's trace now links SC-001→T-100, SC-002→T-200.
Deep dive — cascade required

Cross-impl cascade (one 021 contract, two implementations). The narrow heuristic is duplicated in packages/core (the verify generator) and packages/schema (the verify-view-stale rule). A /spectastic.propose against 021 must land in both, or the generator and the validator drift on what a "test task" is.

P-7 "presence is not containment." This is the canonical lesson again: the structural gate went green (validate clean) while the artifact it guards is substantively empty. The completeness check named in Fix is the real close — make the silent pass loud.

Scope note. 025's verify.html is a derived view — do not hand-edit it. It will trace correctly the moment 021's fix lands and it is regenerated (spectastic verify 025-id-uniqueness). No 025 change is owed (REQ-LIFECYCLE-007: the lowest-passing rung is spec/021 — a 025-only fix recurs for the next fixture-driven feature).

No verify.html generated since 032 — validate is silent on absence, only drift

Spec upstream

Specs 032–036 (the decider arc) shipped Accepted with no verify.html — breaking an unbroken 021→031 streak. They were hand-implemented without running /spectastic.implement's completion step or spectastic verify, and nothing caught it: verify-view-stale guards a verify.html against drift, but an absent one trips no rule. Regeneration fails — the next hand-built slice recurs.

Expected
Every spec bundle from 021 onward carries a current verify.html (P-7's artifact form, 021 · FR-001); an Accepted bundle without one is caught by validate/CI, not shipped silently.
Actual
specs/032..036/ have no verify.html (present for every spec 021–031). spectastic validate passes clean — no rule asserts presence — so five bundles landed on main missing their P-7 view.
Diagnosis
verify.html generation is advisory: materialised by /spectastic.implement on completion, or by a manual spectastic verify <id>. 032–036 were implemented directly (code + tests, boxes ticked) without either, and no conformance rule enforces the artifact's presence — verify-view-stale only fires when a verify.html exists (drift/completeness). Same P-7 "structural gate green while the artifact is missing" lesson as T-001, one level up: not an empty trace, but no artifact. The generator (packages/cli/src/commands/verify.ts) works — the gap is enforcement, a P-8/T-009 shape (the guarantee lives in advisory prose, not a rule).
Fix
Immediate (just-do): backfill 032–036 with spectastic verify <id>. Durable (this card, spec/021): /spectastic.propose a requirement + validate rule — an Accepted spec bundle MUST carry a verify.html whose links are current — a verify-view-missing sibling to verify-view-stale, so CI rejects absence. Backfill alone recurs (REQ-LIFECYCLE-007: the lowest-passing rung is spec/021).
Resolved
Presence gap fixed by 2026-07-09-verify-view-missing — added FR-010 + the verify-view-missing rule (auto-derived floor; unit test + fixtures); 032–036 backfilled and traces for 032/033 completed (Tests-subsection retrofit). Trace-join half fixed by 2026-07-09-verify-trace-path-fallback — FR-003 modified so a phase with no <h3>Tests</h3> subsection falls back to identifying test tasks by path (.test./.spec.), mirrored in the generator + the drift rule. 034–036's tasks.html closures were authored so every SC resolves to a path-recognised test, and 032–036's verify.html were regenerated with real Run/Demo blocks. Both halves of T-002 now closed; 487 tests green, validate 0 errors.
Deep dive — scope + enforcement

Why spec/021, not just-do. Backfilling the five files is revert-safe and clears the immediate symptom, but the defect is "verify.html not generated" as a pattern: with generation advisory and no presence rule, any future CLI-bypassing or hand-built slice omits it again and validate stays green. The regen test only passes at the enforcement layer — a rule that fails on absence. That rule is 021's contract (it owns verify.html + the verify-view-stale rule), so the owner is upstream.

P-8 alignment. This is the same "guarantees live in the kernel or CI, never advisory prose" principle the decider arc (033–036) was built around — turned on verify.html itself. The presence rule is the CI-gate half; pairing it with init --tools' pre-commit validate would make a missing verify.html un-committable.

Backfill outcome + a second finding. spectastic verify regenerated all five (present ✓), but the SC→test traces are thin: 033–036 render "— no test task cites this SC —" for every SC (032: 2 of 4 populated). Partly structure (036's tasks.html has no <h3>Tests (write & fail first)</h3> subsection), but 033 has the subsection and SC-linked test tasks and still traces empty — a likely trace-join defect in the generator, a separate card (implementation/021) worth opening. It also sharpens the durable fix here: the enforcement rule should assert the trace is non-empty, not merely that the file exists — presence ≠ containment, the T-001 lesson, again.

verify.html presents an unverified command as runnable — it failed in practice (Gradle no-TTY → NPE)

Spec upstream

Debugging a verify.html Run block whose command NPE'd when actually run, root cause was a spec gap — verify can emit a Run/Demo command it never executed, presenting it with the same authority as a checked one; fixed by requiring the derived view to distinguish verified commands (actually run) from suggested ones, or to withhold unrun commands; regeneration fails at implementation — the bare-regenerate path has no notion of "unchecked", so any session repeats it.

Expected
A command shown in verify.html's Run/Demo block either ran successfully (and is marked verified) or is clearly flagged as an unchecked suggestion — never presented as if it works when it hasn't been exercised.
Actual
verify.html suggested a Gradle command it "admittedly hadn't checked"; run for real it threw an NPE because Gradle gives the spawned process no TTY. A P-7 ("done means verified") violation surfaced by the derived view itself.
Diagnosis
spectastic verify run bare (no piped captured commands) fills the Run/Demo block with unexecuted commands and no "verified vs suggested" distinction; 021's contract doesn't require the view to mark or withhold unrun commands. FR-003 (the Run/Demo grounding) is silent on the checked/unchecked axis.
Fix
specs/021-verify-view/spec.html — add a requirement (via /spectastic.propose) that a Run/Demo command carries a verified/suggested status, and that verify only marks a command verified when a real run was captured (the piped-JSON path); unrun commands render as explicitly unchecked.
Fixed
FR-011 landed: an unverified command is emitted with data-status="suggested" (verified?: boolean on the captured run), so the view no longer presents it as runnable.
Deep dive — principles-adjacent (P-7)

Principles invariant implicated but not owned here. This is the concrete P-7 ("done means verified; presence is not proof") showing up in the tool that is supposed to materialise P-7. The fix is a 021 spec change (checked/unchecked status on Run commands), not a principles amendment — P-7 already says the right thing; 021's derived view just needs to stop presenting unverified commands as verified. No cross-spec contract; no deferred scope promoted. Notably the 041/042 verify.html Run blocks authored this session were grounded in commands actually run — this card is about the general verify path, not those instances.
