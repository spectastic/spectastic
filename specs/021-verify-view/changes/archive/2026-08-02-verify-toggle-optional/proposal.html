Change proposal · 021-verify-view

A required field that says "none" five times in six is costing the others their attention

The toggle row is filled, conformant, and carries no information in 50 of 61 views. A reader learns to skip it — and learns it on the way past every other row.

Status Applied Change ID 2026-08-02-verify-toggle-optional Spec 021-verify-view Source Considerations: verify-view-actionable (D-004); resolves TBD-verify-toggle-optional Author Brian Corbin · @briancorbinxyz Created 02 Aug 2026 Targets 1 modified (FR-004) Read time

FR-004 requires the Run/Demo block to carry a toggle — "a feature flag / env var / setting, or an explicit none". Across all 61 verify views that field is the literal string none in 50. It is filled, conformant, and informationless five times in six. The requirement is not wrong about what a toggle is; it is wrong that every feature has one to report. This modifies FR-004 so the toggle is carried when there is one, and otherwise omitted — where the format's existing loud-gap treatment already renders absence visibly, without asking an author to type a word that means nothing. It is the same reasoning 083 used to make its new field optional, applied one field over; leaving the two inconsistent would mean the estate's newest field is optional because absence is honest, while its oldest neighbour still mandates a placeholder.

A required field that says "none" five times in six is costing the others their attention

Applied

1 · Intent

021 built the Run/Demo block so a reviewer could answer four questions from one artifact: how do I build it, what do I turn on, how do I test it, how do I see it. The toggle exists because the dogfood case that motivated the spec genuinely had one, and a feature you cannot see because a flag is off is a real and infuriating failure.

An audit of all 61 views measured how often that question has an answer. The toggle field holds the literal string none in 50 of 61 — with a handful of near-variants (none — no feature flag) that are the same answer typed longer. Eleven views carry a real toggle. The requirement is doing its job in those eleven and manufacturing a row of chrome in the rest.

A required field with nothing to say is not free. It costs the attention of every row a reader passes on the way to the one they want, and it teaches the habit of skimming a block whose whole purpose is that it can be trusted line by line. That cost is now measurable in a second place: the same audit found readers were not finding the command they needed, and the block they were skimming is where it was.

2 · Scope

In scope

  • Making the toggle a field carried when the feature has one, rather than one every capture must answer.
  • Keeping the explicit none available for the case where an author wants to say, positively, that they checked and there is no flag.
  • Consistency with the sibling field added by 083, which is optional on exactly this reasoning.

Out of scope

  • Removing the field. Eleven views carry a real toggle and it is load-bearing in every one of them.
  • Rewriting the 50 existing none values. They stay: they are accurate, they were honestly captured, and a sweep to blank them would be churn with no reader benefit.
  • Any change to how absence renders. The loud "not recorded" treatment already exists and is exactly the behaviour this relies on.

3 · Approach

Modify FR-004 rather than add a requirement, because the sentence being corrected is inside it: the block's four fields are enumerated as a single obligation, and only one of the four is being relaxed. Splitting that into a second requirement would leave a reader holding two rules about one list.

The relaxation is deliberately narrow. The toggle stays a named part of the block, stays typed, and stays rendered — what changes is that a capture with nothing to report may omit it and let the format say so, instead of being obliged to assert none. An author who wants to record that they checked keeps that option, and it now means something, because it is a choice rather than the only legal way to fill a mandatory box.

Note what this does not claim. Making the field optional will not by itself cause anyone to fill it more thoughtfully; the survey's D-004 is explicit that the pressure to record something has to come from the gap being conspicuous, and that no validator should be added here. This change removes a compulsory non-answer. It does not manufacture a real one.

4 · Deltas

One delta.

verify.html MUST carry a Run/Demo block built from typed elements: a run command, a test command citing the test task(s) it runs, and a demo path citing the SC-NNN it satisfies. The block MUST also carry a toggle — a feature flag, environment variable or setting — where the feature has one; where it has none, the toggle MAY be omitted and render as an unrecorded field rather than being asserted as "none". The demo path MUST be medium-agnostic — a click-path for a UI, an import for a library, a request for a service.

Rationale

The one net-new artifact. Typed (not prose) so it is greppable and a missing field renders loudly; medium-agnostic because spec-kit's "every feature runs from the CLI" was too rigid. The toggle became conditional after an audit of all 61 views found the field held the literal string none in 50 of them — filled, conformant and informationless five times in six, which costs every other row in the block the reader's attention. The explicit none remains available for an author who wants to record positively that they checked; it stops being the only legal way to satisfy a mandatory field. No validator enforces the toggle either way: the pressure to record one is the conspicuousness of its absence, per the same reasoning that keeps 083 FR-001 optional.

5 · Risk register

The adversarial pass does not trigger by the standing rule — one modified delta, no removal, a single topic prefix. It is recorded as considered rather than skipped silently. One risk is worth naming without it, because it is the obvious objection.

Relaxing a required field can hide a real one. A feature that genuinely has a toggle, whose author omits it, now produces a view that looks the same as a feature with no toggle at all — where previously the author was at least obliged to type something. That is true, and it is the cost being accepted. It is bounded by the fact that the previous obligation was satisfiable with none, which is precisely what an author in a hurry types: the mandatory field never distinguished "no toggle" from "did not think about it" either. The change trades a false signal that looked like an answer for an honest one that looks like a gap.

6 · Tasks

Scoped to this change only.

  • Soften the toggle from an assertion to a conditional in the capture prompt, and re-sync the command copies commands/spectastic.implement.md
  • Confirm an omitted toggle still renders its loud gap, so relaxing the requirement changes no behaviour tests/verify.view.spec.ts

No generator change is needed: the field is already optional in the captured shape, and the requirement is what made it feel mandatory.

7 · Open questions

None outstanding. Whether to delete the field rather than relax it was settled by the eleven views that carry a real toggle; whether to sweep the existing 50 was settled against, since those values are accurate and were honestly captured.
