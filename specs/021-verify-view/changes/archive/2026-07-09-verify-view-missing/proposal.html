Change proposal · 021-verify-view

Enforce verify.html presence

Close the gap that let 032–036 ship with no verify.html: verify-view-stale guards a view that exists; nothing requires one to exist.

Status Applied Spec 021-verify-view Change 2026-07-09-verify-view-missing Created 09 Jul 2026 Origin Triage 021/T-002

Add one requirement — FR-010 — that a terminal-state spec bundle under the verify-view convention MUST carry a verify.html, enforced by a new verify-view-missing validate rule (a presence sibling to the drift-guarding verify-view-stale). Forward-only: 001–020 predate the convention and are exempt. Completeness of a present view is already FR-008's job; this closes the absence hole.

1 · Scope

One added requirement + one validate rule. No existing requirement changes; FR-008 (completeness of a present trace) and the verify-view-stale rule are untouched. Forward-only, so no existing bundle regresses: 021–036 already carry a verify.html; 001–020 are grandfathered.

2 · Approach

The rule derives the convention floor from the repo itself — the lowest spec id that has a verify.html (021 today) — and flags any terminal-status spec at or above that floor whose bundle lacks one. No hard-coded spec number; self-maintaining, and silent when validating a partial set (the same whole-project-context caveat as no-broken-defer-to).

3 · Deltas

A spec bundle whose <spec-status> has reached a terminal state (accepted / superseded / deprecated) and which falls under the verify-view convention MUST carry a verify.html. spectastic validate MUST report a finding — the verify-view-missing rule — when such a bundle lacks one. The convention floor is the lowest spec id in the project that already carries a verify.html (forward-only from 021-verify-view; specs 001–020 predate it and are exempt). This closes the gap where FR-008 / verify-view-stale only guard a verify.html that already exists.

Reason. 032–036 shipped Accepted with no verify.html and validate stayed clean — the generation step is advisory (implement-on-completion / manual spectastic verify) and no rule enforced presence (triage 021/T-002). P-8: the guarantee belongs in a CI-checkable rule, not advisory prose.

4 · Risk register

Grandfather boundary wrong → false positives on 001–020

Concern. A naive "every Accepted spec needs verify.html" would flag the 20 specs that predate the convention.

Response. Mitigated by the auto-derived floor: the rule enforces presence only at/above the lowest spec that already has a verify.html (021). 001–020 sit below the floor and never fire. Verified: the current repo validates clean under the rule.

Partial validation set → false negative or noise

Concern. Validating a single spec.html in isolation can't tell "no verify.html" from "verify.html not in the set."

Response. The rule is cross-file and needs whole-project context — identical to no-broken-defer-to. It computes the floor from the set it's given and only flags a bundle whose spec is present but verify is absent; CI runs the full glob. Documented as a caveat, not a silent guess.
