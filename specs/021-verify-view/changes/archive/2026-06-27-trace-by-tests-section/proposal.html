The verify view's SC→test trace (FR-003) came up empty for 025-id-uniqueness because the implementation identifies a "test task" purely by file path (TEST_PATH), and fixture-driven test tasks — how every schema rule is tested (fixtures/<rule>/) — don't match. And FR-008's drift check stayed silent, because it verifies consistency (empty == empty), not completeness. The silent pass is what let this ship — that is the part worth closing.

Trace test tasks by the Tests subsection, not by file path

Applied

1 · Intent

Spec 021-verify-view promises a success-criterion → test-task trace as the artifact form of P-7 (done means verified). On 025-id-uniqueness that trace rendered completely empty — all three SCs showed "— no test task cites this SC —" — even though the feature is thoroughly tested. The cause is a too-narrow notion of "test task": both the generator (verify.ts:62) and the validator (verify-view-stale.ts:25) identify one by file path (/(?:(?:^|\/)tests?\/)|(?:\.(?:test|spec)\.[tj]sx?$)/), so fixture-driven test tasks — paths under fixtures/, which is how spectastic's own schema rules are tested — never match.

Worse, nothing complained: spectastic validate was clean because the anti-drift rule (FR-008) only checks that the view's links are consistent with the bundle (empty matches empty) — it never checks that a trace is complete. A silent green on an empty proof view is exactly the "presence is not containment" failure the project has paid for before. This proposal fixes both: identify a test task structurally, and make the empty trace loud.

2 · Scope

In scope

  • MODIFY FR-003 — identify a test task by the story's Tests subsection (the task whose nearest preceding <h3> is the Tests heading), independent of file path. The path heuristic is replaced, not retained — a single authority.
  • MODIFY FR-008 — the validator also fails when a closed SC resolves to no test task, computed per-SC (not a flat union), so its completeness check reasons over the same mapping the generator renders.
  • Regenerate every extant verify.html as part of this change, so the strengthened FR-008 never lands ahead of the regenerations (the NFR-002 rollout mitigation).

Out of scope

  • Recognising test patterns beyond the structured tasks.html (e.g. inferring tests from source) — that is a larger change.
  • Re-authoring any verify.html by hand — they are derived views, regenerated by the rollout task above, never hand-edited.

3 · Approach

The signal already exists in every tasks.html: the /spectastic.tasks convention opens each story with an <h3>Tests (write & fail first)</h3> subsection. Make that the authoritative marker — a <spec-task> under a story's Tests heading is a test task, whatever its file path. Both implementations of the contract change in lockstep: packages/core/src/commands/verify.ts (the generator's SC→test join) and packages/schema/src/rules/verify-view-stale.ts (the validator's expected-set computation), so the two never disagree on what a test task is. Then add one finding to the validator: a closed SC (one cited by a US-phase note) with zero resolving test-task links is reported, naming the gap and the regeneration fix — the completeness check that turns the silent pass loud.

4 · Deltas

Two MODIFY deltas, both must-tier; target= links to the live spec.

What changes: define how a "test task" is identified — structurally, by the story's Tests subsection, not by file path.

The aggregation MUST trace each SC-NNN to its acceptance scenario and to the test task(s) that verify it — where a test task is a <spec-task> whose nearest preceding heading is the story's <h3>Tests (write & fail first)</h3> subsection, identified by that structural position and independent of its file path (so fixture-driven test tasks, whose paths live under fixtures/, are recognised; a task under the story's Implementation subsection is not a test task). These traces MUST be materialised as static links at generation time, with no cross-file fetching at render time.

Rationale

Single-file HTML cannot fetch siblings (P-1, P-4); generation is the only moment siblings are read. The earlier path-only heuristic (tests/ / .test.) silently excluded the fixture-driven tests spectastic itself uses, producing an empty trace (triage 021 · T-001). The Tests subsection is the authoring convention's own signal — already present in every tasks.html.

What changes: the validator also fails on an empty/incomplete trace, not only on drift — completeness, not just consistency.

spectastic validate MUST report a finding when a verify.html's derived links no longer match the current SC-NNN, acceptance, or test-task IDs in its sibling bundle, or when a closed SC-NNN resolves to no test task (an empty or incomplete trace); the finding MUST name the divergence or the gap and the regeneration fix.

Rationale

Anti-drift and anti-empty, made loud (the linter-is-not-noise discipline). The prior rule checked only that the view was consistent with the bundle, so an all-empty trace passed silently — a "presence is not containment" green (P-7). Completeness closes that gap: a proof view with no proof is itself a finding.

5 · Risk register

The adversarial risk pass ran (the proposal touches must-tier requirements, per REQ-CHANGE-004). Three findings — all dispositioned mitigated by the author (via interview); each mitigation is folded into the deltas, §2 scope, and §6 below. No identified risk remains.

Dropping the path filter without bounding collection to the Tests subsection's DOM range over-traces: collectTestTasks scans the whole phase-usN section, which holds both the <h3>Tests</h3> and <h3>Implementation</h3> subsections — so impl tasks (T-110, T-210) get pulled in as "proof," and the new FR-008 completeness check goes green on the wrong-but-full trace.

FR-003 delta: "any <spec-task> under the user story's Tests subsection … independent of its file path"; grounded in verify.ts collectTestTasks + the per-phase join, which today is narrowed only by TEST_PATH.

Mitigated (author-confirmed): a test task is a <spec-task> whose nearest preceding <h3> is the Tests heading (subsection-scoped), not merely "in the phase" — sharpened in the FR-003 delta and §6, with a fixture asserting an Implementation-subsection task does not appear in the proof leg.

Strengthening FR-008 to fail on an empty proof leg will newly fail every pre-existing verify.html — all generated under the old path-only rule with tests under fixtures/ — on the next validate, breaking the clean tree on day one and undermining NFR-002's "rebuild-and-diff is a meaningful drift signal."

NFR-002: "running the generator twice … yields a byte-identical verify.html, so a CI rebuild-and-diff is a meaningful drift signal" — vs the new finding firing on every legacy view. (Note: SC-002 already implied completeness — "each as a resolving link to … its closing test task(s)" — specified but unenforced.)

Mitigated (author-confirmed): this change regenerates every extant verify.html (not just 025) as part of itself, so the strengthened FR-008 never lands ahead of the regenerations — added to §2 in-scope and §6. The apply-time hazard the adversarial pass existed to catch.

§2 scopes only mirroring test-task identification across the two impls, but the real divergence is the SC-closure join: the validator collects test tasks as a flat order-independent union (verify-view-stale) while the generator maps them per-SC — and the new completeness check makes that per-SC join load-bearing in the validator for the first time, so the two can agree on "what is a test task" yet disagree on "is this SC covered."

§2 in-scope: "the validator also fails when a closed SC resolves to no test task"; §6 task 2: "Mirror the identical identification …" — the join is never named, though the triage deep-dive flagged generator/validator drift.

Mitigated (author-confirmed): §2 and §6 now require the validator to compute the trace per-SC (not a flat union), so the completeness check reasons over the same SC→tasks mapping the generator renders. Identification parity is necessary but not sufficient — join parity is the real contract.
