Specification · 021-verify-view

Verify view

A generated verify.html per spec that answers "how do I run it, and how do I know it works?" — by aggregating what already exists and grounding the one missing piece in the run that actually happened.

Status Accepted Spec ID 021-verify-view Owner Brian Corbin · @briancorbinxyz Reviewers — Created 24 Jun 2026 Principlesv1.2.0 Smallest demoableAfter /implement finishes a spec, specs/<id>/verify.html exists and shows traced SC → acceptance → test links plus a Run/Demo block whose commands are the ones that just ran. Read time

The lifecycle is rich at the front and silent after "implementation complete": nothing tells a teammate how to run, demo, or verify the built feature. This spec adds a generated, derived verify.html per spec that aggregates the existing success criteria, acceptance, and test tasks as traced links (never copied), and adds the one missing artifact — a medium-agnostic Run/Demo block that /implement fills from the commands it actually ran. A single spectastic verify generator produces it, called by /implement at completion and runnable standalone to regenerate the links; it carries no status of its own, and spectastic validate flags it when its links drift. It is the larger sibling of the ratified P-7 — the principle named the bar, this view helps a human confirm it.

Depends on principles v1.2.0 (P-7) and reads the existing structure of spec.html/tasks.html; wires into two named upstreams — the validator (002-validate-cli) and the implement hook (014-core-implement). Owns no shared mutable state.

1 · Context

The lifecycle is rich at the front — spec.html carries success criteria (SC-NNN) and per-story acceptance; tasks.html opens each story with test-first phases citing the FR-NNN/SC-NNN they close — but once /implement ticks the last box, nothing answers the question a teammate actually asks: "It's built. How do I run it, see it work, and what do I turn on?" A good merge request reads what · why · how · validation; spectastic has homes for three (tasks / spec / plan) and validation is homeless. Dogfooding spec-tictactoe proved it real — the UI shipped with no way to tell how to run the whole thing, and "done" to "I can see it" was private archaeology.

P-7 · Done means verified now names the universal bar; this spec adds the per-feature artifact that says how a human confirms this feature. The design rationale — why generate not write, aggregate not copy, a standalone file — lives in verify-considerations.html; its decisions (D-2 aggregate-don't-copy, D-3 standalone file, D-4 no-new-verb / derived view) are settled inputs here. Users: the reviewer who lands in specs/<id>/ after a build, and the author who wants the validation section to keep itself honest.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Run and demo a built feature P1

As a reviewer who just pulled a finished spec, I want to open one file and see exactly how to run, toggle, test, and demo the feature so that I can see it work without reading the source or asking the author.

Acceptance: Opening specs/<id>/verify.html shows a Run/Demo block with the build/start command, any required toggle (or an explicit "none"), the exact test command, and a human demo path; copy-pasting the Run and Tests commands reproduces the feature's verification.

US2 · Trace a success criterion to its proof P1

As a reviewer, I want to follow each success criterion to its acceptance scenario and the test task that closes it so that I can confirm every claimed outcome is actually verified, not asserted.

Acceptance: verify.html lists every SC-NNN from the spec, each linking to its acceptance scenario and the closing test task(s); the links resolve to the real anchors in the sibling spec.html/tasks.html; no SC prose is copied, only linked.

US3 · Keep the view honest as the spec changes P2

As a spec author, I want spectastic validate to tell me when a verify.html has drifted from its spec/tasks so that a stale validation section fails loudly instead of lying.

Acceptance: After adding or renaming an SC-NNN/test task without regenerating, spectastic validate on the spec directory reports a staleness finding naming the divergence and the fix (spectastic verify <id>); regenerating clears it.

Edge cases

  • Nothing ran. A docs-only or non-runtime task leaves the Run/Tests path empty — the typed elements render the absence loudly (an explicit "no tests for this slice"), never a silent blank.
  • JavaScript off. Every traced link and the whole Run/Demo block are still present — the links are static, materialised at generation time.
  • Regenerate after bundle edits. The standalone generator re-derives the links from the current bundle while preserving the Run/Demo block /implement captured.
  • Spec implemented before this landed. Existing specs get no verify.html automatically; they backfill on demand (deferred — see §3).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A spectastic verify <spec-id> generator MUST produce specs/<spec-id>/verify.html as a single self-contained HTML artifact in the spectastic design system (same stylesheet, semantic-tag vocabulary, and calm typography as every other artifact).

Rationale

Single generator, one code path. A CLI subcommand, not a lifecycle verb — the 8-verb surface is unchanged (D-4).

verify.html MUST aggregate the spec's success criteria, per-story acceptance scenarios, and the test-first tasks that close them by reference only — as links to the anchors in the sibling spec.html/tasks.html — and MUST NOT copy their prose.

Rationale

D-2: copying guarantees drift; the borrowed parts can't drift because they are links.

The aggregation MUST trace each SC-NNN to its acceptance scenario and to the test task(s) that verify it — where a test task is a <spec-task> whose nearest preceding heading is the story's <h3>Tests (write & fail first)</h3> subsection, identified by that structural position and independent of its file path (so fixture-driven test tasks, whose paths live under fixtures/, are recognised; a task under the story's Implementation subsection is not a test task). These traces MUST be materialised as static links at generation time, with no cross-file fetching at render time.

Rationale

Single-file HTML cannot fetch siblings (P-1, P-4); generation is the only moment siblings are read. The earlier path-only heuristic (tests/ / .test.) silently excluded the fixture-driven tests spectastic itself uses, producing an empty trace (triage 021 · T-001). The Tests subsection is the authoring convention's own signal — already present in every tasks.html.

verify.html MUST carry a Run/Demo block built from typed elements: a run command, a toggle (feature flag / env var / setting, or an explicit "none"), a test command citing the test task(s) it runs, and a demo path citing the SC-NNN it satisfies. The demo path MUST be medium-agnostic — a click-path for a UI, an import for a library, a request for a service.

Rationale

The one net-new artifact. Typed (not prose) so it is greppable and a missing field renders loudly; medium-agnostic because spec-kit's "every feature runs from the CLI" was too rigid.

/implement MUST, at the last-tick completion transition, invoke the generator to materialise or refresh verify.html, populating the run and test elements from the commands it actually executed in its Verify step.

Rationale

Grounds the Run block in a real run (the REQ-LIFECYCLE-006 discipline), not aspirational prose — riding the Verify step and last-tick flip /implement already runs.

The generator MUST be runnable standalone (spectastic verify <spec-id>) to regenerate the aggregated links from the current bundle, and standalone regeneration MUST preserve the authored Run/Demo block previously captured by /implement.

Rationale

One generator, two callers. The links are derived (safe to rebuild anytime); the Run block is grounded evidence (must survive a links-only refresh).

verify.html MUST NOT carry its own <spec-status>; it derives its lifecycle state from the spec bundle (per REQ-LIFECYCLE-005).

Rationale

It is a view, not an independent lifecycle participant — one fewer status to keep in sync, and it can never contradict the spec it describes.

spectastic validate MUST report a finding when a verify.html's derived links no longer match the current SC-NNN, acceptance, or test-task IDs in its sibling bundle, or when a closed SC-NNN resolves to no test task (an empty or incomplete trace); the finding MUST name the divergence or the gap and the regeneration fix.

Rationale

Anti-drift and anti-empty, made loud (the linter-is-not-noise discipline). The prior rule checked only that the view was consistent with the bundle, so an all-empty trace passed silently — a "presence is not containment" green (P-7). Completeness closes that gap: a proof view with no proof is itself a finding.

A missing or empty typed element in the Run/Demo block SHOULD render visibly as an unfilled field rather than collapsing to nothing, so an incomplete Run block is obvious on sight.

A spec bundle whose <spec-status> has reached a terminal state (accepted / superseded / deprecated) and which falls under the verify-view convention MUST carry a verify.html. spectastic validate MUST report a finding — the verify-view-missing rule — when such a bundle lacks one. The convention floor is the lowest spec id in the project that already carries a verify.html (forward-only from this spec; specs 001–020 predate it and are exempt). This closes the gap where FR-008 / verify-view-stale only guard a verify.html that already exists.

Rationale

Added by 2026-07-09-verify-view-missing from triage T-002: 032–036 shipped Accepted with no verify.html because generation is advisory and no rule enforced presence. P-8 — the guarantee belongs in a CI-checkable rule.

Non-functional

verify.html MUST be fully readable with JavaScript disabled — every traced link and the entire Run/Demo block visible — consistent with progressive enhancement (P-4).

Regeneration MUST be idempotent: running the generator twice against an unchanged bundle (and unchanged captured Run block) yields a byte-identical verify.html, so a CI rebuild-and-diff is a meaningful drift signal.

Out of scope (deferred to other slices)

  • Backfilling verify.html for already-implemented specs 001–020 — forward-only (consistent with P-7's scope); they regenerate on demand later.
  • Promoting the agent-facing verification detail out of CLAUDE.md into an AGENTS.md — only if/when spectastic goes cross-tool.
  • A new lifecycle verb for verification — explicitly rejected (D-4); the generator is a CLI subcommand, not a hero verb.
  • Reviving spec-kit's "every feature must be CLI-runnable" rule — the Run/Demo block is medium-agnostic instead.

4 · Data model

This feature owns one artifact and a small typed vocabulary; it reads (never mutates) the sibling spec/tasks.

Entities

verify.html
The derived per-spec view. Two regions: an aggregated trace (each SC-NNN → acceptance → closing test task, as links) and the Run/Demo block. No own status; derives from the bundle.
Run/Demo block
Typed elements for run, toggle, tests (cites test tasks), and demo (cites the SC it satisfies). The demo field is medium-agnostic.
Captured run record
The literal run/test commands /implement executed in its Verify step, written into the Run/Demo block as grounded evidence. This is the only hand-authored content; everything else is derived.

Invariant: the trace region is pure derivation (rebuildable anytime); the captured run record is grounded evidence (must survive a links-only regeneration, per FR-006). The generator re-derives the links and preserves the run record.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

After a spec is implemented, a reviewer who has never seen it can run, toggle, test, and demo the feature using only verify.html — without reading the implementation source or asking the author.

100% of the spec's SC-NNN appear in verify.html, each as a resolving link to its acceptance scenario and its closing test task(s); zero SC prose is duplicated (links only).

The run and test commands shown in verify.html are the commands that actually executed during /implement; a reviewer copy-pasting them reproduces the feature's verification with no edits.

When an SC-NNN or test task is added or renamed in the bundle without regenerating, spectastic validate reports the drift; after spectastic verify <id>, validate is clean.

With JavaScript disabled, verify.html still renders every traced link and the complete Run/Demo block.

6 · Assumptions

Every spec already carries SC-NNN, per-story acceptance, and test-first tasks that cite the FR-NNN/SC-NNN they close — the aggregator reads existing structure, it does not require authors to add new trace metadata.

/implement's Verify step runs real commands whose text can be captured programmatically (it already runs "the smallest possible verification the task admits").

Forward-only: this binds specs implemented after 021 lands; existing specs are not retroactively given a verify.html.

7 · Open questions

None outstanding — every decision was anchored in the interview (full aggregate + Run block; grounded Run block; typed elements; derived status; one generator / two callers; validate-flags-staleness). The cross-file build-step constraint is resolved by FR-003 (static links at generation time). Tag names, generator package, and the link-matching algorithm are deferred to /spectastic.plan, not open questions.
