Spec 011-core-spec Created 16 Jun 2026 Read time

Cards

Re-entry gated by --reentry flag instead of destination state

Spec upstream

Cascade of 008/T-001 with an extra failure mode: spectastic spec overwrites an existing destination silently when the user omits --reentry. The flag is the wrong gate — the destination's <spec-status> should be.

Expected
Running spectastic spec "<description>" against a fresh directory authors; against an existing Draft spec it edits in place (with or without an explicit flag); against an Accepted spec it refuses (or routes the user to /spectastic.propose). The behaviour is driven by destination state, not by a separate flag.
Actual
CLI subcommand (packages/cli/src/commands/spec.ts) splits on the --reentry <spec-id> flag. Without it, fs.writeFile overwrites whatever is there — including a Draft spec the user just authored or an Accepted spec they intended to amend through proper channels. With it, the kernel sharpens an existing spec but doesn't check the spec's status before doing so.
Diagnosis
011's spec doesn't constrain the verb's behaviour against an existing destination. The current implementation pairs a CLI flag with kernel-level re-entry logic, but the flag-driven gate is orthogonal to the lifecycle state that actually determines whether the artifact is loose or locked. Per REQ-LIFECYCLE-004, only past-Draft artifacts carry consumer commitments worth protecting.
Fix
Open /spectastic.propose against specs/011-core-spec/spec.html: ADD an FR specifying destination-state-aware behaviour (fresh → author; Draft → edit in place + changelog entry; past-Draft → refuse, with optional --force override). The --reentry flag can stay as a hint for the kernel's prompt-construction (Sharpen-rather-than-Author phrasing) but should NOT be the gate for whether to overwrite. Hotfix the CLI subcommand to read the destination's <spec-status> before the branch.
Closed by
P-6 ratification + 2026-06-16-p6-cascade-spec (MODIFIED FR-003 — landed as cascade-MODIFY against the existing FR-003 rather than a new FR, since FR-003 already governed the invocation surface). CLI hotfix at packages/cli/src/commands/spec.ts via shared gateOnDestinationState helper; both invocation paths gated (re-entry via --reentry AND fresh-mode against the resolved output). Silent-overwrite failure mode closed.
Deep dive — extra failure beyond 008's pattern

Two of three cascade cards from 008/T-001. 011's failure mode is worse than 008's: 008 errs on the side of ceremony (refuses Draft edits when it shouldn't), while 011 errs the other way (silently overwrites Draft specs the user may not have meant to discard). The latter is more dangerous because there's no signal — the previous content is just gone. Hotfix is correspondingly more urgent. Version-policy half of 008's defect does NOT cascade (spec.html template carries no <b>Version</b> field).
