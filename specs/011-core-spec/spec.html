1 · Context

Today's /spectastic.spec is the most-complex interactive verb. The markdown at commands/spectastic.spec.md instructs the LLM to run a two-phase interview: chat phase (context, user stories, edge cases, data model, out-of-scope prose) and a decision phase using Claude Code's AskUserQuestion to anchor every decidable choice (smallest demoable, priorities, scope splits, quantified NFRs) before writing. An unresolved <spec-question> in a finished artifact signals interview failure.

This works in Claude Code because AskUserQuestion ships there; it doesn't work elsewhere. The kernel from 006-kernel-extraction defines AIProvider.ask<T>() as the abstract counterpart — same bounded-choice contract, with the surface (Claude Code tool call / MCP elicitation / VS Code quick-pick / web modal) wired by the consumer. spec exercises that abstraction end-to-end for the first time. Re-entry mode is in scope from day one because the markdown already supports it (step 6); folding it in is cheap because the same interview engine handles both paths.

2 · User scenarios & testing

Each story is independently testable.

US1 · Maintainer authors a fresh feature spec via CLI P1

As a spectastic maintainer outside Claude Code, I want to run spectastic spec "<feature>" and walk through an interactive two-phase interview that produces a populated specs/<id>/spec.html so that I can author specs from any terminal.

Acceptance: spectastic spec "test feature" creates specs/NNN-test-feature/, copies the template with corrected asset paths, runs the interview, and writes a populated spec.html. spectastic validate against the new file returns no findings.

US2 · Maintainer re-enters an existing spec to deepen it P1

As a maintainer revisiting an earlier spec, I want to run spectastic spec <existing-spec-id> and have the verb sharpen the artifact without losing prior content so that I can deepen a spec without re-deriving the original interview.

Acceptance: spectastic spec 011-core-spec reads the existing file, runs a re-entry interview, and either adds content (new FRs with fresh IDs, extended rationale, new changelog entries) or asks explicit confirmation before removing/overwriting. Stable IDs survive; no FR-ID is reused.

US3 · Future MCP / VS Code consumer invokes specCommand natively P2

As a future MCP / VS Code author, I want to import specCommand from @spectastic/core/commands/spec and supply a custom AIProvider whose ask<T>() renders bounded choices natively so that the spec interview reaches users in their tool of choice without re-implementing the procedure.

Acceptance: A test under packages/core/test/ constructs a stub AIProvider scripting the answers, calls specCommand(input, ctx), and receives a SpecResult whose html matches the CLI's output. No process spawn; no Claude Code dependency.

Edge cases

Five tracked failure modes the verb handles
  • Re-entry overwrite risk — the verb detects an existing spec.html and switches to re-entry mode automatically. Removals or overwrites of existing requirements require explicit user confirmation via an ask<T>() call; the default is to preserve and extend.
  • Stub-AI test determinism — the interview's decision phase loops until exhaustion, which is hard to fixture. The stub AIProvider supplies a scripted answer queue; if the queue empties while the verb still asks questions, the test fails loudly with the unconsumed question text — surfacing interview drift rather than hanging.
  • Budget gauge crossing the amber band — when the in-progress draft enters the amber band (≥ 80% of authored-words <spec-budget>, per REQ-FORMAT-004), the verb surfaces a splitting nudge via ask<T>(): "Should some of this be its own slice?" with the out-of-scope move as the recommended option.
  • Unresolved questions at write-time — if the decision phase exits with any decidable question still open, the verb either re-prompts or records the item in <spec-questions> with reasoning. Genuinely-undecidable items survive; decidable ones do not.
  • Spec ID collision — the verb scans specs/ for the highest existing number and increments. If the user supplies an explicit ID that collides with an existing directory, the verb refuses and asks for confirmation to switch into re-entry mode against the existing spec.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional — the spec verb

specCommand MUST conform to the kernel contract in 006 FR-003: signature async function specCommand(input: SpecInput, ctx: KernelContext): Promise<SpecResult>, pure with respect to arguments, all IO + AI access through ctx. No module-level side effects; no implicit process.cwd() or console.

specCommand MUST be implemented at packages/core/src/commands/spec.ts, exported via the subpath @spectastic/core/commands/spec. The package's exports field MUST gain this subpath additively; the umbrella index.ts MUST NOT eagerly re-export it (per 006 FR-002).

@spectastic/cli MUST ship a spec subcommand with two invocation forms: spectastic spec "<feature-description>" (auto-assigns a Spec ID) and spectastic spec <existing-spec-id> (resolves specs/<spec-id>/spec.html). Regardless of invocation form, the subcommand MUST gate its destructive behaviour on the resolved destination's <spec-status> per P-6: a fresh path or Draft destination MUST be authored / edited in place (preserve existing IDs; append a one-line <spec-changelog> entry); a past-Draft destination (Accepted, In Review, Superseded, Deprecated, Blocked) MUST be refused with a typed error pointing at /spectastic.propose. A --force override MAY bypass the past-Draft refuse with a one-line warning that the operation skips the change-management surface. Argument shape MAY hint at the kernel's prompt construction (Sharpen-vs-Author phrasing) but MUST NOT be the gate for overwriting. The subcommand owns shell-side concerns (argument parsing, exit-code translation, writing the result HTML to disk); the kernel function owns the interview and HTML generation.

The verb MUST implement the two-phase interview defined in commands/spectastic.spec.md. The chat phase MUST use ctx.ai.chat() for narrative capture (context, user-story prose, edge cases, data-model intent, out-of-scope prose); the decision phase MUST use ctx.ai.ask<T>() for bounded choices (smallest demoable, priorities, scope splits, quantified NFRs). The decision phase MUST loop until decision exhaustion per the discipline in CLAUDE.md.

Re-entry mode MUST detect an existing spec.html at the resolved path and load its content before interviewing. The verb MUST preserve existing requirements, IDs, and changelog entries. Additions (new requirements, extended <details> rationale, new changelog entries) are permitted unconditionally; removals or overwrites of existing content MUST require explicit confirmation via ctx.ai.ask<T>() before being applied.

The smallest-demoable prompt MUST be the first decision-phase question in fresh mode. If the user's answer reaches for "the whole feature" or "all surfaces at once", the verb SHOULD push back with a follow-up ask<T>() offering 2–3 narrower framings before proceeding.

The artifact generated by specCommand MUST include a completed INVEST self-check (<dl class="invest">) with all six rows populated. The V row MUST link to a SC- ID; the T row MUST link to an acceptance scenario or requirement. If any row is honestly ✗, the verb MUST surface a warning in the returned SpecResult.

The verb MUST track the in-progress draft's authored word count against the spec's declared <spec-budget>. When the draft enters the amber band (≥ 80% of budget, per REQ-FORMAT-004), the verb MUST surface a splitting nudge via ctx.ai.ask<T>() with options to (a) move material to <spec-out-of-scope> with defer-to="TBD-<topic>", (b) scaffold a sibling spec, or (c) acknowledge and proceed.

Every <spec-question> in the generated artifact MUST represent a genuinely-undecidable item. The verb MUST attempt to anchor every decidable question via ctx.ai.ask<T>() first; only items the user explicitly declines to decide (or that depend on absent upstream information) survive into the open-questions register.

The kernel function MUST return a structured SpecResult containing the generated html string, the resolved specId, and a requirementsCount. The kernel MUST NOT write to the filesystem; the CLI subcommand (or any downstream surface) owns the writeFile call. This split keeps the kernel pure and testable per 006 FR-003.

The verb MUST be unit-tested at packages/core/test/spec.test.ts with a stub AIProvider supplying scripted chat responses and ask<T>() answers. CLI integration tests at packages/cli/test/cli.test.ts MUST cover the wiring end-to-end (argument parsing, file write, exit code).

commands/spectastic.spec.md MUST gain a MAY-Bash-to-CLI note per 006 FR-009: the LLM MAY shell out to spectastic spec for deterministic operations (template copy, asset path rewrite, ID assignment, file write) but MUST NOT be required to. The markdown procedure remains the source of truth for the interview.

specCommand's docblock SHOULD link to the canonical procedure file (commands/spectastic.spec.md) per 006 FR-008. The docblock summarises the contract; the markdown remains the canonical procedure.

Non-functional

The extraction MUST NOT regress any scenario in bench/baselines.json past its declared budget. The init-help-cold-start scenario remains the explicit lazy-loading regression guard — spec.ts MUST NOT import the HTML template, parse5, or any heavyweight dependency at module load; all such work happens inside the command function on first call.

Out of scope (deferred to other slices)

  • Import specs authored by other tools (OpenSpec, GitHub Spec Kit). Cross-tool ingest is its own design problem.
  • Spec analytics — requirement-count trends, churn, budget-band crossings over time. Useful telemetry; not write-path concern.
  • Cross-spec authoring — generating a parent spec from a set of child slices, or vice versa. Adjacent to <spec-parent> but a distinct workflow.
  • Extract /spectastic.plan — sibling slice. Pairs with this one and reuses the interview engine.
  • Extract /spectastic.tasks — also pairs naturally; deterministic generation from spec + plan.

4 · Data model

Four types this slice owns: SpecInput, SpecResult, InterviewPhase, and the re-exported Question shape from 006.

Entities

SpecInput
Fields: description: string (the user's feature description or, in re-entry mode, the spec ID), specId?: string (optional explicit ID; otherwise auto-assigned by scanning specs/), mode?: 'fresh' | 'reentry' (optional explicit mode; otherwise inferred — re-entry if the resolved spec.html exists, fresh otherwise).
SpecResult
Fields: html: string (the populated spec.html content, ready to write to disk), specId: string (the resolved ID, fresh or pre-existing), requirementsCount: number (count of <spec-requirement> elements in the result). The caller writes html to specs/<specId>/spec.html; the kernel never touches the filesystem.
InterviewPhase
An internal discriminated union: { kind: 'chat', prompt: string } for free-form narrative capture (consumed by ctx.ai.chat()) or { kind: 'decision', questions: Question[] } for bounded-choice anchoring (consumed by ctx.ai.ask<T>()). The verb sequences phases; the AIProvider materialises them in the consumer's surface (Claude Code tool call, MCP elicitation, VS Code quick-pick).
Question
Re-exported from @spectastic/core's main entry (defined by 006 FR-007). Shape mirrors Claude Code's AskUserQuestion: { question: string, header: string, options: { label: string, description: string }[], multiSelect?: boolean }. 1–4 questions per ask<T>() call; 2–4 options per question.

5 · Success criteria

Technology-agnostic, measurable outcomes.

A test under packages/core/test/spec.test.ts drives specCommand against a stub AIProvider scripted to mirror the answers a maintainer would give to a known fixture feature. The returned SpecResult.html is byte-identical (modulo trivial whitespace normalisation and the dynamic Created date) to the artifact today's /spectastic.spec would produce against the same scripted answers.

Re-entry mode against an existing spec.html fixture preserves every existing <spec-requirement id="…"> ID, every existing <spec-changelog> entry, and every existing <spec-question>. New requirements (if any) receive fresh IDs that do not collide with the existing set. No FR-ID is reused or renumbered.

Running node packages/cli/dist/index.js spec "test feature" in a clean temp workspace creates specs/001-test-feature/spec.html with no [PLACEHOLDER] tokens remaining, asset paths correctly rewritten to ../../assets/spec.css + ../../assets/spec.js, and spectastic validate specs/001-test-feature/spec.html returns zero findings.

pnpm bench passes all scenarios within their declared budgets. The init-help-cold-start p50 stays within ±20% of today's baseline (52 ms on CI) — proving the new spec subpath does not eagerly load HTML-generation or template-parsing dependencies onto the init path.

6 · Assumptions

Two preconditions: 006-kernel-extraction has shipped (with the AIProvider interface and a working Claude adapter), and the markdown procedure remains canonical.

006-kernel-extraction has shipped, including the AIProvider interface and a concrete Claude adapter sufficient for the CLI's spec subcommand to drive a real interview. If the Claude adapter is not yet ready when this slice implements, the CLI subcommand temporarily ships with a clearer "AI provider not yet wired" error; the kernel function itself is testable against a stub AIProvider regardless.

The canonical procedure for the spec interview remains commands/spectastic.spec.md; the kernel function summarises and points back via its docblock. Auto-generating the markdown from the docblock is explicitly out of scope per 006's decisions log.
