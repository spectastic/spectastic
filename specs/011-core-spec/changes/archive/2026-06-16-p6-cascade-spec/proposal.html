Gate invocation forms on destination state (cite P-6)

Mechanical application of newly-ratified P-6 to the spec verb's invocation gate. The most urgent of the four cascades — current behaviour silently overwrites Draft specs.

Status Applied Change ID 2026-06-16-p6-cascade-spec Spec 011-core-spec Source 011/T-001 · sibling of 2026-06-16-p6-draft-is-loose Author Brian Corbin · @briancorbinxyz Created 16 Jun 2026 Targets 1 modified (FR-003) Read time

FR-003 currently keys invocation behaviour off the argument shape (description-string → fresh; spec-id → re-entry). Per 011/T-001, this lets a fresh-mode invocation against a path with an existing Draft spec silently overwrite it (no flag, no signal). Per P-6, destination state — not argument shape — is the right gate. MODIFY FR-003 to consult <spec-status> on the resolved path before deciding to author / edit / refuse.

Gate invocation forms on destination state (cite P-6)

Applied

1 · Intent

One of four mechanical cascades from P-6. Of the four, this one matters most operationally: 011's current behaviour silently overwrites Draft specs the user may not have meant to discard (per 011/T-001's deep-dive — "silently overwrites" is more dangerous than 008's over-eager refuse, because there's no signal). MODIFY FR-003 to make destination state the gate, not the argument shape.

2 · Scope

In scope

  • MODIFY FR-003 to gate invocation behaviour on the resolved destination's <spec-status> per P-6.
  • Hotfix packages/cli/src/commands/spec.ts to read destination state before fs.writeFile.

Out of scope

  • FR-005's re-entry-mode protections for content preservation (preserves IDs / changelog entries; requires explicit confirmation for removals). Untouched — it governs the shape of re-entry, not whether re-entry triggers.
  • Removing the implicit argument-shape detection. Argument shape can still hint at the user's intent for prompt construction (fresh vs sharpen phrasing); it just no longer gates the destructive write.

3 · Approach

Single MODIFY on FR-003. The post-state preserves the two invocation forms (description-string for fresh authoring; spec-id for re-entry) but adds the destination-state gate as the actual decision point: a fresh path or Draft destination → author / edit in place; past-Draft destination → refuse with pointer to /spectastic.propose; --force override available. Argument shape becomes a prompt-construction hint, not a destructive gate.

4 · Deltas

What changes: Invocation behaviour gates on destination <spec-status> per P-6, not on argument shape; argument shape remains a prompt-construction hint.

@spectastic/cli MUST ship a spec subcommand with two invocation forms: spectastic spec "<feature-description>" (auto-assigns a Spec ID) and spectastic spec <existing-spec-id> (resolves specs/<spec-id>/spec.html). Regardless of invocation form, the subcommand MUST gate its destructive behaviour on the resolved destination's <spec-status> per P-6: a fresh path or Draft destination MUST be authored / edited in place (preserve existing IDs; append a one-line <spec-changelog> entry); a past-Draft destination (Accepted, In Review, Superseded, Deprecated, Blocked) MUST be refused with a typed error pointing at /spectastic.propose. A --force override MAY bypass the past-Draft refuse with a one-line warning that the operation skips the change-management surface. Argument shape MAY hint at the kernel's prompt construction (Sharpen-vs-Author phrasing) but MUST NOT be the gate for overwriting.

Rationale

Cascade of 011/T-001: the original FR-003's argument-shape-driven gate let a fresh-mode invocation silently overwrite a Draft spec at the resolved path. P-6 ratified destination-state as the right gate; this FR honours it. The "silently overwrites Draft" failure mode is more dangerous than 008's over-rigid refuse — no signal — which is why this cascade gets priority operationally.

5 · Risk register
