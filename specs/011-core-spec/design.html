Design · 011-core-spec

Core spec verb — implementation plan

How specCommand ships — a two-phase interview engine running on top of ai.chat() + ai.ask<T>(), fresh and re-entry modes from one code path, structured SpecResult for the caller to write.

Status Accepted Spec 011-core-spec Owner Brian Corbin · @briancorbinxyz Branch main (squashed-snapshot pattern) Created 16 Jun 2026 Read time

Extract /spectastic.spec into @spectastic/core/commands/spec per the 006 kernel contract; reuse ClaudeProvider from 007. Centrepiece: a two-phase interview engine alternating ai.chat() (narrative) + ai.ask<T>() (bounded choice), looping until a typed "complete?" ask returns done. Fresh and re-entry share the engine — re-entry parses the existing spec.html and restricts deltas to ADD / ENHANCE unless the user confirms removal. Kernel returns SpecResult { html, specId, requirementsCount, warnings }; caller writes to disk. Single PR; ships as v0.1.0-pre.13; bench-gated.

3 · Approach

Three moves, one PR. One: specCommand at packages/core/src/commands/spec.ts orchestrates an interview-engine helper that alternates chat (narrative slots) and ask<T>() (bounded choices), looping until a dedicated termination ask resolves. Two: reentry.ts parses an existing spec.html via parse5, snapshots the stable ID set + changelog + open-questions, and seeds the engine with an ADD-or-ENHANCE-only constraint; removals require explicit ask<T>() confirmation. Three: a spectastic spec CLI subcommand at packages/cli/src/commands/spec.ts handles argument parsing, ID assignment, directory creation, template copy with asset-path rewrite, and writing the kernel's HTML result to disk.

The interview engine is the architecturally-interesting piece. Today's slash-command runs inside Claude Code's conversation context; the kernel can't rely on that. specCommand builds an internal InterviewSession tracking filled narrative slots, anchored decisions, and open questions. Each loop iteration prompts the LLM via chat() with session state to choose the next phase + payload; the engine dispatches accordingly. Termination is its own typed commitment (D-005) — not a heuristic.

4 · Alternatives considered

OptionRobustnessSurface fitEffortTotal
Hard-coded question script (no LLM-driven sequencing)42410
Pure conversational chat() loop (no ask<T>())2349
LLM-driven phase sequencing + typed ask<T>() anchoring — chosen34310

The hard-coded script is deterministic but can't follow conversational threads or surface non-obvious questions the way the slash-command markdown intends. The pure chat() loop matches today's Claude-Code-only behaviour but defeats the point of ask<T>() — future MCP and VS Code surfaces would re-build bounded-choice UI from prose. The chosen approach uses chat() for phase sequencing and ask<T>() for commitments, preserving the discipline that decidable questions are typed commitments while letting non-Claude-Code surfaces render bounded choices natively.

5 · Decisions

D-001 · Two-phase interview as an explicit state machine

Status
Accepted
Context
The slash-command markdown sequences phases implicitly inside Claude Code's conversation context; the kernel must model sequencing explicitly.
Decision
Internal InterviewSession tracks filled slots, anchored decisions, open questions. Each loop iteration: ai.chat() with session state picks next phase; dispatch { kind: 'chat', prompt } → ai.chat() appends to slot, or { kind: 'decision', questions } → ai.ask<T>() records picks. LLM-driven alternation, not fixed.
Consequences
+ Mirrors slash-command discipline; + future surfaces receive typed phase events; + stub-AIProvider tests script the sequence deterministically. − Engine complexity sits in core; docblock must summarise faithfully.

D-002 · Re-entry detection and ADD/ENHANCE-only deltas

Status
Accepted
Context
FR-005 requires re-entry to preserve existing IDs and changelog entries; removals require explicit confirmation. The kernel needs structural enforcement, not prompt instructions alone.
Decision
reentry.ts parses the existing spec.html via parse5; snapshots { requirements: { id, level, html }[], changelog, openQuestions }. The engine receives the snapshot and is constrained to ADD (new requirement with fresh ID = max(existingIds) + 1) or ENHANCE (extend <details> rationale; id=, priority=, primary statement intact). REMOVE/OVERWRITE triggers dedicated ai.ask<T>() confirmation; default is preserve.
Consequences
+ ID-preservation is structural, not prompt-policed; + fresh-vs-re-entry diff is one conditional branch. − parse5 exercised at runtime (already present transitively); − malformed-existing-spec needs a clear error path.

D-003 · INVEST self-check generated as a final, dedicated phase

Status
Accepted
Context
FR-007 requires all six INVEST rows populated; V links to SC- ID; T links to acceptance or requirement; ✗ rows surface a warning.
Decision
After the main loop terminates, a dedicated INVEST pass batches 1–2 ai.ask<T>() calls (honouring the four-question limit), each offering "✓ — linkage" / "✗ — flag in warnings". V option set derives from actual SC-NNN IDs in the artifact; T spans acceptance scenarios + requirements. ✗ picks append to SpecResult.warnings.
Consequences
+ Linkage structurally validated (option sets derived from artifact); + warnings flow through typed result. − 1–2 extra ask calls in the trailing phase.

D-004 · Budget gauge — running word count, amber-band warning via SpecResult.warnings

Status
Accepted
Context
FR-008 requires a splitting nudge when the draft crosses 70% of <spec-budget>. The slash-command surfaces this conversationally; the kernel needs a typed channel.
Decision
After each ENHANCE/ADD delta, the engine strips HTML tags and recomputes the word count. Crossing 70% fires one ai.ask<T>(): (a) move material to <spec-out-of-scope> with defer-to="TBD-<topic>", (b) scaffold sibling spec (recorded in warnings), (c) acknowledge and proceed. The crossing also unconditionally appends to SpecResult.warnings.
Consequences
+ Splitting discipline reaches non-Claude-Code surfaces; + caller chooses the rendering. − O(n) recomputation per delta; n stays small.

D-005 · Interview termination via a dedicated ask<T>() "complete?" question

Status
Accepted
Context
"Decision exhaustion" is the bound in CLAUDE.md's interview discipline. Pure heuristics over/undershoot; pure LLM judgement risks runaway loops.
Decision
Past a minimum of three iterations, the engine fires ai.ask<T>() with two options: "Continue — a careful reviewer would still surface a non-obvious question" or "Complete — every decidable question is anchored." Continue is the recommended default; complete advances to the INVEST pass. A 24-iteration hard ceiling backstops pathological loops and appends a warning.
Consequences
+ Termination is a typed commitment, matching the discipline's framing. − One ask call per iteration past the minimum; ceiling is a backstop.

D-006 · User-story extraction from chat — structured prompt + JSON parse

Status
Accepted
Context
Chat captures user-story prose; the artifact requires structured As a / I want to / so that triples. Deriving them is an LLM task.
Decision
After user-story chat capture, one ai.chat() call with a structured-prompt + JSON instruction (matching 007 D-002) extracts the triples as [{ role, action, outcome }]. Parse, retry once with stricter system prompt; both-failure path appends a warning, doesn't block. Each triple becomes a US-N block.
Consequences
+ Reuses 007's proven JSON-parse-with-retry pattern; + structured triples enable a later per-story priority ask. − Two-call worst case; − parse failure degrades to warning.

D-007 · Smallest-demoable as the first decision-phase question — always, fresh mode

Status
Accepted
Context
FR-006 mandates smallest-demoable as the first decision-phase question in fresh mode. LLM-driven sequencing could defer it; the spec says it can't.
Decision
Fresh-mode's first decision iteration is hard-coded: one ai.ask<T>() with three options derived from input.description via a one-shot chat(). If an option reaches for "the whole feature" wording, a follow-up ai.ask<T>() offers 2–3 narrower framings (FR-006's SHOULD). Re-entry skips this — the boundary is set.
Consequences
+ FR-006 structurally enforced; + SHOULD-tier follow-up is concrete. − One hard-coded branch in an LLM-driven loop; isolated to the first iteration.

D-008 · Single-PR migration, bench-gated, v0.1.0-pre.13

Status
Accepted
Context
The slice lands verb + CLI subcommand + markdown update + the first heavy exercise of ai.ask<T>(). Staging adds version coordination without reducing review scope.
Decision
Single PR per 006/007 precedent (their D-008). Ships as v0.1.0-pre.13. Bench enforces lazy-loading (spec.ts stays off init path); CLI tests prove wiring; npm view confirms the slice.
Consequences
+ Atomic; + reverts cleanly. − Larger diff than typical; bench/test failure blocks the whole slice.

8 · Complexity tracking

Two deliberate additions warrant flagging:

LLM-driven phase sequencing (D-001) instead of fixed alternation. Adds engine complexity — the loop queries the LLM for "what next?" rather than walking a script. Justified: the slash-command discipline is exactly this — the human picks the next probe based on what's missing, not a fixed order. A scripted alternation over-asks (every slot mechanically) or under-asks (misses non-obvious follow-ups). Debuggability cost addressed by snapshotting phase sequences in unit tests.

INVEST pass as a dedicated trailing phase (D-003), not inline. Could fold into the main loop; the trailing pass costs 1–2 extra calls. Justified because FR-007's linkage (V → SC-NNN, T → acceptance|FR) requires the artifact substantively complete before the question is well-posed — option sets derive from generated IDs that don't exist mid-interview.
