AI provider injection point for deterministic CI

A stub AIProvider routed via env var so CI integration tests assert on real generated artifacts without burning API spend or losing determinism to small-model drift.

1 · Context

The CLI integration tests shipped in 15514a3 cover the deterministic surface of all 8 verb subcommands: state-gate behaviour per P-6 (refuse / edit-in-place / --force), error paths, arg validation. For the 6 AI-using verbs (triage, principles, tasks, spec, plan, propose) the tests stop short of happy-path coverage — they assert that the CLI reaches the AI layer (via the "ANTHROPIC_API_KEY is not set" error when the env var is empty) but can't assert on the actual generated artifact without a real LLM call.

Real-LLM CI was considered and rejected. The full reasoning lives in the project's feedback-ai-in-ci-uses-stubs memory; the summary: small models (Gemma 2 2B at q4 fits GitHub Actions' 7GB easily) intermittently produce malformed JSON / drop closing braces / pick slightly different phrasings even at temperature=0, turning every failing test into "is this a real regression or just the model being non-deterministic." Claude in CI burns API spend per push and leaks the key to forked PRs. Stub providers with hand-curated responses are deterministic, fast, and catch the regressions integration tests are meant to catch (prompt-format drift, parse-shape breakage, wiring bugs).

The load-bearing piece is the injection point itself. Once a stub provider can be injected via env var, the surface unlocks two follow-on slices that are out of scope here: per-verb stub-using happy-path tests can extend coverage to specific output shapes, and a separate pnpm test:smoke tier can run the same tests against real Claude (or an Ollama provider, when one exists) for local pre-tag verification.

2 · User scenarios & testing

Each story is independently testable.

US1 · Test author writes a deterministic integration test P1

As a test author building integration coverage for an AI-using verb, I want to point the CLI at a JSON script of canned responses so that my test asserts on the actual generated artifact without an API key.

Acceptance: Setting SPECTASTIC_AI_STUB=path/to/script.json in the spawned process's environment routes the CLI's AI calls through StubAIProvider, which consumes responses from the script's chat / ask / subagent arrays sequentially. The test asserts on real CLI output (exit code, summary stdout, generated file contents).

US2 · CI runs the same tests deterministically P1

As a CI maintainer, I want the integration tests to use the stub by default so that the suite stays fast, deterministic, and doesn't burn API spend or leak keys to forked PRs.

Acceptance: Test fixtures in the repository under packages/cli/test/fixtures/ ship as committed JSON files. CI runs pnpm vitest run with SPECTASTIC_AI_STUB set per test; suite passes deterministically with no real LLM call.

US3 · Stub surfaces script gaps loudly P2

As a test author debugging a failing fixture, I want the stub to throw a descriptive error naming the method + invocation count when the script runs out of responses so that I don't waste time debugging a phantom LLM-side bug — the message tells me to extend the script.

Acceptance: When a CLI test invokes the stub N + 1 times against a script defining N responses for that method, the thrown StubAIProviderError's .message names the method (chat / ask / subagent), the invocation count (N + 1), and the script's defined count (N).

Edge cases

Tracked failure modes the stub handles
  • Stub script malformed JSON — constructor throws StubAIProviderError naming the parse failure + file path. Test surfaces the path so the author knows which fixture to fix.
  • Stub script schema mismatch (e.g. chat is not an array of strings, ask entries are not flat string-valued objects) — schema validator throws StubAIProviderError naming the offending path (chat[2], ask[0].Header, etc.). Validated at load time, not lazily on first call.
  • Stub script missing a section (e.g. only chat defined) — missing sections default to empty arrays; overflow throws on first attempt to use that section.
  • SPECTASTIC_AI_STUB set to a missing file — constructor throws StubAIProviderError naming the path.
  • SPECTASTIC_AI_STUB unset — factory falls through to ClaudeProvider; production behaviour unchanged.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

StubAIProvider MUST live at packages/core/src/providers/stub.ts and be exported on its own subpath (@spectastic/core/providers/stub) per the lazy-loading discipline in 006 FR-002. The package's main entry MUST NOT eagerly load it.

StubAIProvider MUST implement the AIProvider interface (chat, ask<T>, subagent) from @spectastic/core as a complete drop-in for ClaudeProvider — no method may be a no-op or "not implemented" throw.

The constructor MUST accept either (a) a filesystem path to a JSON script or (b) an inline StubScript object. Both paths produce a fully-loaded, validated provider; inline construction supports unit tests that don't want to touch disk.

The script schema MUST be: { chat?: string[], ask?: Record<string,string>[], subagent?: { output: string }[] }. Missing top-level sections MUST default to empty arrays. Each method consumes its corresponding array sequentially per call.

The script MUST be validated against the schema in FR-004 at construction time (load-time), not lazily on first call. A schema mismatch MUST throw StubAIProviderError whose .message names the offending JSON path (e.g. chat[2], ask[0].Header).

Rationale

Load-time validation surfaces fixture mistakes loudly, before the test runs. Lazy validation would let a malformed script silently pass the first few calls and only fail when an unrelated path is exercised — much harder to debug.

Sequential consumption per method: the Nth call to chat returns script.chat[N-1]. Overflow (the script defines fewer responses than the test invokes) MUST throw StubAIProviderError whose .message names the method, the invocation count, and the script's defined count.

@spectastic/cli MUST gain a new module at packages/cli/src/ai-factory.ts exporting async function createAIProvider(): Promise<AIProvider>. The factory MUST route to StubAIProvider when process.env.SPECTASTIC_AI_STUB is set (passing the env-var value as the script path); otherwise it falls through to ClaudeProvider.

Both branches of createAIProvider() MUST be lazy-loaded — the factory MUST NOT top-level-import either ClaudeProvider or StubAIProvider. The factory module itself MUST be lazy-imported inside each CLI verb's .action() handler (matching the existing pattern for command imports).

The 6 AI-using verb CLI subcommands — principles, tasks, plan, spec, propose, triage — MUST be wired through createAIProvider(). No remaining direct new ClaudeProvider() calls may appear in packages/cli/src/commands/.

Each of the 6 AI-using verbs MUST gain exactly one stub-driven happy-path integration test in its packages/cli/test/<verb>.integration.test.ts file. Each test MUST set SPECTASTIC_AI_STUB to a fixture script path and assert on the real generated artifact's structural shape (title / IDs / status pill / version field as applicable to the verb).

The stub provider MUST ship with kernel-level unit tests at packages/core/test/stub-provider.test.ts covering: sequential consumption per method, overflow error shape, file-path constructor, inline-object constructor, missing-file error, malformed-JSON error, schema-mismatch error.

Non-functional

The injection point MUST NOT regress any scenario in bench/baselines.json past its declared budget. The init-help-cold-start scenario (150 ms budget) is the explicit guard against eager-loading either provider through the factory.

Stub-script load + first chat response SHOULD complete in under 10 ms in-process. This is a trivial JSON.parse + shape walk + array access; it exists as a quantified budget so test latency from a thousand-call script stays sub-second.

Out of scope (deferred to other slices)

  • A pnpm test:smoke script that re-runs the integration tests against real Claude when ANTHROPIC_API_KEY is set. The injection-point + per-verb tests this slice ships are the foundation; the smoke runner is a separate slice.
  • An OllamaProvider class for the smoke tier (local-only prompt-iteration testing against Gemma / Llama / etc.). Same shape as ClaudeProvider; lands when the smoke tier needs it.
  • A recording mode that captures real Claude responses into a stub script for fixture seeding. Useful for bootstrapping a new verb's fixture; not load-bearing for this slice.
  • Hot-reload of the stub script while a test is running. Test fixtures are static.
  • Per-prompt response matching (vs sequential consumption). Sequential keeps test scripts trivially writable; matching adds combinatorial complexity for zero gain in fixture-driven tests.

4 · Data model

One new interface (StubScript) and one new error class (StubAIProviderError) are added to @spectastic/core/providers/stub. No changes to existing types.

Entities

StubScript
Script object loaded from JSON. Fields:
  • chat?: string[] — array of raw responses for chat(); consumed sequentially.
  • ask?: Record<string, string>[] — array of answer objects for ask<T>(); each object's keys correspond to question headers, values are selected option labels.
  • subagent?: { output: string }[] — array of subagent results for subagent(); each object has the same shape as SubagentResult from @spectastic/core.
StubAIProviderError
Subclass of Error with .name === 'StubAIProviderError'. Thrown for: file read failure, JSON parse failure, schema validation failure (includes the offending JSON path in .message), method overflow (includes the method name + invocation count + script size in .message).

The validator MUST be hand-rolled (per propose-time decision: no Zod dependency added). Roughly 30 lines of pure TypeScript walking the parsed object, checking types per the schema in FR-004. The hand-rolled choice keeps the package dependency surface minimal — Zod's ~70KB doesn't earn its weight for a schema this narrow.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

Running each of the 6 AI-using verbs' integration tests with SPECTASTIC_AI_STUB set to its fixture script produces the expected generated artifact, asserted on by structural checks (title contains expected project / spec ID; element IDs present; status pill matches expected lifecycle state; version field matches FR-008 of 008 where applicable). Suite passes pnpm vitest run with no real LLM call.

Removing SPECTASTIC_AI_STUB from the test process's environment causes the CLI to attempt a real Claude call and fail on the missing API key — proves the factory routes correctly to ClaudeProvider when the stub var is unset.

A stub script that overflows (N + 1 invocations against a script defining N responses) produces a StubAIProviderError whose .message names both the method (chat / ask / subagent) and the call count vs script size, observable via the failing test's stderr.

6 · Assumptions

The AIProvider interface declared in @spectastic/core's types.ts is stable enough that a drop-in stub doesn't drift away from ClaudeProvider. If the interface gains a new method (e.g. stream()), this slice's stub will need an additive method; that's a small follow-up.

JSON files are the right fixture format. Alternatives (YAML, TypeScript, function-returning-script) were considered but rejected: JSON is trivially editable, doesn't need a parser dep, surfaces cleanly in git diff, and lets fixtures be written by hand without compilation.
