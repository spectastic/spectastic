Implementation plan · 015-ai-stub-injection

AI provider injection point for deterministic CI

How we will build it.

Status Accepted Spec 015-ai-stub-injection Owner Brian Corbin · @briancorbinxyz Branch main (squashed-snapshot pattern) Created 17 Jun 2026 Read time

One new class (StubAIProvider), one new module (ai-factory.ts), one new hand-rolled validator (validateStubScript) + a six-file fixture set, wired through six CLI verb subcommands. Most of the surface lives in staging from the pre-spec implementation (commit 9ed455e, soft-reset); the spec sharpened scope to add load-time validation (FR-005) and per-verb happy-path tests (FR-010) beyond the principles demo. Single biggest risk: fixture drift — if a verb's prompt structure changes the script breaks the test as a false positive. Mitigated by colocation (fixtures + tests + verb impl all touched in one PR when prompts evolve).

3 · Approach

Add one new subpath (@spectastic/core/providers/stub) exporting StubAIProvider + StubAIProviderError + the hand-rolled validateStubScript walker. Constructor accepts either a file path or an inline StubScript; both paths run the validator before storing the script. Sequential consumption per method; overflow throws a descriptive error.

Add one new CLI module (packages/cli/src/ai-factory.ts) exporting createAIProvider(), which checks process.env.SPECTASTIC_AI_STUB and lazy-imports either the stub or Claude. Each of the six AI-using verb CLIs (principles, tasks, plan, spec, propose, triage) drops its direct ClaudeProvider construction in favour of createAIProvider(). The factory itself is lazy-imported inside each verb's .action() handler (matching the existing pattern for kernel command imports), so the cold-start path is unchanged.

Per-verb fixture scripts live at packages/cli/test/fixtures/<verb>-script.json. Each AI-using verb's integration test gains one happy-path case that sets SPECTASTIC_AI_STUB to its fixture's path and asserts on the generated artifact's structural shape.

5 · Decisions

D-001 · Hand-rolled recursive validator with JSON-path errors

Status
Accepted
Context
FR-005 demands load-time schema validation; the script schema is three top-level keys with simple shapes. Zod was considered (see §4) but its ~70 KB and dep-graph addition don't earn their keep.
Decision
One function: validateStubScript(parsed: unknown, path = ''): asserts parsed is StubScript. Recursive walk through the parsed object; throws StubAIProviderError with the offending JSON path (e.g. chat[2], ask[0].Header) on first mismatch. ~30 lines TS.
Consequences
+ No new dep; bundle size unchanged.
+ Error messages name the failure site precisely.
− If the script schema grows beyond ~5 keys with branching shapes, the hand-rolled walker becomes harder to maintain than a Zod schema. Revisit if that happens.

D-002 · Central createAIProvider() factory with env-var routing

Status
Accepted
Context
FR-006/007/008 require both stub and Claude to be reachable from the CLI, lazy-loaded, with selection driven by SPECTASTIC_AI_STUB. Alternatives: per-verb env-var checks (DRY violation, missing-check bugs), or two separate helpers (createClaudeProvider + createStubProvider) called from each verb's own switch (same problem).
Decision
One module: packages/cli/src/ai-factory.ts exporting async function createAIProvider(): Promise<AIProvider>. Reads process.env.SPECTASTIC_AI_STUB; lazy-imports the matching provider. Each verb's .action handler lazy-imports the factory module itself; both provider modules stay off the cold-start path.
Consequences
+ One canonical injection point — adding a new provider class later (Ollama, mock) is one-line in this module.
+ Lazy-load chain preserved end-to-end; init-help-cold-start bench untouched.
− The env var is implicit — easy to forget to set in a new test. Mitigated by clear test-file authoring pattern + the FR-009 audit (no remaining new ClaudeProvider() in verb commands).

D-003 · Sequential consumption with descriptive overflow errors

Status
Accepted
Context
FR-006 mandates sequential consumption; "per-prompt response matching" was rejected at spec time as combinatorial complexity without benefit for fixture-driven tests. Overflow needs to surface loudly so a stale fixture doesn't masquerade as an LLM-side bug.
Decision
Each method holds a private index; the Nth call returns array element [N-1] and increments. Overflow throws StubAIProviderError with the method name (chat / ask / subagent), the invocation count, and the script's defined count. No wraparound; no retries.
Consequences
+ Fixture authoring is trivial: list responses in expected call order.
+ Overflow errors point directly at the fix (extend the array).
− Test author must know the verb's exact call order — but that's the contract the test is verifying anyway. If a verb's call order changes, the test failing on overflow IS the regression signal.

D-004 · Separate JSON fixture files per verb

Status
Accepted
Context
FR-010 mandates one happy-path test per AI-using verb. Two layouts considered: separate .json files at packages/cli/test/fixtures/<verb>-script.json vs inline-via-writeFileSync within the test (the shape already used by the principles demo).
Decision
Separate files at packages/cli/test/fixtures/<verb>-script.json. The principles demo (currently inline) refactors to the file pattern as part of this slice. Fixtures are read at test setup; tests reference them by relative path.
Consequences
+ Fixtures are diff-able in isolation; reviewing a fixture change doesn't require parsing test code.
+ Fixtures are shareable across tests if a verb gains a second happy-path variant later.
− More files (one per verb); a fixtures/ dir to maintain. Acceptable tradeoff at six files.

7 · Risks & mitigations

RiskLikelihoodImpactMitigation
Fixture drift — a verb's prompt structure or call order changes, breaking the fixture as a false-positive test failure. MM Fixtures + tests + verb impl all touched in one PR when prompts evolve. Overflow error message points directly at the fix. Treat fixture failures as "investigate the prompt change" before "investigate the test."
ask<T>() shape mismatch — propose / spec / plan invoke ask() with N questions; fixture must provide an answer object whose keys match the question headers exactly, or the kernel's downstream parsing fails. ML StubAIProvider's ask() doesn't validate against the questions array (sequential consumption, not key-matching). If the kernel rejects the fixture's answer (missing key, wrong shape), the verb's existing error path surfaces it in the test stderr. Fixture author iterates.
Subagent JSON-in-output validity — propose's adversarial pass parses critic output as JSON; fixture must put valid JSON inside the output string. Doubly-escaped JSON inside JSON is easy to get wrong. LL Document the fixture format in fixtures/propose-script.json with an inline comment-style schema example at the top of the file (JSON doesn't support comments; use a leading key like "_doc"). Validator skips unknown top-level keys to leave room for this.

8 · Complexity tracking

The staged implementation from commit 9ed455e (soft-reset to author this spec first) is the starting point for the impl tasks. The tasks list explicitly reuses that code where it matches the spec and sharpens / adds where the spec went further (FR-005 load-time validation; FR-010 per-verb tests). Treating it as starting state rather than ground-up rewrite saves ~80% of the work without skipping the spec/plan discipline.
