Hybrid corpus citation

Applied

1 · Intent

The 051 two-layer-identity amendment fixed where a corpus id lives — a pack owns a slug, the project owns an opaque KB-NNNN in a root registry. The citation contract (FR-002) still describes the old flat KB-NNN@edition that resolved against the loaded packs by array order — the exact non-determinism the split exists to end. This amendment is the citation half: a citation names the project's KB-NNNN and resolves against the one registry, so a given citation always lands on exactly one document.

Two clarifications ride with it, both from the considerations brief. The @edition pins the document edition (a source's provenance date), never the marketplace plugin version that anchors a re-import — conflating them would make the pin meaningless. And because the token is deliberately opaque (no pack or reference name, so a rename can't rot it), a render layer surfaces the human label from the registry so the citation still reads at its site — the hybrid.

2 · Scope

In scope

  • MODIFY FR-002 — the citation is KB-NNNN@edition, resolving against the root registry (repo-unique, deterministic); @edition pins the document edition, not the marketplace plugin version; a bare KB-NNNN still SHOULD warn.
  • ADD FR-006 (should) — a render / validate layer surfaces the reference's human label (marketplace · plugin · slug) from the registry row beside the opaque token.
  • MODIFY SC-001 — re-word the must-tier acceptance from the pack-resolved KB-001@edition demonstration to the registry-resolved KB-NNNN@edition world.

Out of scope

  • Flipping resolution to registry-only (dropping the pack-scan fallback) and re-pointing every existing KB-NNN@edition citation to its new KB-NNNN — the migration slice, alongside the pack re-authoring.
  • The corpus import command that populates the registry a citation now resolves against — this amendment consumes the registry (051 FR-009); that spec builds what fills it.
  • The validate gates that a cited id resolves and a pinned edition is current — 053's contract, unchanged in shape by this amendment (they resolve via the same updated resolver).

3 · Approach

The hybrid keeps two properties that pull against each other. Stable: the token is an opaque KB-NNNN — no embedded name, so a pack or reference rename never rots a live citation (the persistent- identifier rule the brief draws from DOI/PID practice). Legible: a reader at the citation site still needs to know what KB-0007 is — so the label (finance-settlement · settlement-windows) is derived at render / validate time from the registry row, never stored in the token. The id resolves; the label is a view over the resolution.

Like the 051 amendment, this is scoped non-breaking: the resolver gains registry-first resolution but keeps its existing pack-scan as a fallback, so a repo whose citations haven't migrated yet still resolves exactly as today. Dropping the fallback and re-pointing existing citations is the migration slice — so applying this adds no new finding to the shipped corpus. The citation grammar itself is unchanged (KB-\d{3,} already admits the four-digit baseline); only resolution semantics and the rendered label are new.

4 · Deltas

One MODIFY + one ADD, both within 052's FR-* topic.

What changes: the flat KB-NNN@edition (resolved by pack array order) becomes an opaque KB-NNNN@edition resolved against the root registry, with @edition pinned to the document edition (not the marketplace version).

A corpus citation MUST take the form KB-NNNN@edition — the project-assigned, opaque KB-NNNN (051 FR-002) pinned to the edition the claim was grounded against. The citation MUST resolve against the project's root knowledge/index.md registry (051 FR-009), where the KB-NNNN is repo-unique — so resolution is deterministic, ending the array-order ambiguity a per-pack KB-NNN produced when two packs shared an id. The @edition MUST pin the document edition (the referenced document's provenance edition, FR-003), MUST NOT be the source marketplace's plugin version — the two are different axes (a plugin release need not change a document's edition, and an edition can change without one). A bare KB-NNNN without an @edition SHOULD warn. The id grammar (KB-\d{3,}) is unchanged; KB-NNNN (four digits) is the baseline.

Rationale

The scholarly "as of" access date, made machine-checkable — and now unambiguous: the pin resolves against the one repo-unique registry rather than whichever pack loaded first. Keeping @edition the document edition (not the plugin version) is the brief's edition-vs-version distinction: a version bump that leaves a document's text untouched must not appear to change what a decision read.

What changes: the must-tier acceptance still demonstrates the old pack-scoped KB-001@edition; re-word it to the registry-resolved KB-NNNN@edition world so the criterion proves the amended FR-002, not the model it retires.

A plan decision citing a corpus reference by its project-assigned KB-NNNN@edition renders the verified (green) grounded state, the citation resolves against the root knowledge/index.md registry to exactly one document, and the edition-pinned form is confirmed well-formed.

A tool that renders or validates a corpus citation SHOULD surface the reference's human label — its source marketplace, plugin, and slug (or its title) from the root-registry row — beside the opaque KB-NNNN@edition token, so a citation reads at its site without a mutable name in the id. The label MUST be derived at render / validate time from the registry, never stored in the token (the persistent-identifier rule: no semantic meaning in the id, so a rename cannot rot a citation). Where the registry is absent or has no matching row — a plain-agent context with no spectastic present, or a project whose corpus has not been imported yet — the label derivation is a no-op and the token renders opaque, which is acceptable: in a plain-agent context there are no spectastic citations to render (the binding is harness-side, FR-004), and before an import there is no row to draw a label from. The label lands ahead of the ingester that fills the registry (TBD-corpus-root-index-ingester) deliberately, as the contract for how a resolved citation reads — exactly as 051's registry convention landed ahead of its ingester.

Rationale

Resolves the tension a stable id creates: an opaque token is rename-proof but unreadable, and a readable token (a baked-in name) rots. Deriving the label from the registry at render time gets both — the citation is stable in the artifact and legible to the reader. should, not must: resolution (FR-002) is what correctness needs; the label is a readability affordance, and one only a spectastic repo with a registry present can offer.

5 · Risk register

The adversarial pass ran (the amendment touches a must-tier requirement). One <spec-risk> per finding; status="identified" until dispositioned. Apply refuses while any remain identified.

FR-002 makes it a MUST that a citation "resolve against the root registry," but the original tasks only touched the resolver and left the 053 grounding gate calling resolveCitation(packs, citation) with no registry — so a compliant new-model KB-0007@edition would get a false unresolved/provenance error (packs no longer carry a KB-NNNN, per 051 FR-004).

§Approach "the resolver gains registry-first resolution but keeps its existing pack-scan as a fallback … every current caller is unaffected" — the "unaffected" design is exactly what left the enforcement path unregistered.

Mitigated by revision. Added a §6 task threading the loaded registry through corpusGroundingFindings and its CLI scanCorpusGrounding wrapper, so the gate resolves the way FR-002 mandates. Still additive/non-breaking — an empty or absent registry falls back to the pack-scan, and no new-model citation exists to false-error on until the ingester populates the registry — so this apply changes no shipped citation's behaviour while making the MUST honoured by construction once a row exists.

The amendment MODIFYs FR-002 but the must-tier SC-001 still demonstrates the retired model — a pack-resolved three-digit KB-001@2024-05-28 — so the spec's own proof of FR-002 certifies the model FR-002 is replacing (the identical stale-sibling class the 051 amendment's SC-001 hit).

Live SC-001: "A plan decision citing KB-001@2024-05-28 renders the verified (green) grounded state…"

Mitigated by revision. Added a MODIFY SC-001 delta re-wording the acceptance to a registry-resolved KB-NNNN@edition, plus a §6 prose-reconciliation task for the matching non-requirement text (the smallest-demoable, US1/US2 acceptance, the TL;DR, the §4 data-model entity) — mirroring exactly what the 051 amendment did for its own SC-001.

FR-006 (the render label) reads from a registry whose populating ingester this same proposal defers out-of-scope, so it lands ahead of what fills it and can be exercised end-to-end by nothing in the repo yet — a should-tier UX affordance bundled with a must-tier resolution-contract change.

§Scope out-of-scope "The corpus import command that populates the registry … that spec builds what fills it," directly against the in-scope FR-006 that consumes those rows.

Mitigated by revision (kept, scoped). FR-006's wording now states plainly that the label derivation is a no-op until a registry row exists, and that it lands ahead of the ingester deliberately — as the contract for how a resolved citation reads, exactly as 051's registry convention (FR-009) landed ahead of its ingester. The considerations brief (D-003) bundles the opaque token and its rendered label as one decision — "the hybrid" — so the citation-contract spec is its right home; the should tier keeps it from firing as a gap where no registry is present.
