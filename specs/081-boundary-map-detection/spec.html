Boundary map detection

Where a project already names its own rings, read them. Do not invent a second vocabulary beside the one it maintains.

Status Accepted Spec ID 081-boundary-map-detection Owner Brian Corbin · @briancorbinxyz Reviewers — Created 02 Aug 2026 Principlesv1.9.0 Smallest demoableA project with tag-based module rules is read, and its named units and permitted directions are printed back. Read time

079 gives units and the edges between them. It does not say which units are allowed to depend on which — the arrangement a change has to respect when the question is "domain, service, or neither". Projects that care about this already declare it, in a boundary configuration they maintain for their own linter. This reads that declaration rather than asking anyone to restate it. Only positive forms are in scope: maps that name their units and the permitted directions between them. Forbidden-edge configurations are recorded as a known gap, because a rule that only says what may not happen is structurally silent about a destination that does not exist yet — which is precisely the case a placement question is hardest on. 1 · Context

The estate's detection convention is to read the declaration an ecosystem already makes rather than to ask for a new one: the coverage category detects a configured threshold, not a coverage library; contract-first detects a checked-in contract, not a web framework. The same move is available for architectural boundaries, because a project that enforces its rings maintains a configuration that names them — and it maintains it for its own reasons, so it stays current.

Two findings shape the scope. The tools split on form: some name their units and the permitted directions between them, while others only forbid specific edges over path patterns. Only the first answers "where does this go" — a forbidden-edge list can rule a destination out but cannot enumerate the destinations, and it says nothing at all about a directory that does not exist yet. This repository is itself an example of the weaker form, and of something more useful: its single rule encodes a pairwise package edge, which is 079's relation, not a ring map.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Read the rings a project already declares P1

As a tool, I want to read a project's declared boundary map so that I know the named units and which may depend on which without asking anyone to restate it.

Acceptance: given a project with a tag-based module-boundary configuration, the detected map lists its named units and the permitted directions. A project with no such configuration yields no map, not an empty one.

US2 · Be told when the declaration cannot answer the question P2

As a reviewer, I want a project whose only boundary configuration is a forbidden-edge list to be reported as unmapped so that I am not shown a partial order dressed up as a ring map.

Acceptance: a project carrying only forbidden-edge rules reports no map and states why. It is not an error, and it is not silence.

Edge cases

  • A project declaring both a positive map and forbidden edges — the positive map is the map; the forbidden edges are not merged into it.
  • A configuration that names units but declares no constraints between them: a legal map with no directions, distinct from no map.
  • A map whose named units do not correspond to any unit 079 resolves. Reported, not reconciled — the two vocabularies are allowed to differ.
  • A malformed or unparseable boundary configuration: no map, never a crash.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

Detection MUST read a project's declared positive boundary map — one that names its units and the permitted directions between them — where the project maintains one.

Rationale

The project already maintains this for its own linter, so it is current by construction. Asking for a restatement would create a second vocabulary to drift against the first.

Detection MUST NOT derive a boundary map from a configuration that only forbids edges, and MUST report such a project as having no map together with the reason.

Rationale

A forbidden-edge list yields at best a partial order over paths that already exist, and is silent by construction about a destination that does not — the exact case a placement question is hardest on. Presenting that as a map would let it appear to answer a question it structurally cannot.

A detected map MUST be informational: no enforcement decision MUST be derived from its presence, absence, or content.

Rationale

P-14 records that this judgment is review-caught rather than machine-enforceable, and 075 refused a neighbouring layer check for the same reason. Gating here would contradict both and newly gap projects for an architecture the tool cannot actually evaluate.

Where a project declares both a positive map and forbidden edges, the positive map MUST be reported as the map, and the forbidden edges MUST NOT be merged into it.

A map naming units that do not correspond to any unit resolved by 079 SHOULD be reported as-is rather than reconciled or discarded.

Rationale

A boundary vocabulary is the project's own and need not match the unit vocabulary; forcing a reconciliation would either drop real information or invent a correspondence nobody declared.

A malformed or unreadable boundary configuration MUST yield no map, and MUST NOT raise.

Non-functional

Detection MUST make at most 0 network calls, write at most 0 files, and complete within the existing detection budget of under 500 ms.

Rationale

This runs alongside the enforcement detector on ordinary invocations, so it must not widen the cost of a routine run.

Detection MUST read a bounded set of conventional configuration locations rather than searching the tree: at most 0 unbounded recursive scans.

Rationale

The same bound the contract detector holds. Unbounded recursion is how a detector's cost becomes a function of repository size rather than of convention.

Out of scope (deferred to other slices)

  • Enforcing a declared boundary map. Already planted by the agent-architecture survey as the P-8 guarantee half; this slice is its detection-side companion, not a replacement.
  • Deriving a usable partial order from forbidden-edge configurations, including this repository's own — recorded as a gap by FR-002 rather than half-supported.
  • Authoring a boundary map for a project that has none. Detection reads what exists; asking a project to declare rings it has not adopted is a different question.
  • Using a detected map as evidence in a placement decision.

4 · Data model

One entity, and the deliberate distinction between two ways of having none.

Entities

Boundary map
A project's declared arrangement of its own units: a set of named units, and the permitted dependency directions between them. A map may name units and declare no directions between them; that is a map with no constraints, and it is not the same as having no map.

Three states, and conflating any two of them loses the information this slice exists to carry: a map (the project names its rings), no map (the project declares nothing about them), and unmapped-by-form (the project declares boundaries, but only as forbidden edges, which cannot enumerate destinations). The third is the one a reader most needs distinguished, because it is the case where a project believes it has declared its architecture and the tool cannot use what it declared.

5 · Success criteria

Technology-agnostic, measurable outcomes.

A project maintaining a positive boundary configuration has its named units and permitted directions read with at most 0 additional authored files.

A project whose only boundary configuration forbids edges is reported as unmapped with a stated reason, and contributes at most 0 derived directions.

Across the full fixture set, a detected boundary map changes at most 0 enforcement verdicts.

A malformed boundary configuration produces at most 0 raised errors and at most 0 maps.

6 · Assumptions

A project that cares about its boundaries enough for a tool to route by them has already configured a linter to enforce them. Projects that maintain the arrangement only in prose are out of reach here, and that is accepted.

Boundary configurations live at conventional, nameable locations per ecosystem — the same assumption the contract detector already makes, and the reason NFR-002's bound is affordable.
