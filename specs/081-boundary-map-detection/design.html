5 · Approach

The two formats look incompatible and are not. Nx gives a set of tags and a set of allowed tag-to-tag pairs. import-linter gives an ordered list where lower may not import higher. Expand the ordering — each layer may depend on every layer below it — and it becomes exactly the same thing: named units, and the directed pairs permitted between them. Nothing is lost, because the ordering was the constraint. That common denominator is what a consumer can reason about without knowing which linter produced it.

The awkward part is where Nx keeps its constraints. They live either in an ESLint config or in nx.json, under two different key names, while tags live in either project.json or a package.json sub-key. Reading only nx.json — the obvious guess — would miss the more common form entirely and silently report no map for a project that plainly has one. So detection reads the bounded set of named locations, and treats a partial read as no map rather than a partial one.

An ESLint config is JavaScript, and this project does not execute artifacts it reads (P-11). The constraint block is JSON-shaped, so it is extracted textually; when that fails, the answer is no map. That is the right failure direction for something explicitly informational — a wrong map would mislead a placement verdict, while a missing one merely leaves it with less evidence.

7 · Decisions

D-001 · Detect Nx and import-linter, the two positive forms

Status
Accepted
Context
FR-001 scopes to positive maps — those naming their units. Nx and import-linter are the two mainstream instances, one per major ecosystem, and their shapes differ enough that supporting only one would let the internal representation quietly become whatever that one emits.
Decision
Read both. Nx from its bounded set of locations; import-linter from setup.cfg or .importlinter.
Consequences
+ The normalisation in D-002 is forced to be genuine rather than shaped by a single source. + Covers the JS and Python sides of the category the spec scopes to. − Two formats is more surface than one, and Nx's is more scattered than it first appears. − Neither can be verified against a real project in this repository; both rest on fixtures built from the documented shapes.

D-002 · Normalise to named units plus permitted directed pairs

Status
Accepted
Context
Nx yields a tag-constraint graph; import-linter yields an ordered layer list where "lower layers are not allowed to depend on higher layers" — verified in its docs. Expanding that ordering into pairs is lossless precisely because the ordering is the constraint.
Decision
One shape: a set of named units, and the directed pairs permitted between them, with the source format recorded for provenance. An ordered list expands on read; a tag graph is already pairs.
Consequences
+ A consumer reasons about one shape without knowing the source. + A non-total-order tag graph survives, which an ordered-layers representation would distort. − The pair set is larger than the ordering that produced it, so a deeply layered project expands quadratically; bounded in practice by layer counts that are small by nature. − "Which layer is above which" is no longer directly readable, only derivable.

D-003 · Read the INI subset directly rather than take a dependency

Status
Accepted
Context
import-linter's config is INI: a named section and flat key = value lines, with no nesting. This slice needs two keys from it. Earlier in this same module a YAML parser was taken as a dependency (079 D-003) rather than hand-read, so the asymmetry deserves stating.
Decision
Read the narrow INI subset directly — section headers and flat keys — and take no dependency.
Consequences
+ No new supply-chain surface for two keys. + The subset genuinely has no ambiguity: unlike YAML's anchors, block scalars and flow style, an INI section header and a flat key have one reading. − It is the same class of shortcut refused for YAML, and the justification is the format's simplicity rather than a principle; a reviewer is entitled to weigh that differently. − An exotic INI feature (line continuations, interpolation) would be misread; mitigated because the failure direction is "no map".

D-004 · Extract an ESLint config's constraints as text; never evaluate it

Status
Accepted
Context
Nx's more widespread constraint form lives in an ESLint config, which is JavaScript. P-11 holds that artifacts are data and not instructions, and executing a config file to read it would be exactly the thing that principle forbids. The constraint block itself is JSON-shaped.
Decision
Extract the constraint block textually and parse it as data. Where extraction fails, report no map rather than a partial one.
Consequences
+ No arbitrary code from a scanned repository is ever run. + The failure direction is right for something informational: a missing map costs a placement verdict some evidence, a wrong one would mislead it. − A config that computes its constraints programmatically is unreadable, and will silently look unmapped. − Textual extraction is a heuristic; the tests pin the documented shape, not every shape.

D-005 · A units-module adapter, not an enforce detector

Status
Accepted
Context
The reuse argument points at enforce/detect.ts, whose FileSignal shape this resembles. But that module exists to answer enforcement questions, and FR-003 makes a detected map explicitly non-enforcing.
Decision
Place it in units/adapters/ beside the workspace adapters, behind the port style 079 established.
Consequences
+ The units model — edges and boundaries — stays in one place, and 082 imports one module family. + Nothing in an enforcement path can accidentally start gating on it. − Some shape is duplicated rather than shared with the enforce detector; judged the lesser cost against a map appearing to be an enforcement signal.
