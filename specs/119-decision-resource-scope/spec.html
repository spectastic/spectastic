Specification · 119-decision-resource-scope

Decision resource scope

A governance decision can scope a repo-relative path, but not a resource that lives in another service. Let a decision name the data store it governs — and who owns it — so the gate can tell a write it may make from one it may not.

Status Draft Spec ID 119-decision-resource-scope Owner Brian Corbin · @briancorbinxyz Reviewers Guardrail layer (112–118) Created 13 Sep 2026 Principlesv1.9.0 Smallest demoableThe position-keeper's D-007, resource-scoped: evaluated with a non-owner project identity it flags the write; with the owner identity it reproduces today's verdict exactly. Read time

A guardrail decision (112) scopes a repo-relative path glob — src/**/persistence/** — which cannot name a data store in another repository. This spec adds a resource scope: a decision names the store it governs by a federation-unique datastore coordinate, the owner project that may write it, and the owner-internal path where a direct write is sanctioned. The verdict becomes owner-aware — in the owning service it reproduces today's path rule exactly; in any other service a detected touch is a violation even when cleanly layered in the non-owner's own repo, because the defect is ownership, not layering, the one thing a path glob cannot express. The comparison needs only the current project identity (067) and the owner coordinate; the cross-repo read is deferred to federation, so this slice is proven single-repo with fixture identities.

1 · Context

The guardrail layer (112–118) catches the position-keeper's D-007 — a direct UPDATE positions outside the persistence adapter — because the decision, the sanctioned path, and the offending file share one checkout. Its scope is a repo-relative path glob, matched against staged files in the same repo. The survey cross-repo guardrails established that this cannot cross a service boundary: a path glob has no grammar for a file — still less a table — in another repository, and the store a decision protects is exactly what a microservice split moves out of reach.

A run spike settled the fix. A decision that names the resource it governs and the owner that may write it turns the verdict owner-aware: in the owning service it behaves precisely as the path rule does today; in any other service a touch of that store is a violation — including one impeccably layered in the non-owner's own code, because what is wrong is whose store it is, not where the write sits. It is the first primitive toward cross-repo enforcement, worth building before federation because it is what the distribution surface would carry.

2 · User scenarios & testing

Each story is independently testable: US1 alone — the non-owner branch — is a viable MVP that catches the case a path glob cannot.

US1 · A consuming service is flagged for reaching into a store it doesn't own P1

As a reviewer in a consuming service, I want the gate to flag a change that touches a data store my service does not own — even when the change is cleanly layered in my own repo — so that a cross-service reach into another team's store is caught, not silently merged.

Acceptance: for a decision owned by position-keeper, a verdict run under a different project identity flags any detected touch — a well-layered write in the consumer's own adapter just the same.

US2 · The owning service sees no regression P1

As a reviewer in the owning service, I want a resource-scoped decision to behave exactly like today's path-scoped one, so that adopting the resource scope costs me no change in verdict.

Acceptance: under the owner's identity, a resource-scoped decision flags a write outside allowed-in and is silent inside it — identical to the path-scoped equivalent, every scenario.

US3 · An author is told when the ownership rule is mis-declared P2

As a spec author, I want to declare which service owns a store and where it may be written, and be told at commit time if I mis-declare it, so that the ownership rule is well-formed before it reaches CI.

Acceptance: a malformed <spec-resource> — bad coordinate, ill-formed owner, or an owner that disagrees with the coordinate's authority — is reported by validate at error severity.

Edge cases

  • A decision carries both <spec-path> and <spec-resource> — each scope is evaluated independently.
  • allowed-in absent — no sanctioned direct-write path, so even the owner's direct touch is a violation (fully locked).
  • The current identity is the bare, unqualified default — treated as never the owner (fail safe: an unidentified project cannot claim ownership).
  • The content pattern under-detects a real cross-service touch (an API call, a topic, a migration is not a SQL string) — a recorded ceiling, not an edge case this slice closes.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A decision MUST be able to declare a resource scope with a <spec-resource> element inside its <spec-scope> — a sibling to <spec-path>/<spec-module> — carrying a coordinate (the store), an owner (the project that may write it), and an optional allowed-in (the owner-internal path where a direct write is sanctioned).

The resource coordinate MUST be a well-formed datastore resource coordinate (spectastic://<owner>/<project>/datastore/<name>); datastore MUST be added to the shared RESOURCE_KINDS grammar (067) so the identity engine and this scope agree on what is well-formed.

The merge verdict MUST be owner-aware for a resource-scoped decision: when the current project is the decision's owner, a detected touch outside allowed-in is a violation and one inside it is not (the existing path rule); when the current project is not the owner, any detected touch is a violation.

The owner-aware verdict MUST honour the decision's declared posture (block / warn, spec 112) uniformly for both the owner-internal and the non-owner case — the resource scope changes where a touch is allowed, not how a violation is graded.

A validate rule SHOULD report, at error severity, a malformed resource declaration: a coordinate of the wrong kind or shape, an owner that is not a well-formed project identity, or an owner that disagrees with the coordinate's own authority segments.

A decision with no <spec-resource> MUST behave exactly as today — the resource scope is purely additive, and no existing path-scoped decision changes verdict.

Detection of a resource touch SHOULD reuse the decision's existing enforcement rules (the content pattern, the path deny) — the resource scope adds no new detector; it changes only the allowed-zone evaluation to be owner-aware.

Non-functional

The verdict kernel MUST stay deterministic and I/O-free: it reads no config, no clock, no network, and carries at most 0 filesystem, network, or model imports on its path. The current project identity is injected as data by the caller (resolved once via the 067 identity source), never read inside the kernel.

The datastore coordinate SHOULD resolve through exactly 1 identity grammar (the shared 067 RESOURCE_KINDS / classifier) with 0 second parsers — so a coordinate this scope accepts and one the identity engine accepts can never disagree.

Out of scope (deferred to other slices)

  • Reading another repository's decision inside this repo's CI — the cross-repo distribution surface. This slice proves the non-owner branch with a fixture project identity; the live cross-repo read is federation-gated.
  • Cross-service touch detection beyond the content pattern — an API call, a topic subscription, or a migration is not a SQL string, so the pattern proxy under-detects. Recorded as a ceiling.
  • The duplication case — a non-owner building its own parallel store (not touching the named one) is a placement question (resemblance-is-not-ownership, P-14 review-caught), not a resource-scope violation.

4 · Data model

Two concepts, one extended and one new.

Entities

Resource scope
A store a decision governs: a datastore coordinate, an owner (the one project that may write it), and an optional owner-internal allowed-in path. Invariant: exactly one owning project, and the owner agrees with the coordinate's own authority.
Governance decision (extended)
Its scope may now carry a resource alongside, or instead of, a path. With no resource scope it is identical to a pre-119 decision.

The load-bearing invariant is owner-aware evaluation: ownership is the decision's owner compared to the current project identity, and the bare default is never an owner. Ownership is a property of the coordinate, not the file — which is why a well-layered write in a non-owner's own adapter is still a violation.

6 · Assumptions

The current project identity reaches the verdict's caller through the 067 resolver (resolveProjectConfig) and is passed into the kernel as data — the spike confirmed this is all the owner comparison needs.

The content pattern (or path deny) remains the touch detector; the resource scope reinterprets the allowed zone, not what counts as a touch. Better cross-service detection is deferred.

7 · Open questions

None outstanding — the scope, the declaration shape, the coordinate kind, and the non-owner posture were all anchored in the interview, and the run spike de-risked the verdict semantics.
