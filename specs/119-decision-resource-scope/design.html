Design · 119-decision-resource-scope

Decision resource scope

How we will build it.

Status Accepted Spec 119-decision-resource-scope Owner Brian Corbin · @briancorbinxyz Branch main Created 13 Sep 2026 Read time

Five small extensions of seams the guardrail layer already has: parse a <spec-resource> into the decision, add a datastore kind to the shared coordinate grammar, make verdictFor owner-aware by injecting the current project identity, and clone the decision-well-formed rule for the new shape. The one real risk is the honest ceiling the spec already records — the content pattern under-detects a real cross-service touch — which this design does not try to close.

6 · Approach

Extend five existing files and add one. In @spectastic/schema: add datastore to RESOURCE_KINDS, and a new resource-scope-well-formed rule cloned from decision-well-formed. In @spectastic/core: parse <spec-resource> into a ResourceScope on GovernanceDecision (types + parse), and make verdictFor owner-aware — it gains an optional currentProject, and for a resource-scoped decision it compares that identity to the decision's owner: the owner gets today's path rule, everyone else gets an any-touch rule. In @spectastic/cli: the verdict command resolves the identity via resolveProjectConfig (as it already does for --explain) and passes it, keeping the kernel pure. Detection is unchanged — the resource scope reinterprets the allowed zone, not what counts as a touch.

Governing decision acknowledged. This surface (packages/core/src/guardrail/**) is governed by 113-guardrail-retrieval/D-001 — "no model or network on the retrieval path." D-004 and NFR-001 uphold it: the identity is injected at the CLI edge, the kernel imports no config or network, and the no-network scan is extended to the new branch — so the owner comparison adds capability without touching the purity that decision protects.

7 · Alternatives considered

The one real design fork is how the kernel receives the current project identity and what it does when that identity is absent (the interview's second question).

OptionBack-compat (FR-006)Secure-by-default (P-9)Kernel purity (NFR-001)Total
Optional currentProject; absent → non-owner55515
Optional field; absent → skip resource eval51511
Required param on verdictFor15511

The winner fails safe (an unknown identity flags rather than passes) and keeps every existing pure-fixture caller working with no identity supplied; "skip eval" fails open, and "required param" breaks back-compat.

8 · Decisions

D-001 · Parse <spec-resource> into a ResourceScope on the decision

Status
Accepted
Context
The scope grammar already loops <spec-path>/<spec-module> children (parse.ts:40–51). A resource is a third sibling.
Decision
Add resource?: ResourceScope to GovernanceDecision; populate it from a <spec-resource> child in the existing scope loop.
Consequences
+ Reuses the parse seam; no new top-level element. − Two scope kinds now coexist (path, resource); both are evaluated (an edge case the verdict handles).

D-002 · Add datastore to the shared coordinate grammar

Status
Accepted
Context
RESOURCE_KINDS (project-shared.ts:63) is the single list the 067 identity engine reads; a coordinate kind must live there to validate.
Decision
Add 'datastore' to RESOURCE_KINDS; the coordinate validates through classifyProjectId/parseResourceUri — no second parser (NFR-002).
Consequences
+ Federation-unique and addressable by construction. − A new permanent kind (IDs are contracts, P-3) — chosen deliberately over the generic resource.

D-003 · Owner-aware verdict — inject identity, branch on ownership

Status
Accepted
Decision drivers
Back-compat · secure-by-default · kernel purity
Considered options
  • Optional currentProject; absent → non-owner (chosen) — + fails safe, back-compat. − a resource decision with no identity always flags (acceptable: identity is resolvable).
  • Absent → skip resource eval — + simplest. − fails open, hides a real touch.
  • Required param — + explicit. − breaks pure-fixture callers.
Context
The run spike (Grounding row 6, ran) settled the semantics across scenarios A–D; the branch point is verdictFor's allowed.some(matchesGlob) zone check.
Decision
VerdictInput gains currentProject?: string. For a resource-scoped decision: owner → the existing path rule against allowed-in; non-owner (including absent/unqualified) → any detected touch is a violation, at the decision's declared posture (FR-004).
Consequences
+ Catches the ownership-not-layering case a path glob cannot (scenario D). − Live cross-repo use needs the deferred federated read; this slice proves it with fixture identities.

D-004 · Resolve identity at the CLI edge; keep the kernel pure

Status
Accepted
Context
The guardrail kernel imports no @spectastic/corpus; the CLI verdict command already calls resolveProjectConfig for --explain.
Decision
The CLI resolves the current project via resolveProjectConfig (067) and passes it into verdictCommand; the kernel receives it as data and reads no config (NFR-001).
Consequences
+ Kernel stays deterministic and I/O-free; the no-network scan still passes. − One more field threaded from edge to kernel.

D-005 · resource-scope-well-formed clones decision-well-formed

Status
Accepted
Context
decision-well-formed.ts is the shape-rule precedent (parse → finding), registered in rules/index.ts.
Decision
A new rule errors on a malformed <spec-resource>: wrong-kind/ill-formed coordinate, an owner that is not a well-formed project identity, or an owner disagreeing with the coordinate's authority (FR-005).
Consequences
+ Author is told at commit/CI; reuses the proven rule shape. − One more registered rule to maintain.

D-006 · TDD with the spike's four scenarios as fixtures

Status
Accepted
Context
The spike already defined owner A/B and non-owner C/D as fixtures; the guardrail layer is tests-first throughout.
Decision
Write the four verdict scenarios, the validate-rule fixtures, and the purity scan red first; then the owner-aware branch.
Consequences
+ Discovery is already done; the tests are the spec's success criteria made mechanical. − None material.

10 · Risks & mitigations

RiskLikelihoodImpactMitigation
The content pattern under-detects a real cross-service touch (an API call / topic / migration is not a SQL string).HMRecorded ceiling in the spec, not closed here; deferred to TBD-resource-touch-detection. The scope still catches every touch the existing detectors see.
Identity normalisation: an owner-qualified owner vs a differently-shaped current identity mis-compares.LMExact-match on the resolved owner-qualified identity; a bare/unqualified identity is never an owner (fail-safe), covered by a fixture.
A decision carrying both a path and a resource scope double-evaluates.LLIntended — each scope is independent (spec edge case); a fixture asserts neither suppresses the other.

11 · Complexity tracking

The design adds no complexity beyond the spec's contract: every change is an extension of an existing seam (parse loop, coordinate list, verdict zone check, rule registry). The only new file kinds are a schema rule and its fixtures, both cloned from a proven precedent.

The current project identity is resolvable at the CLI edge via resolveProjectConfig and meaningful to compare — true today for any project with a spectastic.json project or an owner-qualified default; the bare fallback is handled as non-owner.

12 · Open questions

None outstanding — the two design forks (test style, identity injection) were anchored in the interview, and the run spike settled the verdict semantics. The cross-repo read and better touch detection are explicitly deferred in the spec, not open here.
