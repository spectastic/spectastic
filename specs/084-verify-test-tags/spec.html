Specification · 084-verify-test-tags

A durable test selector

A list of file paths says where this spec's tests lived on the day it was captured. A tag says which tests are this spec's, including the ones written since.

Status Accepted Spec ID 084-verify-test-tags Owner Brian Corbin · @briancorbinxyz Reviewers — Created 02 Aug 2026 Principlesv1.9.0 Smallest demoableA command that reports which tests carry a given spec's tag, and what that spec's testsCite would be if derived from them. Read time

Across 60 populated verify views, 44 tests commands are hand-maintained lists of file paths — 138 files, up to 11 in one command — 6 run the whole suite, and none carries a filter. The list fails asymmetrically: delete a named file and the runner exits non-zero, but add a test and it is silently never run under that spec's command. Suites grow. Separately, testsCite — the test-task ids a command claims to cover — is written into the view and read by nothing, so it is an author's assertion verified never. This spec establishes a tag convention (a test declares the spec and the requirements or tasks it closes), a deterministic reader that maps tags back to those ids, and derivation of testsCite from what is actually tagged. The tags ship where they work today; first-class runner filtering waits on a runner upgrade this spec deliberately does not perform.

1 · Context

The verify view's tests field is the healthiest in the block — copy-pasteable in 60 of 61 views. That measurement asks whether a reader can run something. It does not ask whether what runs is this spec's tests, nor whether the command will still mean that later. On those two axes the field looks different: 44 of 60 commands enumerate file paths by hand, 6 run the entire suite, and not one uses a filter.

Enumeration fails in one direction only, which is why nobody notices. Remove a named file and the runner reports no tests found and exits non-zero — loud, and correct. Add a test and nothing happens: it is not in the list, so it never runs under that spec's command, and every check stays green. Suites grow far more often than they shrink, so the protection sits on the side that is not the problem.

The browser suite shows the same thing structurally. Its specs are organised by concern — theme, verify, contract — which is the sane way to organise them, and it means a file path cannot express "the browser tests for this spec" at all. That mapping has only ever existed in the author's head at capture time.

There is a second, larger prize. The captured shape already carries testsCite, the test-task ids a command covers. It is rendered into the view and consulted by nothing: no rule reads it, no check compares it to reality. It is a claim made once and verified never. If a test declares which requirement it closes, that claim can be derived from what actually ran — and a derived citation and its subject cannot quietly disagree. The full argument is in the actionability survey (D-005).

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Select a spec's tests without naming files P1

As a reviewer or an author returning to a spec, I want to run exactly that spec's tests by naming the spec, not its files so that the selection keeps working after the files are renamed, split or added to.

Acceptance: A test declaring a spec's tag is selected by a command naming only that tag; a test added later carrying the same tag is selected by the same unchanged command; and a file rename changes nothing.

US2 · Derive the citation instead of asserting it P1

As a reviewer, I want to see a citation that came from the tests themselves so that what the view claims about coverage and what the suite actually covers cannot silently diverge.

Acceptance: Given tagged tests, the tool reports the requirement and task ids they close; that set is what the verify view records, and a discrepancy between a hand-written citation and the derived one is reportable rather than invisible.

US3 · Adopt it without a flag day P2

As a maintainer of a large existing suite, I want to tag incrementally so that an untagged suite keeps working exactly as it does now.

Acceptance: With no tags anywhere, every existing command and view behaves as before; derivation reports nothing rather than failing; and a partially tagged suite yields a partial result that is labelled as partial rather than presented as complete.

Edge cases

  • A test tagged with a spec id that does not exist — reported, not silently dropped, because a typo'd tag otherwise looks exactly like a spec with no tests.
  • A test tagged with a requirement id that its spec does not define — the same failure one level down, and reported the same way.
  • A requirement with no tagged test at all — a legitimate finding, and distinct from a requirement whose tests exist but are untagged. The tool must not conflate them.
  • A test covering two specs — permitted; tags are a set, not a single owner.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A test MUST be able to declare the spec it belongs to, and MAY additionally declare the requirement or task ids it closes, using a convention expressible in every test runner the project uses.

Rationale

Expressible-in-every-runner is the binding constraint, not elegance: a convention only one runner supports splits the estate in half and leaves the browser suite — where file paths fail hardest — unable to participate.

A deterministic reader MUST scan the project's test files and report, for each declared tag, the tests carrying it — using no network, no runner execution and no model.

Rationale

Executing the suite to discover its tags would make every consumer of this information as slow and as failure-prone as the suite. Reading is enough, and reading is reproducible.

The reader MUST report a tag naming a spec, requirement or task that does not exist as a finding, and MUST NOT silently discard it.

Rationale

A typo'd tag is indistinguishable from an untested spec if it is dropped — and the two call for opposite responses.

The reader MUST distinguish a requirement with no tagged test from a requirement whose tests exist but carry no tag, and report them differently.

Rationale

During incremental adoption almost everything is untagged. A tool that reports that as "untested" would be wrong about the entire estate on the day it ships, and would be ignored thereafter.

A verify view's testsCite SHOULD be derived from the tags of the tests the captured command selects; where it is authored by hand instead, a disagreement with the derived set MUST be reportable.

Rationale

The field is written into every view and read by nothing. Derivation is the point of the tag convention, not a bonus: it converts the estate's only traceability claim from prose into something a machine can contradict.

With no tags present anywhere, every existing command, view and check MUST behave exactly as it did before this spec, and the reader MUST report an empty result rather than an error.

A partially tagged project's derived result MUST be labelled as partial, stating how much of the suite carries tags, rather than presented as a complete picture of coverage.

Rationale

A derived citation covering three of a spec's twenty tests is more dangerous than none, because it looks authoritative. Partial results must announce themselves.

At least one real suite SHOULD be tagged as a pilot, and its derived citation compared against the hand-written one, so the convention is proven against real tests rather than fixtures.

Non-functional

The reader MUST be deterministic: the same tree yields byte-identical output across runs, with results ordered independently of filesystem enumeration order, and MUST complete a full scan of this repository's ~240 test files in under 5 s.

100% of the reader's behaviour SHOULD be available without executing any test, so that a project with a failing or slow suite can still derive its citations.

Out of scope (deferred to other slices)

  • Upgrading the unit-test runner to a version with first-class tag filtering. Two majors across every test file, and it earns its own justification rather than riding along here.
  • Executing a view's captured commands to prove they still run. A tag makes that check worth doing; it is still a separate mechanism.
  • Failing a build because a requirement has no tagged test. Adoption has to come first — a gate on a convention nobody has applied yet would fail everything on day one.
  • Tagging the whole existing suite. This spec proves the convention on a pilot; a sweep of ~240 files is its own piece of work.

4 · Data model

Two concepts, one of which already exists and is being given a source of truth.

Entities

Test tag
A declaration, attached to a test, that it belongs to a spec and optionally that it closes named requirements or tasks. A tag is one of a set — a test may carry several, and a single test may legitimately serve two specs. A tag names an artifact that must exist; a tag naming nothing is an error, not a no-op.
Derived citation
The set of requirement and task ids obtained by reading the tags of the tests a command selects. It replaces the authored testsCite as the source of truth for what a command covers. Its defining property is that it cannot disagree with the suite without something noticing — which is exactly the property the authored form lacks.

The invariant worth stating: a derived citation is only as complete as the tagging beneath it, and completeness is not observable from the citation itself. A spec with three tagged tests out of twenty produces a confident-looking citation covering three. That is why FR-007 makes partiality part of the result rather than something a reader is expected to infer.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

For a tagged spec, adding a new test that carries its tag causes that test to be selected by the spec's unchanged recorded command — with 0 edits to the verify view — and renaming a test file changes nothing.

For the pilot suite, the citation derived from tags is compared against the hand-written one and every difference is explained — either the hand-written set was wrong, or the tagging is incomplete and says so.

On a project with no tags, 100% of existing verify views, commands and validate findings are unchanged, and the reader exits successfully reporting an empty result.

6 · Assumptions

Tags will be applied to new tests once the convention exists. This is the assumption most likely to be wrong — it is the same bet the toggle field lost, where a required field was answered none 50 times out of 61 — which is why FR-008 insists on a real pilot rather than a fixture, and why the coverage gate is deferred until adoption is observable rather than hoped for.

A tag convention expressible in the current runners is good enough to prove the idea, even though one of them cannot filter on it natively until it is upgraded. The reader does not depend on runner support; only the convenience of running by tag does.

7 · Open questions

None outstanding. Tag granularity (spec plus requirement or task ids) and the staged posture toward the runner upgrade were both anchored in the interview behind the survey's D-005; the per-runner syntax is a design decision, not an open question.
