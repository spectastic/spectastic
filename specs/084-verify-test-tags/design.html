Design · 084-verify-test-tags

A durable test selector

The convention that works in both runners today turns out to be the plainest one available — a token in the test's own title.

Status Accepted Spec 084-verify-test-tags Owner Brian Corbin · @briancorbinxyz Created 02 Aug 2026 Principles v1.9.0 ArchitectureOne deterministic kernel reader over the test tree, with a thin CLI surface. No runner integration, no execution. Coverage Diff-aware: new lines covered by unit tests over real fixtures; a change never lowers coverage of what it touches. Read time

Grounding collapsed the expected two-convention design into one. A tag embedded in the test's title is filterable in both runners the project uses today: Playwright reads @-prefixed title tokens natively with --grep, and the installed Vitest 2.1.9 filters titles with -t — verified by running it (9 selected, 17 skipped). So the runner upgrade buys boolean tag expressions and config-declared tags, not the convention itself, and this spec is unblocked. The reader is a pure kernel module over the test tree; it never executes a test.

3 · Data model & contracts

No interface crosses a repository boundary: a kernel reader and a CLI subcommand, both internal. No contract file is declared.

The tag grammar is the closest thing to a contract here, and it is deliberately tiny. A spec tag is @NNN — the spec's leading number. A qualified tag is @NNN:ID, where ID is a requirement or task id defined by that spec. Qualification matters: a bare @FR-001 would collide across every spec in the estate, since requirement ids are only unique within their own document.

The grammar has one useful property that is not an accident: because a qualified tag begins with the spec tag, a substring filter on @084 selects both the spec-tagged and the requirement-tagged tests. The simple case needs no boolean expression, which is exactly what the current runner cannot do.

5 · Approach

  1. Fix the grammar — @NNN and @NNN:ID, embedded in the test title.
  2. Build the reader — a kernel module that walks test files, extracts tags from title string literals and from Playwright tag arrays, and returns a sorted, deterministic map.
  3. Resolve against the estate — check each tag names a spec that exists and an id that spec defines; classify the rest.
  4. Expose it — a thin CLI subcommand that prints the derived citation for a spec plus the partiality figure.
  5. Pilot it — tag the browser suite's verify tests and compare the derived citation with the hand-written one.

7 · Decisions

Status Accepted

Context The expectation was two conventions — Playwright's native tags, and something else for Vitest 2.1.9. Grounding found both runners filter on the test title today, verified by running vitest -t (9 selected, 17 skipped) rather than by reading the help text.

Decision One convention: an @NNN token in the test title, optionally qualified as @NNN:ID. Both runners filter it today; the reader parses it statically.

Consequences
+ One convention across the estate, and the browser suite — where paths fail hardest — participates immediately.
+ A substring filter on the spec tag selects qualified tests too, so the common case needs no boolean expression, which is precisely what the installed runner lacks.
− Titles get noisier, and a tag is a string in a sentence rather than structured metadata.
− Nothing validates the token at author time on Vitest 2.1.9: a typo yields an empty run. The upgrade fixes exactly this, which is the honest case for taking it later.

Status Accepted

Context The reader could discover tags by executing the suite with a reporter, or by parsing sources. Execution would inherit the suite's runtime and its failure modes.

Decision Parse sources. Extract tags from title string literals and Playwright tag arrays; never run a test. Match NFR-002 so a project with a red suite can still derive.

Consequences
+ Fast, deterministic, and usable when the suite is broken — which is when traceability is most wanted.
− A dynamically-constructed title (a template literal, a loop) is invisible to a parser. Accepted: such a test can carry a literal tag in its describe, and the reader reports what it can see rather than guessing.
− A parser cannot tell a real declaration from one quoted inside a string. Found while piloting: this spec's own test file embeds it('typo @999:FR-001') as fixture data, and the reader dutifully reported it as a tag naming a missing spec. The same cause inflates the "tests seen" count that partiality is measured against. Both are accepted rather than solved — the alternative is a real TypeScript parse, which is a large dependency for a small gain, and the failure is loud rather than silent. Recorded here so the count is read as an estimate.

Status Accepted

Context FR-004 and FR-007 both turn on not overclaiming during incremental adoption, when almost everything is untagged.

Decision The result carries counts, not just a set: tests tagged, tests seen, and per-requirement status distinguishing no tagged test from tests exist but are untagged. A derived citation is always accompanied by its coverage figure.

Consequences
+ A three-of-twenty citation cannot masquerade as complete, which is the failure mode that would discredit the whole convention early.
− Every consumer must render the partiality figure, or it is decorative. The CLI does; a future gate must too.

10 · Complexity tracking

No principle exceptions. The reader is a new kernel module rather than a helper inside verify because three consumers already want it — the verify generator, a deferred coverage gate, and the CLI — which is the fat-core test, not a speculative one.

11 · Open questions

None outstanding. The convention, the parse-don't-execute stance and the partiality contract were settled here; the runner upgrade is deferred by the spec rather than open.
