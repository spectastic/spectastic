1 · Context

Today's /spectastic.principles verb is an LLM-executed procedure in commands/spectastic.principles.md: copy templates/principles.html, interview the user for project name + 3–5 principles + governance, fill the template, write the file. No TypeScript exists; future surfaces (MCP, VS Code, web editor) cannot reach the verb without re-implementing it.

006 established the architecture (per-verb subpaths, async function …Command(input, ctx), injected KernelContext with optional ai, markdown canonical, slash commands MAY call kernel via Bash). principles is the natural next slice: smallest slash verb, near-pure template generation, exercises AIProvider on a low-stakes verb whose worst failure mode is a re-run.

2 · User scenarios & testing

Each story is independently testable: if you implemented only US1, you would still have a viable MVP that proves the shape.

US1 · Maintainer authors fresh principles via the CLI P1

As a maintainer setting up spectastic in a new repo, I want to run spectastic principles and get the same interview-driven principles.html the slash command produces so that the verb is reachable without Claude Code (scripting, non-Claude environments).

Acceptance: Running spectastic principles in a clean directory with a stubbed AIProvider returning canned answers produces a principles.html byte-identical (modulo trivial whitespace) to today's slash-command flow on the same inputs. Exit code 0 on success, 2 on usage error.

US2 · Downstream surface invokes the kernel programmatically P2

As a future MCP / VS Code author, I want to import principlesCommand from @spectastic/core/commands/principles with a custom AIProvider so that the surface drives principles authoring without spawning a CLI.

Acceptance: A test under packages/core/test/principles.test.ts calls principlesCommand(input, ctx) with a stub ctx.ai, asserts on the returned { html, principlesCount }, spawns no process, resolves well under 100 ms with a synchronous stub.

Edge cases

Three tracked failure modes the extraction handles
  • Caller passes no ctx.ai — the function rejects with a typed error rather than reading from globals. Verbs that require AI must declare it; deterministic verbs (validate) leave the field optional.
  • Interview returns fewer than 3 or more than 5 principles — the procedure clamps and surfaces a warning in the result; behaviour matches today's slash-command guidance ("3–5 core principles").
  • Template path drift — kernel locates templates/principles.html via ctx.cwd + relative resolution (no process.cwd() reads). If the template is missing, the function rejects with a typed error pointing the caller at the missing path.

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

principlesCommand MUST conform to 006 FR-007: signature async function principlesCommand(input: PrinciplesInput, ctx: KernelContext): Promise<PrinciplesResult>, no module-level side effects, no implicit process.cwd() / process.env reads, all IO via ctx.fs, all AI access via ctx.ai.

The implementation MUST live at packages/core/src/commands/principles.ts and be exported via the per-verb subpath @spectastic/core/commands/principles per 006 FR-002. It MUST NOT be re-exported from the package's main entry.

@spectastic/cli MUST expose a spectastic principles subcommand that imports principlesCommand from @spectastic/core/commands/principles. The subcommand owns shell-side concerns (argv, interview prompt UX, stdout/stderr, exit codes: 0 success, 2 usage error); the kernel owns the deterministic core (template fill, ID assignment, HTML assembly).

v1 scope MUST be fresh-generation focused. The kernel function MUST gate its behaviour on the destination's <spec-status> per P-6: a Draft destination (or fresh path with no destination) MUST be authored / edited in place (preserve the existing ID; append a one-line <spec-changelog> entry); a past-Draft destination (Accepted, In Review, Superseded, Deprecated, Blocked) MUST be refused with a typed error pointing at /spectastic.propose. A --force override MAY bypass the past-Draft refuse, but invoking it MUST emit a one-line warning that the operation skips the change-management surface.

The kernel function MUST be unit-tested at packages/core/test/principles.test.ts as a pure function (stub ctx.ai + ctx.fs, no real IO, no process spawn) and the CLI subcommand MUST be integration-tested at packages/cli/test/cli.test.ts (process spawn, stubbed AI, byte-identical output assertion). Both layers per 006 FR-010.

commands/spectastic.principles.md MUST be updated with a one-paragraph note that for deterministic operations the LLM MAY invoke spectastic principles via Bash. The markdown remains canonical; the kernel is an alternate path. Slash-command behaviour MUST NOT regress.

principlesCommand's docblock MUST link to commands/spectastic.principles.md as the canonical procedure per 006 FR-008. The markdown MUST NOT be auto-generated in v1.

The generated principles.html artifact MUST carry a version below 1.0.0 (default v0.1.0) while its <spec-status> is draft. The kernel MUST NOT emit v1.0.0 (or higher) on a Draft artifact. Graduation to v1.0.0 MUST happen at the Draft → Accepted bundled-flip prompt per REQ-LIFECYCLE-005, not in this verb. Subsequent in-place edits while Draft MAY bump the pre-1.0 version (e.g. v0.1.0 → v0.2.0) but MUST NOT cross the 1.0.0 boundary.

Rationale

Companion to FR-004 (Draft-aware refuse) per P-6. Pre-1.0 versioning matches the project-wide discipline already enforced for the @spectastic/* npm packages (006 FR-012); extending it to generated artifacts is consistent. A Draft artifact with no consumers anchored against it must not claim v1.0.0 — the version field reads as a contract; the contract doesn't exist yet.

Non-functional

The extraction MUST NOT regress any bench/baselines.json scenario past budget. The init-help-cold-start scenario (150 ms) MUST stay green — the new subcommand MUST NOT land on the cold-start path via eager imports.

  • Multi-version history tracking inside the kernel. Today's changelog discipline in the artifact itself is sufficient.

4 · Data model

Two types this slice owns: PrinciplesInput (caller-supplied seeds) and PrinciplesResult (the rendered HTML + count). The kernel renders the string; the caller decides where to write it.

Entities

PrinciplesInput
Fields: projectName?: string (if omitted, the function prompts via ctx.ai); principlesCount?: number (target count for the interview, clamped to 3–5 to match today's guidance). All fields optional; the kernel function fills gaps by interviewing through ctx.ai.
PrinciplesResult
Fields: html: string (the rendered principles.html content, ready to write); principlesCount: number (the actual number of P-N blocks emitted). The kernel does not write the file; the caller (CLI subcommand or downstream surface) decides the output path and performs the write. This keeps the kernel pure and lets downstream surfaces (preview UIs, MCP) consume the rendered HTML without committing to a filesystem.

5 · Success criteria

Technology-agnostic, measurable outcomes.

Given a stubbed AIProvider returning canned answers (project name + 3 principles + governance), principlesCommand returns a PrinciplesResult whose html is byte-identical (modulo trivial whitespace) to the file today's slash command produces on the same inputs.

packages/core/test/principles.test.ts imports principlesCommand from the subpath, calls it with stub ctx.fs + ctx.ai, asserts on the returned shape without spawning any process. packages/cli/test/cli.test.ts spawns spectastic principles, feeds canned answers, asserts the resulting file matches the kernel's output.

pnpm bench passes all scenarios within their bench/baselines.json budgets. The init-help-cold-start p50 stays within ±20% of today's baseline — adding the subcommand MUST NOT grow cold-start time.

6 · Assumptions

Two preconditions: 006's kernel package shape is in place, and the AI-stubbing pattern is conventional for the test stack.

006-kernel-extraction has shipped packages/core/ with the KernelContext and AIProvider interfaces, per-verb subpath exports, and tsup multi-entry build. This slice adds one verb on top of that foundation; it does not re-derive the architecture.

Stubbing ctx.ai in vitest with canned responses is straightforward for a verb that uses ai.chat() and ai.ask<T>() for bounded-choice questions. The Claude implementation that lands with 007-core-triage will follow the same interface, so this slice's stub pattern transfers.
