Cards

Generated principles.html is v1.0.0 + refuses re-run even when still Draft

Spec upstream

Debugging spectastic principles smoke test, root cause was two upstream gaps in 008's spec — no initial-version policy (so the implementation hardcoded v1.0.0 against fresh-draft semantics) and FR-004's refuse-if-exists rule treats every re-run as ceremonious supersession even when the destination is still Draft and unratified; fixed by amending FR-004 + adding an FR for the version policy via /spectastic.propose; regeneration fails because the next LLM session has no spec language constraining either behaviour.

Expected
(a) A freshly-generated principles.html carries a pre-1.0 version (e.g. v0.1.0) while still Draft; only Accepted ratification graduates it to v1.0.0. (b) Re-running spectastic principles against a Draft destination edits in place — no Supersede ceremony when the prior artifact has not been ratified.
Actual
(a) Generated artifact ships at v1.0.0 on first author (see packages/core/src/commands/principles.ts line 139: <b>Version</b><span>v1.0.0</span>) while <spec-status value="draft">Draft</spec-status> — version and lifecycle state contradict. (b) Re-run is forced through the refuse-if-exists path (per FR-004); the only re-run path is --force (overwrite, treated as supersession) or a full /spectastic.propose against the artifact. No in-place-edit-while-Draft affordance.
Diagnosis
Two distinct upstream gaps in 008's spec. (1) No FR constrains the initial-version policy of the generated artifact; the implementation chose v1.0.0 as a sensible default, but that conflicts with the project-wide pre-1.0 convention captured in 006 FR-012 for npm packages — the same discipline should apply to any generated artifact until it earns Accepted. (2) FR-004's blanket "reject (typed error) if a principles.html already exists" treats Draft and Accepted destinations identically; Draft means unratified, and unratified artifacts have no contract to protect — in-place edit is the natural authoring loop. Per REQ-LIFECYCLE-004 of the meta-spec, Draft is the only state where the artifact has no consumer commitments; the verb should honour that asymmetry.
Fix
Open /spectastic.propose against specs/008-core-principles/spec.html with two changes: (a) modify FR-004 to scope the refuse-if-exists rule to destinations whose <spec-status> is past Draft (Accepted / In Review / Superseded / Deprecated / Blocked); when the destination is Draft, default behaviour is in-place edit (preserve ID, append a one-line <spec-changelog> entry). --force remains the override for past-Draft destinations. (b) add FR-008 specifying the initial version policy: generated artifacts MUST carry a version below 1.0.0 (recommend v0.1.0) while their <spec-status> is Draft; graduation to v1.0.0 ties to the Draft → Accepted bundled-flip prompt. Hotfix the implementation (packages/core/src/commands/principles.ts line 139) to emit v0.1.0 in the same PR; CLI subcommand gains the Draft-state detection + in-place-edit path.
Closed by
Both halves landed. Half (a) — Draft-aware refuse — landed via P-6 ratification + 2026-06-16-p6-cascade-principles (FR-004 MODIFIED) + the CLI hotfix at packages/cli/src/commands/principles.ts via shared gateOnDestinationState helper. Half (b) — version policy (Draft → v0.1.0 vs v1.0.0) — landed via 2026-06-16-version-policy (FR-008 ADDED) + kernel hotfix at packages/core/src/commands/principles.ts:139. The original smoke-test contradiction (v1.0.0 + Draft) no longer reproduces.
Deep dive — principles candidate + cross-spec implications

Candidate principle. The user's framing — "less ceremony when we have not officially ratified" — generalises beyond the principles verb. It's a cross-cutting invariant: artifacts in Draft state are loose; ratified states are locked. This could land as a project principle (e.g. P-6 · Draft is loose, ratified is locked) in a follow-up against principles.html itself — but that's expansion, not the immediate fix. Surface here; do not silently promote.

Cross-spec. If the P-6 principle lands, the same Draft-vs-ratified asymmetry will need to surface in the analogous verbs that generate artifacts: specCommand (011), planCommand (012), tasksCommand (009), proposeCommand (013). Each of those has the same potential gap if its re-run behaviour conflates Draft destinations with ratified ones. The 008 proposal should explicitly defer the cross-verb sweep to either (a) the P-6 principles proposal cascading downstream, or (b) a per-verb triage when each surfaces the same defect.

Hotfix vs amendment sequence. Hotfix lands with the amendment in a single PR: the spec change to FR-004 + new FR-008 ride alongside the impl change to the hardcoded v1.0.0 + the CLI's Draft-detection logic. No need to land the impl ahead of the spec because the user has a current pain point but no third-party dependency.

Connection to 006 FR-012. The pre-1.0 versioning policy already exists for the @spectastic/* npm packages ("breaking changes MAY land in minor version bumps until 1.0.0"). Extending the same discipline to generated artifacts is consistent — the principle is the same shape ("pre-1.0 means content can shift without ceremony") in both surfaces.
