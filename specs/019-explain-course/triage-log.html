Defects against the 019-explain-course spec. Cards append-only; IDs stable.

Spec 019-explain-course Created 20 Jun 2026 Read time

Two defects found by opening the first real generated course (007-core-triage): the quiz gate fired on the wrong objective, and the teach-back had no way to respond. Both are implementation defects in assembleCourse — regeneration reproduces them — and both slipped a structural-only SC-003 test.

Cards

Quiz gate marks only the last objective (closure-over-var)

Implementation code

Debugging "only the last objective revealed its answer," root cause was an implementation closure-over-var bug in the generated quiz-gate script; fixed by block-scoping the per-objective bindings; regeneration fails (the generator emits the same broken script every time).

Expected
Answering objective N's quiz reveals objective N's answer and ticks objective N's mastery checkbox (FR-006).
Actual
Answering any quiz revealed only the last objective's answer and would tick the last objective's checkbox; objectives 1..N−1 never responded.
Diagnosis
The gate script declared correct, objId, checkbox, answer with var inside a for…of loop. var is function-scoped, so every change handler closed over the same bindings, which hold the final iteration's values. Flagged at author time by linter S1515 and dismissed as style. SC-003's test was structural (asserted the script string) and never executed the JS, so the broken-but-present gate passed.
Fix
packages/core/src/commands/course.ts — GATE_SCRIPT uses const for the per-iteration bindings. Guard: tests/course.gate.spec.ts drives a generated course in a real browser and asserts the answered objective's checkbox (not the last) is ticked; plus a structural assertion in the integration test that the gate script carries no var.
Deep dive — none required

Self-contained implementation fix. No cross-spec contract, principles invariant, or deferred scope touched.

Teach-back prompt has no affordance to respond

Implementation code

Debugging "no way to write anything down for teach-back," root cause was the implementation rendering the prompt as static prose with no input; fixed by adding a non-persisted <textarea>; regeneration fails (every generated course omitted the input).

Expected
The ungraded teach-back (FR-007) lets the learner articulate the answer in their own words — the testing-effect benefit requires actually writing it.
Actual
assembleCourse rendered <spec-decision><h4>Teach-back</h4><p>prompt</p></spec-decision> — a rhetorical question with nowhere to respond.
Diagnosis
FR-007 says "teach-back prompt"; the implementation took "prompt" literally and omitted the response affordance. The spec is satisfiable with an input — this is an implementation gap, not a spec defect.
Fix
packages/core/src/commands/course.ts — render a <textarea> under the teach-back prompt. Content is intentionally not persisted (courses are ephemeral/git-ignored, FR-001); the value is articulating in-session. A label states this.
Deep dive — none required

Within FR-007 as written; no amendment needed.

A wrong quiz answer still reads as "Correct"

Implementation code

Debugging "an incorrect answer still shows as correct," root cause was the implementation rendering a static Correct: <answer> reveal and only the correct option's feedback — ignoring the learner's choice; fixed by surfacing the chosen option's feedback plus a correct/incorrect verdict; regeneration passes (the §4 data model already specifies per-option feedback, so a faithful build would not recur).

Expected
Answering a quiz tells the learner whether their choice was right and shows feedback for the option they picked (FR-005 "MCQ-with-feedback"; §4 data model "per-option feedback").
Actual
The reveal always reads "Correct: <correct option>" regardless of selection; a wrong pick shows the same panel, and only the correct option's feedback is ever displayed.
Diagnosis
renderObjective hard-codes feedback = feedback[correctIndex] and a static Correct: <correctOption> label; the gate toggles .correct/.incorrect classes that carry no CSS, so nothing reflects the learner's answer.
Fix
packages/core/src/commands/course.ts — the gate writes a per-answer verdict + the chosen option's feedback into the reveal; the static "Correct:" line becomes the neutral reference answer. Guard: extend tests/course.gate.spec.ts to assert a wrong pick surfaces an incorrect verdict and the chosen option's feedback.
<p>Correct: <strong>{correctOption}</strong>. {feedback[correctIndex]}</p> // static — identical for every choice gate(change): verdict = chosen === correct ? "Correct" : "Not quite"; show options[chosen] + feedback[chosen], then the correct answer
Deep dive — none required

No cross-spec contract, principles invariant, or deferred scope. The spec's per-option-feedback data model already covers the behaviour; this is code drift, not a missing requirement.

explain --course can't run inside Claude Code — its kernel verification needs ANTHROPIC_API_KEY

Cross-spec upstream

Debugging "spectastic course exits 2 with ANTHROPIC_API_KEY is not set when a course is generated from within Claude Code," root cause was a cross-spec collision: the course verb's blind-check guarantee (FR-004, plan D-001, honouring P-8) lives in the kernel and needs a live model, but 006 FR-009 promises the kernel is an alternate path a slash command MUST NOT be required to invoke — yet explain --course requires the shell-out and there is no keyless in-host provider; fixed upstream by reconciling the two (a keyless in-host verification path that keeps the guarantee kernel-side); regeneration fails — another session building to the current 019 plan + 006 FR-009 would rebuild the same required, key-needing shell-out.

Expected
A course generated from the in-host slash-command path (which, per the standing convention, "uses the in-host Claude session and needs no key") completes — the blind guessability + analogy-fit checks run without an API key (006 FR-009: the kernel is an alternate code path, not a hard dependency; markdown works end-to-end without it).
Actual
commands/spectastic.explain.md --course step 3 shells out to spectastic course; the CLI's createAIProvider returns a ClaudeProvider that throws ANTHROPIC_API_KEY is not set and exits 2. The only keyless route is the CI stub (SPECTASTIC_AI_STUB), so --course is unusable inside Claude Code.
Diagnosis
The verification guarantee (FR-004 guessability, SC-002) is kernel-owned per plan D-001 and P-8; 060 FR-005 added a second kernel AI call (verifyAnalogyFit). Both call ctx.ai.subagent, and the CLI wires ctx.ai to a key-requiring ClaudeProvider (packages/cli/src/ai-factory.ts). 006 FR-009 says a slash command MUST NOT be required to invoke the kernel — but --course is. The two contracts were never reconciled for the one verb whose guarantee is an AI call the in-host session can't make keyless. Predates 060 (guessability alone has needed the key since 019); 060 amplified, didn't cause.
Fix
Needs a /spectastic.propose against specs/019-explain-course/ (touching 006 FR-009), then packages/cli/src/ai-factory.ts + commands/spectastic.explain.md. Not a code-only patch — it needs the design decision (see deep dive).
Closed by
Direction (a) from the deep dive: applied 2026-07-26-keyless-in-host-verification, landing NFR-003 — the guarantee stays kernel-side (P-8), the slash path stays keyless (006 FR-009). Implemented as a new D-006/D-007 in-host AIProvider: packages/core/src/providers/claude-cli.ts's ClaudeCliProvider shells to claude -p <prompt> --output-format text, one fresh process per call, structurally source-blind (no drafting context, no --resume); packages/cli/src/ai-factory.ts's createAIProvider gained the precedence rung (stub → key → claude-on-PATH → an actionable error naming every option); packages/cli/src/commands/course.ts now catches a provider-construction failure and exits cleanly with that actionable message rather than an uncaught stack trace. Verified live (no stub, no key, real claude binary): a genuine course draft's guessability check ran the real blind judgment via ClaudeCliProvider and the course wrote — see smoke.md § Keyless in-host smoke. Drained as US3, T-300–T-321.
Deep dive — cascade required (cross-spec + principles)

Cross-spec contract. 006 FR-009 ("the kernel is an alternate code path, not a hard dependency; markdown procedures continue to work end-to-end without the kernel") collides with 019's design (course's blind-check guarantee is kernel-owned and needs a live model). They disagree only for course — the one AI-coupled verb whose slash-command procedure delegates the AI step to the kernel rather than doing it in-agent (the way spec/plan/ propose/tasks keep their reasoning in the in-host session, so their CLI path is genuinely optional).

Principles dimension. P-8 ("guarantees live in the kernel or CI") is what makes the naive fix — move the blind checks to the in-host agent — unattractive: it would demote the SC-002 guarantee to advisory markdown a model can skip (T-009). The reconciliation must keep the guarantee kernel-side while giving the kernel keyless model access in-host.

Candidate directions for the propose (not decided here). (a) A keyless in-host AIProvider that routes subagent calls through the harness's own model access instead of an API key — keeps the guarantee in the kernel (P-8) and the slash path keyless (006 FR-009). (b) The in-host agent runs the blind checks and the kernel accepts/records the verdicts — keyless, but advisory (tension with P-8 / SC-002). (c) Document --course as key-required in-host — rejected by the reporter ("should be possible within claude code too"). No safe hotfix-now; route to /spectastic.propose.
