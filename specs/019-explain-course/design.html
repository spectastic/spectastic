Design · 019-explain-course

explain --course — the grounded course

How we will build it.

Status Accepted Spec 019-explain-course Owner Brian Corbin · @briancorbinxyz Branch 019-explain-course Created 20 Jun 2026 Read time

A hybrid: /spectastic.explain --course <target> drives the in-session agent to retrieve source and draft ≤7 objectives (Read + MCQ) as a structured JSON draft, then hands that draft to a new stub-testable CLI/kernel (spectastic course) that verifies it — every cited reference confirmed to exist, every quiz item posed to a blind AI call and rejected if answerable without the source — assembles a course.html from a new template, and writes it to .spectastic/courses/. The agent owns generation and the regenerate-or-drop loop; the kernel owns the testable guarantees. Biggest risk: the guessability check is itself an LLM judgment — guarded by a conservative reject rule, stub-driven tests, and a manual smoke.

2 · Technical context

Language(s)
TypeScript 5.7+ on Node 20+, ESM (the kernel + CLI). The command file is markdown prose; the generated course.html is HTML with a small inline script.
Frameworks
commander.js (CLI), vitest (tests), tsup (build), pnpm workspace. The existing AIProvider (015) + StubAIProvider. No new dependency.
Storage
.spectastic/courses/<date>-<slug>/course.html, git-ignored (the CLI ensures a .spectastic/.gitignore); --keep retains. No database; no cross-session state (NFR-001 bounds size).
Testing
Stub-driven integration over the course CLI (the 015 pattern): canned generation + guessability responses; assert structure, existence (SC-001), guessable-item rejection (SC-002), no-JS self-mark (SC-003). Plus a manual real-LLM smoke.
Perf targets
None quantified. Generation/verification is an LLM batch bounded by ≤7 objectives × one blind call each; not a latency surface. CI uses the stub (sub-second).
Constraints
Single-file self-contained course.html, no build step, reuse <spec-*> + spec.css/spec.js (NFR-002); --course rides the opt-in extended explain verb (FR-011); apart from the course dir, mutate no tracked source.

3 · Approach

Split by what each side is best at. The agent generates — it has Read/Grep, so it resolves the target, reads real source, and drafts ≤7 objectives (each a Read explanation, an MCQ with per-option feedback, an ungraded teach-back, and the list of references it cited) as a structured JSON course draft. The kernel verifies — a new spectastic course reads the draft on stdin, confirms every cited reference exists in the repo, and poses each quiz item to a blind AI call (question only, no source) via AIProvider.subagent; an item answered correctly blind is reported as guessable. The agent regenerates reported items (or drops the objective after retries, per FR-004) and re-submits; on a clean draft the kernel assembles course.html from a new templates/course.html skeleton and writes it under .spectastic/courses/.

The verification, assembly, and write — the testable guarantees — live in code routed through the AIProvider factory, so the whole path is stub-driven in CI with no API spend. The interactive quiz gate is a small inline script generated into each course.html, degrading to a self-markable ledger with JS off.

4 · Alternatives considered

The decisive choice is the implementation surface. Scores 1 (poor) – 5 (excellent).

OptionTestable guaranteesRetrieval qualityBuild effortFit to specTotal
Markdown-only (agent does everything)255315
CLI/kernel end-to-end (+ new retrieval util)522413
Hybrid (agent drafts, kernel verifies/writes)553518

Markdown-only keeps retrieval strong but makes the anti-hallucination guarantees agent-driven, not CI-testable — cutting against 015's whole reason for the stub. CLI-end-to-end makes everything testable but forces a brittle retrieval util for fuzzy targets. Hybrid takes the agent's retrieval and keeps the guarantees in stub-tested code.

5 · Decisions

D-001 · Hybrid surface — agent drafts, kernel verifies + assembles + writes

Status
Accepted
Context
The course writes an artifact and must verify it (SC-001/SC-002) — unlike the markdown-only coach. Generation wants the agent's Read/Grep; verification wants deterministic, stub-testable code.
Decision
The --course branch of explain.md drives the agent to draft objectives; a new spectastic course kernel verifies, assembles from a template, and writes. The agent owns generation; the kernel owns the testable guarantees.
Consequences
+ Best retrieval and CI-testable guarantees. + Reuses the AIProvider/stub infra. − Two surfaces + a contract between them (D-002). − Heaviest verb to date.

D-002 · Course-draft contract — JSON on stdin; agent owns the regenerate-or-drop loop

Status
Accepted
Context
The agent and kernel need a contract, and FR-004 requires guessable items to be regenerated then dropped. Regeneration is generation — the agent's job.
Decision
The agent emits a course draft JSON (objectives[]: title, read, quiz{question, options, correctIndex, feedback}, teachBack, refs[]) piped to spectastic course --target <t> [--keep] on stdin. The kernel validates the draft schema on load, verifies, and reports per-item pass/fail; the agent regenerates failures (cap retries, then drops the objective) and re-submits; a clean draft is written.
Consequences
+ Stateless, idempotent kernel; the loop lives where generation lives. + No draft file in the tracked tree (stdin). − The schema must be validated loudly (R2).

D-003 · Guessability = a blind per-item AIProvider call; existence = repo lookup

Status
Accepted
Context
FR-004 needs real blinding — an item is "guessable" if answerable without the source.
Decision
Each quiz item is posed to AIProvider.subagent with the question + options only (no source) in a fresh context; a correct blind answer ⇒ reject. Reference existence is a plain repo lookup (resolve spec IDs / element IDs / paths via fs/glob). Both route through the factory, so the stub drives them in tests.
Consequences
+ Genuine blinding; deterministic under the stub. + No new AI infra. − One extra AI call per quiz item (bounded by ≤7 objectives). − The blind judge can err (R1).

D-004 · templates/course.html skeleton + inline gate script; degrades to self-mark

Status
Accepted
Context
NFR-002 wants single-file reuse of the <spec-*> vocabulary; FR-006 wants a quiz gate that never dead-ends with JS off (P-4).
Decision
Add templates/course.html: <spec-meta> + objectives as a <spec-task> mastery ledger, each with <spec-tabs> (Read / Quiz) and a <spec-decision> teach-back prompt, plus a small inline gate <script>. The kernel fills it. With JS off, checkboxes are directly markable and the correct answer renders inline. Gate JS stays out of shared spec.js.
Consequences
+ Self-contained, no build step; shared spec.js stays clean. + Consistent structure across courses. − A 4th artifact template to maintain.

D-005 · Ephemeral storage under .spectastic/courses/, git-ignored, --keep

Status
Accepted
Context
FR-001 (D-008): courses are ephemeral and outside specs/.
Decision
Write to .spectastic/courses/<date>-<slug>/course.html. The kernel ensures a .spectastic/.gitignore (*) on first write so courses are ignored by default; --keep records the course as intended-to-track (e.g. a sibling marker / un-ignore).
Consequences
+ The contract tree stays clean; ephemerality is the default. − A first-write side effect (creating .spectastic/.gitignore); idempotent.

D-006 · Keyless in-host verification via a claude -p provider

Status
Accepted
Context
The applied NFR-003 requires the blind checks (D-003, plus 060's analogy-fit) to run keyless in-host — but createAIProvider returns a key-requiring ClaudeProvider (packages/cli/src/ai-factory.ts:52) and Claude Code carries no ANTHROPIC_API_KEY. Verified this turn: /opt/homebrew/bin/claude (2.1.153) supports -p/--print, and a keyless round-trip works — env -u ANTHROPIC_API_KEY claude -p "…" --output-format text returned its answer using the session's subscription auth, no key. The AIProvider.subagent(prompt) seam (packages/core/src/types.ts:119) takes only a prompt string.
Decision
Add an in-host AIProvider (a ClaudeCliProvider) whose subagent() shells to claude -p <prompt> --output-format text — no API key, using the host session. createAIProvider gains a precedence rung: SPECTASTIC_AI_STUB (CI) → an explicit ANTHROPIC_API_KEY (ClaudeProvider) → the claude binary detected on PATH (the in-host provider) → an actionable error naming the options. Detection is host-pluggable, not hard-wired.
Consequences
+ Keyless in-host; the guarantee stays a kernel call (P-8) and 006 FR-009's keyless contract holds. + Reuses the existing AIProvider seam — no interface change; the stub still drives CI. − Couples the in-host case to the claude binary (cross-host is TBD-cross-host-ai-providers). − A claude -p cold start per item is slower than a direct API call and spends subscription quota (bounded by ≤7 items · one call each; R6).

D-007 · Each keyless call stays source-blind and isolated (the FR-004 guard)

Status
Accepted
Context
FR-004/SC-002 require the item be answered "with the source hidden"; the proposal's risk pass flagged that the cheapest keyless path — reusing the in-host session that drafted the course — would leak the source and make the guarantee theatre. NFR-003 mandates source-blind, independent-of-drafting-context calls. The subagent(prompt) signature (types.ts:119) already carries nothing but the prompt.
Decision
The in-host provider spawns a fresh claude -p process per item carrying only the blind prompt (question + options, or the analogy mapping) — no course context, no --resume, no drafting session. Blindness is structural: the provider is handed only the blind prompt string, so it cannot pass what it never receives. A test asserts the provider is invoked prompt-only and rejects any wiring that would thread drafting context in.
Consequences
+ FR-004 blindness holds by construction, not by review; the guard test pins it. + No shared state between draft and check. − A cold process per item (the latency named in D-006's R6), accepted for ≤7 items.

The course's anti-hallucination guarantees (SC-001/SC-002) are only as strong as the blind judge and the existence lookup. Stub tests prove the mechanism (a guessable item is rejected; a missing ref fails); real-course quality rests on the manual smoke. Accept this before implementation.

8 · Complexity tracking

This is the heaviest verb to date; each piece earns its place.

Two surfaces + a contract (D-001/D-002). Justified: the spec's headline value is verification (SC-002), which must be deterministic and CI-tested — that wants code — while generation wants the agent's retrieval. A single surface sacrifices one or the other; the JSON-on-stdin contract is the minimal seam between them.

A 4th artifact template + a new CLI subcommand. Justified: NFR-002 requires a consistent self-contained course.html (a template is how every other artifact gets that), and the kernel needs a CLI entry to be invoked by the slash command and stub-tested like the six AI verbs.

Risk tolerance: Medium. Novel verification (blind guessability) built on the proven AIProvider/stub infrastructure; the only genuinely new infra is the draft contract and the course template.

9 · Open questions

None block implementation. The decisions the spec deferred to this plan are resolved above: the surface is D-001 (hybrid), the guessability mechanism is D-003 (blind AIProvider call). The exact draft-schema field names and the retry cap are implementation details for tasks, not open questions.
