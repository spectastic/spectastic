Keyless in-host course verification

explain --course can't run inside Claude Code because its kernel verification demands an ANTHROPIC_API_KEY. Require a keyless in-host path — the guarantee stays in the kernel.

Status Applied Change ID 2026-07-26-keyless-in-host-verification Spec 019-explain-course Author Brian Corbin · @briancorbinxyz Created 26 Jul 2026 Targets 1 requirement (1 added) Read time

Resolves triage T-004. The course verb's anti-hallucination guarantee — the guessability check (FR-004) and 060's sibling analogy-fit check — lives in the kernel (P-8) and calls a model. Driven from Claude Code the kernel shells out to spectastic course, whose createAIProvider returns a key-requiring ClaudeProvider; with no ANTHROPIC_API_KEY it exits 2 and the verb is unusable in its primary habitat. This adds one must-tier NFR requiring a keyless in-host execution path for that verification — using the host's own model access, keeping the check kernel-side and source-blind, honouring 006 FR-009's keyless-in-host contract. The mechanism is the plan's; CI's deterministic stub is unchanged.

Keyless in-host course verification

Applied

1 · Intent

Creating a course from within Claude Code now fails: spectastic course exits 2 with "ANTHROPIC_API_KEY is not set." The course verb is unique among the AI-coupled verbs — for spec/plan/propose/tasks the in-host agent does the AI reasoning itself, so their CLI path is genuinely optional. But explain --course's markdown procedure delegates its verification step to the kernel (the blind guessability check is a hard guarantee, and P-8 puts guarantees in the kernel, not advisory markdown). The kernel, run as a subprocess, has no way to reach the host's authenticated session and falls back to a direct API key it doesn't have.

The standing contract is that the slash-command path "uses the in-host Claude session and needs no key" (006 FR-009: the kernel is an alternate code path, not a hard dependency). Course honours neither half today. This change fixes the keyless half without weakening the guarantee: the verification stays a real kernel check, but gains a keyless in-host way to reach a model. The reporter's constraint is explicit — "this should be possible within claude code too."

2 · Scope

In scope

  • ADD a must-tier NFR requiring a keyless in-host execution path for the course verb's AI-coupled verification (the FR-004 guessability check and 060's analogy-fit sibling) — no ANTHROPIC_API_KEY required when driven from a host that provides model access.
  • Keep the guarantee kernel-side (P-8) — the in-host path must not demote verification to advisory — and each blind call source-blind and independent of the drafting context (FR-004).
  • An actionable failure when no keyless model access and no key is available, instead of a raw provider stack trace.

Out of scope

  • Clarifying 006 FR-009 itself — that AI-coupled verbs are a sanctioned exception to "markdown works end-to-end without the kernel." This change makes course honour the keyless half; the 006-side wording is a separate consideration.
  • The concrete keyless provider and cross-host support (Cursor, Aider, plain terminals). The plan picks the v1 mechanism (the Claude Code in-host case); a provider catalogue is later.
  • Removing the API-key path. ClaudeProvider stays for headless / keyed runs; the deterministic SPECTASTIC_AI_STUB stays for CI. This only adds a keyless option.

3 · Approach

The spec change is one requirement; the mechanism is the plan's, but the shape is predictable. Add a keyless in-host AIProvider that reaches the host's authenticated model access rather than an API key — for the Claude Code case, a fresh, context-free invocation of the host's own model (e.g. the claude CLI's print mode, which uses the session's auth, not ANTHROPIC_API_KEY). createAIProvider (packages/cli/src/ai-factory.ts) gains a middle rung in its precedence: SPECTASTIC_AI_STUB (CI) → an explicit key (ClaudeProvider) → the keyless in-host provider when host model access is detected → an actionable error naming the options.

Two properties the plan must hold, both flagged by the risk pass: (1) each verification call stays source-blind and isolated — a fresh model context per item, never the session that drafted the course, or FR-004's "answer with the source hidden" is defeated; (2) the keyless mechanism is host-pluggable, not hard-wired to one binary, so "keyless in-host" doesn't silently narrow to "Claude-Code-only" with no honest fallback elsewhere.

The adversarial pass below was run inline (same session, author-as-critic) rather than via an independent spectastic-critic subagent, to respect this session's standing "don't spawn agents" constraint. Independence is therefore weaker than a normal REQ-CHANGE-004 pass — request a fresh critic run before approving if you want the stronger check.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec; op= is one of added | modified | removed | renamed.

The course verb's AI-coupled verification — the guessability check (FR-004) and any sibling blind check — MUST have a keyless in-host execution path: when explain --course is driven from an agent host that provides its own model access, the checks MUST run without an ANTHROPIC_API_KEY, using that host's access rather than a direct API key. The guarantee MUST stay kernel-side — the in-host path MUST NOT demote verification to advisory (P-8) — and each blind call MUST remain source-blind and independent of the drafting context (FR-004). Where neither keyless model access nor a key is available, the verb MUST fail with an actionable message naming the options, never a raw provider stack trace. The deterministic CI stub (SPECTASTIC_AI_STUB) is unchanged; the concrete keyless provider is a plan decision.

Rationale

Resolves T-004. explain --course's primary habitat is an agent host (Claude Code) with no API key; the current kernel path (createAIProvider → ClaudeProvider) makes the verb unusable there. This restores the keyless-in-host half of 006 FR-009 without moving the guarantee out of the kernel (which would violate P-8 and demote SC-002 to advisory). Written as an execution constraint on the existing verification, not a change to what the checks guarantee.

5 · Risk register

From the adversarial pass (run inline — see §3 warning). One <spec-risk> per finding; each carries a target=. Status stays identified until you disposition it — apply refuses while any risk is still identified. Author responses below are drafts; the status transition (and by=) are yours.

The regret risk: "keyless in-host" has exactly one realistic mechanism today — shelling to the host's own CLI (e.g. claude -p) — which couples the kernel to a specific harness. In 30 days the MUST may quietly mean "works in Claude Code, nowhere else," a portability promise the requirement's wording ("an agent host that provides its own model access") overstates.

NFR-003: "when explain --course is driven from an agent host that provides its own model access, the checks MUST run without an ANTHROPIC_API_KEY."

Mitigated. NFR-003 scopes the MUST to hosts that provide model access and requires an actionable fallback otherwise, so it never claims to work where there is none; §3 keeps the provider host-pluggable rather than hard-wired to one binary. The v1 mechanism being Claude-Code-only in practice is named honestly in the TBD-cross-host-ai-providers out-of-scope item — a known, tracked narrowing, not a hidden one.

The most-likely-contradicted requirement: FR-004 requires the quiz be answered "with the source hidden" — a genuinely blind, independent call. The cheapest keyless mechanism is to let the same in-host session that drafted the course also run the check; that session already holds the source, so the "blind" check silently sees what it's supposed to be blind to, and SC-002's guarantee becomes theatre.

FR-004: "an item the model can answer correctly with the source hidden MUST be rejected"; SC-002: "0 quiz items pass the guessability check."

Mitigated. NFR-003 carries the guard clause ("source-blind and independent of the drafting context") and §3 makes an isolated fresh-context call an explicit plan constraint; the §6 guard task turns it into a test that rejects a leaked-context provider. A real implementation trap, closed by a requirement clause + a test — not left to review.

The scope concern (too narrow): deferring the 006 FR-009 clarification leaves that requirement still literally reading "markdown procedures work end-to-end without the kernel" — which course openly breaks. The reconciliation lives only in 019's new NFR plus a TBD- that may never be picked up, so a reader of 006 in 30 days sees a contract course contradicts with no visible carve-out.

§2 out-of-scope: "Clarifying 006 FR-009 itself … defer-to TBD-kernel-optional-ai-verb-carveout."

Accepted. Keeping this change 019-only is the deliberate call — a focused blast radius beats a cross-spec edit for a one-verb fix. The residual (006 FR-009 reads misleadingly until the carve-out lands) is accepted with the follow-up named, not bare: TBD-kernel-optional-ai-verb-carveout carries a specific slug and one-line intent in §2, so it is trackable rather than lost. Its concrete form (a 006 clarification via /spectastic.propose, or a considerations note) is the follow-up owner's call.

Corpus-contradiction slot: the repo's knowledge/spectastic-concepts corpus (KB-001@2026-07-25) covers spec-driven development, RFC 2119, and the grounding discipline — no domain fact bears on the course verb's execution model, so no live 019 requirement contradicts it.
