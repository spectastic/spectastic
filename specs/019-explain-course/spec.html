explain --course — the grounded course

The persistent sibling of the coach: explain --course <target> generates a self-contained course you read, quiz yourself on, and check off — every item grounded in real source and verified against the repository.

1 · Context

The coach (018-explain) answers "explain this" in one ephemeral chat read and writes nothing. But a chat read doesn't build anyone: no artifact to return to, no check that you understood, no structure across a topic. The handover at docs/explain.html always framed the coach as the cheap first half; the course is the second.

This is the course's first slice. The frame is settled by the handover: courses are ephemeral, outside specs/ (D-008); the learner model is per-objective mastery — no learning styles, no recommender, no gamification (D-009); every item is generated from real source and verified against the repo (D-010); the graded teach-back (D-005) is deferred. Stakeholders: the learner ramping on a spec or subsystem, and the maintainer who wants grounded onboarding without hand-writing it.

2 · User scenarios & testing

Each story MUST be independently testable: if you implemented only US1, you would still have a viable MVP.

US1 · Generate a grounded course P1

As a learner ramping on a spec or subsystem, I want to run explain --course <target> and get a self-contained course grounded in that target so that I can study it on my own, trusting that nothing in it was invented.

Acceptance: a git-ignored course.html is written under .spectastic/courses/ with ≤7 objectives, each a Read explanation + an MCQ quiz; every cited reference resolves to real source and every quiz item is verified unguessable without that source.

US2 · Quiz-gated mastery ledger P2

As a learner working through a course, I want each objective to unlock as "mastered" only when I answer its quiz correctly so that the ledger reflects what I actually understand, not what I skimmed.

Acceptance: a correct quiz answer marks the objective's <spec-task> checkbox; with JavaScript off the checkbox is directly tick-able and the quiz + answer render inline — the gate never produces a dead-end.

Edge cases

  • A target that doesn't resolve to real source → refused with a report (as the coach does), never turned into an ungrounded course (FR-002).
  • A target that resolves to more than one artifact → one clarifying question, then proceed.
  • A quiz item that stays guessable after regeneration retries → its objective is dropped rather than shipped weak (FR-004).
  • The underlying spec/code moves → the course goes stale; it is regenerated, never patched (FR-010).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

explain --course <target> MUST generate a self-contained course.html and write it to .spectastic/courses/<date>-<slug>/course.html, git-ignored by default; a --keep flag MUST opt a course into being retained (tracked).

A course MUST cover a single, repo-anchored target — one spec ID, one requirement/decision/success-criterion ID, or one file or directory path. A target that resolves to nothing MUST be refused with a report, not turned into a course.

Every reference the course cites — symbol, path, or ID — MUST resolve to a real artifact in the repository; the course MUST NOT cite anything it has not confirmed exists.

Rationale

D-010; the same grounding guarantee the coach gives at 018 FR-003, now over a generated artifact.

Each quiz item MUST be generated from retrieved real source and MUST pass a guessability check before shipping: an item the model can answer correctly with the source hidden MUST be rejected and regenerated. An objective whose quiz stays guessable after retries MUST be dropped rather than shipped.

Rationale

A quiz answerable from generic knowledge tests nothing about the repo. The guessability check is the verification half of D-010.

A course MUST present its objectives as a mastery ledger of <spec-task> checkboxes; each objective MUST carry a grounded Read explanation and an MCQ-with-feedback quiz.

Mastery MUST be quiz-gated: a correct quiz answer marks the objective mastered. With JavaScript disabled, the checkbox MUST be directly markable and the quiz plus its answer MUST render inline — the gate is a progressive enhancement, never a block.

Rationale

Honors P-4 (enhancement, never dependence): the readable, self-markable baseline survives with JS off.

Each objective SHOULD carry an ungraded teach-back prompt. Grading the teach-back is out of scope (the graded gate is deferred D-005).

A course MUST NOT use streaks, badges, points, XP, or a leaderboard. Informational feedback is the only motivator.

Rationale

D-009: completion-contingent rewards undermine intrinsic motivation; this also keeps the calm house voice.

Objective modality SHOULD follow the objective's Bloom level — recall/understand objectives become MCQ-with-feedback. Apply/create (hands-on Build) objectives are out of scope for this slice.

A stale course MUST be handled by regeneration (re-running explain --course); the verb MUST NOT provide an in-place update or patch path.

--course MUST be a mode of the opt-in extended explain verb (018 FR-009). Apart from writing the course directory, the verb MUST NOT modify tracked repository source.

Non-functional

A v1 course SHOULD contain no more than ~7 objectives, so it stays completable in one sitting; a target warranting more is a signal to narrow scope.

Rationale

Self-paced completion runs ~5–15%; a small, in-flow unit is the guard (D-009).

A generated course.html MUST be a self-contained single file that reuses the existing <spec-*> vocabulary and assets/spec.css / spec.js; it MUST NOT require new custom elements or any build step to view.

Out of scope (deferred to other slices)

  • Hands-on Build objectives (apply/create Bloom levels) and the runnable verification that compiles/tests an exercise against the repo.
  • Ad-hoc topic courses (a target with no repo anchor) — the weakest, ungrounded mode, behind a warning.
  • Band personalization of course depth by --proficiency. The flag exists on the verb (018 FR-006); v1 does not vary course depth by it.
  • Interleaving/spacing across objectives, and cross-spec / multi-target courses.
  • The graded teach-back gate (D-005), and persistent storage of mastery across sessions.

4 · Data model

This feature owns one ephemeral artifact and the objects it composes. None carry stable IDs — a course references the stable IDs it teaches (P-3).

Entities

Course
The generated course.html under .spectastic/courses/<date>-<slug>/. Holds the target and an ordered list of objectives rendered as a mastery ledger. Git-ignored unless --keep.
Objective
One learnable unit: a grounded Read explanation, an MCQ-with-feedback quiz, and an ungraded teach-back prompt. Carries a mastery flag (the ledger checkbox); modality follows its Bloom level (FR-009).
Quiz item
An MCQ generated from retrieved real source, with a correct option and per-option feedback. Verified unguessable-without-source (FR-004); the correct answer drives the mastery gate (FR-006).

A course is generated tooling output, not a hand-authored lifecycle artifact (closer to the validator's SARIF than a spec.html). Ephemeral and git-ignored, it sits outside the validated canonical set — no schema change — and the principles' v1.0.1 clarification permits generated tooling output, so the "no build step" non-goal holds.

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

Across a sample of courses, 100% of the references they cite resolve to artifacts that exist in the repository — zero hallucinated references.

In a shipped course, 0 quiz items pass the guessability check — every quiz item requires its source to answer.

A generated course opens in a browser with no tooling; with JavaScript disabled it remains fully readable and the mastery ledger remains self-markable — no objective becomes a dead-end.

6 · Assumptions

The parent 018-explain is in place: its opt-in extended-verb packaging (and the --proficiency flag it defined) are reused rather than re-specified.

The generating session can read repository source and run an AI to generate and verify items; the exact mechanism (in-session vs. CLI/kernel) is a plan decision.
