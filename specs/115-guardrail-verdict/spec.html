Specification · 115-guardrail-verdict

Merge-stage verdict

At merge, turn the actual diff into a deterministic verdict — this change violates that decision, for this reason, here — composed from the code, the decision, and an enforcer's output, with no model anywhere on the path.

Read time

Slice 3b of the architectural-guardrails design brief (§3.6) — the merge half of "the Priya PR dies." Given the changed paths, retrieve the governing decisions (113) and produce a deterministic verdict per violation: {decision-id, rule-id, reason, file:line, source→target}, reconstructable entirely from disk. It uses the detector/explainer split: spectastic runs its own native path and content detectors and/or ingests an ecosystem enforcer's machine-readable output (SARIF), and composes the traceability (rule-id ↔ decision-id ↔ reason) that no architecture-test tool provides — it never reimplements ArchUnit/Semgrep. Executing an enforcer's run= command from an artifact is deliberately out of scope here (it collides with P-11 and inherits 085's guard-first posture); this slice reads outputs and files, it runs no foreign command and no model.

1 · Context

The plan-stage constraint (114) is a happy-path nudge that reads a design's declared surface; it can be bypassed by committing straight to a branch. The Valmis scenario's most damaging case is exactly that: PositionReconciliationJob with a direct UPDATE positions, no spec, no plan. This slice is the guarantee the nudge is not — it reads the actual diff and produces a verdict that reconstructs from disk, so the same inputs always yield the same result and a reviewer can reproduce it offline with no model in the loop.

Its users are CI (which fails the build on a violation) and the reviewer (who reads a verdict that names the decision and its reason, not just "a rule fired"). The novel value over a generic scanner is the traceability composition: spectastic holds the decision as data, so it can join an enforcer's rule-id back to the decision that motivated it and the reason a human wrote.

2 · User scenarios & testing

Direct write caught natively. A branch changes src/recon/Job.java to run UPDATE positions …. A decision forbids that content outside src/**/persistence/** via a native content rule. spectastic verdict --changed src/recon/Job.java exits non-zero, naming the decision, the rule, and the line; the verdict artifact on disk contains the same, with no model output.

Type-graph violation via the enforcer's output. CI runs the project's ArchUnit/Semgrep and writes SARIF. spectastic verdict --enforcer-output results.sarif maps each SARIF result's rule-id to the decision carrying it and composes the verdict with that decision's reason — spectastic never ran ArchUnit itself.

Reconstructs from disk. Given the changed files, the decision record, the retrieval log, and the enforcer output, the verdict is byte-identical on a re-run — no model, no clock-dependence beyond an injected timestamp.

3 · Requirements

spectastic verdict MUST produce a deterministic verdict for each violation among the changed paths, carrying at least {decision-id, rule-id, reason, file:line}, and MUST exit non-zero when any violation is present. The verdict MUST reconstruct entirely from artifacts on disk (the changed files, the decision record, and — where used — the enforcer output and retrieval log); no field may derive from a model. A native content detector MUST report a violation when a changed file contains a rule's forbidden pattern outside the rule's allowed zone (the decision's scope), with the matched file:line. This is the language-agnostic "only the adapter may touch the data store" case. A native path detector MUST report a violation when a changed file's path matches a rule's forbidden location glob, with the file path. The verdict MUST be able to ingest an ecosystem enforcer's machine-readable output (SARIF): each result's rule-id is matched to a decision carrying that <spec-rule id>, and the verdict is composed with that decision's reason. A result whose rule-id matches no decision is ignored (the enforcer's own concern, not a governance violation). spectastic MUST NOT run the enforcer. The changed paths MUST come from an explicit --changed <paths…> when given, else from git diff --cached HEAD. The verdict kernel MUST take the paths as data (no git dependency in the kernel); reading git is the CLI's concern. The verdict MUST be persisted as a JSON artifact alongside the retrieval log, so a reviewer can reproduce every claim offline and CI can archive it. source→target SHOULD be populated where the detector or enforcer provides it (the changed file → the matched pattern for content; the SARIF location → the rule subject); the guaranteed floor is {decision-id, rule-id, reason, file:line}. The verdict path MUST carry no model client, no network access, and MUST NOT execute any foreign command — a test MUST assert its transitive imports include at most 0 model-client modules, at most 0 network modules, and at most 0 child-process/exec modules. The verdict MUST be deterministic: the same changed files, decisions, and enforcer output yield a byte-identical verdict artifact given an injected clock (at most 1 repeated-run diff).
  • Executing an enforcer's run= command — orchestrating the ecosystem tool by running it, behind 085's guard-first consent + a non-waivable location guard. A separate slice because arbitrary command execution is the highest-risk path (P-11).
  • CI wiring for the verdict — landed, and not where this item expected: 121 makes it a third half of init --tools (a marker-managed, version-pinned, drift-checked GitHub Actions / GitLab CI file running validate + enforce + verdict on every pull request), not the proving example — an installed guarantee survives; a copied example does not. The packaged-action form imagined here (a reusable Action / CI component instead of an npx step) stays open as 121's TBD-spectastic-github-action.
  • The Socratic teaching layer that follows a failure with one question — slice 5.

4 · Data model

Changed set
The paths in the diff under judgment — the actual code that moved.
Detector
A rule's executable check: native content (a forbidden pattern + an allowed zone), native path (a forbidden location glob), or an ingested enforcer output (matched by rule-id).
Violation
A changed location a detector flags, joined to the decision that governs it.
Verdict
The set of violations for a changed set, each {decision-id, rule-id, reason, file:line, source→target?}, plus the inputs it was composed from — the persisted, reconstructable record.

5 · Success criteria

Given a changed file containing a forbidden pattern outside its allowed zone, spectastic verdict exits non-zero with exactly one violation naming the governing decision, the rule id, and the file:line, and the persisted verdict artifact contains the same — reconstructable from the files + decision on disk, with no model output involved.

6 · Assumptions

  • Decisions carry the structured rules (112) — a native rule declares its pattern/location; an ecosystem rule declares its tool + id (matched against SARIF).
  • SARIF is the common enforcer output (Semgrep emits it natively; ArchUnit via a reporter). A minimal reader extracts each result's rule-id and physical location.
  • The retrieval log and the persisted verdict live beside each other under the project's .spectastic/ scratch (committed in the proving example for reproducibility).

7 · Open questions

None outstanding — the execution posture (ingest outputs, defer running run=), the diff source (explicit or git), and the native detector set (path + content) were all anchored in the interview.
