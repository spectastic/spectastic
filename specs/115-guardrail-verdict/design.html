Design · 115-guardrail-verdict

Merge-stage verdict

How we will build it.

Status Accepted Spec 115-guardrail-verdict Owner Brian Corbin · @briancorbinxyz Branch main Created 13 Sep 2026 Read time

A new plumbing command spectastic verdict and a pure kernel that, given the changed paths, retrieves the governing decisions (113), runs native path/content detectors and/or ingests an enforcer's SARIF, and composes a persisted, reconstructable verdict. The whole path is import-guarded against a model, a socket, AND a child process — so executing a foreign command is inexpressible, which is what keeps executing run= honestly out of scope. Biggest risk: whether a given enforcer emits SARIF at all — a recorded ceiling, not a design flaw.

3 · Data model & contracts

No external interface. The verdict consumes 113's GovernanceDecision[], a string[] of changed paths, and an optional SARIF document; it emits a Verdict (a list of Violations +the inputs it was composed from) persisted as JSON. A native rule extends 112's <spec-rule> with an optional pattern= (content) or deny= (path) and an optional allowed-in= (defaults to the decision's scope) — additive; decision-well-formed still only requires tool+id.

6 · Approach

Add a pure verdictFor(changed, decisions, sarif?, now) kernel and a thin verdict CLI. The kernel retrieves the decisions governing the changed paths (113), then for each collects violations from three detector kinds — a content match (a rule's pattern found in a changed file outside its allowed-in zone), a path match (a changed path matching a rule's deny glob), and an ingested SARIF result whose rule-id matches a decision's rule — and composes each into {decision-id, rule-id, reason, file:line, source→target?}. It writes the verdict JSON beside the retrieval log and returns a non-zero-worthy flag when any violation exists. The CLI supplies the changed paths (--changed or git diff --cached HEAD) and the optional --enforcer-output.

8 · Decisions

D-001 · A pure verdict kernel + thin CLI, reusing 113's retrieval

Context. The verdict must map changed paths → governing decisions, which 113 already does (guardrail/retrieve.ts). Decision. verdictFor(...) in guardrail/verdict.ts; the verdict command supplies paths + SARIF. Consequences. + Reuses retrieval + glob; deterministic, testable without git. − A new plumbing command (not a lifecycle verb — the eight stay eight).

D-002 · Two native detectors — content and path

Context. The Priya SQL case is a content pattern outside an allowed zone; a forbidden-location rule is a path match — both language-agnostic (spec §2). Decision. A rule carries pattern+allowed-in (content) or deny (path); the detector reads the changed file's text / path — no foreign process. Consequences. + Catches the direct-write case natively with a real file:line. − Regex content matching has the usual ceilings (comments, string concatenation) — bounded, and the type-graph cases are the enforcer's via SARIF.

D-003 · Ingest the enforcer's SARIF output; never run the enforcer

Context. Spike parsed the SARIF core shape to {ruleId, uri, line} (grounding row 3). Decision. A minimal reader maps each result's rule-id to a decision's <spec-rule id> and composes the verdict with that decision's reason; an unmatched rule-id is ignored. Consequences. + Type-graph traceability with zero foreign execution. − Depends on the project configuring its enforcer to emit SARIF — a recorded ceiling (the reader works; whether an enforcer emits SARIF is the project's config), not something spectastic guarantees.

D-004 · Changed paths from --changed, else git diff --cached HEAD

Context. The drain hook already uses that diff (worktree.ts:79). Decision. The kernel takes paths as data; the CLI reads git only when --changed is absent. Consequences. + Kernel is pure + testable; CI or the drain hook can supply paths directly. − Two entry shapes to document.

D-005 · The kernel cannot execute a foreign command, by construction

Context. Executing run= collides with P-11; the guarantee must be structural, not a promise. Decision. The verdict kernel imports no child_process/exec (nor model/network); a test walks the import graph and asserts 0 of each. Consequences. + "Execute before guard" is inexpressible — the strongest form of the 085 lesson. − Executing run= is a separate, guarded slice (TBD-guardrail-verdict-exec).

D-006 · Test-first, medium risk

Context. SARIF ingestion is the one small unknown, de-risked by the spike. Decision. TDD; medium risk tolerance (a shade above 112/113/114 for the SARIF leg). Consequences. + Regression-guarded. − None material.

10 · Risks & mitigations

An enforcer that does not emit SARIF

Likelihood medium, impact low. Mitigation: the native detectors stand alone; SARIF is additive. The ceiling (enforcer must be configured to emit SARIF) is recorded in D-003; a non-SARIF format is a bounded reader addition, not a redesign.

Foreign execution creeping onto the verdict path

Likelihood low, impact high. Mitigation: the no-exec import-graph test (D-005) fails the day a child_process import appears.

Regex content detection false positives/negatives

Likelihood medium, impact low. Mitigation: the pattern is author-declared per rule; the verdict is a merge gate a human reviews, and the type-graph precision lives in the ingested enforcer, not the regex.
