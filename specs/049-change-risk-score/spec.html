Change-risk score

A deterministic scan that flags and scores the capability a diff adds, so a change's footprint gets a human look.

1 · Context

A spec-clean change can still hide malice in the plan, tasks, or code, and spectastic scans none of it — it has no risk primitive. The supply-chain-integrity research concluded plainly that detecting an xz-style backdoor is undecidable and no tool should claim otherwise. What it can do cheaply is surface the capability a diff adds — a binary blob, a build-script or packaging edit, an install hook, a high-entropy payload, a new dependency — the signals the xz campaign threw off. That forces a human to look; it raises the attacker's cost without pretending to close the door.

The users are the engineer checking a diff before committing and the reviewer / CI gating a merge. This spec is P-12's guarantee half, staged cheap-first.

2 · User scenarios & testing

Each story is independently testable — US1 alone is a viable MVP.

US1 · See a diff's footprint before committing P1

As an engineer, I want to run spectastic change-risk on my uncommitted changes so that I see whether the diff touches more than I intended before I commit it.

Acceptance: on a diff that adds a binary and edits a CI workflow, it prints two findings (binary-blob = high, build-script = medium), a score, and a band; a docs-only diff prints zero findings, score 0, green, exit 0.

US2 · Surface the score at review / CI time P2

As a reviewer or CI pipeline, I want the scan to run against the change under review and report a score so that changes whose footprint exceeds their purpose get a human look.

Acceptance: a CI job runs change-risk --range <base>..HEAD, prints findings + score + band, and — with no threshold configured — exits 0 (advisory).

US3 · Opt into a failing threshold P3

As a security-conscious maintainer, I want to set a score threshold that fails the build so that a red-band change can't merge without a deliberate acknowledgement.

Acceptance: with changeRisk.failAt: 60 set, a diff scoring 70 exits non-zero and fails the CI job; the same diff with no failAt exits 0.

Edge cases

  • Empty diff → zero findings, score 0, green, exit 0.
  • Not a git repo, or an invalid --range → a clear error and a non-zero exit; never a silent pass.
  • A routine dependency bump → only the low-weight new-dependency flag; advisory, does not block unless failAt is set.
  • An expected binary (a test fixture) → still flagged; per-finding suppression is deferred.
  • Absent or malformed changeRisk config → the scan still runs advisory, never silently skipped (NFR-004).

3 · Requirements

Conformance keywords (MUST, SHOULD, MAY) follow RFC 2119.

Functional

A change-risk CLI subcommand MUST read a git diff and print its findings, a score, and a band. Its output MUST state that it surfaces risk for review and does not detect or certify safety.

The scan MUST detect five red-flag categories: a binary/opaque blob added, a build-script / CI / packaging edit, an install or post-install hook, a high-entropy or base64 payload, and a new dependency.

Each finding MUST carry a weight tier: high for an install hook, a binary blob, or an entropy blob; medium for a build-script / CI / packaging edit; low for a new dependency.

Rationale

A routine dependency bump must not score like an install hook.

The scan MUST emit a composite 0–100 change-risk score, a risk-weighted aggregation of the findings, and MUST map it to a green / amber / red band.

The band thresholds MUST be configurable in spectastic.json, shipping defaults (green < 25, amber 25–60, red > 60) when unconfigured.

The command MUST be advisory by default — reporting findings and score, exiting 0, never failing a build or blocking a commit — unless an opt-in threshold is configured.

An opt-in changeRisk.failAt score in spectastic.json SHOULD cause a non-zero exit when the score meets or exceeds it, so a CI job can gate on it.

With no range given, the scan MUST default to the uncommitted local diff (working tree + staged); a --range <base>..<head> flag MUST select an explicit range for CI use.

A CI job SHOULD run the scan against the change's base (merge-base with the default branch), reusing the security-review job pattern; advisory unless failAt is set.

Non-functional

The scan MUST be deterministic: the same diff yields byte-identical findings and score across runs and machines, with no network calls and no dependence on the clock or a random source.

Detection MUST be language-agnostic — file paths, diff structure, and content patterns, not any per-language toolchain — so it runs on any repository.

The scan SHOULD complete on a 1,000-line diff in under 2 seconds at p95, in-process.

Absent or malformed changeRisk configuration MUST fall back to running the scan and reporting advisory findings — never silently skipping it (secure-by-default, per P-9).

Out of scope (deferred to other slices)

  • Slice 2 — the spec-anchored capability/scope-delta at the coding-drain hook, scoring a task's footprint against what its authorized spec sanctioned. The headliner; its own sibling spec.
  • Per-finding allowlist / suppression — needed once a team gates on failAt, not for the advisory v1.
  • Call-graph capability analysis (Capslock-style) — an advisory ceiling, language-limited.
  • LLM semantic intent-vs-code review — non-deterministic and itself attackable; never a sole gate.
  • Spectastic's own build-layer provenance (reproducible builds, hash-pinned Actions) — a separate track.

4 · Data model

Three entities, all in-memory and per-run — nothing is persisted.

Entities

RedFlagFinding
category (one of the five), weight (high / medium / low), file path, evidence (the matched line or reason).
ChangeRiskReport
findings[], score (0–100), band (green / amber / red), and the resolved exitCode.
changeRisk (config)
Optional spectastic.json section: bands (amber / red thresholds) and failAt (opt-in gate score). Absent → defaults + advisory.

The score is derived from the findings and their weights — never authored, never stored (NFR-001).

5 · Success criteria

Technology-agnostic, measurable outcomes. These are how we know it worked.

On a fixture diff adding a binary blob and editing a CI/build file, the scan reports exactly those two findings with the right tiers (high, medium), a 0–100 score, and the matching band — identical on a repeat run.

A docs-only / no-capability diff produces zero findings, score 0, the green band, and exit 0.

With no changeRisk.failAt set, the command exits 0 for any score; with failAt at or below the score, it exits non-zero.

The scan completes on a 1,000-line diff in under 2 seconds at p95 with no network access observed.

6 · Assumptions

The scan runs inside a git repository and can obtain a diff (working-tree, staged, or a range) via git — the assumption the coding drain's worktree sandbox already makes.

The v1 weight tiers and default bands are reasonable starting points, not calibrated truth — hence opt-in gating.
