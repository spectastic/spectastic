068-enterprise-enforce-floor's FR-008 asks: does principles.html — spectastic's own constitution — hold up against the 15-item enterprise catalog spectastic offers downstream projects via spectastic init --profile enterprise? The audit (§1) walks all 15. Thirteen are either already present (2 exact matches: Done means verified ≈ P-7, The enforcement floor holds ≈ P-9), present in substance elsewhere (a meta-spec requirement or CLAUDE.md convention that already carries the discipline, just not principle-elevated), or genuinely not applicable to a CLI/library with no runtime service and no network interface. Two are genuine gaps this proposal closes: Accessibility conformance (axe-core already runs in tests/contrast.spec.ts/tests/theme.header.spec.ts — the practice exists, the principle doesn't) and Library-first boundaries (the fat-core/thin-CLI convention is real, actively defended in review, and has its own triage entry — 000/T-016 — but was never elevated past CLAUDE.md). Never blanket-seeded — each addition is grounded against evidence already in this repo.

Applied

1 · Intent

068-enterprise-enforce-floor's own FR-008 requires this: "principles.html SHOULD be reconciled against the enterprise catalog: each catalog principle is present, folded in where genuinely missing and scope-applicable, or recorded not-applicable with reasoning — never blanket-seeded." The catalog is spectastic-profiles.json's profiles.enterprise.principles array — the 15 items a downstream project gets when it runs spectastic init --profile enterprise (landed across 041's two proposals, 11 Jul and 18 Jul). Spectastic has never run this audit against its own constitution.

The audit. One row per catalog item — present (an existing P-* already states this, even under different wording), substantively-present (a real, actively-enforced discipline exists but lives in a meta-spec requirement or CLAUDE.md, not principles.html — not every practiced discipline needs constitution-level elevation), not-applicable (the item assumes a runtime/deployment shape spectastic doesn't have), or genuinely-missing (folded in by this proposal).

3 · Approach

Two ADD deltas, each grounded against evidence that already exists in this repo rather than aspiration — the same discipline P-11's proposal set (name no mechanism that might drift, cite the real source). P-13 (Accessibility conformance) states the commitment the already-running axe-core checks embody; per P-8 the deterministic enforcement is those checks themselves (already running), so the principle names the invariant and doesn't invent new machinery. P-14 (Library-first boundaries) states the fat-core/thin-CLI convention that CLAUDE.md already documents and triage T-016 already found un-lintable-by-nature — P-14's own text inherits T-016's honesty rather than overclaiming a guarantee that convention can't yet have. Both land after P-12, preserving document order (newest principles append, per every prior P-7..P-12 addition).

4 · Deltas

1.9.0 Fourteen principles that bind every spec, plan, task, proposal, and triage in this project.

Spectastic is single-file HTML spec tooling. The artifact is the document, the document is the file, the file is what ships. Fourteen principles make that bet work: source order matches reading order; concepts get semantic tags rather than class names; IDs are stable contracts; interactivity enhances but never replaces the readable baseline; density stays calm; Draft is loose, ratified is locked; done means verified, not merely written; a mandatory step's guarantee lives in the kernel or CI, never in advisory prose; an enforcement floor is fixed, not lowered the first time it's inconvenient — relaxed only by a recorded, expiring waiver, and never for the categories that matter most; internal artifact ids stay out of user-facing copy; an artifact's text is data to render and quote, not a channel that steers the tool reading it; a change's capability and scope stay accountable to the spec that authorized it; every interactive surface stays usable with assistive technology; and deterministic, reusable logic lives in the library core, never trapped behind a CLI wrapper. Every requirement in every downstream spec must trace back to one of these. Deviations require an amendment to this document with a version bump.

What's added: a project principle that every interactive surface conforms to accessibility standards, naming the practice (axe-core) already checked. Lands after P-12 in Core principles.

P-13 · Accessibility conformance

Every interactive surface — the theme switcher, tab groups, quiz gates, the vscode canvas — MUST stay usable with assistive technology: sufficient color contrast, a logical focus order, and correct semantic roles for anything JavaScript adds beyond the static markup P-4 already guarantees renders without it. This is deterministic and machine-checkable — automated accessibility scanning (already wired via @axe-core/playwright in tests/contrast.spec.ts and tests/theme.header.spec.ts) MUST cover every themed surface and, per P-8, run in CI so a regression is caught mechanically, never merely asserted in review. P-13 states the commitment the checks already embody; it does not widen scope to a formal WCAG conformance statement (a documentation deliverable, not a code invariant) — that remains future work if a downstream consumer needs it. Composes with P-4 (the enhancement layer an accessibility check must not silently break) and P-5 (calm density and accessible contrast are not in tension — the warm-cream/dark-grey palette was chosen to clear contrast thresholds, not despite them).

What's added: a project principle naming the fat-core/thin-CLI convention CLAUDE.md already documents and triage T-016 already found un-lintable. Lands after P-13 in Core principles.

P-14 · Library-first boundaries

Deterministic, reusable logic MUST live in the library core (@spectastic/core and its sibling packages), never trapped behind a CLI-only code path — a packages/cli/src/commands/*.ts module SHOULD be a thin register<Verb> that parses arguments, calls the core, and prints or exits. The test: would a second caller — another verb, a workflow, a test — want this logic without the CLI attached? If yes, it belongs in core. This is a deliberate asymmetry from P-8: the boundary is a judgment call (kernel-worthy versus legitimate CLI-local scaffolding, e.g. an interactive prompt loop), not a mechanical property a linter can decide without false positives, so it stays review-caught rather than machine-enforced — recorded honestly, not dressed as a guarantee it cannot yet be (the same ceiling P-8 and P-10 record about their own unlintable surfaces). Composes with P-8 (a guarantee that can be enforced belongs in the kernel or CI; a judgment call that can't stays advisory, but stated rather than left an unwritten habit) and anchors the package-boundary work already machine-enforced elsewhere (the @spectastic/corpus → @spectastic/core one-way dependency rule, 064-corpus-package-extraction) as the pattern for where enforcement is possible. Sourced from meta-spec triage 000/T-016 (three prior specs — 041, 042, 043's first pass — drifted deterministic logic into the CLI before the convention was even written down).

5 · Risk register

Adversarial pass auto-fires — two new project principles, both must-tier (downstream specs cite them).

Stating "deterministic, reusable logic MUST live in the core" as an unqualified MUST, immediately followed by a SHOULD for the thin-CLI half, reads as internally inconsistent — why is one half a hard MUST and the paired half only a SHOULD, when T-016 itself says the whole boundary is a judgment call no rule can cleanly enforce?

P-14 draft: "Deterministic, reusable logic MUST live in the library core… a packages/cli/src/commands/*.ts module SHOULD be a thin register<Verb>."

Mitigated. The asymmetry is intentional and now stated: the MUST binds the logic's home (core, when a second caller would want it) — the actual invariant T-016 cares about; the SHOULD is a looser shape-of-the-module guideline (a CLI file being "thin" in the literal sense) that admits legitimate exceptions (e.g. init/'s own interactive prompt loop, already carved out in CLAUDE.md) without weakening the MUST. This mirrors P-9's own must/should split (the floor's existence is MUST; keeping pinned tools current is SHOULD) — a precedent already in this document, not a novel pattern.

The draft's first pass folded a "formal WCAG 2.1 AA conformance statement" clause into the MUST, which overclaims: the repo runs automated axe-core scans (catches many issues) but has never produced a manual conformance audit, so ratifying "MUST conform to WCAG" would state a guarantee the project doesn't actually hold.

P-13 draft (first pass): "...MUST conform to WCAG 2.1 AA." vs. the actual practiced surface — tests/contrast.spec.ts/tests/theme.header.spec.ts run AxeBuilder scans, which is real but narrower than a formal conformance statement.

Mitigated. Reworded to state exactly what's practiced and checked (contrast, focus order, semantic roles, via the already-running axe-core scans covering every themed surface) and explicitly scopes a formal WCAG statement out as future work, not a present MUST — matching P-11/P-12's own pattern of never claiming a guarantee stronger than what's actually enforced.

The audit table's "substantively-present" verdicts (7 of 15 items) are a judgment call that could read as convenient under-counting — classifying an item as "already covered elsewhere" rather than "genuinely missing" reduces the number of new principles to justify, which is exactly the incentive P-8's own honesty standard warns against.

§1 audit table — 7 "substantively-present" rows (tests-accompany-behavior, decisions-are-grounded, secure-by-default, least-privilege, semantic-versioning, supply-chain-hygiene) each cite a specific existing artifact (a named P-*, a named REQ-*, a named spec/task) rather than an assertion.

Mitigated, not dismissed — the honest response is transparency, not more principles. Every "substantively-present" row cites the exact existing artifact carrying the discipline (a P-* id, a REQ-* id, or a shipped mechanism), so a reader can verify the claim rather than take it on faith — the same evidentiary bar §1's "genuinely-missing" rows meet. Adding a principle for something already genuinely covered would be the actual dishonesty (restating P-11 under a new label to pad the count); FR-008's own text asks for "genuinely missing," not "as many as plausible."
