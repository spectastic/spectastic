Add P-9 — The enforcement floor holds

Applied

1 · Intent

041 lets a project pick an enforcement profile; 042 turns that profile's floor into a gate (spectastic enforce). But nothing said what to do when a gate tool breaks. On a dogfooded Enterprise/Java project (T-014), a pinned Error Prone 2.36 failed on JDK 26 and the reflexive fix was to disable it — the exact move that hollows out the floor the profile promised. A bump to 2.50 resolved it (and likely the sibling SpotBugs/Spotless pins). The gap is a missing project-wide invariant: weakening a gate is a last resort, not a first response. Because this reflex can occur under any profile and against any tool, it belongs at the constitution — not only in 042's command or 041's profile data.

3 · Approach

A single ADD delta in the voice of P-7/P-8 (both enforcement-discipline principles, so P-9 sits naturally beside them). MUST: fix-before-disable. MUST: any weakening is explicit and recorded. SHOULD: keep pinned gate dependencies current enough to run. It composes with P-7/P-8 rather than overlapping: P-7 is what "done" means, P-8 is where a guarantee lives, P-9 is that a live guarantee is not quietly switched off. Forward-only from v1.4.0.

4 · Deltas

What's added: a project principle that a failing enforcement gate is fixed before it is disabled. Lands after P-8 in Core principles.

P-9 · The enforcement floor holds

An enforcement gate exists to catch defects; weakening it is a defect in waiting. When a gate tool fails — a version incompatibility, a new toolchain, a false positive — the first response MUST be to fix the gate (bump the tool, adjust its config, pin a known-good version), not to remove it. Disabling or loosening a gate MUST be a last resort that is explicit and recorded. Pinned enforcement dependencies SHOULD be kept current enough to run against the project's actual toolchain. Composes with P-7 and P-8: a gate you turned off proves nothing.

5 · Risk register

Adversarial pass auto-fires — adding a project principle is must-tier (downstream specs cite it).

Read absolutely, P-9 forbids legitimately removing a redundant or deprecated gate

Concern. "Fix before remove; disabling is a last resort" could be read as "never remove a gate," blocking the removal of a genuinely redundant, superseded, or wrong tool — turning the floor into a ratchet that only tightens.

Mitigated. The wording is "last resort that is explicit and recorded," not "never." Deliberate removal with a recorded rationale is permitted; what P-9 forbids is the silent, reflexive switch-off as the first response to inconvenience.

P-9 is a dev-practice rule, off-theme from the artifact-design principles

Concern. P-1..P-5 govern the HTML spec artifact; a software-enforcement-discipline principle could read as scope creep in the constitution.

Mitigated. P-7 (verification discipline) and P-8 (guarantee location) already established enforcement-discipline principles; P-9 sits with them, not with P-1..P-5. Forward-only, so no retroactive re-audit.
