Add P-7 — Done means verified

Applied

1 · Intent

The lifecycle is rich at the front — spec.html carries measurable success criteria, per-story acceptance, an INVEST self-check; tasks.html is test-first — but it has never named a single, non-negotiable bar for done. The bar exists in practice: CLAUDE.md § Verification discipline says interactive HTML needs a browser-level test, that "presence ≠ containment", that a green structural check is not "verified" for anything with a runtime, and that the linter is not noise. But it is guidance nothing traces to, so a spec's success criteria can pass without ever clearing it.

The cost is paid and on the record. 019-explain-course's quiz gate shipped a closure-over-var bug that marked only the last objective; the SC-003 test asserted only that the gate script existed, so it went green. A human opening the artifact caught it. 020's canvas nodes and hover card passed every "it renders" check and were still visibly cropped. The fix each time was a behaviour-level test — but only because someone remembered the discipline, not because anything required it. Elevating it to a principle makes the bar greppable, citable from any spec's success criteria, and load-bearing rather than optional.

3 · Approach

Single ADD delta. P-7 follows the shape of P-1..P-6: a short heading + a body that states the constraint and its consequence, phrased as a positive assertion of what "done" requires rather than a list of prohibitions. It names the bar in three clauses — tests pass, spectastic validate clean, runtime exercised — and draws the line the 019 regression taught: a green structural check on something with a runtime is not "done".

The runtime clause is deliberately medium-aware, not browser-only: interactive HTML is exercised in a browser (the 019/020 lesson), while a CLI or library is exercised in its own test harness. This avoids over-narrowing the principle to the HTML artifacts and keeps it true for the kernel/CLI packages, which have runtimes but no browser. P-7 references the verification discipline in CLAUDE.md for the agent-facing detail rather than inlining a toolchain that will drift.

4 · Deltas

What's added: a new project principle making verification the definition of done. Lands in principles.html's Core principles section, after P-6.

P-7 · Done means verified

An increment is not done because the code exists; it is done when it is verified. The bar: its tests pass, spectastic validate is clean, and any artifact with a runtime has been exercised — interactive HTML in a browser (not merely asserted present: presence ≠ containment), a CLI or library in its own test harness. A green structural check on something with a runtime is not "done"; a behaviourally-broken-but-present enhancement passes every string assertion. Every downstream spec's success criteria MUST trace to this bar, and the authoring/verification toolchain MUST NOT report an interactive artifact verified on structural evidence alone.

The agent-facing detail — Playwright for interactive artifacts, the cheap structural backstop in vitest, containment-and-on-screen-bounds over mere render, the linter-is-not-noise rule — lives in CLAUDE.md § Verification discipline and is the canonical elaboration of this principle. P-7 names the bar; CLAUDE.md says how to clear it.

5 · Risk register

Adversarial pass auto-fires per the propose-time heuristic — adding a project principle is foundationally must-tier (downstream specs will cite P-7, so a wrong P-7 cascades). Three findings below. The two wording forks (R-1, R-2) were anchored with the author before drafting and the chosen wording resolves them; R-3 is folded into the principle body. Status starts at identified; the author response records the commitment.

Mandating "every feature ships a verify.html" binds the principle to an unbuilt mechanism

Concern. The verify brief's draft P-7 ends "…and every feature ships a verify.html that says how a human confirms it." But verify.html is itself only a draft design brief (verify-considerations.html, status Draft, TBD-verify-spec) — no verb produces it. Ratifying a principle that mandates an artifact nothing generates makes every existing and new feature instantly non-conformant against a bar no tooling can satisfy. A principle that can never be met is unenforceable, and principles are non-negotiable per the header.

30-day frame. Within 30 days a new spec's principles check flags "no verify.html" as a P-7 violation the author cannot fix (the generator doesn't exist), forcing either a P-7 errata or a rushed verify.html spec — the heavier path the brief explicitly warned against ("the principle could land first and stand alone").

Author response. Accepted; resolved before drafting. P-7 asserts the bar only (tests pass / validate clean / runtime exercised). The "ships a verify.html" sentence is removed from the principle and the mechanism is deferred to TBD-verify-spec (see §2 Out of scope). The principle now stands alone and is satisfiable today. Committed mitigated.

"Anything with a runtime … in a browser" over-narrows to HTML and excludes the CLI/kernel

Concern. The brief's draft says "anything with a runtime has been exercised in a browser." But the @spectastic CLI and kernel packages have runtimes with no browser — they are exercised in vitest/CLI harnesses. A literal reading makes every CLI feature non-conformant (it was never "exercised in a browser") while the actual 019/020 lesson was specifically about interactive HTML. The clause conflates the medium of the lesson with the universal bar.

30-day frame. A CLI feature spec is told its success criteria don't trace to P-7 because nothing ran "in a browser", even though its terminal/test-harness verification is exactly right; the contradiction surfaces as a defect against P-7's wording.

Author response. Accepted; resolved before drafting. The runtime clause is medium-aware: interactive HTML in a browser, a CLI/library in its own test harness. The principle binds the bar (runtime exercised, not structurally asserted) without prescribing the browser for non-HTML runtimes. Committed mitigated.

P-7 risks duplicating — and drifting from — the CLAUDE.md verification detail

Concern. The discipline already exists in prose under CLAUDE.md § Verification discipline (Playwright specifics, the structural backstop, the containment rule, the linter rule). If P-7 restates that detail it becomes a second copy that drifts the moment CLAUDE.md changes — the exact failure mode the verify brief itself rails against (generate/reference, don't copy). But if P-7 says too little, it loses the teeth the 019 regression showed were necessary.

30-day frame. Someone updates the Playwright guidance in CLAUDE.md; P-7's inlined copy now contradicts it, and a reviewer can't tell which is authoritative.

Author response. Folded into the wording. P-7 names the bar and the one load-bearing rule ("structural check ≠ done", "presence ≠ containment") and explicitly points at CLAUDE.md § Verification discipline as "the canonical elaboration" for the toolchain detail. One source of truth for the detail; the principle references rather than copies it. Committed mitigated.
