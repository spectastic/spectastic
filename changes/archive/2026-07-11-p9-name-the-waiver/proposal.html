"Explicit and recorded" now has a mechanism: a per-category waiver with a reason, an owner, and an expiry — and a floor that some categories can never leave.

P-9 ("The enforcement floor holds") already requires that loosening a gate be "explicit and recorded … never a silent convenience", but it named no mechanism — so a reader knew the rule and not the shape. The 042 change 2026-07-11-relax-a-requirement built that shape: a per-category enforcement waiver (in the project's config) carrying a justification, an owner, and a mandatory expiry, which demotes a floor category to an advisory warning in its own relaxed tally rather than silently dropping it — and an un-relaxable floor (enterprise: security + supply-chain) no waiver can weaken. This amendment folds that mechanism into P-9 so the principle and the tool agree: the coupled half the 042 proposal flagged.

Applied

1 · Intent

This is the coupled principles half of the 042 change 2026-07-11-relax-a-requirement, which added a per-category enforcement waiver so a team can deliberately relax one floor category without the gate silently going dark. P-9 is the principle that governs exactly that act — "Disabling or loosening a gate MUST be a last resort that is explicit and recorded … never a silent convenience" — but until now it named no mechanism, so the "recorded" form was left to a comment or a tracked issue. The 042 change makes it concrete: a structured, expiring, owned waiver that warns in its own tally. Naming that mechanism in P-9 closes the gap between the principle and the tool so they read as one thing, which is the whole point of the request that prompted this (principles and enforcement should align intuitively).

P-9 · The enforcement floor holds

An enforcement gate exists to catch defects; weakening it is a defect in waiting. When a gate tool fails — a version incompatibility, a new toolchain, a false positive — the first response MUST be to fix the gate (bump the tool, adjust its config, pin a known-good version), not to remove it. Disabling or loosening a gate MUST be a last resort that is explicit and recorded — a comment, a changelog line, a tracked issue — never a silent convenience. For the profile enforcement floor specifically, that recorded form is a structured waiver: a per-category entry in the project's configuration carrying a justification, an owner, and a mandatory expiry, which demotes the category to an advisory warning surfaced in its own tally rather than silently dropping it — and the highest-risk categories a profile chooses to protect (MUST include security and supply-chain at the enterprise tier) are un-relaxable, so no waiver can weaken them. Pinned enforcement dependencies SHOULD be kept current enough to run against the project's actual toolchain. The floor a profile promises (041) is only real if it isn't quietly lowered the first time it's inconvenient; this is the discipline the enforcement gate (042) protects and the enterprise profile seeds. Composes with P-7 (done means verified) and P-8 (guarantees live where they can't be skipped): a gate you turned off proves nothing.
