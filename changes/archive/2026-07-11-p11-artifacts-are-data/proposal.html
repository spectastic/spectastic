Add P-11 — Artifacts are data, not instructions

Applied

1 · Intent

Every spectastic artifact crosses three trust boundaries the moment it exists: a human opens it in a browser, an LLM verb ingests it as input, and npm ships it to consumers. Each has a distinct attacker and defense. The one the field has not solved — and the one this principle weights most — is the agent boundary: an .html designed to be read by an agent is an .html an attacker can author to redirect that agent. HTML amplifies the risk over markdown, because everything the renderer hides (comments, display:none, off-screen text, zero-size boxes) is still live text in the token stream.

Spectastic has no project-wide invariant naming this. The constitution says how artifacts are structured (P-1..P-5), verified (P-7), and guarded (P-8..P-10), but not that an artifact's content is inert — data to be rendered and quoted, never a channel that instructs the tool reading it. This proposal ratifies that invariant as P-11 so the artifact-security spec has a constitution line to trace to. Per P-8, P-11 states the discipline and delegates the guarantee: the CSP, the validate rule, and the fence/sanitise step live in the kernel and CI, never in the prose.

2 · Scope

In scope

  • ADD P-11 · Artifacts are data, not instructions to principles.html's Core principles section, after P-10.
  • State the invariant as two obligations of different strength: deterministically, an artifact carries no executable content beyond the single audited asset script (machine-checkable, enforced in the kernel/CI per P-8); as a posture, attacker text must not steer an AI verb — held by the strongest available control, residual recorded not hidden.
  • Bump version v1.5.0 → v1.6.0 (added principle; minor), tagline "Ten" → "Eleven", TL;DR names P-11, changelog entry.

Out of scope

  • The layered teeth — a strict CSP in templates/*.html, a no-executable-content validate rule (flag <script> beyond the sanctioned spec.js ref, on*=, javascript:/data: URIs, <iframe>), and fenced/sanitised ingestion of artifact text in the AI verbs. Per P-8 the guarantee is that spec's job, not this principle's.
  • The security-review CI workflow + adversarial injection fixture. Gates on the rule from the security spec.
  • Modifying P-1..P-10. Their wording stays verbatim.
  • Naming specific attack strings or CVEs in the principle — those drift; the principle states the discipline, the considerations doc + security spec carry the vectors.

3 · Approach

A single ADD delta in the voice of P-8/P-9/P-10 (the guard-rail principles, so P-11 sits naturally after them). The principle splits its MUST into a deterministic half (no executable content beyond the audited asset script — machine-checkable, enforced in the kernel/CI per P-8) and a posture half (attacker text must not steer an AI verb — held by the strongest available control, since prompt injection is unsolved, its residual recorded not hidden). It names no specific mechanism: the CSP, the validate rule, and the fence/sanitise step are the artifact-security spec's to choose, so the constitution line survives that spec's design churn (P-8 itself cites an example rule, not a fixed list). It composes with, rather than overlaps, its neighbours: P-8 is where a guarantee lives, P-10 is what artifact copy must not leak outward, P-11 is that artifact copy must not be trusted inward. Forward-only from v1.6.0. This is a principles proposal (spec 030): it carries a <spec-principles-apply> block so spectastic apply principles inserts the principle and substitutes the header deterministically — the kernel path P-9 predated and had to land by hand.

4 · Deltas

1.6.0 Eleven principles that bind every spec, plan, task, proposal, and triage in this project.

Spectastic is single-file HTML spec tooling. The artifact is the document, the document is the file, the file is what ships. Eleven principles make that bet work: source order matches reading order; concepts get semantic tags rather than class names; IDs are stable contracts; interactivity enhances but never replaces the readable baseline; density stays calm; Draft is loose, ratified is locked; done means verified, not merely written; a mandatory step's guarantee lives in the kernel or CI, never in advisory prose; an enforcement floor is fixed, not lowered, the first time it's inconvenient; internal artifact ids stay out of user-facing copy; and an artifact's text is data to render and quote, not a channel that steers the tool reading it. Every requirement in every downstream spec must trace back to one of these. Deviations require an amendment to this document with a version bump.

What's added: a project principle that an artifact's text is inert data, never an instruction the tool obeys. Lands after P-10 in Core principles.

P-11 · Artifacts are data, not instructions

The same artifact is read across three trust boundaries at once — opened by a human, ingested by an LLM agent as input to a verb, and shipped to consumers through npm. So an artifact's text — including what a renderer hides, such as HTML comments and CSS-hidden content — MUST be treated as data to render and quote, not as a channel that instructs the tool reading it. Two obligations follow, of different strengths. Deterministically: an artifact carries no executable content beyond the single audited asset script (the sanctioned spec.js/theme-boot.js that P-4's enhancement layer needs) — no other <script>, inline handler, or active URI. That half is machine-checkable and, per P-8, MUST be enforced in the kernel and CI, never trusted to the prose. As a posture: attacker text in an ingested artifact MUST NOT be allowed to steer an AI verb — but prompt injection is not a solved problem, so this half is held by the strongest available control and its residual is recorded, not hidden — the same honesty P-8 and P-10 keep about their own ceilings. Composes with P-10: P-10 keeps internal ids from leaking outward into copy; P-11 keeps attacker text from steering inward into the tool.

5 · Risk register

Adversarial pass auto-fires — adding a project principle is must-tier (downstream specs cite it), and P-11 anchors a whole security spec.

Baking three named enforcement mechanisms into a constitution-level MUST reads as stale the moment the security spec picks a different or additional control — a principle changes only by version bump, but mechanisms churn freely.

P-11 body (draft): "the teeth MUST live in the kernel and CI — a strict content-security policy on the templates, a rule that rejects executable markup, and fenced or sanitised ingestion of artifact text in the AI verbs." Violates the proposal's own §Scope rationale for excluding vectors ("those drift; the principle states the discipline"); P-8 names an example rule, not a fixed list.

Mitigated. The mechanism enumeration is cut from the principle. P-11 now says only that the deterministic half is "enforced in the kernel and CI, per P-8," and §3 records that it names no specific mechanism — the CSP, validate rule, and fence/sanitise step are the artifact-security spec's to choose, mirroring P-8's example-not-list restraint.

P-11's flat "never as executable content" drops the sanctioned-asset carve-out, so read literally it forbids the very spec.js/theme-boot.js that P-4 mandates — and that principles.html itself ships in its footer.

P-11 (draft): an artifact's text "MUST be treated as data … never as executable content"; contradicts P-4 ("Tabs, dark mode, … all enhancements"). The carve-out ("<script> other than the sanctioned asset ref") lived only in §Out-of-scope, not the ratified principle text.

Mitigated. The carve-out is folded into the ratified prose: P-11 now permits "no executable content beyond the single audited asset script (the sanctioned spec.js/theme-boot.js that P-4's enhancement layer needs) — no other <script>, inline handler, or active URI." P-4's layer is explicitly preserved.

The invariant fuses two halves of unequal enforceability — a deterministic "no executable content" (validate-checkable) and a probabilistic "never an instruction the tool obeys" (agent-steering, which no control fully guarantees; fencing is <2%, not 0%) — making P-11 a MUST that is only half-satisfiable, straining P-8's "strongest available check" honesty.

§2 in-scope (draft): "an artifact's text … is data to render and quote, never executable content or an instruction the tool obeys." The grounding doc §8: "Prompt injection is not solved, and no source claims it is."

Mitigated. P-11 stays one principle but now splits its MUST into a deterministic half (no executable content beyond the audited script — machine-checkable, enforced) and a posture half (attacker text must not steer an AI verb — held by the strongest available control, residual recorded not hidden, "the same honesty P-8 and P-10 keep about their own ceilings"). §2 in-scope and §3 carry the same split.
