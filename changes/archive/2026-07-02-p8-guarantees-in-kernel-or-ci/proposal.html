Add P-8 — Guarantees live in the kernel or CI

A verb loaded as a skill is advisory. If a step must happen, its guarantee cannot live in the prompt.

Spectastic's verbs are slash-commands loaded as skills; their mandatory steps — the pre-verb decision interview, the post-verb git commit and §6 fold — are prose an LLM can skip. The whole reliability arc (T-004 skipped fold, T-006 stale copies, T-008 unreliable invocation) shares one root cause, confirmed by a ~20-source cross-tool survey: a step is guaranteed only when deterministic code the model can't skip runs it or rejects its absence. This proposal ratifies that as P-8 · Guarantees live in the kernel or CI. Add P-8 — Guarantees live in the kernel or CI

Applied

1 · Intent

Spectastic drives its lifecycle through slash-commands loaded as skills, and every command's procedure is markdown: "interview the user before writing", "commit after apply", "re-sync .claude/commands/", "fold §6 into tasks.html". A skill is advisory to the model — it can skip, reorder, or half-satisfy any of these — so none of those steps is guaranteed. That is not a tuning problem to be fixed with better wording; it is structural.

The cost is on the record, three times over. T-004: an apply skipped the §6 fold because the fold lived only in prose. T-006: the installed command copies drifted from source, so the executed procedure wasn't the current one. T-008: the verbs invoke unreliably because their descriptions are advisory. Two skill-creator eval pilots then confirmed descriptions cannot carry a reliability guarantee at all. A cross-tool survey (~20 primary sources) found the same law everywhere: across Cursor, Copilot, Windsurf, Cline, MCP, and Claude Code, a step is guaranteed only when a harness-invoked process can say deny; markdown, rules files, and MCP tool descriptions are all advisory. Spectastic already owns the deterministic layer — the kernel — where every reliable step (apply's fold and commit, the validate rules) already lives. This principle names where a guarantee must live, so the lifecycle stops writing guarantees into prose that can't hold them.

3 · Approach

Single ADD delta, following the shape of P-1..P-7: a short heading + a body that states the constraint and its consequence. The load-bearing move is to split the guarantee by the step's nature, because the two kinds can't be enforced the same way. A mandatory side effect (a commit, a fold, a status flip) is pure code — a deterministic owner just runs it, model-independent. A mandatory judgment step (the decision interview) can't be forced: a marker the model writes to pass a gate is one it can fake. So the enforcement is honest about its limit — reject the artifact where a skip leaves detectable residue (an unresolved <spec-question> failing validate + CI), and fall back to an independent review pass (the adversarial critic, or a human) where it leaves none. The principle does not claim a mechanism can force good judgment; it forbids presenting prose as the guarantee. This keeps P-8 satisfiable today: it does not demand every step become a kernel function, only that a step whose omission is a defect have a deterministic owner, a checkable rejection, or — for irreducibly-judgment steps — the strongest available review.

Per the anchored decisions, P-8 stays the invariant and defers the mechanism (validate --strict, init --tools) to TBD-guarantee-layer-spec — avoiding the P-7 trap of coupling a ratified principle to unbuilt tooling. Forward-only, so the existing lifecycle (which still carries markdown steps) is not declared broken overnight.

4 · Deltas

What's added: a new project principle placing the guarantee for any mandatory step in the kernel or CI, never in command markdown. Lands in principles.html's Core principles section, after P-7.

P-8 · Guarantees live in the kernel or CI

A step whose omission is a defect MUST NOT rely on command markdown as its guarantee. A verb loaded as a skill is advisory: the model can skip, reorder, or half-satisfy any instruction in the prompt, so command markdown, skill descriptions, and rules files guide but never enforce. The enforcement takes one of two shapes by the step's nature. A mandatory side effect (a git commit, a §6 fold, a status flip) MUST have a deterministic owner — the kernel, or a CI/VCS gate — that runs it regardless of model cooperation. A mandatory judgment step (the decision-phase interview) cannot be forced: the model that half-performs it is the same one deciding whether to record a gap, so a marker it writes to pass a gate is one it can fake. P-8 therefore requires the strongest available check, not a pretence of one — where a skipped judgment leaves detectable residue in the artifact (an unresolved <spec-question>), a checkable rule MUST reject it (spectastic validate + CI); where it leaves none, the backstop MUST be an independent review pass (the propose-time adversarial critic, or a human), never a self-issued marker. P-8 does not claim any mechanism can force good judgment; it forbids presenting prose as the guarantee and requires deterministic enforcement wherever the step admits it.

Advisory guidance stays permitted and encouraged: CLAUDE.md elaborating how to clear a bar is guidance, not a guarantee — P-8 forbids only placing the guarantee itself in prose. P-8 (where guarantees live) composes with P-7 (what "done" means): they share the validate/CI infrastructure without duplicating ownership. The invariant is satisfiable today — the kernel already owns apply's commit and §6 fold, and validate already carries checkable rules (e.g. skill-metadata-shape); P-8 generalizes that existing pattern and binds new work to it. The concrete strict-CI gate and per-harness hook installer are its immediate next spec (TBD-guarantee-layer-spec); the cross-tool survey is docs/guarantee-layer-considerations.html and the finding is meta-spec triage T-009. Forward-only: P-8 binds new and amended specs from v1.3.0; it does not retroactively re-open specs 001–029.

5 · Risk register

Adversarial pass auto-fires per the propose-time heuristic — adding a project principle is foundationally must-tier (downstream specs will cite P-8, so a wrong P-8 cascades). Findings below; status starts at identified and the author response records the commitment. The two decidable forks (retroactivity; invariant-vs-mechanism) were anchored with the author before drafting.

The judgment-step guarantee is self-defeating — it rejects fakeable markers, then relies on one

Concern. The original body opened with an absolute MUST ("a step whose omission is a defect MUST have a deterministic owner") and then named the judgment-step guarantee as "an unresolved <spec-question> failing validate." But the absence of an open question is exactly the fakeable marker the same sentence disavows: the model that half-does the interview also decides whether to leave a question open, so a shallow-but-tidy interview passes the gate. Stated as a MUST cited by every downstream spec, an unsatisfiable clause quietly erodes all eight principles. 30-day frame: the first mandatory judgment step whose omission leaves no artifact residue forces either a theater marker (the anti-pattern P-8 disavows) or a self-declared non-conformance to a MUST that can't be met.

Mitigated (author-committed). Reworded to remove the self-defeat. The opening MUST is now "MUST NOT rely on command markdown as its guarantee" (satisfiable). Side effects get a deterministic owner (hard MUST); judgment steps get "the strongest available check, not a pretence of one" — reject on detectable residue, and where a skip leaves none, an independent review pass (the adversarial critic or a human), explicitly "never a self-issued marker." P-8 now states plainly it "does not claim any mechanism can force good judgment."

P-8 overlaps P-7 and, read literally, forbids P-7's "the how lives in CLAUDE.md prose" delegation

Concern. P-7 ("Done means verified") already locates enforcement in validate + tests, and its second paragraph explicitly delegates its how to advisory prose: "P-7 names the bar; CLAUDE.md says how to clear it… the canonical elaboration of this principle." P-8's judgment-step mechanism routes through the same validate/CI locus (shared ownership of the gate is ambiguous), and P-8's "a guarantee never lives in prose the model can skip" reads as making P-7's own delegation the forbidden anti-pattern. Neither principle says which governs on collision. 30-day frame: an author can't tell whether the open-<spec-question> rule traces to P-7 or P-8, or whether citing CLAUDE.md for verification "how" now violates P-8.

Mitigated (author-committed). Reconciled in the wording. P-8 now distinguishes advisory guidance (permitted, encouraged — CLAUDE.md elaborating how to clear a bar) from the guarantee itself (must be deterministic); it forbids only the latter in prose. It states P-8 "composes with P-7… they share the validate/CI infrastructure without duplicating ownership": P-7 governs what "done" means, P-8 governs where a guarantee lives. No P-7 wording changes. Recommend mitigated.

The proposal defers 100% of new enforcement, so P-8 could ship as a citation ritual with no teeth

Concern. §2's first out-of-scope item defers all new enforcement (the strict CI gate, the hook/pre-commit installer, interview-rejection-in-CI) to TBD-guarantee-layer-spec, and the second (defer-to="never", forward-only) exempts all existing verbs. So at ratification P-8 adds zero new enforcement — unlike P-7, which shipped with tests + validate already enforceable day one. 30-day frame: another apply skips a step (the exact T-004/T-006/T-008 class P-8 diagnoses), and P-8 is cited in the postmortem as a ratified diagnosis whose fix was deferred — a citation, not a guard.

Mitigated (author-committed) — the guarantee-layer spec is the next lifecycle move. The body now shows P-8 is satisfiable today by pointing at enforcement that already exists — the kernel owns apply's commit + §6 fold; validate already carries checkable rules (e.g. the just-shipped skill-metadata-shape) — so P-8 generalizes a live pattern rather than an unbuilt one, and it will reject a new plan that puts a mandatory step only in markdown (passes the P-5 "would it reject a plan" test). The residual — a strict CI gate for existing verbs — is legitimately a follow-on (P-6 and P-7 also preceded their full mechanisms); it's reframed from an unscheduled TBD to the immediate next spec, which the author commits to authoring next (/spectastic.spec for the guarantee layer).
