The principles' goals say "no separate CLI required" and the non-goals say "Introduce a build step." Both wordings predate Tier 1 of the strategy plan and read as categorical bans. Clarify tooling scope of "no build step" and "no separate CLI"

Applied

1 · Intent

Principles v1.0 was written when the lifecycle ran entirely through Claude Code slash commands and the artifact was the only deliverable. Two wordings in §Scope reflected that moment: a goal that said the lifecycle runs through slash commands "no separate CLI required", and a non-goal that ruled out introducing "a build step". Read literally, both reject any tooling that grows around the spec artifact.

The strategy plan at ~/.claude/plans/serialized-whistling-sundae.md commits to a TypeScript foundation: validator, schema package, MCP server, VS Code extension, and a future kernel. Every one of those has its own build step. The existing Python scripts/spectastic init CLI already exists alongside the slash-command lifecycle, so the "no separate CLI" wording is in tension with reality already. Clarifying both wordings now — before spec 002-validate-cli accepts — keeps the rest of the lifecycle principles-clean.

The clarification narrows the scope of each statement. It does not redefine a principle (none of P-1 through P-5 are touched), does not remove anything, does not add anything new. The principles' own amendment process names this as a PATCH version bump (wording change), taking v1.0.0 to v1.0.1.

2 · Scope

In scope

  • Modify one bullet in <spec-goals> to permit complementary CLIs alongside the slash-command lifecycle.
  • Modify one bullet in <spec-non-goals> to scope the "no build step" rule to the spec artifact, not its tooling.
  • Bump principles version 1.0.0 → 1.0.1 and append a changelog entry citing this proposal.

Out of scope

  • Touching any of P-1 through P-5. The five core principles are unchanged.
  • Touching the other two non-goals ("Adopt a JavaScript framework", "Convert markdown"). Both remain in force as written.
  • Adding new goals or non-goals. This proposal only narrows existing wordings.
  • Codifying which tooling languages are permitted. The narrowed wording permits build steps generally; specific stack choices are decided per-spec.

3 · Approach

Two op="modified" deltas, both targeting §scope (the only section anchor that exists — the goals/non-goals lists themselves have no stable IDs). Each delta carries an inline post-state quoting the new bullet verbatim so reviewers see exactly what they're approving without reading the diff. Apply rewrites the matching list items in principles.html in place, leaving the rest of §Scope and all other sections untouched.

No new file. No structural reorganisation. No ADR. The amendment is a wording clarification under an existing process — the smallest possible footprint that resolves the tension.

4 · Deltas

Two modifications. Distinct sub-anchors under §scope — §scope/goals and §scope/non-goals — disambiguate which list is being changed; the inline post-state names the specific bullet.

What changes: Soften the categorical "no separate CLI required" wording in <spec-goals>. The lifecycle remains the primary driver; complementary CLIs are explicitly permitted. Reflects that the existing Python scripts/spectastic init already runs alongside the slash-command lifecycle, and that Tier 1's Node CLI is part of the same pattern.

Post-state (<spec-goals> bullet 3):

Drive the lifecycle through Claude Code slash commands; complementary CLIs are permitted.

What changes: Scope the "Introduce a build step" non-goal to the spec artifact, not to consuming tooling. The artifact remains hand-editable single-file .html with no build step; packages that read or generate spec artifacts (validator, VS Code extension, MCP server, kernel) may have their own toolchains. This is the wording the spec for 002-validate-cli flagged as a precondition.

Post-state (<spec-non-goals> bullet 2):

Introduce a build step for the spec artifact. Source .html is what ships; tooling that reads or generates spec artifacts may have its own build step.
