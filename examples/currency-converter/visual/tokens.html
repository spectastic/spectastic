What version the design system is on

A version, the policy for moving it, and the promise that moving it does not reopen finished work.

Illustrative, but the vocabulary is real: a token set missing its version or its forward binding would be reported, a release classified outside the three tiers would be, and a release removing a token it deprecates in the same breath would be. Converted from a speculative JSON sketch — the last piece of it still in the old form.

1 · Version and policy

Bump policy. MAJOR when a token is removed or its meaning is redefined; MINOR when a token is added or deprecated; PATCH for a value change that alters no binding. The policy lives here rather than in a document elsewhere, because the moment it matters is the moment somebody is about to bump — and that is not a moment anyone goes looking for documentation.

Forward-only. This version binds work authored or amended from 2.0.0 onward. A screen accepted under 2.0.x stays conformant to 2.0.x; a bump does not reopen it. Without that clause every change to a shared design system is a migration project, which is why most teams quietly stop making them.

The external base is versioned separately. @acme/tokens moves on somebody else's schedule, so folding its version into this one would reproduce exactly the error this artifact exists to prevent, one level up.

Added color.accent. Deprecated legacy.accent, which keeps working and names its replacement through the token format's own deprecation channel in tokens/base.tokens.json — so the rename is legible to every other tool that reads the file, not only to this one.

The change class above is the producer's claim and nothing verifies it. There is no classified taxonomy of breaking design changes to check it against: the equivalent for an API contract carries hundreds of rules, and for tokens the state of the art is a diffing plugin. A tool asserting the class would be inventing the taxonomy and then presenting its invention as a finding.
