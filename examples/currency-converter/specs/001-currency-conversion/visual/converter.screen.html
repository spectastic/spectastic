Screen · 001-currency-conversion

Convert

Enter an amount, pick a pair, read a rate — and every way that can fail to happen.

Illustrative. This bundle is a speculative example, but the vocabulary below is real: the shape of every element here is checked, and a state that failed to say where it came from would be reported. Converted from a speculative JSON sketch that predated the vocabulary.

1 · The screen and its states

One screen, ten states. Six were derived from the declared contract's responses and four could not have been — which is the clearest available evidence that contract-derived states are a floor and not a ceiling. The amount field is the only editable control; currency choice is a sheet rather than an inline picker, because the list is long enough to need search.

No amount entered yet. No HTTP status corresponds to this, and no contract could have produced it.

The amount field holds focus on open, so the first keystroke lands somewhere useful.

In flight. Distinct from cold-start: the previous rate is still on screen and dimmed rather than removed.

Announced politely on change, not on every keystroke.

In flight with nothing cached. The only state where the amount field is the sole content.

A rate, its pair, and when it was fetched.

The rate line is a live region so a refreshed value is spoken without moving focus.

Three responses, one state. 400, 404 and 422 differ to a client and are indistinguishable to a person who mistyped a currency code. The collapse is a decision rather than a derivation, and recording it here is what makes it reviewable — and disagreeable.

Reachable only with a revoked key, which a user cannot cause and cannot fix. Designed anyway, because a state that renders nothing is how a blank screen ships.

Retry-After is required by the contract, so this state can name a time rather than say "try again later".

The upstream is down. The cached rate stays visible and is marked stale rather than cleared.

No request was made. There is no status code for a request that never left the device.

Derived from a field rather than a response — asOf is older than the freshness window. Neither purely derived nor purely authored, which is why the source vocabulary is a string and not a boolean.

The badge carries text as well as colour, so it survives greyscale and forced-colors.

The staleness check runs against the cached value, not a fresh request.

2 · Annotations with no accessibility analogue

These stay prose and stay unchecked. The vocabulary names the gap rather than pretending to cover it — an analytics event is not a property of the interface a user perceives, so the accessibility tree has nothing to say about it.

Recorded against the same screen, separated only so the checked and unchecked halves are not confused.

Specified now so that answering the analytics-consent question is a switch rather than a retrofit. No event ships until it is answered, and no payload carries anything identifying.

A rate_converted event on the convert button, carrying the pair only.
