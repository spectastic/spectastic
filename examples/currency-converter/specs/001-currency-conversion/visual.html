A worked exemplar for the visual-spec survey, hand-written to show what a generated visual view might contain. Governed by TBD-visual-spec-vocabulary, TBD-visual-annotation-schema and TBD-fidelity-measurement. Nothing generates it, nothing validates its contents, and no fidelity check reads it.

This is a generated view, not the output of a new verb. The survey scored a dedicated emit verb and rejected it; what it chose was the chassis contracts already use — the design declares, a sidecar holds the real thing, and a view is materialised from both and drift-checked. This file is that third leg, which is why it is named for what it shows rather than for a handoff ceremony, and why nothing here implies a /spectastic.handoff.

The renders below are materialised, not embedded. The artifact CSP is deny-by-default and an inline frame is an error-severity violation, so a live surface cannot be transcluded into a spectastic artifact — the copy is made at generate time and has to be drift-checked, exactly as an embedded contract is. They are also inline SVG rather than raster exports, which is a convenience of this example and not a recommendation.

1 · Renders — three of the ten states

Each render is evidence of one cell in the variant grid: a state, in a mode, on a platform. A render deliberately does not follow the theme you are reading in. A diagram should — it is an illustration, and an illustration that stays light inside a dark page is a defect. A render must not, because it is evidence of a specific mode, and restyling it to match the reader would destroy the thing it is evidence of. The two cases look identical and want opposite treatment.

The Refresh control in the offline render is aria-disabled, not disabled — a disabled control cannot be focused and therefore cannot explain why it is unavailable. That is an annotation, not a drawing decision, which is why it is recorded below rather than left for a reader to notice.

2 · States — six derived, four authored

The derived states came from the declared contract's error responses. The authored ones could not have: there is no status code for a request that was never made. The derivation is a floor, not a ceiling — and where several responses collapse to one state, the collapse is recorded rather than implied, because an unrecorded collapse and an omission look the same to a reviewer.

Every annotation below is expressed in terms the accessibility tree already carries, so a declared annotation is directly assertable on both a web surface and a native one rather than needing translation. Two of the eight rows — tracking and content budgets — have nothing behind them in any existing vocabulary. They are the honest gaps, and they are recorded as gaps rather than improvised into a tenth taxonomy.

4 · The variant grid, and the platform baselines

One spec, an axis grid over it: mode × platform × size class, resolved in a declared order. Platform is a peer of mode rather than a theme, because it selects an interaction model and not only values.

PlatformInput modelDesigned againstLast verified against
iOStouchiOS 26.0iOS 26.1
iPadOStouch + pointeriPadOS 26.0iPadOS 26.0
macOSpointer + keyboardmacOS 26.0— never verified —
tvOSDeclined. A converter is entered a digit at a time and read once; on a focus-engine remote that is worse than not existing. Declined with a reason so the grid records a decision rather than an absence — D-004.

The platform baseline is the fourth clock, and nobody owns it. A design drawn against one OS version can be invalidated by the next without anyone touching the app, the design file or the token set. Recording what each context was designed and last verified against means a measured deviation can be attributed to a platform that moved, rather than being blamed on the implementation or the design. macOS records never verified rather than omitting the row, so the gap is visible instead of absent.

6 · Three clocks

Three things here change at three different rates, and putting one number over all of them would be wrong about at least two.

WhatVersionMechanism
Token set2.1.0, binds forward from 2.0.0Semver with a stated bump policy. Forward-only: a screen ratified under 2.0.x stays conformant to 2.0.x, so a bump is not a migration project. legacy.accent is deprecated with a named replacement rather than removed.
This visual specNoneA change log and typed deltas, exactly as its sibling spec and design carry. Asking "what version is this screen" is asking the wrong question of the wrong artifact.
The renders aboveNoneRatified 11 Aug 2026. A baseline, superseded rather than incremented; re-ratification is a human act and nothing promotes itself.

The token set's release carries a change class of non-breaking. That is the producer's claim and nothing verifies it — there is no classified taxonomy of breaking design changes to check it against. The equivalent question for an API contract has 509 classified rules behind it; for a token set, the state of the art is a diffing plugin. Claiming detection here would mean inventing the taxonomy first.
