3 · Data model & contracts

The conceptual entities in the spec's §4 land as two value types and one cache entry. Rate is a struct with a Decimal ratio and a non-optional Date; the non-optionality is what makes "a Rate with no observation time is not a Rate" true in the type system rather than in prose. Conversion is computed, never stored — it holds a reference to the Rate it used so a figure on screen can always answer its own age.

Conceptual entityPhysical shapeNotes
Ratestruct Rate { base, quote: CurrencyCode; ratio: Decimal; asOf: Date }Decimal, not Double — a binary float cannot hold a minor unit exactly.
ConversionComputed value; not persistedRounds to the quote currency's minor unit at the point of display only.

One operation, GET /v1/rates. The consumer may rely on asOf being present on every 200 and on Retry-After being present on every 429 — both are required in the schema precisely because a screen state depends on each. Six documented error responses; the mapping from those responses to screen states is many-to-one and is recorded in the surface declaration rather than left to the reader, per FR-003.

Exemplar note: a real project would declare contracts/rates.openapi.yaml. A declared path resolves against the directory validate was invoked in, and this project is nested inside another, so the path is written repo-relative here to keep the check honest rather than suppressed. It is the one place the exemplar cannot be both realistic and validated at once.

4 · Visual surface

The <spec-visual> declaration below is real — its shape is checked, and both declared paths are resolved against this project. Everything after it illustrates capabilities that are still proposed: the screen vocabulary, the variant grid, the platform baselines and the versioning policy are described here rather than read by anything.

One screen, ten states, three platform contexts. The surface varies across mode and size class and is declined on tvOS with a reason — a converter wants a keyboard. The token set is the project's and resolves to a directory, because it is split one file per mode; the grid is the project's too and resolves to a file, because its axes resolve in the order they are written and a directory has no order; the screens are this feature's own. States, and where they came from

Six of the ten states were derived from the declared contract's error responses; four were not, and could not have been. The derivation is a floor, and saying so is the point of recording the source on every state. The table itself is no longer written here — it is generated into the declaration above from the screen sidecar, so it cannot drift from what that file actually says. Changing a state and not regenerating is reported.

Platform baselines

Each platform context declares the OS it was designed against and the one it was last verified against, so a measured deviation can be attributed to a platform that moved rather than to the implementation or the design. macOS records null for last-verified rather than omitting the field: the gap is visible instead of absent. tvOS is declined with a reason.

Versioning

Three clocks, and they are deliberately not one number. The token set carries semver (2.1.0) with a stated bump policy and forward-only binding from 2.0.0 — screens ratified under 2.0.x stay conformant to 2.0.x, so a bump is not a migration project. This design and its spec carry no version at all; their history is the change log. The captured renders carry a ratification date and no version — a baseline is superseded, never incremented, and re-ratifying is a human act. The token set's changeClass is the producer's claim and nothing verifies it.

6 · Approach

A cache-first read path. The view renders from the cached Rate synchronously, which is what makes NFR-001 reachable without treating the network as fast. A refresh writes the cache and the view follows. The state machine is derived from the cache's contents and the last request's outcome, so no state is reachable by two routes.

B and C differ only in whether the view can render before any request completes. That single difference is what makes the offline and cold-start states distinguishable, and it is why C wins on a criterion that looks like performance and is really about how many honest states the screen has.

8 · Decisions

D-001 · Cache-first read, background refresh

Status
Accepted
Context
NFR-001 puts a 100 ms ceiling on a keystroke and P-2 requires every screen to work with no network. Both are unreachable if the view awaits a request.
Decision
The view reads the cache synchronously and never awaits the network. A refresh task writes the cache; the view follows.
Consequences
+ NFR-001 becomes an architectural property rather than a latency hope. + Offline and cold-start become distinguishable states rather than one error. − A user can be shown a rate the app already knows is being replaced, for the duration of a refresh. − The cache is now a thing that can be wrong, and nothing invalidates it except time.

D-002 · The freshness window is 60 minutes

Status
Accepted
Context
FR-002 fires on a window the spec deliberately declines to set, because it is a screen property rather than a property of a Rate. Nothing measured tells us where it belongs.
Decision
60 minutes, as a declared token so it is one edit and one test rather than a constant in a view.
Consequences
+ Testable and adjustable without touching the state machine. + A single place to point at when someone disagrees. − Chosen by judgment, not evidence; it is marked assumed for that reason and is the most likely thing in this design to be wrong. − Too short manufactures a stale badge on a good rate, and a badge that is usually on is a badge nobody reads.

D-003 · Three error responses collapse to one state, and the collapse is recorded

Status
Accepted
Context
The contract distinguishes 400 (malformed), 404 (unknown code) and 422 (pair not quoted). To a person who mistyped a currency these are one situation with one remedy. Deriving three states would manufacture two screens nobody can tell apart.
Decision
Collapse them to invalid-pair, and record the collapse on the state itself. A derivation that discards information records what it discarded.
Consequences
+ The screen has ten honest states rather than twelve with two duplicates. + A reviewer can see the collapse and disagree with it, which they cannot do with an omission. − Diagnostic detail is lost at the UI layer and has to be recovered from logs. − If 422 later needs its own remedy, the collapse has to be unpicked and the state list renumbered.

D-004 · tvOS is declined, not deferred

Status
Accepted
Context
The product ships on four Apple platforms. A converter is entered a digit at a time and read once, which on a focus-engine remote is worse than the alternative of not existing.
Decision
Record tvOS in the variant grid as declined, with the reason, rather than leaving the cell empty or listing it as a future variant.
Consequences
+ The grid records a decision where it would otherwise record an absence, and the two are indistinguishable to a reader. + Nobody re-litigates it in six months without reading why. − It is a judgment about a platform nobody has tested this on. − If the app later gains a browse-shaped feature, the decline has to be revisited per feature rather than per product.

11 · Complexity tracking

Ten states for one screen is more than it looks like it needs, and six of them are unreachable in normal use. The alternative is the current screen, which has one state and the defect this spec exists to remove. The cost is accepted; the count is capped by the contract rather than by taste, which is what keeps it from growing.

12 · Open questions

None outstanding. The freshness window is decided and marked assumed rather than left open, since an open question here would block estimation for a value that can be changed in one place.
