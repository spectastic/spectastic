Closed specs never flip Draft → Accepted

Spec upstream

Debugging shipped specs (002-validate-cli, 003-init-node-port) still showing "Draft" after end-to-end completion; root cause was the meta-spec's lifecycle is missing a requirement that names when a spec transitions Draft → Accepted; fixed by adding a status-transition requirement and a corresponding step in /spectastic.implement for the last-task tick; regeneration fails because nothing in the current artifacts tells the next LLM session to flip status when tasks drain.

Expected
A spec whose tasks.html has every <input type="checkbox"> ticked and whose tests pass should carry <spec-status value="accepted">Accepted</spec-status>.
Actual
Both 002-validate-cli (50/50 tasks, 58/58 tests, Tier 1 shipped 14 Jun 2026) and 003-init-node-port (29/29 tasks, 58/58 tests, Python retired 15 Jun 2026) still carry <spec-status value="draft">Draft</spec-status>.
Diagnosis
The meta-spec names the lifecycle status values via REQ-LIFECYCLE-002 ("Each template SHOULD include a <spec-status> reflecting Draft / In Review / Accepted / Superseded / Deprecated") but no requirement defines when a spec transitions between those states, and no slash command in the lifecycle flips the status. Author memory is the only mechanism; it fails silently.
Fix
Add a new requirement (provisionally REQ-LIFECYCLE-004) to examples/spectastic-spec.html: "Spec status MUST transition from Draft to Accepted when the last unchecked <input type='checkbox'> in the spec's tasks.html is ticked, and the integration tests pass." Update commands/spectastic.implement.md's tick-step to detect last-tick and prompt-or-perform the status flip. Hotfix: flip 002 and 003 to Accepted now (catch-up) before the amendment lands.
Closed by
(a) Hotfix 15 Jun 2026 — flipped 002-validate-cli and 003-init-node-port to Accepted. (b) Applied 2026-06-15-lifecycle-state-transitions: modified REQ-LIFECYCLE-002 + added REQ-LIFECYCLE-004 (finite state machine for artifact lifecycle, with tasks-less-artifact clause). Adversarial pass produced 3 findings, all mitigated. Meta-spec status flipped Draft → Accepted at apply time. (c) Updated commands/spectastic.implement.md step 8 — last-tick detection surfaces an explicit Draft → Accepted confirmation prompt that reminds the author to verify tests pass.
Deep dive — hotfix required before amendment

The proposed REQ-LIFECYCLE-004 won't retroactively affect specs whose last-task moment has already passed. Two specs need an immediate hotfix before the upstream change lands:

  • 002-validate-cli — flip Draft → Accepted; FR-011 alignment proposal already applied; integration test (SC-001) verified.
  • 003-init-node-port — flip Draft → Accepted; byte-identity parity with Python verified via diff -r; Python script and 001-cli supersession both landed.

The upstream amendment lands via /spectastic.propose against examples/spectastic-spec.html adding REQ-LIFECYCLE-004 and updating commands/spectastic.implement.md prose. After the amendment, future specs will not exhibit this drift — the tick-step of the last task in any tasks.html will surface the status flip as part of the standard implement flow.

No cross-spec contract is touched (the meta-spec stands alone for the lifecycle protocol). No project-wide principle is violated — P-1..P-5 are about HTML format, IDs, and typography, not status semantics. No deferred functionality is exposed.

plan.html and tasks.html statuses never transition; spec.html flip is unreliable in practice

Spec upstream

Debugging shipped specs (002, 003) whose sibling plan.html + tasks.html stay in Draft after the spec.html itself is Accepted, plus spec 004 whose all three artifacts are still Draft despite a successful first npm publish; root cause was REQ-LIFECYCLE-004 covers spec.html via the tasks-driven last-tick trigger and covers tasks-less artifacts (principles, meta-spec, triage logs, inbox) via author affirmation but leaves plan.html and tasks.html in a gap — they belong to a spec that has a tasks.html so the tasks-less clause doesn't apply, but they don't have their own tasks.html to drive the last-tick trigger; fixed by extending REQ-LIFECYCLE-004 so plan/tasks status bundles with the parent spec (one author confirmation flips all three siblings) and tightening /spectastic.implement's last-tick step to always perform the bundled flip; regeneration fails because the next LLM session will keep ticking boxes without flipping any pills.

Expected
Shipped specs have all three artifacts (spec.html, plan.html, tasks.html) at Accepted. In-progress specs have all three at Draft. The three siblings move together as one logical lifecycle unit.
Actual
Audit of the live repo: specs/002-validate-cli/{plan,tasks}.html Draft (spec is Accepted from the T-001 hotfix); specs/003-init-node-port/{plan,tasks}.html Draft (spec is Accepted from the same hotfix); specs/004-npm-publish-workflow/{spec,plan,tasks}.html all three Draft despite the first npm publish landing successfully this session. Three specs, nine artifacts, only two are Accepted.
Diagnosis
Two reinforcing gaps. (a) REQ-LIFECYCLE-004's Draft→Accepted trigger ("last unchecked checkbox in the artifact's tasks.html") only fits the spec.html artifact. The tasks-less clause that follows ("for artifacts without a tasks.html...") covers principles, meta-spec, triage, and inbox — but explicitly assumes the artifact has no associated tasks.html. plan.html and tasks.html fall outside both clauses: they have a tasks.html (the same one), but it's not theirs. (b) Even for spec.html, the LLM-driven last-tick prompt is unreliable: spec 004 drained to T-907 without ever surfacing the flip prompt, because the remaining tasks (T-310, T-905) were manual user gates that paused the drain before the LLM could detect last-tick. The discipline that's supposed to surface the flip is fragile when manual gates are interleaved with code tasks.
Fix
Extend REQ-LIFECYCLE-004 with a bundling clause: a spec's plan.html and tasks.html status MUST track the parent spec.html status — they move together as one logical unit. The same author confirmation that flips spec.html flips all three siblings (and appends matching <spec-changelog> entries to each). Tighten commands/spectastic.implement.md step 8 to always check the bundle-trigger condition after each tick: count remaining unchecked boxes in tasks.html; if zero, prompt the bundled flip even when the current invocation just ticked a non-final box in a partial drain. Hotfix: catch-up flip 002/003 plan + tasks to Accepted; flip 004's spec/plan/tasks to Accepted as part of this triage's fix landing.
Closed by
2026-06-16-lifecycle-sibling-bundling applied on 16 Jun 2026. Landed REQ-LIFECYCLE-005 as a separate requirement (not an extension of -004 as originally proposed in this card — separating preserves -004's transition-event semantics and lets -005 carry the readiness-vs-immutability clarification). Adversarial pass forced two scope refinements: the implement-step predicate is scoped to Draft state (preventing re-confirmation loops on already-Accepted specs), and the hotfix shrunk from 9 artifacts to 4 (002 plan + tasks; 003 plan + tasks). 004's bundle stays Draft pending T-905 (manual PR-breaking smoke for SC-003) — the same predicate that forbids re-confirmation loops also forbids smuggling 004's flip through the apply step before its trigger has legitimately fired.
Deep dive — hotfix list + cascade through the implement command

The hotfix lands in two strokes:

  • 002-validate-cli/plan.html + tasks.html — flip Draft → Accepted; append a one-line changelog entry citing this card.
  • 003-init-node-port/plan.html + tasks.html — same.
  • 004-npm-publish-workflow/spec.html + plan.html + tasks.html — all three; the first npm publish (v0.1.0-pre.3 + .4) is the affirmation; the spec is the operative contract for the publish workflow.

The upstream amendment lands via /spectastic.propose against examples/spectastic-spec.html. The proposal adds the bundling clause to REQ-LIFECYCLE-004 and tightens the implement command prose. After the amendment, the next session's drain reliably flips all three siblings on the last tick — no more nine-artifact lag.

Cascade vs T-001: T-001 closed the spec.html-only flip protocol; T-002 closes the plan + tasks coverage gap that T-001's fix didn't address. The two amendments are sequential refinements of the same REQ.

Triage defaults to the symptom/presentation layer instead of laddering to the highest layer that must change

Spec upstream

The no-open-questions case (020 T-005) was first classified at the presentation layer (a 020 reader bug) and only reached the correct cross-spec root cause — the <spec-questions> format contract — after author pushback. Triage's speed-optimised procedure carries "fix at the highest layer that needed to change" as a discipline line but no explicit root-cause-laddering step that forces probing upstream before classifying. Regeneration fails — another session reproduces the easy-layer default.

Expected
Triage proactively tests whether the symptom's true owner is upstream (spec / cross-spec / principles) before settling on the convenient layer.
Actual
Optimised for speed, it lands on the presentation/implementation layer first; the deeper layer surfaced only after the user pushed back (T-005).
Diagnosis
The triage command (commands/spectastic.triage.md) states the highest-layer discipline but lacks a procedural step that ladders the root cause ("if only the symptom layer changed, would the regen test recur?") before the layer is committed.
Fix
/spectastic.propose against the meta-spec — add a root-cause-laddering step/gate to the triage procedure (a single "is the owner actually upstream?" probe wired into the regeneration test), without losing the <30-second-card ergonomics. Touches commands/spectastic.triage.md + likely a REQ-TOOL-* clause.
Deep dive — self-referential; speed-vs-depth tension

Worked example: 020 T-005 (presentation-first → cross-spec after pushback). The fix must add depth without killing the format's deliberate speed (a card reads in <30s): a single laddering prompt tied to the existing regeneration test, not a heavy analysis pass. The discipline already says "fix at the highest layer"; this makes it a step, not just a maxim. No cross-spec contract beyond the triage command; no new principle.
