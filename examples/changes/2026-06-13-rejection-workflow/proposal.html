Rejection workflow at both lifecycle surfaces

Codify how the lifecycle records "considered, decided against" — for inbox cards and for authored proposals.

Add REQ-CHANGE-005 codifying the rejection workflow at both lifecycle surfaces. Surface A (pre-propose): inbox cards MAY carry data-status="rejected" + a Reason field, mirroring the existing data-status="done" convention. Rejection workflow at both lifecycle surfaces

Proposed

1 · Intent

Spectastic's <spec-status> vocabulary has always included withdrawn, but no command implemented it; an authored proposal the author decided against would either sit in changes/<slug>/ indefinitely or get manually deleted, losing history either way. Inbox cards had no terminal-rejected state at all for routed layers — only just-do cards had data-status="done". The lifecycle could not record "considered, decided against," so it didn't.

The fix is to codify rejection at both surfaces with one requirement and one apply-mode extension. Rejection preserves history: the card stays in the inbox; the proposal moves to a sibling subdirectory parallel to archive; the live spec's changelog records the consideration-and-withdrawal so future-you reaches the rejected idea via the spec, not by walking changes/.

2 · Scope

In scope

  • One new requirement (REQ-CHANGE-005) codifying both surfaces.
  • data-status="rejected" for <spec-triage> cards; matching CSS treatment paralleling DONE.
  • /spectastic.apply --withdraw <slug> --reason="…" mode with preconditions, folder move to examples/changes/withdrawn/<slug>/, path rewrites, and the live-spec changelog "Considered, withdrew" entry.
  • Documentation in commands/spectastic.triage.md (Surface A) and commands/spectastic.apply.md (Surface B).

Out of scope

  • Un-withdrawing a proposal. Withdraw is one-way; if you change your mind, write a new proposal — the withdrawn one stays as history.
  • Bulk rejection of inbox cards. Per-card discipline.
  • Auto-reject inbox cards stale for N days. Process theatre for a personal-project inbox.
  • A formal anchor convention for linking rejected inbox cards from the live spec (the way archived proposals get linked from changelog). Currently the changelog links the proposal slug only; an inbox-card link would need an #I-NNN anchor scheme. Capture if friction surfaces.

3 · Approach

The two surfaces share one discipline — preserve, don't delete — and implement it with the same shape: a status change in the artifact, no file deletion. Surface A flips data-status on a card; Surface B flips <spec-status> on a proposal and moves the folder. Neither path removes anything from the repository.

Surface B's folder destination is deliberately parallel to archive/, not nested inside it. archive/ is reserved for applied proposals; mixing withdrawn into the same directory would conflate the two terminal states and break the convention that "everything in archive/ landed in the live spec." A sibling withdrawn/ keeps both states visible and legible at directory level.

Withdraw is a mode of /spectastic.apply, not a new verb. Verb count stays at eight. The conceptual adjacency holds: both modes are terminal lifecycle moves on an authored proposal that update the live spec's changelog. Apply lands; withdraw rejects; both record.

4 · Deltas

One <spec-delta>. target= links to the live spec. op= is added.

Items considered but decided against MUST be preserved as history, not deleted. The lifecycle SHOULD support rejection at both surfaces:

Surface A — Inbox cards (pre-propose). A <spec-triage> card in inbox.html MAY carry data-status="rejected" and a <dt>Rejected because</dt> row inside its <dl>. The card stays in inbox.html (mirrors the existing data-status="done" convention for just-do cards). CSS renders a REJECTED pill, muted body, and strikethrough title.

Surface B — Authored proposals (post-propose). /spectastic.apply SHOULD accept a withdrawal mode invoked as --withdraw <slug> --reason="<one-line>". The mode:

  • Refuses if the proposal status is already applied or withdrawn.
  • Refuses if --reason is empty.
  • Flips status to withdrawn.
  • Moves the folder from examples/changes/<slug>/ to examples/changes/withdrawn/<slug>/ (a sibling of archive/, not nested).
  • Appends a <spec-changelog> entry to the live spec it targeted: "Considered <slug>, withdrew on <date> because <reason>."
  • Appends a changelog entry to the moved proposal recording the withdrawal date and reason verbatim.

Withdraw is terminal — to revive a withdrawn proposal, author a new one. Implementation ownership: Surface A in commands/spectastic.triage.md; Surface B's procedure in commands/spectastic.apply.md's Withdraw procedure section.

Rationale

The <spec-status value="withdrawn"> vocabulary has existed since v0.1 but has had no workflow behind it — an authored proposal the author decided against would either sit in changes/<slug>/ indefinitely or get manually deleted. Inbox cards had no terminal-rejected state for routed layers. The lifecycle had no way to record "considered, decided against." This requirement closes both gaps with one discipline — preserve, don't delete — and one apply-mode extension. Priority should rather than must because we're codifying from zero applications; re-evaluate after ≥3 worked rejections.

5 · Risk register

Populated by the adversarial risk pass forced via --adversarial (the heuristic doesn't fire — single-topic, should-tier, single ADD — exactly the shape REQ-CHANGE-004's R1 finding flagged the heuristic would miss). The second worked example of the risk pass on a lifecycle change.

The "withdraw is terminal; to revive a withdrawn proposal, author a new one" one-way door will be the regretted line within 30 days the first time the author withdraws under uncertainty and immediately wants the proposal back.

The REQ-CHANGE-005 body asserts "Withdraw is terminal — to revive a withdrawn proposal, author a new one", reinforced by the §2 out-of-scope bullet "Un-withdrawing a proposal. Withdraw is one-way; if you change your mind, write a new proposal — the withdrawn one stays as history" with defer-to="never". Terminal-by-design is being codified before any worked example of a withdrawal has happened — the same "codifying from zero applications" concern the proposal itself acknowledges in the Rationale, but applied only to the priority level (should vs. must), not to the irreversibility decision. The first real withdrawal that happens for a reversible reason (interrupted draft, changed mind mid-day) will hit a hard wall, and the cost of re-authoring vs. flipping a status field is exactly the friction that drives "manually delete the folder" — the failure mode the proposal exists to prevent.

Genuine — and the failure-mode pattern is well-named. The "terminal" framing is intended as discipline, not a technical lock: nothing prevents a manual recovery (git revert the move, flip status). The right mitigation is to say so explicitly in the requirement body — replace "Withdraw is terminal — to revive a withdrawn proposal, author a new one" with "Withdraw is intended as terminal: there is no --unwithdraw command. If you withdrew by accident or under time pressure, restoring the folder and status manually is unsupported but not forbidden; if your design has updated, author a new proposal." That keeps the discipline (no command surface for un-withdraw, no metric for tracking it) while removing the false impression that recovery is impossible. Proposed transition: mitigated after the REQ body language is softened to acknowledge manual recovery.

REQ-CHANGE-005's withdrawn-folder path shape contradicts REQ-CHANGE-001's mandatory date-prefixed path contract for change-proposal artifacts.

REQ-CHANGE-001 mandates "Spec evolution MUST happen via change-proposal artifacts at specs/<spec-id>/changes/<YYYY-MM-DD>-<slug>/proposal.html" — the date prefix is part of the MUST-tier contract for where a change-proposal artifact lives. REQ-CHANGE-005's §4 delta and the apply.md Withdraw procedure both specify the destination as "examples/changes/withdrawn/<slug>/" — slug only, no date prefix — while applied proposals at changes/archive/<date>-<slug>/ (per the live spec's existing changelog entries) keep the date. Withdrawn proposals are still change-proposal artifacts; dropping the date prefix on one terminal state but not the other splits the path contract on terminal-state grounds REQ-CHANGE-001 never authorised, and breaks the convention that any future spectastic validate --strict would key on.

Genuine ambiguity in the REQ-CHANGE-005 body. In the propose/apply implementation, <slug> is actually the full folder name including the date prefix (e.g. 2026-06-13-rejection-workflow); the destination IS preserving the date, just under a different ambiguous variable name. The critic is reading <slug> as the kebab-case tail only — which is exactly the trap a fresh reader hits. Mitigation: rewrite the body to use <YYYY-MM-DD>-<slug> explicitly everywhere (matching REQ-CHANGE-001's notation) so the date preservation is unambiguous. Same fix in the apply.md Withdraw procedure. Proposed transition: mitigated after the REQ body and apply.md both use the explicit notation.

§2 Scope bundles three structurally distinct concerns — an inbox-card CSS state convention, an apply-command mode extension, and a brand-new top-level directory taxonomy (withdrawn/) — under a single requirement, exactly the bundling pattern the previous proposal's R3 already flagged as a scope smell.

§2 in-scope lists three bullets: "data-status="rejected" for <spec-triage> cards…", "/spectastic.apply --withdraw <slug> --reason="…" mode with preconditions, folder move to examples/changes/withdrawn/<slug>/, path rewrites, and the live-spec changelog "Considered, withdrew" entry", and the doc updates. These are two different lifecycle surfaces (pre-propose / post-propose), two different artifact types (triage card / proposal folder), and one new repository-level directory convention — collapsed into a single should-tier requirement justified as "one discipline — preserve, don't delete." The discipline is shared, but the implementation surfaces are not, and the §3 Approach explicitly says the two surfaces "share one discipline … and implement it with the same shape" — which is the rhetorical move a reviewer should flag, not accept, since "same discipline" is not the same as "single requirement." This is the same shape as the prior proposal's R3 (vocabulary bundled with workflow), surviving here because the symmetry argument is more compelling than the split would be.

The pattern is real and worth naming, but the split would be worse than the bundle. Surface A and Surface B share more than discipline: they share the same "considered, decided against" lineage, both need to be discoverable via the same mental model, and both will be applied (or not) by the same author in the same session. Splitting into REQ-CHANGE-005a and REQ-CHANGE-005b would create an artifact-ordering trap (which surface gets the inbox link from the live spec changelog?) and double the proposal authoring overhead for what is fundamentally one discipline. Mitigation: extend §3 Approach with an explicit acknowledgement of the bundle decision, matching the vocabulary-budget paragraph from the prior proposal — name the multi-surface scope, explain why the split would be worse, and own the choice. Proposed transition: mitigated after the §3 acknowledgement paragraph lands.
