Closer to universal developer vocabulary; further from the spec-driven-development frame the rest of the world doesn't share.

Rename /spectastic.implement → /spectastic.build

Withdrawn

1 · Intent

"Implement" was chosen early because the lifecycle reads as spec → implementation; the verb name resonated with that frame. After one full drain cycle (001-cli's 33 tasks), the cost of the choice is visible: implementation reads as a spec-driven-development term-of-art, and the developer-default reading of "execute the task at hand" lives closer to build. "Build" is what every other developer surface in the world calls this: npm build, cargo build, make's default target. The verb that asks the lifecycle's reader to bridge a domain gap can become the verb that doesn't.

This proposal is captured from inbox I-007. The user's stated instinct on capture was to reject it before authoring; this proposal exists so that rejection happens through the lifecycle's mechanisms (risk pass + withdraw flow) rather than as an inbox-side dismissal — the rejection lineage becomes legible to future-you.

3 · Approach

One MODIFY delta on REQ-TOOL-001 is the lifecycle-level change. Everything else is consequence: artifact renames, cross-reference sweeps, symlink refreshes, test-constant update. The rename is mechanical once the requirement moves — the cost is the breadth (~15+ files, ~50+ string occurrences) rather than any single step's complexity.

Two existing meta-spec requirements name the verb directly: REQ-TOOL-003 ("the /spectastic.implement command MUST default to one task per invocation…") and REQ-CHANGE-003 ("/spectastic.implement can target those tasks directly…"). Both need their REQ bodies updated alongside REQ-TOOL-001. The natural sequencing is to bundle those updates into the same apply — a single MODIFY on REQ-TOOL-001 plus two MODIFY-by-side-effect updates to the named requirements. Treating each as its own delta would be more honest; treating them as a single bundled rename matches how a reviewer reads them.

The proposal targets the meta-spec only. specs/001-cli/spec.html#FR-001's mirror of the command list is a cross-spec follow-up that needs its own proposal against the 001-cli spec; without that sibling proposal, 001-cli and the meta-spec disagree on the verb name. The cross-spec gap is named in §2 out-of-scope and flagged in §6 Tasks.

5 · Risk register

Populated by the adversarial risk pass per REQ-CHANGE-004. Heuristic fires automatically: REQ-TOOL-001 is priority="must". The third worked example of the risk pass — the first one in which the heuristic fires without --adversarial being forced.

The rename swaps a verb that pulls weight only inside the spec-driven-development frame for one that collides head-on with the universal developer vocabulary the proposal cites as its own justification — and the proposal explicitly defers the audit that would surface the collision cost.

The §4 delta on REQ-TOOL-001 replaces /spectastic.implement with /spectastic.build on the grounds, per the header italics, that "build is what every other developer surface in the world calls this: npm build, cargo build, make's default target." The §2 out-of-scope register then carries: "A broader audit of verb-name overlap with software-build vocabulary (build systems, build steps, build targets) — the rename's biggest cost vector. Capture if a worked example surfaces friction" with defer-to="TBD-verb-overlap-audit". Naming the biggest cost vector and deferring it is the move most likely to be regretted in 30 days: any spectastic project that also runs a build system now has /spectastic.build overlapping with "build the project" in every readme, every CI log, every chat message — and implement's framing cost was a one-time learning curve, while build's collision cost compounds with every adjacent tool.

This is the proposal's core fragility, surfaced exactly. The cost asymmetry the critic names is the whole game: implement's framing cost is a one-time learning curve, paid once per reader; build's collision cost compounds with every adjacent build tool a user already has in their workflow — every spectastic project running alongside npm, cargo, make, bazel, turbo, any CI pipeline. The proposal's TL;DR cites universality as the reason; the critic correctly observes that universality cuts both ways: the more saturated the verb, the more semantic load it carries. The deferred audit IS the proposal's biggest gap, named in the artifact. Proposed transition: accepted — and acceptance points to withdrawal via /spectastic.apply --withdraw 2026-06-13-implement-to-build --reason="…" rather than mitigation. The collision is too central to address with proposal revisions; the case for build doesn't survive contact with the universality argument.
