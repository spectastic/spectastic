Closes meta-spec triage T-005. REQ-CHANGE-006 mandates that apply fold a proposal's §6 into the target's tasks.html, but defines the fold as an action with no checkable post-condition. When the 2026-06-25-spec-budget-bands apply skipped it (triage T-004), eight tasks were orphaned and a fabricated citation kept shipping until a human noticed — nothing was in a detectably-wrong state. This change ADDs REQ-CHANGE-007: an applied proposal's §6 MUST appear as a provenance-linked folded phase, and spectastic validate MUST flag (error) an applied proposal whose §6 has no matching phase — a fold-gap drift guard shaped like the existing verify-view-stale rule.

Detect a skipped task-fold

Approved

1 · Intent

REQ-CHANGE-006 makes /spectastic.apply a uniform accept-and-route step: it folds a proposal's §6 tasks into the target's tasks.html as a provenance-linked phase, and /spectastic.implement drains them. But the requirement specifies the fold only as something apply does — there is no post-condition a later check can test. So when an apply run omits the fold, the corpus contains no malformed artifact: the deltas are in the spec, the folder is in archive/, the status reads applied. Everything looks done.

That is exactly what happened on 26 Jun 2026 with 2026-06-25-spec-budget-bands (meta-spec triage T-004): the deltas folded, the folder archived, but the §6 task-fold was skipped. Eight implementation tasks were orphaned and a fabricated "Larson" citation kept shipping in assets/spec.js until a human asked where the work went. The failure was invisible because nothing verifies that an applied proposal was actually folded. This change adds the missing post-condition and a validate guard that makes a skipped fold loud.

2 · Scope

In scope

  • ADD REQ-CHANGE-007 to the meta-spec (change-management family): an applied proposal's §6 MUST be represented as a provenance-linked folded phase, and spectastic validate MUST flag — as an error — an applied proposal whose §6 has no matching folded phase.
  • The validate-rule contract (what is checked, at what severity). The rule implementation, fixtures, and an apply-command cross-reference are the §6 tasks, drained by /spectastic.implement.

Out of scope

  • Generalising the guard to "validate every apply step". Only the fold has a checkable present/absent artifact (a phase in the tracker); the archive move and the status flip are self-evident from the folder location and the status pill, so a guard there would add cost without signal.
  • Changing apply's behaviour. Apply already folds (REQ-CHANGE-006); this change does not make apply re-check or self-correct — it makes the omission detectable after the fact via validate.

3 · Approach

Mirror the verify-view-stale drift-guard shape, which is the project's established pattern for "a generated/derived artifact has fallen out of sync with its source". That rule is cross-file and uses a live comparison — it re-derives the expected ID set from the bundle and compares it to what the derived view actually links, with no stored fingerprint. The fold-gap guard is the same: a cross-file rule that, when an applied proposal (<spec-change status="applied">) and the target tracker are in the validated set together, re-derives the provenance link the fold should have written and asserts the tracker carries a phase linking back to that proposal. Present → clean; absent → an error finding on the proposal.

REQ-CHANGE-007 owns the contract — the post-condition plus the validate obligation and its severity — and stays deliberately narrow (the fold post-condition only). The schema rule is the enforcement and folds in as a §6 task. Priority should, matching REQ-CHANGE-004 and REQ-CHANGE-005: codifying from a single incident, to be re-evaluated after it has caught (or failed to catch) a few real lapses.

4 · Deltas

One <spec-delta> per requirement touched. target= links to the live spec; op= is one of added | modified | removed | renamed.

An applied proposal's §6 tasks MUST be represented as a provenance-linked folded phase in the target's tasks.html (the post-condition of the fold mandated by REQ-CHANGE-006). spectastic validate SHOULD enforce this: it MUST raise an error-severity finding for an applied proposal (<spec-change status="applied">, or a proposal under changes/archive/) whose §6 tasks have no matching folded phase — one linking back to that proposal — in the target tracker. The guard is a fold-gap drift check, the same live-comparison shape as the existing verify-view-stale rule, and is scoped to the fold post-condition alone: it MUST NOT attempt to verify other apply steps (the archive move and the status flip are self-evident from the folder location and the status pill).

Rationale

REQ-CHANGE-006 specifies the fold as an action but defines no checkable post-condition, so a skipped fold leaves the corpus in a state that looks complete (deltas folded, folder archived, status applied) while the implementation work is orphaned — exactly the 2026-06-25-spec-budget-bands failure (triage T-004). Error severity (not warning) because an unfolded proposal means real work was silently dropped — a hard correctness gap, like verify-view-stale, not a style nit. Priority should because we codify from one incident; re-evaluate after it has proven itself against a few real applies.

5 · Risk register

The adversarial pass ran (opt-in --adversarial; the change also touches the must-tier change-management family that REQ-CHANGE-006 governs). Three findings; each MUST reach accepted, mitigated, or rejected before apply.

The fold-gap rule keys on applied proposals "under changes/archive/", but validate's file discovery default-ignores **/archive/** — so the rule receives zero archived proposals and silently never fires, and the only obvious fix (un-ignore archive) re-opens the no-duplicate-ids collisions that ignore exists to prevent.

REQ-CHANGE-007: "an applied proposal (… or a proposal under changes/archive/) whose §6 tasks have no matching folded phase" — vs packages/cli/src/glob.ts DEFAULT_IGNORE (and the integration canonical set), both excluding **/archive/** because "archived proposals copy stable IDs by design and would spuriously trip no-duplicate-ids".

Draft (status is the author's to set). Confirmed on disk — this is load-bearing. Every applied proposal is moved to changes/archive/, which is exactly what discovery strips before any rule runs, so the cross-file rule iterates an empty set: the silent-pass the proposal set out to abolish. The naive fix (drop the archive ignore) re-admits duplicate-ID errors across every prior proposal — the "linter is noise" failure this proposal invokes against itself. Options to weigh before apply: (a) a dedicated, scoped validate pass that includes changes/archive/** for this rule only, with no-duplicate-ids held off for archived inputs; (b) re-key the post-condition to run at apply-time-adjacent validation over the live proposal + tracker, before the archive move; (c) reframe REQ-CHANGE-007 so an apply self-verify step (not the HTML validate engine) owns the check. §6 Task 2 gestures at this but understates that option (a)'s scoping is required, not optional.

REQ-CHANGE-006 fixes the fold's provenance as a phase that "MUST link the archived proposal" but never pins the link's machine-readable shape; REQ-CHANGE-007 inherits that looseness ("a phase whose provenance links back to that proposal"), so the guard and the -006 action can disagree on what counts as "folded" — false positives on good applies, false negatives on bad ones.

REQ-CHANGE-006: "a new provenance-linked <spec-task> phase … The provenance MUST link the archived proposal." vs REQ-CHANGE-007's looser "a phase whose provenance links back to that proposal."

Draft (status is the author's to set). Fair. Unlike verify-view-stale, which joins on stable derived IDs (SC-NNN/T-NNN), a folded phase carries no such re-derivable key — only an <a href> into the archive path. The fix is a wording tightening: REQ-CHANGE-007 (or its rule) should pin the join concretely — the folded phase's provenance link resolves to the proposal's own archive path — and match exactly that, so a correctly-folded phase per -006 always passes. Resolvable before apply.

Scope is too narrow on the one axis that matters: it fixes what is checked and at what severity but defers the can-the-rule-even-observe-its-inputs question (given archived proposals are default-ignored) into a §6 task — so the meta-spec takes on a MUST-flag obligation whose feasibility is unproven at approval time.

§6 Task 2: "a cross-file rule sees nothing if only one side is present; extend the glob / canonical set if it doesn't" — the load-bearing design question, deferred out of the requirement.

Draft (status is the author's to set). Agreed, and R1 is the proof: the file-discovery interaction with no-duplicate-ids belongs in the Approach, not a task. Mitigation: fold the discovery design (which of R1's options a/b/c, and its no-duplicate-ids interaction) into this proposal's Approach — or a short plan.html — before apply, so REQ-CHANGE-007 is not a MUST whose implementability is unsettled.
