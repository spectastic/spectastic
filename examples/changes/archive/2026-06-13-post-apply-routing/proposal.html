Post-apply routing rule

Applied

1 · Intent

The propose template puts a scoped task list inside every proposal precisely so small changes don't have to round-trip through /spectastic.plan and /spectastic.tasks to land. /spectastic.apply's documentation knows this implicitly — it never names it. A fresh reader who applies their first proposal hits an unsignposted fork: are the proposal's inline tasks the breakdown, or do I re-run plan and tasks now?

Surfaced during the I-009 → REQ-TOOL-003 follow-up. The user asked the question directly: "should I be rerunning plan now since we absorbed our proposal, and then running tasks, and then implement?" The fact that the lifecycle's prose left the answer to chat is exactly the gap.

2 · Scope

In scope

  • One new requirement (REQ-CHANGE-003) naming the small-vs-large routing rule and the boundary heuristic.
  • A What's next subsection in commands/spectastic.apply.md §Output describing the rule in command-file prose.
  • A one-line nudge in the per-apply console report so the user sees the routing question without re-reading the docs.

Out of scope

  • Tightening /spectastic.propose's output prose with a parallel small-vs-large hint. The propose command terminates before the spec moves, so the routing question doesn't bite there — capture separately if it does.
  • A hard automatic switch — the command will not force re-plan for "large" changes. The boundary is fuzzy by design; the user gets the rule, not a guardrail.

3 · Approach

The fix is documentation, but the gap is upstream — a fresh LLM session writing /spectastic.apply from scratch would re-leave the rule implicit because nothing in the meta-spec demands it surface. The requirement closes that loop. Once REQ-CHANGE-003 exists, the command file is bound to honor it, and so is any future regeneration.

The boundary heuristic — "small" vs. "large" — is one sentence: if you'd write more than one new ADR for the change, it's large enough to warrant plan + tasks; otherwise the proposal's inline tasks are the breakdown. Number of deltas is a noisier signal; ADR pressure is the one that tracks the actual decision-cost.

The proposal's task list itself becomes the breadcrumb. When the apply command's console report names the routing, it also points at the archived proposal's §5 Tasks as the small-change path — closing the loop the user just asked about in chat.

4 · Deltas

One <spec-delta>. target= links to the live spec. op= is added.

After /spectastic.apply lands a change, the command SHOULD surface the post-apply routing rule — where the user drives the follow-up implementation work — in both its documented output and its per-apply console report:

  • Small change (one or two requirements, behavioural addition, no new ADRs): drive the inline task list inside the archived proposal. /spectastic.implement can target those tasks directly.
  • Large change (multi-requirement, architectural shift, new topic group): re-run /spectastic.plan against the updated spec to revisit ADRs, then /spectastic.tasks to derive a fresh breakdown, then /spectastic.implement to drain it.

The boundary is fuzzy by design: if more than one new ADR would land, the change is large enough to warrant plan + tasks; otherwise the proposal's inline tasks are the breakdown. The rule is guidance, not a guardrail — apply MUST NOT refuse or auto-trigger plan/tasks based on its own classification.

Rationale

The propose template already encodes the small-change shortcut by hosting tasks inside the proposal artifact. The apply command's prose never names the resulting routing rule, so a fresh reader hits the fork unsignposted. Surfacing the rule turns implicit design into explicit guidance and prevents the lifecycle's reading order from leaving a hole between apply and the next implement.
