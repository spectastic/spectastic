Grounded planning — the plan rests on verified truth

Make /spectastic.plan read the real ground before deciding, so discoveries land at planning, not implementation.

Status Applied Change ID 2026-06-22-plan-grounding Spec spectastic-spec Author Brian Corbin · @briancorbinxyz Created 2026-06-22 Targets 1 requirement (1 added) Read time

Dogfooding surfaced a real gap: /spectastic.plan is spec- and interview-driven but never reads the real code, APIs, or constraints a design rests on — so unverified assumptions are structurally indistinguishable from verified facts in plan.html, and they leak into implementation as surprise discoveries. This change adds REQ-LIFECYCLE-006: the plan procedure SHOULD ground every design-bearing fact against real source before the interview and record each in an evidence ledger (verified | spike | assumed), and MUST NOT hand off to /spectastic.tasks while a must-tier decision rests on an unverified assumption the author hasn't accepted (the gate is the binding clause; the grounding discipline is SHOULD, mirroring REQ-CHANGE-004). Reuses the /spectastic.explain grounding discipline and the adversarial-pass risk-gate shape — no new verb, no new element.

Grounded planning — the plan rests on verified truth

Applied

1 · Intent

The lifecycle's promise is that each phase de-risks the next. Today it breaks at the plan→implement seam. commands/spectastic.plan.md reads the spec in full and runs a two-phase interview, but its only contact with the codebase is step 6 "Skip what's known", which checks the file tree, package.json, and lockfiles — metadata, never file contents or API signatures. Decisions, technical context, the alternatives matrix, and risks are all narrative judgment. The ADR shape is enforced; evidence is not. So a plan can assert "the schema already exposes X" or "this library supports Y" without anyone having opened X or Y — and the implementation phase pays for it with discoveries that should have been caught at planning.

The fix is the field's consensus and spectastic already owns it as a pattern: move investigation into planning, backed by evidence. /spectastic.explain already mandates "resolve every target against real source… cite only references you have confirmed exist this turn." This change lifts that discipline into /spectastic.plan and makes the evidence — and any ungrounded decision — structurally visible, the way a missing delta op renders MISSING OP.

2 · Scope

In scope

  • A grounding phase in /spectastic.plan — read real consuming code, dependency signatures (at the resolved lockfile version), platform constraints, and existing patterns before the interview.
  • An evidence ledger in plan.html: every design-bearing fact as verified | spike | assumed with its source.
  • A grounding= attribute on each <spec-decision>; an ungrounded one renders the UNGROUNDED visible-failure.
  • A grounding gate: no hand-off to /spectastic.tasks while a decision rests on an unverified assumption the user hasn't accepted as a <spec-risk>.
  • Time-boxed spikes permitted during planning to convert "we think" → "we know".

Out of scope

  • A mechanical citation-verification kernel in spectastic validate — deferred to a follow-on slice (reuses the course.ts ref-resolver when built).
  • A new verb — grounding folds into /spectastic.plan, the way clarification folds into its interview.
  • A new custom element — the status rides on an attribute (vocabulary budget untouched).
  • Version-aware symbol/signature checking — left to in-session LSP grounding.

3 · Approach

The contract lands here as REQ-LIFECYCLE-006; its implementation is the procedure + template + CSS. The grounding step sits after the estimability gate (which proves the spec is answerable) and before the interview (which now decides on verified ground rather than producing assumptions). Each design-bearing fact is classified verified (opened this turn — record path:line / symbol / dep@version / URL), spike (run the time-boxed investigation now, record the finding), or assumed (a tracked risk if a decision rests on it).

The gate reuses the propose §8 status model verbatim: an assumption a decision rests on becomes a <spec-risk status="accepted"> only by the user's commitment. No new gate machinery, no new statuses, no new element — the ledger is a plain table reusing <spec-status> pills, and the decision carries a grounding= attribute whose absence renders UNGROUNDED.

4 · Deltas

One <spec-delta>. target= links the live meta-spec; op="added".

The /spectastic.plan procedure SHOULD ground every design-bearing fact against real source before its interview — opening the actual consuming code, the dependency's signature at the resolved lockfile version, and quantified platform constraints, not the file tree alone — and SHOULD record each fact in an evidence ledger as one of verified (opened this turn, with a cited source), spike (resolved by a time-boxed investigation run during planning, with its finding), or assumed (unverified).

Each <spec-decision> SHOULD declare its grounding and cite a verified or spike-resolved source in its Context; a decision that rests on an unverified assumption SHOULD render as a visible failure (the planning analogue of REQ-AUTHOR-001's render-broken-when-malformed discipline).

The gate is the binding clause: the plan MUST NOT be declared ready for /spectastic.tasks while a must-tier decision rests on an assumed or unresolved spike fact, unless the author has accepted it as a tracked <spec-risk> whose status the author commits (per REQ-CHANGE-004's author-owned-status model). This gate is a plan→tasks readiness affirmation, not a Draft content-lock — it mirrors the existing estimability gate, and pure-judgment decisions with no external fact are exempt.

Rationale

Implementation surprises come from planning under unverified assumption. The grounding discipline ships as SHOULD — mirroring REQ-CHANGE-004, which shipped the adversarial pass as guidance from one data point rather than a blanket MUST that hollows into theater. The gate is the MUST that actually stops an ungrounded assumption from reaching implementation silently; lifting the /spectastic.explain "cite only confirmed source" discipline into planning makes "what the plan knows vs. assumes" structurally legible.

5 · Risk register

Populated by the adversarial risk pass (this ADD is must-tier, so the heuristic fires). Each <spec-risk> stays status="identified" until the author commits a transition; /spectastic.apply refuses while any remain identified.

Making grounding a blanket MUST that opens "the actual consuming code, the dependency's signature at the resolved lockfile version, and any quantified platform constraint" for every design-bearing fact turns the authoring-only plan verb into a slow, source-tree-dependent investigation gate; within 30 days authors will routinely classify facts as "judgment" or hand-wave the ledger to escape it, hollowing the MUST into theater — exactly the failure REQ-CHANGE-004 hedged against by shipping as should "from one data point" rather than must.

"it MUST open the actual consuming code, the dependency's signature at the resolved lockfile version, and any quantified platform constraint — not the file tree alone"

Strong point — this is the fork worth pausing on. The MUST is scoped to facts the plan "will touch or depend on" (not "open every file"), but the REQ-CHANGE-004 precedent — shipping the adversarial pass as should from one data point to avoid theater — is exactly on point, and this change rests on one dogfooding session. The teeth that actually prevent the leak are the gate (no hand-off with an ungrounded must-decision), not the obligation to open every file. Author to decide: keep the blanket MUST, or soften the grounding discipline to SHOULD while keeping the gate a MUST. Status left identified for that call.

The proposal strains the plan verb's authoring-only nature by mandating time-boxed spikes "run during planning" — REQ-LIFECYCLE-001 establishes plan.html as one of five same-design-system authoring templates whose contract is a written artifact, and folding live code-execution/investigation into producing it crosses the same plan→implement seam the change claims to protect; it also brushes P-6 ("Draft is loose"), since the plan is authored in Draft yet REQ-LIFECYCLE-006 imposes a hard MUST-NOT hand-off gate on a loose-by-principle artifact.

REQ-LIFECYCLE-001 (five authoring templates, "Each MUST use the same design system") vs. the delta's "spike (resolved by a time-boxed investigation run during planning)"

The gate is a plan→/tasks readiness gate, not a Draft content-lock: P-6 lets a Draft artifact accept in-place edits freely, and this mirrors the existing estimability gate that already refuses to plan while open <spec-question>s remain — a precedent the meta-spec already sanctions. Spikes-during-planning is a deliberate, author-accepted tradeoff (staff practice: de-risk before building); the spike's output is still a written ledger row, so the artifact stays an authoring artifact. Proposed transition: mitigated.

Scope is too broad for one slice: bundling the grounding phase, the evidence-ledger artifact, a new grounding= attribute with an UNGROUNDED visible-failure renderer, AND a hand-off gate gives a single must-tier ADD four independently-riskable surfaces (procedure, template, CSS, gate) — the visible-failure/CSS-rendering surface in particular is exactly the class of interactive/structural artifact the CLAUDE.md verification-discipline note says needs its own browser-level test.

§Scope in-scope item: "A grounding= attribute on each <spec-decision>; an ungrounded one renders the UNGROUNDED visible-failure."

The four surfaces are one cohesive contract (the requirement is meaningless without its rendering + gate), so splitting risks an artifact-ordering trap. Conceded on testing: the UNGROUNDED rendering is CSS-driven visible-failure and gets a browser-level check (computed ::after content on an ungrounded vs. grounded decision) per the CLAUDE.md "presence is not containment" discipline — already named in the verification plan. Proposed transition: mitigated.
